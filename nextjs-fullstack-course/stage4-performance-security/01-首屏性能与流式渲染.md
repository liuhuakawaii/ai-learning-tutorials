# 第一课：首屏性能与流式渲染

## 场景引入

你的 SaaS 产品上线后，用户反馈"打开页面要等好几秒才看到内容"。用 Lighthouse 一跑，LCP 高达 4.2 秒，CLS 0.35，Performance 分数只有 45 分。根本原因是页面采用传统 SSR 模式——服务器必须等所有数据查询完成才能返回 HTML，而其中最慢的统计接口需要 2 秒。更糟糕的是，页面上的图片和广告没有预留尺寸，导致内容不断跳动。用户在等待过程中看不到任何反馈，直接关掉了页面。

## 学习目标

完成本课学习后，你将能够：

1. 理解 Core Web Vitals 指标
2. 掌握流式渲染的原理
3. 使用 Suspense 实现渐进式加载
4. 优化首屏加载时间
5. 避免常见的性能陷阱

## 一、Core Web Vitals

### 1.1 三个核心指标

```
LCP（Largest Contentful Paint）最大内容绘制
  → 衡量加载性能
  → 目标：< 2.5 秒

INP（Interaction to Next Paint）交互到下次绘制
  → 衡量整体交互响应
  → 目标：< 200 毫秒

CLS（Cumulative Layout Shift）累积布局偏移
  → 衡量视觉稳定性
  → 目标：< 0.1
```

### 1.2 生活类比

```
LCP = 餐厅上菜速度
  点单后多久能看到主菜

INP = 服务员处理整次请求的速度
  从你举手到服务员回应并完成第一步处理需要多久

CLS = 菜单会不会突然变化
  点菜时菜单会不会突然换位置
```

## 二、流式渲染

### 2.1 什么是流式渲染

```
传统渲染：
  服务器等待所有数据准备好
  → 生成完整 HTML
  → 一次性发送给浏览器
  → 用户等待时间长

流式渲染：
  服务器先发送页面框架
  → 数据准备好后逐块发送
  → 浏览器逐步显示内容
  → 用户更快看到内容
```

### 2.2 Next.js 中的流式渲染

```tsx
// app/dashboard/page.tsx
import { Suspense } from 'react'

// 慢组件
async function SlowStats() {
  const stats = await fetchStats() // 耗时 2 秒
  return <div>{/* 渲染统计 */}</div>
}

// 快组件
async function QuickHeader() {
  return <h1>Dashboard</h1>
}

export default function DashboardPage() {
  return (
    <div>
      <QuickHeader />
      <Suspense fallback={<StatsSkeleton />}>
        <SlowStats />
      </Suspense>
    </div>
  )
}
```

### 2.3 流式渲染的过程

```
时间线：

0ms    服务器开始渲染
       → 发送 <html><body><h1>Dashboard</h1>

100ms  → 发送 <div>骨架屏</div>

2000ms → 数据准备好
       → 发送真正的统计内容
       → 浏览器替换骨架屏
```

## 三、使用 Suspense

### 3.1 基础用法

```tsx
import { Suspense } from 'react'

export default function Page() {
  return (
    <div>
      <h1>页面标题</h1>

      <Suspense fallback={<div>加载中...</div>}>
        <AsyncComponent />
      </Suspense>
    </div>
  )
}

async function AsyncComponent() {
  const data = await fetchData()
  return <div>{data}</div>
}
```

### 3.2 多个 Suspense

```tsx
export default function DashboardPage() {
  return (
    <div className="grid grid-cols-2 gap-4">
      <Suspense fallback={<CardSkeleton />}>
        <StatsCard />
      </Suspense>

      <Suspense fallback={<CardSkeleton />}>
        <RecentActivity />
      </Suspense>

      <Suspense fallback={<TableSkeleton />}>
        <ProjectsTable />
      </Suspense>

      <Suspense fallback={<ListSkeleton />}>
        <TeamMembers />
      </Suspense>
    </div>
  )
}
```

### 3.3 loading.tsx 等价于 Suspense

```tsx
// app/dashboard/loading.tsx
export default function Loading() {
  return <div>加载中...</div>
}

// 等价于：
// app/dashboard/layout.tsx
export default function Layout({ children }) {
  return (
    <Suspense fallback={<Loading />}>
      {children}
    </Suspense>
  )
}
```

## 四、优化首屏

### 4.1 减少 JavaScript

```tsx
// ❌ 整个页面都是客户端组件
'use client'

export default function Page() {
  const [data, setData] = useState(null)

  useEffect(() => {
    fetch('/api/data').then(r => r.json()).then(setData)
  }, [])

  return <div>{/* ... */}</div>
}

// ✅ 服务端组件，零 JS
export default async function Page() {
  const data = await db.query('SELECT * FROM posts')
  return <div>{/* ... */}</div>
}
```

### 4.2 动态导入

```tsx
// 不需要首屏加载的组件
import dynamic from 'next/dynamic'

const HeavyChart = dynamic(() => import('./HeavyChart'), {
  loading: () => <ChartSkeleton />,
  ssr: false, // 不在服务端渲染
})

export default function Page() {
  return (
    <div>
      <h1>数据图表</h1>
      <HeavyChart />
    </div>
  )
}
```

### 4.3 避免客户端-服务端瀑布流

```tsx
// ❌ 瀑布流
export default function Page() {
  return (
    <Suspense fallback={<SkeletonA />}>
      <ComponentA />
    </Suspense>
  )
}

async function ComponentA() {
  const data = await fetchA()
  return (
    <Suspense fallback={<SkeletonB />}>
      <ComponentB parentId={data.id} />
    </Suspense>
  )
}

// ✅ 并行加载
export default function Page() {
  return (
    <>
      <Suspense fallback={<SkeletonA />}>
        <ComponentA />
      </Suspense>
      <Suspense fallback={<SkeletonB />}>
        <ComponentB />
      </Suspense>
    </>
  )
}
```

## 五、骨架屏最佳实践

### 5.1 匹配真实布局

```tsx
// ❌ 不好的骨架屏
function BadSkeleton() {
  return <div className="animate-pulse">加载中...</div>
}

// ✅ 好的骨架屏
function GoodSkeleton() {
  return (
    <div className="animate-pulse">
      {/* 模拟标题 */}
      <div className="h-8 bg-gray-200 rounded w-1/3 mb-4"></div>

      {/* 模拟卡片 */}
      <div className="grid grid-cols-3 gap-4 mb-6">
        {[1, 2, 3].map(i => (
          <div key={i} className="h-24 bg-gray-200 rounded"></div>
        ))}
      </div>

      {/* 模拟列表 */}
      <div className="space-y-3">
        {[1, 2, 3, 4].map(i => (
          <div key={i} className="h-12 bg-gray-200 rounded"></div>
        ))}
      </div>
    </div>
  )
}
```

### 5.2 使用真实颜色

```tsx
function Skeleton({ className }: { className?: string }) {
  return (
    <div
      className={`bg-gray-200 rounded animate-pulse ${className}`}
    />
  )
}
```

## 八、常见误区

1. **把所有组件都标记为 `'use client'`**：客户端组件会将整个组件树拉入客户端 bundle，增加 JS 体积和 hydration 时间。能用 Server Component 的地方就不要用客户端组件。

2. **骨架屏只显示"加载中..."文字**：骨架屏的价值在于模拟真实内容的布局结构，让用户预判页面形态。一个居中的"加载中..."文字不仅没有减少感知等待时间，反而让页面在数据到达时发生剧烈布局跳动。

3. **Suspense 嵌套导致瀑布流**：把 Suspense 嵌套在需要父组件数据的子组件内部，会导致父组件加载完才开始加载子组件，形成串行瀑布流。应该把独立数据源的 Suspense 平铺在同一层级。

4. **盲目禁用 SSR**：遇到报错就加 `ssr: false` 是常见的偷懒做法，但会丧失 SEO 和首屏性能优势。只有确实依赖浏览器 API 的组件才应该禁用 SSR。

---

## 九、工程建议

1. **用 `loading.tsx` 替代手动 Suspense**：对于路由级的加载状态，直接使用 Next.js 的 `loading.tsx` 约定，比手动在 page 组件中包裹 Suspense 更清晰，也更容易维护。

2. **首屏关键路径控制在 3 个并行请求以内**：通过并行加载 Suspense 边界内的组件，确保首屏渲染不依赖超过 3 个串行网络请求。超出部分考虑预加载或缓存。

3. **在 CI 中集成 Lighthouse 审计**：使用 `lighthouse-ci` 在每次 PR 时自动运行性能审计，设置 Performance 分数阈值（如 80 分），低于阈值则阻止合并。

4. **使用 Web Vitals 持续监控**：部署后通过 `useReportWebVitals` 将 LCP、INP、CLS 数据上报到分析服务，设置告警阈值，第一时间发现性能退化。
