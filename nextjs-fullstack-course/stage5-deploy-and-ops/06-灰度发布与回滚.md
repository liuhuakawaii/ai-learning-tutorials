# 第六课：灰度发布与回滚

## 场景引入

你的团队在周五下午上线了一个"重构后的支付流程"，所有用户同时收到了新版本。半小时后，客服收到大量投诉："付了钱但没到账"。你紧急排查发现是支付回调接口的一个边界条件没有处理好。但此时已经有上百笔订单受到影响。如果当时采用灰度发布——先让 1% 的用户体验新版本，观察 30 分钟无异常再逐步扩大——损失可以控制在个位数。

## 学习目标

完成本课学习后，你将能够：

1. 理解灰度发布的概念
2. 实现功能开关
3. 执行灰度发布策略
4. 快速回滚部署

## 一、灰度发布

### 1.1 什么是灰度发布

> **灰度发布是指将新版本逐步推送给部分用户，观察稳定后再全量发布。**

```
全量发布：
  → 所有用户同时获得新版本
  → 风险高，出问题影响全部用户

灰度发布：
  → 1% 用户先试用
  → 观察稳定性
  → 逐步扩大到 10%、50%、100%
  → 风险可控
```

### 1.2 生活类比

```
全量发布 = 餐厅换菜单
  → 一次性换掉所有菜品
  → 如果客人不喜欢，全部投诉

灰度发布 = 餐厅试新菜
  → 先推出 1-2 道新菜
  → 收集客人反馈
  → 反应好再推广
  → 反应差就撤掉
```

### 1.3 灰度策略

```
按用户百分比：
  → 1% → 10% → 50% → 100%

按用户 ID：
  → 内部员工 → Beta 用户 → 所有用户

按地区：
  → 单个地区 → 多个地区 → 全球

按功能：
  → 单个功能 → 多个功能 → 全部功能
```

## 二、功能开关

### 2.1 什么是功能开关

> **功能开关是一种技术，让你可以在不部署代码的情况下开启或关闭功能。**

### 2.2 简单实现

```tsx
// lib/feature-flags.ts
const featureFlags: Record<string, boolean> = {
  NEW_DASHBOARD: process.env.FEATURE_NEW_DASHBOARD === 'true',
  AI_FEATURES: process.env.FEATURE_AI === 'true',
  BETA_FEATURES: process.env.FEATURE_BETA === 'true',
}

export function isFeatureEnabled(feature: string): boolean {
  return featureFlags[feature] ?? false
}
```

### 2.3 在代码中使用

```tsx
import { isFeatureEnabled } from '@/lib/feature-flags'

export default function Dashboard() {
  if (isFeatureEnabled('NEW_DASHBOARD')) {
    return <NewDashboard />
  }

  return <OldDashboard />
}
```

### 2.4 使用第三方服务

```tsx
// 使用 LaunchDarkly、Flagsmith 或 Vercel Feature Flags
import { flags } from '@/lib/flags'

export default async function Page() {
  const showNewFeature = await flags.isEnabled('new-feature')

  return (
    <div>
      {showNewFeature && <NewFeature />}
    </div>
  )
}
```

## 四、蓝绿部署

### 4.1 什么是蓝绿部署

```
蓝绿部署：
  → 维护两个完全相同的环境
  → 蓝色 = 当前生产
  → 绿色 = 新版本
  → 切换流量从蓝到绿
  → 如果出问题，切回蓝色
```

### 4.2 Docker 实现

```yaml
# docker-compose.blue-green.yml
version: '3'

services:
  app-blue:
    build: .
    environment:
      - APP_VERSION=blue
    ports:
      - "3001:3000"

  app-green:
    build: .
    environment:
      - APP_VERSION=green
    ports:
      - "3002:3000"

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf
```

```nginx
# nginx.conf - 切换到绿色环境
upstream app {
    server app-green:3000;  # 改为 app-blue 切换回去
}
```

## 五、数据库迁移策略

### 5.1 向后兼容的迁移

```
安全的做法：
  1. 添加新字段（向后兼容）
  2. 部署新代码
  3. 迁移数据
  4. 删除旧字段（确认无问题后）

危险的做法：
  ❌ 直接删除字段
  ❌ 直接重命名字段
  ❌ 直接修改字段类型
```

### 5.2 示例

```sql
-- ✅ 安全：添加新字段
ALTER TABLE "User" ADD COLUMN "firstName" TEXT;

-- 部署新代码，同时使用旧字段和新字段

-- 迁移数据
UPDATE "User" SET "firstName" = SPLIT_PART("name", ' ', 1);

-- 确认无问题后，删除旧字段
ALTER TABLE "User" DROP COLUMN "name";
```

## 六、回滚策略

### 6.1 代码回滚

```bash
# Git 回滚
git revert HEAD
git push

# 或
git reset --hard HEAD~1
git push --force
```

### 6.2 数据库回滚

```bash
# Prisma 回滚
npx prisma migrate resolve --rolled-back "migration_name"

# 或恢复备份
psql -U username -d dbname < backup.sql
```

### 6.3 部署回滚

```bash
# Vercel 回滚
vercel rollback

# Docker 回滚
docker-compose down
docker-compose up -d --build <previous-version>
```

## 七、监控和告警

### 7.1 关键指标

```
错误率：
  → 正常：< 1%
  → 警告：1-5%
  → 严重：> 5%

响应时间：
  → 正常：< 500ms
  → 警告：500ms-2s
  → 严重：> 2s

可用性：
  → 目标：99.9%
  → 每月宕机时间：< 43 分钟
```

### 7.2 自动回滚

```yaml
# GitHub Actions 自动回滚
deploy:
  steps:
    - name: Deploy
      run: vercel deploy --prod

    - name: Health Check
      run: |
        for i in $(seq 1 5); do
          if curl -f https://yourapp.com/api/health; then
            echo "Health check passed"
            exit 0
          fi
          sleep 10
        done
        echo "Health check failed, rolling back"
        vercel rollback
        exit 1
```

```

```

```
  □ 无明显错误

  □ 响应时间正常
```

## 十、常见误区

1. **灰度发布就是 A/B 测试**：灰度发布的目的是验证新版本的稳定性（错误率、性能），按百分比逐步放量。A/B 测试的目的是比较两种方案的业务指标（转化率、留存率）。两者目的不同，实现方式也不同。

2. **功能开关可以无限期保留**：功能开关应该有明确的生命周期。功能全量发布后应该清理开关代码，否则代码中会积累大量死分支，增加维护成本。

3. **回滚就是重新部署旧代码**：如果新版本已经执行了数据库迁移（如删除了字段），回滚代码无法恢复数据。数据库迁移必须是向后兼容的，否则回滚流程需要包含数据恢复步骤。

4. **只在大版本发布时才灰度**：任何涉及核心流程的改动（登录、支付、数据写入）都应该灰度发布，不论改动大小。一个小小的正则修改就可能导致所有用户无法注册。

---

## 十一、工程建议

1. **功能开关按用户 ID 哈希分流**：按百分比随机分流会导致同一用户在不同请求中看到不同版本，产生混乱。按用户 ID 哈希可以确保同一用户始终看到同一版本。

2. **灰度发布配合健康检查自动回滚**：在 CI/CD 中部署后自动运行健康检查（错误率、响应时间），如果超过阈值自动触发回滚，减少人工干预时间。

3. **数据库迁移分两步执行**：第一步只做新增操作（加字段、加索引），部署新代码后再做第二步（删除旧字段）。两步之间保留足够的观察窗口。

4. **保留最近 3 个版本的部署产物**：Vercel 默认保留所有历史部署，Docker 镜像至少保留最近 3 个 Tag，确保可以快速回滚到任意一个版本。

```
本课核心要点：

1. 灰度发布逐步推出新版本，降低风险

4. 保留回滚能力，随时可以恢复
```
