# 第一课：数据库基础概念

## 场景引入

你的博客 API 用内存数组存储数据，服务器重启后所有文章和用户数据都消失了。你尝试用 JSON 文件持久化，但发现并发写入时文件会损坏，查询一篇特定文章要遍历整个数组，10 万条数据的搜索变得越来越慢。这时候你需要一个专业的数据存储方案——数据库。它能持久化存储数据、支持高效查询、处理并发访问、保证数据一致性。理解数据库的核心概念（表、行、列、主键、外键），是后端开发的必修课。

## 学习目标

完成本课后，你将能够：

1. 理解什么是数据库以及为什么需要它
2. 区分关系型数据库（RDBMS）和非关系型数据库（NoSQL）
3. 掌握数据库的核心概念：表、行、列、主键、外键
4. 了解 SQL vs NoSQL 的适用场景
5. 理解前端开发者为什么要学习数据库

## 一、什么是数据库

### 1.1 从 Excel 说起

作为前端开发者，你一定用过 Excel 或 Google Sheets。想象一下这个场景：

你在管理一个博客平台的数据，用 Excel 来记录文章信息：

```
┌──────────────────────────────────────────────────────────────────┐
│  文章标题          │  作者     │  状态    │  发布日期   │  浏览量  │
├──────────────────────────────────────────────────────────────────┤
│  TypeScript入门    │  张三    │  已发布  │  2024-01-15 │  1200   │
│  React最佳实践     │  李四    │  已发布  │  2024-02-20 │  3500   │
│  Node.js教程       │  张三    │  草稿   │  -         │  0      │
│  CSS动画技巧       │  王五    │  已发布  │  2024-03-10 │  800    │
└──────────────────────────────────────────────────────────────────┘
```

Excel 能用，但它有明显的局限：

```
Excel 的问题：
┌─────────────────────────────────────────────┐
│ ❌ 只能一个人编辑（多人协作很麻烦）         │
│ ❌ 数据量大了会卡（超过 10 万行就开始慢）   │
│ ❌ 无法设置复杂的关系（文章和评论怎么关联？）│
│ ❌ 没有权限控制（谁能看？谁能改？）         │
│ ❌ 无法高效搜索（找一篇文章要翻半天）       │
│ ❌ 不适合程序读写（你的 API 怎么读 Excel？）│
└─────────────────────────────────────────────┘
```

**数据库（Database）** 就是为了解决这些问题而生的。你可以把它理解为：

> **数据库 = 一个超级增强版的 Excel，专门为程序设计，能存储海量数据，支持多人同时访问，还能高效搜索。**

### 1.2 数据库的核心能力

```
数据库 vs Excel 对比：

┌─────────────┬──────────────────┬──────────────────┐
│   能力       │     Excel        │     数据库        │
├─────────────┼──────────────────┼──────────────────┤
│ 存储容量     │ 几十万行就卡     │ 轻松存几亿条      │
│ 并发访问     │ 基本不支持       │ 支持成千上万连接  │
│ 查询速度     │ 全表扫描，慢     │ 索引加速，毫秒级  │
│ 数据关系     │ 手动维护         │ 外键自动关联      │
│ 数据完整性   │ 基本没有         │ 约束保证准确性    │
│ 权限控制     │ 文件级密码       │ 细粒度权限管理    │
│ 编程接口     │ 需要特殊库       │ 标准 SQL/驱动程序 │
│ 事务支持     │ 不支持           │ ACID 保证一致性   │
└─────────────┴──────────────────┴──────────────────┘
```

### 1.3 生活中的数据库类比：图书馆

把数据库想象成一个图书馆：

```
图书馆的组织方式：
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  🏛️ 图书馆（Database）                                  │
│  ├── 📚 小说区（Table: novels）                         │
│  │   ├── 《三体》         - 编号: 001 - 作者: 刘慈欣    │
│  │   ├── 《活着》         - 编号: 002 - 作者: 余华      │
│  │   └── 《围城》         - 编号: 003 - 作者: 钱钟书    │
│  │                                                      │
│  📚 技术区（Table: tech_books）                          │
│  │   ├── 《JavaScript高级编程》 - 编号: 101              │
│  │   ├── 《CSS揭秘》           - 编号: 102              │
│  │   └── 《Node.js实战》       - 编号: 103              │
│  │                                                      │
│  👤 读者卡（Table: readers）                             │
│  │   ├── 张三 - 卡号: R001 - 会员等级: 金卡             │
│  │   └── 李四 - 卡号: R002 - 会员等级: 银卡             │
│  │                                                      │
│  📋 借阅记录（Table: borrow_records）                    │
│      ├── 记录1: 张三 借了 《三体》 2024-01-10           │
```

- **图书馆** = 数据库（Database）：整个数据的容器
- **不同分区** = 表（Table）：按类别组织数据

- **书的属性** = 列/字段（Column/Field）：数据的各个属性
- **书的编号** = 主键（Primary Key）：唯一标识一条记录

## 二、关系型数据库（RDBMS）详解

### 2.1 什么是关系型数据库

**关系型数据库（Relational Database Management System, RDBMS）** 是目前最常用的数据库类型。它的核心思想是：

> **数据存储在"表"中，表与表之间通过"关系"连接。**

这就像 Excel 里有多个 Sheet，Sheet 之间通过共同的列（比如用户 ID）来关联。

### 2.2 核心概念

#### 表（Table）

表是数据的容器，类似于 Excel 的一个 Sheet。

```
表名: users（用户表）

┌────┬──────────┬────────────────┬─────────┐
│ id │ username │ email          │ age     │
├────┼──────────┼────────────────┼─────────┤
│ 1  │ zhangsan │ zhang@test.com │ 25      │
│ 2  │ lisi     │ lisi@test.com  │ 30      │
│ 3  │ wangwu   │ wang@test.com  │ 28      │
└────┴──────────┴────────────────┴─────────┘

列（Column）: id, username, email, age
行（Row）: 每一行是一条具体的记录
```

#### 行（Row）和列（Column）

```
列（Column）= 字段，定义数据的结构
┌─────────────────────────────────────────┐
│  id  │  username  │  email  │  age      │  ← 列头（Schema）
├──────┼────────────┼─────────┼───────────┤
│  1   │  zhangsan  │  ...    │  25       │  ← 第 1 行（Record）
│  2   │  lisi      │  ...    │  30       │  ← 第 2 行（Record）
└──────┴────────────┴─────────┴───────────┘
```

用 TypeScript 来类比：

```typescript
// 列的定义 = TypeScript 的 interface
interface User {
  id: number;        // 整数列
  username: string;  // 字符串列
  email: string;     // 字符串列
  age: number;       // 整数列
}

// 一行数据 = 一个对象实例
const user: User = {
  id: 1,
  username: 'zhangsan',
  email: 'zhang@test.com',
  age: 25
};
```

#### 主键（Primary Key）

**主键** 是表中唯一标识每一行的字段，就像人的身份证号。

```
主键的特点：
┌─────────────────────────────────────────┐
│ ✅ 唯一性：每行的主键值都不同           │
│ ✅ 非空：主键不能为空（NOT NULL）        │
│ ✅ 不变：一般不会修改                   │
│ ✅ 单一：一张表只有一个主键             │
└─────────────────────────────────────────┘

┌────┬──────────┬────────────────┐
│ id │ username │ email          │
├────┼──────────┼────────────────┤
│ 1  │ zhangsan │ zhang@test.com │  ← id=1 是这条记录的唯一标识
│ 2  │ lisi     │ lisi@test.com  │  ← id=2 是这条记录的唯一标识
│ 3  │ wangwu   │ wang@test.com  │  ← id=3 是这条记录的唯一标识
└────┴──────────┴────────────────┘
  ↑
  主键（Primary Key）
```

#### 外键（Foreign Key）

**外键** 是一个表中引用另一个表主键的字段，用于建立表与表之间的关系。

```
用户表 (users)                          文章表 (posts)
┌────┬──────────┐                      ┌────┬──────────────┬─────────┐
│ id │ username │                      │ id │ title        │ user_id │
├────┼──────────┤                      ├────┼──────────────┼─────────┤
│ 1  │ zhangsan │ ←────────────────────│ 1  │ TS入门       │ 1       │
│ 2  │ lisi     │                      │ 2  │ React实践    │ 2       │
│ 3  │ wangwu   │                      │ 3  │ Node教程     │ 1       │
└────┴──────────┘                      └────┴──────────────┴─────────┘
     ↑ 主键                                   ↑ 外键（引用 users.id）

通过外键，我们知道：
- 文章1 "TS入门" 是 zhangsan 写的（user_id=1）
- 文章2 "React实践" 是 lisi 写的（user_id=2）
- 文章3 "Node教程" 是 zhangsan 写的（user_id=1）
```

用 TypeScript 来理解：

```typescript
// 没有外键时，数据是"扁平"的
interface Post {
  id: number;
  title: string;
  authorName: string;  // 直接存名字，如果作者改名了怎么办？
}

// 有了外键，数据是"关联"的
interface Post {
  id: number;
  title: string;
  authorId: number;    // 存的是 ID，指向 users 表
}

// 查询时再关联
const postWithAuthor = {
  id: 1,
  title: 'TS入门',
  authorId: 1,
  author: {            // 通过外键关联到用户表
    id: 1,
    username: 'zhangsan'
  }
};
```

### 2.3 表之间的关系类型

```
1. 一对一（One-to-One）
   一个用户对应一个个人资料

   users                    profiles
   ┌────┬──────────┐       ┌────┬─────────┬────────┐
   │ id │ username │       │ id │ avatar  │ bio    │
   ├────┼──────────┤       ├────┼─────────┼────────┤
   │ 1  │ zhangsan │──────→│ 1  │ pic.jpg │ 大家好 │
   └────┴──────────┘       └────┴─────────┴────────┘

2. 一对多（One-to-Many）
   一个用户有多篇文章

   users                    posts
   ┌────┬──────────┐       ┌────┬──────────────┬─────────┐
   │ id │ username │       │ id │ title        │ user_id │
   ├────┼──────────┤       ├────┼──────────────┼─────────┤
   │ 1  │ zhangsan │──┬───→│ 1  │ TS入门       │ 1       │
   └────┴──────────┘  │    │ 2  │ Node教程     │ 1       │
                      │    │ 3  │ React实践    │ 2       │
                      │    └────┴──────────────┴─────────┘
                      │
                      └── 一个用户可以写多篇文章

3. 多对多（Many-to-Many）
   一篇文章有多个标签，一个标签属于多篇文章

   posts              post_tags（中间表）          tags
   ┌────┐             ┌─────────┬────────┐       ┌────┐
   │ id │             │ post_id │ tag_id │       │ id │
   ├────┤             ├─────────┼────────┤       ├────┤
   │ 1  │────────────→│ 1       │ 1      │←──────│ 1  │
   │ 2  │────────┬───→│ 1       │ 2      │       │ 2  │
   └────┘        │    │ 2       │ 1      │       │ 3  │
                 │    │ 2       │ 3      │       └────┘
                 │    └─────────┴────────┘
                 │
                 └── 多对多需要一张中间表来连接
```

## 三、非关系型数据库（NoSQL）简介

### 3.1 什么是 NoSQL

**NoSQL（Not Only SQL）** 泛指非关系型数据库。它们不使用传统的表结构，而是采用更灵活的数据模型。

### 3.2 NoSQL 的主要类型

#### 文档型数据库（Document Database）

代表：**MongoDB**

数据以 JSON/BSON 文档的形式存储：

```typescript
// MongoDB 中的一条文档（类似于一个 JS 对象）
{
  _id: "507f1f77bcf86cd799439011",
  username: "zhangsan",
  email: "zhang@test.com",
  posts: [                    // 直接嵌套，不需要 JOIN
    {
      title: "TS入门",
      content: "TypeScript 是...",
      tags: ["TypeScript", "前端"]
    },
    {
      title: "Node教程",
      content: "Node.js 是...",
      tags: ["Node.js", "后端"]
    }
  ]
}
```

#### 键值型数据库（Key-Value Store）

代表：**Redis**

```
最简单的数据模型，就像一个巨大的 Map/Object：

┌──────────────────────┬────────────────────────┐
│  Key（键）            │  Value（值）            │
├──────────────────────┼────────────────────────┤
│  "user:1"            │  {name: "张三", age: 25}│
│  "session:abc123"    │  {userId: 1, exp: ...}  │
│  "cache:posts:list"  │  [{...}, {...}]         │
└──────────────────────┴────────────────────────┘

常用场景：缓存、会话存储、排行榜
```

#### 图数据库（Graph Database）

代表：**Neo4j**

```
适合处理复杂的关系网络：

    张三 ──关注──→ 李四
     │              │
     │写            │写
     ↓              ↓
   TS入门        React实践
     │
     └──点赞──→ 王五

社交网络、推荐系统、知识图谱等场景
```

### 3.3 SQL vs NoSQL 对比

```
┌──────────────┬──────────────────────┬──────────────────────┐
│   特性        │   SQL（关系型）       │   NoSQL（非关系型）   │
├──────────────┼──────────────────────┼──────────────────────┤
│ 数据结构     │ 固定的表结构（Schema）│ 灵活的文档/键值      │
│ 扩展方式     │ 垂直扩展（更强的机器）│ 水平扩展（更多机器）  │
│ 事务支持     │ 强事务（ACID）        │ 通常最终一致性        │
│ 查询语言     │ 标准 SQL              │ 各有各的 API         │
│ 关联查询     │ JOIN 很强大           │ 通常需要嵌套或应用层  │
│ 适用场景     │ 结构化数据、复杂查询  │ 灵活数据、高并发读写  │
│ 学习曲线     │ 需要学习 SQL          │ 对 JS 开发者更直观    │
└──────────────┴──────────────────────┴──────────────────────┘
```

### 3.4 什么时候用哪个

```
选 SQL（PostgreSQL/MySQL）的场景：
┌─────────────────────────────────────────────┐
│ ✅ 数据结构相对固定（用户、订单、文章）      │
│ ✅ 需要复杂的关联查询（JOIN）               │
│ ✅ 需要强事务保证（银行转账、电商下单）      │
│ ✅ 数据一致性要求高                         │
│ ✅ 博客系统、电商系统、CMS                   │
└─────────────────────────────────────────────┘

选 NoSQL（MongoDB）的场景：
┌─────────────────────────────────────────────┐
│ ✅ 数据结构经常变化                         │
│ ✅ 主要是简单的读写操作                     │
│ ✅ 需要处理海量数据和高并发                 │
│ ✅ 日志系统、实时分析、内容管理             │
└─────────────────────────────────────────────┘

选 Redis 的场景：
┌─────────────────────────────────────────────┐
│ ✅ 缓存（加速热门数据的读取）               │
│ ✅ 会话存储（用户登录状态）                 │
│ ✅ 排行榜、计数器                           │
│ ✅ 消息队列                                 │
└─────────────────────────────────────────────┘
```

> **本课程选择 PostgreSQL + Prisma**，因为博客平台的数据结构比较固定，需要复杂的关联查询，PostgreSQL 是最强大的开源关系型数据库。

## 四、数据库、表、记录的关系

### 4.1 层级关系图

```
数据库（Database）
│
├── 表（Table）: users
│   ├── 记录（Record）: { id: 1, name: "张三" }
│   ├── 记录（Record）: { id: 2, name: "李四" }
│   └── 记录（Record）: { id: 3, name: "王五" }
│
├── 表（Table）: posts
│   ├── 记录（Record）: { id: 1, title: "TS入门", author_id: 1 }
│   └── 记录（Record）: { id: 2, title: "React", author_id: 2 }
│
└── 表（Table）: comments
    ├── 记录（Record）: { id: 1, content: "好文！", post_id: 1, user_id: 2 }
    └── 记录（Record）: { id: 2, content: "收藏了", post_id: 1, user_id: 3 }
```

### 4.2 用图书馆类比总结

```
┌──────────────┬──────────────┬────────────────────────────┐
│   数据库概念  │   图书馆类比  │   说明                      │
├──────────────┼──────────────┼────────────────────────────┤
│ 数据库       │ 图书馆       │ 整个数据的容器              │
│ 表           │ 分区/书架    │ 按类别组织数据              │
│ 行/记录      │ 一本书       │ 一条具体的数据              │
│ 列/字段      │ 书的属性     │ 数据的各个属性              │
│ 主键         │ 图书编号     │ 唯一标识一条记录            │
│ 外键         │ 借书卡号     │ 建立记录之间的关联          │
│ 索引         │ 图书索引     │ 加速查找的目录              │
│ 查询         │ 检索图书     │ 从数据库中获取数据          │
│ 事务         │ 一摞借书手续 │ 要么全成功，要么全失败      │
└──────────────┴──────────────┴────────────────────────────┘
```

## 五、前端开发者为什么要懂数据库

### 5.1 全栈开发的必备技能

```
前端开发者的职业发展路径：

初级前端 ──→ 中级前端 ──→ 高级前端 ──→ 全栈工程师
                                        ↑
                                        需要懂数据库！

全栈工程师的技能树：
┌─────────────────────────────────────────┐
│  前端                                   │
│  ├── HTML/CSS/JavaScript               │
│  ├── React/Vue/Angular                  │
│  └── 状态管理、路由、构建工具           │
│                                         │
│  后端                                   │
│  ├── Node.js/Express/Koa               │
│  ├── API 设计（REST/GraphQL）           │
│  └── 数据库（SQL、ORM、数据建模）← 这里 │
└─────────────────────────────────────────┘
```

### 5.2 理解 ORM（对象关系映射）

作为前端开发者，你将来很可能会用到 ORM（比如 Prisma、TypeORM）。ORM 让你用 TypeScript/JavaScript 代码来操作数据库，而不用写 SQL。

```typescript
// 如果你不懂数据库概念，这段代码你可能看不懂
const posts = await prisma.post.findMany({
  where: {
    status: 'PUBLISHED',
    author: {
      username: 'zhangsan'
    }
  },
  include: {
    author: true,        // 为什么要 include？
    tags: true,          // 这是什么意思？
    _count: {
      select: { comments: true }  // 这又是什么？
    }
  },
  orderBy: {
    createdAt: 'desc'    // 为什么要排序？
  },
  skip: 0,              // 分页是什么？
  take: 10
});

// 如果你懂数据库，你就知道这等价于：
// SELECT posts.*, users.*, tags.*, COUNT(comments.id)
// FROM posts
// JOIN users ON posts.author_id = users.id
// LEFT JOIN post_tags ON posts.id = post_tags.post_id
// LEFT JOIN tags ON post_tags.tag_id = tags.id
// LEFT JOIN comments ON posts.id = comments.post_id
// WHERE posts.status = 'PUBLISHED'
//   AND users.username = 'zhangsan'
// GROUP BY posts.id
// ORDER BY posts.created_at DESC
// LIMIT 10 OFFSET 0
```

### 5.3 优化查询性能

```typescript
// ❌ 不懂数据库的前端可能会这样写
// 获取文章列表，然后在前端过滤
const allPosts = await fetch('/api/posts');  // 拉取所有文章！
const publishedPosts = allPosts.filter(p => p.status === 'PUBLISHED');
const sortedPosts = publishedPosts.sort((a, b) => b.createdAt - a.createdAt);
const page1 = sortedPosts.slice(0, 10);     // 只要前 10 条

// ✅ 懂数据库的开发者会在后端处理
// 让数据库做它擅长的事
const posts = await prisma.post.findMany({
  where: { status: 'PUBLISHED' },
  orderBy: { createdAt: 'desc' },
  take: 10  // 只查 10 条，而不是查所有再过滤
});
```

## 六、数据库的基本操作（CRUD）

在开始学习具体语法之前，先了解数据库最核心的四种操作——**CRUD**：

```
CRUD = 四种基本操作

┌──────┬──────────┬────────────────────┬─────────────────┐
│ 操作  │ 英文      │ 含义               │ SQL 关键字       │
├──────┼──────────┼────────────────────┼─────────────────┤
│ C    │ Create   │ 创建/插入数据       │ INSERT INTO     │
│ R    │ Read     │ 读取/查询数据       │ SELECT          │
│ U    │ Update   │ 更新/修改数据       │ UPDATE          │
│ D    │ Delete   │ 删除数据            │ DELETE FROM     │
└──────┴──────────┴────────────────────┴─────────────────┘
```

对应到前端的 HTTP 方法：

```
┌──────────┬──────────┬─────────────────┐
│ CRUD     │ HTTP 方法 │ 用途             │
├──────────┼──────────┼─────────────────┤
│ Create   │ POST     │ 创建新资源       │
│ Read     │ GET      │ 获取资源         │
│ Update   │ PUT/PATCH│ 更新资源         │
│ Delete   │ DELETE   │ 删除资源         │
└──────────┴──────────┴─────────────────┘

POST   /api/posts    → INSERT INTO posts ...
GET    /api/posts    → SELECT * FROM posts
PUT    /api/posts/1  → UPDATE posts SET ... WHERE id = 1
DELETE /api/posts/1  → DELETE FROM posts WHERE id = 1
```

## 常见误区

1. **认为数据库只是"更好的 Excel"**：数据库支持事务（ACID）、并发控制、索引优化、外键约束等 Excel 完全不具备的能力。这些特性保证了数据的完整性和查询性能。
2. **一上来就选 NoSQL 因为"更灵活"**：MongoDB 的灵活性意味着没有 schema 约束，数据质量完全依赖应用层保证。对于结构化数据（用户、订单、文章），关系型数据库的强类型约束反而更安全。
3. **混淆主键和外键**：主键唯一标识本表的一条记录，外键引用其他表的主键来建立关联。一个表只有一个主键，但可以有多个外键。
4. **认为学习数据库只是 DBA 的事**：全栈开发者需要理解表设计、索引原理、查询优化，否则写出的 API 可能有严重的性能问题（如 N+1 查询）。

## 工程建议

1. **先画 ER 图再建表**：在写代码之前，先识别业务实体和它们之间的关系，画出实体关系图。这能帮你发现设计缺陷，避免后期频繁修改表结构。
2. **为每个表选择合适的主键**：自增整数（SERIAL）简单高效，适合内部使用；UUID 适合分布式系统或需要对外暴露的标识符。不要用业务字段（如邮箱）做主键。
3. **理解 CRUD 与 HTTP 方法的对应关系**：Create-POST、Read-GET、Update-PUT/PATCH、Delete-DELETE。这个映射是 RESTful API 设计的基础。
4. **先掌握关系型数据库再学 NoSQL**：关系型数据库的约束、范式、事务等概念是数据管理的基础，掌握了这些再学 MongoDB 或 Redis 会更得心应手。
