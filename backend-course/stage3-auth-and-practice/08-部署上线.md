# 第 8 课：部署上线

## 场景引入

你的博客 API 在本地跑得好好的，推给同事克隆下来却启动不了——"你的 Node 版本是多少？""数据库怎么连？""环境变量在哪配？"你花了一下午帮他配环境。终于上线了，你手动 SSH 到服务器拉代码、编译、重启服务。第二天改了个 bug，又重复一遍。第三天你忘了先跑数据库迁移，线上直接崩了。这些问题的根源是：没有标准化的部署流程。Docker 能解决环境一致性问题，CI/CD 能解决重复部署问题。本课将教你用 Docker 容器化应用、用 docker-compose 编排多服务、用 GitHub Actions 实现一键自动部署。

## 学习目标

完成本课学习后，你将能够：

1. 理解生产环境与开发环境的区别，正确配置环境变量
2. 使用 Docker 容器化 Node.js 应用
3. 编写 Dockerfile 和 docker-compose.yml
4. 将应用部署到 Railway 云平台
5. 配置数据库迁移、域名和 HTTPS
6. 使用 GitHub Actions 实现 CI/CD 自动部署

## 一、部署前准备

### 1.1 环境变量配置

在开发环境中，我们可能直接把数据库密码写在代码里。但在生产环境，这样做极其危险。**环境变量（Environment Variables）** 是在操作系统级别存储配置信息的标准方式。

**生活类比**：想象你住酒店。房卡（环境变量）让你能进入房间（访问数据库），但你不会把房卡信息刻在额头上（写在代码里）。每次住不同的酒店（环境），你用不同的房卡。

```
┌─────────────────────────────────────────────────────────┐
│                    环境变量的作用                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│   开发环境 (development)          生产环境 (production)   │
│   ┌──────────────────┐           ┌──────────────────┐   │
│   │ DB_HOST=localhost│           │ DB_HOST=prod.db  │   │
│   │ DB_PORT=5432     │           │ DB_PORT=5432     │   │
│   │ DB_PASS=123456   │           │ DB_PASS=xK9!mZ   │   │
│   │ JWT_SECRET=dev   │           │ JWT_SECRET=a8f.. │   │
│   │ LOG_LEVEL=debug  │           │ LOG_LEVEL=warn   │   │
│   └──────────────────┘           └──────────────────┘   │
│         ↑                               ↑               │
│    简单密码，方便调试              强密码，安全配置         │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

创建 `.env.production` 文件：

```bash
# .env.production - 生产环境配置
# 数据库连接
DATABASE_URL="postgresql://user:strong_password@prod-host:5432/blog_db?schema=public"

# JWT 配置
JWT_SECRET="your-super-secret-key-at-least-32-chars-long"
JWT_EXPIRES_IN="7d"

# 服务器配置
PORT=3000
NODE_ENV="production"

# 日志配置
LOG_LEVEL="warn"

# 文件上传
UPLOAD_DIR="uploads"
MAX_FILE_SIZE=5242880

# CORS 配置
CORS_ORIGIN="https://yourdomain.com"

# Redis（用于缓存和限流）
REDIS_URL="redis://:password@redis-host:6379"
```

## 二、Docker 容器化

### 2.1 Docker 是什么

**Docker** 是一个容器化平台，它把应用程序及其所有依赖打包成一个标准化的单元，称为**容器（Container）**。

**生活类比 - 集装箱**：

```
┌─────────────────────────────────────────────────────────────────┐
│                      Docker 集装箱类比                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   没有 Docker（传统部署）：                                       │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐                        │
│   │ 机器 A  │  │ 机器 B  │  │ 机器 C  │   每台机器环境不同       │
│   │ Node 14 │  │ Node 18 │  │ Node 16 │   "在我电脑上能跑啊"     │
│   │ PG 12   │  │ PG 15   │  │ PG 13   │                         │
│   └─────────┘  └─────────┘  └─────────┘                        │
│                                                                 │
│   使用 Docker（容器化部署）：                                     │
│   ┌─────────────────────────────────────────┐                   │
│   │              标准集装箱                    │                   │
│   │  ┌─────────────────────────────────┐    │                   │
│   │  │  应用代码 + Node 18 + PG 15    │    │  所有环境一致       │
│   │  │  + 所有依赖 + 配置文件          │    │  "到处都能跑"       │
│   │  └─────────────────────────────────┘    │                   │
│   └─────────────────────────────────────────┘                   │
│         ↑                ↑                ↑                      │
│      机器 A           机器 B           机器 C                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**Docker 核心概念**：

| 概念 | 说明 | 类比 |
|------|------|------|
| **镜像 (Image)** | 只读的应用模板 | 菜谱 |
| **容器 (Container)** | 镜像的运行实例 | 做出来的菜 |
| **Dockerfile** | 构建镜像的指令文件 | 做菜步骤 |
| **Docker Compose** | 多容器编排工具 | 宴席菜单 |

### 2.2 Dockerfile 编写详解

```dockerfile
# Dockerfile - 每一行都有详细注释

# ===== 第一阶段：构建阶段 =====
# FROM：指定基础镜像，就像盖房子要先有地基
# node:20-alpine 是官方精简镜像，体积小，安全性高
FROM node:20-alpine AS builder

# WORKDIR：设置工作目录，后续命令都在此目录执行
# 类比：cd /app
WORKDIR /app

# COPY package*.json：先只复制依赖声明文件
# 为什么？Docker 有缓存机制，如果依赖没变，不用重新安装
COPY package*.json ./
COPY prisma ./prisma/

# RUN：在容器中执行命令
# 安装所有依赖（包括 devDependencies，因为构建需要 TypeScript）
RUN npm ci

# COPY . .：复制所有源代码到容器中
COPY . .

# 生成 Prisma Client
RUN npx prisma generate

# 编译 TypeScript
RUN npm run build

# ===== 第二阶段：生产阶段 =====
# 新的镜像，只包含运行时需要的东西
FROM node:20-alpine AS production

# 设置生产环境变量
ENV NODE_ENV=production

WORKDIR /app

# 只复制 package.json，准备安装生产依赖
COPY package*.json ./
COPY prisma ./prisma/

# 只安装生产依赖，不安装 TypeScript 等开发工具
RUN npm ci --only=production && npm cache clean --force

# 从构建阶段复制编译后的代码
COPY --from=builder /app/dist ./dist

# 生成 Prisma Client（生产环境版本）
RUN npx prisma generate

# EXPOSE：声明容器运行时监听的端口
# 这只是文档说明，实际端口映射在 docker run 时指定
EXPOSE 3000

# USER：切换到非 root 用户，安全最佳实践
RUN addgroup -g 1001 -S nodejs
RUN adduser -S nodeuser -u 1001
USER nodeuser

# CMD：容器启动时执行的命令
# 只能有一个 CMD，最后一个生效
CMD ["node", "dist/index.js"]
```

**Dockerfile 指令速查表**：

```
┌─────────────┬────────────────────────────────────────────┐
│    指令      │                  说明                       │
├─────────────┼────────────────────────────────────────────┤
│ FROM        │ 基础镜像，必须是第一条指令                    │
│ WORKDIR     │ 设置工作目录                                │
│ COPY        │ 从宿主机复制文件到镜像                       │
│ RUN         │ 构建时执行命令（安装依赖等）                  │
│ ENV         │ 设置环境变量                                │
│ EXPOSE      │ 声明端口（文档作用）                         │
│ CMD         │ 容器启动时的默认命令                         │
│ ENTRYPOINT  │ 容器启动时的入口命令（不可被覆盖）            │
│ ARG         │ 构建时的参数                                │
│ USER        │ 指定运行用户                                │
│ HEALTHCHECK │ 容器健康检查                                │
└─────────────┴────────────────────────────────────────────┘
```

### 2.3 多阶段构建

为什么要使用多阶段构建？

```
┌─────────────────────────────────────────────────────────────┐
│                    单阶段 vs 多阶段构建                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   单阶段构建：                                               │
│   ┌───────────────────────────────┐                         │
│   │  源代码                        │                         │
│   │  + node_modules (500MB)        │  → 最终镜像：~600MB     │
│   │  + TypeScript                  │                         │
│   │  + 开发工具                    │                         │
│   └───────────────────────────────┘                         │
│                                                             │
│   多阶段构建：                                               │
│   阶段 1 (builder)          阶段 2 (production)              │
│   ┌─────────────────┐      ┌─────────────────┐              │
│   │  源代码           │      │  编译后的 JS     │              │
│   │  + node_modules   │ ───→ │  + 生产依赖      │              │
│   │  + TypeScript     │ 复制 │  (150MB)         │ → ~180MB    │
│   │  + 编译工具       │      │                  │              │
│   └─────────────────┘      └─────────────────┘              │
│                                                             │
│   结果：镜像体积减少 70%！                                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.5 docker build 与 docker run 命令

```bash
# 构建镜像
# -t：给镜像起名字（tag）
# .：使用当前目录的 Dockerfile
docker build -t blog-api:1.0 .

# 查看本地镜像
docker images

# 运行容器
# -d：后台运行
# -p 3000:3000：端口映射（宿主机:容器）
# --name：给容器起名字
# --env-file：使用环境变量文件
docker run -d \
  -p 3000:3000 \
  --name blog-api \
  --env-file .env.production \
  blog-api:1.0

# 查看运行中的容器
docker ps

# 查看容器日志
docker logs blog-api
docker logs -f blog-api  # 实时查看

# 进入容器内部（调试用）
docker exec -it blog-api sh

# 停止容器
docker stop blog-api

# 删除容器
docker rm blog-api

# 删除镜像
docker rmi blog-api:1.0
```

### 2.6 Docker Compose 多容器编排

在实际项目中，应用通常需要多个服务配合工作。**Docker Compose** 让你用一个文件定义和管理多个容器。

```
┌─────────────────────────────────────────────────────────────┐
│                   Docker Compose 架构                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌─────────────────────────────────────────────────────┐   │
│   │                blog-network (网络)                    │   │
│   │                                                     │   │
│   │   ┌──────────────┐  ┌──────────────┐  ┌──────────┐ │   │
│   │   │   blog-api   │  │  postgres    │  │  redis   │ │   │
│   │   │   (Node.js)  │  │  (数据库)    │  │  (缓存)  │ │   │
│   │   │   :3000      │  │  :5432       │  │  :6379   │ │   │
│   │   └──────┬───────┘  └──────┬───────┘  └────┬─────┘ │   │
│   │          │                 │                │       │   │
│   │          └─────────────────┴────────────────┘       │   │
│   │                    内部通信                          │   │
│   └─────────────────────────────────────────────────────┘   │
│                           ↑                                 │
│                      端口映射                                │
│                           ↓                                 │
│                      宿主机 :3000                           │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

```yaml
# docker-compose.yml - 完整的多容器配置

version: '3.8'

# 服务定义
services:
  # 应用服务
  app:
    build:
      context: .
      dockerfile: Dockerfile
      target: production
    container_name: blog-api
    restart: unless-stopped
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
      - DATABASE_URL=postgresql://bloguser:blogpass123@postgres:5432/blogdb
      - JWT_SECRET=your-jwt-secret-change-in-production
      - REDIS_URL=redis://redis:6379
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started
    networks:
      - blog-network
    volumes:
      - uploads:/app/uploads

  # PostgreSQL 数据库
  postgres:
    image: postgres:15-alpine
    container_name: blog-postgres
    restart: unless-stopped
    environment:
      POSTGRES_USER: bloguser
      POSTGRES_PASSWORD: blogpass123
      POSTGRES_DB: blogdb
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - blog-network
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U bloguser -d blogdb"]
      interval: 10s
      timeout: 5s
      retries: 5

  # Redis 缓存
  redis:
    image: redis:7-alpine
    container_name: blog-redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    volumes:
      - redis_data:/data
    networks:
      - blog-network

# 网络定义
networks:
  blog-network:
    driver: bridge

# 数据卷定义（持久化存储）
volumes:
  postgres_data:
  redis_data:
  uploads:
```

**Docker Compose 常用命令**：

```bash
# 启动所有服务（后台运行）
docker-compose up -d

# 查看服务状态
docker-compose ps

# 查看日志
docker-compose logs -f app
docker-compose logs -f postgres

# 停止所有服务
docker-compose down

# 停止并删除所有数据卷（慎用！会删除数据库数据）
docker-compose down -v

# 重新构建并启动
docker-compose up -d --build

# 进入某个容器
docker-compose exec app sh
docker-compose exec postgres psql -U bloguser -d blogdb

# 执行数据库迁移
docker-compose exec app npx prisma migrate deploy
```

## 三、部署平台

### 3.1 Railway 部署（推荐）

**Railway** 是一个现代化的云部署平台，操作简单，对 Node.js 项目支持极好，非常适合初学者。

**部署步骤**：

```
┌─────────────────────────────────────────────────────────────┐
│                  Railway 部署流程                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. 注册账号          2. 连接 GitHub        3. 选择仓库     │
│   ┌──────────┐        ┌──────────┐         ┌──────────┐    │
│   │ railway. │        │  GitHub  │         │ blog-api │    │
│   │ app      │ ─────→ │  OAuth   │ ──────→ │  仓库    │    │
│   └──────────┘        └──────────┘         └──────────┘    │
│                                             │               │
│                                             ↓               │
│   6. 部署完成           5. 添加数据库       4. 配置环境变量  │
│   ┌──────────┐        ┌──────────┐         ┌──────────┐    │
│   │ 🎉 上线  │ ←───── │PostgreSQL│ ←─────  │ ENV VARS │    │
│   │ 获得域名 │        │ 一键添加  │         │  填写配置  │    │
│   └──────────┘        └──────────┘         └──────────┘    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**详细步骤**：

```bash
# 1. 首先确保项目已推送到 GitHub

# 2. 访问 railway.app 并用 GitHub 登录

# 3. 点击 "New Project" → "Deploy from GitHub repo"

# 4. 选择你的 blog-api 仓库

# 5. Railway 会自动检测到这是一个 Node.js 项目
```

**配置环境变量**：

在 Railway 项目设置中添加环境变量：

```bash
# 在 Railway Dashboard 中设置这些变量
NODE_ENV=production
JWT_SECRET=your-super-secret-jwt-key-change-this
JWT_EXPIRES_IN=7d
PORT=3000
```

**添加 PostgreSQL 数据库**：

```bash
# 在 Railway 项目中：
# 1. 点击 "New" → "Database" → "PostgreSQL"
# 2. Railway 会自动创建数据库并提供 DATABASE_URL
# 3. 点击你的应用服务，在 Variables 标签页可以看到自动注入的变量
```

**配置启动命令**：

```bash
# 在 Railway 的 Settings 中：
# Build Command: npm run build
# Start Command: npm run prisma:migrate && npm start
```

**自动部署配置**（可选，在项目根目录创建）：

```toml
# railway.toml
[build]
builder = "nixpacks"

[deploy]
startCommand = "npx prisma migrate deploy && node dist/index.js"
restartPolicyType = "on_failure"
restartPolicyMaxRetries = 10
```

## 四、数据库迁移在生产环境

### 4.1 Prisma 迁移策略

在生产环境中执行数据库迁移需要特别小心，因为错误的迁移可能导致数据丢失。

```
┌─────────────────────────────────────────────────────────────┐
│                Prisma 迁移命令对比                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   开发环境：                                                 │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  npx prisma migrate dev                             │   │
│   │  • 创建新的迁移文件                                   │   │
│   │  • 应用迁移到数据库                                   │   │
│   │  • 重新生成 Prisma Client                            │   │
│   │  • ⚠️  会重置数据库（开发时安全）                      │   │
│   └─────────────────────────────────────────────────────┘   │
│                                                             │
│   生产环境：                                                 │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  npx prisma migrate deploy                          │   │
│   │  • 只应用待执行的迁移                                 │   │
│   │  • 不会重置数据库                                     │   │
│   │  • 不会生成 Prisma Client                            │   │
│   │  • ✅ 生产环境安全                                    │   │
│   └─────────────────────────────────────────────────────┘   │
│                                                             │
│   其他常用命令：                                             │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  npx prisma migrate status  — 查看迁移状态           │   │
│   │  npx prisma generate        — 重新生成 Client        │   │
│   │  npx prisma db push         — 直接同步（无迁移文件）   │   │
│   └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 6.1 什么是 CI/CD

### 6.2 GitHub Actions 配置

创建 `.github/workflows/deploy.yml`：

```yaml
# .github/workflows/deploy.yml
# GitHub Actions 自动部署工作流

name: Deploy Blog API

# 触发条件
on:
  push:
    branches: [main]  # 只在 main 分支触发
  pull_request:
    branches: [main]  # PR 时运行测试

# 环境变量
env:
  NODE_VERSION: '20'

jobs:
  # ===== Job 1: 测试 =====
  test:
    name: Run Tests
    runs-on: ubuntu-latest

    services:
      # 启动测试数据库
      postgres:
        image: postgres:15
        env:
          POSTGRES_USER: testuser
          POSTGRES_PASSWORD: testpass
          POSTGRES_DB: testdb
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      # 检出代码
      - name: Checkout code
        uses: actions/checkout@v4

      # 安装 Node.js
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: ${{ env.NODE_VERSION }}
          cache: 'npm'

      # 安装依赖
      - name: Install dependencies
        run: npm ci

      # 生成 Prisma Client
      - name: Generate Prisma Client
        run: npx prisma generate

      # 运行数据库迁移
      - name: Run migrations
        run: npx prisma migrate deploy
        env:
          DATABASE_URL: postgresql://testuser:testpass@localhost:5432/testdb

      # 运行测试
      - name: Run tests
        run: npm test
        env:
          DATABASE_URL: postgresql://testuser:testpass@localhost:5432/testdb
          JWT_SECRET: test-secret

      # 代码质量检查
      - name: Run linting
        run: npm run lint

      # TypeScript 类型检查
      - name: Type check
        run: npx tsc --noEmit

  # ===== Job 2: 部署 =====
  deploy:
    name: Deploy to Production
    needs: test  # 依赖测试通过
    runs-on: ubuntu-latest
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'

    steps:
      # 检出代码
      - name: Checkout code
        uses: actions/checkout@v4

      # 部署到 Railway
      - name: Deploy to Railway
        uses: bervProject/railway-deploy@main
        with:
          railway_token: ${{ secrets.RAILWAY_TOKEN }}
          service: blog-api

      # 部署成功通知（可选）
      - name: Notify success
        if: success()
        run: echo "Deployed successfully!"

      # 部署失败通知（可选）
      - name: Notify failure
        if: failure()
        run: echo "Deployment failed!"
```

```yaml
# .github/workflows/ci-cd.yml - 更完整的配置

  push:
    branches: [main, develop]

    branches: [main]

          POSTGRES_USER: test

          DATABASE_URL: postgresql://test:test@localhost:5432/test

    name: Build
```

```dockerfile
RUN adduser -S nodeuser -u 1001
```

## 常见误区

1. **把 `.env` 文件提交到 Git**：数据库密码、JWT 密钥等敏感信息一旦提交到 Git 仓库（尤其是公开仓库），就等于公开了。即使后来删除，Git 历史中仍然存在。必须在 `.gitignore` 中排除 `.env` 文件。

2. **生产环境用 `npm start` 直接启动**：直接用 `node dist/index.js` 启动，进程挂了就彻底挂了。应该用 PM2 或 Docker 的重启策略，进程崩溃后自动重启。

3. **数据库迁移用 `prisma migrate dev`**：`migrate dev` 在开发环境安全，但它会重置数据库。生产环境必须用 `prisma migrate deploy`，只应用待执行的迁移，不会重置数据。

4. **Docker 镜像不优化体积**：把 `node_modules`、TypeScript 源码、开发工具全部打包进镜像，最终镜像 800MB。用多阶段构建可以减到 200MB 以下，构建速度和部署速度都会大幅提升。

## 工程建议

1. **多阶段构建是标配**：第一阶段安装所有依赖并编译 TypeScript，第二阶段只复制编译产物和生产依赖。镜像体积减少 70%，安全性也更高（不包含开发工具）。

2. **用 `depends_on` + `healthcheck` 确保服务就绪**：PostgreSQL 容器启动后还需要几秒初始化数据库。只用 `depends_on` 不够，要配合 `healthcheck` 确保数据库真正准备好后才启动应用。

3. **CI/CD 流水线要包含测试**：GitHub Actions 工作流应该是：代码推送 → Lint 检查 → TypeScript 类型检查 → 运行测试 → 构建 → 部署。测试不过就不部署，避免把 bug 推到生产环境。

4. **敏感信息用平台的 Secret 管理**：Railway、Fly.io 等平台都提供环境变量管理功能；GitHub Actions 用 Repository Secrets。不要把密钥写在 `docker-compose.yml` 或 CI 配置文件中。
