## 场景引入

你的服务运行得很稳定，直到某天用户反馈"网站好慢"。你 SSH 到服务器一看，磁盘满了——日志文件占了 20GB。你清了日志，服务恢复了。但你开始想：为什么没有提前发现？有没有一种方式，能在磁盘到 80% 时就告警，而不是等到满了才知道？

## 一、监控的核心指标

```
四个黄金信号（Google SRE）：

  ┌─────────────────────────────────────────┐
  │  延迟（Latency）                         │
  │  └── 请求响应时间                        │
  │                                          │
  │  流量（Traffic）                         │
  │  └── 每秒请求数                          │
  │                                          │
  │  错误（Errors）                          │
  │  └── 错误率                              │
  │                                          │
  │  饱和度（Saturation）                    │
  │  └── CPU、内存、磁盘使用率               │
  └─────────────────────────────────────────┘
```

```bash
# app         0.50%   128MiB / 512MiB     25%     1.5kB / 2kB   0B / 0B

# redis       0.10%   32MiB / 256MiB      12%     1kB / 1kB     0B / 0B

# 查看容器日志

# 查看容器事件
docker events --filter container=app
```

## 三、轻量级监控方案

### 3.1 cAdvisor + Prometheus + Grafana

```yaml
# docker-compose.monitoring.yml
services:
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:latest
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro
    ports:
      - "8080:8080"
    restart: unless-stopped

  prometheus:
    image: prom/prometheus:latest
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prometheus-data:/prometheus
    ports:
      - "9090:9090"
    restart: unless-stopped

  grafana:
    image: grafana/grafana:latest
    volumes:
      - grafana-data:/var/lib/grafana
    ports:
      - "3001:3000"
    environment:
      GF_SECURITY_ADMIN_PASSWORD: admin
    restart: unless-stopped

volumes:
  prometheus-data:
  grafana-data:
```

### 3.2 简单的健康检查脚本

```bash
#!/bin/bash
# scripts/health-check.sh

# 检查服务状态
check_service() {
    local service=$1
    local url=$2
    
    response=$(curl -s -o /dev/null -w "%{http_code}" "$url" 2>/dev/null)
    
    if [ "$response" = "200" ]; then
        echo "✅ $service: OK"
    else
        echo "❌ $service: FAILED (HTTP $response)"
        # 发送告警
        send_alert "$service" "$response"
    fi
}

send_alert() {
    local service=$1
    local status=$2
    
    # 发送到 Slack / 邮件 / 钉钉
    curl -X POST -H 'Content-type: application/json' \
        --data "{\"text\":\"⚠️ Service $service is down (HTTP $status)\"}" \
        "$SLACK_WEBHOOK_URL"
}

# 检查各个服务
check_service "App" "http://localhost:3000/health"
check_service "PostgreSQL" "http://localhost:5432"
check_service "Redis" "http://localhost:6379"
```

## 四、告警策略

```
告警级别：

  紧急（P0）：
  ├── 服务完全不可用
  ├── 数据丢失
  └── 安全事件

  严重（P1）：
  ├── 错误率 > 5%
  ├── 响应时间 > 5s
  └── 磁盘 > 90%

  警告（P2）：
  ├── 错误率 > 1%
  ├── 响应时间 > 2s
  └── 磁盘 > 80%

  通知方式：
  ├── P0：电话 + 短信 + Slack
  ├── P1：Slack + 邮件
  └── P2：Slack
```

## 常见误区

- **"有日志就够了"**：日志告诉你发生了什么，但不告诉你系统状态。监控告诉你 CPU、内存、磁盘的趋势，让你在问题发生前发现苗头。
- **"监控系统很复杂，小项目用不上"**：`docker stats` + 一个简单的健康检查脚本 + crontab 就是最基本的监控。不需要 Prometheus + Grafana 也能有基本的可观测性。
- **"告警越多越安全"**：告警太多会导致告警疲劳，真正的问题被淹没在噪音中。只对真正需要人工介入的情况告警，其他交给自动处理。
- **"监控只关注技术指标"**：业务指标（注册数、订单数、错误率）同样重要。技术指标正常但业务指标异常，可能说明有逻辑 bug。

---

## 工程建议

- **从最简单的监控开始**：`docker stats` 记录资源使用，健康检查脚本每 5 分钟跑一次，异常时发 Slack 通知。先跑起来，再考虑复杂方案。
- **配置日志轮转**：`max-size: 10m` + `max-file: 3` 防止日志撑满磁盘。这是最容易被忽视但最基础的运维配置。
- **告警分级**：P0（服务不可用）→ 电话+短信，P1（错误率>5%）→ Slack+邮件，P2（磁盘>80%）→ Slack。不同级别不同通知方式。
- **用 cAdvisor + Prometheus + Grafana 建立完整监控**：cAdvisor 采集容器指标，Prometheus 存储时序数据，Grafana 可视化。适合有 5+ 容器的项目。
