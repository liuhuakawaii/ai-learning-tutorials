# 第三课：CPU、内存、磁盘限制

> **课程定位**：合理分配资源，防止一个服务耗尽系统资源
> **前置知识**：Docker 基础
> **预计时长**：20 分钟

---

## 场景引入

你的服务器上有 5 个容器在运行。某天 API 容器出现内存泄漏，内存占用从 200MB 飙升到 2GB，把服务器内存吃光了。PostgreSQL 被 OOM Kill 杀掉，数据丢失。Redis 也被杀了，缓存全没了。一个容器的问题，拖垮了整台服务器。你开始想：能不能限制每个容器最多用多少资源？

---

## 学习目标

1. 理解为什么需要资源限制
2. 掌握内存和 CPU 限制的配置
3. 学会监控资源使用

---

## 一、为什么需要资源限制

```
没有资源限制的风险：

  一个服务内存泄漏 → 占满所有内存 → 其他服务被 OOM Kill
  一个服务 CPU 100% → 其他服务卡顿

  资源限制的作用：
  ✅ 隔离：一个服务的问题不影响其他服务
  ✅ 可预测：确保每个服务有足够资源
  ✅ 安全：防止恶意或 buggy 程序耗尽资源
```

---

## 二、内存限制

```yaml
services:
  app:
    deploy:
      resources:
        limits:
          memory: 512M        # 最大内存
        reservations:
          memory: 256M        # 预留内存
```

```bash
# 运行时限制
docker run -d --memory=512m --memory-reservation=256m my-app

# 查看内存使用
docker stats --format "table {{.Name}}\t{{.MemUsage}}"
```

```
内存超限行为：

  超过 limit → OOM Kill（容器被杀死）
  超过 reservation → 开始使用 swap（如果有的话）
```

---

## 三、CPU 限制

```yaml
services:
  app:
    deploy:
      resources:
        limits:
          cpus: "1.0"         # 最多使用 1 个 CPU
        reservations:
          cpus: "0.5"         # 预留 0.5 个 CPU
```

```bash
# 运行时限制
docker run -d --cpus=1.0 --cpu-shares=512 my-app

# 查看 CPU 使用
docker stats --format "table {{.Name}}\t{{.CPUPerc}}"
```

---

## 四、磁盘限制

```yaml
services:
  app:
    storage_opt:
      size: '1G'              # 限制容器文件系统大小
```

```
注意：磁盘限制需要存储驱动支持
通常使用 volume 来管理存储，而不是限制容器文件系统
```

## 五、监控资源使用

```bash
# 实时监控
docker stats

# 输出示例：
# CONTAINER   CPU %   MEM USAGE / LIMIT   MEM %   NET I/O       BLOCK I/O
# app         0.50%   128MiB / 512MiB     25%     1.5kB / 2kB   0B / 0B
# postgres    1.20%   256MiB / 1GiB       25%     3kB / 4kB     10MB / 5MB
# redis       0.10%   32MiB / 256MiB      12%     1kB / 1kB     0B / 0B

# 查看容器资源限制
docker inspect --format='{{.HostConfig.Memory}}' container_name
```

## 六、最佳实践

```
资源限制最佳实践：

  ✅ 为每个服务设置合理的限制
  ✅ 根据实际使用调整，不要过紧或过松
  ✅ 预留足够资源给系统
  ✅ 监控资源使用，及时调整

  参考配置（1GB RAM 服务器）：
  ├── 系统预留：256MB
  ├── PostgreSQL：256MB
  ├── Redis：128MB
  └── App：384MB
```

## 七、动手练习

```bash
# 1. 启动一个内存限制的容器
docker run -d --memory=100m --name mem-test alpine sh -c "while true; do sleep 1; done"

# 2. 查看资源使用
docker stats mem-test

# 3. 测试超限
docker run --memory=50m alpine sh -c "cat /dev/zero | head -c 100m"
# 应该被 OOM Kill
```

## 常见误区

- **"服务器内存够用就不需要限制"**：不限制的话，一个内存泄漏的容器可以吃光所有内存，影响其他服务。资源限制是隔离机制，不是性能优化。
- **"限制设得越紧越好"**：限制太紧会导致容器频繁 OOM Kill。应该根据实际使用量留 20-30% 的余量。
- **"CPU 限制会让服务变慢"**：CPU 限制是上限，不是分配。如果服务平时只用 0.2 核，限制 1 核不会让它变慢，只是防止它吃光所有 CPU。
- **"docker stats 就够监控了"**：`docker stats` 是实时快照，不能看到历史趋势。生产环境需要 Prometheus + Grafana 等工具记录历史数据。

---

## 工程建议

- **每个服务都设置内存限制**：PostgreSQL 256MB、Redis 128MB、App 384MB（1GB 服务器参考值）。防止一个服务拖垮整台服务器。
- **根据实际使用量设置限制**：先用 `docker stats` 观察正常运行时的资源使用，再设置限制。限制值 = 正常峰值 × 1.3。
- **预留资源给系统**：至少预留 256MB 给操作系统和 Docker 守护进程。不要把所有内存都分配给容器。
- **用 `docker stats` 建立基线**：部署后观察 24 小时的资源使用，了解每个服务的正常范围，作为设置限制和告警阈值的依据。

---

## 小结

1. **内存限制**：`--memory` 防止内存泄漏影响其他服务
2. **CPU 限制**：`--cpus` 防止 CPU 密集型任务影响其他服务
3. **监控**：`docker stats` 查看实时资源使用
4. **合理分配**：根据实际使用设置限制
