# 第六课：安全基线

> **课程定位**：建立安全基线，保护应用和数据
> **前置知识**：Docker 基础
> **预计时长**：25 分钟

---

## 场景引入

你的项目上线了，运行稳定。直到安全团队告诉你：你们的 Docker 镜像里有 3 个高危漏洞，容器以 root 运行，数据库密码写在 docker-compose.yml 里，.env 文件被提交到了 Git。你开始意识到：安全不是可选项，是生产环境的基本要求。你需要建立一套安全基线，让每个部署都符合最低安全标准。

## 一、Docker 安全最佳实践

### 1.1 镜像安全

```dockerfile
# ✅ 使用官方或可信的基础镜像
FROM node:18-alpine

# ✅ 使用特定版本，不用 latest
FROM node:18.17.0-alpine

# ✅ 非 root 用户运行
RUN addgroup -g 1001 -S nodejs && adduser -S nodeuser -u 1001
USER nodeuser

# ✅ 只读文件系统（如果适用）
# 在 docker run 时使用 --read-only

# ✅ 定期更新基础镜像
```

### 1.2 运行时安全

```bash
# ✅ 限制资源
docker run -d --memory=512m --cpus=1 my-app

# ✅ 只读文件系统
docker run -d --read-only --tmpfs /tmp my-app

# ✅ 不要暴露不必要的端口
docker run -d -p 3000:3000 my-app  # 只暴露需要的端口

# ✅ 使用非 root 用户
docker run -d --user 1001:1001 my-app

# ✅ 限制 capabilities
docker run -d --cap-drop=ALL --cap-add=NET_BIND_SERVICE my-app
```

## 二、密钥管理

### 2.1 不要做的事

```
❌ 在 Dockerfile 中硬编码密钥
   ENV DB_PASSWORD=secret123

❌ 在 docker-compose.yml 中写密码
   environment:
     DB_PASSWORD: secret123

❌ 把 .env 提交到 Git
   git add .env

❌ 在代码中打印密钥
   console.log(process.env.API_KEY)
```

### 2.2 正确做法

```yaml
# ✅ 使用 .env 文件，不提交到 Git
# ✅ 使用 Docker Secrets（Swarm 模式）
# ✅ 使用外部密钥管理服务（AWS Secrets Manager、HashiCorp Vault）
# ✅ 运行时通过环境变量传入
```

```bash
# 运行时传入密钥
docker run -d -e DB_PASSWORD=secret my-app

# 或者使用 .env 文件
docker run -d --env-file .env my-app
```

### 2.3 Docker BuildKit Secret

```dockerfile
# syntax=docker/dockerfile:1
FROM node:18-alpine

RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
```

```bash
# 构建时传入密钥
echo "//registry.npmjs.org/:_authToken=xxx" > .npmrc
docker build --secret id=npmrc,src=.npmrc -t my-app .
rm .npmrc
```

## 四、网络安全

```yaml
# ✅ 使用自定义网络
networks:
  app-network:
    driver: bridge

# ✅ 网络隔离
services:
  app:
    networks:
      - app-network
  postgres:
    networks:
      - app-network  # 只在同一网络中可访问
```

```bash
# ✅ 不要暴露数据库端口到宿主机
# 只在内部网络中访问
services:
  postgres:
    expose:
      - "5432"  # 只在 Docker 网络中
    # 不要使用 ports
```

## 五、安全检查清单

```
镜像安全：
□ 使用官方或可信的基础镜像
□ 使用特定版本标签
□ 定期更新基础镜像
□ 扫描镜像漏洞
□ 使用多阶段构建

运行时安全：
□ 非 root 用户运行
□ 资源限制（CPU、内存）
□ 只读文件系统（如适用）
□ 不暴露不必要的端口
□ 限制 capabilities

密钥管理：
□ 密钥不硬编码在代码中
□ 密钥不提交到 Git
□ 使用环境变量或密钥管理服务
□ 定期轮换密钥

网络安全：
□ 使用自定义网络
□ 数据库不暴露到外网
□ 使用 HTTPS
□ 配置防火墙
```

## 常见误区

- **"容器隔离了就很安全"**：容器共享宿主机内核，隔离强度不如虚拟机。以 root 运行的容器如果存在内核漏洞，可能导致容器逃逸。安全需要多层防护。
- **"小项目不需要关注安全"**：自动化扫描工具会无差别地探测所有暴露的服务。攻击者不会因为项目小就放过你。
- **"安全扫描一次就够了"**：新的漏洞每天都在被发现。应该在 CI/CD 中集成自动扫描，每次构建都检查。
- **"用 latest 标签就自动安全了"**：`latest` 不代表最新安全补丁。应该用固定版本标签，定期更新，验证后再部署。

---

## 工程建议

- **在 CI/CD 中集成镜像扫描**：Trivy 或 Docker Scout 在构建流水线中自动扫描，高危漏洞阻断部署。
- **用 BuildKit secret mount 传入构建密钥**：`RUN --mount=type=secret` 确保密钥不会进入镜像层，比 `ARG` 更安全。
- **数据库不暴露到外网**：PostgreSQL、Redis 只通过 Docker 网络访问，不映射端口到宿主机。减少攻击面。
- **建立安全检查清单**：每次发布前检查镜像漏洞、非 root 用户、密钥管理、网络隔离。把清单写进文档，团队共同遵守。

---

## 小结

1. **镜像安全**：官方镜像、特定版本、非 root 用户
2. **密钥管理**：不硬编码、不提交 Git、运行时传入
3. **漏洞扫描**：定期扫描，及时修复
4. **安全检查清单**：建立并执行安全基线
