# 第五课：数据库迁移

> **课程定位**：学会安全地更新数据库结构
> **前置知识**：Docker Compose、PostgreSQL 基础
> **预计时长**：25 分钟

---

## 场景引入

你的应用上线了，用户开始注册和创建数据。产品经理说要加一个"手机号"字段。你直接连上数据库 `ALTER TABLE users ADD COLUMN phone VARCHAR(20)`——线上立刻报错了，因为代码还没有适配这个字段。你开始想：数据库结构变更应该怎么管理？能不能像代码一样有版本控制，能回滚，能在部署时自动执行？

## 学习目标

1. 理解数据库迁移的概念
2. 使用 Prisma 或 Knex 管理迁移

4. 掌握迁移的最佳实践

## 一、什么是数据库迁移

```
数据库迁移 = 版本控制数据库结构

  ┌─────────────────────────────────────────┐
  │           数据库版本历史                  │
  │                                          │
  │  001_create_users.sql                    │
  │  002_add_email_to_users.sql              │
  │  003_create_posts.sql                    │
  │  004_add_index_on_email.sql              │
  │                                          │
  │  每个迁移文件 = 数据库的一次变更           │
  │  可以前进（migrate）或回滚（rollback）    │
  └─────────────────────────────────────────┘
```

## 二、使用 Prisma 管理迁移

### 2.1 初始化 Prisma

```bash
npm install prisma @prisma/client
npx prisma init
```

### 2.2 定义 Schema

```prisma
// prisma/schema.prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id    Int     @id @default(autoincrement())
  email String  @unique
  name  String?
  posts Post[]
}

model Post {
  id       Int    @id @default(autoincrement())
  title    String
  content  String?
  author   User   @relation(fields: [authorId], references: [id])
  authorId Int
}
```

### 2.3 创建迁移

```bash
# 创建迁移文件
npx prisma migrate dev --name init

# 生成 Prisma Client
npx prisma generate
```

### 2.4 在生产环境运行迁移

```bash
# 运行所有待执行的迁移
npx prisma migrate deploy
```

## 三、Docker Compose 集成

### 3.1 迁移作为启动步骤

```yaml
services:
  # 迁移服务
  db-migrate:
    build: .
    command: npx prisma migrate deploy
    environment:
      DATABASE_URL: postgres://postgres:secret@postgres:5432/mydb
    depends_on:
      postgres:
        condition: service_healthy

  # 应用服务
  app:
    build: .
    command: node dist/index.js
    environment:
      DATABASE_URL: postgres://postgres:secret@postgres:5432/mydb
    depends_on:
      db-migrate:
        condition: service_completed_successfully
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:14
    environment:
      POSTGRES_DB: mydb
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  pgdata:
```

### 3.2 在 Dockerfile 中包含迁移

```dockerfile
FROM node:18-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npx prisma generate
RUN npm run build

FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/prisma ./prisma
COPY package.json ./
CMD ["sh", "-c", "npx prisma migrate deploy && node dist/index.js"]
```

## 四、迁移最佳实践

```
✅ 每次变更一个迁移文件
✅ 迁移文件提交到 Git
✅ 先备份再迁移（生产环境）
✅ 迁移要幂等（可重复执行）
✅ 测试环境先验证
❌ 不要手动修改生产数据库
❌ 不要删除已执行的迁移
```

## 常见误区

- **"数据库变更直接连上去改就行"**：手动修改数据库结构无法追溯、无法回滚、不同环境可能不一致。迁移工具让数据库变更像代码一样可管理。
- **"迁移文件可以随便改"**：已经执行过的迁移文件不应该修改。如果需要变更，创建新的迁移文件。修改已执行的迁移会导致不同环境的数据库状态不一致。
- **"Prisma 不支持回滚就不用了"**：Prisma 确实不直接支持回滚，但可以通过创建新的迁移来"撤销"变更。对于大多数场景，这比回滚更安全。
- **"迁移在 CI/CD 里自动跑就行了"**：迁移应该在部署流程中执行，但要有独立的步骤和错误处理。迁移失败时不应该继续部署应用。

---

## 工程建议

- **迁移作为独立的启动步骤**：用 `depends_on` + `condition: service_completed_successfully` 确保迁移完成后再启动应用。
- **每次变更一个迁移文件**：一个迁移做一件事（加字段、加索引、加表），便于理解和回滚。
- **生产环境迁移前先备份**：`pg_dump` 备份数据库，再执行迁移。迁移失败时可以恢复。
- **迁移文件提交到 Git**：迁移文件是项目的一部分，和代码一起 review、一起部署。

---

## 小结

1. **数据库迁移**：版本控制数据库结构变更
2. **Prisma**：现代化的 ORM，内置迁移工具
3. **Docker 集成**：迁移作为启动步骤，确保应用启动前数据库就绪
4. **最佳实践**：每次一个迁移、先备份、先测试
