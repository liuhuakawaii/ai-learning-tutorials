# 03 多步推理评估——任务完成率、步骤合理性、回退处理

> Agent 的价值在于处理复杂任务。多步推理评估就是检验它"想得对不对、做得好不好"。

## 场景引入

你构建了一个数据分析 Agent，要求它完成"从数据库提取数据、清洗、分析趋势、生成图表、撰写报告"这条五步链路。测试发现，Agent 有时在第二步就跑偏了——数据清洗时丢掉了关键字段，导致后续分析全部失准，但它依然自信地生成了一份看起来很专业的错误报告。更糟糕的是，当某一步工具调用失败时，Agent 不会回退重试，而是直接跳过继续执行，最终输出一个残缺的结果。你怎么判断它"想得对不对、做得好不好"？

## 学习目标

- 掌握多步推理任务的评估方法
- 学会评估任务规划和执行质量
- 理解回退处理和错误恢复的评估

## 一、多步推理评估维度

### 1.1 任务完成率

```python
def evaluate_task_completion(
    task_description: str,
    agent_output: str,
    expected_outcome: str,
    client
) -> dict:
    """评估任务完成情况"""
    
    prompt = f"""评估 Agent 是否完成了用户任务。

任务描述：{task_description}
期望结果：{expected_outcome}
Agent 输出：{agent_output}

评估：
1. 任务是否完成？
2. 完成质量如何？
3. 是否有遗漏？

请以 JSON 格式输出：
{{"completed": true/false, "quality": <1-5>, "missing": ["遗漏1"], "reasoning": "理由"}}"""

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        temperature=0,
        response_format={"type": "json_object"}
    )
    
    return json.loads(response.choices[0].message.content)
```

### 1.2 步骤合理性

```python
def evaluate_step_reasoning(
    task: str,
    execution_trace: list[dict],
    client
) -> dict:
    """评估执行步骤的合理性"""
    
    trace_text = "\n".join([
        f"步骤 {s['step']}: {s['thought']} → {s['action']}"
        for s in execution_trace
    ])

任务：{task}

执行步骤：
{trace_text}

评估：
1. 步骤顺序是否合理？
2. 是否有冗余步骤？
3. 是否有遗漏步骤？
4. 每步的推理是否正确？

请以 JSON 格式输出：
{{"reasoning_quality": <1-5>, "redundant_steps": [], "missing_steps": [], "issues": ["问题1"]}}"""

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        temperature=0,
        response_format={"type": "json_object"}
    )
    
    return json.loads(response.choices[0].message.content)
```

### 1.3 回退处理

```python
def evaluate_error_recovery(
    execution_trace: list[dict],
    client
) -> dict:
    """评估错误恢复能力"""
    
    errors = [s for s in execution_trace if s.get("status") == "error"]
    
    if not errors:
        return {"recovery_rate": 1.0, "errors": 0, "recovered": 0}
    
    recovered = 0
    for error in errors:
        # 检查错误后是否有成功的步骤
        error_idx = execution_trace.index(error)
        subsequent = execution_trace[error_idx+1:]
        if any(s.get("status") == "success" for s in subsequent):
            recovered += 1
    
    return {
        "recovery_rate": recovered / len(errors),
        "errors": len(errors),
        "recovered": recovered,
        "unrecovered_errors": [
            e for e in errors 
            if not any(s.get("status") == "success" 
                      for s in execution_trace[execution_trace.index(e)+1:])
        ]
    }
```

## 二、综合评估框架

```python
class MultiStepEvaluator:
    """多步推理评估器"""
    
    def __init__(self, client):
        self.client = client
    
    def evaluate(
        self,
        task: str,
        execution_trace: list[dict],
        final_output: str,
        expected_outcome: str
    ) -> dict:
        """综合评估多步推理"""
        
        results = {
            "task_completion": evaluate_task_completion(
                task, final_output, expected_outcome, self.client
            ),
            "step_reasoning": evaluate_step_reasoning(
                task, execution_trace, self.client
            ),
            "error_recovery": evaluate_error_recovery(
                execution_trace, self.client
            ),
        }
        
        # 综合评分
        completion_score = results["task_completion"]["quality"] / 5.0
        reasoning_score = results["step_reasoning"]["reasoning_quality"] / 5.0
        recovery_score = results["error_recovery"]["recovery_rate"]
        
        results["overall_score"] = (
            completion_score * 0.5 +
            reasoning_score * 0.3 +
            recovery_score * 0.2
        )
        
        return results
```

## 常见误区

1. **只看最终结果不看过程**：Agent 输出了正确答案，但执行路径绕了 8 步才完成本该 3 步搞定的事。过程低效意味着更高的成本和更大的出错概率。
2. **把"完成率低"笼统归因为"模型不行"**：完成率低可能是任务理解错了、可能是规划能力不足、也可能是某一步工具调用失败。不拆分到具体步骤就无法针对性优化。
3. **忽略错误恢复评估**：很多评测只关注"最终是否成功"，不关注中间失败后 Agent 能否自我纠正。一个能在出错后回退重试的 Agent 远比一个"一错到底"的 Agent 可靠。
4. **用人工评估代替自动化评估**：多步推理的评估需要大量用例，人工逐条检查 trace 效率太低且主观偏差大。应尽早建立基于 LLM-as-Judge 的自动化评估流程。

## 工程建议

1. **定义"最优步骤数"基准线**：为每类任务定义一个合理步骤数范围。实际步骤数超过基准线 1.5 倍就标记为"低效"，超过 2 倍标记为"严重低效"。这比单纯看完成率更有诊断价值。
2. **错误恢复评估要注入真实故障**：不能只靠历史数据中的自然错误。在测试环境中人为注入工具超时、返回空结果、返回错误格式等故障，观察 Agent 能否正确回退和重试。
3. **按步骤粒度打分而非只给总分**：评估报告应该展示每一步的推理质量评分，这样才能精确定位"第 3 步的规划有问题"而不是笼统说"Agent 不行"。
4. **建立回归测试机制**：每次修改 Agent 的 Prompt 或工具配置后，自动跑评估套件并与上次结果对比。如果某项指标下降超过阈值，阻断发布。

## 参考答案

### 练习一

**思路**：设计一个多步推理评估用例需要包含：明确的任务描述、预期步骤、预期输出。选择一个需要 3-5 步才能完成的任务，用 MultiStepEvaluator 进行综合评估。

**答案**：

```python
from openai import OpenAI

client = OpenAI()

# 设计评估用例：数据分析任务
eval_case = {
    "task": "分析过去一周的用户注册趋势，找出注册量最高的一天，并给出可能的原因",
    "expected_steps": [
        "查询数据库获取过去7天的注册数据",
        "按日期分组统计每日注册量",
        "找出最大值对应的日期",
        "查询该日期的相关事件（如营销活动）",
        "生成趋势分析报告",
    ],
    "expected_outcome": "过去一周中 X 月 X 日注册量最高，共 N 人，可能原因是当天有营销活动",
    "difficulty": "medium",
}

# 模拟 Agent 执行 trace
execution_trace = [
    {"step": 1, "thought": "需要先查询注册数据", "action": "db_query", "status": "success"},
    {"step": 2, "thought": "数据已获取，按日期分组", "action": "data_groupby", "status": "success"},
    {"step": 3, "thought": "找最大值", "action": "data_max", "status": "success"},
    {"step": 4, "thought": "查询当天事件", "action": "db_query", "status": "error"},
    {"step": 5, "thought": "事件查询失败，用已有数据回答", "action": "generate_answer", "status": "success"},
]


def run_multistep_evaluation(client):
    """运行多步推理评估"""
    trace_text = "\n".join(
        f"步骤 {s['step']}: {s['thought']} → {s['action']} [{s['status']}]"
        for s in execution_trace
    )

    prompt = f"""评估 Agent 的多步推理执行质量。

任务：{eval_case['task']}
期望步骤：{eval_case['expected_steps']}
实际执行：
{trace_text}

请以 JSON 格式评估：
1. task_completion: 任务完成度 (0-5)
2. step_reasoning: 步骤合理性 (0-5)
3. redundant_steps: 冗余步骤列表
4. missing_steps: 遗漏步骤列表
5. error_recovery: 错误恢复质量 (0-5)
6. overall_score: 综合评分 (0-1)
"""

    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        temperature=0,
        response_format={"type": "json_object"},
    )

    return json.loads(response.choices[0].message.content)


# 计算步骤效率
optimal_steps = len(eval_case["expected_steps"])
actual_steps = len(execution_trace)
step_efficiency = optimal_steps / actual_steps if actual_steps > optimal_steps else 1.0

# 计算错误恢复率
errors = [s for s in execution_trace if s["status"] == "error"]
recovered = [e for e in errors if any(
    s["status"] == "success" for s in execution_trace[execution_trace.index(e) + 1:]
)]
recovery_rate = len(recovered) / len(errors) if errors else 1.0

print(f"步骤效率: {step_efficiency:.2f}")
print(f"错误恢复率: {recovery_rate:.2f}")
```

**要点**：
- 多步推理用例应选择需要至少 3 步的任务，太简单的任务无法评估推理能力
- 评估时必须同时看任务完成度和步骤合理性，两者缺一不可
- 常见错误：只用一条 trace 就下结论，应至少跑 5 次取平均值，因为 Agent 的非确定性会导致不同执行路径

### 练习二

**思路**：拿到一个失败的 trace 后，先统计每步的状态，找到第一个 error 步骤，再分析该步骤的 thought/action 是否合理，最后判断错误是否传播到了后续步骤。

**答案**：

```python
import json

# 模拟一个失败的执行 trace
failed_trace = [
    {"step": 1, "thought": "用户要查销售报表", "action": "parse_intent",
     "status": "success", "duration": 0.3},
    {"step": 2, "thought": "需要查询数据库", "action": "db_query",
     "action_input": {"table": "sales", "date": "2024-01"}, "status": "success",
     "duration": 1.2, "observation": "返回 500 条记录"},
    {"step": 3, "thought": "数据太多，需要聚合", "action": "data_aggregate",
     "action_input": {"group_by": "product", "agg": "sum"},
     "status": "error", "duration": 0.8, "error": "ColumnNotFoundError: 'product' column does not exist"},
    {"step": 4, "thought": "聚合失败了，换个方式试试", "action": "data_aggregate",
     "action_input": {"group_by": "product_name", "agg": "sum"},
     "status": "error", "duration": 0.5, "error": "同样的列名错误"},
    {"step": 5, "thought": "两次都失败了，直接用原始数据回答", "action": "generate_answer",
     "status": "success", "duration": 2.0, "observation": "输出了 500 条未聚合的原始数据"},
]


def diagnose_failure(trace: list[dict]) -> dict:
    """诊断多步推理失败的根因"""
    errors = [s for s in trace if s["status"] == "error"]
    if not errors:
        return {"status": "no_failure", "diagnosis": "所有步骤成功"}

    first_error = errors[0]
    first_error_idx = trace.index(first_error)

    # 分析错误传播
    subsequent_failures = [
        s for s in trace[first_error_idx + 1:]
        if s["status"] == "error"
    ]

    # 判断错误类型
    error_msg = first_error.get("error", "")
    if "ColumnNotFound" in error_msg or "NameError" in error_msg:
        root_cause = "数据 schema 不匹配——Agent 对数据库表结构的理解有误"
        fix = "在 Agent 的 System Prompt 中注入数据库 schema 信息，或添加 schema 查询工具"
    elif "Timeout" in error_msg:
        root_cause = "外部服务超时"
        fix = "添加重试机制和超时兜底策略"
    elif "Permission" in error_msg:
        root_cause = "权限不足"
        fix = "在 Agent 执行前检查用户权限"
    else:
        root_cause = "未知错误"
        fix = "需要进一步分析错误日志"

    # 评估恢复质量
    has_later_success = any(
        s["status"] == "success" for s in trace[first_error_idx + 1:]
    )
    if has_later_success:
        last_step = trace[-1]
        if "原始数据" in last_step.get("observation", ""):
            recovery_quality = "差——虽然有后续成功步骤，但输出了未经处理的原始数据，任务目标未达成"
        else:
            recovery_quality = "中——有恢复但质量待评估"
    else:
        recovery_quality = "无恢复——Agent 在错误后直接停止"

    return {
        "status": "failure_diagnosed",
        "first_error_step": first_error["step"],
        "error_message": error_msg,
        "root_cause": root_cause,
        "fix_suggestion": fix,
        "error_propagated": len(subsequent_failures) > 0,
        "recovery_quality": recovery_quality,
    }


diagnosis = diagnose_failure(failed_trace)
print(json.dumps(diagnosis, ensure_ascii=False, indent=2))
```

**要点**：
- 诊断的第一步是找到第一个 error 步骤，后续错误往往是它的连锁反应
- 本案例中 Agent 在第 3 步因 schema 不匹配失败，第 4 步重试用了同样的错误列名，说明 Agent 没有从错误中学习
- 常见错误：把最终失败归因为"模型不行"，实际上根因可能是 prompt 中缺少 schema 信息

### 练习三

**思路**：提高错误恢复能力的核心是让 Agent 在遇到错误时能"分析原因→尝试不同方案→失败时告知用户"，而不是盲目重试或跳过。设计一个包含重试策略、fallback 机制和用户通知的回退策略。

**答案**：

```python
import time
from typing import Callable, Any


class AgentFallbackStrategy:
    """Agent 错误回退策略"""

    def __init__(self, max_retries: int = 2):
        self.max_retries = max_retries
        self.error_log = []

    def execute_with_recovery(
        self,
        action_fn: Callable,
        action_name: str,
        fallback_fn: Callable = None,
        analyze_error_fn: Callable = None,
    ) -> dict:
        """带恢复的执行"""
        last_error = None

        for attempt in range(self.max_retries + 1):
            try:
                result = action_fn()
                return {
                    "success": True,
                    "result": result,
                    "attempts": attempt + 1,
                    "recovered": attempt > 0,
                }
            except Exception as e:
                last_error = e
                self.error_log.append({
                    "action": action_name,
                    "attempt": attempt + 1,
                    "error": str(e),
                    "timestamp": time.time(),
                })

                # 如果有错误分析函数，用它来调整下一次尝试
                if analyze_error_fn and attempt < self.max_retries:
                    adjustment = analyze_error_fn(e)
                    if adjustment.get("should_retry"):
                        # 根据分析结果调整参数
                        action_fn = adjustment.get("adjusted_action", action_fn)
                        continue

                if attempt < self.max_retries:
                    time.sleep(0.5 * (attempt + 1))  # 指数退避

        # 所有重试失败，尝试 fallback
        if fallback_fn:
            try:
                fallback_result = fallback_fn(last_error)
                return {
                    "success": True,
                    "result": fallback_result,
                    "attempts": self.max_retries + 1,
                    "used_fallback": True,
                }
            except Exception as fallback_error:
                pass

        # 彻底失败，返回友好的错误信息
        return {
            "success": False,
            "error": str(last_error),
            "attempts": self.max_retries + 1,
            "user_message": f"抱歉，执行 {action_name} 时遇到问题，请稍后重试或联系客服。",
        }


# 使用示例：数据分析 Agent
strategy = AgentFallbackStrategy(max_retries=2)


def query_sales_data():
    """主查询"""
    raise Exception("ColumnNotFoundError: 'product' not found")


def analyze_error(error):
    """分析错误并给出调整方案"""
    if "ColumnNotFound" in str(error):
        return {
            "should_retry": True,
            "adjusted_action": lambda: {"data": "使用正确的列名查询成功"},
        }
    return {"should_retry": False}


def fallback_report(error):
    """降级方案：返回上次缓存的报表"""
    return {"data": "返回上次缓存的销售报表（数据可能略有延迟）"}


result = strategy.execute_with_recovery(
    action_fn=query_sales_data,
    action_name="查询销售数据",
    fallback_fn=fallback_report,
    analyze_error_fn=analyze_error,
)
print(json.dumps(result, ensure_ascii=False, indent=2))
```

**要点**：
- 回退策略的三个层次：重试（同参数或调整参数）→ 降级（用缓存/备选方案）→ 告知用户
- 关键是 `analyze_error_fn`——盲目重试不如分析错误后调整策略重试
- 常见错误：重试时不改变任何参数直接重试，或者 fallback 输出了过时/不准确的数据却未告知用户
