# 01 可观测性三支柱——Logs / Traces / Metrics 在 AI 应用中的应用

> 看不见就修不了。可观测性是 AI 应用从"能跑"到"能运维"的关键跨越。

## 场景引入

你的 AI 客服系统上线两周后，用户投诉量突然翻倍。你打开服务器日志，发现满屏的 `200 OK`，看起来一切正常。但用户说"回答质量变差了"，产品经理说"响应变慢了"，财务说"API 费用超了预算"。你试图排查，却发现根本不知道是哪个环节出了问题——没有 LLM 调用日志、没有链路追踪、没有成本指标。这时候你才意识到：一个没有可观测性的 AI 应用，就像在黑暗中修车。

## 学习目标

- 理解可观测性的三支柱模型
- 掌握 AI 应用特有的可观测性需求
- 建立 AI 应用的监控思维

## 二、AI 应用的可观测性需求

### 2.1 传统应用 vs AI 应用

```
传统 Web 应用：
  请求 → 处理 → 响应
  监控：延迟、错误率、吞吐量

AI 应用：
  请求 → Prompt 构建 → LLM 调用 → 结果解析 → 后处理 → 响应
       → RAG 检索 → 上下文组装
       → 工具调用 → 结果整合
  
  额外需要监控：
  - Token 消耗（成本）
  - 模型幻觉（质量）
  - 检索质量（RAG）
  - 工具调用成功率（Agent）
```

## 四、追踪设计

### 4.1 请求链路追踪

```python
from opentelemetry import trace

tracer = trace.get_tracer("ai-app")

def process_user_query(query: str):
    """处理用户查询（带追踪）"""
    with tracer.start_as_current_span("process_query") as span:
        span.set_attribute("user_query", query)
        
        # 1. RAG 检索
        with tracer.start_as_current_span("rag_retrieval"):
            contexts = retrieve_contexts(query)
            span.set_attribute("contexts_count", len(contexts))
        
        # 2. LLM 调用
        with tracer.start_as_current_span("llm_call"):
            answer = call_llm(query, contexts)
            span.set_attribute("model", "gpt-4o")
        
        # 3. 后处理
        with tracer.start_as_current_span("post_processing"):
            result = post_process(answer)
        
        return result
```

## 常见误区

1. **把可观测性等同于"打日志"**：只用 `print` 或 `console.log` 记录离散事件，没有结构化字段、没有 Trace ID 关联，出了问题依然无法串联排查。日志只是三支柱之一，缺少 Traces 和 Metrics 就像只有拼图碎片。

2. **照搬传统 Web 应用的监控模板**：传统应用监控 CPU、内存、QPS 就够了，但 AI 应用的核心指标是 Token 消耗、模型延迟分位数、幻觉率。直接套用传统模板会漏掉最关键的信号。

3. **在生产环境记录完整的 Prompt 和 Response**：LLM 的输入输出可能包含用户隐私数据或敏感业务信息。全量记录到日志系统会带来合规风险，应该做脱敏或采样。

4. **指标颗粒度太粗**：只监控"总请求量"和"总错误率"，没有按模型、按功能模块、按用户分组。出问题时知道"整体变差了"，但不知道是哪个模型、哪个功能拖垮了指标。

## 工程建议

1. **用 Trace ID 串联三支柱**：每条日志、每个 Span、每个指标都要携带同一个 Trace ID，这样在 Grafana 看到异常指标时，能一键跳转到对应 Trace 和日志。推荐使用 OpenTelemetry 的 W3C Trace Context 标准做上下文传播。

2. **按业务维度打标签**：指标除了按 `model` 标签分组，还要按 `feature`（功能模块）、`user_tier`（用户等级）、`region`（地域）分组。出问题时能快速定位"是付费用户的 RAG 检索功能变慢了"而不是"整体变慢了"。

3. **日志采样与脱敏并行**：生产环境对正常请求采样 10% 记录完整输入输出用于调试，错误请求 100% 记录。同时对 Prompt 和 Response 中的用户个人信息做正则脱敏后再写入日志系统。

4. **建立指标基线再设告警**：上线后先跑一周收集基线数据（P50/P95 延迟、平均 Token 数、日均成本），再基于基线设置告警阈值。不要凭空拍脑袋设阈值，否则告警要么太松要么太紧。

## 参考答案

### 练习一

**思路**：AI 应用的日志结构需要包含请求标识、用户信息、模型信息、Token 消耗、延迟和业务语义字段。关键是用结构化 JSON 格式，便于后续检索和分析。

**答案**：

```python
import structlog
import uuid
from datetime import datetime


logger = structlog.get_logger()


def create_llm_log_schema() -> dict:
    """AI 应用的结构化日志 schema"""
    return {
        "request_id": "string, 唯一请求标识，用于串联全链路",
        "timestamp": "ISO 8601 时间戳",
        "user_id": "用户标识",
        "session_id": "会话标识",
        "feature": "功能模块，如 rag_query / chat / summary",
        "model": "模型名称，如 gpt-4o",
        "input_tokens": "输入 Token 数",
        "output_tokens": "输出 Token 数",
        "total_tokens": "总 Token 数",
        "latency_ms": "请求耗时（毫秒）",
        "ttft_ms": "首 Token 延迟（毫秒），流式场景",
        "success": "是否成功",
        "error_type": "错误类型（如有）",
        "quality_score": "质量评分（如有自动评估）",
        "retrieved_doc_count": "RAG 召回文档数（如有）",
        "cost_usd": "本次请求成本（美元）",
    }


def log_llm_call(
    request_id: str,
    user_id: str,
    feature: str,
    model: str,
    input_tokens: int,
    output_tokens: int,
    latency_ms: float,
    success: bool,
    quality_score: float = None,
    error_type: str = None,
    session_id: str = None,
):
    """记录 LLM 调用日志"""
    pricing = {"gpt-4o": (2.50, 10.00), "gpt-4o-mini": (0.15, 0.60)}
    input_price, output_price = pricing.get(model, (0.15, 0.60))
    cost = input_tokens * input_price / 1_000_000 + output_tokens * output_price / 1_000_000

    logger.info(
        "llm_call",
        request_id=request_id,
        timestamp=datetime.now().isoformat(),
        user_id=user_id,
        session_id=session_id,
        feature=feature,
        model=model,
        input_tokens=input_tokens,
        output_tokens=output_tokens,
        total_tokens=input_tokens + output_tokens,
        latency_ms=latency_ms,
        success=success,
        error_type=error_type,
        quality_score=quality_score,
        cost_usd=round(cost, 6),
    )


# 使用示例
log_llm_call(
    request_id=str(uuid.uuid4()),
    user_id="user_123",
    feature="rag_query",
    model="gpt-4o",
    input_tokens=1500,
    output_tokens=300,
    latency_ms=2300,
    success=True,
    quality_score=0.87,
)
```

**要点**：
- 每条日志必须携带 `request_id`，用于串联 Traces、Logs 和 Metrics 三支柱
- `cost_usd` 字段应自动计算而非手动填写，否则成本监控无法自动化
- 常见错误：日志用纯文本格式而非结构化 JSON，导致无法按字段检索和聚合分析

### 练习二

**思路**：LLM 调用追踪器需要用 OpenTelemetry 的 Span 模型记录每个操作的层级关系、耗时和属性。核心是支持自动嵌套 Span（父子关系）和异常记录。

**答案**：

```python
import time
import uuid
from dataclasses import dataclass, field
from typing import Optional
from contextlib import contextmanager


@dataclass
class Span:
    span_id: str
    name: str
    parent_id: Optional[str]
    start_time: float
    end_time: Optional[float] = None
    attributes: dict = field(default_factory=dict)
    events: list = field(default_factory=list)
    status: str = "ok"

    @property
    def duration(self) -> Optional[float]:
        if self.end_time:
            return self.end_time - self.start_time
        return None


class SimpleLLMTracer:
    """简单的 LLM 调用追踪器"""

    def __init__(self):
        self.spans: list[Span] = []
        self._current_span_stack: list[str] = []

    @contextmanager
    def start_span(self, name: str, attributes: dict = None):
        span_id = str(uuid.uuid4())[:8]
        parent_id = self._current_span_stack[-1] if self._current_span_stack else None

        span = Span(
            span_id=span_id,
            name=name,
            parent_id=parent_id,
            start_time=time.time(),
            attributes=attributes or {},
        )
        self.spans.append(span)
        self._current_span_stack.append(span_id)

        try:
            yield span
        except Exception as e:
            span.status = "error"
            span.events.append({
                "name": "exception",
                "message": str(e),
                "type": type(e).__name__,
            })
            raise
        finally:
            span.end_time = time.time()
            self._current_span_stack.pop()

    def get_trace_summary(self) -> dict:
        root_spans = [s for s in self.spans if s.parent_id is None]
        total_duration = sum(s.duration or 0 for s in root_spans)

        return {
            "total_spans": len(self.spans),
            "total_duration": total_duration,
            "spans": [
                {
                    "name": s.name,
                    "duration_ms": round((s.duration or 0) * 1000, 2),
                    "parent": s.parent_id,
                    "status": s.status,
                    "attributes": s.attributes,
                }
                for s in self.spans
            ],
        }


# 使用示例
tracer = SimpleLLMTracer()

with tracer.start_span("process_query", {"user_query": "什么是 RAG？"}) as root:
    with tracer.start_span("rag_retrieval") as retrieval:
        retrieval.attributes["top_k"] = 5
        time.sleep(0.2)
        with tracer.start_span("vector_search") as search:
            search.attributes["index"] = "knowledge_base"
            time.sleep(0.15)
        with tracer.start_span("reranking") as rerank:
            rerank.attributes["model"] = "cross-encoder"
            time.sleep(0.1)

    with tracer.start_span("llm_call", {"model": "gpt-4o", "input_tokens": 1200}) as llm:
        time.sleep(1.0)

    with tracer.start_span("post_processing") as post:
        time.sleep(0.05)

summary = tracer.get_trace_summary()
for s in summary["spans"]:
    indent = "  " * (1 if s["parent"] else 0)
    print(f"{indent}{s['name']}: {s['duration_ms']}ms [{s['status']}]")
```

**要点**：
- `start_span` 使用上下文管理器自动管理 Span 的开始/结束，异常时自动标记 error 状态
- 父子关系通过 `_current_span_stack` 实现，保证 Span 嵌套层级正确
- 常见错误：Span 嵌套过深（超过 5 层），导致 Trace 树过于复杂，应该只追踪可独立优化的步骤

### 练习三

**思路**：AI 应用的核心指标应覆盖性能、成本、质量和可用性四个维度。每个指标需要定义计算公式、数据来源和告警阈值。

**答案**：

**要点**：
- 首 Token 延迟（TTFT）比总延迟更能反映用户体验，流式场景必须单独监控
- 单次请求成本是商业可行性的核心指标，需要设多级告警（50% 提醒、80% 警告、95% 限流）
- 常见错误：只监控技术指标（延迟、错误率）而忽略业务指标（忠实度、成本），导致"系统稳定但质量很差"的情况被忽视
