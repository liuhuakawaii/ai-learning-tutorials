# 01 可观测性三支柱

> 看不见就修不了。你的 AI 应用上线两周后用户投诉翻倍，但服务器日志全是 `200 OK`。

## 一个排查困境

你的 AI 客服系统上线两周后，用户投诉量突然翻倍。你打开服务器日志，满屏的 `200 OK`，看起来一切正常。

但用户说"回答质量变差了"，产品经理说"响应变慢了"，财务说"API 费用超了预算"。你试图排查，却发现：

- 没有 LLM 调用日志——不知道每次请求消耗了多少 Token
- 没有链路追踪——不知道延迟出在检索、LLM 还是后处理
- 没有成本指标——不知道费用超支是哪个模型、哪个功能导致的

一个没有可观测性的 AI 应用，就像在黑暗中修车。

## 三支柱

```
Logs（日志）── 记录离散事件
  └── AI 应用：每次 LLM 调用的输入输出、Token 数、延迟

Traces（追踪）── 记录请求的完整链路
  └── AI 应用：从用户输入到最终回答的全链路（检索→LLM→后处理）

Metrics（指标）── 聚合的数值数据
  └── AI 应用：Token 消耗趋势、延迟分位数、成功率、成本
```

三者的关系：Metrics 告诉你"有问题"，Traces 告诉你"问题在哪"，Logs 告诉你"问题是什么"。

## 实验：给你的 AI 应用加一行日志

先从最简单的开始——结构化日志：

```python
import json
import uuid
from datetime import datetime
from openai import OpenAI

client = OpenAI()

def log_llm_call(request_id, model, input_tokens, output_tokens, latency_ms, success, error=None):
    """记录一次 LLM 调用"""
    log_entry = {
        "timestamp": datetime.now().isoformat(),
        "request_id": request_id,
        "model": model,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "total_tokens": input_tokens + output_tokens,
        "latency_ms": latency_ms,
        "success": success,
        "error": error,
    }
    print(json.dumps(log_entry, ensure_ascii=False))

def ask_with_logging(question: str, model: str = "gpt-4o-mini") -> str:
    request_id = str(uuid.uuid4())[:8]
    start = datetime.now()

    try:
        response = client.chat.completions.create(
            model=model,
            messages=[{"role": "user", "content": question}],
            temperature=0.7
        )
        latency = (datetime.now() - start).total_seconds() * 1000
        usage = response.usage

        log_llm_call(
            request_id=request_id,
            model=model,
            input_tokens=usage.prompt_tokens,
            output_tokens=usage.completion_tokens,
            latency_ms=round(latency, 1),
            success=True
        )
        return response.choices[0].message.content

    except Exception as e:
        latency = (datetime.now() - start).total_seconds() * 1000
        log_llm_call(
            request_id=request_id, model=model,
            input_tokens=0, output_tokens=0,
            latency_ms=round(latency, 1), success=False, error=str(e)
        )
        raise

# 测试
answer = ask_with_logging("Python 的 GIL 是什么？")
```

运行后你会看到一行 JSON 日志，包含 request_id、Token 数、延迟、是否成功。这就是可观测性的起点。

## AI 应用特有的指标

传统 Web 应用监控 CPU、内存、QPS 就够了。AI 应用需要额外关注：

| 维度 | 指标 | 为什么重要 |
|------|------|------------|
| 性能 | TTFT（首 Token 延迟） | 直接影响用户感知 |
| 性能 | P50/P95/P99 延迟 | 尾部延迟影响用户体验 |
| 成本 | 单次请求成本 | 决定产品能否盈利 |
| 成本 | 日/月 Token 消耗 | 预算控制 |
| 质量 | 忠实度分数 | 低于阈值说明有幻觉风险 |
| 质量 | 幻觉率 | AI 应用的核心质量指标 |
| 可用性 | 成功率 | 系统稳定性 |

## 实验：追踪一次完整的 RAG 请求

```python
import time
from contextlib import contextmanager

class SimpleTracer:
    def __init__(self):
        self.spans = []
        self._stack = []

    @contextmanager
    def span(self, name: str, attributes: dict = None):
        span_id = f"{name}_{len(self.spans)}"
        parent = self._stack[-1] if self._stack else None
        start = time.time()

        self._stack.append(span_id)
        try:
            yield span
        finally:
            duration = (time.time() - start) * 1000
            self.spans.append({
                "name": name,
                "parent": parent,
                "duration_ms": round(duration, 1),
                "attributes": attributes or {},
            })
            self._stack.pop()

    def print_trace(self):
        print("\n=== Trace ===")
        for s in self.spans:
            indent = "  " if s["parent"] else ""
            attrs = f" {s['attributes']}" if s["attributes"] else ""
            print(f"{indent}{s['name']}: {s['duration_ms']}ms{attrs}")

# 模拟一个 RAG 请求的完整链路
tracer = SimpleTracer()

with tracer.span("process_query", {"query": "什么是 RAG？"}):
    with tracer.span("rag_retrieval"):
        with tracer.span("vector_search", {"top_k": 5}):
            time.sleep(0.15)  # 模拟向量搜索
        with tracer.span("reranking", {"model": "cross-encoder"}):
            time.sleep(0.1)   # 模拟重排序

    with tracer.span("llm_call", {"model": "gpt-4o", "input_tokens": 1200}):
        time.sleep(1.0)       # 模拟 LLM 调用

    with tracer.span("post_processing"):
        time.sleep(0.05)      # 模拟后处理

tracer.print_trace()
```

运行后你会看到一个树形的 Trace，每个步骤的耗时一目了然。如果用户投诉"响应慢"，看 Trace 就知道是检索慢、LLM 慢还是后处理慢。

## Prometheus 指标收集

```python
from prometheus_client import Counter, Histogram, Gauge

# 请求计数
llm_requests = Counter('llm_requests_total', 'Total LLM requests', ['model', 'status'])

# 延迟分布
llm_latency = Histogram('llm_latency_seconds', 'LLM request latency', ['model'])

# Token 消耗
llm_tokens = Counter('llm_tokens_total', 'Total tokens consumed', ['model', 'type'])

# 成本
llm_cost = Gauge('llm_cost_dollars', 'LLM API cost', ['model'])
```

这些指标配合 Grafana 可以搭建 Dashboard，实时展示趋势和异常。

## 关键设计原则

**用 Trace ID 串联三支柱**：每条日志、每个 Span、每个指标都携带同一个 Trace ID。在 Grafana 看到异常指标时，能一键跳转到对应 Trace 和日志。

**按业务维度打标签**：指标除了按 `model` 分组，还要按 `feature`（功能模块）、`user_tier`（用户等级）分组。出问题时能快速定位"是付费用户的 RAG 检索功能变慢了"。

**日志采样与脱敏**：生产环境对正常请求采样 10% 记录完整输入输出，错误请求 100% 记录。对 Prompt 和 Response 中的个人信息做脱敏。

**先建基线再设告警**：上线后先跑一周收集基线数据（P50/P95 延迟、平均 Token 数、日均成本），再基于基线设置告警阈值。

## 常见误判

**把可观测性等同于"打日志"**：只用 `print` 记录离散事件，没有结构化字段、没有 Trace ID 关联，出了问题依然无法串联排查。

**照搬传统 Web 应用的监控模板**：传统应用监控 CPU、内存就够了，AI 应用的核心指标是 Token 消耗、模型延迟分位数、幻觉率。

**在生产环境记录完整的 Prompt 和 Response**：可能包含用户隐私数据，应该做脱敏或采样。

## 练习

### 练习一：给你的 AI 应用加结构化日志

修改你的 AI 应用代码，为每次 LLM 调用记录结构化日志，至少包含：request_id、model、input_tokens、output_tokens、latency_ms、success。

### 练习二：实现一个简单的 Tracer

扩展本课的 `SimpleTracer`，增加以下功能：
- `get_summary()`：返回总耗时、各步骤耗时占比
- `get_bottleneck()`：返回耗时最长的步骤
- 支持异常记录：某个步骤抛异常时记录到 Span 中

### 练习三：设计 5 个核心指标

为你的 AI 应用设计 5 个核心监控指标，每个指标定义：
- 计算公式
- 数据来源
- 告警阈值（warning 和 critical 两级）
