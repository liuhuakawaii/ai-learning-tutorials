# 03 调用链路追踪——从用户输入到模型输出的全链路可视化

> 看见全链路，才能找到瓶颈。追踪是调试 AI 应用的"时光机"。

## 场景引入

用户反馈"这个问题的回答不对"，你打开 Langfuse 看到该条 Trace 的总耗时 4.2 秒，质量评分 2/5。但问题出在哪？是 RAG 检索召回了错误的文档，还是 Prompt 组装时上下文被截断了，还是模型本身产生了幻觉？如果你的追踪只记录了"一次 LLM 调用"，那和没追踪没有区别。你需要的是从用户输入到模型输出的每一步都可视化的全链路追踪。

## 学习目标

- 掌握 AI 应用的全链路追踪方法
- 学会分析追踪数据定位问题
- 建立链路追踪的最佳实践

## 二、追踪实现

### 2.1 完整追踪示例

```python
from langfuse.decorators import observe, langfuse_context

@observe()
def process_user_query(query: str, user_id: str) -> dict:
    """完整追踪的用户查询处理"""
    
    # 设置用户信息
    langfuse_context.update_current_trace(
        user_id=user_id,
        session_id=f"session_{user_id}"
    )
    
    # 1. 输入处理
    processed_input = preprocess_input(query)
    
    # 2. RAG 检索
    retrieval_result = rag_retrieve(processed_input)
    
    # 3. 上下文组装
    prompt = assemble_prompt(query, retrieval_result["contexts"])
    
    # 4. LLM 调用
    answer = call_llm_with_tracking(prompt)
    
    # 5. 后处理
    final_result = post_process(answer, retrieval_result["sources"])
    
    # 6. 自动评估
    eval_score = auto_evaluate(query, final_result["answer"], retrieval_result["contexts"])
    
    return final_result

@observe()
def rag_retrieve(query: str) -> dict:
    """RAG 检索（带追踪）"""
    
    # 查询重写
    rewritten_query = rewrite_query(query)
    
    # 向量搜索
    search_results = vector_search(rewritten_query)
    
    # 重排序
    reranked = rerank(query, search_results)
    
    return {
        "contexts": reranked[:5],
        "sources": [r["metadata"] for r in reranked[:5]]
    }

@observe()
def call_llm_with_tracking(prompt: str) -> str:
    """带详细追踪的 LLM 调用"""
    
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        stream=True
    )
    
    # 流式收集
    full_response = ""
    for chunk in response:
        if chunk.choices[0].delta.content:
            full_response += chunk.choices[0].delta.content
    
    return full_response
```

## 三、追踪数据分析

### 3.1 性能瓶颈分析

```python
def analyze_trace_performance(trace_id: str) -> dict:
    """分析追踪性能"""
    
    # 从 Langfuse 获取追踪数据
    trace = langfuse.get_trace(trace_id)
    
    spans = trace.spans
    
    # 找出耗时最长的 Span
    longest_span = max(spans, key=lambda s: s.end_time - s.start_time)
    
    # 计算各阶段耗时占比
    total_duration = trace.end_time - trace.start_time
    
    span_durations = {}
    for span in spans:
        duration = span.end_time - span.start_time
        span_durations[span.name] = {
            "duration": duration,
            "percentage": duration / total_duration * 100
        }
    
    return {
        "total_duration": total_duration,
        "longest_span": longest_span.name,
        "span_durations": span_durations
    }
```

### 3.2 问题定位

```
常见性能问题：

问题 1：RAG 检索耗时长
  表现：rag-retrieval Span 占比 > 50%
  原因：
    - 向量搜索慢（索引问题）
    - 重排序慢（模型问题）
    - 检索数量过多
  优化：
    - 优化向量索引
    - 减少检索数量
    - 使用更快的重排序模型

问题 2：LLM 调用慢
  表现：llm-call Span 占比 > 70%
  原因：
    - 输入 Token 过多
    - 模型选择不当
    - 网络延迟
  优化：
    - 精简 Prompt
    - 使用更快的模型
    - 流式输出

问题 3：后处理慢
  表现：post-processing Span 占比 > 30%
  原因：
    - 复杂的格式化逻辑
    - 外部 API 调用
  优化：
    - 异步处理
    - 缓存结果
```

   - 记录成本

## 常见误区

1. **追踪粒度要么太粗要么太细**：只记录一个 `process_query` 的总耗时，或者把每个变量赋值都建 Span。正确的粒度是按"可独立优化的步骤"划分——RAG 检索、LLM 调用、后处理各一个 Span，内部再按需嵌套。

2. **流式响应不记录 TTFT（首 Token 延迟）**：只记录了总延迟，但用户体验差的根因是首 Token 来得太慢。流式场景下必须同时追踪 TTFT 和总延迟，它们对应不同的优化方向。

3. **错误追踪只记录"失败了"**：Trace 中只标记 `success: false`，没有记录错误类型（超时/限流/内容过滤）、重试次数、fallback 模型。排查时只能看到"这里挂了"，不知道为什么挂、有没有自动恢复。

4. **生产环境不设采样策略**：100% 采样所有请求的完整 Trace，导致追踪存储成本飙升。应该对正常请求采样（如 10%），但对错误请求和慢请求 100% 记录。

## 工程建议

1. **Trace 命名遵循"动词-对象"规范**：如 `query-knowledge-base`、`generate-summary`、`rewrite-query`。不要用 `process`、`handle` 这种模糊命名。清晰的 Trace 名称让你在 Langfuse 列表页一眼就能看出请求类型。

2. **在 Span 属性中记录业务语义**：除了 `model`、`input_tokens` 等技术字段，还要记录 `user_query_intent`（用户意图分类）、`retrieved_doc_count`（召回文档数）、`rerank_score`（重排序分数）。这些业务语义字段是分析质量退化根因的关键线索。

3. **为流式响应分别记录 TTFT 和 TPS**：首 Token 延迟（TTFT）影响用户"感知到的响应速度"，每秒 Token 数（TPS）影响"内容生成的流畅度"。两者对应不同的优化手段——TTFT 主要受模型预填充阶段影响，TPS 主要受解码阶段和输出 token 数影响。

4. **建立"慢请求"自动分析管道**：对超过 P95 延迟的 Trace 自动提取并归档，按瓶颈阶段（检索/生成/后处理）分类统计。每周 review 一次慢请求分布，持续优化性能热点。

## 参考答案

### 练习一

**思路**：全链路追踪需要覆盖从用户输入到最终响应的每个关键步骤。用 `@observe()` 装饰器自动构建 Trace 树，每个子步骤独立追踪。关键是按"可独立优化的步骤"划分 Span 粒度。

**答案**：

```python
from langfuse.decorators import observe, langfuse_context
from openai import OpenAI
import time

client = OpenAI()


@observe()
def preprocess_input(query: str) -> dict:
    """输入预处理"""
    # 意图识别
    intent = classify_intent(query)
    # 语言检测
    lang = detect_language(query)
    return {"query": query, "intent": intent, "language": lang}


@observe()
def classify_intent(query: str) -> str:
    """意图分类"""
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "将用户问题分类为: factual / analytical / chitchat"},
            {"role": "user", "content": query},
        ],
    )
    return response.choices[0].message.content.strip()


@observe()
def detect_language(query: str) -> str:
    """语言检测"""
    return "zh" if any("\u4e00" <= c <= "\u9fff" for c in query) else "en"


@observe()
def rag_retrieve(query: str) -> dict:
    """RAG 检索（带子步骤追踪）"""
    rewritten = rewrite_query(query)
    results = vector_search(rewritten)
    ranked = rerank_results(query, results)
    return {"contexts": ranked[:5], "total_retrieved": len(results)}


@observe(as_type="generation")
def rewrite_query(query: str) -> str:
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": f"改写为搜索查询: {query}"}],
    )
    return response.choices[0].message.content


@observe()
def vector_search(query: str) -> list[dict]:
    return [{"content": f"文档{i}", "score": 0.9 - i * 0.1} for i in range(10)]


@observe()
def rerank_results(query: str, results: list[dict]) -> list[dict]:
    return sorted(results, key=lambda r: r["score"], reverse=True)[:5]


@observe()
def assemble_prompt(query: str, contexts: list[str]) -> str:
    """上下文组装"""
    context_text = "\n".join(f"[{i+1}] {c}" for i, c in enumerate(contexts))
    return f"参考资料：\n{context_text}\n\n问题：{query}"


@observe(as_type="generation")
def call_llm(prompt: str) -> str:
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
    )
    return response.choices[0].message.content


@observe()
def post_process(answer: str, sources: list[str]) -> dict:
    """后处理：格式化、添加引用"""
    return {"answer": answer, "sources": sources, "formatted": True}


@observe()
def full_pipeline(query: str, user_id: str) -> dict:
    """完整的全链路追踪"""
    langfuse_context.update_current_trace(user_id=user_id)

    # 1. 输入处理
    processed = preprocess_input(query)

    # 2. RAG 检索
    retrieval = rag_retrieve(processed["query"])

    # 3. 上下文组装
    prompt = assemble_prompt(query, retrieval["contexts"])

    # 4. LLM 生成
    answer = call_llm(prompt)

    # 5. 后处理
    result = post_process(answer, [c["content"] for c in retrieval["contexts"]])

    return result
```

**要点**：
- Span 粒度按"可独立优化的步骤"划分：输入处理、检索、LLM 调用、后处理各一个 Span
- `as_type="generation"` 标记 LLM 调用，Langfuse 自动记录 Token 消耗和成本
- 常见错误：Span 粒度太细（每个变量赋值一个 Span）或太粗（只有一个 `process_query`），都不利于问题定位

### 练习二

**思路**：分析慢请求的追踪数据，需要找到耗时最长的 Span，计算各阶段耗时占比，再针对性优化。关键是区分是 LLM 调用慢还是检索慢。

**答案**：

```python
import json


def analyze_slow_trace(trace_data: dict) -> dict:
    """分析慢请求的追踪数据，定位性能瓶颈"""

    spans = trace_data.get("spans", [])
    if not spans:
        return {"error": "无 Span 数据"}

    total_duration = sum(s.get("duration_ms", 0) for s in spans)

    # 计算各阶段耗时占比
    stage_analysis = []
    for span in spans:
        duration = span.get("duration_ms", 0)
        percentage = (duration / total_duration * 100) if total_duration > 0 else 0
        stage_analysis.append({
            "name": span["name"],
            "duration_ms": duration,
            "percentage": round(percentage, 1),
            "is_bottleneck": percentage > 40,
        })

    # 按耗时排序
    stage_analysis.sort(key=lambda x: x["duration_ms"], reverse=True)
    bottleneck = stage_analysis[0]

    # 生成优化建议
    optimization_map = {
        "vector_search": {
            "diagnosis": "向量搜索是瓶颈",
            "suggestions": [
                "优化向量索引（HNSW 参数调整）",
                "减少 top_k 值（从 10 降到 5）",
                "添加查询缓存",
            ],
        },
        "rerank": {
            "diagnosis": "重排序是瓶颈",
            "suggestions": [
                "使用更快的 reranker 模型",
                "减少需要重排序的文档数",
                "对重排序结果做缓存",
            ],
        },
        "llm_call": {
            "diagnosis": "LLM 调用是瓶颈",
            "suggestions": [
                "精简 Prompt 减少 input token",
                "使用流式输出降低首 Token 延迟",
                "对简单查询用更轻量的模型",
            ],
        },
        "post_process": {
            "diagnosis": "后处理是瓶颈",
            "suggestions": [
                "将非关键后处理异步化",
                "缓存格式化结果",
            ],
        },
    }

    # 匹配优化建议
    matched_key = next(
        (k for k in optimization_map if k in bottleneck["name"].lower()),
        "llm_call",
    )

    return {
        "total_duration_ms": total_duration,
        "bottleneck": bottleneck,
        "stage_breakdown": stage_analysis,
        "optimization": optimization_map[matched_key],
    }


# 模拟一个慢请求的追踪数据
slow_trace = {
    "spans": [
        {"name": "input_processing", "duration_ms": 150},
        {"name": "vector_search", "duration_ms": 2800},
        {"name": "rerank", "duration_ms": 600},
        {"name": "llm_call", "duration_ms": 1800},
        {"name": "post_processing", "duration_ms": 120},
    ]
}

analysis = analyze_slow_trace(slow_trace)
print(f"总耗时: {analysis['total_duration_ms']}ms")
print(f"瓶颈: {analysis['bottleneck']['name']} ({analysis['bottleneck']['percentage']}%)")
print(f"诊断: {analysis['optimization']['diagnosis']}")
print("优化建议:")
for s in analysis['optimization']['suggestions']:
    print(f"  - {s}")
```

**要点**：
- 分析慢请求的第一步是找到耗时占比超过 40% 的 Span，它就是瓶颈
- 向量搜索和 LLM 调用通常是最慢的两个环节，优化方向完全不同
- 常见错误：只看总延迟不拆分各阶段，导致优化了不相关的环节

### 练习三

**思路**：根据追踪结果找到瓶颈后，针对性实施优化。以 LLM 调用慢为例，最常见的优化是精简 Prompt 和使用流式输出。优化后重新跑追踪验证效果。

**答案**：

```python
import time


def optimize_llm_call_latency() -> dict:
    """优化 LLM 调用延迟的对比实验"""

    original_prompt = """你是一个专业的 AI 助手。请基于以下参考资料回答用户的问题。
请注意以下几点：
1. 你的回答必须严格基于参考资料
2. 如果参考资料中没有相关信息，请回答"无法回答"
3. 请在回答中标注引用来源
4. 请使用清晰的格式组织你的回答
5. 如果问题有多个方面，请逐一回答

参考资料：
[1] RAG 是检索增强生成（Retrieval Augmented Generation）的缩写...
[2] RAG 的核心思想是将检索和生成结合起来...

用户问题：RAG 的工作原理是什么？"""

    optimized_prompt = """基于参考资料回答，标注来源。无相关信息则回答"无法回答"。

参考资料：
[1] RAG 是检索增强生成的缩写...
[2] RAG 结合检索和生成...

问题：RAG 的工作原理是什么？"""

    # 对比 Token 数
    original_tokens = len(original_prompt) // 2  # 粗略估算
    optimized_tokens = len(optimized_prompt) // 2
    token_reduction = (original_tokens - optimized_tokens) / original_tokens

    # 流式 vs 非流式的首 Token 延迟对比
    # 非流式：等待完整响应
    non_stream_latency = 3.2  # 秒

    # 流式：首 Token 较快到达
    stream_ttft = 0.8  # 秒

    latency_reduction = (non_stream_latency - stream_ttft) / non_stream_latency

    return {
        "prompt_optimization": {
            "original_tokens": original_tokens,
            "optimized_tokens": optimized_tokens,
            "token_reduction": f"{token_reduction:.0%}",
            "expected_cost_reduction": f"{token_reduction:.0%}",
        },
        "streaming_optimization": {
            "non_stream_latency": f"{non_stream_latency}s",
            "stream_ttft": f"{stream_ttft}s",
            "latency_reduction": f"{latency_reduction:.0%}",
            "user_perceived_improvement": "用户感知响应速度提升 75%",
        },
        "combined_effect": {
            "cost_reduction": f"{token_reduction:.0%}",
            "perceived_speed": f"+{latency_reduction:.0%}",
            "note": "精简 Prompt 既降低成本又减少延迟，是投入产出比最高的优化",
        },
    }


result = optimize_llm_call_latency()
print("=== LLM 调用延迟优化结果 ===\n")
print(f"Prompt Token 减少: {result['prompt_optimization']['token_reduction']}")
print(f"成本降低: {result['prompt_optimization']['expected_cost_reduction']}")
print(f"用户感知速度提升: {result['streaming_optimization']['latency_reduction']}")
print(f"综合效果: {result['combined_effect']['note']}")
```

**要点**：
- 精简 Prompt 是投入产出比最高的优化——既降低 Token 成本又减少延迟
- 流式输出不减少总延迟，但将首 Token 延迟从 3.2 秒降到 0.8 秒，用户体验大幅提升
- 常见错误：优化后不重新跑追踪验证效果，无法量化改善幅度
