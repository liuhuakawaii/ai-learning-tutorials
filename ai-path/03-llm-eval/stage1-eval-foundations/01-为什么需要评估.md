# 01 为什么需要评估

> 你的 AI 应用"感觉还不错"——但"感觉"不是工程标准。

## 一个真实事故

某电商公司的 RAG 客服系统上线了。Demo 演示时回答得头头是道，老板很满意。上线第一周：

- 用户问"能退货吗"，系统自信编造了一个不存在的"30 天无理由退换"条款
- 用户问"会员折扣"，系统把去年旧政策当成最新的回答
- 用户问"发票怎么开"，系统回答了正确的流程——但那是三个月前的流程

事后复盘：Demo 时问的那几个问题恰好是效果最好的。真实用户的问题千变万化，团队没有一套系统方法来衡量"到底答得怎么样"。

这门课要解决的就是这个问题。

## 实验：亲手感受"不确定输出"

在开始学评估之前，先亲手感受一下 LLM 输出的不确定性。跑这段代码：

```python
from openai import OpenAI

client = OpenAI()

question = "Python 的列表和元组有什么区别？"

# 同一个问题问 5 次
answers = []
for i in range(5):
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": question}],
        temperature=0.7
    )
    answers.append(response.choices[0].message.content)
    print(f"--- 回答 {i+1} ---")
    print(answers[-1][:200])
    print()
```

你会发现：5 次回答都不完全一样。有的更详细，有的更简洁，有的措辞不同但意思相同，有的可能遗漏了关键点。

**这就是 AI 应用和传统软件的根本区别**：传统软件的 `assert f(2, 3) == 5` 永远成立，但你没法用 `assertEqual` 测试 LLM 的输出。

## AI 应用质量的四个维度

"回答对不对"只是质量的一个维度。一个完整的评估框架需要覆盖四个方向：

### 准确性

不是简单的"对/错"，而是一个光谱：

| 子维度 | 问题 | 例子 |
|--------|------|------|
| 事实正确性 | 回答中的事实是否真实？ | "地球到月球 384,400 公里" vs "500,000 公里" |
| 忠实度 | 回答是否忠实于提供的上下文？ | 文档说"售价 99 元"，回答说"199 元"——幻觉 |
| 相关性 | 回答是否切题？ | 问 CSV 读取，回答 Python 的历史——跑题 |
| 完整性 | 是否覆盖了关键方面？ | 问优缺点，只说了优点 |

**幻觉**是准确性的头号敌人：模型生成了看起来合理、但实际上是编造的信息。而且幻觉往往包装得很专业，不容易被发现。

### 安全性

不只是"不产生有害内容"：

- **提示注入**：用户在输入中嵌入"忽略之前的指令"
- **数据泄露**：模型输出中暴露了 API Key、用户隐私
- **越权访问**：用户 A 通过 AI 访问到用户 B 的数据

### 效率

- 平均响应延迟多少？用户能等 8 秒吗？
- Token 使用是否合理？检索返回 10 个文档片段，其实 3 个就够
- 是否有不必要的重复调用？

### 成本

- 单次请求 API 费用是多少？
- 月度总成本是否可控？
- 简单问题和复杂问题用的是同一个模型吗？

一个真实案例：某 RAG 客服系统准确率 92%，看起来不错。但平均延迟 8 秒、月度 API 费用 $12,000（超出预算 3 倍）。问题出在检索返回了太多文档、System Prompt 太长、没有缓存、没有做模型分级。

## 评估驱动开发

传统开发有 TDD（测试驱动开发）。AI 应用需要 EDD（评估驱动开发）：

```
1. 定义"好回答"的标准（评估指标）
2. 构建评估数据集（Golden Dataset）
3. 开发 / 优化 Prompt / RAG / Agent
4. 跑评估，看分数
5. 根据评估结果调整
6. 重复 3-5
```

核心区别：TDD 是二元的（pass/fail），EDD 是连续的（0-100 分，需要设定阈值）。

评估有三个层次：

| 层次 | 方式 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| 人工评估 | 找人看输出打分 | 最准确 | 慢、贵、主观 | 产品早期，建立标准 |
| 自动评估 | 规则 + LLM-as-Judge | 快、便宜、可扩展 | 可能有偏差 | 日常开发、CI/CD |
| 线上评估 | 用户反馈 + A/B 测试 | 反映真实需求 | 需要流量 | 上线后持续优化 |

三个层次都要有，形成闭环。

## 实验：四维评估你的 AI 应用

找一个你之前做过的 AI 应用（或者课程项目），回答以下问题：

```python
# 把你的评估结果记录下来
my_app_eval = {
    "app_name": "你的应用名称",
    "accuracy": {
        "has_hallucination": True/False,  # 是否遇到过幻觉？
        "hallucination_example": "",       # 具体例子
        "relevancy_issues": "",            # 跑题的情况
    },
    "safety": {
        "can_inject_prompt": True/False,   # 能否通过特殊输入获取系统提示词？
        "leaks_sensitive_info": True/False, # 是否泄露过敏感信息？
    },
    "efficiency": {
        "avg_latency_seconds": 0,          # 平均延迟
        "acceptable": True/False,          # 用户能接受吗？
    },
    "cost": {
        "cost_per_request": 0,             # 单次请求成本
        "monthly_cost": 0,                 # 月度成本
        "within_budget": True/False,       # 是否在预算内？
    }
}
```

这个练习不是形式主义——它会成为你后续构建评估数据集的起点。

## 评估本身的成本

评估不是免费的：

| 环节 | 成本 |
|------|------|
| 构建 Golden Dataset | 人工编写 $5-20/条，从真实数据提取需要清洗标注 |
| 运行自动评估 | 100 条 × 3 指标 × 3 次 = 900 次 API 调用，约 $5-15/轮 |
| 人工评估 | 标注员 $10-30/小时，100 条约 3-5 小时 |

但评估的 ROI 是巨大的：发现一个幻觉问题避免错误决策、优化 Prompt 后 Token 降低 30%、上线前发现安全漏洞避免数据泄露。

建议将评估成本控制在项目总预算的 5-10%。

## 何时评估

| 时机 | 评估内容 |
|------|----------|
| 每次修改 Prompt/检索策略后 | 跑 Golden Dataset 回归测试 |
| 提交 PR | CI 自动跑评估套件，分数不能低于基线 |
| 上线前 | 完整评估 + 安全测试 + 人工审核关键 case |
| 上线后 | 用户反馈 + 线上指标监控 + 定期抽样人工审核 |

## 练习

### 练习一：收集失败案例

从你做过的 AI 应用中收集 5 个"回答不好"的真实案例。每个案例记录：

```python
failure_cases = [
    {
        "id": 1,
        "question": "用户问了什么",
        "bad_answer": "AI 的错误回答",
        "failure_type": "hallucination/outdated/irrelevant/unsafe/incomplete",
        "correct_answer": "应该回答什么",
    },
    # ... 至少 5 个
]
```

这些案例将成为你后续构建评估数据集的原始素材。失败案例比成功案例更有价值——它们暴露了系统的薄弱环节。

### 练习二：温度实验

修改上面实验代码中的 `temperature` 参数（分别试 0、0.3、0.7、1.0、1.5），观察输出的变化：

```python
import json

question = "解释什么是 RAG（检索增强生成）"
results = {}

for temp in [0, 0.3, 0.7, 1.0, 1.5]:
    responses = []
    for _ in range(3):
        response = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": question}],
            temperature=temp
        )
        responses.append(response.choices[0].message.content)
    results[temp] = responses

# 观察：temperature 越高，输出越多样，但质量波动也越大
# 这就是为什么评估需要多次运行取统计值，而不是只跑一次
```

记录你的观察：哪个温度下输出最稳定？哪个温度下偶尔会出现明显错误？
