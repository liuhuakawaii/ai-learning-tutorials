# 03 数据库运维

> 数据库是系统的命脉——迁移、备份、监控，一个都不能少。

## 场景引入

你的 AI Agent 平台上线一周后需要给 `agents` 表加几个字段。直接连数据库 `ALTER TABLE`？线上有百万条数据在跑，一个锁表操作可能让整个服务卡死几分钟。更糟的是如果改错了字段名，回滚要手动修数据。数据库迁移工具就是为了解决这个问题——让每一次结构变更都有版本、可追溯、可回滚。

## 学习目标

- 掌握 Alembic 迁移管理
- 实现数据库备份和恢复
- 理解连接池调优


## 参考答案

### 练习 1

**思路**：数据库迁移的核心是"版本化"——每次结构变更有独立的迁移脚本，支持升级和回滚。Alembic 自动生成迁移脚本后必须人工审查，因为 autogenerate 可能遗漏数据迁移逻辑。数据迁移（如字段拆分、默认值填充）需要单独的迁移脚本，不能和结构迁移混在一起。

**答案**：

```python
# alembic/versions/20250101_add_agent_table.py
"""add_agent_table

Revision ID: a1b2c3d4e5f6
Revises: 
Create Date: 2025-01-01 10:00:00.000000
"""
from alembic import op
import sqlalchemy as sa
from sqlalchemy.dialects.postgresql import JSON, UUID

revision = "a1b2c3d4e5f6"
down_revision = None
branch_labels = None
depends_on = None


def upgrade() -> None:
    # 1. 创建 agents 表
    op.create_table(
        "agents",
        sa.Column("id", UUID(as_uuid=True), primary_key=True),
        sa.Column("name", sa.String(200), nullable=False),
        sa.Column("description", sa.Text, nullable=True),
        sa.Column("system_prompt", sa.Text, nullable=False),
        sa.Column("model", sa.String(100), nullable=False, server_default="gpt-4o-mini"),
        sa.Column("config", JSON, nullable=False, server_default="{}"),
        sa.Column("owner_id", UUID(as_uuid=True), sa.ForeignKey("users.id"), nullable=False, index=True),
        sa.Column("status", sa.String(20), nullable=False, server_default="draft"),
        sa.Column("created_at", sa.DateTime, server_default=sa.func.now()),
        sa.Column("updated_at", sa.DateTime, server_default=sa.func.now(), onupdate=sa.func.now()),
    )

    # 2. 创建索引
    op.create_index("ix_agents_owner_id", "agents", ["owner_id"])
    op.create_index("ix_agents_status", "agents", ["status"])
    op.create_index("ix_agents_created_at", "agents", ["created_at"])


def downgrade() -> None:
    op.drop_index("ix_agents_created_at")
    op.drop_index("ix_agents_status")
    op.drop_index("ix_agents_owner_id")
    op.drop_table("agents")
```

数据迁移示例（字段拆分）：

```python
# alembic/versions/20250201_split_name_field.py
"""split name into first_name and last_name

Revision ID: b2c3d4e5f6a7
Revises: a1b2c3d4e5f6
"""
from alembic import op
import sqlalchemy as sa

revision = "b2c3d4e5f6a7"
down_revision = "a1b2c3d4e5f6"


def upgrade() -> None:
    # 1. 添加新列
    op.add_column("users", sa.Column("first_name", sa.String(100), nullable=True))
    op.add_column("users", sa.Column("last_name", sa.String(100), nullable=True))

    # 2. 数据迁移：拆分 name 到 first_name 和 last_name
    op.execute("""
        UPDATE users SET
            first_name = SPLIT_PART(name, ' ', 1),
            last_name = CASE
                WHEN POSITION(' ' IN name) > 0 THEN SUBSTRING(name FROM POSITION(' ' IN name) + 1)
                ELSE ''
            END
    """)

    # 3. 设置 NOT NULL
    op.alter_column("users", "first_name", nullable=False)

    # 4. 删除旧列
    op.drop_column("users", "name")


def downgrade() -> None:
    op.add_column("users", sa.Column("name", sa.String(200), nullable=True))
    op.execute("UPDATE users SET name = first_name || ' ' || last_name")
    op.alter_column("users", "name", nullable=False)
    op.drop_column("users", "last_name")
    op.drop_column("users", "first_name")
```

```bash
# 迁移操作命令
# 创建迁移（自动检测模型变更）
alembic revision --autogenerate -m "add_agent_table"

# 人工审查后执行升级
alembic upgrade head

# 回滚一步
alembic downgrade -1

# 回滚到指定版本
alembic downgrade a1b2c3d4e5f6

# 查看当前版本
alembic current

# 查看迁移历史
alembic history --verbose
```

**要点**：
- autogenerate 只检测表结构变更，不会自动生成数据迁移逻辑——字段拆分、数据填充等必须手动编写
- 每个迁移脚本必须有 `downgrade` 函数——没有回滚能力的迁移是定时炸弹
- 常见错误：直接在生产数据库上 `ALTER TABLE` 而不用迁移工具——无法追溯变更历史，回滚时只能手动修数据

### 练习 2

**思路**：备份策略的核心是"自动备份 + 定期验证 + 保留策略"。用 cron 定时执行 `pg_dump`，压缩后存储到独立目录。备份不做恢复测试等于没备份——必须定期在测试环境演练完整恢复流程。保留策略按"最近 7 天每天 + 最近 4 周每周"保留。

**答案**：

```bash
#!/bin/bash
# scripts/backup.sh —— PostgreSQL 自动备份脚本

set -euo pipefail

# 配置
BACKUP_DIR="/backups/postgres"
RETENTION_DAYS=7
RETENTION_WEEKS=28
COMPOSE_PROJECT="ai-agent-platform"
DB_USER="${POSTGRES_USER:-agent}"
DB_NAME="${POSTGRES_DB:-agent_platform}"
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="$BACKUP_DIR/backup_${DATE}.sql.gz"

# 创建备份目录
mkdir -p "$BACKUP_DIR"

echo "[$(date)] 开始备份 $DB_NAME..."

# 执行备份并压缩
docker compose -p "$COMPOSE_PROJECT" exec -T postgres \
    pg_dump -U "$DB_USER" -d "$DB_NAME" --format=custom --compress=6 \
    > "$BACKUP_FILE"

# 验证备份文件
FILE_SIZE=$(stat -f%z "$BACKUP_FILE" 2>/dev/null || stat -c%s "$BACKUP_FILE")
if [ "$FILE_SIZE" -lt 1024 ]; then
    echo "[ERROR] 备份文件太小（${FILE_SIZE} bytes），可能备份失败"
    rm -f "$BACKUP_FILE"
    exit 1
fi

echo "[$(date)] 备份完成: $BACKUP_FILE ($(du -h "$BACKUP_FILE" | cut -f1))"

# 清理旧备份：保留最近 N 天的每日备份
find "$BACKUP_DIR" -name "backup_*.sql.gz" -mtime +$RETENTION_DAYS -delete

# 保留每周一的备份（更长期）
WEEKLY_DIR="$BACKUP_DIR/weekly"
mkdir -p "$WEEKLY_DIR"
if [ "$(date +%u)" = "1" ]; then
    cp "$BACKUP_FILE" "$WEEKLY_DIR/"
fi
find "$WEEKLY_DIR" -name "backup_*.sql.gz" -mtime +$RETENTION_WEEKS -delete

echo "[$(date)] 清理完成"
```

恢复脚本：

```bash
#!/bin/bash
# scripts/restore.sh —— PostgreSQL 恢复脚本

set -euo pipefail

if [ -z "${1:-}" ]; then
    echo "用法: $0 <备份文件路径>"
    echo "示例: $0 /backups/postgres/backup_20250101_030000.sql.gz"
    exit 1
fi

BACKUP_FILE="$1"
DB_USER="${POSTGRES_USER:-agent}"
DB_NAME="${POSTGRES_DB:-agent_platform}"
COMPOSE_PROJECT="ai-agent-platform"

if [ ! -f "$BACKUP_FILE" ]; then
    echo "[ERROR] 备份文件不存在: $BACKUP_FILE"
    exit 1
fi

echo "========================================="
echo "警告：此操作将覆盖当前数据库 $DB_NAME 的所有数据！"
echo "备份文件: $BACKUP_FILE"
echo "========================================="
read -p "确认恢复？(输入 yes 继续): " confirm
if [ "$confirm" != "yes" ]; then
    echo "已取消"
    exit 0
fi

echo "[$(date)] 开始恢复..."

# 停止后端服务（避免写入）
docker compose -p "$COMPOSE_PROJECT" stop backend

# 删除并重建数据库
docker compose -p "$COMPOSE_PROJECT" exec -T postgres \
    psql -U "$DB_USER" -c "DROP DATABASE IF EXISTS $DB_NAME;"
docker compose -p "$COMPOSE_PROJECT" exec -T postgres \
    psql -U "$DB_USER" -c "CREATE DATABASE $DB_NAME;"

# 恢复数据
docker compose -p "$COMPOSE_PROJECT" exec -T postgres \
    pg_restore -U "$DB_USER" -d "$DB_NAME" --no-owner --no-acl < "$BACKUP_FILE"

# 重启后端
docker compose -p "$COMPOSE_PROJECT" start backend

echo "[$(date)] 恢复完成"
```

Cron 配置：

```bash
# crontab -e
# 每天凌晨 3 点自动备份
0 3 * * * /app/scripts/backup.sh >> /var/log/backup.log 2>&1
```

**要点**：
- 备份文件必须验证大小——太小说明 `pg_dump` 可能失败了（空输出）
- 恢复前必须停止写入服务——否则恢复过程中有新数据写入会导致数据不一致
- 常见错误：备份做了但从不测试恢复——直到真正需要恢复时才发现备份文件损坏或命令有误。至少每月做一次恢复演练

## 常见误区

| 错误 | 原因 | 解决 |
|------|------|------|
| 迁移失败 | 模型和数据库不一致 | 先检查 diff，再执行 |
| 备份文件损坏 | 没验证备份 | 定期测试恢复 |
| 连接池耗尽 | 连接没归还 | 用 async with session |

## 工程建议

备份不做恢复测试等于没备份——至少每月做一次完整的恢复演练。Alembic 迁移脚本生成后务必人工审查，自动生成的 diff 可能遗漏数据迁移或错误删除列。连接池参数需要根据实际并发量调优，`pool_size` 设太大会耗尽数据库连接，设太小会排队等待，建议从 20 起步并监控连接使用率。

## 本节要点

- Alembic 迁移让数据库版本可控
- 定期备份是数据安全的最后防线
- 连接池配置影响系统并发能力
