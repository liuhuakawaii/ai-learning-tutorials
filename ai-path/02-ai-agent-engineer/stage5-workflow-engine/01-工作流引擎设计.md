# 01 工作流引擎设计

> 工作流引擎是 AI 平台的"大脑"——让复杂的 AI 任务变得可编排、可复用、可监控。

你正在开发 AI 客服平台，产品经理说："用户发消息时，先用 LLM 分析意图，再根据意图调不同工具（查订单、退款、转人工），最后生成回复。"如果用硬编码实现，每次调整流程都要改代码。当流程变复杂——加入并行查询、条件分支、人工审批——代码会变成意大利面。你需要一个可视化的流程编排系统。

## 为什么是 DAG

工作流的本质是一个有向无环图（DAG）：节点是执行单元，边是数据流。

```
[用户输入] → [意图分类] → [条件判断]
                              ↓
                    ┌─── 产品咨询 → [知识库检索] → [生成回复]
                    ├─── 订单查询 → [查订单系统] → [生成回复]
                    └─── 投诉 → [创建工单] → [转人工]
```

为什么是"无环"？因为环意味着死循环——节点 A 的输出是节点 B 的输入，B 的输出又是 A 的输入。工作流必须有明确的终止条件。

## 数据模型

用 Pydantic 定义工作流的数据结构：

```python
from enum import Enum
from pydantic import BaseModel

class NodeType(str, Enum):
    INPUT = "input"          # 接收用户输入
    LLM = "llm"              # 调用大模型
    TOOL = "tool"            # 调用工具
    CONDITION = "condition"  # 条件分支
    HUMAN = "human"          # 人工审批
    PARALLEL = "parallel"    # 并行执行
    OUTPUT = "output"        # 输出结果

class NodeConfig(BaseModel):
    id: str
    type: NodeType
    label: str
    config: dict       # 节点特定配置（LLM 的 prompt、条件的 expression 等）
    position: dict     # 画布位置 {x, y}

class Edge(BaseModel):
    id: str
    source: str              # 源节点 ID
    target: str              # 目标节点 ID
    source_handle: str | None = None  # 条件分支用：true/false

class WorkflowDefinition(BaseModel):
    id: str
    name: str
    nodes: list[NodeConfig]
    edges: list[Edge]
    variables: dict = {}     # 全局变量
    version: int = 1
```

节点类型决定了执行逻辑：LLM 节点调大模型，工具节点调外部 API，条件节点根据表达式选择分支。边决定了执行顺序。

## DAG 验证

保存工作流时必须验证 DAG 合法性，不能等到执行时才发现问题：

```python
from collections import deque, defaultdict

def validate_workflow(workflow: WorkflowDefinition) -> list[str]:
    errors = []
    node_ids = {n.id for n in workflow.nodes}
    
    # 1. 检测环路（Kahn 拓扑排序）
    in_degree = {nid: 0 for nid in node_ids}
    adj = defaultdict(list)
    for edge in workflow.edges:
        adj[edge.source].append(edge.target)
        in_degree[edge.target] += 1
    
    queue = deque(nid for nid, deg in in_degree.items() if deg == 0)
    visited = 0
    while queue:
        current = queue.popleft()
        visited += 1
        for neighbor in adj[current]:
            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)
    
    if visited < len(node_ids):
        cycle_nodes = [nid for nid, deg in in_degree.items() if deg > 0]
        errors.append(f"检测到环路，涉及节点: {cycle_nodes}")
    
    # 2. 检测孤立节点
    connected = set()
    for edge in workflow.edges:
        connected.add(edge.source)
        connected.add(edge.target)
    isolated = node_ids - connected
    if isolated:
        errors.append(f"存在孤立节点: {isolated}")
    
    # 3. 检测 INPUT/OUTPUT 节点
    inputs = [n for n in workflow.nodes if n.type == NodeType.INPUT]
    outputs = [n for n in workflow.nodes if n.type == NodeType.OUTPUT]
    if len(inputs) != 1:
        errors.append(f"INPUT 节点数量应为 1，当前 {len(inputs)}")
    if len(outputs) != 1:
        errors.append(f"OUTPUT 节点数量应为 1，当前 {len(outputs)}")
    
    return errors
```

Kahn 算法的核心：统计每个节点的入度，从入度为 0 的节点开始遍历。如果遍历完的节点数 < 总节点数，说明剩余节点构成环路。

## 节点配置差异化

不同节点类型的配置差异大。LLM 节点需要 model 和 prompt，条件节点需要 expression，工具节点需要 tool_name。用 Pydantic 的 discriminated union 让每种节点有独立的 Config 模型：

```python
from typing import Literal, Annotated
from pydantic import Field

class LLMNodeConfig(BaseModel):
    type: Literal["llm"] = "llm"
    model: str = "gpt-4o"
    prompt_template: str
    temperature: float = 0.7

class ConditionNodeConfig(BaseModel):
    type: Literal["condition"] = "condition"
    expression: str  # 如 "score > 0.8"
    true_label: str = "是"
    false_label: str = "否"

NodeConfig = Annotated[
    LLMNodeConfig | ConditionNodeConfig | ...,
    Field(discriminator="type"),
]
```

这样反序列化时 Pydantic 会根据 `type` 字段自动路由到正确的 Config 类，而不是把所有配置塞进一个 `config: dict`。

## 关键判断

- **先定义数据模型，再实现编辑器和执行引擎。** 模型设计决定后续扩展性——节点类型要可扩展，不能把所有配置塞进 dict。
- **DAG 验证要前置。** 保存时就检测环路、孤立节点、缺失的输入输出，不要等执行时才发现。
- **版本管理从第一天就要做。** 工作流定义变更时需要支持回滚——线上跑的工作流不能因为一次编辑就挂掉。
