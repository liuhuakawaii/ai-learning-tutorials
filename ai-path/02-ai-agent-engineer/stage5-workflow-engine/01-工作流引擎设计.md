# 01 工作流引擎设计

> 工作流引擎是 AI 平台的"大脑"——让复杂的 AI 任务变得可编排、可复用、可监控。

## 场景引入

你正在开发一个 AI 客服平台，产品经理提出一个需求：当用户发送消息时，先用 LLM 分析意图，再根据意图类型调用不同的工具（查订单、退款、转人工），最后生成回复。如果用硬编码实现，每次调整流程都要改代码、测试、上线。当流程变复杂——加入并行查询、条件分支、人工审批——代码会变成一团意大利面。你需要一个可视化的流程编排系统，让非开发人员也能拖拽配置工作流，这就是工作流引擎存在的意义。

## 学习目标

- 理解 DAG（有向无环图）工作流模型
- 设计节点类型和边的语义
- 理解工作流执行模型

## 核心概念

### DAG 模型

```python
# backend/app/workflow/models.py
from enum import Enum
from pydantic import BaseModel

class NodeType(str, Enum):
    LLM = "llm"                    # LLM 调用节点
    TOOL = "tool"                  # 工具调用节点
    CONDITION = "condition"        # 条件分支节点
    HUMAN = "human"                # 人工审批节点
    PARALLEL = "parallel"          # 并行执行节点
    INPUT = "input"                # 输入节点
    OUTPUT = "output"              # 输出节点

class NodeConfig(BaseModel):
    """节点配置"""
    id: str
    type: NodeType
    label: str
    config: dict                   # 节点特定配置
    position: dict                 # 画布位置 {x, y}

class Edge(BaseModel):
    """边（连接线）"""
    id: str
    source: str                    # 源节点 ID
    target: str                    # 目标节点 ID
    source_handle: str | None = None  # 源端口（条件分支用）
    label: str | None = None

class WorkflowDefinition(BaseModel):
    """工作流定义"""
    id: str
    name: str
    description: str
    nodes: list[NodeConfig]
    edges: list[Edge]
    variables: dict = {}           # 全局变量
    version: int = 1
```

### 节点类型定义

| 节点类型 | 功能 | 输入 | 输出 |
|----------|------|------|------|
| INPUT | 接收用户输入 | 用户消息 | 文本 |
| LLM | 调用大模型 | Prompt + 变量 | AI 回复 |
| TOOL | 调用工具 | 参数 | 工具结果 |
| CONDITION | 条件判断 | 条件表达式 | true/false 分支 |
| HUMAN | 人工审批 | 待审批内容 | 审批结果 |
| PARALLEL | 并行执行 | 多个分支 | 聚合结果 |
| OUTPUT | 输出结果 | 最终结果 | 返回给用户 |

## 练习

### 练习 1：模型设计

用 Pydantic 定义完整的工作流模型：

1. 节点配置（各类型的特定配置）
2. 边的定义（包括条件分支的 handle）
3. 工作流定义（包含变量和版本）

### 练习 2：DAG 验证

实现 DAG 验证逻辑：

1. 检测环路
2. 检测孤立节点
3. 检测缺失的输入/输出节点

## 参考答案

### 练习 1

**思路**：各节点类型共享基础字段（id、type、label、position），但配置差异大（LLM 节点需要 model 和 prompt，条件节点需要 expression）。用 Pydantic 的 discriminated union 让每种节点有独立的 Config 模型，边需要支持条件分支的 source_handle。

**答案**：

```python
from __future__ import annotations
from enum import Enum
from typing import Any, Literal, Annotated
from pydantic import BaseModel, Field


class NodeType(str, Enum):
    INPUT = "input"
    LLM = "llm"
    TOOL = "tool"
    CONDITION = "condition"
    HUMAN = "human"
    PARALLEL = "parallel"
    OUTPUT = "output"


class InputNodeConfig(BaseModel):
    type: Literal["input"] = "input"
    variable_name: str = "user_input"
    description: str = ""


class LLMNodeConfig(BaseModel):
    type: Literal["llm"] = "llm"
    model: str = "gpt-4o"
    prompt_template: str
    temperature: float = 0.7
    max_tokens: int = 2000


class ToolNodeConfig(BaseModel):
    type: Literal["tool"] = "tool"
    tool_name: str
    params_mapping: dict[str, str] = {}


class ConditionNodeConfig(BaseModel):
    type: Literal["condition"] = "condition"
    expression: str
    true_label: str = "是"
    false_label: str = "否"


class HumanNodeConfig(BaseModel):
    type: Literal["human"] = "human"
    approval_message: str
    timeout_minutes: int = 60
    on_timeout: str = "reject"


class ParallelNodeConfig(BaseModel):
    type: Literal["parallel"] = "parallel"
    branch_ids: list[str] = []
    wait_all: bool = True


class OutputNodeConfig(BaseModel):
    type: Literal["output"] = "output"
    format: str = "text"
    variable_ref: str = ""


NodeConfig = Annotated[
    InputNodeConfig | LLMNodeConfig | ToolNodeConfig | ConditionNodeConfig
    | HumanNodeConfig | ParallelNodeConfig | OutputNodeConfig,
    Field(discriminator="type"),
]


class Edge(BaseModel):
    id: str
    source: str
    target: str
    source_handle: str | None = None
    label: str | None = None


class WorkflowDefinition(BaseModel):
    id: str
    name: str
    description: str = ""
    nodes: list[NodeConfig]
    edges: list[Edge]
    variables: dict[str, Any] = {}
    version: int = 1
```

**要点**：
- 用 `Literal` 类型字段 + `discriminator` 实现 Pydantic 的 discriminated union，反序列化时自动路由到正确的 Config 类
- 常见错误：把所有节点配置塞进一个 `config: dict`，丢失了类型校验能力，前端也无法根据 schema 自动生成表单
- `source_handle` 是条件分支的关键——同一个条件节点有 true/false 两个出口，靠 handle 区分

### 练习 2

**思路**：DAG 验证分三步——拓扑排序检测环路（Kahn 算法）、集合运算找孤立节点、遍历节点类型检测是否有且仅有 1 个 INPUT 和 1 个 OUTPUT。

**答案**：

```python
from collections import deque, defaultdict
from app.workflow.models import WorkflowDefinition, NodeType


class WorkflowValidationError(Exception):
    def __init__(self, errors: list[str]):
        self.errors = errors
        super().__init__("; ".join(errors))


def validate_workflow(workflow: WorkflowDefinition) -> list[str]:
    errors: list[str] = []
    node_ids = {node.id for node in workflow.nodes}

    # 1. 检测环路（Kahn 拓扑排序）
    in_degree: dict[str, int] = {nid: 0 for nid in node_ids}
    adj: dict[str, list[str]] = defaultdict(list)
    for edge in workflow.edges:
        if edge.source not in node_ids or edge.target not in node_ids:
            errors.append(f"边 {edge.id} 引用了不存在的节点: source={edge.source}, target={edge.target}")
            continue
        adj[edge.source].append(edge.target)
        in_degree[edge.target] += 1

    queue = deque(nid for nid, deg in in_degree.items() if deg == 0)
    visited_count = 0
    while queue:
        current = queue.popleft()
        visited_count += 1
        for neighbor in adj[current]:
            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)

    if visited_count < len(node_ids):
        cycle_nodes = [nid for nid, deg in in_degree.items() if deg > 0]
        errors.append(f"检测到环路，涉及节点: {cycle_nodes}")

    # 2. 检测孤立节点
    connected_nodes: set[str] = set()
    for edge in workflow.edges:
        connected_nodes.add(edge.source)
        connected_nodes.add(edge.target)
    isolated = node_ids - connected_nodes
    if isolated:
        errors.append(f"存在孤立节点（无任何连线）: {isolated}")

    # 3. 检测 INPUT / OUTPUT 节点
    input_nodes = [n for n in workflow.nodes if n.type == NodeType.INPUT]
    output_nodes = [n for n in workflow.nodes if n.type == NodeType.OUTPUT]
    if len(input_nodes) == 0:
        errors.append("缺少 INPUT 节点")
    elif len(input_nodes) > 1:
        errors.append(f"存在多个 INPUT 节点: {[n.id for n in input_nodes]}")
    if len(output_nodes) == 0:
        errors.append("缺少 OUTPUT 节点")
    elif len(output_nodes) > 1:
        errors.append(f"存在多个 OUTPUT 节点: {[n.id for n in output_nodes]}")

    return errors


def validate_or_raise(workflow: WorkflowDefinition):
    errors = validate_workflow(workflow)
    if errors:
        raise WorkflowValidationError(errors)
```

**要点**：
- Kahn 算法通过统计入度检测环路：如果拓扑排序访问的节点数 < 总节点数，说明剩余节点构成环路
- 常见错误：用 DFS 检测环路时只标记 visited 而不区分"在当前路径上"和"之前访问过"，导致误报；或者忽略孤立节点检测，执行引擎遇到无入边的节点时不知道如何触发
- INPUT/OUTPUT 不仅要检测缺失，还要检测重复——多个 INPUT 会导致入口不确定，多个 OUTPUT 会导致结果丢失

## 常见误区

- 认为工作流就是简单的线性步骤串联，忽略了 DAG 中的并行、条件和循环场景
- 在节点配置中硬编码业务参数，导致每次调整都要修改代码重新部署
- 忽略 DAG 验证，不检测环路和孤立节点，导致执行时出现死循环或数据丢失

## 工程建议

- 先定义清晰的节点类型和数据模型，再实现编辑器和执行引擎，模型设计决定后续扩展性
- DAG 验证要前置——在保存工作流时就检测环路、孤立节点、缺失的输入输出节点，而不是执行时才发现
- 节点配置使用 JSON Schema 定义，方便前端自动生成表单和后端校验
- 版本管理要从一开始就做好，工作流定义变更时需要支持回滚和灰度发布

## 本节要点

- 工作流 = DAG（节点 + 边）
- 节点类型决定执行逻辑，边决定执行顺序
- 验证是第一步——不合法的 DAG 不能执行
