## 场景引入

你做了一个 AI 助手帮用户管理邮件。用户说"帮我给项目组发一封进度更新"。AI 理解正确，找到了项目组成员的邮箱，草拟了邮件内容——但邮件里包含了一个还没确认的预算数字。如果 AI 直接发送，这个错误信息就会被五个人同时收到，无法撤回。这就是高风险操作的问题：AI 的理解可能有偏差，但操作的后果是真实且不可逆的。人工确认不是对 AI 的不信任，而是给系统加一道安全阀——在操作执行前，让用户看到 AI 准备做什么，确认无误后再执行。

### 3.2 确认管理器

```typescript
// lib/confirmation-manager.ts
class ConfirmationManager {
  private pending = new Map<string, {
    resolve: (response: ConfirmationResponse) => void
    timeout: NodeJS.Timeout
  }>()

  async requestConfirmation(
    request: ConfirmationRequest
  ): Promise<ConfirmationResponse> {
    return new Promise((resolve, reject) => {
      // 设置超时
      const timeout = setTimeout(() => {
        this.pending.delete(request.id)
        resolve({ confirmed: false, reason: '确认超时' })
      }, request.timeout || 60000)  // 默认 60 秒

      this.pending.set(request.id, { resolve, timeout })

      // 觉醒前端显示确认对话框
      this.notifyFrontend(request)
    })
  }

  respond(id: string, response: ConfirmationResponse) {
    const pending = this.pending.get(id)
    if (!pending) return

    clearTimeout(pending.timeout)
    this.pending.delete(id)
    pending.resolve(response)
  }

  private notifyFrontend(request: ConfirmationRequest) {
    // 通过 WebSocket 或 SSE 通知前端
    // 实际实现取决于你的架构
  }
}

export const confirmationManager = new ConfirmationManager()
```

### 3.3 在 Agent 中集成确认

```typescript
// 在执行工具前检查是否需要确认
async function executeTool(
  toolName: string,
  args: any,
  agentId: string
): Promise<ToolResult> {
  const tool = toolRegistry.get(toolName)
  if (!tool) {
    return { success: false, error: `工具 ${toolName} 不存在` }
  }

  // 检查是否需要确认
  if (tool.requiresConfirmation) {
    const confirmationId = `confirm-${Date.now()}`

    const response = await confirmationManager.requestConfirmation({
      id: confirmationId,
      toolName: tool.name,
      toolDescription: tool.description,
      args,
      riskLevel: tool.riskLevel || 'medium',
      riskDescription: tool.confirmationMessage?.(args) || `确定要执行 ${toolName} 吗？`,
    })

    if (!response.confirmed) {
      return {
        success: false,
        error: `用户取消了操作: ${response.reason || '用户拒绝'}`,
      }
    }

    // 如果用户修改了参数
    if (response.modifiedArgs) {
      args = { ...args, ...response.modifiedArgs }
    }
  }

  // 执行工具
  return await toolRegistry.execute(toolName, args)
}
```

// 在聊天组件中使用
function ChatWithConfirmation() {
  const [confirmationRequest, setConfirmationRequest] = useState<ConfirmationRequest | null>(null)

  // 监听确认请求
  useEffect(() => {
    const eventSource = new EventSource('/api/confirmation/events')

    eventSource.onmessage = (event) => {
      const request = JSON.parse(event.data)
      setConfirmationRequest(request)
    }

    return () => eventSource.close()
  }, [])

  const handleConfirm = async (modifiedArgs?: Record<string, any>) => {
    if (!confirmationRequest) return

    await fetch('/api/confirmation/respond', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        id: confirmationRequest.id,
        confirmed: true,
        modifiedArgs,
      }),
    })

    setConfirmationRequest(null)
  }

  const handleCancel = async (reason?: string) => {
    if (!confirmationRequest) return

    await fetch('/api/confirmation/respond', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({
        id: confirmationRequest.id,
        confirmed: false,
        reason,
      }),
    })

    setConfirmationRequest(null)
  }

  return (
    <div>
      {/* 聊天界面 */}

      {confirmationRequest && (
        <ConfirmationDialog
          request={confirmationRequest}
          onConfirm={handleConfirm}
          onCancel={handleCancel}
        />
      )}
    </div>
  )
}

## 参考答案

### 练习一：识别高风险操作

**思路**：按操作的可逆性和影响范围分级。不可逆操作（发送、删除、支付）是高风险，需要确认；可逆操作（查询、读取）是低风险，直接执行。

**答案**：

**1. 写入操作（需要确认）**
- 发送邮件/消息：发送后不可撤回，且可能涉及多人
- 提交表单/创建记录：可能触发后续业务流程（如创建订单后自动扣款）
- 上传/覆盖文件：覆盖已有文件会导致原数据丢失

**2. 删除操作（需要二次确认）**
- 删除数据库记录：关联数据可能级联删除
- 删除文件/目录：文件恢复困难，尤其是批量删除
- 清空数据：影响范围大，需要明确提示"将删除 N 条数据"

**3. 涉及敏感数据的操作（需要确认 + 权限校验）**
- 查询他人个人信息：涉及隐私，需要权限校验
- 共享/导出数据：数据可能流出安全边界
- 修改用户权限：影响系统安全

**不需要确认的操作（低风险）**
- 搜索知识库、查询天气、读取公开数据——只读操作，不修改任何数据
- 计算、格式转换、文本生成——纯计算/生成，无副作用

**要点**：
- 判断标准：操作是否可逆 × 影响范围大小。不可逆 + 大范围 = 必须确认
- "需要确认"和"需要权限校验"是两个独立维度，不能互相替代
- 常见错误：所有操作都要确认——用户会养成"无脑点确认"的习惯，真正高风险的确认反而被忽略

### 练习二：实现确认流程

**思路**：确认流程的核心是：工具注册时标记 `requiresConfirmation`，执行前检查标记并暂停，通过确认管理器与前端通信，用户响应后恢复或终止。

**答案**：

// 2. 实现确认管理器
interface ConfirmationRequest {
  id: string
  toolName: string
  toolDescription: string
  args: Record<string, any>
  riskLevel: 'low' | 'medium' | 'high'
  riskDescription: string
  timeout: number
  createdAt: Date
}

interface ConfirmationResponse {
  confirmed: boolean
  modifiedArgs?: Record<string, any>
  reason?: string
}

class ConfirmationManager {
  private pending = new Map<string, {
    resolve: (response: ConfirmationResponse) => void
    timeout: NodeJS.Timeout
    request: ConfirmationRequest
  }>()

  async requestConfirmation(request: ConfirmationRequest): Promise<ConfirmationResponse> {
    return new Promise((resolve) => {
      const timeout = setTimeout(() => {
        this.pending.delete(request.id)
        resolve({
          confirmed: false,
          reason: `确认超时（${request.timeout / 1000} 秒未响应），操作已自动取消`,
        })
      }, request.timeout)

      this.pending.set(request.id, { resolve, timeout, request })

      // 通知前端（通过 SSE/WebSocket）
      this.emitToClient('confirmation:request', request)
    })
  }

  respond(id: string, response: ConfirmationResponse): void {
    const pending = this.pending.get(id)
    if (!pending) return

    clearTimeout(pending.timeout)
    this.pending.delete(id)
    pending.resolve(response)
  }

  getPendingRequests(): ConfirmationRequest[] {
    return Array.from(this.pending.values()).map(p => p.request)
  }

  private emitToClient(event: string, data: any) {
    // 实际实现中通过 SSE/Socket.io 推送给前端
    console.log(`[SSE] ${event}:`, JSON.stringify(data, null, 2))
  }
}

export const confirmationManager = new ConfirmationManager()

**要点**：
- `confirmationMessage` 函数根据参数动态生成人类可理解的确认描述，比"确定要执行 send_message 吗？"有用得多
- 确认管理器用 Promise 模式——`requestConfirmation` 返回 Promise，用户确认后 resolve，超时后 reject
- 前端确认框必须显示操作详情（收件人、内容预览），不能只显示工具名
- 常见错误：确认框只有"确认"和"取消"两个按钮，没有"查看详情"——用户不知道自己在确认什么

### 练习三：测试超时

**思路**：超时机制防止 Agent 永久阻塞。测试需要验证：超时后状态正确转换、用户收到超时提示、操作被安全取消（而非自动执行）。

**答案**：

// 测试超时行为
async function testConfirmationTimeout() {
  const manager = new ConfirmationManager()

  // 发起一个 10 秒超时的确认请求
  const request: ConfirmationRequest = {
    id: `confirm-${Date.now()}`,
    toolName: 'send_message',
    toolDescription: '发送消息',
    args: { to: ['张三'], content: '会议提醒', channel: 'email' },
    riskLevel: 'high',
    riskDescription: '即将发送邮件给张三，内容：会议提醒',
    timeout: 10000, // 10 秒超时
    createdAt: new Date(),
  }

  console.log(`[${new Date().toISOString()}] 发起确认请求，超时时间: ${request.timeout / 1000}秒`)
  console.log('等待用户响应...')

  // 不调用 manager.respond()，模拟用户不操作
  const response = await manager.requestConfirmation(request)

  console.log(`[${new Date().toISOString()}] 收到响应:`)
  console.log('  confirmed:', response.confirmed)  // false
  console.log('  reason:', response.reason)          // "确认超时（10秒未响应），操作已自动取消"

  // 验证：超时后操作被取消，而非自动执行
  console.assert(response.confirmed === false, '超时后应自动取消')
  console.assert(response.reason?.includes('超时'), '原因应包含超时说明')
  console.log('✅ 测试通过：超时后自动取消操作')
}

**要点**：
- 超时后必须默认取消（cancel），绝不能默认执行（proceed）——这是安全设计的底线
- 超时时间要合理：太短用户来不及看，太长 Agent 长时间阻塞浪费资源。建议 30-60 秒
- 超时后要从 pending 队列中移除请求，避免内存泄漏
- 常见错误：超时后默认执行高风险操作——用户没看到确认框就自动发送了邮件，这比没有确认机制更糟糕
- 常见错误：只测超时不测正常确认——需要覆盖三种场景：正常确认、用户取消、超时自动取消

---

## 常见误区

1. **所有工具都要用户确认**：如果每个工具调用都弹确认框，用户会很快点"全部确认"而不看内容，确认流于形式。只对高风险操作（写入、删除、支付、权限）要求确认，低风险操作直接执行。
2. **确认对话框只显示工具名**：`"确定要执行 send_email 吗？"` 对用户毫无帮助。确认框要显示人类可理解的操作描述：收件人是谁、邮件内容是什么、发送后能否撤回。
3. **确认超时后默认执行**：用户 60 秒没响应就自动执行高风险操作，这是危险的设计。超时后应该默认取消，或者通知用户操作已超时未执行。
4. **用户修改参数后不重新校验**：用户在确认框中修改了收件人地址，但新地址格式不合法。修改后的参数必须经过和原始调用相同的校验流程。

---

## 工程建议

1. **按风险等级分级处理**：低风险（如保存笔记）直接执行；中风险（如发送消息）显示确认框但不阻塞页面；高风险（如删除数据、支付）显示模态确认框，必须明确点击确认。
2. **确认框支持"修改后执行"**：用户可能只想改一个参数就执行，而不是取消后重新操作。在确认框中展示可编辑的参数字段，修改后重新校验再执行。
3. **确认请求要有唯一 ID 和过期时间**：每个确认请求生成唯一 ID，设置过期时间（如 60 秒）。过期后自动从待确认队列中移除，避免内存泄漏和误响应。
4. **记录所有确认操作的审计日志**：包括谁确认了什么操作、原始参数是什么、是否修改了参数、确认/取消的决定。这是安全审计和问题追溯的关键数据。

---

## 小结

本课的核心要点：

1. **高风险操作需要确认**：写入、删除、支付、权限操作
2. **确认流程**：暂停 → 显示 → 确认/取消 → 继续/终止
3. **确认管理器**：管理待确认的请求
4. **前端确认 UI**：清晰的风险提示和操作详情
5. **超时处理**：避免无限等待
