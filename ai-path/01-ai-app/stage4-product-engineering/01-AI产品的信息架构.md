# 第1课：AI 产品的信息架构

> **课程定位**：架构决策课——在真实约束下做取舍
> **前置知识**：阶段一到三的全部内容
> **预计时长**：35 分钟

你正在做 Knowledge Workspace 这个产品。现在需要决定一件事：对话、知识库、用户设置这三个模块，在页面上怎么组织？数据模型怎么拆？API 怎么分层？

这些问题看起来是"画个架构图"的事，但每一步都有取舍。选错了，后面改的代价不只是重写代码，还有数据迁移和用户习惯的断裂。

---

## 决策一：对话和知识库是什么关系

最容易犯的错是把对话和知识库当成两个独立模块——对话归对话，知识库归知识库，页面上两个入口互不相干。

这样做的问题是：用户打开一个对话，想让它基于某个知识库回答，你得做一个"关联"操作。这个关联放在哪里？放在对话创建的时候？放在对话设置里？放在知识库详情页里？

每多一个关联入口，就多一个需要同步的状态。对话关联了知识库 A，但知识库 A 刚被删除了，这时候对话页面怎么显示？用户在对话中途切换了知识库，之前的上下文还有效吗？

更好的做法是把知识库作为对话的一个配置项，而不是一个独立实体：

```typescript
interface Conversation {
  id: string
  userId: string
  title: string
  model: string
  systemPrompt?: string
  knowledgeBaseId?: string  // 可选关联，不是必选
  createdAt: Date
}
```

`knowledgeBaseId` 是可选的。没有关联知识库的对话就是纯聊天，关联了就有 RAG 能力。这样一个对话的完整上下文（模型、prompt、知识库）都在一个地方，不需要跨模块查询。

但这个决策有代价：如果你想让用户在知识库详情页看到"哪些对话正在使用这个知识库"，就需要反向查询。这时候需要在 KnowledgeBase 上维护一个引用计数或者做反向索引。这就是取舍——正向查询简单了，反向查询复杂了。

## 决策二：消息要不要拆表

对话和消息是一对多关系，这没有争议。争议在于：消息内部的结构要不要进一步拆分？

一条 assistant 消息可能包含：

```typescript
interface Message {
  id: string
  conversationId: string
  role: 'user' | 'assistant' | 'system' | 'tool'
  content: string
  toolCalls?: ToolCall[]      // 工具调用记录
  citations?: Citation[]      // RAG 引用
  tokenUsage?: { prompt: number; completion: number }
  createdAt: Date
}
```

`toolCalls` 和 `citations` 都是内嵌的 JSON。这样做查询简单——一条消息的所有信息都在一行里。但如果你需要统计"某个知识库被引用了多少次"或者"哪个工具调用失败率最高"，就需要扫描所有消息的 JSON 字段。

另一个方案是把 toolCalls 和 citations 拆成独立表：

```typescript
interface Citation {
  id: string
  messageId: string
  documentId: string
  chunkId: string
  score: number
}
```

这样统计查询高效了，但每次读取消息都要 JOIN 两张表。

怎么选？看你产品的核心交互是什么。如果用户主要在对话界面操作，很少做跨对话的统计分析，内嵌 JSON 就够了。如果你的产品有"知识库使用分析""工具调用监控"这类功能，拆表是必要的。

Knowledge Workspace 的场景下，初期用内嵌 JSON，等统计需求明确后再拆。过早拆表带来的 JOIN 成本比后期迁移 JSON 字段的成本更隐蔽、更难排查。

## 决策三：页面结构怎么定

AI 产品的页面结构和传统 CRUD 应用最大的区别是：核心操作（对话）是流式的，不是表单提交。

传统应用的页面结构通常是列表→详情→编辑，用户操作的结果是确定的。AI 产品的对话页面是一个持续滚动的流，用户发送一条消息后等待的是一个不确定长度的流式响应。

这意味着对话页面不能用传统的 loading→done 模式，而是需要：

```typescript
// 对话页面的状态模型
type ConversationState =
  | { status: 'idle' }                          // 等待用户输入
  | { status: 'streaming'; partial: string }     // 流式接收中
  | { status: 'complete'; message: Message }     // 接收完成
  | { status: 'error'; error: string }           // 出错
```

这个状态模型比传统表单复杂得多。如果一开始不把它设计清楚，后面加"中断生成""重新生成""继续生成"这些功能时会非常痛苦。

页面结构建议：

```
/chat                    → 对话列表（最近对话、搜索）
/chat/:id                → 对话详情（消息流、输入框、知识库选择器）
/knowledge               → 知识库列表（状态、文档数、最近使用）
/knowledge/:id           → 知识库详情（文档管理、检索测试）
/settings                → 设置（API Key、模型偏好、配额）
```

注意 `/knowledge/:id` 里有一个"检索测试"功能。这不是可有可无的——用户需要在不创建对话的情况下测试知识库的检索效果。这个功能放在知识库详情页比放在对话页面更合理，因为它的目的是调试知识库，不是调试对话。

## 决策四：统计字段放哪里

用户需要看到自己的 token 用量。这个数据可以从 UsageRecord 表聚合计算，但每次打开页面都做一次聚合查询，数据量大了会慢。

另一个方案是在 User 表上维护冗余字段：

```typescript
interface User {
  // ...
  tokenUsed: number       // 当月已用 token
  tokenLimit: number      // 当月配额
}
```

同样，Conversation 上维护 `messageCount` 和 `tokenUsage`，KnowledgeBase 上维护 `documentCount` 和 `chunkCount`。

冗余字段的好处是列表页查询快——不需要 JOIN 和聚合。代价是每次写入消息、上传文档时，需要同步更新这些字段。同步可以通过数据库触发器、应用层事务或者异步消息队列实现。

触发器最可靠但耦合数据库；应用层事务最灵活但有遗漏风险；异步队列最解耦但有延迟。

对于 Knowledge Workspace 这个规模的产品，应用层事务是合理选择。代码在你手里，出问题排查也方便。等产品规模大到需要分库分表时，再考虑异步队列。

## 决策五：API 要不要区分读写模型

传统 REST API 用 GET 读、POST/PUT/DELETE 写，这没问题。但 AI 产品的对话消息接口有一个特殊需求：流式响应。

```typescript
// 普通 REST：同步请求-响应
POST /api/conversations/:id/messages
// → 返回完整 JSON

// 流式响应：SSE
POST /api/conversations/:id/messages
// → Content-Type: text/event-stream
// → data: {"token": "你"}
// → data: {"token": "好"}
// → data: [DONE]
```

如果一开始把消息接口设计成同步 JSON 响应，后面改成流式需要同时改前端的请求逻辑和响应处理逻辑。两套逻辑并存的维护成本很高。

建议从第一天就用 SSE 流式响应。前端用 `fetch` + `ReadableStream` 消费，不用 `EventSource`（因为 `EventSource` 只支持 GET，不支持 POST 带 body）。

这个决策的代价是调试变复杂——流式响应在浏览器 DevTools 里不如 JSON 好查看。可以用一个独立的 `/api/conversations/:id/messages?stream=false` 参数来支持调试模式下的同步响应。

## 练习

### 练习一：设计你的实体关系

为 Knowledge Workspace 画出 User、Conversation、Message、KnowledgeBase、Document、Chunk、UsageRecord 的实体关系图。标注每个实体的主键、外键和关键冗余字段。用 Mermaid 或手绘都可以。

### 练习二：处理一个边界场景

用户在对话进行到一半时删除了关联的知识库。设计这个操作的前后端处理流程：前端怎么提示？后端怎么处理进行中的对话？已生成的消息里的引用怎么显示？

## 参考答案

### 练习一

核心关系：

- User 1:N Conversation（一个用户有多个对话）
- Conversation 1:N Message（一个对话有多条消息）
- Conversation N:1 KnowledgeBase（可选关联）
- KnowledgeBase 1:N Document（一个知识库有多篇文档）
- Document 1:N Chunk（一篇文档拆成多个块）
- User 1:N UsageRecord（使用记录）

冗余字段：Conversation 上维护 `messageCount`、`tokenUsage`；KnowledgeBase 上维护 `documentCount`、`chunkCount`；User 上维护 `tokenUsed`。

### 练习二

一种合理的处理方式：

- 前端：删除知识库时弹出确认框，提示"有 N 个对话正在使用此知识库，删除后这些对话将失去知识库能力"
- 后端：删除知识库时，将关联对话的 `knowledgeBaseId` 设为 null，不删除对话本身
- 已生成消息中的引用：保留引用文本，但标注"来源文档已删除"。不要悄悄删除引用，那会让用户困惑"为什么之前的回答有引用，现在没了"
