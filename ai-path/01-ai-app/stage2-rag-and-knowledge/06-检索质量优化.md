# 第6课：检索质量优化——从一个失败案例开始排查

> **前置知识**：第 4-5 课的向量检索和引用
> **预计时长**：40 分钟

## 用户投诉了

你的 RAG 系统测试时效果不错，但上线后收到反馈：

> "我问'怎么退货'，AI 回答的是退换货须知的开头部分，真正的退货流程反而没出来。"

你去分析日志，发现两个问题：
1. 用户的问题太简短（"怎么退货"），和文档中的表述（"商品退货退款流程"）有语义鸿沟
2. 向量检索找到了大致相关的文档，但排序不对——最相关的排在了后面

这不是模型的问题，是检索的问题。下面一步步排查和修复。

## 第一步：看检索结果

在修复之前，先看清问题。给检索函数加上日志：

```typescript
async function retrieveWithLogging(query: string, topK: number = 5) {
  const queryEmbedding = await getEmbedding(query)
  const results = await store.search(queryEmbedding, topK)

  console.log(`查询: "${query}"`)
  console.log(`Top ${topK} 结果:`)
  results.forEach((r, i) => {
    console.log(`  ${i + 1}. [${r.similarity.toFixed(4)}] ${r.content.slice(0, 80)}...`)
  })

  return results
}
```

跑一下，你可能会看到：

```
查询: "怎么退货"
Top 5 结果:
  1. [0.8234] 购买须知：所有商品均为正品保证，收到商品后请立即检查...
  2. [0.8156] 退换货须知：本店支持7天无理由退换货...
  3. [0.8012] 商品退货退款流程：第一步登录账户，进入订单详情...
  4. [0.7890] 售后服务：提供7x24小时在线客服...
  5. [0.7654] 联系我们：客服电话 400-xxx-xxxx...
```

最相关的"商品退货退款流程"排在第 3 位。如果 TopK=3，它刚好被包含；但如果 TopK=2，它就被截断了。

## 第二步：Query Rewrite——扩展查询

用户说"怎么退货"，太简短了。可以让模型先把它扩展成更完整的查询：

```typescript
async function rewriteQuery(originalQuery: string): Promise<string> {
  const response = await openai.responses.create({
    model: 'gpt-5.5',
    input: [
      {
        role: 'system',
        content: '将用户的简短查询改写为更完整、更适合搜索的形式。保持原始意图不变，添加相关同义词。只输出改写后的查询，不要解释。'
      },
      { role: 'user', content: originalQuery }
    ],
    temperature: 0.3,
    max_output_tokens: 100,
  })
  return response.output_text || originalQuery
}

// "怎么退货" → "如何申请商品退货退款，需要什么条件和流程"
```

改写后的查询包含更多关键词（"退货""退款""条件""流程"），和文档的匹配概率更高。

**代价**：每次查询多调用一次 LLM，延迟增加 500ms-1s。对于实时问答场景，可以只在查询太短（< 5 个字）时才启用改写。

## 第三步：Rerank——重排序

向量检索是粗排——它用 embedding 的余弦相似度衡量语义接近程度，但这个衡量不够精细。Rerank 是精排——用更精细的模型重新评估每个结果与查询的相关性。

```typescript
async function rerank(
  query: string,
  documents: { content: string; metadata: any }[],
  topK: number = 3
) {
  const documentList = documents
    .map((doc, i) => `[${i + 1}] ${doc.content.slice(0, 300)}`)
    .join('\n\n')

  const response = await openai.responses.create({
    model: 'gpt-5.5',
    input: [
      {
        role: 'system',
        content: '评估每个文档与查询的相关性。输出 JSON: {"rankings": [{"index": 1, "relevance": 0.95}, ...]}。relevance 范围 0-1。'
      },
      {
        role: 'user',
        content: `查询：${query}\n\n文档列表：\n${documentList}`
      }
    ],
    text: { format: { type: 'json_object' } },
    temperature: 0,
  })

  const result = JSON.parse(response.output_text || '{"rankings":[]}')
  return result.rankings
    .sort((a: any, b: any) => b.relevance - a.relevance)
    .slice(0, topK)
    .map((r: any) => documents[r.index - 1])
}
```

Rerank 后，"商品退货退款流程"可能会排到第 1 位——因为它和"怎么退货"的语义关联最强。

**代价**：Rerank 用 LLM 成本较高。高频场景应该用专用 Rerank 模型（如 Cohere Rerank），成本低一个数量级。

## 第四步：混合检索——向量 + 关键词

向量检索擅长语义匹配，但对精确关键词（产品型号、错误码、API 名称）的匹配不如关键词检索。混合检索兼顾两者：

```typescript
async function hybridSearch(
  query: string,
  documents: Document[],
  options: { topK?: number; vectorWeight?: number; keywordWeight?: number } = {}
) {
  const { topK = 5, vectorWeight = 0.7, keywordWeight = 0.3 } = options

  // 向量检索分数
  const queryEmbedding = await getEmbedding(query)
  const vectorScores = documents.map(doc =>
    cosineSimilarity(queryEmbedding, doc.embedding)
  )

  // 关键词检索分数（简化版 BM25）
  const queryTerms = query.toLowerCase().split(/\s+/)
  const keywordScores = documents.map(doc => {
    const content = doc.content.toLowerCase()
    let score = 0
    for (const term of queryTerms) {
      const matches = content.match(new RegExp(term, 'gi'))
      if (matches) score += matches.length
    }
    return Math.min(score / (queryTerms.length * 10), 1)
  })

  // 合并分数
  return documents
    .map((doc, i) => ({
      document: doc,
      score: vectorScores[i] * vectorWeight + keywordScores[i] * keywordWeight,
    }))
    .sort((a, b) => b.score - a.score)
    .slice(0, topK)
}
```

权重（0.7:0.3）没有万能值。如果你的文档中专有名词多（产品名、错误码），关键词权重应该更高。

## 优化的优先级

不要一上来就加 Rerank 和混合检索。检索优化的优先级是：

1. **先改 chunk 策略**——如果 chunk 切得不好，后面加再多优化都是治标不治本
2. **再加 query rewrite**——成本低，效果明显，特别是用户查询普遍较短时
3. **最后上 rerank**——成本高，但在粗排效果已经不错的基础上，rerank 能进一步提升

每一步都要用评测数据验证效果，不要凭感觉。

## 建立评测集

优化检索不能靠"感觉还行"。准备一个评测集：

```typescript
const testCases = [
  { query: '怎么退货', expectedChunks: ['商品退货退款流程'] },
  { query: '退款要多久', expectedChunks: ['退款流程', '审核通过后5个工作日'] },
  { query: '定制商品能退吗', expectedChunks: ['特殊情况', '定制商品不支持退款'] },
]
```

每条包含查询和期望检索到的 chunk。每次调整策略后跑一遍评测集，用命中率和平均排名衡量效果。

50-100 条评测样本能覆盖大部分常见问题。太小（< 10 条）结论不可靠，太大维护成本高。

## 参考答案

Query Rewrite 改写时要保持原始意图不变，不能引入不相关的同义词。过度扩展查询反而会检索到无关内容。

Rerank 的关键判断：向量检索是粗排，Rerank 是精排。先用向量检索缩小候选集（top 20），再用 Rerank 精排取 top 3-5。直接用大模型在全量数据上做 Rerank 成本太高。

**常见错误**：只看整体指标不分析失败案例。平均命中率 90% 看起来不错，但可能有 10% 的查询完全检索不到。逐条分析失败案例，找到共性问题（特定类型的查询、特定领域的文档），才能针对性优化。
