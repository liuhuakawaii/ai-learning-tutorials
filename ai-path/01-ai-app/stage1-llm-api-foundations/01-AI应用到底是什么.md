# 第1课：AI 应用到底是什么

> **前置知识**：有 React / TypeScript / HTTP 基础
> **预计时长**：20 分钟

## 从一个最小调用开始

先跑起来，再讨论它是什么。

```typescript
import OpenAI from 'openai'
const openai = new OpenAI()

const response = await openai.responses.create({
  model: 'gpt-5.5',
  input: [{ role: 'user', content: '用一句话解释什么是 RAG' }],
})

console.log(response.output_text)
```

5 行代码，一次 API 调用，模型返回了一段文字。

如果你觉得"AI 应用不过如此"，那这个故事值得读完：一个前端工程师接到需求"给产品加个 AI 功能"，他用同样的方式接了 ChatGPT API。上线后用户反馈三个问题——回答不引用公司文档、记不住上一轮说了什么、偶尔编造不存在的功能。老板问："这和直接用 ChatGPT 有什么区别？"

区别在哪？往下看。

## "调 API"和"做产品"之间差了什么

刚才那 5 行代码，模型只能凭自己的训练数据回答。它不知道你们公司的文档，不能搜索实时信息，不记得你上一句话说了什么，也没法帮你保存笔记。

一个能上线的 AI 应用，至少需要这五层：

| 层 | 做什么 | 为什么不能省 |
|---|---|---|
| **Prompt** | 定义模型的角色、能力边界和输出格式 | 没有约束的模型会随意发挥 |
| **上下文** | 把检索到的知识、历史对话注入给模型 | 模型不知道你公司的私有文档 |
| **模型** | 理解上下文，生成回答 | 这是唯一的"大脑" |
| **工具** | 让模型能搜索、查数据库、保存文件 | 模型自己只能生成文本 |
| **状态** | 记住会话历史、用户偏好、任务进度 | 没有状态，每次对话都是陌生人 |

用前端开发来类比：Prompt 是组件的 props + 模板，上下文是全局状态，模型是渲染引擎，工具是 API 调用，状态是 localStorage。你不会把一个只有渲染引擎的应用交给用户——AI 应用也一样。

## 一个真实的 AI 应用在做什么

假设你用一个 AI 知识工作台，上传了 3 份产品文档，然后问："我们的登录流程有哪些安全要求？"

系统内部发生了这些事：

1. **理解意图**——用户在问安全要求，不是问登录流程本身
2. **检索知识库**——从 3 份文档中找到 5 个相关片段
3. **组装上下文**——把检索到的片段 + 用户问题 + 系统指令拼成 Prompt
4. **调用模型**——发送给 GPT-4，等待生成回答
5. **后处理**——添加引用来源、检查敏感信息、记录日志

"调用模型"只是第 4 步。前面有意图理解、知识检索，后面有后处理和引用。这门课要带你做的，就是这条完整链路。

## AI 应用和传统 Web 应用的关键差异

传统应用的输出是确定的：输入 `2 + 2`，永远输出 `4`。AI 应用的输出是概率性的：同一个问题问三次，措辞可能不同，偶尔还会出错。

这意味着几件事：

- **测试方式不同**——不能用 `expect(output).toBe(expected)` 测试 AI 输出，需要用评估指标衡量质量
- **成本模型不同**——传统应用是固定服务器成本，AI 应用按 token 计费，用多少花多少，一个 bug 可能导致账单爆炸
- **错误模式不同**——传统应用的错误是 code bug，AI 应用的错误是幻觉、偏见、格式错误
- **迭代方式不同**——改代码不够，还要改 Prompt、改检索策略、改评估标准

这些差异会贯穿整门课。

## 这门课要做什么

课程用一个贯穿项目——**AI Knowledge Workspace（个人知识工作台）**——把所有知识点串起来：

- 上传 PDF / Markdown 文档，建立知识库
- 基于文档的问答，带引用来源
- 工具调用：保存笔记、生成任务
- 流式输出、会话管理、配额限制
- 评估集、日志追踪、成本统计

每个阶段都会在同一个项目上添加功能，而不是每节课写一个独立 demo。你最终会得到一个可运行、可迭代的 AI 产品，而不是一堆散落的代码片段。

## 五个核心概念的直觉

在后续课程中，你会反复遇到这五个概念。这里先给一个直觉，后续每节课会深入展开。

**Prompt 不只是"写个提示词"**。它定义了模型是谁、能做什么、不能做什么、输出什么格式。一个好的 System Prompt 应该像给新同事写的岗位说明书——角色、能力范围、行为约束、输出格式。

**上下文是 AI 应用的核心竞争力**。模型不知道你公司的文档、你上传的资料、你之前的对话。把这些信息注入到上下文中，是让 AI 应用区别于"直接用 ChatGPT"的关键。

**工具让模型从"能说"变成"能做"**。模型只能生成文本，但它可以通过调用工具来搜索、计算、读写文件、调用 API。工具调用的设计（schema、错误处理、人工确认）是 Agent 的基础。

**状态让 AI 应用从"一次性"变成"连续"**。会话历史、用户偏好、任务进度——没有状态管理，每次对话都是一张白纸。

**评估让你知道改动是变好了还是变差了**。传统应用改了代码跑单元测试就行，AI 应用改了 Prompt 需要跑评估集，用数据判断效果。

## 练习

### 练习一：拆解一个你用过的 AI 产品

选择一个你常用的 AI 产品（如 ChatGPT、Cursor、Perplexity），按五个核心组成（Prompt、上下文、模型、工具、状态）分析它：

1. 它的 Prompt 可能包含什么？（角色、格式、约束）
2. 它的"上下文"来自哪里？（你的输入、搜索结果、文件内容）
3. 它调用了哪些"工具"？（搜索、代码执行、文件读取）
4. 它维护了什么"状态"？（对话历史、用户偏好）

## 参考答案

### 练习一

以 **Cursor** 为例：

**Prompt**：角色定义（专业编程助手）、能力范围（TypeScript/React/Python）、行为约束（不编造不存在的 API）、输出格式（Markdown，代码块标注语言）。

**上下文**：当前打开的文件内容（自动注入）、选中的代码片段、项目中的其他文件（通过 @file 引用或自动检索）、终端输出的错误信息、对话历史。

**工具**：代码搜索、文件读写、终端执行、Git 操作、网络搜索。

**状态**：当前对话历史、用户偏好设置（模型选择、主题）、项目索引状态、每个文件的编辑历史。

**关键判断**：不要把 Cursor 简单理解为"嵌入 IDE 的 ChatGPT"。它的核心差异在上下文注入（自动感知当前文件和项目结构）和工具调用（直接修改代码、执行命令），而不是聊天本身。
