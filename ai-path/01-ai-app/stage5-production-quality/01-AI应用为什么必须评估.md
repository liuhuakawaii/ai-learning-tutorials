# 第1课：AI 应用为什么必须评估

> **课程定位**：直接跑第一次评估，从结果中理解为什么需要评估
> **前置知识**：阶段一到四的全部内容
> **预计时长**：25 分钟

你优化了 Knowledge Workspace 的检索策略，改了几个参数，本地测试几个问题感觉效果不错，于是上线了。三天后用户反馈"回答变长了但不准确了"。你回头看日志，发现没有任何对比数据——改之前是什么水平、改之后变好了还是变差了，完全不知道。

这节课不讲理论。我们直接在 Knowledge Workspace 里跑一次评估，然后从结果里理解为什么这件事不能跳过。

---

## 先准备一个最小评估集

在 `ai-knowledge-workspace-kit` 项目里，创建一个评估用例文件。不需要很多，5 条就够：

```json
// evals/cases.json
[
  {
    "id": "basic-fact",
    "question": "这个项目的向量数据库用的是什么？",
    "expectedKeywords": ["pgvector", "PostgreSQL"],
    "type": "factual"
  },
  {
    "id": "how-to",
    "question": "如何添加一个新的文档到知识库？",
    "expectedKeywords": ["upload", "ingest", "chunk"],
    "type": "procedural"
  },
  {
    "id": "refusal",
    "question": "这个项目的创始人是谁？",
    "expectedBehavior": "refuse",
    "type": "refusal"
  },
  {
    "id": "retrieval-quality",
    "question": "embedding 用的什么模型？维度是多少？",
    "expectedKeywords": ["embedding", "dimension"],
    "type": "factual"
  },
  {
    "id": "edge-case",
    "question": "如果文档内容是空的会怎样？",
    "expectedKeywords": ["empty", "error", "skip"],
    "type": "edge"
  }
]
```

5 条用例覆盖了三种场景：事实性问答、操作指引、拒答。这就是评估集的最小形态——不需要完美，但需要覆盖你系统的主要行为模式。

## 写一个评估脚本

```typescript
// evals/run-eval.ts
import { readFile } from 'fs/promises'
import { searchKnowledgeBase } from '../src/retrieval'
import { generateAnswer } from '../src/generation'

interface EvalCase {
  id: string
  question: string
  expectedKeywords?: string[]
  expectedBehavior?: string
  type: string
}

interface EvalResult {
  id: string
  passed: boolean
  score: number
  details: string
}

async function runEval(case_: EvalCase): Promise<EvalResult> {
  const searchResults = await searchKnowledgeBase({
    query: case_.question,
    limit: 5,
    minScore: 0.7,
  })

  const answer = await generateAnswer({
    question: case_.question,
    context: searchResults,
  })

  // 规则评估：关键词命中
  if (case_.expectedKeywords) {
    const hits = case_.expectedKeywords.filter(kw =>
      answer.text.toLowerCase().includes(kw.toLowerCase())
    )
    const score = hits.length / case_.expectedKeywords.length
    return {
      id: case_.id,
      passed: score >= 0.5,
      score,
      details: `命中 ${hits.length}/${case_.expectedKeywords.length} 个关键词`,
    }
  }

  // 规则评估：拒答检查
  if (case_.expectedBehavior === 'refuse') {
    const refused = /无法(找到|回答|确定)|资料中(没有|未找到)|抱歉/.test(answer.text)
    return {
      id: case_.id,
      passed: refused,
      score: refused ? 1 : 0,
      details: refused ? '正确拒答' : '应该拒答但没有',
    }
  }

  return { id: case_.id, passed: false, score: 0, details: '未匹配任何评估规则' }
}

async function main() {
  const cases: EvalCase[] = JSON.parse(
    await readFile('evals/cases.json', 'utf-8')
  )

  console.log(`运行 ${cases.length} 条评估用例...\n`)

  const results: EvalResult[] = []
  for (const c of cases) {
    const result = await runEval(c)
    results.push(result)
    const icon = result.passed ? '✅' : '❌'
    console.log(`${icon} [${result.id}] ${result.details} (score: ${result.score})`)
  }

  const passed = results.filter(r => r.passed).length
  console.log(`\n总计: ${passed}/${results.length} 通过`)
}

main()
```

运行它：

```bash
npx tsx evals/run-eval.ts
```

你会看到类似这样的输出：

```
运行 5 条评估用例...

✅ [basic-fact] 命中 2/2 个关键词 (score: 1)
✅ [how-to] 命中 2/3 个关键词 (score: 0.67)
❌ [refusal] 应该拒答但没有 (score: 0)
✅ [retrieval-quality] 命中 2/2 个关键词 (score: 1)
❌ [edge-case] 命中 0/3 个关键词 (score: 0)

总计: 3/5 通过
```

## 从结果里看问题

3/5 通过，看起来还行？仔细看两个失败的用例：

**refusal 用例失败**：用户问"这个项目的创始人是谁"，系统没有拒答，而是编了一个答案。这是幻觉——知识库里没有这个信息，系统不应该回答。如果你的评估集没有这条用例，你永远不会发现这个问题，直到用户投诉。

**edge-case 用例失败**：用户问"如果文档内容是空的会怎样"，系统给出了回答但没有命中任何关键词。可能回答是正确的但措辞不同，也可能回答是错的。这说明纯关键词匹配的评估方式有局限——它能检测"有没有提到"，但检测不了"说的对不对"。

这就是为什么需要评估：

1. **你以为没问题的改动，可能有隐藏问题**。检索策略改了几个参数，本地测试几个问题感觉不错——但你的样本量太小，覆盖不了边界场景。
2. **没有评估就没有对比基线**。这次跑出来 3/5，下次改了 Prompt 跑出来 2/5，你知道变差了。如果没有这次的基线，下次的 2/5 你可能觉得"还行"。
3. **评估集本身就是对系统的理解**。写评估用例的过程就是在思考"我的系统应该会什么、不应该会什么"。不写评估集，这些边界情况永远存在于你的盲区里。

---

## 关键词匹配够吗

上面的评估用的是关键词匹配——检查回答里有没有出现期望的词。这只能做最粗粒度的检查。

更精确的评估方式有两种：

**模型评估**：用另一个 LLM 来判断回答是否正确。把问题、上下文、回答一起发给评估模型，让它打分。优点是能理解语义，缺点是有成本和延迟。

**人工评估**：你自己看每条回答，判断对不对。优点是最准确，缺点是慢、不可规模化。

实际项目中三种方式都会用到。规则评估做第一层快速过滤（关键词、长度、格式），模型评估做第二层语义判断，人工抽检做最终校验。后面的课程会展开模型评估和人工评估的具体实现。

## 参考答案

### 练习一

参考用例：

```json
{
  "id": "citation-check",
  "question": "这个项目支持哪些文档格式？",
  "expectedKeywords": ["pdf", "markdown", "txt"],
  "type": "citation"
}
```

```json
{
  "id": "multi-step",
  "question": "如果我要用 OpenAI 的 embedding 模型，需要改哪些配置？",
  "expectedKeywords": ["embedding", "model", "config"],
  "type": "reasoning"
}
```

```json
{
  "id": "out-of-scope",
  "question": "这个项目怎么部署到 Kubernetes？",
  "expectedBehavior": "refuse",
  "type": "refusal"
}
```

常见错误：把"超出范围"的问题写成期望有答案——如果你的知识库里没有部署文档，系统应该拒答而不是编造部署步骤。

### 练习二

```typescript
async function modelEval(question: string, context: string, answer: string): Promise<number> {
  const response = await fetch('https://api.openai.com/v1/chat/completions', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${process.env.OPENAI_API_KEY}`,
    },
    body: JSON.stringify({
      model: 'gpt-4o-mini',
      temperature: 0,
      messages: [
        {
          role: 'system',
          content: '你是评估专家。判断回答是否基于上下文、没有编造。返回 0-1 的分数，JSON 格式。',
        },
        {
          role: 'user',
          content: `问题：${question}\n\n上下文：${context}\n\n回答：${answer}\n\n返回 {"faithfulness": 0-1}`,
        },
      ],
      response_format: { type: 'json_object' },
    }),
  })
  const data = await response.json()
  return JSON.parse(data.choices[0].message.content).faithfulness
}
```

关键词匹配和模型评估的典型差异：关键词匹配漏掉的用例（回答正确但措辞不同），模型评估通常能正确识别。反过来，关键词匹配通过的用例（回答包含关键词但逻辑错误），模型评估也能发现问题。
