# 第1课：AI 应用为什么必须评估

> **课程定位**：理解评估在 AI 产品中的核心地位
> **前置知识**：阶段一到四的全部内容
> **预计时长**：30 分钟

## 场景引入

你的团队上线了一个基于 RAG 的企业知识库助手。上线第一周，用户反馈"回答质量还不错"。第二周，一位工程师优化了检索策略，希望提升召回率。上线后，陆续有用户反馈"回答变长了但不准确了""引用的文档对不上"。你翻遍了日志，发现没有任何对比数据——改之前是什么水平、改之后变好了还是变差了，完全不知道。这时候你才意识到：AI 应用没有评估体系，每次改动都像蒙眼飞刀。

---

## 学习目标

完成本课学习后，你将能够：

1. 理解 AI 应用为什么需要评估
2. 区分传统测试和 AI 评估的差异
3. 设计评估维度
4. 建立评估意识

## 一、传统测试 vs AI 评估

### 1.1 核心差异

```
传统应用测试：
  输入：2 + 2
  期望输出：4
  实际输出：4
  结果：✅ 通过

  输入相同 → 输出一定相同 → 可以用断言测试

AI 应用评估：
  输入："总结这篇文章"
  期望：涵盖 3 个要点
  实际输出 1："文章讨论了 A、B、C..."
  实际输出 2："本文主要探讨了 C、B、A..."
  实际输出 3："作者提出了三个观点..."

  输入相同 → 输出可能不同 → 不能用断言，需要用评估
```

### 1.2 为什么 AI 输出不确定

```
┌─────────────────────────────────────────────────────────────────┐
│                AI 输出不确定的原因                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 温度参数                                                    │
│     temperature > 0 时，每次输出可能不同                          │
│                                                                 │
│  2. 采样策略                                                    │
│     模型从概率分布中采样，不是确定性输出                          │
│                                                                 │
│  3. 上下文差异                                                  │
│     检索到的文档不同，输出也不同                                  │
│                                                                 │
│  4. 模型版本                                                    │
│     模型更新后，同样的输入可能得到不同的输出                      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 二、为什么必须评估

### 2.1 不评估的风险

```
不评估会怎样？

  场景 1：你修改了 System Prompt
    → 不知道改好了还是改坏了
    → 上线后用户投诉才发现问题

  场景 2：你更新了检索策略
    → 不知道召回率是否提升
    → 可能反而降低了回答质量

  场景 3：你切换了模型
    → 不知道新模型是否适合你的场景
    → 可能出现新的幻觉问题

  场景 4：你部署了新版本
    → 不知道是否引入了 bug
    → 线上故障才发现
```

### 2.2 评估的价值

```
┌─────────────────────────────────────────────────────────────────┐
│                    评估的价值                                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  质量保障                                                        │
│  ├── 上线前验证质量                                              │
│  ├── 发现潜在问题                                                │
│  └── 防止回归                                                    │
│                                                                 │
│  迭代依据                                                        │
│  ├── A/B 测试对比                                                │
│  ├── 量化改进效果                                                │
│  └── 指导优化方向                                                │
│                                                                 │
│  信任建立                                                        │
│  ├── 用户信任：有数据支撑                                        │
│  ├── 团队信任：有质量保证                                        │
│  └── 管理信任：有可度量的指标                                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 三、评估维度

### 3.1 RAG 系统的评估维度

```
┌─────────────────────────────────────────────────────────────────┐
│                    RAG 评估维度                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  检索质量                                                        │
│  ├── 召回率（Recall）：相关文档是否被检索到                       │
│  ├── 精确率（Precision）：检索到的文档是否相关                    │
│  └── 排序质量：最相关的是否排在前面                               │
│                                                                 │
│  生成质量                                                        │
│  ├── 忠实度（Faithfulness）：回答是否基于检索结果                 │
│  ├── 相关性（Relevancy）：回答是否与问题相关                     │
│  └── 完整性（Completeness）：回答是否涵盖所有信息                │
│                                                                 │
│  引用质量                                                        │
│  ├── 准确性：引用来源是否正确                                    │
│  ├── 可追溯性：用户能否找到原文                                  │
│  └── 有用性：引用是否帮助理解                                    │
│                                                                 │
│  安全性                                                          │
│  ├── 拒答能力：对不知道的问题是否拒答                            │
│  ├── 幻觉率：编造信息的比例                                      │
│  └── 敏感信息：是否泄露敏感内容                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 评估指标定义

```typescript
interface EvalMetrics {
  // 检索指标
  recall: number        // 召回率：检索到的相关文档 / 所有相关文档
  precision: number     // 精确率：相关文档 / 检索到的所有文档
  mrr: number           // 平均倒数排名：第一个相关结果的位置

  // 生成指标
  faithfulness: number  // 忠实度：回答基于检索结果的比例
  relevancy: number     // 相关性：回答与问题相关的比例
  completeness: number  // 完整性：回答涵盖信息的比例

  // 安全指标
  refusalRate: number   // 拒答率：对不知道的问题拒答的比例
  hallucinationRate: number  // 幻觉率：编造信息的比例
}
```

## 参考答案

### 练习一

**思路**：传统测试和 AI 评估的核心差异在于输出确定性。传统测试输入相同则输出相同，可以用断言；AI 输出具有多样性，需要用评估指标衡量质量范围而非精确匹配。

**答案**：

| 维度 | 传统测试 | AI 评估 |
|------|----------|---------|
| 输入输出关系 | 输入相同 → 输出一定相同 | 输入相同 → 输出可能不同 |
| 测试方法 | 断言（assertEqual） | 评估（评分、指标） |
| 通过标准 | 精确匹配预期值 | 满足质量阈值（如相关性 > 0.7） |
| 测试工具 | Jest、pytest 等测试框架 | 评估集 + 模型评估器 + 人工抽检 |
| 失败原因 | 代码 bug | Prompt 设计、检索质量、模型能力 |
| 回归检测 | 单元测试自动发现 | 需要专门的评估流水线 |

**要点**：
- AI 评估不是"通过/不通过"的二元判断，而是"在多大程度上满足标准"的连续评分
- 评估需要覆盖多种行为模式（回答、拒答、澄清），不能只测"回答正确"这一种
- 常见错误：用传统测试思维做 AI 评估，把期望答案写成精确匹配字符串，导致评估结果波动大、无意义

### 练习二

**思路**：评估维度应围绕 RAG 系统的核心能力设计，分为检索质量、生成质量、安全性三个层面。每个维度用 0-1 连续分量化，设置合理的合格阈值。

**答案**：

评估维度设计：

| 维度 | 指标 | 量化方式 | 合格阈值 |
|------|------|----------|----------|
| 检索质量 | 召回率 | 检索到的相关文档 / 所有相关文档 | ≥ 0.8 |
| 检索质量 | 精确率 | 相关文档 / 检索到的所有文档 | ≥ 0.7 |
| 生成质量 | 忠实度 | 回答基于检索结果的比例 | ≥ 0.9 |
| 生成质量 | 相关性 | 回答与问题相关的程度 | ≥ 0.8 |
| 生成质量 | 完整性 | 回答涵盖必要信息的比例 | ≥ 0.7 |
| 安全性 | 拒答能力 | 对不知道的问题拒答的比例 | ≥ 0.95 |
| 安全性 | 幻觉率 | 编造信息的比例 | ≤ 0.05 |

**要点**：
- 忠实度和拒答能力是最重要的维度——幻觉和不拒答会直接损害用户信任
- 用 0-1 连续分而非布尔值，能更精确地反映质量变化
- 常见错误：只关注"回答是否正确"，忽略拒答能力——用户问了文档里没有的问题，系统编了一个答案，这比不回答更糟糕

### 练习三

**思路**：任何可能影响输出质量的变更都应该触发评估。按变更类型分类，每种场景对应不同的评估重点。

**答案**：

需要评估的场景：

1. **修改 Prompt 后**：评估重点是生成质量（忠实度、相关性、完整性）和安全性（拒答能力）。Prompt 的微小改动可能导致回答风格、拒答阈值发生显著变化。

2. **更新检索策略后**：评估重点是检索质量（召回率、精确率）。新策略可能召回更多文档但精确率下降，导致回答被无关内容干扰。

3. **切换模型后**：评估重点是全维度。不同模型对同一 prompt 的理解不同，可能产生新的幻觉问题或拒答行为变化。

4. **部署新版本后**：评估重点是回归测试——确保新版本不比旧版本差。运行完整评估集，对比前后版本的指标。

5. **知识库内容变更后**：新增或删除文档可能影响检索结果，需要重新评估相关问题的回答质量。

6. **用户反馈质量下降时**：针对反馈的问题类型，定向运行相关评估用例，确认是否是系统性问题。

**要点**：
- 评估不是一次性的，每次可能影响质量的变更都要触发
- 把评估集成到 CI/CD，评估不通过禁止合并代码
- 常见错误：认为"这次改动很小，应该没问题"就跳过评估——小改动可能在边缘场景下产生大影响

---

## 常见误区

1. **用"感觉还行"代替评估**：开发者的主观判断和真实用户的需求往往存在偏差。你觉得"回答挺好的"，可能是因为你已经知道正确答案。没有量化指标，质量改进就是空谈。

2. **只测"快乐路径"**：只用最简单的问题测试，忽略边界情况和异常输入。上线后用户问了一个稍微复杂的问题，系统就可能给出离谱的回答。

3. **评估一次就够了**：认为上线前跑过一次评估就算完成。实际上，模型更新、Prompt 调整、知识库变更都会影响质量，评估必须持续运行。

4. **只看通过率，不看失败原因**：通过率 90% 看起来不错，但如果失败的 10% 都是同一类问题（比如拒答场景），说明系统存在结构性缺陷，需要针对性优化。

## 工程建议

1. **评估先行**：在写第一行业务代码之前，先定义好评估维度和评估集。没有评估标准的优化就是盲改。

2. **评估集要覆盖四类场景**：事实性问题、引用验证、拒答场景、边界情况。至少准备 20 条评估用例，才能基本覆盖常见问题。

3. **把评估集成到 CI/CD**：每次修改 Prompt 或检索策略后，自动运行评估集。评估不通过，禁止合并代码。

4. **保留历史评估结果**：每次评估的结果都要保存，方便对比不同版本的质量变化。这是回滚决策的重要依据。

---

## 小结

本课的核心要点：

1. **AI 输出不确定**：不能用断言测试，需要用评估
2. **必须评估**：防止质量回归，指导优化方向
3. **评估维度**：检索质量、生成质量、引用质量、安全性
4. **评估流程**：构建评估集 → 运行 → 计算指标 → 分析 → 迭代
