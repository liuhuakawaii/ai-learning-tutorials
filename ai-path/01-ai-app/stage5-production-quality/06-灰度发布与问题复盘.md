# 第6课：灰度发布与问题复盘

> **课程定位**：安全部署和持续改进
> **前置知识**：第 4 课的 Prompt 版本管理
> **预计时长**：35 分钟

## 场景引入

你优化了 RAG 系统的 Prompt，评估集通过率从 88% 提升到了 94%。你很有信心，直接全量上线了。上线后第一天，有 3 个用户反馈"回答变得啰嗦了"。第二天，又有人投诉"引用格式变了，找不到原文"。你不得不紧急回滚，但已经影响了两天的用户体验。如果当时先灰度 5% 流量观察一天，这些问题本来可以在影响范围很小时就被发现。

### 练习一

**思路**：发布检查清单覆盖质量、安全、性能、准备四个维度。每个检查项有明确的通过标准，全部通过才能进入灰度阶段。清单应该是可执行的，不是走形式。

- 常见错误：检查清单走形式，"评估集通过率"写了个"已运行"但没有看具体分数

### 练习三

**思路**：持续改进循环是监控 → 分析 → 改进 → 评估 → 发布的闭环。关键是每个改进措施都要纳入评估集，下次运行评估时自动验证改进是否生效。

**答案**：

```typescript
// lib/improvement/cycle.ts

// 1. 设置监控告警
const ALERT_RULES = [
  { metric: 'error_rate', threshold: 0.05, action: 'slack_alert' },
  { metric: 'refusal_rate', threshold: 0.2, action: 'review_prompt' },
  { metric: 'user_negative_feedback', threshold: 0.1, action: 'sample_review' },
]

// 2. 定期分析数据
export async function weeklyAnalysis() {
  const stats = await getTraceStats('current', 'week')

  const insights: string[] = []

  // 分析错误率趋势
  if (stats.errorRate > 0.03) {
    insights.push(`错误率 ${(stats.errorRate * 100).toFixed(1)}%，需要关注`)
  }

  // 分析成本趋势
  if (stats.avgCostPerRequest > 0.05) {
    insights.push(`平均请求成本 $${stats.avgCostPerRequest.toFixed(4)}，偏高`)
  }

  // 分析失败样本
  const failures = await analyzeFailures('current')
  if (failures.total > 10) {
    insights.push(`本周 ${failures.total} 个失败请求，主要失败阶段: ${Object.keys(failures.byStage).join(', ')}`)
  }

  return insights
}

// 3. 制定优化计划
export async function createOptimizationPlan(insights: string[]) {
  const plan = {
    id: `plan-${Date.now()}`,
    insights,
    actions: [] as { description: string; priority: 'high' | 'medium' | 'low' }[],
  }

  for (const insight of insights) {
    if (insight.includes('错误率')) {
      plan.actions.push({
        description: '分析错误日志，找出高频错误原因',
        priority: 'high',
      })
    }
    if (insight.includes('成本')) {
      plan.actions.push({
        description: '优化 Prompt 长度，考虑使用缓存',
        priority: 'medium',
      })
    }
    if (insight.includes('失败')) {
      plan.actions.push({
        description: '收集失败样本，改进检索策略',
        priority: 'high',
      })
    }
  }

  return plan
}

// 4. 改进后纳入评估集验证
export async function validateImprovement(changeId: string) {
  const evalResult = await runEval()

  // 对比改进前后的评估结果
  const previousResult = await getPreviousEvalResult(changeId)

  return {
    before: previousResult,
    after: evalResult,
    improved: evalResult.passed > previousResult.passed,
    details: {
      relevancyChange: evalResult.scores.avgRelevancy - previousResult.scores.avgRelevancy,
      faithfulnessChange: evalResult.scores.avgFaithfulness - previousResult.scores.avgFaithfulness,
    },
  }
}
```

**要点**：
- 持续改进的关键是闭环：监控发现问题 → 分析根因 → 改进 → 评估验证 → 灰度发布 → 继续监控
- 每个改进措施都要纳入评估集，自动验证改进是否生效
- 常见错误：复盘产出的改进措施没有纳入评估集，下次同类问题还会发生

---

## 常见误区

1. **灰度比例跳跃太大**：从 5% 直接跳到 50%，中间没有过渡。如果 5% 的数据有偏差，50% 会放大问题。应该遵循 5% → 20% → 50% → 100% 的渐进节奏。

2. **灰度期间只看"有没有报错"**：没有报错不等于质量没问题。用户可能在默默忍受低质量回答，只是没有反馈。灰度期间必须对比新旧版本的评估指标。

3. **复盘流于形式**：出了问题写个复盘报告，列几个"改进措施"，然后就没有然后了。复盘的价值在于跟踪落实——每个改进措施必须有负责人、截止日期、验收标准。

4. **只复盘大事故，忽略小问题**：认为"只影响了 3 个用户，不算事故"就不复盘。小问题往往是大事故的前兆。建议建立分级机制，medium 及以上的问题都要做简要复盘。

## 工程建议

1. **灰度发布必须有回滚方案**：在开始灰度之前，确保可以一键回滚到旧版本。回滚不是"改回代码再部署"，而是切换版本开关——秒级生效。

2. **灰度观察期至少 24 小时**：AI 应用的质量问题可能不会立即暴露。用户可能在第二天使用时才发现回答不准确。观察期太短（比如 1 小时）会遗漏时间相关的质量问题。

3. **复盘模板标准化**：每个问题复盘必须包含：问题描述、影响范围、根因分析、时间线、改进措施、经验教训。用统一的模板，方便后续统计分析。

4. **建立"问题 → 改进 → 验证"闭环**：复盘产出的改进措施，必须纳入评估集。下次运行评估时，自动验证改进是否生效。没有闭环的复盘就是浪费时间。

---

## 小结

本课的核心要点：

1. **灰度发布**：小流量 → 扩大 → 全量，逐步验证
2. **发布检查清单**：质量、安全、性能、准备
3. **问题复盘**：发现 → 响应 → 分析 → 改进 → 跟踪
4. **持续改进**：监控 → 分析 → 改进 → 评估 → 发布
5. **经验教训**：每次问题都是学习机会
