# 04 传输层——stdio / SSE / Streamable HTTP 的选型与实现

> MCP 支持多种传输方式。选择合适的传输层是部署的关键。

## 场景引入

你在本地用 stdio 模式开发了一个 MCP Server，跑得好好的。但产品上线时，运维说 Server 必须部署在远程服务器上，客户端通过网络调用。你发现 stdio 根本不支持远程通信，需要换成 SSE 或 Streamable HTTP。可是这两种传输方式有什么区别？SSE 的单向流够用吗？Streamable HTTP 的双向流又该怎么实现？选错传输层，后面改起来成本巨大。

## 一、三种传输方式

```
┌─────────────────────────────────────────────────────────────┐
│                    三种传输方式                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. stdio（标准输入输出）                                     │
│  ├── 通过进程的 stdin/stdout 通信                            │
│  ├── 适用于本地工具                                          │
│  ├── 简单、低延迟                                            │
│  └── 不支持远程调用                                          │
│                                                             │
│  2. SSE（Server-Sent Events）                               │
│  ├── 基于 HTTP 的单向流                                      │
│  ├── 适用于远程服务                                          │
│  ├── 支持流式响应                                            │
│  └── 需要额外的请求通道                                      │
│                                                             │
│  3. Streamable HTTP                                         │
│  ├── 基于 HTTP 的双向流                                      │
│  ├── 适用于远程服务                                          │
│  ├── 支持流式请求和响应                                      │
│  └── 更灵活，但实现复杂                                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 二、stdio 实现

```python
import sys
import json

class StdioTransport:
    """stdio 传输"""
    
    def send(self, message: dict):
        """发送消息"""
        json_str = json.dumps(message)
        sys.stdout.write(json_str + "\n")
        sys.stdout.flush()
    
    def receive(self) -> dict:
        """接收消息"""
        line = sys.stdin.readline()
        return json.loads(line)
```

## 四、传输方式选择

```
选择指南：

本地工具 → stdio
- 简单、低延迟
- 无需网络配置
- 适用于 CLI 工具

远程服务 → SSE
- 支持流式响应
- 基于 HTTP，易于部署
- 适用于 Web 服务

高要求场景 → Streamable HTTP
- 支持双向流
- 更灵活
- 适用于复杂场景
```

## 常见误区

```
误区 1：stdio 只能用于开发环境
  stdio 不仅可以用于开发调试，也是 Claude Desktop 等产品的标准通信方式。
  它延迟低、无需网络配置，非常适合本地工具场景。

误区 2：SSE 和 Streamable HTTP 是同一种东西
  SSE 是单向流（Server → Client），Client 的请求需要走另一个 HTTP 通道。
  Streamable HTTP 是双向流，请求和响应都在同一个连接上完成。

误区 3：选传输层只看功能需求
  传输层的选择还要考虑部署环境、网络拓扑、防火墙策略。
  比如有些企业网络会阻断长连接，SSE 就可能不稳定。

误区 4：切换传输层只需要改一行配置
  不同传输层的消息分帧方式、连接管理、错误恢复机制都不同。
  从 stdio 切换到 SSE 意味着要处理网络断连、重连、心跳等问题。
```

---

## 工程建议

```
1. 本地工具优先选 stdio
   如果 Server 和 Client 在同一台机器上，stdio 是最简单的选择。
   不需要处理网络、端口、CORS 等问题。

2. 远程服务用 SSE，复杂场景用 Streamable HTTP
   SSE 基于 HTTP，部署简单，适合大多数远程场景。
   只有在需要真正的双向流式通信时，才考虑 Streamable HTTP。

3. 做好连接生命周期管理
   无论哪种传输层，都要处理连接建立、保活、断开、重连。
   在 Server 的 shutdown hook 中优雅关闭所有连接。

4. 测试时覆盖网络异常
   用 tc（Linux）或 Network Link Conditioner（macOS）模拟丢包、延迟、断连。
   传输层的健壮性比功能正确性更难测试，也更重要。
```

## 参考答案

### 练习一：实现 stdio 传输层

**思路**：stdio 传输层通过进程的 stdin 接收消息、stdout 发送消息，每条消息以换行符分隔。实现时需要处理消息分帧、JSON 解析、错误恢复。

**答案**：

```python
import sys
import json
import asyncio
from typing import Callable, Awaitable


class StdioServerTransport:
    """基于 stdin/stdout 的 MCP 传输层"""

    def __init__(self):
        self._message_handler: Callable[[dict], Awaitable[dict | None]] | None = None
        self._running = False

    def on_message(self, handler: Callable[[dict], Awaitable[dict | None]]):
        """注册消息处理器"""
        self._message_handler = handler

    async def start(self):
        """启动传输层，持续从 stdin 读取消息"""
        self._running = True
        reader = asyncio.StreamReader()
        await asyncio.get_event_loop().connect_read_pipe(
            lambda: asyncio.StreamReaderProtocol(reader), sys.stdin
        )

        while self._running:
            try:
                line = await reader.readline()
                if not line:
                    break  # stdin 关闭

                message = json.loads(line.decode("utf-8").strip())

                if self._message_handler:
                    response = await self._message_handler(message)
                    if response is not None:
                        self._send(response)

            except json.JSONDecodeError:
                error_response = {
                    "jsonrpc": "2.0",
                    "id": None,
                    "error": {"code": -32700, "message": "Parse error"}
                }
                self._send(error_response)
            except Exception as e:
                print(f"Transport error: {e}", file=sys.stderr)

    def _send(self, message: dict):
        """发送消息到 stdout"""
        json_str = json.dumps(message, ensure_ascii=False)
        sys.stdout.write(json_str + "\n")
        sys.stdout.flush()

    async def stop(self):
        """停止传输层"""
        self._running = False


# 使用示例
async def main():
    transport = StdioServerTransport()

    async def handle_message(message: dict) -> dict | None:
        method = message.get("method")
        if method == "initialize":
            return {
                "jsonrpc": "2.0",
                "id": message["id"],
                "result": {"capabilities": {"tools": {}}}
            }
        elif method == "notifications/initialized":
            return None  # Notification 不返回响应
        return {
            "jsonrpc": "2.0",
            "id": message.get("id"),
            "error": {"code": -32601, "message": f"Method not found: {method}"}
        }

    transport.on_message(handle_message)
    await transport.start()


if __name__ == "__main__":
    asyncio.run(main())
```

**要点**：
- stdin 读取时要用 readline() 按行分帧，每行是一个完整的 JSON 消息
- stdout 输出后必须 flush()，否则消息会留在缓冲区
- Notification 没有 id，处理器返回 None 表示不发送响应
- 常见错误：忘记 flush()，导致消息积压在缓冲区，对端收不到

### 练习二：实现 SSE 传输层

**思路**：SSE 模式下 Server 通过 SSE 端点向 Client 推送消息，Client 通过普通 HTTP POST 发送请求。需要实现两个端点：GET /sse 用于推送，POST /messages 用于接收。

**答案**：

```python
import json
import asyncio
import uuid
from typing import Callable, Awaitable
from fastapi import FastAPI, Request
from sse_starlette.sse import EventSourceResponse
from collections import defaultdict

app = FastAPI()


class SSETransportManager:
    """SSE 传输层管理器"""

    def __init__(self):
        self._sessions: dict[str, asyncio.Queue] = {}
        self._message_handler: Callable | None = None

    def on_message(self, handler: Callable):
        self._message_handler = handler

    def create_session(self) -> str:
        """创建新的 SSE 会话"""
        session_id = str(uuid.uuid4())
        self._sessions[session_id] = asyncio.Queue()
        return session_id

    def get_queue(self, session_id: str) -> asyncio.Queue | None:
        return self._sessions.get(session_id)

    async def handle_request(self, session_id: str, message: dict) -> dict | None:
        """处理客户端发来的请求"""
        if self._message_handler:
            return await self._message_handler(session_id, message)
        return None

    async def send_to_session(self, session_id: str, message: dict):
        """向指定会话发送消息"""
        queue = self._sessions.get(session_id)
        if queue:
            await queue.put(message)

    def remove_session(self, session_id: str):
        self._sessions.pop(session_id, None)


manager = SSETransportManager()


@app.get("/sse")
async def sse_endpoint(session_id: str | None = None):
    """SSE 端点：Server 向 Client 推送消息"""
    if not session_id:
        session_id = manager.create_session()

    queue = manager.get_queue(session_id)
    if not queue:
        session_id = manager.create_session()
        queue = manager.get_queue(session_id)

    async def event_generator():
        try:
            # 先发送 session_id 给客户端
            yield {"event": "session", "data": json.dumps({"session_id": session_id})}

            while True:
                message = await queue.get()
                yield {"data": json.dumps(message, ensure_ascii=False)}
        except asyncio.CancelledError:
            manager.remove_session(session_id)

    return EventSourceResponse(event_generator())


@app.post("/messages")
async def messages_endpoint(request: Request):
    """HTTP POST 端点：接收客户端请求"""
    body = await request.json()
    session_id = request.headers.get("X-Session-Id", "")

    response = await manager.handle_request(session_id, body)
    if response:
        # 通过 SSE 推送响应
        await manager.send_to_session(session_id, response)
        return {"status": "ok"}
    return {"status": "notification_received"}


# 使用示例：uvicorn sse_server:app --host 0.0.0.0 --port 8080
```

**要点**：
- SSE 是单向流（Server → Client），Client 的请求需要走另一个 HTTP POST 通道
- 每个 Client 连接对应一个 SSE 会话，用 session_id 关联请求和响应
- 需要处理连接断开（CancelledError）时清理会话资源
- 常见错误：只实现了 SSE 推送，没有实现 POST 接收端点，导致 Client 无法发送请求

### 练习三：选择传输方式

**思路**：分析不同场景的特点，从部署环境、网络拓扑、性能要求、复杂度等维度选择合适的传输方式。

**答案**：

```
场景分析与传输方式选择：

场景 1：本地 CLI 工具（如代码格式化、本地文件搜索）
  推荐：stdio
  理由：
  - Server 和 Client 在同一台机器上
  - 不需要网络通信
  - 延迟最低（进程间通信）
  - 无需处理网络断连、重连、CORS 等问题

场景 2：团队内部的数据库查询服务
  推荐：SSE
  理由：
  - Server 部署在远程服务器
  - 需要流式返回查询结果
  - 基于 HTTP，部署简单（Nginx 反向代理即可）
  - 防火墙友好（只用标准 HTTP 端口）

场景 3：实时协作编辑（多人同时编辑文档）
  推荐：Streamable HTTP
  理由：
  - 需要真正的双向实时通信
  - Server 需要主动推送变更给所有 Client
  - SSE 的单向流不够用（Client 推送要走另一个通道，延迟高）

场景 4：企业内网的 AI 助手（连接多个内部系统）
  推荐：stdio（本地）+ SSE（远程）
  理由：
  - 本地工具（文件系统、Git）用 stdio，零配置
  - 远程服务（数据库、内部 API）用 SSE，统一 HTTP 入口
  - 混合部署，各取所长

选择决策表：
┌──────────────────┬──────────┬──────────┬──────────────────┐
│  场景特征         │  stdio   │  SSE     │  Streamable HTTP │
├──────────────────┼──────────┼──────────┼──────────────────┤
│  本地部署         │  ✓ 最佳  │  △ 可用  │  △ 可用          │
│  远程部署         │  ✗ 不行  │  ✓ 最佳  │  ✓ 可用          │
│  需要流式响应     │  ✓ 支持  │  ✓ 最佳  │  ✓ 支持          │
│  需要双向实时     │  ✓ 支持  │  △ 需额外│  ✓ 最佳          │
│  防火墙限制       │  N/A     │  ✓ 友好  │  ✓ 友好          │
│  实现复杂度       │  低      │  中      │  高              │
└──────────────────┴──────────┴──────────┴──────────────────┘
```

**要点**：
- 没有"最好"的传输方式，只有"最适合"的
- 选择时要考虑部署环境、网络拓扑、防火墙策略，不只是功能需求
- 切换传输层不只是改一行配置，需要处理连接管理、错误恢复等差异
- 常见错误：开发时用 stdio，上线时才发现需要换成 SSE，改起来成本巨大
