# 02 协议架构——Host / Client / Server 三层模型与消息流

> MCP 的三层架构：Host 管理环境，Client 负责通信，Server 提供能力。

## 场景引入

你在团队里搭建了一个数据库查询的 MCP Server，本以为接入 Claude Desktop 就完事了。结果产品经理说要在 VS Code 里也能用，另一个团队说要在他们的自定义 Web 应用里集成。你发现不同宿主环境对 Client 的管理方式完全不同——有的允许并行连接多个 Server，有的只支持单连接。Host、Client、Server 三层之间到底该怎么分工？消息从用户输入到工具结果返回，中间经过了哪些环节？不搞清楚这些，集成工作就是一团乱麻。

---

## 学习目标

- 深入理解 MCP 的三层架构
- 掌握消息流的完整路径
- 理解各层的职责和交互

## 一、三层架构

```
┌─────────────────────────────────────────────────────────────┐
│                    MCP 三层架构                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Host（宿主）                                                │
│  ├── 运行 AI 应用的环境                                      │
│  ├── 管理 Client 的生命周期                                  │
│  ├── 处理用户交互                                            │
│  └── 例：VS Code、Claude Desktop、自定义应用                  │
│                                                             │
│  Client（客户端）                                            │
│  ├── 与 Server 建立连接                                      │
│  ├── 发现 Server 提供的工具                                  │
│  ├── 发送工具调用请求                                        │
│  └── 处理 Server 返回的结果                                  │
│                                                             │
│  Server（服务端）                                            │
│  ├── 提供工具能力（Tool / Resource / Prompt）                │
│  ├── 处理 Client 的请求                                      │
│  ├── 执行具体的工具逻辑                                      │
│  └── 例：数据库工具、文件系统工具、API 工具                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

---

## 二、消息流

```
完整消息流：

1. 初始化
   Host → Client: 创建 Client 实例
   Client → Server: 建立连接
   Client → Server: 初始化请求（capabilities）
   Server → Client: 初始化响应（capabilities）

2. 工具发现
   Client → Server: tools/list 请求
   Server → Client: 工具列表（名称、描述、参数）

3. 工具调用
   User → Host: 用户请求
   Host → Client: 转发请求
   Client → Server: tools/call 请求
   Server: 执行工具
   Server → Client: 返回结果
   Client → Host: 转发结果
   Host → User: 展示结果
```

## 三、消息格式

```json
// 请求
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "database_query",
    "arguments": {
      "sql": "SELECT * FROM users LIMIT 10"
    }
  }
}

// 响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "[{\"id\": 1, \"name\": \"Alice\"}, ...]"
      }
    ]
  }
}
```

## 四、能力协商

```python
# Client 初始化请求
{
    "capabilities": {
        "tools": {},
        "resources": {"subscribe": true},
        "prompts": {}
    }
}

# Server 初始化响应
{
    "capabilities": {
        "tools": {"listChanged": true},
        "resources": {"subscribe": true},
        "prompts": {}
    }
}
```

## 常见误区

```
误区 1：Host 和 Client 是同一个东西
  Host 是运行环境（如 VS Code），Client 是通信模块。
  一个 Host 可以管理多个 Client，每个 Client 连接一个 Server。

误区 2：Server 只能提供 Tool
  MCP Server 可以同时提供三种原语：Tool（操作）、Resource（数据）、Prompt（模板）。
  根据场景选择合适的原语，不要把所有东西都塞进 Tool。

误区 3：消息流是单向的
  MCP 的消息流是双向的。Server 可以主动发送通知给 Client，
  比如资源变更通知、进度更新等，不只是被动响应请求。

误区 4：能力协商只在初始化时发生一次
  虽然主要协商在初始化时完成，但能力可以动态更新。
  Server 可以通过 notifications/tools/list_changed 通知 Client 工具列表已变更。
```

## 工程建议

```
1. 画出你的消息流图
   在开发之前，先画出从用户输入到工具结果返回的完整消息流。
   这能帮你明确哪些逻辑放在 Host、哪些放在 Client、哪些放在 Server。

2. Host 层做权限控制
   Host 负责管理 Client 生命周期和用户交互，是实施权限控制的最佳位置。
   不要把权限逻辑下沉到 Server，那样每个 Server 都要重复实现。

3. Client 层做错误转换
   Client 应该把 Server 返回的协议级错误转换为对 Host 友好的格式。
   Host 不应该知道 JSON-RPC 错误码的细节。

4. Server 层保持无状态（尽量）
   Server 应该尽量无状态，状态由 Host 或外部系统管理。
   这样 Server 才能水平扩展，支持多实例部署。
```

### 练习二：构造工具调用的请求和响应消息

**思路**：按照 JSON-RPC 2.0 规范构造完整的消息，注意 id 匹配、params 结构、result 格式。

**答案**：

```json
// 场景：调用 database_query 工具，查询活跃用户

// 1. Client → Server：tools/call 请求
{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "database_query",
    "arguments": {
      "sql": "SELECT id, name, email FROM users WHERE status = 'active' LIMIT 10"
    }
  }
}

// 2. Server → Client：成功响应
{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "[{\"id\": 1, \"name\": \"Alice\", \"email\": \"alice@example.com\"}, {\"id\": 2, \"name\": \"Bob\", \"email\": \"bob@example.com\"}]"
      }
    ]
  }
}

// 3. Server → Client：错误响应（SQL 语法错误）
{
  "jsonrpc": "2.0",
  "id": 42,
  "error": {
    "code": -32001,
    "message": "Tool execution failed: SQL syntax error near 'SELEC'"
  }
}

// 4. Server → Client：错误响应（工具不存在）
{
  "jsonrpc": "2.0",
  "id": 42,
  "error": {
    "code": -32601,
    "message": "Method not found: tools/call for 'nonexistent_tool'"
  }
}
```

**要点**：
- 请求的 id 和响应的 id 必须匹配，用于关联请求和响应
- tools/call 的 params 包含两层：name（工具名）和 arguments（工具参数）
- 成功用 result，失败用 error，两者不能同时出现
- 常见错误：把工具参数直接放在 params 顶层，缺少 name/arguments 的嵌套结构

### 练习三：描述完整的消息流

**思路**：按时间顺序梳理从用户输入到结果返回的每一步，标注每个环节的消息类型和方向。

**答案**：

```
完整消息流（用户问"数据库里有多少活跃用户？"）：

阶段 1：初始化（连接建立时执行一次）

  Step 1: Host 创建 Client 实例
    Host → Client: new MCPClient()

  Step 2: Client 连接 Server
    Client → Server: 建立传输层连接（stdio/SSE/HTTP）

  Step 3: 能力协商
    Client → Server: {
      "method": "initialize",
      "params": {
        "capabilities": { "tools": {}, "resources": {} }
      }
    }
    Server → Client: {
      "result": {
        "capabilities": { "tools": { "listChanged": true } }
      }
    }

  Step 4: 初始化完成
    Client → Server: { "method": "notifications/initialized" }

阶段 2：工具发现（初始化后执行一次）

  Step 5: Client 获取工具列表
    Client → Server: { "method": "tools/list" }
    Server → Client: {
      "result": {
        "tools": [
          { "name": "database_query", "description": "执行只读 SQL 查询", ... }
        ]
      }
    }

阶段 3：工具调用（每次用户请求执行）

  Step 6: 用户输入
    User → Host: "数据库里有多少活跃用户？"

  Step 7: Host 将用户消息 + 工具列表发给 AI 模型
    Host → AI: [用户消息, 可用工具列表]

  Step 8: AI 模型决定调用工具
    AI → Host: 调用 database_query(sql="SELECT COUNT(*) FROM users WHERE status='active'")

  Step 9: Host 转发给 Client
    Host → Client: tools/call 请求

  Step 10: Client 发送给 Server
    Client → Server: {
      "method": "tools/call",
      "params": { "name": "database_query", "arguments": { "sql": "..." } }
    }

  Step 11: Server 执行查询
    Server: 执行 SQL，获取结果 [{ "count": 1250 }]

  Step 12: Server 返回结果
    Server → Client: {
      "result": { "content": [{ "type": "text", "text": "[{\"count\": 1250}]" }] }
    }

  Step 13: Client 转发给 Host
    Client → Host: 工具执行结果

  Step 14: Host 将结果交给 AI 生成自然语言
    Host → AI: 工具结果
    AI → Host: "数据库中有 1250 个活跃用户。"

  Step 15: Host 展示给用户
    Host → User: "数据库中有 1250 个活跃用户。"
```

**要点**：
- 初始化和工具发现只在连接建立时执行一次，工具调用每次用户请求都执行
- AI 模型不直接和 Server 通信，所有通信都经过 Host 和 Client 中转
- Server 返回的是原始数据，AI 模型负责将数据转化为自然语言
- 常见错误：认为 AI 直接调用 Server，忽略了 Host/Client 的中转角色
