# 第 1 课：MCP 设计哲学——为什么需要标准化的工具协议

> **课程定位**：理解 MCP 协议的设计动机和核心价值
> **前置知识**：02-ai-agent-engineer-course 的 Function Calling 经验
> **预计时长**：40 分钟

## 场景引入

你正在开发一个 AI 编程助手，需要让它能查询数据库、读写文件、调用内部 API。每个工具都要单独写一套 Function Calling schema、调用逻辑和错误处理。更糟糕的是，当产品从 Claude 迁移到 GPT 平台时，所有工具适配代码都要重写一遍。团队里另一个项目也需要同样的数据库查询工具，但因为代码和当前项目耦合太深，根本无法复用。你开始意识到：AI 工具生态缺少一个像 USB 那样的统一接口标准。

---

## 学习目标

完成本课学习后，你将能够：

1. 用自己的话解释 MCP 是什么以及为什么需要它
2. 说出 MCP 的三层架构（Host / Client / Server）
3. 对比 MCP 与 Function Calling、API Gateway 的差异
4. 判断一个场景是否适合用 MCP 实现

## 一、没有 MCP 的世界

### 1.1 工具集成的痛点

```
场景：你正在开发一个 AI 助手，需要集成以下工具：

  工具 1：查询公司数据库
  工具 2：读写项目文件
  工具 3：调用内部 API
  工具 4：发送 Slack 消息
  工具 5：操作 Jira 工单

没有 MCP 之前，你需要：

  ┌─────────────────────────────────────────────────────────┐
  │  每个工具都要：                                          │
  │                                                         │
  │  1. 写一套 Function Calling schema                      │
  │  2. 写一套调用逻辑                                      │
  │  3. 写一套错误处理                                      │
  │  4. 写一套权限控制                                      │
  │  5. 写一套日志记录                                      │
  │                                                         │
  │  5 个工具 × 5 套代码 = 25 个模块                         │
  │                                                         │
  │  而且：                                                 │
  │  - 每个 AI 平台的 Function Calling 格式不同             │
  │  - 换一个 AI 平台，所有工具都要重写                       │
  │  - 工具不能在其他项目中复用                               │
  │  - 每个工具的质量参差不齐                                 │
  └─────────────────────────────────────────────────────────┘
```

## 二、MCP 的三层架构

```
MCP 协议的三层模型：

┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  Host（宿主）                                            │   │
│  │  运行 AI 应用的环境                                      │   │
│  │  例：VS Code、Claude Desktop、你的 AI 应用               │   │
│  │  职责：管理 Client 生命周期、控制权限                      │   │
│  └─────────────────────────┬───────────────────────────────┘   │
│                            │                                    │
│  ┌─────────────────────────▼───────────────────────────────┐   │
│  │  Client（客户端）                                        │   │
│  │  与 Server 通信的模块                                    │   │
│  │  职责：发现工具、调用工具、处理响应                        │   │
│  │                                                          │   │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐              │   │
│  │  │ 工具发现  │  │ 工具调用  │  │ 结果处理  │              │   │
│  │  └──────────┘  └──────────┘  └──────────┘              │   │
│  └─────────────────────────┬───────────────────────────────┘   │
│                            │                                    │
│  ┌─────────────────────────▼───────────────────────────────┐   │
│  │  Server（服务端）                                        │   │
│  │  提供工具能力的服务                                       │   │
│  │  例：数据库 Server、文件系统 Server、Slack Server         │   │
│  │                                                          │   │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐              │   │
│  │  │  Tool    │  │ Resource │  │ Prompt   │              │   │
│  │  │ (工具)   │  │ (资源)   │  │ (模板)   │              │   │
│  │  └──────────┘  └──────────┘  └──────────┘              │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

通信流程：
  Host 启动 → 创建 Client → Client 连接 Server
  → Client 发现 Server 提供的工具（tools/list）
  → AI 模型决定调用哪个工具
  → Client 发送调用请求（tools/call）
  → Server 执行并返回结果
  → Client 将结果交给 AI 模型
```

## 三、MCP 的三种原语

```
MCP Server 可以提供三种能力：

1. Tool（工具）
   - AI 可以主动调用的操作
   - 类比：函数调用
   - 例：query_database(sql), send_email(to, body)

2. Resource（资源）
   - AI 可以读取的数据
   - 类比：REST API 的 GET 端点
   - 例：db://tables, file:///path/to/file

3. Prompt Template（提示模板）
   - Server 端管理的可复用 Prompt
   - 类比：函数模板
   - 例：sql-template(table, columns)

三者的关系：
┌─────────────────────────────────────────────┐
│  Tool    = AI 可以"做"什么（动作）           │
│  Resource = AI 可以"看"什么（数据）          │
│  Prompt   = AI 可以"用"什么（模板）          │
└─────────────────────────────────────────────┘
```

## 四、MCP vs 其他方案

```
┌─────────────────┬──────────────┬──────────────┬──────────────┐
│  维度            │ Function     │ MCP          │ API Gateway  │
│                  │ Calling      │              │              │
├─────────────────┼──────────────┼──────────────┼──────────────┤
│  工具定义        │ 各平台不同   │ 统一标准     │ RESTful      │
│  跨平台复用      │ ✗ 不能       │ ✓ 可以       │ △ 部分       │
│  工具发现        │ 手动配置     │ 自动发现     │ 手动配置     │
│  资源访问        │ 不支持       │ 原生支持     │ 需要额外开发 │
│  Prompt 管理     │ 不支持       │ 原生支持     │ 不支持       │
│  安全模型        │ 各平台不同   │ 统一标准     │ OAuth/API Key│
│  AI 优化        │ 针对特定模型 │ 通用 AI 协议 │ 不针对 AI    │
│  社区生态        │ 分散         │ 统一生态     │ 成熟但非 AI  │
└─────────────────┴──────────────┴──────────────┴──────────────┘

选择建议：
  - 工具只给一个 AI 平台用 → Function Calling 就够了
  - 工具要给多个 AI 平台/应用复用 → 用 MCP
  - 工具是通用 API，不专门给 AI 用 → 用 API Gateway
```

## 五、MCP 的实际价值

```
对工具开发者：
  ┌─────────────────────────────────────────────────────────┐
  │  实现一次 MCP Server                                    │
  │  → 所有支持 MCP 的 Host 都能用                          │
  │  → VS Code、Claude Desktop、Cursor、自定义 AI 应用      │
  │  → 不用为每个平台写适配代码                               │
  └─────────────────────────────────────────────────────────┘

对 AI 应用开发者：
  ┌─────────────────────────────────────────────────────────┐
  │  集成 MCP Client                                        │
  │  → 自动获得社区贡献的所有 MCP Server                     │
  │  → 数据库、文件系统、GitHub、Slack、Jira...              │
  │  → 不用自己写每个工具的集成代码                           │
  └─────────────────────────────────────────────────────────┘

对企业：
  ┌─────────────────────────────────────────────────────────┐
  │  内部系统开发 MCP Server                                │
  │  → 所有 AI 应用都能访问内部系统                          │
  │  → 统一的权限控制和审计日志                               │
  │  → 工具可以在团队间共享                                   │
  └─────────────────────────────────────────────────────────┘
```

## 六、什么时候用 MCP

```
适合用 MCP 的场景：

  ✓ 工具需要给多个 AI 应用/平台复用
  ✓ 需要标准化的工具发现和调用机制
  ✓ 需要统一的权限控制和审计
  ✓ 企业内部系统需要被 AI 访问
  ✓ 想参与社区工具生态

不适合用 MCP 的场景：

  ✗ 工具只给一个项目用，且不会复用
  ✗ 简单的 API 调用，Function Calling 就够了
  ✗ 对延迟极其敏感（MCP 有额外的协议开销）
  ✗ 工具不需要 AI 调用，是人直接用的

决策流程图：
┌─────────────────────────────────────────────────┐
│  工具需要给多个 AI 应用用？                       │
│  ├── 否 → Function Calling 就够了                │
│  └── 是 → 需要工具发现机制？                      │
│           ├── 否 → 手动配置 Function Calling      │
│           └── 是 → 需要统一的安全模型？            │
│                    ├── 否 → 简单 MCP Server       │
│                    └── 是 → 完整 MCP + 安全层     │
└─────────────────────────────────────────────────┘
```

## 常见误区

```
误区 1：MCP 就是 Function Calling 的替代品
  MCP 不是替代 Function Calling，而是在其之上建立了标准化的工具协议层。
  Function Calling 解决的是"模型怎么调用函数"，MCP 解决的是"工具怎么跨平台复用"。

误区 2：所有工具都应该用 MCP 封装
  如果工具只给一个项目用、不会复用、不需要工具发现，直接用 Function Calling 更简单。
  MCP 的价值在标准化和复用，简单场景引入 MCP 反而增加不必要的协议开销。

误区 3：MCP Server 必须用官方 SDK 开发
  MCP 是一个开放协议，用原始 HTTP 请求也能实现。
  官方 SDK 只是简化开发的工具，理解协议本身比掌握 SDK 更重要。

误区 4：三层架构意味着必须有三个独立进程
  Host、Client、Server 是逻辑分层，不是物理分层。
  一个应用可以同时充当 Host 和 Client，Server 也可以嵌入在同一进程中。
```

## 工程建议

```
1. 先判断再引入
   在决定用 MCP 之前，先回答三个问题：
   - 这个工具会给多个 AI 应用使用吗？
   - 需要自动化的工具发现机制吗？
   - 需要统一的权限控制和审计吗？
   三个都是否，就用 Function Calling。

2. 从一个 Tool 开始
   不要一开始就设计完整的 Server。先封装一个最有价值的 Tool，
   验证 MCP 在你的场景中是否真的带来收益，再逐步扩展。

3. 描述比代码更重要
   MCP Tool 的 description 是 AI 模型决定是否调用它的唯一依据。
   花时间写好描述，比花时间优化代码更有价值。

4. 协议优先，SDK 次之
   先理解 JSON-RPC 2.0 消息格式和 MCP 的方法定义，
   再用 SDK 简化开发。这样在遇到 SDK 问题时，你能用原始请求调试。
```

## 参考答案

### 练习一：用 USB 类比解释 MCP 三层架构

**思路**：将 MCP 的 Host、Client、Server 三层分别映射到 USB 生态中的电脑操作系统、USB 控制器、USB 设备，用具体例子说明每层的职责。

**答案**：

```
USB 类比 MCP 三层架构：

┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  Host = 电脑操作系统（Windows/macOS）                     │   │
│  │  - 管理所有 USB 控制器的生命周期                          │   │
│  │  - 决定哪些设备可以连接、哪些需要驱动                      │   │
│  │  - 对应 MCP：VS Code、Claude Desktop 管理 Client          │   │
│  └─────────────────────────┬───────────────────────────────┘   │
│                            │                                    │
│  ┌─────────────────────────▼───────────────────────────────┐   │
│  │  Client = USB 控制器（USB Host Controller）              │   │
│  │  - 负责与设备通信（发送指令、接收数据）                    │   │
│  │  - 一个控制器可以连接一个设备                              │   │
│  │  - 对应 MCP：Client 负责与 Server 通信                    │   │
│  └─────────────────────────┬───────────────────────────────┘   │
│                            │                                    │
│  ┌─────────────────────────▼───────────────────────────────┐   │
│  │  Server = USB 设备（U盘、键盘、打印机）                   │   │
│  │  - 提供具体能力（存储、输入、打印）                        │   │
│  │  - 设备即插即用，操作系统自动识别                          │   │
│  │  - 对应 MCP：Server 提供 Tool/Resource/Prompt             │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                 │
│  关键类比：                                                      │
│  - USB 协议统一了接口 → MCP 协议统一了工具接口                   │
│  - USB 设备即插即用 → MCP Server 自动发现工具                    │
│  - 一个电脑可接多个 USB 设备 → 一个 Host 可连多个 Server         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**要点**：
- Host 不是 Client，Host 是运行环境，Client 是通信模块，两者职责不同
- 一个 Host 可以管理多个 Client，每个 Client 对应一个 Server
- 常见错误：把 Host 和 Client 混为一谈，认为它们是同一个东西

### 练习二：对比 MCP 和 Function Calling

**思路**：分别分析两种场景的特点，从工具复用性、开发成本、跨平台能力等维度对比，说明各自的适用边界。

**答案**：

```
场景 (a)：简单的天气查询工具

  推荐方案：Function Calling

  分析：
  - 工具逻辑简单（调用天气 API 返回结果）
  - 只给一个 AI 应用使用
  - 不需要跨平台复用
  - 不需要工具发现机制

  对比：
  ┌──────────────┬───────────────────┬───────────────────┐
  │  维度         │ Function Calling  │ MCP               │
  ├──────────────┼───────────────────┼───────────────────┤
  │  开发成本     │ 低（几行代码）    │ 高（协议+传输层）  │
  │  维护成本     │ 低               │ 中                 │
  │  复用性       │ 无               │ 高                 │
  │  适用性       │ ✓ 最佳           │ △ 过度设计         │
  └──────────────┴───────────────────┴───────────────────┘

场景 (b)：数据库查询工具（多平台复用）

  推荐方案：MCP

  分析：
  - 需要在 VS Code、Claude Desktop、自定义应用中使用
  - 工具逻辑复杂（连接池、权限控制、SQL 校验）
  - 需要统一的安全模型和审计日志
  - 团队其他项目也需要复用

  对比：
  ┌──────────────┬───────────────────┬───────────────────┐
  │  维度         │ Function Calling  │ MCP               │
  ├──────────────┼───────────────────┼───────────────────┤
  │  开发成本     │ 高（每个平台一套）│ 中（一套 Server）  │
  │  维护成本     │ 高（多处修改）    │ 低（一处修改）     │
  │  复用性       │ ✗ 需要重写       │ ✓ 即插即用         │
  │  跨平台       │ ✗ 格式不统一     │ ✓ 统一协议         │
  │  工具发现     │ ✗ 手动配置       │ ✓ 自动发现         │
  │  适用性       │ △ 勉强能用       │ ✓ 最佳             │
  └──────────────┴───────────────────┴───────────────────┘
```

**要点**：
- 核心判断标准是"工具是否需要跨平台复用"，而不是"工具复杂度"
- Function Calling 不是过时方案，简单场景它更轻量
- 常见错误：所有工具都用 MCP 封装，导致简单场景引入不必要的协议开销

### 练习三：设计公司内部系统的 MCP Server

**思路**：以代码仓库（如 GitLab）为例，从三种原语（Tool、Resource、Prompt）的角度分别设计，确保每种原语都符合其定义（Tool 做操作、Resource 做只读、Prompt 做模板）。

**答案**：

```
以代码仓库（GitLab）MCP Server 为例：

一、Tool（操作类）

  1. create_merge_request
     description: "创建合并请求"
     参数: project_id, source_branch, target_branch, title, description

  2. merge_merge_request
     description: "合并指定的合并请求"
     参数: project_id, merge_request_iid

  3. create_issue
     description: "创建 Issue"
     参数: project_id, title, description, labels

  4. post_comment
     description: "在 Issue 或 MR 上添加评论"
     参数: project_id, target_type, target_iid, body

  5. trigger_pipeline
     description: "触发 CI/CD 流水线"
     参数: project_id, branch, variables

二、Resource（只读数据）

  1. gitlab://projects
     description: "项目列表"
     返回: 项目名称、ID、描述、最近活跃时间

  2. gitlab://projects/{project_id}/merge_requests
     description: "项目的合并请求列表"
     返回: MR 标题、状态、作者、创建时间

  3. gitlab://projects/{project_id}/pipelines
     description: "项目的流水线列表"
     返回: 流水线状态、分支、触发时间

  4. gitlab://projects/{project_id}/file/{path}
     description: "读取项目文件内容"
     返回: 文件内容（限 1MB）

三、Prompt Template（模板）

  1. code_review_helper
     description: "代码审查助手，根据 MR diff 生成审查意见"
     参数: diff_text, language, review_focus（功能/性能/安全）

  2. issue_triage_helper
     description: "Issue 分类助手，自动判断优先级和标签"
     参数: issue_title, issue_description

  3. commit_message_helper
     description: "Commit 消息生成助手"
     参数: diff_text, convention（conventional/semantic）
```

**要点**：
- Tool 设计原则：单一职责，一个 Tool 只做一件事
- Resource 设计原则：只读、幂等，返回 AI 需要的最小数据集
- Prompt 设计原则：参数化、可复用，description 要让 AI 知道什么时候用
- 常见错误：把所有功能都塞进 Tool，忽略了 Resource 和 Prompt 的价值
