# 通用基准评估——MMLU / HumanEval / GSM8K 到底测了什么

> 课型：概念建模课
> 目标：理解主流基准测试测了什么、怎么跑、怎么解读

## 从"感觉好一点"到数据说话

你微调完一个模型，用几个测试问题试了试，感觉"好像比之前好了一点"。但"感觉好一点"能写进报告吗？能说服老板继续投入资源吗？

你需要一套客观的评估体系。但基准测试不是万能的——MMLU 80 分不代表你的模型在你的业务场景上好用。

## 主流基准测什么

```
基准            测什么          满分   7B模型典型分数
MMLU            知识广度        100    65-75
HumanEval       代码生成        100    50-80
GSM8K           数学推理        100    60-90
HellaSwag       常识推理        100    75-85
ARC-Challenge   科学推理        100    50-70
```

**MMLU**：57 个学科的选择题（物理、历史、法律、医学……），测知识广度不是深度。

**HumanEval**：164 个 Python 编程题，给函数签名和 docstring 让模型写实现，pass@1 指标。

**GSM8K**：8500 道小学数学应用题，需要多步推理。

**HellaSwag**：常识推理，选择最合理的句子延续，人类准确率 95%。

## 用 lm-eval-harness 跑基准

```bash
pip install lm-eval

# 跑单个基准
lm_eval --model hf \
  --model_args pretrained=./merged_model \
  --tasks mmlu \
  --num_fewshot 5 \
  --batch_size 8

# 跑多个基准
lm_eval --model hf \
  --model_args pretrained=./merged_model \
  --tasks mmlu,hellaswag,arc_challenge,gsm8k \
  --num_fewshot 5 \
  --batch_size 8
```

参数说明：
- `--num_fewshot 5`：每个题目给 5 个示例。这个参数对结果影响很大，对比不同模型时必须保持一致
- `--batch_size`：根据 GPU 显存调整，太大会 OOM
- `--tasks`：逗号分隔跑多个基准

## 对比微调前后

```python
import subprocess
import json


def run_eval(model_path: str, tasks: str, output_dir: str) -> dict:
    subprocess.run([
        "lm_eval", "--model", "hf",
        "--model_args", f"pretrained={model_path}",
        "--tasks", tasks,
        "--num_fewshot", "5",
        "--batch_size", "8",
        "--output_path", output_dir,
    ], check=True)

    with open(f"{output_dir}/results.json") as f:
        results = json.load(f)

    summary = {}
    for task_name, task_results in results["results"].items():
        for metric_name, value in task_results.items():
            if "acc" in metric_name or "pass" in metric_name:
                summary[task_name] = value
    return summary


# 对比
base_results = run_eval("./base_model", "mmlu,hellaswag,gsm8k", "./eval_base")
ft_results = run_eval("./merged_model", "mmlu,hellaswag,gsm8k", "./eval_ft")

print(f"{'基准':<20} {'基座':>8} {'微调':>8} {'变化':>8}")
print("-" * 50)
for task in base_results:
    base = base_results[task]
    ft = ft_results.get(task, 0)
    delta = ft - base
    indicator = "+" if delta > 0 else ""
    print(f"{task:<20} {base:>7.2%} {ft:>7.2%} {indicator}{delta:>7.2%}")
```

## 怎么解读结果

**微调后 MMLU 下降了 2-3 分**。正常。这叫"灾难性遗忘"——模型专注于你的领域任务，通用能力略有下降。关键是领域任务的提升是否值得。

**微调后 HumanEval 下降了 5 分以上**。需要关注。代码能力下降太多，说明训练数据可能有问题。

**所有基准都没变化**。微调可能没生效。检查训练 loss 是否真的下降了。

**微调后 GSM8K 下降明显**。数学推理对训练数据的分布很敏感。如果训练数据全是对话格式，数学推理能力可能退化。

## 基准测试的局限

基准分数只是参考，不是真相：

**MMLU 分数高不代表你的业务场景好用**。一个 MMLU 80 分的模型在你的医疗问答任务上可能还不如 MMLU 70 分的模型。

**不同架构的模型不能直接比分数**。MoE 模型参数多但激活参数少，直接比 Dense 模型的分数不公平。

**few-shot 数量影响很大**。5-shot 比 0-shot 可能高 10 分。对比不同模型时必须用相同的 few-shot 配置。

**评估工具有版本差异**。不同版本的 lm-eval-harness 结果可能有微小差异。

## 除了基准，还要测什么

基准测的是通用能力。你的业务场景需要专门的评估：

```python
def domain_evaluation(model, test_data: list[dict], tokenizer) -> dict:
    """领域任务评估"""
    correct = 0
    results = []

    for item in test_data:
        prompt = f"### 指令：{item['instruction']}\n### 回答："
        inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

        with __import__("torch").no_grad():
            outputs = model.generate(**inputs, max_new_tokens=256, temperature=0)

        predicted = tokenizer.decode(outputs[0][inputs.input_ids.shape[1]:], skip_special_tokens=True)
        is_correct = item["output"].strip() in predicted.strip()

        if is_correct:
            correct += 1
        results.append({
            "instruction": item["instruction"][:50],
            "expected": item["output"][:50],
            "predicted": predicted[:50],
            "correct": is_correct,
        })

    return {
        "accuracy": correct / len(test_data),
        "details": results[:10],
    }
```

领域评估比基准测试更重要。基准分数是给外人看的，领域准确率是给你自己看的。

## 参考答案

### 练习一

`--num_fewshot` 对结果影响很大，文档中通常用 5-shot。`--batch_size` 根据 GPU 显存调整，4090 用 8-16。评估结果保存到文件，方便后续对比。

### 练习二

预期：MMLU 下降 1-3 分是正常的。如果领域任务提升 > 10%，通用能力下降 3 分以内，微调是成功的。如果通用能力下降 > 5 分，需要检查训练数据是否太窄。

### 练习三

评估集应该是独立收集的，不是训练集的子集。覆盖业务场景的典型难度分布。包含边界情况（歧义、多义、反常识）。评估集的质量直接决定评估结果的可信度。
