# 02 微调方法全景——Full Fine-tuning / LoRA / QLoRA / Prefix Tuning

## 场景引入

你决定微调模型，但搜了一圈发现方法多得让人眼花：Full Fine-tuning、LoRA、QLoRA、Prefix Tuning、Adapter、P-Tuning……每个论文都说自己的方法最好。Full FT 效果最好但要 80GB 显存，LoRA 只需 16GB 但效果能保证吗？QLoRA 进一步压缩到 6GB，代价又是什么？选错方法可能浪费数天时间和几百块 GPU 费用。

## 一、微调方法概览

```
微调方法：

1. Full Fine-tuning（全量微调）
   - 更新所有参数
   - 效果最好
   - 资源需求最高

2. LoRA（Low-Rank Adaptation）
   - 只更新低秩矩阵
   - 效果接近全量微调
   - 资源需求低

3. QLoRA（Quantized LoRA）
   - 量化 + LoRA
   - 进一步降低资源需求
   - 适合消费级硬件

4. Prefix Tuning
   - 只更新前缀参数
   - 资源需求最低
   - 效果有限
```

---

## 二、LoRA 原理

```
LoRA 原理：

原始模型参数：W (d × d)
LoRA 分解：W + ΔW = W + B × A

其中：
- A: (r × d) 低秩矩阵
- B: (d × r) 低秩矩阵
- r: 秩（通常 4-64）

优势：
- 只需训练 A 和 B
- 参数量大幅减少
- 效果接近全量微调
```

---

## 三、QLoRA 原理

```
QLoRA 原理：

1. 将模型量化为 4-bit
2. 在量化模型上应用 LoRA
3. 只训练 LoRA 参数

优势：
- 内存占用大幅减少
- 7B 模型只需 6GB 显存
- 效果接近 LoRA
```

## 常见误区

1. **认为 Full Fine-tuning 一定效果最好**：当数据量不足时，全量微调反而容易过拟合，效果可能不如 LoRA。数据量小于 1000 条时，LoRA 通常是更安全的选择。

2. **QLoRA 效果一定比 LoRA 差很多**：实验表明 QLoRA 和 LoRA 的效果差距通常在 1-2% 以内。对于大多数应用场景，这个差距完全可以接受，而显存节省是巨大的。

3. **看到 Prefix Tuning 参数最少就选它**：Prefix Tuning 虽然参数量极小（<0.1%），但在复杂任务上效果明显不如 LoRA。参数少不等于性价比高。

4. **忽略方法的工程成熟度**：LoRA 拥有最成熟的工具链（PEFT、TRL）和最大的社区支持。选择一个工具链不成熟的方法，后续遇到问题可能找不到解决方案。

---

## 工程建议

1. **LoRA 是默认选择**：除非有明确理由，否则一律用 LoRA。它的效果、效率、工具链成熟度都是最优的，是目前微调社区的事实标准。

2. **显存不够用 QLoRA，不要降模型**：与其用更小的模型 + LoRA，不如用目标模型 + QLoRA。QLoRA 的质量损失远小于模型参数量减半带来的能力下降。

3. **先跑基准再选方法**：在同一数据集上分别用 LoRA 和 QLoRA 跑一个快速实验（1 epoch），对比效果后再做最终选择，而不是纯靠理论判断。

4. **关注新方法但不急于采用**：持续关注 DoRA、rsLoRA 等新方法的进展，但等它们的工具链和社区验证成熟后再考虑采用。

## 参考答案

### 练习一：对比题

**思路**：从参数量、显存需求、效果、适用场景、工具链成熟度五个维度系统对比四种微调方法。

**答案**：

| 维度 | Full Fine-tuning | LoRA | QLoRA | Prefix Tuning |
|------|-----------------|------|-------|---------------|
| 可训参数占比 | 100% | 0.1-1% | 0.1-1% | <0.1% |
| 7B 模型显存需求 | 60-80GB | 16-20GB | 6-10GB | 4-8GB |
| 效果 | 最好（数据充足时） | 接近全量微调（95-99%） | 略低于 LoRA（1-2%差距） | 较差，复杂任务退化明显 |
| 训练速度 | 慢 | 快 | 中等 | 最快 |
| 推理延迟 | 无额外延迟 | 合并后无延迟 | 合并后无延迟 | 有额外开销 |
| 适配器大小 | 等于原模型 | 几十 MB | 几十 MB | 几 MB |
| 工具链成熟度 | 高 | 最高（PEFT/TRL） | 高 | 中等 |
| 多任务切换 | 需要多个完整模型 | 热切换 LoRA 适配器 | 热切换 LoRA 适配器 | 切换前缀 |
| 过拟合风险 | 数据少时高 | 低 | 低 | 最低 |

核心差异总结：
- **Full FT**：效果天花板最高，但资源需求也最高，适合数据充足（>10K 条）且有 A100 集群的场景
- **LoRA**：性价比之王，效果接近 Full FT 但资源需求低一个数量级，是大多数场景的首选
- **QLoRA**：在 LoRA 基础上进一步压缩显存，适合消费级 GPU（RTX 4090 / 3090）
- **Prefix Tuning**：参数最少但效果最差，只适合资源极度受限且任务简单的场景

**要点**：
- 不能只看参数量多少就判断方法好坏——Prefix Tuning 参数最少但效果也最差
- 工具链成熟度直接影响开发效率——LoRA 有 PEFT、TRL 等成熟工具，遇到问题容易找到解决方案
- 常见错误：认为 QLoRA 效果一定比 LoRA 差很多——实验表明差距通常在 1-2% 以内

### 练习三：原理题

**思路**：从数学原理、直觉理解和工程实现三个层面解释 LoRA。

**答案**：

**LoRA（Low-Rank Adaptation）的工作原理：**

1. **核心假设**：微调时的权重变化量 ΔW 是低秩的，即可以用两个小矩阵的乘积来近似。

2. **数学表达**：
   ```
   原始模型：y = W·x
   微调后：  y = W·x + ΔW·x = W·x + B·A·x

   其中：
   - W ∈ R^(d×d)  ：原始权重（冻结，不训练）
   - A ∈ R^(r×d)  ：下投影矩阵（可训练）
   - B ∈ R^(d×r)  ：上投影矩阵（可训练）
   - r << d        ：秩（通常 8-64）

   参数量对比（d=4096）：
   - 全量微调 ΔW：4096×4096 = 16,777,216 参数
   - LoRA (r=16)：2×16×4096 = 131,072 参数
   - 压缩比：131,072 / 16,777,216 ≈ 0.78%
   ```

3. **直觉理解**：
   - 预训练模型已经学到了丰富的通用知识
   - 微调只需要"调整"模型的一小部分行为方向
   - 这个"调整方向"的自由度远小于权重矩阵的全维度
   - 所以用两个小矩阵（A 和 B）就能近似表达这个调整

4. **前向传播**：
   ```
   输入 x
     ├──────┐
     │      │
     ▼      ▼
   [W·x]  [A·x] → [B·(A·x)] × (alpha/r)
     │      │
     ▼      ▼
   [W·x + (alpha/r)·B·A·x] = 最终输出
   ```

5. **推理时合并**：训练完成后，LoRA 可以合并到原始权重中，不引入额外计算开销：
   ```
   W' = W + (alpha/r)·B·A
   推理时和原始模型完全一样，无额外延迟
   ```

**要点**：
- "低秩"是 LoRA 的核心——它假设微调的调整量可以用远小于原始维度的空间来表达
- alpha/r 是缩放因子，控制 LoRA 对原始权重的影响程度
- LoRA 的独特优势是合并后无推理延迟、可以叠加多个适配器、支持热切换
- 常见错误：把 LoRA 理解为"只训练部分权重"——LoRA 是在原始权重旁边加了一个旁路（B·A），不是选择性地训练原始权重的一部分
