# 01 为什么微调——Prompt Engineering vs RAG vs Fine-tuning 的选型

> 不是所有问题都需要微调。选对方法比选对模型更重要。

## 场景引入

你的老板说："这个通用大模型回答我们公司的产品问题总是胡说八道，微调一下就好了。"你花了一周准备数据、租了 GPU、跑完微调，结果发现效果还不如在 Prompt 里加几句产品说明。问题出在哪？不是微调本身有问题，而是你选错了方法。Prompt Engineering、RAG、Fine-tuning 各有适用场景，选错方法就是白费力气。

---

## 学习目标

- 理解 Prompt Engineering、RAG、Fine-tuning 的区别
- 掌握三种方法的适用场景
- 学会根据需求选择合适的方法

---

## 一、三种方法对比

```
┌─────────────────────────────────────────────────────────────┐
│           Prompt Engineering vs RAG vs Fine-tuning          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Prompt Engineering                                         │
│  ├── 原理：通过提示词引导模型行为                            │
│  ├── 成本：低（无需训练）                                    │
│  ├── 效果：有限（受限于模型能力）                            │
│  └── 适用：简单任务、快速迭代                                │
│                                                             │
│  RAG（检索增强生成）                                         │
│  ├── 原理：检索外部知识辅助生成                              │
│  ├── 成本：中（需要构建知识库）                              │
│  ├── 效果：好（可以访问最新信息）                            │
│  └── 适用：知识密集型任务                                    │
│                                                             │
│  Fine-tuning（微调）                                        │
│  ├── 原理：用领域数据训练模型                                │
│  ├── 成本：高（需要数据和计算资源）                          │
│  ├── 效果：好（可以改变模型行为）                            │
│  └── 适用：特定领域、特定风格                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 二、选型决策树

```
选型决策树：

你的需求是什么？
├── 简单任务优化 → Prompt Engineering
│   ├── 调整输出格式
│   ├── 改变回答风格
│   └── 添加约束条件
│
├── 访问外部知识 → RAG
│   ├── 最新信息
│   ├── 私有数据
│   └── 专业知识
│
└── 改变模型行为 → Fine-tuning
    ├── 特定领域
    ├── 特定风格
    └── 特定任务
```

## 三、适用场景

```
适用场景：

Prompt Engineering：
- 快速原型开发
- 简单任务调整
- 成本敏感场景

RAG：
- 知识问答系统
- 文档检索
- 实时信息查询

Fine-tuning：
- 特定领域（医疗、法律、金融）
- 特定风格（正式、口语、专业）
- 特定任务（代码生成、文本分类）
```

---

## 四、组合使用

```
组合使用：

1. Prompt + RAG
   - 用 Prompt 引导 RAG 行为
   - 优化检索结果的使用

2. RAG + Fine-tuning
   - 微调模型更好地使用检索结果
   - 提高 RAG 的效果

3. Prompt + Fine-tuning
   - 微调后用 Prompt 进一步优化
   - 适应不同场景
```

## 五、决策矩阵

```
决策矩阵：

| 因素 | Prompt | RAG | Fine-tuning |
|------|--------|-----|-------------|
| 开发成本 | 低 | 中 | 高 |
| 维护成本 | 低 | 中 | 高 |
| 效果提升 | 有限 | 好 | 很好 |
| 灵活性 | 高 | 中 | 低 |
| 适用范围 | 广 | 中 | 窄 |
```

---

## 常见误区

1. **遇到效果不好就想微调**：很多时候 Prompt Engineering 或 RAG 就能解决问题，微调是成本最高的方案。先试 Prompt 优化，再试 RAG，最后才考虑微调。

2. **认为微调能让模型"学会新知识"**：微调主要是调整模型的行为方式和输出风格，而不是注入新知识。需要模型掌握最新信息，应该用 RAG 而不是微调。

3. **忽略组合使用的效果**：Prompt、RAG、Fine-tuning 不是互斥的。微调后的模型配合精心设计的 Prompt 和 RAG 检索，效果通常远超单独使用任何一种方法。

4. **只考虑效果不考虑维护成本**：微调模型需要持续维护——数据更新、模型重训、版本管理。如果团队没有持续投入的能力，RAG 可能是更可持续的方案。

---

## 工程建议

1. **用决策树做选型**：面对需求时，按"简单调整？→ Prompt；需要外部知识？→ RAG；需要改变模型行为？→ 微调"的顺序逐级判断，避免过早进入微调。

2. **先做 MVP 验证**：在投入大量资源做微调前，先用 Prompt + 小规模 RAG 做一个 MVP，验证需求是否真的需要微调级别的效果提升。

3. **量化微调 ROI**：微调的收益要能衡量——准确率提升多少、用户满意度提升多少、节省了多少人工审核成本。没有明确 ROI 的微调项目不值得启动。

4. **建立方法切换的评估标准**：定义清晰的指标（如准确率 > 85%），当某种方法达到标准就停止升级，避免过度工程化。

## 参考答案

### 练习一：选型题

**思路**：根据课程中的决策树，按"简单调整？→ Prompt；需要外部知识？→ RAG；需要改变模型行为？→ 微调"的顺序逐级判断。选择一个具体场景进行分析。

**答案**：

假设场景：**公司需要一个客服机器人，能回答产品问题、处理退换货请求、保持品牌语气。**

分析过程：

| 需求 | 适合的方法 | 原因 |
|------|-----------|------|
| 回答产品问题（价格、功能、参数） | RAG | 产品信息会更新，需要访问最新数据 |
| 处理退换货流程 | Prompt Engineering | 流程固定，用 Prompt 指令即可 |
| 保持品牌语气 | Fine-tuning | 需要改变模型的输出风格 |
| 理解用户意图（投诉/咨询/退货） | Fine-tuning 或 Prompt | 取决于准确率要求 |

最终选型：

1. **第一阶段**（MVP）：Prompt Engineering + RAG
   - 用 Prompt 定义客服角色和回答规范
   - 用 RAG 接入产品知识库
   - 开发成本低，1-2 周可上线

2. **第二阶段**（优化）：Fine-tuning + RAG
   - 用历史客服对话数据微调模型，学习品牌语气
   - 保持 RAG 接入最新产品信息
   - 只有当第一阶段准确率 < 80% 时才进入

**要点**：
- 不要一上来就微调，先用低成本方案验证需求
- RAG 适合处理会变化的知识，微调适合处理固定的行为模式
- 常见错误：用微调来注入产品知识——产品信息会更新，微调的知识是静态的，应该用 RAG

### 练习二：对比题

**思路**：在同一个任务上分别用三种方法测试，对比效果、成本和维护难度。

**答案**：

任务：**让模型以 JSON 格式输出情感分析结果**

```python
import json
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="not-needed")
model = "qwen2.5:7b"

test_text = "这款手机拍照很清晰，但电池续航太差了，用半天就没电。"

# 方法 1：Prompt Engineering
response = client.chat.completions.create(
    model=model,
    messages=[{
        "role": "user",
        "content": f"""请对以下文本进行情感分析，以 JSON 格式输出：
- sentiment: positive/negative/mixed
- aspects: 列出提到的方面及对应情感

文本：{test_text}

只输出 JSON，不要其他内容。"""
    }],
    response_format={"type": "json_object"},
)
print("=== Prompt Engineering ===")
print(json.dumps(json.loads(response.choices[0].message.content), ensure_ascii=False, indent=2))

# 方法 2：RAG（检索相似的情感分析案例作为参考）
# 假设已有情感分析案例库
examples = [
    {"text": "屏幕显示效果很好，但系统经常卡顿", "output": {"sentiment": "mixed", "aspects": [{"aspect": "屏幕", "sentiment": "positive"}, {"aspect": "系统", "sentiment": "negative"}]}},
]

response = client.chat.completions.create(
    model=model,
    messages=[{
        "role": "user",
        "content": f"""参考以下情感分析案例：
{json.dumps(examples, ensure_ascii=False)}

请对以下文本进行同样的情感分析：
{test_text}"""
    }],
)
print("\n=== RAG ===")
print(response.choices[0].message.content)

# 方法 3：Fine-tuning（需要先准备训练数据并微调模型）
# 微调后的模型能更稳定地输出正确格式
# 这里模拟微调后的效果
print("\n=== Fine-tuning ===")
print("微调后的模型能稳定输出正确格式，准确率更高，但需要投入训练时间和数据准备成本。")
```

对比结果：

| 维度 | Prompt | RAG | Fine-tuning |
|------|--------|-----|-------------|
| 开发时间 | 1 小时 | 1-2 天 | 1-2 周 |
| 格式稳定性 | 中（可能输出非 JSON） | 中 | 高 |
| 准确率 | 70-80% | 80-90% | 90-95% |
| 维护成本 | 低 | 中 | 高 |
| 灵活性 | 高（随时改 Prompt） | 中 | 低（需要重训） |

**要点**：
- Prompt Engineering 最快但效果最不稳定
- RAG 可以通过引入案例来提升效果，但增加了检索复杂度
- Fine-tuning 效果最好但成本最高，适合需求稳定的场景
- 常见错误：在需求还不明确时就做微调——需求变化后微调模型需要重训

### 练习三：组合题

**思路**：设计一个三种方法组合使用的方案，发挥各自优势。

**答案**：

场景：**智能代码审查助手**

```python
# 架构设计：
# 1. Fine-tuning：让模型学会代码审查的风格和关注点
# 2. RAG：检索项目的编码规范和历史审查记录
# 3. Prompt Engineering：控制输出格式和审查维度

class CodeReviewAssistant:
    def __init__(self):
        # 微调后的模型（学会了代码审查风格）
        self.model = "codereview-finetuned"
        # 项目编码规范知识库
        self.knowledge_base = CodingStandardsKB()
        # 历史审查记录
        self.review_history = ReviewHistoryDB()

    def review(self, code: str, language: str) -> dict:
        # Step 1: RAG - 检索相关规范和历史案例
        standards = self.knowledge_base.search(f"{language} coding standards")
        similar_reviews = self.review_history.find_similar(code, top_k=3)

        # Step 2: Prompt Engineering - 构造审查指令
        prompt = f"""请审查以下 {language} 代码。

项目编码规范：
{standards}

类似代码的历史审查记录：
{similar_reviews}

审查维度：
1. 潜在 Bug 和安全问题
2. 性能优化建议
3. 代码可读性和可维护性
4. 是否符合项目规范

代码：
```{language}
{code}
```

请以 JSON 格式输出审查结果。"""

        # Step 3: Fine-tuned 模型生成审查意见
        response = self.client.chat.completions.create(
            model=self.model,
            messages=[{"role": "user", "content": prompt}],
            response_format={"type": "json_object"},
        )

        return json.loads(response.choices[0].message.content)
```

组合方式说明：

| 方法 | 职责 | 作用 |
|------|------|------|
| Fine-tuning | 学习代码审查的专业风格 | 输出更专业、更准确的审查意见 |
| RAG | 检索项目规范和历史案例 | 确保审查符合项目标准，不重复已知问题 |
| Prompt | 控制输出格式和审查维度 | 保证输出结构化，覆盖所有审查维度 |

**要点**：
- 三种方法各司其职：微调管"怎么说"，RAG 管"说什么"，Prompt 管"输出什么格式"
- 组合使用的效果远超单独使用任何一种方法
- 常见错误：试图用一种方法解决所有问题——每种方法有各自擅长的领域，合理分工才能发挥最大效果
