## 四、模型加载实战

```python
# 用 Hugging Face Transformers 加载模型
from transformers import AutoTokenizer, AutoModelForCausalLM
import torch

# 1. 选择模型
model_name = "Qwen/Qwen2.5-7B-Instruct"

# 2. 加载 Tokenizer
tokenizer = AutoTokenizer.from_pretrained(model_name, trust_remote_code=True)

# 3. 加载模型（自动检测设备）
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,      # 使用 BF16 精度
    device_map="auto",                # 自动分配 GPU
    trust_remote_code=True,
)

# 4. 推理测试
messages = [
    {"role": "system", "content": "你是一个有用的助手。"},
    {"role": "user", "content": "用 Python 写一个快速排序"},
]

text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt").to(model.device)

outputs = model.generate(**inputs, max_new_tokens=512, temperature=0.7)
print(tokenizer.decode(outputs[0][inputs.input_ids.shape[1]:], skip_special_tokens=True))
```

## 常见误区

1. **只看参数量选模型**：参数大不等于效果好。Qwen 2.5 7B 在中文任务上可能比 Llama 3.1 70B 表现更好，因为训练数据和优化方向不同。选型要看 benchmark 而不是参数规模。

2. **忽略许可证限制**：部分模型的许可证限制商用场景（如早期 Llama License），部署前务必确认许可证条款，避免法律风险。

3. **盲目追求最大量化**：INT4 量化虽然显存减 75%，但在数学推理和代码生成任务上质量损失明显。需要根据任务类型选择合适的量化等级。

4. **忽略中文场景的特殊需求**：英文 benchmark 表现好的模型在中文任务上可能拉胯。面向中文用户时，C-Eval 和 CMMLU 比 MMLU 更有参考价值。

---

## 工程建议

1. **先用 Ollama 快速验证**：在正式选型前，用 Ollama 跑几个候选模型做定性测试，比纯看 benchmark 数据更直观。5 分钟内就能对比多个模型的输出质量。

2. **建立选型 checklist**：每次选型时列出任务类型、显存预算、语言需求、量化等级四个维度，按优先级筛选，避免在众多模型中迷失方向。

3. **量化版本先测试再上线**：量化模型在通用对话任务上通常表现良好，但在专业领域（医疗、法律、代码）可能出现严重退化。上线前必须在目标领域做质量回归测试。

4. **关注社区生态**：选择社区活跃度高的模型系列（如 Llama、Qwen），可以获得更完善的工具链支持、更多的微调数据和更及时的问题修复。

## 参考答案

### 练习一：选型题

**思路**：中文客服系统的核心需求是中文理解 + 长文本支持，显存 16GB 是硬约束。根据课程中的选型四象限和决策树，中文场景首选 Qwen 2.5 系列。16GB 显存可以跑 7B FP16（14GB）或 14B INT4（7GB）。考虑到需要长文本支持，Qwen 2.5 7B 支持 128K 上下文，是最佳选择。

**答案**：

选择 **Qwen 2.5 7B-Instruct**，理由如下：

1. **中文能力**：Qwen 2.5 在 C-Eval（89.2）和 CMMLU（90.1）上大幅领先其他模型，中文客服场景必须优先考虑中文能力。
2. **长文本支持**：Qwen 2.5 支持 128K 上下文长度，满足客服系统处理长对话历史和长文档的需求。
3. **显存匹配**：7B 模型 FP16 需要约 14GB 显存，在 16GB 显存下可以正常运行，且无需量化，质量无损。
4. **许可证**：Apache 2.0 许可证，商用无限制。

如果后续需要进一步压缩显存以留出余量给 KV 缓存，可以用 INT8 量化（约 7-8GB 显存），质量损失极小。

**要点**：
- 中文场景必须看 C-Eval 和 CMMLU，不能只看 MMLU
- 长文本需求要关注模型的最大上下文长度（Qwen 2.5 为 128K，部分模型只有 4K-8K）
- 16GB 显存下 7B FP16 是最优解，不要盲目选更大的模型然后重度量化
- 常见错误：选 Llama 3.1 8B 做中文客服——虽然 MMLU 分数接近，但中文 benchmark 差距巨大（C-Eval: 65.8 vs 89.2）

### 练习三：量化题

**思路**：通过实际加载对比 FP16 和 INT4 的显存占用和推理速度，理解量化的实际影响。

**答案**：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch
import time

model_name = "Qwen/Qwen2.5-7B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name, trust_remote_code=True)

# FP16 加载
print("=== FP16 加载 ===")
model_fp16 = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.float16,
    device_map="auto",
    trust_remote_code=True,
)
print(f"FP16 显存占用: {torch.cuda.memory_allocated() / 1024**3:.2f} GB")

# 推理测试
messages = [{"role": "user", "content": "用 Python 写一个冒泡排序"}]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt").to(model_fp16.device)

start = time.time()
outputs = model_fp16.generate(**inputs, max_new_tokens=256)
fp16_time = time.time() - start
print(f"FP16 推理时间: {fp16_time:.2f}s")

# 清理显存
del model_fp16
torch.cuda.empty_cache()

# INT4 量化加载（需要 bitsandbytes）
from transformers import BitsAndBytesConfig

bnb_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.float16)
print("\n=== INT4 加载 ===")
model_int4 = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=bnb_config,
    device_map="auto",
    trust_remote_code=True,
)
print(f"INT4 显存占用: {torch.cuda.memory_allocated() / 1024**3:.2f} GB")

inputs = tokenizer(text, return_tensors="pt").to(model_int4.device)
start = time.time()
outputs = model_int4.generate(**inputs, max_new_tokens=256)
int4_time = time.time() - start
print(f"INT4 推理时间: {int4_time:.2f}s")
```

预期结果：
- FP16 显存约 14GB，INT4 显存约 4GB（减少约 70%）
- INT4 推理速度可能略快（数据搬运量小），但质量在复杂任务上有损

**要点**：
- FP16 vs INT4 的显存差异是 3-4 倍，不仅仅是"减半"
- 量化后的质量损失在简单任务上不明显，但在数学推理和代码生成任务上可能显著
- 常见错误：只对比显存不对比输出质量——显存省了但输出变差就得不偿失

### 练习四：实战题

**思路**：使用 Hugging Face Transformers 加载 7B 模型并完成对话推理，掌握基本的模型加载和推理流程。

**答案**：

```python
from transformers import AutoTokenizer, AutoModelForCausalLM
import torch

# 选择模型
model_name = "Qwen/Qwen2.5-7B-Instruct"

# 加载 Tokenizer
tokenizer = AutoTokenizer.from_pretrained(model_name, trust_remote_code=True)

# 加载模型
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
    trust_remote_code=True,
)

# 构造对话
messages = [
    {"role": "system", "content": "你是一个有用的助手。"},
    {"role": "user", "content": "用 Python 写一个快速排序，并解释时间复杂度。"},
]

# 应用 chat template
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt").to(model.device)

# 生成
outputs = model.generate(**inputs, max_new_tokens=512, temperature=0.7)
response = tokenizer.decode(outputs[0][inputs.input_ids.shape[1]:], skip_special_tokens=True)
print(response)
```

**要点**：
- `trust_remote_code=True` 是 Qwen 等模型必须的参数，否则可能加载失败
- `apply_chat_template` 会自动添加模型需要的特殊标记（如 `<|im_start|>`），不要手动拼接 prompt
- `device_map="auto"` 会自动将模型分配到可用的 GPU 上
- 常见错误：忘记设置 `torch_dtype`——默认用 float32 会占用双倍显存
