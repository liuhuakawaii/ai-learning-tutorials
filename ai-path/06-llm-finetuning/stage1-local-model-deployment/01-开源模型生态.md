# 01 开源模型选型——从 Hugging Face 上百个模型里找到你该用的那一个

> 前置知识：了解大模型基本概念（参数、推理）
> 预计时长：50 分钟

你打开 Hugging Face，搜 "7B"，出来几百个模型。Llama、Qwen、Mistral、DeepSeek、Gemma、Phi……每个都说自己很强，参数从 0.5B 到 405B，架构有 Dense 有 MoE，量化格式五花八门。你该选哪个？

选错模型的代价不是"效果差一点"——是你花了两天下载一个 140GB 的模型，发现你的 24GB 显卡根本跑不起来，或者跑起来了但中文输出一塌糊涂，又得从头来。

这节课解决一个问题：**怎么用最少的时间，选到最适合你场景的模型**。

---

## 选型的四个硬约束

选模型不是"哪个分数高选哪个"。你得先回答四个问题：

**1. 你拿它做什么？**

不同任务适合不同模型，这不是玄学，是训练数据决定的：

- 通用对话/写作 → Llama 3.1、Qwen 2.5
- 代码生成 → DeepSeek Coder V2、CodeLlama
- 数学/推理 → DeepSeek V2、Qwen 2.5-Math
- 中文场景 → Qwen 2.5（C-Eval 89.2，比第二名高 20 多分）
- 多模态 → Qwen 2.5-VL、Llama 3.2 Vision

**2. 你有多少显存？**

这是硬约束，没得商量：

```
模型参数    FP16显存    INT4显存
1-3B       2-6GB      0.5-1.5GB
7-8B       14-16GB    3.5-4GB
13-14B     26-28GB    6.5-7GB
70-72B     140-144GB  35-36GB
```

RTX 4090 (24GB) → 能跑 7B FP16 或 14B INT4。超过这个，要么加卡，要么用量化。

**3. 你要不要量化？**

量化是用精度换显存。听着很美好，但有代价：

- INT8：显存减半，质量损失极小，大多数场景安全
- INT4：显存减 75%，在数学推理和代码生成上质量损失明显
- GPTQ/AWQ：GPU 推理专用，AWQ 质量通常优于 GPTQ
- GGUF：CPU/GPU 混合推理，llama.cpp 和 Ollama 用这个格式

**4. 语言需求是什么？**

如果面向中文用户，Qwen 2.5 在 C-Eval (89.2) 和 CMMLU (90.1) 上碾压其他模型。Llama 3.1 的中文 benchmark 只有 65-67，差距巨大。别看 MMLU 分数接近就以为中文也差不多。

## 一个真实的选型过程

假设你的场景是：**为公司搭建中文客服助手，显卡 RTX 4090 (24GB)，需要处理长对话历史**。

第一步，排除：
- 需要 70B？24GB 跑不了 FP16，INT4 量化后质量在中文场景损失大 → 不选
- 需要代码生成？客服不需要 → 排除 DeepSeek Coder
- 需要英文？主要面向中文 → Llama 中文太弱，排除

第二步，剩下候选：Qwen 2.5 7B、Qwen 2.5 14B (INT4)、Mistral 7B

第三步，关键决策：
- Qwen 2.5 7B FP16：14GB 显存，128K 上下文，中文最强 → 够用
- Qwen 2.5 14B INT4：7GB 显存，但 INT4 在长文本场景可能丢信息
- Mistral 7B：中文能力太弱（C-Eval 62.1）

**结论：Qwen 2.5 7B-Instruct**，FP16 加载，留 10GB 给 KV 缓存和系统开销。

## 快速验证：5 分钟跑起来

最简单的验证方式是 Ollama：

```bash
# 安装 Ollama 后一行命令
ollama run qwen2.5:7b
```

用 Python 调用 Ollama 做对比测试：

```python
import requests

def ask_model(model: str, question: str) -> str:
    resp = requests.post("http://localhost:11434/api/chat", json={
        "model": model,
        "messages": [{"role": "user", "content": question}],
        "stream": False,
    })
    return resp.json()["message"]["content"]

# 对比两个模型
question = "请解释'塞翁失马，焉知非福'的含义，并举一个现代生活中的例子。"
print("=== Qwen 2.5 7B ===")
print(ask_model("qwen2.5:7b", question))
print("\n=== Llama 3.1 8B ===")
print(ask_model("llama3:8b", question))
```

预期结果：Qwen 在成语理解的准确性和中文表达的自然度上明显优于 Llama。

## 用 Hugging Face Transformers 加载

Ollama 适合快速验证，但后续微调需要用 Transformers：

```python
from transformers import AutoTokenizer, AutoModelForCausalLM
import torch

model_name = "Qwen/Qwen2.5-7B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(model_name, trust_remote_code=True)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,
    device_map="auto",
    trust_remote_code=True,
)

messages = [
    {"role": "system", "content": "你是一个有用的助手。"},
    {"role": "user", "content": "用 Python 写一个快速排序"},
]

text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt").to(model.device)
outputs = model.generate(**inputs, max_new_tokens=512, temperature=0.7)
print(tokenizer.decode(outputs[0][inputs.input_ids.shape[1]:], skip_special_tokens=True))
```

几个容易踩的坑：
- `trust_remote_code=True`：Qwen 等模型必须加，否则加载失败
- `apply_chat_template`：自动添加模型需要的特殊标记（如 `<|im_start|>`），不要手动拼 prompt
- 不设 `torch_dtype`：默认 float32，显存翻倍

```
├── 8GB 以下 → 3B 以下模型 (INT4)
├── 16GB    → 7B FP16 或 14B INT4
├── 24GB    → 7B FP16 留余量，或 14B INT4
└── 48GB+   → 14B FP16 或 70B INT4
```

## 容易犯的错

**只看参数量选模型**。Qwen 2.5 7B 在中文任务上可能比 Llama 3.1 70B 更好，因为训练数据和优化方向不同。选型看 benchmark，不看参数规模。

**忽略许可证**。Llama License 早期版本限制商用，部署前确认条款。

**盲目追求量化**。INT4 在数学推理和代码生成上质量损失明显。省了显存但输出变差，得不偿失。

**用英文 benchmark 推断中文能力**。Llama MMLU 73 vs Qwen MMLU 74，看着差不多。但 C-Eval 差 23 分。面向中文用户时，C-Eval 和 CMMLU 才是关键指标。

## 练习

### 练习一：对比测试

用 Ollama 分别运行 Qwen 2.5 7B 和 Llama 3.1 8B，对以下三个 prompt 对比输出质量：

```python
test_prompts = [
    "请解释'塞翁失马，焉知非福'的含义，并举一个现代生活中的例子。",
    "写一封正式的商务邮件，向客户道歉因为物流延迟导致订单晚到。",
    "用 Python 写一个函数，输入一个中文字符串，返回其中包含的数字之和。请用中文注释。",
]

for prompt in test_prompts:
    print(f"=== Prompt: {prompt[:30]}... ===")
    print("Qwen:", ask_model("qwen2.5:7b", prompt))
    print("Llama:", ask_model("llama3:8b", prompt))
    print()
```

记录：哪个模型在中文表达的自然度、成语理解的准确性、中文注释的规范性上更好。

### 练习二：量化对比

对同一个模型分别用 FP16 和 INT4 加载，对比显存占用和推理速度：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
import torch, time

model_name = "Qwen/Qwen2.5-7B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name, trust_remote_code=True)

# FP16
model_fp16 = AutoModelForCausalLM.from_pretrained(
    model_name, torch_dtype=torch.float16, device_map="auto", trust_remote_code=True
)
print(f"FP16 显存: {torch.cuda.memory_allocated() / 1024**3:.2f} GB")

del model_fp16
torch.cuda.empty_cache()

# INT4
bnb_config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_compute_dtype=torch.float16)
model_int4 = AutoModelForCausalLM.from_pretrained(
    model_name, quantization_config=bnb_config, device_map="auto", trust_remote_code=True
)
print(f"INT4 显存: {torch.cuda.memory_allocated() / 1024**3:.2f} GB")
```

预期：FP16 约 14GB，INT4 约 4GB。但要注意 INT4 在复杂任务上的质量变化。

## 参考答案

### 练习一

预期结论：Qwen 2.5 在中文表达的自然度、成语理解的准确性、中文注释的规范性上明显优于 Llama 3.1。这与 benchmark 数据一致——C-Eval 89.2 vs 65.8。

测试要用多样化的 prompt，不能只测一个问题。除了正确性，还要关注流畅度、用词准确性、文化理解。

### 练习二

预期结果：
- FP16 显存约 14GB，INT4 显存约 4GB（减少约 70%）
- INT4 推理速度可能略快（数据搬运量小）
- 质量差异在简单任务上不明显，但在数学推理和代码生成任务上可能显著

常见错误：只对比显存不对比输出质量。

### 练习三

选型过程：
1. 排除：70B 模型 16GB 跑不了 FP16；英文模型中文能力不够
2. 候选：Qwen 2.5 7B (FP16, 14GB)、Qwen 2.5 14B (INT4, 7GB)
3. 决策：Qwen 2.5 7B-Instruct，FP16 加载
   - 中文能力：C-Eval 89.2，客服场景必须
   - 长文本：支持 128K 上下文
   - 显存：FP16 约 14GB，16GB 够用
   - 许可证：Apache 2.0，商用无限制

常见错误：选 Llama 3.1 8B 做中文客服——MMLU 分数接近，但 C-Eval 差 23 分。
