# 06 阶段实战——在本地部署一个 OpenAI 兼容的模型服务

> 把 Ollama、vLLM、OpenAI 兼容 API 串成一个完整的本地部署方案。

你前 5 课分别学了 Ollama、llama.cpp、vLLM、OpenAI 兼容 API。单独都会用，但现在有个真实需求：**在本地部署一个稳定的模型服务，接入你现有的应用，和云端模型做效果对比**。

选哪个引擎？怎么保证稳定性？延迟够不够？这些问题需要一个完整的实战来回答。

---

## 部署方案选择

三种方案，各有适用场景：

```
场景              推荐方案      理由
开发测试          Ollama       5 分钟跑起来，零配置
内部工具          llama.cpp    资源占用最低，CPU 也能跑
面向用户的服务    vLLM         高并发，PagedAttention 优化
```

本课用 Ollama 做主方案（最简单），最后讲 vLLM 的生产部署。

---

## Step 1：用 Ollama 启动服务

```bash
# 安装 Ollama（Linux/macOS）
curl -fsSL https://ollama.ai/install.sh | sh

# 下载模型
ollama pull qwen2.5:7b

# 启动服务（默认监听 11434 端口）
ollama serve
```

验证服务是否正常：

```bash
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5:7b",
    "messages": [{"role": "user", "content": "你好"}]
  }'
```

如果返回 JSON 带有 `choices` 字段，服务正常。

---

## Step 2：用 OpenAI SDK 接入

Ollama 暴露了 OpenAI 兼容 API，所以你可以直接用 OpenAI 的 Python SDK：

```python
from openai import OpenAI

# 只需要改 base_url，其他代码和用 OpenAI 一样
client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="not-needed",  # Ollama 不需要 API key
)

response = client.chat.completions.create(
    model="qwen2.5:7b",
    messages=[
        {"role": "system", "content": "你是一个专业的法律助手。"},
        {"role": "user", "content": "合同和协议有什么区别？"},
    ],
    temperature=0.7,
    max_tokens=512,
)

print(response.choices[0].message.content)
```

这意味着你现有的用 OpenAI SDK 的应用，只需要改一行 `base_url`，就能切换到本地模型。

## Step 3：和云端模型做对比

```python
def compare_local_vs_cloud(question: str):
    """对比本地模型和云端模型"""
    local_client = OpenAI(base_url="http://localhost:11434/v1", api_key="not-needed")
    cloud_client = OpenAI()  # 默认用 OPENAI_API_KEY 环境变量

    local_resp = local_client.chat.completions.create(
        model="qwen2.5:7b",
        messages=[{"role": "user", "content": question}],
    )
    cloud_resp = cloud_client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": question}],
    )

    print(f"问题：{question}")
    print(f"本地模型：{local_resp.choices[0].message.content[:200]}")
    print(f"云端模型：{cloud_resp.choices[0].message.content[:200]}")

# 测试
compare_local_vs_cloud("用 Python 实现一个 LRU 缓存，要求支持 get 和 put 操作。")
compare_local_vs_cloud("解释一下什么是 Docker 的多阶段构建，为什么需要它？")
```

对比时注意：
- 用多样化的问题测试，不要只测一个
- 覆盖你的业务场景的典型难度
- 除了正确性，还要看响应速度、输出格式稳定性

## Step 4：性能基准测试

```python
import time
import statistics

def benchmark(client: OpenAI, model: str, prompt: str, runs: int = 10) -> dict:
    """跑性能基准"""
    latencies = []

    for _ in range(runs):
        start = time.time()
        client.chat.completions.create(
            model=model,
            messages=[{"role": "user", "content": prompt}],
            max_tokens=256,
        )
        latencies.append(time.time() - start)

    latencies.sort()
    return {
        "p50": latencies[len(latencies) // 2],
        "p95": latencies[int(len(latencies) * 0.95)],
        "p99": latencies[int(len(latencies) * 0.99)],
        "avg": statistics.mean(latencies),
    }

# 测试
client = OpenAI(base_url="http://localhost:11434/v1", api_key="not-needed")
result = benchmark(client, "qwen2.5:7b", "用一句话解释什么是微调。")
print(f"P50: {result['p50']:.3f}s | P95: {result['p95']:.3f}s | P99: {result['p99']:.3f}s")
```

一个 "感觉还行" 的服务，P99 可能是 10 秒。必须量化。

## Step 5（可选）：vLLM 生产部署

如果需要高并发，切换到 vLLM：

```bash
# 安装 vLLM
pip install vllm

# 启动服务（OpenAI 兼容 API）
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --host 0.0.0.0 \
  --port 8000 \
  --max-model-len 4096
```

vLLM 的优势是 PagedAttention，高并发下吞吐量远超 Ollama。但配置更复杂，显存管理需要调参。

## 你可能遇到的问题

**Ollama 服务启动后连不上**：检查端口是否被占用（`lsof -i :11434`），防火墙是否放行。

**响应速度很慢**：可能是模型太大，显存不够导致部分层在 CPU 上运行。用 `ollama ps` 查看模型是否完全加载到 GPU。

**输出质量不如预期**：确认用的是正确的模型版本（`ollama list`）。同一个模型名可能有多个版本。

**vLLM 启动报 CUDA OOM**：减小 `--max-model-len`，或者用量化版本。vLLM 的显存管理比 Ollama 更激进。

---

## 容易犯的错

**本地模型一定比云端便宜**。GPU 服务器有固定成本。每月请求量低于几千次时，API 调用可能更划算。做 TCO 分析再决策。

**用简单问题测试就上线**。简单问答本地模型可能不错，但复杂推理、长文本理解、代码生成上和云端差距明显。测试集要覆盖业务场景的难度分布。

**不做性能测试就上线**。延迟、吞吐量、并发能力必须量化。一个 P99 10 秒的服务是不可接受的。

**忽略模型更新**。开源模型迭代很快，新版本通常有显著提升。部署后不关注迭代，半年后可能落后一个时代。

### 练习三：性能压测

用 `benchmark` 函数测试不同并发下的延迟变化：

```python
# 单线程 vs 多线程
from concurrent.futures import ThreadPoolExecutor

def concurrent_benchmark(client, model, prompt, concurrency: int):
    """并发性能测试"""
    def single_request():
        start = time.time()
        client.chat.completions.create(
            model=model,
            messages=[{"role": "user", "content": prompt}],
            max_tokens=128,
        )
        return time.time() - start

    with ThreadPoolExecutor(max_workers=concurrency) as pool:
        futures = [pool.submit(single_request) for _ in range(concurrency)]
        latencies = [f.result() for f in futures]

    print(f"并发 {concurrency}: 平均 {sum(latencies)/len(latencies):.3f}s, 最大 {max(latencies):.3f}s")

# 测试不同并发级别
for c in [1, 2, 4, 8]:
    concurrent_benchmark(client, "qwen2.5:7b", "用一句话解释微调。", c)
```

## 参考答案

### 练习一

部署完成后，确保：
- `ollama serve` 在后台运行
- OpenAI SDK 的 `base_url` 指向 `http://localhost:11434/v1`
- 多轮对话时把 assistant 的回复也 append 到 messages 列表

### 练习二

关键点：
- 用 `time.time()` 记录每个请求的延迟
- 质量评分需要人工判断，不要只看"对不对"，还要看"说得好不好"
- JSON 格式化输出最容易出问题——本地模型可能输出非标准 JSON

### 练习三

预期结果：
- 并发 1-2 时延迟接近
- 并发 4 以上时 Ollama 延迟明显上升（它不是为高并发设计的）
- 如果需要高并发，切换到 vLLM
