# 04 状态管理——Agent 间共享状态的设计与实现

> 多 Agent 系统的核心难题：多个 Agent 如何共享和协调状态？

## 场景引入

当多个 Agent 共同处理一个任务时，它们需要共享一些数据：查询结果、分析结论、错误信息。如果每个 Agent 自己维护一份状态，很快就会出现数据不一致的问题。你需要一个统一的状态管理方案，让所有 Agent 读写同一份"真相"。

## 学习目标

- 掌握多 Agent 状态管理的设计方法
- 理解状态共享和同步机制
- 学会处理状态冲突

## 一、状态设计原则

```
状态设计原则：

1. 单一数据源
   - 状态是唯一的真相来源
   - 避免状态分散在多个地方

2. 不可变更新
   - 状态更新返回新对象
   - 不直接修改原状态

3. 类型安全
   - 使用 TypedDict 定义状态结构
   - 编译时检查类型

4. 最小化
   - 状态只包含必要信息
   - 避免状态过大
```

## 二、状态管理实现

```python
from typing import TypedDict, Annotated
from operator import add

class MultiAgentState(TypedDict):
    messages: Annotated[list, add]  # 消息列表，自动累加
    current_agent: str
    task: str
    results: dict
    iteration: int
    errors: list

# 状态更新函数
def update_state(state: MultiAgentState, updates: dict) -> MultiAgentState:
    """安全地更新状态"""
    new_state = {**state}
    for key, value in updates.items():
        if key in new_state:
            if isinstance(new_state[key], list) and isinstance(value, list):
                new_state[key] = new_state[key] + value
            elif isinstance(new_state[key], dict) and isinstance(value, dict):
                new_state[key] = {**new_state[key], **value}
            else:
                new_state[key] = value
    return new_state
```

## 三、共享状态模式

```
共享状态模式：

1. 中心化状态
   - 所有 Agent 读写同一个状态
   - 简单，但可能有冲突

2. 消息传递
   - Agent 间通过消息通信
   - 每个 Agent 有自己的局部状态

3. 黑板模式
   - 共享的"黑板"存储数据
   - Agent 读写黑板上的数据

4. 事件驱动
   - Agent 发布事件
   - 其他 Agent 订阅事件
```

## 四、状态持久化

```python
import json

class StatePersistence:
    """状态持久化"""
    
    def __init__(self, storage_path: str):
        self.storage_path = storage_path
    
    def save_state(self, state_id: str, state: dict):
        """保存状态"""
        path = f"{self.storage_path}/{state_id}.json"
        with open(path, "w") as f:
            json.dump(state, f)
    
    def load_state(self, state_id: str) -> dict:
        """加载状态"""
        path = f"{self.storage_path}/{state_id}.json"
        with open(path, "r") as f:
            return json.load(f)
```

## 常见误区

1. **状态更新不是原子操作**：多个 Agent 同时读写同一个状态字段，可能导致数据竞争。在并发场景下，需要使用锁或消息队列来保证状态更新的原子性。
2. **状态过大影响性能**：把所有历史消息、中间结果、调试信息全部放进 State，导致 State 对象越来越大，每次节点传递都要序列化大量数据。State 应该只包含必要的运行时信息。
3. **没有状态持久化**：长时间运行的任务，如果进程崩溃，所有状态都丢失了。需要在关键检查点持久化状态，支持断点续传。

## 工程建议

1. **从单 Agent 开始，按需演进**：先用单 Agent 验证核心逻辑，当遇到上下文瓶颈、能力稀释或需要并行处理时，再拆分为多 Agent。不要为了"看起来高级"而引入多 Agent 架构。
2. **为每个 Agent 定义清晰的职责边界**：每个 Agent 应该有单一、明确的职责（如"只负责搜索""只负责分析"），输入输出格式在设计阶段就确定下来，避免职责重叠和数据格式混乱。
3. **建立可观测性基础设施**：从第一版开始就为每个 Agent 添加结构化日志和追踪机制，记录输入、输出、耗时、错误。多 Agent 系统的调试难度远高于单 Agent，没有日志就是在"盲人摸象"。
4. **在关键决策节点加入人工审批**：涉及高风险操作（删除数据、发送消息、支付）和不可逆操作时，使用 Human-in-the-loop 机制暂停执行，等待人类确认后再继续。
