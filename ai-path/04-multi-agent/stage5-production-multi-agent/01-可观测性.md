# 01 可观测性——多 Agent 系统的追踪、日志、指标设计

> 多 Agent 系统比单 Agent 复杂得多。可观测性是调试和优化的关键。

## 场景引入

你的多 Agent 系统在测试环境运行良好，但部署到生产后，用户反馈"有时候结果很奇怪"。你查看日志，只看到一堆分散的 API 调用记录，完全无法还原某个请求经过了哪些 Agent、每个 Agent 做了什么决策。没有可观测性，多 Agent 系统就是一个黑盒。

## 一、多 Agent 追踪

```python
class MultiAgentTracer:
    """多 Agent 追踪器"""
    
    def __init__(self):
        self.traces = {}
    
    def start_trace(self, trace_id: str, task: str):
        """开始追踪"""
        self.traces[trace_id] = {
            "id": trace_id,
            "task": task,
            "spans": [],
            "start_time": datetime.now().isoformat()
        }
    
    def add_span(self, trace_id: str, agent_name: str, action: str, result: str):
        """添加 Span"""
        self.traces[trace_id]["spans"].append({
            "agent": agent_name,
            "action": action,
            "result": result[:100],
            "timestamp": datetime.now().isoformat()
        })
    
    def end_trace(self, trace_id: str):
        """结束追踪"""
        self.traces[trace_id]["end_time"] = datetime.now().isoformat()
```

## 二、Agent 日志

```python
class AgentLogger:
    """Agent 日志"""
    
    def __init__(self, agent_name: str):
        self.agent_name = agent_name
        self.logger = structlog.get_logger()
    
    def log_execution(self, task: str, result: str, duration: float):
        """记录执行日志"""
        self.logger.info(
            "agent_execution",
            agent=self.agent_name,
            task=task[:100],
            result=result[:100],
            duration=duration
        )
    
    def log_error(self, task: str, error: str):
        """记录错误日志"""
        self.logger.error(
            "agent_error",
            agent=self.agent_name,
            task=task[:100],
            error=error
        )
```

## 三、多 Agent 指标

```python
class MultiAgentMetrics:
    """多 Agent 指标"""
    
    def __init__(self):
        self.agent_metrics = {}
    
    def record_agent_execution(self, agent_name: str, duration: float, success: bool):
        """记录 Agent 执行指标"""
        if agent_name not in self.agent_metrics:
            self.agent_metrics[agent_name] = {
                "total_executions": 0,
                "success_count": 0,
                "total_duration": 0
            }
        
        metrics = self.agent_metrics[agent_name]
        metrics["total_executions"] += 1
        metrics["total_duration"] += duration
        if success:
            metrics["success_count"] += 1
    
    def get_agent_summary(self, agent_name: str) -> dict:
        """获取 Agent 摘要"""
        metrics = self.agent_metrics.get(agent_name, {})
        return {
            "total_executions": metrics.get("total_executions", 0),
            "success_rate": metrics.get("success_count", 0) / metrics.get("total_executions", 1),
            "avg_duration": metrics.get("total_duration", 0) / metrics.get("total_executions", 1)
        }
```

## 四、监控 Dashboard

```python
def multi_agent_dashboard():
    """多 Agent 监控 Dashboard"""
    st.title("多 Agent 系统监控")
    
    # Agent 状态
    st.header("Agent 状态")
    agents = get_all_agents()

        col2.metric(f"{agent['name']} 成功率", f"{agent['success_rate']:.1%}")
        col3.metric(f"{agent['name']} 平均耗时", f"{agent['avg_duration']:.2f}s")
    
    # 执行追踪
    st.header("最近执行")
    traces = get_recent_traces()

                st.write(f"- [{span['agent']}] {span['action']}: {span['result']}")
```

## 常见误区

1. **日志粒度太粗**：只记录了"任务开始"和"任务结束"，中间经过了哪些 Agent、每个 Agent 做了什么决策完全无法追踪。需要在每个 Agent 的输入和输出都添加结构化日志。
2. **追踪 ID 没有贯穿整个链路**：用户请求、Supervisor 决策、Agent 执行、结果返回使用了不同的追踪 ID，无法将一个请求的完整链路串联起来。需要在请求入口生成唯一的 trace_id 并向下传递。
3. **指标只关注成功率，忽略延迟分布**：成功率 99% 看起来很好，但如果那 1% 的失败请求全部超时 30 秒，用户体验会非常差。需要同时监控 P50、P95、P99 延迟。

---

## 工程建议

1. **从单 Agent 开始，按需演进**：先用单 Agent 验证核心逻辑，当遇到上下文瓶颈、能力稀释或需要并行处理时，再拆分为多 Agent。不要为了"看起来高级"而引入多 Agent 架构。
2. **为每个 Agent 定义清晰的职责边界**：每个 Agent 应该有单一、明确的职责（如"只负责搜索""只负责分析"），输入输出格式在设计阶段就确定下来，避免职责重叠和数据格式混乱。
3. **建立可观测性基础设施**：从第一版开始就为每个 Agent 添加结构化日志和追踪机制，记录输入、输出、耗时、错误。多 Agent 系统的调试难度远高于单 Agent，没有日志就是在"盲人摸象"。
4. **在关键决策节点加入人工审批**：涉及高风险操作（删除数据、发送消息、支付）和不可逆操作时，使用 Human-in-the-loop 机制暂停执行，等待人类确认后再继续。
