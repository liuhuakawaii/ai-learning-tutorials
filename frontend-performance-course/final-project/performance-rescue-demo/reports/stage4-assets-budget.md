# 第四阶段：资源与预算报告

## 场景引入

优化完成后，你需要为页面建立资源预算——就像给项目设定"资源信用卡额度"，每次 PR 新增资源都要检查是否超标。没有预算的优化是不可持续的：这次你把 JS 从 800KB 优化到 180KB，下次同事加一个图表库又涨回 400KB。预算 + CI 检查才能让优化效果持久。

---

## 常见误区

1. **预算只看总大小不看细分**：总传输 500KB 达标，但 JS 占了 450KB、图片只有 50KB——资源分布不合理。应该按类型分别设预算。
2. **预算超标就放宽预算**：预算是约束，不是摆设。超标时应该先分析原因，能优化就优化，实在需要新功能才记录豁免理由。
3. **忽略第三方脚本预算**：第三方脚本往往是体积大户（GA + GTM + 客服 = 200KB+），但开发者容易忽略。应该单独设预算并限制数量。
4. **只做预算检查不做缓存策略**：预算控制体积，缓存控制重复访问速度。两者缺一不可。

## 工程建议

1. **按资源类型分别设预算**：JS ≤ 200KB、CSS ≤ 50KB、图片 ≤ 200KB、字体 ≤ 100KB、第三方 ≤ 100KB，总计 ≤ 500KB（gzip 后）。
2. **静态资源文件名带 hash + 缓存 1 年**：`Cache-Control: public, max-age=31536000, immutable`，配合构建工具的 contenthash，实现"永久缓存+即时更新"。
3. **用 bundlesize 在 CI 中自动检查**：在 package.json 中配置体积上限，CI 中运行 `npx bundlesize`，超标时构建失败。
4. **记录资源组成变化趋势**：每次构建后记录各类型资源的体积，画趋势图，及时发现体积膨胀。
