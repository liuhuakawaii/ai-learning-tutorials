# 第5课：Lighthouse 报告解读

> **课程定位**：学会使用 Lighthouse 做自动化性能审计，正确解读报告
> **前置知识**：了解 Core Web Vitals，会使用 Chrome DevTools
> **预计时长**：35 分钟

## 场景引入

你的团队要求每次 PR 合并前 Lighthouse Performance 得分必须 ≥ 90。你花了一天优化，终于跑到了 92 分，PR 顺利合并。但上线后用户反馈页面依然很慢。仔细一看报告才发现：你只看了分数，没看 Opportunities 部分里"Serve images in next-gen formats"预计能节省 2.1 秒——3MB 的 PNG 图片从未压缩过。Lighthouse 报告的价值不在分数本身，而在报告中那些具体的、可操作的优化建议。

---

## 学习目标

完成本课学习后，你将能够：

1. 通过 DevTools、CLI 和 PageSpeed Insights 运行 Lighthouse
2. 解读 Performance 得分的计算方式
3. 区分 Opportunities、Diagnostics 和 Passed Audits 三个部分
4. 从报告中提取最有价值的优化建议
5. 了解 Lighthouse 的局限性，避免过度依赖分数

## 二、运行 Lighthouse

### 2.1 DevTools 中运行

```
步骤：
1. 打开 Chrome DevTools（F12）
2. 切换到 "Lighthouse" 标签
3. 选择审计类别（至少选 "Performance"）
4. 选择设备（Mobile 或 Desktop）
5. 点击 "Analyze page load"
6. 等待约 30-60 秒
7. 查看报告
```

### 2.2 CLI 运行

```bash
# 全局安装
npm install -g lighthouse

# 运行审计
lighthouse https://example.com --output html --output-path ./report.html

# 指定设备为桌面端
lighthouse https://example.com --preset=desktop

# 只运行 Performance 类别
lighthouse https://example.com --only-categories=performance
```

### 2.3 PageSpeed Insights

```
访问 https://pagespeed.web.dev/

优势：
- 同时展示 Lab 数据（Lighthouse）和 Field 数据（CrUX）
- 不需要安装任何工具
- 结果可以分享链接
```

## 三、报告结构解读

### 3.1 Performance Score（性能得分）

```
┌─────────────────────────────────────────────────────────────────┐
│                    Performance Score 计算                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  得分范围：0-100 分                                              │
│                                                                 │
│  ┌───────────────────────────────────────────────────┐          │
│  │  0-49 分   ❌ 差（Poor）       红色               │          │
│  │  50-89 分  ⚠️ 需改进（Needs Improvement） 橙色    │          │
│  │  90-100 分 ✅ 良好（Good）      绿色              │          │
│  └───────────────────────────────────────────────────┘          │
│                                                                 │
│  得分由以下指标加权计算：                                        │
│  ┌───────────────────────────────────────────────────┐          │
│  │  指标                  权重                        │          │
│  ├───────────────────────────────────────────────────┤          │
│  │  TBT（Total Blocking Time）   30%                  │          │
│  │  LCP（Largest Contentful Paint） 25%               │          │
│  │  CLS（Cumulative Layout Shift）  25%               │          │
│  │  Speed Index                    15%               │          │
│  │  FCP（First Contentful Paint）   10%              │          │
│  │  TTI（Time to Interactive）      已废弃            │          │
│  └───────────────────────────────────────────────────┘          │
│                                                                 │
│  ⚠️ 注意：得分是 Lab 数据，不是 Field 数据                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.2 Metrics（核心指标）

```
报告顶部展示的核心指标：

  ┌──────────────────────────────────────────────────────────────┐
  │  指标               值        评级                           │
  ├──────────────────────────────────────────────────────────────┤
  │  FCP                1.2s      ✅ Good                        │
  │  LCP                2.8s      ⚠️ Needs Improvement           │
  │  TBT                350ms     ⚠️ Needs Improvement           │
  │  CLS                0.05      ✅ Good                        │
  │  Speed Index        2.1s      ✅ Good                        │
  └──────────────────────────────────────────────────────────────┘

  各指标含义：
  - FCP：第一个内容出现的时间
  - LCP：最大内容出现的时间
  - TBT：主线程被长任务阻塞的总时间（Lab 中替代 INP）
  - CLS：布局偏移总量
  - Speed Index：页面内容可见区域填充速度的视觉指标
```

## 四、常见审计项详解

```
┌─────────────────────────────────────────────────────────────────┐
│              常见 Opportunities 审计项                            │
├─────────────────────────────┬───────────────────────────────────┤
│  审计项                      │  问题和优化方向                    │
├─────────────────────────────┼───────────────────────────────────┤
│  Eliminate render-blocking   │  CSS/JS 阻塞了首次渲染            │
│  resources                   │  → defer/async JS, 内联关键 CSS   │
├─────────────────────────────┼───────────────────────────────────┤
│  Properly size images        │  图片尺寸过大                     │
│                              │  → 响应式图片 srcset              │
├─────────────────────────────┼───────────────────────────────────┤
│  Serve images in next-gen    │  使用了 JPEG/PNG 而非 WebP/AVIF  │
│  formats                     │  → 转换为现代格式                 │
├─────────────────────────────┼───────────────────────────────────┤
│  Reduce unused JavaScript    │  加载了不需要的 JS 代码           │
│                              │  → Code splitting, tree shaking  │
├─────────────────────────────┼───────────────────────────────────┤
│  Reduce unused CSS           │  加载了不需要的 CSS               │
│                              │  → 提取关键 CSS，异步加载其余     │
├─────────────────────────────┼───────────────────────────────────┤
│  Minify CSS / JavaScript     │  代码未压缩                       │
│                              │  → 使用构建工具压缩               │
├─────────────────────────────┼───────────────────────────────────┤
│  Enable text compression     │  未启用 Gzip/Brotli 压缩          │
│                              │  → 服务器配置压缩                 │
├─────────────────────────────┼───────────────────────────────────┤
│  Efficient cache policy      │  静态资源缓存策略不合理           │
│                              │  → 设置长期缓存 + 内容哈希        │
├─────────────────────────────┼───────────────────────────────────┤
│  Avoid chaining critical     │  关键资源有串行依赖链             │
│  requests                    │  → preload 关键资源               │
├─────────────────────────────┼───────────────────────────────────┤
│  Preload key requests        │  关键资源没有预加载               │
│                              │  → <link rel="preload">          │
└─────────────────────────────┴───────────────────────────────────┘
```

## 五、Lighthouse 的局限性

```
┌─────────────────────────────────────────────────────────────────┐
│                    Lighthouse 的局限性                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. 变异性（Variability）                                        │
│     每次运行结果可能不同，网络、CPU、服务器状态都会影响           │
│     → 建议：多次运行取中位数                                     │
│                                                                 │
│  2. 单页面测试                                                  │
│     只测试你输入的那一个 URL，不覆盖整个网站                     │
│     → 建议：测试多个关键页面                                     │
│                                                                 │
│  3. Lab 数据 only                                               │
│     无法反映真实用户在不同设备/网络下的体验                      │
│     → 建议：同时关注 CrUX Field 数据                             │
│                                                                 │
│  4. 无法测量 INP                                                │
│     INP 需要真实用户交互，Lab 环境无法模拟                       │
│     → TBT 是 Lab 中最接近 INP 的替代指标                         │
│                                                                 │
│  5. 不是性能的全部                                              │
│     得分高不代表用户体验好，得分低也不一定代表体验差              │
│     → 以真实用户数据为最终判断依据                               │
│                                                                 │
│  6. 模拟环境的局限                                              │
│     CPU 节流是模拟，不是真实降速                                  │
│     → 测试结果可能比真实低端设备好                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 常见误区

1. **只看分数不看 Opportunities**：Lighthouse 最有价值的部分是 Opportunities（优化机会），它按预计节省时间排序，告诉你具体该优化什么。分数只是一个摘要。
2. **只跑一次就下结论**：Lighthouse 每次运行结果可能不同，受网络、CPU、服务器状态影响。应该多次运行取中位数，或者用 Lighthouse CI 的 Median 计算。
3. **追求 100 分满分**：从 90 分到 100 分的投入产出比极低，可能需要花大量时间处理微小的优化。把精力放在 Opportunities 中节省时间最多的项目上。
4. **用 Lighthouse Mobile 分数代替真实移动体验**：Lighthouse 的 CPU 节流是模拟，不是真实降速。真实低端设备的性能可能比 Lighthouse 模拟的更差。

## 工程建议

1. **优先处理 Estimated Savings 最大的 Opportunities**：这些是投入产出比最高的优化项，通常能带来秒级的性能提升。
2. **在 CI 中集成 Lighthouse CI**：设定 Performance 得分阈值（如 ≥ 80），PR 不达标时自动阻断合并。
3. **同时测试 Mobile 和 Desktop**：两个模式的得分差距通常很大，Mobile 模式更能暴露性能问题。
4. **关注 Diagnostics 中的 JavaScript execution time**：如果 JS 执行时间过长，说明有长任务需要拆分，这直接影响 INP。

## 动手练习

### 练习一：运行并解读 Lighthouse

1. 选择一个网站，分别用 Mobile 和 Desktop 模式运行 Lighthouse
2. 对比两次结果的差异
3. 记录：Performance 得分、各指标值、前 3 个 Opportunities

### 练习二：分析 Opportunities

1. 找到报告中 Estimated Savings 最大的 3 个优化项
2. 逐个点击查看详情
3. 对每个优化项写出具体的修复方案

### 练习三：CLI 批量测试

```bash
# 对同一个页面运行 3 次，观察结果变异性
for i in 1 2 3; do
  lighthouse https://example.com --output json --output-path ./report-$i.json
done
```

## 小结

本课的核心要点：

1. **Performance Score 由 5 个指标加权计算**：TBT(30%)、LCP(25%)、CLS(25%)、SI(15%)、FCP(10%)
2. **Opportunities 是最有价值的部分**：按预计节省时间排序，优先处理排在前面的
3. **Diagnostics 提供诊断信息**：需要自行判断优化方案
4. **Lighthouse 是 Lab 数据**：无法替代 Field 数据，无法测量 INP
5. **多次运行取中位数**：变异性大，单次结果不可靠
