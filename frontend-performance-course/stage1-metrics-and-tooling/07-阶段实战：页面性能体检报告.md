# 第7课：阶段实战——页面性能体检报告

> **课程定位**：第一阶段综合实战，输出一份完整的页面性能体检报告
> **前置知识**：掌握 Core Web Vitals、DevTools、Lighthouse、性能归因方法
> **预计时长**：60 分钟

---

## 学习目标

完成本课学习后，你将能够：

1. 独立完成一个页面的性能体检
2. 使用 Lighthouse、Performance 面板、Network 面板采集数据
3. 将发现的问题按影响程度排序
4. 输出一份结构清晰的性能体检报告
5. 为后续优化工作建立优先级

## 五、优先级排序矩阵

```
┌─────────────────────────────────────────────────────────────────┐
│                    优先级排序矩阵                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│                    修复难度                                      │
│                    低          中          高                    │
│               ┌───────────┬───────────┬───────────┐             │
│          高   │  ⭐ P0    │   P1      │   P2      │             │
│  影           │  立刻做   │  尽快做   │  规划做   │             │
│  响           ├───────────┼───────────┼───────────┤             │
│  程     中    │   P1      │   P2      │   P3      │             │
│  度           │  尽快做   │  规划做   │  有空再做  │             │
│               ├───────────┼───────────┼───────────┤             │
│          低   │   P2      │   P3      │   P4      │             │
│               │  规划做   │  有空再做  │  可能不做  │             │
│               └───────────┴───────────┴───────────┘             │
│                                                                 │
│  排序规则：                                                      │
│  - 影响高 + 修复容易 = P0（立刻做）                              │
│  - 影响高 + 修复较难 = P1（尽快做）                              │
│  - 影响中 + 修复容易 = P1（尽快做）                              │
│  - 其他按优先级递减                                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 六、完整报告示例

```markdown
# 性能体检报告 - example.com

## 1. 基本信息
- 测试 URL：https://example.com/product-page
- 测试时间：2026-06-08
- 测试工具：Lighthouse 12.x, Chrome DevTools 126

## 2. Lighthouse 报告

### Mobile 模式
| 指标 | 值 | 评级 |
|------|-----|------|
| Performance | 45 | ❌ Poor |
| FCP | 1.8s | ✅ Good |
| LCP | 4.2s | ❌ Poor |
| TBT | 680ms | ❌ Poor |
| CLS | 0.22 | ⚠️ Needs Improvement |
| Speed Index | 3.5s | ⚠️ Needs Improvement |

### Top 3 Opportunities
1. **Serve images in next-gen formats** - 节省 2.1s
2. **Reduce unused JavaScript** - 节省 1.5s
3. **Eliminate render-blocking resources** - 节省 0.8s

## 3. Performance Trace

- LCP 元素：产品主图 `<img class="hero-product">`
- LCP 时间：4.2s
- 图片加载时间：2.0s-4.0s（2 秒才下载完）
- 原因：3MB 的 PNG 图片，没有压缩，没有 preload

- Long Tasks：3 个
  - app.js 执行：350ms
  - analytics.js 执行：180ms
  - vendor.js 执行：150ms

## 4. Network 分析

- 总资源：4.8MB，42 个请求
- JS：1.2MB（15 个文件）
- 图片：3.1MB（8 张图片）
- CSS：180KB（3 个文件）
- 字体：200KB（3 个字体文件）

## 5. 问题清单

### 问题 1：产品主图未压缩（PNG 3MB）
- 影响指标：LCP
- 证据：Network 面板显示 hero.png 大小 3MB，加载耗时 2s
- 根因：设计师提供的原图直接使用，未压缩和格式转换
- 影响程度：高
- 修复方案：转 WebP/AVIF，压缩至 200KB 以内，添加 preload

### 问题 2：首屏加载了不需要的 JS（analytics + chat）
- 影响指标：TBT, LCP
- 证据：analytics.js 180ms + chat.js 120ms 阻塞主线程
- 根因：同步加载了首屏不需要的第三方脚本
- 影响程度：高
- 修复方案：使用 defer 或延迟加载

### 问题 3：图片没有设置尺寸
- 影响指标：CLS
- 证据：Layout Shift Regions 显示产品图加载后偏移 0.15
- 根因：img 标签没有 width/height 属性
- 影响程度：中
- 修复方案：添加 width/height 或 aspect-ratio

### 问题 4：Web 字体未优化
- 影响指标：LCP, CLS
- 证据：3 个字体文件 200KB，font-display: block
- 根因：使用了默认的 font-display 设置
- 影响程度：中
- 修复方案：改用 font-display: swap，预加载关键字体

## 6. 优先级排序

| 优先级 | 问题 | 预期效果 |
|--------|------|----------|
| P0 | 产品主图压缩 | LCP -2s |
| P0 | 延迟加载第三方脚本 | TBT -300ms |
| P1 | 图片设置尺寸 | CLS -0.15 |
| P1 | 字体优化 | LCP -0.3s, CLS -0.05 |

## 7. 下一步行动

1. 立刻：压缩产品主图并转 WebP，添加 preload
2. 立刻：defer 第三方脚本
3. 本周：给所有图片添加 width/height
4. 本周：优化字体加载策略
```

## 小结

本课的核心要点：

1. **体检是优化的起点**：没有体检的优化是盲目的
2. **证据驱动**：每个问题都要有数据或截图支撑
3. **优先级排序**：影响大且容易修复的先做
4. **报告要标准化**：使用统一模板，便于团队沟通和跟踪
5. **Lab + Field**：尽量同时采集两种数据
