# 第6课：性能归因方法

> **课程定位**：从"发现问题"到"定位根因"，掌握系统化的性能归因思路
> **前置知识**：会使用 Chrome DevTools Performance 和 Lighthouse
> **预计时长**：40 分钟

## 场景引入

Lighthouse 报告显示你的页面 LCP 是 4.5 秒，评级为"差"。但报告只告诉你"最大内容绘制慢"，没告诉你具体原因。你盲目地压缩了所有图片，LCP 只从 4.5 秒降到了 4.2 秒。后来用 DevTools 的 Performance 面板一查，才发现 LCP 元素是一段文字，真正的瓶颈是 2MB 的 CSS 文件阻塞了渲染——和图片根本没关系。性能优化最怕的不是问题难，而是找错了方向。系统化的归因方法能帮你避免这种无效劳动。

---

## 学习目标

完成本课学习后，你将能够：

1. 针对 LCP 慢的问题，通过决策树快速定位根因
2. 针对 CLS 高的问题，找到导致布局偏移的元素和原因
3. 针对 INP 差的问题，定位是哪个交互、哪段代码导致的
4. 使用 Network 瀑布图分析资源加载瓶颈
5. 使用 Bundle 分析工具找出 JS 包中的"大胖子"

### 2.1 LCP 图片优化清单

```
LCP 元素是图片时的检查清单：

  ☐ 图片格式是否为 WebP 或 AVIF？
  ☐ 图片尺寸是否与显示尺寸匹配？（不要用 2000px 图显示 400px 区域）
  ☐ 是否使用了 <link rel="preload"> 提前加载？
  ☐ 是否使用了 fetchpriority="high"？
  ☐ 图片是否被 CSS/JS 阻塞了加载？
  ☐ 图片是否在首屏？如果是，不要用 loading="lazy"
  ☐ 是否使用了 CDN 分发图片？
```

```html
<!-- LCP 图片的最佳实践 -->
<link rel="preload" as="image" href="/hero.webp" type="image/webp">
<img src="/hero.webp"
     alt="Hero"
     width="800" height="600"
     fetchpriority="high"
     decoding="async">
```

### 2.2 LCP 文本优化清单

```
LCP 元素是文本时的检查清单：

  ☐ 关键 CSS 是否已内联？
  ☐ 非关键 CSS 是否异步加载？
  ☐ JS 是否使用了 defer 或 async？
  ☐ Web 字体是否使用了 font-display: swap/optional？
  ☐ 字体文件是否已预加载？
  ☐ 字体是否做了子集化？
  ☐ TTFB 是否 < 800ms？
```

## 三、CLS 归因方法

### 3.1 找到导致偏移的元素

```
方法 1：DevTools Layout Shift Regions
  1. 打开 DevTools → More tools → Rendering
  2. 勾选 "Layout Shift Regions"
  3. 刷新页面
  4. 发生偏移的元素会被蓝色/绿色高亮

方法 2：Performance 面板
  1. 录制页面加载
  2. 在主线程中找到 "Layout Shift" 色块
  3. 点击查看哪些元素发生了偏移

方法 3：web-vitals attribution
  onCLS((metric) => {
    for (const entry of metric.entries) {
      console.log('偏移元素:', entry.sources?.[0]?.node);
      console.log('偏移原因:', entry.sources?.[0]?.previousRect);
      console.log('偏移后:', entry.sources?.[0]?.currentRect);
    }
  });
```

```
│                                                                 │

│  │   → 添加 width/height 或 aspect-ratio                        │
```

## 四、INP 归因方法

### 4.1 INP 的三段式拆解

```
INP = 输入延迟 + 处理时间 + 呈现延迟

  ┌──────────┐ ┌──────────┐ ┌──────────┐
  │ 输入延迟  │ │ 处理时间  │ │ 呈现延迟  │
  │          │ │          │ │          │
  │ 主线程忙 │ │ JS 执行  │ │ Layout   │
  │ 事件排队 │ │ DOM 更新 │ │ Paint    │
  │          │ │          │ │ Composite│
  └──────────┘ └──────────┘ └──────────┘

  哪段最长？
  → 输入延迟长：主线程有长任务在执行
  → 处理时间长：事件处理函数太重
  → 呈现延迟长：DOM 变更触发了大面积回流
```

### 4.2 使用 web-vitals attribution 定位

```javascript
import { onINP } from 'web-vitals';

onINP((metric) => {
  const attr = metric.attribution;
  console.log('交互类型:', attr.interactionType);  // 'pointer' | 'keyboard'
  console.log('目标元素:', attr.interactionTarget);  // 比如 "button.submit"
  console.log('输入延迟:', attr.inputDelay);
  console.log('处理时间:', attr.processingDuration);
  console.log('呈现延迟:', attr.presentationDelay);
  console.log('事件处理脚本:', attr.eventEntry?.target);
});
```

### 4.3 使用 DevTools Interactions 面板

```
DevTools Performance 面板中的 Interactions 轨道：

  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  Interactions                                             │
  │  ┌──────┐  ┌──────┐                                     │
  │  │click │  │input │                                     │
  │  │120ms │  │350ms │ ← 橙色/红色 = 超过阈值               │
  │  └──────┘  └──────┘                                     │
  │                                                          │
  │  点击交互 → 查看详情：                                    │
  │  ├── Input Delay: 80ms（主线程有任务在排队）              │
  │  ├── Processing Time: 220ms（事件处理函数耗时长）         │
```

## 五、Network 瀑布图分析

### 5.1 如何读瀑布图

```
Network 瀑布图中的关键信息：

  ┌──────────────────────────────────────────────────────────┐
  │  资源名称    类型    大小    时间    瀑布图               │
  ├──────────────────────────────────────────────────────────┤
  │  index.html  doc    15KB   120ms   ██                   │
  │  styles.css  css    45KB   200ms     ████               │
  │  app.js      js     300KB  400ms     ████████           │
  │  hero.jpg    img    800KB  600ms       ██████████████   │
  │  font.woff2  font   30KB   150ms     ███               │
  └──────────────────────────────────────────────────────────┘

  颜色含义（在瀑布图中的色块）：
  ├── 浅灰 = 等待（Queuing）
  ├── 白色 = DNS/TCP/TLS
  ├── 绿色 = 等待服务器响应（TTFB）
  ├── 蓝色 = 内容下载
  └── 红色 = 阻塞时间

  关键观察点：
  1. 有没有资源阻塞了其他资源的加载？
  2. 资源是否可以并行加载？
  3. 有没有不必要的资源？
  4. TTFB 是否过长？
```

### 5.2 常见的瀑布图模式

```
模式 1：串行依赖链（问题）
  HTML ──→ CSS ──→ JS ──→ 图片
  每个资源都等前一个加载完才开始
  优化：preload、并行加载

模式 2：阻塞渲染（问题）
  HTML ████████████████
       ████████████████ ← CSS 阻塞渲染
       ██████████████████████ ← JS 阻塞解析
                             ← 到这里才开始渲染
  优化：内联关键 CSS、defer JS

模式 3：合理并行（好的模式）
  HTML ██
  CSS    ████
  JS     ████
  图片     ████████
  字体   ███
  所有资源尽可能并行加载
```

## 六、Bundle 分析

### 6.1 为什么要分析 Bundle？

```
你可能不知道你的 JS Bundle 里有什么：

  app.js (300KB gzip)
  ├── React + ReactDOM (120KB)
  ├── Lodash（全量引入）(70KB)
  ├── Moment.js + 所有语言包 (65KB)
  ├── 你的业务代码 (30KB)
  ├── Chart.js（首屏不需要）(10KB)
  └── 其他依赖 (5KB)

  问题：
  - Lodash 全量引入了 70KB，但你只用了 3 个函数
  - Moment.js 65KB，可以用 dayjs（2KB）替代
  - Chart.js 首屏不需要，应该懒加载
```

### 6.2 Bundle 分析工具

```bash
# Webpack：webpack-bundle-analyzer
npm install --save-dev webpack-bundle-analyzer
npx webpack-bundle-analyzer stats.json

# Vite：rollup-plugin-visualizer
npm install --save-dev rollup-plugin-visualizer

# Next.js：@next/bundle-analyzer
npm install @next/bundle-analyzer
```

## 常见误区

1. **只看 Lighthouse 分数就下结论**：Lighthouse 是实验室数据，网络条件和设备性能都是模拟的。真实用户的 LCP 可能比 Lighthouse 报告差 2-3 倍，必须结合 CrUX 等真实用户数据才能做出准确判断。

2. **把所有性能问题都归因于 JS 太大**：JS 包体积确实影响加载速度，但 LCP 更多受图片加载和服务器响应速度影响。盲目做代码分割而忽略图片优化和 CDN 配置，可能收效甚微。

3. **忽略瀑布图中的串行依赖**：很多开发者只关注单个资源的加载时间，忽略了资源之间的依赖关系。A 等 B 加载完才开始、B 又等 C——这种串行链条才是性能瓶颈的根源。

4. **把 INP 问题等同于 JS 执行慢**：INP 包含三段延迟（输入延迟、处理时间、呈现延迟），很多时候瓶颈在输入延迟（主线程被占用）而非处理时间本身。

---

## 工程建议

1. **建立"归因清单"模板**：为 LCP、CLS、INP 各建一个排查清单，按优先级排列检查项。新项目上线前按清单逐项检查，避免遗漏关键因素。

2. **在 CI 中集成性能归因脚本**：使用 Lighthouse CI 或 WebPageTest API 自动跑性能测试，当指标超过阈值时自动触发归因分析，而不是等用户投诉才手动排查。

3. **用 Chrome DevTools 的 Performance 录制功能做深度归因**：Lighthouse 报告只告诉你"什么慢"，Performance 录制能告诉你"为什么慢"。对关键页面定期录制，建立性能基线。

4. **区分"加载性能"和"运行时性能"**：LCP/CLS 是加载阶段的问题，INP 是运行阶段的问题。不要用加载优化手段（如预加载）去解决运行时问题（如长任务阻塞），反之亦然。

---

## 小结

本课的核心要点：

1. **LCP 归因**：先找到 LCP 元素 → 判断类型 → 检查加载链路 → 针对性优化
2. **CLS 归因**：找到偏移元素 → 判断原因 → 预留空间或优化加载策略
3. **INP 归因**：找到慢交互 → 拆解三段延迟 → 定位最慢的部分
4. **Network 瀑布图**：识别串行依赖链、阻塞资源、不必要的加载
5. **Bundle 分析**：找出 JS 包中的"大胖子"，按需加载、替换、tree shaking
