# 第3课：Lab 数据与 Field 数据

> **课程定位**：理解两种性能数据的本质区别，学会选择正确的测量方式
> **前置知识**：了解 Core Web Vitals（LCP、INP、CLS）
> **预计时长**：30 分钟

## 场景引入

你花了一周优化公司官网，Lighthouse 从 60 分提升到 95 分，团队一片欢呼。上线后老板在手机上打开："怎么还是这么慢？"你一脸困惑地跑了一遍 PageSpeed Insights，发现 CrUX 真实用户数据的 LCP P75 是 4.2 秒——和你笔记本上测的 1.5 秒天差地别。原因很简单：你在高性能 MacBook 上用模拟 4G 网络测试，而真实用户在地铁上用千元机 + 3G 信号访问。这就是 Lab 数据和 Field 数据的本质区别：一个是实验室里的理想条件，一个是真实世界的残酷现实。

---

## 学习目标

完成本课学习后，你将能够：

1. 用自己的话解释 Lab 数据和 Field 数据的本质区别
2. 说清楚为什么性能优化必须同时依赖两种数据
3. 列举至少 3 种获取 Lab 数据的工具和 3 种获取 Field 数据的方式
4. 使用 `web-vitals` 库在项目中采集真实用户性能数据
5. 识别"只优化 Lab 分数而忽略真实用户"这一常见陷阱

## 一、两种数据，两个世界

### 1.1 从一次"翻车"说起

你刚花了一周优化公司官网，Lighthouse 跑出了 95 分，团队一片欢呼。上线后老板打开手机一看："怎么还是这么慢？"

这不是段子，这是无数团队的真实经历。问题出在哪？**你优化的是 Lab 数据，而老板体验的是 Field 数据。**

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   Lab 数据（实验室数据）          Field 数据（真实用户数据）      │
│   ┌─────────────────────┐        ┌─────────────────────┐        │
│   │                     │        │                     │        │
│   │   固定设备           │        │   千差万别的设备     │        │
│   │   模拟 4G 网络       │        │   地铁上 3G 信号     │        │
│   │   空 CPU 负载        │        │   后台 20 个 App    │        │
│   │   每次结果一致       │        │   结果天差地别       │        │
│   │                     │        │                     │        │
│   │   Lighthouse: 95    │        │   P75 LCP: 4.2s     │        │
│   │                     │        │                     │        │
│   └─────────────────────┘        └─────────────────────┘        │
│                                                                 │
│          "实验室里一切完美"           "用户那边一塌糊涂"          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 一句话定义

- **Lab 数据（Lab Data）**：在受控环境中，用固定配置的设备和网络模拟用户访问，采集到的性能数据。
- **Field 数据（Field Data）**：也叫 RUM（Real User Monitoring），从真实用户的浏览器中采集到的性能数据。

## 二、Lab 数据详解

### 2.1 Lab 数据的核心工具

```
┌─────────────────────────────────────────────────────────────────┐
│                    Lab 数据采集工具                               │
├───────────────┬─────────────────────────────────────────────────┤
│  Lighthouse   │  Chrome 内置性能审计，0-100 分评分              │
│               │  提供具体优化建议，支持 CLI 和 CI                │
├───────────────┼─────────────────────────────────────────────────┤
│  WebPageTest  │  全球多地点测试，瀑布图、视频对比                │
│               │  支持自定义脚本，可模拟不同设备/网络             │
├───────────────┼─────────────────────────────────────────────────┤
│  Chrome       │  Performance 面板录制完整加载过程                │
│  DevTools     │  Network 面板查看资源瀑布图，支持节流模拟        │
├───────────────┼─────────────────────────────────────────────────┤
│  PageSpeed    │  Google 在线检测，底层用 Lighthouse + CrUX       │
│  Insights     │  同时展示 Lab 和 Field 数据                     │
└───────────────┴─────────────────────────────────────────────────┘
```

### 2.2 Lab 数据的优缺点

```
┌─────────────────────┬───────────────────────────────────────────┐
│  优点               │  缺点                                      │
├─────────────────────┼───────────────────────────────────────────┤
│  结果可重复         │  不代表真实用户体验                         │
│  可在上线前测试     │  无法覆盖所有设备/网络/地域组合             │
│  方便调试和定位问题  │  无法反映用户行为差异                       │
│  适合 CI/CD 集成    │  CPU 节流是模拟，不是真实降速               │
└─────────────────────┴───────────────────────────────────────────┘
```

## 三、Field 数据详解

### 3.1 Field 数据的采集过程

```
  用户A（北京·iPhone·5G）       用户B（成都·红米·4G）
  ┌──────────────┐              ┌──────────────┐
  │  LCP: 1.2s   │              │  LCP: 5.8s   │
  │  INP: 80ms   │              │  INP: 320ms  │
  │  CLS: 0.05   │              │  CLS: 0.15   │
  └──────┬───────┘              └──────┬───────┘
         │                             │
         └────────────┬────────────────┘
                      ▼
         ┌─────────────────────────┐
         │    汇聚成统计数据         │
         │    LCP P75 = 2.8s       │
         │    INP P75 = 180ms      │
         │    CLS P75 = 0.08       │
         └─────────────────────────┘
```

Google 评估 Core Web Vitals 时看的是 **P75**（第 75 百分位数），即"75% 的用户遇到的数值"。

### 3.2 Field 数据的核心来源

```
┌──────────────────┬──────────────────────────────────────────────┐
│  CrUX            │  Google 官方 Field 数据集，搜索排名的依据     │
│                  │  通过 API、BigQuery、Dashboard 可查            │
├──────────────────┼──────────────────────────────────────────────┤
│  web-vitals 库   │  Google 官方轻量 JS 库（~1.5KB）              │
│                  │  采集 LCP、INP、CLS，可自定义上报              │
├──────────────────┼──────────────────────────────────────────────┤
│  自建 RUM        │  PerformanceObserver + 自定义上报             │
│                  │  完全掌控数据维度和采样率                      │
├──────────────────┼──────────────────────────────────────────────┤
│  第三方 RUM      │  Sentry、Datadog、New Relic、阿里云 ARMS     │
│                  │  开箱即用，自带可视化面板                      │
└──────────────────┴──────────────────────────────────────────────┘
```

### 3.3 Field 数据的优缺点

```
┌─────────────────────┬───────────────────────────────────────────┐
│  优点               │  缺点                                      │
├─────────────────────┼───────────────────────────────────────────┤
│  反映真实用户体验   │  需要足够流量才有统计意义                   │
│  覆盖所有设备/网络  │  问题难以复现和调试                         │
│  Google 排名的依据  │  CrUX 需要 28 天积累数据                    │
│  可按维度下钻分析   │  INP 需要用户交互才能采集                   │
└─────────────────────┴───────────────────────────────────────────┘
```

## 四、Lab vs Field 完整对比

| 对比维度 | Lab 数据 | Field 数据 |
|---------|---------|-----------|
| **环境** | 受控、固定配置 | 真实、千差万别 |
| **设备** | 固定型号 | 用户实际设备 |
| **网络** | 模拟 4G/Slow 4G | 用户实际网络 |
| **可重复性** | 高 | 低 |
| **调试能力** | 强（可暂停、回放） | 弱（难复现） |
| **适用阶段** | 开发、CI/CD | 上线后监控 |
| **核心工具** | Lighthouse、DevTools | CrUX、web-vitals |
| **Google 排名** | 不直接影响 | 直接影响 |

## 五、正确的工作流

```
┌─────────────────────────────────────────────────────────────────┐
│                Lab + Field 协同工作流                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. Field 发现问题    "product 页面 LCP P75 = 4.2s"             │
│         │                                                       │
│         ▼                                                       │
│  2. Lab 复现定位      DevTools 发现首屏大图没 lazy load          │
│         │                                                       │
│         ▼                                                       │
│  3. Lab 验证修复      Lighthouse 确认 LCP 降到 1.8s             │
│         │                                                       │
│         ▼                                                       │
│  4. Field 确认效果    上线后 P75 LCP 回归到 2.0s 以内            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**一句话总结**：Field 发现问题 → Lab 定位问题 → Lab 验证修复 → Field 确认效果。

## 六、实操：获取性能数据

### 6.1 获取 CrUX 数据

**最简单的方式**：访问 https://pagespeed.web.dev/ ，输入 URL，下半部分就是 CrUX 数据。

```bash
# API 方式查询
curl "https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url=https://example.com&strategy=mobile"
```

### 6.2 使用 web-vitals 采集

```bash
npm install web-vitals
```

```javascript
import { onLCP, onINP, onCLS } from 'web-vitals';

function sendToAnalytics(metric) {
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating,
    page: window.location.pathname,
    timestamp: Date.now(),
  });

  if (navigator.sendBeacon) {
    navigator.sendBeacon('/api/vitals', body);
  } else {
    fetch('/api/vitals', { body, method: 'POST', keepalive: true });
  }
}

onLCP(sendToAnalytics);
onINP(sendToAnalytics);
onCLS(sendToAnalytics);
```

### 6.3 采样策略

```javascript
// 高流量网站不需要 100% 采集，1%-10% 采样率通常够用
const shouldSample = Math.random() < 0.1;

function report(metric) {
  if (!shouldSample) return;
  navigator.sendBeacon('/api/vitals', JSON.stringify(metric));
}

onLCP(report);
onINP(report);
onCLS(report);
```

## 常见误区

1. **追求 Lighthouse 100 分却不看线上数据**：Lighthouse 满分不代表用户体验好。Lab 数据是基准线，不是终点线。真正的性能标准是真实用户数据。
2. **只看一次 Lighthouse 结果就下结论**：Lab 数据有变异性，网络波动、CPU 负载、服务器状态都会影响结果。应该多次运行取中位数。
3. **用 Lab 数据代替 Field 数据做决策**：Google 搜索排名依据的是 CrUX Field 数据，不是 Lighthouse 分数。优化 Lab 分数但 Field 数据没有改善，等于白做。
4. **认为 Field 数据无法调试**：虽然 Field 数据难以复现，但 web-vitals 的 attribution 功能可以帮你定位问题元素和交互，结合 Lab 工具就能找到根因。

## 工程建议

1. **建立 Lab + Field 的完整工作流**：Field 发现问题 → Lab 定位问题 → Lab 验证修复 → Field 确认效果。
2. **在 CI 中集成 Lighthouse CI**：每次 PR 合并前自动跑 Lighthouse，设定性能分数阈值作为门禁，防止性能退化。
3. **设置合理的采样率**：高流量网站不需要 100% 采集，1%-10% 的采样率通常足够建立统计模型，同时减少对用户的影响。
4. **调严 Lab 环境**：如果 Lab 和 Field 差距太大，尝试用更慢的 CPU 节流（6x）和更慢的网络（Slow 3G）来模拟真实用户的低端环境。

## 七、常见陷阱：只优化 Lab 分数

## 小结

本课的核心要点：

1. **Lab 数据是"受控实验"**，可重复、可调试，适合开发阶段和 CI
2. **Field 数据是"真实世界"**，覆盖所有设备/网络/地域，是搜索排名依据
3. **两种数据缺一不可**：Lab 调试定位，Field 了解真实体验
4. **正确工作流**：Field 发现 → Lab 定位 → Lab 验证 → Field 确认
5. **警惕"只优化 Lab 分数"**：Lighthouse 100 分 ≠ 用户体验好
