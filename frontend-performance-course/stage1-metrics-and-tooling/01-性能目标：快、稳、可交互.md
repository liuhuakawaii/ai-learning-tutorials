# 第1课：性能目标：快、稳、可交互

> **课程定位**：前端性能与体验工程第一课，建立性能优化的全局认知
> **前置知识**：有前端开发基础（HTML/CSS/JS），了解浏览器基本工作原理
> **预计时长**：30 分钟

## 场景引入

你的团队刚完成了一个电商网站的改版，页面设计精美、功能完整。上线后老板在自己的旗舰手机上打开，体验流畅，非常满意。但运营数据显示：移动端转化率比改版前下降了 15%，跳出率上升了 20%。用低端安卓机测试才发现，首屏加载需要 6 秒，点击"加入购物车"按钮后将近 1 秒才有反应，页面加载过程中广告位把商品列表挤来挤去，用户经常误点。这些"看不见"的问题，正是前端性能优化要解决的核心——用户不会告诉你页面慢，他们只会默默离开。

## 一、为什么性能很重要？

### 1.1 一个真实的数字

```
┌─────────────────────────────────────────────────────────────────┐
│                    性能差的代价                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Amazon：页面加载每慢 100ms，销售额下降 1%                      │
│                                                                 │
│   Google：搜索结果展示每慢 500ms，流量下降 20%                   │
│                                                                 │
│   BBC：页面加载每多 1 秒，流失 10% 的用户                        │
│                                                                 │
│   Vodafone：LCP 优化 31%，潜在客户增加 8%                        │
│                                                                 │
│   Yahoo：页面加载每快 400ms，流量增加 9%                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

这些不是理论数据，是真实发生的商业损失。性能就是钱。

### 1.2 用户感知的三个维度

前端性能不是一个单一的指标，用户从三个维度感知你的页面是否"好用"：

```
┌─────────────────────────────────────────────────────────────────┐
│                用户感知的三个维度                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   🏃 快（Speed）                                                │
│   ├── 页面内容多快能展示出来？                                   │
│   ├── 用户看到的第一个画面是什么时候？                           │
│   ├── 最大的内容块（图片、标题）什么时候出现？                   │
│   └── 对应指标：LCP（Largest Contentful Paint）                  │
│                                                                 │
│   🔒 稳（Stability）                                            │
│   ├── 页面加载过程中内容会不会乱跳？                             │
│   ├── 图片加载后下面的文字会不会被挤下去？                       │
│   ├── 广告弹出后整个页面会不会抖动？                             │
│   └── 对应指标：CLS（Cumulative Layout Shift）                   │
│                                                                 │
│   ⚡ 可交互（Interactivity）                                     │
│   ├── 点击按钮后多久才有反应？                                   │
│   ├── 输入框打字会不会卡顿？                                     │
│   ├── 页面滚动是否流畅？                                         │
│   └── 对应指标：INP（Interaction to Next Paint）                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 二、快：页面加载速度

### 2.1 什么是"快"？

用户对"快"的感知不是看你服务器响应多快，而是**他们多久能看到有意义的内容**。

```
用户打开页面后的心理时间线：

  0ms        页面空白 ────────────────────── 用户：还在等...
  │
  500ms      开始出现内容 ────────────────── 用户：好像在加载
  │
  1000ms     主要内容出现 ────────────────── 用户：可以了
  │
  2500ms     所有内容加载完成 ────────────── 用户：不错
  │
  4000ms     还在转圈 ────────────────────── 用户：怎么这么慢？
  │
  8000ms     还是空白 ────────────────────── 用户：算了不等了（关闭页面）
```

### 2.2 Google 的速度标准

Google 把页面速度分成了三个等级：

```
┌──────────────────────────────────────────────────────────────┐
│              LCP（最大内容绘制）速度标准                       │
├────────────────┬─────────────────┬───────────────────────────┤
│     Good       │ Needs Improve   │        Poor               │
│    ✅ 良好      │  ⚠️ 需改进      │       ❌ 差                │
├────────────────┼─────────────────┼───────────────────────────┤
│   ≤ 2.5 秒     │  2.5 ~ 4 秒     │       > 4 秒              │
├────────────────┼─────────────────┼───────────────────────────┤
│  75% 的用户    │  部分用户感到    │  大量用户流失              │
│  能接受        │  不耐烦          │  转化率显著下降            │
└────────────────┴─────────────────┴───────────────────────────┘
```

**LCP（Largest Contentful Paint）** 就是页面上最大的那个内容块出现的时间。通常是：
- 一张 Hero 图片
- 一个大标题
- 视频的封面图

## 三、稳：视觉稳定性

### 3.1 什么是"稳"？

你有没有遇到过这种情况：

```
你正在看一篇文章，准备点击一个链接

  ┌──────────────────────────────┐
  │  标题                        │
  │  ───────────────────────     │
  │  一些正文内容...              │
  │  [点击这里查看详情]  ← 你准备点这里
  │  更多内容...                 │
  └──────────────────────────────┘

突然一个广告加载出来，整个页面往下移了：

  ┌──────────────────────────────┐
  │  标题                        │
  │  ───────────────────────     │
  │  ╔══════════════════════╗    │
  │  ║   广告 Banner         ║    │  ← 刚加载出来的广告
  │  ╚══════════════════════╝    │
  │  一些正文内容...              │
  │  [点击这里查看详情]           │  ← 链接被挤下去了
  │  更多内容...                 │
  └──────────────────────────────┘

你点到了广告，而不是你想点的链接。
```

这就是**布局抖动（Layout Shift）**——页面内容在用户眼前移动。

### 3.2 CLS 的标准

```
┌──────────────────────────────────────────────────────────────┐
│              CLS（累积布局偏移）标准                           │
├────────────────┬─────────────────┬───────────────────────────┤
│     Good       │ Needs Improve   │        Poor               │
│    ✅ 良好      │  ⚠️ 需改进      │       ❌ 差                │
├────────────────┼─────────────────┼───────────────────────────┤
│   ≤ 0.1        │  0.1 ~ 0.25     │       > 0.25              │
├────────────────┼─────────────────┼───────────────────────────┤
│  页面稳定      │  偶尔有抖动      │  频繁抖动，影响操作        │
└────────────────┴─────────────────┴───────────────────────────┘
```

### 3.3 常见的布局抖动来源

```
导致 CLS 的常见原因：

  1. 图片没有设置宽高
     <img src="photo.jpg">  ← 没有 width/height
     图片加载完成后才撑开空间

  2. 动态插入的内容
     广告、Cookie 提示、通知栏
     从上面插入，把下面的内容往下挤

  3. Web 字体加载
     FOUT（Flash of Unstyled Text）
     字体加载完成后文字宽度变化，导致布局重排

  4. 动态计算高度
     JS 读取 API 数据后渲染列表
     列表高度不确定，影响下方元素位置
```

## 四、可交互：响应速度

### 4.1 什么是"可交互"？

页面加载完成了，用户能看到内容了，但这不等于页面就"好用"了。如果用户点了按钮，过了半秒页面才反应——这就是交互延迟。

```
用户交互的时间感知：

  ┌────────────────────────────────────────────────────┐
  │                                                    │
  │   0 ~ 100ms    感觉是"即时"的                       │
  │   用户心理：这个按钮响应真快                         │
  │                                                    │
  │   100 ~ 300ms  感觉有延迟但可接受                    │
  │   用户心理：稍微慢了点，但还行                       │
  │                                                    │
  │   300ms ~ 1s   明显感觉卡                           │
  │   用户心理：这个网站有点卡                           │
  │                                                    │
  │   > 1s         完全失去耐心                          │
  │   用户心理：是不是没点到？再点一次（重复操作）         │
  │                                                    │
  │   > 5s         放弃                                 │
  │   用户心理：算了不用了                               │
  │                                                    │
  └────────────────────────────────────────────────────┘
```

### 4.2 INP 的标准

**INP（Interaction to Next Paint）** 衡量的是用户交互后页面多久能更新视觉反馈。

```
┌──────────────────────────────────────────────────────────────┐
│              INP（交互到下次绘制）标准                         │
├────────────────┬─────────────────┬───────────────────────────┤
│     Good       │ Needs Improve   │        Poor               │
│    ✅ 良好      │  ⚠️ 需改进      │       ❌ 差                │
├────────────────┼─────────────────┼───────────────────────────┤
│   ≤ 200ms      │  200 ~ 500ms    │       > 500ms             │
├────────────────┼─────────────────┼───────────────────────────┤
│  操作流畅      │  偶尔卡顿        │  明显卡顿，影响使用        │
└────────────────┴─────────────────┴───────────────────────────┘
```

### 4.3 为什么页面会"卡"？

```
主线程被占用的原因：

  主线程（Main Thread）
  ┌──────────────────────────────────────────────────────┐
  │                                                      │
  │  ╔═══════════════════╗                               │
  │  ║  执行一大段 JS     ║ ← 任务太长，主线程被占用       │
  │  ║  （500ms+）        ║                               │
  │  ╚═══════════════════╝                               │
  │           ↑                                          │
  │           │                                          │
  │     用户此时点击按钮                                   │
  │     事件被排在队列里等待                               │
  │     主线程忙完 JS 才能处理点击事件                      │
  │           │                                          │
  │           ↓                                          │
  │  ╔═══════════════════╗                               │
  │  ║  处理点击事件       ║ ← 延迟了 500ms 才开始处理     │
  │  ╚═══════════════════╝                               │
  │                                                      │
  └──────────────────────────────────────────────────────┘

  这 500ms 就是用户的等待时间。
```

常见原因：
- 大量未优化的 JavaScript 一次性执行
- 复杂的 DOM 操作（如表格排序、列表渲染）
- 同步的布局计算（强制回流）
- 第三方脚本（广告、分析、聊天插件）

## 五、Core Web Vitals 概览

### 5.1 三大指标总结

```
┌─────────────────────────────────────────────────────────────────┐
│                 Core Web Vitals 一览                             │
├─────────┬──────────────┬─────────────┬─────────────┬───────────┤
│  指标   │  衡量什么     │   Good      │  Needs Imp  │   Poor    │
├─────────┼──────────────┼─────────────┼─────────────┼───────────┤
│  LCP    │  加载速度     │  ≤ 2.5s     │  2.5~4s     │  > 4s     │
│         │  内容何时可见 │             │             │           │
├─────────┼──────────────┼─────────────┼─────────────┼───────────┤
│  INP    │  交互响应     │  ≤ 200ms    │  200~500ms  │  > 500ms  │
│         │  操作后多久   │             │             │           │
│         │  有视觉反馈   │             │             │           │
├─────────┼──────────────┼─────────────┼─────────────┼───────────┤
│  CLS    │  视觉稳定性   │  ≤ 0.1      │  0.1~0.25   │  > 0.25   │
│         │  内容是否乱跳 │             │             │           │
└─────────┴──────────────┴─────────────┴─────────────┴───────────┘
```

### 5.2 它们在页面生命周期中的位置

```
页面加载时间线：

  ←─── 加载阶段 ──────────────────────────────────→  交互阶段 ──→

  DNS → TCP → TLS → 请求 → 响应 → 解析 → 渲染 → 用户操作
                                                    ↓
  ├── TTFB ──┤                                      INP
                    ├── FCP ──┤
                              ├── LCP ──┤
                                        ├── CLS 持续测量 ──→

  TTFB = Time to First Byte（服务器响应速度）
  FCP  = First Contentful Paint（第一个内容出现）
  LCP  = Largest Contentful Paint（最大内容出现）
  INP  = Interaction to Next Paint（交互响应）
  CLS  = Cumulative Layout Shift（布局稳定性）
```

## 七、建立正确的优化思维

### 7.1 先测量，再优化

```
┌─────────────────────────────────────────────────────────────────┐
│              正确的性能优化流程                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ❌ 错误做法：                                                  │
│   "我觉得页面很慢，先压缩一下图片吧"                             │
│   → 没有数据支撑，可能根本不是图片的问题                         │
│                                                                 │
│   ✅ 正确做法：                                                  │
│   1. 先用工具测量，拿到数据                                      │
│   2. 找到最大的瓶颈是什么                                        │
│   3. 针对性优化                                                  │
│   4. 再次测量，对比效果                                          │
│   5. 记录优化前后的数据                                          │
│                                                                 │
│   口诀：测量 → 定位 → 优化 → 验证 → 记录                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 7.2 Lighthouse 分数不是一切

```
一个常见的误区：

  ┌──────────────────────────────────────┐
  │                                      │
  │  Lighthouse Performance: 98 分       │
  │  ─────────────────────────           │
  │                                      │
  │  "我们的网站性能非常好！"             │
  │                                      │
  │  但是...                             │
  │                                      │
  │  真实用户数据（CrUX）：              │
  │  LCP P75 = 4.5s   (Poor!)           │
  │  INP P75 = 380ms  (Needs Imp!)      │
  │  CLS P75 = 0.32   (Poor!)           │
  │                                      │
  │  Lighthouse 是在你的笔记本上跑的      │
  │  真实用户用的是千元机 + 3G 网络       │
  │                                      │
  └──────────────────────────────────────┘
```

**关键认知**：
- Lighthouse 是 Lab 数据（实验室数据）
- 真实用户的数据才是 Field 数据
- 你需要同时关注两者，但最终以 Field 数据为准
- 我们会在第 3 课详细讲解 Lab 和 Field 数据的区别

## 动手练习

### 练习一：打开 Lighthouse 跑一次测试

```
步骤：
1. 打开 Chrome 浏览器
2. 访问你常用的任意一个网站
3. 按 F12 打开 DevTools
4. 切换到 "Lighthouse" 面板
5. 选择 "Performance" 类别
6. 点击 "Analyze page load"
7. 记录 Performance 得分和三个核心指标的数值

问题：
- 这个网站的 LCP、INP、CLS 分别是多少？
- 哪个指标最差？你觉得可能是什么原因？
```

### 练习二：感受布局抖动

```
步骤：
1. 找一个新闻网站或博客
2. 在手机上打开（或者用 DevTools 模拟手机）
3. 等页面加载完成
4. 从头到尾慢慢滚动
5. 观察是否有内容突然跳动或位移

问题：
- 你观察到了几次布局抖动？
- 每次抖动是什么原因导致的？（图片加载？广告？动态内容？）
- 如果你是这个网站的开发者，你会怎么修复？
```

### 练习三：感受交互延迟

```
步骤：
1. 打开一个大型 SPA 应用（如 Gmail、Figma 网页版、或你自己的项目）
2. 打开 DevTools → Performance 面板
3. 开启 CPU 4x 节流（模拟低端设备）
4. 在页面上进行操作：点击按钮、输入文字、切换 Tab
5. 观察操作后的响应延迟

问题：
- 在 CPU 节流的情况下，哪些操作明显变卡了？
- 这种卡顿对用户体验有什么影响？
- 你认为开发者可以做什么来改善这种情况？
```

## 常见误区

1. **只在高端设备上测试**：开发者的 MacBook Pro 上一切流畅，但真实用户可能用的是千元安卓机 + 3G 网络。性能优化必须覆盖低端设备场景。
2. **把 Lighthouse 分数当作最终目标**：Lighthouse 98 分不等于用户体验好。Lighthouse 是实验室数据，真实用户的网络、设备、地域差异都会导致完全不同的体验。
3. **凭感觉优化而不是用数据驱动**：觉得"图片可能太大了"就去压缩图片，但实际瓶颈可能在服务器响应慢或 JS 阻塞渲染。没有测量的优化是盲目的。
4. **只关注加载速度，忽视交互响应和视觉稳定性**：页面加载快不代表体验好，用户点击按钮后卡顿、内容乱跳同样是严重的性能问题。

## 工程建议

1. **建立性能预算**：在项目初期就设定明确的性能目标（如 LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1），并在 CI/CD 中加入性能检测门禁。
2. **用真实设备测试**：至少准备一台低端安卓机作为测试机，不要只依赖 Chrome DevTools 的 CPU 节流模拟。
3. **先测量再优化**：用 Lighthouse、DevTools Performance 面板或 web-vitals 库采集数据，找到最大的瓶颈再动手。
4. **性能优化是持续过程**：不是一次优化就完事，要建立线上监控机制，持续追踪 Core Web Vitals 的变化趋势。

## 小结

本课的核心要点：

1. **性能影响商业指标**：Amazon 的 100ms 延迟 = 1% 销售额损失，这不是理论数据
2. **用户感知三个维度**：快（LCP）、稳（CLS）、可交互（INP）
3. **Core Web Vitals 是 Google 的标准**：LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1 为"良好"
4. **性能是搜索排名因素**：内容相近时，性能更好的页面排名更高
5. **先测量再优化**：没有数据支撑的优化是盲目的
