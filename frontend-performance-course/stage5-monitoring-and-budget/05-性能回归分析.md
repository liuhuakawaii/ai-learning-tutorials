# 第5课：性能回归分析

> **课程定位**：发现、诊断和修复性能退化
> **前置知识**：了解性能监控和 Web Vitals 采集
> **预计时长**：30 分钟

## 场景引入

周一早上你打开性能监控面板，发现 LCP P75 从 1.8s 飙升到了 3.2s——上周五还是正常的。你查看最近的 PR，发现周末有 5 个 PR 合并，每个看起来都"没问题"。但其中有一个 PR 引入了一个 200KB 的图表库，另一个 PR 新增了一个同步加载的第三方脚本。每个 PR 单独看影响不大，但叠加起来就导致了性能回归。你需要一套机制，能快速定位是哪个 commit 引入了性能退化。

---

## 学习目标

1. 理解什么是性能回归
2. 掌握发现性能回归的方法
3. 学会诊断性能回归的原因
4. 建立性能回归的处理流程

## 一、什么是性能回归

```
┌──────────────────────────────────────────────────────────────┐
│              性能回归                                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  定义：性能指标随时间恶化                                     │
│                                                              │
│  常见原因：                                                   │
│  - 新增功能增加了 JS 体积                                    │
│  - 引入了大型依赖                                            │
│  - 新增了第三方脚本                                          │
│  - 数据量增长导致渲染变慢                                    │

│  - API 响应变慢                                              │
│                                                              │
│  特点：                                                       │
│  - 渐进式：每次退化一点，不易察觉                             │
│  - 累积式：多次小退化累积成大问题                             │
│  - 隐蔽性：开发环境可能不明显                                 │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 二、发现性能回归

### 2.1 CI 中检测

```yaml
# GitHub Actions：PR 时运行 Lighthouse
- name: Lighthouse CI
  run: lhci autorun
  # 断言失败时阻止合并
```

```javascript
// lighthouserc.js
assertions: {
  'categories:performance': ['error', { minScore: 0.9 }],
  'largest-contentful-paint': ['error', { maxNumericValue: 2500 }],
  'cumulative-layout-shift': ['error', { maxNumericValue: 0.1 }],
}
```

### 2.2 线上监控告警

```javascript
// 设置告警阈值
const ALERT_THRESHOLDS = {
  LCP: { warning: 2500, critical: 4000 },
  INP: { warning: 200, critical: 500 },
  CLS: { warning: 0.1, critical: 0.25 },
};

function checkRegression(metric) {
  const threshold = ALERT_THRESHOLDS[metric.name];
  if (!threshold) return;

  // 计算 7 天移动平均
  const avg7d = get7DayAverage(metric.name);
  const current = metric.value;

  // 如果当前值比 7 天平均差 20% 以上
  if (current > avg7d * 1.2) {
    sendAlert({
      type: 'performance-regression',
      metric: metric.name,
      current,
      average: avg7d,
      change: ((current - avg7d) / avg7d * 100).toFixed(1) + '%',
    });
  }
}
```

### 2.3 版本对比


## 三、诊断性能回归

### 3.1 二分查找

```
┌──────────────────────────────────────────────────────────────┐
│              二分查找法                                        │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  步骤：                                                       │
│  1. 确定性能正常的时间点（commit A）                          │
│  2. 确定性能退化的时间点（commit B）                          │
│  3. 取中间点 commit C                                        │
│     - 如果 C 正常 → 问题在 C-B 之间                          │
│     - 如果 C 退化 → 问题在 A-C 之间                          │
│  4. 重复直到找到具体 commit                                  │
│                                                              │
│  工具：                                                       │
│  - git bisect                                                │
│  - 手动测试                                                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

```bash
# 使用 git bisect
git bisect start
git bisect bad HEAD          # 当前版本有性能问题
git bisect good abc1234      # 之前的正常版本

# Git 会自动 checkout 中间版本
# 测试性能后标记
git bisect good  # 或 git bisect bad

# 重复直到找到具体 commit
```

## 常见误区

1. **性能回归只看 Lighthouse 分数**：Lighthouse 分数是 Lab 数据，受测试环境影响大。真正的性能回归应该看线上 Web Vitals 的 P75 变化——如果线上 LCP P75 突然升高，才是真正的回归。
2. **发现回归后立即回滚**：回滚是紧急手段，不是常规流程。应该先评估影响范围（哪些页面、多少用户、退化了多少），如果影响不大，可以在正常迭代中修复。
3. **用 git bisect 时只跑一次 Lighthouse**：Lighthouse 分数有波动，单次测试可能误判。每个 commit 应该至少跑 3 次取中位数，或者用更稳定的指标（如 JS 体积）做初筛。
4. **只修复当前回归，不复盘流程**：每次回归都应该问"为什么 CI 没有发现？"——是断言太松、测试页面不全、还是根本没跑 Lighthouse？修复流程比修复问题更重要。

## 工程建议

1. **在采集数据中嵌入版本号**：构建时把 `GIT_COMMIT_SHA` 注入到前端代码中，采集 Web Vitals 时附带版本号，这样在看板中可以按版本对比指标变化。
2. **设置 7 天移动平均告警**：不要对单次指标波动告警（会产生噪音）。计算 7 天移动平均，当前值比平均值高 20% 以上时才告警，这样能过滤掉正常的日间波动。
3. **用 bundle size diff 做 PR 级检测**：在 CI 中运行 `bundlesize`，对比 PR 前后的 JS/CSS 体积变化。体积增长超过 10KB 时在 PR 中评论提醒，让 reviewer 关注。
4. **建立回归处理 SOP**：发现 → 评估（影响范围）→ 诊断（定位 commit）→ 修复 → 复盘（更新检查规则）。把 SOP 写成文档，让团队每个人都知道怎么处理。

## 小结

1. **性能回归**：性能指标随时间恶化，渐进且隐蔽
2. **发现**：CI 断言、线上告警、版本对比
3. **诊断**：二分查找、资源分析、性能分析
4. **修复**：找到原因 → 实施优化 → 验证效果
5. **复盘**：为什么没发现？如何防止？
