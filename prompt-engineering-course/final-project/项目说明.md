# 综合项目：Prompt Engineering Toolkit

## 场景引入

在实际产品开发中，团队常常面临这样的困境：精心设计的 Prompt 在测试环境中表现良好，一旦上线就频繁出现输出格式不一致、Token 成本失控、响应质量波动等问题。手动调试 Prompt 费时费力，不同开发者各自为战导致模板无法复用，出了问题也难以追溯和定位。你需要一套工程化的工具链，将 Prompt 的设计、测试、优化和监控纳入标准化流程，让团队能像管理代码一样管理 Prompt。

## 项目概述

构建一个完整的 Prompt Engineering 工具包（Prompt Engineering Toolkit），整合课程所学的全部知识，实现从模板管理、测试评估、优化分析到生产监控的端到端 Prompt 工程化流程。

## 项目目标

1. **模板引擎**：实现可复用的 Prompt 模板系统，支持变量替换、条件渲染、模板继承
2. **测试评估**：构建 Prompt 测试框架，支持批量运行、自动评分、报告生成
3. **优化分析**：实现 Prompt 质量分析和优化建议，支持 Token 成本追踪
4. **生产监控**：构建 Prompt 运行监控系统，支持性能追踪、错误告警、仪表盘展示

## 功能要求

### 模板引擎（template_engine）

- 支持 Jinja2 语法的 Prompt 模板解析
- 变量类型定义、默认值、必填校验
- 条件渲染和循环渲染
- 模板继承与组合
- 渲染结果的格式验证

### 测试评估（testing）

- 测试用例定义（输入、期望输出、评估标准）
- 批量运行测试用例
- 多维度自动评分（精确匹配、语义相似、格式合规）
- HTML/Markdown 格式的测试报告

### 优化分析（optimizer）

- Prompt 长度和复杂度分析
- Token 使用量估算和成本计算
- 指令清晰度评分
- 优化建议生成（精简、拆分、补充）

### 生产监控（monitor）

- Prompt 调用追踪（延迟、Token、成功率）
- 错误分类和告警
- 运行趋势分析
- 监控数据可视化仪表盘

## 技术要求

- **Python 3.10+**
- 使用 **Pydantic** 进行数据验证
- 使用 **Jinja2** 作为模板引擎
- 使用 **Rich** 进行终端输出美化
- 使用 **pytest** 编写测试
- 代码需通过 `ruff` 检查
- 所有公共 API 需有类型注解

## 验收标准

- [ ] 模板引擎能正确解析和渲染包含变量、条件、循环的 Prompt 模板
- [ ] 测试框架能批量运行测试用例并生成评分报告
- [ ] 优化器能分析 Prompt 并给出具体的优化建议
- [ ] 监控模块能追踪调用数据并生成可视化仪表盘
- [ ] `scripts/check.py` 能通过所有完整性检查
- [ ] 所有模块有完整的类型注解和文档字符串
- [ ] 项目能通过 `pytest` 测试

## 常见误区

- 把模板引擎做得过于复杂，支持了大量永远不会用到的语法特性，反而增加了维护成本
- 测试用例只覆盖"正常路径"，忽略了边界情况（空输入、超长输入、特殊字符），上线后频繁出错
- 监控只关注延迟和成功率，忽略了 Token 成本的趋势变化，月底账单远超预期
- 优化建议模块过度依赖规则而非实际数据，给出的建议脱离业务上下文

## 工程建议

- 模板引擎优先支持 Jinja2 的核心子集（变量、条件、循环），不要自己造轮子
- 测试框架应支持"快照测试"——记录上次的输出作为基线，后续改动自动对比差异
- 监控仪表盘建议使用 Prometheus + Grafana 方案，社区生态成熟且可视化能力强
- 优化分析模块应结合实际调用数据（而非纯规则），用统计方法识别低效 Prompt
