# 第三课：缓存策略与数据一致性

## 场景引入

你的 SaaS 产品有一个数据看板页面，每次刷新都要等 2 秒才能看到数据。产品经理问你"能不能快一点"，你加上了缓存，页面秒开了。但第二天用户投诉："我明明更新了项目名称，页面上显示的还是旧的。"你发现是缓存没有及时失效。更麻烦的是，两个管理员同时编辑同一个项目，页面显示的数据互相覆盖，用户看到的是"幽灵数据"。缓存带来了速度，也带来了一致性难题。

## 学习目标

完成本课学习后，你将能够：

1. 理解 Next.js 的缓存层次
2. 掌握不同缓存策略的使用场景
3. 实现数据一致性
4. 避免缓存相关的常见问题

## 一、缓存层次

### 1.1 四层缓存

```
请求级缓存（Request Memoization）
  → 同一请求中重复的 fetch 自动去重
  → 生命周期：单次请求

数据缓存（Data Cache）
  → 跨请求持久化缓存
  → 生命周期：直到手动重新验证

全路由缓存（Full Route Cache）
  → 静态路由的 HTML 和 RSC 缓存
  → 生命周期：直到重新部署或重新验证

路由缓存（Router Cache）
  → 客户端路由缓存
  → 生命周期：会话期间（动态）或 5 分钟（静态）
```

### 1.2 缓存流程图

```
浏览器请求
  ↓
路由缓存（客户端）
  ↓ 命中 → 直接显示
  ↓ 未命中
全路由缓存
  ↓ 命中 → 返回缓存的 HTML
  ↓ 未命中
数据缓存
  ↓ 命中 → 用缓存数据渲染
  ↓ 未命中
执行 Server Component
  ↓
数据库/外部 API
  ↓
返回数据，写入缓存
```

## 二、fetch 缓存

### 2.1 默认行为

```tsx
// 默认缓存（STATIC）
const data = await fetch('https://api.example.com/data')

// 不缓存（DYNAMIC）
const data = await fetch('https://api.example.com/data', {
  cache: 'no-store'
})

// 设置过期时间
const data = await fetch('https://api.example.com/data', {
  next: { revalidate: 60 }  // 60 秒后可以重新验证
})
```

### 2.2 revalidate 选项

```tsx
// 路由级重新验证
export const revalidate = 60

// 请求级重新验证
const data = await fetch(url, {
  next: { revalidate: 60 }
})

// 标签级重新验证
const data = await fetch(url, {
  next: { tags: ['posts'] }
})

// 路径级重新验证
import { revalidatePath } from 'next/cache'
revalidatePath('/posts')
```

## 三、数据库查询缓存

### 3.1 Prisma 不自动缓存

```tsx
// Prisma 查询不会被自动缓存
const users = await prisma.user.findMany() // 每次都查数据库

// 手动缓存
import { unstable_cache } from 'next/cache'

const getCachedUsers = unstable_cache(
  async () => prisma.user.findMany(),
  ['users'],
  { revalidate: 60 }
)

const users = await getCachedUsers()
```

### 3.2 使用 React cache

```tsx
import { cache } from 'react'

const getUser = cache(async (id: string) => {
  return prisma.user.findUnique({ where: { id } })
})

// 同一请求中多次调用只执行一次
const user1 = await getUser('1')
const user2 = await getUser('1') // 使用缓存
```

## 四、重新验证策略

### 4.1 基于时间

```tsx
// 每 60 秒重新验证
export const revalidate = 60

export default async function Page() {
  const data = await fetch('https://api.example.com/data', {
    next: { revalidate: 60 }
  })
  // ...
}
```

### 4.2 基于标签

```tsx
// 标记缓存
const posts = await fetch('https://api.example.com/posts', {
  next: { tags: ['posts'] }
})

// 按标签清除
'use server'

import { revalidateTag } from 'next/cache'

export async function createPost() {
  await db.post.create({ data })
  revalidateTag('posts')
}
```

### 4.3 基于路径

```tsx
'use server'

import { revalidatePath } from 'next/cache'

export async function updatePost(id: string) {
  await db.post.update({ where: { id }, data })
  revalidatePath('/posts')
  revalidatePath(`/posts/${id}`)
}
```

## 五、数据一致性

### 5.1 乐观更新

```tsx
'use client'

import { useOptimistic } from 'react'

export function PostList({ posts }) {
  const [optimisticPosts, addOptimistic] = useOptimistic(
    posts,
    (state, newPost) => [...state, newPost]
  )

  async function handleCreate() {
    addOptimistic({ id: 'temp', title: '新文章...' })
    await createPost()
  }

  return <ul>{optimisticPosts.map(...)}</ul>
}
```

### 5.2 重新验证后刷新

```tsx
'use server'

export async function createPost(formData: FormData) {
  await db.post.create({ data })

  // 重新验证后页面会自动刷新
  revalidatePath('/posts')

  return { success: true }
}
```

## 六、缓存失效

### 6.1 手动失效

```tsx
// 重新验证特定路径
revalidatePath('/dashboard')

// 重新验证特定标签
revalidateTag('user-data')

// 重新验证整个缓存
revalidatePath('/', 'layout')
```

### 6.2 自动失效

```tsx
// 基于时间自动失效
export const revalidate = 60 // 60 秒后自动失效

// 基于条件自动失效
const data = await fetch(url, {
  next: {
    revalidate: process.env.NODE_ENV === 'production' ? 60 : 0
  }
})
```

## 七、常见误区

### 7.1 问题：数据不更新

```tsx
// ❌ 问题：数据一直不更新
const data = await fetch('/api/data') // 默认缓存

// ✅ 解决：设置不缓存或重新验证
const data = await fetch('/api/data', {
  cache: 'no-store'
})
```

### 7.2 问题：缓存太多

```tsx
// ❌ 问题：缓存占用太多内存
const data = await fetch(url, {
  next: { revalidate: false } // 永久缓存
})

// ✅ 解决：设置合理的过期时间
const data = await fetch(url, {
  next: { revalidate: 3600 } // 1 小时
})
```

### 7.3 问题：缓存太频繁

```tsx
// ❌ 问题：每次都重新请求
const data = await fetch(url, {
  cache: 'no-store'
})

// ✅ 解决：适当缓存
const data = await fetch(url, {
  next: { revalidate: 60 }
})
```

## 八、工程建议

1. **按数据更新频率分层设置缓存策略**：静态配置数据（如套餐信息）用长时间缓存（1 小时），用户数据用短时间缓存（60 秒），实时数据（如通知计数）用 `no-store`。

2. **数据库查询配合 `unstable_cache` 使用**：Prisma 查询不会被 Next.js 自动缓存，需要用 `unstable_cache` 包裹。注意设置合理的 `revalidate` 时间和 `tags`，以便精确控制缓存失效。

3. **使用 `revalidateTag` 替代 `revalidatePath` 做精确失效**：`revalidatePath` 会使整条路由的缓存失效，影响范围大。`revalidateTag` 只失效标记了该标签的请求，粒度更细、性能更好。

4. **在 Server Action 中同时处理数据写入和缓存失效**：创建/更新/删除操作完成后，立即调用 `revalidateTag` 或 `revalidatePath`，避免用户看到过期数据。

## 参考答案

### 练习 1：实现缓存策略

**思路**：根据数据更新频率分层设置缓存。静态配置数据用长时间缓存，用户数据用短时间缓存，实时数据不缓存。同时实现基于标签的手动重新验证。

**答案**：

```tsx
// app/dashboard/page.tsx
import { unstable_cache } from 'next/cache'
import { revalidateTag } from 'next/cache'

// 静态配置数据：缓存 1 小时
const getPricingPlans = unstable_cache(
  async () => {
    return prisma.pricingPlan.findMany({ where: { active: true } })
  },
  ['pricing-plans'],
  { revalidate: 3600, tags: ['pricing'] }
)

// 用户数据：缓存 60 秒
const getUserProjects = unstable_cache(
  async (userId: string) => {
    return prisma.project.findMany({
      where: { userId },
      orderBy: { updatedAt: 'desc' }
    })
  },
  ['user-projects'],
  { revalidate: 60, tags: ['user-projects'] }
)

// 实时数据：不缓存
async function getNotifications(userId: string) {
  return prisma.notification.findMany({
    where: { userId, read: false }
  })
}

export default async function DashboardPage() {
  const session = await getSession()
  const plans = await getPricingPlans()
  const projects = await getUserProjects(session.userId)
  const notifications = await getNotifications(session.userId)

  return (
    <div>
      <h1>数据看板</h1>
      <section>
        <h2>套餐信息（缓存 1 小时）</h2>
        {plans.map(plan => <div key={plan.id}>{plan.name}</div>)}
      </section>
      <section>
        <h2>我的项目（缓存 60 秒）</h2>
        {projects.map(project => <div key={project.id}>{project.name}</div>)}
      </section>
      <section>
        <h2>通知（实时）</h2>
        {notifications.map(n => <div key={n.id}>{n.message}</div>)}
      </section>
    </div>
  )
}

// 手动重新验证
'use server'
export async function refreshProjects() {
  revalidateTag('user-projects')
}
```

**要点**：
- 静态数据用 `revalidate: 3600`（1 小时），用户数据用 `revalidate: 60`（60 秒）
- 为缓存设置 `tags`，方便后续精确失效
- 实时数据（如通知）使用 `no-store` 或不使用 `unstable_cache`
- 手动验证用 `revalidateTag` 而非 `revalidatePath`，粒度更细

### 练习 2：实现数据一致性

**思路**：使用 React 的 `useOptimistic` 实现乐观更新，让用户立即看到反馈。同时在 Server Action 中调用 `revalidatePath` 确保服务端数据刷新后页面同步更新。

**答案**：

```tsx
// app/projects/project-list.tsx
'use client'

import { useOptimistic } from 'react'
import { updateProjectName } from '@/app/actions/project'

interface Project {
  id: string
  name: string
}

export function ProjectList({ projects }: { projects: Project[] }) {
  const [optimisticProjects, addOptimistic] = useOptimistic(
    projects,
    (state, { id, name }: { id: string; name: string }) =>
      state.map(p => p.id === id ? { ...p, name } : p)
  )

  async function handleRename(id: string, newName: string) {
    addOptimistic({ id, name: newName })
    await updateProjectName(id, newName)
  }

  return (
    <ul>
      {optimisticProjects.map(project => (
        <li key={project.id}>
          <span>{project.name}</span>
          <button onClick={() => handleRename(project.id, '新名称')}>
            重命名
          </button>
        </li>
      ))}
    </ul>
  )
}

// app/actions/project.ts
'use server'

import { revalidatePath } from 'next/cache'

export async function updateProjectName(id: string, name: string) {
  const session = await getSession()
  if (!session.userId) throw new Error('未登录')

  await prisma.project.update({
    where: { id, userId: session.userId },
    data: { name }
  })

  revalidatePath('/projects')
  revalidatePath(`/projects/${id}`)
}
```

**要点**：
- `useOptimistic` 的第二个参数是更新函数，接收当前状态和乐观值，返回新状态
- Server Action 中必须同时更新数据库和调用 `revalidatePath`，否则刷新后会回退到旧数据
- 乐观更新是"先显示后提交"，如果提交失败需要有回退机制

### 练习 3：性能测试

**思路**：使用 `console.time` 对比有缓存和无缓存场景下的接口响应时间，并通过多次请求验证缓存命中率。

**答案**：

```tsx
// app/api/test-cache/route.ts
import { NextResponse } from 'next/server'

export async function GET(request: Request) {
  const { searchParams } = new URL(request.url)
  const useCache = searchParams.get('cache') !== 'false'

  const results: { label: string; duration: number }[] = []

  // 测试 1：无缓存
  const start1 = performance.now()
  await fetch(`${process.env.NEXT_PUBLIC_URL}/api/projects`, {
    cache: 'no-store'
  })
  results.push({ label: '无缓存', duration: performance.now() - start1 })

  // 测试 2：有缓存（第二次请求应命中缓存）
  const start2 = performance.now()
  await fetch(`${process.env.NEXT_PUBLIC_URL}/api/projects`, {
    next: { revalidate: 60 }
  })
  results.push({ label: '首次请求（写入缓存）', duration: performance.now() - start2 })

  const start3 = performance.now()
  await fetch(`${process.env.NEXT_PUBLIC_URL}/api/projects`, {
    next: { revalidate: 60 }
  })
  results.push({ label: '缓存命中', duration: performance.now() - start3 })

  // 测试 3：不同 revalidate 时间
  const strategies = [0, 10, 60, 300]
  for (const seconds of strategies) {
    const start = performance.now()
    await fetch(`${process.env.NEXT_PUBLIC_URL}/api/projects`, {
      next: { revalidate: seconds }
    })
    results.push({
      label: `revalidate=${seconds}s`,
      duration: performance.now() - start
    })
  }

  return NextResponse.json({ results })
}
```

**要点**：
- 使用 `performance.now()` 而非 `Date.now()` 获取更精确的时间
- Request Memoization 在同一请求内自动去重，跨请求需要用 `unstable_cache` 测试
- 缓存命中后响应时间应显著低于首次请求
- 测试时注意区分 Data Cache 和 Router Cache 的不同效果
