# 安全审查清单

## 场景引入

你的 SaaS 产品即将上线，安全团队要求提交一份安全审查报告。你需要系统性地检查认证、权限、输入验证和数据安全等关键领域，确保没有已知漏洞。这份清单是审查的基础框架，每通过一项打勾，未通过的列入"待改进"。

## 认证
- [x] 密码使用 bcrypt 哈希存储
- [x] Session 使用 iron-session 加密，HttpOnly cookie
- [x] 未登录用户不能访问 Dashboard（middleware 拦截）
- [x] 登录/注册页面已登录用户自动跳转

## 权限
- [x] 所有写操作校验用户角色
- [x] 项目操作校验团队归属
- [x] 审计日志仅 admin/owner 可见
- [x] 成员移除不能操作 owner

## 输入验证
- [x] 表单数据使用 Zod schema 校验
- [x] 服务端校验（不依赖客户端）
- [x] 项目名称长度限制

## 数据安全
- [x] Prisma 参数化查询（防 SQL 注入）
- [x] 级联删除（用户/团队删除时清理关联数据）
- [x] 数据库索引优化查询性能

## 待改进
- [ ] CSRF token 验证
- [ ] 速率限制（登录/注册接口）
- [ ] 敏感操作二次验证
- [ ] 审计日志保留策略

## 常见误区

1. **安全审查只做一次就够了**：每次新增功能、修改 API、升级依赖都可能引入新的安全问题。安全审查应该在每个阶段里程碑时重复执行。

2. **打了勾就代表安全了**：清单上的每一项都需要实际验证，而不是凭印象打勾。比如"输入验证使用 Zod"，需要确认每个 Server Action 都确实调用了 Zod 校验。

3. **只关注 OWASP Top 10，忽略业务逻辑漏洞**：越权访问、竞态条件、配额绕过等业务逻辑漏洞不在 OWASP Top 10 中，但对 SaaS 产品的影响同样严重。

4. **依赖 `npm audit` 就认为依赖安全了**：`npm audit` 只检查已知漏洞，零日漏洞和恶意包不在检查范围内。还应该定期审查新增依赖的可信度。

## 工程建议

1. **将安全审查纳入 CI/CD Pipeline**：使用 `npm audit --audit-level=high` 在 CI 中自动检查依赖漏洞，高危漏洞阻止部署。

2. **为每个审查项添加验证方法**：不只是打勾，还要记录验证方式——是代码审查、自动化测试还是手动测试，确保审查可追溯。

3. **"待改进"项按优先级排序并设定截止日期**：CSRF token 验证和速率限制是高优先级，应该在上线前完成。审计日志保留策略可以放到上线后第一个迭代。

4. **建立安全事件响应流程**：提前定义发现漏洞后的处理流程——谁负责、如何通知用户、如何修复、如何复盘，避免出问题时手忙脚乱。
