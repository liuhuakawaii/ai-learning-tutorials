# 权限矩阵

## 场景引入

你的 SaaS 产品支持团队协作，团队中有 Owner、Admin、Member 三种角色。产品经理问你："普通成员能不能删除项目？""Admin 能不能修改计费设置？"你需要一份清晰的权限矩阵来定义每种角色可以执行哪些操作，确保开发团队在实现权限校验时有统一的参考标准。

| 操作 | Owner | Admin | Member |
|------|-------|-------|--------|
| team:update | ✅ | ✅ | ❌ |
| team:delete | ✅ | ❌ | ❌ |
| member:invite | ✅ | ✅ | ❌ |
| member:remove | ✅ | ✅ | ❌ |
| project:create | ✅ | ✅ | ✅ |
| project:update | ✅ | ✅ | ✅ |
| project:delete | ✅ | ✅ | ❌ |
| document:create | ✅ | ✅ | ✅ |
| document:delete | ✅ | ✅ | ❌ |
| billing:update | ✅ | ❌ | ❌ |
| audit:read | ✅ | ✅ | ❌ |

## 常见误区

1. **权限矩阵只定义了"谁能做什么"，没定义"谁能看什么"**：数据可见性也是权限的一部分。比如 Member 是否能看到团队的套餐信息？Admin 是否能看到所有成员的审计日志？

2. **权限检查只在前端做**：前端根据权限矩阵隐藏/显示按钮只是体验优化，真正的权限校验必须在 `can()` 函数中服务端执行。

3. **新增操作时忘记更新权限矩阵**：每次添加新的写操作（如 `document:share`、`project:archive`），都应该同步更新权限矩阵并在 `can()` 函数中添加对应检查。

4. **Owner 的权限无限大**：即使是 Owner，也不应该有绕过业务规则的权限（如超出套餐限制创建项目）。Owner 权限应该限定在管理操作范围内。

## 工程建议

1. **权限矩阵以代码形式维护**：将权限矩阵定义在 `lib/permissions.ts` 中，与代码一起版本控制，避免文档和代码不一致。

2. **`can()` 函数返回详细的拒绝原因**：不只是返回 `false`，而是返回"需要 Admin 以上权限"或"只能操作自己创建的资源"，方便前端展示友好的错误提示。

3. **权限变更需要审计日志**：修改成员角色、移除成员等权限变更操作必须记录到审计日志，包含操作人、被操作人、变更前后角色。

4. **定期审查权限矩阵的合理性**：随着产品迭代，可能需要新增角色（如 Billing Admin）或调整权限边界，每季度审查一次。
