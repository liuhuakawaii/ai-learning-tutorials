# 第五课：日志和错误监控

## 场景引入

你的 SaaS 产品上线一周后，有用户反馈"付款后订单状态没变"。你登录服务器想排查原因，却发现 `console.log` 的输出早已被滚动覆盖，没有任何持久化的错误记录。你只能猜测可能是支付回调出了问题，但无法确认是哪笔订单、什么时间、什么原因失败的。更糟糕的是，这个 bug 已经默默存在了三天，影响了十几个用户，而你完全不知道。如果没有结构化的日志和错误监控，生产环境就像一个黑盒。

## 学习目标

完成本课学习后，你将能够：

1. 理解日志的重要性
2. 实现结构化日志
3. 集成错误监控服务
4. 设置告警规则

## 一、为什么需要日志

### 1.1 日志的作用

```
问题排查：
  → 发生错误时，查看日志定位原因
  → 重现问题现场

安全审计：
  → 追踪谁做了什么
  → 发现异常行为

性能分析：
  → 找出慢请求
  → 识别瓶颈

业务分析：
  → 用户行为统计
  → 功能使用情况
```

### 1.2 生活类比

```
日志 = 行车记录仪

记录内容：
  → 时间
  → 位置
  → 速度
  → 事件

用途：
  → 事故调查
  → 保险理赔
  → 行程回顾
```

## 二、日志级别

### 2.1 常用级别

```
ERROR  错误
  → 严重问题，需要立即处理
  → 例子：数据库连接失败、支付失败

WARN   警告
  → 潜在问题，需要关注
  → 例子：API 响应慢、磁盘空间不足

INFO   信息
  → 正常操作记录
  → 例子：用户登录、订单创建

DEBUG  调试
  → 详细的调试信息
  → 例子：函数参数、中间变量
```

## 三、结构化日志

### 3.1 安装日志库

```bash
npm install pino pino-pretty
```

### 3.2 创建日志工具

```tsx
// lib/logger.ts
import pino from 'pino'

const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  transport: process.env.NODE_ENV === 'development'
    ? { target: 'pino-pretty', options: { colorize: true } }
    : undefined,
  formatters: {
    level: (label) => {
      return { level: label.toUpperCase() }
    },
  },
  timestamp: () => `,"time":"${new Date().toISOString()}"`,
})

export default logger
```

### 3.3 使用日志

```tsx
import logger from '@/lib/logger'

// 基本用法
logger.info('用户登录成功')
logger.error('数据库连接失败')

// 带上下文
logger.info({
  userId: '123',
  action: 'login',
  ip: '192.168.1.1'
}, '用户登录成功')

// 错误日志
try {
  await riskyOperation()
} catch (error) {
  logger.error({
    err: error,
    operation: 'riskyOperation'
  }, '操作失败')
}
```

## 四、在 Next.js 中使用

### 4.1 API 路由日志

```tsx
// app/api/users/route.ts
import logger from '@/lib/logger'
import { NextResponse } from 'next/server'

export async function GET() {
  const startTime = Date.now()

  try {
    const users = await prisma.user.findMany()

    logger.info({
      method: 'GET',
      path: '/api/users',
      duration: Date.now() - startTime,
      count: users.length
    }, '获取用户列表')

    return NextResponse.json(users)
  } catch (error) {
    logger.error({
      err: error,
      method: 'GET',
      path: '/api/users',
      duration: Date.now() - startTime
    }, '获取用户列表失败')

    return NextResponse.json(
      { error: 'Internal Server Error' },
      { status: 500 }
    )
  }
}
```

### 4.2 Server Action 日志

```tsx
'use server'

import logger from '@/lib/logger'

export async function createPost(formData: FormData) {
  const startTime = Date.now()

  try {
    const post = await prisma.post.create({ data })

    logger.info({
      action: 'createPost',
      postId: post.id,
      userId: session.userId,
      duration: Date.now() - startTime
    }, '文章创建成功')

    return { success: true }
  } catch (error) {
    logger.error({
      err: error,
      action: 'createPost',
      userId: session.userId,
      duration: Date.now() - startTime
    }, '文章创建失败')

    return { error: '创建失败' }
  }
}
```

## 六、日志最佳实践

### 6.1 记录什么

```
必须记录：
  ✅ 错误和异常
  ✅ 认证事件（登录、登出）
  ✅ 权限变更
  ✅ 数据修改操作
  ✅ 外部 API 调用

可选记录：
  → 请求和响应
  → 性能指标
  → 用户行为
```

### 6.2 不要记录什么

```
不要记录：
  ❌ 密码
  ❌ API 密钥
  ❌ 信用卡号
  ❌ 个人敏感信息
  ❌ 大量调试信息（生产环境）
```

### 6.3 日志格式

```json
{
  "level": "INFO",
  "time": "2024-01-15T10:30:00.000Z",
  "message": "用户登录成功",
  "context": {
    "userId": "123",
    "email": "user@example.com",
    "ip": "192.168.1.1"
  },
  "duration": 150
}
```

## 八、日志分析

### 8.1 常用查询

```sql
-- 查找最近的错误
SELECT * FROM logs
WHERE level = 'ERROR'
  AND time > NOW() - INTERVAL '1 hour'
ORDER BY time DESC;

-- 统计错误数量
SELECT
  DATE_TRUNC('hour', time) as hour,
  COUNT(*) as error_count
FROM logs
WHERE level = 'ERROR'
GROUP BY hour
ORDER BY hour DESC;
```

### 练习一：实现结构化日志

**思路**：安装 pino 日志库，创建统一的日志工具模块，在 API 路由中用结构化方式记录请求、响应和错误。

**答案**：

```bash
npm install pino pino-pretty
```

```typescript
// lib/logger.ts
import pino from 'pino'

const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  transport:
    process.env.NODE_ENV === 'development'
      ? { target: 'pino-pretty', options: { colorize: true } }
      : undefined,
  formatters: {
    level: (label) => ({ level: label.toUpperCase() }),
  },
  timestamp: () => `,"time":"${new Date().toISOString()}"`,
  redact: ['req.headers.authorization', 'password', 'token'],
})

export default logger
```

```typescript
// lib/api-logger.ts — API 路由的日志中间件
import { NextRequest } from 'next/server'
import logger from './logger'

export function createRequestLogger(req: NextRequest) {
  const requestId = crypto.randomUUID()

  return logger.child({
    requestId,
    method: req.method,
    path: req.nextUrl.pathname,
    userAgent: req.headers.get('user-agent'),
  })
}
```

```typescript
// app/api/users/route.ts
import { NextResponse } from 'next/server'
import { createRequestLogger } from '@/lib/api-logger'

export async function GET(req: Request) {
  const log = createRequestLogger(req as NextRequest)
  const startTime = Date.now()

  try {
    const users = await prisma.user.findMany()

    log.info({
      duration: Date.now() - startTime,
      count: users.length,
    }, '获取用户列表成功')

    return NextResponse.json(users)
  } catch (error) {
    log.error({
      err: error,
      duration: Date.now() - startTime,
    }, '获取用户列表失败')

    return NextResponse.json(
      { error: 'Internal Server Error' },
      { status: 500 }
    )
  }
}
```

**要点**：
- pino 默认输出 JSON 格式，可被 ELK、Grafana Loki 等日志平台直接解析
- `redact` 配置自动脱敏敏感字段，避免密码或 token 出现在日志中
- 使用 `logger.child()` 为每个请求创建带上下文的子 logger，方便关联同一请求的所有日志

### 练习三：设置告警

**思路**：在 Sentry 中配置告警规则，分别设置错误率告警、新问题告警和性能告警，并配置通知渠道。

**答案**：

```
Sentry 告警配置步骤：

1. 登录 Sentry Dashboard → 项目设置 → Alerts

2. 创建错误率告警：
   - 名称：错误率飙升
   - 条件：当错误事件数在 5 分钟内超过 10 次
   - 动作：发送邮件通知 + Slack 通知

3. 创建新问题告警：
   - 名称：新错误出现
   - 条件：当新的 Issue 第一次出现时
   - 动作：发送邮件通知

4. 创建性能告警：
   - 名称：响应时间过长
   - 条件：当 P95 响应时间超过 2 秒
   - 动作：发送邮件通知

5. 配置通知渠道：
   - 邮件：默认已配置
   - Slack：Settings → Integrations → Slack → 安装并选择频道
```

```typescript
// lib/alerts.ts — 自定义告警逻辑（可选，配合 Sentry 使用）
import logger from './logger'

interface AlertConfig {
  errorRateThreshold: number  // 错误率阈值（百分比）
  windowMinutes: number       // 统计窗口（分钟）
  responseTimeThreshold: number  // 响应时间阈值（毫秒）
}

const defaultConfig: AlertConfig = {
  errorRateThreshold: 5,
  windowMinutes: 5,
  responseTimeThreshold: 2000,
}

const metrics = {
  requests: [] as { time: number; isError: boolean; duration: number }[],
}

export function recordRequest(isError: boolean, duration: number) {
  metrics.requests.push({ time: Date.now(), isError, duration })

  const windowMs = defaultConfig.windowMinutes * 60 * 1000
  const cutoff = Date.now() - windowMs
  metrics.requests = metrics.requests.filter((r) => r.time > cutoff)

  const total = metrics.requests.length
  const errors = metrics.requests.filter((r) => r.isError).length
  const errorRate = total > 0 ? (errors / total) * 100 : 0
  const avgDuration =
    total > 0
      ? metrics.requests.reduce((sum, r) => sum + r.duration, 0) / total
      : 0

  if (errorRate > defaultConfig.errorRateThreshold && total >= 10) {
    logger.error({
      alert: 'ERROR_RATE_HIGH',
      errorRate: errorRate.toFixed(2),
      totalRequests: total,
      windowMinutes: defaultConfig.windowMinutes,
    }, `错误率告警：${errorRate.toFixed(1)}% 超过阈值 ${defaultConfig.errorRateThreshold}%`)
  }

  if (avgDuration > defaultConfig.responseTimeThreshold && total >= 10) {
    logger.warn({
      alert: 'RESPONSE_TIME_HIGH',
      avgDuration: avgDuration.toFixed(0),
      threshold: defaultConfig.responseTimeThreshold,
    }, `响应时间告警：平均 ${avgDuration.toFixed(0)}ms 超过阈值 ${defaultConfig.responseTimeThreshold}ms`)
  }
}
```

**要点**：
- 告警阈值要根据业务基线设置，过低会导致告警疲劳，团队最终会忽略所有告警
- 分级告警：P0（服务不可用）→ 电话 + 短信，P1（错误率飙升）→ 邮件 + Slack，P2（性能下降）→ 邮件
- Sentry 内置的告警规则足够覆盖大部分场景，自定义告警逻辑只在需要更细粒度控制时使用

## 十、常见误区

1. **用 `console.log` 当生产日志**：`console.log` 没有日志级别、没有结构化输出、没有持久化，生产环境中输出会被滚动覆盖且无法检索。应该使用 pino 等结构化日志库。

2. **日志中记录敏感信息**：密码、API 密钥、信用卡号、用户身份证号等绝不应该出现在日志中。即使是 DEBUG 级别，日志也可能被持久化存储和被第三方日志服务索引。

3. **所有异常都用 Sentry 捕获**：用户输入验证失败、404 等业务预期的错误不需要上报 Sentry，否则会产生大量噪音淹没真正的 bug。只上报非预期的服务器错误。

4. **告警阈值设置过低**：把告警阈值设得太低（如每分钟 1 个错误就告警）会导致告警疲劳，团队最终会忽略所有告警。应该根据业务基线设置合理的阈值。

## 十一、工程建议

1. **日志统一使用 JSON 格式**：JSON 格式的日志可以被 ELK、Grafana Loki 等日志平台自动解析和索引，支持结构化查询。pino 默认输出 JSON。

2. **为每个请求生成唯一的 Request ID**：在中间件中生成 `x-request-id`，贯穿整个请求链路（API → 数据库 → 外部服务），方便排查跨服务问题。

3. **Sentry 配置 `tracesSampleRate` 控制采样率**：生产环境建议设置为 0.1（10%），既能看到性能趋势又不会产生过多数据。错误捕获率建议保持 100%。

4. **设置分级告警策略**：P0（服务不可用）→ 电话 + 短信，P1（错误率飙升）→ 邮件 + Slack，P2（性能下降）→ 邮件。不同级别对应不同的响应时效。
