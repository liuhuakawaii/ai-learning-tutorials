# 第一课：音视频基础概念

## 场景引入

你打开一个 1080p 的视频文件，发现它只有 200MB，而同样时长的原始视频数据却有几十 GB。这中间发生了什么？

答案是**编码**。摄像头每秒采集 30 帧 1920×1080 的图像，每帧包含约 600 万个像素，每个像素占 3 字节（RGB），原始数据量约为：

```
1920 × 1080 × 3 字节 × 30 帧 = 约 186 MB/秒
```

一小时的原始视频就是 670 GB。显然，我们不可能在网络上传输这么大的数据。编码器通过去除人眼不敏感的冗余信息，将数据压缩到原来的 1/100 甚至 1/1000，这就是编解码存在的意义。

本课将建立音视频的核心概念框架，理解这些概念是后续所有学习的基础。

## 学习目标

完成本课学习后，你将能够：

1. 理解编解码的基本原理，区分有损压缩与无损压缩
2. 区分容器格式与编码格式，解释它们的关系
3. 计算音频的采样率、位深对文件大小的影响
4. 理解帧率与码率的概念，区分 CBR 与 VBR
5. 根据实际场景选择合适的音视频参数

## 编解码基础

### 什么是编解码

**编码（Encode）** 是将原始音视频数据转换为压缩格式的过程。**解码（Decode）** 是其逆过程——将压缩数据还原为可播放的原始数据。

```
原始数据 → [编码器] → 压缩文件 → [解码器] → 播放数据
```

编码器的核心任务是**压缩**——用更少的数据表达几乎相同的信息。不同编码器的区别在于压缩算法和压缩效率。

### 有损压缩 vs 无损压缩

**无损压缩**：解码后的数据与原始数据完全一致。适用于文本、代码、医学影像等对精度要求极高的场景。典型格式：PNG、FLAC、ZIP。

**有损压缩**：解码后的数据与原始数据存在差异，但这种差异在人眼/人耳的感知阈值以下。适用于音视频等多媒体场景。典型格式：JPEG、MP3、H.264。

```javascript
// 有损压缩的原理示意：丢弃高频细节
// 原始像素值（8×8 块）
const original = [
  [139, 144, 149, 153, 155, 155, 155, 155],
  [144, 151, 153, 156, 159, 156, 156, 156],
  [150, 155, 160, 163, 158, 156, 156, 156],
  [159, 161, 162, 160, 160, 159, 159, 159],
  [159, 160, 161, 162, 162, 155, 155, 155],
  [161, 161, 161, 161, 160, 157, 157, 157],
  [162, 162, 161, 163, 162, 157, 157, 157],
  [162, 162, 161, 161, 163, 158, 158, 158]
];

// 经过 DCT 变换 + 量化后，高频系数被舍弃
// 解码后略有差异，但人眼难以察觉
```

关键区别在于**压缩比**和**可逆性**：

| 特性 | 无损压缩 | 有损压缩 |
|------|----------|----------|
| 可逆性 | 完全可逆 | 不可逆 |
| 压缩比 | 2:1 ~ 5:1 | 10:1 ~ 100:1 |
| 典型场景 | 存档、医学 | 流媒体、通话 |
| 音频格式 | FLAC、ALAC | MP3、AAC |
| 视频格式 | FFV1、HuffYUV | H.264、H.265 |

## 容器格式

### 容器是什么

容器（Container）是一个"包裹"，它把编码后的音频流、视频流、字幕、元数据等打包在一起。容器本身不负责压缩，它只负责**封装和同步**。

```
┌─────────────────────────────────────┐
│           容器 (MP4)                │
│  ┌──────────┐  ┌──────────┐        │
│  │ 视频轨道  │  │ 音频轨道  │        │
│  │ (H.264)  │  │  (AAC)   │        │
│  └──────────┘  └──────────┘        │
│  ┌──────────┐  ┌──────────────────┐│
│  │ 字幕轨道  │  │ 元数据(时长/作者) ││
│  └──────────┘  └──────────────────┘│
└─────────────────────────────────────┘
```

### 常见容器格式对比

| 容器 | 视频编码 | 音频编码 | 特点 |
|------|----------|----------|------|
| MP4 | H.264/H.265 | AAC | 浏览器兼容性最好 |
| WebM | VP8/VP9/AV1 | Vorbis/Opus | 开源免费，Chrome 推荐 |
| MKV | 几乎所有 | 几乎所有 | 功能最强，但浏览器不支持 |
| FLV | H.264 | AAC/AAC+ | 旧式直播方案 |

```javascript
// 判断浏览器是否支持某个容器+编码组合
const video = document.createElement('video');

// MP4 + H.264 + AAC（几乎所有浏览器都支持）
console.log(video.canPlayType('video/mp4; codecs="avc1.42E01E, mp4a.40.2"'));
// 返回 "probably" 或 "maybe"

// WebM + VP9
console.log(video.canPlayType('video/webm; codecs="vp9, vorbis"'));
// Chrome 返回 "probably"，Safari 可能返回 ""

// MKV（浏览器普遍不支持）
console.log(video.canPlayType('video/x-matroska'));
// 返回 ""
```

### 容器 ≠ 编码

这是初学者最常犯的错误。".mp4" 只说明了容器格式，不说明视频用什么编码。同一个 MP4 文件可以使用 H.264、H.265 甚至 AV1 编码。

```javascript
// 用 MediaSource API 检查实际编码支持
const ms = new MediaSource();
console.log(MediaSource.isTypeSupported('video/mp4; codecs="hev1.1.6.L93.B0"'));
// H.265/HEVC — Safari 支持，Chrome 可能不支持

console.log(MediaSource.isTypeSupported('video/mp4; codecs="av01.0.08M.08"'));
// AV1 — 新版 Chrome/Firefox 支持
```

## 采样率与位深

### 采样率

声音是连续的模拟波形，计算机需要将其离散化。**采样率**（Sample Rate）是每秒采集声音样本的次数，单位为 Hz。

```
模拟信号：～～～～～～～～～～
采样点：  ↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓
数字序列：[3][7][5][2][6][8][4][1]
```

根据**奈奎斯特定理**，采样率必须至少是信号最高频率的 2 倍。人耳听觉范围是 20Hz-20kHz，因此 CD 标准采样率为 44100Hz。

| 采样率 | 应用场景 |
|--------|----------|
| 8000 Hz | 电话语音 |
| 16000 Hz | 语音识别 |
| 22050 Hz | 低质量音乐 |
| 44100 Hz | CD 音质 |
| 48000 Hz | 专业音频/视频 |
| 96000 Hz | 高解析度音频 |

### 位深

**位深**（Bit Depth）决定了每个采样点的精度。16 位意味着每个采样值可以是 2^16 = 65536 个级别之一。

```javascript
// 16 位 PCM 数据的取值范围
const MIN_16BIT = -32768;  // 0x8000
const MAX_16BIT = 32767;   // 0x7FFF

// 从 AudioBuffer 获取 PCM 数据
const audioContext = new AudioContext();
const buffer = audioContext.createBuffer(1, 44100, 44100);
const channelData = buffer.getChannelData(0); // Float32Array，范围 -1.0 到 1.0

// 将 Float32 转为 16 位整数
function float32ToInt16(float32Array) {
  const int16Array = new Int16Array(float32Array.length);
  for (let i = 0; i < float32Array.length; i++) {
    const s = Math.max(-1, Math.min(1, float32Array[i]));
    int16Array[i] = s < 0 ? s * 0x8000 : s * 0x7FFF;
  }
  return int16Array;
}
```

### 文件大小计算

音频文件大小的计算公式：

```
文件大小(字节) = 采样率 × 位深/8 × 声道数 × 时长(秒)
```

```javascript
function calcAudioSize(sampleRate, bitDepth, channels, durationSec) {
  const bytes = sampleRate * (bitDepth / 8) * channels * durationSec;
  return {
    bytes,
    kb: (bytes / 1024).toFixed(2),
    mb: (bytes / 1024 / 1024).toFixed(2)
  };
}

// CD 音质：44100Hz, 16bit, 立体声, 1分钟
const cdQuality = calcAudioSize(44100, 16, 2, 60);
console.log(`CD 音质 1 分钟: ${cdQuality.mb} MB`); // 约 10.09 MB

// 电话语音：8000Hz, 16bit, 单声道, 1分钟
const phoneQuality = calcAudioSize(8000, 16, 1, 60);
console.log(`电话语音 1 分钟: ${phoneQuality.kb} KB`); // 约 937.50 KB
```

## 帧率

**帧率**（Frame Rate）是每秒显示的图像帧数，单位 fps（frames per second）。

| 帧率 | 应用场景 | 视觉感受 |
|------|----------|----------|
| 24 fps | 电影 | 电影感，有轻微运动模糊 |
| 25 fps | PAL 电视 | 欧洲/中国电视标准 |
| 30 fps | 网络视频 | 流畅，文件适中 |
| 60 fps | 游戏/体育 | 非常流畅 |
| 120 fps | 慢动作/VR | 极致流畅 |

```javascript
// 帧率与帧间隔的关系
const frameRates = [24, 25, 30, 60];

frameRates.forEach(fps => {
  const interval = 1000 / fps; // 每帧间隔（毫秒）
  console.log(`${fps} fps → 每帧 ${interval.toFixed(2)} ms`);
});
// 24 fps → 每帧 41.67 ms
// 25 fps → 每帧 40.00 ms
// 30 fps → 每帧 33.33 ms
// 60 fps → 每帧 16.67 ms

// 在 requestAnimationFrame 中控制帧率
function throttledRender(callback, targetFps) {
  const interval = 1000 / targetFps;
  let lastTime = 0;

  function loop(timestamp) {
    if (timestamp - lastTime >= interval) {
      callback(timestamp);
      lastTime = timestamp;
    }
    requestAnimationFrame(loop);
  }

  requestAnimationFrame(loop);
}
```

## 码率

**码率**（Bitrate）是每秒传输的数据量，单位通常为 kbps（千比特/秒）或 Mbps。

### CBR vs VBR

**CBR（Constant Bit Rate）**：固定码率，每秒数据量恒定。优点是网络传输稳定，缺点是简单场景浪费带宽、复杂场景质量不足。

**VBR（Variable Bit Rate）**：可变码率，根据内容复杂度动态调整。优点是质量更均匀、总体文件更小，缺点是难以预测带宽需求。

```
CBR: ████████████████████████████████ (恒定)
VBR: ████ ████████ ██ ██████████ ████ (随内容变化)
```

### 码率计算

```javascript
// 视频文件大小估算
function calcVideoSize(videoBitrate, audioBitrate, durationSec) {
  // 码率单位：bps（比特/秒）
  const totalBits = (videoBitrate + audioBitrate) * durationSec;
  const totalBytes = totalBits / 8;
  return {
    mb: (totalBytes / 1024 / 1024).toFixed(2)
  };
}

// 1080p 视频，视频码率 5Mbps，音频码率 128kbps，时长 10 分钟
const size = calcVideoSize(5_000_000, 128_000, 600);
console.log(`文件大小: ${size.mb} MB`); // 约 366.21 MB

// 720p 视频，视频码率 2Mbps，音频码率 128kbps，时长 1 小时
const size2 = calcVideoSize(2_000_000, 128_000, 3600);
console.log(`文件大小: ${size2.mb} MB`); // 约 921.63 MB
```

### 码率与质量的关系

码率越高，质量越好，但存在**边际递减效应**。超过一定阈值后，码率翻倍也不会带来明显画质提升：

```
质量 ↑
     │        ╭─────────── 趋于饱和
     │      ╭─╯
     │    ╭─╯
     │  ╭─╯
     │╭─╯
     ├──────────────────── 码率 →
```

## 常见误区

### 误区一：容器格式等于编码格式

".mp4 文件用的是 H.264 编码"——这是一种常见误解。MP4 只是容器，它可以装 H.264、H.265、AV1 等不同编码的视频流。判断一个文件的实际编码，需要检查其内部的 codec 信息，而非仅看扩展名。

### 误区二：码率越高画质越好

码率对画质的影响存在上限。一个 720p 的视频，即使码率设为 50Mbps，也不会比 5Mbps 的码率有明显提升，因为画面本身的信息量就那么多。真正影响画质的因素依次是：分辨率 > 编码器效率 > 码率设置。

### 误区三：帧率越高越好看

60fps 确实比 30fps 更流畅，但电影工业长期使用 24fps 是因为它带有一种"电影感"——轻微的运动模糊让画面更有质感。高帧率在体育直播和游戏中是优势，但在叙事性内容中未必是。

### 误区四：采样率越高音质越好

48kHz 已经覆盖了人耳能听到的全部频率范围。将采样率提高到 96kHz 或 192kHz，在大多数播放场景下人耳无法分辨差异，只会增加文件大小。

```javascript
    container: 'WebM'
  }

```

### 兼容性优先原则

在 Web 开发中，优先选择兼容性最好的组合：

1. **视频**：MP4 容器 + H.264 编码 + AAC 音频（全平台兼容）
2. **音频**：AAC 格式（MP4 容器）或 MP3（兼容性最广）
3. **实时通信**：Opus 编码（低延迟，WebRTC 标准）

## 小结

本课建立了音视频的核心概念框架：

- **编解码**：将原始数据压缩为更小体积的过程，有损压缩是多媒体的基石
- **容器格式**：将音视频流打包的"包裹"，不等于编码格式
- **采样率与位深**：决定音频质量的两个核心参数
- **帧率**：每秒画面数，不同场景有不同的最佳选择
- **码率**：每秒数据量，存在边际递减效应

理解这些概念后，你就能在实际项目中做出合理的技术选型，而不是盲目追求高参数。

## 参考答案

### 练习一

**思路**：套用音频文件大小计算公式，注意将秒数转换正确。

**答案**：

```javascript
// 3分30秒 = 210秒
const sampleRate = 44100;
const bitDepth = 16;
const channels = 2;
const duration = 210;

const bytes = sampleRate * (bitDepth / 8) * channels * duration;
const mb = bytes / 1024 / 1024;

console.log(`原始数据大小: ${mb.toFixed(2)} MB`);
// 输出: 约 35.28 MB
```

**要点**：
- 3 分 30 秒 = 210 秒，不是 3.5 分钟再乘以 60
- 16 位 = 2 字节，需要除以 8
- 立体声 = 2 声道

### 练习二

**思路**：容器只负责封装，不决定编码格式。

**答案**：

1. **错误**。MP4 是容器格式，它可以封装 H.264、H.265、AV1 等多种编码。虽然最常见的组合确实是 MP4 + H.264，但这不是必然关系。
2. **错误**。WebM 容器支持 VP8、VP9 和 AV1 视频编码，以及 Vorbis 和 Opus 音频编码。
3. **错误**。MKV 和 MP4 都只是容器，画质取决于内部的编码格式和码率设置，与容器本身无关。MKV 的优势在于支持更多的编码格式和功能特性（如多音轨、多字幕），而非画质。

**要点**：
- 容器 ≠ 编码，这是音视频领域最常见的误解
- 判断画质需要看编码器、码率、分辨率等参数，而非容器格式

### 练习三

**思路**：屏幕录制内容变化较少（不像电影那样有大量运动），可以用较低码率。4G 网络需要考虑带宽限制。

**答案**：

```javascript
const screenRecordingConfig = {
  // 屏幕录制以文字为主，720p 足够清晰
  resolution: '1280×720',
  // PPT 切换不需要高帧率，代码演示也相对静态
  fps: 24,
  // 屏幕内容变化少，2Mbps 足够保证文字清晰
  videoBitrate: '2 Mbps',
  // 讲解语音为主，128kbps 足够
  audioBitrate: '128 kbps',
  // H.264 兼容性最好，AV1 压缩效率更高但编码慢
  videoCodec: 'H.264',
  audioCodec: 'AAC',
  container: 'MP4'
};

// 带宽需求：约 2.13 Mbps，4G 网络完全可承载
// 1 小时课程文件大小：约 960 MB
```

**要点**：
- 屏幕录制内容以文字为主，分辨率不需要太高，但要保证文字清晰可读
- 低帧率可以显著降低文件大小，PPT 讲解场景 24fps 足够
- 4G 网络实际下行速率通常在 5-20 Mbps，2 Mbps 码率可以流畅播放
