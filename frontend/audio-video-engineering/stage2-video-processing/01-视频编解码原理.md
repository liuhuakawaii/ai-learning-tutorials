# 视频编解码原理：为什么 H.265 比 H.264 小一半

## 现象

同一个 1080p 视频，H.264 编码 500MB，H.265 编码 250MB，画质几乎一样。H.265 是怎么做到的？

答案不是"更好的压缩算法"这么简单。要理解它，需要知道视频压缩到底在压缩什么。

## 视频压缩的三个维度

视频压缩在三个维度上消除冗余：

```
空间冗余（帧内）
  一帧图像中，相邻像素通常很相似
  一片蓝天不需要存储每个像素的独立颜色
  → 帧内预测（I 帧）

时间冗余（帧间）
  连续帧之间，大部分内容没变
  一个静止的背景只需要存一次
  → 运动估计和补偿（P 帧、B 帧）

感知冗余（量化）
  人眼对高频细节不敏感
  模糊一点点不会被察觉
  → 量化（有损压缩的核心）
```

## I 帧、P 帧、B 帧

```
I 帧（关键帧）：完整图像，不依赖其他帧
  压缩比最低，但可以独立解码
  视频跳转只能跳到 I 帧

P 帧（预测帧）：只存储与前一帧的差异
  需要参考前面的帧才能解码
  压缩比中等

B 帧（双向预测帧）：参考前后两帧的差异
  压缩比最高，但解码需要前后帧
  延迟最高

典型 GOP 结构：
  I B B P B B P B B P B B I ...
  │                           │
  └───── 一个 GOP ─────────────┘
```

await ffmpeg.FS('writeFile', 'input.mp4', inputData)

// 提取帧类型信息

## H.264 vs H.265 的核心差异

```
H.264 (AVC)                    H.265 (HEVC)
├── 宏块大小：16×16             ├── CTU 大小：64×64
├── 帧内预测：4 种模式          ├── 帧内预测：35 种模式
├── 运动补偿：最大 16×16        ├── 运动补偿：最大 64×64
├── 熵编码：CABAC              ├── 熵编码：改进的 CABAC
└── 并行处理：有限              └── 并行处理：Tiles + WPP
```

H.265 的关键改进：

1. **更大的编码单元**：64×64 的 CTU 比 16×16 的宏块更高效，大面积平坦区域（天空、墙壁）压缩比大幅提升
2. **更精细的运动估计**：支持更小的运动补偿块和更多的参考帧
3. **更好的帧内预测**：35 种预测模式比 H.264 的 4 种更精确

```javascript
// 浏览器支持检测
function checkHEVCSupport() {
  const video = document.createElement('video')
  // Main profile, level 4.0
  const hevc = video.canPlayType('video/mp4; codecs="hev1.1.6.L93.B0"')
  // Main 10 profile (HDR)
  const hevc10 = video.canPlayType('video/mp4; codecs="hev1.2.4.L120.B0"')

  return {
    hevc: hevc === 'probably',
    hevc10: hevc10 === 'probably',
    note: hevc === '' ? '需要回退到 H.264' : '支持 H.265'
  }
}
```

## 运动估计

运动估计是帧间压缩的核心：找到当前帧中每个块在参考帧中的最佳匹配位置。

```typescript
// 简化的全搜索运动估计
function motionEstimation(
  currentBlock: Uint8Array,  // 当前块的像素数据
  referenceFrame: Uint8Array, // 参考帧
  blockSize: number,          // 块大小（如 16）
  searchRange: number,        // 搜索范围（如 32）
  frameWidth: number
): { dx: number; dy: number; sad: number } {
  let bestDx = 0, bestDy = 0, bestSad = Infinity

  for (let dy = -searchRange; dy <= searchRange; dy++) {
    for (let dx = -searchRange; dx <= searchRange; dx++) {
      let sad = 0 // Sum of Absolute Differences
      for (let y = 0; y < blockSize; y++) {
        for (let x = 0; x < blockSize; x++) {
          const refIdx = (y + dy) * frameWidth + (x + dx)
          const curIdx = y * blockSize + x
          sad += Math.abs(currentBlock[curIdx] - referenceFrame[refIdx])
        }
      }
      if (sad < bestSad) {
        bestSad = sad
        bestDx = dx
        bestDy = dy
      }
    }
  }

  return { dx: bestDx, dy: bestDy, sad: bestSad }
}
```

## 量化

量化是有损压缩的核心——把精确的数值"四舍五入"到更粗的精度：

```
原始 DCT 系数：  [127, -45, 23, -8, 3, -1, 0, 0]
量化步长：        [16,  16,  32,  32, 64, 64, 64, 64]
量化后：          [8,   -3,  1,   0,  0,  0,  0,  0]
```

量化步长越大，压缩比越高，但画质越差。这就是为什么码率设置会影响画质——码率越低，量化步长越大。

## 你可能踩的坑

**坑一：用 I 帧间隔太长**

I 帧间隔太长会导致 seek 慢、错误传播严重。直播场景建议 2 秒一个 I 帧。

**坑二：B 帧太多导致延迟**

实时通信场景不适合用 B 帧——解码 B 帧需要缓存后续帧，增加延迟。WebRTC 默认不用 B 帧。

**坑三：忽略编码器的 preset**

H.264/H.265 编码器都有 preset（ultrafast/medium/slow）。preset 越慢压缩效率越高，但编码时间越长。离线转码用 slow，实时编码用 ultrafast。

```javascript
async function bitrateComparison(inputData) {
  const ffmpeg = createFFmpeg({ log: true })
  await ffmpeg.load()
  await ffmpeg.FS('writeFile', 'input.mp4', inputData)

  const bitrates = ['1000k', '5000k', '20000k']

  for (const bitrate of bitrates) {
    await ffmpeg.run(
      '-i', 'input.mp4',
      '-b:v', bitrate,
      '-preset', 'medium',
      `output_${bitrate}.mp4`
    )

    const output = ffmpeg.FS('readFile', `output_${bitrate}.mp4`)
    console.log(`${bitrate}: ${(output.length / 1024 / 1024).toFixed(2)} MB`)
  }
}
```
