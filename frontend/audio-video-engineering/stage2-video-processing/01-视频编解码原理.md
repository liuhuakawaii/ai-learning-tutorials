# 第一课：视频编解码原理

## 场景引入

你用手机录制了一段 5 分钟的 1080p 视频，原始数据量大约 1GB（每秒 30 帧，每帧 1920×1080×3 字节）。但实际保存到手机里的文件只有 50MB 左右，体积缩小了 20 倍，画面却看不出明显差别。

这背后就是视频编解码（Video Codec）的工作。理解编解码原理，是做一切音视频工程的基础——无论是选择编码参数、优化转码性能，还是排查播放卡顿问题，都需要对编码原理有清晰认知。

本课将从编码的核心思路出发，讲解主流编码标准的设计差异和工程选型。

## 学习目标

1. 理解视频压缩的核心思路：空间冗余、时间冗余、视觉冗余
2. 掌握 H.264 的 Profile、Level、I/P/B 帧、GOP 等核心概念
3. 了解 H.265、VP9、AV1 的改进点和适用场景
4. 理解帧间压缩的运动估计与参考帧机制
5. 掌握 CBR、VBR、CRF 三种码率控制策略的工程取舍

## 视频压缩的核心思路

视频压缩的本质是**消除冗余**。一段原始视频中存在三种主要冗余：

1. **空间冗余**：同一帧内，相邻像素往往颜色相近。例如一片蓝天，大量像素值几乎相同。
2. **时间冗余**：相邻帧之间，大部分内容没有变化。一段静态场景，前后两帧只有极少数像素不同。
3. **视觉冗余**：人眼对亮度的敏感度高于色度，对高频细节（边缘锐度）的敏感度低于低频信息（整体色调）。

编解码器的工作就是利用这三种冗余，用尽可能少的比特表示尽可能高质量的画面。

## H.264/AVC

H.264 是目前兼容性最广泛的视频编码标准，由 ITU-T 和 ISO/IEC 联合制定，2003 年发布。绝大多数设备和浏览器都支持硬件解码 H.264。

### Profile

Profile 定义了编码器可以使用哪些工具。H.264 常见的三个 Profile：

| Profile | 用途 | 支持的工具 |
|---------|------|-----------|
| Baseline | 视频通话、移动端 | I 帧、P 帧，无 B 帧，不支持 CABAC |
| Main | 流媒体、标清电视 | I/P/B 帧，CABAC 熵编码 |
| High | 蓝光、高清广播 | 8×8 变换，自适应量化矩阵 |

工程选型时，如果需要兼容旧设备（如低端 Android 手机），选择 Baseline；如果追求画质和压缩效率，选择 High Profile。

### Level

Level 限制了分辨率、帧率、码率的上限。例如：

- Level 3.1：最高支持 1280×720@30fps，最大码率 14Mbps
- Level 4.1：最高支持 1920×1080@30fps，最大码率 50Mbps
- Level 5.1：最高支持 4096×2304@60fps

```javascript
// FFmpeg 查看视频的 Profile 和 Level
// ffprobe -v quiet -show_streams -select_streams v:0 input.mp4 | grep -E "profile|level"

// 输出示例：
// profile=High
// level=41   // 即 Level 4.1
```

### I 帧、P 帧、B 帧

这是 H.264 帧类型的核心概念：

- **I 帧（Intra Frame）**：关键帧，独立编码，不依赖其他帧。体积最大，但可以独立解码。
- **P 帧（Predicted Frame）**：前向预测帧，参考前面的 I 帧或 P 帧，只编码差异部分。
- **B 帧（Bi-directional Frame）**：双向预测帧，同时参考前后帧，压缩率最高但解码复杂度也最高。

```javascript
// 帧序列示例：IBBPBBPBBPBBP...
// I 帧 → B B → P → B B → P → B B → P → ...
// 编码顺序和显示顺序不同：
// 编码顺序: I P B B P B B P ...
// 显示顺序: I B B P B B P B B ...
```

### GOP（Group of Pictures）

GOP 是两个 I 帧之间的帧序列。GOP 越大，压缩率越高（因为 I 帧少），但随机访问（seek）时需要解码更多帧才能定位到目标帧。

```javascript
// FFmpeg 设置 GOP 大小
// ffmpeg -i input.mp4 -g 60 output.mp4
// -g 60 表示每 60 帧一个 I 帧，即 30fps 下每 2 秒一个关键帧

// 设置关键帧最小间隔
// -keyint_min 30  表示关键帧最小间隔 30 帧
```

典型的流媒体场景中，GOP 设置为 2 秒（即 30fps 下 `-g 60`），这样 seek 体验和压缩效率之间取得平衡。

## H.265/HEVC

H.265 于 2013 年发布，是 H.264 的继任者。核心改进包括：

1. **编码单元（CTU）**：H.264 使用固定的 16×16 宏块，H.265 支持 64×64 的编码树单元（CTU），大块区域压缩效率更高。
2. **更多帧内预测模式**：H.264 有 9 种帧内预测方向，H.265 扩展到 35 种。
3. **改进的运动补偿**：支持更灵活的分区和更精确的运动矢量。

```javascript
// H.264 vs H.265 压缩效率对比
// 相同画质下，H.265 通常比 H.264 节省 30%-50% 码率

// FFmpeg 使用 H.265 编码
// ffmpeg -i input.mp4 -c:v libx265 -crf 28 -preset medium output_h265.mp4

// 对比文件大小
// H.264 CRF 23 → 约 50MB
// H.265 CRF 28 → 约 35MB（画质相当）
```

H.265 的主要问题是**编码速度慢**（约为 H.264 的 2-5 倍耗时）和**专利授权费用复杂**，这限制了其在 Web 端的普及。

---

## VP9

VP9 是 Google 开发的**免版税**视频编码标准，主要集成在 WebM 容器中。它是 YouTube 的默认编码格式。

```javascript
// VP9 编码示例
// ffmpeg -i input.mp4 -c:v libvpx-vp9 -crf 30 -b:v 0 output.webm

// VP9 的优势：
// 1. 免版税，无需支付授权费用
// 2. Chrome、Firefox、Edge 原生支持
// 3. YouTube 视频默认使用 VP9 编码
```

VP9 在压缩效率上与 H.265 接近，但编码速度更快。缺点是 Safari 不支持（直到 macOS Monterey 才开始支持部分 VP9）。

---

## AV1

AV1 是由 Alliance for Open Media（AOMedia）开发的下一代免版税编码标准，成员包括 Google、Mozilla、Cisco、Microsoft、Netflix 等。

```javascript
// AV1 编码示例（使用 libaom-av1）
// ffmpeg -i input.mp4 -c:v libaom-av1 -crf 30 -b:v 0 output_av1.mp4

// 使用 SVT-AV1 编码器（更快）
// ffmpeg -i input.mp4 -c:v libsvtav1 -crf 30 -preset 6 output_av1.mp4
```

AV1 相比 H.265 的改进：

1. 压缩效率再提升 20%-30%
2. 免版税，消除了专利障碍
3. 浏览器支持逐步完善：Chrome、Firefox、Edge 已支持，Safari 从 macOS Ventura 开始支持

```javascript
// 检测浏览器是否支持 AV1 解码
const canPlayAV1 = MediaSource.isTypeSupported('video/mp4; codecs="av01.0.08M.08"');
console.log('AV1 支持:', canPlayAV1);
```

AV1 的主要问题是**编码速度极慢**（传统编码器约为 H.264 的 10-50 倍耗时），但 SVT-AV1 编码器大幅改善了这个问题。

## 帧间压缩：运动估计与参考帧

帧间压缩是视频压缩的核心技术。其基本思想是：找到相邻帧中相似的块，只编码它们之间的差异。

### 运动估计

运动估计的目标是为当前帧的每个块，在参考帧中找到最匹配的位置，计算出**运动矢量**（位移量）。

```javascript
// 运动估计简化示意
// 当前帧的块 B 在参考帧中搜索最佳匹配
// 搜索范围：参考帧中 B 周围 ±N 像素
// 匹配标准：SAD（绝对误差和）或 SATD（哈达玛变换后的绝对误差和）

function calculateSAD(currentBlock, referenceBlock, offsetX, offsetY) {
  let sad = 0;
  for (let y = 0; y < blockHeight; y++) {
    for (let x = 0; x < blockWidth; x++) {
      const refX = x + offsetX;
      const refY = y + offsetY;
      sad += Math.abs(
        currentBlock[y][x] - referenceBlock[refY][refX]
      );
    }
  }
  return sad;
}
```

### 参考帧管理

H.264 支持多参考帧（最多 16 个），编码器可以选择历史中任意一帧作为参考。H.265 进一步支持参考帧列表的灵活管理。

```javascript
// 参考帧结构示意
// DPB（Decoded Picture Buffer）存储已解码的帧
// 编码当前帧时，从 DPB 中选择最佳参考帧
// 选择策略：时间距离近、内容相似度高的帧优先
```

## Rate Control：码率控制

码率控制决定了编码器如何分配比特预算，直接影响画质和文件大小。

### CBR（Constant Bitrate）

固定码率，每秒输出恒定的比特数。适合实时流媒体（带宽可预测），但画质不稳定——复杂场景模糊，简单场景浪费比特。

```javascript
// FFmpeg CBR 编码
// ffmpeg -i input.mp4 -c:v libx264 -b:v 4M -maxrate 4M -bufsize 8M output.mp4
```

### VBR（Variable Bitrate）

可变码率，编码器根据场景复杂度动态调整码率。复杂场景分配更多比特，简单场景减少比特。画质更稳定，但文件大小不可预测。

```javascript
// FFmpeg VBR 编码（双 pass）
// 第一遍：分析视频内容
// ffmpeg -i input.mp4 -c:v libx264 -b:v 4M -pass 1 -f null /dev/null
// 第二遍：根据分析结果编码
// ffmpeg -i input.mp4 -c:v libx264 -b:v 4M -pass 2 output.mp4
```

### CRF（Constant Rate Factor）

恒定质量因子，最简单的质量控制方式。CRF 值越低画质越好（0 为无损，51 为最差），x264 推荐默认值 23。

```javascript
// FFmpeg CRF 编码
// ffmpeg -i input.mp4 -c:v libx264 -crf 23 output.mp4

// CRF 值参考：
// 18：视觉无损
// 23：默认值，画质与大小平衡
// 28：可接受画质，文件较小
```

## 常见误区

### 误区一：H.265 一定比 H.264 好

H.265 压缩效率更高，但编码速度慢、解码需要硬件支持、专利费用复杂。对于 Web 场景，H.264 的兼容性远比压缩效率重要。

### 误区二：编码格式等于容器格式

编码格式（Codec）是视频数据的压缩算法，容器格式（Container）是封装视频、音频、字幕的文件格式。同一个容器可以装不同编码的视频：

```javascript
// .mp4 容器可以包含：
// H.264 视频 + AAC 音频（最常见）
// H.265 视频 + AAC 音频
// AV1 视频 + Opus 音频

// .webm 容器可以包含：
// VP8/VP9 视频 + Vorbis/Opus 音频
// AV1 视频 + Opus 音频
```

### 误区三：码率越高画质越好

码率和画质不是线性关系。超过某个阈值后，提高码率对画质提升微乎其余，只会增大文件体积。合理的做法是使用 CRF 模式，让编码器自动分配比特。

---

## 工程建议

1. **优先选择 H.264**：兼容性最好，硬件解码支持最广泛，适合大多数场景
2. **考虑 H.265 的场景**：存储空间敏感（如监控录像）、目标设备确认支持硬件解码
3. **AV1 适合长期存储**：YouTube、Netflix 等平台已大规模使用，浏览器支持逐步完善
4. **GOP 设为 2 秒**：流媒体场景下，2 秒的 GOP 是 seek 体验和压缩效率的平衡点
5. **使用 CRF 模式**：除非有严格的码率限制（如直播推流），否则 CRF 是最省心的质量控制方式
6. **Profile 选择 High**：除非需要兼容 2010 年以前的设备

## 小结

本课讲解了视频编解码的核心原理：

- 视频压缩的本质是消除空间冗余、时间冗余和视觉冗余
- H.264 是兼容性最广泛的标准，理解 Profile、Level、I/P/B 帧和 GOP 是基本功
- H.265 压缩效率更高但兼容性差，VP9 免版税但 Safari 支持晚，AV1 是未来趋势
- 帧间压缩通过运动估计和参考帧消除时间冗余
- CBR 适合实时场景，VBR 画质更稳定，CRF 是最简单的质量控制方式

## 参考答案

### 练习一

**思路**：YUV420 格式下，每像素 1.5 字节（Y 全量，U/V 各 1/4）。

**答案**：

```javascript
// 原始数据量计算
const width = 1920;
const height = 1080;
const fps = 30;
const duration = 10;
const bytesPerPixel = 1.5; // YUV420

const frameSize = width * height * bytesPerPixel;
const totalFrames = fps * duration;
const rawSize = frameSize * totalFrames;

console.log(`每帧大小: ${(frameSize / 1024 / 1024).toFixed(2)} MB`);
// 每帧大小: 2.97 MB

console.log(`原始总大小: ${(rawSize / 1024 / 1024).toFixed(2)} MB`);
// 原始总大小: 890.63 MB

// 压缩比
const encodedSize = 5 * 1024 * 1024; // 5MB
const compressionRatio = rawSize / encodedSize;
console.log(`压缩比: ${compressionRatio.toFixed(1)}:1`);
// 压缩比: 177.1:1
```

**要点**：
- YUV420 中每个 2×2 像素块共享一组 UV 值，所以每像素平均 1.5 字节
- 10 秒原始视频约 890MB，压缩到 5MB，压缩比约 177:1

### 练习二

**思路**：使用 FFprobe 的 `-show_frames` 参数配合 `-select_streams v:0` 只查看视频帧。

**答案**：

```bash
# 使用 FFprobe 输出帧信息（JSON 格式便于解析）
ffprobe -v quiet -show_frames -select_streams v:0 -show_entries frame=pict_type,pkt_size,pts_time input.mp4 | head -30

# 解析输出的 Python 脚本
import json
import subprocess

def analyze_frames(video_path, num_frames=10):
    cmd = [
        'ffprobe', '-v', 'quiet',
        '-print_format', 'json',
        '-show_frames',
        '-select_streams', 'v:0',
        '-count_frames',
        video_path
    ]
    result = subprocess.run(cmd, capture_output=True, text=True)
    data = json.loads(result.stdout)

    for i, frame in enumerate(data['frames'][:num_frames]):
        frame_type = frame['pict_type']
        size = int(frame['pkt_size'])
        pts = float(frame['pts_time'])
        print(f"帧 {i}: 类型={frame_type}, 大小={size}字节, 时间戳={pts:.3f}s")

analyze_frames('input.mp4')
```

**典型输出**：

```
帧 0: 类型=I, 大小=52480字节, 时间戳=0.000s
帧 1: 类型=B, 大小=8192字节, 时间戳=0.033s
帧 2: 类型=B, 大小=7680字节, 时间戳=0.067s
帧 3: 类型=P, 大小=15360字节, 时间戳=0.100s
帧 4: 类型=B, 大小=6144字节, 时间戳=0.133s
帧 5: 类型=B, 大小=5632字节, 时间戳=0.167s
帧 6: 类型=P, 大小=14336字节, 时间戳=0.200s
```

**要点**：
- I 帧体积最大（约 50KB），因为独立编码
- B 帧体积最小（约 5-8KB），因为双向预测
- P 帧介于两者之间（约 14KB）

### 练习三

**思路**：根据场景特点选择 Profile、Level、码率控制方式和关键参数。

**答案**：

```
场景 A：移动端视频通话
- 编码器：H.264 Baseline Profile（无 B 帧，解码复杂度低）
- 分辨率：640×480 或 480×360
- 帧率：15-24fps
- 码率控制：CBR，码率 500Kbps-1Mbps
- GOP：1 秒（关键帧间隔 15-24 帧），方便弱网下快速恢复

场景 B：视频网站点播
- 编码器：H.264 High Profile（或 H.265 如果目标设备支持）
- 分辨率：1080p
- 帧率：30fps
- 码率控制：CRF 20-23（质量优先）
- GOP：2 秒（60 帧）
- 编码预设：slow 或 medium（画质优先）

场景 C：监控录像
- 编码器：H.265（节省存储空间）
- 分辨率：1080p 或 4K
- 帧率：15-25fps
- 码率控制：VBR，平均码率 2-4Mbps
- GOP：4-8 秒（减少 I 帧，进一步节省空间）
- 特点：支持动态 GOP，运动检测时提高帧率和码率
```

**要点**：
- 视频通话优先低延迟，使用 CBR 和短 GOP
- 点播优先画质，使用 CRF 和慢速预设
- 监控优先存储效率，使用 H.265 和长 GOP
