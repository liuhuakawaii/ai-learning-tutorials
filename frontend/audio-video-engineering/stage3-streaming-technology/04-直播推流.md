# 第四课：直播推流

## 场景引入

一个游戏主播打开 OBS，点击"开始推流"，画面就出现在了 Twitch 上数万观众的屏幕上。这中间发生了什么？

主播的电脑每秒产生 30 帧 1080p 的画面，经过编码压缩后通过 **RTMP 协议**推送到直播服务器。服务器接收到流数据后，进行**转码**生成多个码率版本，再切片为 HLS 分片，通过 CDN 分发给全球观众。整个链路的延迟通常在 1-3 秒。

本课将从推流协议开始，完整学习直播的技术栈。

## 学习目标

完成本课学习后，你将能够：

1. 理解 RTMP 协议的工作原理和消息格式
2. 了解 SRT 协议的低延迟特性
3. 使用 OBS 配置推流参数
4. 使用 FFmpeg 实现服务端转码
5. 实现直播录制和回放功能

## RTMP 协议

### RTMP 概述

**RTMP（Real-Time Messaging Protocol）** 是 Adobe 开发的实时消息传输协议，虽然已经不再更新，但仍然是直播推流的事实标准。

RTMP 工作在 TCP 之上，使用持久连接，端口 1935：

```
主播端 ──RTMP──→ 媒体服务器 ──HLS/DASH──→ 观众端
         TCP:1935          HTTP:443
```

### 握手过程

RTMP 连接建立需要三次握手：

```
客户端                         服务端
  │                              │
  │── C0 (version byte) ───────→│
  │── C1 (1536 bytes random) ──→│
  │                              │
  │←── S0 (version byte) ───────│
  │←── S1 (1536 bytes random) ──│
  │←── S2 (echo of C1) ─────────│
  │                              │
  │── C2 (echo of S1) ─────────→│
  │                              │
  │   连接建立，开始传输消息        │
```

### 消息类型

RTMP 定义了多种消息类型：

| 类型 ID | 名称 | 用途 |
|---------|------|------|
| 1 | Set Chunk Size | 设置分块大小 |
| 3 | Acknowledgement | 确认收到的字节数 |
| 4 | UserControl | 控制消息（流开始/暂停等） |
| 5 | Window Ack Size | 窗口确认大小 |
| 8 | Audio Message | 音频数据 |
| 9 | Video Message | 视频数据 |
| 18 | Data Message | 元数据（宽高、码率等） |
| 20 | Command Message | 命令（connect, publish, play） |

### 推流命令流程

```
客户端                               服务端
  │                                    │
  │── connect("app") ────────────────→│
  │←── Window Ack Size ───────────────│
  │←── Set Peer Bandwidth ────────────│
  │←── _result("connect") ────────────│
  │                                    │
  │── createStream ──────────────────→│
  │←── _result("createStream") ───────│
  │                                    │
  │── publish("streamKey") ──────────→│
  │←── onStatus("Publish.Start") ─────│
  │                                    │
  │── @setDataFrame (metadata) ──────→│
  │── Video: sequence header ────────→│  ← SPS/PPS
  │── Audio: sequence header ────────→│  ← AAC 配置
  │── Video: keyframe ───────────────→│
  │── Audio: frame ──────────────────→│
  │── Video: inter frame ────────────→│
  │── ... 持续推流 ...                 │
```

## SRT 协议

### SRT 概述

**SRT（Secure Reliable Transport）** 是 Haivision 开源的视频传输协议，专为不可靠网络上的低延迟视频传输设计。

SRT 的核心特性：

| 特性 | 说明 |
|------|------|
| 基于 UDP | 避免 TCP 的队头阻塞问题 |
| ARQ | 自动重传丢失的包 |
| FEC | 前向纠错，用冗余数据恢复丢失 |
| 加密 | AES-128/256 端到端加密 |
| 低延迟 | 可配置，通常 120ms-2s |

### SRT vs RTMP

| 特性 | RTMP | SRT |
|------|------|-----|
| 传输层 | TCP | UDP |
| 延迟 | 较高（受 TCP 重传影响） | 低（可配置） |
| 抗丢包 | TCP 自动重传，但延迟大 | ARQ + FEC，延迟可控 |
| 防火墙 | 端口 1935 常被封 | 任意端口 |
| 加密 | 不原生支持 | AES 内置 |
| 生态 | 极成熟，所有平台支持 | 逐渐增长 |

## OBS 推流配置

### 关键参数

OBS 推流时需要配置以下参数：

```javascript
// OBS 推流配置参数（概念模型）
const streamConfig = {
  // 服务器地址
  server: 'rtmp://live.example.com/live',
  streamKey: 'your-stream-key-here',

  // 视频设置
  video: {
    resolution: '1920x1080',       // 输出分辨率
    fps: 30,                        // 帧率
    downscale: '1280x720',         // 缩放后的推流分辨率（可选）
  },

  // 编码设置
  encoder: {
    type: 'x264',                   // 或 'nvenc'（NVIDIA GPU 编码）
    rateControl: 'CBR',             // CBR（恒定码率）适合直播
    bitrate: 4500,                  // 码率 (kbps)
    keyframeInterval: 2,            // 关键帧间隔（秒）← 非常重要！
    preset: 'veryfast',             // CPU 编码预设
    profile: 'high',
    tune: 'zerolatency',            // 低延迟调优
  },

  // 音频设置
  audio: {
    codec: 'AAC',
    bitrate: 160,                   // 音频码率 (kbps)
    sampleRate: 44100,              // 采样率
    channels: 'stereo',             // 声道
  },
};
```

### 关键帧间隔的重要性

**关键帧间隔（GOP size）** 是直播中最容易被忽视但影响最大的参数：

```
关键帧间隔 = 2 秒，帧率 = 30fps
→ 每 60 帧一个关键帧
→ HLS 分片时长必须是关键帧间隔的整数倍
→ 观众进入直播间最多等 2 秒看到第一个完整画面
```

关键帧间隔太大的问题：
- 观众首帧等待时间长
- seek 精度差（只能在关键帧处切换）
- HLS 切片不灵活

关键帧间隔太小的问题：
- 压缩效率降低（关键帧比 P/B 帧大很多）
- 带宽浪费

## 服务端转码

### FFmpeg 转码

服务器接收到推流后，需要转码为多种码率以支持自适应播放：

```bash
#!/bin/bash
# transcode.sh - 接收 RTMP 推流并转码为多码率 HLS

INPUT="rtmp://0.0.0.0:1935/live/stream"
OUTPUT_DIR="/var/www/hls/stream"

mkdir -p ${OUTPUT_DIR}/{360p,720p,1080p}

ffmpeg -i ${INPUT} \
  -map 0:v -map 0:v -map 0:v -map 0:a \
  \
  -c:v:0 libx264 -b:v:0 800k  -s:v:0 640x360 \
    -preset veryfast -tune zerolatency \
    -g 60 -keyint_min 60 -sc_threshold 0 \
  \
  -c:v:1 libx264 -b:v:1 2500k -s:v:1 1280x720 \
    -preset veryfast -tune zerolatency \
    -g 60 -keyint_min 60 -sc_threshold 0 \
  \
  -c:v:2 libx264 -b:v:2 5000k -s:v:2 1920x1080 \
    -preset veryfast -tune zerolatency \
    -g 60 -keyint_min 60 -sc_threshold 0 \
  \
  -c:a aac -b:a 160k -ar 44100 \
  \
  -f hls -hls_time 2 -hls_list_size 6 \
  -hls_flags delete_segments+append_list \
  -hls_segment_filename '${OUTPUT_DIR}/%v/seg_%03d.ts' \
  \
  -var_stream_map "v:0,a:0 v:1,a:0 v:2,a:0" \
  ${OUTPUT_DIR}/%v/playlist.m3u8
```

参数说明：

| 参数 | 说明 |
|------|------|
| `-g 60` | GOP 大小 60 帧（30fps 下 2 秒一个关键帧） |
| `-keyint_min 60` | 最小关键帧间隔，确保对齐 |
| `-sc_threshold 0` | 禁用场景切换检测 |
| `-hls_time 2` | 每个分片 2 秒 |
| `-hls_list_size 6` | 播放列表保留 6 个分片（12 秒窗口） |
| `-hls_flags delete_segments` | 自动删除旧分片，节省磁盘 |
| `-tune zerolatency` | 零延迟调优，减少编码缓冲 |

node-media-server 是一个轻量级的 Node.js 媒体服务器，支持 RTMP 输入和 HLS/DASH 输出：

```javascript
          ['-vf', 'scale=640:360'],
          ['-b:v', '800k'],
          ['-g', '60'],
          ['-keyint_min', '60'],
          ['-sc_threshold', '0'],
        ],
        ac: 'aac',
        acParam: ['-b:a', '128k', '-ar', '44100'],
      },
      {
        app: 'live',
        hls: true,
        hlsFlags: '[hls_time=2:hls_list_size=6:hls_flags=delete_segments]',
        hlsKeep: false,
        vc: 'libx264',
        vcParam: [
          ['-vf', 'scale=1920:1080'],
          ['-b:v', '5000k'],
          ['-g', '60'],
          ['-keyint_min', '60'],
          ['-sc_threshold', '0'],
        ],
        ac: 'aac',
        acParam: ['-b:a', '160k', '-ar', '44100'],
      },
    ],
  },
};

const nms = new NodeMediaServer(config);

nms.on('prePublish', (id, StreamPath, args) => {
  console.log('[推流开始]', StreamPath);
  // 可以在这里验证推流密钥
  const streamKey = StreamPath.split('/').pop();
  if (!isValidStreamKey(streamKey)) {
    const session = nms.getSession(id);
    session.reject();
    console.log('[推流拒绝] 无效的流密钥');
  }
});

nms.on('donePublish', (id, StreamPath, args) => {
  console.log('[推流结束]', StreamPath);
});

nms.run();

function isValidStreamKey(key) {
  // 验证推流密钥的逻辑
  return key && key.length > 10;
}
```

## 录制回放

### DVR 录制

直播录制（DVR）允许观众回看直播内容：

```javascript
const fs = require('fs');
const path = require('path');

class StreamRecorder {
  constructor(outputDir) {
    this.outputDir = outputDir;
    this.recording = false;
    this.startTime = null;
    this.segmentIndex = 0;
  }

  startRecording(streamId) {
    const recordDir = path.join(this.outputDir, streamId, 'record');
    fs.mkdirSync(recordDir, { recursive: true });

    this.recording = true;
    this.startTime = Date.now();
    this.recordDir = recordDir;

    // 记录元数据
    const metadata = {
      streamId,
      startTime: new Date().toISOString(),
      segments: [],
    };
    fs.writeFileSync(
      path.join(recordDir, 'metadata.json'),
      JSON.stringify(metadata, null, 2)
    );

    console.log(`[录制] 开始录制 ${streamId}`);
  }

  onSegment(segmentPath, duration) {
    if (!this.recording) return;

    const segmentName = `record_${this.segmentIndex.toString().padStart(6, '0')}.ts`;
    const destPath = path.join(this.recordDir, segmentName);

    // 将直播分片复制到录制目录
    fs.copyFileSync(segmentPath, destPath);

    this.segmentIndex++;
  }

  stopRecording() {
    if (!this.recording) return;

    this.recording = false;
    const duration = (Date.now() - this.startTime) / 1000;

    // 更新元数据
    const metadataPath = path.join(this.recordDir, 'metadata.json');
    const metadata = JSON.parse(fs.readFileSync(metadataPath, 'utf-8'));
    metadata.endTime = new Date().toISOString();
    metadata.duration = duration;
    metadata.totalSegments = this.segmentIndex;
    fs.writeFileSync(metadataPath, JSON.stringify(metadata, null, 2));

    // 生成回放用的 m3u8
    this.generatePlaybackPlaylist();

    console.log(`[录制] 录制结束，共 ${this.segmentIndex} 个分片，时长 ${duration.toFixed(1)}s`);
  }

  generatePlaybackPlaylist() {
    let playlist = '#EXTM3U\n#EXT-X-VERSION:3\n#EXT-X-TARGETDURATION:2\n';
    playlist += '#EXT-X-MEDIA-SEQUENCE:0\n';

    for (let i = 0; i < this.segmentIndex; i++) {
      const name = `record_${i.toString().padStart(6, '0')}.ts`;
      playlist += `#EXTINF:2.000,\n${name}\n`;
    }

    playlist += '#EXT-X-ENDLIST\n';

    fs.writeFileSync(path.join(this.recordDir, 'playlist.m3u8'), playlist);
  }
}
```

## 常见误区

### 误区一：关键帧间隔不影响画质

关键帧间隔直接决定了压缩效率。间隔从 2 秒增加到 10 秒，同等画质下码率可以降低 10-15%。但代价是 seek 精度变差、首帧延迟增大。直播场景推荐 2 秒。

### 误区二：CBR 和 VBR 在直播中没区别

直播必须用 **CBR（恒定码率）**。VBR 在复杂画面时码率飙升，可能导致网络拥塞和推流卡顿。点播才适合 VBR。

### 误区三：推流断开后观众会自动重连

大多数播放器在流中断后会停止播放。需要在客户端实现重连逻辑，同时服务端需要处理推流断开后的状态管理。

### 误区四：转码不消耗资源

实时转码对 CPU/GPU 的消耗非常大。1080p30 的 H.264 软编码大约需要一个完整的 CPU 核心。多码率转码需要合理的硬件规划。

## 工程建议

1. **关键帧间隔设 2 秒**：这是 HLS 兼容性和延迟的最佳平衡点
2. **使用硬件编码**：生产环境优先使用 NVIDIA NVENC 或 Intel QSV，降低 CPU 负载
3. **推流断开自动重连**：OBS 默认会尝试重连，但自研推流端需要手动实现
4. **监控推流健康指标**：码率、帧率、丢帧率、连接状态
5. **录制要考虑磁盘空间**：1080p4500kbps 一小时约 2GB，需要定期清理或转存到对象存储
6. **gop_cache 开启**：让新观众能快速看到画面，不需要等下一个关键帧

```javascript
const nms = new NodeMediaServer(config);

nms.on('postPublish', (id, StreamPath, args) => {

nms.on('donePublish', (id, StreamPath, args) => {
  console.log(`[Event] donePublish: ${StreamPath}`);

console.log('RTMP 服务器已启动: rtmp://localhost:1935/live');
console.log('HLS 播放地址: http://localhost:8000/live/<streamKey>/index.m3u8');
```

**要点**：
- `gop_cache: true` 让新观众可以立即看到最近的关键帧，大幅缩短首帧时间
- `hls_time=2` 每个分片 2 秒，配合 2 秒关键帧间隔实现低延迟
- `delete_segments` 自动清理旧分片，避免磁盘被写满

### 练习二

**思路**：监听 `postPublish` 和 `donePublish` 事件控制录制，在推流过程中将 HLS 分片复制到录制目录，推流结束后生成完整的播放列表。

**答案**：

```javascript
const fs = require('fs');
const path = require('path');
const chokidar = require('chokidar');

class LiveRecorder {
  constructor(mediaRoot) {
    this.mediaRoot = mediaRoot;
    this.activeRecordings = new Map();
  }

  startRecording(streamPath) {
    const streamKey = streamPath.split('/').pop();
    const hlsDir = path.join(this.mediaRoot, 'live', streamKey);
    const recordDir = path.join(this.mediaRoot, 'recordings', streamKey);

    fs.mkdirSync(recordDir, { recursive: true });

    const state = {
      segments: [],
      startTime: Date.now(),
      watcher: null,
    };

    // 监控 HLS 分片目录，自动复制新分片
    const watcher = chokidar.watch(path.join(hlsDir, '*.ts'), {
      persistent: true,
      ignoreInitial: true,
    });

    watcher.on('add', (filePath) => {
      const filename = path.basename(filePath);
      const dest = path.join(recordDir, filename);

      // 等待文件写入完成
      setTimeout(() => {
        if (fs.existsSync(filePath)) {
          fs.copyFileSync(filePath, dest);
          state.segments.push({
            filename,
            time: Date.now(),
          });
          console.log(`[录制] 保存分片: ${filename}`);
        }
      }, 500);
    });

    state.watcher = watcher;
    this.activeRecordings.set(streamKey, state);
    console.log(`[录制] 开始录制: ${streamKey}`);
  }

  stopRecording(streamPath) {
    const streamKey = streamPath.split('/').pop();
    const state = this.activeRecordings.get(streamKey);

    if (!state) return;

    state.watcher.close();

    const recordDir = path.join(this.mediaRoot, 'recordings', streamKey);
    const duration = (Date.now() - state.startTime) / 1000;

    // 生成完整播放列表
    let playlist = '#EXTM3U\n#EXT-X-VERSION:3\n';
    playlist += '#EXT-X-TARGETDURATION:2\n';
    playlist += '#EXT-X-MEDIA-SEQUENCE:0\n';

    state.segments.forEach((seg) => {
      playlist += `#EXTINF:2.000,\n${seg.filename}\n`;
    });

    playlist += '#EXT-X-ENDLIST\n';

    fs.writeFileSync(path.join(recordDir, 'playlist.m3u8'), playlist);
    this.activeRecordings.delete(streamKey);

    console.log(`[录制] 录制完成: ${streamKey}, ${state.segments.length} 分片, ${duration.toFixed(1)}s`);
  }
}

// 集成到 node-media-server
const NodeMediaServer = require('node-media-server');

const config = {
  rtmp: { port: 1935, chunk_size: 60000, gop_cache: true },
  http: { port: 8000, mediaroot: './media', allow_origin: '*' },
  trans: {
    ffmpeg: '/usr/bin/ffmpeg',
    tasks: [{
      app: 'live',
      hls: true,
      hlsFlags: '[hls_time=2:hls_list_size=10:hls_flags=delete_segments]',
    }],
  },
};

const nms = new NodeMediaServer(config);
const recorder = new LiveRecorder('./media');

nms.on('postPublish', (id, StreamPath) => {
  recorder.startRecording(StreamPath);
});

nms.on('donePublish', (id, StreamPath) => {
  recorder.stopRecording(StreamPath);
});

nms.run();
```

**要点**：
- 使用 chokidar 监控分片目录，实时复制新生成的分片到录制目录
- 延迟 500ms 复制确保分片已完全写入磁盘
- 停止录制时生成带 `#EXT-X-ENDLIST` 的完整播放列表

### 练习三

**思路**：使用 FFmpeg 的 `-map` 参数将输入流映射到多个输出，每个输出使用不同的码率和分辨率。

**答案**：

```bash
#!/bin/bash
# multi-rate-transcode.sh

INPUT="rtmp://0.0.0.0:1935/live/stream"
OUTPUT_DIR="/var/www/hls"
STREAM_KEY="${1:-default}"

mkdir -p ${OUTPUT_DIR}/${STREAM_KEY}/{360p,720p,1080p}

ffmpeg -i ${INPUT} \
  -map 0:v -map 0:v -map 0:v -map 0:a -map 0:a -map 0:a \
  \
  -c:v:0 libx264 -b:v:0 800k  -s:v:0 640x360  -preset veryfast \
  -c:v:1 libx264 -b:v:1 2500k -s:v:1 1280x720 -preset veryfast \
  -c:v:2 libx264 -b:v:2 5000k -s:v:2 1920x1080 -preset veryfast \
  \
  -c:a:0 aac -b:a:0 96k  -ar:a:0 44100 \
  -c:a:1 aac -b:a:1 128k -ar:a:1 44100 \
  -c:a:2 aac -b:a:2 160k -ar:a:2 44100 \
  \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  -tune zerolatency \
  \
  -f hls -hls_time 2 -hls_list_size 10 \
  -hls_flags delete_segments+append_list \
  -hls_segment_type mpegts \
  \
  -var_stream_map "v:0,a:0 v:1,a:1 v:2,a:2" \
  \
  -master_pl_name master.m3u8 \
  -hls_segment_filename ${OUTPUT_DIR}/${STREAM_KEY}/%v/seg_%03d.ts \
  ${OUTPUT_DIR}/${STREAM_KEY}/%v/playlist.m3u8

echo "转码完成，输出目录: ${OUTPUT_DIR}/${STREAM_KEY}"
echo "主播放列表: ${OUTPUT_DIR}/${STREAM_KEY}/master.m3u8"
```

**要点**：
- `-preset veryfast` 在实时转码中优先保证速度，牺牲一些压缩效率
- `-tune zerolatency` 减少编码器内部缓冲，降低转码延迟
- `-g 60 -keyint_min 60` 在 30fps 下每 2 秒一个关键帧，与 `-hls_time 2` 对齐
- 每个码率独立的音频编码允许不同码率使用不同音频质量
