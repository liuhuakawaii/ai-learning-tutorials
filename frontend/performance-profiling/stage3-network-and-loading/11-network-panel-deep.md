# Network 面板深度

> 一个请求从发起到内容到达浏览器，中间经历了什么？Network 面板的 Timing 轨道把每一步都拆开了。

## 打开 Network 面板

`F12` → Network 面板。勾选 "Preserve log" 可以在页面跳转后保留请求记录。勾选 "Disable cache" 模拟首次访问（无缓存）。

刷新页面，你会看到一列请求。每一行代表一个资源：HTML、CSS、JS、图片、字体、API 调用。

列的含义：
- **Name**：资源文件名
- **Status**：HTTP 状态码
- **Type**：资源类型（document、stylesheet、script、image 等）
- **Size**：资源大小（压缩后）
- **Time**：请求耗时
- **Waterfall**：请求的时间线条

## Timing 轨道的每个阶段

点击任意一个请求，切到 **Timing** 标签页。你会看到请求被拆成多个阶段：

**Queueing（排队）**：请求创建后到实际开始的等待时间。浏览器对同一域名有并发限制（HTTP/1.1 通常是 6 个），超出的请求要排队。如果你看到很多请求排队，说明并发请求太多了。

**Stalled（阻塞）**：类似排队，但原因更多样——等待 TCP 连接可用、被更高优先级的请求抢占等。

**DNS Lookup（DNS 解析）**：把域名转换成 IP 地址。第一次访问某个域名时需要 DNS 解析，后续会缓存。如果 DNS 时间很长（>100ms），考虑用 `dns-prefetch`。

**Initial connection（TCP 连接）**：建立 TCP 连接的三次握手。如果是 HTTPS，还包含 TLS 协商。如果这个阶段很长，说明到服务器的网络延迟高。

**Request sent（发送请求）**：浏览器发送请求头和请求体的时间。通常很快（<1ms），除非上传了大文件。

**Waiting (TTFB)（等待首字节）**：从请求发出到收到服务器第一个字节的时间。这是衡量服务器响应速度的关键指标。TTFB 高说明服务器处理慢或网络延迟大。

**Content Download（内容下载）**：接收响应内容的时间。取决于响应体大小和网络带宽。

## 判断瓶颈在哪里

看 Timing 轨道，哪个阶段最长，瓶颈就在哪：

- **TTFB 长**（>200ms）：服务器慢或网络延迟高。方向：优化服务端、用 CDN、用缓存
- **Content Download 长**：资源太大或带宽不够。方向：压缩资源、代码分割、图片优化
- **Queueing/Stalled 长**：并发请求太多或域名有限制。方向：减少请求数、用 HTTP/2、域名分片
- **DNS + Initial connection 长**：到服务器的连接建立慢。方向：用 `preconnect`、用 CDN

## 请求优先级

浏览器不是同时发出所有请求。它会根据资源类型和在文档中的位置分配优先级：

- **Highest**：HTML 文档、CSS（`<head>` 中的 `<link>`）
- **High**：`<script>` 标签（在 `<head>` 中的 sync script）
- **Medium**：图片（首屏可见的）
- **Low**：异步 script（`async`/`defer`）、非首屏图片
- **Lowest**：`prefetch` 的资源

在 Network 面板里，右键列标题勾选 "Priority"，可以看到每个请求的优先级。

如果低优先级的资源（比如首屏图片）加载很慢，可以用 `fetchpriority="high"` 提升优先级：

```html
<img src="hero.jpg" fetchpriority="high" alt="Hero" />
```

## HTTP 版本的影响

Network 面板的列里也可以看到每个请求的协议版本。

**HTTP/1.1**：每个 TCP 连接一次只能处理一个请求。浏览器会为同一域名打开 6 个连接，但 6 个以上就要排队。

**HTTP/2**：一个 TCP 连接可以多路复用多个请求。理论上不需要排队，但浏览器仍然有优先级调度。

**HTTP/3**：基于 QUIC，解决了 TCP 的队头阻塞问题。

在 Network 面板里，如果你看到大量请求排队且协议是 HTTP/1.1，升级到 HTTP/2 可能会显著改善加载速度。

## 响应头里的性能信息

点击一个请求，看 **Headers** 标签。几个和性能相关的响应头：

- `Content-Encoding: gzip` / `br`：响应是否压缩了
- `Cache-Control: max-age=31536000`：缓存策略
- `ETag` / `Last-Modified`：条件请求的验证信息
- `Connection: keep-alive`：是否复用 TCP 连接

如果一个 JS/CSS 资源没有 `Cache-Control` 头，每次访问都会重新下载。

## 一个具体的分析

打开一个电商首页，按 Size 列降序排列。找出最大的几个资源：

1. 可能看到一个 200KB+ 的 JS bundle——这是代码分割的优化目标
2. 几张 100KB+ 的图片——这是图片压缩或懒加载的目标
3. 一个 50KB 的字体文件——考虑 `font-display: swap`

再按 Time 列降序排列，找出最慢的请求：

1. 可能是某个第三方 API 调用 TTFB 很高——这是后端优化的目标
2. 可能是一张大图片下载很慢——这是压缩或格式优化的目标

## 参考答案

### 练习一

典型的新闻网站分析结果：

- 最慢的请求通常是首屏图片或第三方广告脚本
- TTFB 可能在 50-300ms 之间（取决于服务器和 CDN）
- Content Download 对大资源来说可能是主要瓶颈
- 如果有很多来自同一域名的小请求，Queueing 可能很明显

关键判断：如果 TTFB 占了总时间的大部分，优化方向是服务端或 CDN；如果 Content Download 占大部分，优化方向是资源压缩。

### 练习二

HTTP/2 相比 HTTP/1.1 的典型优势：
- 请求不再按域名 6 个一组排队
- 多个小请求可以共享一个 TCP 连接
- 总加载时间通常减少 20-40%（对于请求多的页面）

但 HTTP/2 不是万能的——对于单个大文件的下载，速度差异不大。
