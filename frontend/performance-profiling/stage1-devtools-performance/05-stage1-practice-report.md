# 阶段实战：分析一个真实页面并输出性能报告

> 前四课学了面板操作、帧率、渲染流水线和 Main 轨道。现在把它们组合起来，对一个真实页面做完整的性能分析。

## 这节课要做什么

选择一个真实网站（不是你自己写的 demo），用 Performance 面板做一次完整的加载和交互分析，输出一份结构化的性能报告。

这不是走流程——报告的目的是训练你从数据中提取结论的能力。

## 选择分析目标

建议选择以下类型的页面：
- 电商首页（内容多、交互复杂、有大量图片）
- 新闻/资讯列表页（长列表、无限滚动）
- 后台管理系统的仪表盘（图表多、数据量大）

避免选择：
- 纯静态页面（没有太多可分析的内容）
- 需要登录才能访问的页面（登录流程会干扰录制）
- 你自己写的简单 demo（缺乏真实复杂度）

## 录制两份 trace

### Trace 1：页面加载

1. 打开无痕模式窗口（避免扩展程序干扰）
2. 打开 DevTools → Performance 面板
3. 点击刷新按钮（Record and reload）
4. 等页面完全加载并停止录制

### Trace 2：用户交互

1. 保持同一个页面
2. 点击圆点按钮开始录制
3. 执行一次典型用户操作（比如点击导航、滚动列表、打开下拉菜单）
4. 停止录制

## 分析框架

对每份 trace，按以下维度分析：

### 1. 帧率概览

- Frames 轨道上掉帧（红色竖线）的比例大约是多少？
- 最严重的掉帧持续了多久？
- 掉帧发生在加载阶段还是交互阶段？

### 2. 长任务识别

- Main 轨道上有几个超过 50ms 的 Task？
- 最长的 Task 耗时多少？
- 这些长任务是 JavaScript 执行（黄色）还是渲染（紫色/绿色）？

### 3. 渲染流水线分析

- 点击最长的 Task，看 Summary 标签
- Scripting / Rendering / Painting 各占多少比例？
- 有没有强制同步布局的迹象（密集排列的紫色 Layout 色块）？

### 4. 关键函数

- 在 Bottom-Up 标签下，Self Time 最高的 5 个函数是什么？
- 这些函数是你认识的业务代码还是第三方库？
- 有没有可以识别的反模式（如频繁的 `getBoundingClientRect`、大量的 `createElement`）？

### 5. 网络影响

- Network 轨道上有多少个请求？
- 有没有请求阻塞了渲染（出现在渲染之前且耗时较长）？
- 请求是串行还是并行的？

## 怎样判断优化方向

看 Summary 里三类工作的比例，决定优化策略：

**Scripting 占比高（>60%）**：
- JavaScript 执行时间过长
- 方向：代码拆分、懒加载、减少不必要的计算、用 Web Worker

**Rendering 占比高（>30%）**：
- 样式计算或布局开销大
- 方向：减少 DOM 节点数、避免强制同步布局、用 CSS Containment

**Painting 占比高（>20%）**：
- 绘制区域大或绘制效果复杂
- 方向：减少绘制区域、用 `transform` 代替位置属性、减少 `box-shadow` 和 `blur`

## 一份好的报告长什么样

好的性能报告不是把面板上的数字抄一遍。它应该包含：

**数据**：具体的数字和百分比
**判断**：基于数据得出的结论
**归因**：问题可能出在哪里
**建议**：具体的优化方向

不推荐：

```
Scripting 占比 72%，Rendering 占比 18%，Painting 占比 10%。
```

推荐：

```
Scripting 占比 72%，主要来自一个 120ms 的初始化 Task。
Bottom-Up 显示 Self Time 最高的是一个 JSON.parse 调用（35ms），
这可能是首屏数据的解析。建议检查是否可以流式解析或延迟解析非首屏数据。
```

## 练习

### 练习一：完成完整分析

选择一个真实网站，按上面的框架完成两份 trace 的分析，输出完整的性能报告。

报告中至少要包含：
- 3 个具体的数字结论（不能只说"很多""很少"）
- 2 个有依据的优化建议
- 1 个你在分析中发现的意外或疑问

### 练习二：对比两个网站

选两个同类型的网站（比如两个新闻网站或两个电商平台），分别做性能分析，对比它们的差异。

记录：
- 哪个网站的掉帧更严重？
- 两个网站的 Scripting / Rendering / Painting 比例有什么不同？
- 它们各自的主要瓶颈是什么？

---

## 参考答案

这个练习没有标准答案——每个网站的性能特征都不同。但一份合格的报告应该满足：

1. **数据准确**：数字来自实际录制，不是估计
2. **分析有逻辑**：从数据到结论有推理过程，不是直接跳到结论
3. **建议可操作**：优化建议应该是具体的（"减少首页加载的 JS 体积"而不是"优化性能"）
4. **发现了至少一个非显而易见的问题**：比如你可能发现某个看起来很简单的操作其实触发了大量布局计算

对比练习的价值在于：你会发现不同网站的瓶颈完全不同。有的卡在 JavaScript 执行，有的卡在布局计算，有的卡在网络加载。这让你理解性能优化没有通用方案——必须先分析，再优化。
