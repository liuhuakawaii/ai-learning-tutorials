# Performance 面板全景

> 打开 Chrome DevTools 的 Performance 面板，满屏的色块、时间线、火焰图——它们各自代表什么？

## 为什么要先认识面板

很多开发者第一次打开 Performance 面板的反应是：点录制，等几秒，停止，然后盯着一堆彩色条看半天，关掉。

问题不在于工具不好用，而在于面板的信息密度太高。如果不理解每个区域在表达什么，录制再多次也找不到问题。

这节课的目标很简单：让你下次打开 Performance 面板时，能说出"这块红色是什么意思""这条线为什么突然变高""下面这个表格在告诉我什么"。

## 录制一个最简单的 trace

打开 Chrome，进入任意页面（建议先用一个内容较多的页面，比如新闻网站或电商首页）。

1. `F12` 打开 DevTools，切到 Performance 面板
2. 点击左上角的刷新按钮（Record and reload），不是中间那个圆点
3. 等页面加载完成并停止录制

刷新按钮和圆点按钮的区别：刷新按钮会从页面加载的第一帧开始录制，覆盖完整的加载过程；圆点按钮从当前时刻开始录制，适合分析交互行为。

## 时间线区域

录制完成后，最上面是一条横向时间线。它不是一个图表，而是一个可交互的时间轴——你可以用鼠标框选一段区域来放大查看。

时间线上方有两条细线：

- **FPS 轨道**（绿色/红色柱状）：每一帧的帧率。绿色表示接近 60fps，红色表示掉帧
- **CPU 轨道**（面积图）：CPU 在每个时间段的忙碌程度

这两条线的关系很直观：CPU 持续高负载时，FPS 往往会下降。但高 CPU 不一定导致掉帧——如果任务被合理分散到多帧，CPU 高但 FPS 仍然可以是绿色的。

## Main 轨道

时间线中间最大的区域是 **Main 轨道**，它展示的是主线程上发生的所有事情。

每个色块是一个 Task（任务）。色块的宽度代表任务的执行时长。色块堆叠的深度代表调用栈的层级——外层是调用者，内层是被调用者。

颜色含义：
- **黄色**：JavaScript 执行
- **紫色**：样式计算和布局（Recalculate Style、Layout）
- **绿色**：绘制和合成（Paint、Composite）
- **灰色**：系统开销

点击任意一个色块，下方的 Summary 面板会显示这个任务的详细信息。

## Summary 面板

选中某个 Task 后，底部面板会切换到三个标签页：

**Summary 标签**：饼图形式展示这个任务的时间分布——Scripting、Rendering、Painting 各占多少。如果 Scripting 占了 90%，说明 JavaScript 是瓶颈；如果 Painting 占大头，可能是视觉效果太复杂。

**Bottom-Up 标签**：按耗时从高到低排列所有函数。这里能看到哪个函数最耗时。注意 Self Time 和 Total Time 的区别——Self Time 是函数自身执行的时间（不含调用的子函数），Total Time 包含所有子调用。一个函数 Total Time 很长但 Self Time 很短，说明它的子调用才是问题。

**Call Tree 标签**：按调用树的结构展示，从根节点开始展开。适合从顶层追踪某个操作的完整调用链。

**Event Log 标签**：按时间顺序列出所有事件，包括浏览器内部事件。当你需要确认某个事件的触发时机时用它。

## 火焰图

Main 轨道本身就是火焰图的一种表现形式。火焰图的核心规则：

- 横轴是时间，越往右越晚
- 纵轴是调用栈深度，越往下层级越深
- 每个色块是一个函数调用，宽度 = 执行时长

一个常见的误解是"色块越宽说明这个函数越慢"。这不完全正确——色块宽度包含子调用的时间。要判断函数本身是否慢，需要看 Summary 面板里的 Self Time。

## 其他轨道

Main 轨道下方可能还有其他轨道，取决于页面使用了哪些特性：

- **Network 轨道**：网络请求的时间线，每个横条是一个请求，颜色区分请求类型
- **Frames 轨道**：每一帧的截图缩略图，鼠标悬停可以看到该帧的页面快照
- **Timings 轨道**：性能标记（Performance Mark）和用户自定义的时间点
- **Interactions 轨道**：用户交互事件（点击、输入等）的响应时间

## 一个具体的观察

打开一个新闻网站首页录制一次 trace，在 Main 轨道上找一个较宽的黄色色块。点击它，看 Summary 面板。

你可能会看到类似这样的分布：
- Scripting: 72%
- Rendering: 18%
- Painting: 10%

再切到 Bottom-Up 标签，看看 Self Time 最高的几个函数。如果看到 `parseHTML` 或 `compile code` 排在前面，说明 JavaScript 解析和编译占了大量时间——这在首次加载包含大量 JS 的页面时很常见。

如果看到某个你认识的第三方库函数排在前面（比如 `react-dom.development.js` 里的某个函数），那你就有明确的优化方向了。

## 常见的误读

**误读一**："页面加载了 3 秒，说明性能差。" 不一定。3 秒是墙上时间（wall time），包含了网络等待。在 Performance 面板里，你需要关注的是 Main 轨道上 JavaScript 的实际执行时间，而不是总时长。

**误读二**："CPU 轨道一直是满的，说明 CPU 不够用。" 在录制期间 CPU 满载是正常的，因为录制本身就会消耗资源。关键是看录制期间 FPS 有没有持续掉帧。

**误读三**："Bottom-Up 里排第一的函数就是罪魁祸首。" 不一定。Self Time 最高的函数确实执行时间最长，但它可能是一个合理开销很大的操作（比如首次渲染的 `commitRoot`）。真正需要关注的是那些"不应该花这么久"的函数。

## 练习

### 练习一：录制并解读

打开你最常用的一个网站（不是 localhost），用 Performance 面板录制一次页面加载。

1. 找到 Main 轨道上最宽的三个色块，分别记录它们的 Task 类型和耗时
2. 点击最宽的那个色块，在 Bottom-Up 标签下找出 Self Time 最高的三个函数
3. 在 Summary 标签下，记录 Scripting / Rendering / Painting 的百分比

### 练习二：对比加载与交互

对同一个网站做两次录制：
1. 第一次用刷新按钮录制页面加载
2. 第二次用圆点按钮录制一次滚动或点击操作

对比两次录制的 Main 轨道，描述加载过程和交互过程在任务分布上有什么不同。

---

## 参考答案

### 练习一

记录结果会因网站不同而变化，但你应该能观察到：

- 首次加载通常 Scripting 占比最高（60-80%），因为浏览器要解析、编译和执行大量 JavaScript
- 最宽的色块往往出现在页面初始化阶段，包含 React/Vue 的 hydration 或框架初始化
- Self Time 最高的函数通常是浏览器内部函数（如 `parseHTML`、`compile`）或框架的渲染函数

关键不是记住了什么数字，而是你开始能读懂面板在说什么。

### 练习二

加载录制和交互录制的典型差异：

- 加载录制的 Main 轨道前期非常密集，大量任务连续执行，几乎没有空闲
- 交互录制的任务分布更分散，单个任务通常更短
- 加载录制中 Network 轨道会很丰富；交互录制中 Network 轨道可能只有零星请求
- 交互录制中如果出现长任务（>50ms 的色块），往往比加载时的长任务更影响用户体验，因为它会阻塞用户的下一步操作
