# 01. 脚手架设计原则

> 脚手架不是"生成一堆文件"——它是团队工程规范的可执行表达

## 本课目标

- 理解脚手架的本质和价值
- 掌握脚手架设计的核心原则
- 建立脚手架设计的思维模型

## 从一个真实场景说起

你有没有这样的经历：

1. **新项目启动时**：花半天时间配置 ESLint、Prettier、TypeScript、Webpack，结果发现配置错了
2. **团队协作时**：每个人生成的项目结构都不一样，代码风格也不统一
3. **技术升级时**：想升级某个工具，但不知道会影响哪些配置，不敢轻易改动
4. **项目复制时**：从 A 项目复制配置到 B 项目，结果漏了几个文件，线上出了问题

这些问题的根源是：**团队的工程规范没有被工具化**。

脚手架的价值就是把"应该怎么做"变成"自动怎么做"。

## 脚手架的本质

脚手架不是简单的"文件复制器"，而是**团队工程规范的可执行表达**。

举个例子：

```bash
# 没有脚手架时
mkdir my-app
cd my-app
npm init -y
npm install react react-dom
npm install -D typescript @types/react @types/react-dom
# 手动创建 tsconfig.json
# 手动创建 .eslintrc.js
# 手动创建 .prettierrc
# 手动创建 src/index.tsx
# 手动创建 public/index.html
# ... 还有 20 个配置文件
```

```bash
# 有脚手架时
npx create-my-app my-app
# 选择 React + TypeScript + ESLint + Prettier
# 5 分钟后，一个完整可运行的项目就创建好了
```

脚手架不只是省时间，更重要的是**保证一致性**。

## 脚手架设计的核心原则

### 原则一：约定优于配置（Convention over Configuration）

**核心思想**：脚手架应该提供合理的默认值，用户只需要关注差异化的部分。

**为什么重要**：

- 减少决策疲劳：用户不需要纠结每个配置项
- 保证一致性：所有项目都遵循相同的约定
- 降低学习成本：新成员只需要知道"约定是什么"

**反例**：

```bash
# 反例：每个配置都要用户选择
? 使用什么包管理器？(npm/yarn/pnpm)
? 使用什么 TypeScript 版本？(4.x/5.x)
? 使用什么 ESLint 版本？(7.x/8.x)
? 使用什么 Prettier 版本？(2.x/3.x)
? 是否启用严格模式？(y/n)
? 是否启用 JSX？(y/n)
? 是否启用 ESModule？(y/n)
# ... 20 个问题
```

**正例**：

```bash
# 正例：只问关键问题
? 项目名称：my-app
? 选择技术栈：(React + TypeScript + Vite)
? 是否需要 ESLint？(y/n)
? 是否需要 Prettier？(y/n)
# 5 个问题就够了
```

### 原则二：零配置理念（Zero Configuration）

**核心思想**：用户不做任何配置，脚手架就能工作。

**为什么重要**：

- 降低入门门槛：新手也能快速开始
- 减少配置错误：用户不会配错
- 提升开发体验：开箱即用

**反例**：

```bash
# 反例：需要大量配置才能运行
npx create-my-app my-app
cd my-app
npm install
# 报错：缺少 .env 文件
cp .env.example .env
# 报错：缺少数据库配置
# 手动修改 config/database.js
# 报错：缺少 API 密钥
# 手动修改 .env
# 终于能运行了，但花了 30 分钟
```

**正例**：

```bash
# 正例：开箱即用
npx create-my-app my-app
cd my-app
npm run dev
# 立即运行，所有配置都有合理默认值
```

### 原则三：可扩展性（Extensibility）

**核心思想**：脚手架应该支持用户扩展和定制。

**为什么重要**：

- 满足不同需求：不同项目有不同需求
- 支持团队定制：不同团队有不同规范
- 便于维护：核心稳定，扩展灵活

**反例**：

```bash
# 反例：硬编码，无法定制
npx create-my-app my-app --template react
# 只能生成 React 项目
# 想用 Vue？没门
# 想加 GraphQL？没门
# 想换 CSS 方案？没门
```

**正例**：

```bash
# 正例：支持插件扩展
npx create-my-app my-app --template react
# 添加 GraphQL 支持
my-cli add graphql
# 添加 CSS Modules 支持
my-cli add css-modules
# 添加 Storybook 支持
my-cli add storybook
```

### 原则四：渐进式（Progressive）

**核心思想**：脚手架应该支持从简单到复杂的渐进式配置。

**为什么重要**：

- 适合不同阶段：从 MVP 到企业级
- 降低复杂度：先简单，后复杂
- 支持演进：随着项目成长逐步完善

**反例**：

```bash
# 反例：要么全有，要么全无
npx create-my-app my-app --full
# 生成 100+ 文件，很多用不上
# 想要简单点？没门
```

**正例**：

```bash
# 正例：渐进式配置
npx create-my-app my-app
# 最小化配置，能运行就行
cd my-app
my-cli add typescript
# 添加 TypeScript 支持
my-cli add eslint
# 添加 ESLint 支持
my-cli add storybook
# 添加 Storybook 支持
```

## 脚手架的分类

### 按生成方式分类

#### 1. 静态模板型

**特点**：基于模板文件直接复制或简单变量替换。

**适用场景**：
- 项目结构固定
- 配置项少
- 不需要复杂逻辑

**例子**：
```bash
# 使用 degit 复制模板
degit user/template my-app
```

**优点**：简单、快速、易维护
**缺点**：灵活性差、无法处理复杂逻辑

#### 2. 动态生成型

**特点**：根据用户输入动态生成文件和配置。

**适用场景**：
- 项目结构可变
- 配置项多
- 需要复杂逻辑

**例子**：
```bash
# 使用脚手架工具
npx create-react-app my-app
npx create-vue my-app
```

**优点**：灵活、强大、可定制
**缺点**：复杂、维护成本高

#### 3. 混合型

**特点**：结合静态模板和动态生成。

**适用场景**：
- 大部分文件静态，少部分动态生成
- 需要平衡灵活性和简单性

**例子**：
```bash
# 复制模板，然后动态生成部分文件
npx create-next-app my-app
```

### 按使用场景分类

#### 1. 项目脚手架

**特点**：创建完整的项目结构。

**例子**：
- Create React App
- Vue CLI
- Next.js Create

#### 2. 代码生成器

**特点**：在现有项目中生成代码片段。

**例子**：
- Plop.js
- Hygen
- 自定义生成器

#### 3. 配置脚手架

**特点**：生成或更新配置文件。

**例子**：
- ESLint 配置生成器
- TypeScript 配置生成器
- Webpack 配置生成器

## 脚手架设计的关键决策

### 决策一：模板引擎选择

| 模板引擎 | 优点 | 缺点 | 适用场景 |
|----------|------|------|----------|
| EJS | 简单、直观、JavaScript 原生 | 功能相对简单 | 简单项目 |
| Handlebars | 功能强大、社区活跃 | 学习曲线稍高 | 复杂项目 |
| Mustache | 极简、无逻辑 | 功能有限 | 极简项目 |
| Pug | 强大、灵活 | 语法差异大 | 特定需求 |

**建议**：大多数情况下选择 EJS，简单够用。

### 决策二：交互方式选择

| 交互方式 | 优点 | 缺点 | 适用场景 |
|----------|------|------|----------|
| 命令行参数 | 快速、可脚本化 | 记忆负担重 | 简单项目 |
| 交互式问答 | 用户友好、引导性强 | 速度慢 | 复杂项目 |
| 配置文件 | 可复用、可版本控制 | 需要手动创建 | 团队项目 |

**建议**：组合使用，命令行参数 + 交互式问答。

### 决策三：模板管理方式

| 管理方式 | 优点 | 缺点 | 适用场景 |
|----------|------|------|----------|
| 内置模板 | 简单、快速、离线可用 | 更新不便 | 个人项目 |
| 远程模板 | 灵活、可共享、可更新 | 依赖网络 | 团队项目 |
| 混合方式 | 平衡灵活性和简单性 | 实现复杂 | 大型项目 |

**建议**：先内置常用模板，支持远程模板扩展。

## 脚手架的常见陷阱

### 陷阱一：过度设计

**问题**：想一次性支持所有场景，导致脚手架过于复杂。

**表现**：
- 配置项太多，用户不知道选什么
- 模板太多，维护成本高
- 插件系统太复杂，没人用

**解决方案**：
- 从最小可用版本开始
- 根据实际需求逐步扩展
- 保持核心简单

### 陷阱二：忽视错误处理

**问题**：只考虑 happy path，不考虑错误情况。

**表现**：
- 网络失败时没有提示
- 文件已存在时没有处理
- 依赖安装失败时没有回滚

**解决方案**：
- 每个操作都要有错误处理
- 提供清晰的错误信息
- 支持重试和回滚

### 陷阱三：不考虑升级

**问题**：脚手架生成的项目无法升级。

**表现**：
- 想升级某个工具，但配置冲突
- 想添加新功能，但结构不支持
- 脚手架新版和旧版不兼容

**解决方案**：
- 设计可升级的配置结构
- 提供迁移工具
- 保持向后兼容

### 陷阱四：忽视用户体验

**问题**：只考虑功能，不考虑使用体验。

**表现**：
- 命令太长，记不住
- 交互太复杂，不想用
- 反馈不明确，不知道发生了什么

**解决方案**：
- 简化命令
- 优化交互流程
- 提供清晰的反馈

## 脚手架设计流程

### 第一步：明确目标

- 脚手架要解决什么问题？
- 目标用户是谁？
- 核心功能是什么？

### 第二步：设计交互

- 用户如何使用脚手架？
- 需要哪些输入？
- 输出什么结果？

### 第三步：设计模板

- 需要哪些模板文件？
- 模板如何组织？
- 模板如何扩展？

### 第四步：实现核心

- 实现基本的文件复制
- 实现变量替换
- 实现错误处理

### 第五步：优化体验

- 添加交互式问答
- 添加进度提示
- 添加错误信息

### 第六步：测试验证

- 测试各种场景
- 验证输出正确性
- 收集用户反馈

## 本课小结

本课我们理解了脚手架设计的核心原则：

1. **约定优于配置**：提供合理默认值，用户只需关注差异
2. **零配置理念**：开箱即用，降低入门门槛
3. **可扩展性**：支持用户定制和扩展
4. **渐进式**：从简单到复杂，逐步完善
