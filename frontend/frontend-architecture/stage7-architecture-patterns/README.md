# stage7：架构模式与状态管理

> 架构不是画大图，是为真实问题选择合适的解法——然后在变化中持续调整

## 学习目标

完成本阶段后，你将能够：
- 理解前端架构的本质：在约束条件下做出可维护的技术决策
- 区分全局状态、局部状态和服务端状态，选择合适的状态管理方案
- 设计数据获取与缓存策略，理解 SWR/React Query 的核心原理
- 规划路由架构，实现路由守卫、动态路由和面包屑生成
- 理解微前端的适用场景和主流方案（qiankun/Module Federation/single-spa/iframe）
- 掌握微前端落地中的真实问题：样式隔离、JS 沙箱、通信机制、共享依赖
- 设计国际化架构，处理多语言、RTL 布局、日期和货币格式化
- 构建主题与换肤系统，支持暗色模式和用户自定义主题
- 制定架构演进策略，管理技术债，记录架构决策（ADR）
- 综合运用所学知识，为一个真实业务场景设计微前端架构方案

## 前置要求

- 完成 stage1 工程化基础与 Monorepo
- 完成 stage2 组件库设计

## 学习建议

1. **从问题出发**：每个架构模式都是为了解决特定问题。先理解问题，再学方案。不要为了用 Zustand 而用 Zustand
2. **关注权衡**：没有完美的架构，只有合适的取舍。每节课都会强调方案的代价和边界
3. **动手验证**：看完代码示例后，自己动手写一遍。架构决策需要在代码层面验证可行性
4. **联系实际**：把你当前项目的问题带进来。学完状态管理后，回去看看项目里的状态是怎么管理的，有没有更好的方式
5. **不要过度设计**：小项目不需要微前端，简单场景不需要 Redux。架构的复杂度应该匹配问题的复杂度

## 阶段项目

为一个真实业务场景设计微前端架构方案。

### 项目要求

假设你所在团队负责一个大型 B2B SaaS 平台，包含以下子系统：
- **主控制台**：用户管理、权限管理、系统设置（React 18）
- **数据分析**：图表、报表、数据导出（Vue 3）
- **工单系统**：工单列表、工单详情、消息通知（React 18）
- **运营后台**：活动管理、内容管理、营销工具（Vue 3）

不同子系统由不同团队维护，技术栈不完全统一，需要独立开发、独立部署，但用户需要在一个统一的平台中使用。

完成以下工作：

**第一步：需求分析**
- 梳理各子系统的功能边界和技术约束
- 分析团队协作模式和部署流程
- 明确性能、体验、开发效率的优先级

**第二步：方案选型**
- 对比 qiankun、Module Federation、single-spa、iframe 四种方案
- 从技术匹配度、团队能力、迁移成本、社区生态四个维度评估
- 给出选型结论和理由

**第三步：架构设计**
- 设计主应用与子应用的通信机制
- 设计共享依赖策略（公共库、组件库、工具函数）
- 设计样式隔离方案
- 设计路由和导航方案
- 设计公共上下文（用户信息、权限、主题）

**第四步：落地计划**
- 制定渐进式迁移路径
- 设计开发和部署流程
- 识别风险点和应对方案

### 验收标准

- 提供完整的需求分析文档
- 方案选型有对比表格和决策理由
- 架构设计包含通信、依赖、样式、路由四个维度
- 提供关键代码示例（主应用加载子应用、通信机制、共享依赖配置）
- 有明确的落地计划和风险分析
- 架构方案可落地，不是纸上谈兵

## 常见问题

### Q: 小项目需要考虑架构吗？

A: 需要，但不需要复杂的架构。小项目的核心架构决策可能是"用 useState 还是 useReducer"、"API 调用放哪里"、"路由怎么组织"。架构的复杂度应该匹配项目的复杂度。一个 5 个页面的项目引入 Redux + 微前端就是过度设计。

### Q: 状态管理到底该用什么？

A: 先问自己：状态需要跨多少组件共享？如果只在父子组件间传递，用 props 和 Context 就够了。如果需要在不相关的组件间共享，再考虑 Zustand/Jotai 这样的轻量方案。只有在状态逻辑非常复杂（大量异步操作、乐观更新、缓存）时，才考虑 Redux Toolkit 或 React Query。

### Q: 微前端适合什么场景？

A: 微前端适合"多个团队维护多个子系统，需要统一入口"的场景。如果你的团队不到 20 人，项目能在一个仓库里维护，大概率不需要微前端。微前端会引入额外的复杂度（通信、样式隔离、构建部署），这些复杂度需要足够大的收益来抵消。

### Q: 架构决策记录（ADR）真的有必要吗？

A: 非常有必要。三个月后你会忘记"为什么当时选了 Zustand 而不是 Redux"。ADR 不需要很长，一两页说明问题、方案、决策和后果就行。它的价值在于让未来的你（和新同事）理解当时的技术决策，而不是重复踩坑。
