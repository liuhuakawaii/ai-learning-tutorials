# 01. 前端架构不是画大图 —— 从真实需求出发，架构是为了解决具体问题

> 好的架构不是看起来很厉害的图，而是让团队在变化面前不用推倒重来的那些决策

## 本课目标

- 理解前端架构的本质：在约束条件下做出可维护的技术决策
- 识别过度设计和设计不足的区别
- 掌握从真实需求出发思考架构的方法
- 理解架构决策的生命周期：它不是一次性的，而是持续演进的

## 一个典型的架构失败

某团队启动一个新的 SaaS 项目，技术负责人花两周设计了一套"完美"的架构：

```
├── packages/
│   ├── core/              # 核心抽象层
│   ├── adapters/          # 框架适配层（React/Vue 双框架支持）
│   ├── plugins/           # 插件系统
│   ├── state-machine/     # 状态机引擎
│   ├── event-bus/         # 事件总线
│   ├── di-container/      # 依赖注入容器
│   └── utils/             # 工具函数
├── apps/
│   └── main/              # 主应用
└── scripts/               # 构建和部署脚本
```

三个月后：

- 团队只有 4 个人，没人用过依赖注入容器，每次改代码都要先理解抽象层
- "双框架支持"从来没有第二个框架接入过
- 状态机引擎比业务逻辑还复杂
- 新人入职要花两周才能理解项目的调用链路
- 最终团队花了两个月把架构简化回了普通 React + Zustand 的结构

这个故事的教训是：**架构的价值不在于它的抽象程度，而在于它解决了多少真实问题**。

## 什么是前端架构

前端架构不是画一张系统图，不是选一个状态管理库，不是把项目拆成 20 个包。

前端架构是在特定约束下，为了解决真实问题而做出的一系列技术决策：

```
前端架构 = 约束条件 + 真实问题 + 技术决策 + 决策后果
```

### 约束条件

每个项目都有约束，架构决策必须在约束内做出：

```yaml
团队约束:
  - 团队规模: 4 人
  - 技术栈熟悉度: React 熟练，Vue 了解
  - 工程化经验: 有 Monorepo 经验，无微前端经验

业务约束:
  - 项目周期: 3 个月 MVP
  - 用户量: 初期 1000 人，预期一年内增长到 10 万
  - 多端需求: 仅 PC Web，暂无移动端

技术约束:
  - 必须对接公司已有的 Java 后端
  - 必须使用公司统一的 Ant Design
  - 必须支持 IE 11（别问为什么）
```

同样的需求，约束不同，架构决策就不同。4 人团队和 40 人团队的架构不可能一样。

### 真实问题

架构要解决的是真实存在的问题，不是假设的问题：

```typescript
// 真实问题：多个页面需要共享用户信息
// ❌ 假设的问题：未来可能需要支持多租户
// ❌ 假设的问题：未来可能需要支持微前端

// 基于真实问题的决策：
// 用户信息在 3 个页面用到 → 用 Context 或 Zustand 存一份
// 不需要为"未来可能的需求"引入复杂的架构
```

判断一个问题是否"真实"的方法：

```
1. 这个问题现在是否存在？（不是"未来可能会遇到"）
2. 这个问题是否在重复出现？（不是"偶尔一次"）
3. 这个问题的代价是否值得解决？（不是"理论上可以优化"）
4. 解决方案的复杂度是否匹配问题的复杂度？
```

### 技术决策

架构决策不是"选最好的方案"，而是"在约束下选最合适的方案"：

```typescript
// 场景：需要在多个组件间共享表单状态

// 方案 A：Redux Toolkit
// 优点：强大的 DevTools、中间件支持、时间旅行调试
// 代价：样板代码多、学习曲线陡、对于简单表单过于复杂
// 适合：表单逻辑非常复杂、需要撤销/重做、需要持久化

// 方案 B：Zustand
// 优点：API 简洁、无样板代码、学习成本低
// 代价：DevTools 不如 Redux、中间件生态较小
// 适合：中等复杂度的状态共享

// 方案 C：React Hook Form + Context
// 优点：表单专用、性能好、无额外状态库
// 代价：跨组件共享需要额外处理
// 适合：表单是主要场景、不需要全局状态

// 方案 D：URL 参数
// 优点：状态可分享、刷新不丢失、无需额外库
// 代价：只能存简单数据、URL 会变长
// 适合：筛选条件、分页、搜索关键词
```

没有"最好的方案"，只有"在当前约束下最合适的方案"。

### 决策后果

每个架构决策都有后果，包括正面的和负面的：

```typescript
// 决策：使用 Zustand 管理全局状态
// 正面后果：
//   - 状态逻辑集中在 store 中，易于理解和调试
//   - 组件间共享状态变得简单
//   - 团队学习成本低

// 负面后果：
//   - 需要约定 store 的组织方式（否则会乱）
//   - 状态更新逻辑和 UI 逻辑分离，可能增加理解成本
//   - 如果状态量增长，可能需要拆分多个 store

// 中性后果：
//   - 需要决定哪些状态放全局，哪些留组件内
//   - 需要处理异步状态（loading、error）
```

好的架构决策会明确列出这些后果，而不是只说"用 Zustand 就好了"。

## 过度设计 vs 设计不足

架构有两个极端，都不好：

### 过度设计的信号

```typescript
// 信号 1：抽象层比业务代码还多
import { useService } from '@/core/di';
import { createMachine } from '@/core/state-machine';
import { EventBus } from '@/core/event-bus';

// 一个简单的表单提交，需要经过三层抽象
const formMachine = createMachine({
  states: {
    idle: { on: { SUBMIT: 'submitting' } },
    submitting: { on: { SUCCESS: 'success', ERROR: 'error' } },
    success: { on: { RESET: 'idle' } },
    error: { on: { RETRY: 'submitting', RESET: 'idle' } },
  },
});

// 实际上一个 useState 就够了
const [status, setStatus] = useState<'idle' | 'loading' | 'success' | 'error'>('idle');
```

```typescript
// 信号 2：为不存在的需求做设计
// "我们需要支持 React 和 Vue 双框架"
//   → 实际只有 React 一个框架
// "我们需要插件系统，方便未来扩展"
//   → 实际三年没有写过一个插件
// "我们需要微前端，因为未来可能拆分"
//   → 实际只有 5 个页面
```

```typescript
// 信号 3：新人要花很长时间才能开始写业务代码
// "我入职两周了，还在理解项目的抽象层"
// "我写一个按钮要经过 5 个文件"
// "我不知道改这行代码会影响哪些地方"
```

### 设计不足的信号

```typescript
// 信号 1：到处复制粘贴
// 页面 A 的用户信息获取
const fetchUserA = async () => {
  const res = await fetch('/api/user');
  const data = await res.json();
  setUser(data);
  setPermissions(data.permissions);
  setTheme(data.preferences.theme);
};

// 页面 B 的用户信息获取（几乎一样）
const fetchUserB = async () => {
  const res = await fetch('/api/user');
  const data = await res.json();
  setUserInfo(data);
  setRoles(data.roles);
  setLanguage(data.preferences.language);
};
```

```typescript
// 信号 2：改一个地方要改十个地方
// "我改了用户接口的返回格式，然后发现 15 个页面都报错了"
// "我加了一个新的权限角色，然后需要在 8 个文件里都加判断"
```

```typescript
// 信号 3：没人敢重构
// "这段代码没人敢动，因为不知道会影响什么"
// "上次有人重构了工具函数，结果三个页面挂了"
// "这个组件有 2000 行，但没人想拆它"
```

### 如何找到平衡

```
一个简单的判断标准：

如果一个抽象能减少 3 处以上的重复代码，它大概率值得做。
如果一个抽象只减少 1 处重复，但它让代码更清晰，它可能值得做。
如果一个抽象增加了理解成本但没有减少重复代码，它不值得做。
```

## 从需求到架构的思考路径

不要从"用什么技术"开始，从"要解决什么问题"开始：

### 第一步：列出真实需求

```yaml
需求清单:
  - 用户登录后能看到自己的信息
  - 用户信息在导航栏、个人中心、设置页面都要显示
  - 用户修改信息后，所有页面同步更新
  - 用户权限不同，看到的菜单不同
  - 支持深色模式切换
  - 表单数据在切换页面后保留
```

### 第二步：识别状态归属

```yaml
状态分类:
  用户信息:
    使用范围: 全局（导航栏、多个页面）
    更新频率: 低（登录时获取，偶尔更新）
    方案: 全局状态（Zustand store）

  表单数据:
    使用范围: 局部（当前页面）
    更新频率: 高（用户每次输入）
    方案: 局部状态（useState）或表单库

  深色模式:
    使用范围: 全局
    更新频率: 极低
    方案: CSS 变量 + localStorage

  权限信息:
    使用范围: 全局
    更新频率: 低
    方案: 从用户信息中派生，不单独存储
```

### 第三步：选择合适的技术

```typescript
// 基于上面的分析，做出技术决策：

// 1. 全局状态：Zustand（因为只需要共享用户信息，不需要 Redux 的复杂度）
import { create } from 'zustand';

interface UserStore {
  user: User | null;
  setUser: (user: User) => void;
  logout: () => void;
}

const useUserStore = create<UserStore>((set) => ({
  user: null,
  setUser: (user) => set({ user }),
  logout: () => set({ user: null }),
}));

// 2. 表单状态：React Hook Form（因为表单复杂度中等，需要校验）
import { useForm } from 'react-hook-form';

function SettingsForm() {
  const { register, handleSubmit, formState: { errors } } = useForm<SettingsData>();
  // ...
}

// 3. 深色模式：CSS 变量（因为只需要切换颜色，不需要 JS 状态管理）
// 在 CSS 中定义变量，切换时修改 data-theme 属性
```

### 第四步：验证决策

```typescript
// 验证方法：用最小代码实现核心场景

// 场景：用户登录后，导航栏显示用户名
function App() {
  return (
    <Layout>
      <Navbar /> {/* 需要显示用户名 */}
      <Routes>
        <Route path="/dashboard" element={<Dashboard />} />
        <Route path="/settings" element={<Settings />} />
      </Routes>
    </Layout>
  );
}

function Navbar() {
  const user = useUserStore((state) => state.user);
  return <div>{user?.name}</div>;
}

// 如果这个实现足够简单、清晰、能满足需求，那架构决策就是对的。
// 如果你发现需要写很多胶水代码才能让它工作，可能需要重新评估。
```

## 架构决策的生命周期

架构不是一次性的决策，它会随着项目演进：

```
阶段 1：MVP（0-3 个月）
  约束：快速交付、验证业务
  架构：简单直接，能跑就行
  技术：useState + Context + fetch

阶段 2：增长期（3-12 个月）
  约束：功能增多、团队扩大
  架构：引入状态管理、代码分割、基础规范
  技术：Zustand + React Query + ESLint

阶段 3：成熟期（1-3 年）
  约束：维护成本、性能、多团队协作
  架构：模块化、Monorepo、设计系统
  技术：Nx/Turborepo + 组件库 + 微前端（如果需要）

阶段 4：平台期（3 年以上）
  约束：技术债、渐进式迁移
  架构：架构演进、模块替换、渐进式重构
  技术：ADR 记录 + 渐进式迁移策略
```

每个阶段的架构决策都不同。MVP 阶段的"简单直接"不是设计不足，而是正确的决策。成熟期的"模块化"不是过度设计，而是应对增长的必要手段。

## 练习

### 练习一：识别过度设计

以下哪个场景属于过度设计？为什么？

**场景 A**：一个 3 人的创业团队，做一个内部管理工具（5 个页面），引入了 Redux Toolkit + Redux Saga + 自定义中间件 + 模块化 store 设计。

**场景 B**：一个 20 人的团队，做一个电商平台（30+ 页面），引入了 Zustand + React Query。

**场景 C**：一个 5 人的团队，做一个企业官网（8 个页面），引入了 Next.js + MDX + 自定义 CMS。

### 练习二：状态归属分析

一个电商购物车功能，有以下状态：

```yaml
- 购物车商品列表
- 每个商品的数量
- 优惠券信息
- 收货地址
- 商品总价
- 推荐商品列表
- 购物车是否打开（抽屉模式）
```

请分析每个状态的使用范围、更新频率，并给出推荐的状态管理方案。

---

## 参考答案

### 练习一

**场景 A 是过度设计**。

理由：
- 5 个页面的内部管理工具，状态复杂度很低，Redux Toolkit + Redux Saga 的样板代码和学习成本远超收益
- Redux Saga 主要解决复杂的异步流程（竞态、取消、重试），内部管理工具通常不需要
- 3 人团队中如果有 1 人不熟悉 Redux，会显著降低开发效率
- 更合适的方案：Zustand 或 useState + Context

**场景 B 不是过度设计**。

理由：
- 30+ 页面的电商平台，状态复杂度中等偏高
- Zustand 比 Redux 轻量，适合中等规模项目
- React Query 处理服务端状态（商品列表、订单），是正确的工具
- 20 人团队需要一定的规范和约束，Zustand 的简单 API 降低了协作成本

**场景 C 需要看具体需求**。

理由：
- 如果是静态企业官网，Next.js + MDX 是合理的选择（SSG 支持、SEO 友好）
- 自定义 CMS 可能是过度的——如果内容不频繁更新，Markdown 文件就够了
- 如果需要频繁更新内容且有非技术人员编辑，CMS 是必要的
- 关键判断：内容更新频率和编辑者的技术能力

### 练习二

```
购物车商品列表:
  使用范围: 全局（商品详情页"加入购物车"、购物车页面、结算页面、导航栏购物车图标）
  更新频率: 中等（用户增删商品时）
  方案: Zustand store 或 React Query 缓存

每个商品的数量:
  使用范围: 全局（和商品列表绑定）
  更新频率: 中等
  方案: 和商品列表存在同一个 store 中

优惠券信息:
  使用范围: 局部（仅结算页面）
  更新频率: 低（选择优惠券时）
  方案: 局部状态（useState）或结算页的表单状态

收货地址:
  使用范围: 局部（结算页面）+ 全局（导航栏可能显示默认地址城市）
  更新频率: 低
  方案: 放在购物车 store 中，但只在需要时获取

商品总价:
  使用范围: 全局（导航栏购物车图标可能显示总价）
  更新频率: 派生值（从商品列表和优惠券计算）
  方案: 从 store 中的其他状态派生（computed/getter），不单独存储

推荐商品列表:
  使用范围: 局部（购物车页面底部）
  更新频率: 低（页面加载时获取一次）
  方案: React Query 缓存（服务端状态）

购物车是否打开:
  使用范围: 局部（仅控制抽屉的显示/隐藏）
  更新频率: 高（用户每次点击）
  方案: 局部状态（useState）或 Zustand 的 UI slice
```
