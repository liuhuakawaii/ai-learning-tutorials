# stage5：前端监控体系

> 从"出了问题用户告诉你"到"系统主动发现问题"，建立前端可观测性

## 学习目标

完成本阶段后，你将能够：
- 理解可观测性三支柱（日志、指标、链路）在前端的应用
- 设计完整的错误监控系统，包括错误分类、捕获、上报和还原
- 掌握 Source Map 管理和错误堆栈解析
- 采集 Core Web Vitals 等性能指标，并理解每个指标的工程含义
- 设计用户行为追踪方案，区分自动埋点和手动埋点的适用场景
- 搭建监控数据大盘，配置告警规则
- 理解 A/B 测试和特性开关的工程实现
- 对比主流监控平台，能为团队选择合适的方案
- 从零实现一个轻量级前端监控 SDK

## 前置要求

## 学习建议

1. **先理解问题**：每节课都从"这个东西解决什么问题"开始，不要跳过问题直接看方案
2. **动手实现**：课时 01-09 的代码示例都要跑一遍，课时 10 的项目要从零写
3. **关注边界**：监控不是越多越好，关注采样率、数据量、隐私合规
4. **对比思考**：每个方案都有适用场景和代价，不要只记"最佳实践"
5. **结合实际**：想一想你当前项目有没有监控，缺什么，为什么缺

## 阶段项目

实现一个轻量级前端监控 SDK，包含以下功能：

- **错误捕获**：JavaScript 运行时错误、Promise 异常、资源加载错误、网络请求错误
- **性能采集**：LCP、FID/INP、CLS、TTFB，以及页面加载瀑布图数据
- **行为追踪**：PV/UV、点击事件、路由变化、自定义事件
- **数据上报**：批量上报、失败重试、Beacon API 优先、采样控制
- **Source Map 还原**：服务端错误堆栈还原

**验收标准**：
- SDK 能在浏览器环境中正常运行，不产生未捕获异常
- 错误捕获覆盖率：运行时错误、Promise 异常、资源加载错误均可捕获
- 性能指标采集准确，与 Chrome DevTools 数值偏差在 5% 以内
- 数据上报在网络断开时不丢失（使用 localStorage 缓存 + 恢复上报）
- SDK 体积 < 10KB（gzip 后）
- 提供 TypeScript 类型定义
- 提供完整的使用文档和 API 说明

## 常见问题

### Q: 前端监控和后端监控有什么区别？

A: 后端监控主要关注服务健康（CPU、内存、QPS、错误率），环境可控。前端监控面对的是用户的浏览器环境——网络状况各异、设备性能不同、浏览器版本碎片化，而且数据采集本身不能影响用户体验。前端监控的核心挑战是在"不可控环境中采集可信数据"。

### Q: 什么时候应该引入监控？

A: 不需要等到项目"足够大"。哪怕是一个内部工具，只要有用户在用，就需要知道它什么时候出问题。建议在项目初始化时就加入最基础的错误监控（接入 Sentry 只需要几分钟），后续再逐步完善性能和行为监控。

### Q: 监控会影响性能吗？

A: 会，但可以控制在极低水平。关键是：用 Performance Observer 而不是轮询、批量上报而不是逐条发送、采样而不是全量采集。一个设计合理的监控 SDK 对页面性能的影响应该在 1% 以内。

### Q: 自建还是用 SaaS？

A: 90% 的团队应该用 SaaS（Sentry、DataDog 等）。自建方案适合：数据合规要求不允许数据出境、需要深度定制采集和分析逻辑、团队有足够的基础设施运维能力。自建的成本不仅在开发，更在长期维护。
