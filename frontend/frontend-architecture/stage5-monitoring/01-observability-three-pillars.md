# 01. 可观测性三支柱 —— 日志、指标、链路，前端为什么需要可观测性

> 从"出了问题用户投诉"到"系统主动发现并定位问题"，理解可观测性在前端工程中的价值

## 本课目标

- 理解可观测性（Observability）和监控（Monitoring）的区别
- 掌握可观测性三支柱：日志（Logs）、指标（Metrics）、链路（Traces）的核心概念
- 理解前端为什么需要可观测性，以及前端可观测性的特殊挑战
- 建立前端可观测性的整体心智模型

## 一个让人沮丧的场景

周五下午五点，产品经理发来消息："有用户反馈页面打不开。"

你打开浏览器，输入地址，页面正常加载。你问用户用的什么浏览器，用户说"用的手机"。你问什么手机，用户说"好像是华为"。你问什么系统版本，用户说"不知道"。你问是所有页面都打不开还是只有某个页面，用户说"就那个页面"。

你花了半小时，拿到了三个截图、一段模糊的描述，然后开始排查。又过了两小时，你发现是某个第三方 SDK 在特定 WebView 版本下抛了异常，但你的应用没有捕获这个错误，导致页面白屏。

从用户反馈到定位问题，花了接近三小时。

如果你有一个错误监控系统，这个异常在第一个用户遇到时就会被捕获，你会收到一条包含设备型号、浏览器版本、错误堆栈、用户操作路径的完整报告。定位时间从三小时缩短到五分钟。

这就是可观测性的价值：**让系统内部状态可见，让问题定位从"猜测"变成"查数据"**。

## 监控和可观测性不是一回事

这两个词经常混用，但它们代表不同的思维方式。

**监控（Monitoring）** 是"我知道我要看什么"。你预先定义好指标（CPU 使用率、错误率、响应时间），设置阈值，超过就告警。监控回答的是"系统是否健康"。

**可观测性（Observability）** 是"我能在事后问出新问题"。系统产生的数据足够丰富，让你能在没有预见的情况下，通过这些数据推断系统内部发生了什么。可观测性回答的是"为什么系统不健康"。

举个前端的例子：

- 监控告诉你："页面错误率从 0.1% 升到了 2%"
- 可观测性让你能追问："这些错误集中在哪些页面？哪些浏览器？哪些用户？错误发生前用户做了什么？是哪个接口失败导致的？"

可观测性不是"更多的监控"，而是**一种系统设计哲学**——让系统产生足够丰富的内部信号，使得任何未预见的问题都能通过这些信号诊断。

## 可观测性三支柱

可观测性建立在三种类型的遥测数据（Telemetry Data）之上。

### 1. 日志（Logs）

日志是离散的事件记录。每条日志描述一个特定时刻发生了一件事。

```
[2024-01-15T10:23:45.123Z] ERROR  [PaymentService] Payment failed for order #12345
  userId: "u_789"
  amount: 99.00
  currency: "CNY"
  errorCode: "CARD_DECLINED"
  retryCount: 2
```

日志的特点：
- **非结构化或半结构化**：传统日志是文本，现代日志通常用 JSON
- **事件驱动**：每条日志对应一个事件
- **上下文丰富**：可以携带任意字段
- **量大**：一个中等规模的应用每天可能产生数百万条日志

前端日志的典型场景：
- 用户操作记录（点击、滚动、页面跳转）
- 接口请求和响应详情
- 错误发生时的完整上下文
- 第三方 SDK 的行为记录

### 2. 指标（Metrics）

指标是随时间变化的数值。它们是聚合的、可计算的、适合做趋势分析的。

```
# 每秒请求数
http_requests_total{method="GET", path="/api/users", status="200"} 1523

# 页面加载时间分布
page_load_duration_seconds{page="/home", quantile="0.5"} 1.2
page_load_duration_seconds{page="/home", quantile="0.95"} 3.8
page_load_duration_seconds{page="/home", quantile="0.99"} 8.1

# 错误计数
frontend_errors_total{type="javascript", page="/checkout"} 47
```

指标的特点：
- **数值型**：可以做加减、平均、百分位计算
- **时间序列**：每个指标都有时间戳
- **存储高效**：相比日志，指标的存储和查询成本低得多
- **适合告警**：阈值检测、趋势异常检测

前端指标的典型场景：
- Core Web Vitals（LCP、CLS、INP）
- 页面错误率
- 接口成功率和延迟分布
- PV/UV 统计

### 3. 链路（Traces）

链路追踪记录一个请求从发起到完成的完整路径，包括经过的每一个服务和每一个操作。

```
Trace ID: abc123def456
├── [Browser] GET /api/order/detail (总耗时 850ms)
│   ├── [API Gateway] 路由转发 (2ms)
│   ├── [Order Service] 查询订单 (120ms)
│   │   ├── [MySQL] SELECT * FROM orders WHERE id = ? (45ms)
│   │   └── [Redis] GET order:cache:123 (3ms)
│   ├── [User Service] 查询用户信息 (80ms)
│   │   └── [MySQL] SELECT * FROM users WHERE id = ? (60ms)
│   └── [Payment Service] 查询支付状态 (200ms)
│       └── [Third Party] 调用支付网关 (180ms)
```

链路的特点：
- **端到端视角**：跨越前端、网关、后端、数据库
- **因果关系**：能清楚看到时间花在哪里
- **依赖关系**：能发现服务间的调用拓扑
- **慢请求分析**：定位瓶颈在哪一环

前端在链路中的角色：
- 前端是链路的起点——用户点击按钮到看到结果的完整时间
- 前端可以生成 Trace ID 并传递给后端，实现全链路追踪
- 前端的链路追踪更关注"从用户感知到渲染完成"的时间线

## 三支柱如何协作

这三种数据不是孤立的，它们在问题排查中形成互补：

```
用户反馈："页面很慢"

第一步：看指标
  → 发现 LCP 从 1.5s 升到 4.2s（指标告诉你"慢了"）

第二步：看链路
  → 追踪发现 /api/products 接口从 200ms 升到 2.1s（链路告诉你"慢在哪"）
  → 进一步追踪发现数据库查询从 50ms 升到 1.8s

第三步：看日志
  → 查看数据库慢查询日志，发现某张表缺少索引（日志告诉你"为什么慢"）
```

指标发现问题，链路定位瓶颈，日志找到根因。

## 前端可观测性的特殊挑战

后端可观测性已经非常成熟（Prometheus + Grafana + Jaeger 几乎是标配），但前端有独特的挑战。

### 环境不可控

后端运行在你控制的服务器上，CPU、内存、网络环境一致。前端运行在用户的浏览器里：

- 设备性能差异巨大（旗舰手机 vs 五年前的低端机）
- 网络环境不可预测（Wi-Fi vs 4G vs 弱网）
- 浏览器版本碎片化（Chrome 120 vs Safari 15 vs 微信 WebView）
- 浏览器扩展可能干扰页面行为

这意味着前端采集的数据本身就有噪声，需要在分析时考虑这些变量。

### 数据采集的性能代价

后端 SDK 可以放心地同步写日志。前端不行——任何监控代码都会和业务代码竞争 CPU 时间和网络带宽。

```javascript
// 这样做会阻塞主线程
function logEvent(event) {
  const data = JSON.stringify(event);
  navigator.sendBeacon('/api/log', data); // 好的做法
  // XMLHttpRequest.open('POST', '/api/log', false); // 坏的做法——同步请求
}
```

前端监控的铁律：**监控不能成为性能问题的原因**。

### 数据量与成本的矛盾

一个日活 100 万的应用，每个用户每次访问产生 50 条日志、20 个指标、10 条链路——一天就是 8000 万条数据。存储和处理这些数据的成本很高。

所以前端监控必须考虑：
- **采样**：不是每条数据都需要上报
- **聚合**：在客户端做初步聚合，减少上报量
- **分级**：错误全量上报，性能按采样率上报，行为日志按需上报

### 隐私合规

前端数据直接关联用户行为，需要考虑：
- 不能采集用户输入的密码、信用卡号
- 不能未经同意采集用户行为轨迹
- 数据传输和存储需要加密
- 需要符合 GDPR、个人信息保护法等法规要求

## 三支柱在前端的具体形态

后端的三支柱有成熟的技术栈（Prometheus + ELK + Jaeger），前端的形态不太一样。

### 前端日志：事件流

前端日志不像后端那样写文件，而是以事件流的形式上报到服务端。典型的前端日志事件：

```javascript
// 一条错误日志
{
  type: 'error',
  timestamp: 1705312425123,
  level: 'error',
  message: "Cannot read properties of undefined (reading 'name')",
  stack: "TypeError: Cannot read properties...\n  at UserCard (UserCard.tsx:15)",
  url: 'https://app.example.com/dashboard',
  userAgent: 'Mozilla/5.0 (iPhone; CPU iPhone OS 17_2...',
  sessionId: 'sess_abc123',
  userId: 'u_789',
  appVersion: 'v2.1.0',
  breadcrumbs: [
    { timestamp: 1705312420000, type: 'navigation', message: 'Route: /dashboard' },
    { timestamp: 1705312422000, type: 'click', message: 'button#load-profile' },
    { timestamp: 1705312424000, type: 'http', message: 'GET /api/user/u_789 → 200' },
  ]
}
```

这条日志包含了错误本身、用户操作路径、环境信息。面包屑（breadcrumbs）是前端日志区别于后端日志的关键特征——它记录了错误发生前的用户操作序列，对排查"用户做了什么触发了这个错误"非常有用。

### 前端指标：时序数据

前端指标以时序数据的形式存储，适合做趋势分析和告警：

```
# 每分钟的 LCP P75 值
frontend_web_vital{metric="lcp", quantile="0.75", page="/dashboard"} 
  2024-01-15T10:00:00Z  1.8
  2024-01-15T10:01:00Z  1.9
  2024-01-15T10:02:00Z  2.1
  2024-01-15T10:03:00Z  3.5  ← 突然升高
  2024-01-15T10:04:00Z  4.2  ← 持续升高，触发告警
```

指标的价值在于趋势。单个 LCP 值 3.5 秒不能说明什么问题，但如果 P75 LCP 从 1.8 秒在几分钟内上升到 4.2 秒，说明有事情发生了——可能是新版本部署、CDN 故障、第三方脚本变慢。

### 前端链路：用户操作到渲染完成

前端的链路追踪关注的是"从用户感知到结果呈现"的完整时间线：

```
用户点击"搜索"按钮
  ├── 事件处理：12ms
  ├── 发起请求：GET /api/search?q=keyword
  │   ├── DNS: 5ms
  │   ├── TCP: 15ms
  │   ├── TLS: 20ms
  │   ├── TTFB: 180ms
  │   └── Download: 45ms
  ├── 数据处理：8ms
  ├── React 渲染：35ms
  └── DOM 更新 + 绘制：12ms
  总耗时：335ms
```

后端链路追踪用 Trace ID 串联跨服务调用，前端同样可以生成 Trace ID 并通过请求头传递给后端，实现端到端的全链路追踪：

```javascript
// 前端生成 Trace ID 并传递给后端
const traceId = crypto.randomUUID();

fetch('/api/search', {
  headers: {
    'X-Trace-Id': traceId,
    'X-Span-Id': crypto.randomUUID(),
  },
});

// 后端收到后，把这个 Trace ID 写入日志和链路追踪系统
// 这样就可以把前端的请求和后端的处理串联起来
```

## 一个真实的事故复盘

用一个真实场景展示三支柱如何协作定位问题。

**背景**：某电商网站，周五下午 3 点，错误率监控大盘突然变红。

**时间线**：

```
15:00 - 指标告警：/checkout 页面错误率从 0.2% 上升到 8%
15:01 - 值班工程师收到告警，打开 Grafana
15:02 - 查看错误详情：错误类型都是 "TypeError: Cannot read property 'total' of undefined"
15:03 - 查看链路追踪：错误发生在调用 /api/cart 之后
15:04 - 查看日志：/api/cart 接口返回 200，但 data 字段为 null
15:05 - 追踪后端日志：购物车服务的缓存刚刚过期，回源查询时数据库连接池满了
15:06 - 执行预案：清空购物车服务缓存，重启数据库连接池
15:08 - 指标恢复：错误率回落到 0.2%
```

从告警到恢复，总共 8 分钟。如果没有可观测性系统：
- 你不知道出了问题（没有告警）
- 你知道出了问题但不知道什么问题（没有错误详情）
- 你知道什么问题但不知道在哪（没有链路追踪）
- 最终定位可能需要几小时

## 核心概念：信号、上下文、关联

在深入具体技术之前，理解三个核心概念。

### 信号（Signal）

信号是系统发出的任何可观测数据点。一条错误日志是一个信号，一个 LCP 数值是一个信号，一个 Trace Span 也是一个信号。

好的信号应该具备：
- **时间戳**：什么时候发生的
- **来源**：哪个页面、哪个组件、哪个接口
- **上下文**：发生时的环境信息

### 上下文（Context）

上下文是让信号有意义的附加信息。同样是"TypeError: Cannot read property 'name' of undefined"，有没有上下文的区别是：

```
没有上下文：
  Error: TypeError: Cannot read property 'name' of undefined
  at UserCard (UserCard.tsx:15)

有上下文：
  Error: TypeError: Cannot read property 'name' of undefined
  at UserCard (UserCard.tsx:15)
  userId: "u_789"
  page: "/dashboard"
  apiResponse: { status: 200, data: null }
  userAction: "点击了个人中心"
  device: "iPhone 14, iOS 17.2, Safari"
  networkType: "4g"
```

第二种让你能立刻判断：接口返回了 null，UserCard 没有做空值保护。没有上下文的话，你只能看堆栈猜。

### 关联（Correlation）

关联是把不同类型的信号用 ID 串联起来。一个典型的关联链：

```
用户点击"提交订单"（行为追踪）
  → 发起 POST /api/order（日志 + 链路）
  → 接口返回 500（日志）
  → 前端展示错误提示（行为追踪）
  → 用户刷新页面（行为追踪）
  → 页面加载变慢（指标）
```

通过 Session ID 和 Trace ID，你可以把这些信号串成一条完整的事故链。

## 前端可观测性的成熟度模型

不同团队对可观测性的需求不同。可以用一个成熟度模型来评估你当前的位置和下一步目标。

```
Level 0：无监控
  现状：出问题靠用户反馈，开发环境用 console.log 调试
  风险：问题发现慢，定位慢，影响范围不可控
  
Level 1：错误监控
  工具：接入 Sentry 或类似平台
  能力：自动捕获 JS 错误和 Promise 异常，Source Map 还原
  收益：不再依赖用户反馈，错误发生后几分钟内能看到
  
Level 2：性能监控
  新增：Core Web Vitals 采集，页面加载时间监控
  能力：知道哪些页面慢，性能趋势如何
  收益：性能退化能在发布后及时发现
  
Level 3：行为追踪
  新增：PV/UV 统计，用户操作路径，转化漏斗
  能力：理解用户如何使用产品，在哪里流失
  收益：产品决策有数据支撑
  
Level 4：全链路可观测性
  新增：前端到后端的链路追踪，自定义业务指标
  能力：端到端的问题定位，业务指标实时监控
  收益：复杂问题的快速定位，数据驱动的运维决策
  
Level 5：智能运维
  新增：异常检测，自动归因，智能告警
  能力：系统自动发现异常模式，预测潜在问题
  收益：从"被动响应"到"主动预防"
```

大多数团队应该先达到 Level 1（花一天时间接入 Sentry），然后根据业务需要逐步提升。

## 前端可观测性与后端可观测性的对比

| 维度 | 后端 | 前端 |
|------|------|------|
| 运行环境 | 可控（服务器） | 不可控（用户浏览器） |
| 数据采集 | 同步写日志，无性能顾虑 | 异步上报，不能阻塞主线程 |
| 数据量 | 按请求计，可预测 | 按用户会话计，流量更大 |
| 链路追踪 | 跨服务调用，成熟方案多 | 浏览器到网关，方案较少 |
| 告警灵敏度 | 秒级 | 分钟级（需要聚合统计） |
| 隐私考量 | 较少（服务端数据） | 较多（关联用户行为） |
| 数据噪声 | 较低（环境一致） | 较高（设备/网络碎片化） |

理解这些差异很重要。不要试图把后端的监控方案直接搬到前端——它们的约束条件不同，需要不同的设计决策。

## 一个最小的前端可观测性实践

在后面的课程中会详细展开每个组件，这里先用一个最简单的例子让你感受一下前端可观测性的价值。

```javascript
// 最小的前端监控初始化
const monitor = {
  sessionId: crypto.randomUUID(),
  
  init() {
    // 捕获 JavaScript 错误
    window.addEventListener('error', (event) => {
      this.report({
        type: 'error',
        message: event.message,
        filename: event.filename,
        lineno: event.lineno,
        colno: event.colno,
        stack: event.error?.stack,
      });
    });

    // 捕获未处理的 Promise 异常
    window.addEventListener('unhandledrejection', (event) => {
      this.report({
        type: 'unhandledrejection',
        message: event.reason?.message || String(event.reason),
        stack: event.reason?.stack,
      });
    });

    // 页面加载完成后采集性能指标
    window.addEventListener('load', () => {
      setTimeout(() => {
        const timing = performance.getEntriesByType('navigation')[0];
        this.report({
          type: 'performance',
          dns: timing.domainLookupEnd - timing.domainLookupStart,
          tcp: timing.connectEnd - timing.connectStart,
          ttfb: timing.responseStart - timing.requestStart,
          domReady: timing.domContentLoadedEventEnd - timing.startTime,
          load: timing.loadEventEnd - timing.startTime,
        });
      }, 0);
    });

    // 记录页面访问
    this.report({
      type: 'pv',
      url: location.href,
      referrer: document.referrer,
    });
  },

  report(data) {
    const payload = {
      ...data,
      sessionId: this.sessionId,
      timestamp: Date.now(),
      url: location.href,
      userAgent: navigator.userAgent,
    };

    // 优先使用 Beacon API，页面关闭时也能发送
    if (navigator.sendBeacon) {
      navigator.sendBeacon('/api/monitor', JSON.stringify(payload));
    } else {
      fetch('/api/monitor', {
        method: 'POST',
        body: JSON.stringify(payload),
        keepalive: true,
      });
    }
  },
};

monitor.init();
```

这段代码不到 80 行，但已经能捕获：
- JavaScript 运行时错误
- 未处理的 Promise 异常
- 页面加载性能数据
- 页面访问记录

当然，这只是起点。真实的监控系统需要处理采样、聚合、重试、Source Map 还原、数据安全等问题——这些就是后续课程要展开的内容。

### 这段代码做了什么

逐个拆解这段代码中的可观测性信号：

```javascript
// 1. 日志信号：错误事件
// 当 JS 运行时抛出未捕获的异常时，自动采集错误消息、文件名、行号、堆栈
// 这是最基础的可观测性——没有它，你对线上的错误一无所知

// 2. 日志信号：Promise 异常
// async/await 普及后，这类错误越来越多
// 很多开发者忘记 .catch()，错误被静默吞掉

// 3. 指标信号：性能数据
// Navigation Timing API 提供页面加载各阶段的精确时间
// 这些数据可以回答"页面为什么慢"

// 4. 日志信号：页面访问
// 每次页面加载记录一条 PV，是行为追踪的起点
```

## 常见误区

### 误区一：前端不需要可观测性

**错误理解**：前端就是展示页面，出了问题看浏览器控制台就行

**正确理解**：你无法打开每个用户的浏览器控制台。线上问题的排查依赖远程可观测性。而且很多问题只在特定条件下出现（特定设备、特定网络、特定数据），本地无法复现。

### 误区二：监控就是加 try-catch

**错误理解**：把代码包在 try-catch 里，捕获了异常就算有监控了

**正确理解**：try-catch 只解决了错误捕获的一个环节。完整的监控包括：错误捕获、上下文收集、Source Map 还原、聚合去重、告警通知、趋势分析。只捕获不上报，等于没捕获。

### 误区三：监控数据越多越好

**错误理解**：把所有能采集的数据都采集了，以后总会有用

**正确理解**：数据有成本——采集成本（性能开销）、传输成本（带宽）、存储成本（服务器）、分析成本（人力）。采集用不到的数据是浪费。应该从问题出发：你想回答什么问题？需要什么数据？先设计问题，再设计采集。

### 误区四：上了 Sentry 就有可观测性了

**错误理解**：接入 Sentry 等工具就等于有了完整的可观测性

**正确理解**：Sentry 主要解决错误监控，不覆盖性能指标、用户行为、业务指标。而且工具只是手段，真正的可观测性需要：合理的数据采集策略、有效的告警规则、清晰的值班流程、团队的问题复盘文化。

### 误区五：可观测性是运维的事

**错误理解**：前端开发只需要写功能代码，监控是运维团队的事

**正确理解**：前端代码运行在用户浏览器中，传统的运维手段（SSH 登录服务器看日志、看 CPU 监控）完全不适用。前端开发必须自己建立可观测性——没有人比你更了解你的代码可能在哪里出错、哪些性能指标重要、哪些用户行为值得追踪。

### 误区六：console.log 就够了

**错误理解**：开发时用 console.log 调试，线上出了问题让用户截图控制台

**正确理解**：console.log 有几个致命问题：生产环境通常被移除、无法聚合分析、没有上下文、没有时间线、无法设置告警。console.log 是个人调试工具，不是生产监控手段。

## 本课小结

1. **可观测性 vs 监控**：监控是"我知道看什么"，可观测性是"我能问新问题"
2. **三支柱**：日志记录事件、指标度量趋势、链路追踪路径
3. **协作方式**：指标发现问题、链路定位瓶颈、日志找到根因
4. **前端特殊性**：环境不可控、性能敏感、数据量大、隐私合规
5. **核心原则**：监控不能成为性能问题的原因；先设计问题，再设计采集

## 参考答案

### 练习一

典型的前端项目监控现状分析：

```
常见现状：
- 没有任何监控，出问题靠用户反馈
- 或者只接入了 Sentry 做错误监控
- 没有性能监控
- 没有行为追踪
- 没有告警机制

缺失环节：
- 错误发生后无法还原现场（没有 Source Map）
- 不知道哪些页面最慢
- 不知道用户在哪个环节流失
- 不知道哪些错误影响了最多的用户

理想架构：
  浏览器端
    ├── 错误监控（Sentry 或自建）
    ├── 性能采集（Web Vitals + Navigation Timing）
    ├── 行为追踪（PV、点击、路由变化）
    └── 数据上报（Beacon API + 失败重试）
         │
         ▼
  数据接收服务
    ├── 采样和过滤
    ├── 数据校验
    └── 写入消息队列
         │
         ▼
  存储层
    ├── 错误日志（Elasticsearch）
    ├── 性能指标（Prometheus / ClickHouse）
    └── 行为事件（ClickHouse）
         │
         ▼
  展示与告警
    ├── Grafana 数据大盘
    ├── 告警规则（PagerDuty / 飞书机器人）
    └── 周报/月报自动生成
```

### 练习二

1. **指标（Metrics）**：LCP 是一个随时间变化的性能数值，属于指标
2. **链路（Traces）**：描述了一个请求从前端到后端的完整路径，属于链路追踪
3. **日志（Logs）**：一条具体的错误事件记录，属于日志
4. **指标（Metrics）**：接口延迟的百分位统计，属于指标
5. **日志（Logs）**：一个具体的用户操作事件，属于日志（也可视为行为追踪的一部分，但本质上是事件记录）

注意：实际系统中这些分类不是非此即彼的。一条错误日志可能同时携带 Trace ID（关联链路），一个性能指标可能附带用户行为上下文。三支柱是分析框架，不是硬性分类。

