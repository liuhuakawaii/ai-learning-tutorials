# 01. 性能优化心智模型 —— 测量→分析→优化→验证，不要凭感觉优化

> 性能优化不是"听说加个 CDN 就快了"，而是一个有纪律的工程循环

## 本课目标

- 建立"测量→分析→优化→验证"的性能优化心智模型
- 理解为什么凭感觉优化是危险的
- 掌握性能优化的最小闭环
- 理解性能指标与用户体验的关系
- 为后续 9 课建立方法论基础

## 一个典型的性能优化失败

团队反馈"首页加载慢"，你花了一周做了以下优化：

- 给所有图片加了懒加载
- 引入了代码分割
- 配置了 HTTP 缓存
- 开启了 Gzip 压缩

上线后，产品经理说"感觉没什么变化"。

你跑了一下 Lighthouse，分数从 62 涨到了 67。然后你发现，首页加载慢的真正原因是首屏那个 3MB 的 Hero 视频——它没有 poster 图，视频加载前页面一直是白的。而你优化的那些东西，对首屏体验几乎没有影响。

这就是凭感觉优化的典型结果：**花了时间，做了正确的优化，但优化的不是瓶颈**。

## 测量→分析→优化→验证

性能优化必须遵循一个闭环，任何一步都不能跳过。

### 第一步：测量（Measure）

在做任何优化之前，先用工具量化当前状态。

```
你需要回答的问题：
1. 当前的性能指标是什么？（LCP、INP、CLS、TTFB、FCP）
2. 用户感知到的加载体验是怎样的？（录屏、瀑布图）
3. 瓶颈在哪里？（网络？渲染？JS 执行？第三方脚本？）

工具：
- Lighthouse：综合评分 + 优化建议
- Chrome DevTools Performance：运行时性能分析
- Chrome DevTools Network：请求瀑布图
- Web Vitals 扩展：实时指标
- web-vitals 库：RUM 数据采集
```

测量的关键原则：**用真实数据，不用猜测**。

```javascript
// 不要这样做
console.time('render'); // 这种测量太粗糙，不能反映用户体验
renderLargeList();

// 应该这样做
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) {
      console.warn(`Long task: ${entry.duration}ms`, entry);
    }
  }
});
observer.observe({ type: 'longtask', buffered: true });
```

### 第二步：分析（Analyze）

拿到数据后，找到真正的瓶颈。

```
分析框架：按影响程度排序

1. 首屏白屏时间长？
   → 检查 TTFB（后端问题？CDN 问题？）
   → 检查渲染阻塞资源（CSS？JS？字体？）
   → 检查关键资源是否被正确预加载

2. 主要内容出现慢？（LCP 高）
   → LCP 元素是什么？（图片？文本？视频？）
   → LCP 元素什么时候开始加载？
   → 有没有不必要的加载延迟？

3. 页面交互卡顿？（INP 高）
   → 主线程有没有长任务？
   → 事件处理函数里做了什么重计算？
   → 有没有不必要的重渲染？

4. 页面布局跳动？（CLS 高）
   → 什么元素在移动？（图片？广告？动态内容？）
   → 有没有为动态内容预留空间？
```

分析的关键原则：**找到最大的瓶颈，而不是最容易优化的点**。

一个有用的思考方式是"如果我只能做一件事，做什么对用户体验改善最大？"

### 第三步：优化（Optimize）

针对分析出的瓶颈，选择合适的优化策略。

```
优化策略选择的思考框架：

1. 这个优化能带来多大的指标改善？
2. 实现成本是多少？（开发时间、代码复杂度）
3. 有没有副作用？（功能降级、维护成本）
4. 能不能用更简单的方案达到类似效果？

例如：LCP 高因为首屏大图加载慢
- 方案 A：图片压缩 + WebP → 成本低，效果中等
- 方案 B：图片预加载（preload） → 成本极低，效果明显
- 方案 C：SSR 内联关键 CSS + 图片 → 成本高，效果好
- 方案 D：用 CSS 渐变做占位 → 成本极低，感知改善

通常先做成本低、效果明显的方案。
```

优化的关键原则：**一次只改一个变量，方便验证效果**。

如果你同时改了缓存策略、加了代码分割、又改了图片格式，你无法确定哪个优化起了作用。

### 第四步：验证（Verify）

优化后，重新测量，确认效果。

```
验证清单：
1. 优化后的指标是否改善？（对比 before/after）
2. 改善幅度是否符合预期？
3. 有没有引入新问题？（回归测试）
4. 在不同网络条件下表现如何？（Chrome DevTools 限速）
5. 在不同设备上表现如何？（低端手机模拟）

如果指标没有改善：
- 是不是优化的不是瓶颈？→ 回到分析步骤
- 是不是测量方式有问题？→ 回到测量步骤
- 是不是优化没有生效？→ 检查代码和配置
```

验证的关键原则：**用和测量时相同的条件做对比**。

如果测量时用的是 3G 网络模拟，验证时也要用 3G 网络模拟。用不同条件测出的数字没有可比性。

## 为什么不能凭感觉优化

### 原因一：人的感知不可靠

```
实验：两段相同的动画，一段 60fps，一段 50fps
- 大多数人分辨不出差异

实验：两个页面，一个 LCP 2.0s，一个 LCP 2.3s
- 用户感知不到这 300ms 的差异

但：一个 LCP 2.0s，一个 LCP 4.5s
- 用户能明显感觉到后者更慢

启示：优化要集中在用户能感知到的差异上。
把 LCP 从 2.0s 优化到 1.8s 的价值，远小于从 8s 优化到 3s。
```

### 原因二：瓶颈会转移

```
场景：你发现首页 JS bundle 有 800KB，花了两天做了代码分割，
      bundle 降到 200KB。

但你没注意到：首页的 LCP 元素是一张 2MB 的 Hero 图片，
             它的加载时间远超 JS 的解析时间。

你的优化是正确的（JS 确实太大了），但不是当前的瓶颈。
```

### 原因三：优化有代价

```
每个优化都有成本：

代码分割：
  收益：减少首屏 JS 体积
  代价：增加请求数、增加代码复杂度、可能有瀑布式加载

SSR：
  收益：改善 FCP/LCP
  代价：增加服务器成本、增加部署复杂度、需要处理 hydration

图片懒加载：
  收景：减少首屏资源体积
  代价：非首屏图片可能加载延迟、CLS 风险

如果凭感觉优化，可能会引入不必要的复杂度，
而真正的瓶颈只需要一行配置就能解决。
```

## 性能指标回顾

在后续课程中，我们会反复使用这些指标。先建立整体认知。

### Core Web Vitals

```
┌─────────────────────────────────────────────────┐
│              Core Web Vitals                      │
├──────────┬──────────┬──────────┬─────────────────┤
│  指标     │  衡量什么  │  Good    │  Poor           │
├──────────┼──────────┼──────────┼─────────────────┤
│  LCP     │  加载速度  │  ≤2.5s   │  >4s            │
│  INP     │  交互响应  │  ≤200ms  │  >500ms         │
│  CLS     │  视觉稳定  │  ≤0.1    │  >0.25          │
└──────────┴──────────┴──────────┴─────────────────┘
```

### 其他重要指标

```
TTFB（Time to First Byte）：
  衡量服务器响应速度
  Good: ≤800ms
  影响因素：服务器性能、CDN、数据库查询、网络距离

FCP（First Contentful Paint）：
  衡量首次内容出现时间
  Good: ≤1.8s
  影响因素：渲染阻塞资源、服务器响应时间

TBT（Total Blocking Time）：
  衡量主线程被长任务阻塞的总时间
  Good: ≤200ms
  影响因素：JS 执行时间、主线程任务调度
```

### 指标之间的关系

```
时间线：
0ms ──── TTFB ──── FCP ──── LCP ──── TTI
 │        │         │        │        │
 │     服务器响应  首次内容  主要内容  可交互
 │
 用户点击/导航

关键关系：
- TTFB 是所有后续指标的起点
- FCP 反映"页面开始有内容"
- LCP 反映"页面主要内容加载完成"
- INP 反映"页面是否流畅可交互"
- CLS 反映"页面是否稳定不跳动"

优化顺序通常是：
1. 先优化 TTFB（如果瓶颈在后端）
2. 再优化 LCP（首屏主要内容）
3. 然后优化 INP（交互响应）
4. 最后关注 CLS（视觉稳定）
```

## 性能优化的层次

```
┌─────────────────────────────────────────┐
│            用户体验层                      │
│   用户感知到的"快"或"慢"                   │
├─────────────────────────────────────────┤
│            指标层                         │
│   LCP / INP / CLS / TTFB / FCP          │
├─────────────────────────────────────────┤
│            优化策略层                      │
│   网络优化 / 渲染优化 / 资源优化 / 代码优化  │
├─────────────────────────────────────────┤
│            工具层                         │
│   Lighthouse / DevTools / Web Vitals     │
└─────────────────────────────────────────┘

每一层都服务于上一层：
- 工具帮助你发现问题
- 优化策略解决问题
- 指标衡量效果
- 用户体验是最终目标
```

## 一个完整的优化闭环示例

```
场景：电商首页 LCP = 4.8s（Poor）

第一步：测量
  - Lighthouse Performance: 55
  - LCP: 4.8s（LCP 元素是首屏 Banner 图，1.2MB JPEG）
  - TTFB: 300ms（正常）
  - FCP: 1.5s（正常）
  - JS Bundle: 450KB（偏大但不是主要瓶颈）

第二步：分析
  - FCP 到 LCP 之间有 3.3s 的间隔
  - Banner 图在 HTML 中是 <img src="banner.jpg">
  - 图片没有 preload，浏览器在解析到 img 标签后才开始下载
  - 图片是 JPEG 格式，1.2MB

  结论：LCP 瓶颈是 Banner 图的加载时间

第三步：优化（按优先级排序）
  1. 给 Banner 图加 preload → 让浏览器提前开始下载
  2. 图片转 WebP → 体积减少 40%
  3. 提供响应式图片 → 移动端加载小图

  代码改动：
```

```html
<!-- 优化前 -->
<img src="banner.jpg" alt="Banner">

<!-- 优化后 -->
<!-- 在 <head> 中添加 preload -->
<link rel="preload" as="image" href="/images/banner.webp" type="image/webp">

<!-- 响应式图片 -->
<picture>
  <source srcset="/images/banner-mobile.webp" media="(max-width: 768px)" type="image/webp">
  <source srcset="/images/banner.webp" type="image/webp">
  <img src="/images/banner.jpg" alt="Banner" width="1200" height="400">
</picture>
```

```
第四步：验证
  - Lighthouse Performance: 55 → 82
  - LCP: 4.8s → 1.9s
  - 改善幅度：60%
  - 代码改动量：5 行 HTML
  - 副作用：无

这个案例说明：正确的优化不一定是复杂的。
找到真正的瓶颈，用最简单的方案解决它。
```

## 常见的性能优化误区

### 误区一：追求 Lighthouse 100 分

```
Lighthouse 100 分不等于用户体验好。

原因：
1. Lighthouse 是实验室环境，不等于真实用户环境
2. 某些优化对分数影响大但对用户感知影响小
3. 过度优化可能引入不必要的复杂度

正确态度：
  Lighthouse 的价值在于它给出的优化建议，而不是那个数字。
  85 分和 95 分的差距，用户可能完全感知不到。
  把精力放在用户能感知到的差异上。
```

### 误区二：只关注首屏加载

```
首屏加载只是性能的一部分。

用户在页面上的时间分配：
  首屏加载：2-5 秒
  页面交互：几分钟到几十分钟

如果页面加载很快但交互卡顿，用户体验同样差。

完整的性能关注点：
  1. 首屏加载（FCP、LCP）
  2. 交互响应（INP）
  3. 视觉稳定（CLS）
  4. 运行时性能（帧率、内存）
  5. 后台性能（不影响用户操作的计算）
```

### 误区三：优化是后期做的事

```
"先实现功能，后面再优化"——这句话在很多项目里意味着"永远不会优化"。

更好的方式：
  1. 项目初期就设定性能预算
  2. CI 中集成 Lighthouse 检查
  3. 代码审查时关注性能影响
  4. 新功能上线前测量性能指标

预防问题比修复问题成本低得多。
一个新引入的 500KB 依赖，在 PR 阶段发现并拒绝，
比上线三个月后再来优化要容易得多。
```

### 误区四：所有用户都一样

```
同一个页面，不同用户的体验可能天差地别。

用户 A：iPhone 15 Pro + 5G + 上海
  → 页面 1 秒加载完成，非常流畅

用户 B：Redmi Note 10 + 3G + 西部县城
  → 页面 8 秒加载，交互卡顿

只在开发者的 MacBook Pro 上测试，会严重低估真实用户的体验问题。

建议：
  1. 用 Chrome DevTools 模拟低端设备和慢网络
  2. 采集 RUM 数据，关注 P75/P95 而不是平均值
  3. 按设备类型和网络条件分析性能数据
```

### 误区五：所有优化都值得做

```
优化有边际收益。

把 LCP 从 8s 优化到 3s：用户感知巨大改善，跳出率下降 30%
把 LCP 从 3s 优化到 2.5s：用户感知改善很小，跳出率下降 2%
把 LCP 从 2.5s 优化到 2.0s：用户几乎感知不到，跳出率无显著变化

但第三步的优化成本可能和第一步一样高。

正确做法：
  1. 先解决最大的瓶颈
  2. 指标达到 Good 标准后，转向其他方向
  3. 不要为了 0.1s 的改善引入大量复杂度
```

## Chrome DevTools 性能分析快速入门

```
Network 面板：
  - 查看请求瀑布图（哪些请求串行、哪些并行）
  - 查看每个请求的耗时分解（DNS、TCP、TTFB、下载）
  - 模拟慢网络（Fast 3G、Slow 4G）
  - 模拟离线状态
  - 查看资源体积和压缩情况

Performance 面板：
  - 录制页面加载和交互过程
  - 查看主线程活动（哪些任务耗时最长）
  - 查看帧率（FPS）
  - 查看内存使用趋势
  - 识别长任务（> 50ms 的任务）

Coverage 面板：
  - 查看 JS/CSS 的代码使用率
  - 找到未使用的代码（红色部分）
  - 指导代码分割和 Tree Shaking

Lighthouse 面板：
  - 一键生成性能报告
  - 提供具体的优化建议
  - 支持移动端和桌面端测试
```

```javascript
// Performance API：代码内嵌的性能测量
// 测量一段代码的执行时间
performance.mark('start-compute');
const result = heavyComputation();
performance.mark('end-compute');

performance.measure('compute-duration', 'start-compute', 'end-compute');

const measure = performance.getEntriesByName('compute-duration')[0];
console.log(`计算耗时: ${measure.duration.toFixed(2)}ms`);

// 测量页面加载各阶段时间
const timing = performance.timing;
const metrics = {
  DNS: timing.domainLookupEnd - timing.domainLookupStart,
  TCP: timing.connectEnd - timing.connectStart,
  TTFB: timing.responseStart - timing.requestStart,
  DOMContentLoaded: timing.domContentLoadedEventEnd - timing.navigationStart,
  Load: timing.loadEventEnd - timing.navigationStart,
};
console.table(metrics);
```

## 本课小结

性能优化不是一门"技巧集合"，而是一种工程纪律：

1. **先测量**：用工具量化问题，不要猜
2. **再分析**：找到真正的瓶颈，不是最容易优化的点
3. **然后优化**：一次一个变量，选择成本最低的方案
4. **最后验证**：用相同条件对比，确认效果

在后续的课程中，我们会深入每个具体的优化领域。但无论学什么技巧，都不要忘记这个闭环。

这些领域不是孤立的。一个真实项目的性能优化通常需要同时关注多个领域。但学习时建议按顺序来，因为后面的课程会引用前面的概念。

## 练习

### 练习一：分析一个性能问题

以下是一个 Lighthouse 报告的关键数据：

```
Performance Score: 45
FCP: 2.1s
LCP: 6.8s
TBT: 890ms
CLS: 0.32
TTFB: 180ms

资源统计：
- JS Bundle: 780KB (3 个文件)
- CSS: 120KB (2 个文件)
- 图片: 2.5MB (12 张，其中首屏 3 张)
- 字体: 350KB (4 个字体文件，无 preload)
- 第三方脚本: 200KB (分析、广告、客服)

LCP 元素: 一张 800KB 的产品展示图
CLS 最大贡献者: 一个动态加载的广告位
TBT 主要来源: 一个 400KB 的 JS 文件在首屏执行
```

请分析：

## 参考答案

### 练习一

**瓶颈分析（按影响程度排序）：**

```
1. CLS = 0.32（Poor）
   影响：用户正在阅读或点击时内容跳动，可能导致误操作
   原因：广告位动态加载没有预留空间
   这是最紧迫的问题，因为它直接影响可用性

2. LCP = 6.8s（Poor）
   影响：用户等待近 7 秒才能看到主要内容
   原因：800KB 产品图没有预加载，可能还是 JPEG 格式
   这是第二紧迫的问题，直接影响用户留存

3. TBT = 890ms（Poor）
   影响：页面加载期间交互无响应约 1 秒
   原因：400KB JS 在首屏同步执行
   这是第三紧迫的问题，影响首次交互体验

4. 字体 350KB 无预加载
   影响：可能导致 FOIT（文字不可见）或 FOUT（布局偏移）
   这也是一个问题，但优先级低于前三项
```

**如果只能做 3 个优化：**

```
优化一：修复 CLS（广告位预留空间）
  方案：给广告位容器设置固定高度
  代码：<div class="ad-slot" style="min-height: 250px">
  预期效果：CLS 从 0.32 降到 < 0.1
  代价：几乎为零
  理由：这是最容易修复、影响最直接的问题

优化二：优化 LCP（图片预加载 + 格式优化）
  方案：
  1. <link rel="preload"> 预加载产品图
  2. 转 WebP 格式（800KB → ~400KB）
  3. 提供响应式图片
  预期效果：LCP 从 6.8s 降到 ~3s
  代价：需要图片处理流程支持 WebP
  理由：LCP 是 Core Web Vitals 中权重最大的指标

优化三：优化 TBT（JS 代码分割 + 延迟执行）
  方案：
  1. 将 400KB JS 拆分，非首屏功能用 dynamic import
  2. 首屏必要的代码用 requestIdleCallback 延迟执行
  预期效果：TBT 从 890ms 降到 ~300ms
  代价：增加代码分割的复杂度
  理由：TBT 直接影响 INP，影响用户交互体验
```

### 练习二

```
测量指标：
1. Core Web Vitals（LCP、INP、CLS）—— SEO 相关 + 用户体验核心
2. TTFB —— 判断后端是否有瓶颈
3. FCP —— 判断首屏渲染是否有阻塞
4. JS Bundle 体积 —— 影响解析和执行时间
5. 请求数量和总大小 —— 影响加载时间

测量工具：
- Lighthouse：综合评分和优化建议
- Chrome DevTools Network：请求瀑布图
- Chrome DevTools Performance：运行时分析
- web-vitals 库：采集 RUM 数据

测量环境：
1. 实验室测试：
   - Chrome DevTools 限速模拟 3G/4G
   - CPU 4x/6x 降速模拟低端设备
   - 每个条件测试 3 次取中位数
2. 真实用户数据：
   - web-vitals 采集 P75 数据
   - 按设备类型（mobile/desktop）和网络条件分组

性能基准线：
- LCP: ≤ 2.5s（Good 标准）
- INP: ≤ 200ms（Good 标准）
- CLS: ≤ 0.1（Good 标准）
- JS Bundle: ≤ 300KB (gzip)
- 首屏请求数: ≤ 20
```
