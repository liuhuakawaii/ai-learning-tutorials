# stage6：前端性能优化

> 从"感觉页面有点慢"到"用数据驱动每一个优化决策"，建立系统化的性能优化能力

## 学习目标

完成本阶段后，你将能够：
- 建立"测量→分析→优化→验证"的性能优化心智模型，拒绝凭感觉优化
- 理解浏览器关键渲染路径，掌握重排、重绘、合成层的性能影响
- 精通 HTTP 缓存策略设计，合理使用强缓存与协商缓存
- 掌握 React/Vue 框架级性能优化模式，避免不必要的渲染
- 设计代码分割与懒加载策略，控制首屏资源体积
- 制定图片与媒体优化方案，选择合适的格式和加载策略
- 解决字体加载导致的 FOIT/FOUT 问题
- 理解 SSR/SSG/ISR/ESR 的原理与选型依据
- 建立性能预算体系，配置持续监控
- 使用 Chrome DevTools 和 Lighthouse 对真实项目进行完整性能审计

## 学习建议

1. **先测量再优化**：每节课都强调"没有数据就没有结论"。在动手优化前，先用工具量化问题
2. **理解原理**：不要只记"加个 memo"，要理解为什么组件会重复渲染、memo 的代价是什么
3. **关注用户体验**：性能优化的最终目标是用户体验，不是 Lighthouse 分数
4. **权衡代价**：每个优化都有代价——代码复杂度、维护成本、首屏 vs 次屏。学会做取舍
5. **结合实际**：拿你当前项目跑一遍 Lighthouse，找到最大的瓶颈，用本阶段学到的方法逐个解决

## 阶段项目

对一个真实项目进行完整的性能审计与优化。

### 项目要求

选择一个真实存在的前端项目（可以是你自己的项目，也可以是开源项目），完成以下工作：

**第一步：基线测量**
- 使用 Lighthouse 生成性能报告
- 使用 Chrome DevTools Performance 面板录制加载和运行时性能
- 记录所有 Core Web Vitals 指标
- 生成性能瀑布图

**第二步：问题分析**
- 识别首屏加载瓶颈（资源体积、请求数、渲染阻塞）
- 识别运行时性能问题（长任务、内存泄漏、过度渲染）
- 按影响程度排序问题

**第三步：实施优化**
- 网络层：缓存策略、资源预加载、代码分割
- 渲染层：减少重排重绘、优化组件渲染
- 资源层：图片优化、字体优化、第三方脚本治理
- 每个优化都要有 before/after 数据对比

**第四步：验证与监控**
- 重新运行 Lighthouse，对比优化前后分数
- 配置性能预算，防止回退
- 撰写性能优化报告

### 验收标准

- 提供完整的 Lighthouse before/after 报告
- Lighthouse Performance 分数提升 ≥ 15 分
- LCP 改善 ≥ 30%
- 至少实施 5 项不同类型的优化
- 每项优化都有数据支撑（不是"感觉快了"）
- 提供性能预算配置
- 提供完整的优化报告，包含问题分析、优化方案、效果对比

## 常见问题

### Q: 性能优化应该什么时候做？

A: 不要等到"页面很慢"再优化。理想情况是在项目初期就建立性能预算和监控，在开发过程中持续关注。但现实中大多数项目是在体验明显变差后才开始优化。无论哪种情况，第一步都是测量——先量化问题，再决定要不要优化、优化什么。

### Q: Lighthouse 分数重要吗？

A: 分数是参考，不是目标。Lighthouse 的价值在于它帮你发现问题（具体的优化建议），而不是那个三位数。一个 90 分的网站用户体验可能比 100 分的网站更好。关注用户感知到的性能指标（LCP、INP、CLS），而不是分数本身。

### Q: 优化到什么程度算够？

A: 当优化的边际收益不值得投入的时间和复杂度时。把 LCP 从 8 秒优化到 3 秒是必要的，从 2.5 秒优化到 2.0 秒可能不值得为此引入 SSR。具体标准取决于你的用户群体和业务场景。

### Q: 前端性能优化和后端性能优化有什么关系？

A: 两者都会影响用户体验。TTFB（首字节时间）主要由后端决定，FCP/LCP/INP 主要由前端决定。一个常见的错误是前端花了大量精力优化渲染，但瓶颈其实在后端接口慢。性能优化要端到端看，先确定瓶颈在哪一端。
