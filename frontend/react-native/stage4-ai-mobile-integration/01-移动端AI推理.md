# 移动端 AI 推理

## 场景引入

你的团队训练了一个图像分类模型，准确率达到 95%，老板要求把它集成到公司的 React Native App 里。你在服务器上跑得好好的，一放到手机上就出问题：模型加载要 8 秒，推理一次要 3 秒，手机烫得能煎鸡蛋，电量掉得飞快。

这不是模型的问题，而是移动端 AI 推理有完全不同的约束条件。服务端可以堆 GPU，移动端只有巴掌大的芯片和 4000mAh 的电池。本节课带你理解移动端推理的核心挑战，并学会用 TensorFlow Lite 和 Expo Modules 将 AI 模型部署到手机上。

## 学习目标

- 理解移动端 AI 推理的三大约束：算力、内存、功耗
- 了解主流移动端推理框架（Core ML、NNAPI、ONNX Runtime、TFLite）的定位与差异
- 掌握 TensorFlow Lite 模型的转换与优化流程
- 学会使用 Expo Modules 集成 on-device 模型推理

## 移动端 AI 的三大挑战

### 算力限制

旗舰手机的 SoC（如骁龙 8 Gen3、A17 Pro）算力大约是桌面 GPU 的 1/10 到 1/50。更关键的是，移动端 CPU 需要同时处理 UI 渲染、网络请求、后台服务等多个任务，能分配给 AI 推理的算力非常有限。

```typescript
// 在移动端，推理时间是核心指标
const startTime = performance.now();
const result = await model.predict(inputTensor);
const inferenceTime = performance.now() - startTime;

// 移动端目标：单次推理 < 100ms 才能保证流畅体验
if (inferenceTime > 100) {
  console.warn(`推理耗时 ${inferenceTime}ms，考虑模型量化或降级`);
}
```

### 内存限制

移动端 App 的内存预算通常在 100-300MB，一个浮点模型就可能占用几十到上百 MB。加载模型时如果内存峰值过高，系统会直接杀掉进程。

```typescript
// 移动端模型大小与内存估算
interface ModelMemoryEstimate {
  modelSizeMB: number;        // 模型文件大小
  activationMemoryMB: number; // 推理时激活值内存
  totalPeakMB: number;        // 峰值总内存

  // 一般来说：峰值内存 ≈ 模型大小 × 1.5 ~ 2
}

function estimateMemory(modelSizeMB: number): ModelMemoryEstimate {
  const activationMemoryMB = modelSizeMB * 0.5;
  return {
    modelSizeMB,
    activationMemoryMB,
    totalPeakMB: modelSizeMB + activationMemoryMB,
  };
}

// 典型场景
estimateMemory(50);  // { modelSizeMB: 50, activationMemoryMB: 25, totalPeakMB: 75 }
estimateMemory(200); // { modelSizeMB: 200, activationMemoryMB: 100, totalPeakMB: 300 } — 移动端危险区间
```

### 功耗限制

持续的 AI 推理会导致 CPU/GPU 高负载运行，直接后果是发热和电量消耗。用户不会为了一个 AI 功能而牺牲手机续航。

```typescript
// 推理频率控制策略
class InferenceThrottler {
  private lastInferenceTime = 0;
  private minIntervalMs: number;

  constructor(minIntervalMs: number = 500) {
    this.minIntervalMs = minIntervalMs;
  }

  shouldRun(): boolean {
    const now = Date.now();
    if (now - this.lastInferenceTime < this.minIntervalMs) {
      return false; // 节流：避免过于频繁的推理
    }
    this.lastInferenceTime = now;
    return true;
  }
}
```

## 主流移动端推理框架对比

| 框架 | 平台 | 开发商 | 特点 |
|------|------|--------|------|
| Core ML | iOS/macOS | Apple | 深度集成 Apple 硬件，支持 Neural Engine 加速 |
| NNAPI | Android | Google | Android 标准推理 API，厂商可自定义 HAL 层加速 |
| TensorFlow Lite | 跨平台 | Google | 生态成熟，模型压缩工具链完善 |
| ONNX Runtime | 跨平台 | Microsoft | 支持多种硬件后端，模型格式通用性强 |
| MNN | 跨平台 | 阿里巴巴 | 国内使用广泛，对端侧场景优化深入 |

选择建议：React Native 项目优先考虑 TFLite（生态最成熟）或 ONNX Runtime（格式通用），通过 Expo Modules 桥接原生能力。

## TensorFlow Lite 模型转换与优化

### 从 PyTorch/TensorFlow 到 TFLite

模型从训练框架到移动端需要经过两步转换：

```python
# PyTorch → ONNX → TFLite 的典型流程（在 Python 环境执行）

# 1. PyTorch 导出为 ONNX
import torch
dummy_input = torch.randn(1, 3, 224, 224)
torch.onnx.export(model, dummy_input, "model.onnx", opset_version=13)

# 2. ONNX 转换为 TFLite（需要 onnx2tf 工具）
# pip install onnx2tf
import onnx
from onnx2tf import convert
convert(
    input_onnx_file_path="model.onnx",
    output_folder_path="./tflite_output",
)

# 3. 量化压缩（INT8 量化可将模型缩小 4 倍）
import tensorflow as tf
converter = tf.lite.TFLiteConverter.from_saved_model("./tflite_output")
converter.optimizations = [tf.lite.Optimize.DEFAULT]
converter.target_spec.supported_types = [tf.int8]
tflite_model = converter.convert()

with open("model_quantized.tflite", "wb") as f:
    f.write(tflite_model)
```

### TypeScript 封装层

```typescript
// src/services/TfliteService.ts
import { requireNativeModule } from 'expo-modules-core';

interface TfliteNativeModule {
  loadModel(modelName: string): Promise<boolean>;
  predict(inputData: number[], inputShape: number[]): Promise<number[]>;
}

const nativeModule = requireNativeModule<TfliteNativeModule>('TfliteInference');

export class TfliteService {
  private loaded = false;

  async loadModel(modelName: string): Promise<void> {
    this.loaded = await nativeModule.loadModel(modelName);
  }

  async predict(inputData: Float32Array, shape: number[]): Promise<Float32Array> {
    if (!this.loaded) {
      throw new Error('模型未加载，请先调用 loadModel');
    }
    const result = await nativeModule.predict(Array.from(inputData), shape);
    return new Float32Array(result);
  }

  // 图像分类的便捷方法
  async classifyImage(imagePixels: Float32Array): Promise<{ label: string; confidence: number }[]> {
    const output = await this.predict(imagePixels, [1, 224, 224, 3]);
    return this.decodeClassifications(output);
  }

  private decodeClassifications(output: Float32Array): { label: string; confidence: number }[] {
    const labels = ['猫', '狗', '鸟', '鱼']; // 实际应从配置加载
    return Array.from(output)
      .map((confidence, index) => ({ label: labels[index] || '未知', confidence }))
      .sort((a, b) => b.confidence - a.confidence)
      .slice(0, 3);
  }
}
```

## 常见误区

1. **直接把服务端模型搬到移动端**：服务端模型通常是 FP32 精度、大参数量，直接使用会导致内存溢出和极慢的推理速度。必须经过量化和裁剪。

2. **只看模型文件大小**：模型文件小不代表推理快。有些压缩技术（如剪枝）减小了文件体积但不会加速推理，因为硬件需要的是稠密计算。

3. **忽略模型预处理开销**：图像模型的 resize、normalize 等预处理在移动端可能占总耗时的 30-50%，不能只优化推理本身。

4. **在 JS 线程做推理**：推理必须在原生层执行，在 JS 线程做会导致界面卡死。通过 Expo Modules 桥接是正确做法。

5. **一次性加载所有模型**：移动端内存有限，应该按需加载模型，用完及时释放。

## 工程建议

- **模型大小目标**：移动端模型控制在 10-30MB 以内，超过 50MB 会影响下载转化率和启动速度
- **量化优先级**：先试 FP16 → 再试 INT8 → 最后考虑知识蒸馏缩小模型
- **推理频率控制**：摄像头实时场景限制在 10-15 FPS，语音场景 100ms 间隔足够
- **异步加载**：App 启动时预加载模型到内存，但不要阻塞首屏渲染
- **性能监控**：记录每次推理的耗时和内存占用，线上收集 P95/P99 数据
- **降级策略**：设备算力不足时，回退到服务端推理或使用更小的模型

## 小结

移动端 AI 推理的核心是在算力、内存、功耗三大约束下找到平衡点。TensorFlow Lite 是目前最成熟的移动端推理方案，配合 Expo Modules 可以优雅地集成到 React Native 应用中。关键是：转换模型格式 → 量化压缩 → 原生层集成 → 性能监控，形成完整的工程闭环。

## 参考答案

### 练习一

**思路**：当前模型 120MB，推理时峰值内存约 180-240MB，超出 150MB 预算。需要通过量化将模型缩小到安全区间。

**答案**：

第一步：FP16 量化，模型缩小到约 60MB，峰值内存约 90MB，精度损失极小（< 0.5%），在目标设备上可运行。

第二步：如果 60MB 仍然偏大，进行 INT8 量化，模型进一步缩小到约 30MB，峰值内存约 45MB，精度损失 1-3%。

第三步：如果精度损失不可接受，考虑知识蒸馏训练一个更小的学生模型（如 MobileNetV3-Small），再做 FP16 量化，兼顾精度和大小。

**要点**：
- 峰值内存 ≈ 模型大小 × 1.5，不能只看模型文件大小
- FP16 是性价比最高的第一步优化
- INT8 量化需要校准数据集，精度损失与数据分布相关

### 练习二

**思路**：结合时间戳节流、输入哈希缓存和设备状态感知三个维度。

**答案**：

```typescript
class SmartInferenceThrottler {
  private lastInferenceTime = 0;
  private resultCache = new Map<string, { result: number[]; timestamp: number }>();
  private baseIntervalMs: number;
  private cacheMaxAge: number;

  constructor(baseIntervalMs = 300, cacheMaxAge = 5000) {
    this.baseIntervalMs = baseIntervalMs;
    this.cacheMaxAge = cacheMaxAge;
  }

  async runInference(
    input: Float32Array,
    inferFn: (input: Float32Array) => Promise<number[]>
  ): Promise<number[] | null> {
    const cacheKey = this.computeHash(input);
    const cached = this.resultCache.get(cacheKey);
    if (cached && Date.now() - cached.timestamp < this.cacheMaxAge) {
      return cached.result;
    }

    const now = Date.now();
    const interval = this.getAdaptiveInterval();
    if (now - this.lastInferenceTime < interval) {
      return cached?.result ?? null;
    }

    this.lastInferenceTime = now;
    const result = await inferFn(input);
    this.resultCache.set(cacheKey, { result, timestamp: now });
    this.pruneCache();
    return result;
  }

  private getAdaptiveInterval(): number {
    // 实际项目中可结合设备温度、电量等信息动态调整
    return this.baseIntervalMs;
  }

  private computeHash(input: Float32Array): string {
    let hash = 0;
    for (let i = 0; i < Math.min(input.length, 64); i++) {
      hash = ((hash << 5) - hash + input[i]) | 0;
    }
    return hash.toString(36);
  }

  private pruneCache(): void {
    const now = Date.now();
    for (const [key, value] of this.resultCache) {
      if (now - value.timestamp > this.cacheMaxAge) {
        this.resultCache.delete(key);
      }
    }
  }
}
```

**要点**：
- 输入哈希采样前 64 个元素即可，完整哈希太慢
- 缓存过期时间应根据场景调整：实时检测 1-3 秒，低频场景 10-30 秒
- 设备负载自适应需要原生层提供 CPU/温度信息
