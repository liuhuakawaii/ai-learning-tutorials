# 空间计算概览：选错平台，后面全白搭

## 当前项目状态

你准备进入空间计算开发。第一个要做的决定不是学什么框架，而是**在哪个平台上做**。这个决定会直接影响后面每一课的技术选型、交互设计和性能预算。

选错了，后面所有代码都要重写。

## 一个真实场景

团队要做一个工业培训应用：工人在真实设备旁边看到虚拟操作指引。需求看起来简单，但技术选型阶段就踩了坑：

- 方案 A：用 HoloLens 2 + Unity，画质好、手势精准，但单台 3500 美元，500 个工人就是 175 万
- 方案 B：用 Quest 3 + WebXR，单台 500 美元，但需要确认 WebXR 的手势追踪够不够用
- 方案 C：用手机 AR，零硬件成本，但工人要一手拿手机一手操作设备

三个方案没有绝对的对错，但选错了代价很大。

## AR / VR / MR 的实际区别

这四个概念在行业文档里经常混用，但在工程上它们决定了你的渲染策略和交互模型：

```
AR（增强现实）
  摄像头画面 + 虚拟叠加层
  用户仍看到真实世界
  典型：手机 AR 尺子、Pokémon GO

VR（虚拟现实）
  完全替换视觉环境
  用户看不到真实世界
  典型：Beat Saber、Half-Life: Alyx

MR（混合现实）
  虚拟物体与真实环境深度融合
  虚拟物体能被真实物体遮挡
  典型：Apple Vision Pro、Quest 3 透视模式

XR（总称）
  涵盖以上所有，WebXR API 就是用这个命名
```

从工程角度看，MR 的难度最高——你需要理解真实环境的几何结构才能做遮挡。VR 最"简单"——环境完全由你控制。

## 四个主流平台的工程约束

### Meta Quest 3

消费级 MR 一体机，当前性价比最高。

```typescript
// Quest 的 WebXR 能力检测
async function checkQuestCapabilities() {
  if (!navigator.xr) return { supported: false };

  const vr = await navigator.xr.isSessionSupported('immersive-vr');
  const ar = await navigator.xr.isSessionSupported('immersive-ar');

  return {
    supported: vr || ar,
    vr,
    ar, // Quest 3 支持透视模式（AR）
    handTracking: true, // 内置手势追踪
    constraints: {
      gpu: '骁龙 XR2 Gen 2，约为手机旗舰 1.5 倍',
      resolution: '单眼 2064×2208',
      fps: 90, // 必须稳定 90fps
      memory: '8GB，应用可用 4-5GB'
    }
  };
}
```

### Apple Vision Pro

高端空间计算平台，眼动 + 手势为主要交互方式。

开发约束：M2 + R1 双芯片，单眼 3664×3200，无手柄——所有交互靠眼睛看 + 手捏。这意味着你的 UI 设计必须考虑"视线精度"问题（用户的眼睛不像手指那样精确）。

### HoloLens 2

企业级 MR，工业/医疗领域有成熟应用，但视野角只有 52°（比 Quest 3 窄），消费市场几乎不存在。

### PSVR2

主机 VR 外设，画质好但有线连接，仅支持 PS5 平台，不适合 Web 开发。

## 选平台的决策框架

```
你的目标平台是什么？
│
├─ 跨平台（Quest + Vision Pro + PC）→ WebXR + Three.js
│   优势：一套代码多端运行，迭代快
│   代价：性能上限低于原生
│
├─ Quest 独占 → Unity + XR Interaction Toolkit
│   优势：性能好，SDK 成熟
│   代价：需要学 C# + Unity 编辑器
│
├─ 高画质游戏 → Unreal + OpenXR
│   优势：渲染能力最强
│   代价：学习曲线陡，包体大
│
└─ 手机 AR → WebXR 或 ARKit/ARCore
    优势：零硬件成本
    代价：交互受限（手持设备）
```

## WebXR 的跨平台优势

如果你是前端开发者，WebXR + Three.js 是最自然的起点：

```typescript
class XRApp {
  private session: XRSession | null = null;

  async start() {
    if (!navigator.xr) throw new Error('浏览器不支持 WebXR');

    // 自动选择最佳模式
    const mode = await navigator.xr.isSessionSupported('immersive-ar')
      ? 'immersive-ar'
      : 'immersive-vr';

    this.session = await navigator.xr.requestSession(mode, {
      requiredFeatures: ['local-floor'],
      optionalFeatures: ['hand-tracking', 'hit-test']
    });

    // 同一份代码在 Quest、Vision Pro、PC 浏览器上都能运行
    console.log(`已启动 ${mode} 会话`);
  }
}
```

WebXR 的迭代速度比原生快 5-10 倍（热重载 vs 编译），适合验证交互设计。等产品方向确定后，再考虑是否需要原生重写。

## 四个你大概率会踩的坑

**坑一：AR 比 VR 简单**

恰恰相反。AR 需要处理真实环境的不确定性（光照变化、遮挡、追踪丢失），VR 的环境完全由你控制，出问题的概率低得多。

**坑二：WebXR 性能太差**

WebGPU 正在缩小差距。对于非游戏类应用（培训、展示、协作），WebXR 的性能完全够用。关键是做好资源管理和渲染优化。

**坑三：先学 Unity 再说**

如果你是前端开发者，Three.js 的学习曲线比 Unity 平缓得多。选工具应该基于团队技能，不是"别人都用 Unity"。

**坑四：XR 开发就是 3D 建模**

XR 开发的核心是交互设计和性能优化，不是建模。模型可以买或用 AI 生成，但交互逻辑和 90fps 的性能约束必须自己搞定。

### 练习二：能力检测代码

写一个 TypeScript 函数 `detectXRSupport()`，检测当前浏览器是否支持 `immersive-vr` 和 `immersive-ar`，返回一个结构化的支持信息对象。要求处理 `navigator.xr` 不存在的情况。

## 参考答案

### 练习一

推荐 WebXR + Three.js。理由：团队熟悉 TypeScript，Three.js 是 TS 优先的库，学习成本最低。Web 开发热重载比 Unity 编译快 5-10 倍，2 个月 MVP 时间紧张，开发速度是关键。WebXR 在 Quest、PC 浏览器上都能运行，无需为不同平台编译。不选 Unity 的原因：学 C# + Unity 编辑器需要至少 1 个月，留给实际开发的时间不够。不选 Unreal 的原因：C++ 学习曲线更陡，VR 模板偏游戏向。

### 练习二

```typescript
interface XRSupportInfo {
  supported: boolean;
  immersiveVR: boolean;
  immersiveAR: boolean;
  error?: string;
}

async function detectXRSupport(): Promise<XRSupportInfo> {
  if (!navigator.xr) {
    return { supported: false, immersiveVR: false, immersiveAR: false,
             error: '当前浏览器不支持 WebXR' };
  }

  try {
    const [vr, ar] = await Promise.all([
      navigator.xr.isSessionSupported('immersive-vr'),
      navigator.xr.isSessionSupported('immersive-ar')
    ]);
    return { supported: vr || ar, immersiveVR: vr, immersiveAR: ar };
  } catch (e) {
    return { supported: false, immersiveVR: false, immersiveAR: false,
             error: `检测失败: ${(e as Error).message}` };
  }
}
```
