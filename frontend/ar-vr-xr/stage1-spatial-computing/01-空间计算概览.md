# 01 - 空间计算概览

## 场景引入

你戴上 Apple Vision Pro，看到一个虚拟的 Safari 浏览器悬浮在客厅的墙壁上，用手轻轻一拨，页面自然滚动。这不是科幻电影，而是 2024 年已经量产的空间计算体验。

空间计算（Spatial Computing）正在从"极客玩具"变成"下一代计算平台"。作为开发者，你需要理解：这个领域有哪些技术路线？主流设备的能力和限制是什么？市场正在往哪个方向走？

本课不写代码，而是帮你建立**行业认知地图**——后续所有技术决策都建立在这个基础上。

## 学习目标

- 清晰区分 AR、VR、MR、XR 的技术边界
- 了解主流 XR 设备的硬件能力与开发约束
- 掌握空间计算市场的关键趋势
- 能为项目选择合适的技术路线

## AR / VR / MR / XR：到底有什么区别？

这四个概念经常被混用，但它们代表不同的技术路线，直接影响你的开发策略。

### AR（增强现实）

AR 在真实世界上叠加数字信息。用户仍然看到现实环境，虚拟内容作为"增强层"存在。

典型例子：手机上的 AR 尺子、Google Maps 的 AR 导航、Pokémon GO。

技术特点：
- 依赖摄像头捕捉真实环境
- 虚拟内容需要与真实世界**对齐**（需要 SLAM 或标记点追踪）
- 不遮挡现实视野，信息密度有限

### VR（虚拟现实）

VR 完全替代用户的视觉环境，将人沉浸在一个纯虚拟世界中。

典型例子：Beat Saber、Half-Life: Alyx、VRChat。

技术特点：
- 不依赖摄像头（或仅用于追踪）
- 完全控制渲染环境，性能预算更可控
- 沉浸感强，但存在眩晕风险

### MR（混合现实）

MR 是 AR 和 VR 的融合。虚拟物体与真实环境深度融合，能被真实物体遮挡，也能遮挡真实物体。

典型例子：Apple Vision Pro 的空间计算、HoloLens 的工业应用。

技术特点：
- 需要深度传感器理解真实环境的几何结构
- 虚实遮挡关系是核心难点
- 计算量最大，对硬件要求最高

### XR（扩展现实）

XR 是一个**总称**，涵盖 AR、VR、MR 以及未来可能出现的其他形式。在行业文档和 API 中，XR 通常作为统称使用。

```typescript
// WebXR API 就是用 XR 作为统称
navigator.xr?.isSessionSupported('immersive-vr')
navigator.xr?.isSessionSupported('immersive-ar')
```

## 主流设备生态

### Meta Quest 系列

**定位**：消费级 VR/MR 一体机

Quest 3 是当前性价比最高的 MR 设备，支持全彩透视（passthrough），可以同时运行 VR 和 MR 应用。

开发约束：
- 骁龙 XR2 Gen 2 芯片，GPU 性能约为手机旗舰的 1.5 倍
- 单眼 2064×2208 分辨率，要求稳定 90fps（部分场景 120fps）
- 基于 Android，支持 Unity、Unreal 和 WebXR
- 内存限制 8GB，应用可用约 4-5GB

```typescript
// Meta Quest WebXR 开发：检查设备支持
async function checkQuestSupport(): Promise<boolean> {
  if (!navigator.xr) return false

  // Quest 支持 immersive-vr 和 immersive-ar（透视模式）
  const vrSupported = await navigator.xr.isSessionSupported('immersive-vr')
  const arSupported = await navigator.xr.isSessionSupported('immersive-ar')

  console.log(`VR 支持: ${vrSupported}, AR 支持: ${arSupported}`)
  return vrSupported || arSupported
}
```

### Apple Vision Pro

**定位**：高端空间计算平台

Vision Pro 代表了当前最先进的空间计算体验，但价格和用户规模限制了它的市场影响。

开发约束：
- M2 + R1 双芯片架构，R1 专门处理传感器数据
- 单眼 3664×3200 分辨率，Micro-OLED，刷新率 90Hz
- 眼动追踪 + 手势追踪为主要交互方式（无手柄）
- 基于 visionOS，支持 SwiftUI、RealityKit 和 WebXR
- 应用内存限制约 5-6GB

```swift
// visionOS 的 SwiftUI 空间布局（与传统 2D UI 完全不同）
import SwiftUI
import RealityKit

struct ContentView: View {
    var body: some View {
        // 在 3D 空间中放置一个窗口
        VStack {
            Text("Hello, Spatial Computing!")
                .font(.title)
        }
        .frame(width: 400, height: 300)
        // visionOS 自动处理窗口在空间中的定位
    }
}
```

### Microsoft HoloLens 2

**定位**：企业级 MR 设备

HoloLens 2 在工业、医疗、教育领域有成熟应用，但消费市场几乎不存在。

开发约束：
- 骁龙 850 芯片，性能有限
- 透视式 AR，视野角约 52°（比 Quest 3 窄）
- 手势追踪 + 眼动追踪 + 语音输入
- 基于 Windows，支持 Unity + MRTK（Mixed Reality Toolkit）

### PSVR2

**定位**：主机 VR 外设

PSVR2 依托 PS5 的 GPU 性能，提供高质量 VR 体验，但受限于有线连接和 PS5 生态。

开发约束：
- 单眼 2000×2040 OLED，110° 视野
- 眼动追踪支持（可用于注视点渲染）
- 仅支持 PS5 平台，开发需要 PlayStation 开发者资质

## 市场趋势

### 趋势一：MR 成为主流

纯粹的 VR（完全遮挡现实）正在让位于 MR（虚实融合）。Quest 3 的全彩透视、Vision Pro 的空间计算都指向同一个方向：未来的 XR 设备不会让你与现实隔绝，而是**增强**现实。

对开发者的影响：你的应用需要同时考虑虚拟内容和真实环境的交互，不能只管渲染一个封闭的虚拟世界。

### 趋势二：交互范式从手柄转向手眼追踪

Vision Pro 放弃了手柄，完全依赖眼动+手势。Quest 3 也在强化手部追踪。手柄不会消失（游戏场景仍需要），但手眼追踪正在成为**默认交互方式**。

对开发者的影响：你需要设计不依赖精确手柄输入的交互方案，这比传统 UI 设计复杂得多。

### 趋势三：WebXR 的地位在提升

随着设备种类增多，跨平台需求变强。WebXR 天然跨平台（只要设备有浏览器），加上 WebGPU 带来的性能提升，WebXR 正在从"玩具"变成"可行的生产方案"。

```typescript
// WebXR 的跨平台优势：同一份代码在 Quest、Vision Pro、PC 上都能运行
class XRApplication {
  private session: XRSession | null = null

  async start(): Promise<void> {
    if (!navigator.xr) {
      throw new Error('当前浏览器不支持 WebXR')
    }

    // 尝试 immersive-ar，回退到 immersive-vr
    const mode = await navigator.xr.isSessionSupported('immersive-ar')
      ? 'immersive-ar'
      : 'immersive-vr'

    this.session = await navigator.xr.requestSession(mode, {
      requiredFeatures: ['local-floor'],
      optionalFeatures: ['hand-tracking', 'hit-test']
    })

    console.log(`已启动 ${mode} 会话`)
  }
}
```

### 趋势四：空间计算 + AI

大语言模型和计算机视觉的结合正在为 XR 带来新能力：环境理解（识别房间里的物体）、自然语言交互（用语音控制虚拟物体）、智能内容生成（根据场景自动创建 3D 内容）。

## 常见误区

### 误区一："XR 开发就是 3D 建模"

XR 开发的核心不是建模，而是**交互设计和性能优化**。模型资源可以购买或用 AI 生成，但交互逻辑和性能调优必须自己做。

### 误区二："WebXR 性能太差，不能做正经应用"

WebGPU 的出现大幅缩小了 WebXR 与原生的性能差距。对于非游戏类应用（培训、展示、协作），WebXR 的性能完全够用。关键是做好资源管理和渲染优化。

### 误区三："AR 比 VR 简单"

恰恰相反。AR 需要处理真实环境的不确定性（光照变化、遮挡、追踪丢失），技术难度通常高于 VR。VR 的环境完全由你控制，出问题的概率低得多。

### 误区四："先学 Unity 再考虑其他"

Unity 是成熟的 XR 开发工具，但不是唯一选择。如果你是前端开发者，WebXR + Three.js 的学习曲线更平缓，迁移成本更低。选择工具链应该基于**团队技能和项目需求**，而不是"别人都用 Unity"。

## 工程建议

1. **先明确目标平台再选技术栈**。Quest 独占 vs 跨平台 vs Web-only，技术选择完全不同
2. **从 VR 开始，再做 AR**。VR 的开发和调试环境更可控，适合建立基础
3. **性能预算前置**。XR 的性能硬约束（90fps、延迟）必须从架构设计阶段就考虑，不能事后优化
4. **真机测试必不可少**。模拟器无法还原真实的空间感知和舒适度体验
5. **关注 WebXR 标准演进**。WebXR 的规范还在快速发展，定期查看 [WebXR Device API](https://www.w3.org/TR/webxr/) 的更新

## 小结

本课建立了空间计算的行业认知地图：

- **技术路线**：AR（增强现实）→ VR（虚拟现实）→ MR（混合现实），XR 是统称
- **设备生态**：Quest（消费级 MR）、Vision Pro（高端空间计算）、HoloLens（企业 MR）、PSVR2（主机 VR）
- **关键趋势**：MR 主流化、手眼交互、WebXR 崛起、AI 融合
- **开发策略**：目标平台决定技术栈，性能预算前置，真机测试不可省

## 练习

### 练习一：设备选型分析

你的团队计划开发一个工业培训应用，工人需要在真实设备旁边看到虚拟操作指引。预算有限，目标用户约 500 人，需要支持手势操作。请分析应该选择哪款 XR 设备，并说明理由。

### 练习二：技术路线判断

一个前端团队（5 人，熟悉 React/TypeScript）要开发一个 VR 会议室原型，要求 2 个月内交付 MVP。请推荐技术栈（Unity/Unreal/WebXR 三选一），并说明理由。

---

## 参考答案

### 练习一

**思路**：需要从场景需求（AR/MR）、交互方式（手势）、预算、用户规模四个维度分析。

**答案**：推荐 **Meta Quest 3**。理由：

1. **场景匹配**：工人需要看到真实设备 + 虚拟指引 = MR 场景。Quest 3 支持全彩透视，能同时显示真实环境和虚拟内容
2. **手势支持**：Quest 3 内置手部追踪，无需额外硬件
3. **预算友好**：Quest 3 约 500 美元/台，500 人总计约 25 万美元，远低于 HoloLens 2（3500 美元/台）的 175 万美元
4. **开发生态**：Unity + Quest 有大量工业应用案例和成熟 SDK

不选 HoloLens 2 的原因：价格过高，且微软已减少硬件投入。不选 Vision Pro 的原因：价格（3499 美元/台）远超预算。

**要点**：
- 工业场景优先考虑设备耐用性和企业支持
- 手势交互在工业场景中比手柄更实用（工人可能戴手套）
- 需要考虑设备管理和批量部署方案

### 练习二

**思路**：评估团队技能匹配度、开发效率和交付周期。

**答案**：推荐 **WebXR + Three.js**。理由：

1. **技能匹配**：团队熟悉 TypeScript，Three.js 是 TypeScript 优先的库，学习曲线最平缓
2. **开发效率**：Web 开发热重载（HMR）比 Unity 的编译迭代快 5-10 倍，2 个月 MVP 时间紧张，开发速度是关键
3. **跨平台**：WebXR 在 Quest、PC 浏览器上都能运行，无需为不同平台编译
4. **协作友好**：前端团队不需要学习 C# 和 Unity 编辑器，保持团队效率

不选 Unity 的原因：团队需要学习 C# + Unity 编辑器，2 个月时间不够。不选 Unreal 的原因：C++ 学习曲线更陡，且 VR 模板偏游戏向。

**要点**：
- WebXR 适合展示类、协作类 VR 应用，不适合高画质游戏
- MVP 阶段优先验证交互设计，画质可以后续迭代
- 如果后续需要原生性能，可以用 Unity 重写核心模块

**常见错误写法**：选择 Unreal，理由是"画质最好"。问题在于：画质不是 MVP 阶段的核心目标，且团队技能不匹配会导致项目失败。
