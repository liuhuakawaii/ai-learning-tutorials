# 第4课：Chrome DevTools Performance

> **课程定位**：掌握最核心的性能诊断工具，学会读取性能火焰图
> **前置知识**：了解 Core Web Vitals 和 Lab/Field 数据的区别
> **预计时长**：45 分钟

## 场景引入

用户反馈你的 Web 应用在点击"提交订单"按钮后要等将近 1 秒才有反应。你打开代码看了一圈，看不出哪里有问题——事件处理函数只有几行代码。直到你打开 Chrome DevTools 的 Performance 面板，录制了一次点击操作，才发现真相：点击事件触发时，主线程正被一个 800ms 的第三方分析脚本阻塞，点击事件在队列里排了 600ms 才开始处理。没有 Performance 面板，你永远想不到问题出在第三方脚本上。

---

## 学习目标

完成本课学习后，你将能够：

1. 打开 Performance 面板并录制一次完整的页面加载 trace
2. 读懂火焰图中每个区域的含义（FPS、CPU、Network、Main Thread）
3. 识别长任务（Long Tasks）、LCP 标记、布局偏移
4. 使用 CPU 和网络节流模拟低端设备环境
5. 通过 Performance 面板定位一个具体的性能瓶颈

## 二、录制一次 Trace

### 2.1 录制步骤

```
录制页面加载 trace 的标准流程：

  1. 打开 DevTools → Performance 面板
  2. 点击左上角的刷新按钮（🔄 Reload）
     → 这会录制从页面加载开始到 Load 事件完成的完整过程
  3. 等待录制完成（自动停止）
  4. 分析结果

  或者手动录制：
  1. 点击录制按钮（⚫ 圆点）
  2. 在页面上进行操作（点击、滚动、输入）
  3. 点击停止按钮
  4. 分析交互过程中的性能问题
```

### 2.2 开启节流

```
为了模拟真实用户的低配环境，需要开启节流：

  ┌─────────────────────────────────────────────────────┐
  │  CPU 节流：                                          │
  │  ├── No throttling（不节流）→ 你自己的高性能电脑     │
  │  ├── 4x slowdown → 模拟中端手机                     │
  │  └── 6x slowdown → 模拟低端手机                     │
  │                                                     │
  │  网络节流：                                          │
  │  ├── Online（不节流）→ 你的宽带速度                  │
  │  ├── Fast 3G → 下行 ~1.5Mbps, RTT ~150ms            │
  │  ├── Slow 3G → 下行 ~400Kbps, RTT ~500ms            │
  │  └── Custom → 自定义下行/上行/延迟                   │
  └─────────────────────────────────────────────────────┘

  建议的测试配置：
  - CPU: 4x slowdown
  - 网络: Fast 4G（Chrome DevTools 中选 "Slow 4G"）
  - 这样能暴露大多数真实用户会遇到的问题
```

## 三、读懂火焰图

### 3.1 概览区解读

```
FPS 图表：
  ┌──────────────────────────────────────────┐
  │  ▄   ▄▄   ▄                              │  ← 绿色 = 帧率正常（60fps）
  │  █   ██   █                              │
  │  █   ██   █▄▄                            │
  │  █   ██   ███                            │
  │  ▀▀▀▀▀▀▀▀▀▀▀▀                            │  ← 红色 = 严重掉帧
  └──────────────────────────────────────────┘
  红色区域表示帧率低于 30fps，用户会感到卡顿

CPU 图表：
  ┌──────────────────────────────────────────┐
  │        ▄▄▄▄                              │
  │  ▄▄▄▄▄██████▄▄                           │  ← 颜色越深 = CPU 占用越高
  │  ███████████████                         │
  └──────────────────────────────────────────┘

Network 图表：
  ┌──────────────────────────────────────────┐
  │  ██ ▄▄  ▄▄  ▄  ▄ ▄                      │  ← 每个色条 = 一个资源
  │  ██ ██  ██  █  █ █                       │  ← 色条越长 = 加载越慢
  │                                          │
  │  颜色含义：                               │
  │  蓝色 = HTML                              │
  │  紫色 = CSS                               │
  │  黄色 = JS                                │
  │  绿色 = 图片                              │
  │  灰色 = 其他                              │
  └──────────────────────────────────────────┘
```

### 3.2 主线程火焰图解读

```
火焰图中的每一行代表一个调用栈：

  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  ┌──────────────────────────────────────────┐            │
  │  │  Task（任务）                              │  ← 顶层   │
  │  │  耗时: 85ms ⚠️ Long Task                  │            │
  │  │  ┌────────────────────────────────────┐   │            │
  │  │  │  Evaluate Script（执行脚本）        │   │  ← 调用   │
  │  │  │  ┌──────────────────────────────┐  │   │            │
  │  │  │  │  compile（编译）              │  │   │  ← 调用   │
  │  │  │  └──────────────────────────────┘  │   │            │
  │  │  │  ┌──────────────────────────────┐  │   │            │
  │  │  │  │  execute（执行）              │  │   │  ← 调用   │
  │  │  │  │  ┌────────────────────────┐  │  │   │            │
  │  │  │  │  │  parseHTML（解析HTML）  │  │  │   │            │
  │  │  │  │  └────────────────────────┘  │  │   │            │
  │  │  │  │  ┌────────────────────────┐  │  │   │            │
  │  │  │  │  │  recalcStyle（计算样式）│  │  │   │            │
  │  │  │  │  └────────────────────────┘  │  │   │            │
  │  │  │  └──────────────────────────────┘  │   │            │
  │  │  └────────────────────────────────────┘   │            │
  │  └──────────────────────────────────────────┘            │
  │                                                          │
  │  阅读方法：                                               │
  │  - 从上往下看：顶层是 Task，嵌套的是子调用                 │
  │  - 色块越宽 = 耗时越长                                    │
  │  - 点击色块 → 下方详情面板显示调用栈和耗时                 │
  │  - 红色三角 = Long Task（> 50ms）                         │
  │                                                          │
  └──────────────────────────────────────────────────────────┘
```

### 3.3 颜色含义

```
火焰图中色块的颜色代表不同类型的活动：

  ┌─────────────┬────────────────────────────────────┐
  │  颜色       │  含义                               │
  ├─────────────┼────────────────────────────────────┤
  │  蓝色       │  HTML 解析（Parse HTML）             │

## 四、识别关键标记

### 4.1 LCP 标记

```
在概览区和主线程中，你会看到一些关键标记：

  ┌──────────────────────────────────────────────────────────┐
  │                                                          │
  │  绿色竖线 ─── FCP（First Contentful Paint）              │
  │              第一个内容出现在屏幕上的时间                   │
  │                                                          │
  │  蓝色竖线 ─── LCP（Largest Contentful Paint）            │
  │              最大内容元素出现的时间                         │
  │              点击可查看是哪个 DOM 元素                     │
  │                                                          │
  │  红色竖线 ─── DCL（DOMContentLoaded）                    │
  │              DOM 解析完成                                 │
  │                                                          │
  │  蓝色竖线 ─── Load 事件                                  │
  │              所有资源加载完成                              │
  │                                                          │
  └──────────────────────────────────────────────────────────┘

  时间轴示意：
  ─────────────────────────────────────────────────────→ 时间
  │                    │         │              │
  FCP                  LCP       DCL            Load
  0.8s                 1.5s      1.2s           2.0s
```

### 4.2 长任务标记

```
  主线程中的红色三角标志：

  ┌──────────────────────────────────────────────────────┐
  │                                                      │
  │        ▼ 红色三角                                     │
  │  ┌───────────────────────────────────┐               │
  │  │                                   │               │
  │  │   Long Task（长任务）              │               │
  │  │   耗时: 120ms                     │               │
  │  │   超过 50ms 阈值                  │               │
  │  │   这段时间主线程被阻塞             │               │
  │  │   用户点击等交互需要排队等待        │               │
  │  │                                   │               │
  │  └───────────────────────────────────┘               │
  │                                                      │
  └──────────────────────────────────────────────────────┘

  查看方法：
  1. 在主线程中找到红色三角标记的任务
  2. 点击该任务
  3. 查看下方 Call Stack（调用栈）
  4. 找到耗时最长的函数
  5. 点击源码链接跳转到对应代码
```

### 4.3 布局偏移标记

  │  │ Layout Shift │  ← 紫色/粉色色块                   │
  │  │ 偏移值: 0.15 │                                    │

## 五、实用调试流程

### 5.1 标准诊断流程

```
性能诊断的标准流程：

  1. 开启节流（CPU 4x + Fast 4G）
         │
         ▼
  2. 录制页面加载 trace（点击刷新按钮）
         │
         ▼
  3. 看概览区
     ├── FPS 有红色？→ 有掉帧问题
     ├── CPU 持续高峰？→ 主线程繁忙
     └── Network 有长条？→ 有慢资源
         │
         ▼
  4. 看 LCP 标记
     ├── LCP 时间是多少？
     └── LCP 元素是什么？（点击标记查看）
         │
         ▼
  5. 在主线程中找 Long Tasks
     ├── 有哪些超过 50ms 的任务？
     └── 它们在 LCP 之前还是之后？
         │
         ▼
  6. 点击最长的任务，查看调用栈
     ├── 是哪个函数耗时最长？
     ├── 是自己写的代码还是第三方库？
     └── 能否拆分、延迟或移除？
         │
         ▼
  7. 查看 Network 瀑布图
     ├── 有没有阻塞渲染的资源？
     ├── 资源加载顺序是否合理？
     └── 有没有可以并行加载的资源？
```

### 5.2 一个完整的案例

```
假设 LCP 是 4.5 秒，需要找到原因：

  步骤 1：找到 LCP 元素
  → 点击 LCP 标记 → 发现是一张 hero.jpg

  步骤 2：在 Network 中找到这个资源
  → hero.jpg 从 2.0s 才开始加载，3.8s 才加载完
  → 原因：HTML 中有大量 <script> 阻塞了解析

  步骤 3：查看主线程
  → 发现 1.0s-2.0s 之间有一个 1000ms 的长任务
  → 这是 app.js 的编译和执行

  步骤 4：查看 app.js 内容
  → 发现 app.js 有 500KB，包含很多首屏不需要的代码

  优化方案：
  → 给 script 添加 defer
  → 拆分 app.js，首屏代码单独打包
  → 给 hero.jpg 添加 preload
  → 优化后 LCP 从 4.5s 降到 1.8s
```

```
录制用户交互（而不是页面加载）：

  1. 先加载页面，等页面完全就绪
  2. 点击录制按钮（⚫ 圆点）

## 常见误区

1. **不开节流就录制**：在高性能电脑上录制的 trace 无法暴露真实用户的问题。必须开启 CPU 4x 节流和网络节流，才能模拟低端设备的体验。
2. **只看概览区不深入主线程**：概览区能告诉你"有问题"，但只有深入火焰图的主线程，才能找到具体是哪个函数、哪段代码导致的瓶颈。
3. **忽略交互过程的录制**：很多人只录制页面加载，不录制用户交互。INP 相关的问题只能通过录制交互过程来发现。
4. **把 Long Task 等同于性能问题**：不是所有超过 50ms 的任务都需要优化，关键看它是否在用户交互时阻塞了主线程。首屏加载期间的 Long Task 和交互时的 Long Task 优先级完全不同。

## 工程建议

1. **养成录制 trace 的习惯**：遇到性能问题时，第一反应不是看代码，而是录制一个 trace。数据比直觉更可靠。
2. **导出 trace 文件分享给团队**：Performance 面板支持导出 .json 文件，团队成员可以在任何 Chrome 中导入查看，便于协作排查。
3. **结合 Performance Insights 面板**：新版 Chrome 的 Performance Insights 面板更友好，能按优先级列出问题并给出优化建议，适合快速定位。
4. **建立标准诊断流程**：开节流 → 录制 → 看概览 → 找 LCP → 找 Long Task → 查调用栈 → 看网络瀑布图，形成肌肉记忆。

## 动手练习

### 练习一：录制并分析一个页面

```
步骤：
1. 打开任意一个网站（建议选择内容丰富的页面）
2. 打开 DevTools → Performance 面板
3. 开启 CPU 4x 节流
4. 点击刷新按钮录制页面加载
5. 回答以下问题：
   - FCP 和 LCP 分别是多少？
   - LCP 元素是什么？（点击 LCP 标记查看）
   - 有没有超过 50ms 的 Long Task？
   - 最长的 Long Task 是多少 ms？它在做什么？
```

### 练习二：定位一个 Long Task

```
步骤：
1. 在上一个练习的录制结果中
2. 找到主线程中最长的红色任务
3. 点击它，查看 Call Stack（调用栈）
4. 找到耗时最长的函数（最宽的色块）
5. 点击源码链接查看具体代码
6. 分析：
   - 这段代码在做什么？
   - 为什么它耗时这么长？
   - 有什么优化方案？（拆分？延迟？Web Worker？）
```

### 练习三：录制交互过程

```
步骤：
1. 打开一个有交互功能的页面（搜索框、按钮、列表等）
2. 先等页面加载完成
3. 点击录制按钮开始录制
4. 执行以下操作：
   - 在搜索框输入文字
   - 点击一个按钮
   - 滚动一个长列表
5. 停止录制
6. 分析：
   - 输入文字时有无卡顿？主线程在忙什么？
   - 点击按钮后多久有视觉反馈？
   - 滚动是否流畅？有没有掉帧？
```

## 参考答案

### 练习一：录制并分析一个页面

**思路**：用 DevTools Performance 面板录制页面加载，培养从火焰图中提取关键信息的能力。

**答案**：

```markdown
以录制一个电商首页为例：

1. DevTools → Performance → 开启 CPU 4x 节流
2. 点击录制按钮旁的"刷新"图标（录制页面加载）
3. 等待页面加载完成，自动停止

分析结果：
- FCP: 1.2s（绿色竖线）→ 第一个内容出现
- LCP: 3.5s（蓝色竖线）→ 首屏 banner 图加载完成
- LCP 元素: <img class="hero-banner" />（点击 LCP 标记查看）

Long Tasks 分析：
- 1.0s-1.3s: main.js 编译和执行（300ms，红色三角）
  → 这是应用主脚本，包含 React 初始化
- 2.0s-2.1s: 第三方分析脚本（100ms，红色三角）
  → Google Analytics 的 gtag.js
- 2.5s-2.6s: 广告脚本（80ms，红色三角）
  → 广告 SDK 初始化

超过 50ms 的 Long Task 有 3 个，总计约 480ms。
```

**要点**：
- 红色三角标记的就是 Long Task（超过 50ms），点击可查看调用栈
- LCP 标记通常是页面加载中最重要的性能标记
- 开启 CPU 节流后录制的结果更接近真实用户体验

### 练习二：定位一个 Long Task

**思路**：深入火焰图，找到最长任务的具体调用栈，分析优化方案。

**答案**：

```markdown
定位步骤：

1. 在主线程中找到最宽的红色任务（300ms 的 main.js 执行）
2. 点击该任务，下方出现 Call Stack 面板
3. 调用栈展开：
   ├── evaluateScript (300ms)
   │   ├── Module._compile (280ms)
   │   │   ├── initializeApp (180ms) ← 最耗时
   │   │   │   ├── createRouter (60ms)
   │   │   │   ├── initStore (80ms) ← 数据初始化
   │   │   │   └── renderApp (40ms)
   │   │   └── registerPlugins (100ms)
   │   └── ...

4. 点击 initializeApp 跳转到源码
5. 发现 initStore 中同步解析了一个 200KB 的 JSON 配置

分析：
- 这段代码在做什么？→ 初始化应用状态，同步解析大 JSON
- 为什么耗时长？→ JSON.parse(200KB) 在主线程执行约 80ms
- 优化方案：
  1. 把 JSON 解析移到 Web Worker
  2. 或者用流式解析（如 JSONStream）
  3. 或者把配置数据改为按需加载
```

**要点**：
- 点击调用栈中的函数名可以直接跳转到源码
- 最宽的色块就是瓶颈所在，先优化它
- 不是所有 Long Task 都需要优化，关键是它是否阻塞了用户交互

### 练习三：录制交互过程

**思路**：录制用户交互（而非页面加载），发现 INP 相关的性能问题。

**答案**：

```markdown
录制步骤：

1. 打开有搜索功能的页面
2. 等页面完全加载
3. 点击录制按钮（⚫）开始录制
4. 执行操作：
   a. 在搜索框输入 "performance"
   b. 点击搜索按钮
   c. 滚动搜索结果列表
5. 停止录制

分析结果：

输入文字时：
- 每次按键触发 input 事件
- 主线程有 60ms 的处理任务（filter + render）
- 无明显卡顿，但 CPU 节流后会变成 240ms

点击搜索按钮后：
- 点击后 200ms 才开始处理（Input Delay）
  → 原因：前一个 keyup 事件的处理还没完成
- 搜索处理耗时 150ms
- 总交互延迟 350ms

滚动列表：
- 滚动时有频繁的 layout + paint
- 原因：滚动事件中触发了强制同步布局
- 优化：用 IntersectionObserver 替代滚动事件中的 offsetHeight 读取
```

**要点**：
- 交互录制和页面加载录制是独立的，需要分别录制
- Input Delay（主线程忙导致事件排队）是 INP 差的常见原因
- 滚动性能问题通常来自滚动事件中的强制同步布局

## 小结

本课的核心要点：

1. **Performance 面板是最强大的性能调试工具**，可以录制页面加载和用户交互的完整时间线
2. **火焰图从上到下**是调用栈，色块越宽耗时越长，红色三角是 Long Task
3. **关键标记**：FCP（绿色）、LCP（蓝色）、Long Task（红色三角）、Layout Shift
4. **标准流程**：开节流 → 录制 → 看概览 → 找 LCP → 找 Long Task → 查调用栈
5. **录制交互**同样重要：INP 问题只能通过录制交互过程来发现
