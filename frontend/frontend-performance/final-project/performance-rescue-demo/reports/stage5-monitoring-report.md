# 第五阶段：监控与回归报告

## 场景引入

优化和预算都做好了，但领导问："上线后怎么保证不会又变慢？"你需要建立一套完整的监控体系：CI 中 Lighthouse 自动检查防止代码级退化，线上 Web Vitals 采集监控真实用户体验，看板展示趋势，超标时自动告警。这样即使有人引入了性能退化，也能在影响大量用户之前被发现和修复。

---

## 常见误区

1. **监控体系建好后不维护**：告警规则过时、看板数据不准、采集代码和业务代码脱节。监控体系需要定期 review，确保数据准确。
2. **只看 Lighthouse 不看线上数据**：Lighthouse 是 Lab 数据，不反映真实用户在各种设备和网络下的体验。必须同时采集线上 Web Vitals。
3. **告警太多导致麻木**：LCP 波动 5% 就告警，团队每天收到几十条通知，很快就不再关注。应该区分 warning 和 critical，减少噪音。
4. **回归发现后只修复不复盘**：每次回归都应该问"为什么 CI 没发现？"——是断言太松、测试页面不全、还是根本没跑 Lighthouse？

## 工程建议

1. **用 P75 作为核心监控指标**：Google 评估 Core Web Vitals 就是看 P75。看板上最醒目的位置展示 P75 LCP、P75 INP、P75 CLS。
2. **设置 7 天移动平均告警**：当前值比 7 天平均值高 20% 以上时告警，过滤掉正常的日间波动。
3. **告警通知到具体负责人**：用 Slack/钉钉 Webhook 发送到团队频道，消息包含页面路径、指标值、阈值和建议排查方向。
4. **把性能数据和业务指标关联**：在看板中关联 LCP 和跳出率、INP 和转化率，用数据证明性能优化的商业价值。

## 回归规则

- LCP p75 > 2.5s：必须分析并修复或给出豁免理由
- INP p75 > 200ms：必须定位慢交互
- CLS p75 > 0.1：必须定位布局偏移来源
- 初始脚本或图片超预算：必须解释是否属于首屏必要资源

## 处理流程

1. 复现超标页面和用户路径
2. 对比最近一次正常报告
3. 定位新增资源、长任务或布局偏移
4. 修复后重新运行 Lighthouse CI
5. 更新本报告
