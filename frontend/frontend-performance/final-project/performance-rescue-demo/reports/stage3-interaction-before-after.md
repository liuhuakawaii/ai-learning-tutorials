# 第三阶段：交互优化对比

## 场景引入

首屏加载优化完成后，用户反馈"页面打开了但操作起来还是卡"——搜索框输入文字有明显延迟、点击"加入购物车"按钮要等半秒才有反应、商品列表滚动掉帧。这些是交互性能问题，核心指标是 INP（Interaction to Next Paint）。你需要用 Performance 面板录制交互过程，找到阻塞主线程的长任务，把同步大任务拆分成异步小任务。

---

## 常见误区

1. **用 setTimeout(fn, 0) 就能拆分长任务**：setTimeout 的延迟时间不精确，而且会在宏任务队列中排队。更好的方案是用 `scheduler.yield()`（如果可用）或 `requestAnimationFrame` + `setTimeout` 组合。
2. **防抖延迟设得太长**：搜索防抖 500ms 会让用户觉得"输入后要等半秒才有结果"。通常 200-300ms 是比较好的平衡点。
3. **虚拟滚动只看渲染性能不看内存**：虚拟滚动确实减少了 DOM 数量，但如果数据量特别大（10 万条），内存中仍然有 10 万个对象。需要同时考虑数据分页或懒加载。
4. **优化后不重新测量 INP**：交互优化的效果需要在实际交互中测量。用 `monitor.html` 采集优化前后的 INP 对比，不能只看 Lighthouse 分数。

## 工程建议

1. **用 Performance 面板录制交互过程**：点击录制 → 执行交互（输入、点击、滚动）→ 停止录制 → 查看 Main 轨道中的长任务，找到最耗时的函数调用。
2. **搜索输入用防抖 + 虚拟滚动组合**：防抖减少过滤次数，虚拟滚动减少 DOM 数量。两者配合可以把搜索交互的 INP 从 500ms 降到 50ms。
3. **加入购物车用乐观更新**：先更新 UI（按钮变灰、数量 +1），再发送请求。如果请求失败再回滚。这样用户感知的延迟几乎为零。
4. **用 requestIdleCallback 处理低优先级任务**：商品列表的图片懒加载、统计上报等非关键任务，用 requestIdleCallback 在主线程空闲时执行。
