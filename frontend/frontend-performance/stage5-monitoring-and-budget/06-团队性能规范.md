# 第6课：团队性能规范

> **课程定位**：建立团队级别的性能优化实践和规范
> **前置知识**：了解性能预算、CI 检查和监控
> **预计时长**：30 分钟

## 场景引入

你是团队里唯一关注性能的工程师。每次 Code Review 你都要提醒同事"这个 import 方式 tree shake 不了"、"这个图片没压缩"、"这个第三方脚本应该延迟加载"。但你不可能 review 所有 PR，有些性能问题就这样溜进了主分支。你需要把性能最佳实践写成团队规范，让自动化工具代替人工检查，让每个开发者都成为"性能守护者"。

### 3.2 自动化检查

```yaml
# GitHub Actions：PR 时自动检查
name: Performance Check

on: pull_request

jobs:
  performance:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Check bundle size
        run: npx bundlesize

      - name: Run Lighthouse
        run: lhci autorun

      - name: Check for large files
        run: |
          # 检查是否有超过 500KB 的文件
          find . -type f -size +500k -not -path './node_modules/*' | head -10
```

## 参考答案

### 练习一：制定规范

**思路**：为团队制定性能规范文档，包含代码规范、资源规范、性能预算。

**答案**：

```markdown
# 前端性能规范 v1.0

## 一、代码规范

### JavaScript
- 所有 script 标签使用 defer 或 async
- 首屏 JS 总大小 ≤ 200KB (gzipped)
- 禁止使用同步 XMLHttpRequest
- 大型依赖必须按需导入（lodash-es, date-fns）
- 超过 50ms 的计算任务必须拆分或使用 Web Worker

### CSS
- 关键 CSS 内联（< 10KB）
- 非关键 CSS 使用 media 属性异步加载
- 禁止使用 @import（阻塞渲染）
- 使用 CSS 变量减少重复代码

### React/Next.js
- 组件默认使用 Server Component
- 只在需要交互时标记 'use client'
- 列表项组件必须使用 memo
- 传给 memo 组件的回调必须使用 useCallback

## 二、资源规范

### 图片
- 照片使用 WebP/AVIF 格式
- 所有 <img> 必须有 width/height
- 首屏图片使用 fetchpriority="high"
- 非首屏图片使用 loading="lazy"
- 单张图片 ≤ 200KB

### 字体
- 使用 WOFF2 格式
- 中文字体必须子集化（≤ 100KB）
- font-display: swap + size-adjust
- 首屏字体 ≤ 2 个文件

### 第三方脚本
- 分析脚本使用 defer 加载
- 聊天/客服工具延迟加载
- 广告脚本按需加载
- 每季度审计第三方脚本

## 三、性能预算

### 指标预算
- LCP ≤ 2.5s (P75)
- INP ≤ 200ms (P75)
- CLS ≤ 0.1 (P75)

### 资源预算
- JS ≤ 200KB (gzipped)
- CSS ≤ 50KB (gzipped)
- 图片 ≤ 200KB (单张)
- 总传输 ≤ 500KB

### CI 检查
- Lighthouse Performance ≥ 80
- 资源大小超标时构建失败
- PR 时自动运行性能检查
```

**要点**：
- 规范必须可执行，配合 CI 自动检查
- 区分"必须"（CI 拦截）和"建议"（PR 评论）
- 每季度 review 一次规范，适应技术变化

### 练习三：知识库

**思路**：创建性能优化 FAQ 文档，整理常见问题和解决方案。

**答案**：

```markdown
# 性能优化 FAQ

## Q: 如何优化 LCP？
A:
1. 找到 LCP 元素（通常是首屏最大的图片）
2. 添加 <link rel="preload"> 预加载
3. 使用 WebP/AVIF 现代格式
4. 使用 srcset 提供响应式尺寸
5. 添加 fetchpriority="high" 提升优先级
6. 内联关键 CSS，减少渲染阻塞

## Q: 如何减少 CLS？
A:
1. 所有 <img> 设置 width/height
2. 使用 aspect-ratio CSS 属性
3. 字体用 font-display: swap + size-adjust
4. 动态内容（广告、通知）预留空间
5. 用 position: fixed 插入通知栏

## Q: 什么时候用 memo？
A:
- 组件渲染成本高（> 1ms）
- 经常因父组件渲染而被带动
- props 通常不变
- 先用 Profiler 确认问题存在

## Q: 如何优化 INP？
A:
1. 找到最慢的交互（用 web-vitals 的 onINP）
2. 拆解时间：输入延迟 + 处理时间 + 呈现延迟
3. 输入延迟大 → 减少主线程阻塞（拆分长任务）
4. 处理时间大 → 优化事件处理器（Web Worker）
5. 呈现延迟大 → 减少 DOM 变更范围

## Q: 第三方脚本如何优化？
A:
1. 审计所有第三方脚本的必要性
2. 高优先级：defer 加载
3. 中优先级：页面加载后延迟加载
4. 低优先级：用户交互后加载
5. 考虑 Partytown 移到 Web Worker
```

**要点**：
- FAQ 应该基于团队真实遇到的问题
- 答案要具体可执行，不要泛泛而谈
- 定期更新，补充新问题和新方案

## 常见误区

1. **规范写成文档就完事了**：文档没人看。规范必须配合自动化工具（CI 检查、PR 模板、ESLint 规则）才能真正执行。"能被机器检查的规范才是好规范。"
2. **规范太严格导致开发效率下降**：如果每个 PR 都因为"图片没压缩"被打回，开发者会反感。规范应该区分"必须"（CI 拦截）和"建议"（PR 评论），给团队适应的时间。
3. **只关注前端性能，忽略后端影响**：API 响应慢 500ms 也会拖慢 LCP。性能规范应该覆盖全链路：前端资源优化 + 后端接口性能 + CDN 配置 + 缓存策略。
4. **规范不更新**：浏览器能力在提升，最佳实践也在变化。比如 AVIF 格式两年前兼容性差，现在主流浏览器都支持了。规范应该每季度 review 一次。

## 工程建议

1. **把性能检查项写进 PR 模板**：在 `.github/PULL_REQUEST_TEMPLATE.md` 中添加"性能检查清单"，让开发者在提交 PR 时自查。这不是强制的，但能提升意识。
2. **用 ESLint 插件做代码级检查**：`eslint-plugin-import` 可以检查导入方式，`eslint-plugin-performance` 可以检查常见性能反模式。这些在保存代码时就能发现问题。
3. **建立性能优化知识库**：把常见问题（如"如何优化 LCP"、"什么时候用 memo"）整理成 FAQ 文档，新成员入职时能快速了解团队的性能最佳实践。
4. **定期分享性能优化案例**：每次性能回归修复后，在团队周会上分享根因和修复方案。真实的案例比抽象的规范更有说服力。

## 小结

1. **团队规范**：让性能优化成为团队实践，而非个人习惯
2. **代码规范**：导入、组件、样式的最佳实践
3. **资源规范**：图片、字体、第三方脚本的标准
4. **流程集成**：开发、Review、发布各阶段的检查
5. **性能文化**：持续优化、数据驱动、知识分享
