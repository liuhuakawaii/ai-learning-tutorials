# 第1课：浏览器加载链路

> **课程定位**：理解浏览器从输入 URL 到页面呈现的完整链路
> **前置知识**：了解 Core Web Vitals，会使用 Chrome DevTools
> **预计时长**：40 分钟

## 场景引入

你的网站部署在国内服务器上，国内用户访问速度还行，但海外用户反馈"打开页面要等 10 秒"。你用 DevTools Network 面板一看，TTFB 高达 3.5 秒——光是等服务器响应就花了 3.5 秒。进一步分析发现：DNS 解析 200ms、TCP 连接 150ms、TLS 协商 300ms、服务器处理 2.8 秒。问题出在没有用 CDN，海外用户每次请求都要跨越太平洋。理解加载链路的每个阶段，才能精准定位"慢"在哪一步。

## 一、完整的加载链路

```
浏览器从输入 URL 到页面呈现的完整过程：

  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
  │  DNS   │  │  TCP   │  │  TLS   │  │ 请求/  │  │  页面  │
  │  解析  │→│  连接  │→│  协商  │→│  响应  │→│  渲染  │
  │        │  │        │  │        │  │        │  │        │
  │ 域名   │  │ 三次   │  │ 加密   │  │ 服务器 │  │ DOM    │
  │ → IP   │  │ 握手   │  │ 握手   │  │ 处理   │  │ CSSOM  │
  └────────┘  └────────┘  └────────┘  └────────┘  └────────┘
     ~50ms      ~50ms       ~100ms     200~2000ms   100~3000ms
     (首次)     (首次)      (首次)

  总耗时 = DNS + TCP + TLS + TTFB + 内容下载 + 解析渲染

  优化目标：让每一阶段尽可能短，让可以并行的阶段并行
```

## 二、DNS 解析

### 2.1 什么是 DNS

```
DNS（Domain Name System）= 域名 → IP 地址的翻译服务

  你输入：https://example.com
  DNS 翻译：example.com → 93.184.216.34

  浏览器需要知道 IP 地址才能建立连接

  DNS 解析过程：
  ┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ 浏览器   │ →   │ 本地DNS  │ →   │ 根DNS    │ →   │ 权威DNS  │
  │ 缓存     │     │ 服务器   │     │ 服务器   │     │ 服务器   │
  └──────────┘     └──────────┘     └──────────┘     └──────────┘
    有缓存？          有缓存？         找到 .com        找到
    直接用            直接用           的 DNS           example.com
```

### 2.2 DNS 优化

```html
<!-- DNS Prefetch：提前解析域名 -->
<link rel="dns-prefetch" href="//cdn.example.com">
<link rel="dns-prefetch" href="//analytics.google.com">

<!-- Preconnect：提前解析 + 建立 TCP + TLS 连接 -->
<link rel="preconnect" href="https://cdn.example.com">

<!-- 用在 <head> 中，尽早开始 -->
```

## 三、TCP 连接

### 3.1 三次握手

```
TCP 三次握手：

  客户端                    服务器
    │                         │
    │──── SYN ─────────────→  │  第 1 次：我要连接
    │                         │
    │←─── SYN + ACK ────────  │  第 2 次：好的，我也准备好了
    │                         │
    │──── ACK ─────────────→  │  第 3 次：确认，连接建立
    │                         │
    │    连接已建立            │

  耗时：1 个 RTT（Round Trip Time，往返时间）
  典型值：国内 ~30ms，跨洋 ~150ms
```

### 3.2 HTTP/2 多路复用

```
HTTP/1.1 vs HTTP/2：

  HTTP/1.1：
  ┌──────────────────────────────────────────┐
  │ 连接 1: 请求A ██████████████████          │
  │ 连接 2: 请求B      ██████████████████    │
  │ 连接 3: 请求C           █████████████    │
  │ ...                                      │
  │ 浏览器最多同时 6 个连接                   │
  │ 超过 6 个请求需要排队                     │
  └──────────────────────────────────────────┘

  HTTP/2：
  ┌──────────────────────────────────────────┐
  │ 一个连接:                                 │
  │   请求A ██                                │
  │   请求B ████                              │
  │   请求C ██                                │
  │   请求D ████                              │
  │   请求E ██                                │
  │ 所有请求在一个连接上并行传输              │
  └──────────────────────────────────────────┘

  HTTP/2 优势：一个连接搞定，没有连接数限制
```

## 四、TLS 协商

### 4.1 TLS 握手

```
TLS 1.2 vs TLS 1.3：

  TLS 1.2（2 个 RTT）：
  客户端 ──→ ClientHello ──→ 服务器
  客户端 ←── ServerHello ── 服务器
  客户端 ──→ Key Exchange → 服务器
  客户端 ←── Finished ──── 服务器
  耗时：~200ms（跨洋）

  TLS 1.3（1 个 RTT）：
  客户端 ──→ ClientHello + KeyShare ──→ 服务器
  客户端 ←── ServerHello + Finished ── 服务器
  耗时：~100ms（跨洋）

  TLS 1.3 还支持 0-RTT（首次连接后）：
  客户端直接发送加密数据，无需等待握手
```

### 4.2 TLS 优化

```
优化手段：
1. 升级到 TLS 1.3（减少 1 个 RTT）
2. 使用 TLS Session Resumption（会话复用）
3. 使用 OCSP Stapling（减少证书验证时间）
4. 使用 CDN（CDN 的 TLS 终止通常更快）
```

## 五、TTFB

### 5.1 什么是 TTFB

```
TTFB（Time to First Byte）= 从发出请求到收到第一个字节的时间

  TTFB 的组成：
  ┌────────────────────────────────────────────────────┐
  │                                                    │
  │  TTFB = DNS + TCP + TLS + 服务器处理时间           │
  │                                                    │
  │  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────────────┐     │
  │  │ DNS  │ │ TCP  │ │ TLS  │ │ 服务器处理    │     │
  │  │ 50ms │ │ 50ms │ │ 100ms│ │ 200ms       │     │
  │  └──────┘ └──────┘ └──────┘ └──────────────┘     │
  │  TTFB = 400ms                                      │
  │                                                    │
  └────────────────────────────────────────────────────┘

  Google 推荐的 TTFB 阈值：
  ├── Good: ≤ 800ms
  ├── Needs Improvement: 800ms ~ 1800ms
  └── Poor: > 1800ms
```

### 5.2 影响 TTFB 的因素

```
┌──────────────────────────────────────────────────────────────┐
│              影响 TTFB 的因素                                  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  网络因素：                                                   │
│  ├── 用户与服务器的物理距离                                   │
│  ├── DNS 解析时间                                             │
│  ├── TCP/TLS 握手时间                                         │
│  └── 网络拥塞                                                 │
│                                                              │
│  服务器因素：                                                 │
│  ├── 服务器处理时间（数据库查询、业务逻辑）                   │
│  ├── 服务器负载                                               │
│  ├── 是否使用了 CDN                                           │
│  └── 是否有缓存                                               │
│                                                              │
│  应用因素：                                                   │
│  ├── 重定向次数（每次重定向都增加一个 TTFB）                  │
│  ├── 是否使用了 SSR（服务端渲染）                             │
│  └── API 响应时间                                             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 六、资源加载瀑布图

### 6.1 浏览器如何发现资源

```
浏览器的资源发现过程（Parser-driven loading）：

  1. 下载 HTML
  2. 开始解析 HTML
  3. 遇到 <link rel="stylesheet"> → 发起 CSS 请求
  4. 遇到 <script src> → 发起 JS 请求（可能阻塞解析）
  5. 遇到 <img> → 发起图片请求
  6. 解析 CSS → 发现 background-image → 发起图片请求
  7. 解析 JS → 可能动态创建 DOM → 发现新资源

  关键点：浏览器只有解析到资源引用时才会发起请求
  资源发现越晚，加载就越晚
```

### 6.2 浏览器资源优先级

```
┌──────────────────────────────────────────────────────────────┐
│              浏览器资源加载优先级                              │
├──────────────────────┬───────────────────────────────────────┤
│  最高优先级           │  当前页面的 CSS（渲染阻塞）            │
│                      │  当前页面的 <script>（解析阻塞）       │
├──────────────────────┼───────────────────────────────────────┤
│  高优先级             │  <link rel="preload"> 的资源          │
│                      │  首屏可见的图片（LCP 元素）            │
├──────────────────────┼───────────────────────────────────────┤
│  中优先级             │  异步脚本（async）                    │
│                      │  字体文件                             │
│                      │  首屏图片                             │
├──────────────────────┼───────────────────────────────────────┤
│  低优先级             │  defer 脚本                           │
│                      │  非首屏图片                           │
│                      │  loading="lazy" 的图片                 │
└──────────────────────┴───────────────────────────────────────┘
```

## 七、关键指标映射

```
加载链路中的每个阶段对应不同的性能指标：

  DNS → TCP → TLS → 请求 → 服务器处理 → 响应 → 解析 → 渲染
  │     │     │     │         │          │      │      │
  │     │     │     │         │          │      │      └─ FCP/LCP
  │     │     │     │         │          │      └─ DOMContentLoaded
  │     │     │     │         │          └─ 内容下载时间
  │     │     │     │         └─ TTFB 的一部分
  │     │     │     └─ TTFB
  │     │     └─ TLS 时间
  │     └─ TCP 时间
  └─ DNS 时间

  优化哪个阶段取决于瓶颈在哪里：
  - TTFB 高？→ 优化服务器、用 CDN、减少重定向
  - FCP 慢？→ 优化 CSS 加载、减少阻塞资源
  - LCP 慢？→ 优化 LCP 资源加载、减少阻塞
```

## 参考答案

### 练习一：查看加载链路

**思路**：用 Network 面板的 Timing 标签查看请求的各个阶段耗时，理解加载链路的时间分布。

**答案**：

```markdown
操作步骤和分析：

1. 打开 DevTools → Network 面板
2. 刷新页面
3. 点击第一个请求（HTML 文档）
4. 点击 Timing 标签

典型结果：
- Queueing: 0.5ms → 浏览器排队等待
- DNS Lookup: 12ms → DNS 解析
- Initial Connection: 25ms → TCP 握手
- SSL: 15ms → TLS 握手
- TTFB: 180ms → 服务器处理时间
- Content Download: 35ms → 内容下载

总时间: 267.5ms

分析：
- TTFB 180ms → 良好（< 800ms）
- DNS + TCP + TLS = 52ms → 正常
- 如果 DNS 很高（>100ms）→ 考虑 DNS 预解析
- 如果 TTFB 很高（>800ms）→ 考虑 CDN 或优化后端
```

**要点**：
- Timing 标签展示了请求从排队到完成的完整生命周期
- TTFB 是最重要的指标，包含 DNS + TCP + TLS + 服务器处理时间
- 不同资源的 Timing 可能差异很大，需要逐个检查关键资源

### 练习二：TTFB 分析

**思路**：对比同一网站在不同网络条件下的 TTFB，理解 CDN 和地理位置对响应速度的影响。

**答案**：

```markdown
测试方法：

1. 直接访问（服务器在美国）：
   - TTFB: 350ms
   - DNS: 15ms, TCP: 80ms, TLS: 50ms, 服务器处理: 205ms

2. 通过 CDN 访问（节点在本地）：
   - TTFB: 85ms
   - DNS: 5ms, TCP: 10ms, TLS: 8ms, 服务器处理: 62ms

对比：
- TTFB 从 350ms 降到 85ms（降低 76%）
- 网络延迟从 145ms 降到 23ms（降低 84%）
- 服务器处理从 205ms 降到 62ms（降低 70%）

CDN 的作用：
1. DNS 解析更快 → CDN 有本地 DNS 缓存
2. TCP/TLS 连接更快 → 物理距离近，RTT 更小
3. 服务器处理更快 → CDN 缓存了静态资源，不需要回源
```

**要点**：
- TTFB 的理想值是 ≤ 800ms，优秀值是 ≤ 200ms
- CDN 可以显著降低 TTFB，特别是跨洋访问的场景
- TLS 1.3 比 TLS 1.2 少一个 RTT 握手时间

### 练习三：绘制加载链路

**思路**：用 Network 面板记录所有资源的加载顺序，画出瀑布图，找到串行依赖链。

**答案**：

```markdown
资源加载瀑布图（简化）：

时间轴 → 0ms    200ms   400ms   600ms   800ms   1000ms
         |       |       |       |       |       |
HTML     ████████
CSS           ████████████
JS-main       ████████████████████
JS-vendor          ██████████████████████
hero.jpg                    ████████████████████
font.woff2                    ████████████
analytics.js                            ████████████

串行依赖链发现：
1. HTML 完成后才发现需要 CSS 和 JS → 串行
2. JS-main 完成后才发现 hero.jpg → 串行（LCP 瓶颈！）
3. font.woff2 在 CSS 解析后才开始加载 → 串行

优化方案：
1. 给 hero.jpg 添加 <link rel="preload"> → 打破依赖链 2
2. 给 font.woff2 添加 <link rel="preload"> → 打破依赖链 3
3. 同步 script 改为 defer → 减少依赖链 1 的阻塞
```

**要点**：
- 瀑布图中越靠左开始的资源，发现时间越早
- 串行依赖链是性能瓶颈的根源，A 等 B 完成才能开始
- preload 是打破串行依赖链的最有效手段

## 常见误区

1. **只关注页面渲染时间，忽视 TTFB**：TTFB 是加载链路的起点，如果 TTFB 高达 2 秒，后续再怎么优化图片和 JS 也无法弥补。先确保 TTFB ≤ 800ms。
2. **认为 HTTP/2 就不需要优化连接**：HTTP/2 的多路复用消除了连接数限制，但 TCP + TLS 握手的 RTT 开销依然存在。preconnect 仍然有价值。
3. **过度使用 preconnect**：每个 preconnect 都会消耗 DNS + TCP + TLS 资源，如果最终没有用到该源的资源，反而浪费。每个页面 preconnect 不超过 3 个。
4. **忽视重定向对 TTFB 的影响**：每次重定向都增加一个完整的 TTFB 周期。HTTP → HTTPS 的重定向、带 www 和不带 www 的重定向，都应该在服务器端一次性完成。

## 工程建议

1. **优先优化 TTFB**：使用 CDN 就近服务、启用服务器端缓存、优化数据库查询，确保 TTFB ≤ 800ms。
2. **升级到 TLS 1.3**：比 TLS 1.2 少一个 RTT 握手时间，对跨洋连接效果显著。
3. **配置 HTTP/2 或 HTTP/3**：HTTP/2 多路复用消除了 HTTP/1.1 的 6 连接限制，HTTP/3 基于 QUIC 进一步减少握手延迟。
4. **用 DevTools Timing 标签分析每个阶段**：点击 Network 面板中任意请求的 Timing 标签，可以看到 DNS、TCP、TLS、TTFB、内容下载各阶段的精确耗时。

## 小结

本课的核心要点：

1. **加载链路五阶段**：DNS → TCP → TLS → 请求/响应 → 渲染
2. **TTFB 是关键指标**：包含 DNS + TCP + TLS + 服务器处理，Google 推荐 ≤ 800ms
3. **HTTP/2 多路复用**：一个连接传输所有资源，消除了 HTTP/1.1 的连接数限制
4. **TLS 1.3 更快**：比 TLS 1.3 少一个 RTT，还支持 0-RTT
5. **资源发现是瓶颈**：浏览器只有解析到资源引用才会发起请求，preload 可以提前
