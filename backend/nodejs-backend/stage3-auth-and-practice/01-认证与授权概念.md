# 第一课：认证与授权概念

## 场景引入

你正在开发一个博客平台，用户可以注册、登录、发布文章。某天你发现一个问题：任何人只要知道文章的 URL，就能直接编辑甚至删除别人的文章。更糟糕的是，你的 API 没有任何身份验证，任何人都可以冒充任何用户发送请求。这背后的核心问题是：HTTP 协议本身是无状态的，服务器无法区分"谁在发请求"，也无法判断"这个人有没有权限做这件事"。要解决这些问题，你需要理解认证（Authentication）和授权（Authorization）这两个后端开发中最基础也最重要的概念。

## 学习目标

完成本课学习后，你将能够：

1. 清晰区分 **认证（Authentication）** 和 **授权（Authorization）**
2. 理解 HTTP 无状态的本质，以及为什么需要认证机制
3. 掌握三种主流认证方式的原理与适用场景
4. 理解 HTTPS 在认证中的关键作用
5. 建立密码安全存储的基本意识

## 一、为什么需要认证？—— HTTP 是无状态的

### 1.1 生活类比：金鱼的记忆

想象你去一家餐厅吃饭：

```
有状态的场景（TCP 连接）：
  你走进餐厅 → 服务员认识你 → 点菜 → 上菜 → 结账
  整个过程中，服务员一直记得你是谁

无状态的场景（HTTP）：
  你走进餐厅 → 服务员问"您是谁？" → 你自我介绍 → 点菜
  你去拿个调料回来 → 服务员又问"您是谁？" → 你又自我介绍
  每一次互动，服务员都把你当陌生人
```

**HTTP 协议就是那个"金鱼记忆"的服务员。** 每次 HTTP 请求都是独立的，服务器不知道这次请求和上次请求来自同一个人。

### 1.2 技术层面的理解

```
客户端（浏览器）                          服务器
    |                                    |
    |--- 请求1: GET /api/articles ------>|
    |<-- 响应1: 返回文章列表 ------------|
    |                                    |
    |    （服务器已经忘了你是谁）           |
    |                                    |
    |--- 请求2: GET /api/profile -------->|
    |<-- 响应2: 你是谁？401 未授权 -------|
    |                                    |
```

这就是为什么我们需要某种"身份证明"——让服务器在每次请求时都能识别你是谁。

### 1.3 作为前端开发者，你其实已经接触过

你可能已经用过这些方式来维持"状态"：

```javascript
// 方式1：localStorage 存 token
localStorage.setItem('token', 'abc123')

// 方式2：Cookie（浏览器自动发送）
document.cookie = 'session_id=xyz789'

// 方式3：请求头携带 token
fetch('/api/profile', {
  headers: {
    'Authorization': 'Bearer abc123'
  }
})
```

这些本质上都是在解决同一个问题：**如何让无状态的 HTTP 请求携带身份信息。**

## 二、认证 vs 授权：你是谁 vs 你能做什么

### 2.1 核心区别

```
┌─────────────────────────────────────────────────────┐
│                   认证 (Authentication)              │
│                   "你是谁？"                         │
│                                                     │
│   用户 ──→ 提供凭据（密码/Token）──→ 服务器验证       │
│                                                     │
│   结果：确认用户身份（登录成功/失败）                  │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                   授权 (Authorization)               │
│                   "你能做什么？"                      │
│                                                     │
│   已认证用户 ──→ 请求某资源 ──→ 服务器检查权限         │
│                                                     │
│   结果：允许/拒绝访问（403 Forbidden）                │
└─────────────────────────────────────────────────────┘
```

### 2.2 生活类比：公司门禁

```
认证（Authentication）：
  你刷工卡进入公司大门
  系统验证：这张卡是有效的，你是员工张三
  ✅ 认证通过

授权（Authorization）：
  你走到财务室门口，刷卡
  系统验证：你是张三，但你的角色是"开发工程师"
  ❌ 你没有权限进入财务室（403 Forbidden）

  你走到开发部，刷卡
  系统验证：你是张三，你的角色是"开发工程师"
  ✅ 授权通过
```

### 2.3 在博客系统中的体现

```typescript
// 认证：这个请求是谁发的？
// 通过 Token 识别用户身份
const user = await verifyToken(req.headers.authorization)
// user = { id: 1, email: 'zhangsan@example.com', role: 'USER' }

// 授权：这个用户能做这件事吗？
// 场景1：普通用户想删除别人的文章
if (user.role !== 'ADMIN' && article.authorId !== user.id) {
  return res.status(403).json({ error: '你没有权限删除这篇文章' })
}

// 场景2：普通用户想访问管理后台
if (user.role !== 'ADMIN') {
  return res.status(403).json({ error: '仅管理员可访问' })
}
```

### 2.4 认证与授权的流程图

```
用户请求
    │
    ▼
┌──────────┐     失败      ┌──────────────┐
│  认证阶段  │ ──────────→ │ 401 未认证     │
│ 你是谁？   │              │ "请先登录"     │
└────┬───────┘              └──────────────┘
     │ 成败
     ▼
┌──────────┐     失败      ┌──────────────┐
│  授权阶段  │ ──────────→ │ 403 未授权     │
│ 你能做啥？ │              │ "权限不足"     │
└────┬───────┘              └──────────────┘
     │ 成功
     ▼
┌──────────┐
│ 处理请求   │
│ 返回响应   │
└──────────┘
```

> **关键记忆点：401 = 未认证（不知道你是谁），403 = 未授权（知道你是谁，但你没权限）**

## 三、常见认证方式对比

### 3.1 Session + Cookie（传统方式）

#### 原理图解

```
┌──────────┐                              ┌──────────┐
│  浏览器   │                              │  服务器   │
└────┬─────┘                              └────┬─────┘
     │                                         │
     │  1. POST /login {email, password}       │
     │ ──────────────────────────────────────→ │
     │                                         │ 2. 验证密码
     │                                         │ 3. 创建 Session
     │                                         │    sessionStore[abc123] = {userId: 1}
     │                                         │
     │  4. Set-Cookie: session_id=abc123       │
     │ ←────────────────────────────────────── │
     │                                         │
     │  （浏览器自动保存 Cookie）                │
     │                                         │
     │  5. GET /api/profile                    │
     │     Cookie: session_id=abc123           │
     │ ──────────────────────────────────────→ │
     │                                         │ 6. 查找 Session
     │                                         │    sessionStore[abc123]
     │                                         │    → {userId: 1} → 找到用户
     │  7. 返回用户信息                          │
     │ ←────────────────────────────────────── │
```

#### 代码示例

```typescript
// 服务器端 Session 存储（内存示例，生产环境用 Redis）
const sessionStore: Record<string, { userId: number; createdAt: Date }> = {}

// 登录时创建 Session
app.post('/login', (req, res) => {
  const { email, password } = req.body

  // 验证密码...（省略）
  const user = verifyUser(email, password)

  if (user) {
    // 生成 Session ID
    const sessionId = generateRandomString()

    // 存储 Session
    sessionStore[sessionId] = {
      userId: user.id,
      createdAt: new Date()
    }

    // 通过 Cookie 发送给浏览器
    res.cookie('session_id', sessionId, {
      httpOnly: true,    // JavaScript 无法读取（防 XSS）
      secure: true,      // 只在 HTTPS 下发送
      sameSite: 'strict' // 防 CSRF
    })

    res.json({ message: '登录成功' })
  }
})

// 后续请求：从 Cookie 中取出 Session ID，查找用户
app.get('/api/profile', (req, res) => {
  const sessionId = req.cookies.session_id

  if (!sessionId || !sessionStore[sessionId]) {
    return res.status(401).json({ error: '未登录' })
  }

  const session = sessionStore[sessionId]
  const user = findUserById(session.userId)

  res.json(user)
})
```

#### 优缺点

```
优点：
  ✅ 服务端可控（随时可以废除 Session）
  ✅ Cookie 自动发送，前端无需手动处理
  ✅ 安全性较好（Session ID 不含敏感信息）

缺点：
  ❌ 服务端需要存储 Session（内存/Redis）
  ❌ 多服务器部署需要共享 Session（Session 同步问题）
  ❌ 不适合前后端分离项目（Cookie 跨域限制）
  ❌ 移动端支持不好（原生 App 没有 Cookie 机制）
```

### 3.2 Token / JWT（现代方式）

#### 原理图解

```
┌──────────┐                              ┌──────────┐
│  浏览器   │                              │  服务器   │
└────┬─────┘                              └────┬─────┘
     │                                         │
     │  1. POST /login {email, password}       │
     │ ──────────────────────────────────────→ │
     │                                         │ 2. 验证密码
     │                                         │ 3. 生成 JWT Token
     │                                         │    (包含用户信息 + 签名)
     │  4. 返回 Token                          │
     │ ←────────────────────────────────────── │
     │                                         │
     │  （前端存储 Token：localStorage/内存）     │
     │                                         │
     │  5. GET /api/profile                    │
     │     Authorization: Bearer eyJhbG...     │
     │ ──────────────────────────────────────→ │
     │                                         │ 6. 验证 Token 签名
     │                                         │    解码出用户信息
     │                                         │    （不需要查数据库！）
     │  7. 返回用户信息                          │
     │ ←────────────────────────────────────── │
```

#### 代码示例

```typescript
import jwt from 'jsonwebtoken'

const SECRET = 'your-secret-key'

// 登录时生成 Token
app.post('/login', (req, res) => {
  const { email, password } = req.body
  const user = verifyUser(email, password)

  if (user) {
    // 生成 JWT Token
    const token = jwt.sign(
      { userId: user.id, email: user.email, role: user.role },
      SECRET,
      { expiresIn: '7d' }
    )

    res.json({ token, user })
  }
})

// 后续请求：从 Header 中取出 Token，验证
app.get('/api/profile', (req, res) => {
  const authHeader = req.headers.authorization

  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return res.status(401).json({ error: '未登录' })
  }

  const token = authHeader.split(' ')[1]

  try {
    const payload = jwt.verify(token, SECRET)
    // payload = { userId: 1, email: 'test@example.com', role: 'USER' }
    const user = findUserById(payload.userId)
    res.json(user)
  } catch (error) {
    res.status(401).json({ error: 'Token 无效或已过期' })
  }
})
```

#### 优缺点

```
优点：
  ✅ 无状态（服务端不需要存储 Token）
  ✅ 跨域友好（通过 Header 发送，不受 Cookie 限制）
  ✅ 前后端分离标配
  ✅ 移动端友好
  ✅ 可以包含用户信息（减少数据库查询）

缺点：
  ❌ 一旦签发，无法在服务端主动废除（除非用黑名单）
  ❌ Token 较长（相比 Session ID）
  ❌ 不能在 Token 中存敏感信息（Base64 可解码）
```

### 3.3 OAuth 2.0（第三方登录）

#### 原理图解（简化版）

```
用户想用 GitHub 账号登录你的博客：

┌──────────┐     ┌──────────┐     ┌──────────┐
│  用户     │     │  你的博客  │     │  GitHub  │
└────┬─────┘     └────┬─────┘     └────┬─────┘
     │                │                │
     │ 1. 点击"用 GitHub 登录"           │
     │ ──────────────→│                │
     │                │                │
     │ 2. 跳转到 GitHub 授权页面          │
     │ ←──────────────│                │
     │                │                │
     │ 3. 用户在 GitHub 授权              │
     │ ───────────────────────────────→│
     │                │                │
     │ 4. GitHub 回调你的博客，带授权码     │
     │                │←───────────────│
     │                │                │
     │                │ 5. 用授权码换 Token │
     │                │ ──────────────→│
     │                │                │
     │                │ 6. 返回 Access Token│
     │                │←───────────────│
     │                │                │
     │                │ 7. 用 Token 获取用户信息
     │                │ ──────────────→│
     │                │                │
     │                │ 8. 返回 GitHub 用户信息
     │                │←───────────────│
     │                │                │
     │ 9. 登录成功，创建/关联本地账号       │
     │ ←──────────────│                │
```

#### 简单理解

```
OAuth 2.0 就像"代驾"：
  你想开车（访问用户数据），但车不是你的
  你找车主（用户）要了授权（授权码）
  车主给了你一张临时通行证（Access Token）
  你凭这张通行证开车（访问资源）
  通行证有有效期，过期需要重新申请
```

### 3.4 三种方式对比总结

```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│     特性      │ Session+Cookie│    JWT       │  OAuth 2.0   │
├──────────────┼──────────────┼──────────────┼──────────────┤
│ 状态          │ 有状态        │ 无状态       │ 取决于实现     │
│ 存储位置      │ 服务端        │ 客户端       │ 客户端        │
│ 跨域支持      │ 差（Cookie）  │ 好（Header） │ 好            │
│ 移动端支持    │ 一般          │ 好           │ 好            │
│ 服务端可控    │ 强            │ 弱           │ 强            │
│ 扩展性        │ 差（需共享）  │ 好           │ 好            │
│ 适用场景      │ 传统 Web 应用 │ 前后端分离    │ 第三方登录     │
│ 实现复杂度    │ 低            │ 低           │ 高            │
└──────────────┴──────────────┴──────────────┴──────────────┘
```

> **对于我们的博客项目，选择 JWT 作为主要认证方式，OAuth 2.0 作为可选的第三方登录扩展。**

## 四、HTTPS 的重要性

### 4.1 为什么认证必须配合 HTTPS

```
没有 HTTPS（HTTP 明文传输）：

  浏览器                    攻击者                   服务器
    │                        │                        │
    │ Authorization:         │                        │
    │ Bearer eyJhbG...       │                        │
    │ ────────→              │                        │
    │              攻击者可以看到！                      │
    │              复制 Token                          │
    │                        │ ──────────────────────→ │
    │                        │    用你的 Token 冒充你    │
    │                        │                        │

有了 HTTPS（加密传输）：

  浏览器                    攻击者                   服务器
    │                        │                        │
    │ 加密数据: a8f2k3...    │                        │
    │ ────────→              │                        │
    │              攻击者只能看到乱码                     │
    │              无法解密                             │
    │                        │                        │
```

### 4.2 HTTPS 做了什么

```
HTTPS = HTTP + TLS/SSL

三个保护：
  1. 加密（Encryption）：数据被加密，中间人看不懂
  2. 身份验证（Authentication）：确认你连接的是真正的服务器
  3. 完整性（Integrity）：数据传输过程中不会被篡改

类比：
  HTTP  = 明信片（谁都能看到内容）
  HTTPS = 信封信件（只有收件人能拆开看）
```

### 4.3 开发环境怎么办

```typescript
// 开发环境（localhost）可以不用 HTTPS
// 因为数据不出本机，没有中间人风险

// 生产环境必须用 HTTPS！
// 方案1：使用云平台自动配置（Railway、Vercel）
// 方案2：Let's Encrypt 免费证书
// 方案3：Nginx 反向代理 + 证书
```

## 五、安全基础知识：密码绝不能明文存储

### 5.1 为什么不能明文存储密码

```
如果你的数据库被泄露了：

明文存储：
  用户表
  ┌─────┬─────────────┬──────────┐
  │ id  │ email       │ password │
  ├─────┼─────────────┼──────────┤
  │ 1   │ test@a.com  │ 123456   │  ← 攻击者直接看到密码！
  │ 2   │ admin@a.com │ admin888 │  ← 而且很多人在不同网站用同一个密码
  └─────┴─────────────┴──────────┘

加密存储（后面会详细讲 bcrypt）：
  用户表
  ┌─────┬─────────────┬──────────────────────────────────┐
  │ id  │ email       │ password                          │
  ├─────┼─────────────┼──────────────────────────────────┤
  │ 1   │ test@a.com  │ $2b$10$N9qo8uLOickgx2ZMRZoMy... │
  │ 2   │ admin@a.com │ $2b$10$RtMiHAZMwODnQ3KjnMEHt... │
  └─────┴─────────────┴──────────────────────────────────┘
  攻击者拿到的是哈希值，无法还原原始密码
```

### 5.2 密码安全的黄金法则

```
法则1：永远不要明文存储密码
法则2：永远不要在日志中打印密码
法则3：永远不要在 API 响应中返回密码
法则4：使用专业的密码哈希算法（bcrypt），不要自己发明
法则5：密码传输必须使用 HTTPS
```

```typescript
// ❌ 错误示范
const user = await db.user.create({
  data: {
    email: 'test@example.com',
    password: '123456'  // 明文存储！
  }
})

console.log('用户密码:', user.password)  // 日志打印密码！

res.json({
  id: user.id,
  email: user.email,
  password: user.password  // API 返回密码！
})

// ✅ 正确示范
const hashedPassword = await bcrypt.hash('123456', 10)

const user = await db.user.create({
  data: {
    email: 'test@example.com',
    password: hashedPassword  // 加密存储
  }
})

// 日志中不打印密码
console.log('用户创建成功:', user.email)

// API 响应中不返回密码
res.json({
  id: user.id,
  email: user.email
  // 不包含 password 字段
})
```

## 参考答案

### 练习 1：理解认证与授权

**思路**：区分认证和授权的关键是看操作的目的——验证身份属于认证，检查权限属于授权。

**答案**：
1. **认证**：用户输入邮箱和密码，服务器验证凭据确认身份
2. **授权**：用户已认证，但系统检查其角色是否有权访问管理后台
3. **认证**：通过 GitHub OAuth 验证用户身份（第三方认证）
4. **授权**：系统检查当前用户是否为文章的所有者（资源权限）
5. **认证**：验证 Token 的签名和有效期，确认身份合法性

**要点**：
- 401 = 未认证（不知道你是谁），403 = 未授权（知道你是谁但没权限）
- 认证是授权的前提：必须先确认身份，才能判断权限
- OAuth 2.0 本质上也是认证（通过第三方确认身份），不是授权

### 练习 2：设计权限矩阵

**思路**：按角色从低到高设计权限，遵循最小权限原则——每个角色只拥有完成其职责所需的最低权限。GUEST 只能浏览，USER 能操作自己的内容，EDITOR 能管理内容，ADMIN 拥有全部权限。

**答案**：
```
操作                    GUEST   USER    EDITOR   ADMIN
浏览文章                 ✅      ✅      ✅       ✅
发表评论                 ❌      ✅      ✅       ✅
发布文章                 ❌      ❌      ✅       ✅
编辑自己的文章            ❌      ✅      ✅       ✅
编辑别人的文章            ❌      ❌      ✅       ✅
删除自己的文章            ❌      ✅      ✅       ✅
删除任何文章              ❌      ❌      ❌       ✅
管理用户                 ❌      ❌      ❌       ✅
管理分类/标签             ❌      ❌      ✅       ✅
```

**要点**：
- USER 可以删除自己的文章，但不能删除别人的（资源所有权验证）
- EDITOR 可以编辑别人的文章（内容审核需要），但不能删除任意文章
- 只有 ADMIN 拥有删除任意文章和管理用户的权限
- 这个矩阵可以直接转化为 `requireRole` 和 `requireOwnership` 中间件的配置

### 练习 3：画出认证流程图

**思路**：按照用户操作的完整生命周期，从注册到删除文章，标注每一步的认证/授权要求和可能的错误状态码。

**答案**：
```
完整认证授权流程：

[1] POST /api/auth/register
    Body: { email, username, password }
    │
    ├─ 成功 → 201 Created + { user, accessToken, refreshToken }
    │
    ├─ 邮箱已存在 → 409 Conflict
    ├─ 输入不合法 → 422 Unprocessable Entity
    └─ 服务器错误 → 500 Internal Server Error

[2] POST /api/auth/login
    Body: { email, password }
    │
    ├─ 成功 → 200 OK + { user, accessToken, refreshToken }
    │
    ├─ 邮箱或密码错误 → 401 Unauthorized
    └─ 输入不合法 → 422 Unprocessable Entity

[3] POST /api/articles
    Header: Authorization: Bearer <accessToken>
    Body: { title, content }
    │
    ├─ 成功 → 201 Created + { article }
    │
    ├─ 无 Token → 401 Unauthorized
    ├─ Token 过期 → 401 Unauthorized (code: TOKEN_EXPIRED)
    └─ Token 无效 → 401 Unauthorized (code: TOKEN_INVALID)

[4] PUT /api/articles/:id
    Header: Authorization: Bearer <accessToken>
    Body: { title, content }
    │
    ├─ 成功 → 200 OK + { article }
    │
    ├─ 无 Token → 401 Unauthorized
    ├─ 文章不是自己的 → 403 Forbidden
    └─ 文章不存在 → 404 Not Found

[5] DELETE /api/articles/:id
    Header: Authorization: Bearer <accessToken>
    │
    ├─ 成功 → 200 OK
    │
    ├─ 无 Token → 401 Unauthorized
    ├─ 文章不是自己的 → 403 Forbidden
    └─ 文章不存在 → 404 Not Found
```

**要点**：
- 注册和登录是公开接口，不需要 Token
- 发布文章需要认证（authenticate），但不需要检查所有权（创建者就是自己）
- 编辑和删除需要认证 + 所有权验证（requireOwnership）
- 状态码必须准确：401 表示未认证，403 表示已认证但无权限

## 常见误区

1. **混淆 401 和 403 状态码**：很多人分不清 401 Unauthorized 和 403 Forbidden 的区别。401 表示"未认证"（服务器不知道你是谁），403 表示"未授权"（服务器知道你是谁，但你没有权限）。用错了状态码会导致前端无法正确处理错误逻辑。

2. **认为 JWT 比 Session 安全**：JWT 和 Session 各有优劣，不存在谁更安全。JWT 的 Payload 是 Base64 编码，任何人都能解码看到内容。真正的安全性取决于密钥强度和传输方式（HTTPS），而非令牌格式本身。

3. **在前端硬编码 Token**：有些初学者把 JWT Token 直接写在前端代码中，或者用 `localStorage` 存储却不做 XSS 防护。Token 一旦泄露，攻击者可以在任何地方冒充该用户。

4. **忽略 HTTPS 的重要性**：在开发环境用 HTTP 没问题，但生产环境如果不启用 HTTPS，Token 在传输过程中会被中间人截获。认证机制再强，传输不加密也等于零。

---

## 工程建议

1. **选择认证方案时考虑架构**：传统同源 Web 应用用 Session + Cookie 即可；前后端分离项目优先选 JWT；需要第三方登录时引入 OAuth 2.0。不要为了"看起来现代"而盲目使用 JWT。

2. **Token 存储策略要慎重**：JWT 存 `localStorage` 简单但易受 XSS 攻击；存 `httpOnly Cookie` 更安全但需防 CSRF。建议 Access Token 存内存（变量），Refresh Token 存 httpOnly Cookie。

3. **401/403 的前端处理要区分**：收到 401 时应跳转登录页或刷新 Token；收到 403 时应提示"权限不足"而非重新登录。两者混用会导致用户体验混乱。

4. **密码存储是底线**：无论项目大小，密码都必须用 bcrypt 等专业算法加密存储。即使是个人项目、即使是内部系统，明文存储密码都是不可接受的。

## 小结

本课我们学习了认证与授权的核心概念：

| 概念 | 要点 |
|------|------|
| **HTTP 无状态** | 每次请求都是独立的，需要额外机制传递身份信息 |
| **认证 (Authentication)** | 验证"你是谁"，如登录、Token 验证 |
| **授权 (Authorization)** | 验证"你能做什么"，如角色检查、权限控制 |
| **Session + Cookie** | 传统方式，有状态，适合同源 Web 应用 |
| **JWT Token** | 现代方式，无状态，前后端分离标配 |
| **OAuth 2.0** | 第三方登录，如 GitHub、Google 登录 |
| **HTTPS** | 认证的基础设施，保护 Token 不被窃取 |
| **密码安全** | 永远不要明文存储，使用 bcrypt 等专业算法 |
