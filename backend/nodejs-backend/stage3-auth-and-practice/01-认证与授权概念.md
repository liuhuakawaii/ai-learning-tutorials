# 认证与授权概念

你的博客 API 现在能读写数据了，但有一个致命问题：任何人只要知道接口地址，就能以任何用户的身份发文章、删评论。HTTP 是无状态的——服务器处理完一个请求就忘了"你是谁"，下次请求又得重新认识。

这节课解决两个问题：怎么让服务器记住"你是谁"（认证），怎么判断"你能不能做这件事"（授权）。

## 认证 vs 授权

先区分这两个概念：

```
认证（Authentication）→ "你是谁？"
  用户说"我是张三"，服务器要验证他真的是张三

授权（Authorization）→ "你能做什么？"
  张三能编辑自己的文章，但不能编辑李四的文章
```

认证在前，授权在后。你得先知道来的是谁，才能判断他有没有权限。

## 三种主流认证方式

### Session + Cookie

最传统的做法。服务器存一份会话数据，客户端通过 Cookie 带上会话 ID。

```
客户端                          服务器
  │  POST /login                │
  │  { email, password }        │
  │────────────────────────────►│ 验证密码
  │                             │ 创建 session: { userId: 1, role: 'user' }
  │  200 OK                     │ 存在内存/Redis 里
  │  Set-Cookie: sid=abc123     │
  │◄────────────────────────────│
  │                             │
  │  GET /api/posts             │
  │  Cookie: sid=abc123         │
  │────────────────────────────►│ 查 session：abc123 → userId=1
  │                             │ 知道这是张三
  │  200 OK [张三的文章]         │
  │◄────────────────────────────│
```

优点：服务端控制，随时可以废除某个会话。
缺点：服务器要存会话数据，分布式部署时要共享存储（比如 Redis）。

### JWT（JSON Web Token）

当前最流行的方式。用户登录后，服务器签发一个加密的 token，客户端每次请求带上它。服务器不需要存任何会话数据。

```
客户端                          服务器
  │  POST /login                │
  │  { email, password }        │
  │────────────────────────────►│ 验证密码
  │                             │ 签发 JWT（包含 userId, role）
  │  200 OK                     │
  │  { token: "eyJhbG..." }    │
  │◄────────────────────────────│
  │                             │
  │  GET /api/posts             │
  │  Authorization: Bearer eyJ..│
  │────────────────────────────►│ 验证签名 → 解出 userId=1
  │                             │ 不需要查数据库/缓存
  │  200 OK                     │
  │◄────────────────────────────│
```

JWT 的结构是三段 Base64 用点号连接：

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEsInJvbGUiOiJ1c2VyIn0.SflKxwRJSMeKKF2QT4fwpM

  头部（Header）  → 算法信息
  载荷（Payload） → 用户数据（不要放密码！）
  签名（Signature）→ 用密钥加密，防篡改
```

注意：JWT 的载荷是 Base64 编码，不是加密。任何人都能解码看到内容，但无法篡改（因为没有密钥重新签名）。

优点：无状态，服务端不存东西，天然适合分布式。
缺点：签发后无法主动废除（除非用黑名单）。

### OAuth 2.0

"用 GitHub/Google/微信登录"就是 OAuth。它解决的是"让第三方安全地访问你的资源"的问题。

```
用户 → 点击"用 GitHub 登录"
     → 跳转到 GitHub 授权页面
     → 用户同意
     → GitHub 回调你的应用，带一个 code
     → 你的服务器用 code 换 access_token
     → 用 token 获取用户信息
     → 创建/找到本地用户，签发自己的 JWT
```

OAuth 的流程比较复杂，但核心思想是：用户不需要把 GitHub 密码告诉你，只需要在 GitHub 那边授权"允许这个应用读取我的基本信息"。

## 选哪个？

```
场景                          推荐方案
─────────────────────────────────────────
传统 Web 应用（有页面）        Session + Cookie
前后端分离 API                JWT
需要第三方登录                OAuth 2.0 + JWT
微服务间通信                  JWT 或 mTLS
```

本课程用 JWT，因为博客 API 是前后端分离的。

## 密码存储的铁律

**永远不要存明文密码。**

用户注册时，你应该存的是密码的哈希值。登录时，把用户输入的密码也哈希一下，和数据库里的哈希值比对。

```
注册流程：
  用户输入密码 "myPassword123"
  → 用 bcrypt 生成哈希 "$2b$10$xK..."
  → 存入数据库

登录流程：
  用户输入密码 "myPassword123"
  → 用 bcrypt 比对数据库里的哈希
  → 匹配 → 签发 JWT
  → 不匹配 → 拒绝
```

为什么用 bcrypt 而不是 SHA256？bcrypt 有"盐"（salt）和"成本因子"（cost），能防彩虹表攻击和暴力破解。SHA256 太快了，攻击者一秒钟能试几十亿个密码。

## HTTPS 的重要性

JWT 在传输过程中是明文的。如果没有 HTTPS，中间人可以截获 token 冒充用户。

```
没有 HTTPS：
  用户 ──── token: eyJhbG... ────► 服务器
            ↑
          攻击者截获

有 HTTPS：
  用户 ════ 加密通道 ═══════════► 服务器
            ↑
          攻击者看不到内容
```

开发环境用 HTTP 没问题，但生产环境必须上 HTTPS。

## 一个完整的认证流程长什么样

把上面的概念串起来：

```
1. 注册
   POST /api/auth/register
   { name, email, password }
   → bcrypt 哈希密码 → 存入数据库 → 返回 JWT

2. 登录
   POST /api/auth/login
   { email, password }
   → bcrypt 比对密码 → 签发 JWT

3. 访问受保护的接口
   GET /api/posts/mine
   Authorization: Bearer <token>
   → 中间件验证 JWT → 解出 userId → 查询该用户的文章

4. 权限控制
   DELETE /api/posts/1
   → 验证 JWT → 解出 userId 和 role
   → 检查：是文章作者？是管理员？→ 允许/拒绝
```

这些流程在接下来的课时里会逐步实现。

## 参考答案

### 练习一

1. HS256（HMAC-SHA256）
2. userId: 1, name: "张三", role: admin, iat: 1700000000
3. JWT 的 Payload 只是 Base64 编码，不是加密。任何人拿到 token 都能解码看到内容，所以不能放密码、银行卡号等敏感数据。

### 练习二

```js
const crypto = require('crypto')

function hashPassword(password) {
  return crypto.createHash('sha256').update(password).digest('hex')
}

function verifyPassword(password, hash) {
  return hashPassword(password) === hash
}

// 问题：相同密码产生相同哈希
// "123456" → 永远是同一个值
// 攻击者可以用彩虹表反查
// bcrypt 每次加不同的盐，同一个密码产生不同的哈希
```

### 练习三要点

```
POST /api/auth/register
  请求：{ name, email, password }
  处理：验证邮箱格式 → 检查邮箱是否已注册 → bcrypt 哈希密码 → 存库 → 签发 JWT
  响应：{ token, user: { id, name, email } }

POST /api/auth/login
  请求：{ email, password }
  处理：查邮箱 → 用户不存在就 401 → bcrypt 比对 → 不匹配就 401 → 签发 JWT
  响应：{ token, user: { id, name, email } }

GET /api/posts/mine
  请求头：Authorization: Bearer <token>
  处理：验证 JWT → 解出 userId → 查询该用户的文章
  响应：{ data: [...] }
```
