# 05 - 代码审查自动化

## 场景引入

团队采用 PR 工作流，但 Code review 成为瓶颈：资深工程师花大量时间审查代码，初级工程师的 PR 反馈周期长，一些常见的问题（命名不规范、缺少测试、类型覆盖不足）反复出现。你需要一套自动化的审查体系，把机器能做的事交给机器，让人专注于架构和业务逻辑的审查。

## 学习目标

- 设计高效的 PR 审查流程
- 使用 GitHub Actions 实现自动化检查
- 了解 AI 辅助审查工具的使用场景
- 建立代码审查清单
- 实现类型覆盖率监控

## 一、PR 审查流程

一个完整的 PR 审查流程应该包含自动检查和人工审查两个阶段：

```typescript
interface ReviewPipeline {
  // 阶段 1：自动化检查（机器执行）
  automated: {
    lint: boolean          // ESLint 检查
    typeCheck: boolean     // TypeScript 类型检查
    test: boolean          // 单元测试通过
    coverage: boolean      // 覆盖率达标
    build: boolean         // 构建成功
  }
  // 阶段 2：人工审查
  manual: {
    architecture: boolean  // 架构合理性
    businessLogic: boolean // 业务逻辑正确性
    readability: boolean   // 代码可读性
  }
}
```

自动检查的执行顺序：快速检查先执行，失败即终止。lint → typecheck → test → coverage → build。

## 二、GitHub Actions 集成

使用 GitHub Actions 构建完整的 CI 流水线：

```yaml
# .github/workflows/pr-check.yml
name: PR 质量检查

on:
  pull_request:
    branches: [main, develop]

concurrency:
  group: ${{ github.workflow }}-${{ github.head_ref }}
  cancel-in-progress: true

jobs:
  quality-gate:
    name: 质量门禁
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - name: 检出代码
        uses: actions/checkout@v4

      - name: 安装 Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: 安装依赖
        run: npm ci

      - name: ESLint 检查
        run: npm run lint:check

      - name: TypeScript 类型检查
        run: npm run typecheck

      - name: 运行测试
        run: npm run test:run

      - name: 检查覆盖率
        run: npm run test:coverage

      - name: 构建检查
        run: npm run build
```

PR 自动标签配置：

```yaml
# .github/labeler.yml

    - any-glob-to-any-file: 'src/api/**'

  - changed-files:
    - any-glob-to-any-file: '**/*.test.ts'
```

## 三、AI 辅助审查工具

AI 工具可以辅助发现常见问题，但不能替代人工审查。AI 审查适合的场景：命名建议、代码风格一致性、潜在的安全问题、性能反模式。不适合的场景：架构设计决策、业务逻辑正确性、团队协作规范。

```yaml
# .github/workflows/ai-review.yml
name: AI 辅助审查

on:
  pull_request:
    types: [opened, synchronize]

permissions:
  pull-requests: write
  contents: read

jobs:
  ai-review:
    runs-on: ubuntu-latest
    steps:
      - name: 检出代码
        uses: actions/checkout@v4

      - name: 获取 PR diff
        id: diff
        run: |
          git fetch origin ${{ github.base_ref }} --depth=1
          DIFF=$(git diff origin/${{ github.base_ref }}...HEAD)
          echo "diff<<EOF" >> $GITHUB_OUTPUT
          echo "$DIFF" >> $GITHUB_OUTPUT
          echo "EOF" >> $GITHUB_OUTPUT

      - name: AI 审查
        uses: ai-code-review/action@v1
        with:
          diff: ${{ steps.diff.outputs.diff }}
          focus: 'type-safety,naming,performance'
```

## 四、审查清单

建立标准化的审查清单，确保每次审查覆盖关键点：

```markdown
# 代码审查清单

## 自动化检查（CI 执行）
- [ ] ESLint 检查通过（0 errors, 0 warnings）
- [ ] TypeScript 类型检查通过
- [ ] 所有测试通过
- [ ] 测试覆盖率 ≥ 80%
- [ ] 无硬编码密钥或敏感信息

## 代码质量（审查者检查）
- [ ] 命名清晰，符合项目规范
- [ ] 函数职责单一，长度合理（< 50 行）
- [ ] 错误处理完善，有明确的错误边界
- [ ] 无 any 类型，类型标注完整
- [ ] 新增功能有对应的测试用例

## 架构设计（资深工程师检查）
- [ ] 变更方向符合项目架构
- [ ] 依赖关系合理，无循环依赖
- [ ] 抽象层次适当，不过度设计
- [ ] 向后兼容，无 breaking changes
```

自动化审查清单检查：

```typescript
// scripts/automated-review.ts
import { ESLint } from 'eslint'

interface ChecklistResult {
  item: string
  passed: boolean
  details?: string
}

async function runAutomatedReview(): Promise<ChecklistResult[]> {
  const results: ChecklistResult[] = []

  const eslint = new ESLint()
  const lintResults = await eslint.lintFiles(['src/**/*.ts'])
  const errorCount = lintResults.reduce((sum, r) => sum + r.errorCount, 0)

  results.push({
    item: 'ESLint 检查',
    passed: errorCount === 0,
    details: errorCount > 0 ? `发现 ${errorCount} 个错误` : undefined,
  })

  return results
}
```

## 五、类型覆盖率

类型覆盖率衡量代码中类型标注的完整程度：

```bash
npm install -D type-coverage
```

```json
{
  "scripts": {
    "type-coverage": "type-coverage --detail --strict",
    "type-coverage:check": "type-coverage --at-least 95"
  }
}
```

自定义类型覆盖率检查：

```typescript
// scripts/type-coverage.ts
import * as ts from 'typescript'

interface TypeCoverageReport {
  totalIdentifiers: number
  typedIdentifiers: number
  coverage: number
  untypedFiles: { file: string; count: number }[]
}

function analyzeTypeCoverage(
  fileNames: string[],
  options: ts.CompilerOptions
): TypeCoverageReport {
  const program = ts.createProgram(fileNames, options)
  const checker = program.getTypeChecker()

  let totalIdentifiers = 0
  let typedIdentifiers = 0
  const untypedFiles: Map<string, number> = new Map()

  for (const sourceFile of program.getSourceFiles()) {
    if (sourceFile.isDeclarationFile) continue

    let fileTotal = 0
    let fileTyped = 0

    function visit(node: ts.Node) {
      if (ts.isIdentifier(node)) {
        const symbol = checker.getSymbolAtLocation(node)
        if (symbol) {
          const type = checker.getTypeOfSymbolAtLocation(symbol, node)
          fileTotal++
          if (type.flags !== ts.TypeFlags.Any && type.flags !== ts.TypeFlags.Unknown) {
            fileTyped++
          }
        }
      }
      ts.forEachChild(node, visit)
    }

    visit(sourceFile)

    if (fileTotal > 0) {
      totalIdentifiers += fileTotal
      typedIdentifiers += fileTyped
      if (fileTyped / fileTotal < 0.95) {
        untypedFiles.set(sourceFile.fileName, fileTotal - fileTyped)
      }
    }
  }

  return {
    totalIdentifiers,
    typedIdentifiers,
    coverage: totalIdentifiers > 0 ? (typedIdentifiers / totalIdentifiers) * 100 : 100,
    untypedFiles: Array.from(untypedFiles.entries()).map(([file, count]) => ({ file, count })),
  }
}
```

在 CI 中检查类型覆盖率：

```yaml
# .github/workflows/type-coverage.yml
name: 类型覆盖率检查

on:
  pull_request:
    paths: ['src/**/*.ts']

jobs:
  type-coverage:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run type-coverage:check
```

## 常见误区

1. **自动化替代人工审查**：自动化检查只能发现表面问题，架构设计、业务逻辑等深层问题仍需人工审查。

2. **审查清单过长**：清单太长会导致审查疲劳。保持清单精简，只保留最关键的检查项。

3. **CI 检查过于严格**：过高的覆盖率阈值或过严的 lint 规则会导致 PR 长时间无法合并。

4. **忽略审查反馈的闭环**：发现问题后没有跟进修复，自动化检查就失去了意义。

## 工程建议

1. **分层自动化**：快速检查在本地 pre-commit hook 中执行，完整检查在 CI 中执行。减少等待时间。

2. **审查轮值**：不要让同一个人一直做审查，建立轮值制度。不同的人关注不同的方面。

3. **审查模板**：为 PR 描述创建模板，要求作者说明变更原因、测试方案、回滚计划。

4. **渐进式提升**：对于存量项目，先设置较低的覆盖率阈值（如 60%），然后每次 PR 要求新代码覆盖率不低于 80%。

## 小结

代码审查自动化是团队协作效率的倍增器。通过 GitHub Actions 集成自动化检查，使用 AI 工具辅助审查，建立标准化的审查清单，监控类型覆盖率，可以让人工审查专注于更有价值的问题。

### 练习三

**思路**：使用 TypeScript Compiler API 扫描 AST，查找 `any` 类型的使用。

**答案**：

```typescript
// scripts/check-any-usage.ts
import * as ts from 'typescript'

interface AnyUsage {
  file: string
  line: number
  column: number
  context: string
}

function findAnyUsage(fileNames: string[]): AnyUsage[] {
  const program = ts.createProgram(fileNames, {
    target: ts.ScriptTarget.ESNext,
    module: ts.ModuleKind.ESNext,
    strict: true,
  })
  const checker = program.getTypeChecker()
  const usages: AnyUsage[] = []

  for (const sourceFile of program.getSourceFiles()) {
    if (sourceFile.isDeclarationFile) continue

    function visit(node: ts.Node) {
      if (ts.isTypeNode(node)) {
        const type = checker.getTypeAtLocation(node)
        if (type.flags & ts.TypeFlags.Any) {
          const { line, character } = sourceFile.getLineAndCharacterOfPosition(node.getStart())
          usages.push({
            file: sourceFile.fileName,
            line: line + 1,
            column: character + 1,
            context: node.getText(sourceFile).slice(0, 50),
          })
        }
      }
      ts.forEachChild(node, visit)
    }
    visit(sourceFile)
  }
  return usages
}

const files = process.argv.slice(2)
const usages = findAnyUsage(files)

if (usages.length > 0) {
  console.error(`发现 ${usages.length} 处 any 类型使用:`)
  for (const usage of usages) {
    console.error(`  ${usage.file}:${usage.line}:${usage.column} - ${usage.context}`)
  }
  process.exit(1)
} else {
  console.log('未发现 any 类型使用')
}
```

**要点**：TypeScript Compiler API 可以访问完整的类型信息；`type.flags & ts.TypeFlags.Any` 检测 any 类型。
