# 06 - 阶段实战：测试体系建设

## 场景引入

你所在的团队决定为项目引入完整的测试体系。项目已经运行了一段时间，代码量不小，但测试覆盖率接近零。你需要从零搭建一套可持续维护的测试基础设施，涵盖单元测试、集成测试、类型测试、契约测试，并将其融入 CI 流水线。

## 学习目标

- 设计分层测试策略，明确每层测试的职责边界
- 搭建完整的测试基础设施，包括工具配置和辅助函数
- 构建 CI 流水线中的质量门禁
- 实现测试工具库，提升测试编写效率
- 建立覆盖率监控体系

## 一、测试体系架构

一个完整的测试体系应该包含四层：

```typescript
interface TestPyramid {
  // 第一层：单元测试（占比 70%）—— 单个函数/类，全部 Mock
  unit: { scope: '单个函数/类'; speed: '< 100ms'; tools: 'Vitest' }
  // 第二层：集成测试（占比 20%）—— 多个模块协作，真实数据库
  integration: { scope: '多个模块协作'; speed: '< 1s'; tools: 'Vitest + TestContainers' }
  // 第三层：契约测试（占比 5%）—— 服务间接口，Mock 服务端
  contract: { scope: '服务间接口'; speed: '< 500ms'; tools: 'Zod + Pact' }
  // 第四层：E2E 测试（占比 5%）—— 完整用户流程，完整环境
  e2e: { scope: '完整用户流程'; speed: '< 30s'; tools: 'Playwright' }
}
```

## 三、测试辅助工具库

构建可复用的测试工具：

```typescript
// tests/helpers/mock.ts
import { vi } from 'vitest'

export function createMock<T extends (...args: any[]) => any>(
  implementation?: T
): ReturnType<typeof vi.fn<T>> {
  return implementation ? vi.fn(implementation) : vi.fn()
}

export function createMockService<T>(methods: (keyof T)[]): T {
  const service = {} as T
  for (const method of methods) { (service as any)[method] = vi.fn() }
  return service
}
```

## 四、分层测试实践

### 单元测试

```typescript
// src/modules/user/user.service.test.ts
import { describe, it, expect, vi, beforeEach } from 'vitest'
import { UserService } from './user.service'
import { createUser } from '@tests/helpers/fixture'

describe('UserService', () => {
  let service: UserService
  let mockRepository: { findById: any; save: any; delete: any }

  beforeEach(() => {
    mockRepository = { findById: vi.fn(), save: vi.fn(), delete: vi.fn() }
    service = new UserService(mockRepository as any)
  })

  it('用户存在时应返回用户', async () => {
    const user = createUser()
    mockRepository.findById.mockResolvedValue(user)
    const result = await service.getUserById(user.id)
    expect(result).toEqual(user)
  })

  it('用户不存在时应抛出 NotFoundError', async () => {
    mockRepository.findById.mockResolvedValue(null)
    await expect(service.getUserById('nonexistent')).rejects.toThrow('User not found')
  })
})
```

### 集成测试

```typescript
// src/modules/user/user.integration.test.ts
import { describe, it, expect, beforeAll, afterAll } from 'vitest'
import { UserService } from './user.service'
import { UserRepository } from './user.repository'
import { createTestDatabase } from '@tests/helpers/database'

describe('UserService 集成测试', () => {
  let service: UserService
  let db: ReturnType<typeof createTestDatabase>

  beforeAll(async () => {
    db = createTestDatabase()
    service = new UserService(new UserRepository(db as any))
  })

  afterAll(async () => { await db.cleanup() })

  it('完整的用户生命周期', async () => {
    const user = await service.createUser({ name: '测试用户', email: 'test@example.com' })
    expect(user.id).toBeDefined()

    const found = await service.getUserById(user.id)
    expect(found.name).toBe('测试用户')

    await service.deleteUser(user.id)
    await expect(service.getUserById(user.id)).rejects.toThrow()
  })
})
```

### 契约测试

```typescript
// tests/contracts/user-api.contract.ts
import { describe, it, expect } from 'vitest'
import { z } from 'zod'

const UserSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1),
  email: z.string().email(),
  role: z.enum(['admin', 'user']),
})

const ApiResponseSchema = <T extends z.ZodType>(dataSchema: T) =>
  z.object({ code: z.number(), message: z.string(), data: dataSchema })

describe('User API 契约', () => {
  const UserResponseSchema = ApiResponseSchema(UserSchema)

  it('GET /api/users/:id 响应应符合契约', async () => {
    const response = await fetch('http://localhost:3000/api/users/1')
    const data = await response.json()
    expect(UserResponseSchema.safeParse(data).success).toBe(true)
  })
})
```

## 五、CI 流水线集成

将所有测试层集成到 CI 流水线中：

```yaml
# .github/workflows/test-pipeline.yml
name: 测试流水线

on:
  push: { branches: [main] }
  pull_request: { branches: [main] }

jobs:
  fast-checks:
    name: 快速检查
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run lint:check
      - run: npm run typecheck
      - run: npm run type-coverage:check

  unit-tests:
    name: 单元测试
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run test:run -- --coverage
      - uses: actions/upload-artifact@v4
        with: { name: coverage, path: coverage/ }

  integration-tests:
    name: 集成测试
    needs: fast-checks
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:15
        env: { POSTGRES_PASSWORD: test }
        options: --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }
      - run: npm ci
      - run: npm run test:integration
        env: { DATABASE_URL: postgresql://postgres:test@localhost:5432/test }
```

## 六、覆盖率监控

建立覆盖率监控，跟踪质量趋势：

```typescript
// scripts/coverage-monitor.ts
import fs from 'fs'

interface CoverageReport {
  timestamp: string
  branch: string
  summary: { statements: number; branches: number; functions: number; lines: number }
  files: { path: string; coverage: number }[]
}

function generateCoverageReport(): CoverageReport {
  const coverageData = JSON.parse(
    fs.readFileSync('coverage/coverage-summary.json', 'utf-8')
  )

  return {
    timestamp: new Date().toISOString(),
    branch: process.env.GITHUB_REF_NAME || 'local',
    summary: {
      statements: coverageData.total.statements.pct,
      branches: coverageData.total.branches.pct,
      functions: coverageData.total.functions.pct,
      lines: coverageData.total.lines.pct,
    },
    files: Object.entries(coverageData)
      .filter(([key]) => key !== 'total')
      .map(([path, data]: [string, any]) => ({ path, coverage: data.lines.pct }))
      .filter((f) => f.coverage < 80),
  }
}
```

## 常见误区

1. **追求 100% 覆盖率**：100% 覆盖率不等于没有 bug。过度追求覆盖率会导致测试代码质量下降，维护成本上升。80% 是合理的基准线。

2. **测试层职责不清**：单元测试不应该依赖数据库，集成测试不应该 Mock 核心依赖。每层测试有自己的职责边界。

3. **测试代码不维护**：测试代码和生产代码一样需要维护。过时的测试比没有测试更糟糕，因为它会给出错误的信心。

4. **CI 流水线太慢**：所有测试都跑一遍会导致 CI 时间过长。应该按 PR 的变更范围选择性执行测试。

## 工程建议

1. **从最脆弱的模块开始**：不要试图一次性覆盖所有代码。先为 bug 最多、变更最频繁的模块写测试，收益最大。

2. **测试辅助工具是投资**：花时间构建 fixture、mock 工具、测试数据库管理等基础设施，能显著降低后续测试编写的门槛。

3. **覆盖率是指标不是目标**：覆盖率低说明有盲区，但覆盖率高不代表质量好。关注测试的质量而不是数量。

4. **持续改进**：定期回顾测试策略，根据项目演进调整测试层的比重和工具选择。测试体系不是一成不变的。

```yaml
    name: 单元测试

      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'npm' }

      - run: npm run test:run -- --coverage

  integration-tests:
    name: 集成测试
    needs: fast-checks

      - uses: actions/checkout@v4

```

**要点**：快速检查最先执行，快速失败；单元测试和集成测试可以并行。
