# 05 性能优化

## 场景引入

你的 TypeScript 项目有 2000 多个文件，`tsc --build` 需要 45 秒才能完成。每次保存文件后等半分钟才能看到编译结果，团队的 CI 流水线也因为编译时间过长而频繁超时。你尝试了各种"优化技巧"，但大部分都是过时的建议或不适用于你的场景。你需要系统性地理解 TypeScript 编译性能的瓶颈在哪里，以及哪些优化手段真正有效。

## 学习目标

- 理解 TypeScript 编译器的工作原理和性能瓶颈
- 掌握增量编译和项目引用等核心编译优化策略
- 了解 const enum、类型导入等影响编译速度的代码模式
- 掌握 Tree Shaking 原理和配置方法
- 学会使用 profiling 工具定位性能瓶颈

## 一、理解编译性能瓶颈

TypeScript 编译器的耗时主要在三个阶段：

```typescript
// 阶段 1：解析（Parse）— 将源码转为 AST
// 耗时与代码行数成正比，通常不是瓶颈

// 阶段 2：类型检查（Type Check）— 验证类型正确性
// 这是最耗时的阶段，复杂类型推导会指数级增加耗时

// 阶段 3：发射（Emit）— 生成 JavaScript 代码
// 包括降级语法、生成 source map

// 实测：用 --generateTrace 分析编译耗时
// tsc --generateTrace traceDir
// 然后用 chrome://tracing 加载生成的 JSON 文件
```

## 二、增量编译与项目引用

### 增量编译

```json
// tsconfig.json
{
  "compilerOptions": {
    "incremental": true,
    "tsBuildInfoFile": "./.tsbuildinfo",
    "composite": true
  }
}
```

增量编译的核心是 `.tsbuildinfo` 文件，它记录了每个文件的依赖关系和上次编译结果的哈希值。只有文件内容变化时才会重新检查。

```json
// .tsbuildinfo 内容（简化）
{
  "program": {
    "fileInfos": {
      "src/index.ts": { "version": "abc123", "signature": "def456" },
      "src/utils.ts": { "version": "ghi789", "signature": "jkl012" }
    },
    "referencedMap": {
      "src/index.ts": ["src/utils.ts"]
    }
  }
}
```

### 项目引用：拆分大型项目

当项目超过 1000 个文件时，单个 `tsconfig.json` 会导致全量编译。项目引用将代码拆分为多个子项目，只编译变化的部分：

```json
// tsconfig.json（根配置）
{
  "files": [],
  "references": [
    { "path": "./packages/core" },
    { "path": "./packages/api" },
    { "path": "./packages/web" }
  ]
}
```

```json
// packages/core/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "outDir": "./dist",
    "rootDir": "./src",
    "declaration": true,
    "declarationMap": true
  },
  "include": ["src/**/*"]
}
```

```json
// packages/api/tsconfig.json
{
  "compilerOptions": {
    "composite": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"],
  "references": [
    { "path": "../core" }
  ]
}
```

```bash
# 只编译变化的项目及其依赖
tsc --build --verbose

# 输出：
# Projects in this build:
#   * packages/core/tsconfig.json
#   * packages/api/tsconfig.json
#   * packages/web/tsconfig.json
#
# Project 'packages/core' is up to date
# Project 'packages/api' is up to date because it depends on 'packages/core'
# Building project 'packages/web'...
```

## 三、类型系统优化

复杂的类型推导是编译慢的主要原因。以下是减少类型系统开销的具体策略：

```typescript
// 1. 使用 type-only 导入，让编译器跳过运行时代码生成
import type { User, Order } from './types'
import { createOrder } from './services'

// 2. 避免过度使用条件类型
// 慢：深层嵌套的条件类型
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K] }
  : T

// 快：递归次数有限的版本
type ShallowPartial<T> = { [K in keyof T]?: T[K] extends object ? Partial<T[K]> : T[K] }

// 3. 避免大型联合类型的交叉
// 慢：100 个字段的大接口交叉
type SlowIntersection = HugeInterfaceA & HugeInterfaceB & HugeInterfaceC

// 快：用 extends 继承
interface FastExtension extends HugeInterfaceA, HugeInterfaceB, HugeInterfaceC {}

// 4. 缓存复杂类型的计算结果
// 慢：每次使用都重新计算
function process<T extends Record<string, unknown>>(
  data: T
): { [K in keyof T]: ProcessedValue<T[K]> } {
  // ...
}

// 快：用接口缓存结果类型
interface ProcessedData<T extends Record<string, unknown>> {
  [K in keyof T]: ProcessedValue<T[K]>
}
function process<T extends Record<string, unknown>>(
  data: T
): ProcessedData<T> {
  // ...
}
```

### const enum 的取舍

```typescript
// const enum：编译时内联，零运行时开销
const enum Status {
  Active = 1,
  Inactive = 2,
  Deleted = 3,
}
const s = Status.Active // 编译为: const s = 1

// 问题：
// 1. 不能用 Object.values(Status) 遍历
// 2. 不支持 isolatedModules（Babel、esbuild 等工具）
// 3. 跨项目引用时可能产生运行时错误

// 推荐：用 as const 替代
const STATUS = {
  ACTIVE: 1,
  INACTIVE: 2,
  DELETED: 3,
} as const

type Status = (typeof STATUS)[keyof typeof STATUS] // 1 | 2 | 3
```

## 四、Tree Shaking 与打包优化

Tree Shaking 的核心是让打包工具（webpack、Rollup、esbuild）识别并删除未使用的代码：

```typescript
// 不利于 Tree Shaking 的写法
// 1. 导出一个大对象
export const utils = {
  formatDate: (d: Date) => { /* ... */ },
  formatCurrency: (n: number) => { /* ... */ },
  parseUrl: (url: string) => { /* ... */ },
}
// import { utils } from './utils'  // 即使只用 utils.formatDate，整个对象都会被打包

// 利于 Tree Shaking 的写法
// 2. 独立导出每个函数
export function formatDate(d: Date): string { /* ... */ }
export function formatCurrency(n: number): string { /* ... */ }
export function parseUrl(url: string): URL { /* ... */ }
// import { formatDate } from './utils'  // 只打包 formatDate
```

```json
// package.json 中声明副作用
{
  "name": "my-lib",
  "sideEffects": false,
  "module": "dist/index.mjs",
  "main": "dist/index.cjs",
  "types": "dist/index.d.ts"
}
```

```typescript
// webpack.config.js
module.exports = {
  mode: 'production',
  optimization: {
    usedExports: true,    // 标记未使用的导出
    minimize: true,        // 删除未使用的代码
    concatenateModules: true, // 模块合并（作用域提升）
  },
}
```

## 五、Profiling：定位真实瓶颈

不要凭感觉优化，用工具找到真正的瓶颈：

```typescript
// Node.js 内置 profiler
// --cpu-prof 生成 CPU 分析文件
// node --cpu-prof --cpu-prof-dir=./profiling dist/index.js

// 用 0x 生成火焰图
// npx 0x dist/index.js

// 手动计时关键操作
import { performance, PerformanceObserver } as perf_hooks

const obs = new PerformanceObserver((items) => {
  items.getEntries().forEach((entry) => {
    console.log(`${entry.name}: ${entry.duration.toFixed(2)}ms`)
  })
})
obs.observe({ entryTypes: ['measure'] })

function benchmark(name: string, fn: () => void, iterations = 1000) {
  performance.mark(`${name}-start`)
  for (let i = 0; i < iterations; i++) {
    fn()
  }
  performance.mark(`${name}-end`)
  performance.measure(name, `${name}-start`, `${name}-end`)
}

// 使用
benchmark('type-check', () => {
  // 模拟类型检查操作
  type ComplexType = DeepPartial<ApiResponse<UserProfile>>[]
})
```

### TypeScript 编译器 API 性能分析

```typescript
import ts from 'typescript'

// 用 Compiler API 分析编译过程
function analyzeCompilation(configPath: string) {
  const config = ts.readConfigFile(configPath, ts.sys.readFile)
  const parsedConfig = ts.parseJsonConfigFileContent(
    config.config,
    ts.sys,
    './'
  )
  
  const start = performance.now()
  const program = ts.createProgram({
    rootNames: parsedConfig.fileNames,
    options: parsedConfig.options,
  })
  
  const diagnostics = [
    ...program.getGlobalDiagnostics(),
    ...program.getSyntacticDiagnostics(),
    ...program.getSemanticDiagnostics(),
  ]
  
  const elapsed = performance.now() - start
  console.log(`Compilation: ${elapsed.toFixed(2)}ms`)
  console.log(`Files: ${program.getSourceFiles().length}`)
  console.log(`Diagnostics: ${diagnostics.length}`)
  
  return { program, diagnostics, elapsed }
}
```

## 常见误区

1. **盲目开启 strict 模式**：strict 模式会增加类型检查的计算量，大型遗留项目应逐步开启而不是一步到位
2. **过度使用泛型**：深层嵌套的泛型会让类型推导指数级变慢，必要时用具体类型替代
3. **忽略 declaration 文件生成**：`declaration: true` 会显著增加编译时间，库项目才需要开启
4. **把所有优化都用上**：const enum、条件类型、模板字面量类型都有适用场景，不是所有地方都需要

## 工程建议

1. **项目超过 500 文件就启用项目引用**：按业务域拆分（core、api、web、admin），每个子项目独立编译
2. **CI 中使用 `tsc --build`**：配合 `.tsbuildinfo` 缓存，只编译变化的部分，配合 `--force` 做全量构建
3. **用 type-only import**：所有只用于类型的导入都用 `import type`，减少编译器的工作量
4. **定期审查编译耗时**：在 CI 中记录 `tsc --extendedDiagnostics` 的输出，设置编译时间告警阈值

## 小结

本课从 TypeScript 编译器的工作原理出发，介绍了编译性能瓶颈的定位方法，以及增量编译、项目引用、类型优化、Tree Shaking 等核心优化策略。核心原则：**先测量再优化，用数据驱动决策，不要凭直觉做性能调优**。

## 参考答案

### 练习一

**思路**：运行 `tsc --extendedDiagnostics`，重点关注 Check time 占总时间的比例。

**答案**：
```bash
tsc --extendedDiagnostics 2>&1 | grep -E "time|Files|Types|Instantiations"
```

分析方法：
- 如果 Check time 占比 > 70%：瓶颈在类型检查，优化方向是简化复杂类型、使用 `import type`
- 如果 Parse time 占比 > 30%：文件太多，优化方向是项目引用拆分
- 如果 I/O Read time 占比 > 20%：磁盘慢或文件太多，考虑排除不需要的文件

常见优化建议：
1. 检查是否有不必要的 `.d.ts` 文件被包含，调整 `include`/`exclude` 配置
2. 将 `skipLibCheck: true` 加入 tsconfig，跳过第三方库的类型检查
3. 使用 `import type` 导入只用于类型的模块

**要点**：
- `Instantiations` 数值高说明泛型推导复杂，考虑简化泛型
- `Symbols` 和 `Types` 数值高说明类型系统负担重
- 每次优化后重新测量，用数据验证效果

### 练习二

**思路**：创建两个 tsconfig 文件，core 配置 composite，app 通过 references 引用 core。

**答案**：
```json
// tsconfig.core.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "strict": true,
    "composite": true,
    "outDir": "./dist/core",
    "rootDir": "./src/core",
    "declaration": true,
    "declarationMap": true
  },
  "include": ["src/core/**/*"]
}
```

```json
// tsconfig.app.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "strict": true,
    "composite": true,
    "outDir": "./dist/app",
    "rootDir": "./src/app"
  },
  "include": ["src/app/**/*"],
  "references": [
    { "path": "./tsconfig.core.json" }
  ]
}
```

```json
// tsconfig.json（根配置）
{
  "files": [],
  "references": [
    { "path": "./tsconfig.core.json" },
    { "path": "./tsconfig.app.json" }
  ]
}
```

```bash
# 构建命令
tsc --build tsconfig.core.json tsconfig.app.json
```

**要点**：
- `composite: true` 是项目引用的必要条件
- `declaration: true` 让下游项目可以引用类型
- 根配置的 `files: []` 防止根目录被直接编译

### 练习三

**思路**：将默认导出的大对象改为独立的命名导出。

**答案**：
```typescript
// utils.ts
export function add(a: number, b: number): number {
  return a + b
}

export function subtract(a: number, b: number): number {
  return a - b
}

export function multiply(a: number, b: number): number {
  return a * b
}

export function divide(a: number, b: number): number {
  if (b === 0) throw new Error('Division by zero')
  return a / b
}

// package.json 中添加
// { "sideEffects": false }
```

```typescript
// 使用方
import { add } from './utils'
// 打包时 subtract、multiply、divide 会被 Tree Shaking 移除
```

**要点**：
- 命名导出比默认导出更利于 Tree Shaking
- `sideEffects: false` 告诉打包工具整个模块没有副作用
- 函数内部不要有副作用（修改全局变量、操作 DOM），否则 Tree Shaking 不会移除
