# 02 日志与可观测性

## 场景引入

凌晨三点，线上告警响了。你打开监控面板，看到错误率飙升，但 `console.log` 输出的日志全是 `Error: something went wrong`——没有请求 ID、没有用户信息、没有调用链路。你花了两个小时在海量日志里捞线索，最终发现是一个第三方支付接口超时导致的连锁反应。如果日志里有 trace ID 和结构化上下文，定位时间可以缩短到五分钟。

## 学习目标

- 理解结构化日志相比 `console.log` 的本质优势
- 使用 pino 实现生产级结构化日志
- 设计日志级别策略，避免日志风暴或日志缺失
- 通过 Trace ID 实现跨服务请求追踪
- 用 OpenTelemetry 将日志、指标、链路追踪统一为可观测性体系

## 一、结构化日志：从文本到 JSON

传统日志是人类可读的文本，但生产环境的日志消费者是机器。结构化日志输出 JSON，让日志平台（ELK、Loki、Datadog）可以高效索引和查询。

```typescript
// 反面教材：console.log
console.log(`User ${userId} created order ${orderId}`)
// 输出: User u_123 created order o_456
// 问题：无法按 userId 或 orderId 过滤

// 正确做法：结构化日志
import pino from 'pino'

const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  formatters: {
    level(label: string) {
      return { level: label }
    }
  },
  timestamp: pino.stdTimeFunctions.isoTime,
})

logger.info({ userId: 'u_123', orderId: 'o_456' }, 'Order created')
// 输出: {"level":"info","time":"2025-01-15T10:30:00.000Z","userId":"u_123","orderId":"o_456","msg":"Order created"}
```

### pino 子 Logger：携带上下文

```typescript
function createContextLogger(context: Record<string, unknown>) {
  return logger.child(context)
}

// 在请求处理中
app.use((req, res, next) => {
  req.log = createContextLogger({
    requestId: req.headers['x-request-id'] || crypto.randomUUID(),
    method: req.method,
    url: req.url,
  })
  next()
})

// 业务代码中
async function handleCreateOrder(req: Request) {
  req.log.info({ userId: req.user.id }, 'Processing order creation')
  
  const order = await createOrder(req.body)
  
  req.log.info({ orderId: order.id, total: order.total }, 'Order created successfully')
}
```

## 二、日志级别策略

日志级别不是随便选的，它决定了生产环境能输出什么信息。级别设太高会丢失排查线索，设太低会产生日志风暴。

```typescript
// 日志级别定义与使用场景
const LOG_LEVELS = {
  fatal: 60,  // 进程即将崩溃，必须立即处理
  error: 50,  // 操作失败，需要人工介入
  warn:  40,  // 异常但可恢复，可能是潜在问题
  info:  30,  // 关键业务事件，正常流程的里程碑
  debug: 20,  // 开发调试信息，生产环境默认关闭
  trace: 10,  // 最详细的追踪信息，仅在排查特定问题时开启
}

// 实际使用示例
function processPayment(order: Order, amount: number): Result<Payment, AppError> {
  logger.info({ orderId: order.id, amount }, 'Payment processing started')
  
  const result = gateway.charge(order.paymentMethod, amount)
  
  if (!result.ok) {
    logger.error({
      orderId: order.id,
      errorCode: result.error.code,
      gateway: 'stripe',
    }, 'Payment failed')
    return result
  }
  
  // 调试信息：生产环境默认不输出
  logger.debug({
    orderId: order.id,
    transactionId: result.value.id,
    processingTimeMs: result.value.processingTime,
  }, 'Payment gateway response details')
  
  return result
}

// 生产环境配置
const logger = pino({
  level: process.env.NODE_ENV === 'production' ? 'info' : 'debug',
})
```

## 三、Trace ID：请求全链路追踪

一个请求从 API 网关到数据库可能经过多个服务，Trace ID 把所有日志串联起来：

```typescript
import { AsyncLocalStorage } from 'async_hooks'

// 用 AsyncLocalStorage 在整个请求生命周期传播上下文
interface RequestContext {
  traceId: string
  spanId: string
  userId?: string
}

const requestContext = new AsyncLocalStorage<RequestContext>()

// 中间件：为每个请求创建上下文
function traceMiddleware(req: Request, res: Response, next: NextFunction) {
  const traceId = (req.headers['x-trace-id'] as string) || crypto.randomUUID()
  const spanId = crypto.randomUUID().slice(0, 8)
  
  requestContext.run({ traceId, spanId }, () => {
    // 设置响应头，方便客户端关联
    res.setHeader('x-trace-id', traceId)
    next()
  })
}

// 获取当前上下文的日志函数
function getLogger() {
  const ctx = requestContext.getStore()
  if (!ctx) return logger
  return logger.child({ traceId: ctx.traceId, spanId: ctx.spanId })
}

// 业务代码中使用
async function createOrder(input: CreateOrderInput): Promise<Order> {
  const log = getLogger()
  log.info({ items: input.items.length }, 'Creating order')
  
  const order = await db.orders.create(input)
  log.info({ orderId: order.id }, 'Order created in database')
  
  await sendConfirmationEmail(order)
  log.info({ orderId: order.id }, 'Confirmation email sent')
  
  return order
}
```

## 四、OpenTelemetry：统一可观测性

日志只是可观测性的三分之一。OpenTelemetry（OTel）将日志（Logs）、指标（Metrics）、链路追踪（Traces）统一为一套标准：

```typescript
import { NodeSDK } from '@opentelemetry/sdk-node'
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http'
import { OTLPMetricExporter } from '@opentelemetry/exporter-metrics-otlp-http'
import { PeriodicExportingMetricReader } from '@opentelemetry/sdk-metrics'

// 初始化 OpenTelemetry SDK
const sdk = new NodeSDK({
  serviceName: 'order-service',
  traceExporter: new OTLPTraceExporter({
    url: 'http://otel-collector:4318/v1/traces',
  }),
  metricReader: new PeriodicExportingMetricReader({
    exporter: new OTLPMetricExporter({
      url: 'http://otel-collector:4318/v1/metrics',
    }),
    exportIntervalMillis: 15000,
  }),
  instrumentations: [
    getNodeAutoInstrumentations({
      '@opentelemetry/instrumentation-http': { enabled: true },
      '@opentelemetry/instrumentation-express': { enabled: true },
      '@opentelemetry/instrumentation-pg': { enabled: true },
    }),
  ],
})

sdk.start()
```

### 自定义 Span：追踪业务操作

```typescript
import { trace, SpanStatusCode } from '@opentelemetry/api'

const tracer = trace.getTracer('order-service')

async function processOrder(orderId: string): Promise<void> {
  // 创建一个子 Span
  return tracer.startActiveSpan('processOrder', async (span) => {
    try {
      span.setAttribute('order.id', orderId)
      
      // 子操作也可以有自己的 Span
      const order = await tracer.startActiveSpan('fetchOrder', async (childSpan) => {
        try {
          const result = await db.orders.findById(orderId)
          childSpan.setAttribute('order.total', result.total)
          return result
        } finally {
          childSpan.end()
        }
      })
      
      await tracer.startActiveSpan('chargePayment', async (childSpan) => {
        try {
          await paymentGateway.charge(order)
          childSpan.setAttribute('payment.provider', 'stripe')
        } catch (error) {
          childSpan.setStatus({ code: SpanStatusCode.ERROR, message: String(error) })
          throw error
        } finally {
          childSpan.end()
        }
      })
      
      span.setStatus({ code: SpanStatusCode.OK })
    } catch (error) {
      span.setStatus({ code: SpanStatusCode.ERROR, message: String(error) })
      throw error
    } finally {
      span.end()
    }
  })
}
```

## 五、Metrics：关键业务指标

```typescript
import { metrics } from '@opentelemetry/api'

const meter = metrics.getMeter('order-service')

// 计数器：订单创建总数
const orderCounter = meter.createCounter('orders.created', {
  description: 'Total number of orders created',
})

// 直方图：订单处理耗时
const orderDuration = meter.createHistogram('order.processing.duration', {
  description: 'Time to process an order in milliseconds',
  unit: 'ms',
})

// 仪表盘：当前活跃连接数
const activeConnections = meter.createUpDownGauge('connections.active', {
  description: 'Number of active connections',
})

// 在业务代码中使用
async function handleCreateOrder(req: Request) {
  const startTime = performance.now()
  
  try {
    const order = await createOrder(req.body)
    
    orderCounter.add(1, {
      'order.type': order.type,
      'payment.method': order.paymentMethod,
    })
    
    return order
  } finally {
    const duration = performance.now() - startTime
    orderDuration.record(duration, { 'order.type': req.body.type })
  }
}
```

## 常见误区

1. **日志里打印敏感信息**：用户密码、Token、身份证号直接出现在日志中，应建立脱敏规则
2. **所有操作都打 info 日志**：数据库查询、缓存命中这类高频操作应该用 debug，否则会产生日志风暴
3. **只看日志不看指标**：日志告诉你"发生了什么"，指标告诉你"趋势如何"，两者缺一不可
4. **Trace ID 不传播**：服务间调用时丢掉了上游的 Trace ID，导致链路断裂无法串联

## 工程建议

1. **日志格式在项目启动时统一**：选择 pino 或 winston，定义好字段规范（timestamp、level、message、context），不要让团队成员各自为政
2. **为日志建立分级存储**：error 存 30 天，info 存 7 天，debug 不持久化，用日志平台的 retention 策略控制成本
3. **健康检查端点不打日志**：`GET /health` 每 10 秒调用一次，如果打 info 日志会产生大量无用输出
4. **用 correlation ID 串联日志和 Sentry**：同一个 traceId 同时出现在日志和 Sentry 错误报告中，方便交叉排查

## 小结

本课从 `console.log` 的局限性出发，介绍了结构化日志、日志级别策略、Trace ID 传播和 OpenTelemetry 统一可观测性体系。核心理念：**可观测性不是事后加的日志，而是从架构设计时就内嵌的系统能力**。

## 参考答案

### 练习一

**思路**：按请求生命周期逐个节点设计日志，每个节点包含足以排查问题的上下文。

**答案**：
```typescript
// 用户注册流程日志规范
// 1. 收到注册请求 — info
logger.info({ email: input.email, source: 'web' }, 'Registration request received')

// 2. 参数校验失败 — warn
logger.warn({ email: input.email, errors: validationErrors }, 'Registration validation failed')

// 3. 邮箱已存在 — warn（不是 error，这是正常业务分支）
logger.warn({ email: input.email }, 'Registration rejected: email already exists')

// 4. 数据库写入 — debug
logger.debug({ email: input.email }, 'Creating user in database')

// 5. 发送验证邮件 — info
logger.info({ userId: user.id, email: user.email }, 'Verification email sent')

// 6. 邮件发送失败 — error（但不影响注册成功）
logger.error({ userId: user.id, err: error }, 'Failed to send verification email')

// 7. 注册完成 — info
logger.info({ userId: user.id, duration: elapsed }, 'Registration completed')
```

**要点**：
- 邮箱已存在是 warn 不是 error，这是正常业务逻辑
- 邮件发送失败是 error，因为这需要人工介入
- 每条日志携带标识符（email 或 userId），方便按用户查询

### 练习二

**思路**：用 AsyncLocalStorage 存储请求上下文，中间件在请求开始时创建上下文，getLogger 从 store 中读取。

**答案**：
```typescript
import { AsyncLocalStorage } from 'async_hooks'
import pino from 'pino'
import { Request, Response, NextFunction } from 'express'

const baseLogger = pino({ level: 'info' })

interface TraceContext {
  traceId: string
}

const traceStore = new AsyncLocalStorage<TraceContext>()

export function traceMiddleware(req: Request, res: Response, next: NextFunction) {
  const traceId = (req.headers['x-request-id'] as string) || crypto.randomUUID()
  res.setHeader('x-trace-id', traceId)
  traceStore.run({ traceId }, () => next())
}

export function getLogger() {
  const ctx = traceStore.getStore()
  if (ctx) {
    return baseLogger.child({ traceId: ctx.traceId })
  }
  return baseLogger
}
```

**要点**：
- 优先从请求头获取 traceId，支持上游服务传递
- `traceStore.run()` 确保整个请求处理链都在同一个上下文中
- 没有 traceId 时返回基础 logger，避免业务代码报错

### 练习三

**思路**：用 `tracer.startActiveSpan` 创建 Span，设置查询属性，记录结果数量，在 finally 中结束 Span。

**答案**：
```typescript
import { trace, SpanStatusCode } from '@opentelemetry/api'

const tracer = trace.getTracer('product-service')

async function searchProducts(keyword: string, category?: string) {
  return tracer.startActiveSpan('searchProducts', async (span) => {
    try {
      span.setAttribute('search.keyword', keyword)
      if (category) span.setAttribute('search.category', category)
      
      const results = await db.products.search({ keyword, category })
      
      span.setAttribute('search.results_count', results.length)
      span.setStatus({ code: SpanStatusCode.OK })
      
      return results
    } catch (error) {
      span.setStatus({
        code: SpanStatusCode.ERROR,
        message: error instanceof Error ? error.message : 'Unknown error',
      })
      throw error
    } finally {
      span.end()
    }
  })
}
```

**要点**：
- Span 属性用点分隔命名空间（`search.keyword`），遵循 OpenTelemetry 语义规范
- `finally` 中调用 `span.end()` 确保即使异常也能正确关闭 Span
- 结果数量作为属性记录，方便在 Grafana 中按结果数分析查询质量
