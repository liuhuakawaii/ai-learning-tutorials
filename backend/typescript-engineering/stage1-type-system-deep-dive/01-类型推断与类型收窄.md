# 01 - 类型推断与类型收窄

很多工程师写 TypeScript 时习惯到处手动标注类型，觉得"标注越多越安全"。但实际上，TypeScript 的类型推断已经能帮你做大量工作，过度标注反而会丢失精度。更常见的问题是：代码明明跑起来没问题，但 TypeScript 报错说某个属性不存在——你不知道该用 `as` 强转还是应该写类型守卫。

这节课要搞清楚两件事：TypeScript 什么时候帮你推断类型，以及你怎么帮它在运行时精确收窄类型。

## 类型推断的三种机制

### 基础推断：let 和 const 的区别

```typescript
let userName = "张三"          // 推断为 string
const userId = "abc-123"      // 推断为 "abc-123"（字面量类型）
let retryCount = 3            // 推断为 number
const maxRetries = 5          // 推断为 5（字面量类型）
```

`const` 声明的变量不能重新赋值，所以 TypeScript 推断为最窄的字面量类型。`let` 声明的变量可能被重新赋值，所以推断为宽泛的基础类型。

### 最佳公共类型

当 TypeScript 需要从多个表达式推断一个公共类型时，它会选择"最佳公共类型"：

```typescript
const orderItems = [
  { productId: "p1", quantity: 2 },
  { productId: "p2", quantity: 3, discount: 0.1 },
]
// 推断为 { productId: string; quantity: number; discount?: number }[]
```

注意 `discount` 变成了可选属性，因为第一个元素没有这个字段。这在处理 API 响应合并时经常遇到——如果你期望所有元素结构一致，这种推断可能掩盖数据不一致的问题。

### 上下文类型推断

当表达式出现在有明确类型注解的位置时，TypeScript 会从上下文推断类型：

```typescript
type OrderEventHandler = (event: { orderId: string; status: string }) => void

const handleOrder: OrderEventHandler = (event) => {
  // event 自动推断为 { orderId: string; status: string }
  console.log(event.orderId, event.status)
}
```

你不需要在回调参数上标注类型，TypeScript 从 `OrderEventHandler` 的定义推断出来了。

## 类型收窄：让编译器自己判断

类型推断解决的是"TypeScript 帮你写类型"的问题。类型收窄解决的是"TypeScript 帮你在每个分支里精确判断类型"的问题。

### typeof 守卫

最基础的收窄方式，但只能判断基础类型：

```typescript
function formatId(id: string | number): string {
  if (typeof id === "string") {
    return id.toUpperCase()
  }
  return id.toFixed(0)
}
```

一个历史包袱：`typeof null === "object"`。所以如果你要判断对象类型，`typeof` 不够用。

### instanceof 守卫

用于判断类的实例：

```typescript
class OrderNotFoundError {
  constructor(public orderId: string) {}
}

class PaymentDeclinedError {
  constructor(public reason: string, public retryable: boolean) {}
}

function formatError(error: OrderNotFoundError | PaymentDeclinedError): string {
  if (error instanceof OrderNotFoundError) {
    return `订单 ${error.orderId} 不存在`
  }
  return `支付被拒绝: ${error.reason}${error.retryable ? "，可重试" : ""}`
}
```

`instanceof` 的限制是只能用于 class，接口（interface）没有运行时存在。

### in 操作符

当你需要区分对象类型但没有 class 时：

```typescript
interface EmailNotification { type: "email"; to: string; subject: string }
interface SmsNotification { type: "sms"; phone: string; message: string }

function send(notification: EmailNotification | SmsNotification) {
  if ("subject" in notification) {
    sendEmail(notification.to, notification.subject)
  } else {
    sendSms(notification.phone, notification.message)
  }
}
```

### 自定义类型守卫

内置守卫不够用时，比如你从 API 拿到的数据类型是 `unknown`，需要自己写判断逻辑：

```typescript
interface OrderItem {
  productId: string
  quantity: number
  unitPrice: number
}

function isOrderItem(value: unknown): value is OrderItem {
  return (
    typeof value === "object" && value !== null &&
    "productId" in value && "quantity" in value && "unitPrice" in value &&
    typeof (value as OrderItem).productId === "string" &&
    typeof (value as OrderItem).quantity === "number" &&
    typeof (value as OrderItem).unitPrice === "number"
  )
}
```

关键在 `value is OrderItem` 这个类型谓词。它告诉 TypeScript：当这个函数返回 `true` 时，参数的类型就是 `OrderItem`。如果只写返回 `boolean`，调用方无法收窄类型。

### 判别联合：最实用的收窄模式

上面几种收窄方式都有局限。判别联合是为收窄而设计的数据结构：

```typescript
type PaymentResult =
  | { status: "success"; transactionId: string; paidAt: Date }
  | { status: "failed"; errorCode: string; retryable: boolean }
  | { status: "pending"; estimatedCompletion: Date }

function handlePayment(result: PaymentResult): string {
  switch (result.status) {
    case "success":
      return `支付成功，交易号 ${result.transactionId}`
    case "failed":
      return `支付失败: ${result.errorCode}${result.retryable ? "，可重试" : ""}`
    case "pending":
      return `支付处理中，预计 ${result.estimatedCompletion.toISOString()} 完成`
    default: {
      const _exhaustive: never = result
      return _exhaustive
    }
  }
}
```

`default` 分支里的 `never` 类型确保你处理了所有变体——如果以后新增一个 `status: "refunded"` 但忘记更新函数，TypeScript 会在编译时报错。

## const assertions 和 satisfies

```typescript
const ORDER_STATUS = {
  PENDING: "pending", PAID: "paid", SHIPPED: "shipped", CANCELLED: "cancelled",
} as const

type OrderStatus = (typeof ORDER_STATUS)[keyof typeof ORDER_STATUS]
// "pending" | "paid" | "shipped" | "cancelled"
```

`as const` 让 TypeScript 把每个属性推断为字面量类型而不是 `string`。配合 `keyof typeof` 可以从常量对象自动生成联合类型。

```typescript
type RouteConfig = { path: string; method: "GET" | "POST" | "PUT" | "DELETE"; auth?: boolean }

const routes = {
  getUser: { path: "/api/users/:id", method: "GET", auth: true },
  healthCheck: { path: "/health", method: "GET" },
} satisfies Record<string, RouteConfig>

// routes.getUser.method 的类型是 "GET"（字面量），不是 string
```

`satisfies` 和类型注解的区别：类型注解会把类型拓宽为 `RouteConfig`，丢失字面量信息；`satisfies` 只在赋值时做兼容性检查，不改变变量的推断类型。

## 什么时候用 as，什么时候收窄

- **优先用类型收窄**：`typeof`、`instanceof`、`in`、判别联合
- **只在别无选择时用 `as`**：比如操作第三方库返回的不准确类型
- **永远不要用 `as any`**：这等于关闭了类型检查

## 常见陷阱

1. **类型守卫只在同步代码中有效**：`await` 之后不能假设之前的收窄仍然成立
2. **数组的 `filter` 不自动收窄**：`arr.filter(x => x != null)` 的结果类型仍然包含 `null`，必须传入类型守卫函数
3. **`in` 操作符在属性名重叠时不可靠**：如果两个接口都有 `type` 字段，`"type" in obj` 无法区分

## 练习

### 练习一：实现 isNonNullable 守卫

编写一个 `isNonNullable<T>(value: T): value is NonNullable<T>` 类型守卫函数，用它过滤数组中的 `null` 和 `undefined`。对比直接用 `filter(x => x != null)` 的类型结果差异。

### 练习二：Result 类型与穷尽检查

设计一个 `Result<T, E>` 判别联合类型，包含 `success` 和 `failure` 两种变体。实现一个 `match` 函数，接收 `Result` 和两个回调（成功/失败），确保 `default` 分支的穷尽检查生效。

### 练习三：用 satisfies 设计路由表

用 `satisfies` 设计一个类型安全的 API 路由表。每个路由有 `method`（GET/POST/PUT/DELETE）、`path` 和可选的 `auth` 字段。要求 `routes.getUser.method` 的类型是 `"GET"` 而不是 `string`。

## 参考答案

### 练习一

```typescript
function isNonNullable<T>(value: T): value is NonNullable<T> {
  return value !== null && value !== undefined
}

const apiResponse = [1, null, "订单已创建", undefined, 42, null]
const cleaned = apiResponse.filter(isNonNullable)
// 类型是 (string | number)[]

// 不用类型守卫：结果类型仍包含 null
const stillDirty = apiResponse.filter(x => x != null)
// 类型是 (string | number | null | undefined)[]
```

### 练习二

```typescript
type Result<T, E = Error> =
  | { kind: "success"; value: T }
  | { kind: "failure"; error: E }

function match<T, E, U>(
  result: Result<T, E>,
  onSuccess: (value: T) => U,
  onFailure: (error: E) => U
): U {
  switch (result.kind) {
    case "success": return onSuccess(result.value)
    case "failure": return onFailure(result.error)
    default: {
      const _exhaustive: never = result
      throw new Error(`未处理的变体: ${JSON.stringify(_exhaustive)}`)
    }
  }
}
```

### 练习三

```typescript
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE"
type RouteEntry = { method: HttpMethod; path: string; auth?: boolean }

const routes = {
  getUser: { method: "GET", path: "/api/users/:id", auth: true },
  createUser: { method: "POST", path: "/api/users", auth: true },
  healthCheck: { method: "GET", path: "/health" },
} satisfies Record<string, RouteEntry>

// method 类型是 "GET"，不是 string
const method = routes.getUser.method
```
