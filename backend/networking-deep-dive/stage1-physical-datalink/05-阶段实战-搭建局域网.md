# 阶段实战：搭建一个小型局域网并抓包分析

## 任务目标

在这个实战中，你要搭建一个包含 3 台设备的小型局域网，观察交换机的学习过程、ARP 交互、广播行为，并用 Wireshark 抓包验证。

## 网络拓扑

```
设备A (192.168.1.10)  ←→  交换机  ←→  设备B (192.168.1.20)
                           ↑
                       设备C (192.168.1.30)
```

可以用以下方式模拟：
- 3 个虚拟机（VirtualBox/VMware）
- 或 1 台电脑 + 2 个虚拟机
- 或 Docker 容器 + macvlan 网络

## 步骤一：配置 IP 地址

确保三台设备在同一子网：

```bash
# 设备A
sudo ip addr add 192.168.1.10/24 dev eth0

# 设备B
sudo ip addr add 192.168.1.20/24 dev eth0

# 设备C
sudo ip addr add 192.168.1.30/24 dev eth0
```

验证连通性：
```bash
# 从设备A ping 设备B
ping -c 3 192.168.1.20
```

## 步骤二：观察交换机 MAC 学习

如果你有管理型交换机，登录管理界面查看 MAC 地址表。

如果没有，用 Linux 的 `bridge` 命令创建软件交换机：

```bash
# 创建网桥
sudo ip link add br0 type bridge
sudo ip link set eth0 master br0
sudo ip link set eth1 master br0
sudo ip link set br0 up

# 查看 MAC 地址表
bridge fdb show
```

## 步骤三：抓包观察 ARP 交互

在设备C 上抓包，观察设备A 和设备B 通信时的 ARP 行为：

```bash
# 在设备C 上抓包
sudo tcpdump -i eth0 arp -nn

# 在设备A 上 ping 设备B
ping -c 1 192.168.1.20
```

设备C 会看到：
1. 设备A 的 ARP Request（广播，所有设备都能收到）
2. 设备B 的 ARP Reply（单播，只有设备A 收到）

为什么设备C 能看到 ARP Request 但看不到 ARP Reply？因为 ARP Request 是广播，ARP Reply 是单播。

## 步骤四：观察广播风暴（安全环境）

**警告**：这个实验只在隔离的测试环境中进行，不要在生产网络中操作。

在设备A 上创建一个环路，观察广播风暴：

```bash
# 创建两个虚拟网桥形成环路
sudo ip link add br0 type bridge
sudo ip link add br1 type bridge
sudo ip link set eth0 master br0
sudo ip link set eth1 master br1

# 连接两个网桥形成环路
sudo ip link add veth0 type veth peer name veth1
sudo ip link set veth0 master br0
sudo ip link set veth1 master br1
sudo ip link set veth0 up
sudo ip link set veth1 up
```

观察 CPU 使用率和网络流量——广播风暴会让 CPU 飙升。

## 步骤五：用 Wireshark 分析完整会话

1. 在设备A 上启动 Wireshark 抓包
2. 从设备A 访问设备B 上的一个 HTTP 服务
3. 停止抓包，分析整个会话的帧序列

你应该能看到：
1. ARP Request/Reply（获取设备B 的 MAC）
2. TCP 三次握手（SYN, SYN-ACK, ACK）
3. HTTP 请求/响应
4. TCP 四次挥手

## 阶段总结

通过这个实战，你应该理解了：

1. **交换机如何学习 MAC 地址**：通过观察帧的源 MAC
2. **ARP 如何工作**：广播请求，单播回复
3. **广播域是什么**：同一 VLAN 内所有设备都能收到广播
4. **环路会导致什么**：广播风暴，网络瘫痪
5. **帧的完整生命周期**：从应用层数据到物理信号

### 练习二：回答问题

1. 如果设备A 和设备B 在不同子网（如 192.168.1.0/24 和 192.168.2.0/24），ARP 行为会有什么不同？
2. 为什么 ARP Reply 是单播而不是广播？
3. 交换机的 MAC 地址表有大小限制吗？如果满了会怎样？

## 参考答案

### 练习一

帧序列图示例：
```
设备A                    交换机                    设备B
  |                       |                         |
  | ARP Request (广播)    |                         |
  | --------------------> | -------------------->   |
  |                       |                         |
  | ARP Reply (单播)      |                         |
  | <-------------------- | <--------------------   |
  |                       |                         |
  | TCP SYN               |                         |
  | --------------------> | -------------------->   |
  |                       |                         |
  | TCP SYN-ACK           |                         |
  | <-------------------- | <--------------------   |
  |                       |                         |
  | HTTP GET              |                         |
  | --------------------> | -------------------->   |
  |                       |                         |
  | HTTP Response         |                         |
  | <-------------------- | <--------------------   |
```

### 练习二

1. **不同子网**：设备A 会先查路由表，发现目标在不同子网，于是 ARP 请求网关的 MAC，而不是设备B 的 MAC。帧的目的 MAC 是网关，不是设备B。

2. **ARP Reply 为什么是单播**：因为 ARP Request 中已经包含了发送方的 MAC 地址，Reply 直接发给发送方即可，不需要广播。

3. **MAC 地址表满了**：交换机会退化为集线器模式，所有帧都会泛洪到所有端口。这会导致性能下降和安全隐患。典型的 CAM 表大小是 8K-64K 条目。

**常见错误**：以为交换机"记住"了所有设备。实际上 MAC 地址表有老化时间（通常 5 分钟），如果设备长时间不通信，条目会被删除。
