# 阶段实战：排查三个真实生产环境的网络问题

## 任务目标

在这个实战中，你要用前面学到的工具和方法，排查三个真实生产环境的网络问题。每个问题都有具体的症状、排查过程和解决方案。

## 问题一：Web 服务响应慢

### 症状

用户反馈网站加载慢，首页加载时间从 2 秒变成 10 秒。

### 排查过程

**第一步：确认问题**

```bash
# 测量响应时间
curl -w "@curl-format.txt" -o /dev/null -s http://example.com

# curl-format.txt 内容:
#     time_namelookup:  %{time_namelookup}\n
#        time_connect:  %{time_connect}\n
#     time_appconnect:  %{time_appconnect}\n
#    time_pretransfer:  %{time_pretransfer}\n
#       time_redirect:  %{time_redirect}\n
#  time_starttransfer:  %{time_starttransfer}\n
#                     ----------\n
#          time_total:  %{time_total}\n
```

输出示例：
```
    time_namelookup:  0.012
       time_connect:  0.034
    time_appconnect:  0.156
   time_pretransfer:  0.156
      time_redirect:  0.000
 time_starttransfer:  8.234
                    ----------
         time_total:  8.234
```

分析：DNS 和连接都很快，但 `time_starttransfer` 很高，说明服务器处理慢。

**第二步：检查服务器状态**

```bash
# 查看服务器负载
ssh server "uptime"

# 查看 CPU 使用率
ssh server "top -bn1 | head -5"

# 查看内存使用
ssh server "free -h"

# 查看磁盘 I/O
ssh server "iostat -x 1 5"
```

**第三步：检查网络路径**

```bash
# 测量延迟
ping -c 10 server_ip

# 查看路径
traceroute server_ip

# 检查丢包
ping -c 100 server_ip | tail -1
```

**第四步：抓包分析**

```bash
# 在服务器上抓包
sudo tcpdump -i eth0 port 80 -w slow.pcap

# 在客户端访问
curl http://example.com

# 分析抓包结果
# 观察是否有重传、窗口大小、延迟
```

### 根因

服务器数据库查询慢，导致 HTTP 响应延迟。

### 解决方案

1. 优化数据库查询
2. 添加缓存
3. 增加服务器资源

## 问题二：间歇性连接失败

### 症状

用户反馈网站间歇性无法访问，有时正常，有时超时。

### 排查过程

**第一步：确认问题**

```bash
# 持续测试
for i in {1..100}; do
  curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://example.com
  sleep 1
done
```

输出示例：
```
200 0.234
200 0.256
000 10.001
200 0.245
000 10.002
```

分析：间歇性超时，成功时响应很快。

**第二步：检查服务器状态**

```bash
# 查看服务器连接数
ssh server "ss -t | wc -l"

# 查看 SYN_RECV 状态
ssh server "ss -t state syn-recv | wc -l"

# 查看 TIME_WAIT 状态
ssh server "ss -t state time-wait | wc -l"
```

**第三步：检查防火墙**

```bash
# 查看防火墙规则
ssh server "iptables -L -n -v"

# 查看连接跟踪表
ssh server "cat /proc/net/nf_conntrack | wc -l"

# 查看连接跟踪限制
ssh server "sysctl net.netfilter.nf_conntrack_max"
```

**第四步：抓包分析**

```bash
# 在服务器上抓包
sudo tcpdump -i eth0 port 80 -w intermittent.pcap

# 分析抓包结果
# 观察是否有 RST、丢包、重传
```

### 根因

连接跟踪表满，导致新连接被丢弃。

### 解决方案

```bash
# 增大连接跟踪表
sudo sysctl -w net.netfilter.nf_conntrack_max=262144

# 缩短连接跟踪超时
sudo sysctl -w net.netfilter.nf_conntrack_tcp_timeout_established=300
```

## 问题三：跨机房延迟高

### 症状

北京用户访问上海服务器，延迟 100ms，影响用户体验。

### 排查过程

**第一步：测量延迟**

```bash
# 测量 RTT
ping -c 100 server_ip

# 输出示例:
# rtt min/avg/max/mdev = 98.1/100.2/102.3/1.2 ms
```

**第二步：查看路径**

```bash
# 查看路由路径
traceroute server_ip

# 输出示例:
# 1  192.168.1.1  1.2 ms
# 2  10.0.0.1  5.6 ms
# 3  172.16.0.1  12.3 ms
# 4  220.181.0.1  50.5 ms
# 5  101.4.0.1  98.7 ms
# 6  server_ip  100.2 ms
```

**第三步：分析瓶颈**

```bash
# 用 mtr 分析每一跳
mtr -c 100 server_ip

# 输出示例:
# Host                   Loss%   Snt   Last   Avg  Best  Wrst StDev
# 1. 192.168.1.1          0.0%   100    1.1   1.2   1.0   1.5   0.1
# 2. 10.0.0.1             0.0%   100    5.5   5.6   5.4   5.8   0.1
# 3. 172.16.0.1           0.0%   100   12.3  12.4  12.1  12.8   0.2
# 4. 220.181.0.1          0.0%   100   50.5  50.6  50.3  50.9   0.1
# 5. 101.4.0.1            0.0%   100   98.7  98.8  98.5  99.1   0.1
# 6. server_ip            0.0%   100  100.2 100.3 100.0 100.6   0.1
```

分析：第 3 跳到第 4 跳延迟增加 38ms，说明跨越了骨干网。

**第四步：计算 BDP**

```bash
# 假设带宽 100 Mbps
bandwidth_mbps=100
rtt_ms=100
bdp_bytes=$((bandwidth_mbps * rtt_ms * 1000 / 8))
echo "BDP: $bdp_bytes bytes"

# 输出:
# BDP: 1250000 bytes = 1.25 MB
```

### 根因

跨机房物理距离导致延迟高，BDP 大。

### 解决方案

1. **使用 CDN**：把静态资源缓存到离用户近的节点
2. **就近部署**：在上海部署服务器
3. **优化协议**：使用 HTTP/2、QUIC 减少连接数
4. **增大窗口**：充分利用带宽

```bash
# 增大 TCP 窗口
sudo sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"
sudo sysctl -w net.ipv4.tcp_wmem="4096 65536 16777216"
```

## 总结

通过这三个案例，你应该掌握了：

1. **系统化排查方法**：从症状到根因，逐步缩小范围
2. **工具链的使用**：ping、traceroute、mtr、ss、tcpdump 的组合使用
3. **性能分析方法**：带宽、延迟、BDP 的计算和分析
4. **常见问题的解决**：服务器性能、连接跟踪、跨机房延迟

## 参考答案

### 练习一

```bash
# 模拟丢包
sudo tc qdisc add dev eth0 root netem loss 5%

# 测试
ping -c 100 8.8.8.8 | tail -1
# 应该看到约 5% 丢包

# 排查
mtr -c 100 8.8.8.8
# 观察哪一跳开始丢包

# 恢复
sudo tc qdisc del dev eth0 root
```

### 练习二

1. **排查流程**：确认问题 → 测量指标 → 分析路径 → 抓包分析 → 定位根因

2. **判断瓶颈位置**：
   - 客户端：检查本地网络、DNS、防火墙
   - 服务器：检查负载、连接数、资源使用
   - 网络路径：检查延迟、丢包、路由

3. **监控网络性能**：
   - 定期测量延迟和丢包
   - 监控连接数和端口使用
   - 设置告警阈值

**常见错误**：只关注带宽，忽略延迟和丢包。实际上延迟和丢包对用户体验的影响可能更大。
