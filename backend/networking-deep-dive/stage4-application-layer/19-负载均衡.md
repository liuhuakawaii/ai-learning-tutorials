# 负载均衡——L4/L7 区别、一致性哈希、健康检查

## 为什么需要负载均衡

单台服务器的处理能力有限。当请求量增大时，需要多台服务器分担负载。

负载均衡器把请求分发到多台后端服务器：
```
客户端 → 负载均衡器 → 服务器1
                   → 服务器2
                   → 服务器3
```

## L4 负载均衡 vs L7 负载均衡

### L4 负载均衡（传输层）

工作在 TCP/UDP 层，只看 IP 地址和端口，不看应用层内容。

特点：
- 速度快，延迟低
- 支持任何 TCP/UDP 应用
- 不能根据应用层内容做决策
- 连接直接转发，不终止

典型实现：
- Linux Virtual Server (LVS)
- AWS Network Load Balancer (NLB)

### L7 负载均衡（应用层）

工作在 HTTP 层，可以看 URL、Cookie、Header 等。

特点：
- 功能丰富（URL 路由、会话保持、SSL 卸载）
- 延迟较高（需要解析应用层）
- 只支持特定协议（HTTP、HTTPS、gRPC）
- 终止 TLS 连接

典型实现：
- Nginx
- HAProxy
- AWS Application Load Balancer (ALB)

## 负载均衡算法

### 轮询（Round Robin）

按顺序轮流分发请求：
```
请求1 → 服务器1
请求2 → 服务器2
请求3 → 服务器3
请求4 → 服务器1
```

优点：简单公平
缺点：不考虑服务器负载差异

### 加权轮询（Weighted Round Robin）

根据服务器权重分发：
```
服务器1 权重 3：请求1, 4, 7
服务器2 权重 2：请求2, 5
服务器3 权重 1：请求3, 6
```

优点：考虑服务器性能差异
缺点：权重需要手动配置

### 最少连接（Least Connections）

把请求分发到当前连接数最少的服务器。

优点：自动适应服务器负载
缺点：需要跟踪连接数

### IP 哈希（IP Hash）

根据客户端 IP 地址哈希，同一客户端总是访问同一服务器。

优点：实现会话保持
缺点：客户端分布不均时负载不均衡

## 一致性哈希

普通哈希的问题：服务器增减时，几乎所有请求都会重新分配。

一致性哈希把服务器和请求都映射到一个环上：
```
         服务器1
           ↓
    请求1 → ● ← 请求3
           ↑
         服务器2
           ↓
    请求2 → ● ← 请求4
```

当服务器增减时，只有部分请求需要重新分配。

### 虚拟节点

为了解决节点分布不均的问题，每个服务器对应多个虚拟节点。

```
服务器1 → 虚拟节点 1a, 1b, 1c
服务器2 → 虚拟节点 2a, 2b, 2c
```

## 健康检查

负载均衡器需要知道后端服务器是否健康，避免把请求发到故障服务器。

### 主动健康检查

负载均衡器定期发送探测请求：
```
每 10 秒 → GET /health → 200 OK → 服务器健康
每 10 秒 → GET /health → 超时 → 服务器不健康
```

### 被动健康检查

根据实际请求的响应判断：
```
连续 3 次请求失败 → 标记为不健康
连续 3 次请求成功 → 标记为健康
```

### 健康检查端点

应用通常提供专门的健康检查端点：
```bash
# 简单健康检查
GET /health → 200 OK

# 详细健康检查
GET /health → {
    "status": "healthy",
    "database": "connected",
    "cache": "connected"
}
```

## 实验：用 Nginx 配置负载均衡

### 安装 Nginx

```bash
sudo apt install nginx
```

### 配置负载均衡

编辑 `/etc/nginx/nginx.conf`：

```nginx
http {
    upstream backend {
        # 轮询
        server 192.168.1.101:8080;
        server 192.168.1.102:8080;
        server 192.168.1.103:8080;
        
        # 加权轮询
        # server 192.168.1.101:8080 weight=3;
        # server 192.168.1.102:8080 weight=2;
        
        # IP 哈希
        # ip_hash;
        
        # 最少连接
        # least_conn;
    }

    server {
        listen 80;
        
        location / {
            proxy_pass http://backend;
        }
    }
}
```

### 测试负载均衡

```bash
# 重启 Nginx
sudo systemctl restart nginx

# 测试
curl http://localhost

# 多次请求，观察分发到不同服务器
for i in {1..10}; do
  curl -s http://localhost | grep "Server"
done
```

## 实验：用 HAProxy 配置负载均衡

### 安装 HAProxy

```bash
sudo apt install haproxy
```

### 配置 HAProxy

编辑 `/etc/haproxy/haproxy.cfg`：

```
frontend http_front
    bind *:80
    default_backend servers

backend servers
    balance roundrobin
    server server1 192.168.1.101:8080 check
    server server2 192.168.1.102:8080 check
    server server3 192.168.1.103:8080 check
```

### 测试健康检查

```bash
# 启动 HAProxy
sudo systemctl start haproxy

# 停止一个后端服务器，观察 HAProxy 日志
sudo systemctl stop backend1

# HAProxy 会自动把请求发到健康的服务器
```

## 负载均衡的常见问题

### 会话保持

某些应用需要同一用户的请求始终发到同一服务器。

解决方案：
- IP 哈希
- Cookie 插入
- 会话外部存储（Redis）

### SSL 卸载

在负载均衡器上终止 TLS，后端服务器只需要处理 HTTP。

优点：
- 减少后端服务器 CPU 负担
- 集中管理证书
- 简化后端配置

### WebSocket 支持

WebSocket 是长连接，需要特殊的负载均衡配置。

## 参考答案

### 练习一

配置示例：
```nginx
upstream backend {
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
    server 127.0.0.1:8083;
}
```

测试：
```bash
for i in {1..9}; do curl -s http://localhost; done
```

应该看到请求分发到 3 个不同的服务器。

### 练习二

1. **L4 适用场景**：TCP/UDP 应用、高性能需求、不需要应用层路由。**L7 适用场景**：HTTP 应用、需要 URL 路由、需要 SSL 卸载。

2. **一致性哈希**：解决服务器增减时大量请求重新分配的问题。只有部分请求需要重新分配，减少缓存失效。

3. **健康检查间隔**：通常 5-30 秒。太频繁会增加服务器负担，太稀疏会延迟故障检测。

**常见错误**：以为负载均衡器能自动解决所有性能问题。实际上负载均衡器本身也可能成为瓶颈，需要合理配置和监控。
