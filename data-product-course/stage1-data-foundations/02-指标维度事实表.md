# 第2课：指标、维度、事实表和宽表

> **课程定位**：掌握数据产品设计的核心概念，建立数据建模的基本思维
> **前置知识**：第1课（数据产品是什么）
> **预计时长**：50 分钟

---

## 场景引入

周一开周会，老板问"上周活跃用户多少？"，产品说 12 万，数据分析师说 8 万，运营说 15 万。三个人报了三个数，吵了半小时才发现：产品说的"活跃"是"打开过 App"，分析师说的是"产生过交易"，运营说的是"浏览超过 3 个页面"。同一个词，三种口径，三个结论。这就是不定义指标、不统一维度的代价——你连吵架的基础都没有。

## 一、从一个简单问题开始

### 1.1 老板的问题

老板走过来说："我想看看我们产品的销售情况。"

你会怎么回答？你需要问清楚：

- "销售情况"是指什么？→ **指标**
- 按什么角度分析？→ **维度**
- 数据的详细程度？→ **粒度**

```
┌──────────────────────────────────────────────────────────────┐
│                    老板想要什么？                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  "销售情况"                                                  │
│     │                                                        │
│     ├── 指标：销售额、订单数、客单价、退货率                   │
│     │                                                        │
│     ├── 维度：按时间、按地区、按品类、按渠道                   │
│     │                                                        │
│     └── 粒度：按天还是按月？按省还是按市？                     │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 二、指标（Metric）

### 2.1 什么是指标？

**指标**是衡量业务状况的数值。它回答"是多少"的问题。

```
┌──────────────────────────────────────────────────────────────┐
│                    常见指标示例                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  电商领域：                                                   │
│  ├── 销售额（GMV）                                           │
│  ├── 订单数                                                  │
│  ├── 客单价 = 销售额 / 订单数                                │
│  ├── 转化率 = 下单人数 / 访问人数                             │
│  └── 退货率 = 退货订单数 / 总订单数                           │
│                                                              │
│  招聘领域：                                                   │
│  ├── 岗位数量                                                │
│  ├── 平均薪资                                                │
│  ├── 薪资中位数                                              │
│  ├── 热门技能 TOP10                                          │
│  └── 城市岗位分布                                            │
│                                                              │
│  内容领域：                                                   │
│  ├── 文章数                                                  │
│  ├── 阅读量                                                  │
│  ├── 点赞数                                                  │
│  ├── 平均阅读时长                                            │
│  └── 分享率                                                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 指标的分类

```
┌──────────────────────────────────────────────────────────────┐
│                    指标的两种类型                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  原子指标（可以直接从数据计算）                                │
│  ├── 销售额 = SUM(金额)                                      │
│  ├── 订单数 = COUNT(订单)                                    │
│  └── 用户数 = COUNT(DISTINCT 用户ID)                         │
│                                                              │
│  派生指标（由原子指标组合计算）                                │
│  ├── 客单价 = 销售额 / 订单数                                │
│  ├── 转化率 = 下单人数 / 访问人数                             │
│  └── 同比增长率 = (本期 - 上期) / 上期                        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 2.3 好指标 vs 坏指标

```
┌──────────────────────────────────────────────────────────────┐
│                    好指标的特征                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  ✅ 好指标                                                   │
│  ├── 可量化：有明确的计算公式                                 │
│  ├── 可行动：指标变化能指导业务决策                           │
│  ├── 可对比：能做时间对比、横向对比                           │
│  └── 有基准：有正常范围，能判断好坏                           │
│                                                              │
│  ❌ 坏指标                                                   │
│  ├── 模糊："用户满意度"（怎么量化？）                         │
│  ├── 虚荣："总注册用户数"（不活跃有什么用？）                  │
│  └── 无法行动："天气温度"（看了能干嘛？）                     │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 三、维度（Dimension）

### 3.1 什么是维度？

**维度**是分析数据的角度。它回答"按什么分组"的问题。

```
┌──────────────────────────────────────────────────────────────┐
│                    常见维度                                    │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  时间维度：                                                   │
│  ├── 年、季度、月、周、天                                    │
│  ├── 工作日 / 周末                                           │
│  └── 上午 / 下午 / 晚上                                      │
│                                                              │
│  地理维度：                                                   │
│  ├── 国家、省、市、区                                        │
│  └── 一线城市 / 二线城市 / 三线城市                          │
│                                                              │
│  产品维度：                                                   │
│  ├── 品类、品牌、型号                                        │
│  └── 价格区间                                                │
│                                                              │
│  用户维度：                                                   │
│  ├── 新用户 / 老用户                                         │
│  ├── 渠道来源                                                │
│  └── 会员等级                                                │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 维度的作用

维度让你能从不同角度切片看数据：

```
销售额（指标）
    │
    ├── 按时间维度：这个月 vs 上个月
    ├── 按地区维度：北京 vs 上海 vs 广州
    ├── 按品类维度：电子产品 vs 服装 vs 食品
    └── 按渠道维度：APP vs 小程序 vs PC

同样的"销售额"，加上不同维度，能看到完全不同的故事。
```

## 四、事实（Fact）

### 4.1 什么是事实？

**事实**是业务过程中发生的可度量事件。它是数据的主体。

```
┌──────────────────────────────────────────────────────────────┐
│                    事实的例子                                  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  电商：                                                       │
│  └── 一笔订单（包含：订单ID、用户ID、商品ID、金额、时间）      │
│                                                              │
│  招聘：                                                       │
│  └── 一条岗位（包含：岗位ID、公司、职位、薪资、城市、发布时间）│
│                                                              │
│  内容：                                                       │
│  └── 一次阅读（包含：文章ID、用户ID、阅读时长、来源渠道）      │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 事实的特征

```
事实 = 谁 + 什么 + 多少 + 什么时候 + 在哪里

订单事实：
├── 谁（用户ID）
├── 买了什么（商品ID）
├── 多少钱（金额）
├── 什么时候（下单时间）
└── 在哪里下单（渠道）
```

## 五、事实表与维度表

### 5.1 事实表（Fact Table）

**事实表**存储业务事件的核心数据，通常是数值型的度量值。

```sql
-- 订单事实表
CREATE TABLE fact_orders (
    order_id      INT PRIMARY KEY,
    user_id       INT,           -- 维度：用户
    product_id    INT,           -- 维度：产品
    amount        DECIMAL(10,2), -- 度量：金额
    quantity      INT,           -- 度量：数量
    order_date    DATE,          -- 维度：时间
    channel       VARCHAR(50)    -- 维度：渠道
);
```

### 5.2 维度表（Dimension Table）

**维度表**存储描述性的、通常是文本型的属性信息。

```sql
-- 产品维度表
CREATE TABLE dim_products (
    product_id    INT PRIMARY KEY,
    product_name  VARCHAR(100),
    category      VARCHAR(50),
    brand         VARCHAR(50),
    price_range   VARCHAR(20)    -- 价格区间：低/中/高
);

-- 用户维度表
CREATE TABLE dim_users (
    user_id       INT PRIMARY KEY,
    username      VARCHAR(50),
    city          VARCHAR(50),
    user_type     VARCHAR(20),   -- 新用户/老用户
    register_date DATE
);
```

### 5.3 星型模型

事实表和维度表组合形成**星型模型**：

```
                    ┌─────────────┐
                    │  dim_date   │
                    │  时间维度表  │
                    └──────┬──────┘
                           │
┌─────────────┐    ┌──────┴──────┐    ┌─────────────┐
│ dim_products │────│ fact_orders │────│  dim_users  │
│  产品维度表  │    │  订单事实表  │    │  用户维度表  │
└─────────────┘    └──────┬──────┘    └─────────────┘
                           │
                    ┌──────┴──────┐
                    │ dim_channel │
                    │  渠道维度表  │
                    └─────────────┘

查询示例：
SELECT 
    d.month,
    p.category,
    SUM(f.amount) as total_sales
FROM fact_orders f
JOIN dim_date d ON f.order_date = d.date
JOIN dim_products p ON f.product_id = p.product_id
GROUP BY d.month, p.category;
```

## 六、宽表（Wide Table）

### 6.1 什么是宽表？

**宽表**是把事实和维度信息合并到一张表中，方便查询但可能有数据冗余。

```sql
-- 宽表：把订单、产品、用户信息合并
CREATE TABLE wide_orders (
    -- 订单信息
    order_id      INT PRIMARY KEY,
    amount        DECIMAL(10,2),
    quantity      INT,
    order_date    DATE,
    
    -- 产品信息（冗余）
    product_name  VARCHAR(100),
    category      VARCHAR(50),
    brand         VARCHAR(50),
    
    -- 用户信息（冗余）
    username      VARCHAR(50),
    city          VARCHAR(50),
    user_type     VARCHAR(20),
    
    -- 渠道信息（冗余）
    channel       VARCHAR(50)
);
```

### 6.2 星型模型 vs 宽表

```
┌──────────────────────────────────────────────────────────────┐
│                星型模型 vs 宽表                                │
├────────────────┬─────────────────┬───────────────────────────┤
│     维度       │    星型模型      │       宽表                │
├────────────────┼─────────────────┼───────────────────────────┤
│  数据冗余      │  低（规范化）    │  高（反规范化）            │
│  查询复杂度    │  需要 JOIN      │  单表查询                  │
│  查询性能      │  较慢           │  较快                      │
│  存储空间      │  较小           │  较大                      │
│  更新维护      │  容易           │  复杂（多处需同步）        │
│  适用场景      │  OLTP 写入多    │  OLAP 查询多               │
└────────────────┴─────────────────┴───────────────────────────┘

数据产品通常用宽表，因为：
- 查询频繁，JOIN 性能差
- 数据是批量写入，不是频繁更新
- 用户查询模式多样，无法预建所有视图
```

### 6.3 实际例子：招聘数据宽表

```sql
-- 招聘数据宽表
CREATE TABLE wide_jobs (
    -- 主键
    job_id            VARCHAR(50) PRIMARY KEY,
    
    -- 岗位信息
    title             VARCHAR(200),
    company           VARCHAR(200),
    city              VARCHAR(50),
    district          VARCHAR(50),
    
    -- 薪资信息
    salary_min        DECIMAL(10,2),
    salary_max        DECIMAL(10,2),
    salary_avg        DECIMAL(10,2),
    salary_unit       VARCHAR(10),    -- 元/月、元/年
    
    -- 要求信息
    experience        VARCHAR(50),    -- 1-3年、3-5年
    education         VARCHAR(20),    -- 本科、硕士
    skills            TEXT,           -- Python,Java,React
    
    -- 来源信息
    source            VARCHAR(50),    -- 数据来源网站
    source_url        VARCHAR(500),
    
    -- 时间信息
    publish_date      DATE,
    crawl_time        TIMESTAMP,
    batch_id          VARCHAR(50)     -- 采集批次号
);
```

## 七、粒度（Granularity）

### 7.1 什么是粒度？

**粒度**是数据的详细程度。它决定了一行数据代表什么。

```
┌──────────────────────────────────────────────────────────────┐
│                    粒度的例子                                  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  销售数据的粒度选择：                                         │
│                                                              │
│  细粒度（一行 = 一笔订单）                                    │
│  ├── order_id: 1001                                          │
│  ├── user_id: U001                                           │
│  ├── product_id: P001                                        │
│  ├── amount: 299.00                                          │
│  └── order_time: 2024-01-15 14:30:00                         │
│                                                              │
│  中粒度（一行 = 一天的汇总）                                  │
│  ├── date: 2024-01-15                                        │
│  ├── total_orders: 150                                       │
│  ├── total_amount: 45000.00                                  │
│  └── avg_order_amount: 300.00                                │
│                                                              │
│  粗粒度（一行 = 一个月的汇总）                                │
│  ├── month: 2024-01                                          │
│  ├── total_orders: 4500                                      │
│  ├── total_amount: 1350000.00                                │
│  └── avg_order_amount: 300.00                                │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 7.2 如何选择粒度？

```
粒度选择原则：

1. 能细就细（可以聚合，无法拆分）
   └── 存细粒度数据，需要时再聚合

2. 根据查询需求选择
   ├── 需要看单条详情 → 细粒度
   ├── 需要看趋势对比 → 中粒度
   └── 需要看整体概况 → 粗粒度

3. 考虑存储和性能
   └── 细粒度数据量大，查询慢
```

## 八、建立指标体系

### 8.1 指标体系的结构

```
┌──────────────────────────────────────────────────────────────┐
│                    指标体系的层次                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  第一层：核心指标（北极星指标）                                │
│  └── 1-2 个，代表业务核心目标                                 │
│                                                              │
│  第二层：一级指标                                              │
│  └── 3-5 个，支撑核心指标                                     │
│                                                              │
│  第三层：二级指标                                              │
│  └── 每个一级指标拆解出 2-3 个                                │
│                                                              │
│  第四层：操作指标                                              │
│  └── 日常监控、可直接行动                                     │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 8.2 例子：招聘数据产品的指标体系

```
核心指标：市场活跃度
    │
    ├── 一级指标：岗位数量
    │   ├── 今日新增岗位数
    │   ├── 本周新增岗位数
    │   └── 岗位增长率
    │
    ├── 一级指标：薪资水平
    │   ├── 平均薪资
    │   ├── 薪资中位数
    │   ├── 薪资范围分布
    │   └── 薪资同比变化
    │
    ├── 一级指标：技能需求
    │   ├── 热门技能 TOP10
    │   ├── 技能需求变化趋势
    │   └── 新兴技能出现
    │
    └── 一级指标：地域分布
        ├── 城市岗位数量排名
        ├── 城市薪资排名
        └── 远程岗位占比
```

## 常见误区

- **指标越多越好的幻觉**：堆砌几十个指标，看起来很全面，实际上没人看、没人用。好的指标体系是少而精的，每个指标都要能指导行动。
- **维度越细越好的误解**：把数据拆到"按天-按城市-按渠道-按品类-按用户等级"，结果每个格子里只有 0-2 条数据，统计意义为零。维度选择要考虑数据量是否支撑。
- **把宽表当万能解药**：宽表查询快，但数据冗余大、更新麻烦。如果业务需要频繁更新单个字段（比如用户等级），星型模型反而更合适。
- **忽略粒度设计**：一开始就按月汇总，后来发现需要看每天的趋势，但历史数据已经无法拆回去了。粒度选择的原则是"能细就细，需要时再聚合"。

---

## 工程建议

- **指标口径必须文档化**：每个指标的计算公式、数据来源、筛选条件都要写进数据字典。"活跃用户"到底是 UV 还是登录用户，必须白纸黑字写清楚，不能靠口头约定。
- **维度设计要参考实际查询场景**：在设计维度表之前，先收集业务方常用的查询条件（按什么筛选、按什么分组），再决定维度表包含哪些属性。
- **事实表和宽表的选择看读写比例**：写多读少用星型模型（OLTP），读多写少用宽表（OLAP）。数据产品通常是批量写入、频繁查询，所以宽表更常见。
- **粒度选择要考虑未来需求**：如果不确定将来要分析到什么粒度，先按最细粒度存储。存储成本远低于"重新采集历史数据"的成本。

## 小结

本课的核心要点：

1. **指标**是"是多少"，衡量业务状况的数值
2. **维度**是"按什么分"，分析数据的角度
3. **事实**是业务事件，包含度量值和外键
4. **事实表**存事件数据，**维度表**存描述信息
5. **宽表**把事实和维度合并，适合 OLAP 查询
6. **粒度**决定一行数据的详细程度，能细就细
7. **指标体系**有层次：核心 → 一级 → 二级 → 操作
