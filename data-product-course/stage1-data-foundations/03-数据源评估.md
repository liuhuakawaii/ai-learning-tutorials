# 第3课：数据源评估

> **课程定位**：学会评估和选择合适的数据源，了解常见数据获取方式的优缺点
> **前置知识**：第2课（指标、维度、事实表）
> **预计时长**：45 分钟

---

## 场景引入

你要做一个商品价格监控产品，找到了三个数据源：一个是电商平台的官方 API（免费但每天限 1000 次调用），一个是第三方数据服务商（付费但数据全），还有一个方案是自己写爬虫（免费但要自己维护）。你选了官方 API，上线后发现 1000 次调用根本不够用；换爬虫方案，上线两周后目标网站改了页面结构，爬虫全部报错。你这才意识到，选数据源不是看"能不能拿到数据"，而是要从可靠性、质量、成本、合规性四个维度综合评估。

---

## 学习目标

完成本课学习后，你将能够：

1. 列举常见的数据源类型及其适用场景
2. 从可靠性、质量、成本、合规性四个维度评估数据源
3. 区分 API、文件、网页、手工导入四种获取方式
4. 为一个业务场景选择合适的数据源组合
5. 识别数据源的潜在风险

## 二、数据源评估的四个维度

### 2.1 可靠性

```
┌──────────────────────────────────────────────────────────────┐
│                    可靠性评估                                  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  问这些问题：                                                 │
│  ├── 数据源是否稳定运行？（SLA 是多少？）                     │
│  ├── 接口是否经常变动？                                       │
│  ├── 数据是否及时更新？                                       │
│  └── 历史数据是否可追溯？                                     │
│                                                              │
│  评分标准：                                                   │
│  ├── ⭐⭐⭐⭐⭐ 官方 API，有 SLA 保障                         │
│  ├── ⭐⭐⭐⭐  知名第三方，长期稳定                           │
│  ├── ⭐⭐⭐   公开数据，更新频率一般                         │
│  ├── ⭐⭐    网页采集，可能变动                              │
│  └── ⭐     不明来源，稳定性未知                             │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 2.2 数据质量

```
┌──────────────────────────────────────────────────────────────┐
│                    数据质量评估                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  完整性：字段是否齐全？缺失率多少？                           │
│  ├── 好：所有字段都有值                                      │
│  └── 差：大量 NULL 或空字符串                                │
│                                                              │
│  准确性：数据是否正确？                                       │
│  ├── 好：经过验证，与实际一致                                │
│  └── 差：有明显错误（如负数价格）                            │
│                                                              │
│  一致性：同一实体的数据是否一致？                             │
│  ├── 好：同一商品在不同表中信息相同                          │
│  └── 差：同一商品名称不统一                                  │
│                                                              │
│  及时性：数据是否最新？                                       │
│  ├── 好：实时或近实时更新                                    │
│  └── 差：数据延迟严重                                        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 三、四种获取方式详解

### 3.1 API 接口

```
┌──────────────────────────────────────────────────────────────┐
│                    API 接口                                    │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  优点：                                                       │
│  ├── 数据结构化，格式规范                                    │
│  ├── 有官方文档，对接简单                                    │
│  ├── 数据质量有保障                                          │
│  └── 合规性明确                                              │
│                                                              │
│  缺点：                                                       │
│  ├── 可能有速率限制                                          │
│  ├── 可能需要付费                                            │
│  ├── 数据范围受限于接口设计                                  │
│  └── 接口可能变更或下线                                      │
│                                                              │
│  适用场景：                                                   │
│  ├── 天气数据（和风天气、OpenWeatherMap）                    │
│  ├── 金融数据（股票、汇率）                                  │
│  ├── 地理数据（高德、百度地图）                              │
│  └── 社交媒体（Twitter、微博）                               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**示例：调用天气 API**

```python
import requests

# 和风天气 API 示例
def get_weather(city: str) -> dict:
    api_key = "your_api_key"
    url = f"https://devapi.qweather.com/v7/weather/now"
    params = {
        "location": city,
        "key": api_key
    }
    response = requests.get(url, params=params)
    return response.json()

weather = get_weather("101010100")  # 北京
print(weather)
```

**示例：网页采集**

```python
import requests
from bs4 import BeautifulSoup

def scrape_jobs(url: str) -> list:
    response = requests.get(url, headers={"User-Agent": "Mozilla/5.0"})
    soup = BeautifulSoup(response.text, "html.parser")
    
    jobs = []
    for item in soup.select(".job-item"):
        job = {
            "title": item.select_one(".title").text.strip(),
            "company": item.select_one(".company").text.strip(),
            "salary": item.select_one(".salary").text.strip(),
        }
        jobs.append(job)
    
    return jobs
```

## 常见误区

- **只看"免费"就决定用**：免费 API 看似零成本，但可能有严格的调用限制；网页采集看似免费，但开发和维护成本可能远高于付费 API。评估成本要算总账，包括开发、运维、合规成本。
- **过度相信数据源的质量**：官方 API 的数据也可能有缺失值、格式不一致、更新延迟等问题。任何数据源在使用前都应该做采样检查，不能想当然地认为"官方的就一定没问题"。
- **只准备一个数据源**：单一数据源一旦出问题（API 下线、网站改版、服务条款变更），整个产品就瘫痪了。生产环境至少要有一个备选方案。
- **忽视合规性直到出事**：很多人拿到数据就用，从不检查服务条款和 robots.txt。直到收到律师函才意识到问题的严重性。合规性评估应该在技术评估之前完成。

---

## 工程建议

- **用决策树做数据源选择**：先问"有没有官方 API？"，再问"有没有公开数据文件？"，最后才考虑网页采集。优先级是：API > 文件 > 爬虫 > 手工录入。
- **为每个数据源做"四维评估卡"**：用统一的模板记录可靠性、质量、成本、合规性的评分和理由。这样在做决策时有据可依，也方便团队沟通。
- **建立数据源监控机制**：定期检查数据源的可用性（API 是否正常返回）、数据质量（缺失率是否异常）、更新频率（是否符合预期）。推荐每天自动化跑一次检查脚本。
- **数据源组合时要设计降级策略**：主数据源不可用时，自动切换到备用数据源。切换时要在日志中记录，以便后续排查数据差异。

## 小结

本课的核心要点：

1. **数据源分类**：内部数据 vs 外部数据
2. **评估维度**：可靠性、质量、成本、合规性
3. **四种获取方式**：API、文件、网页、手工，各有优缺点
4. **组合策略**：通常需要多种数据源互相补充
5. **风险识别**：稳定性、质量、合规、成本四大风险
