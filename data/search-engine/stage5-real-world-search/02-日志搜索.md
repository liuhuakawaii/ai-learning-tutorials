# 日志搜索：用 ELK Stack 构建日志分析平台

## 场景引入

凌晨三点，线上服务开始大量报错。运维工程师打开 Kibana，输入错误关键词，几秒钟内定位到是数据库连接池耗尽导致的。从告警到定位根因，整个过程不到五分钟。

这背后是 ELK Stack 在工作：应用日志被实时采集、解析、存储，运维人员可以随时搜索和分析。日志搜索的挑战在于：如何高效处理每秒数万条日志，并支持实时查询？本节课将带你搭建完整的日志搜索 pipeline。

## ELK Stack 架构概览

ELK Stack 由三个核心组件组成：**Elasticsearch**（存储和查询）、**Logstash**（采集和解析）、**Kibana**（可视化）。数据流向为：应用产生日志 → Logstash 采集解析 → Elasticsearch 存储索引 → Kibana 可视化查询。

生产环境通常加入 **Filebeat** 做轻量级采集：`应用 → Filebeat → Kafka(可选) → Logstash → Elasticsearch → Kibana`。本节课用 Python 替代 Filebeat 和 Logstash，直接向 Elasticsearch 写入。

### 为什么需要 Kafka 作为缓冲层

在高并发场景下，日志量可能瞬间暴增（如大促期间）。如果 Filebeat 直接写 Logstash，Logstash 处理不过来时会丢数据。Kafka 作为中间缓冲层的好处：

1. **削峰填谷**：日志量突增时 Kafka 先存起来，Logstash 按自己的处理能力消费。
2. **解耦**：生产者和消费者独立扩展，增加新的日志消费者不需要改动采集端。
3. **数据保真**：Kafka 的持久化机制保证日志不会因为下游故障而丢失。

典型的消息格式：

```python
import json
from datetime import datetime

def create_kafka_message(log_entry: dict, topic: str = "app-logs") -> dict:
    return {
        "topic": topic,
        "key": log_entry.get("service", "unknown").encode("utf-8"),
        "value": json.dumps({
            "@timestamp": log_entry.get("@timestamp", datetime.utcnow().isoformat()),
            "level": log_entry["level"],
            "service": log_entry["service"],
            "message": log_entry["message"],
            "metadata": {
                "host": log_entry.get("host"),
                "trace_id": log_entry.get("trace_id"),
                "env": log_entry.get("env", "production")
            }
        }).encode("utf-8")
    }
```

Kafka topic 按日志类型划分（app-logs、access-logs、error-logs），不同类型的日志可以有不同的消费速度和保留策略。

## 日志索引设计

日志数据有明显的时间特征，通常按日期创建索引：

```python
from elasticsearch import Elasticsearch
from datetime import datetime

es = Elasticsearch("http://localhost:9200")

def create_daily_index(date_str: str = None):
    if date_str is None:
        date_str = datetime.now().strftime("%Y.%m.%d")

    index_name = f"logs-{date_str}"
    mapping = {
        "mappings": {
            "properties": {
                "@timestamp": {"type": "date"},
                "level": {"type": "keyword"},
                "service": {"type": "keyword"},
                "host": {"type": "keyword"},
                "message": {
                    "type": "text",
                    "fields": {"keyword": {"type": "keyword", "ignore_above": 512}}
                },
                "trace_id": {"type": "keyword"},
                "duration_ms": {"type": "float"},
                "status_code": {"type": "integer"},
                "error_type": {"type": "keyword"}
            }
        },
        "settings": {"number_of_shards": 1, "number_of_replicas": 0}
    }

    es.indices.create(index=index_name, body=mapping, ignore=400)
    return index_name
```

按日期分索引的好处：可以按时间范围快速删除旧日志，单个索引体积可控，查询时指定索引模式减少扫描范围。

### 索引命名策略的选择

除了按日期分索引，还有其他策略可选：

```python
# 策略1：按日期（最常用）
index_name = f"logs-{datetime.now().strftime('%Y.%m.%d')}"
# 适合：日志量中等（每天 1-100GB）

# 策略2：按日期+服务名
index_name = f"logs-{service_name}-{datetime.now().strftime('%Y.%m.%d')}"
# 适合：不同服务的日志量差异很大

# 策略3：按小时（高流量场景）
index_name = f"logs-{datetime.now().strftime('%Y.%m.%d-%H')}"
# 适合：每秒数万条日志，单日数据量超 100GB

# 策略4：使用 ILM 自动滚动
# 由 ES 自动管理索引滚动，无需手动创建
# 适合：不想手动管理索引生命周期的场景
```

选择哪种策略取决于日志量和查询模式。如果查询经常跨越多个日期，按日期分索引最方便；如果某个服务的日志量远大于其他服务，按服务名分索引可以避免单索引过大。

### 字段类型的设计考量

日志字段的类型选择直接影响存储成本和查询性能：

```python
# message 字段的设计
"message": {
    "type": "text",                    # 支持全文搜索
    "fields": {
        "keyword": {
            "type": "keyword",
            "ignore_above": 512        # 超过 512 字符的不建 keyword
        }
    },
    "norms": false                     # 禁用 norms 节省内存（不需要按文档长度归一化）
}

# level 字段为什么用 keyword 而不是 enum
# keyword 支持任意值，新增日志级别不需要改 mapping
"level": {"type": "keyword"}

# host 字段用 keyword，因为 IP 地址不需要分词
"host": {"type": "keyword"}

# duration_ms 用 float 而不是 integer
# 因为有些场景需要记录 0.5ms 这样的精确耗时
"duration_ms": {"type": "float"}
```

`norms: false` 是日志场景的重要优化。norms 用于记录文档长度信息，帮助短文档获得更高分数。日志搜索不需要这个特性（我们不关心短日志比长日志更重要），禁用 norms 可以节省约 10% 的索引空间。

## 日志生成与采集

用 Python 模拟应用日志的生成：

```python
import random
from datetime import datetime

SERVICES = ["user-service", "order-service", "payment-service", "gateway"]
LOG_LEVELS = ["INFO", "WARN", "ERROR", "DEBUG"]
ERROR_TYPES = ["TimeoutError", "ConnectionError", "ValueError", "DatabaseError"]

LOG_TEMPLATES = {
    "INFO": [
        "Request processed successfully, duration={duration}ms",
        "User {user_id} logged in from {host}",
        "Order {order_id} created, total={amount}元",
    ],
    "WARN": [
        "Slow query detected, duration={duration}ms",
        "Rate limit approaching: {current}/{limit} requests",
    ],
    "ERROR": [
        "Database connection timeout after {duration}ms",
        "Failed to process payment for order {order_id}: {error}",
        "Unhandled exception: {error}, trace_id={trace_id}",
    ]
}

def generate_log_entry():
    level = random.choices(LOG_LEVELS, weights=[60, 20, 10, 10])[0]
    service = random.choice(SERVICES)
    template = random.choice(LOG_TEMPLATES.get(level, LOG_TEMPLATES["INFO"]))

    message = template.format(
        duration=random.randint(10, 2000),
        user_id=f"U{random.randint(1000, 9999)}",
        host=f"192.168.1.{random.randint(1, 254)}",
        order_id=f"ORD{random.randint(100000, 999999)}",
        amount=random.randint(10, 5000),
        current=random.randint(80, 100), limit=100,
        error=random.choice(ERROR_TYPES),
        trace_id=f"trace-{random.randint(10000, 99999)}",
    )

    return {
        "@timestamp": datetime.utcnow().isoformat(),
        "level": level,
        "service": service,
        "host": f"server-{random.randint(1, 5)}",
        "message": message,
        "trace_id": f"trace-{random.randint(10000, 99999)}",
        "duration_ms": random.randint(10, 2000),
        "status_code": random.choice([200, 200, 200, 400, 500, 503]),
        "error_type": random.choice(ERROR_TYPES) if level == "ERROR" else None
    }
```

日志按级别加权生成，INFO 占 60%，ERROR 占 10%，模拟真实场景中的分布。

### 结构化日志 vs 非结构化日志

日志分为结构化和非结构化两种，对搜索效率影响巨大：

```python
# 非结构化日志（传统方式，不推荐）
# "2024-01-15 10:30:45 ERROR [user-service] Database connection timeout after 500ms, host=192.168.1.10"
# 需要正则解析才能提取字段，搜索效率低

# 结构化日志（推荐）
# 直接输出 JSON 格式
import json
import logging

class JSONFormatter(logging.Formatter):
    def format(self, record):
        log_data = {
            "@timestamp": datetime.utcnow().isoformat(),
            "level": record.levelname,
            "service": record.name,
            "message": record.getMessage(),
            "module": record.module,
            "line": record.lineno
        }
        if hasattr(record, "trace_id"):
            log_data["trace_id"] = record.trace_id
        if record.exc_info:
            log_data["exception"] = self.formatException(record.exc_info)
        return json.dumps(log_data, ensure_ascii=False)

# 使用示例
logger = logging.getLogger("user-service")
handler = logging.StreamHandler()
handler.setFormatter(JSONFormatter())
logger.addHandler(handler)
logger.setLevel(logging.INFO)

# 带上下文的日志记录
logger.info("用户登录成功", extra={"trace_id": "trace-12345"})
```

结构化日志的优势：不需要正则解析，直接入库即可搜索；字段精确匹配比全文搜索快得多；聚合分析更准确。生产环境中应该强制使用结构化日志。

## 批量写入与生命周期管理

日志系统需要高吞吐写入，使用批量 API：

```python
from elasticsearch.helpers import bulk

def bulk_write_logs(count: int = 1000, batch_size: int = 500):
    index_name = create_daily_index()

    def generate_actions():
        for _ in range(count):
            yield {"_index": index_name, "_source": generate_log_entry()}

    success, failed = bulk(es, generate_actions(), chunk_size=batch_size)
    print(f"写入完成: 成功 {success}, 失败 {failed}")
    return index_name

def setup_index_lifecycle():
    policy = {
        "policy": {
            "phases": {
                "hot": {"actions": {"rollover": {"max_size": "50gb", "max_age": "1d"}}},
                "warm": {"min_age": "7d", "actions": {"shrink": {"number_of_shards": 1}}},
                "delete": {"min_age": "30d", "actions": {"delete": {}}}
            }
        }
    }
    es.ilm.put_lifecycle(name="logs-policy", body=policy)
```

`bulk` API 将多条日志合并成一次网络请求，大幅提高写入效率。索引生命周期管理（ILM）自动处理索引的滚动、降温和删除。

### 批量写入的性能调优

批量写入的性能取决于多个参数的配合：

```python
from elasticsearch.helpers import bulk, parallel_bulk
from concurrent.futures import ThreadPoolExecutor
import queue

# 方式1：简单批量（适合中等流量）
def simple_bulk_write(logs: list[dict], index_name: str):
    actions = [{"_index": index_name, "_source": log} for log in logs]
    success, errors = bulk(es, actions, chunk_size=500, request_timeout=30)
    return success, errors

# 方式2：并行批量（适合高流量）
def parallel_bulk_write(log_generator, index_name: str, thread_count: int = 4):
    def generate_actions():
        for log in log_generator():
            yield {"_index": index_name, "_source": log}

    for success, result in parallel_bulk(
        es, generate_actions(),
        thread_count=thread_count,
        chunk_size=1000,
        max_retries=3,
        initial_backoff=2,
        request_timeout=60
    ):
        if not success:
            print(f"写入失败: {result}")

# 方式3：异步缓冲写入（生产环境推荐）
class AsyncLogWriter:
    def __init__(self, index_name: str, buffer_size: int = 5000, flush_interval: float = 5.0):
        self.index_name = index_name
        self.buffer_size = buffer_size
        self.flush_interval = flush_interval
        self.buffer = queue.Queue(maxsize=buffer_size * 2)
        self.running = True

    def add(self, log_entry: dict):
        try:
            self.buffer.put_nowait(log_entry)
        except queue.Full:
            print("缓冲区满，丢弃日志")

    def _flush(self):
        logs = []
        while not self.buffer.empty() and len(logs) < self.buffer_size:
            try:
                logs.append(self.buffer.get_nowait())
            except queue.Empty:
                break

        if logs:
            actions = [{"_index": self.index_name, "_source": log} for log in logs]
            bulk(es, actions, chunk_size=1000, request_timeout=30)

    def start(self):
        import threading
        def flush_loop():
            while self.running:
                self._flush()
                import time
                time.sleep(self.flush_interval)

        thread = threading.Thread(target=flush_loop, daemon=True)
        thread.start()
```

关键参数说明：
- `chunk_size`：每次批量请求的文档数，500-2000 是常用范围。太小会增加网络开销，太大会增加单次请求延迟。
- `thread_count`：并行写入线程数，通常 2-4 个。太多线程会增加 ES 的写入压力。
- `flush_interval`：缓冲区刷新间隔，5-10 秒。太频繁会增加 ES 的 refresh 压力。

## 日志搜索与分析

日志搜索的核心场景包括关键词搜索、时间范围过滤、错误聚合分析：

```python
def search_logs(keyword: str = None, level: str = None,
                time_range: str = "1h", page: int = 1, size: int = 50):
    filter_clauses = [
        {"range": {"@timestamp": {"gte": f"now-{time_range}"}}}
    ]
    if level:
        filter_clauses.append({"term": {"level": level}})

    body = {
        "query": {
            "bool": {
                "must": [{"match": {"message": keyword}}] if keyword else [{"match_all": {}}],
                "filter": filter_clauses
            }
        },
        "sort": [{"@timestamp": {"order": "desc"}}],
        "from": (page - 1) * size, "size": size,
        "highlight": {"fields": {"message": {}}}
    }
    return es.search(index="logs-*", body=body)

def analyze_errors(time_range: str = "24h"):
    body = {
        "query": {"bool": {"filter": [
            {"term": {"level": "ERROR"}},
            {"range": {"@timestamp": {"gte": f"now-{time_range}"}}}
        ]}},
        "aggs": {
            "error_by_service": {
                "terms": {"field": "service", "size": 10},
                "aggs": {
                    "error_types": {"terms": {"field": "error_type", "size": 5}},
                    "timeline": {"date_histogram": {"field": "@timestamp", "fixed_interval": "1h"}}
                }
            }
        },
        "size": 0
    }
    return es.search(index="logs-*", body=body)
```

时间范围过滤放在 `filter` 上下文，不参与评分，性能最优。错误分析聚合按服务和错误类型交叉统计。

### 慢查询分析

日志搜索中一个常见需求是找出耗时最长的请求：

```python
def find_slow_queries(time_range: str = "1h", threshold_ms: float = 1000):
    body = {
        "query": {
            "bool": {
                "filter": [
                    {"range": {"@timestamp": {"gte": f"now-{time_range}"}}},
                    {"range": {"duration_ms": {"gte": threshold_ms}}}
                ]
            }
        },
        "sort": [{"duration_ms": {"order": "desc"}}],
        "size": 50,
        "aggs": {
            "slow_by_service": {
                "terms": {"field": "service", "size": 10},
                "aggs": {
                    "avg_duration": {"avg": {"field": "duration_ms"}},
                    "p95_duration": {
                        "percentiles": {"field": "duration_ms", "percents": [50, 95, 99]}
                    }
                }
            },
            "slow_over_time": {
                "date_histogram": {"field": "@timestamp", "fixed_interval": "5m"},
                "aggs": {
                    "avg_duration": {"avg": {"field": "duration_ms"}}
                }
            }
        }
    }
    return es.search(index="logs-*", body=body)
```

百分位数聚合（percentiles）比平均值更有参考意义：P95 表示 95% 的请求耗时低于这个值，比平均值更能反映真实用户体验。

### 日志模式识别

自动识别日志中的异常模式：

```python
def detect_log_patterns(time_range: str = "1h"):
    body = {
        "query": {
            "bool": {
                "filter": [
                    {"range": {"@timestamp": {"gte": f"now-{time_range}"}}},
                    {"term": {"level": "ERROR"}}
                ]
            }
        },
        "aggs": {
            "error_messages": {
                "terms": {
                    "field": "message.keyword",
                    "size": 20,
                    "order": {"_count": "desc"}
                },
                "aggs": {
                    "first_seen": {"min": {"field": "@timestamp"}},
                    "last_seen": {"max": {"field": "@timestamp"}},
                    "affected_services": {"cardinality": {"field": "service"}},
                    "affected_hosts": {"cardinality": {"field": "host"}}
                }
            }
        },
        "size": 0
    }
    result = es.search(index="logs-*", body=body)

    patterns = []
    for bucket in result["aggregations"]["error_messages"]["buckets"]:
        patterns.append({
            "error_message": bucket["key"],
            "count": bucket["doc_count"],
            "first_seen": bucket["first_seen"]["value_as_string"],
            "last_seen": bucket["last_seen"]["value_as_string"],
            "affected_services": bucket["affected_services"]["value"],
            "affected_hosts": bucket["affected_hosts"]["value"],
            "severity": "critical" if bucket["affected_services"]["value"] > 2 else "warning"
        })

    return sorted(patterns, key=lambda x: x["count"], reverse=True)
```

通过 message.keyword 精确匹配来聚合相同错误，可以快速发现"某个错误在短时间内大量出现"的异常模式。`cardinality` 聚合统计受影响的服务和主机数量，帮助判断影响范围。

## 日志关联分析

通过 trace_id 关联同一次请求的所有日志，排查跨服务问题：

```python
def trace_request(trace_id: str):
    body = {
        "query": {"term": {"trace_id": trace_id}},
        "sort": [{"@timestamp": {"order": "asc"}}],
        "size": 100
    }
    result = es.search(index="logs-*", body=body)

    timeline = []
    for hit in result["hits"]["hits"]:
        src = hit["_source"]
        timeline.append({
            "time": src["@timestamp"],
            "service": src["service"],
            "level": src["level"],
            "message": src["message"],
        })

    return {
        "trace_id": trace_id,
        "span_count": len(timeline),
        "timeline": timeline
    }
```

通过 trace_id 串联所有服务的日志，按时间排序形成完整调用链，对排查微服务架构中的延迟问题非常有效。

### 调用链分析与瓶颈定位

单纯的日志时间线还不够，需要计算服务间的调用延迟：

```python
from datetime import datetime
from collections import defaultdict

def analyze_trace_bottleneck(trace_id: str):
    trace_data = trace_request(trace_id)
    timeline = trace_data["timeline"]

    if len(timeline) < 2:
        return {"trace_id": trace_id, "bottleneck": None, "message": "日志不足"}

    # 计算相邻日志的时间间隔
    intervals = []
    for i in range(1, len(timeline)):
        t1 = datetime.fromisoformat(timeline[i - 1]["time"].replace("Z", "+00:00"))
        t2 = datetime.fromisoformat(timeline[i]["time"].replace("Z", "+00:00"))
        gap_ms = (t2 - t1).total_seconds() * 1000
        intervals.append({
            "from_service": timeline[i - 1]["service"],
            "to_service": timeline[i]["service"],
            "gap_ms": gap_ms,
            "from_level": timeline[i - 1]["level"],
            "to_level": timeline[i]["level"]
        })

    # 找出最大间隔作为瓶颈
    bottleneck = max(intervals, key=lambda x: x["gap_ms"])
    total_duration = sum(i["gap_ms"] for i in intervals)

    # 按服务统计耗时
    service_time = defaultdict(float)
    for interval in intervals:
        service_time[interval["to_service"]] += interval["gap_ms"]

    return {
        "trace_id": trace_id,
        "total_duration_ms": round(total_duration, 2),
        "span_count": len(timeline),
        "bottleneck": {
            "service": bottleneck["to_service"],
            "gap_ms": round(bottleneck["gap_ms"], 2),
            "percentage": round(bottleneck["gap_ms"] / total_duration * 100, 1)
        },
        "service_breakdown": {k: round(v, 2) for k, v in sorted(
            service_time.items(), key=lambda x: x[1], reverse=True
        )},
        "has_error": any(t["level"] == "ERROR" for t in timeline)
    }
```

这个分析函数不仅找出瓶颈服务，还计算每个服务的耗时占比，帮助快速定位性能问题。

## 日志告警系统

基于日志数据实现实时告警：

```python
import time
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class AlertRule:
    name: str
    condition: Callable
    threshold: float
    window_minutes: int = 5
    cooldown_minutes: int = 15
    last_triggered: float = 0

class LogAlertEngine:
    def __init__(self):
        self.rules: list[AlertRule] = []

    def add_rule(self, rule: AlertRule):
        self.rules.append(rule)

    def check_alerts(self):
        alerts = []
        now = time.time()

        for rule in self.rules:
            # 检查冷却期
            if now - rule.last_triggered < rule.cooldown_minutes * 60:
                continue

            body = {
                "query": {
                    "bool": {
                        "filter": [
                            {"range": {"@timestamp": {"gte": f"now-{rule.window_minutes}m"}}}
                        ]
                    }
                },
                "aggs": {
                    "by_service": {
                        "terms": {"field": "service", "size": 20},
                        "aggs": {
                            "error_count": {
                                "filter": {"term": {"level": "ERROR"}}
                            },
                            "error_rate": {
                                "bucket_script": {
                                    "buckets_path": {
                                        "total": "_count",
                                        "errors": "error_count._count"
                                    },
                                    "script": "params.errors / params.total * 100"
                                }
                            }
                        }
                    }
                },
                "size": 0
            }

            result = es.search(index="logs-*", body=body)

            for bucket in result["aggregations"]["by_service"]["buckets"]:
                error_rate = bucket.get("error_rate", {}).get("value", 0)
                if rule.condition(error_rate, rule.threshold):
                    alerts.append({
                        "rule": rule.name,
                        "service": bucket["key"],
                        "error_rate": round(error_rate, 2),
                        "threshold": rule.threshold,
                        "timestamp": datetime.utcnow().isoformat()
                    })
                    rule.last_triggered = now

        return alerts

# 使用示例
alert_engine = LogAlertEngine()
alert_engine.add_rule(AlertRule(
    name="高错误率告警",
    condition=lambda rate, threshold: rate > threshold,
    threshold=10.0,
    window_minutes=5,
    cooldown_minutes=15
))
```

告警系统的关键设计：冷却期防止重复告警，滑动窗口避免瞬时抖动触发误报，按服务粒度告警而非全局告警。

## 常见误区

1. **所有日志写入同一个索引**：日志量大时单索引会膨胀到数百 GB，应按日期自动滚动。
2. **日志消息不做结构化**：至少要提取 level、service、trace_id 等结构化字段。
3. **查询时不限时间范围**：不加时间范围的查询会扫描全部历史索引，性能极差。
4. **忽略索引生命周期**：日志无限增长最终会撑满磁盘，必须配置自动删除策略。
5. **所有字段都建索引**：大文本字段应关闭索引或用 keyword 类型，避免索引膨胀。
6. **日志量不做采样**：DEBUG 级别日志量巨大，生产环境应该按比例采样。
7. **告警阈值不调整**：不同服务的正常错误率不同，不应该用统一阈值。

## 工程建议

1. **使用 ILM 管理索引生命周期**：热阶段 7 天、温阶段 30 天、之后自动删除。
2. **日志采样**：DEBUG 级别日志可以按 10% 采样写入，减少存储压力。
3. **设置合理的分片数**：日志索引 1-2 个分片足够，过多分片会增加协调开销。
4. **使用 Pipeline 预处理**：ES Ingest Pipeline 可以在写入前解析日志格式。
5. **告警集成**：配合 ElastAlert 实现基于日志的自动告警。
6. **日志分级存储**：热数据用 SSD，温数据用 HDD，冷数据归档到对象存储。
7. **查询性能优化**：对高频查询字段建 keyword 索引，避免对 message 做聚合。
8. **容量规划**：按日志量 × 保留天数 × 1.5（副本+索引开销）估算存储需求。

## 小结

日志搜索的核心是高效的写入、结构化的存储和灵活的查询。ELK Stack 提供了从采集到可视化的完整方案。按日期分索引配合生命周期管理，保证系统长期稳定运行。trace_id 关联让跨服务问题排查变得高效。告警系统将被动排查变为主动发现。

### 练习一

**思路**：用正则表达式匹配 Nginx 日志的各个字段，根据状态码自动映射日志级别。

**答案**：

```python
import re
from datetime import datetime

NGINX_PATTERN = re.compile(
    r'(?P<ip>\S+) - - \[(?P<time>[^\]]+)\] '
    r'"(?P<method>\S+) (?P<path>\S+) (?P<protocol>\S+)" '
    r'(?P<status>\d+) (?P<size>\d+)'
)

def parse_nginx_log(line: str) -> dict:
    match = NGINX_PATTERN.match(line)
    if not match:
        return {"raw": line, "parse_error": True}
    g = match.groupdict()
    return {
        "@timestamp": datetime.strptime(g["time"], "%d/%b/%Y:%H:%M:%S %z").isoformat(),
        "client_ip": g["ip"],
        "method": g["method"],
        "path": g["path"],
        "status_code": int(g["status"]),
        "level": "ERROR" if int(g["status"]) >= 500 else
                 "WARN" if int(g["status"]) >= 400 else "INFO"
    }
```

**要点**：正则表达式的命名分组让代码可读性更好。根据状态码自动映射日志级别。

### 练习三

**思路**：用 date_histogram 按小时聚合，嵌套按 level 分组，找出 ERROR 最多的时段。

```python
def analyze_hourly_trend():
    body = {
        "query": {"range": {"@timestamp": {"gte": "now-24h"}}},
        "aggs": {
            "hourly": {
                "date_histogram": {"field": "@timestamp", "fixed_interval": "1h"},
                "aggs": {
                    "by_level": {"terms": {"field": "level", "size": 5}}
                }
            }
        },
        "size": 0
    }
    result = es.search(index="logs-*", body=body)
    max_error = {"hour": None, "count": 0}
    hourly = []
    for bucket in result["aggregations"]["hourly"]["buckets"]:
        levels = {b["key"]: b["doc_count"] for b in bucket["by_level"]["buckets"]}
        err = levels.get("ERROR", 0)
        if err > max_error["count"]:
            max_error = {"hour": bucket["key_as_string"], "count": err}
        hourly.append({"hour": bucket["key_as_string"], "total": bucket["doc_count"], **levels})
    return {"hourly": hourly, "peak_error_hour": max_error}
```

**要点**：嵌套聚合在一次请求中完成按时间和按级别的交叉统计，遍历结果时同步追踪 ERROR 最多的时段。

### 练习四

**思路**：分别查询当前 5 分钟和前一个 5 分钟的 ERROR 数量，计算增长率。

**答案**：

```python
def detect_error_spike(service: str = None, multiplier: float = 3.0):
    filter_current = [
        {"term": {"level": "ERROR"}},
        {"range": {"@timestamp": {"gte": "now-5m", "lt": "now"}}}
    ]
    filter_previous = [
        {"term": {"level": "ERROR"}},
        {"range": {"@timestamp": {"gte": "now-10m", "lt": "now-5m"}}}
    ]

    if service:
        filter_current.append({"term": {"service": service}})
        filter_previous.append({"term": {"service": service}})

    current_body = {
        "query": {"bool": {"filter": filter_current}},
        "aggs": {"by_service": {"terms": {"field": "service", "size": 20}}},
        "size": 0
    }
    previous_body = {
        "query": {"bool": {"filter": filter_previous}},
        "aggs": {"by_service": {"terms": {"field": "service", "size": 20}}},
        "size": 0
    }

    current = es.search(index="logs-*", body=current_body)
    previous = es.search(index="logs-*", body=previous_body)

    prev_counts = {
        b["key"]: b["doc_count"]
        for b in previous["aggregations"]["by_service"]["buckets"]
    }

    spikes = []
    for bucket in current["aggregations"]["by_service"]["buckets"]:
        svc = bucket["key"]
        curr_count = bucket["doc_count"]
        prev_count = prev_counts.get(svc, 0)

        if prev_count > 0 and curr_count >= prev_count * multiplier:
            spikes.append({
                "service": svc,
                "current_count": curr_count,
                "previous_count": prev_count,
                "ratio": round(curr_count / prev_count, 2)
            })
        elif prev_count == 0 and curr_count > 5:
            spikes.append({
                "service": svc,
                "current_count": curr_count,
                "previous_count": 0,
                "ratio": float("inf")
            })

    return {"spikes": spikes, "check_time": datetime.utcnow().isoformat()}
```

**要点**：比较相邻两个时间窗口的 ERROR 数量，用比率而非绝对值判断异常。处理了前一个窗口为零的边界情况。
