# 索引构建

## 场景引入

前面几节课我们学会了倒排索引的结构和查询方法，但一直是在内存中处理小规模数据。真实搜索引擎需要索引数十亿文档，倒排索引的大小可能超过可用内存。

假设你需要索引 10 亿网页，平均每篇 1000 个词项。即使每个 Posting 只占 8 字节，整个倒排索引也需要约 7.5TB。一台服务器的内存通常只有 256GB~1TB，根本装不下。这就是索引构建要解决的核心问题：**如何在有限内存下，高效地构建超大规模倒排索引**。

## 学习目标

1. 理解内存索引和磁盘索引的区别
2. 掌握 BSBI 和 SPIMI 两种经典索引构建算法
3. 理解分布式索引的两种分区策略
4. 用 Python 实现索引的构建、持久化和加载
5. 掌握增量索引和索引压缩的基本思想

## 为什么索引构建是一个难题

索引构建的核心挑战不是"能不能建"，而是"能不能在有限资源下高效地建"。让我们用具体数字感受一下：

```
假设场景: 索引 10 亿网页
- 平均每篇文档 1000 个词项（去重后约 300 个唯一词项）
- 总 Posting 数: 10亿 × 300 = 3000 亿个 Posting
- 每个 Posting 存储 doc_id(4字节) + tf(2字节) + 位置列表(平均8字节) = 14 字节
- 总数据量: 3000亿 × 14字节 ≈ 4.2TB

内存限制: 典型服务器 256GB 内存
- 内存只能容纳约 6% 的索引数据
- 必须使用磁盘辅助构建
```

这个数字解释了为什么不能简单地"把所有文档读进内存然后建索引"。我们需要分块处理、磁盘归并、分布式存储等一系列工程手段。

### 构建速度的重要性

索引构建速度直接决定了数据的**时效性**：

- 新闻搜索引擎：记者发布的文章需要在几分钟内被搜索到
- 电商搜索引擎：新上架的商品需要尽快出现在搜索结果中
- 社交搜索引擎：用户的帖子需要实时可搜索

如果索引构建需要 24 小时，那么用户搜索到的内容永远是昨天的。这就是为什么索引构建速度是一个核心指标。

## 内存索引 vs 磁盘索引

```
内存索引: 词典 + Posting Lists 全部在内存
  优点: 查询速度快 (纳秒级)   缺点: 容量受限于内存
  适用: 文档量 < 1000万

磁盘索引: 词典在内存, Posting Lists 在磁盘
  优点: 容量几乎无限          缺点: 磁盘 I/O 带来延迟 (毫秒级)
  适用: 大规模搜索引擎 (10亿+文档)
```

实际生产中通常采用**混合方案**：词典常驻内存（几 GB），Posting List 存磁盘，热门词项缓存在内存。

### 内存索引的容量估算

```
假设 1000 万篇文档:
- 唯一词项数: 约 500 万（中文词汇量 + 英文词汇 + 数字等）
- 词典存储: 500万 × (平均20字节词项 + 8字节指针) ≈ 140MB
- Posting Lists: 假设平均每个词项出现在 2000 篇文档
  500万 × 2000 × 8字节 ≈ 80GB
- 总内存需求: 约 80GB

结论: 1000 万篇文档的索引需要约 80GB 内存
      这在单台服务器上是可行的（高端服务器有 256GB+ 内存）
      但如果文档量增长到 1 亿，就需要磁盘索引了
```

### 磁盘索引的存储格式

磁盘索引通常将数据组织为以下格式：

```
词典文件 (dictionary.bin):
┌──────────┬──────────┬──────────┐
│ 词项1    │ 偏移量1  │ 长度1    │
│ 词项2    │ 偏移量2  │ 长度2    │
│ ...      │ ...      │ ...      │
└──────────┴──────────┴──────────┘

Posting 文件 (postings.bin):
┌────────────────────────────────┐
│ 词项1 的 Posting List          │
│ [doc_id, tf, pos1, pos2, ...]  │
├────────────────────────────────┤
│ 词项2 的 Posting List          │
│ [doc_id, tf, pos1, pos2, ...]  │
└────────────────────────────────┘
```

词典文件很小（几 GB），可以全部加载到内存。Posting 文件很大（几 TB），按需从磁盘读取。

## BSBI 算法

**Blocked Sort-Based Indexing** 的核心思想：将文档分块 → 每块内存排序建索引 → 写入磁盘段文件 → 多路归并。

```
文档集合 → 分块 → 块1/块2/块3/块4
                 ↓ 各块内存处理+排序写盘
              段文件1/段文件2/段文件3/段文件4
                 ↓ 多路归并
              最终索引
```

BSBI 的名字来源于它需要对 (term, doc_id) 对进行排序。排序是 BSBI 的核心步骤——通过排序，相同 term 的 Posting 会聚集在一起，方便后续合并。

```python
import os
import json
import tempfile
from collections import defaultdict
from typing import Iterator


class BSBIIndexer:
    def __init__(self, block_size: int = 1000, index_dir: str = None):
        self.block_size = block_size
        self.index_dir = index_dir or tempfile.mkdtemp(prefix="bsbi_")
        self.segments = []

    def build(self, documents: Iterator[tuple[int, list[str]]]):
        block = []
        block_id = 0
        for doc_id, terms in documents:
            block.append((doc_id, terms))
            if len(block) >= self.block_size:
                self.segments.append(self._process_block(block, block_id))
                block = []
                block_id += 1
        if block:
            self.segments.append(self._process_block(block, block_id))
        self._merge_segments()

    def _process_block(self, block: list, block_id: int) -> str:
        local_index = defaultdict(list)
        for doc_id, terms in block:
            seen = set()
            for term in terms:
                if term not in seen:
                    local_index[term].append(doc_id)
                    seen.add(term)

        segment_path = os.path.join(self.index_dir, f"segment_{block_id:04d}.jsonl")
        with open(segment_path, "w", encoding="utf-8") as f:
            for term in sorted(local_index.keys()):
                f.write(json.dumps({"term": term, "doc_ids": local_index[term]}, ensure_ascii=False) + "\n")
        print(f"块 {block_id}: {len(block)} 篇文档, {len(local_index)} 个词项")
        return segment_path

    def _merge_segments(self):
        open_files = [open(p, "r", encoding="utf-8") for p in self.segments]
        current = {}
        for i, f in enumerate(open_files):
            line = f.readline()
            if line:
                entry = json.loads(line)
                current[i] = (entry["term"], entry["doc_ids"])

        merged_index = defaultdict(list)
        while current:
            min_term = min(v[0] for v in current.values())
            for i in list(current.keys()):
                if current[i][0] == min_term:
                    merged_index[min_term].extend(current[i][1])
                    line = open_files[i].readline()
                    if line:
                        entry = json.loads(line)
                        current[i] = (entry["term"], entry["doc_ids"])
                    else:
                        del current[i]

        for f in open_files:
            f.close()

        final_path = os.path.join(self.index_dir, "final_index.json")
        with open(final_path, "w", encoding="utf-8") as f:
            json.dump(dict(merged_index), f, ensure_ascii=False, indent=2)
        print(f"归并完成: {len(merged_index)} 个词项")
```

### BSBI 的工作流程详解

1. **分块读取**：每次读取 `block_size` 篇文档到内存
2. **构建局部索引**：在内存中为当前块构建倒排索引
3. **排序写盘**：将局部索引按 term 排序后写入段文件
4. **多路归并**：打开所有段文件，每次取最小的 term，合并所有段中该 term 的 Posting List
5. **输出最终索引**：归并完成后得到全局有序的倒排索引

### BSBI 的内存分析

```
假设 block_size = 1000 篇文档
- 每篇文档平均 300 个唯一词项
- 每个 (term, doc_id) 对占 8 字节
- 一个块的内存需求: 1000 × 300 × 8 = 2.4MB
- 加上词典开销: 约 5MB/块

结论: BSBI 的内存需求主要取决于 block_size
      1000 篇文档的块只需要几 MB 内存
      即使是 100 万篇文档的块，也只需要几 GB 内存
```

## SPIMI 算法

**Single-Pass In-Memory Indexing** 是 BSBI 的改进：直接在内存中构建倒排索引，不需要排序步骤，内存利用率更高。

BSBI 需要先收集所有 (term, doc_id) 对，然后排序，再写盘。SPIMI 直接用哈希表（字典）构建倒排索引，省去了排序步骤。

```python
class SPIMIIndexer:
    def __init__(self, memory_limit: int = 10000, index_dir: str = None):
        self.memory_limit = memory_limit
        self.index_dir = index_dir or tempfile.mkdtemp(prefix="spimi_")
        self.segments = []

    def build(self, documents: Iterator[tuple[int, list[str]]]):
        current_index = defaultdict(list)
        current_size = 0
        block_id = 0

        for doc_id, terms in documents:
            seen = set()
            for term in terms:
                if term not in seen:
                    current_index[term].append(doc_id)
                    current_size += 1
                    seen.add(term)

            if current_size >= self.memory_limit:
                self._flush_block(current_index, block_id)
                current_index = defaultdict(list)
                current_size = 0
                block_id += 1

        if current_index:
            self._flush_block(current_index, block_id)

    def _flush_block(self, index: dict, block_id: int):
        segment_path = os.path.join(self.index_dir, f"spimi_{block_id:04d}.jsonl")
        with open(segment_path, "w", encoding="utf-8") as f:
            for term in sorted(index.keys()):
                doc_ids = sorted(set(index[term]))
                f.write(json.dumps({"term": term, "doc_ids": doc_ids}, ensure_ascii=False) + "\n")
        self.segments.append(segment_path)
```

### SPIMI 与 BSBI 的关键区别

BSBI 构建的是 `(term, doc_id)` 对的排序列表，SPIMI 构建的是直接的倒排索引。这个区别带来了两个优势：

1. **不需要排序**：SPIMI 使用哈希表直接构建索引，省去了排序的 O(n log n) 开销
2. **内存利用率更高**：BSBI 需要额外存储 (term, doc_id) 对，SPIMI 直接存储 Posting List

### BSBI vs SPIMI

| 特性 | BSBI | SPIMI |
|------|------|-------|
| 内存数据结构 | 排序的 (term, doc_id) 列表 | 倒排索引 |
| 是否需要排序 | 是 | 否 |
| 内存利用率 | 较低 | 较高 |
| 构建速度 | 较慢 | 较快 |
| 实现复杂度 | 较高 | 较低 |
| 适用场景 | 教学演示 | 生产环境 |

### 内存监控：何时刷盘

SPIMI 的关键决策是**何时将内存中的索引刷到磁盘**。`memory_limit` 参数控制这个阈值。选择过小会导致频繁刷盘，选择过大会导致内存溢出。

```python
import sys

def estimate_index_size(index: dict) -> int:
    """估算内存中索引的字节数"""
    total = 0
    for term, doc_ids in index.items():
        total += sys.getsizeof(term)  # 词项本身
        total += sys.getsizeof(doc_ids)  # Posting List
        total += len(doc_ids) * 8  # 每个 doc_id 约 8 字节
    return total


class SPIMIWithMemoryMonitor(SPIMIIndexer):
    def build(self, documents: Iterator[tuple[int, list[str]]]):
        current_index = defaultdict(list)
        block_id = 0

        for doc_id, terms in documents:
            seen = set()
            for term in terms:
                if term not in seen:
                    current_index[term].append(doc_id)
                    seen.add(term)

            # 每 1000 篇文档检查一次内存
            if doc_id % 1000 == 0:
                size_mb = estimate_index_size(current_index) / (1024 * 1024)
                if size_mb > self.memory_limit:
                    print(f"内存使用 {size_mb:.1f}MB 超过限制，刷盘...")
                    self._flush_block(current_index, block_id)
                    current_index = defaultdict(list)
                    block_id += 1

        if current_index:
            self._flush_block(current_index, block_id)
```

## 索引持久化

索引构建完成后需要持久化到磁盘，以便后续加载使用。持久化格式的选择直接影响加载速度和存储效率。

```python
class PersistentIndex:
    def __init__(self):
        self.index: dict[str, list[int]] = {}
        self.doc_store: dict[int, dict] = {}

    def add_document(self, doc_id: int, terms: list[str], metadata: dict = None):
        self.doc_store[doc_id] = metadata or {}
        seen = set()
        for term in terms:
            if term not in seen:
                if term not in self.index:
                    self.index[term] = []
                self.index[term].append(doc_id)
                seen.add(term)

    def save(self, path: str):
        data = {
            "index": self.index,
            "doc_store": {str(k): v for k, v in self.doc_store.items()},
        }
        with open(path, "w", encoding="utf-8") as f:
            json.dump(data, f, ensure_ascii=False, indent=2)
        size = os.path.getsize(path)
        print(f"索引已保存: {path} ({size / 1024:.1f} KB)")

    @classmethod
    def load(cls, path: str) -> "PersistentIndex":
        with open(path, "r", encoding="utf-8") as f:
            data = json.load(f)
        idx = cls()
        idx.index = data["index"]
        idx.doc_store = {int(k): v for k, v in data["doc_store"].items()}
        return idx

    def search(self, query_terms: list[str]) -> list[dict]:
        if not query_terms:
            return []
        result_sets = [set(self.index.get(t, [])) for t in query_terms]
        doc_ids = set.intersection(*result_sets) if result_sets else set()
        return [{"doc_id": did, **self.doc_store.get(did, {})} for did in sorted(doc_ids)]
```

### 持久化格式的选择

JSON 格式适合教学和小规模数据，但生产环境通常使用更高效的格式：

```
JSON 格式:
  优点: 可读性强，调试方便
  缺点: 文本解析慢，存储空间大（比二进制大 3-5 倍）
  适用: 小规模索引（< 100MB）

二进制格式 (如 Protocol Buffers, MessagePack):
  优点: 解析快，存储空间小
  缺点: 不可读，需要额外的序列化/反序列化代码
  适用: 大规模索引（> 1GB）

自定义格式 (如 Lucene 的 .tim/.doc 格式):
  优点: 针对索引特性优化，支持随机访问
  缺点: 实现复杂
  适用: 生产级搜索引擎
```

### 增量索引

实际搜索引擎不是一次性构建索引，而是持续更新。增量索引的核心挑战是**如何在不停服的情况下更新索引**。

```python
class IncrementalIndex:
    """支持增量更新的索引"""

    def __init__(self, base_index_path: str = None):
        self.base_index = PersistentIndex.load(base_index_path) if base_index_path else PersistentIndex()
        self增量_index = PersistentIndex()  # 内存中的增量索引
        self.deleted_ids: set[int] = set()  # 已删除的文档

    def add_document(self, doc_id: int, terms: list[str], metadata: dict = None):
        self增量_index.add_document(doc_id, terms, metadata)
        self.deleted_ids.discard(doc_id)  # 如果之前被删除，取消删除标记

    def delete_document(self, doc_id: int):
        self.deleted_ids.add(doc_id)

    def search(self, query_terms: list[str]) -> list[dict]:
        # 搜索基础索引
        base_results = self.base_index.search(query_terms)
        # 搜索增量索引
       增量_results = self增量_index.search(query_terms)
        # 合并结果，排除已删除的文档
        all_results = {}
        for r in base_results + 增量_results:
            doc_id = r["doc_id"]
            if doc_id not in self.deleted_ids:
                all_results[doc_id] = r
        return sorted(all_results.values(), key=lambda x: x["doc_id"])

    def merge_to_base(self, output_path: str):
        """将增量索引合并到基础索引"""
        for term, doc_ids in self增量_index.index.items():
            for doc_id in doc_ids:
                if doc_id not in self.deleted_ids:
                    self.base_index.add_document(doc_id, [term],
                                                  self增量_index.doc_store.get(doc_id))
        self.base_index.save(output_path)
        self增量_index = PersistentIndex()
        self.deleted_ids = set()
```

### 合并策略

增量索引的合并策略有两种：

1. **立即合并**：每次有新文档就更新基础索引。简单但效率低，因为每次都要重写整个索引。
2. **批量合并**：增量索引积累到一定大小后，批量合并到基础索引。效率高但有延迟。

实际系统通常采用**分层合并**策略（类似 LSM-Tree）：

```
层级 0: 内存增量索引 (最新数据)
  ↓ 累积到阈值后刷盘
层级 1: 磁盘段文件 (最近数据)
  ↓ 累积到阈值后合并
层级 2: 基础索引 (历史数据)
```

## 分布式索引

当单机无法承载全部索引时，需要将索引分布到多台机器上：

**文档分区**：每台机器存储一部分文档的完整索引。查询广播到所有机器，合并结果。
- 优点：查询可并行，扩展性好
- 缺点：每台机器处理所有词项

**词项分区**：每台机器存储一部分词项的 Posting List。按词项路由查询。
- 优点：每台机器数据量更小
- 缺点：多词查询需跨机器通信

```python
class DistributedIndexRouter:
    def __init__(self, strategy: str = "document", num_shards: int = 3):
        self.strategy = strategy
        self.num_shards = num_shards
        self.shards = [PersistentIndex() for _ in range(num_shards)]

    def add_document(self, doc_id: int, terms: list[str], metadata: dict = None):
        if self.strategy == "document":
            shard_id = doc_id % self.num_shards
            self.shards[shard_id].add_document(doc_id, terms, metadata)
        else:
            for term in terms:
                shard_id = hash(term) % self.num_shards
                self.shards[shard_id].add_document(doc_id, terms, metadata)

    def search(self, query_terms: list[str]) -> list[dict]:
        if self.strategy == "document":
            all_results = []
            for shard in self.shards:
                all_results.extend(shard.search(query_terms))
            return sorted(all_results, key=lambda x: x["doc_id"])
        else:
            result_sets = []
            for term in query_terms:
                shard_id = hash(term) % self.num_shards
                results = self.shards[shard_id].search([term])
                result_sets.append(set(r["doc_id"] for r in results))
            common_ids = set.intersection(*result_sets) if result_sets else set()
            return [{"doc_id": did} for did in sorted(common_ids)]
```

### 文档分区 vs 词项分区的选择

两种分区策略各有优劣，选择取决于查询模式：

```
文档分区适合:
- 查询词项数量少（1-3 个词）
- 需要快速返回结果（并行查询）
- 文档量远大于词项量

词项分区适合:
- 查询词项数量多（5+ 个词）
- 词项分布不均匀（少数词项很热门）
- 需要高效的单词项查询
```

实际系统通常采用**文档分区**，因为：
1. 查询通常是 2-4 个词，并行查询的开销可控
2. 文档分区的扩展性更好——增加机器只需要迁移部分文档
3. 词项分区的跨机器通信开销难以控制

### 一致性哈希

分布式索引的一个关键问题是**如何分配数据到机器**。简单的取模哈希（`doc_id % num_shards`）有一个问题：当机器数量变化时，几乎所有数据都需要重新分配。

一致性哈希解决了这个问题：

```python
import hashlib

class ConsistentHash:
    def __init__(self, nodes: list[str], virtual_nodes: int = 150):
        self.ring = {}
        self.sorted_keys = []
        for node in nodes:
            for i in range(virtual_nodes):
                key = self._hash(f"{node}:{i}")
                self.ring[key] = node
                self.sorted_keys.append(key)
        self.sorted_keys.sort()

    def _hash(self, key: str) -> int:
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def get_node(self, doc_id: int) -> str:
        if not self.ring:
            return None
        h = self._hash(str(doc_id))
        for key in self.sorted_keys:
            if h <= key:
                return self.ring[key]
        return self.ring[self.sorted_keys[0]]
```

一致性哈希的优势：当增加或减少机器时，只需要重新分配少量数据（约 1/N 的数据），而不是全部数据。

## 常见误区

1. **认为索引构建是一次性操作**：搜索引擎需要持续更新索引（增量索引）。每天有新文档发布、旧文档更新、过期文档删除，索引必须跟上这些变化。
2. **忽略索引存储格式**：JSON 可读但效率低，生产环境应使用二进制格式。一个 10GB 的 JSON 索引可能只需要 2-3GB 的二进制格式。
3. **过早引入分布式**：单机可支撑千万级文档，不要过早分布式。分布式带来的一致性、故障处理、网络通信等问题会显著增加系统复杂度。
4. **不考虑构建速度**：索引构建速度决定数据时效性。如果构建需要 24 小时，用户搜索到的内容永远是昨天的。
5. **忽略内存监控**：索引构建过程中内存使用是动态变化的，必须监控内存使用情况，避免 OOM（Out of Memory）。
6. **混淆词项和词**：一个中文词可能被分词器切分成多个词项，索引构建时要注意分词的一致性——索引和查询必须使用同一个分词器。
7. **忘记去重**：同一篇文档中同一个词项可能出现多次，索引时需要记录词频（term frequency），但 Posting List 中不应有重复的 doc_id。

## 工程建议

1. **从 SPIMI 开始**：比 BSBI 更高效，实现更简单。SPIMI 不需要排序步骤，内存利用率更高。
2. **监控内存使用**：构建过程中避免 OOM。使用 `memory_limit` 参数控制刷盘时机，定期检查内存使用情况。
3. **使用 SSD**：磁盘 I/O 是瓶颈，SSD 比 HDD 快 10~100 倍。如果预算允许，索引构建服务器应该全部使用 SSD。
4. **并行构建**：多个块可并行处理，充分利用多核 CPU。使用 `ThreadPoolExecutor` 或 `ProcessPoolExecutor` 并行处理多个块。
5. **索引压缩**：对 Posting List 使用 VByte 或 PForDelta 压缩。压缩可以减少 50-80% 的存储空间和 I/O 开销。
6. **批量合并**：增量索引积累到一定大小后再合并到基础索引，避免频繁的全量重建。
7. **监控构建指标**：记录每块的处理时间、内存使用、磁盘写入量，便于定位瓶颈和优化。
8. **测试构建正确性**：索引构建完成后，使用已知查询验证结果的正确性。随机抽查几个词项的 Posting List，确认文档数量和内容正确。

## 小结

- **内存索引 vs 磁盘索引**：小规模用内存，大规模需要磁盘
- **BSBI**：先排序再构建，逻辑清晰但效率较低
- **SPIMI**：直接构建倒排索引，内存利用率更高
- **多路归并**：将多个段文件合并为最终索引
- **持久化**：JSON 格式序列化，支持快速加载
- **增量索引**：支持不停服的索引更新
- **分布式索引**：文档分区和词项分区两种策略

索引构建是搜索引擎的基础设施。下节课我们将把前五节课的知识整合起来，构建一个完整的倒排索引系统。

### 练习一

**思路**：分块后提交给线程池，每个线程独立处理一个块，最后归并。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed


class ParallelBSBIIndexer(BSBIIndexer):
    def __init__(self, block_size=1000, max_workers=4, index_dir=None):
        super().__init__(block_size, index_dir)
        self.max_workers = max_workers

    def build(self, documents):
        blocks = []
        block = []
        for doc_id, terms in documents:
            block.append((doc_id, terms))
            if len(block) >= self.block_size:
                blocks.append(block); block = []
        if block:
            blocks.append(block)

        with ThreadPoolExecutor(max_workers=self.max_workers) as executor:
            futures = {executor.submit(self._process_block, b, i): i for i, b in enumerate(blocks)}
            for future in as_completed(futures):
                self.segments.append(future.result())

        self.segments.sort()
        self._merge_segments()
```

**要点**：块之间处理独立，天然适合并行；段文件名用 block_id 避免冲突。归并阶段必须串行，因为需要保证全局有序。

### 练习二

增量索引方案：

1. **检测变更**：每篇文档存储 `content_hash` 和 `last_modified`，增量抓取时对比 hash
2. **不停服更新**：新文档写入内存增量索引，定时合并到主索引，原子指针切换
3. **处理删除**：使用删除列表（或布隆过滤器）标记已删除文档，查询时过滤

```
新文档 → 增量索引(RAM) → 定时合并 → 新磁盘索引 ← 原子切换
查询 → 路由层 → 主索引 + 增量索引，排除删除列表
```

**要点**：Lucene 使用类似 Segment 策略；删除用标记删除而非物理删除；增量索引大小需控制在内存可承受范围内。

### 练习三

**思路**：VByte 编码用 7 位存储数据，1 位作为延续标志。小于 128 的数用 1 字节，小于 16384 的数用 2 字节，以此类推。

```python
def vbyte_encode(number: int) -> bytes:
    """将整数编码为 VByte 格式"""
    if number < 0:
        raise ValueError("VByte 不支持负数")
    result = []
    while True:
        result.append(number & 0x7F)  # 取低 7 位
        number >>= 7
        if number == 0:
            break
    result.reverse()
    # 最高位设为 1 表示最后一个字节
    result[-1] |= 0x80
    return bytes(result)


def vbyte_decode(data: bytes) -> tuple[int, int]:
    """解码 VByte，返回 (数值, 消耗的字节数)"""
    result = 0
    for i, byte in enumerate(data):
        result = (result << 7) | (byte & 0x7F)
        if byte & 0x80:  # 最高位为 1，表示结束
            return result, i + 1
    raise ValueError("无效的 VByte 编码")


def vbyte_encode_list(numbers: list[int]) -> bytes:
    """编码一个整数列表"""
    return b"".join(vbyte_encode(n) for n in numbers)


def vbyte_decode_list(data: bytes) -> list[int]:
    """解码一个整数列表"""
    result = []
    pos = 0
    while pos < len(data):
        value, consumed = vbyte_decode(data[pos:])
        result.append(value)
        pos += consumed
    return result


# 测试
original = [1, 127, 128, 16383, 16384, 1000000]
encoded = vbyte_encode_list(original)
decoded = vbyte_decode_list(encoded)
print(f"原始: {original}")
print(f"解码: {decoded}")
print(f"压缩率: {len(encoded) / (len(original) * 4):.2%}")
```

**要点**：VByte 编码对小数值非常高效（大部分 doc_id 差值很小）；压缩率取决于数值分布；实际系统中通常先对 Posting List 做差值编码（delta encoding），再用 VByte 压缩。

### 练习五

**思路**：实现三级索引结构，内存增量层达到阈值后刷到磁盘段层，磁盘段层数量达到阈值后合并到基础索引层。

```python
class LSMIndex:
    def __init__(self, memory_limit: int = 10000, segment_limit: int = 5):
        self.memory_index = defaultdict(list)
        self.memory_size = 0
        self.memory_limit = memory_limit
        self.segments: list[dict] = []  # 磁盘段层
        self.segment_limit = segment_limit
        self.base_index: dict[str, list[int]] = {}  # 基础索引层

    def add_document(self, doc_id: int, terms: list[str]):
        seen = set()
        for term in terms:
            if term not in seen:
                self.memory_index[term].append(doc_id)
                self.memory_size += 1
                seen.add(term)

        if self.memory_size >= self.memory_limit:
            self._flush_memory()

    def _flush_memory(self):
        """将内存索引刷到磁盘段层"""
        segment = {}
        for term, doc_ids in self.memory_index.items():
            segment[term] = sorted(set(doc_ids))
        self.segments.append(segment)
        self.memory_index = defaultdict(list)
        self.memory_size = 0

        if len(self.segments) >= self.segment_limit:
            self._merge_segments()

    def _merge_segments(self):
        """合并磁盘段到基础索引"""
        merged = defaultdict(list)
        for segment in self.segments:
            for term, doc_ids in segment.items():
                merged[term].extend(doc_ids)

        for term, doc_ids in merged.items():
            if term in self.base_index:
                self.base_index[term] = sorted(set(self.base_index[term] + doc_ids))
            else:
                self.base_index[term] = sorted(set(doc_ids))

        self.segments = []

    def search(self, query_terms: list[str]) -> list[int]:
        """查询时搜索所有层级"""
        if not query_terms:
            return []

        result_sets = []

        # 搜索基础索引
        for term in query_terms:
            if term in self.base_index:
                result_sets.append(set(self.base_index[term]))

        # 搜索磁盘段
        for segment in self.segments:
            for term in query_terms:
                if term in segment:
                    result_sets.append(set(segment[term]))

        # 搜索内存索引
        for term in query_terms:
            if term in self.memory_index:
                result_sets.append(set(self.memory_index[term]))

        if not result_sets:
            return []
        return sorted(set.intersection(*result_sets))
```

**要点**：LSM-Tree 结构是 LevelDB、RocksDB 等存储引擎的核心思想；内存层保证写入速度，磁盘层保证查询效率；合并策略需要平衡写入延迟和查询性能。
