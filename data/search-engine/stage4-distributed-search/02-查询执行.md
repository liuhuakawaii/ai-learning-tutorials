# 查询执行流程

## 场景引入

你在 Elasticsearch 中执行了一个看似简单的查询，返回了 10 条结果。但你有没有想过，这 10 条结果背后发生了什么？查询被发送到了哪个节点？每个分片各自做了什么工作？结果是如何汇聚并排序的？

理解查询执行流程，不仅能帮你写出更高效的查询，还能在排查慢查询时知道瓶颈在哪里。比如你发现一个查询在 3 个分片上分别耗时 50ms、60ms、500ms，总耗时是 500ms 而不是 160ms——因为协调节点必须等待最慢的分片返回。找到那个 500ms 的分片并优化它，比优化其他两个分片有效得多。

这门课会从底层拆解 Elasticsearch 的查询执行机制，让你不仅知道"怎么查"，更知道"为什么这么查"以及"慢在哪里"。

## 学习目标

完成本课学习后，你将能够：

1. 理解 Query-Then-Fetch 两阶段查询模型的完整细节
2. 掌握 scatter/gather 模式在分布式搜索中的作用
3. 了解 DFS Query-Then-Fetch 的使用场景和性能代价
4. 使用 Python 和 REST API 追踪查询执行过程
5. 掌握 Scroll、Search After、PIT 等分页机制的原理和适用场景
6. 能够通过 profile API 定位查询瓶颈

## 查询的基本流程

Elasticsearch 的分布式搜索采用 **Query-Then-Fetch** 模型，分为两个阶段。这个设计思想可以追溯到 2004 年 Google 的 MapReduce 论文——将计算分发到数据所在的位置，再汇聚结果。

```
┌─────────────────────────────────────────────────────────────┐
│                   Query-Then-Fetch 流程                      │
│                                                             │
│  Phase 1: Query Phase（查询阶段）                            │
│  ┌──────────┐                                               │
│  │  Client   │──── search request ────→ Coordinating Node   │
│  └──────────┘                            │                  │
│                                          ▼                  │
│                    ┌───────┬───────┬───────┐                │
│                    │Shard 0│Shard 1│Shard 2│                │
│                    │ 10个ID│ 10个ID│ 10个ID│                │
│                    │+score │+score │+score │                │
│                    └───┬───┴───┬───┴───┬───┘                │
│                        ▼       ▼       ▼                    │
│                  Coordinating Node 汇聚排序                  │
│                  从30个结果中选出 Top 10                      │
│                                                             │
│  Phase 2: Fetch Phase（获取阶段）                            │
│                    ┌───────┬───────┬───────┐                │
│                    │Shard 0│Shard 1│Shard 2│                │
│                    │ 3个doc│ 5个doc│ 2个doc│                │
│                    └───┬───┴───┬───┴───┬───┘                │
│                        ▼       ▼       ▼                    │
│                  Coordinating Node 组装最终结果              │
│                  返回 10 条完整文档给 Client                  │
└─────────────────────────────────────────────────────────────┘
```

### Query Phase

协调节点将搜索请求转发给索引中的**每一个分片**（主分片或副本分片选其一）。每个分片在本地执行查询，返回匹配文档的 `_id` 和 `_score`。Query Phase 只返回文档标识符和排序值，**不返回完整文档内容**。

Query Phase 内部的工作流程：

1. 协调节点解析查询 DSL，构建搜索上下文（Search Context）
2. 将请求并行发送到所有相关分片
3. 每个分片在本地 Lucene 索引上执行查询
4. 分片对结果排序，取 Top N 个文档的 `_id` 和排序值
5. 将结果返回给协调节点

### Fetch Phase

协调节点对所有分片返回的结果进行全局排序，取 Top N，然后根据 `_id` 从对应分片获取完整文档。

Fetch Phase 的关键点：

1. 协调节点合并所有分片的结果，全局排序取 Top N
2. 向包含目标文档的分片发送 GET 请求
3. 分片返回完整文档的 `_source` 字段
4. 协调节点组装最终响应返回给客户端

```bash
# 使用 profile API 查看查询执行细节
GET /products/_search
{
  "profile": true,
  "query": { "match": { "name": "机械键盘" } },
  "size": 3
}
```

profile 结果会显示每个分片的执行耗时和查询细节：

```json
{
  "shards": [{
    "id": "[node-1][index-name][0]",
    "searches": [{
      "query": [{
        "type": "TermQuery",
        "description": "name:机械",
        "time_in_nanos": 125000
      }],
      "collector": [{
        "name": "SimpleTopScoreDocCollector",
        "reason": "search_top_hits"
      }]
    }]
  }]
}
```

## Python 实现查询追踪

```python
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")

response = es.search(
    index="products",
    body={
        "query": {
            "bool": {
                "must": [{"match": {"name": "机械键盘"}}],
                "filter": [{"range": {"price": {"gte": 100, "lte": 500}}}]
            }
        },
        "size": 10,
        "sort": [{"price": "asc"}]
    }
)

print(f"总命中数: {response['hits']['total']['value']}")
print(f"查询耗时: {response['took']}ms")

for hit in response['hits']['hits']:
    print(f"  ID: {hit['_id']}, 分数: {hit['_score']}")
```

使用 explain 查看评分详情：

```python
response = es.search(
    index="products",
    body={
        "explain": True,
        "query": {"match": {"name": "蓝牙耳机"}},
        "size": 2
    }
)

for hit in response['hits']['hits']:
    explanation = hit.get('_explanation', {})
    print(f"文档 {hit['_id']}: 分数={explanation.get('value', 'N/A')}")
    # 打印评分明细
    for detail in explanation.get('details', []):
        print(f"  - {detail.get('description', '')}: {detail.get('value', 0)}")
```

## DFS Query-Then-Fetch

标准 Query-Then-Fetch 有一个问题：每个分片只根据自己的本地数据计算 IDF（逆文档频率）。如果数据在分片间分布不均匀，评分会有偏差。

```
┌─────────────────────────────────────────────────────────────┐
│              IDF 计算差异问题                                │
│                                                             │
│  Shard 0: 文档 1000 条，包含"机械键盘" 50 条                 │
│           IDF("机械键盘") = log(1000/50) = 3.0              │
│                                                             │
│  Shard 1: 文档 1000 条，包含"机械键盘" 5 条                  │
│           IDF("机械键盘") = log(1000/5) = 5.3               │
│                                                             │
│  同一个查询词，在不同分片上的 IDF 值差距很大                  │
└─────────────────────────────────────────────────────────────┘
```

**DFS Query-Then-Fetch** 在正式查询前增加一个预查询阶段，先从所有分片收集词频信息，计算全局 IDF。

```bash
GET /products/_search?search_type=dfs_query_then_fetch
{
  "query": { "match": { "name": "机械键盘" } }
}
```

用 Python 使用 DFS：

```python
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")

# 标准查询
response_normal = es.search(
    index="products",
    body={"query": {"match": {"name": "机械键盘"}}},
    search_type="query_then_fetch"
)

# DFS 查询
response_dfs = es.search(
    index="products",
    body={"query": {"match": {"name": "机械键盘"}}},
    search_type="dfs_query_then_fetch"
)

# 对比评分差异
print("标准查询结果:")
for hit in response_normal["hits"]["hits"]:
    print(f"  ID: {hit['_id']}, Score: {hit['_score']:.4f}")

print("\nDFS 查询结果:")
for hit in response_dfs["hits"]["hits"]:
    print(f"  ID: {hit['_id']}, Score: {hit['_score']:.4f}")
```

使用场景：小索引多分片、需要精确评分排序、性能对比测试。注意：DFS 会增加额外的网络开销（一次额外的 round trip），大多数场景标准 Query-Then-Fetch 够用。在生产环境中，DFS 通常只用于 A/B 测试中需要精确比较相关性的场景。

## 分片选择策略

```
┌─────────────────────────────────────────────────────────────┐
│                   分片选择策略                                │
│                                                             │
│  1. 主分片和副本分片二选一，选负载较低的那个                   │
│  2. 使用 routing 时只查询指定分片                             │
│  3. 按 shard preference 指定优先级                           │
│     _local: 优先使用协调节点本地的分片                        │
│     _primary: 只查询主分片（写后读一致性）                    │
│     _only_nodes:node-1: 限定在某些节点上的分片                │
│     _prefer_nodes:node-1,node-2: 优先某些节点                │
│     custom_value: 自定义值，相同值路由到相同分片              │
└─────────────────────────────────────────────────────────────┘
```

```python
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")

# 写后读一致性：写入后立即搜索使用 _primary
es.index(index="products", id="123", document={"name": "新商品"})

response = es.search(
    index="products",
    body={"query": {"term": {"_id": "123"}}},
    params={"preference": "_primary"}
)
```

### preference 对缓存的影响

Elasticsearch 的分片级缓存（shard request cache）依赖于请求被路由到相同的分片。使用 preference 可以确保同一用户的请求总是路由到同一分片，提升缓存命中率。

```python
def search_with_user_affinity(es, user_id, query_body):
    """使用用户 ID 作为 preference，确保缓存亲和性"""
    response = es.search(
        index="products",
        body=query_body,
        preference=f"user_{user_id}"
    )
    return response

# 同一用户的多次查询会路由到相同的分片，提升缓存命中率
user_query = {
    "query": {"match": {"name": "手机"}},
    "size": 10
}
result = search_with_user_affinity(es, "user_001", user_query)
```

## Scroll 和 Search After

### Scroll API（适合离线遍历）

Scroll API 创建一个搜索上下文（search context），保持搜索状态，适合批量遍历大量文档。

```python
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")

# 创建 scroll 上下文
response = es.search(
    index="products",
    body={"query": {"match_all": {}}, "size": 100},
    scroll="2m"  # 搜索上下文保持 2 分钟
)

scroll_id = response["_scroll_id"]
all_docs = response["hits"]["hits"]
total = response["hits"]["total"]["value"]

print(f"总文档数: {total}")
print(f"第一批: {len(response['hits']['hits'])} 条")

while True:
    response = es.scroll(scroll_id=scroll_id, scroll="2m")
    hits = response["hits"]["hits"]
    if not hits:
        break
    all_docs.extend(hits)
    print(f"已获取: {len(all_docs)} 条")

# 必须清除 scroll 上下文释放资源
es.clear_scroll(scroll_id=scroll_id)
print(f"遍历完成，共获取 {len(all_docs)} 条文档")
```

Scroll 的资源消耗：每个 scroll 上下文会占用堆内存来保存查询结果的位图（bitset）。大量并发的 scroll 请求会导致 OOM。

### Search After（适合实时翻页）

Search After 不保存搜索上下文，而是基于上一页最后一条的排序值来定位下一页。性能稳定，不随页数增加而下降。

```python
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")

def search_after_pagination(es, index, query_body, page_size=20):
    """使用 search_after 实现深度分页"""
    sort_fields = [{"_id": "asc"}]  # 必须有唯一排序字段作为 tiebreaker
    search_after = None
    all_results = []

    while True:
        body = {
            **query_body,
            "size": page_size,
            "sort": sort_fields
        }
        if search_after:
            body["search_after"] = search_after

        response = es.search(index=index, body=body)
        hits = response["hits"]["hits"]

        if not hits:
            break

        all_results.extend(hits)
        search_after = hits[-1]["sort"]

    return all_results

# 使用示例
results = search_after_pagination(
    es, "products",
    {"query": {"match_all": {}}},
    page_size=50
)
print(f"共获取 {len(results)} 条文档")
```

### Point In Time (PIT)

ES 7.10 引入了 Point In Time，提供了一致性视图快照。与 search_after 配合使用，可以在不保持搜索上下文的情况下实现一致性分页。

```python
from elasticsearch import Elasticsearch

es = Elasticsearch("http://localhost:9200")

# 创建 PIT
pit_response = es.open_point_in_time(index="products", keep_alive="5m")
pit_id = pit_response["id"]

# 使用 PIT + search_after 分页
response = es.search(
    body={
        "size": 20,
        "sort": [{"price": "asc"}, {"_id": "asc"}],
        "pit": {"id": pit_id, "keep_alive": "5m"},
        "query": {"match_all": {}}
    }
)

# 获取最后一条的 sort 值
last_sort = response["hits"]["hits"][-1]["sort"]

# 下一页，使用 PIT 确保一致性视图
response = es.search(
    body={
        "size": 20,
        "sort": [{"price": "asc"}, {"_id": "asc"}],
        "pit": {"id": pit_id, "keep_alive": "5m"},
        "search_after": last_sort,
        "query": {"match_all": {}}
    }
)

# 关闭 PIT
es.close_point_in_time(id=pit_id)
```

## 搜索上下文的生命周期

理解搜索上下文对排查内存问题至关重要：

```
┌─────────────────────────────────────────────────────────────┐
│               搜索上下文生命周期                              │
│                                                             │
│  查询开始 ──→ 创建 Search Context                            │
│           ──→ 分配内存保存 bitset 和排序队列                  │
│           ──→ 执行 Query Phase                               │
│           ──→ 执行 Fetch Phase                               │
│           ──→ 返回结果后释放 Search Context                   │
│                                                             │
│  Scroll: Context 持续存在直到超时或 clear_scroll              │
│  Search After: 无持久 Context，每次查询独立                   │
│  PIT: 轻量级快照，只保存 Lucene segment 引用                  │
└─────────────────────────────────────────────────────────────┘
```

用 Python 监控搜索上下文：

```python
def check_search_contexts(es):
    """查看当前搜索上下文数量"""
    nodes_stats = es.nodes.stats(metric=["search"])
    for node_id, node_data in nodes_stats["nodes"].items():
        search_stats = node_data.get("indices", {}).get("search", {})
        open_contexts = search_stats.get("open_contexts", 0)
        query_total = search_stats.get("query_total", 0)
        query_time = search_stats.get("query_time_in_millis", 0)
        print(f"节点 {node_data['name']}:")
        print(f"  打开的搜索上下文: {open_contexts}")
        print(f"  累计查询次数: {query_total}")
        print(f"  累计查询耗时: {query_time}ms")

check_search_contexts(es)
```

## Multi Search API

批量查询可以减少网络 round trip，适合首页需要同时获取搜索结果和聚合数据的场景。

```python
from elasticsearch import Elasticsearch
from elasticsearch.helpers import bulk

es = Elasticsearch("http://localhost:9200")

def multi_search_demo(es):
    """使用 msearch 一次执行多个查询"""
    searches = [
        # 第一个查询：获取搜索结果
        {"index": "products"},
        {"query": {"match": {"name": "手机"}}, "size": 10},
        # 第二个查询：获取分类聚合
        {"index": "products"},
        {"size": 0, "aggs": {"categories": {"terms": {"field": "category", "size": 10}}}},
        # 第三个查询：获取品牌聚合
        {"index": "products"},
        {"size": 0, "aggs": {"brands": {"terms": {"field": "brand", "size": 10}}}},
    ]

    response = es.msearch(body=searches)

    # 解析结果
    for i, result in enumerate(response["responses"]):
        if "hits" in result:
            print(f"查询 {i}: 命中 {result['hits']['total']['value']} 条")
        elif "aggregations" in result:
            for agg_name, agg_data in result["aggregations"].items():
                print(f"查询 {i} 聚合 {agg_name}:")
                for bucket in agg_data["buckets"][:5]:
                    print(f"  {bucket['key']}: {bucket['doc_count']}")

multi_search_demo(es)
```

## 常见误区

1. **认为查询直接到达目标分片**：协调节点会把请求转发到所有相关分片，分片多时网络开销很大。

2. **忽略评分准确性**：默认 IDF 是分片级别的。排序准确性很重要时应使用 `dfs_query_then_fetch`。

3. **Scroll 用于实时翻页**：Scroll 保持搜索上下文消耗大量内存，只适合离线遍历。实时翻页用 `search_after`。

4. **认为 profile API 代表生产性能**：开启 profile 会显著增加查询耗时（通常增加 2-10 倍），只在调试时使用。

5. **过度使用 from+size**：深度分页导致协调节点收集 (from+size)*分片数 个结果，开销巨大。ES 默认限制 `max_result_window` 为 10000。

6. **忽略 search_after 的排序要求**：search_after 必须有唯一排序字段作为 tiebreaker，否则可能漏数据或重复。

7. **忘记清除 scroll 上下文**：scroll 超时后自动清除，但大量并发 scroll 应主动 clear_scroll 释放资源。

## 工程建议

1. **监控 Query Phase 耗时**：通过 `?profile=true` 或慢查询日志定位最慢分片。

```python
from elasticsearch import Elasticsearch
import json

es = Elasticsearch("http://localhost:9200")

def analyze_shard_performance(es, index, query_body):
    """分析每个分片的查询性能"""
    response = es.search(index=index, body={"profile": True, **query_body})

    shard_times = []
    for shard in response.get("profile", {}).get("shards", []):
        shard_id = shard["id"]
        total_time_ns = 0
        for search in shard.get("searches", []):
            for query in search.get("query", []):
                total_time_ns += query.get("time_in_nanos", 0)
        shard_times.append({
            "shard": shard_id,
            "time_ms": total_time_ns / 1_000_000
        })

    # 找出最慢的分片
    shard_times.sort(key=lambda x: x["time_ms"], reverse=True)
    print("分片性能分析:")
    for st in shard_times:
        print(f"  {st['shard']}: {st['time_ms']:.2f}ms")

    if shard_times:
        max_time = shard_times[0]["time_ms"]
        min_time = shard_times[-1]["time_ms"]
        if max_time > min_time * 3:
            print(f"警告: 最慢分片耗时是最快分片的 {max_time/max(min_time,0.001):.1f} 倍")

    return {
        "total_time_ms": response["took"],
        "shard_details": shard_times
    }

result = analyze_shard_performance(
    es, "products",
    {"query": {"match": {"name": "机械键盘"}}, "size": 10}
)
print(json.dumps(result, indent=2, ensure_ascii=False))
```

2. **使用 preference 提升缓存命中率**：相同用户查询路由到相同分片，利于缓存。

3. **深度分页用 search_after**：避免 from+size 超过 10000。

4. **批量查询减少 Round Trip**：使用 `_msearch` API 一次执行多个搜索。

5. **合理设置 timeout**：防止单个慢查询拖垮集群。

```bash
GET /products/_search
{
  "query": { "match_all": {} },
  "timeout": "5s"
}
```

```python
def safe_search(es, index, query_body, timeout="5s"):
    """带超时保护的查询"""
    try:
        response = es.search(
            index=index,
            body=query_body,
            params={"timeout": timeout}
        )
        if response.get("timed_out"):
            print("警告: 查询超时，结果可能不完整")
        return response
    except Exception as e:
        print(f"查询失败: {e}")
        return None
```

6. **使用 terminate_after 限制分片扫描文档数**：在不需要精确总数的场景下，可以提前终止查询。

```python
response = es.search(
    index="products",
    body={"query": {"match": {"name": "手机"}}},
    params={"terminate_after": 1000}  # 每个分片最多扫描 1000 条
)
```

## 小结

Elasticsearch 的分布式查询采用 Query-Then-Fetch 两阶段模型。Query Phase 从各分片收集 ID 和排序值，Fetch Phase 根据 ID 获取完整文档。DFS Query-Then-Fetch 通过预查询计算全局 IDF 提升评分准确性。理解执行流程能帮助我们做出正确的优化决策——何时用 routing 减少分片扫描，何时用 search_after 替代深度分页，何时启用 DFS 提升精度。scroll 适合离线遍历但要注意资源消耗，search_after 是实时深度分页的最佳选择，PIT 提供了一致性视图保障。profile API 是排查慢查询的利器，但只在调试时使用。

### 练习一

**思路**：计算 Query Phase 和 Fetch Phase 的网络传输量。

**答案**：

Query Phase：每个分片返回 5 个文档的 `_id` + `_score`，约 100 字节/分片，3 个分片共 300 字节。Fetch Phase：Top 5 文档分布在分片上，传输约 5KB。总计约 5.3KB。Query-Then-Fetch 分两阶段——先传 ID（小数据量排序），再取文档（按需传输）。

**要点**：Query Phase 传输量与分片数成正比，Fetch Phase 只与返回文档数成正比。

### 练习二

**思路**：使用 `profile=True` 参数获取分片级执行详情。

**答案**：

```python
from elasticsearch import Elasticsearch
import json

def analyze_query_performance(es_host, index, query_body):
    es = Elasticsearch(es_host)
    response = es.search(index=index, body={"profile": True, **query_body})
    results = []
    for shard in response.get("profile", {}).get("shards", []):
        shard_info = {"shard_id": shard["id"], "searches": []}
        for search in shard.get("searches", []):
            for query in search.get("query", []):
                shard_info["searches"].append({
                    "type": query["type"],
                    "time_ms": query["time_in_nanos"] / 1_000_000
                })
        results.append(shard_info)
    return {"total_time_ms": response["took"], "shard_details": results}

result = analyze_query_performance("http://localhost:9200", "products",
    {"query": {"match": {"name": "机械键盘"}}, "size": 10})
print(json.dumps(result, indent=2, ensure_ascii=False))
```

**要点**：profile 只在调试时使用；关注分片间耗时差异。

**答案**：

| 方案 | 第100页性能 | 实时性 | 内存消耗 | 推荐度 |

| from+size | 差 | 好 | 高 | 不推荐 |

### 练习四

**思路**：结合 PIT 和 search_after，注意异常处理和 PIT 续期。

**答案**：

```python
from elasticsearch import Elasticsearch

class PITPaginator:
    def __init__(self, es_host, index, keep_alive="5m"):
        self.es = Elasticsearch(es_host)
        self.index = index
        self.keep_alive = keep_alive
        self.pit_id = None
        self.stats = {"pages": 0, "total_docs": 0, "errors": 0}

    def __enter__(self):
        pit_response = self.es.open_point_in_time(
            index=self.index, keep_alive=self.keep_alive
        )
        self.pit_id = pit_response["id"]
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        if self.pit_id:
            try:
                self.es.close_point_in_time(id=self.pit_id)
            except Exception:
                pass
        return False

    def fetch_all(self, query, sort_fields, page_size=100):
        all_docs = []
        search_after = None

        while True:
            try:
                body = {
                    "size": page_size,
                    "sort": sort_fields,
                    "pit": {"id": self.pit_id, "keep_alive": self.keep_alive},
                    "query": query
                }
                if search_after:
                    body["search_after"] = search_after

                response = self.es.search(body=body)
                hits = response["hits"]["hits"]
                if not hits:
                    break

                all_docs.extend(hits)
                search_after = hits[-1]["sort"]
                self.stats["pages"] += 1
                self.stats["total_docs"] = len(all_docs)

                # 更新 PIT ID（可能被刷新）
                if "pit_id" in response:
                    self.pit_id = response["pit_id"]

            except Exception as e:
                self.stats["errors"] += 1
                print(f"第 {self.stats['pages']+1} 页出错: {e}")
                break

        return all_docs

# 使用示例
with PITPaginator("http://localhost:9200", "products") as paginator:
    docs = paginator.fetch_all(
        query={"match_all": {}},
        sort_fields=[{"price": "asc"}, {"_id": "asc"}],
        page_size=50
    )
    print(f"遍历完成: {paginator.stats}")
```

**要点**：PIT ID 可能在查询响应中被刷新，需要更新；使用 with 语句确保资源释放。

### 练习五

**思路**：对比 msearch 和分别执行的网络 round trip 差异。

**答案**：

```python
from elasticsearch import Elasticsearch
import time

es = Elasticsearch("http://localhost:9200")

def separate_searches(es, index, keyword):
    """分别执行 5 个查询"""
    start = time.time()

    r1 = es.search(index=index, body={"query": {"match": {"name": keyword}}, "size": 10})
    r2 = es.search(index=index, body={"size": 0, "aggs": {"cat": {"terms": {"field": "category"}}}})
    r3 = es.search(index=index, body={"size": 0, "aggs": {"brand": {"terms": {"field": "brand"}}}})
    r4 = es.search(index=index, body={"size": 0, "aggs": {"price": {"histogram": {"field": "price", "interval": 100}}}})
    r5 = es.search(index=index, body={"size": 0, "aggs": {"hot": {"significant_terms": {"field": "name.keyword"}}}})

    elapsed = time.time() - start
    return elapsed, [r1, r2, r3, r4, r5]

def batch_search(es, index, keyword):
    """使用 msearch 批量查询"""
    start = time.time()

    searches = [
        {"index": index},
        {"query": {"match": {"name": keyword}}, "size": 10},
        {"index": index},
        {"size": 0, "aggs": {"cat": {"terms": {"field": "category"}}}},
        {"index": index},
        {"size": 0, "aggs": {"brand": {"terms": {"field": "brand"}}}},
        {"index": index},
        {"size": 0, "aggs": {"price": {"histogram": {"field": "price", "interval": 100}}}},
        {"index": index},
        {"size": 0, "aggs": {"hot": {"significant_terms": {"field": "name.keyword"}}}},
    ]

    response = es.msearch(body=searches)
    elapsed = time.time() - start
    return elapsed, response["responses"]

t1, _ = separate_searches(es, "products", "手机")
t2, _ = batch_search(es, "products", "手机")

print(f"分别执行: {t1*1000:.0f}ms")
print(f"msearch: {t2*1000:.0f}ms")
print(f"加速比: {t1/t2:.1f}x")
```

**要点**：msearch 减少网络 round trip，但每个查询仍然独立执行；适合首页多查询并行的场景。
