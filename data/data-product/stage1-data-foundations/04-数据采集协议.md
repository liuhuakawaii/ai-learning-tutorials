> **课程定位**：设计合理的采集策略，确保数据采集的稳定性和效率
> **前置知识**：第3课（数据源评估）
> **预计时长**：50 分钟

---

## 场景引入

你的爬虫跑了三个月一直很稳定，某天突然连续采集到大量空数据。你查了半天才发现，目标网站加了反爬机制，返回的都是验证码页面。你加了重试逻辑，但重试了 10 次还是失败，反而把 IP 封了。后来你反思：如果当时有合理的采集频率（不会触发反爬）、有指数退避重试（不会在限流时继续高频请求）、有监控告警（第一时间发现异常），这件事根本不会发展到 IP 被封的地步。

### 3.1 全量采集

```
┌──────────────────────────────────────────────────────────────┐
│                    全量采集                                    │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  定义：每次都采集所有数据                                     │
│                                                              │
│  优点：                                                       │
│  ├── 实现简单                                                │

│  ├── 数据量大时耗时长                                        │

│                                                              │
│  适用场景：                                                   │
│  ├── 数据量小（< 1000 条）                                   │
│  ├── 数据变化频繁                                            │
│  ├── 无法判断哪些是新增                                      │
│  └── 首次采集                                                │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**全量采集代码示例：**

```python
def full_crawl():
    """全量采集"""
    all_data = []
    page = 1
    
    while True:
        data = fetch_page(page)
        if not data:
            break
        all_data.extend(data)
        page += 1
    
    # 清空旧数据，写入新数据
    save_to_database(all_data, mode="replace")
    return len(all_data)
```

## 四、失败重试机制

### 4.1 为什么需要重试？

```
常见失败原因：
├── 网络波动（临时连接超时）
├── 目标网站限流（返回 429）
├── 服务器临时错误（返回 500）
└── 并发过高（请求被拒绝）

这些问题通常是临时的，重试后可能成功。
```

### 4.2 重试策略设计

```
┌──────────────────────────────────────────────────────────────┐
│                    重试策略                                    │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  固定间隔重试                                                 │
│  ├── 每次重试间隔相同（如 5 秒）                             │
│  ├── 简单但可能造成请求堆积                                  │
│  └── 适用：网络波动                                         │
│                                                              │
│  指数退避重试                                                 │
│  ├── 每次重试间隔翻倍（1s → 2s → 4s → 8s）                 │
│  ├── 避免请求堆积                                            │
│  └── 适用：限流场景                                         │
│                                                              │
│  最大重试次数                                                 │
│  ├── 设置最大重试次数（如 3 次）                             │
│  ├── 超过次数后记录失败                                      │
│  └── 避免无限重试                                           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 4.3 重试代码实现

```python
import time
import requests
from functools import wraps

def retry_with_backoff(max_retries=3, base_delay=1):
    """指数退避重试装饰器"""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(max_retries):
                try:
                    return func(*args, **kwargs)
                except requests.RequestException as e:
                    if attempt == max_retries - 1:
                        raise e
                    
                    delay = base_delay * (2 ** attempt)
                    print(f"请求失败，{delay}秒后重试: {e}")
                    time.sleep(delay)
            
            return None
        return wrapper
    return decorator

@retry_with_backoff(max_retries=3, base_delay=2)
def fetch_page(url: str) -> dict:
    """带重试的请求"""
    response = requests.get(url, timeout=10)
    response.raise_for_status()
    return response.json()
```

## 五、采集策略配置

### 5.1 并发控制

```python
import asyncio
import aiohttp
from asyncio import Semaphore

# 并发控制配置
MAX_CONCURRENT = 5  # 最大并发数
REQUEST_DELAY = 1   # 请求间隔（秒）

async def fetch_with_limit(url: str, sem: Semaphore):
    """带并发限制的请求"""
    async with sem:
        await asyncio.sleep(REQUEST_DELAY)
        async with aiohttp.ClientSession() as session:
            async with session.get(url) as response:
                return await response.json()

async def batch_fetch(urls: list):
    """批量请求"""
    sem = Semaphore(MAX_CONCURRENT)
    tasks = [fetch_with_limit(url, sem) for url in urls]
    return await asyncio.gather(*tasks, return_exceptions=True)
```

## 六、数据校验

### 6.1 采集后校验

```python
def validate_crawled_data(data: list) -> dict:
    """校验采集数据"""
    result = {
        "total": len(data),
        "valid": 0,
        "invalid": 0,
        "errors": []
    }
    
    for i, item in enumerate(data):
        try:
            # 检查必填字段
            assert "id" in item, "缺少 id 字段"
            assert "title" in item, "缺少 title 字段"
            
            # 检查数据类型
            assert isinstance(item["id"], (int, str)), "id 类型错误"
            
            # 检查数据范围
            if "price" in item:
                assert item["price"] >= 0, "价格不能为负"
            
            result["valid"] += 1
            
        except AssertionError as e:
            result["invalid"] += 1
            result["errors"].append({
                "index": i,
                "error": str(e),
                "data": item
            })
    
    return result
```

### 6.2 数据完整性检查

```python
def check_data_completeness(crawled_count: int, expected_count: int) -> dict:
    """检查数据完整性"""
    completeness = crawled_count / expected_count if expected_count > 0 else 0
    
    return {
        "crawled": crawled_count,
        "expected": expected_count,
        "completeness": f"{completeness:.2%}",
        "is_complete": completeness >= 0.95,  # 95% 以上认为完整
        "status": "OK" if completeness >= 0.95 else "WARNING"
    }
```

## 常见误区

- **重试万能论**：设了重试机制就觉得万事大吉。实际上，盲目重试可能导致问题恶化——限流时高频重试会让封禁更严重，解析错误时重试完全是浪费时间。重试前要先判断错误类型。
- **增量采集一定比全量好**：增量采集省资源，但需要维护采集状态（上次采集时间、最大 ID 等）。如果状态管理出错，可能漏采数据且无法发现。数据量小（< 1000 条）时，全量采集反而更简单可靠。
- **并发数越高采集越快**：并发数过高会触发目标网站的反爬机制，导致 IP 被封或返回假数据。合理控制并发数和请求间隔，比"暴力采集"更高效。
- **忽略监控告警**：采集系统最常见的故障是"静默失败"——爬虫在跑，但采集到的数据量为零或异常少。没有告警机制，可能过了好几天才发现。

---

## 工程建议

- **采集协议配置用代码管理**：把采集频率、并发数、重试策略等写成配置类或配置文件，而不是散落在各个脚本里。这样修改策略时只需要改配置，不需要改业务代码。
- **建立采集日志规范**：每次采集都要记录：开始时间、结束时间、采集数据量、成功数、失败数、耗时、批次号。这些日志是排查问题的第一手资料。
- **重试策略要区分错误类型**：网络超时和限流用指数退避重试（最多 3-5 次）；4xx 客户端错误不重试（说明请求本身有问题）；解析错误不重试（重试也不会变）。把错误分类写进协议文档。
- **设置采集量异常告警**：如果某次采集的数据量比历史平均值偏差超过 20%，自动触发告警。这比"采集失败"告警更实用，因为很多问题是"采集到了错误数据"而不是"采集失败"。

```
├── 采集模式：增量（只采最新行情）

├── 频率：每天 2 次（早 8 点、晚 20 点）
├── 理由：商品价格不会每分钟变动，每天 2 次足以捕捉促销和调价

场景 C：政府公开统计数据
├── 频率：每周 1 次
├── 理由：政府统计数据更新频率低（月度/季度），每周检查一次即可
├── 采集模式：全量（数据量小，全量更可靠）
└── 注意：政府网站可能在月底集中更新，可在月初采集

场景 D：社交媒体热门话题
├── 频率：每 30 分钟
├── 理由：热点话题变化快，需要准实时捕捉
├── 采集模式：增量（只采新话题或热度变化的话题）
└── 注意：API 调用成本高，可只在白天高频、夜间低频
```

**要点**：
- 频率不是越高越好——过高会触发反爬，过低会错过重要变化
- 要区分"数据源更新频率"和"业务需要的更新频率"，取两者中较高的

### 练习二

**思路**：增量采集的核心是记录"上次采集到哪里"，然后只采集新增部分。需要考虑状态记录、去重和日志。

**答案**：

```python
import json
from datetime import datetime
from pathlib import Path

class IncrementalCrawler:
    """增量采集器"""

    STATE_FILE = "crawl_state.json"

    def __init__(self, source_name: str):
        self.source_name = source_name
        self.state = self._load_state()

    def _load_state(self) -> dict:
        """加载上次采集状态"""
        path = Path(self.STATE_FILE)
        if path.exists():
            with open(path, "r", encoding="utf-8") as f:
                return json.load(f)
        return {}

    def _save_state(self):
        """保存采集状态"""
        with open(self.STATE_FILE, "w", encoding="utf-8") as f:
            json.dump(self.state, f, ensure_ascii=False, indent=2)

    def _get_last_crawl_time(self) -> datetime:
        """获取上次采集时间"""
        last_time = self.state.get(self.source_name, {}).get("last_crawl_time")
        if last_time:
            return datetime.fromisoformat(last_time)
        return datetime(2024, 1, 1)  # 默认从年初开始

    def _get_crawled_ids(self) -> set:
        """获取已采集的 ID 集合"""
        return set(self.state.get(self.source_name, {}).get("crawled_ids", []))

    def crawl(self, fetch_func, save_func):
        """执行增量采集"""
        last_time = self._get_last_crawl_time()
        crawled_ids = self._get_crawled_ids()

        # 采集新增数据
        new_items = fetch_func(since=last_time)

        # 去重：过滤已采集的记录
        unique_items = [item for item in new_items if item["id"] not in crawled_ids]

        if unique_items:
            # 保存数据
            save_func(unique_items)

            # 更新状态
            new_ids = {item["id"] for item in unique_items}
            self.state[self.source_name] = {
                "last_crawl_time": datetime.now().isoformat(),
                "crawled_ids": list(crawled_ids | new_ids)
            }
            self._save_state()

        # 记录日志
        print(f"[{datetime.now()}] {self.source_name}: "
              f"采集 {len(new_items)} 条, 新增 {len(unique_items)} 条, "
              f"去重 {len(new_items) - len(unique_items)} 条")

        return unique_items
```

**要点**：
- 状态文件要持久化存储（JSON 或数据库），不能只存在内存里
- 去重用集合（set）查找，时间复杂度 O(1)
- crawled_ids 列表会随时间增长，定期清理过期 ID 或改用布隆过滤器

### 练习三

**思路**：重试机制要区分错误类型——网络超时和限流可以重试，客户端错误（4xx）和解析错误不应该重试。用指数退避避免请求堆积。

**答案**：

```python
import time
import requests
import logging
from functools import wraps

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

# 可重试的 HTTP 状态码
RETRYABLE_STATUS_CODES = {429, 500, 502, 503, 504}

def retry_with_backoff(max_retries: int = 3, base_delay: float = 1.0):
    """指数退避重试装饰器，区分可重试和不可重试错误"""
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            last_exception = None

            for attempt in range(max_retries):
                try:
                    response = func(*args, **kwargs)

                    # 检查 HTTP 状态码
                    if response.status_code in RETRYABLE_STATUS_CODES:
                        if attempt < max_retries - 1:
                            delay = base_delay * (2 ** attempt)
                            logger.warning(
                                f"[重试 {attempt + 1}/{max_retries}] "
                                f"状态码 {response.status_code}，"
                                f"{delay}秒后重试"
                            )
                            time.sleep(delay)
                            continue
                        else:
                            response.raise_for_status()

                    # 2xx 或其他非重试状态码，直接返回
                    return response

                except requests.ConnectionError as e:
                    last_exception = e
                    if attempt < max_retries - 1:
                        delay = base_delay * (2 ** attempt)
                        logger.warning(
                            f"[重试 {attempt + 1}/{max_retries}] "
                            f"连接错误: {e}，{delay}秒后重试"
                        )
                        time.sleep(delay)
                    else:
                        logger.error(
                            f"[失败] 连接错误，已重试 {max_retries} 次: {e}"
                        )
                        raise

                except requests.Timeout as e:
                    last_exception = e
                    if attempt < max_retries - 1:
                        delay = base_delay * (2 ** attempt)
                        logger.warning(
                            f"[重试 {attempt + 1}/{max_retries}] "
                            f"超时: {e}，{delay}秒后重试"
                        )
                        time.sleep(delay)
                    else:
                        logger.error(
                            f"[失败] 超时，已重试 {max_retries} 次: {e}"
                        )
                        raise

            raise last_exception
        return wrapper
    return decorator


@retry_with_backoff(max_retries=3, base_delay=2.0)
def fetch_url(url: str) -> requests.Response:
    """带重试的请求函数"""
    return requests.get(url, timeout=10)


# 使用示例
try:
    response = fetch_url("https://example.com/api/data")
    print(f"成功: {response.status_code}")
except requests.RequestException as e:
    print(f"最终失败: {e}")
```

**要点**：
- 可重试错误：网络超时、连接失败、429 限流、5xx 服务器错误
- 不可重试错误：4xx 客户端错误（请求本身有问题）、解析错误
- 指数退避公式：delay = base_delay × 2^attempt（1s → 2s → 4s）
- 每次重试都要记录日志，方便排查问题

### 练习四

**思路**：按照采集协议文档模板，为"技术文章热度分析"产品填写完整协议。

**答案**：

```markdown
# 数据采集协议：技术文章热度分析

## 1. 基本信息

- 数据源：掘金、思否、CSDN 技术社区
- 数据内容：技术文章的标题、作者、阅读量、点赞数、评论数、标签
- 更新频率：实时（文章随时发布）

## 2. 采集频率

- 采集周期：每天 2 次
- 采集时间：08:00、20:00
- 时区：Asia/Shanghai (UTC+8)
- 备注：非采集时段如发现热点事件，可手动触发采集

## 3. 采集策略

- 采集模式：增量（按发布时间筛选最近 12 小时内的新文章）
- 并发数：3（每个站点 1 个并发）
- 请求间隔：2 秒
- 超时时间：15 秒
- User-Agent：随机轮换（维护 5 个 UA）

## 4. 重试策略

- 最大重试次数：3
- 重试间隔：指数退避（2s → 4s → 8s）
- 重试条件：网络超时、429 限流、5xx 服务器错误
- 不重试条件：4xx 客户端错误（非 429）、解析错误

## 5. 数据校验

- 必填字段：article_id、title、author、source、source_url
- 数据类型：view_count/like_count/comment_count 必须为非负整数
- 范围校验：view_count 不超过 1 亿（防止脏数据）
- 去重规则：按 article_id + source 去重

## 6. 监控告警

- 告警条件：
  - 采集失败（单站点连续 3 次失败）
  - 数据量异常（偏差 > 30%）
  - 采集超时（> 30 分钟）
- 告警方式：钉钉机器人通知

## 7. 异常处理

- 采集失败：记录日志，跳过当前批次，下次重试
- 数据异常：隔离到异常数据表，人工检查后决定是否入库
- 源站变更：告警通知开发者，暂停该站点采集，更新解析规则后恢复
```

**要点**：
- 采集协议要具体到数字——"适当降低频率"不如"每 2 秒一次"明确
- 异常处理要有预案，不能只写"处理一下"
