# 07 阶段实战：数据源调研报告

前六课学了数据产品、指标维度、数据源评估、采集协议、数据字典、数据生命周期。现在要把这些知识串起来——选一个主题，从零完成一份数据源调研报告。

这份报告不是交作业用的文档，而是你后续开发数据产品的蓝图。三个月后你重新看这份报告，应该能快速理解当时的决策理由。

## 任务说明

选择一个你感兴趣的主题，完成以下六个部分：

1. **项目概述**：为什么做这个数据产品？给谁用？核心价值是什么？
2. **数据源调研**：有哪些可用数据源？可靠性、质量、成本、合规性如何？
3. **字段设计**：需要哪些字段？类型、单位、枚举值是什么？
4. **指标体系**：核心指标是什么？怎么拆解成可计算的一级、二级指标？
5. **采集策略**：多久采集一次？增量还是全量？失败了怎么办？
6. **合规边界**：哪些数据可以采集？哪些不能？有什么风险？

## 推荐主题

| 主题 | 数据源 | 分析维度 | 核心价值 |
|------|--------|---------|---------|
| 招聘岗位与薪资趋势 | 招聘网站 | 城市、职位、技能、薪资 | 了解就业市场 |
| 商品价格监控 | 电商平台 | 商品、价格、促销、库存 | 价格趋势分析 |
| 技术文章热度分析 | 技术社区 | 技术分类、阅读量、互动 | 技术趋势洞察 |
| 城市天气与空气质量 | 天气 API、环保数据 | 城市、时间、指标 | 环境数据分析 |
| 开源项目增长趋势 | GitHub API | 语言、Star、贡献者 | 开源生态分析 |

选主题时先想"数据源是否真的能拿到"。很多人先选好主题、写好概述，再去调研数据源，结果发现理想的数据源根本不存在或成本太高。**正确顺序是先调研可行性，再确定主题。**

## 示例：招聘数据调研报告

下面是一个完整的示例，展示每个部分应该写到什么程度。

### 项目概述

IT 行业求职者和招聘方都需要了解市场行情：哪些技能热门？薪资水平如何？哪些城市机会多？本项目构建一个招聘数据分析平台，帮助用户洞察就业市场。

目标用户：
- 求职者：了解薪资水平、技能需求
- HR：了解市场竞争、制定招聘策略
- 培训机构：了解技能需求、调整课程方向

### 数据源调研

| 数据源 | 类型 | 内容 | 更新频率 | 可靠性 | 合规性 |
|--------|------|------|----------|--------|--------|
| 招聘网 A | 网页采集 | IT 岗位信息 | 实时 | ⭐⭐⭐ | 中风险 |
| 招聘网 B | API | 岗位信息 | 每天 | ⭐⭐⭐⭐ | 低风险 |
| 政府统计局 | API | 城市编码 | 每年 | ⭐⭐⭐⭐⭐ | 低风险 |

招聘网 A 可靠性三星：网站稳定，但页面结构可能变化，需要解析 HTML，维护成本较高。合规性中风险：需遵守 robots.txt，控制采集频率。

招聘网 B 可靠性四星：有官方 API，文档完善。成本：基础免费，高级付费。合规性低风险：官方授权。

主要数据源选招聘网 A——数据量大，覆盖面广。补充数据源选招聘网 B——API 稳定，作为备份。

### 字段设计（清洗表示例）

| 字段名 | 中文名 | 类型 | 可空 | 单位 | 枚举值 | 描述 | 示例 |
|--------|--------|------|------|------|--------|------|------|
| job_id | 岗位ID | VARCHAR(50) | 否 | - | - | 唯一标识 | "bj_10001" |
| title | 岗位名称 | VARCHAR(200) | 否 | - | - | 岗位标题 | "高级前端工程师" |
| company | 公司名称 | VARCHAR(200) | 否 | - | - | 招聘公司 | "某科技有限公司" |
| city | 城市 | VARCHAR(50) | 否 | - | - | 工作城市 | "北京" |
| salary_min | 最低薪资 | DECIMAL(10,2) | 否 | 元/月 | - | 薪资下限 | 20000.00 |
| salary_max | 最高薪资 | DECIMAL(10,2) | 否 | 元/月 | - | 薪资上限 | 35000.00 |
| experience | 经验要求 | VARCHAR(50) | 是 | - | 1-3年,3-5年,5-10年,不限 | 工作经验 | "3-5年" |
| education | 学历要求 | VARCHAR(20) | 是 | - | 大专,本科,硕士,博士,不限 | 最低学历 | "本科" |
| skills | 技能要求 | TEXT | 是 | - | - | 技能标签 | "React,TypeScript" |
| crawl_time | 采集时间 | DATETIME | 否 | - | - | 数据采集时间 | "2024-01-15 08:30:00" |
| batch_id | 批次号 | VARCHAR(50) | 否 | - | - | 采集批次标识 | "batch_20240115_001" |

### 指标体系

核心指标：市场活跃度 = 近 7 天新增岗位数

```
市场活跃度（近7天新增岗位数）
├── 岗位数量
│   ├── 今日新增岗位数
│   ├── 本周新增岗位数
│   └── 岗位增长率（周环比）
├── 薪资水平
│   ├── 平均薪资
│   ├── 薪资中位数
│   └── 薪资范围分布
├── 技能需求
│   ├── 热门技能 TOP10
│   └── 技能需求变化趋势
└── 地域分布
    ├── 城市岗位数量排名
    └── 远程岗位占比
```

| 指标 | 计算公式 | 数据来源 |
|------|----------|----------|
| 今日新增岗位数 | COUNT(jobs WHERE publish_date = today) | clean_jobs |
| 平均薪资 | AVG(salary_avg) | clean_jobs |
| 热门技能 TOP10 | GROUP BY skills ORDER BY COUNT DESC | clean_jobs |

## 编写时的常见问题

**找不到免费数据源怎么办？** 考虑公开数据集（Kaggle、UCI）、政府公开数据、学术用途授权，或者先用模拟数据开发，后续替换。

**数据源不稳定怎么办？** 建立备份方案：多个数据源互相备份、本地缓存历史数据、监控数据源状态。

**不确定数据是否合规怎么办？** 保守处理：查看 robots.txt、查看服务条款、控制采集频率。拿不准的就不采。

## 报告编写的关键原则

**写给"未来的自己"看**。假设三个月后你重新看这份报告，能不能快速理解当时的决策理由？每个结论都要写理由，不能只写结果。

**数据字典从最小可用版本开始**。先定义核心字段（10-15 个），保证每个字段有含义、类型、单位、来源、示例。后续需要时再扩展。

**采集策略要考虑"第一天就能跑起来"**。不要设计一个需要 3 个月开发才能上线的方案。先用最简单的方式（比如每天全量采集 100 条）跑通整个流程，再逐步优化。

**标注"待验证"的假设**。有些结论是你基于经验推测的（比如"数据源每天更新"），还没有实际验证。标注出来，后续测试后再确认。

## 验收标准

写完报告后，用这个清单自检：

- [ ] 每个字段有含义、类型、单位、来源
- [ ] 明确数据更新频率
- [ ] 明确哪些数据不采集
- [ ] 有初版指标体系（核心指标 + 一级 + 二级）
- [ ] 数据源评估覆盖可靠性、质量、成本、合规性四个维度
- [ ] 采集策略包含频率、重试机制

## 练习

选择一个主题，完成一份完整的数据源调研报告。要求：

1. 至少调研 2 个数据源，从四个维度评估
2. 数据字典至少定义 10 个字段，每个字段有类型、单位、示例
3. 指标体系至少有核心指标 + 3 个一级指标
4. 采集策略包含频率和重试机制
5. 明确标注哪些数据不采集，以及为什么不采集

完成报告后，对照验收标准自检。如果有"待验证"的假设，用代码实际测试一个数据源，验证数据获取是否可行。

## 进阶挑战

完成基本报告后，可以尝试：

**实际测试数据源**。写代码测试数据获取，记录实际遇到的问题（反爬、格式变化、数据缺失），把结果补充到报告中。

**设计数据质量规则**。为每个字段设计校验规则（薪资不能为负、城市不能为空），定义异常数据的处理策略。

**估算资源需求**。根据数据源的数据量，估算每天的采集量、存储需求、数据库表大小。
