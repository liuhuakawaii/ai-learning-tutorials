## 一、从一个真实场景说起

### 1.1 小王的困境

小王是一个前端开发者，老板让他做一个"竞品价格监控系统"。小王写了一个 Python 脚本：

```python
import requests
from bs4 import BeautifulSoup
import csv

# 爬取竞品价格
response = requests.get("https://competitor.com/products")
soup = BeautifulSoup(response.text, "html.parser")

prices = []
for item in soup.select(".product"):
    name = item.select_one(".title").text.strip()
    price = item.select_one(".price").text.strip()
    prices.append({"name": name, "price": price})

# 保存到 CSV
with open("prices.csv", "w", newline="") as f:
    writer = csv.DictWriter(f, fieldnames=["name", "price"])
    writer.writeheader()
    writer.writerows(prices)

print("Done!")
```

老板问了三个问题：

1. "昨天的数据和今天有什么变化？" → 小王发现 CSV 每次都被覆盖
2. "哪些商品降价了？" → 小王发现没有历史数据可以对比
3. "脚本报错了你知道吗？" → 小王发现没有错误通知

**这就是"脚本"和"产品"的区别。**

### 1.2 脚本 vs 产品的对比

```

├─────────────────┬─────────────────┬─────────────────────────────┤

├─────────────────┼─────────────────┼─────────────────────────────┤

└─────────────────┴─────────────────┴─────────────────────────────┘
```

## 二、数据产品的定义

### 2.1 什么是数据产品？

**数据产品** = 把原始数据经过采集、清洗、存储、分析后，以可查询、可理解、可操作的方式交付给用户的系统。

```
┌─────────────────────────────────────────────────────────────────┐
│                      数据产品的组成                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐ │
│   │  数据源   │ →  │  ETL     │ →  │  存储    │ →  │  展示    │ │
│   │          │    │          │    │          │    │          │ │
│   │ API/网页  │    │ 采集     │    │ 数据库   │    │ Dashboard│ │
│   │ CSV/文件  │    │ 清洗     │    │ 数据仓库 │    │ 报表     │ │
│   │ 数据库   │    │ 转换     │    │          │    │ 导出     │ │
│   └──────────┘    └──────────┘    └──────────┘    └──────────┘ │
│        │               │               │               │       │
│        ▼               ▼               ▼               ▼       │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │                    运维与监控                            │  │
│   │  定时任务 | 失败重试 | 告警通知 | 数据质量报告            │  │
│   └─────────────────────────────────────────────────────────┘  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 数据产品的核心特征

一个合格的数据产品应该具备以下特征：

```
┌──────────────────────────────────────────────────────────────┐
│                    数据产品 5 大特征                          │

│                                                              │

│  4. 可操作                                                   │

│                                                              │
│  5. 可持续                                                   │
│     └── 自动运行、自动重试、异常告警                           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 五、为什么"可追溯"比"图表炫"更重要

### 5.1 一个反面案例

某团队做了一个很漂亮的数据大屏，老板很满意。但有一天老板问：

> "这个数字是怎么算出来的？数据来源是哪里？为什么跟上个月对不上？"

团队答不上来。因为：
- 没有记录数据来源
- 没有记录计算逻辑
- 没有保留历史版本

**漂亮的大屏变成了"不可信的数字"。**

### 5.2 可追溯的含义

```
┌──────────────────────────────────────────────────────────────┐
│                    可追溯 = 你能回答这些问题                   │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  关于数据来源：                                               │
│  ├── 这条数据是从哪里采集的？                                 │
│  ├── 什么时候采集的？                                         │
│  └── 采集时用的什么参数？                                     │
│                                                              │
│  关于数据处理：                                               │
│  ├── 经过了哪些清洗步骤？                                     │
│  ├── 哪些记录被过滤了？为什么？                               │
│  └── 处理的批次号是什么？                                     │
│                                                              │
│  关于数据质量：                                               │
│  ├── 有多少数据通过了质量检查？                               │
│  ├── 有多少数据被标记为异常？                                 │
│  └── 异常数据的原因是什么？                                   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 5.3 数据产品的信任公式

```
数据产品的价值 = 数据质量 × 可追溯性 × 可用性

如果可追溯性 = 0，无论图表多炫，价值 = 0
```

## 常见误区

- **"能跑就行"心态**：脚本能跑出结果不等于它是数据产品。没有错误处理、没有历史记录、没有监控的脚本，迟早会在生产环境出问题。
- **过度追求炫酷的前端**：花大量时间做动画和大屏效果，却忽略了数据的可追溯性和准确性。记住：漂亮的图表如果数据不可信，价值为零。
- **认为数据产品必须从零开始**：很多人觉得做数据产品就要重写整套系统，其实现有的脚本只要加上定时运行、增量存储、错误告警就能从阶段 1 进化到阶段 3。
- **忽略运维能力**：只关注数据采集和展示，不做监控、不做告警、不做备份。数据产品是长期运行的系统，运维能力决定了它能活多久。

---

## 工程建议

- **从脚本到产品的演进可以渐进式推进**：先加上定时任务和增量存储（阶段 2），再加日志和数据质量检查（阶段 3），最后加 Dashboard 和 API（阶段 4）。不需要一步到位。
- **优先实现"可追溯"**：每条数据都记录来源 URL、采集时间、采集批次号。这三个字段的成本几乎为零，但能在数据出问题时救命。
- **建立基本的告警机制**：即使只是脚本失败时发一封邮件或一条钉钉消息，也比"出了问题三天后才发现"强一百倍。推荐从最简单的 `try/except + 通知` 开始。
- **用配置文件管理运行参数**：把采集频率、目标 URL、重试次数等放在配置文件里，而不是硬编码在脚本中。这样调整策略时不需要改代码。

## 小结

本课的核心要点：

1. **数据产品 ≠ 脚本**：数据产品是可追溯、可信赖、可查询、可操作、可持续的系统
2. **四个演进阶段**：一次性脚本 → 可重复脚本 → 数据管道 → 数据产品
3. **可追溯最重要**：没有可追溯性，漂亮的图表毫无价值
4. **前端优势**：你已有的 React/TypeScript/HTTP 知识可以直接迁移到数据产品开发
5. **技术栈**：pandas + FastAPI + PostgreSQL + React + Docker

## 参考答案

### 练习一

**思路**：判断是否为数据产品，核心看是否具备"可追溯、可信赖、可查询、可操作、可持续"五大特征。如果只是手动执行、结果覆盖写入、没有监控和历史记录，就是脚本。

**答案**：

```
A. 每天自动运行 + 结果存数据库 + 有 Dashboard
   → 数据产品。具备定时运行（可持续）、数据库存储（可追溯）、Dashboard（可查询）。

B. 手动运行 + CSV 转 Excel
   → 普通脚本。手动执行、无自动调度、无历史保留、无监控。

C. 定时发送的邮件报告 + 包含趋势图
   → 数据产品。定时自动运行（可持续）、有趋势图（可查询/可操作）、数据经过分析处理。

D. 一次性的数据迁移脚本
   → 普通脚本。一次性使用、无持续运行需求、无监控。

E. 实时股票行情监控 + 有告警功能
   → 数据产品。实时采集（可持续）、有告警（可操作）、行情数据可查询。
```

**要点**：
- 数据产品的核心不是"有没有界面"，而是有没有完整的运维闭环
- "定时运行 + 历史保留 + 错误告警"是从脚本进化为产品的最低门槛

### 练习二

**思路**：按照数据产品的四个组成部分（数据源 → ETL → 存储 → 展示）逐一思考，同时考虑运维能力。

**答案**：

```
1. 数据来源：
   - 主要来源：技术社区网页采集（掘金、思否、CSDN 等）
   - 补充来源：各平台开放 API（如有）
   - 辅助来源：RSS 订阅源

2. 需要采集的字段：
   - 文章信息：标题、作者、发布时间、URL
   - 互动数据：阅读量、点赞数、评论数、收藏数
   - 内容标签：技术分类（前端/后端/AI 等）、标签
   - 元数据：采集时间、来源平台、批次号

3. 用户想看到什么：
   - 热度排名：按阅读量/点赞数排序的热门文章
   - 趋势变化：某技术方向的文章数量随时间变化
   - 平台对比：同一话题在不同平台的热度差异
   - 作者排行：高产且高互动的作者

4. 需要的运维能力：
   - 定时采集（每天 2-3 次，错峰执行）
   - 增量采集（只采新增文章，避免重复）
   - 数据质量检查（阅读量不能为负、标题不能为空）
   - 采集失败告警（邮件/钉钉通知）
   - 采集日志（记录每次采集的数据量和耗时）
```

**要点**：
- 设计数据产品时先想"用户要什么"，再反推"需要采集什么"
- 运维能力从第一天就要考虑，不要等上线后再补

### 练习三

**思路**：对照自检清单逐项评估，诚实面对项目现状，列出缺失的能力。

**答案**：

```
示例评估（假设之前做过一个"竞品价格监控脚本"）：

自检清单结果：
□ 数据采集脚本能自动定时运行吗？        → 否（手动运行）
☑ 数据是增量追加还是每次覆盖？          → 覆盖写入
□ 有数据质量检查规则吗？                → 否
□ 脚本失败时会通知你吗？                → 否
□ 能追溯某条数据是什么时候采集的吗？    → 否
□ 非技术人员能查看数据吗？              → 否（只有 CSV 文件）
□ 能按条件筛选和导出数据吗？            → 否

勾选 0 个 → 处于阶段 1（一次性脚本）

缺少的能力：
1. 自动定时运行（需要加 cron 或 APScheduler）
2. 增量存储（需要改用数据库，按日期追加）
3. 数据质量检查（价格不能为负、商品名不能为空）
4. 失败告警（至少发一封邮件）
5. 可追溯性（每条数据记录采集时间和来源 URL）
6. 可视化界面（最低成本方案：用 Next.js 做个简单 Dashboard）
```

**要点**：
- 自检的目的不是评判好坏，而是明确下一步改进方向
- 从阶段 1 到阶段 3 的升级成本并不高，核心是加上定时任务、增量存储和错误告警
