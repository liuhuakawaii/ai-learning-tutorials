# 01 数据产品是什么

老板让你做个"竞品价格监控"。你花了一个周末写了个 Python 爬虫，每天手动跑一次，导出 CSV 发给老板。第一周挺好。第二周老板问"上周三的数据和这周三有什么变化？"，你才发现 CSV 每次都被覆盖了，历史数据全没了。第三周脚本报错了，你根本不知道，直到老板问"怎么没更新？"才去检查。

一个能跑的脚本和一个能用的产品之间，差的不只是功能，而是整套思维方式。

## 脚本和产品的核心区别

不是"有没有界面"的问题。一个命令行工具也可以是数据产品，一个有漂亮 Dashboard 的系统也可能是半成品。区别在于五个维度：

| 维度 | 普通脚本 | 数据产品 |
|------|---------|---------|
| 运行方式 | 手动执行 | 定时自动运行 |
| 数据存储 | 覆盖写入 | 增量追加，保留历史 |
| 错误处理 | print 报错 | 告警通知，自动重试 |
| 数据质量 | 不检查 | 有规则验证 |
| 可追溯性 | 无 | 批次号、日志、版本 |

回到开头那个爬虫——它在每个维度上都踩了坑：手动运行（不可持续）、覆盖写入（丢失历史）、没有错误通知（出了问题不知道）、没有数据质量检查（脏数据直接交付）、没有批次号（无法追溯）。这不是功能问题，是思维方式的问题。

## 什么是数据产品

数据产品 = 把原始数据经过采集、清洗、存储、分析后，以可查询、可理解、可操作的方式交付给用户的系统。

它有四个核心环节：

```
数据源 → ETL（采集、清洗、转换）→ 存储 → 展示
  ↓         ↓                      ↓       ↓
API/网页   增量采集               数据库   Dashboard
CSV/文件   去重校验               数据仓库  报表导出
数据库     格式标准化                   API 接口
```

每个环节都有对应的运维能力：定时任务、失败重试、告警通知、数据质量报告。**没有运维能力的数据产品，迟早会退化成一个出问题才知道的脚本。**

## 从脚本到产品的四个阶段

不需要一步到位。大多数数据产品都是从脚本慢慢长出来的：

**阶段 1：一次性脚本**。手动运行，结果打印到控制台或写入文件，用完就删。

**阶段 2：可重复脚本**。参数化配置，结果保存到文件，有基本的错误处理。能重复跑，但还是手动触发。

**阶段 3：数据管道**。定时运行，增量更新，有日志和批次号，有数据质量检查。到这里，它已经是一个可靠的数据采集系统了。

**阶段 4：数据产品**。在管道基础上加 Dashboard、API 接口、用户权限、告警和监控。非技术人员可以直接使用。

大多数人卡在阶段 1-2。从阶段 2 到阶段 3 的升级成本并不高——加上定时任务、增量存储和错误告警，就能从"偶尔能用"变成"持续可靠"。

## 现在处于哪个阶段

做一个自检：

- [ ] 数据采集脚本能自动定时运行吗？
- [ ] 数据是增量追加还是每次覆盖？
- [ ] 有数据质量检查规则吗？
- [ ] 脚本失败时会通知你吗？
- [ ] 能追溯某条数据是什么时候采集的吗？
- [ ] 非技术人员能查看数据吗？
- [ ] 能按条件筛选和导出数据吗？

勾选 ≤ 2 个 → 阶段 1-2。勾选 3-5 个 → 阶段 3。勾选 6-7 个 → 你已经在做数据产品了。

## 数据产品的常见类型

**监控型**：价格监控（电商比价、机票追踪）、舆情监控（社交媒体、新闻）、系统监控。核心是"变化时通知我"。

**分析型**：市场分析（行业报告、竞品分析）、用户分析（行为分析、留存分析）、运营分析（转化漏斗、ROI）。核心是"帮我理解数据"。

**查询型**：搜索引擎、数据查询（招聘信息、企业信息）、推荐系统。核心是"帮我找到想要的"。

**报告型**：定期报告（周报月报自动生成）、数据大屏、合规报告。核心是"定期给我看结果"。

不同类型技术重点不同——监控型重实时性和告警，分析型重数据质量和查询性能，查询型重搜索算法，报告型重定时任务和可视化。但底层都需要：可追溯、可信赖、可持续。

## 为什么"可追溯"比"图表炫"更重要

某团队做了一个很漂亮的数据大屏，老板很满意。有一天老板问："这个数字是怎么算出来的？数据来源是哪里？为什么跟上个月对不上？"团队答不上来。漂亮的大屏变成了"不可信的数字"。

可追溯意味着你能回答三个问题：

关于来源——这条数据从哪里采集的？什么时候采集的？采集时用的什么参数？

关于处理——经过了哪些清洗步骤？哪些记录被过滤了？处理的批次号是什么？

关于质量——有多少数据通过了质量检查？有多少被标记为异常？

**数据产品的价值 = 数据质量 × 可追溯性 × 可用性。如果可追溯性为 0，无论图表多炫，价值为 0。**

## 一个完整的数据产品长什么样

以"招聘数据分析"为例：

```
数据源                     ETL                    存储
┌─────────┐           ┌──────────┐          ┌──────────┐
│ 招聘网站 │ ───────→  │ 采集岗位 │ ───────→ │ raw 表   │
│ API     │           │ 清洗薪资 │          │          │
│ CSV     │           │ 去重标准化│          │ clean 表 │
└─────────┘           └──────────┘          │ metrics  │
                                            └──────────┘
                                                  │
                                                  ▼
用户界面                                  ┌──────────┐
┌─────────────────────────┐         ┌──────────┐
│ Dashboard               │ ←─────  │ FastAPI  │
│ 薪资趋势 | 城市分布      │         │ /trends  │
│ 技能排名 | 岗位对比      │         │ /ranking │
│ 筛选器：时间|城市|职位    │         └──────────┘
└─────────────────────────┘

运维
┌─────────────────────────────────────────────────┐
│ 定时采集（每天 8:00）| 失败重试 | 告警 | 质量报告 │
└─────────────────────────────────────────────────┘
```

这就是你在本课程结束时要能独立搭建的东西。不需要一步到位，但每一层你都应该知道为什么需要它、怎么实现它。

## 容易踩的坑

**"能跑就行"心态**。脚本能跑出结果不等于它是数据产品。没有错误处理、没有历史记录、没有监控的脚本，迟早会在生产环境出问题——而且你大概率是最后一个知道的人。

**过度追求前端效果**。花大量时间做动画和大屏，却忽略了数据的可追溯性和准确性。漂亮的图表如果数据不可信，价值为零。

**认为必须从零开始**。现有的脚本只要加上定时运行、增量存储、错误告警，就能从阶段 1 进化到阶段 3。不需要重写整套系统。

**忽略运维能力**。只关注数据采集和展示，不做监控、不做告警、不做备份。数据产品是长期运行的系统，运维能力决定了它能活多久。

## 参考答案

### 练习一

A. **数据产品**。定时运行（可持续）、数据库存储（可追溯）、Dashboard（可查询）。

B. **普通脚本**。手动执行、无自动调度、无历史保留、无监控。

C. **数据产品**。定时自动运行（可持续）、有趋势图（可查询/可操作）、数据经过分析处理。

D. **普通脚本**。一次性使用、无持续运行需求、无监控。

E. **数据产品**。实时采集（可持续）、有告警（可操作）、行情数据可查询。

核心判断标准不是"有没有界面"，而是有没有完整的运维闭环——定时运行、历史保留、错误告警是从脚本进化为产品的最低门槛。

### 练习二

1. 数据来源：技术社区网页采集（掘金、思否、CSDN 等）、各平台开放 API（如有）、RSS 订阅源。

2. 需要采集的字段：
   - 文章信息：标题、作者、发布时间、URL
   - 互动数据：阅读量、点赞数、评论数、收藏数
   - 内容标签：技术分类（前端/后端/AI 等）、标签
   - 元数据：采集时间、来源平台、批次号

3. 用户想看到什么：
   - 热度排名：按阅读量/点赞数排序的热门文章
   - 趋势变化：某技术方向的文章数量随时间变化
   - 平台对比：同一话题在不同平台的热度差异

4. 需要的运维能力：
   - 定时采集（每天 2-3 次，错峰执行）
   - 增量采集（只采新增文章，避免重复）
   - 数据质量检查（阅读量不能为负、标题不能为空）
   - 采集失败告警（邮件/钉钉通知）

设计数据产品时先想"用户要什么"，再反推"需要采集什么"。运维能力从第一天就要考虑，不要等上线后再补。
