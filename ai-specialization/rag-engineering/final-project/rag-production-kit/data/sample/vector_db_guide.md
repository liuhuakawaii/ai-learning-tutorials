# 向量数据库选型指南

## 场景引入

搭建 RAG 系统时，向量数据库是核心基础设施之一。市面上有 Milvus、Qdrant、Weaviate、Pinecone、ChromaDB 等众多选择，它们在性能、可扩展性、运维复杂度和成本上差异显著。选错数据库可能导致后期迁移成本高昂，或者在生产环境中遇到性能瓶颈。本指南帮助你根据实际场景做出合理选型。

## 概述

向量数据库是 RAG 系统的核心组件之一，负责存储和检索高维向量。
选择合适的向量数据库对系统的性能和可扩展性至关重要。

## 主流向量数据库

### Milvus
- 开源，支持分布式部署
- 支持多种索引类型（HNSW、IVF 等）
- 适合大规模生产环境

### Qdrant
- Rust 实现，性能优异
- 支持丰富的过滤条件
- 提供云服务和自部署选项

### Weaviate
- GraphQL API
- 内置向量化模块
- 适合快速原型开发

### Pinecone
- 全托管服务
- 使用简单，无需运维
- 适合小规模应用

### ChromaDB
- 轻量级，适合开发测试
- Python 原生支持
- 嵌入式部署

## 选型建议

| 场景 | 推荐 | 原因 |
|------|------|------|
| 生产大规模 | Milvus | 分布式、高可用 |
| 高性能需求 | Qdrant | Rust 实现、低延迟 |
| 快速原型 | ChromaDB | 简单易用 |
| 全托管 | Pinecone | 无需运维 |

## 常见误区

- 只看性能指标不看运维成本——自部署 Milvus 需要管理 etcd、MinIO 等依赖，小团队未必有运维能力
- 认为 ChromaDB 只能用于开发测试——对于小规模应用（<100 万向量），ChromaDB 的嵌入式模式完全够用
- 忽略数据规模增长——选型时只看当前数据量，没有预留 10 倍增长的空间

## 工程建议

- 小团队优先选择 Qdrant（自部署简单）或 Pinecone（全托管），避免 Milvus 的运维复杂度
- 选型时用真实数据量做压测——在你的数据规模下测试召回率和延迟，而非依赖公开 benchmark
- 向量数据库应支持元数据过滤（如按文档类型、时间范围过滤），这在生产环境中是刚需
