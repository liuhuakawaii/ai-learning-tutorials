# 03 - 依赖关系图谱

> **课程定位**：本课教你用工具自动提取和分析代码库的依赖关系，为迁移规划提供数据支撑。
>
> **前置要求**：了解模块化编程概念（import/export）
>
> **预计时长**：2 小时

---

## 场景引入

你要把一个 Vue 2 项目迁移到 Vue 3。领导问："这个迁移大概要多久？"你打开项目目录，看到 500 多个 `.vue` 文件、200 多个 `.js` 文件，分布在 15 个目录里。你不知道哪些模块互相依赖、哪些是孤立的、改一个文件会影响多少其他文件。

你试着改了一个工具函数的签名，结果 npm run build 报了 47 个错误——这些错误分散在 23 个文件里，有些你甚至不知道它们和那个工具有关。

这就是缺乏依赖分析的代价。在迁移之前，你需要一张**地图**——一张告诉你"改了 A 会影响 B、C、D"的地图。这张地图就是依赖关系图谱。

## 1. 依赖关系基础

### 1.1 什么是依赖关系

当模块 A 导入了模块 B，我们说 A 依赖 B。这种关系是有方向的：

```
  A 依赖 B   →   A → B

  具体例子：
  orderService.js → database.js    (订单服务依赖数据库)
  orderService.js → emailService.js (订单服务依赖邮件服务)
  emailService.js → config.js      (邮件服务依赖配置)
  database.js     → config.js      (数据库依赖配置)

  依赖图：
                  config.js
                  ▲       ▲
                  │       │
          emailService.js database.js
                  ▲       ▲
                  │       │
                  └──┬────┘
                     │
              orderService.js
```

### 1.2 依赖类型

```
依赖类型分类：

1. 直接依赖（Direct）
   A 直接 import B
   orderService → database

2. 间接依赖（Transitive）
   A 依赖 B，B 依赖 C，所以 A 间接依赖 C
   orderService → emailService → config
   orderService 间接依赖 config

3. 开发依赖（Dev Dependency）
   只在开发/测试时使用
   orderService.test → orderService
   orderService → jest (devDependency)

4. 循环依赖（Circular）
   A 依赖 B，B 也依赖 A
   orderService → inventoryService → orderService  ← 问题！

5. 外部依赖（External）
   依赖 npm 包，不是项目内部代码
   orderService → express
   orderService → lodash
```

### 1.3 为什么依赖分析对迁移至关重要

```
没有依赖分析的迁移：
  "我把这个工具函数改了"
  → 47 个编译错误
  → 分散在 23 个文件里
  → 修复 A 时又引入了 3 个新错误
  → 陷入泥潭

有依赖分析的迁移：
  "我要改 utils/format.js"
  → 依赖分析显示：直接被 8 个文件引用
  → 影响范围明确：先改这 8 个文件
  → 这 8 个文件可以作为一个迁移批次
  → 可控、可测试、可回滚
```

## 2. 使用 madge 分析依赖

madge 是 Node.js 生态中最流行的依赖分析工具，支持 JavaScript、TypeScript、CSS 预处理器等。

### 2.1 安装和基本使用

```bash
npm install -g madge

# 分析当前目录的依赖关系
madge src/

# 生成依赖图（需要安装 graphviz）
madge src/ --image deps.svg

# 找出循环依赖
madge src/ --circular

# 找出某个文件的所有依赖（递归）
madge src/ --depends src/services/order.js

# 找出依赖某个文件的所有文件
madge src/ --depends src/utils/format.js --reverse
```

### 2.2 用 madge 做迁移分析

```javascript
// analyze-deps.mjs - 用 madge API 分析项目依赖
import madge from "madge";

async function analyzeProject(projectPath) {
  const result = await madge(projectPath, {
    fileExtensions: ["js", "ts", "jsx", "tsx", "vue"],
    excludeRegExp: [/node_modules/, /\.test\./, /\.spec\./],
  });

  const depGraph = result.obj();
  const stats = {
    totalFiles: Object.keys(depGraph).length,
    totalDeps: Object.values(depGraph).reduce((sum, deps) => sum + deps.length, 0),
    circularDeps: result.circular(),
    orphans: [],
    hubs: [],
  };

  // 找出孤立文件（叶子节点）
  const allDeps = new Set(Object.values(depGraph).flat());
  for (const file of Object.keys(depGraph)) {
    if (!allDeps.has(file) && depGraph[file].length > 0) {
      stats.orphans.push(file);
    }
  }

  // 找出"枢纽"文件（被最多文件依赖）
  const dependantCount = {};
  for (const [file, deps] of Object.entries(depGraph)) {
    for (const dep of deps) {
      dependantCount[dep] = (dependantCount[dep] || 0) + 1;
    }
  }
  stats.hubs = Object.entries(dependantCount)
    .sort((a, b) => b[1] - a[1])
    .slice(0, 10)
    .map(([file, count]) => ({ file, dependants: count }));

  return stats;
}

// 迁移批次规划
function planMigrationBatches(stats, depGraph) {
  const batches = [];
  const migrated = new Set();

  // 第一批：没有内部依赖的叶子模块
  const leaves = Object.entries(depGraph)
    .filter(([, deps]) => deps.length === 0)
    .map(([file]) => file);

  if (leaves.length > 0) {
    batches.push({
      batch: 1,
      description: "叶子模块（无依赖，可独立迁移）",
      files: leaves,
    });
    leaves.forEach(f => migrated.add(f));
  }

  // 后续批次：依赖已迁移模块的文件
  let batchNum = 2;
  while (migrated.size < Object.keys(depGraph).length) {
    const canMigrate = Object.entries(depGraph)
      .filter(([file]) => !migrated.has(file))
      .filter(([, deps]) => deps.every(d => migrated.has(d)))
      .map(([file]) => file);

    if (canMigrate.length === 0) {
      const remaining = Object.keys(depGraph).filter(f => !migrated.has(f));
      batches.push({
        batch: batchNum,
        description: "循环依赖模块（需要一起迁移）",
        files: remaining,
      });
      break;
    }

    batches.push({
      batch: batchNum,
      description: `依赖已迁移模块的文件`,
      files: canMigrate,
    });
    canMigrate.forEach(f => migrated.add(f));
    batchNum++;
  }

  return batches;
}

const stats = await analyzeProject("./src");
console.log("=== 项目依赖分析 ===");
console.log(`总文件数: ${stats.totalFiles}`);
console.log(`总依赖数: ${stats.totalDeps}`);
console.log(`循环依赖: ${stats.circularDeps.length} 组`);
console.log(`孤立文件: ${stats.orphans.length} 个`);
console.log("\n=== 枢纽文件（影响范围最大）===");
stats.hubs.forEach(h => console.log(`  ${h.file} (${h.dependants} 个文件依赖它)`));
```

## 3. 使用 dependency-cruiser 做深度分析

dependency-cruiser 是另一个强大的依赖分析工具，它支持自定义规则，可以检测违反架构约束的依赖。

### 3.1 配置依赖规则

```bash
npm install -g dependency-cruiser
depcruise --init  # 生成配置文件
```

```javascript
// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    {
      name: "no-circular",
      comment: "禁止循环依赖",
      severity: "error",
      from: {},
      to: { circular: true },
    },
    {
      name: "no-orphans",
      comment: "禁止孤立模块",
      severity: "warn",
      from: {
        orphan: true,
        pathNot: ["\\.config\\.", "index\\.ts$", "\\.d\\.ts$"],
      },
      to: {},
    },
    {
      name: "layer-isolation",
      comment: "UI 层不能直接访问数据库层",
      severity: "error",
      from: { path: "^src/(components|pages)" },
      to: { path: "^src/database" },
    },
  ],
  options: {
    doNotFollow: { path: "node_modules" },
    tsPreCompilationDeps: true,
  },
};
```

### 3.2 迁移规则示例

在迁移过程中，你可以用 dependency-cruiser 来强制执行迁移策略：


## 4. 构建自定义依赖分析器

当现成工具不能满足需求时，你可以构建自己的依赖分析器。以下是一个基于 AST 的自定义分析器：

```javascript
// custom-dep-analyzer.mjs - 自定义依赖分析器
import * as parser from "@babel/parser";
import traverse from "@babel/traverse";
import * as t from "@babel/types";
import fs from "fs";
import path from "path";

class DependencyAnalyzer {
  constructor(projectRoot) {
    this.projectRoot = projectRoot;
    this.depGraph = new Map();
  }

  analyzeFile(filePath) {
    const code = fs.readFileSync(filePath, "utf-8");
    const relativePath = path.relative(this.projectRoot, filePath);

    const ast = parser.parse(code, {
      sourceType: "module",
      plugins: ["typescript", "jsx", "decorators-legacy"],
    });

    const fileInfo = {
      imports: [],
      exports: [],
      dynamicImports: [],
    };

    traverse.default(ast, {
      ImportDeclaration: (path) => {
        fileInfo.imports.push({
          source: path.node.source.value,
          specifiers: path.node.specifiers.map((s) => {
            if (t.isImportDefaultSpecifier(s)) return { type: "default", name: s.local.name };
            if (t.isImportNamespaceSpecifier(s)) return { type: "namespace", name: s.local.name };
            return { type: "named", name: s.local.name, imported: s.imported?.name };
          }),
          line: path.node.loc?.start.line,
          isTypeOnly: path.node.importKind === "type",
        });
      },

      CallExpression: (path) => {
        // 动态 import()
        if (t.isImport(path.node.callee) && path.node.arguments.length === 1) {
          const arg = path.node.arguments[0];
          if (t.isStringLiteral(arg)) {
            fileInfo.dynamicImports.push({
              source: arg.value,
              line: path.node.loc?.start.line,
            });
          }
        }

        // require() 调用
        if (t.isIdentifier(path.node.callee, { name: "require" })) {
          const arg = path.node.arguments[0];
          if (t.isStringLiteral(arg)) {
            fileInfo.imports.push({
              source: arg.value,
              line: path.node.loc?.start.line,
              type: "require",
            });
          }
        }
      },

      ExportNamedDeclaration: (path) => {
        if (path.node.source) {
          fileInfo.exports.push({ type: "re-export", source: path.node.source.value });
        }
      },
      ExportDefaultDeclaration: () => {
        fileInfo.exports.push({ type: "default" });
      },
      ExportAllDeclaration: (path) => {
        fileInfo.exports.push({ type: "wildcard", source: path.node.source.value });
      },
    });

    this.depGraph.set(relativePath, fileInfo);
    return fileInfo;
  }

  analyzeDirectory(dir) {
    const files = this._scanFiles(dir);
    for (const file of files) {
      this.analyzeFile(file);
    }
    return this.depGraph;
  }

  // 检测循环依赖
  findCircularDeps() {
    const visited = new Set();
    const recursionStack = new Set();
    const circulars = [];

    const dfs = (file, currentPath = []) => {
      visited.add(file);
      recursionStack.add(file);
      currentPath.push(file);

      const info = this.depGraph.get(file);
      if (!info) return;

      for (const imp of info.imports) {
        const resolved = this._resolveImport(imp.source, file);
        if (!resolved) continue;

        if (!visited.has(resolved)) {
          dfs(resolved, [...currentPath]);
        } else if (recursionStack.has(resolved)) {
          const cycleStart = currentPath.indexOf(resolved);
          circulars.push(currentPath.slice(cycleStart).concat(resolved));
        }
      }

      recursionStack.delete(file);
    };

    for (const file of this.depGraph.keys()) {
      if (!visited.has(file)) dfs(file);
    }

    return circulars;
  }

  // 影响分析
  impactAnalysis(targetFile) {
    const affected = new Set();
    const queue = [targetFile];

    while (queue.length > 0) {
      const current = queue.shift();
      for (const [file, info] of this.depGraph) {
        const deps = info.imports
          .map((i) => this._resolveImport(i.source, file))
          .filter(Boolean);
        if (deps.includes(current) && !affected.has(file)) {
          affected.add(file);
          queue.push(file);
        }
      }
    }

    return [...affected];
  }

  _scanFiles(dir) {
    const exts = [".js", ".ts", ".jsx", ".tsx", ".vue"];
    const files = [];
    const entries = fs.readdirSync(dir, { withFileTypes: true });
    for (const entry of entries) {
      const fullPath = path.join(dir, entry.name);
      if (entry.isDirectory() && entry.name !== "node_modules") {
        files.push(...this._scanFiles(fullPath));
      } else if (exts.includes(path.extname(entry.name))) {
        files.push(fullPath);
      }
    }
    return files;
  }

  _resolveImport(source, fromFile) {
    if (!source.startsWith(".")) return null;
    const dir = path.dirname(fromFile);
    const resolved = path.resolve(dir, source);
    const exts = ["", ".js", ".ts", ".jsx", ".tsx", "/index.js", "/index.ts"];
    for (const ext of exts) {
      const full = resolved + ext;
      if (this.depGraph.has(path.relative(this.projectRoot, full))) {
        return path.relative(this.projectRoot, full);
      }
    }
    return null;
  }
}

// 使用示例
const analyzer = new DependencyAnalyzer("./src");
analyzer.analyzeDirectory("./src");

console.log("=== 循环依赖 ===");
const circulars = analyzer.findCircularDeps();
if (circulars.length === 0) {
  console.log("  无循环依赖");
} else {
  circulars.forEach((cycle, i) => {
    console.log(`  循环 ${i + 1}: ${cycle.join(" → ")}`);
  });
}

console.log("\n=== 影响分析：修改 utils/format.js ===");
const affected = analyzer.impactAnalysis("utils/format.js");
console.log(`  直接和间接受影响的文件: ${affected.length} 个`);
affected.forEach((f) => console.log(`    ${f}`));
```

## 5. 基于依赖图谱划分迁移边界

依赖分析最重要的应用是**划分迁移边界**——决定哪些文件应该作为一个批次一起迁移。

### 5.1 迁移边界划分原则

```
好的迁移边界：

┌─────────────────────────────────────────┐
│ Batch 1: 独立工具模块                    │
│ ┌────────┐ ┌────────┐ ┌────────┐       │
│ │format.js│ │date.js │ │math.js │       │
│ └────────┘ └────────┘ └────────┘       │
│ 这些模块没有内部依赖，可以独立迁移        │
├─────────────────────────────────────────┤
│ Batch 2: 业务服务层                      │
│ ┌──────────────┐ ┌──────────────┐       │
│ │orderService  │ │userService   │       │
│ └──────┬───────┘ └──────┬───────┘       │
│        │                │               │
│   (依赖 Batch 1 的工具模块)              │
├─────────────────────────────────────────┤
│ Batch 3: API 层                          │
│ ┌──────────────┐                        │
│ │  routes/api   │                       │
│ └──────┬───────┘                        │
│        │                                │
│   (依赖 Batch 2 的服务层)                │
└─────────────────────────────────────────┘

迁移顺序：Batch 1 → Batch 2 → Batch 3
每个批次迁移后都可以独立测试
```

### 5.2 自动划分迁移批次

```javascript
// plan-migration.mjs - 基于依赖图谱自动规划迁移批次
function planMigrationBatches(depGraph) {
  const batches = [];
  const migrated = new Set();
  const inDegree = {};

  // 计算每个文件的入度
  for (const [file, info] of depGraph) {
    if (!inDegree[file]) inDegree[file] = 0;
    for (const imp of info.imports) {
      const resolved = resolveImport(imp.source, file);
      if (resolved && depGraph.has(resolved)) {
        inDegree[resolved] = (inDegree[resolved] || 0) + 1;
      }
    }
  }

  // 拓扑排序，逐批规划
  let batchNum = 1;
  while (migrated.size < depGraph.size) {
    const ready = [...depGraph.keys()].filter(
      (f) => !migrated.has(f) && (inDegree[f] || 0) === 0
    );

    if (ready.length === 0) {
      const remaining = [...depGraph.keys()].filter((f) => !migrated.has(f));
      batches.push({
        batch: batchNum,
        type: "circular",
        files: remaining,
        note: "循环依赖模块，必须作为整体迁移",
      });
      break;
    }

    batches.push({
      batch: batchNum,
      type: "independent",
      files: ready,
      note: `可独立迁移的模块（${ready.length} 个文件）`,
    });

    for (const file of ready) {
      migrated.add(file);
      const info = depGraph.get(file);
      for (const imp of info.imports) {
        const resolved = resolveImport(imp.source, file);
        if (resolved && inDegree[resolved]) {
          inDegree[resolved]--;
        }
      }
    }

    batchNum++;
  }

  return batches;
}
```

## 6. 常见误区

### 误区一："循环依赖不重要"

循环依赖是迁移的噩梦。如果 A 依赖 B，B 也依赖 A，你不能单独迁移 A 或 B——必须一起迁移，这大大增加了工作量和风险。

**正确做法**：在迁移前先消除循环依赖。常见的方法是提取公共接口到第三个模块 C，让 A 和 B 都依赖 C。

### 误区二："只看直接依赖就够了"

改了一个文件，你以为只影响 3 个直接依赖，结果那 3 个依赖又被其他 15 个文件依赖——实际影响范围远超预期。

**正确做法**：做递归影响分析，计算完整的传递依赖链。

### 误区三："依赖分析只需要做一次"

依赖关系是动态的——每次 git merge 都可能引入新的依赖或断开旧的依赖。

**正确做法**：将依赖分析集成到 CI/CD 流水线中，每次提交都自动运行，及时发现循环依赖和架构违规。

### 误区四："外部依赖不用管"

外部依赖（npm 包）也可能影响迁移。如果老代码依赖的 npm 包不支持新框架版本，你需要找到替代方案或自己封装。

**正确做法**：在依赖分析中同时统计外部依赖，检查它们的版本和兼容性。

## 小结

本课的核心内容：

1. **依赖关系图谱是迁移的地图**——没有地图的迁移是盲目的
2. **madge 和 dependency-cruiser 是核心工具**——前者快速分析，后者深度规则检查
3. **循环依赖是迁移的最大障碍**——必须在迁移前检测和解决
4. **影响分析告诉你"改 A 会影响多少"**——用递归传递依赖计算完整影响范围
5. **基于依赖图谱规划迁移批次**——从叶子节点开始，逐层向上

## 参考答案

### 练习一

**思路**：用 madge 的命令行工具或 API 进行分析，记录各项指标。

**答案**：（以一个典型的中小型项目为例）

```
$ madge src/ --json
{
  "src/utils/format.js": [],
  "src/utils/date.js": ["src/utils/format.js"],
  "src/services/user.js": ["src/utils/format.js", "src/utils/date.js"],
  "src/services/order.js": ["src/utils/format.js", "src/services/user.js"],
  "src/routes/api.js": ["src/services/order.js", "src/services/user.js"],
  "src/app.js": ["src/routes/api.js"]
}

1. 文件数：6 个，依赖关系：7 条
2. 循环依赖：无
3. 被依赖最多的文件：
   - format.js（被 3 个文件依赖）
   - date.js（被 1 个文件依赖）
   - validator.js（被 2 个文件依赖）
4. 修改 format.js 的影响范围：
   - 直接：date.js, userService.js, orderService.js
   - 间接：apiRoutes.js（依赖 userService 和 orderService）
   - 最终：app.js（依赖 apiRoutes）
   - 总计：5 个文件受影响
```

**要点**：format.js 是整个项目的"枢纽"——被最多文件依赖，修改它的影响范围最大。在迁移时，这类文件应该最后迁移（因为改了它会影响所有依赖它的文件），或者优先给它补充测试。

### 练习二

**思路**：计算每个文件的入度（被依赖次数），入度为 0 的文件可以独立迁移。

**答案**：

```
入度计算：
  format.js: 0（无文件依赖它）
  date.js: 0
  validator.js: 0
  userService.js: 2（被 orderService 和 apiRoutes 依赖）
  orderService.js: 1（被 apiRoutes 依赖）
  apiRoutes.js: 1（被 app.js 依赖）
  app.js: 0（它是入口，不被任何文件依赖）

迁移批次规划：

Batch 1（叶子模块，可独立迁移）：
  - format.js（无内部依赖）
  - date.js（无内部依赖）
  - validator.js（无内部依赖）
  - app.js（虽然有依赖，但它是入口文件，入度为 0）
  理由：这些文件不被任何内部文件依赖，迁移它们不会影响其他文件。

Batch 2（依赖 Batch 1 的模块）：
  - userService.js（依赖 format.js 和 validator.js，它们已在 Batch 1 迁移）
  - orderService.js（依赖 format.js 和 date.js，它们已在 Batch 1 迁移）
  理由：它们的所有依赖都已迁移完成，可以安全地迁移。

Batch 3（依赖 Batch 2 的模块）：
  - apiRoutes.js（依赖 userService.js 和 orderService.js，它们已在 Batch 2 迁移）
  理由：它依赖的模块都已迁移。

每个批次迁移后都可以独立测试：
  Batch 1 测试：每个工具函数的单元测试
  Batch 2 测试：服务层的集成测试
  Batch 3 测试：API 端到端测试
```

**要点**：迁移批次的划分遵循拓扑排序的原则——先迁移没有依赖的模块，再迁移依赖它们的模块。这样每个批次迁移时，它的依赖已经就绪，可以独立测试。
