# 01 - 代码迁移的工程现实

> **课程定位**：Part 1 开篇，建立迁移决策的工程判断力。
>
> **前置要求**：维护过 1 年以上代码库
>
> **预计时长**：1.5 小时

---

你刚接手一个 4 年前用 jQuery + PHP 写的订单管理系统。12 万行代码、300 多个 SQL 查询、零测试、文档过期。产品经理要加"智能推荐"，现有架构撑不住。

CTO 提了两个方案：花 6 个月重写成 React + Node.js，或者在现有系统上修修补补。团队开了三天会，谁也说服不了谁。

这不是虚构场景。本课要回答：**什么条件下应该迁移，什么条件下应该维护，以及如何做出理性决策。**

---

## 技术债的四种类型

技术债不是一种东西。Martin Fowler 的四象限分类：

```
                鲁莽（Reckless）
                     │
        ┌────────────┼────────────┐
        │  鲁莽-有意   │  鲁莽-无意   │
        │ "没时间做    │ "什么是分层？" │
        │  设计"       │            │
────────┼────────────┼────────────┼────
不情愿   │  谨慎-有意   │  谨慎-无意   │  情愿
        │ "先上线再说， │ "新需求来了，  │
        │  后面再重构"  │  当时的架构    │
        │            │  已经不适用了"  │
        └────────────┼────────────┘
                     │
                谨慎（Prudent）
```

**谨慎-有意**：团队知道不是最优，基于现实约束做了有意识取舍。有记录、有偿还计划。通常不需要大规模迁移，定期技术债冲刺即可。

**鲁莽-有意**：团队知道正确做法但选择无视。"没时间写测试"。如果工程文化没改变，迁移后新代码很快也会变成同样的债。

**谨慎-无意**：按当时最佳实践设计，但业务发展后不再合适。3 年前用 Redux 是合理的，现在 Zustand 更适合。最适合渐进式迁移。

**鲁莽-无意**：团队不知道好的实践。"什么是依赖注入？"迁移前必须先提升团队能力。

**关键洞察**：盲目选择"迁移"而不分析技术债类型，是迁移失败的第一个原因。

## 决策框架

```
当前系统能否满足未来 2 年的业务需求？
     │
     ├── 能 → 维护 + 偿还关键路径上的技术债
     │
     └── 不能 → 技术债的主要类型是什么？
              │
              ├── 局部问题 → 渐进式迁移
              │
              └── 系统性问题 → 评估重写成本
                       │
                       ├── 代码量 < 5 万行 → 可能重写
                       │
                       └── 代码量 > 5 万行 → 渐进式迁移
```

| 维度 | 维护 | 渐进式迁移 | 完全重写 |
|------|------|-----------|---------|
| 风险 | 低 | 中 | 高 |
| 周期 | 持续 | 数月 | 数月到数年 |
| 业务影响 | 最小 | 可控 | 可能中断 |
| 典型失败原因 | 技术债失控 | 迁移范围蔓延 | 重写永远完不成 |

Joel Spolsky 在 2000 年写过："完全重写是软件公司能做的最危险的事情之一。"重写的隐性成本包括：

- **知识丢失**：老代码有大量边界条件处理，不会出现在文档里
- **功能对等的幻觉**：老系统上千个细小行为，用户已习以为常
- **机会成本**：重写期间不能加新功能，竞品不会等你
- **二进制状态**：重写只有完成或没完成，渐进式迁移每完成一个模块就产生价值

## 案例：Netscape vs Shopify

**Netscape（1998）**：决定完全重写浏览器引擎。原计划 1 年，实际花了 3 年。重写期间 IE 抢走 80% 市场份额。最终被 AOL 收购，浏览器项目开源——Firefox 的起源。

**Shopify**：核心是 300 万行 Ruby on Rails 单体。没有重写，而是渐进式拆分：用依赖分析工具找耦合点，将高内聚模块逐步拆为独立服务，通过 API 与老系统通信，灰度发布切流量。5 年拆成 100+ 微服务，零重大事故。

## 成本-收益分析

迁移不是"感觉该做就做"的决定。

```
总迁移成本 = 分析成本 + 转换成本 + 测试成本 + 风险成本 + 机会成本

迁移价值 = (迁移后维护成本节省 + 新能力带来的业务价值) × 时间跨度
迁移成本 = 直接成本 + 风险成本 + 机会成本

当 迁移价值 / 迁移成本 > 2 时，迁移值得做
当 比值在 1-2 之间时，需要更细致的分析
当 比值 < 1 时，维护是更优选择
```

用代码估算迁移成本：

```typescript
interface MigrationEstimate {
  codebaseLines: number;
  testCoveragePercent: number;
  teamSize: number;
  teamFamiliarityScore: number; // 1-10
  documentationQuality: number; // 1-10
  businessComplexity: number; // 1-10
}

function estimateMigrationCost(estimate: MigrationEstimate) {
  const {
    codebaseLines, testCoveragePercent, teamSize,
    teamFamiliarityScore, documentationQuality, businessComplexity,
  } = estimate;

  const analysisHours = (codebaseLines / 1000) * 3;
  const conversionHours = (codebaseLines / 1000) * 6;

  const testMultiplier = testCoveragePercent < 30 ? 2.5
    : testCoveragePercent < 60 ? 1.8 : testCoveragePercent < 80 ? 1.3 : 1.0;
  const docMultiplier = documentationQuality < 3 ? 2.0
    : documentationQuality < 6 ? 1.5 : 1.0;
  const famMultiplier = teamFamiliarityScore < 3 ? 2.0
    : teamFamiliarityScore < 6 ? 1.4 : 1.0;

  const totalHours = (analysisHours + conversionHours)
    * testMultiplier * docMultiplier * famMultiplier;
  const estimatedMonths = totalHours / (teamSize * 160);
  const riskScore = (10 - testCoveragePercent / 10)
    + (10 - documentationQuality) + (businessComplexity > 7 ? 3 : 0);

  const riskLevel = riskScore > 20 ? "high" : riskScore > 12 ? "medium" : "low";
  let recommendation: "maintain" | "migrate" | "rewrite";
  if (codebaseLines < 50000 && riskLevel !== "high") {
    recommendation = estimatedMonths < 3 ? "rewrite" : "migrate";
  } else if (riskLevel === "high" && estimatedMonths > 12) {
    recommendation = "migrate";
  } else {
    recommendation = estimatedMonths < 6 ? "migrate" : "maintain";
  }

  return { estimatedMonths, estimatedCost: totalHours * 800, riskLevel, recommendation };
}

const result = estimateMigrationCost({
  codebaseLines: 120000, testCoveragePercent: 5, teamSize: 6,
  teamFamiliarityScore: 3, documentationQuality: 2, businessComplexity: 8,
});
// 预估工期: 28.1 个月, 风险: high, 推荐: migrate（渐进式）
```

## Strangler Fig Pattern

渐进式迁移的核心模式。新系统作为代理层接入，逐个模块替换老系统，业务不中断。

```
阶段 1：代理层拦截          阶段 2：逐步替换           阶段 3：老系统退役
┌──────────────┐          ┌──────────────┐          ┌──────────────┐
│   代理层      │          │   代理层      │          │   新系统      │
│  ┌────────┐  │          │  ┌────────┐  │          │  ┌────────┐  │
│  │新模块 A │  │          │  │新模块 A │  │          │  │新模块 A │  │
│  │新模块 B │  │          │  │新模块 B │  │          │  │新模块 B │  │
│  │老模块 C │──→ 老系统   │  │新模块 C │  │          │  │新模块 C │  │
│  └────────┘  │          │  └────────┘  │          │  └────────┘  │
└──────────────┘          └──────────────┘          └──────────────┘
```

核心原则：
1. **不修改老代码**：老代码继续运行，新代码通过代理层接入
2. **逐个模块替换**：每次只迁移一个模块，验证后再迁移下一个
3. **随时可回滚**：代理层可以随时将流量切回老模块
4. **业务不中断**：整个迁移过程中系统一直正常运行

```typescript
import express from "express";

const app = express();

const routeConfig: Record<string, "new" | "legacy"> = {
  "/api/users": "new",
  "/api/orders": "legacy",
  "/api/products": "new",
  "/api/payments": "legacy",
};

app.use((req, res, next) => {
  const target = routeConfig[req.path];
  console.log(`[代理] ${req.path} → ${target === "new" ? "新系统" : "老系统"}`);
  next();
});

app.get("/api/users", (req, res) => {
  res.json({ source: "new-system", users: [] });
});

app.listen(3000);
```

随着迁移推进，`routeConfig` 中越来越多路由从 `"legacy"` 变成 `"new"`。

## 常见误区

**"老代码太烂了，必须重写"** — 用数据说话。统计 bug 率、变更频率、新人上手时间，评估是否能渐进式解决。

**"新技术栈一定更好"** — 迁移目标应该是解决具体业务问题，不是追求最新技术。

**"迁移期间不能加新功能"** — 用 Strangler Fig Pattern，迁移和新功能并行。新功能直接用新架构，老功能逐步迁移。

**"迁移是一个项目"** — 迁移是持续过程，融入日常开发节奏，每个迭代完成一小部分。

## 练习

### 练习一：技术债分类

一个 3 年前的 React 项目，有以下问题。请分类（谨慎-有意 / 鲁莽-有意 / 谨慎-无意 / 鲁莽-无意）：

- 组件文件平均 800 行，最大 2500 行
- Redux store 结构不规范
- 没有 TypeScript
- 部分 API 调用用了已废弃的第三方库
- 代码注释很少，但有基本 README

### 练习二：迁移决策

项目信息：8 万行 jQuery + PHP 7.2，测试覆盖率 15%，5 人团队，2 人是原作者，文档差，电商核心系统，竞争压力中等。请做出迁移决策并说明理由。

---

## 参考答案

### 练习一

1. **组件过大**：谨慎-无意。React 项目随业务增长自然膨胀，是演化结果。
2. **Redux 不规范**：需进一步判断。知道最佳实践但"没时间改"是鲁莽-有意；当时不熟悉是鲁莽-无意。
3. **没有 TypeScript**：取决于项目启动时 TS 普及程度，可能是谨慎-有意或谨慎-无意。
4. **废弃第三方库**：谨慎-无意。库的废弃是外部因素，最适合渐进式迁移解决。
5. **注释少但有 README**：谨慎-无意。有一定文档意识，忙于功能开发。

大部分属于"谨慎-无意"——系统演化的自然结果。渐进式迁移最合适。

### 练习二

**推荐策略：渐进式迁移**

- 8 万行超过 5 万行阈值，完全重写隐性成本过高
- 测试覆盖率 15% 很低，但渐进式迁移过程中会逐步补充
- 5 人团队不足以支撑重写，但可以每个迭代 1-2 人做迁移
- 竞品压力中等，不能完全停滞，渐进式允许同时做新功能
- 业务复杂度高，重写遗漏风险极大

具体建议：第 1 个月补充核心路径端到端测试；第 2-3 个月从耦合度最低的模块开始迁移；第 4 个月起逐步迁移业务模块；新功能用新架构开发。
