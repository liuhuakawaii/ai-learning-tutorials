# 01 - 代码迁移的工程现实

> **课程定位**：本课是 Part 1 的开篇，帮助你理解代码迁移在真实工程中的处境与决策逻辑。
>
> **前置要求**：有维护过 1 年以上代码库的经验
>
> **预计时长**：1.5 小时

---

## 场景引入

你刚加入一家电商公司，接手了一个 4 年前用 jQuery + PHP 写的订单管理系统。这个系统有 12 万行代码、300 多个 SQL 查询、零测试覆盖、文档只有一份过期的 ER 图。产品经理想加一个"智能推荐"功能，但现有架构根本支撑不了。

CTO 提了两个方案：**方案 A**——花 6 个月重写成 React + Node.js；**方案 B**——在现有系统上修修补补。团队开了三天会，谁也说服不了谁。重写派认为老代码已经不可维护，继续投入是浪费；保守派则指出上次重写 CRM 系统花了 18 个月、预算超了 3 倍，最后还不如老系统稳定。

这不是虚构的场景——几乎所有有一定历史的软件团队都面临这个困境。本课要回答的核心问题是：**在什么条件下应该迁移，什么条件下应该维护，以及如何做出理性决策。**

## 1. 技术债的分类

技术债不是一种东西。把它当成一个整体来讨论，会导致决策失误。Martin Fowler 将技术债分为四个象限：

```
                    鲁莽（Reckless）
                         │
            ┌────────────┼────────────┐
            │            │            │
            │  鲁莽-有意   │  鲁莽-无意   │
            │            │            │
            │ "没时间做    │ "什么是分层？" │
            │  设计"       │            │
    ────────┼────────────┼────────────┼────
    不情愿   │            │            │   情愿
    (Deliberate)│ 谨慎-有意   │  谨慎-无意   │(Prudent)
            │            │            │
            │ "先上线再说， │ "新需求来了，  │
            │  后面再重构"  │  当时的架构    │
            │            │  已经不适用了"  │
            └────────────┼────────────┘
                         │
                    谨慎（Prudent）
```

### 1.1 谨慎-有意（Prudent Deliberate）

团队清楚知道当前方案不是最优的，但基于现实约束做出了有意识的取舍。例如：为了赶在竞品之前上线，选择了一个"够用但不优雅"的数据库设计方案，同时记录了后续需要优化的事项。

**特征**：有记录、有计划、有偿还时间表。

**迁移策略**：这种技术债通常不需要大规模迁移，可以通过定期的"技术债冲刺"逐步偿还。

### 1.2 鲁莽-有意（Reckless Deliberate）

团队知道正确的做法，但选择无视。"没时间写测试""设计模式太复杂，直接 if-else 就行"。

**特征**：没有记录，没有偿还计划，债务像滚雪球一样增长。

**迁移策略**：这种技术债往往需要结构性改造。但问题在于：如果团队的工程文化没有改变，迁移后的新代码很快也会变成同样的技术债。

### 1.3 谨慎-无意（Prudent Inadvertent）

团队按照当时的最佳实践做了设计，但随着业务发展和新技术出现，原来的设计不再合适。例如：3 年前用 Redux 做状态管理是合理的，但现在 Zustand 或 Jotai 更适合这个项目的规模。

**特征**：不是错误，是演化的必然结果。

**迁移策略**：最适合渐进式迁移。旧代码在它被设计的时代是合理的，只需要在新功能中使用新模式，逐步替换。

### 1.4 鲁莽-无意（Reckless Inadvertent）

团队不知道什么是好的实践。"什么是依赖注入？""为什么要分层？"——这不是选择，而是能力边界。

**特征**：代码质量差不是因为偷懒，而是因为缺乏知识。

**迁移策略**：迁移之前必须先提升团队能力。否则新代码会重复同样的问题。

**关键洞察**：不同类型的技术债需要不同的处理方式。盲目选择"迁移"而不分析技术债的类型，是迁移失败的第一个原因。

## 2. 迁移 vs 重写 vs 维护：决策框架

```
┌─────────────────────────────────────────────────────────┐
│              迁移决策树                                    │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  当前系统能否满足未来 2 年的业务需求？                       │
│       │                                                 │
│       ├── 能 → 维护 + 偿还关键路径上的技术债                │
│       │                                                 │
│       └── 不能 → 技术债的主要类型是什么？                   │
│                │                                        │
│                ├── 局部问题（某些模块差）→ 渐进式迁移        │
│                │                                        │
│                └── 系统性问题（架构过时）→ 评估重写成本       │
│                         │                               │
│                         ├── 代码量 < 5 万行 → 可能重写     │
│                         │                               │
│                         └── 代码量 > 5 万行 → 渐进式迁移    │
│                              （重写的隐性成本远超预期）      │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 2.1 三个选项的本质区别

| 维度 | 维护 | 渐进式迁移 | 完全重写 |
|------|------|-----------|---------|
| 风险 | 低 | 中 | 高 |
| 周期 | 持续 | 数月 | 数月到数年 |
| 业务影响 | 最小 | 可控 | 可能中断 |
| 适用场景 | 技术债可控 | 架构问题但业务复杂 | 代码量小且架构过时 |
| 典型失败原因 | 技术债失控 | 迁移范围蔓延 | 重写永远完不成 |

### 2.2 重写的隐性成本

Joel Spolsky 在 2000 年写过一篇经典文章 "Things You Should Never Do"，核心观点是：**完全重写是软件公司能做的最危险的事情之一。**

重写的隐性成本包括：

1. **知识丢失**：老代码里有大量的边界条件处理、特殊业务规则，这些不会出现在任何文档里。重写时你一定会遗漏它们，然后在生产环境中逐个踩坑。

2. **功能对等的幻觉**：你以为重写只需要"复制功能"，但实际上老系统有上千个细小的行为，用户已经习以为常。每遗漏一个，就是一个 bug 报告。

3. **机会成本**：重写期间，团队不能给老系统加新功能。竞品可不会等你重写完。

4. **二进制状态**：重写只有两种结果——完成或没完成。在完成之前，它对业务的贡献是零。渐进式迁移则不同，每完成一个模块，就能立即产生价值。

## 3. 案例分析

### 3.1 失败案例：Netscape 的重写噩梦

1998 年，Netscape 决定完全重写浏览器引擎。当时的 CEO Barksdale 和团队认为老代码太乱，不如从零开始。结果：

- 重写花了 **3 年**（原计划 1 年）
- 重写期间 IE 抢走了 80% 的市场份额
- 最终发布时，新浏览器仍然有大量 bug
- Netscape 被 AOL 收购，浏览器项目最终开源——这就是 Firefox 的起源

**教训**：重写期间市场不会等你。老代码再烂，它能跑、能赚钱。新代码再优雅，在完成之前一文不值。

### 3.2 失败案例：某银行核心系统重写

国内某银行 2016 年启动核心系统重写项目，计划用 Java 微服务替换原来的 COBOL 单体系统。原计划 2 年、预算 8000 万。实际情况：

- 第 1 年：需求分析和架构设计（还在正常范围）
- 第 2 年：发现老系统有 3000 多个存储过程，每个都包含复杂的业务逻辑，文档严重缺失
- 第 3 年：预算追加到 2 亿，开始"兼容模式"——新系统必须同时支持新老两套接口
- 第 4 年：新系统的复杂度已经超过了老系统，团队开始质疑重写的必要性
- 最终：项目在第 5 年被叫停，保留老系统，只迁移了部分外围模块

**教训**：大型系统的重写成本呈非线性增长。代码量翻倍，重写成本可能翻 4 倍。

### 3.3 成功案例：Shopify 的渐进式迁移

Shopify 的核心是一个巨大的 Ruby on Rails 单体应用（称为 Shopify Core），代码量超过 300 万行。他们没有选择重写，而是采用了渐进式策略：

1. **识别边界**：用依赖分析工具找出模块之间的耦合点
2. **提取服务**：将高内聚的功能模块逐步拆分为独立服务
3. **保持兼容**：新服务通过 API 与老系统通信，用户无感知
4. **逐步切换**：用灰度发布将流量从老模块切到新服务
5. **持续运行**：在整个过程中，老系统一直正常运行，业务从未中断

**结果**：5 年内将单体拆分成了 100+ 微服务，零重大事故。

**教训**：渐进式迁移的风险是可控的——每一步都是一个独立的小变更，可以单独验证和回滚。

## 4. 成本-收益分析

迁移不是"感觉该做就做"的决定。它需要量化的成本-收益分析。

### 4.1 迁移成本模型

```
总迁移成本 = 分析成本 + 转换成本 + 测试成本 + 风险成本 + 机会成本

其中：
  分析成本 = 理解老代码的时间 × 人力成本
  转换成本 = 代码转换 + 数据迁移 + 配置迁移 + 文档更新
  测试成本 = 编写测试 + 回归测试 + 性能测试 + 安全测试
  风险成本 = 概率(重大故障) × 影响(业务损失)
  机会成本 = 迁移期间不能做的新功能的价值
```

### 4.2 简化的决策公式

```
迁移价值 = (迁移后维护成本节省 + 新能力带来的业务价值) × 时间跨度
迁移成本 = 直接成本 + 风险成本 + 机会成本

当 迁移价值 / 迁移成本 > 2 时，迁移值得做
当 比值在 1-2 之间时，需要更细致的分析
当 比值 < 1 时，维护是更优选择
```

### 4.3 用代码估算迁移成本

```typescript
interface MigrationEstimate {
  codebaseLines: number;
  testCoveragePercent: number;
  teamSize: number;
  teamFamiliarityScore: number; // 1-10
  documentationQuality: number; // 1-10
  businessComplexity: number; // 1-10
}

function estimateMigrationCost(estimate: MigrationEstimate): {
  estimatedMonths: number;
  estimatedCost: number;
  riskLevel: "low" | "medium" | "high";
  recommendation: "maintain" | "migrate" | "rewrite";
} {
  const {
    codebaseLines,
    testCoveragePercent,
    teamSize,
    teamFamiliarityScore,
    documentationQuality,
    businessComplexity,
  } = estimate;

  const analysisHours = (codebaseLines / 1000) * 3;
  const conversionHours = (codebaseLines / 1000) * 6;

  const testMultiplier = testCoveragePercent < 30 ? 2.5
    : testCoveragePercent < 60 ? 1.8
    : testCoveragePercent < 80 ? 1.3
    : 1.0;

  const docMultiplier = documentationQuality < 3 ? 2.0
    : documentationQuality < 6 ? 1.5
    : 1.0;

  const familiarityMultiplier = teamFamiliarityScore < 3 ? 2.0
    : teamFamiliarityScore < 6 ? 1.4
    : 1.0;

  const totalHours = (analysisHours + conversionHours)
    * testMultiplier
    * docMultiplier
    * familiarityMultiplier;

  const estimatedMonths = totalHours / (teamSize * 160);
  const estimatedCost = totalHours * 800;

  const riskScore = (10 - testCoveragePercent / 10)
    + (10 - documentationQuality)
    + (businessComplexity > 7 ? 3 : 0);

  const riskLevel = riskScore > 20 ? "high"
    : riskScore > 12 ? "medium"
    : "low";

  let recommendation: "maintain" | "migrate" | "rewrite";
  if (codebaseLines < 50000 && riskLevel !== "high") {
    recommendation = estimatedMonths < 3 ? "rewrite" : "migrate";
  } else if (riskLevel === "high" && estimatedMonths > 12) {
    recommendation = "migrate";
  } else {
    recommendation = estimatedMonths < 6 ? "migrate" : "maintain";
  }

  return { estimatedMonths, estimatedCost, riskLevel, recommendation };
}

const result = estimateMigrationCost({
  codebaseLines: 120000,
  testCoveragePercent: 5,
  teamSize: 6,
  teamFamiliarityScore: 3,
  documentationQuality: 2,
  businessComplexity: 8,
});

console.log(`预估工期: ${result.estimatedMonths.toFixed(1)} 个月`);
console.log(`预估成本: ¥${(result.estimatedCost / 10000).toFixed(0)} 万`);
console.log(`风险等级: ${result.riskLevel}`);
console.log(`推荐策略: ${result.recommendation}`);
```

运行这段代码，你会得到类似这样的输出：

```
预估工期: 28.1 个月
预估成本: ¥108 万
风险等级: high
推荐策略: migrate
```

**解读**：这个 12 万行、测试覆盖率 5%、文档几乎为零的项目，重写需要 28 个月。风险等级为 high，推荐渐进式迁移而非完全重写。

## 5. Strangler Fig Pattern

渐进式迁移的核心模式是 **Strangler Fig Pattern**（绞杀者无花果模式），由 Martin Fowler 在 2004 年提出。

```
绞杀者无花果的生长过程：

第 1 阶段：新系统作为代理层          第 2 阶段：逐步替换旧模块
┌──────────────┐                    ┌──────────────┐
│   客户端      │                    │   客户端      │
└──────┬───────┘                    └──────┬───────┘
       │                                   │
       ▼                                   ▼
┌──────────────┐                    ┌──────────────┐
│   代理层      │                    │   代理层      │
│  ┌────────┐  │                    │  ┌────────┐  │
│  │新模块 A │  │                    │  │新模块 A │  │
│  └────────┘  │                    │  └────────┘  │
│  ┌────────┐  │                    │  ┌────────┐  │
│  │新模块 B │  │                    │  │新模块 B │  │
│  └────────┘  │                    │  └────────┘  │
│  ┌────────┐  │                    │  ┌────────┐  │
│  │老模块 C │──┼──→ 老系统         │  │新模块 C │  │
│  └────────┘  │                    │  └────────┘  │
└──────────────┘                    └──────────────┘

第 3 阶段：老系统逐步消亡
┌──────────────┐
│   客户端      │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│   新系统      │
│  ┌────────┐  │
│  │新模块 A │  │
│  └────────┘  │
│  ┌────────┐  │
│  │新模块 B │  │
│  └────────┘  │
│  ┌────────┐  │
│  │新模块 C │  │
│  └────────┘  │
└──────────────┘
老系统已完全退役
```

### 5.1 核心原则

1. **不修改老代码**：老代码继续正常运行，新代码通过代理层接入
2. **逐个模块替换**：每次只迁移一个模块，验证通过后再迁移下一个
3. **随时可回滚**：代理层可以随时将流量切回老模块
4. **业务不中断**：在整个迁移过程中，系统一直在正常运行

### 5.2 代理层实现示例

```typescript
import express from "express";

const app = express();

const routeConfig: Record<string, "new" | "legacy"> = {
  "/api/users": "new",
  "/api/orders": "legacy",
  "/api/products": "new",
  "/api/payments": "legacy",
};

app.use((req, res, next) => {
  const target = routeConfig[req.path];

  if (target === "new") {
    console.log(`[代理] ${req.path} → 新系统`);
    next();
  } else {
    console.log(`[代理] ${req.path} → 老系统`);
    next();
  }
});

app.get("/api/users", (req, res) => {
  res.json({ source: "new-system", users: [] });
});

app.get("/api/products", (req, res) => {
  res.json({ source: "new-system", products: [] });
});

app.listen(3000, () => {
  console.log("代理服务运行在 http://localhost:3000");
  console.log("路由配置:", routeConfig);
});
```

这个代理层是渐进式迁移的基础。随着迁移的推进，`routeConfig` 中越来越多的路由会从 `"legacy"` 变成 `"new"`，直到老系统完全退役。

## 6. 常见误区

### 误区一："老代码太烂了，必须重写"

老代码"烂"是一个主观判断。你需要分析它具体"烂"在哪里：是命名不规范（小事），是缺少测试（可以补），是架构根本性错误（大事），还是技术栈过时（中等事）。不同的问题需要不同的解决方案。

**正确做法**：用数据说话。统计老代码的 bug 率、变更频率、新人上手时间，然后评估这些问题是否能通过渐进式方式解决。

### 误区二："新技术栈一定更好"

2024 年用 React 重写一个 2020 年的 Vue 2 项目，然后 2027 年你可能又会想用"更好的框架"重写那个 React 项目。技术栈的更新是永恒的，迁移不能解决所有问题。

**正确做法**：迁移的目标应该是解决具体的业务问题（性能、可维护性、招聘难度），而不是追求"最新最好的技术"。

### 误区三："迁移期间不能加新功能"

这是最危险的误区。如果迁移意味着 6 个月不能加新功能，那你的竞品会非常感谢你。

**正确做法**：用 Strangler Fig Pattern，迁移和新功能开发并行。新功能直接用新架构开发，老功能逐步迁移。

### 误区四："测试覆盖率高就可以放心重写"

测试只能证明"测试覆盖到的行为没有被破坏"。但老系统的很多行为是测试没有覆盖的——那些隐式的、用户习以为常的行为。

**正确做法**：在迁移前，先补充关键路径的端到端测试和集成测试，而不仅仅是单元测试。

### 误区五："迁移是一个项目"

迁移不是"完成就结束"的项目，而是一个持续的过程。它更像是"系统演进"的一部分。

**正确做法**：将迁移融入日常开发节奏，每个迭代完成一小部分迁移，而不是设立一个独立的"迁移项目"。

## 7. 决策检查清单

在决定是否迁移之前，回答以下问题：

```
┌──────────────────────────────────────────────────────────┐
│                迁移决策检查清单                              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  □ 当前系统能否满足未来 2 年的业务需求？                      │
│    → 不能：+1 分（倾向迁移）                                │
│                                                          │
│  □ 主要技术债属于哪种类型？                                  │
│    → 谨慎-无意：+1 分（适合迁移）                            │
│    → 鲁莽-有意：+0 分（先改文化）                            │
│    → 鲁莽-无意：-1 分（先提升能力）                          │
│                                                          │
│  □ 测试覆盖率是多少？                                      │
│    → > 60%：+1 分                                         │
│    → < 30%：-1 分（先补测试）                               │
│                                                          │
│  □ 团队对老代码的熟悉程度？                                  │
│    → 高：+1 分                                             │
│    → 低：-1 分（先做代码分析）                               │
│                                                          │
│  □ 代码量是否超过 5 万行？                                   │
│    → 是：必须渐进式迁移                                     │
│    → 否：可以考虑完全重写                                    │
│                                                          │
│  □ 迁移期间能否保持业务连续性？                               │
│    → 能：+1 分                                             │
│    → 不能：-2 分（重新评估方案）                              │
│                                                          │
│  总分 ≥ 3：建议迁移                                        │
│  总分 1-2：谨慎评估，补充条件后再决定                          │
│  总分 ≤ 0：暂不迁移，先解决前置问题                           │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

## 小结

本课的核心观点：

1. **技术债不是一种东西**——不同类型需要不同处理方式
2. **重写是软件工程中最危险的操作之一**——成本呈非线性增长，风险极高
3. **渐进式迁移几乎总是更安全的选择**——Strangler Fig Pattern 让每一步都可控
4. **迁移决策需要量化分析**——用数据代替直觉，用成本-收益模型代替"感觉该做"
5. **迁移和业务发展必须并行**——不能因为迁移而停止业务迭代

## 参考答案

### 练习一

**思路**：逐个分析每个问题的产生原因和团队的主观意愿。

**答案**：

1. **组件文件过大（800-2500 行）**：谨慎-无意。React 项目随着业务增长，组件自然会变大。团队可能一开始做了合理拆分，但需求迭代导致组件不断膨胀。这是演化的必然结果，不是偷懒。

2. **Redux store 结构不规范**：需要进一步判断。如果团队知道 Redux 最佳实践但"没时间改"，是鲁莽-有意；如果团队当时不熟悉 Redux 最佳实践，是鲁莽-无意。

3. **没有 TypeScript**：谨慎-有意或谨慎-无意。取决于项目启动时 TypeScript 的普及程度。如果 3 年前团队评估后认为 JS 够用，是有意的；如果当时没考虑过 TS，是无意的。

4. **使用已废弃的第三方库**：谨慎-无意。库的废弃是外部因素，不是团队的选择。这恰恰是渐进式迁移最适合解决的问题。

5. **代码注释少但有 README**：谨慎-无意。团队可能认为代码自解释即可，或者忙于功能开发。README 的存在说明团队有一定的文档意识。

**要点**：这些技术债中，大部分属于"谨慎-无意"类型——它们是系统演化的自然结果。这说明渐进式迁移是最合适的策略：不需要推倒重来，只需要在日常开发中逐步改善。

### 练习二

**思路**：用本课的决策框架逐一分析。

**答案**：

**推荐策略：渐进式迁移**

分析过程：

1. **代码量 8 万行**：超过 5 万行阈值，完全重写的隐性成本过高。排除重写。

2. **测试覆盖率 15%**：很低，迁移风险较高。但这恰恰说明需要迁移——老系统的测试覆盖率低意味着变更风险大，而渐进式迁移过程中会逐步补充测试。

3. **团队规模 5 人**：不足以支撑完全重写（重写需要至少一半人全力投入），但可以支持渐进式迁移（每个迭代分配 1-2 人做迁移，其余人维护老系统）。

4. **竞品压力中等**：没有紧迫到必须冒险重写，但也不能完全停滞。渐进式迁移允许同时做新功能和迁移。

5. **业务复杂度高**：高复杂度意味着老系统有很多隐式业务规则，重写时遗漏的风险极大。渐进式迁移每次只动一个模块，风险可控。

**具体建议**：
- 第 1 个月：补充核心业务路径的端到端测试，用本课介绍的代码估算工具评估各模块的迁移成本
- 第 2-3 个月：从耦合度最低的模块开始迁移（如用户管理），建立迁移工具链
- 第 4 个月起：逐步迁移业务模块，每个模块一个迭代
- 持续：新功能用新架构开发，老功能按优先级迁移

**要点**：这个决策的关键依据是代码量（8 万行）和业务复杂度（高）。这两个因素使得重写的隐性成本和风险都不可接受。渐进式迁移虽然周期更长，但每一步都是可控的。
