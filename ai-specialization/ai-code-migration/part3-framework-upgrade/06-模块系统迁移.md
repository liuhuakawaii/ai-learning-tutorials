# 第六课：模块系统迁移——从 CommonJS 到 ESM 的工程化转换

## 场景引入

你的团队维护着一个 Node.js 后端服务，项目始于 2019 年，全部使用 CommonJS 模块系统。随着 Node.js 22 的发布和 ESM 生态的成熟，越来越多的依赖库开始只提供 ESM 版本。

最近你尝试升级 `node-fetch` 到最新版本时遇到了这样的报错：

```
Error [ERR_REQUIRE_ESM]: require() of ES Module
D:\project\node_modules\node-fetch\src\index.js not supported.
Instead change the require of index.js in D:\project\src\api\client.js
to a dynamic import() which is available in all CommonJS modules.
```

这不是个例。chalk、glob、execa 等流行库都已转为 ESM-only。你的项目被困在了 CommonJS 的"版本锁定"中——不是因为你的代码有问题，而是因为模块系统不兼容。

模块系统迁移的本质是改变代码的**组织方式和加载机制**。CommonJS 和 ESM 的差异不仅仅是语法，还涉及执行时机、静态分析能力、循环依赖处理等深层差异。

## 学习目标

1. 理解 CommonJS 和 ESM 的核心差异，不只是语法层面
2. 将 `require`/`module.exports` 转换为 `import`/`export`
3. 正确配置 `package.json` 的 `type` 字段和文件扩展名
4. 处理迁移过程中的循环依赖问题
5. 利用动态 `import()` 实现渐进式迁移
6. 配置构建工具实现 Tree Shaking

## 核心概念

### 一、CommonJS 与 ESM 的本质差异

很多人认为 CommonJS 和 ESM 的区别只是语法不同——`require()` 换成 `import`，`module.exports` 换成 `export`。这种理解是片面的。两者的根本差异在于**模块解析和执行的时机**。

```
┌─────────────────────────────────────────────────────────────┐
│              CommonJS vs ESM 执行模型对比                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  CommonJS（运行时加载）                                      │
│  ┌───────────────────────────────────────────────┐         │
│  │ 代码执行到 require() 时                        │         │
│  │   ↓                                           │         │
│  │ 同步读取文件 → 编译并执行 → 缓存导出值          │         │
│  │   ↓                                           │         │
│  │ 返回导出值（可以是任意类型）                     │         │
│  └───────────────────────────────────────────────┘         │
│                                                             │
│  ESM（编译时静态分析）                                       │
│  ┌───────────────────────────────────────────────┐         │
│  │ 解析阶段：扫描所有 import/export 语句           │         │
│  │   ↓                                           │         │
│  │ 构建模块依赖图 → 实例化 → 按拓扑序求值          │         │
│  │   ↓                                           │         │
│  │ 导出的是活绑定（Live Binding），不是值的拷贝     │         │
│  └───────────────────────────────────────────────┘         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**导出语义不同**：CommonJS 导出的是值的拷贝，ESM 导出的是活绑定。

```js
// counter.cjs（CommonJS）
let count = 0;
function increment() { count++; }
module.exports = { count, increment };

// main.cjs
const { count, increment } = require('./counter.cjs');
increment();
console.log(count); // 0（值的拷贝，不会变化）
```

```js
// counter.mjs（ESM）
export let count = 0;
export function increment() { count++; }

// main.mjs
import { count, increment } from './counter.mjs';
increment();
console.log(count); // 1（活绑定，同步反映变化）
```

**条件导入行为不同**：CommonJS 允许在条件语句中使用 `require()`，ESM 的 `import` 必须在模块顶层。ESM 中需要改用动态 `import()`。

### 二、package.json 配置

`type` 字段决定了 Node.js 如何解释项目中的 `.js` 文件：

| 配置 | 效果 |
|------|------|
| `"type": "module"` | `.js` 文件按 ESM 解析，CommonJS 文件用 `.cjs` |
| `"type": "commonjs"`（默认） | `.js` 文件按 CommonJS 解析，ESM 文件用 `.mjs` |

在渐进式迁移阶段，可以同时支持两种模块系统：

```json
{
  "name": "my-backend-service",
  "version": "2.0.0",
  "type": "module",
  "engines": { "node": ">=18.0.0" },
  "exports": {
    ".": {
      "import": "./src/index.mjs",
      "require": "./src/index.cjs"
    }
  },
  "main": "./src/index.cjs",
  "module": "./src/index.mjs"
}
```

### 三、语法转换：require 到 import

```js
// CommonJS
const express = require('express');
const { readFile, writeFile } = require('fs/promises');
const config = require('./config.json', { type: 'json' });

// ESM
import express from 'express';
import { readFile, writeFile } from 'fs/promises';
import config from './config.json' with { type: 'json' };
```

关键差异：
1. ESM 中引用本地文件必须带扩展名（`.js`、`.mjs`）
2. JSON 导入需要 `with { type: 'json' }` 语法（Node.js 22+）
3. ESM 中没有 `__dirname` 和 `__filename`，需要手动构建

```js
// CommonJS
const path = require('path');
const dataDir = path.join(__dirname, '../data');

// ESM
import { fileURLToPath } from 'url';
import { dirname, join } from 'path';
const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);
const dataDir = join(__dirname, '../data');
```

导出语法转换：

```js
// CommonJS
function createUser(data) { /* ... */ }
module.exports = { createUser };

// ESM
export function createUser(data) { /* ... */ }
```

### 四、循环依赖处理

循环依赖是模块系统迁移中最棘手的问题之一。CommonJS 和 ESM 处理循环依赖的方式完全不同。

```
┌─────────────────────────────────────────────────────────┐
│              循环依赖处理机制对比                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  CommonJS：部分导出                                     │
│  ┌───────────────────────────────────────────┐         │
│  │ A require(B) → 执行 B                     │         │
│  │   B require(A) → A 尚未执行完              │         │
│  │   → 返回 A 当前已导出的部分（可能不完整）    │         │
│  └───────────────────────────────────────────┘         │
│  结果：B 拿到的是 A 的部分导出                           │
│                                                         │
│  ESM：活绑定 + TDZ                                      │
│  ┌───────────────────────────────────────────┐         │
│  │ 解析阶段：A 和 B 的绑定关系已建立           │         │
│  │ 求值阶段：按拓扑序执行                      │         │
│  │   如果在初始化阶段访问未完成的绑定           │         │
│  │   → 抛出 ReferenceError（TDZ）             │         │
│  └───────────────────────────────────────────┘         │
│  结果：只有函数内的延迟访问才能成功                       │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

处理循环依赖的策略：

**策略一：提取共享模块**——将 A 和 B 共同依赖的部分提取到第三个模块 C，打破循环。

```js
// 旧代码：order.js 和 inventory.js 互相依赖
// 新代码：提取 shared/order-types.js，order 和 inventory 各自依赖它
```

**策略二：延迟导入**——在函数内部使用动态 `import()` 推迟加载时机。

```js
export async function createOrder(items) {
  const { checkStock } = await import('./inventory.js');
  // ...
}
```

### 五、动态 import 与渐进式迁移

动态 `import()` 是渐进式迁移的关键工具。它允许在 CommonJS 项目中按需加载 ESM 模块：

```js
// src/api/client.js（CommonJS）
async function createApiClient() {
  const { default: fetch } = await import('node-fetch');
  const { default: chalk } = await import('chalk');

  return {
    async get(endpoint) {
      console.log(chalk.blue(`GET ${endpoint}`));
      const response = await fetch(`https://api.example.com${endpoint}`);
      return response.json();
    },
  };
}

module.exports = { createApiClient };
```

在 ESM 项目中，动态 `import()` 可以实现代码分割和按需加载：

```js
// src/router.mjs
export async function handleRequest(route) {
  const handlers = {
    '/users': () => import('./handlers/users.mjs'),
    '/orders': () => import('./handlers/orders.mjs'),
  };
  const loader = handlers[route];
  if (!loader) return { status: 404, body: 'Not Found' };
  const { default: handler } = await loader();
  return handler();
}
```

### 六、Tree Shaking 原理与实践

Tree Shaking 是 ESM 的重要优势。因为 ESM 的 `import`/`export` 是静态声明，构建工具可以在编译时分析出哪些导出被使用了，从而移除未使用的代码。

```
┌─────────────────────────────────────────────────────────┐
│              Tree Shaking 工作原理                       │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  源代码：                                                │
│  // utils.js                                            │
│  export function formatDate(d) { ... }                  │
│  export function formatCurrency(n) { ... }              │
│  export function generateId() { ... }                   │
│                                                         │
│  // app.js                                              │
│  import { formatDate } from './utils.js';               │
│                                                         │
│  构建工具静态分析：                                      │
│  formatDate → 被使用 ✓  保留                            │
│  formatCurrency → 未使用 ✗  移除                        │
│  generateId → 未使用 ✗  移除                            │
│                                                         │
│  CommonJS 无法做到：                                     │
│  const utils = require('./utils');                      │
│  // 运行时才知道用了 utils.formatDate                   │
│  // 编译器必须保留整个 utils 对象                        │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

要让 Tree Shaking 真正生效：
1. 使用具名导出（named export），避免默认导出整个对象
2. 确保构建工具支持（Vite、Webpack 5+、Rollup 都支持）
3. 在 `package.json` 中设置 `"sideEffects": false`

### 七、自动化 Codemod 工具

手动转换大量文件效率低下，下面是一个基于 `ts-morph` 的 CommonJS → ESM 转换器：

```js
// scripts/cjs-to-esm-codemod.mjs
import { Project, SyntaxKind } from 'ts-morph';
import { writeFileSync } from 'fs';

function transformFile(filePath) {
  const project = new Project({ compilerOptions: { allowJs: true } });
  const sourceFile = project.addSourceFileAtPath(filePath);
  const changes = [];

  sourceFile.forEachDescendant((node) => {
    if (node.isKind(SyntaxKind.CallExpression)) {
      const expression = node.getExpression();
      if (expression.getText() === 'require') {
        const args = node.getArguments();
        if (args.length === 0) return;
        const modulePath = args[0].getText().replace(/['"]/g, '');
        const parent = node.getParent();

        if (parent?.isKind(SyntaxKind.VariableDeclaration)) {
          const varName = parent.getName();
          if (varName.startsWith('{')) {
            const bindings = varName.replace(/[{}]/g, '').split(',').map(s => s.trim());
            changes.push({ type: 'destructured-import', bindings, modulePath,
              start: parent.getPos(), end: parent.getParent().getParent().getEnd() });
          } else {
            changes.push({ type: 'default-import', defaultName: varName, modulePath,
              start: parent.getParent().getParent().getPos(),
              end: parent.getParent().getParent().getEnd() });
          }
        }
      }
    }

    if (node.isKind(SyntaxKind.PropertyAccessExpression) && node.getText() === 'module.exports') {
      const parent = node.getParent();
      if (parent?.isKind(SyntaxKind.BinaryExpression)) {
        const right = parent.getRight();
        if (right?.isKind(SyntaxKind.ObjectLiteralExpression)) {
          const exportNames = right.getProperties().map(p => p.getName());
          changes.push({ type: 'named-exports', exportNames,
            start: parent.getPos(), end: parent.getEnd() });
        }
      }
    }
  });

  let newCode = sourceFile.getFullText();
  const imports = changes.filter(c => c.type === 'default-import' || c.type === 'destructured-import');
  const exportChanges = changes.filter(c => c.type === 'named-exports');

  let importStatements = '';
  for (const imp of imports) {
    const ext = imp.modulePath.startsWith('.') ? '.js' : '';
    if (imp.type === 'default-import') {
      importStatements += `import ${imp.defaultName} from '${imp.modulePath}${ext}';\n`;
    } else {
      importStatements += `import { ${imp.bindings.join(', ')} } from '${imp.modulePath}${ext}';\n`;
    }
  }

  for (const imp of imports.reverse()) {
    newCode = newCode.slice(0, imp.start) + '/* REMOVED */' + newCode.slice(imp.end);
  }
  for (const exp of exportChanges.reverse()) {
    newCode = newCode.slice(0, exp.start) + exp.exportNames.map(n => `export { ${n} };`).join('\n') + newCode.slice(exp.end);
  }

  newCode = newCode.replace(/\/\* REMOVED \*\/\n?/g, '');
  newCode = importStatements + '\n' + newCode;

  return newCode;
}

const targetFile = process.argv[2];
if (!targetFile) { console.error('用法: node cjs-to-esm-codemod.mjs <文件路径>'); process.exit(1); }

const result = transformFile(targetFile);
const outputFile = targetFile.replace(/\.js$/, '.mjs');
writeFileSync(outputFile, result);
console.log(`转换完成：${targetFile} → ${outputFile}`);
```

## 常见误区

**误区一：认为加了 `"type": "module"` 就完成了迁移**

设置 `type: "module"` 只是告诉 Node.js 如何解析 `.js` 文件。如果你的代码中还有 `require()` 调用，运行时会直接报错。迁移必须是语法和配置同时完成的。

**误区二：在 ESM 中用 `require()` 加载 JSON**

迁移到 ESM 后，需要使用 `import ... with { type: 'json' }` 语法（Node.js 22+），或者用 `fs.readFileSync` 读取后 `JSON.parse`。

**误区三：忽略本地模块路径的扩展名**

CommonJS 中 `require('./utils')` 会自动尝试 `utils.js`、`utils/index.js` 等。ESM 不会——你必须写完整的路径 `import { x } from './utils.js'`。这是迁移中最常见的报错来源。

**误区四：认为 ESM 一定比 CommonJS 快**

ESM 的优势在于静态分析和 Tree Shaking，不是运行时性能。选择 ESM 的理由是生态兼容性和代码优化能力，不是运行速度。

## 小结与练习

### 小结

1. CommonJS 和 ESM 的核心差异在于执行时机——运行时加载 vs 编译时静态分析
2. ESM 导出的是活绑定，CommonJS 导出的是值拷贝，这影响了循环依赖的行为
3. `package.json` 的 `type` 字段决定 `.js` 文件的解析方式，迁移期间可用 `.mjs`/`.cjs` 共存
4. ESM 中本地模块路径必须带扩展名，没有 `__dirname`/`__filename` 需要手动构建
5. 循环依赖可通过提取共享模块或延迟导入解决
6. 动态 `import()` 是渐进式迁移的关键工具
7. Tree Shaking 是 ESM 的重要优势，需要具名导出和 `"sideEffects": false` 配合

### 练习一：模块语法转换

将以下 CommonJS 模块转换为 ESM：

```js
// services/email-service.js
const nodemailer = require('nodemailer');
const { readFile } = require('fs/promises');
const path = require('path');
const config = require('../config.json');
const { formatDate } = require('../utils/date-helpers');

class EmailService {
  constructor() {
    this.transporter = nodemailer.createTransport(config.smtp);
  }
  async sendOrderConfirmation(order) {
    const templatePath = path.join(__dirname, '../templates/order-confirm.html');
    const template = await readFile(templatePath, 'utf-8');
    const html = template.replace('{{name}}', order.customerName);
    await this.transporter.sendMail({ from: config.email.from, to: order.email, html });
  }
}

module.exports = EmailService;
module.exports.createEmailService = () => new EmailService();
```

## 参考答案

### 练习一

**思路**：将 `require` 替换为 `import`，`module.exports` 替换为 `export`。本地路径加 `.js` 扩展名，`__dirname` 用 `import.meta.url` 替代，JSON 导入使用 `with` 语法。

**答案**：

```js
// services/email-service.mjs
import nodemailer from 'nodemailer';
import { readFile } from 'fs/promises';
import { dirname, join } from 'path';
import { fileURLToPath } from 'url';
import config from '../config.json' with { type: 'json' };
import { formatDate } from '../utils/date-helpers.js';

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

export default class EmailService {
  constructor() {
    this.transporter = nodemailer.createTransport(config.smtp);
  }
  async sendOrderConfirmation(order) {
    const templatePath = join(__dirname, '../templates/order-confirm.html');
    const template = await readFile(templatePath, 'utf-8');
    const html = template.replace('{{name}}', order.customerName);
    await this.transporter.sendMail({ from: config.email.from, to: order.email, html });
  }
}

export function createEmailService() {
  return new EmailService();
}
```

**要点**：`import.meta.url` + `fileURLToPath` 替代 `__dirname`；JSON 导入需要 `with { type: 'json' }`；本地模块路径必须带 `.js` 扩展名。

### 练习二

**思路**：将"获取用户订单"提取为独立的服务模块，让 controller 依赖 service 而不是互相依赖。

**答案**：

```js
// services/user-order-service.mjs
export async function getUserOrders(userId) {
  return [{ id: 1, userId }];
}

export async function getUserProfile(userId) {
  return { userId, name: '用户' + userId };
}

export async function getUserOrderSummary(userId) {
  const [profile, orders] = await Promise.all([
    getUserProfile(userId),
    getUserOrders(userId),
  ]);
  return { ...profile, orderCount: orders.length };
}
```

```js
// controllers/user.mjs
import { getUserOrderSummary } from '../services/user-order-service.mjs';
export async function handleGetUserProfile(userId) {
  return getUserOrderSummary(userId);
}
```

```js
// controllers/order.mjs
import { getUserOrders } from '../services/user-order-service.mjs';
export async function handleGetUserOrders(userId) {
  return getUserOrders(userId);
}
```

**要点**：循环依赖的根源是两个模块互相调用对方的函数；将共享逻辑提取到 service 层是最干净的解法；重构后的依赖关系是单向的：controller → service。
