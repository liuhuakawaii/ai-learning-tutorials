# 依赖注入与接口抽象

## 场景引入

你的团队正在把一个使用 MySQL 的后端服务迁移到 PostgreSQL。数据库层涉及 80 多个文件，散布在业务逻辑的各个角落——直接 `import mysql` 后在 controller 里写 SQL，没有统一的数据访问层。

```typescript
// 每个 controller 都直接调用 MySQL
import mysql from 'mysql2/promise';

async function getUser(id: string) {
  const conn = await mysql.createConnection({ /* 硬编码配置 */ });
  const [rows] = await conn.execute('SELECT * FROM users WHERE id = ?', [id]);
  return rows[0];
}

async function createOrder(userId: string, items: Item[]) {
  const conn = await mysql.createConnection({ /* 硬编码配置 */ });
  // MySQL 特有的语法：INSERT IGNORE
  await conn.execute('INSERT IGNORE INTO orders ...', [...]);
}
```

直接改？你得同时修改 80 个文件的 SQL 语法、连接配置、ORM 适配，还要保证线上服务不中断。MySQL 的 `INSERT IGNORE` 在 PostgreSQL 中是 `ON CONFLICT DO NOTHING`，MySQL 的 `AUTO_INCREMENT` 在 PostgreSQL 中是 `SERIAL`——这些差异散布在整个代码库里。

正确做法是：先在旧代码和新代码之间建立一层抽象接口，让两个数据库实现可以并行运行。通过依赖注入，业务代码只依赖接口，不关心底层是 MySQL 还是 PostgreSQL。切换数据库只需要改一个配置，而不是改 80 个文件。

这就是依赖注入和接口抽象在代码迁移中的核心价值：**它让新旧代码能够并行运行，把一个危险的"一刀切"切换变成安全的渐进式迁移**。

## 学习目标

完成本课学习后，你将能够：

1. 理解依赖注入在代码迁移中的作用
2. 实现适配器模式（Adapter Pattern）包装遗留代码

4. 设计迁移边界的 TypeScript 接口
5. 构建新旧代码并行运行的架构

## 核心概念

### 为什么迁移需要依赖注入

想象一下没有抽象层的代码结构——业务代码直接依赖具体实现：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  UserController│────▶│   MySQL      │────▶│   MySQL DB   │
│  OrderController│──▶│   Driver     │────▶│              │
│  PaymentCtrl   │───▶│              │────▶│              │
└──────────────┘     └──────────────┘     └──────────────┘

迁移时的问题：要同时修改所有 Controller
```

引入依赖注入后：

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  UserController│──┐ │              │     │   MySQL DB   │
│  OrderController│─┤ │  Database    │─┬──▶│              │
│  PaymentCtrl   │─┤▶│  Interface   │ │   └──────────────┘
└──────────────┘ │ │              │ │
                  │ └──────────────┘ │   ┌──────────────┐
                  │                   └──▶│  PostgreSQL  │
                  │                       │     DB       │
                  │                       └──────────────┘
                  │
            只依赖接口，不关心实现
```

依赖注入的核心思想是**依赖倒置原则**（Dependency Inversion Principle）：高层模块不应该依赖低层模块，两者都应该依赖抽象。

在迁移场景中，这意味着：

1. **业务代码依赖接口**：Controller 只知道"我需要一个数据库"，不知道是 MySQL 还是 PostgreSQL
2. **实现细节可替换**：MySQL 和 PostgreSQL 都实现同一个接口，可以互相替换
3. **切换通过配置控制**：改一行配置就能切换数据库，不需要改业务代码

### 接口抽象的核心思想

接口抽象不是"未来可能需要"的过度设计，而是迁移场景中的必要工具。它的核心是定义一个**契约**——所有实现都必须遵守的行为规范：

```
┌─────────────────────────────────────────────────────────┐
│                    UserRepository 接口                    │
├─────────────────────────────────────────────────────────┤
│  findById(id: string): Promise<User | null>              │
│  create(data: CreateUserDto): Promise<User>              │
│  update(id: string, data: UpdateUserDto): Promise<User>  │
│  delete(id: string): Promise<void>                       │
│  findByEmail(email: string): Promise<User | null>        │
└─────────────────────────────────────────────────────────┘
            ▲                       ▲
            │                       │
┌───────────┴──────────┐  ┌────────┴──────────────┐
│  MySQLUserRepository │  │ PostgresUserRepository │
│  - 用 mysql2 实现    │  │  - 用 pg 实现          │
│  - INSERT IGNORE     │  │  - ON CONFLICT         │
│  - AUTO_INCREMENT    │  │  - SERIAL              │
└──────────────────────┘  └───────────────────────┘
```

### JavaScript/TypeScript 中的依赖注入（无框架）

很多工程师一提到依赖注入就想到 Spring、NestJS 这些框架。实际上，TypeScript 中最简单、最实用的依赖注入就是**构造函数参数**：

```typescript
// 定义接口
interface UserRepository {
  findById(id: string): Promise<User | null>;
  create(data: CreateUserDto): Promise<User>;
  update(id: string, data: UpdateUserDto): Promise<User>;
  delete(id: string): Promise<void>;
}

// 业务代码只依赖接口
class UserService {
  // 依赖通过构造函数注入
  constructor(private readonly userRepo: UserRepository) {}

  async getUser(id: string): Promise<User> {
    const user = await this.userRepo.findById(id);
    if (!user) throw new Error(`User ${id} not found`);
    return user;
  }

  async register(data: CreateUserDto): Promise<User> {
    const existing = await this.userRepo.findByEmail(data.email);
    if (existing) throw new Error('Email already registered');
    return this.userRepo.create(data);
  }
}

// MySQL 实现
class MySQLUserRepository implements UserRepository {
  constructor(private readonly pool: mysql.Pool) {}

  async findById(id: string): Promise<User | null> {
    const [rows] = await this.pool.execute(
      'SELECT * FROM users WHERE id = ?', [id]
    );
    return rows[0] as User || null;
  }

  async create(data: CreateUserDto): Promise<User> {
    const [result] = await this.pool.execute(
      'INSERT INTO users (name, email) VALUES (?, ?)',
      [data.name, data.email]
    );
    return { id: result.insertId, ...data };
  }

  // ... 其他方法
}

// PostgreSQL 实现
class PostgresUserRepository implements UserRepository {
  constructor(private readonly pool: pg.Pool) {}

  async findById(id: string): Promise<User | null> {
    const result = await this.pool.query(
      'SELECT * FROM users WHERE id = $1', [id]
    );
    return result.rows[0] || null;
  }

  async create(data: CreateUserDto): Promise<User> {
    const result = await this.pool.query(
      'INSERT INTO users (name, email) VALUES ($1, $2) RETURNING *',
      [data.name, data.email]
    );
    return result.rows[0];
  }

  // ... 其他方法
}

// 组装：根据配置选择实现
function createUserService(): UserService {
  const dbType = process.env.DB_TYPE || 'mysql';

  if (dbType === 'mysql') {
    const pool = mysql.createPool({ /* MySQL 配置 */ });
    const repo = new MySQLUserRepository(pool);
    return new UserService(repo);
  } else {
    const pool = new pg.Pool({ /* PostgreSQL 配置 */ });
    const repo = new PostgresUserRepository(pool);
    return new UserService(repo);
  }
}
```

注意这里没有使用任何 DI 框架。**构造函数注入是最简单、最透明的依赖注入方式**——你一眼就能看出 `UserService` 依赖什么，不需要理解框架的魔法。

### Python 中的依赖注入（无框架）

Python 中的依赖注入同样简单，使用类型注解和默认参数：

```python
from abc import ABC, abstractmethod
from typing import Optional, Protocol
from dataclasses import dataclass

# 使用 Protocol 定义接口（Python 3.8+）
class UserRepository(Protocol):
    def find_by_id(self, id: str) -> Optional['User']: ...
    def create(self, data: 'CreateUserDto') -> 'User': ...
    def update(self, id: str, data: 'UpdateUserDto') -> 'User': ...
    def delete(self, id: str) -> None: ...

@dataclass
class User:
    id: str
    name: str
    email: str

@dataclass
class CreateUserDto:
    name: str
    email: str

# 业务代码只依赖协议
class UserService:
    def __init__(self, user_repo: UserRepository):
        self._user_repo = user_repo

    def get_user(self, id: str) -> User:
        user = self._user_repo.find_by_id(id)
        if not user:
            raise ValueError(f"User {id} not found")
        return user

    def register(self, data: CreateUserDto) -> User:
        existing = self._user_repo.find_by_email(data.email)
        if existing:
            raise ValueError("Email already registered")
        return self._user_repo.create(data)

# MySQL 实现
class MySQLUserRepository:
    def __init__(self, connection_string: str):
        import mysql.connector
        self._conn = mysql.connector.connect(connection_string)

    def find_by_id(self, id: str) -> Optional[User]:
        cursor = self._conn.cursor(dictionary=True)
        cursor.execute("SELECT * FROM users WHERE id = %s", (id,))
        row = cursor.fetchone()
        return User(**row) if row else None

    def create(self, data: CreateUserDto) -> User:
        cursor = self._conn.cursor()
        cursor.execute(
            "INSERT INTO users (name, email) VALUES (%s, %s)",
            (data.name, data.email)
        )
        self._conn.commit()
        return User(id=str(cursor.lastrowid), name=data.name, email=data.email)

# PostgreSQL 实现
class PostgresUserRepository:
    def __init__(self, connection_string: str):
        import psycopg2
        self._conn = psycopg2.connect(connection_string)

    def find_by_id(self, id: str) -> Optional[User]:
        cursor = self._conn.cursor(cursor_factory=psycopg2.extras.DictCursor)
        cursor.execute("SELECT * FROM users WHERE id = %s", (id,))
        row = cursor.fetchone()
        return User(**row) if row else None

    def create(self, data: CreateUserDto) -> User:
        cursor = self._conn.cursor()
        cursor.execute(
            "INSERT INTO users (name, email) VALUES (%s, %s) RETURNING id",
            (data.name, data.email)
        )
        user_id = cursor.fetchone()[0]
        self._conn.commit()
        return User(id=str(user_id), name=data.name, email=data.email)

# 组装
import os

def create_user_service() -> UserService:
    db_type = os.environ.get("DB_TYPE", "mysql")

    if db_type == "mysql":
        repo = MySQLUserRepository(os.environ["MYSQL_URL"])
    else:
        repo = PostgresUserRepository(os.environ["POSTGRES_URL"])

    return UserService(repo)
```

## 适配器模式在迁移中的应用

迁移场景中，新旧系统的接口往往不兼容。适配器模式可以把旧接口包装成新接口，让业务代码统一使用新接口：

```typescript
// 旧系统接口（已经存在的代码，不能修改）
class LegacyUserService {
  async getUserById(userId: number): Promise<{ user_id: number; user_name: string }> {
    // 旧系统的实现
    return { user_id: userId, user_name: 'John' };
  }

  async createUser(userName: string): Promise<number> {
    // 返回新用户的 ID
    return 123;
  }
}

// 新系统接口（迁移目标）
interface ModernUserService {
  findById(id: string): Promise<User | null>;
  create(data: CreateUserDto): Promise<User>;
}

// 适配器：把旧接口包装成新接口
class LegacyUserAdapter implements ModernUserService {
  constructor(private readonly legacy: LegacyUserService) {}

  async findById(id: string): Promise<User | null> {
    // 转换参数：string → number
    const numericId = parseInt(id, 10);
    if (isNaN(numericId)) return null;

    // 调用旧接口
    const legacyResult = await this.legacy.getUserById(numericId);

    // 转换结果：旧格式 → 新格式
    return {
      id: String(legacyResult.user_id),
      name: legacyResult.user_name,
      email: '', // 旧系统没有这个字段
    };
  }

  async create(data: CreateUserDto): Promise<User> {
    // 调用旧接口
    const newId = await this.legacy.createUser(data.name);

    // 转换结果
    return {
      id: String(newId),
      name: data.name,
      email: data.email,
    };
  }
}

// 使用：业务代码不知道底层是旧系统还是新系统
async function setupApp() {
  let userService: ModernUserService;

  if (process.env.USE_LEGACY === 'true') {
    // 使用旧系统（通过适配器）
    const legacy = new LegacyUserService();
    userService = new LegacyUserAdapter(legacy);
  } else {
    // 使用新系统
    userService = new PostgresUserService();
  }

  // 业务代码统一使用 ModernUserService 接口
  const user = await userService.findById('123');
}
```

适配器模式的关键价值在于：**你可以在不修改旧代码的情况下，让旧代码符合新接口**。这对于迁移场景至关重要——你不能要求旧系统"改一下接口"，因为它还在运行。

## 渐进式引入 DI：从紧耦合到松耦合

实际项目中，你不可能一步到位把所有代码改成依赖注入。正确做法是渐进式重构：

```
步骤 1: 提取接口
    从现有代码中提取出接口定义
    （不改变任何行为，只是新增接口类型）

步骤 2: 让现有类实现接口
    class MySQLUserRepo implements UserRepository { ... }
    （添加 implements 声明，不改变方法）

步骤 3: 修改调用方的类型声明
    constructor(private repo: MySQLUserRepo)
    → constructor(private repo: UserRepository)
    （只改类型，不改实现）

步骤 4: 注入实例
    在组装点（main.ts）创建实例并传入
    （把 new MySQLUserRepo() 从各处移到一个地方）

步骤 5: 添加新实现
    class PostgresUserRepo implements UserRepository { ... }
    （新增实现，不影响旧代码）

步骤 6: 切换
    通过配置切换实现
    （安全地渐进式迁移）
```

每一步都是安全的——代码行为没有改变，只是结构在优化。任何时候停下来，代码都是可运行的。

## Mock 与测试：依赖注入如何让迁移可测试

依赖注入的另一个巨大好处是**可测试性**。当你需要测试业务逻辑时，不需要真实的数据库：

```typescript
// 测试用的 Mock 实现
class MockUserRepository implements UserRepository {
  private users: Map<string, User> = new Map();

  async findById(id: string): Promise<User | null> {
    return this.users.get(id) || null;
  }

  async create(data: CreateUserDto): Promise<User> {
    const user: User = {
      id: String(this.users.size + 1),
      name: data.name,
      email: data.email,
    };
    this.users.set(user.id, user);
    return user;
  }

  async update(id: string, data: UpdateUserDto): Promise<User> {
    const existing = this.users.get(id);
    if (!existing) throw new Error('Not found');
    const updated = { ...existing, ...data };
    this.users.set(id, updated);
    return updated;
  }

  async delete(id: string): Promise<void> {
    this.users.delete(id);
  }

  // 测试辅助方法
  seed(users: User[]): void {
    for (const user of users) {
      this.users.set(user.id, user);
    }
  }

  reset(): void {
    this.users.clear();
  }
}

// 测试代码
describe('UserService', () => {
  let service: UserService;
  let mockRepo: MockUserRepository;

  beforeEach(() => {
    mockRepo = new MockUserRepository();
    service = new UserService(mockRepo);
  });

  test('getUser returns user when exists', async () => {
    mockRepo.seed([{ id: '1', name: 'John', email: 'john@example.com' }]);

    const user = await service.getUser('1');
    expect(user.name).toBe('John');
  });

  test('getUser throws when user not found', async () => {
    await expect(service.getUser('999')).rejects.toThrow('User 999 not found');
  });

  test('register prevents duplicate emails', async () => {
    mockRepo.seed([{ id: '1', name: 'John', email: 'john@example.com' }]);

    await expect(
      service.register({ name: 'Jane', email: 'john@example.com' })
    ).rejects.toThrow('Email already registered');
  });
});
```

没有依赖注入的话，测试就必须连接真实的数据库——慢、不稳定、需要清理数据。有了依赖注入，测试可以在毫秒级别完成，不依赖任何外部服务。

## 2025 年的 DI 工具

虽然构造函数注入在大多数场景下足够好，但大型项目可能需要更强大的 DI 工具：

**TypeScript 生态：**

```typescript
// TSyringe（微软出品，轻量级）
import { container, injectable, inject } from 'tsyringe';

@injectable()
class UserService {
  constructor(@inject('UserRepository') private repo: UserRepository) {}
}

// 注册实现
container.register('UserRepository', {
  useClass: process.env.DB === 'pg' ? PostgresUserRepository : MySQLUserRepository
});

// 解析时自动注入
const service = container.resolve(UserService);
```

```typescript
// InversifyJS（功能更丰富）
import { Container, injectable, inject, interfaces } from 'inversify';

const container = new Container();
container.bind<UserRepository>('UserRepository').to(MySQLUserRepository);
container.bind<UserService>('UserService').to(UserService);
```

**Python 生态：**

```python
# dependency-injector（最流行的 Python DI 框架）
from dependency_injector import containers, providers
from dependency_injector.wiring import Provide, inject

class Container(containers.DeclarativeContainer):
    config = providers.Configuration()

    user_repo = providers.Singleton(
        MySQLUserRepository,
        connection_string=config.db.url
    )

    user_service = providers.Factory(
        UserService,
        user_repo=user_repo
    )

@inject
def get_user(user_id: str, service: UserService = Provide[Container.user_service]):
    return service.get_user(user_id)
```

但要注意：**在迁移场景中，引入 DI 框架本身就是一个迁移任务**。不要在迁移数据库的同时引入一个新的 DI 框架——这会让问题复杂度翻倍。先用构造函数注入完成数据库迁移，稳定之后再考虑是否需要引入框架。

## 常见误区

**误区一：过度设计 DI 容器**

为一个只有 5 个服务的小项目引入 InversifyJS + 装饰器 + 自动扫描，增加了大量认知负担和调试难度。构造函数注入在 90% 的场景下足够。

**误区二：迁移时一步到位引入框架**

同时做数据库迁移 + DI 框架引入 + 接口重构，风险叠加。应该分步：先引入接口抽象，再迁移数据库，最后评估是否需要框架。

**误区三：接口设计过于宽泛**

```typescript
// 错误：接口太大，什么都放进去
interface Database {
  findUser(id: string): Promise<User>;
  createOrder(data: OrderDto): Promise<Order>;
  getProducts(filter: ProductFilter): Promise<Product[]>;
  // ... 20 个方法
}
```

接口应该按**业务领域**划分，每个接口只包含相关的方法。这样迁移时可以逐个领域替换，不需要一次性切换所有功能。

**误区四：忽略错误处理的一致性**

MySQL 和 PostgreSQL 的错误类型不同。MySQL 抛出 `ER_DUP_ENTRY`，PostgreSQL 抛出 `23505`（unique_violation）。接口层需要统一错误处理：

```typescript
// 接口层统一错误
class DuplicateError extends Error {
  constructor(entity: string, field: string) {
    super(`${entity} with this ${field} already exists`);
    this.name = 'DuplicateError';
  }
}

// MySQL 实现中转换错误
async create(data: CreateUserDto): Promise<User> {
  try {
    // ... MySQL 操作
  } catch (error) {
    if (error.code === 'ER_DUP_ENTRY') {
      throw new DuplicateError('User', 'email');
    }
    throw error;
  }
}

// PostgreSQL 实现中转换错误
async create(data: CreateUserDto): Promise<User> {
  try {
    // ... PostgreSQL 操作
  } catch (error) {
    if (error.code === '23505') {
      throw new DuplicateError('User', 'email');
    }
    throw error;
  }
}
```

## 小结

- 依赖注入让新旧代码能够并行运行，是迁移场景的核心架构模式
- 接口抽象定义契约，适配器包装旧实现，两者配合实现安全迁移
- 构造函数注入是最简单、最实用的 DI 方式，不需要框架
- 渐进式引入 DI：提取接口 → 实现接口 → 修改类型 → 注入实例 → 添加新实现 → 切换
- DI 让代码可测试，Mock 实现可以在不依赖外部服务的情况下验证业务逻辑

### 练习二：设计适配器

假设旧系统有一个这样的接口：

```python
class LegacyPayment:
    def charge(self, user_id: int, amount_cents: int) -> dict:
        # 返回 {'status': 'ok', 'transaction_id': '...'}
        pass
```

新系统的接口是：

```python
class PaymentService(Protocol):
    def process_payment(self, user_id: str, amount: Decimal) -> PaymentResult: ...
```

请编写一个适配器，将旧接口包装成新接口。

---

## 参考答案

### 练习一

**思路**：提取数据库操作为接口，让 `OrderService` 依赖接口而不是具体实现。使用构造函数注入传递实现。

**答案**：

```typescript
// 1. 定义接口
interface Order {
  id: string;
  userId: string;
  total: number;
  createdAt: Date;
}

interface CreateOrderDto {
  userId: string;
  total: number;
}

interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  create(data: CreateOrderDto): Promise<Order>;
}

// 2. MySQL 实现
import mysql from 'mysql2/promise';

class MySQLOrderRepository implements OrderRepository {
  constructor(private readonly pool: mysql.Pool) {}

  async findById(id: string): Promise<Order | null> {
    const [rows] = await this.pool.execute(
      'SELECT * FROM orders WHERE id = ?', [id]
    );
    return (rows as any[])[0] || null;
  }

  async create(data: CreateOrderDto): Promise<Order> {
    const [result] = await this.pool.execute(
      'INSERT INTO orders (user_id, total) VALUES (?, ?)',
      [data.userId, data.total]
    );
    return {
      id: String((result as any).insertId),
      userId: data.userId,
      total: data.total,
      createdAt: new Date(),
    };
  }
}

// 3. PostgreSQL 实现
import pg from 'pg';

class PostgresOrderRepository implements OrderRepository {
  constructor(private readonly pool: pg.Pool) {}

  async findById(id: string): Promise<Order | null> {
    const result = await this.pool.query(
      'SELECT * FROM orders WHERE id = $1', [id]
    );
    return result.rows[0] || null;
  }

  async create(data: CreateOrderDto): Promise<Order> {
    const result = await this.pool.query(
      'INSERT INTO orders (user_id, total) VALUES ($1, $2) RETURNING *',
      [data.userId, data.total]
    );
    return result.rows[0];
  }
}

// 4. 重构后的 OrderService
class OrderService {
  // 只依赖接口，不关心具体实现
  constructor(private readonly orderRepo: OrderRepository) {}

  async getOrder(id: string): Promise<Order> {
    const order = await this.orderRepo.findById(id);
    if (!order) throw new Error(`Order ${id} not found`);
    return order;
  }

  async createOrder(userId: string, total: number): Promise<Order> {
    return this.orderRepo.create({ userId, total });
  }
}

// 5. 组装点
function createOrderService(): OrderService {
  const dbType = process.env.DB_TYPE || 'mysql';

  if (dbType === 'mysql') {
    const pool = mysql.createPool({
      host: process.env.MYSQL_HOST,
      user: process.env.MYSQL_USER,
      database: process.env.MYSQL_DB,
    });
    return new OrderService(new MySQLOrderRepository(pool));
  } else {
    const pool = new pg.Pool({
      connectionString: process.env.POSTGRES_URL,
    });
    return new OrderService(new PostgresOrderRepository(pool));
  }
}
```

**要点**：
- `OrderRepository` 接口定义了契约，业务代码只依赖这个接口
- MySQL 和 PostgreSQL 各自实现接口，处理各自的语法差异
- 组装点（`createOrderService`）负责根据配置创建正确的实现
- `OrderService` 的代码完全不需要修改就能切换数据库

### 练习二

**思路**：适配器需要处理三类转换：参数类型转换（`int` → `string`、`int` → `Decimal`）、返回值转换（`dict` → `PaymentResult`）、错误处理转换。

**答案**：

```python
from decimal import Decimal
from dataclasses import dataclass
from typing import Protocol

# 新系统的类型定义
@dataclass
class PaymentResult:
    success: bool
    transaction_id: str
    amount: Decimal
    user_id: str

class PaymentService(Protocol):
    def process_payment(self, user_id: str, amount: Decimal) -> PaymentResult: ...

# 旧系统接口（不能修改）
class LegacyPayment:
    def charge(self, user_id: int, amount_cents: int) -> dict:
        # 模拟旧系统的实现
        return {'status': 'ok', 'transaction_id': 'txn_123'}

# 适配器
class LegacyPaymentAdapter:
    def __init__(self, legacy: LegacyPayment):
        self._legacy = legacy

    def process_payment(self, user_id: str, amount: Decimal) -> PaymentResult:
        # 1. 参数转换：string → int
        try:
            numeric_user_id = int(user_id)
        except ValueError:
            raise ValueError(f"Invalid user ID: {user_id}")

        # 2. 参数转换：Decimal → cents (int)
        # 旧系统用分（cents），新系统用元（Decimal）
        amount_cents = int(amount * 100)

        # 3. 调用旧接口
        try:
            result = self._legacy.charge(numeric_user_id, amount_cents)
        except Exception as e:
            # 4. 错误处理转换
            raise PaymentError(f"Payment failed: {e}") from e

        # 5. 返回值转换：dict → PaymentResult
        if result.get('status') != 'ok':
            raise PaymentError(f"Payment failed: {result}")

        return PaymentResult(
            success=True,
            transaction_id=result['transaction_id'],
            amount=amount,
            user_id=user_id,
        )

# 自定义异常
class PaymentError(Exception):
    pass

# 使用示例
legacy = LegacyPayment()
adapter = LegacyPaymentAdapter(legacy)

# 业务代码使用新接口
result = adapter.process_payment("123", Decimal("99.99"))
print(f"Payment successful: {result.transaction_id}")
```

**要点**：
- 参数转换要处理类型不匹配的情况（如 `user_id` 不是数字）
- 金额单位转换（元→分）是常见的坑，必须明确
- 错误处理需要统一，旧系统的异常要转换为新系统的异常类型
- 适配器不改变业务逻辑，只做格式转换
