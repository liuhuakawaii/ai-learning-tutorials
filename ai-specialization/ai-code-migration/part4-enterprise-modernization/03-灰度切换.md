# 第三课：灰度切换——可控的风险释放

## 场景引入

你已经完成了新系统的开发和等价性测试，测试环境一切正常。现在面对的问题是：怎么把 1000 万用户的流量从旧系统切到新系统？

如果直接全量切换，一旦出问题就是 P0 级事故。如果只切 1% 的流量，要验证多久才能确认没问题？按什么维度选择那 1% 的用户？切过去之后发现新系统有 bug，怎么在 30 秒内把用户切回来？

灰度切换（Canary Release / Gradual Rollout）是解决这个问题的标准方案。它不是简单的"切一部分流量"，而是一套包含用户分群、指标监控、自动决策、快速回滚的完整工程实践。

## 学习目标

完成本课学习后，你将能够：

1. 设计多维度的灰度分群策略（按用户、地域、功能、时间）
2. 实现基于指标的自动灰度推进和回滚
3. 处理灰度过程中的状态一致性问题
4. 设计"杀伤开关"（Kill Switch）实现秒级回滚
5. 建立灰度切换的监控和告警体系

## 核心概念

### 一、灰度分群策略

```
灰度分群的四个维度：

维度 1：按用户 ID
  适用场景：用户级功能迁移
  实现：用户 ID 哈希取模 → 分桶
  优点：同一用户体验一致
  缺点：用户间行为差异大

维度 2：按地域/机房
  适用场景：基础设施迁移
  实现：按请求来源 IP 或数据中心路由
  优点：便于就近部署和运维
  缺点：地域间网络差异影响对比

维度 3：按功能模块
  适用场景：模块级逐步迁移
  实现：API 网关按路径路由
  优点：每次迁移范围可控
  缺点：模块间依赖需要处理

维度 4：按时间窗口
  适用场景：低峰期验证
  实现：定时任务在指定时段切换
  优点：出问题影响范围小
  缺点：不能持续验证
```

### 二、灰度推进策略

```
推荐的灰度推进阶梯：

  流量占比
  100% ─────────────────────────────────────── ★ 全量
   95% ────────────────────────────────── ●
   80% ───────────────────────────── ●
   50% ──────────────────────── ●
   20% ─────────────────── ●
    5% ────────────── ●
    1% ───────── ●
    0% ──── ●
         Day1  Day2  Day3  Day4  Day5  Day6  Day7

每一步的推进条件：
  1. 错误率 ≤ 旧系统的 1.5 倍
  2. P99 延迟 ≤ 旧系统的 1.2 倍
  3. 核心业务指标无异常（转化率、支付成功率等）
  4. 连续运行时间 ≥ 观察窗口（通常 2-4 小时）

每一步的回滚条件（满足任一即回滚）：
  1. 错误率 > 旧系统的 2 倍
  2. P99 延迟 > 旧系统的 2 倍
  3. 核心业务指标下降 > 1%
  4. 出现 P0/P1 级别告警
```

### 三、一致性哈希分桶

灰度切换的核心技术是"确定性分桶"——同一个用户在不同时间、不同服务实例上应该被分到同一个桶。

```
一致性哈希分桶：

  user_id → hash(user_id) % 100 → bucket_id

  bucket_id < gray_percent → 新系统
  bucket_id >= gray_percent → 旧系统

  示例：gray_percent = 5
  hash("user_001") % 100 = 3  → 新系统 (3 < 5)
  hash("user_002") % 100 = 47 → 旧系统 (47 >= 5)
  hash("user_003") % 100 = 2  → 新系统 (2 < 5)

  当 gray_percent 从 5 调到 20：
  hash("user_001") % 100 = 3  → 新系统 (3 < 20)  ✓ 保持
  hash("user_002") % 100 = 47 → 旧系统 (47 >= 20) ✓ 保持
  hash("user_003") % 100 = 2  → 新系统 (2 < 20)  ✓ 保持
```

### 四、灰度过程中的状态问题

灰度切换最棘手的问题是：用户 A 在新系统创建了订单，然后被切回旧系统，旧系统里没有这个订单。

```
状态一致性问题场景：

  用户 A（已切到新系统）
    → 创建订单 #12345
    → 订单写入新数据库
    
  此时灰度回滚，用户 A 被切回旧系统
    → 查看"我的订单"
    → 旧系统查不到 #12345
    → 用户困惑："我刚下的单去哪了？"

解决方案：
  1. 共享数据库（推荐）：新旧系统读写同一个库
  2. 数据同步：新系统写入后同步到旧系统
  3. 路由粘性：一旦用户被分配到新系统，在该会话内不切换
  4. 读写分离：写操作走旧系统，读操作可以走新系统
```

### 五、Kill Switch 设计

Kill Switch 是灰度回滚的终极手段——一个可以在秒级内将所有流量切回旧系统的开关。

```
Kill Switch 架构：

  ┌─────────────────────────────────────────────┐
  │              配置中心（etcd/Consul）            │
  │  gray.enabled = true                         │
  │  gray.percent = 20                           │
  │  gray.emergency_rollback = false             │
  └──────────────┬──────────────────────────────┘
                 │ 配置变更实时推送
    ┌────────────┼────────────┐
    ▼            ▼            ▼
  实例 1       实例 2       实例 3
  (读取配置)   (读取配置)   (读取配置)

  紧急回滚操作：
  1. 设置 gray.emergency_rollback = true
  2. 所有实例 1 秒内检测到变更
  3. 所有流量立即切回旧系统
  4. 不需要重启服务，不需要部署
```

## 完整代码示例

### 示例一：灰度路由器

```typescript
// canary/router.ts
import { createHash } from 'crypto'

interface CanaryConfig {
  enabled: boolean
  percent: number
  emergencyRollback: boolean
  stickySession: boolean
  overrideUsers: string[]
  excludeUsers: string[]
}

interface RoutingDecision {
  target: 'legacy' | 'new'
  reason: string
  bucketId: number
}

class CanaryRouter {
  private config: CanaryConfig
  private configWatcher: ConfigWatcher

  constructor(configCenter: ConfigCenter) {
    this.config = {
      enabled: false,
      percent: 0,
      emergencyRollback: false,
      stickySession: true,
      overrideUsers: [],
      excludeUsers: [],
    }

    this.configWatcher = configCenter.watch('canary', (newConfig) => {
      this.config = { ...this.config, ...newConfig }
    })
  }

  route(userId: string, sessionId?: string): RoutingDecision {
    if (this.config.emergencyRollback) {
      return { target: 'legacy', reason: 'emergency_rollback', bucketId: -1 }
    }

    if (!this.config.enabled) {
      return { target: 'legacy', reason: 'canary_disabled', bucketId: -1 }
    }

    if (this.config.excludeUsers.includes(userId)) {
      return { target: 'legacy', reason: 'excluded_user', bucketId: -1 }
    }

    if (this.config.overrideUsers.includes(userId)) {
      return { target: 'new', reason: 'override_user', bucketId: -1 }
    }

    const bucketId = this.getBucket(userId)

    if (this.config.stickySession && sessionId) {
      const sessionBucket = this.getBucket(sessionId)
      if (sessionBucket < this.config.percent) {
        return { target: 'new', reason: 'sticky_session', bucketId: sessionBucket }
      }
      return { target: 'legacy', reason: 'sticky_session', bucketId: sessionBucket }
    }

    if (bucketId < this.config.percent) {
      return { target: 'new', reason: 'canary_bucket', bucketId }
    }

    return { target: 'legacy', reason: 'canary_bucket', bucketId }
  }

  private getBucket(key: string): number {
    const hash = createHash('md5').update(key).digest('hex')
    return parseInt(hash.slice(0, 8), 16) % 100
  }

  getConfig(): CanaryConfig {
    return { ...this.config }
  }
}
```

### 示例二：自动灰度推进器

```typescript
// canary/auto-promoter.ts
interface PromotionStep {
  percent: number
  minDurationMinutes: number
  successCriteria: {
    maxErrorRateMultiplier: number
    maxLatencyMultiplier: number
    maxBusinessMetricDrop: number
  }
}

interface StepMetrics {
  errorRateLegacy: number
  errorRateNew: number
  latencyP99Legacy: number
  latencyP99New: number
  conversionRateLegacy: number
  conversionRateNew: number
}

class AutoPromoter {
  private steps: PromotionStep[]
  private currentStepIndex: number = 0
  private stepStartTime: Date = new Date()
  private metricsCollector: MetricsCollector
  private canaryRouter: CanaryRouter

  constructor(
    steps: PromotionStep[],
    metricsCollector: MetricsCollector,
    canaryRouter: CanaryRouter
  ) {
    this.steps = steps
    this.metricsCollector = metricsCollector
    this.canaryRouter = canaryRouter
  }

  async evaluate(): Promise<{
    action: 'hold' | 'promote' | 'rollback'
    reason: string
    currentPercent: number
    nextPercent?: number
  }> {
    const step = this.steps[this.currentStepIndex]
    const elapsed = Date.now() - this.stepStartTime.getTime()
    const minDuration = step.minDurationMinutes * 60 * 1000

    if (elapsed < minDuration) {
      return {
        action: 'hold',
        reason: `观察期未满，还需 ${Math.ceil((minDuration - elapsed) / 60000)} 分钟`,
        currentPercent: step.percent,
      }
    }

    const metrics = await this.metricsCollector.getComparison(window: '1h')

    const rollbackReason = this.checkRollbackCriteria(step, metrics)
    if (rollbackReason) {
      await this.rollback()
      return {
        action: 'rollback',
        reason: rollbackReason,
        currentPercent: 0,
      }
    }

    const meetsPromotion = this.checkPromotionCriteria(step, metrics)
    if (!meetsPromotion) {
      return {
        action: 'hold',
        reason: '未达到推进标准，继续观察',
        currentPercent: step.percent,
      }
    }

    if (this.currentStepIndex < this.steps.length - 1) {
      this.currentStepIndex++
      const nextStep = this.steps[this.currentStepIndex]
      this.stepStartTime = new Date()
      this.canaryRouter.updateConfig({ percent: nextStep.percent })

      return {
        action: 'promote',
        reason: `已推进到第 ${this.currentStepIndex + 1} 步`,
        currentPercent: step.percent,
        nextPercent: nextStep.percent,
      }
    }

    return {
      action: 'promote',
      reason: '所有步骤完成，灰度已达到 100%',
      currentPercent: step.percent,
      nextPercent: 100,
    }
  }

  private checkRollbackCriteria(step: PromotionStep, metrics: StepMetrics): string | null {
    const criteria = step.successCriteria

    if (metrics.errorRateNew > metrics.errorRateLegacy * criteria.maxErrorRateMultiplier * 2) {
      return `错误率过高: 新 ${metrics.errorRateNew}% vs 旧 ${metrics.errorRateLegacy}%`
    }

    if (metrics.latencyP99New > metrics.latencyP99Legacy * criteria.maxLatencyMultiplier * 2) {
      return `延迟过高: 新 ${metrics.latencyP99New}ms vs 旧 ${metrics.latencyP99Legacy}ms`
    }

    const conversionDrop = 
      (metrics.conversionRateLegacy - metrics.conversionRateNew) / metrics.conversionRateLegacy
    if (conversionDrop > criteria.maxBusinessMetricDrop * 2) {
      return `转化率下降: ${((conversionDrop) * 100).toFixed(2)}%`
    }

    return null
  }

  private checkPromotionCriteria(step: PromotionStep, metrics: StepMetrics): boolean {
    const criteria = step.successCriteria

    const errorRateOk = 
      metrics.errorRateNew <= metrics.errorRateLegacy * criteria.maxErrorRateMultiplier
    const latencyOk = 
      metrics.latencyP99New <= metrics.latencyP99Legacy * criteria.maxLatencyMultiplier

    const conversionDrop = metrics.conversionRateLegacy > 0
      ? (metrics.conversionRateLegacy - metrics.conversionRateNew) / metrics.conversionRateLegacy
      : 0
    const conversionOk = conversionDrop <= criteria.maxBusinessMetricDrop

    return errorRateOk && latencyOk && conversionOk
  }

  private async rollback(): Promise<void> {
    this.canaryRouter.updateConfig({
      enabled: true,
      percent: 0,
      emergencyRollback: true,
    })
    await this.metricsCollector.alert('GRAYSCALE_ROLLBACK', {
      step: this.currentStepIndex,
      percent: this.steps[this.currentStepIndex].percent,
    })
  }
}
```

### 示例三：Nginx 灰度配置

```nginx
# nginx/canary.conf

upstream legacy_backend {
    server 10.0.1.1:8080;
    server 10.0.1.2:8080;
}

upstream new_backend {
    server 10.0.2.1:8080;
    server 10.0.2.2:8080;
}

# Lua 一致性哈希灰度（简化版）
lua_shared_dict canary_config 1m;

server {
    listen 80;
    location /api/ {
        set $target "legacy";
        access_by_lua_block {
            local config = ngx.shared.canary_config
            if not config:get("enabled") then
                ngx.var.target = "legacy"
                return
            end
            local user_id = ngx.var.cookie_user_id or ""
            local bucket = ngx.crc32_long(user_id) % 100
            if bucket < (config:get("percent") or 0) then
                ngx.var.target = "new"
            end
        }
        proxy_pass http://${target}_backend;
    }
}
```

## 常见误区

### 误区一：灰度只是切流量

灰度切换不仅是"把一部分流量导到新系统"，还需要配套的监控、对比、回滚、数据一致性保障。没有这些配套的灰度就是"盲切"。

### 误区二：用随机数做灰度分桶

`Math.random() < 0.1` 做 10% 灰度——这意味着同一个用户每次请求可能被路由到不同系统。必须用一致性哈希保证同一用户始终路由到同一个系统。

### 误区三：灰度回滚后不做根因分析

回滚只是止血。回滚后必须分析为什么新系统出问题，修复后再重新灰度。否则问题会反复出现。

### 误区四：灰度观察期太短

切了 1% 的流量，观察 5 分钟就推进到 10%——1% 的流量可能没有覆盖到所有边界条件。观察期应该至少覆盖一个完整的业务周期（如 24 小时）。

### 误区五：没有设置自动回滚

人工发现异常 → 人工决定回滚 → 人工执行回滚，这个过程可能需要 10-30 分钟。自动回滚可以在 1 分钟内完成，将损失降到最低。

## 小结

灰度切换的核心要素：

1. **一致性分桶**：同一用户始终路由到同一系统
2. **阶梯推进**：从 1% → 5% → 20% → 50% → 100% 逐步推进
3. **自动回滚**：基于错误率、延迟、业务指标自动触发回滚
4. **Kill Switch**：秒级全量回滚的紧急开关
5. **观察窗口**：每一步都有足够的观察时间

## 参考答案

### 练习一

**思路**：支付系统风险极高，需要更保守的灰度策略和更严格的回滚条件。

**答案**：

| 天数 | 流量 | 监控指标 | 回滚条件 |
|------|------|---------|---------|
| Day 1 | 1% (内部账号) | 支付成功率 100% | 任何失败 |
| Day 2 | 2% | 成功率 ≥ 99.99%、对账一致 | 成功率 < 99.95% |
| Day 3 | 5% | +退款成功率 | 成功率下降 > 0.01% |
| Day 4 | 10% | +用户投诉率 | 投诉率上升或对账差异 |
| Day 5 | 30% | +各渠道独立成功率 | 任一渠道下降 |
| Day 6 | 60% | 全量监控 | 任何 P0/P1 告警 |
| Day 7 | 100% | 持续一周密集监控 | 保留旧系统热备 |

关键指标：支付成功率、对账差异、P99 延迟、各渠道成功率、退款成功率。

### 练习二

**思路**：使用配置中心实时推送，避免轮询延迟。

**答案**：

```typescript
// kill-switch 核心实现
import { EventEmitter } from 'events'

class KillSwitch extends EventEmitter {
  private active = false
  private etcdClient: EtcdClient

  constructor(etcdEndpoints: string[]) {
    super()
    this.etcdClient = new EtcdClient(etcdEndpoints)
    // etcd watch 长连接推送，延迟 < 100ms
    this.etcdClient.watch('canary/emergency_rollback', (event) => {
      this.active = event.value.toString() === 'true'
      if (this.active) this.emit('activated')
    })
  }

  isActive(): boolean { return this.active }

  async activate(): Promise<void> {
    await this.etcdClient.put('canary/emergency_rollback', 'true')
    this.active = true  // 本地立即生效，不等 watch 回调
    this.emit('activated')
  }
}
```

实现要点：
- etcd watch 是长连接推送，不是轮询
- `activate()` 本地立即生效，多实例各自 watch 同一 key
- 提供 HTTP API 供运维手动触发
