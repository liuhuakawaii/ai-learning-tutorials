# 第一课：渐进式迁移策略——不停机的系统现代化

## 场景引入

你是某金融公司的技术负责人。公司有一个运行了六年的核心交易系统，代码量 50 万行，日均交易额 2 亿元。系统架构老旧（单体应用 + 存储过程 + jQuery 前端），但业务不能停——系统停一小时意味着直接损失数百万。

CTO 要求你"在不影响业务的前提下完成系统现代化"。这句话的潜台词是：你不能停旧系统，不能做一次性切换，不能有数据丢失，不能让用户体验到任何中断。

这就是企业级迁移的核心挑战——**在飞行中换引擎**。渐进式迁移不是技术问题，而是**工程策略问题**。本课讲的是如何设计一套让新旧系统安全共存、逐步切换的迁移架构。

## 学习目标

完成本课学习后，你将能够：

1. 理解渐进式迁移的核心原则和反模式
2. 设计绞杀者模式（Strangler Fig Pattern）的迁移架构
3. 实现新旧系统的并行运行（双跑）策略
4. 处理数据层的一致性问题
5. 制定按模块、按流量、按功能的多维度切换策略

## 核心概念

### 一、渐进式迁移的三个原则

```
渐进式迁移三原则：

┌─────────────────────────────────────────────────────────┐
│                                                         │
│  原则 1：可回滚（Reversible）                            │
│  任何时候都能回到上一个稳定状态                            │
│  → 不做不可逆操作，不做大爆炸切换                          │
│                                                         │
│  原则 2：可观测（Observable）                            │
│  随时知道新旧系统的运行状态                               │
│  → 流量分布、错误率、性能指标、数据一致性                   │
│                                                         │
│  原则 3：可增量（Incremental）                           │
│  每次只迁移一小部分，验证后再继续                          │
│  → 按模块、按用户、按流量逐步切换                          │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

违反这三个原则的常见做法：
- **大爆炸重写**：停掉旧系统，全面切换到新系统 → 违反可回滚
- **黑盒切换**：切换后不知道新系统是否正常 → 违反可观测
- **全量迁移**：一次把所有功能都迁移过来 → 违反可增量

### 二、绞杀者模式（Strangler Fig Pattern）

绞杀者无花果树的生长方式：种子落在宿主树上，根系向下生长扎入土壤，逐渐包裹宿主树，最终完全替代。迁移也应如此。

```
绞杀者模式的演进过程：

阶段 1：路由层拦截
┌─────────────────────────────────┐
│           API Gateway / Nginx    │
│  ┌──────────┐  ┌──────────┐    │
│  │ 旧系统    │  │ 新系统    │    │
│  │ (99%流量) │  │ (1%流量)  │    │
│  └──────────┘  └──────────┘    │
└─────────────────────────────────┘

阶段 2：逐模块替换
┌─────────────────────────────────┐
│           API Gateway / Nginx    │
│  ┌──────────┐  ┌──────────┐    │
│  │ 旧系统    │  │ 新系统    │    │
│  │ (60%流量) │  │ (40%流量) │    │
│  │ 用户管理已迁移              │    │
│  └──────────┘  └──────────┘    │
└─────────────────────────────────┘

阶段 3：旧系统退役
┌─────────────────────────────────┐
│           API Gateway / Nginx    │
│  ┌──────────┐  ┌──────────┐    │
│  │ 旧系统    │  │ 新系统    │    │
│  │ (待下线)  │  │ (99%流量) │    │
│  └──────────┘  └──────────┘    │
└─────────────────────────────────┘
```

### 三、迁移单元的粒度选择

选择迁移的基本单元决定了迁移的难度和风险。

```
粒度选择对比：

┌──────────────┬────────────────┬────────────────┬─────────────────┐
│   粒度        │   示例          │   优点          │   缺点           │
├──────────────┼────────────────┼────────────────┼─────────────────┤
│   API 端点    │  /api/users    │  最小迁移单元    │  数据层耦合      │
│              │                │  风险最低       │  需要数据同步     │
├──────────────┼────────────────┼────────────────┼─────────────────┤
│   业务模块    │  用户管理       │  功能完整       │  迁移工作量大     │
│              │                │  可独立验证     │  模块间耦合难处理  │
├──────────────┼────────────────┼────────────────┼─────────────────┤
│   页面/视图   │  /dashboard    │  用户可见       │  前后端都要迁移   │
│              │                │  体验可对比     │  可能跨多个模块   │
├──────────────┼────────────────┼────────────────┼─────────────────┤
│   数据实体    │  订单表         │  数据一致性好   │  影响面广        │
│              │                │  一次迁移彻底   │  回滚困难        │
└──────────────┴────────────────┴────────────────┴─────────────────┘
```

### 四、新旧系统的数据一致性

渐进式迁移最棘手的问题是**数据层**。新旧系统可能同时读写同一个数据源，必须保证数据一致。

```
数据层迁移策略：

策略 1：共享数据库
  新旧系统直接连接同一个数据库
  + 实现简单，数据天然一致
  - 旧系统的数据库 schema 限制新系统设计
  - 存储过程和触发器可能产生副作用

策略 2：数据库复制
  旧系统写主库，新系统通过 CDC 读副本
  + 新系统可以有独立 schema
  - 有同步延迟
  - 双写场景数据一致性难保证

策略 3：API 桥接
  新系统通过旧系统的 API 读写数据
  + 完全解耦，互不影响
  - 旧系统 API 可能不够用
  - 性能可能不满足要求
```

### 五、迁移状态机

```
模块迁移状态流转：

  [未迁移] → [迁移中] → [双跑验证] → [新系统主导] → [旧系统退役]
      ↑           ↓            ↓              ↓
      └─── [回滚] ←┘          └── [回滚] ←───┘

每个状态转换都需要：
  1. 明确的验收标准（什么条件下进入下一状态）
  2. 监控指标（如何判断系统正常）
  3. 回滚条件（什么情况下触发回滚）
  4. 回滚步骤（如何安全地回到上一状态）
```

## 完整代码示例

### 示例一：路由层流量分配

```typescript
// gateway/traffic-router.ts
import { Request, Response, NextFunction } from 'express'

interface RouteConfig {
  path: string
  method: string
  target: 'legacy' | 'new' | 'both'
  trafficSplit?: {
    legacy: number  // 0-100
    new: number     // 0-100
  }
}

interface MigrationState {
  routes: RouteConfig[]
  updatedAt: Date
  updatedBy: string
}

class TrafficRouter {
  private state: MigrationState
  private metricsCollector: MetricsCollector

  constructor(initialState: MigrationState) {
    this.state = initialState
    this.metricsCollector = new MetricsCollector()
  }

  middleware() {
    return (req: Request, res: Response, next: NextFunction) => {
      const route = this.matchRoute(req.path, req.method)
      if (!route) {
        return next()
      }

      const target = this.resolveTarget(route)
      const startTime = Date.now()

      req.headers['x-migration-target'] = target
      req.headers['x-request-id'] = this.generateRequestId()

      res.on('finish', () => {
        this.metricsCollector.record({
          path: req.path,
          method: req.method,
          target,
          statusCode: res.statusCode,
          latencyMs: Date.now() - startTime,
          timestamp: new Date(),
        })
      })

      next()
    }
  }

  private matchRoute(path: string, method: string): RouteConfig | undefined {
    return this.state.routes.find(
      r => path.startsWith(r.path) && (r.method === '*' || r.method === method)
    )
  }

  private resolveTarget(route: RouteConfig): 'legacy' | 'new' {
    if (route.target === 'legacy') return 'legacy'
    if (route.target === 'new') return 'new'

    const split = route.trafficSplit
    if (!split) return 'legacy'

    const roll = Math.random() * 100
    return roll < split.legacy ? 'legacy' : 'new'
  }

  private generateRequestId(): string {
    return `req_${Date.now()}_${Math.random().toString(36).slice(2, 8)}`
  }

  updateRoute(path: string, config: Partial<RouteConfig>) {
    const route = this.state.routes.find(r => r.path === path)
    if (route) {
      Object.assign(route, config)
      this.state.updatedAt = new Date()
    }
  }
}
```

### 示例二：双跑对比器

```typescript
// gateway/dual-run-comparator.ts
interface ComparisonResult {
  requestId: string
  path: string
  legacyResponse: {
    statusCode: number
    body: unknown
    latencyMs: number
  }
  newResponse: {
    statusCode: number
    body: unknown
    latencyMs: number
  }
  match: boolean
  differences: string[]
  timestamp: Date
}

class DualRunComparator {
  private results: ComparisonResult[] = []

  async compare(
    requestId: string,
    path: string,
    legacyCall: () => Promise<ApiResponse>,
    newCall: () => Promise<ApiResponse>
  ): Promise<ComparisonResult> {
    const [legacyResult, newResult] = await Promise.allSettled([
      legacyCall(),
      newCall(),
    ])

    const legacyResponse = this.extractResponse(legacyResult)
    const newResponse = this.extractResponse(newResult)

    const differences = this.findDifferences(legacyResponse.body, newResponse.body)

    const result: ComparisonResult = {
      requestId,
      path,
      legacyResponse,
      newResponse,
      match: differences.length === 0,
      differences,
      timestamp: new Date(),
    }

    this.results.push(result)
    return result
  }

  private extractResponse(
    result: PromiseSettledResult<ApiResponse>
  ): { statusCode: number; body: unknown; latencyMs: number } {
    if (result.status === 'fulfilled') {
      return {
        statusCode: result.value.status,
        body: result.value.data,
        latencyMs: result.value.latencyMs,
      }
    }
    return { statusCode: 500, body: null, latencyMs: 0 }
  }

  private findDifferences(
    legacy: unknown,
    current: unknown,
    path = ''
  ): string[] {
    const diffs: string[] = []

    if (typeof legacy !== typeof current) {
      diffs.push(`${path}: 类型不同 ${typeof legacy} vs ${typeof current}`)
      return diffs
    }

    if (legacy === null || current === null) {
      if (legacy !== current) {
        diffs.push(`${path}: ${legacy} vs ${current}`)
      }
      return diffs
    }

    if (Array.isArray(legacy) && Array.isArray(current)) {
      if (legacy.length !== current.length) {
        diffs.push(`${path}: 数组长度不同 ${legacy.length} vs ${current.length}`)
      }
      const minLen = Math.min(legacy.length, current.length)
      for (let i = 0; i < minLen; i++) {
        diffs.push(...this.findDifferences(legacy[i], current[i], `${path}[${i}]`))
      }
      return diffs
    }

    if (typeof legacy === 'object') {
      const legacyKeys = Object.keys(legacy as object).sort()
      const currentKeys = Object.keys(current as object).sort()
      
      for (const key of legacyKeys) {
        if (!(key in (current as object))) {
          diffs.push(`${path}.${key}: 新系统缺少此字段`)
        }
      }
      for (const key of currentKeys) {
        if (!(key in (legacy as object))) {
          diffs.push(`${path}.${key}: 新系统多出此字段`)
        }
      }
      for (const key of legacyKeys) {
        if (key in (current as object)) {
          diffs.push(
            ...this.findDifferences(
              (legacy as any)[key],
              (current as any)[key],
              `${path}.${key}`
            )
          )
        }
      }
      return diffs
    }

    if (legacy !== current) {
      diffs.push(`${path}: 值不同 ${JSON.stringify(legacy)} vs ${JSON.stringify(current)}`)
    }

    return diffs
  }

  getMatchRate(): number {
    if (this.results.length === 0) return 100
    const matched = this.results.filter(r => r.match).length
    return (matched / this.results.length) * 100
  }

  getReport(): {
    total: number
    matched: number
    mismatched: number
    matchRate: number
    topDifferences: Array<{ path: string; count: number }>
  } {
    const diffCounts = new Map<string, number>()
    for (const result of this.results) {
      if (!result.match) {
        for (const diff of result.differences) {
          const key = diff.split(':')[0]
          diffCounts.set(key, (diffCounts.get(key) || 0) + 1)
        }
      }
    }

    return {
      total: this.results.length,
      matched: this.results.filter(r => r.match).length,
      mismatched: this.results.filter(r => !r.match).length,
      matchRate: this.getMatchRate(),
      topDifferences: Array.from(diffCounts.entries())
        .sort((a, b) => b[1] - a[1])
        .slice(0, 10)
        .map(([path, count]) => ({ path, count })),
    }
  }
}
```

### 示例三：迁移进度追踪

```typescript
// migration/tracker.ts
type ModuleStatus = 
  | 'not_started'
  | 'in_progress'
  | 'dual_running'
  | 'new_primary'
  | 'legacy_decommissioned'
  | 'rolled_back'

interface ModuleMigration {
  moduleName: string
  status: ModuleStatus
  startDate?: Date
  targetDate?: Date
  completionDate?: Date
  owner: string
  dependencies: string[]
  metrics: {
    totalEndpoints: number
    migratedEndpoints: number
    trafficPercentNew: number
    errorRateLegacy: number
    errorRateNew: number
    latencyP99Legacy: number
    latencyP99New: number
  }
  blockers: string[]
  notes: string[]
}

class MigrationTracker {
  private modules: Map<string, ModuleMigration> = new Map()

  addModule(module: ModuleMigration) {
    this.modules.set(module.moduleName, module)
  }

  transition(moduleName: string, newStatus: ModuleStatus): boolean {
    const mod = this.modules.get(moduleName)
    if (!mod) return false

    if (!this.canTransition(mod.status, newStatus)) {
      return false
    }

    mod.status = newStatus
    if (newStatus === 'legacy_decommissioned' || newStatus === 'rolled_back') {
      mod.completionDate = new Date()
    }

    return true
  }

  private canTransition(from: ModuleStatus, to: ModuleStatus): boolean {
    const validTransitions: Record<ModuleStatus, ModuleStatus[]> = {
      not_started: ['in_progress'],
      in_progress: ['dual_running', 'rolled_back'],
      dual_running: ['new_primary', 'in_progress', 'rolled_back'],
      new_primary: ['legacy_decommissioned', 'dual_running', 'rolled_back'],
      legacy_decommissioned: [],
      rolled_back: ['in_progress'],
    }
    return validTransitions[from]?.includes(to) ?? false
  }

  getOverallProgress(): {
    total: number
    completed: number
    inProgress: number
    blocked: number
    percentage: number
  } {
    const modules = Array.from(this.modules.values())
    return {
      total: modules.length,
      completed: modules.filter(m => m.status === 'legacy_decommissioned').length,
      inProgress: modules.filter(m => 
        ['in_progress', 'dual_running', 'new_primary'].includes(m.status)
      ).length,
      blocked: modules.filter(m => m.blockers.length > 0).length,
      percentage: modules.length > 0
        ? (modules.filter(m => m.status === 'legacy_decommissioned').length / modules.length) * 100
        : 0,
    }
  }

  getDependencyOrder(): string[] {
    const visited = new Set<string>()
    const order: string[] = []

    const visit = (name: string) => {
      if (visited.has(name)) return
      visited.add(name)
      const mod = this.modules.get(name)
      if (mod) {
        for (const dep of mod.dependencies) {
          visit(dep)
        }
      }
      order.push(name)
    }

    for (const name of this.modules.keys()) {
      visit(name)
    }

    return order
  }
}
```

## 常见误区

### 误区一：在迁移过程中重构业务逻辑

迁移和重构是两件独立的事。迁移是换技术栈，重构是改业务代码。同时进行会导致问题来源无法定位。正确做法是先迁移后重构。

### 误区二：新系统完全复制旧系统的 API

新系统应该有自己设计良好的 API，而不是照搬旧系统的。可以在路由层做适配，让旧客户端不感知变化。

### 误区三：忽略数据迁移的工作量

代码迁移通常只占总工作量的 30-40%，数据迁移才是大头。数据库 schema 变更、数据格式转换、历史数据清洗，每一项都可能比代码迁移更耗时。

### 误区四：没有建立回滚机制就推进迁移

每个迁移步骤都应该有对应的回滚方案。如果回滚方案不明确，说明这一步的迁移粒度太大，需要拆分。

### 误区五：只做功能验证，不做性能验证

新系统功能正确但性能差 10 倍的情况很常见。迁移验证必须包含性能对比。

## 小结

渐进式迁移的核心策略：

1. **绞杀者模式**：新系统逐步替代旧系统，而非一次性替换
2. **路由层控制**：在网关层实现流量分配和灰度切换
3. **双跑对比**：新旧系统同时处理请求，对比结果确保一致性
4. **迁移状态机**：每个模块有明确的状态流转和回滚路径
5. **数据优先**：数据层的迁移方案比代码层更重要

## 参考答案

### 练习一

**思路**：按依赖关系排序，从被依赖最多的模块开始。

**答案**：

迁移顺序（6 轮）：

**第 1 轮：用户管理**
- 理由：几乎所有模块都依赖用户认证和权限，迁移后其他模块可以通过新系统的用户 API 认证
- 风险：低（用户数据结构简单，读多写少）

**第 2 轮：商品管理**
- 理由：订单和库存都依赖商品信息，且商品管理相对独立
- 风险：低（主要是 CRUD 操作）

**第 3 轮：库存管理**
- 理由：订单创建时需要扣减库存，必须在订单迁移前完成
- 风险：中（涉及并发扣减，需要保证数据一致性）

**第 4 轮：订单管理**
- 琊由：核心业务模块，依赖用户、商品、库存
- 风险：高（业务逻辑复杂，涉及状态机）

**第 5 轮：支付管理**
- 理由：依赖订单状态，且涉及第三方支付接口
- 风险：高（资金安全，不允许出错）

**第 6 轮：物流管理**
- 理由：依赖订单，但相对独立，可以最后迁移
- 风险：低（主要是信息查询和状态更新）

### 练习二

**思路**：渐进式增加新系统流量比例，每天监控关键指标。

**答案**：

```
Day 1: 1% → 只迁移内部测试账号的请求
  监控：错误率 < 0.1%，延迟 P99 < 500ms
  回滚条件：任何 5xx 错误

Day 2: 5% → 扩大到小部分真实流量
  监控：错误率 < 0.05%，数据一致性 100%
  回滚条件：错误率 > 0.1% 或数据不一致

Day 3: 20% → 扩大到一个区域的流量
  监控：订单创建成功率、支付成功率、库存一致性
  回滚条件：成功率下降 > 1%

Day 4: 50% → 交替分配流量
  监控：对比新旧系统的性能指标
  回滚条件：P99 延迟差异 > 20%

Day 5: 80% → 新系统为主
  监控：全链路指标、用户投诉率
  回滚条件：用户投诉率上升

Day 6: 95% → 旧系统仅保留紧急回滚通道
  监控：稳定性指标
  回滚条件：任何 P0 级别故障

Day 7: 100% → 完全切换，旧系统进入退役流程
  监控：持续观察一周
```
