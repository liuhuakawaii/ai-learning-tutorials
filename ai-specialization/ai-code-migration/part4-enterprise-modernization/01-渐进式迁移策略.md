# 01 - 渐进式迁移策略

> **课程定位**：Part 4 核心策略课，设计不停机的系统现代化方案。
>
> **前置要求**：了解微服务架构基础
>
> **预计时长**：1.5 小时

---

你是某金融公司技术负责人。核心交易系统运行六年，50 万行代码，日均交易额 2 亿元。CTO 要求"在不影响业务的前提下完成系统现代化"。你不能停旧系统，不能做一次性切换，不能有数据丢失。

这就是**在飞行中换引擎**。

---

## 三个原则

**可回滚**：任何时候都能回到上一个稳定状态。不做不可逆操作，不做大爆炸切换。

**可观测**：随时知道新旧系统的运行状态。流量分布、错误率、性能指标、数据一致性。

**可增量**：每次只迁移一小部分，验证后再继续。

违反原则：大爆炸重写（违反可回滚）、黑盒切换（违反可观测）、全量迁移（违反可增量）。

---

## 绞杀者模式

```
阶段 1：路由层拦截          阶段 2：逐模块替换          阶段 3：旧系统退役
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│   API Gateway    │       │   API Gateway    │       │   API Gateway    │
│ ┌──────┐┌──────┐│       │ ┌──────┐┌──────┐│       │ ┌──────┐┌──────┐│
│ │旧(99%)││新(1%)││       │ │旧(60%)││新(40%)││       │ │      ││新(99%)││
│ └──────┘└──────┘│       │ └──────┘└──────┘│       │ └──────┘└──────┘│
└─────────────────┘       └─────────────────┘       └─────────────────┘
```

---

## 数据层策略

**共享数据库**：新旧系统直接连接同一个数据库。简单但旧 schema 限制新设计。

**数据库复制**：旧系统写主库，新系统通过 CDC 读副本。有同步延迟。

**API 桥接**：新系统通过旧系统 API 读写。完全解耦但可能性能不够。

---

## 迁移状态机

```
[未迁移] → [迁移中] → [双跑验证] → [新系统主导] → [旧系统退役]
    ↑           ↓            ↓              ↓
    └─── [回滚] ←┘          └── [回滚] ←───┘
```

每个转换需要：验收标准、监控指标、回滚条件、回滚步骤。

## 实战：路由层流量分配

```typescript
import { Request, Response, NextFunction } from 'express'

interface RouteConfig { path: string; method: string; target: 'legacy' | 'new' | 'both'; trafficSplit?: { legacy: number; new: number } }

class TrafficRouter {
  constructor(private routes: RouteConfig[]) {}

  middleware() {
    return (req: Request, res: Response, next: NextFunction) => {
      const route = this.routes.find(r => req.path.startsWith(r.path) && (r.method === '*' || r.method === req.method));
      if (!route) return next();
      const target = this.resolveTarget(route);
      req.headers['x-migration-target'] = target;
      const start = Date.now();
      res.on('finish', () => this.recordMetric({ path: req.path, target, status: res.statusCode, latency: Date.now() - start }));
      next();
    };
  }

  private resolveTarget(route: RouteConfig): 'legacy' | 'new' {
    if (route.target !== 'both') return route.target;
    return Math.random() * 100 < (route.trafficSplit?.legacy ?? 100) ? 'legacy' : 'new';
  }

  private recordMetric(data: any) { /* 记录到监控系统 */ }
  updateRoute(path: string, config: Partial<RouteConfig>) { const r = this.routes.find(r => r.path === path); if (r) Object.assign(r, config); }
}
```

## 实战：双跑对比器

```typescript
class DualRunComparator {
  private results: { match: boolean; diffs: string[] }[] = []

  async compare(legacyCall: () => Promise<any>, newCall: () => Promise<any>) {
    const [legacy, current] = await Promise.allSettled([legacyCall(), newCall()]);
    const legacyBody = legacy.status === 'fulfilled' ? legacy.value.data : null;
    const newBody = current.status === 'fulfilled' ? current.value.data : null;
    const diffs = this.findDiffs(legacyBody, newBody);
    const result = { match: diffs.length === 0, diffs };
    this.results.push(result);
    return result;
  }

  private findDiffs(a: any, b: any, path = ''): string[] {
    const diffs: string[] = [];
    if (typeof a !== typeof b) { diffs.push(`${path}: 类型不同`); return diffs; }
    if (a === null || b === null) { if (a !== b) diffs.push(`${path}: null vs non-null`); return diffs; }
    if (Array.isArray(a) && Array.isArray(b)) {
      if (a.length !== b.length) diffs.push(`${path}: 长度 ${a.length} vs ${b.length}`);
      for (let i = 0; i < Math.min(a.length, b.length); i++) diffs.push(...this.findDiffs(a[i], b[i], `${path}[${i}]`));
      return diffs;
    }
    if (typeof a === 'object') {
      for (const key of new Set([...Object.keys(a), ...Object.keys(b)])) {
        if (!(key in a)) diffs.push(`${path}.${key}: 新系统多出`);
        else if (!(key in b)) diffs.push(`${path}.${key}: 新系统缺少`);
        else diffs.push(...this.findDiffs(a[key], b[key], `${path}.${key}`));
      }
      return diffs;
    }
    if (a !== b) diffs.push(`${path}: ${a} vs ${b}`);
    return diffs;
  }

  getMatchRate() { return this.results.length === 0 ? 100 : (this.results.filter(r => r.match).length / this.results.length) * 100; }
}
```

## 练习

### 练习一：迁移顺序

电商系统：用户管理、商品管理、订单管理、支付管理、库存管理、物流管理。设计迁移顺序。

### 练习二：流量切换计划

设计 7 天将 `/api/orders` 从旧系统迁移到新系统的计划。每天有明确流量百分比、监控指标、回滚条件。

---

## 参考答案

### 练习一

1. **用户管理**（被所有模块依赖，风险低）
2. **商品管理**（订单和库存依赖，相对独立）
3. **库存管理**（订单创建时需要扣减，必须在订单前完成）
4. **订单管理**（核心业务，依赖前三者）
5. **支付管理**（依赖订单，涉及资金安全）
6. **物流管理**（依赖订单，相对独立）

### 练习二

Day 1: 1%（内部测试账号，错误率<0.1%）→ Day 2: 5%（小部分真实流量）→ Day 3: 20%（一个区域）→ Day 4: 50%（交替分配）→ Day 5: 80%（新系统为主）→ Day 6: 95%（旧系统仅保留回滚通道）→ Day 7: 100%（完全切换，持续观察一周）。每天有回滚条件：错误率超标、数据不一致、P99延迟差异>20%。
