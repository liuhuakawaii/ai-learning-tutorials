# 第四课：回滚机制——迁移失败时的安全网

## 场景引入

凌晨两点，你被电话叫醒——灰度到 30% 的新系统出现了问题。过去一小时里，新系统处理的订单中有 0.3% 出现了金额计算错误。错误率不高，但涉及真金白银，必须立即回滚。

你需要在最短的时间内完成三件事：把所有流量切回旧系统、修复已出错的数据、记录问题以便后续排查。如果回滚过程本身出了问题（比如旧系统容量不够承受 100% 流量），后果更加严重。

回滚不是"把开关拨回去"这么简单。它是一个需要提前设计、反复演练、精确执行的工程操作。本课讲的是如何设计可靠的回滚机制，确保任何迁移操作都能安全退出。

## 学习目标

完成本课学习后，你将能够：

1. 设计多层级的回滚策略（代码、数据、流量、配置）
2. 实现数据层的可逆操作
3. 处理回滚过程中的数据一致性问题
4. 设计回滚演练（Game Day）流程
5. 建立回滚的监控和告警体系

## 核心概念

### 一、回滚的四个层次

```
回滚层次模型（从外到内）：

┌──────────────────────────────────────────────┐
│  层次 1：流量回滚                              │
│  把用户流量切回旧系统                           │
│  恢复时间：秒级                                │
│  数据影响：无                                  │
├──────────────────────────────────────────────┤
│  层次 2：配置回滚                              │
│  恢复到旧的配置版本                            │
│  恢复时间：秒级到分钟级                         │
│  数据影响：无                                  │
├──────────────────────────────────────────────┤
│  层次 3：代码回滚                              │
│  部署旧版本的代码                              │
│  恢复时间：分钟级                              │
│  数据影响：无（如果 schema 没变）               │
├──────────────────────────────────────────────┤
│  层次 4：数据回滚                              │
│  恢复到旧的数据状态                            │
│  恢复时间：分钟级到小时级                       │
│  数据影响：可能丢失新数据                       │
└──────────────────────────────────────────────┘

优先级：能用流量回滚就不动代码，能用代码回滚就不动数据。
数据回滚是最后手段，风险最高。
```

### 二、数据回滚的挑战

```
数据回滚的三类场景：

场景 1：只读数据迁移
  旧格式 → 新格式（如 JSON 字段结构变化）
  回滚策略：保留旧格式字段，回滚时切换读取逻辑
  风险：低

场景 2：追加写入
  新系统写入了旧系统没有的数据
  回滚策略：通过新系统 API 或数据库直接查询
  风险：中（需要保留新系统访问能力）

场景 3：覆盖写入
  新系统修改了旧系统也能看到的数据
  回滚策略：操作日志回放、数据库时间点恢复
  风险：高（可能丢失在新系统上产生的数据）

┌─────────────────────────────────────────────────┐
│           数据回滚决策树                           │
│                                                 │
│  数据是否被新系统修改？                            │
│    ├─ 否 → 流量回滚即可                          │
│    └─ 是 → 修改是否可逆？                        │
│         ├─ 是（有操作日志）→ 日志回放             │
│         └─ 否 → 数据库快照恢复                   │
│              └─ 快照是否可用？                    │
│                   ├─ 是 → 时间点恢复             │
│                   └─ 否 → 手动修复（最后手段）    │
└─────────────────────────────────────────────────┘
```

### 三、可逆操作设计

迁移过程中应该尽可能设计"可逆"的操作，让回滚成为安全的默认行为。

```
可逆 vs 不可逆操作：

可逆操作：
  + 新增字段（加列）→ 回滚时忽略新字段
  + 新增表/集合 → 回滚时不访问新表
  + 新增 API 端点 → 回滚时不调用新端点
  + 双写（同时写新旧系统）→ 回滚时只写旧系统

不可逆操作：
  - 删除字段（删列）→ 数据丢失，无法回滚
  - 重命名字段 → 旧代码找不到字段
  - 修改数据格式 → 旧代码无法解析
  - 删除旧 API → 调用方报错

设计原则：
  迁移过程中只做"加法"，不做"减法"。
  删除操作留到迁移完全确认成功后再执行。
```

### 四、回滚的时间窗口

```
迁移阶段与回滚成本的关系：

  回滚
  成本
    │
  高│                                    ● 数据回滚
    │                              ●
    │                        ●
    │                  ●
    │            ● 代码回滚
    │       ●
  低│  ● 流量回滚
    └──────────────────────────────────────
      迁移早期          迁移中期        迁移后期

  时间越长 → 数据积累越多 → 回滚成本越高
  
  结论：尽早发现需要回滚的问题
  方法：小流量 + 长观察期 + 自动检测
```

### 示例一：多层级回滚控制器

```typescript
// rollback/controller.ts
interface RollbackStep {
  name: string
  execute: () => Promise<boolean>
  verify: () => Promise<boolean>
  rollbackTimeEstimate: number // 秒
  dependencies: string[]
}

interface RollbackPlan {
  steps: RollbackStep[]
  maxRollbackTimeSeconds: number
  notificationChannels: string[]
}

class RollbackController {
  private plans: Map<string, RollbackPlan> = new Map()
  private executionLog: Array<{
    plan: string
    step: string
    status: 'success' | 'failed' | 'skipped'
    timestamp: Date
    duration: number
    error?: string
  }> = []

  registerPlan(name: string, plan: RollbackPlan): void {
    this.plans.set(name, plan)
  }

  async executeRollback(planName: string): Promise<{
    success: boolean
    totalTime: number
    failedStep?: string
  }> {
    const plan = this.plans.get(planName)
    if (!plan) {
      throw new Error(`Rollback plan "${planName}" not found`)
    }

    const startTime = Date.now()
    const executedSteps: string[] = []

    for (const step of plan.steps) {
      const stepStart = Date.now()

      try {
        const canExecute = step.dependencies.every(
          dep => executedSteps.includes(dep)
        )

        if (!canExecute) {
          this.log(planName, step.name, 'skipped', Date.now() - stepStart)
          continue
        }

        const executed = await this.executeWithTimeout(
          step.execute,
          step.rollbackTimeEstimate * 1000
        )

        if (!executed) {
          this.log(planName, step.name, 'failed', Date.now() - stepStart, 'Execution returned false')
          await this.notify(plan, `回滚步骤 "${step.name}" 失败`)
          return {
            success: false,
            totalTime: Date.now() - startTime,
            failedStep: step.name,
          }
        }

        const verified = await step.verify()
        if (!verified) {
          this.log(planName, step.name, 'failed', Date.now() - stepStart, 'Verification failed')
          await this.notify(plan, `回滚步骤 "${step.name}" 验证失败`)
          return {
            success: false,
            totalTime: Date.now() - startTime,
            failedStep: step.name,
          }
        }

        executedSteps.push(step.name)
        this.log(planName, step.name, 'success', Date.now() - stepStart)

      } catch (error) {
        this.log(
          planName, step.name, 'failed',
          Date.now() - stepStart,
          error instanceof Error ? error.message : String(error)
        )
        await this.notify(plan, `回滚步骤 "${step.name}" 异常: ${error}`)
        return {
          success: false,
          totalTime: Date.now() - startTime,
          failedStep: step.name,
        }
      }
    }

    await this.notify(plan, `回滚计划 "${planName}" 执行成功，耗时 ${Date.now() - startTime}ms`)
    return { success: true, totalTime: Date.now() - startTime }
  }

  private async executeWithTimeout(
    fn: () => Promise<boolean>,
    timeoutMs: number
  ): Promise<boolean> {
    return Promise.race([
      fn(),
      new Promise<boolean>((_, reject) =>
        setTimeout(() => reject(new Error('Timeout')), timeoutMs)
      ),
    ])
  }

  private log(plan: string, step: string, status: 'success' | 'failed' | 'skipped', duration: number, error?: string): void {
    this.executionLog.push({ plan, step, status, timestamp: new Date(), duration, error })
  }

  private async notify(plan: RollbackPlan, message: string): Promise<void> {
    console.log(`[ROLLBACK] ${message}`)
  }
}
```

### 示例二：数据回滚——操作日志回放

```typescript
// rollback/data-rollback.ts
interface OperationLog {
  id: string
  timestamp: Date
  entityType: string
  entityId: string
  operation: 'create' | 'update' | 'delete'
  before: Record<string, unknown> | null
  after: Record<string, unknown> | null
  userId: string
  source: 'legacy' | 'new'
}

class DataRollbackManager {
  private operationLogRepo: OperationLogRepository
  private entityRepos: Map<string, EntityRepository<any>>

  constructor(
    operationLogRepo: OperationLogRepository,
    entityRepos: Map<string, EntityRepository<any>>
  ) {
    this.operationLogRepo = operationLogRepo
    this.entityRepos = entityRepos
  }

  async rollbackToTime(targetTime: Date): Promise<{
    reverted: number
    skipped: number
    failed: number
    details: Array<{ entityId: string; action: string; success: boolean }>
  }> {
    const logs = await this.operationLogRepo.findAfter(targetTime, {
      source: 'new',
      orderBy: 'timestamp DESC',
    })

    const results = {
      reverted: 0,
      skipped: 0,
      failed: 0,
      details: [] as Array<{ entityId: string; action: string; success: boolean }>,
    }

    for (const log of logs) {
      try {
        const repo = this.entityRepos.get(log.entityType)
        if (!repo) {
          results.skipped++
          results.details.push({
            entityId: log.entityId,
            action: `跳过: 未知实体类型 ${log.entityType}`,
            success: false,
          })
          continue
        }

        const currentEntity = await repo.findById(log.entityId)

        switch (log.operation) {
          case 'create':
            if (currentEntity) {
              await repo.delete(log.entityId)
              results.reverted++
              results.details.push({
                entityId: log.entityId,
                action: '删除（回滚创建操作）',
                success: true,
              })
            } else {
              results.skipped++
            }
            break

          case 'update':
            if (log.before && currentEntity) {
              await repo.update(log.entityId, log.before)
              results.reverted++
              results.details.push({
                entityId: log.entityId,
                action: '恢复到更新前状态',
                success: true,
              })
            } else {
              results.skipped++
            }
            break

          case 'delete':
            if (log.before) {
              await repo.create(log.before)
              results.reverted++
              results.details.push({
                entityId: log.entityId,
                action: '恢复（回滚删除操作）',
                success: true,
              })
            } else {
              results.skipped++
              results.details.push({
                entityId: log.entityId,
                action: '跳过: 无恢复数据',
                success: false,
              })
            }
            break
        }
      } catch (error) {
        results.failed++
        results.details.push({
          entityId: log.entityId,
          action: `失败: ${error instanceof Error ? error.message : String(error)}`,
          success: false,
        })
      }
    }

    return results
  }

  async validateRollback(targetTime: Date): Promise<{
    canRollback: boolean
    issues: string[]
    estimatedOperations: number
  }> {
    const logs = await this.operationLogRepo.findAfter(targetTime, {
      source: 'new',
    })

    const issues: string[] = []

    const createWithoutBefore = logs.filter(
      l => l.operation === 'create' && !l.after
    )
    if (createWithoutBefore.length > 0) {
      issues.push(`${createWithoutBefore.length} 条创建记录缺少恢复数据`)
    }

    const updateWithoutBefore = logs.filter(
      l => l.operation === 'update' && !l.before
    )
    if (updateWithoutBefore.length > 0) {
      issues.push(`${updateWithoutBefore.length} 条更新记录缺少更新前数据`)
    }

    const deleteWithoutBefore = logs.filter(
      l => l.operation === 'delete' && !l.before
    )
    if (deleteWithoutBefore.length > 0) {
      issues.push(`${deleteWithoutBefore.length} 条删除记录缺少恢复数据`)
    }

    return {
      canRollback: issues.length === 0,
      issues,
      estimatedOperations: logs.length,
    }
  }
}
```

### 示例三：回滚演练（Game Day）

```typescript
// rollback/game-day.ts
interface GameDayScenario {
  name: string
  setup: () => Promise<void>
  injectFailure: () => Promise<void>
  rollbackPlan: string
  expectedRecoveryTime: number
  successCriteria: () => Promise<boolean>
}

class GameDayRunner {
  private results: Array<{ scenario: string; success: boolean; recoveryTime: number; issues: string[] }> = []

  constructor(private rollbackController: RollbackController) {}

  async runScenario(scenario: GameDayScenario): Promise<void> {
    console.log(`\n=== 演练: ${scenario.name} ===`)
    const issues: string[] = []

    try { await scenario.setup() } catch (e) {
      this.results.push({ scenario: scenario.name, success: false, recoveryTime: 0, issues: [`准备失败: ${e}`] })
      return
    }

    try { await scenario.injectFailure() } catch (e) {
      this.results.push({ scenario: scenario.name, success: false, recoveryTime: 0, issues: [`注入失败: ${e}`] })
      return
    }

    const startTime = Date.now()
    const rollback = await this.rollbackController.executeRollback(scenario.rollbackPlan)
    const recoveryTime = Date.now() - startTime

    if (!rollback.success) issues.push(`回滚失败: ${rollback.failedStep}`)
    if (recoveryTime > scenario.expectedRecoveryTime * 1.5) issues.push(`恢复超时: ${recoveryTime}ms`)

    const criteriaOk = await scenario.successCriteria().catch(() => false)
    if (!criteriaOk) issues.push('未达成功标准')

    this.results.push({ scenario: scenario.name, success: issues.length === 0, recoveryTime, issues })
  }

  getReport() { return { passed: this.results.filter(r => r.success).length, failed: this.results.filter(r => !r.success).length, results: this.results } }
}
```

## 常见误区

### 误区一：回滚方案等到需要时才设计

回滚方案必须在迁移开始前设计好。迁移过程中出了问题才临时想回滚方案，时间压力下容易出错。

### 误区二：只测试正向流程，不测试回滚

迁移演练应该包括"迁移 → 发现问题 → 回滚 → 验证"的完整流程。只测试迁移不测试回滚，回滚时可能发现回滚方案本身有 bug。

### 误区三：回滚后不做数据校验

流量切回旧系统后，必须检查旧系统的数据是否一致。特别是新旧系统共享数据库时，新系统可能写入了旧系统不认识的数据。

### 误区四：保留太多历史版本

回滚不需要保留所有历史版本。通常保留"当前版本"和"上一个稳定版本"两个版本就够了。保留太多版本会增加维护成本和出错概率。

### 误区五：回滚是失败的表现

回滚是工程成熟的标志。能回滚说明你的系统有安全网。不能回滚的迁移是在裸奔。

## 小结

回滚机制的核心设计：

1. **四层回滚**：流量 → 配置 → 代码 → 数据，从低风险到高风险
2. **可逆设计**：迁移过程中只做加法，不做减法
3. **操作日志**：记录所有数据变更的 before/after，支持日志回放
4. **回滚演练**：定期 Game Day，验证回滚方案的可靠性
5. **自动触发**：基于监控指标自动触发回滚，减少人工延迟

## 参考答案

### 练习一

**思路**：三种场景对应不同的回滚层次。

**答案**：

**场景 1：数据迁移失败**

策略：双读模式
- 迁移过程中，新系统同时从本地和 S3 读取，本地优先
- 迁移中断时，已迁移的文件在 S3，未迁移的文件在本地
- 回滚操作：不需要回滚，系统自动降级到本地读取
- 验证：检查本地文件是否完整

**场景 2：对象存储服务不可用**

策略：读写降级
- 正常情况：写入 S3 + 本地备份，读取 S3
- S3 不可用时：读取本地备份
- 回滚操作：切换配置 `storage.primary = 'local'`
- 验证：所有头像正常加载

**场景 3：URL 格式变化导致前端异常**

策略：URL 兼容层
- 迁移前：`/avatars/user_123.jpg`
- 迁移后：`https://cdn.example.com/avatars/user_123.jpg`
- 实现：后端 API 返回 `avatarUrl` 字段，前端只使用这个字段
- 回滚操作：后端修改 `avatarUrl` 的生成逻辑，返回旧格式 URL
- 验证：前端页面正常显示头像

```typescript
// 配置驱动的 URL 生成
function getAvatarUrl(userId: string): string {
  const config = getStorageConfig()
  
  if (config.avatarSource === 's3') {
    return `${config.cdnBase}/avatars/${userId}.jpg`
  }
  return `/avatars/${userId}.jpg`
}
```
