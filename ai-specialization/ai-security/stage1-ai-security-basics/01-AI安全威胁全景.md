## 场景引入

2023 年，三星半导体部门的工程师将公司源代码粘贴到 ChatGPT 中寻求代码优化建议，数周后这些商业秘密已进入 OpenAI 的训练数据池，三星不得不全面禁止内部使用 ChatGPT。同一时期，攻击者仅用一句"忽略之前所有指令"就让 Bing Chat 泄露了内部代号"Sydney"和完整的系统 Prompt。这两个事件揭示了一个关键事实：AI 系统的安全威胁既来自传统基础设施层面（数据防泄漏），也来自 AI 特有的攻击面（Prompt 注入），而大多数团队在上线第一个 AI 应用时对此毫无准备。

## 1. 为什么 AI 安全很重要

### 1.1 AI 安全 vs 传统安全

```
传统软件安全                    AI 系统安全
┌─────────────────┐            ┌─────────────────┐
│ 确定性行为       │            │ 概率性行为       │
│ 代码即逻辑       │            │ 数据即逻辑       │
│ 输入→处理→输出   │            │ 输入→推理→生成   │
│ 边界清晰         │            │ 边界模糊         │
│ 漏洞可复现       │            │ 行为不确定       │
└─────────────────┘            └─────────────────┘
        ↓                              ↓
  规则驱动防御                   概率驱动防御
  签名匹配有效                   需要语义理解
  攻击面相对固定                 攻击面持续演化
```

```python
class AISecurityChecklist:
    """AI 系统安全评估检查清单"""

    def __init__(self):
        self.categories = {
            "data_security": [
                "训练数据来源是否可信",
                "是否有数据质量验证流程",
                "是否实施数据分类分级",
                "是否有数据防泄漏措施",
                "是否定期审查训练数据"
            ],
            "model_security": [
                "模型来源是否可信",
                "是否有模型完整性验证",
                "是否进行安全基准测试",
                "是否有模型版本管理",
                "是否限制模型信息暴露"
            ],
            "application_security": [
                "是否有输入验证机制",
                "是否实施 Prompt 注入防御",
                "是否有输出过滤机制",
                "是否有访问控制和鉴权",
                "是否有审计日志"
            ],
            "infrastructure_security": [
                "API 是否使用 HTTPS",
                "密钥管理是否安全",
                "是否有速率限制",
                "是否有资源配额控制",
                "是否有监控告警"
            ],
            "operational_security": [
                "是否有安全事件响应流程",
                "是否有定期安全评估",
                "是否有红队测试",
                "是否有安全培训计划",
                "是否有合规审查机制"
            ]
        }

    def evaluate(self, system_config: dict) -> dict:
        results = {}
        for category, checks in self.categories.items():
            results[category] = {
                "total": len(checks),
                "passed": 0,
                "failed": 0,
                "details": []
            }
            for check in checks:
                passed = self._evaluate_check(check, system_config)
                results[category]["details"].append({
                    "check": check,
                    "passed": passed
                })
                if passed:
                    results[category]["passed"] += 1
                else:
                    results[category]["failed"] += 1
        return results

    def _evaluate_check(self, check: str, config: dict) -> bool:
        # 简化的检查逻辑
        return config.get(check, False)

    def generate_report(self, results: dict) -> str:
        report = "# AI 安全评估报告\n\n"
        total_passed = sum(r["passed"] for r in results.values())
        total_checks = sum(r["total"] for r in results.values())
        score = (total_passed / total_checks) * 100

        report += f"## 总体评分: {score:.1f}/100\n\n"
        for category, result in results.items():
            report += f"### {category}\n"
            report += f"- 通过: {result['passed']}/{result['total']}\n"
            for detail in result["details"]:
                status = "✅" if detail["passed"] else "❌"
                report += f"  {status} {detail['check']}\n"
            report += "\n"
        return report


# 使用示例
checklist = AISecurityChecklist()
config = {
    "训练数据来源是否可信": True,
    "是否有数据质量验证流程": True,
    "是否有输入验证机制": True,
    "是否实施 Prompt 注入防御": False,
    "是否有输出过滤机制": True
}
results = checklist.evaluate(config)
print(checklist.generate_report(results))
```

## 6. 代码实战

### 6.1 简单威胁建模工具

```python
from dataclasses import dataclass
from enum import Enum
from typing import list

class Severity(Enum):
    LOW = 1
    MEDIUM = 2
    HIGH = 3
    CRITICAL = 4

@dataclass
class Threat:
    name: str
    category: str
    severity: Severity
    description: str
    mitigation: str
    component: str

class ThreatModel:
    def __init__(self, system_name: str):
        self.system_name = system_name
        self.threats: list[Threat] = []
        self.components: dict[str, list[str]] = {}

    def add_component(self, name: str, description: str):
        self.components[name] = description

    def add_threat(self, threat: Threat):
        self.threats.append(threat)

    def get_threats_by_severity(self, severity: Severity) -> list[Threat]:
        return [t for t in self.threats if t.severity == severity]

    def get_risk_score(self) -> float:
        if not self.threats:
            return 0.0
        total = sum(t.severity.value for t in self.threats)
        max_possible = len(self.threats) * Severity.CRITICAL.value
        return (total / max_possible) * 100

    def generate_report(self) -> str:
        report = f"# 威胁建模报告: {self.system_name}\n\n"
        report += f"## 风险评分: {self.get_risk_score():.1f}/100\n\n"

        for severity in Severity:
            threats = self.get_threats_by_severity(severity)
            if threats:
                report += f"### {severity.name} 级别威胁 ({len(threats)})\n"
                for t in threats:
                    report += f"- **{t.name}** ({t.component})\n"
                    report += f"  - 描述: {t.description}\n"
                    report += f"  - 缓解: {t.mitigation}\n\n"
        return report


# 使用示例

model.add_component("Web 接口", "用户交互界面")
model.add_component("LLM API", "大语言模型服务")

model.add_threat(Threat(
    name="Prompt 注入",
    category="注入攻击",
    severity=Severity.HIGH,
    description="用户输入恶意指令覆盖系统行为",
    mitigation="输入过滤 + 指令隔离 + 输出验证",
    component="Web 接口"
))

model.add_threat(Threat(
    name="知识库投毒",
    category="数据安全",
    severity=Severity.CRITICAL,
    description="攻击者向知识库注入恶意文档",
    mitigation="文档审核 + 来源验证 + 定期清理",
    component="知识库"
))

print(model.generate_report())
```

## 7. 对比表

| 维度 | 传统安全 | AI 安全 |
|------|----------|---------|
| 攻击面 | 代码、协议、配置 | 数据、模型、Prompt、工具 |
| 漏洞性质 | 确定性、可复现 | 概率性、不确定 |
| 防御方法 | 规则匹配、签名检测 | 语义理解、行为分析 |
| 测试方法 | 渗透测试、模糊测试 | 红队测试、对抗样本 |
| 更新频率 | 按版本发布 | 持续学习、实时更新 |
| 评估标准 | CVSS 评分 | 多维度风险评估 |
| 合规要求 | 等保、ISO 27001 | AI Act、算法备案 |

## 8. 常见误区

1. **"AI 安全就是传统安全"**: AI 安全需要专门的方法论和工具
2. **"模型越大越安全"**: 规模不等于安全性，大模型可能有更多攻击面
3. **"安全只在部署时考虑"**: 安全应该贯穿整个 AI 生命周期
4. **"一次安全评估就够了"**: AI 系统需要持续的安全监控和评估
5. **"开源模型更安全"**: 开源模型也需要安全审计和验证

## 工程建议

1. **在项目启动阶段就进行 AI 威胁建模**：不要等到上线前才考虑安全。在架构设计阶段使用 STRIDE 模型对数据流、模型调用链和工具接口逐项分析，将安全需求写入技术方案文档，与功能需求同等评审。
2. **建立分层防御体系，不依赖单一安全措施**：输入层做验证和过滤，Prompt 层做指令隔离，输出层做 PII 检测和内容审核，基础设施层做速率限制和访问控制。每一层单独被绕过的概率不低，但多层叠加后攻击成功率会指数下降。
3. **为 AI 系统建立独立的安全监控与审计管道**：记录每次 Prompt 注入尝试、异常输出、工具调用日志，并设置告警阈值。传统 APM 工具不覆盖语义层面的安全事件，需要额外接入内容分类器和异常行为检测模块。
4. **制定 AI 安全事件响应预案并定期演练**：明确数据泄露、模型被越狱、供应链投毒等场景的响应流程、责任人和止损措施，每季度至少做一次桌面推演或红队测试。

## 总结

- AI 安全面临独特的挑战：不确定性、可解释性、数据依赖性
- 威胁贯穿 AI 生命周期的每个阶段
- 需要纵深防御的策略，不能依赖单一安全措施
- 安全思维应从项目开始就融入，而非事后补充

### 练习 1: 威胁识别

**思路**：以一个典型的 RAG 知识库问答系统为例，从数据层、模型层、应用层、基础设施层四个维度梳理威胁。优先考虑出现概率高且影响严重的威胁，结合课程中的 AI-STRIDE 模型和攻击影响矩阵进行排序。

**答案**：

以"企业内部 RAG 知识库问答系统"为例，Top 5 安全威胁：

| 排名 | 威胁名称 | 所属层级 | 风险等级 | 原因分析 |
|------|----------|----------|----------|----------|
| 1 | Prompt 注入 | 应用层-输入 | HIGH | 用户可通过精心构造的输入覆盖系统指令，绕过权限控制或泄露敏感信息。RAG 场景下攻击者可通过查询注入操纵检索结果。 |
| 2 | 知识库数据投毒 | 数据层 | CRITICAL | 若知识库文档上传接口缺乏审核，攻击者可注入恶意文档，导致模型在特定话题上输出虚假信息，且难以被常规测试发现。 |
| 3 | 敏感信息泄露 | 模型层-输出 | HIGH | 检索到的文档可能包含薪酬、合同等敏感内容，若输出层未做 PII 检测和脱敏，会直接暴露给用户。 |
| 4 | 供应链攻击 | 基础设施层 | HIGH | 依赖的 Embedding 模型或第三方库可能被篡改（如 PoisonGPT 场景），模型完整性难以保证。 |
| 5 | 向量数据库未授权访问 | 数据层 | MEDIUM | 向量数据库若未配置访问控制，攻击者可直接读取/篡改向量数据，破坏检索结果的完整性和保密性。 |

**要点**：
- 威胁识别应覆盖数据层、模型层、应用层、基础设施层，不能只关注 LLM 本身
- 使用 AI-STRIDE 模型可以系统性地避免遗漏
- 风险排序应综合考虑发生概率和影响程度

### 练习 3: 案例研究

**思路**：选择一个有公开信息的 AI 安全事件，从攻击路径、影响范围、根因分析和教训四个方面进行结构化分析。重点关注攻击者利用了哪些安全薄弱环节，以及防御侧可以采取哪些措施。

**答案**：

**案例：DeepSeek 数据库泄露事件 (2025)**

**事件概述**：
2025 年初，安全研究人员发现中国 AI 公司 DeepSeek 的一个可公开访问的数据库泄露了超过 100 万条聊天记录和内部日志，包括 API 密钥、后端架构细节等敏感信息。

**攻击路径分析**：
```
攻击者发现公开可访问的 ClickHouse 数据库
    │
    ▼
无需认证即可直接连接数据库端口
    │
    ▼
获取完整的聊天记录表和系统日志表
    │
    ▼
从日志中提取 API 密钥和后端架构信息
    │
    ▼
可能利用泄露的密钥进行进一步攻击
```

**影响评估**：
| 维度 | 影响 |
|------|------|
| 数据泄露 | 100 万+ 条用户聊天记录，含个人信息 |
| 系统安全 | API 密钥、后端架构细节泄露 |
| 用户信任 | 用户对平台数据保护能力产生严重质疑 |
| 合规风险 | 违反个人信息保护法，面临监管处罚 |
| 商业损失 | 竞争对手可利用架构信息进行针对性攻击 |

**根因分析**：
1. **基础设施配置错误**：数据库端口对外暴露且无认证
2. **缺乏安全审计**：未定期检查对外暴露的服务
3. **密钥管理不当**：日志中明文记录 API 密钥
4. **安全开发生命周期缺失**：部署阶段的安全检查不充分

**可吸取的教训**：
1. **基础设施安全同样重要**：AI 系统的安全不能只关注 Prompt 和模型，数据库、API 网关等基础设施的安全配置是第一道防线
2. **最小暴露原则**：所有数据库和服务端口必须限制访问，使用 VPC 和防火墙规则
3. **日志脱敏**：日志中绝对不能记录 API 密钥、密码等敏感信息
4. **定期安全扫描**：使用自动化工具定期扫描对外暴露的服务和端口

**要点**：
- AI 安全事件往往不是因为 LLM 本身被攻破，而是基础设施配置错误
- 日志中的敏感信息泄露是常见但容易被忽视的风险
- 安全事件的影响是多维度的：数据、信任、合规、商业
