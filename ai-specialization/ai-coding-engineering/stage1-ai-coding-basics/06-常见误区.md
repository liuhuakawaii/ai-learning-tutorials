# 06 - 常见误区

> **课程定位**：识别 AI 编程中的典型认知误区，建立正确的使用心态。
>
> **前置要求**：有使用 AI 编程工具的实际经验（01-05 课）
>
> **预计时长**：1 小时

---

## 场景引入

你在团队里推广 AI 编程工具，遇到两种极端反应：一种是"AI 要取代我们了，学编程没用了"，另一种是"AI 写的代码质量太差，不如自己写"。两种观点都有人深信不疑，但都偏离了事实。你发现，很多开发者对 AI 编程工具的认知停留在"听说"层面，要么过度恐惧，要么过度轻视。如何帮自己和团队建立对 AI 编程的准确认知？

---

## 学习目标

1. 识别 10 个 AI 编程的常见误区
2. 理解每个误区背后的真相
3. 建立"AI 是工具，不是替代品"的核心认知
4. 学会评估 AI 能力的真实边界
5. 形成可持续的 AI 编程工作习惯

---

## 误区与真相

### 误区 1：AI 会取代程序员

```
┌──────────────────────────────────────────────────────────────┐
│  Myth: AI 会取代程序员，学编程没用了                            │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Reality: AI 改变的是编程方式，不是取消编程                     │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ 以前：手写每一行代码                                     │  │
│  │   └── 70% 时间写代码，30% 时间思考                       │  │
│  │                                                        │  │
│  │ 现在：AI 辅助生成代码                                    │  │
│  │   └── 30% 时间写代码，50% 时间思考+审查，20% 时间调试    │  │
│  │                                                        │  │
│  │ 趋势：编程能力不是贬值，而是升级                         │  │
│  │   └── 从"写代码"到"指挥 AI + 审查代码"                  │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  你仍然需要理解：                                             │
│  • 数据结构和算法                                            │
│  • 系统设计和架构                                            │
│  • 安全和性能                                                │
│  • 业务逻辑和需求分析                                        │
│  • 调试和问题排查                                            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 误区 2：AI 生成的代码不需要测试

```
┌──────────────────────────────────────────────────────────────┐
│  Myth: AI 写的代码质量很高，不需要测试                          │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Reality: AI 代码更需要测试                                   │
│                                                              │
│  原因：                                                       │
│  1. AI 代码看起来"正确"但可能有隐藏 bug                       │
│  2. 你不完全理解 AI 的实现方式                                │
│  3. AI 可能使用了你不熟悉的 API 用法                          │
│  4. 边界情况经常被遗漏                                        │
│                                                              │
│  正确做法：                                                   │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ AI 生成代码                                              │  │
│  │       │                                                │  │
│  │       ▼                                                │  │
│  │ 审查代码（第 05 课的清单）                                │  │
│  │       │                                                │  │
│  │       ▼                                                │  │
│  │ 编写/运行测试                                            │  │
│  │       │                                                │  │
│  │       ▼                                                │  │
│  │ 测试通过 → 使用                                          │  │
│  │ 测试失败 → 修改 → 重新测试                               │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

```
│                                                              │
│  AI 看不到的：                                                │
```

### 误区 6：AI 的回答总是正确的

```
┌──────────────────────────────────────────────────────────────┐
│  Myth: AI 给出的答案/代码是权威的、正确的                       │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Reality: AI 会"自信地犯错"（Hallucination）                  │
│                                                              │
│  常见的 AI 错误类型：                                         │
│                                                              │
│  1. 编造不存在的 API                                          │
│     AI：使用 db.findManyWithPagination()                     │
│     真相：这个方法不存在                                      │
│                                                              │
│  2. 使用过时的 API                                            │
│     AI：使用 req.param('id')                                 │
│     真相：Express 5 已经废弃这个用法                           │
│                                                              │
│  3. 逻辑错误但看起来合理                                      │
│     AI：if (user.role = 'admin')  // 赋值不是比较             │
│     真相：应该是 === 而不是 =                                 │
│                                                              │
│  4. 过于自信地给出错误解释                                     │
│     AI："这个错误是因为 X"（实际原因是 Y）                     │
│                                                              │
│  正确做法：验证每一个 AI 的输出                                │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

```
┌──────────────────────────────────────────────────────────────┐

│                                                              │

│                                                              │

│     你不懂数据库索引 → 不知道该让 AI 优化什么                  │
│                                                              │
│  3. 调试需要深入理解                                          │

│                                                              │
│  4. 架构决策需要经验                                          │

│                                                              │
│  AI 是学习的加速器，不是替代品：                               │
│  • 用 AI 快速理解新概念                                       │
│  • 用 AI 生成学习用的示例代码                                 │
│  • 用 AI 解释你不理解的代码                                   │
│                                                              │

```

### 误区 8：AI 补全的代码一定是最佳实践

```
┌──────────────────────────────────────────────────────────────┐
│  Myth: AI 补全的代码代表了最佳实践                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Reality: AI 输出的是"最常见的写法"，不一定是"最好的写法"       │
│                                                              │
│  AI 的训练数据特点：                                          │
│  • 包含大量 Stack Overflow 答案（质量参差不齐）                │
│  • 包含过时的代码模式                                         │
│  • "常见" ≠ "最佳"                                           │
│                                                              │
│  例子：                                                       │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ AI 常生成：class 组件（因为训练数据中存量更大）           │  │
│  │ 最佳实践：函数组件 + Hooks                               │  │
│  │                                                        │  │
│  │ AI 常生成：callback 风格的异步代码                       │  │
│  │ 最佳实践：async/await                                   │  │
│  │                                                        │  │
│  │ AI 常生成：lodash 工具函数                               │  │
│  │ 最佳实践：原生方法（现代 JS 已支持大部分功能）             │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  正确做法：用你的专业知识判断，不要盲从 AI                     │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 常见误区

| 误区 | 为什么危险 | 正确做法 |
|------|-----------|----------|
| 把 AI 当搜索引擎用 | 得到的答案缺乏上下文，质量不稳定 | 带着具体的代码上下文和明确的任务描述提问 |
| 用了 AI 就不写文档了 | 代码意图丢失，后续维护成本翻倍 | 让 AI 帮你生成文档，但必须人工审核准确性 |
| 每次都开新对话 | 丢失之前的上下文和决策记录 | 在同一对话中迭代，复杂任务用文件记录中间结果 |
| 团队成员各自用不同工具 | 代码风格不一致，审查成本增加 | 团队统一工具选择和使用规范 |

---

## 工程建议

1. **建立团队 AI 使用规范**：明确规定哪些场景适合用 AI（样板代码、测试、文档）、哪些场景需要手动处理（核心业务逻辑、安全代码），让团队有统一的判断标准。
2. **定期分享 AI 踩坑经验**：每周花 15 分钟让团队成员分享一个 AI 犯错的案例。这比任何培训都有效——真实案例能快速建立"质疑—验证—信任"的正确习惯。
3. **把"AI 不能替代的能力"纳入成长计划**：系统设计、需求分析、代码审查、安全意识——这些能力在 AI 时代反而更重要。团队的培养计划应该明确覆盖这些方向。
4. **用 AI 加速学习而非替代学习**：鼓励团队成员用 AI 快速理解新概念和代码库，但要求每个人在 code review 中能解释清楚自己提交的每一行代码。

---

## 总结

本课要点：

1. **10 个误区**：从"取代程序员"到"用 AI 是作弊"，逐一破除
2. **核心真相**：AI 是放大器，不是替代品
3. **正确心态**：质疑—验证—信任的节奏
4. **持续学习**：AI 加速学习，但不替代学习
5. **专业体现**：知道何时用、如何审查、如何负责

## 动手练习

### 练习 1：误区自查（15 分钟）

回顾你使用 AI 编程工具的经历，诚实地回答：
1. 你是否曾经不审查就使用 AI 代码？
2. 你是否曾经因为 AI 给了答案就不深入学习？
3. 你是否曾经过度依赖某个工具？

对每个"是"的回答，写出你将如何改进。

### 练习 2：AI 错误收集（20 分钟）

在接下来的编程中，专门记录 AI 犯的错误：
1. 编造不存在的 API（Hallucination）
2. 使用过时的写法
3. 遗漏边界情况
4. 安全问题

收集至少 3 个真实案例，分析错误模式。

评估你在以下"AI 不能替代"的能力上的水平（1-5 分）：

| 能力 | 当前水平 | 计划如何提升 |
|------|----------|-------------|

## 参考答案

### 练习 1：误区自查

**思路**：这个练习的核心是建立"元认知"——意识到自己在使用 AI 工具时的不自觉习惯。大多数人至少会在 1-2 个问题上回答"是"，这很正常。关键是为每个"是"写出具体的改进措施。

**答案**：

示例自查结果和改进计划：

| 问题 | 我的回答 | 改进措施 |
|------|---------|---------|
| 是否不审查就使用？ | 是，写 demo 时经常直接用 | 建立"三秒规则"：Tab 接受后至少扫一眼安全相关代码（密码、SQL、token） |
| 是否因此不深入学习？ | 是，遇到 React Hooks 时直接问 AI 不看文档 | 每次 AI 给出答案后追问"为什么这样设计？"，把解释记到个人笔记 |
| 是否过度依赖某个工具？ | 是，几乎只用 ChatGPT，不会用 IDE 内置工具 | 本周尝试 Copilot Chat 的 @workspace 功能，对比效果 |

改进计划示例（针对"不审查就使用"）：
- 第 1 周：每次 Tab 接受后花 3 秒检查是否有 SQL 注入、明文密码、硬编码密钥
- 第 2 周：扩展检查范围，加入边界情况（null、空数组）和错误处理

**要点**：
- 诚实面对自己的习惯是改变的第一步——不要自我欺骗
- 改进计划要具体可执行，不要写"以后注意审查"这种模糊目标
- 从最容易犯的 1-2 个误区开始改，不要试图一次改所有
- 每周回顾一次，看看习惯是否真的改变了

### 练习 2：AI 错误收集

**思路**：收集 AI 犯错的真实案例比任何理论培训都有效。重点是识别错误模式——同一种错误在不同场景下会反复出现，识别模式后就能快速拦截。

**答案**：

收集的真实案例示例：

**案例 1：编造不存在的 API**
```typescript
// AI 生成的代码
const users = await prisma.user.findManyWithPagination({
  page: 1,
  size: 20,
});

// 真相：Prisma 没有 findManyWithPagination 方法
// 正确写法：
const users = await prisma.user.findMany({
  skip: (page - 1) * pageSize,
  take: pageSize,
});
```
错误模式：AI 倾向于生成"语义化"的方法名，但这些方法在实际库中不存在。

**案例 2：使用过时的写法**
```typescript
// AI 生成的代码
app.get('/users/:id', (req, res) => {
  const id = req.param('id'); // ❌ Express 5 已废弃
});

// 正确写法：
app.get('/users/:id', (req, res) => {
  const id = req.params.id;
});
```
错误模式：AI 的训练数据包含大量旧版本代码，容易生成过时的 API 用法。

**案例 3：遗漏边界情况**
```typescript
// AI 生成的代码
function getAveragePrice(products: Product[]): number {
  return products.reduce((sum, p) => sum + p.price, 0) / products.length;
  // ❌ products 为空数组时返回 NaN
}

// 正确写法：
function getAveragePrice(products: Product[]): number {
  if (products.length === 0) return 0;
  return products.reduce((sum, p) => sum + p.price, 0) / products.length;
}
```
错误模式：AI 默认生成"快乐路径"代码，空值、空数组、并发等边界情况需要你主动补充。

**案例 4：安全问题**
```typescript
// AI 生成的代码
const user = await db.query(
  `SELECT * FROM users WHERE email = '${req.body.email}'`
);
// ❌ SQL 注入
```
错误模式：AI 可能生成使用字符串拼接的 SQL，尤其是在"快速生成"场景下。

**要点**：
- 每个错误案例都应该归类到一个模式中，方便后续快速识别
- "编造 API"是最常见的错误——永远查官方文档验证 AI 给出的方法名
- "快乐路径代码"是最隐蔽的错误——看起来逻辑正确，但边界情况下会崩溃
- 建立团队共享的"AI 常犯错误"文档，新人可以直接参考

### 练习 3：能力评估

**思路**：这个练习的目的是识别"AI 不能替代的核心能力"，并针对性提升。AI 时代，这些能力反而更重要——因为 AI 负责写代码，你负责审查、设计和决策。

**答案**：

示例评估结果：

| 能力 | 当前水平 | 提升计划 |
|------|---------|---------|
| 系统设计 | 3/5 | 每周读一个系统设计案例（如设计短链服务），用 AI 辅助理解但自己做决策 |
| 需求分析 | 4/5 | 在写代码前先用 WHAT/WHY/HOW 模板梳理需求，减少返工 |
| 代码审查 | 3/5 | 每次 PR 审查时使用五维度清单，重点提升安全审查能力 |
| 性能优化 | 2/5 | 本周学习 N+1 查询的识别和优化，用 AI 生成的代码做练习 |
| 安全意识 | 2/5 | 完成 OWASP Top 10 的学习，每天审查一个 AI 生成的代码的安全问题 |

2 周提升计划（针对评分最低的两项）：

**性能优化（第 1 周）：**
- Day 1-2：学习 N+1 查询的识别方法
- Day 3-4：学习 Prisma 的 include 和批量查询
- Day 5：用 AI 生成一个有性能问题的代码，自己优化

**安全意识（第 2 周）：**
- Day 1-2：学习 OWASP Top 10 中的注入、XSS、认证漏洞
- Day 3-4：每天审查 2 个 AI 生成的函数，专门找安全问题
- Day 5：为项目创建安全审查清单

**要点**：
- 诚实评分是前提——大多数人会高估自己，建议让同事互评
- 2 周计划要聚焦，不要贪多——一次只提升 1-2 项
- 用 AI 辅助学习这些能力（如让 AI 解释系统设计案例），但最终要自己掌握
- 这些能力在 AI 时代反而更值钱——能审查 AI 代码的人比能写代码的人更稀缺
