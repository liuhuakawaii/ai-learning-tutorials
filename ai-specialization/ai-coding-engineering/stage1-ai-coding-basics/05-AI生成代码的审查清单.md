# 05 - AI 生成代码的审查清单

> **课程定位**：AI 写的代码不等于好代码。建立系统性的审查习惯，确保 AI 生成的代码达到生产标准。
>
> **前置要求**：掌握 Chat 模式和上下文管理（03、04 课）
>
> **预计时长**：1.5 小时

---

## 场景引入

你用 AI 快速生成了一个用户注册模块，代码看起来逻辑清晰、风格整洁，于是直接提交上线。一周后，安全团队发现登录接口存在 SQL 注入漏洞——AI 用的是字符串拼接而非参数化查询。你回看代码，发现 AI 确实生成了一段"看起来正确"但实际危险的代码。这件事让你意识到：AI 生成的代码不等于好代码，系统性的审查不是可选项，而是必选项。

---

## 学习目标

1. 理解为什么必须审查 AI 生成的每一行代码
2. 掌握 5 个维度的系统审查方法（安全、正确性、边界、性能、风格）
3. 能识别 AI 代码中常见的隐藏 bug 模式
4. 建立可复用的审查清单和流程
5. 学会区分"可以接受"和"必须修改"的代码

## 2. 五维度审查清单

### 2.1 安全性审查（Security）

```
┌──────────────────────────────────────────────────────────────┐
│                安全性审查要点                                   │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  ☐ SQL 注入                                                  │
│    检查：是否使用参数化查询？                                  │
│    ❌ `SELECT * FROM users WHERE id = '${id}'`               │
│    ✅ `SELECT * FROM users WHERE id = $1`, [id]              │
│                                                              │
│  ☐ XSS（跨站脚本）                                           │
│    检查：用户输入是否直接渲染到 HTML？                         │
│    ❌ `innerHTML = userInput`                                │
│    ✅ `textContent = userInput` 或使用框架的转义               │
│                                                              │
│  ☐ 密码处理                                                  │
│    检查：是否使用 bcrypt/argon2？是否明文存储？                │
│    ❌ `if (user.password === inputPassword)`                 │
│    ✅ `if (await bcrypt.compare(input, user.passwordHash))`  │
│                                                              │
│  ☐ 认证和授权                                                │
│    检查：是否验证用户身份？是否有权限检查？                    │
│    ❌ 不检查 req.user 就执行敏感操作                          │
│    ✅ 中间件验证 + 业务层权限检查                              │
│                                                              │
│  ☐ 敏感信息                                                  │
│    检查：是否硬编码密钥？是否在日志中打印敏感信息？            │
│    ❌ `const API_KEY = 'sk-1234567890'`                      │
│    ✅ `const API_KEY = process.env.API_KEY`                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**示例：AI 生成的代码中的安全问题**

```typescript
// AI 生成的登录函数 — 包含多个安全问题
async function login(req: Request, res: Response) {
  const { email, password } = req.body;

  // ❌ 问题 1：SQL 注入
  const user = await db.query(`SELECT * FROM users WHERE email = '${email}'`);

  // ❌ 问题 2：明文密码比较
  if (user.password === password) {
    // ❌ 问题 3：token 没有过期时间
    const token = jwt.sign({ id: user.id }, 'hardcoded-secret');
    // ❌ 问题 4：返回了密码字段
    res.json({ user, token });
  }
}

// ✅ 修复后的版本
async function login(req: Request, res: Response) {
  const { email, password } = LoginSchema.parse(req.body);

  // ✅ 参数化查询
  const user = await db.query('SELECT * FROM users WHERE email = $1', [email]);
  if (!user) throw new AuthError('Invalid credentials');

  // ✅ bcrypt 比较
  const isValid = await bcrypt.compare(password, user.passwordHash);
  if (!isValid) throw new AuthError('Invalid credentials');

  // ✅ 有过期时间的 token
  const token = jwt.sign(
    { id: user.id, role: user.role },
    process.env.JWT_SECRET!,
    { expiresIn: '24h' }
  );

  // ✅ 排除密码字段
  const { passwordHash, ...safeUser } = user;
  res.json({ user: safeUser, token });
}
```

### 2.2 正确性审查（Correctness）

```
检查项：
☐ 逻辑是否正确？
   • 条件判断的方向对不对（if vs if not）
   • 循环的边界条件（< vs <=, 0-indexed vs 1-indexed）
   • 返回值是否符合预期

☐ 类型是否正确？
   • 返回类型与函数签名一致
   • null/undefined 是否被正确处理
   • 集合类型（Array、Map）的元素类型

☐ API 用法是否正确？
   • 使用的库版本是否兼容
   • 方法名和参数是否正确
   • 异步操作是否正确 await

☐ 业务逻辑是否符合需求？
   • 是否遗漏了需求中的某个条件
   • 是否添加了需求中没有的功能
```

**示例：AI 的逻辑错误**

```typescript
// AI 生成的分页函数 — 有逻辑错误
function paginate<T>(items: T[], page: number, size: number): T[] {
  // ❌ 错误：page 从 0 开始还是从 1 开始？逻辑不一致
  const start = page * size;     // 假设 page 从 0 开始
  const end = start + size;
  return items.slice(start, end);
}

// 调用方期望 page 从 1 开始
paginate(users, 1, 10); // ❌ 返回第 11-20 条，而不是第 1-10 条

// ✅ 修复：明确约定并保持一致
function paginate<T>(items: T[], page: number, size: number): T[] {
  // page 从 1 开始
  const startIndex = (page - 1) * size;
  const endIndex = startIndex + size;
  return items.slice(startIndex, endIndex);
}
```

**示例：AI 遗漏的边界情况**

```typescript
// AI 生成的平均值函数 — 忽略空数组
function average(numbers: number[]): number {
  // ❌ 空数组会返回 NaN（0/0）
  return numbers.reduce((sum, n) => sum + n, 0) / numbers.length;
}

// ✅ 修复：处理空数组
function average(numbers: number[]): number {
  if (numbers.length === 0) return 0;
  return numbers.reduce((sum, n) => sum + n, 0) / numbers.length;
}

// AI 生成的日期格式化 — 忽略时区
function formatDate(date: Date): string {
  // ❌ 不同服务器时区不同，结果不一致
  return date.toISOString().split('T')[0];
}

// ✅ 修复：指定时区或使用 UTC
function formatDate(date: Date): string {
  return date.toLocaleDateString('zh-CN', { timeZone: 'Asia/Shanghai' });
}
```

### 2.4 性能审查（Performance）

```
检查项：
☐ 数据库查询
   • N+1 查询问题
   • 是否缺少索引
   • 是否查询了不需要的字段

☐ 循环中的操作
   • 循环内是否有 await（串行执行）
   • 循环内是否有数据库/网络调用
   • 是否可以用 Map/Set 替代数组查找

☐ 内存使用
   • 是否有内存泄漏的风险
   • 大数据集是否分批处理
   • 是否有不必要的对象拷贝

☐ 算法复杂度
   • 时间复杂度是否合理
   • 是否有嵌套循环可以优化
```

**示例：AI 的性能问题**

```typescript
// AI 生成的代码 — N+1 查询
async function getOrderDetails(orders: Order[]) {
  for (const order of orders) {
    // ❌ 每次循环都执行数据库查询，100 个订单 = 100 次查询
    order.user = await db.users.findById(order.userId);
    order.items = await db.items.findByOrderId(order.id);
  }
  return orders;
}

// ✅ 批量查询
async function getOrderDetails(orders: Order[]) {
  const userIds = [...new Set(orders.map(o => o.userId))];
  const orderIds = orders.map(o => o.id);

  const [users, items] = await Promise.all([
    db.users.findByIds(userIds),    // 1 次查询
    db.items.findByOrderIds(orderIds), // 1 次查询
  ]);

  const userMap = new Map(users.map(u => [u.id, u]));
  const itemsByOrder = groupBy(items, 'orderId');

  return orders.map(order => ({
    ...order,
    user: userMap.get(order.userId),
    items: itemsByOrder.get(order.id) ?? [],
  }));
}
```

## 4. AI 代码中常见的隐藏 Bug 模式

### 4.1 模式一：快乐路径代码

```typescript
// AI 默认生成"一切顺利"的代码，忽略异常
// ❌ AI 生成
async function transferMoney(from: string, to: string, amount: number) {
  const sender = await db.accounts.findById(from);
  const receiver = await db.accounts.findById(to);
  sender.balance -= amount;
  receiver.balance += amount;
  await db.accounts.update(sender);
  await db.accounts.update(receiver);
}

// ✅ 需要补充
async function transferMoney(from: string, to: string, amount: number) {
  if (amount <= 0) throw new ValidationError('Amount must be positive');

  const sender = await db.accounts.findById(from);
  if (!sender) throw new NotFoundError('Sender not found');
  if (sender.balance < amount) throw new InsufficientFundsError();

  const receiver = await db.accounts.findById(to);
  if (!receiver) throw new NotFoundError('Receiver not found');

  // 使用事务确保原子性
  await db.transaction(async (tx) => {
    await tx.accounts.update(from, { balance: sender.balance - amount });
    await tx.accounts.update(to, { balance: receiver.balance + amount });
  });
}
```

### 4.2 模式二：时区和日期问题

```typescript
// ❌ AI 生成 — 时区隐患
function isExpired(expiryDate: string): boolean {
  return new Date(expiryDate) < new Date(); // 服务器时区可能不同
}

// ✅ 明确使用 UTC
function isExpired(expiryDate: string): boolean {
  return new Date(expiryDate).getTime() < Date.now();
}
```

### 4.3 模式三：异步错误处理

```typescript
// ❌ AI 生成 — 异步操作没有错误处理
async function syncData() {
  const data = await fetch('/api/data');
  const json = await data.json(); // 如果 fetch 失败呢？
  saveToDatabase(json); // 缺少 await
}

// ✅ 完整的异步错误处理
async function syncData() {
  try {
    const response = await fetch('/api/data');
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}: ${response.statusText}`);
    }
    const json = await response.json();
    await saveToDatabase(json);
  } catch (error) {
    logger.error('Data sync failed', { error });
    throw error;
  }
}
```

### 4.4 模式四：不安全的类型断言

```typescript
// ❌ AI 生成 — 类型断言掩盖了潜在错误
const user = getUser(id) as User; // 如果返回 undefined 呢？
console.log(user.name); // 运行时崩溃

// ✅ 安全的类型守卫
const user = getUser(id);
if (!user) throw new NotFoundError('User not found');
console.log(user.name); // 安全
```

## 6. 常见误区

| 错误 | 为什么危险 | 正确做法 |
|------|-----------|----------|
| Tab 狂按不看 | 引入安全漏洞和 bug | 每次接受至少扫一眼 |
| "AI 写的应该没问题" | 你对代码负最终责任 | 按清单系统审查 |
| 只看功能不看安全 | 数据泄露、被攻击 | 安全是第一审查维度 |
| 不写测试就提交 | 线上 bug 难以追踪 | 至少验证核心路径 |
| 审查时只看快乐路径 | 边界情况是 bug 高发区 | 专门检查 null、空、并发 |
| 复制 AI 代码不理解 | 无法维护和调试 | 确保理解每一行 |
| 不检查依赖版本 | 过时 API 可能有漏洞 | 确认库版本和用法 |

## 7. 工程建议

1. **建立团队级审查清单**：基于本课的五维度清单，结合项目特点定制一份团队共享的审查清单。把它贴在 PR 模板中，让每次 AI 生成的代码变更都经过标准化审查。
2. **安全审查优先级最高**：在审查流程中，始终把安全性放在第一位。SQL 注入、XSS、密码处理、敏感信息泄露这些问题一旦上线，修复成本远高于功能 bug。
3. **为 AI 代码写测试**：AI 生成的核心业务代码，至少覆盖成功路径和主要失败路径的测试。测试不仅是验证手段，也是理解 AI 代码逻辑的最佳方式——如果写不出测试，说明你还没理解这段代码。
4. **记录 AI 的典型错误模式**：团队内部维护一份"AI 常犯错误"文档（如快乐路径代码、N+1 查询、缺少 null 检查），新人和老人都可以在审查时快速对照。

## 8. 总结

本课要点：

1. **必须审查**：AI 代码 90% 正确，但那 10% 可能包含严重问题
2. **五维度检查**：安全 → 正确性 → 边界 → 性能 → 风格
3. **隐藏 Bug 模式**：快乐路径、时区问题、异步错误、类型断言
4. **审查流程**：快速扫描 → 逐行审查 → 运行验证
5. **责任归属**：你对代码负最终责任，不是 AI

### 练习 1：Bug 猎手

**思路**：让 AI 生成三个函数，然后用五维度审查清单逐项检查。AI 的典型问题是：安全维度（SQL 注入、明文密码）、边界维度（null/空数组）、性能维度（N+1 查询）。审查时按"安全 → 正确性 → 边界 → 性能 → 风格"的优先级检查。

**答案**：

**1. 用户注册函数的典型问题：**

```typescript
// AI 可能生成的有问题的版本
async function register(req: Request, res: Response) {
  const { email, password, name } = req.body;

  // ❌ 安全：SQL 注入
  const existing = await db.query(`SELECT * FROM users WHERE email = '${email}'`);

  // ❌ 安全：明文存储密码
  const user = await db.query(
    `INSERT INTO users (email, password, name) VALUES ('${email}', '${password}', '${name}')`
  );

  // ❌ 安全：token 无过期时间
  const token = jwt.sign({ id: user.id }, 'secret');

  res.json({ user, token });
}
```

| 问题 | 维度 | 严重程度 | 修复方案 |
|------|------|---------|---------|
| SQL 注入（字符串拼接） | 安全 | 🔴 严重 | 改用参数化查询 |
| 明文存储密码 | 安全 | 🔴 严重 | 使用 bcrypt.hash |
| 硬编码 JWT secret | 安全 | 🔴 严重 | 从环境变量读取 |
| token 无过期时间 | 安全 | 🟡 中等 | 添加 expiresIn |
| 未验证邮箱格式 | 边界 | 🟡 中等 | 使用 Zod 验证 |
| 未检查 email 唯一性 | 正确性 | 🟡 中等 | 先查重再插入 |
| 返回了密码字段 | 安全 | 🟡 中等 | 排除 passwordHash |

**2. 订单查询函数的典型问题：**

```typescript
// AI 可能生成的有性能问题的版本
async function getOrders(userId: string) {
  const orders = await prisma.order.findMany({ where: { userId } });

  // ❌ 性能：N+1 查询
  for (const order of orders) {
    order.user = await prisma.user.findUnique({ where: { id: order.userId } });
    order.items = await prisma.orderItem.findMany({ where: { orderId: order.id } });
  }

  return orders;
}
```

| 问题 | 维度 | 严重程度 | 修复方案 |
|------|------|---------|---------|
| N+1 查询（循环内 await） | 性能 | 🔴 严重 | 用 include 或批量查询 |
| 无分页 | 边界 | 🟡 中等 | 添加 skip/take 参数 |
| 未检查 userId 有效性 | 边界 | 🟢 轻微 | 验证 userId 格式 |

**3. 文件上传处理函数的典型问题：**

| 问题 | 维度 | 严重程度 | 修复方案 |
|------|------|---------|---------|
| 未限制文件大小 | 安全 | 🔴 严重 | 设置 multer limits |
| 未检查文件类型 | 安全 | 🔴 严重 | 验证 MIME type |
| 未过滤文件名 | 安全 | 🔴 严重 | 生成随机文件名，防止路径穿越 |
| 无并发上传限制 | 边界 | 🟡 中等 | 添加 rate limiting |

**要点**：
- 安全问题永远是第一优先级——SQL 注入、密码处理、文件上传是 AI 最常犯的三类安全错误
- AI 生成的代码通常只覆盖"快乐路径"，边界情况需要你主动补充
- 性能问题（N+1 查询）在数据量小时不会暴露，但上线后会成为定时炸弹
- 审查时按"安全 → 正确性 → 边界 → 性能 → 风格"的顺序，效率最高

### 练习 2：安全审查实战

**思路**：让 AI 生成完整的登录/注册模块，然后专门从安全角度审查。重点关注四条线：SQL 注入、密码处理、JWT 实现、错误信息泄露。

**答案**：

AI 生成的登录/注册模块中常见的安全问题清单：

**SQL 注入风险：**
```typescript
// ❌ 常见问题：字符串拼接
const user = await db.query(`SELECT * FROM users WHERE email = '${email}'`);

// ✅ 修复：参数化查询
const user = await prisma.user.findUnique({ where: { email } });
```

**密码处理问题：**
```typescript
// ❌ 常见问题
if (user.password === inputPassword) { ... }  // 明文比较
const hash = md5(password);                     // 弱哈希
const hash = await bcrypt.hash(password, 4);    // salt rounds 太低

// ✅ 修复
const isValid = await bcrypt.compare(inputPassword, user.passwordHash);
const hash = await bcrypt.hash(password, 12);   // salt rounds >= 12
```

**JWT 实现问题：**
```typescript
// ❌ 常见问题
const token = jwt.sign({ id: user.id }, 'hardcoded-secret');  // 硬编码
const token = jwt.sign({ id: user.id }, secret);               // 无过期时间
const token = jwt.sign({ id: user.id, password: user.password }, secret); // 暴露敏感信息

// ✅ 修复
const token = jwt.sign(
  { id: user.id, role: user.role },
  process.env.JWT_SECRET!,
  { expiresIn: '24h', algorithm: 'HS256' }
);
```

**错误信息泄露：**
```typescript
// ❌ 常见问题
res.status(401).json({ error: '密码错误' });  // 暴露"用户存在"
res.status(500).json({ error: error.message }); // 暴露内部错误详情

// ✅ 修复：统一错误信息
res.status(401).json({ error: '邮箱或密码错误' }); // 不区分邮箱不存在和密码错误
res.status(500).json({ error: '服务器内部错误' });  // 不暴露内部详情
```

**要点**：
- 安全审查四条线：注入 → 密码 → Token → 信息泄露
- 登录失败时统一返回"邮箱或密码错误"，不要告诉攻击者是哪个错了
- JWT secret 必须从环境变量读取，且不能有默认值
- bcrypt 的 salt rounds 至少 12，低于 10 不安全

### 练习 3：创建项目审查清单

**思路**：基于本课的通用五维度清单，结合项目特点做裁剪和补充。核心原则是：保留通用检查项，删除不适用的，添加项目特有的。

**答案**：

以一个 Express + Prisma + PostgreSQL 项目为例：

```markdown
# AI 生成代码审查清单

## 1. 安全性 🔴（每次必查）
- [ ] SQL 查询使用 Prisma ORM（禁止原生 SQL 字符串拼接）
- [ ] 密码使用 bcrypt（salt rounds >= 12），不存储明文
- [ ] JWT secret 从环境变量读取，token 有过期时间
- [ ] 用户输入使用 Zod 验证，不在业务层处理原始 req.body
- [ ] 错误响应不泄露内部信息（统一"服务器内部错误"）
- [ ] 敏感接口有认证中间件保护
- [ ] 文件上传有类型和大小限制

## 2. 正确性 🟡
- [ ] 函数返回类型与 Prisma model 一致
- [ ] null/undefined 有处理（Prisma 返回 null 而非 undefined）
- [ ] 异步操作正确 await
- [ ] 业务逻辑符合需求描述

## 3. 边界情况 🟡
- [ ] 空数组/空字符串有处理
- [ ] 分页参数有默认值和上限（pageSize <= 100）
- [ ] 唯一约束冲突有友好错误提示
- [ ] 日期操作使用 UTC 或明确时区

## 4. 性能 🟢
- [ ] 无 N+1 查询（使用 include 或批量查询）
- [ ] 循环内无 await（使用 Promise.all）
- [ ] 大量数据有分页处理

## 5. 风格 🟢
- [ ] 使用 AppError 子类处理错误，不用 try-catch 吞错误
- [ ] 命名符合项目规范（camelCase 函数，kebab-case 文件）
- [ ] 无 any 类型
- [ ] 函数长度不超过 50 行
```

**要点**：
- 🔴 = 每次 Tab 接受后必查，🟡 = 每个 PR 必查，🟢 = 定期抽查
- 项目特有的检查项比通用清单更有价值——比如"禁止原生 SQL"是 Prisma 项目的强约束
- 清单应该放在 PR 模板中，让每次代码变更都经过标准化审查
- 清单不是一成不变的，随着项目演进和踩坑经验持续更新
