# 01 - 团队 AI 编程规范设计

> 建立团队统一的 AI 辅助编程标准，让 AI 成为团队的倍增器而非混乱源

## 场景引入

团队接入 AI 编程工具三个月后，问题开始浮现：张三用 Cursor 写的代码风格和李四用 Copilot 生成的完全不同，review 时互相看不懂；王五把公司 API 密钥直接贴进了 Prompt，代码被提交到了公开仓库；更头疼的是，每个人都说自己摸索出了一套"好用的 Prompt"，但这些经验随着人员流动全部丢失。技术负责人意识到，没有统一的 AI 编程规范，AI 工具不仅没有提效，反而在制造新的混乱。

## 学习目标

- 理解为什么团队需要统一的 AI 编程规范
- 掌握 AI 工具选型的方法论
- 学会设计和管理团队 Prompt 库
- 制定适合团队的 AI 编程编码规范

## 1. 为什么需要团队 AI 编程规范

### 1.1 无规范的痛点

```
团队成员各自使用不同 AI 工具
          │
          ▼
┌─────────────────────────────────┐
│  · 代码风格不一致               │
│  · Prompt 质量参差不齐          │
│  · 安全风险无人管控             │
│  · 知识无法复用沉淀             │
│  · 效果无法度量对比             │
└─────────────────────────────────┘
          │
          ▼
    AI 反而降低团队效率
```

### 1.2 规范化后的收益

| 维度 | 无规范 | 有规范 |
|------|--------|--------|
| 代码质量 | 风格混乱，review 困难 | 统一标准，自动化检查 |
| 安全性 | 密钥泄露、漏洞引入 | 自动检测，合规保障 |
| 效率 | 重复造轮子 | Prompt 库复用 |
| 知识 | 散落在个人电脑 | 结构化团队资产 |
| 度量 | 凭感觉评估 | 数据驱动决策 |

         │             │              │
         └─────────────┼─────────────┘

### 2.2 工具对比表

| 工具 | 适用场景 | 安全性 | 成本 | 定制化 |
|------|---------|--------|------|--------|
| GitHub Copilot | 通用编码 | 中 | $19/月/人 | 低 |
| Cursor | 全栈开发 | 中 | $20/月/人 | 中 |
| Cline + 本地模型 | 高安全要求 | 高 | 硬件成本 | 高 |
| Continue.dev | 混合部署 | 高 | 免费 | 高 |
| 企业私有部署 | 金融/政府 | 最高 | 高 | 最高 |

### 2.3 选型决策流程

```python
def select_ai_tool(team_context: dict) -> str:
    """团队 AI 工具选型决策函数"""

    # 第一步：安全合规要求
    if team_context["data_classification"] == "机密":
        return "本地模型 + 私有部署"

    # 第二步：团队规模与预算
    if team_context["team_size"] < 5 and team_context["budget"] < 500:
        return "Cursor 或 Continue.dev"

    # 第三步：技术栈匹配
    if team_context["primary_language"] == "Python":
        return "GitHub Copilot（Python 优化最佳）"

    # 第四步：已有基础设施
    if team_context["has_github_enterprise"]:
        return "GitHub Copilot Enterprise"

    return "GitHub Copilot Business（默认推荐）"
```

## 6. 常见误区

### ❌ 错误 1：完全放任 AI 生成代码

```typescript
// AI 生成了看似正确但有安全隐患的代码
const query = `SELECT * FROM users WHERE id = ${userId}`;
// SQL 注入风险！必须人工审查并改用参数化查询
```

### ❌ 错误 2：Prompt 库没有版本管理

```
问题：Prompt 被随意修改，导致同一天不同人使用同一 Prompt
却得到完全不同的输出质量

解决：使用 Git 管理 Prompt，每次修改需要 PR review
```

### ❌ 错误 3：忽略团队成员的 AI 技能差异

```
错误做法：一刀切要求所有人使用相同的复杂 Prompt

正确做法：
  - 初级：使用预置 Prompt 模板
  - 中级：能够修改和组合 Prompt
  - 高级：能够创建和优化 Prompt
```

### ❌ 错误 4：不设安全红线

```bash
# 绝对禁止的操作
git commit -m "feat: add API key"  # AI 可能建议直接硬编码
# 必须使用环境变量或密钥管理服务
```

## 7. 工程建议

1. **先试点再推广**：不要一次性全团队铺开 AI 规范，先选 2-3 个志愿者项目跑通流程，收集真实反馈后再推广，避免"规范写了没人用"的尴尬。
2. **Prompt 库用 Git 管理**：把 Prompt 当代码管，每次修改走 PR review，这样既能追溯历史版本，也能让团队在 review Prompt 的过程中互相学习。
3. **安全红线必须自动化**：靠人工记住"不能把密钥提交到仓库"是不可靠的，必须在 CI/CD 中配置 Gitleaks 等工具自动拦截，把安全检查从"靠自觉"变成"靠系统"。
4. **规范文档控制在 10 页以内**：核心规范要精简可读，详细内容放附录或模板中。提供检查清单替代长篇文字，让开发者能在 5 分钟内了解关键要求。

## 参考答案

### 练习 1：工具选型决策

**思路**：根据课程中的三维决策框架（安全、预算、技术栈），结合团队实际情况进行匹配。安全要求高的团队必须优先考虑本地化部署，小团队优先考虑性价比。

**答案**：

**团队 1：5 人创业团队，全栈 TypeScript，预算有限**

推荐工具：**Cursor（$20/月/人）或 Continue.dev（免费）**

理由：
- 团队规模小，不需要企业级管理功能，Copilot Business 的统一管理优势体现不出来
- Cursor 内置 AI 对话 + 代码编辑一体化体验，全栈开发效率高
- 预算有限时 Continue.dev + 本地 Ollama 模型是零成本方案
- TypeScript 技术栈在 Cursor 中的补全效果优秀

**团队 2：50 人金融公司后端团队，Java 为主，数据安全要求极高**

推荐工具：**企业私有部署（Azure OpenAI + Continue.dev）或 Cline + 本地模型**

理由：
- 金融数据安全是硬性约束，代码不能发送到外部服务器
- Azure OpenAI 提供私有化部署，数据不离开企业网络
- Continue.dev 支持混合部署，连接私有模型端点
- 50 人规模需要统一管理、审计日志、权限控制等企业功能
- Java 生态在 GitHub Copilot 中优化较好，但安全优先级更高

**团队 3：20 人互联网公司，Python + Go 混合技术栈，已使用 GitLab**

推荐工具：**GitLab Duo + Cursor 混合使用**

理由：
- 已使用 GitLab，GitLab Duo 是原生集成方案，无需额外配置
- GitLab Duo 的 Code Suggestions 直接在 MR 中提供 AI 审查
- Python + Go 混合栈需要工具对两种语言都有良好支持
- Cursor 作为补充工具用于复杂的代码生成和重构任务
- 20 人规模可以用 GitLab 群组统一管理 API Key

**要点**：
- 安全合规是硬约束，不满足安全要求的工具直接排除，不看性价比
- 小团队优先选体验好、上手快的工具；大团队优先选可管理、可审计的工具
- 混合技术栈场景下，单一工具可能无法覆盖所有语言，考虑组合使用
- 已有基础设施（如 GitLab）的集成成本是重要考量因素

### 练习 2：Prompt 模板设计

**思路**：Prompt 模板需要包含完整的元信息（便于管理和检索）、明确的约束条件（控制输出质量）、标准化的输出格式（便于集成到工作流）。关键是变量定义要清晰，示例要具体。

**答案**：

```markdown
# Prompt: RESTful API 生成 OpenAPI 3.0 文档

## 元信息
- **ID**: PROMPT-DOC-001
- **版本**: 1.0.0
- **作者**: @team-lead
- **适用场景**: 为已有的 Express/Fastify 路由代码生成 OpenAPI 3.0 规范文档
- **适用模型**: GPT-4o / Claude 3.5 Sonnet
- **最后更新**: 2026-06-22

## Prompt 内容

你是一位 API 文档专家。请根据以下路由代码，生成完整的 OpenAPI 3.0 规范文档。

**路由代码**:
\`\`\`typescript
{{route_code}}
\`\`\`

**约束条件**:
1. 使用 OpenAPI 3.0.3 规范
2. 所有端点必须包含 description 和 summary
3. 请求参数必须包含类型、是否必填、示例值
4. 响应必须包含成功（200/201）和错误（400/401/404/500）的 Schema
5. 使用 components/schemas 复用类型定义
6. 包含 securitySchemes 定义认证方式

**输出格式**:
\`\`\`yaml
# 完整的 OpenAPI 3.0 YAML 文档
\`\`\`

## 变量说明

| 变量 | 类型 | 必填 | 说明 |
|------|------|------|------|
| route_code | code | 是 | Express/Fastify 路由文件的完整代码 |

## 使用示例

### 示例 1
**输入**:
> 粘贴 src/routes/users.ts 的代码（包含 GET /users、POST /users、GET /users/:id）

**期望输出**:
\`\`\`yaml
openapi: 3.0.3
info:
  title: User API
  version: 1.0.0
paths:
  /api/users:
    get:
      summary: 获取用户列表
      description: 分页获取用户列表，支持按角色筛选
      parameters:
        - name: page
          in: query
          schema: { type: integer, default: 1 }
        # ... 完整输出
\`\`\`

### 示例 2
**输入**:
> 粘贴 src/routes/orders.ts 的代码

**期望输出**:
> 完整的 OpenAPI YAML，包含订单相关的所有端点定义

## 效果评估

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 采纳率 | ≥ 70% | 生成的文档可直接使用或只需微调 |
| Schema 完整性 | 100% | 所有端点都有对应的 Schema 定义 |
| 示例值可用性 | ≥ 80% | 示例值可直接用于测试 |

## 版本历史

| 版本 | 日期 | 变更说明 |
|------|------|---------|
| 1.0.0 | 2026-06-22 | 初始版本 |
```

**要点**：
- 元信息中的 ID、版本、作者便于 Prompt 库的检索和管理
- 变量用 `{{variable}}` 占位符标记，支持工具自动化填充
- 约束条件明确指定 OpenAPI 版本号和必须包含的字段，避免 AI 输出不一致
- 效果评估指标量化，便于后续迭代优化 Prompt

### 练习 3：规范文档编写

**思路**：规范文档要具体、可执行、可验证。使用 MUST/SHOULD/MAY 区分强制和建议等级。安全红线必须明确列出，不能模糊表述。

**答案**：

```markdown
# 团队 AI 编程使用规范 v1.0

## 1. 允许使用的工具

### 允许列表
| 工具 | 用途 | 配置要求 |
|------|------|---------|
| GitHub Copilot Business | 代码补全 | 统一组织账号，禁用个人 Key |
| Cursor Pro | 复杂代码生成 | 仅用于非敏感项目 |

### 禁止列表
- 禁止使用个人 API Key 调用任何 AI 服务
- 禁止使用免费公共 AI API（如 ChatGPT 网页版）处理公司代码
- 禁止安装未通过安全审查的 AI 插件

## 2. AI 代码标注要求

所有 AI 生成或 AI 辅助编写的代码，必须在函数/类级别添加标注：

\`\`\`typescript
/**
 * @ai-assisted GitHub Copilot
 * @ai-reviewed-by @zhangsan
 * @ai-reviewed-at 2026-06-22
 * @ai-modifications 补充了错误处理和边界检查
 */
\`\`\`

Git 提交信息中必须注明：
\`\`\`
feat(module): 功能描述

AI-Assisted: yes
AI-Tool: GitHub Copilot v2
AI-Reviewed: yes
\`\`\`

## 3. 安全红线清单

1. **MUST NOT** 硬编码任何密钥、密码、Token 到代码中
2. **MUST NOT** 将 .env、secrets/、credentials/ 等文件提交到仓库
3. **MUST NOT** 使用字符串拼接构建 SQL 查询，必须使用参数化查询
4. **MUST NOT** 在 Prompt 中包含客户数据、用户隐私信息或内部 API 密钥
5. **MUST NOT** 将 AI 生成的代码直接合并到 main 分支，必须经过人工 Review
6. **MUST NOT** 使用未经许可证审查的 AI 推荐依赖（GPL/AGPL 需法务确认）
7. **MUST** 在 CI 中配置 Gitleaks 密钥扫描，每次 PR 自动执行
8. **MUST** 配置 .copilotignore 排除敏感文件

## 4. Review 流程说明

\`\`\`
PR 提交 → CI 自动检查 → AI 自动审查 → 人工 Review → 合并
\`\`\`

**人工 Review 要求**：
- AI 生成代码必须至少 1 位 reviewer 批准
- 安全相关代码（认证、加密、权限）必须 2 位 reviewer 批准
- 架构变更必须 Tech Lead 审批

**Review 检查重点**：
- [ ] AI 标注完整
- [ ] 无硬编码密钥
- [ ] 输入验证完整
- [ ] 错误处理正确
- [ ] 无 AI 幻觉（虚构的 API 或函数）
- [ ] 测试覆盖关键路径
```

**要点**：
- 安全红线用 MUST NOT 明确禁止，不留模糊空间，每条都可以在 CI 中自动化检查
- AI 代码标注不仅是注释，还要在 Git 提交信息中记录，便于追溯和审计
- Review 流程分层：普通代码 1 人 Review，安全代码 2 人 Review，架构变更 Tech Lead 审批
- 规范文档本身也要有版本号和变更记录，便于后续迭代
