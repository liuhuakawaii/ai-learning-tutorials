# 03 - 知识沉淀与 Prompt 管理

> 将个人经验转化为团队资产，让 AI 编程能力持续积累和传承

## 场景引入

团队里公认 AI 编程用得最好的老刘提了离职。交接时大家才发现，他积累了上百条精心调试过的 Prompt、一套针对公司代码库的 AI 审查规则、以及无数次踩坑后总结的"什么时候该信 AI、什么时候不该信"的直觉——这些全都存在他个人电脑的笔记软件里，无法导出、无法共享。新人入职后，同样的坑要重新踩一遍，同样的 Prompt 要重新摸索一遍。你意识到：个人的 AI 能力如果不沉淀为团队资产，团队永远在原地踏步。

## 学习目标

- 理解知识沉淀在 AI 编程中的重要性
- 掌握结构化知识文档的设计方法
- 学会 Prompt 库的版本管理和效果评估
- 建立团队知识共享和传承机制

## 3. Prompt 库管理系统

### 3.1 Prompt 元数据设计

```typescript
interface PromptMetadata {
  id: string;
  name: string;
  version: string;
  category: string;
  tags: string[];
  author: string;
  createdAt: string;
  updatedAt: string;

  // 适用性
  supportedModels: string[];
  supportedLanguages: string[];
  taskType: 'generation' | 'review' | 'refactoring' | 'testing' | 'documentation';

  // 效果指标
  metrics: {
    usageCount: number;
    acceptanceRate: number;      // AI 输出被直接采纳的比率
    modificationRate: number;    // 需要修改的比率
    averageQuality: number;      // 平均质量评分 1-5
    lastUsedAt: string;
  };

  // 审核状态
  review: {
    status: 'draft' | 'review' | 'approved' | 'deprecated';
    reviewedBy?: string;
    reviewedAt?: string;
  };
}

interface Prompt {
  metadata: PromptMetadata;
  content: string;
  variables: PromptVariable[];
  examples: PromptExample[];
  notes: string;
}

interface PromptVariable {
  name: string;
  description: string;
  type: 'string' | 'number' | 'boolean' | 'code';
  required: boolean;
  defaultValue?: string;
}

interface PromptExample {
  input: Record<string, string>;
  expectedOutput: string;
  actualOutput?: string;
  quality?: number;
}
```

### 3.3 Prompt 效果评估脚本

```python
# scripts/evaluate_prompts.py
import json
from pathlib import Path
from datetime import datetime, timedelta

class PromptEvaluator:
    def __init__(self, prompts_dir: str, feedback_file: str):
        self.prompts_dir = Path(prompts_dir)
        self.feedback = self._load_feedback(feedback_file)

    def _load_feedback(self, path: str) -> list[dict]:
        """加载用户反馈数据"""
        with open(path, 'r', encoding='utf-8') as f:
            return json.load(f)

    def calculate_metrics(self, prompt_id: str) -> dict:
        """计算单个 Prompt 的效果指标"""
        feedbacks = [f for f in self.feedback if f['prompt_id'] == prompt_id]

        if not feedbacks:
            return {'status': 'no_data'}

        total = len(feedbacks)
        accepted = sum(1 for f in feedbacks if f['action'] == 'accepted')
        modified = sum(1 for f in feedbacks if f['action'] == 'modified')
        rejected = sum(1 for f in feedbacks if f['action'] == 'rejected')

        return {
            'usage_count': total,
            'acceptance_rate': accepted / total,
            'modification_rate': modified / total,
            'rejection_rate': rejected / total,
            'average_quality': sum(f['quality'] for f in feedbacks) / total,
            'last_used': max(f['timestamp'] for f in feedbacks),
        }

    def generate_report(self) -> str:
        """生成 Prompt 库效果报告"""
        report = ["# Prompt 库效果报告\n"]
        report.append(f"生成时间: {datetime.now().isoformat()}\n")

        for prompt_file in self.prompts_dir.glob("**/*.md"):
            prompt_id = prompt_file.stem
            metrics = self.calculate_metrics(prompt_id)

            if metrics.get('status') == 'no_data':
                continue

            report.append(f"\n## {prompt_id}")
            report.append(f"- 使用次数: {metrics['usage_count']}")
            report.append(f"- 采纳率: {metrics['acceptance_rate']:.1%}")
            report.append(f"- 修改率: {metrics['modification_rate']:.1%}")
            report.append(f"- 平均质量: {metrics['average_quality']:.1f}/5.0")

            # 预警
            if metrics['acceptance_rate'] < 0.5:
                report.append(f"- ⚠️ 采纳率过低，建议优化")
            if metrics['rejection_rate'] > 0.3:
                report.append(f"- 🔴 拒绝率过高，建议废弃或重写")

        return '\n'.join(report)

    def recommend_actions(self) -> list[dict]:
        """基于数据推荐操作"""
        actions = []

        for prompt_file in self.prompts_dir.glob("**/*.md"):
            prompt_id = prompt_file.stem
            metrics = self.calculate_metrics(prompt_id)

            if metrics.get('status') == 'no_data':
                continue

            if metrics['acceptance_rate'] < 0.3:
                actions.append({
                    'prompt_id': prompt_id,
                    'action': 'deprecate',
                    'reason': '采纳率低于 30%',
                })
            elif metrics['acceptance_rate'] > 0.8 and metrics['usage_count'] > 50:
                actions.append({
                    'prompt_id': prompt_id,
                    'action': 'promote',
                    'reason': '高质量高使用量，推荐为标准模板',
                })

        return actions


if __name__ == '__main__':
    evaluator = PromptEvaluator(
        prompts_dir='./prompts',
        feedback_file='./data/feedback.json'
    )
    print(evaluator.generate_report())
```

## 6. 常见误区

### ❌ 错误 1：知识文档只写不更新

```
问题：文档写完就再也没人维护，内容过时

解决：
- 文档绑定代码版本，代码更新时文档同步更新
- 设置季度审查提醒
- 将文档更新纳入 Definition of Done
```

### ❌ 错误 2：Prompt 库没有反馈机制

```
问题：Prompt 只管发布不管效果，好用不好用都不知道

解决：
- 每次使用后收集反馈（1-5 分评分）
- 定期分析采纳率、修改率
- 淘汰低质量 Prompt，推广高质量 Prompt
```

### ❌ 错误 3：知识孤岛

```
问题：知识散落在各处，Slack 里、Wiki 里、个人笔记里

解决：
- 建立统一的知识库仓库
- 制定知识录入流程
- 搜索和导航要便利
```

### ❌ 错误 4：只关注 Prompt 不关注经验

```
问题：只收集 Prompt，忽略使用经验和踩坑记录

解决：知识库应包含
- Prompt 模板（直接可用）
- 最佳实践（方法论）
- 踩坑记录（避坑指南）
- 工具配置（环境搭建）
```

## 7. 工程建议

1. **知识沉淀要"轻"不要"重"**：不要追求完美的知识库结构，先从"踩坑即记录"开始，一个 Markdown 文件加上标签就够了。等积累到一定规模再考虑分类和模板化。
2. **Prompt 效果必须量化**：每次使用 Prompt 后记录采纳率和质量评分，用数据淘汰低质量 Prompt，而不是凭感觉。没有数据的 Prompt 库只是一个"文本收藏夹"。
3. **自动化知识收集**：通过 GitHub Actions 在 PR 合并时自动提取 AI 相关知识（使用的 Prompt、审查发现的问题），减少手动录入的负担，让知识沉淀融入日常工作流。
4. **绑定代码版本更新**：知识文档必须和代码版本关联，代码更新时触发文档审查提醒，避免文档内容过时误导后来者。

**知识条目元数据字段设计**：

```typescript
interface KnowledgeEntry {
  id: string;                    // 唯一标识，如 KB-SEC-001
  title: string;                 // 标题
  category: 'prompt' | 'best-practice' | 'pitfall';  // 分类
  tags: string[];                // 标签，如 ['typescript', 'security', 'sql']
  author: string;                // 作者
  createdAt: string;             // 创建日期
  updatedAt: string;             // 最后更新
  difficulty: 'beginner' | 'intermediate' | 'advanced';  // 难度
  applicableModels: string[];    // 适用模型
  applicableLanguages: string[]; // 适用语言
  status: 'draft' | 'approved' | 'deprecated';  // 状态
  usageCount: number;            // 使用次数
  qualityScore: number;          // 质量评分 1-5
}
```

**要点**：
- 一级分类按用途划分（Prompt / 最佳实践 / 踩坑），二级分类按领域划分（安全 / 逻辑 / 性能）
- 元数据字段支持多维检索（按标签、语言、模型、难度）和自动化分析（使用次数、质量评分）
- templates 目录提供标准化模板，降低知识录入门槛

### 练习 2：编写 Prompt 模板

**思路**：选择"单元测试生成"这个常见场景，设计一个包含完整元信息、变量定义、使用示例和效果评估标准的 Prompt 模板。

**答案**：

```markdown
# Prompt: 单元测试生成

## 元信息
- **ID**: PROMPT-TEST-001
- **版本**: 1.0.0
- **作者**: @qa-lead
- **适用场景**: 为已有的 TypeScript/JavaScript 函数生成 Vitest 单元测试
- **适用模型**: GPT-4o / Claude 3.5 Sonnet
- **最后更新**: 2026-06-22

## Prompt 内容

你是一位资深测试工程师。请为以下函数生成完整的单元测试。

**函数代码**:
\`\`\`typescript
{{function_code}}
\`\`\`

**测试框架**: {{test_framework}}（默认 Vitest）

**约束条件**:
1. 测试必须覆盖正常路径、边界条件、错误处理三个维度
2. 每个测试用例必须有清晰的中文描述（it('应该...')）
3. Mock 所有外部依赖（数据库、API、文件系统）
4. 测试必须独立运行，不依赖执行顺序
5. 包含类型边界测试（null、undefined、空数组、超大值）

**输出格式**:
\`\`\`typescript
import { describe, it, expect, vi } from '{{test_framework}}';
// Mock 声明
// 测试用例
\`\`\`

## 变量说明

| 变量 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| function_code | code | 是 | - | 需要生成测试的函数代码 |
| test_framework | string | 否 | vitest | 测试框架，支持 vitest / jest |
| coverage_level | string | 否 | standard | 覆盖级别：basic / standard / thorough |

## 使用示例

### 示例 1：工具函数测试
**输入**:
> 函数代码：一个 parseQueryString 函数，将 URL 查询字符串解析为对象

**期望输出**:
\`\`\`typescript
import { describe, it, expect } from 'vitest';
import { parseQueryString } from './queryString';

describe('parseQueryString', () => {
  it('应该解析基本的键值对', () => {
    expect(parseQueryString('?name=alice&age=30')).toEqual({ name: 'alice', age: '30' });
  });

  it('应该处理没有 ? 前缀的字符串', () => {
    expect(parseQueryString('name=alice')).toEqual({ name: 'alice' });
  });

  it('应该返回空对象当输入为空字符串', () => {
    expect(parseQueryString('')).toEqual({});
  });

  it('应该解码 URL 编码的字符', () => {
    expect(parseQueryString('?name=%E4%B8%AD%E6%96%87')).toEqual({ name: '中文' });
  });

  it('应该处理重复的 key，取最后一个值', () => {
    expect(parseQueryString('?a=1&a=2')).toEqual({ a: '2' });
  });
});
\`\`\`

| 覆盖完整性 | ≥ 80% | 正常路径 + 边界条件 + 错误处理 |
| Mock 正确性 | ≥ 90% | Mock 声明正确，不遗漏外部依赖 |
| 可运行性 | 100% | 生成的测试可以直接运行通过 |

## 版本历史

| 版本 | 日期 | 变更说明 |

```

**要点**：
- 变量 `coverage_level` 支持 basic/thorough 等级别切换，适应不同场景需求
- 效果评估中的"可运行性"要求 100%，意味着生成的测试必须能直接执行，不能有语法错误
- 示例包含工具函数和 Service 函数两种典型场景，覆盖简单到复杂的测试生成

### 练习 3：知识评估实践

**思路**：从 Prompt 清晰度、约束完整性、AI 输出质量、改进建议四个维度系统评估。好的 Prompt 应该有明确的输入输出定义、充分的边界条件约束、以及可验证的质量标准。

**答案**：

**评估报告**：

```markdown
# Prompt 评估报告：数组去重函数

## 评估对象
\```
请帮我写一个函数，功能是：输入一个数组，返回去重后的结果。

要求：
1. 保持原数组顺序
2. 时间复杂度 O(n)
3. 支持对象数组去重（按 JSON 字符串比较）
\```

## 1. Prompt 清晰度评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 功能描述 | ⭐⭐⭐⭐ | "输入数组返回去重结果"明确 |
| 输入定义 | ⭐⭐ | 未说明数组元素类型（number? string? mixed?） |
| 输出定义 | ⭐⭐ | 未说明返回新数组还是修改原数组 |
| 语言/框架 | ⭐ | 未指定编程语言 |

**总评**: 清晰度 3/5 — 功能目标明确，但输入输出的类型和行为定义不够精确。

## 2. 约束完整性评估

| 维度 | 评分 | 说明 |
|------|------|------|
| 顺序约束 | ⭐⭐⭐⭐⭐ | "保持原数组顺序"明确 |
| 性能约束 | ⭐⭐⭐⭐ | "O(n)"明确，但未说明空间复杂度 |
| 对象去重 | ⭐⭐⭐ | "按 JSON 字符串比较"可行但有局限 |
| 边界条件 | ⭐ | 未说明空数组、null/undefined 元素、嵌套对象等处理方式 |

**总评**: 约束完整性 2.5/5 — 有性能和功能约束，但缺少关键边界条件。

**缺失的约束**：
- 空数组输入应返回什么？
- 数组中包含 `null`、`undefined` 如何处理？
- 嵌套对象的 JSON 序列化顺序问题（`{a:1, b:2}` vs `{b:2, a:1}`）
- 是否需要支持自定义比较函数？

## 3. AI 输出质量预测

使用此 Prompt 调用 GPT-4o，预期会得到类似以下输出：

\`\`\`typescript
function unique<T>(arr: T[]): T[] {
  const seen = new Set<string>();
  return arr.filter(item => {
    const key = typeof item === 'object' ? JSON.stringify(item) : String(item);
    if (seen.has(key)) return false;
    seen.add(key);
    return true;
  });
}
\`\`\`

**质量评估**：
- ✅ 满足 O(n) 时间复杂度（Set 查找 O(1)）
- ✅ 保持原数组顺序（filter 保持顺序）
- ⚠️ JSON.stringify 对象比较有顺序问题：`{a:1, b:2}` 和 `{b:2, a:1}` 被视为不同
- ⚠️ 未处理 `null` 和 `undefined` 的特殊行为
- ❌ 未提供类型定义和 JSDoc 注释

## 4. 改进建议

优化后的 Prompt：

\`\`\`
请用 TypeScript 编写一个数组去重函数 unique<T>(arr: T[]): T[]。

要求：
1. 保持原数组顺序（返回新数组，不修改原数组）
2. 基本类型（number, string, boolean）使用值比较
3. 对象类型使用 JSON.stringify 排序后比较（解决键顺序问题）
4. null 和 undefined 视为相同值
5. 时间复杂度 O(n)，空间复杂度 O(n)
6. 包含完整的 TypeScript 泛型类型定义
7. 包含 JSDoc 注释和 3 个使用示例
8. 同时生成配套的单元测试用例（使用 Vitest）
\`\`\`

**改进点**：
1. 指定编程语言（TypeScript）和函数签名
2. 明确基本类型和对象类型的比较策略
3. 补充边界条件处理（null/undefined）
4. 要求类型定义和文档注释
5. 同步生成测试用例，可验证正确性
```

**要点**：
- 原始 Prompt 的核心问题是"约束不够具体"，导致 AI 输出质量不稳定
- JSON.stringify 对象比较存在键顺序问题，这是 Prompt 未覆盖的边界条件
- 改进后的 Prompt 将模糊的要求转化为可验证的具体约束（如"排序后比较"）
- 评估报告应量化评分并给出具体的改进版本，而非泛泛的建议
