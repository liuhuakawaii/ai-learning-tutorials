# 02 - AI 代码审查流程

> 将 AI 代码审查嵌入团队 CI/CD 流水线，实现自动化、标准化的质量保障

## 场景引入

周一早上，你在 GitHub 上看到一个 PR：AI 生成了 200 行认证模块代码，逻辑看起来没问题，reviewer 两分钟就点了 Approve。两周后线上爆出安全漏洞——AI 在 JWT 验证中遗漏了过期时间检查，攻击者可以用永不过期的 token 访问系统。你开始反思：如果有一套自动化的 AI 代码审查流程，在 PR 阶段就能拦截这类问题，而不是等到线上才暴露，该多好？

## 学习目标

- 理解 AI 代码审查与传统 code review 的区别与互补
- 掌握 GitHub Actions 自动审查工作流的搭建
- 学会设计审查规则和质量门禁
- 建立 AI 辅助的人工 review 流程

## 1. AI 代码审查概述

### 1.1 审查层次模型

```
┌─────────────────────────────────────────────┐
│            Layer 4: 架构审查（人工）          │
│         设计模式、系统架构、可扩展性           │
├─────────────────────────────────────────────┤
│          Layer 3: 业务逻辑审查（AI+人工）      │
│        业务正确性、边界条件、异常处理          │
├─────────────────────────────────────────────┤
│          Layer 2: 安全与性能审查（AI）         │
│       SQL 注入、XSS、内存泄漏、算法复杂度      │
├─────────────────────────────────────────────┤
│          Layer 1: 风格与规范检查（自动化）      │
│       代码格式、命名规范、注释完整度           │
└─────────────────────────────────────────────┘
```

### 1.2 AI 审查 vs 人工审查

| 维度 | AI 审查 | 人工审查 |
|------|--------|---------|
| 速度 | 秒级完成 | 数小时到数天 |
| 一致性 | 100% 一致 | 受审查者状态影响 |
| 覆盖面 | 可全量扫描 | 通常抽查 |
| 深度理解 | 模式匹配为主 | 真正理解业务 |
| 创造性 | 有限 | 可提出架构优化 |
| 最佳用途 | 规范检查、安全扫描 | 业务逻辑、架构评审 |

## 2. GitHub Actions 自动审查工作流

### 2.1 完整工作流配置

```yaml
# .github/workflows/ai-code-review.yml
name: AI Code Review

on:
  pull_request:
    types: [opened, synchronize]
    branches: [main, develop]

permissions:
  contents: read
  pull-requests: write

jobs:
  ai-review:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - name: Checkout code
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Get changed files
        id: changed-files
        uses: tj-actions/changed-files@v44
        with:
          files: |
            **/*.ts
            **/*.tsx
            **/*.py
            **/*.js

      - name: Static analysis
        if: steps.changed-files.outputs.any_changed == 'true'
        run: |
          echo "Running static analysis on changed files..."
          npx eslint ${{ steps.changed-files.outputs.all_changed_files }} \
            --format json --output-file eslint-report.json || true

      - name: Security scan
        if: steps.changed-files.outputs.any_changed == 'true'
        run: |
          echo "Running security scan..."
          npx semgrep --config auto --json \
            ${{ steps.changed-files.outputs.all_changed_files }} \
            > semgrep-report.json || true

      - name: AI Review
        if: steps.changed-files.outputs.any_changed == 'true'
        uses: ./.github/actions/ai-review
        with:
          files: ${{ steps.changed-files.outputs.all_changed_files }}
          eslint-report: eslint-report.json
          semgrep-report: semgrep-report.json
        env:
          OPENAI_API_KEY: ${{ secrets.AI_REVIEW_API_KEY }}

      - name: Post review comment
        if: steps.changed-files.outputs.any_changed == 'true'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const review = fs.readFileSync('ai-review.md', 'utf8');
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: review
            });
```

### 2.2 自定义 AI Review Action

```yaml
# .github/actions/ai-review/action.yml
name: 'AI Code Review'
description: 'AI-powered code review for pull requests'

inputs:
  files:
    description: 'Changed files list'
    required: true
  eslint-report:
    description: 'ESLint report path'
    required: false
  semgrep-report:
    description: 'Semgrep report path'
    required: false

runs:
  using: 'composite'
  steps:
    - name: Run AI review
      shell: bash
      run: |
        node .github/actions/ai-review/review.js \
          --files "${{ inputs.files }}" \
          --eslint "${{ inputs.eslint-report }}" \
          --semgrep "${{ inputs.semgrep-report }}" \
          --output ai-review.md
```

### 2.3 Review 脚本核心逻辑

```javascript
// .github/actions/ai-review/review.js
const fs = require('fs');
const { execSync } = require('child_process');

async function reviewFiles(files, eslintReport, semgrepReport) {
  const results = [];

  for (const file of files.split(' ')) {
    if (!fs.existsSync(file)) continue;

    const content = fs.readFileSync(file, 'utf8');
    const lines = content.split('\n').length;

    // 跳过过大文件（AI token 限制）
    if (lines > 500) {
      results.push({
        file,
        issue: '文件过大，建议拆分后审查',
        severity: 'warning',
      });
      continue;
    }

    const prompt = buildReviewPrompt(file, content, eslintReport, semgrepReport);
    const review = await callAI(prompt);

    results.push({
      file,
      review: parseReview(review),
      severity: classifySeverity(review),
    });
  }

  return generateReport(results);
}

function buildReviewPrompt(filename, content, eslint, semgrep) {
  return `你是一位资深代码审查者。请审查以下代码文件：

**文件**: ${filename}

**ESLint 结果**: ${eslint || '无'}

**安全扫描结果**: ${semgrep || '无'}

**代码**:
\`\`\`
${content}
\`\`\`

请从以下维度审查：
1. 🔴 严重问题（必须修复）
2. 🟡 建议改进（推荐修复）
3. 🟢 代码亮点（值得学习）

输出格式为 Markdown 表格。`;
}
```

## 6. 常见误区

### ❌ 错误 1：完全依赖 AI 审查结果

```
AI 可能漏报业务逻辑错误，或者误报正常代码。
AI 审查是辅助工具，不能替代人工 review。

正确做法：AI 审查 + 人工 review 双保险
```

### ❌ 错误 2：审查规则过于严格

```yaml
# ❌ 过于严格导致大量误报，开发者直接忽略所有警告
rules:
  max_function_lines: 10  # 太严格
  max_complexity: 3       # 太严格

# ✅ 合理设置
rules:
  max_function_lines: 50
  max_complexity: 10
```

### ❌ 错误 3：审查 Prompt 不够具体

```markdown
# ❌ 太模糊
请审查这段代码

# ✅ 具体明确
请从以下角度审查这段 TypeScript 代码：
1. 是否存在 SQL 注入风险
2. 错误处理是否完整
3. 是否有潜在的内存泄漏
以 Markdown 表格格式输出，包含行号和严重级别。
```

### ❌ 错误 4：不跟踪审查效果

```
问题：配置了 AI 审查但从不检查其效果

解决：定期统计
- AI 审查发现的问题数量
- 人工 review 发现但 AI 遗漏的问题
- AI 误报率
- 审查后线上 bug 变化趋势
```

## 7. 工程建议

1. **AI 审查是辅助不是替代**：始终保留人工 review 环节，AI 擅长发现模式化问题（硬编码、SQL 注入），但业务逻辑错误和架构缺陷仍需人工判断。
2. **审查规则渐进式收紧**：刚开始配置宽松的规则（只拦截严重问题），团队适应后再逐步增加检查项，避免一次性上线过多规则导致开发者直接忽略所有警告。
3. **审查 Prompt 要具体明确**：不要写"请审查这段代码"，而要明确指定审查维度（安全、性能、风格）、输出格式（Markdown 表格）、严重级别分类，这样 AI 的输出才能直接集成到工作流中。
4. **定期复盘审查效果**：每月统计 AI 审查的准确率、误报率和漏报率，根据数据调整 Prompt 和规则，形成"审查→反馈→优化"的闭环。

## 参考答案

### 练习 1：配置 GitHub Actions 审查工作流

**思路**：搭建完整的 CI 审查流水线，包括静态分析（ESLint）、安全扫描（Semgrep）、AI 审查三个阶段，最后将审查结果作为 PR 评论发布。关键是配置好每个步骤的输入输出衔接。

**答案**：

```yaml
# .github/workflows/ai-code-review.yml
name: AI Code Review

on:
  pull_request:
    types: [opened, synchronize]
    branches: [main, develop]

permissions:
  contents: read
  pull-requests: write

jobs:
  ai-review:
    runs-on: ubuntu-latest
    timeout-minutes: 15

    steps:
      - name: Checkout code
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Get changed files
        id: changed-files
        uses: tj-actions/changed-files@v44
        with:
          files: |
            **/*.ts
            **/*.tsx

      - name: ESLint analysis
        if: steps.changed-files.outputs.any_changed == 'true'
        run: |
          npx eslint ${{ steps.changed-files.outputs.all_changed_files }} \
            --format json --output-file eslint-report.json || true

      - name: Security scan with Semgrep
        if: steps.changed-files.outputs.any_changed == 'true'
        uses: returntocorp/semgrep-action@v1
        with:
          config: auto
          generateSarif: true

      - name: AI Review
        if: steps.changed-files.outputs.any_changed == 'true'
        env:
          OPENAI_API_KEY: ${{ secrets.AI_REVIEW_API_KEY }}
        run: |
          node .github/actions/ai-review/review.js \
            --files "${{ steps.changed-files.outputs.all_changed_files }}" \
            --eslint eslint-report.json \
            --output ai-review.md

      - name: Post review comment
        if: steps.changed-files.outputs.any_changed == 'true'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const review = fs.readFileSync('ai-review.md', 'utf8');
            await github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: review
            });
```

```javascript
// .github/actions/ai-review/review.js
const fs = require('fs');

async function callAI(prompt) {
  const response = await fetch('https://api.openai.com/v1/chat/completions', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${process.env.OPENAI_API_KEY}`,
    },
    body: JSON.stringify({
      model: 'gpt-4o',
      messages: [{ role: 'user', content: prompt }],
      temperature: 0.1,
    }),
  });
  const data = await response.json();
  return data.choices[0].message.content;
}

async function main() {
  const args = process.argv.slice(2);
  const filesIdx = args.indexOf('--files');
  const eslintIdx = args.indexOf('--eslint');
  const outputIdx = args.indexOf('--output');

  const files = args[filesIdx + 1].split(' ');
  const eslintPath = eslintIdx >= 0 ? args[eslintIdx + 1] : null;
  const outputPath = args[outputIdx + 1];

  let eslintReport = '';
  if (eslintPath && fs.existsSync(eslintPath)) {
    eslintReport = fs.readFileSync(eslintPath, 'utf8');
  }

  const reviews = [];

  for (const file of files) {
    if (!fs.existsSync(file)) continue;
    const content = fs.readFileSync(file, 'utf8');
    if (content.split('\n').length > 500) {
      reviews.push(`### ${file}\n⚠️ 文件过大（>500行），建议拆分后审查\n`);
      continue;
    }

    const prompt = `请审查以下 TypeScript 代码，从安全、性能、可维护性三个维度分析。
输出 Markdown 表格格式，包含：行号、问题类型、严重级别（🔴/🟡/🟢）、描述、修复建议。

ESLint 结果: ${eslintReport || '无'}

文件: ${file}
\`\`\`typescript
${content}
\`\`\``;

    const review = await callAI(prompt);
    reviews.push(`### ${file}\n${review}\n`);
  }

  const report = `## 🤖 AI 代码审查报告\n\n` +
    `**审查文件数**: ${files.length}\n` +
    `**审查时间**: ${new Date().toISOString()}\n\n` +
    reviews.join('\n---\n\n');

  fs.writeFileSync(outputPath, report);
}

main().catch(console.error);
```

**要点**：
- 工作流分三阶段：ESLint 静态分析 → Semgrep 安全扫描 → AI 综合审查，层层递进

### 练习 3：模拟 AI 审查实践

**思路**：分别从 AI 审查和人工审查两个角度分析这段代码，对比两者能发现的问题类型。AI 擅长发现模式化的安全漏洞，人工擅长理解业务逻辑缺陷。

**答案**：

**AI 审查结果**：

| # | 行号 | 问题类型 | 严重级别 | 描述 | 修复建议 |
|---|------|---------|---------|------|---------|
| 1 | 4 | SQL 注入 | 🔴 严重 | 使用 f-string 拼接 SQL，`from_account` 和 `to_account` 未转义 | 使用参数化查询：`cursor.execute("SELECT balance FROM accounts WHERE id = %s", (from_account,))` |
| 2 | 6 | SQL 注入 | 🔴 严重 | UPDATE 语句同样使用 f-string 拼接 | 同上，使用参数化查询 |
| 3 | 7 | SQL 注入 | 🔴 严重 | UPDATE 语句同样使用 f-string 拼接 | 同上 |
| 4 | 3 | 资源泄漏 | 🟡 建议 | 数据库连接未使用 with 语句或 try-finally，异常时连接不会关闭 | 使用 `with database.connect() as conn:` 或在 finally 中关闭 |
| 5 | 4 | 未检查查询结果 | 🟡 建议 | `fetchone()` 可能返回 None（账户不存在），直接取 [0] 会抛异常 | 添加空值检查 |
| 6 | 全局 | 缺少事务回滚 | 🟡 建议 | 转账操作未使用事务，扣款成功但加款失败会导致资金丢失 | 使用 `try-except` 包裹，异常时 `conn.rollback()` |
| 7 | 2 | 返回值不当 | 🟢 建议 | 函数始终返回 "success"，即使余额不足也不返回失败状态 | 返回操作结果对象，包含成功/失败状态和原因 |

**人工审查补充发现**：

| # | 问题类型 | 描述 |
|---|---------|------|
| 1 | 业务逻辑缺陷 | 余额不足时函数静默返回 "success"，调用方无法得知转账是否真正执行 |
| 2 | 并发安全 | 两个并发请求可能同时读取余额都足够，导致超额扣款（TOCTOU 竞态条件） |
| 3 | 金额精度 | `amount` 参数类型未定义，浮点数运算可能导致精度丢失，应使用 Decimal |
| 4 | 缺少幂等性 | 同一笔转账重复调用会重复扣款，缺少幂等键或唯一约束 |
| 5 | 审计缺失 | 没有记录转账日志，出问题后无法追溯 |

**对比结论**：

- AI 审查在 **安全漏洞检测**（SQL 注入、资源泄漏）方面表现优秀，能快速发现模式化问题
- 人工审查在 **业务逻辑缺陷**（并发安全、幂等性、审计日志）方面更胜一筹，需要理解转账业务的上下文
- 两者互补是最佳实践：AI 做第一轮快速扫描，人工做第二轮业务逻辑审查

**要点**：
- AI 审查擅长发现"代码模式"层面的问题（SQL 注入、资源泄漏、空值处理），速度快且一致
- 人工审查擅长发现"业务语义"层面的问题（竞态条件、幂等性、金额精度），需要理解业务上下文
- 审查 Prompt 要具体指定维度和输出格式，模糊的 Prompt 会导致 AI 遗漏关键问题
- 建立 AI 审查 + 人工审查的双保险机制，两者各司其职而非互相替代
