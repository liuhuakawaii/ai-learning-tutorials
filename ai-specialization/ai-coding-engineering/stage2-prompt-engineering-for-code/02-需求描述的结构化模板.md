# Lesson 02: 需求描述的结构化模板

> **课程定位**：从"知道原则"到"可执行模板"——用 WHAT/WHY/HOW 模式将需求描述标准化。
>
> **前置要求**：Lesson 01（四大核心原则）。
>
> **预计时长**：50 分钟

---

## 场景引入

产品经理给了你一句话需求："做一个用户管理功能。"你把这句话原封不动丢给 AI，AI 生成了 CRUD 代码。但上线后发现：没有分页导致大数据量卡死，没有输入验证导致脏数据入库，没有权限控制导致任何人都能删除用户。你反复和 AI 沟通了 8 轮才勉强可用。如果一开始就用结构化模板把需求拆成 WHAT/WHY/HOW 三段，可能 1-2 轮就能搞定。

---

## 学习目标

完成本课后，你将能够：

1. 理解并运用 **WHAT/WHY/HOW** 三段式需求描述模式
2. 使用**可复用模板**快速描述 API、数据库 Schema、UI 组件等常见需求
3. 将模糊的业务需求转化为 AI 可执行的结构化 Prompt
4. 识别并避免需求描述中的常见陷阱
5. 建立个人/团队的需求模板库

## 2. WHAT/WHY/HOW 模式详解

### 2.1 三段式结构

```
┌──────────────────────────────────────────────────────┐
│              WHAT / WHY / HOW 模式                    │
│                                                      │
│  ┌──────────────────────────────────────────────┐    │
│  │ WHAT — 做什么                                │    │
│  │ 功能的精确描述：输入、输出、行为              │    │
│  │ "实现一个用户搜索 API，返回分页结果"          │    │
│  └──────────────────────────────────────────────┘    │
│                      ▼                               │
│  ┌──────────────────────────────────────────────┐    │
│  │ WHY — 为什么做                               │    │
│  │ 业务背景、使用场景、解决的问题                │    │
│  │ "管理后台的用户列表页需要按姓名/邮箱搜索"    │    │
│  └──────────────────────────────────────────────┘    │
│                      ▼                               │
│  ┌──────────────────────────────────────────────┐    │
│  │ HOW — 怎么做                                 │    │
│  │ 技术方案、约束条件、遵循的规范                │    │
│  │ "用 Prisma 模糊匹配，Zod 验证，分页默认20条" │    │
│  └──────────────────────────────────────────────┘    │
│                                                      │
└──────────────────────────────────────────────────────┘
```

### 2.2 各部分详细说明

| 部分 | 回答的问题 | 包含内容 | 常见遗漏 |
|------|-----------|---------|---------|
| WHAT | "做什么？" | 功能名称、输入/输出、核心行为 | 边界情况、异常行为 |
| WHY | "为什么做？" | 业务场景、用户角色、解决的痛点 | 性能需求、安全需求 |
| HOW | "怎么做？" | 技术栈、约束、规范、参考代码 | 错误处理策略、日志策略 |

## 3. 可复用模板：API 端点

### 3.1 API 端点模板

```markdown
## [WHAT] API 端点描述

**路由**：{METHOD} {路径}
**功能**：一句话描述
**请求参数**：
  - Query: {参数名}: {类型} — {说明} (必填/可选, 默认值)
  - Body: {字段名}: {类型} — {说明} (必填/可选)
**响应格式**：
  - 成功 (200): {结构描述}
  - 失败 (400/404/500): {错误格式}

## [WHY] 业务背景

**场景**：谁在什么场景下使用
**目的**：解决什么问题
**关联**：与哪些功能关联

## [HOW] 技术方案

**技术栈**：框架、ORM、验证库
**约束**：类型安全、错误处理、性能要求
**参考**：现有的类似实现路径
```

### 3.2 实际填充示例

**TypeScript + Express 示例**

```typescript
// ===== 填充后的 Prompt =====
// [WHAT]
// POST /api/orders — 创建新订单
// 请求 Body: { items: Array<{ productId: string; quantity: number }>; couponCode?: string }
// 响应 (201): { id: string; total: number; status: 'pending'; createdAt: string }
// 响应 (400): { error: string; details: ValidationError[] }
// 响应 (404): { error: string } — 商品不存在

// [WHY]
// 电商用户在购物车页面点击"下单"后，需要创建订单并扣减库存。
// 需要保证原子性：订单创建和库存扣减要么同时成功，要么同时失败。

// [HOW]
// Express + TypeScript + Prisma + Zod
// 使用 Prisma 事务保证原子性
// 不使用 any，错误用 AppError 类
// 库存不足时返回 409 Conflict

// ===== AI 生成的代码 =====
import { Router, Request, Response } from 'express';
import { PrismaClient, Prisma } from '@prisma/client';
import { z } from 'zod';
import { AppError } from '../errors/AppError';

const prisma = new PrismaClient();
const router = Router();

const createOrderSchema = z.object({
  items: z.array(z.object({
    productId: z.string().cuid(),
    quantity: z.number().int().positive(),
  })).min(1).max(50),
  couponCode: z.string().optional(),
});

router.post('/api/orders', async (req: Request, res: Response) => {
  const parsed = createOrderSchema.safeParse(req.body);
  if (!parsed.success) {
    res.status(400).json({ error: 'Validation failed', details: parsed.error.flatten() });
    return;
  }

  const { items, couponCode } = parsed.data;

  try {
    const order = await prisma.$transaction(async (tx) => {
      // 1. 验证所有商品存在且库存充足
      for (const item of items) {
        const product = await tx.product.findUnique({ where: { id: item.productId } });
        if (!product) {
          throw new AppError(`Product ${item.productId} not found`, 'PRODUCT_NOT_FOUND', 404);
        }
        if (product.stock < item.quantity) {
          throw new AppError(
            `Insufficient stock for ${product.name}: requested ${item.quantity}, available ${product.stock}`,
            'INSUFFICIENT_STOCK',
            409
          );
        }
      }

      // 2. 计算总价
      let total = 0;
      for (const item of items) {
        const product = await tx.product.findUnique({ where: { id: item.productId } });
        total += product!.price * item.quantity;
      }

      // 3. 应用优惠券（如果有）
      if (couponCode) {
        const coupon = await tx.coupon.findUnique({ where: { code: couponCode } });
        if (coupon && coupon.active) {
          total *= (1 - coupon.discount / 100);
        }
      }

      // 4. 创建订单
      const order = await tx.order.create({
        data: {
          total: Math.round(total * 100) / 100,
          status: 'pending',
          items: {
            create: items.map(item => ({
              productId: item.productId,
              quantity: item.quantity,
            })),
          },
        },
        include: { items: true },
      });

      // 5. 扣减库存
      for (const item of items) {
        await tx.product.update({
          where: { id: item.productId },
          data: { stock: { decrement: item.quantity } },
        });
      }

      return order;
    });

    res.status(201).json({
      id: order.id,
      total: order.total,
      status: order.status,
      createdAt: order.createdAt.toISOString(),
    });
  } catch (error) {
    if (error instanceof AppError) {
      res.status(error.statusCode).json({ error: error.message });
      return;
    }
    throw error;
  }
});

export default router;
```

## 4. 可复用模板：数据库 Schema

### 4.1 Schema 模板

```markdown
## [WHAT] 数据模型描述

**模型名**：{ModelName}
**用途**：一句话说明
**字段**：
  - {字段名}: {类型} — {说明} (约束)
**关系**：
  - {关系类型}: 与 {Model} 的关系 — {说明}
**索引**：{字段} — {原因}

## [WHY] 业务背景

**数据用途**：谁读写这些数据
**查询模式**：最常用的查询是什么
**数据量级**：预估数据量

## [HOW] 技术方案

**ORM**：Prisma / Drizzle / TypeORM
**数据库**：PostgreSQL / MySQL / SQLite
**特殊需求**：软删除、审计日志、多租户
```

### 4.2 实际填充示例

**Prisma Schema 示例**

```prisma
// ===== 填充后的 Prompt =====
// [WHAT] 博客系统的文章模型
// 字段：id, title, slug(唯一), content(长文本), status(draft/published/archived),
//       authorId(外键), publishedAt(可选), createdAt, updatedAt
// 关系：多对一 User(author), 多对多 Tag, 一对多 Comment
// 索引：slug(唯一), [status, publishedAt](列表查询), [authorId, status](作者文章列表)

// [WHY]
// 博客平台的核心数据模型。
// 主要查询：按状态列出文章、按作者查文章、按 slug 查单篇。
// 预计数据量：单作者 500-2000 篇，平台总计 10 万篇以内。

// [HOW]
// Prisma + PostgreSQL
// 需要软删除（用 status=archived 代替物理删除）
// slug 由 title 自动生成，保证唯一

// ===== AI 生成的 Schema =====
model Post {
  id          String      @id @default(cuid())
  title       String      @db.VarChar(200)
  slug        String      @unique @db.VarChar(200)
  content     String      @db.Text
  status      PostStatus  @default(DRAFT)
  publishedAt DateTime?

  authorId String
  author   User   @relation(fields: [authorId], references: [id])

  tags     Tag[]     @relation("PostTags")
  comments Comment[]

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([status, publishedAt])
  @@index([authorId, status])
}

enum PostStatus {
  DRAFT
  PUBLISHED
  ARCHIVED
}

model Tag {
  id    String @id @default(cuid())
  name  String @unique @db.VarChar(50)
  slug  String @unique @db.VarChar(50)
  posts Post[] @relation("PostTags")
}

model Comment {
  id        String   @id @default(cuid())
  content   String   @db.Text
  postId    String
  post      Post     @relation(fields: [postId], references: [id])
  authorId  String
  author    User     @relation(fields: [authorId], references: [id])
  createdAt DateTime @default(now())

  @@index([postId, createdAt])
}
```

### 5.2 实际填充示例

**React + TypeScript + Tailwind 示例**

```typescript
// ===== 填充后的 Prompt =====
// [WHAT] 通用确认对话框组件
// Props:
//   - isOpen: boolean — 控制显示/隐藏
//   - title: string — 对话框标题
//   - message: string — 确认内容
//   - confirmText?: string — 确认按钮文字 (默认 "确认")
//   - cancelText?: string — 取消按钮文字 (默认 "取消")
//   - variant?: 'danger' | 'warning' | 'info' — 视觉风格 (默认 'info')
//   - onConfirm: () => void — 点击确认回调
//   - onCancel: () => void — 点击取消/遮罩回调

// [WHY]
// 项目中多处需要二次确认：删除操作、退出编辑、批量操作等。
// 需要统一的确认体验，支持不同危险等级的视觉区分。

// [HOW]
// React + TypeScript + Tailwind CSS
// 使用 React Portal 渲染到 document.body
// 支持 ESC 键关闭、点击遮罩关闭
// 使用 Framer Motion 做进入/退出动画
// 不使用 any 类型

// ===== AI 生成的代码 =====
import { useEffect, useRef, type ReactNode } from 'react';
import { createPortal } from 'react-dom';
import { motion, AnimatePresence } from 'framer-motion';

interface ConfirmDialogProps {
  isOpen: boolean;
  title: string;
  message: string | ReactNode;
  confirmText?: string;
  cancelText?: string;
  variant?: 'danger' | 'warning' | 'info';
  onConfirm: () => void;
  onCancel: () => void;
}

const variantStyles = {
  danger: {
    icon: '⚠️',
    confirmBg: 'bg-red-600 hover:bg-red-700',
    ring: 'ring-red-500/20',
  },
  warning: {
    icon: '⚡',
    confirmBg: 'bg-amber-600 hover:bg-amber-700',
    ring: 'ring-amber-500/20',
  },
  info: {
    icon: 'ℹ️',
    confirmBg: 'bg-blue-600 hover:bg-blue-700',
    ring: 'ring-blue-500/20',
  },
} as const;

export function ConfirmDialog({
  isOpen,
  title,
  message,
  confirmText = '确认',
  cancelText = '取消',
  variant = 'info',
  onConfirm,
  onCancel,
}: ConfirmDialogProps) {
  const confirmRef = useRef<HTMLButtonElement>(null);
  const style = variantStyles[variant];

  useEffect(() => {
    if (!isOpen) return;

    const handleKeyDown = (e: KeyboardEvent) => {
      if (e.key === 'Escape') onCancel();
    };

    document.addEventListener('keydown', handleKeyDown);
    document.body.style.overflow = 'hidden';

    return () => {
      document.removeEventListener('keydown', handleKeyDown);
      document.body.style.overflow = '';
    };
  }, [isOpen, onCancel]);

  useEffect(() => {
    if (isOpen) {
      confirmRef.current?.focus();
    }
  }, [isOpen]);

  return createPortal(
    <AnimatePresence>
      {isOpen && (
        <motion.div
          className="fixed inset-0 z-50 flex items-center justify-center"
          initial={{ opacity: 0 }}
          animate={{ opacity: 1 }}
          exit={{ opacity: 0 }}
        >
          <motion.div
            className="absolute inset-0 bg-black/50"
            onClick={onCancel}
            initial={{ opacity: 0 }}
            animate={{ opacity: 1 }}
            exit={{ opacity: 0 }}
          />

          <motion.div
            className={`relative mx-4 w-full max-w-md rounded-xl bg-white p-6 shadow-2xl ring-1 ${style.ring}`}
            initial={{ scale: 0.95, opacity: 0 }}
            animate={{ scale: 1, opacity: 1 }}
            exit={{ scale: 0.95, opacity: 0 }}
            role="alertdialog"
            aria-labelledby="dialog-title"
            aria-describedby="dialog-description"
          >
            <div className="mb-4 flex items-center gap-3">
              <span className="text-2xl">{style.icon}</span>
              <h2 id="dialog-title" className="text-lg font-semibold text-gray-900">
                {title}
              </h2>
            </div>

            <div id="dialog-description" className="mb-6 text-sm text-gray-600">
              {message}
            </div>

            <div className="flex justify-end gap-3">
              <button
                onClick={onCancel}
                className="rounded-lg border border-gray-300 px-4 py-2 text-sm font-medium text-gray-700 hover:bg-gray-50"
              >
                {cancelText}
              </button>
              <button
                ref={confirmRef}
                onClick={onConfirm}
                className={`rounded-lg px-4 py-2 text-sm font-medium text-white ${style.confirmBg}`}
              >
                {confirmText}
              </button>
            </div>
          </motion.div>
        </motion.div>
      )}
    </AnimatePresence>,
    document.body
  );
}
```

## 6. 需求拆解技巧

### 6.1 大需求拆小需求

```
大需求："做一个完整的博客系统"
         │
         ▼
拆解为独立的小需求：

  ┌─────────────┐
  │ 数据模型    │ → "定义 Post, Tag, Comment 的 Prisma Schema"
  └──────┬──────┘
         ▼
  ┌─────────────┐
  │ 文章 CRUD   │ → "实现文章的增删改查 API"
  └──────┬──────┘
         ▼
  ┌─────────────┐
  │ 标签管理    │ → "实现标签的 CRUD 和文章-标签关联"
  └──────┬──────┘
         ▼
  ┌─────────────┐
  │ 评论系统    │ → "实现评论的创建、列表、删除"
  └──────┬──────┘
         ▼
  ┌─────────────┐
  │ 前端页面    │ → "文章列表页、详情页、编辑页"
  └─────────────┘
```

### 6.2 拆解原则

| 原则 | 说明 | 示例 |
|------|------|------|
| 单一职责 | 每个 Prompt 只做一件事 | "实现文章创建 API" 而非 "实现文章所有功能" |
| 可验证 | 完成后可以测试 | "实现 GET /api/posts，返回 Post[]" |
| 有依赖顺序 | 先模型后 API 再页面 | Schema → API → 前端 |
| 适当粒度 | 不太粗也不太细 | 一个路由文件而非一个函数 |

## 7. 常见误区

### ❌ 错误 1：缺少 WHY

```
"写一个 Redis 缓存层"
→ AI 不知道缓存什么、缓存策略是什么、TTL 设多少
```

**修复**：补充业务场景——"首页商品列表查询频繁（QPS 500+），需要用 Redis 缓存，TTL 5 分钟，缓存失效时回源数据库"。

### ❌ 错误 2：WHAT 和 HOW 混淆

```
"用 Prisma 写一个查询"
→ 这是 HOW，WHAT 是"查询什么、返回什么"
```

**修复**：WHAT 先说清楚要什么，HOW 再说用什么技术实现。

### ❌ 错误 3：忽略错误场景

```
只描述成功路径，不说失败时怎么办
→ AI 生成的代码缺少错误处理
```

**修复**：在 WHAT 中列出可能的错误场景（400 参数错误、404 不存在、409 冲突等）。

### ❌ 错误 4：模板过于僵硬

```
每次都完整填写模板所有字段，即使很多字段不适用
→ 浪费时间，Prompt 冗长
```

**修复**：只填写与当前需求相关的字段，省略不适用的部分。

### ❌ 错误 5：缺少参考代码

```
"按项目现有风格写"
→ AI 不知道你的风格是什么
```

**修复**：在 HOW 中贴一段现有的参考代码，或说明风格要点。

## 8. 工程建议

1. **维护团队模板库**：将 WHAT/WHY/HOW 模板沉淀为团队共享的 Prompt 模板库，按场景分类（API、Schema、组件），新人可以直接复用，减少摸索成本。

2. **从真实需求开始练习**：不要用虚构需求练习模板，而是从你手头正在做的功能开始。用模板重写你上次给 AI 的 Prompt，对比效果差异，这样学习效率最高。

3. **模板不是越全越好**：只填写与当前需求相关的字段，省略不适用的部分。一个精简但完整的 WHAT/WHY/HOW 比一个面面俱到但大部分是占位符的模板更有效。

4. **建立"需求→Prompt→代码"的审查闭环**：每次用模板生成代码后，回头检查 Prompt 是否遗漏了关键约束，代码是否符合预期，将发现的问题反馈到模板中持续优化。

## 9. 总结

```
结构化模板的价值：

  模糊需求 ──▶ 结构化描述 ──▶ 精准代码
                │
                ├── WHAT: 明确做什么
                ├── WHY:  说明为什么
                └── HOW:  指定怎么做

  效果：减少 60-80% 的反复沟通
```

| 模板类型 | 适用场景 | 核心字段 |
|---------|---------|---------|
| API 端点 | 后端接口开发 | 路由、参数、响应、验证 |
| 数据库 Schema | 数据模型设计 | 模型名、字段、关系、索引 |
| UI 组件 | 前端组件开发 | Props、结构、交互、样式 |
| 通用模板 | 任何需求 | WHAT / WHY / HOW |

## 参考答案

### 练习 1：用模板描述一个 API

**思路**：选择"用户登录 API"作为示例，用 WHAT/WHY/HOW 三段式模板完整描述。关键是 WHAT 部分要列出所有响应场景（包括错误），WHY 部分要说明业务背景，HOW 部分要指定技术约束。

**答案**：

```markdown
## [WHAT] 用户登录 API

**路由**：POST /api/auth/login
**功能**：验证用户邮箱和密码，返回 JWT token

**请求参数**（Body）：
- email: string — 用户邮箱（必填，邮箱格式）
- password: string — 用户密码（必填，非空）

**响应格式**：
- 成功 (200): { user: { id, email, name, role }, token: string, expiresIn: number }
- 失败 (400): { error: "参数验证失败", details: ValidationError[] }
- 失败 (401): { error: "邮箱或密码错误" }
- 失败 (429): { error: "登录尝试过于频繁，请 15 分钟后再试" }

## [WHY] 业务背景

**场景**：用户在登录页面输入邮箱和密码，点击登录按钮
**目的**：验证用户身份，颁发 JWT token 用于后续请求的认证
**关联**：
- 前端登录页面调用此接口
- 登录成功后跳转到 dashboard
- 后续所有需要认证的接口使用返回的 token

**安全需求**：
- 密码传输和存储必须加密
- 登录失败不暴露"邮箱不存在"和"密码错误"的区别（防止邮箱枚举）
- 需要 rate limiting 防止暴力破解

## [HOW] 技术方案

**技术栈**：Express + TypeScript + Prisma + Zod + bcrypt + jsonwebtoken
**约束**：
- 使用 Zod 验证请求体，不直接访问 req.body
- 密码比较使用 bcrypt.compare，不做字符串比较
- JWT secret 从环境变量 JWT_SECRET 读取
- 错误处理使用 AppError 类，不使用 try-catch 吞错误
- 登录失败统一返回 401 + "邮箱或密码错误"
- 添加 rate limiting：15 分钟内最多 5 次登录尝试

**参考**：现有的 POST /api/auth/register 端点的风格
```

**要点**：
- WHAT 部分列出了 4 种响应场景，AI 不会遗漏错误处理
- WHY 部分说明了安全需求，AI 会自动加上 rate limiting 和统一错误信息
- HOW 部分指定了参考代码，AI 生成的风格会与项目一致
- 完整的模板比"写个登录 API"多花 3 分钟，但减少 5 轮以上的返工

### 练习 2：需求拆解

**思路**：将"做一个任务管理系统"拆解为独立的、可验证的小需求。每个小需求用一行结构化描述（WHAT + 核心行为），并按依赖顺序排列。

**答案**：

```
大需求："做一个任务管理系统（类似 Trello）"

拆解为 8 个独立小需求：

1. [数据模型] 定义 Board、List、Card、User 的 Prisma Schema，
   包含一对多关系和必要的索引

2. [用户认证] 实现注册/登录 API（POST /auth/register, POST /auth/login），
   JWT 认证中间件，密码 bcrypt 加密

3. [看板管理] 实现看板的 CRUD API（GET/POST/PUT/DELETE /api/boards），
   支持看板所有者邀请其他用户

4. [列表管理] 实现列表的 CRUD API（GET/POST/PUT/DELETE /api/lists），
   支持拖拽排序（position 字段），列表属于某个看板

5. [任务管理] 实现任务卡片的 CRUD API（GET/POST/PUT/DELETE /api/cards），
   支持在列表间移动、设置截止日期、添加描述

6. [任务分配] 实现任务分配功能（POST /api/cards/:id/assignees），
   支持分配给多个用户，只能分配给看板成员

7. [标签和筛选] 实现标签的 CRUD 和任务标签关联，
   支持按标签、负责人、截止日期筛选任务

8. [提醒通知] 实现截止日期提醒（后台定时任务），
   到期前 24 小时发送通知，支持邮件和站内通知
```

**要点**：
- 拆解原则：单一职责（每个需求只做一件事）、可验证（完成后可以测试）、有依赖顺序（先模型后 API）
- 每个小需求的粒度是"一个路由文件"或"一个功能模块"，不要太粗也不要太细
- 依赖顺序很重要：数据模型 → 认证 → 基础 CRUD → 关联功能 → 高级功能
- 每个小需求都可以独立用 WHAT/WHY/HOW 模板描述，然后交给 AI 实现

### 练习 3：对比有无模板的差异

**思路**：选一个真实功能，先用原来的 Prompt 方式，再用 WHAT/WHY/HOW 模板重新描述，记录两次的代码质量和返工次数差异。

**答案**：

以"实现文章搜索 API"为例：

| 维度 | 原 Prompt："帮我写个文章搜索" | 模板 Prompt（WHAT/WHY/HOW） |
|------|---------------------------|---------------------------|
| 生成代码行数 | 15 行 | 60 行 |
| 框架匹配 | 可能用 Express（项目是 Next.js） | 正确使用 Next.js App Router |
| 搜索功能 | 简单的 LIKE 查询 | Prisma contains + insensitive 模糊匹配 |
| 分页 | 无 | 包含 page/pageSize + total 计算 |
| 输入验证 | 无 | Zod 验证查询参数 |
| 错误处理 | 无或简单 | AppError + 参数验证错误 |
| 响应格式 | { results: [...] } | { data: [...], pagination: {...} }（符合项目规范） |
| 返工轮次 | 5-6 轮 | 1-2 轮 |
| 返工内容 | 补分页、换框架、加验证、改格式、加错误处理 | 调整排序字段、添加索引建议 |

模板 Prompt 示例：
```
[WHAT]
GET /api/posts/search — 文章搜索 API
查询参数：
  - q: string（必填）— 搜索关键词
  - page: number（可选，默认 1）— 页码
  - pageSize: number（可选，默认 20，最大 100）— 每页数量
  - tag: string（可选）— 按标签过滤
响应 (200): { data: Post[], pagination: { page, pageSize, total, totalPages } }
响应 (400): { error: string, details: ValidationError[] }

[WHY]
博客前台页面的文章搜索功能，用户输入关键词搜索标题和内容。
预计数据量：10 万篇文章以内。
需要支持中文搜索（使用 Prisma 的 contains + insensitive）。

[HOW]
Next.js 14 App Router + Prisma + Zod
参考 @file: src/app/api/users/route.ts 的代码风格
响应格式：{ data, pagination }（项目统一格式）
错误处理：使用 src/lib/errors.ts 中的 AppError 类
```

**要点**：
- 模板 Prompt 的返工率降低了 70-80%
- 最大的差异体现在：框架匹配、分页、错误处理、响应格式——这些都是模板中明确约束的
- WHAT 部分的错误场景列表让 AI 不会遗漏错误处理
- HOW 部分的"参考现有代码"让风格完全一致
- 花 3 分钟写模板，省 20 分钟改代码——这个 ROI 非常高
