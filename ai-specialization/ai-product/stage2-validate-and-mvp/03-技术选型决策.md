# 第三课：技术选型决策

## 场景引入

MVP 定义好了，你准备开始写代码。第一个问题就是：用什么技术栈？React 还是 Vue？Next.js 还是 Nuxt？PostgreSQL 还是 MongoDB？部署到 Vercel 还是自己的服务器？你在网上搜了一圈，每个选项都有人说好、有人说差，越看越纠结。

技术选型是开发者最容易过度思考的事情。对于 MVP 来说，选型的核心原则只有一个：**用你最熟悉的，快速出活**。这一课，你会学到如何在"快速开发"和"长期可维护"之间找到平衡点。

## 学习目标

1. 掌握 AI 产品技术选型的核心原则
2. 了解全栈框架、数据库、部署平台的主流选择
3. 学会根据产品阶段选择合适的技术栈
4. 能够为自己的产品做出技术选型决策

## 一、技术选型的核心原则

### 1.1 原则一：选熟悉的，不选"最好"的

```
MVP 阶段最大的敌人是时间。

你熟悉 React？用 React。
你熟悉 Vue？用 Vue。
你熟悉 Python？用 Python。

不要在 MVP 阶段学习新技术栈。
学习曲线 = 时间成本 = 错失市场窗口。
```

### 1.2 原则二：选主流的，不选"前沿"的

```
主流技术的优势：
- 文档完善，遇到问题容易找到解决方案
- 社区活跃，有大量现成的库和工具
- 招人容易（如果你需要招人的话）
- 稳定可靠，不会突然停止维护

前沿技术的风险：
- 文档不完善，踩坑无人解答
- 生态不成熟，缺少配套工具
- 可能很快被弃坑
```

### 1.3 原则三：选能快速迭代的，不选"性能最好"的

```
MVP 阶段最重要的是：快速验证 → 快速迭代。

性能优化是有了用户之后的事情。
MVP 阶段就算慢 100ms，用户也不会在意。
但如果因为选了一个复杂的架构导致开发慢了 2 周，你可能错过市场窗口。
```

## 二、全栈框架选择

### 2.1 主流选项对比

| 框架 | 语言 | 核心优势 | 主要劣势 | 适用场景 |
|------|------|---------|---------|---------|
| **Next.js** | TypeScript | 前后端一体、SSR/SSG、Vercel 一键部署 | 服务端逻辑复杂时臃肿 | SEO 型 SaaS、内容网站 |
| **Nuxt.js** | TypeScript | Vue 生态、自动路由、Nitro 引擎 | 社区比 React 小 | Vue 开发者、内容网站 |
| **FastAPI + React** | Python + TS | Python AI/ML 生态最强、自动文档 | 前后端分离增加复杂度 | AI 密集型产品 |
| **Remix** | TypeScript | Web 标准、嵌套路由、数据突变内置 | 社区较小 | 表单密集型应用 |

### 2.2 选型决策树

```
你最熟悉什么框架？
├── React/Next.js → 直接用 Next.js
├── Vue → 用 Nuxt.js
├── Python → FastAPI + React/Vue
└── 都不太熟 → 用 Next.js（生态最大，资源最多）

你的产品需要 SSR 吗？
├── 需要 SEO → Next.js / Nuxt.js
└── 不需要 → 任何 SPA 框架都行

你的产品 AI 处理重吗？
├── 重（大量 AI 调用、模型推理）→ FastAPI + React
└── 轻（调用外部 AI API）→ Next.js API Routes 就够了
```

## 三、数据库选择

### 3.1 主流选项对比

| 数据库 | 类型 | 核心优势 | 主要劣势 | 适用场景 | 成本 |
|--------|------|---------|---------|---------|------|
| **PostgreSQL** | 关系型 | 功能全面、JSON 支持好、扩展性强 | 配置运维复杂 | 复杂查询、数据关系明确 | 免费层 |
| **SQLite** | 关系型 | 零配置、性能极佳、Turso 提供 Serverless | 不适合高并发 | MVP、单机部署 | 免费 |
| **MongoDB** | 文档型 | 灵活文档模型、Atlas 免费云服务 | 不适合关系查询 | 数据结构不固定 | 免费层 |
| **Vercel Postgres** | Serverless | 与 Next.js 深度集成、零运维 | 功能比原生 PG 少、与 Vercel 绑定 | Next.js 项目 | 低 |

### 3.2 数据库选型建议

```
MVP 阶段推荐：
├── 最简单：SQLite（配合 Turso 可以 Serverless）
├── 最通用：PostgreSQL（配合 Supabase 或 Neon）
└── 最省心：Vercel Postgres（如果你用 Next.js）

什么时候用 MongoDB：
- 数据结构高度不确定，频繁变化
- 不需要复杂的关系查询
- 团队熟悉 MongoDB

什么时候不用 SQLite：
- 需要高并发写入（> 100 QPS）
- 需要多服务器共享数据库
- 需要复杂的事务处理
```

## 四、AI 服务集成

### 4.1 AI API 选择

| 服务 | 核心优势 | 主要劣势 | 价格参考 | 适用场景 |
|------|---------|---------|---------|---------|
| **OpenAI API** | 模型能力最强、API 最成熟 | 价格较高、偶尔不稳定 | GPT-4o-mini: $0.15/1M input | 需要最强模型能力 |
| **Claude API** | 长文本强、安全性好 | 生态比 OpenAI 小 | Sonnet: $3/1M input | 长文本、安全性场景 |
| **国内大模型** | 中文强、价格便宜、合规 | 英文弱、稳定性参差不齐 | 通常比 OpenAI 便宜 50-80% | 中国市场、中文为主 |

### 4.2 AI 集成架构

```typescript
// 推荐：抽象 AI 服务层，方便切换提供商
interface AIService {
  generate(prompt: string, options: GenerateOptions): Promise<string>;
  generateStream(prompt: string, options: GenerateOptions): AsyncGenerator<string>;
}

interface GenerateOptions {
  model?: string;
  temperature?: number;
  maxTokens?: number;
  systemPrompt?: string;
}

// OpenAI 实现
class OpenAIService implements AIService {
  private client: OpenAI;

  constructor(apiKey: string) {
    this.client = new OpenAI({ apiKey });
  }

  async generate(prompt: string, options: GenerateOptions = {}): Promise<string> {
    const response = await this.client.chat.completions.create({
      model: options.model || "gpt-4o-mini",
      messages: [
        ...(options.systemPrompt ? [{ role: "system" as const, content: options.systemPrompt }] : []),
        { role: "user" as const, content: prompt }
      ],
      temperature: options.temperature ?? 0.7,
      max_tokens: options.maxTokens ?? 2000
    });
    return response.choices[0].message.content;
  }

  async *generateStream(prompt: string, options: GenerateOptions = {}): AsyncGenerator<string> {
    const stream = await this.client.chat.completions.create({
      model: options.model || "gpt-4o-mini",
      messages: [
        ...(options.systemPrompt ? [{ role: "system" as const, content: options.systemPrompt }] : []),
        { role: "user" as const, content: prompt }
      ],
      temperature: options.temperature ?? 0.7,
      max_tokens: options.maxTokens ?? 2000,
      stream: true
    });

    for await (const chunk of stream) {
      const content = chunk.choices[0]?.delta?.content;
      if (content) yield content;
    }
  }
}

// 使用示例
const ai = new OpenAIService(process.env.OPENAI_API_KEY);

// 生成文案
const copywriting = await ai.generate(
  `请为以下菜品生成小红书营销文案：
  菜品：红烧肉
  价格：¥38
  特色：肥而不腻，入口即化`,
  {
    systemPrompt: "你是一个专业的餐饮营销文案写手，擅长小红书风格的内容创作。",
    temperature: 0.8
  }
);
```

## 五、部署平台选择

### 5.1 主流部署平台对比

| 平台 | 核心优势 | 主要劣势 | 免费额度 | 适用场景 |
|------|---------|---------|---------|---------|
| **Vercel** | Next.js 原生支持、全球 CDN | 冷启动、与 Next.js 绑定 | 100GB 带宽/月 | Next.js 项目 |
| **Railway** | 支持任意语言、数据库内置 | 国内访问一般 | $5/月额度 | 全栈应用 |
| **Fly.io** | 全球边缘部署、Docker 灵活 | 配置相对复杂 | 3 个共享 CPU VM | 全球低延迟 |
| **Cloudflare Workers** | 全球边缘、免费额度最大 | 运行环境受限 | 10 万请求/天 | API 服务 |

### 5.2 部署选型建议

```
MVP 阶段推荐：

最省心：Vercel（如果用 Next.js）
- push 代码自动部署
- 免费额度足够 MVP 使用
- 无需配置服务器

最灵活：Railway
- 支持任意后端
- 数据库内置
- 适合需要复杂后端的场景

最有性价比：Cloudflare Workers + D1
- 免费额度最大
- 全球边缘部署
- 适合 API 服务
```

## 常见误区

### 误区一：过度设计架构

"我需要微服务、消息队列、Redis 缓存、Kubernetes……"——MVP 阶段不需要这些。一个单体应用 + 一个数据库就够了。等有了用户和流量再考虑架构升级。

### 误区二：选择"最新最好"的技术

"我听说 Bun 比 Node.js 快，我要用 Bun。"——MVP 阶段，稳定性和生态比性能重要 100 倍。选经过生产验证的技术。

### 误区三：忽视 AI API 的成本

在做技术选型时，一定要估算 AI API 的调用成本。如果每用户每月的 AI 成本是 ¥50，而你的定价是 ¥49，这个生意就做不下去。

### 误区四：把技术选型当成不可逆决策

技术选型是可逆的。如果发现选错了，可以换。不要花两周时间纠结选型，快速做出决定，遇到问题再调整。

## 工程建议

### 1. 先做技术 Spike

在正式开发前，花 1-2 天做一个技术 Spike（技术验证原型）：用选定的技术栈实现最核心的功能（如 AI 文案生成），验证可行性。

### 2. 准备 AI API 的降级方案

AI API 可能不稳定、可能限流、可能涨价。准备一个降级方案：主用 OpenAI，备用通义千问。在代码层面抽象 AI 服务，方便切换。

### 3. 用环境变量管理配置

```typescript
// 不要把 API Key、数据库连接等硬编码到代码中
// 使用环境变量
const config = {
  openaiApiKey: process.env.OPENAI_API_KEY,
  databaseUrl: process.env.DATABASE_URL,
  appUrl: process.env.NEXT_PUBLIC_APP_URL
};
```

### 4. 从第一天就开始版本控制

用 Git 管理代码，从第一次 commit 开始。不要等到"做完再推"。频繁 commit，写清楚 commit message。

## 小结

- 技术选型核心原则：选熟悉的、选主流的、选能快速迭代的
- 全栈框架推荐：Next.js（React 生态）、Nuxt（Vue 生态）、FastAPI + React（AI 密集型）
- 数据库推荐：MVP 阶段用 SQLite 或 Vercel Postgres，复杂场景用 PostgreSQL
- AI 服务推荐：OpenAI API（最强）、通义千问（中文/性价比）
- 部署推荐：Vercel（Next.js）、Railway（全栈）、Cloudflare Workers（API）

3. **成本估算**：估算你的 MVP 的月度成本：AI API 调用费、数据库费用、部署费用、域名费用。这些成本是否在你的预算内？

## 参考答案

### 练习一：技术选型决策

**思路**：用课程中的技术选型决策文档模板，先明确产品需求和约束条件，再逐项做选择。核心原则是"选熟悉的，不选最好的"。每个选择都要写出理由和备选方案，这样决策过程是可追溯的。

**答案**：

```markdown
## 技术选型决策文档

### 产品背景
- 产品名称：AI 餐饮营销助手
- MVP 核心功能：输入菜品信息 → AI 生成小红书文案 → 复制使用
- 开发时间预算：7 天
- 团队规模：1 人（独立开发者）
- 核心约束：需要调用 AI API、需要存储生成记录、需要快速部署

### 选型决策

#### 全栈框架
- 选择：Next.js (App Router)
- 理由：
  - 前后端一体，不需要单独部署后端
  - API Routes 足够处理 AI 调用
  - Vercel 一键部署，零运维
  - TypeScript 支持好，减少 bug
- 备选：Nuxt.js（更熟悉 Vue 时选择）、FastAPI + React（AI 处理重时选择）

#### 数据库
- 选择：Vercel Postgres
- 理由：
  - 与 Next.js 深度集成，零配置
  - Serverless 模式，不需要运维
  - 免费额度足够 MVP 使用
  - SQL 语法标准，后续可迁移到任何 PostgreSQL
- 备选：SQLite（最简单，但不适合 Serverless）、Supabase（功能更全，但配置复杂）

#### AI 服务
- 选择：OpenAI API (gpt-4o-mini)
- 理由：
  - 中文文案生成质量最好
  - API 最成熟，文档完善
  - gpt-4o-mini 性价比高（$0.15/1M input tokens）
  - 支持流式输出，用户体验好
- 备选：通义千问（中文强、价格便宜 50-80%）、Claude API（长文本强）

#### 部署平台
- 选择：Vercel
- 理由：
  - Next.js 原生支持，push 代码自动部署
  - 免费额度足够 MVP（100GB 带宽/月）
  - 全球 CDN，访问速度快
  - 环境变量管理方便
- 备选：Railway（需要复杂后端时选择）、Cloudflare Workers（API 服务）

#### 前端样式
- 选择：Tailwind CSS
- 理由：
  - Next.js 创建时可直接选择集成
  - 不需要写 CSS 文件，开发速度快
  - 响应式设计方便
- 备选：shadcn/ui（需要更丰富的组件时）
```

**要点**：
- 每个选择都要写"理由"和"备选"，这样决策是可追溯的
- MVP 阶段选型的核心原则：熟悉 > 最好，主流 > 前沿，快速 > 性能
- 不要在 MVP 阶段学习新技术栈，学习曲线 = 时间成本
- 选型完成后不要再纠结，立即进入开发

### 练习二：技术 Spike

**思路**：技术 Spike 的目的是验证"技术上是否可行"，不是做出完整功能。花 1 天时间，用选定的技术栈实现最核心的功能（如 AI 文案生成的 API 调用），确认能跑通。如果核心功能跑不通，可以及时调整技术方案。

**答案**：

```markdown
## 技术 Spike 报告

### 目标
验证 OpenAI API 能否可靠地生成小红书风格的餐饮营销文案

### 实现内容
1. 创建 Next.js 项目
2. 配置 OpenAI API Key
3. 实现 API Route 调用 OpenAI
4. 编写 Prompt 并测试输出质量
5. 前端调用 API 并展示结果

### 核心代码

```typescript
// src/app/api/generate/route.ts
import { NextRequest, NextResponse } from 'next/server';
import OpenAI from 'openai';

const openai = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

export async function POST(request: NextRequest) {
  const { dishName, price, features } = await request.json();

  const response = await openai.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      {
        role: 'system',
        content: '你是一个专业的餐饮营销文案写手，擅长小红书风格的内容创作。'
      },
      {
        role: 'user',
        content: `请为以下菜品生成一条小红书风格的营销文案：
菜品名称：${dishName}
价格：${price}
特色：${features}
要求：200-300 字，包含 3-5 个话题标签，开头有吸引力，结尾有行动号召。`
      }
    ],
    temperature: 0.8,
    max_tokens: 1000,
  });

  return NextResponse.json({
    copywriting: response.choices[0].message.content
  });
}
```

### 测试结果

| 测试项 | 结果 | 备注 |
|--------|------|------|
| API 调用成功率 | 100% (10/10) | 无超时或报错 |
| 平均响应时间 | 3.2 秒 | 可接受，后续可加流式输出 |
| 文案质量 | 7/10 | 基本可用，Prompt 需优化 |
| 中文质量 | 8/10 | 无明显语法错误 |
| 话题标签生成 | ✅ | 自动生成 #标签 |

### 结论
技术可行，可以进入 MVP 开发阶段。需要优化的点：
1. Prompt 需要迭代，让文案更像真人写的
2. 考虑加流式输出，减少用户等待感
3. 需要处理 API 超时和限流的情况

### 练习三：成本估算
