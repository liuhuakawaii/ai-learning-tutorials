# 第二课：MVP 设计原则

## 场景引入

验证通过了——Landing Page 转化率 8%，访谈中 7/10 的餐饮老板确认了痛点，还有 3 个人当场转了定金。你兴奋地开始规划产品功能：AI 文案生成、多平台适配、数据分析看板、团队协作、品牌管理、自动发布、定时发布、竞品监控……

停。这正是 MVP 最大的陷阱——功能膨胀。你以为在做"最小可行产品"，实际上在做"完整版产品"。这一课，你会学到如何砍掉 80% 的功能，只保留真正创造核心价值的那 20%。

## 学习目标

1. 理解 MVP 的真正含义：不是"简陋"，而是"聚焦"
2. 掌握功能优先级排序的方法
3. 学会用"用户故事"定义 MVP 范围
4. 了解 MVP 的常见类型和适用场景

## 一、MVP 的真正含义

### 1.1 MVP 不是"简陋的产品"

```
常见误解：MVP = 做一个功能少一点的版本
正确理解：MVP = 能验证核心假设的最简版本

MVP 的目的不是"发布产品"，而是"验证假设"。
如果一个 Landing Page 就能验证你的核心假设，那 Landing Page 就是你的 MVP。
```

### 1.2 MVP 的三个核心要素

```typescript
interface MVPDefinition {
  // 1. 核心假设：你最需要验证的是什么？
  coreHypothesis: string;

  // 2. 核心功能：验证这个假设需要的最小功能集
  coreFeatures: string[];

  // 3. 核心用户：你的 MVP 面向的是谁？
  coreUser: string;
}

// 示例：AI 餐饮营销助手
const mvp: MVPDefinition = {
  coreHypothesis: "餐饮老板愿意为 AI 生成的营销内容付费",
  coreFeatures: [
    "输入菜品名和价格 → 生成小红书文案",
    "用户可以复制文案"
  ],
  coreUser: "个体餐饮老板，不雇营销人员，自己发社交媒体"
};
// 注意：只做了"小红书"一个平台，没有抖音、朋友圈、数据分析、团队协作
```

### 1.3 "你不是在做产品，你是在验证假设"

```
完整产品思维：
我要做一个餐饮营销平台，包含 AI 文案、数据分析、多平台发布、团队协作...

MVP 思维：
我需要验证一个假设：餐饮老板愿意为 AI 生成的营销内容付费。
验证这个假设需要什么？一个能生成文案的工具 + 一个付费入口。
其他所有功能都可以等验证通过后再做。
```

## 二、功能优先级排序

### 2.1 用"影响-努力"矩阵排序

```typescript
interface Feature {
  name: string;
  impact: number;      // 1-5，对核心假设验证的影响
  effort: number;      // 1-5，开发工作量
  priority: 'must' | 'should' | 'could' | 'wont';
}

function prioritizeFeature(feature: Feature): Feature {
  const ratio = feature.impact / feature.effort;

  if (ratio >= 2) feature.priority = 'must';    // 高影响，低努力
  else if (ratio >= 1) feature.priority = 'should';
  else if (ratio >= 0.5) feature.priority = 'could';
  else feature.priority = 'wont';               // 低影响，高努力

  return feature;
}

// AI 餐饮营销助手的功能排序
const features: Feature[] = [
  { name: "AI 生成小红书文案", impact: 5, effort: 2, priority: 'must' },
  { name: "用户输入菜品信息", impact: 5, effort: 1, priority: 'must' },
  { name: "复制文案到剪贴板", impact: 4, effort: 1, priority: 'must' },
  { name: "多平台适配（抖音/朋友圈）", impact: 3, effort: 3, priority: 'should' },
  { name: "文案模板库", impact: 3, effort: 3, priority: 'should' },
  { name: "用户账号系统", impact: 2, effort: 3, priority: 'should' },
  { name: "数据分析看板", impact: 2, effort: 4, priority: 'could' },
  { name: "自动发布到平台", impact: 2, effort: 5, priority: 'could' },
  { name: "团队协作", impact: 1, effort: 5, priority: 'wont' },
  { name: "品牌管理", impact: 1, effort: 4, priority: 'wont' }
].map(prioritizeFeature);

// Must Have（MVP 必须包含）：
// - AI 生成小红书文案
// - 用户输入菜品信息
// - 复制文案到剪贴板

// Should Have（MVP 后第一个迭代）：
// - 多平台适配
// - 文案模板库
// - 用户账号系统

// Could Have / Won't Have（后续版本）：
// - 数据分析、自动发布、团队协作、品牌管理
```

### 2.2 MoSCoW 方法

```
Must Have（必须有）：没有这个功能，产品就无法使用
Should Have（应该有）：重要但可以推迟到下一个版本
Could Have（可以有）：锦上添花，有时间就做
Won't Have（不会有）：这个版本明确不做

MVP = 只做 Must Have
```

### 2.3 用"用户故事"定义功能

每个功能都应该从用户故事的角度描述：


## 三、MVP 的类型

### 3.1 Landing Page MVP

```
适用场景：验证需求是否存在
验证假设：用户是否对这个产品感兴趣
开发成本：1-2 天
验证周期：1 周

做法：
- 搭建产品介绍页面
- 收集邮箱或预购
- 不需要任何后端开发
```

### 3.2 Wizard of Oz MVP

```
适用场景：验证 AI 能力是否满足需求
验证假设：AI 生成的内容是否让用户满意
开发成本：1-3 天
验证周期：1-2 周

做法：
- 前端看起来是 AI 在工作
- 实际上是人工在后台完成任务
- 用户不知道是人工做的

适用情况：
- 你不确定 AI 能否可靠完成任务
- 你想快速测试用户对输出质量的反应
- 你不想投入时间做 AI 集成
```

### 3.3 单功能 MVP

```
适用场景：验证核心功能的价值
验证假设：这个功能是否足够让用户付费
开发成本：1-2 周
验证周期：2-4 周

做法：
- 只做一个核心功能
- 界面简单但功能完整
- 不需要账号系统、不需要设置页面

示例：
一个页面：输入框（菜品信息）+ 生成按钮 + 结果展示 + 复制按钮
```

### 3.4 Concierge MVP

```
适用场景：验证完整的服务体验
验证假设：用户是否愿意为完整的服务流程付费
开发成本：2-4 周
验证周期：2-4 周

做法：
- 提供完整的服务，但部分环节由人工完成
- 随着验证通过，逐步用自动化替代人工
- 适合需要高度定制化的场景
```

## 四、MVP 设计实战

### 4.1 定义你的 MVP

用以下模板定义 MVP：

```markdown
## MVP 定义文档

### 核心假设
[你最需要验证的一个假设]

### 目标用户
[最具体的一个用户群体]

### 核心用户故事
作为 [用户]，我想 [做什么]，这样我就能 [获得什么价值]

### Must Have 功能
1. [功能 1] — [为什么必须有]
2. [功能 2] — [为什么必须有]
3. [功能 3] — [为什么必须有]

### 明确不做的功能
1. [功能 X] — [为什么不做]
2. [功能 Y] — [为什么不做]
3. [功能 Z] — [为什么不做]

### 成功标准
- [指标 1]：达到 X 算成功
- [指标 2]：达到 Y 算成功

### 时间预算
- 开发时间：X 天
- 验证周期：Y 周
```

### 4.2 实战示例：AI 餐饮营销助手 MVP

```markdown
## MVP 定义文档：AI 餐饮营销助手

### 核心假设
餐饮老板愿意为 AI 生成的小红书营销文案付费（¥49/月）

### 目标用户
个体餐饮老板（1-3 家门店），不雇营销人员，自己运营小红书

### 核心用户故事
作为餐饮老板，我想输入菜品信息后一键生成小红书文案，
这样我就不用花 30 分钟自己写文案了。

### Must Have 功能
1. 菜品信息输入（名称、价格、特色）— 获取 AI 生成所需的输入
2. AI 文案生成（小红书风格）— 核心价值
3. 文案复制功能 — 用户需要把文案粘贴到小红书
4. 3 种文案风格（种草/促销/日常）— 覆盖主要使用场景

### 明确不做的功能
1. 多平台支持 — 先只做小红书，验证后再扩展
2. 账号系统 — 用简单的 token 验证，不做注册登录
3. 数据分析 — MVP 阶段不需要
4. 自动发布 — 用户手动复制粘贴即可
5. 团队协作 — 只服务个体老板

### 成功标准
- 10 个用户连续使用 7 天
- 5 个用户愿意付费 ¥49/月
- 生成的文案 80% 被用户直接使用（不修改或少量修改）

### 时间预算
- 开发时间：7 天
- 验证周期：2 周
```

### 4.3 MVP 的技术架构

```typescript
// MVP 阶段的技术架构应该是最简单的
// 不要过度设计，不要引入不必要的复杂度

// 架构选择：Next.js + AI API + 简单数据库
const mvpArchitecture = {
  frontend: "Next.js（全栈框架，前后端一体）",
  ai: "OpenAI API（直接调用，不封装）",
  database: "SQLite 或 Vercel Postgres（最小化）",
  auth: "简单的 API Key 验证（不做完整账号系统）",
  deployment: "Vercel（一键部署）"
};

// 功能模块
const mvpModules = {
  // 1. 输入模块
  input: {
    fields: ["菜品名称", "价格", "特色描述"],
    validation: "基础校验（非空、长度限制）"
  },

  // 2. AI 生成模块
  generator: {
    model: "gpt-4o-mini",
    prompt: "根据菜品信息生成小红书风格的营销文案",
    styles: ["种草风", "促销风", "日常风"]
  },

  // 3. 输出模块
  output: {
    display: "展示生成的文案",
    copy: "一键复制到剪贴板",
    regenerate: "不满意可重新生成"
  }
};
```

## 五、砍功能的艺术

### 5.1 问自己三个问题

对每个想加的功能，问：

```
1. 这个功能对验证核心假设是必须的吗？
   不是 → 砍掉

2. 如果不做这个功能，用户就无法使用产品吗？
   不是 → 砍掉

3. 这个功能可以在下一个版本再加吗？
   可以 → 砍掉
```

### 5.2 常见的"伪需求"功能

```typescript
const pseudoFeatures = [
  {
    feature: "用户注册/登录系统",
    whyFake: "MVP 阶段可以用简单的 token 或邀请码",
    whenToBuild: "有了 100+ 用户后再做"
  },
  {
    feature: "管理后台",
    whyFake: "MVP 阶段直接操作数据库就行",
    whenToBuild: "需要频繁调整配置时再做"
  },
  {
    feature: "数据分析看板",
    whyFake: "MVP 阶段用日志 + 简单统计就够",
    whenToBuild: "有了稳定用户群后，用数据驱动决策"
  },
  {
    feature: "多语言支持",
    whyFake: "先做好一种语言，验证市场后再扩展",
    whenToBuild: "决定进入新市场时"
  },
  {
    feature: "移动端适配",
    whyFake: "先做桌面端，看用户是否真的需要移动端",
    whenToBuild: "用户反馈需要移动端时"
  }
];
```

### 5.3 "功能债务"思维

```
不是"不做"，而是"以后做"。

把砍掉的功能记在一个清单里，标注优先级。
MVP 验证通过后，根据用户反馈决定下一步做什么。

这样你既保持了 MVP 的聚焦，又不会遗漏重要的功能。
```

## 六、MVP 的时间管理

### 6.1 时间盒（Timeboxing）

```
给 MVP 一个明确的时间限制：

Week 1：
├── Day 1-2：搭建项目框架 + AI 集成
├── Day 3-4：核心功能开发
├── Day 5：UI 简单美化
├── Day 6：测试和修复
└── Day 7：部署上线

原则：
- 时间到了就发布，不管"完不完美"
- 宁可功能少，也不要延期
- "完成"比"完美"重要
```

### 6.2 80/20 法则

```
80% 的价值来自 20% 的功能。

在 AI 餐饮营销助手的例子中：
- 80% 的价值 = 输入菜品 → 生成文案 → 复制使用
- 剩余 20% 的价值 = 多平台、模板库、数据分析、团队协作

MVP 只做那 20% 的核心功能。
```

## 常见误区

### 误区一：把 MVP 做成"完整但简陋的产品"

"我先把账号系统做好，再加上支付，然后做核心功能……"——这是最常见的错误。MVP 的顺序应该是：先做核心功能，验证通过后再加其他。

### 误区二：害怕发布"不完美"的产品

你的 MVP 一定会有很多问题：界面丑陋、功能不全、偶尔出 bug。这没关系。MVP 的目的不是展示你的技术能力，而是验证用户需求。

### 误区三：忽视"明确不做的功能"

只列出"要做什么"是不够的。你必须明确"不做什么"，并且把这些决定写下来。当团队成员或用户提出新需求时，你可以用这份清单来拒绝。

### 误区四：MVP 做完就不迭代

MVP 是起点，不是终点。上线后收集用户反馈，快速迭代，逐步增加功能。不要做完 MVP 就开始做"V2.0"，而是持续小步迭代。

## 工程建议

### 1. 用脚手架工具加速

Next.js、Vite、Create React App 等脚手架工具可以帮你跳过项目初始化的繁琐工作。不要从零搭建项目。

### 2. 用第三方服务减少开发量

```
认证：Clerk、Auth0、NextAuth（不要自己做）
支付：Stripe、LemonSqueezy（不要自己做支付逻辑）
邮件：Resend、SendGrid（不要自己搭邮件服务）
部署：Vercel、Netlify（不要自己配服务器）
```

### 3. 写"刚好够用"的代码

MVP 阶段的代码不需要完美。不需要设计模式、不需要过度抽象、不需要完美的类型定义。能跑就行，验证通过后再重构。

### 4. 保持部署的简单性

MVP 阶段应该能一键部署。Vercel + GitHub 的组合可以实现 push 后自动部署。不要在运维上浪费时间。

## 小结

- MVP 的目的是**验证假设**，不是发布产品
- 用 MoSCoW 方法排序功能，MVP 只做 Must Have
- 用"用户故事"定义功能范围，每个故事有明确的验收标准
- 常见 MVP 类型：Landing Page、Wizard of Oz、单功能、Concierge
- 给 MVP 设定时间盒，"完成"比"完美"重要

## 练习

1. **功能排序**：为你选定的产品列出 15 个想做的功能，用"影响-努力"矩阵排序，选出 5 个 Must Have。

2. **MVP 定义**：用 MVP 定义文档模板，为你的产品写一份 MVP 定义。重点回答：核心假设是什么？验证它需要的最小功能集是什么？

3. **砍功能练习**：如果你只能用 7 天开发 MVP，你会保留哪些功能？砍掉哪些？为什么？

4. **MVP 类型选择**：你的产品最适合哪种 MVP 类型（Landing Page / Wizard of Oz / 单功能 / Concierge）？为什么？

## 参考答案

### 练习一：功能排序

**思路**：先列出所有想做的功能，然后用"影响-努力"矩阵对每个功能打分（影响 1-5 分，努力 1-5 分），计算比值（影响/努力）。比值 ≥ 2 的是 Must Have，1-2 的是 Should Have，0.5-1 的是 Could Have，< 0.5 的是 Won't Have。

**答案**：

```typescript
// 以 AI 餐饮营销助手为例的功能排序
const features = [
  // Must Have（影响/努力 ≥ 2）
  { name: "菜品信息输入（名称、价格、特色）", impact: 5, effort: 1, ratio: 5.0, priority: "Must" },
  { name: "AI 生成小红书文案", impact: 5, effort: 2, ratio: 2.5, priority: "Must" },
  { name: "一键复制文案", impact: 4, effort: 1, ratio: 4.0, priority: "Must" },
  { name: "3 种文案风格选择", impact: 4, effort: 2, ratio: 2.0, priority: "Must" },
  { name: "错误提示与加载状态", impact: 4, effort: 2, ratio: 2.0, priority: "Must" },

  // Should Have（比值 1-2）
  { name: "文案历史记录", impact: 3, effort: 2, ratio: 1.5, priority: "Should" },
  { name: "重新生成", impact: 3, effort: 1, ratio: 3.0, priority: "Must" },
  { name: "多平台适配（抖音/朋友圈）", impact: 3, effort: 3, ratio: 1.0, priority: "Should" },

  // Could Have（比值 0.5-1）
  { name: "文案模板库", impact: 3, effort: 4, ratio: 0.75, priority: "Could" },
  { name: "用户账号系统", impact: 2, effort: 3, ratio: 0.67, priority: "Could" },
  { name: "文案效果数据追踪", impact: 2, effort: 4, ratio: 0.5, priority: "Could" },

  // Won't Have（比值 < 0.5）
  { name: "自动发布到小红书", impact: 2, effort: 5, ratio: 0.4, priority: "Won't" },
  { name: "数据分析看板", impact: 1, effort: 4, ratio: 0.25, priority: "Won't" },
  { name: "团队协作", impact: 1, effort: 5, ratio: 0.2, priority: "Won't" },
  { name: "品牌管理", impact: 1, effort: 4, ratio: 0.25, priority: "Won't" },
];
```

**要点**：
- "影响"的判断标准是对核心假设验证的帮助程度，不是"用户觉得好不好"
- Must Have 不超过 5 个，否则 MVP 就不是"最小"了
- "重新生成"看似小功能，但对用户体验影响大，容易被忽略
- 砍掉的功能不是不做，是"以后做"，记在功能债务清单里

### 练习二：MVP 定义

**思路**：用课程中的 MVP 定义文档模板，围绕"核心假设"展开。先明确你最需要验证的一个假设，再反推验证它需要的最小功能集。关键是把范围缩到最小——如果一个功能不能直接帮助验证核心假设，就砍掉。

**答案**：

```markdown
## MVP 定义文档：AI 餐饮营销助手

### 核心假设
餐饮老板愿意为 AI 生成的小红书营销文案付费（¥49/月）

### 目标用户
个体餐饮老板（1-3 家门店），不雇营销人员，自己运营小红书，每天花 30 分钟以上写文案

### 核心用户故事
作为餐饮老板，我想输入菜品信息后一键生成小红书文案，这样我就不用花 30 分钟自己写文案了。

### Must Have 功能
1. 菜品信息输入（名称、价格、特色）— 获取 AI 生成所需的输入
2. AI 文案生成（小红书风格）— 核心价值所在
3. 文案复制功能 — 用户需要把文案粘贴到小红书
4. 3 种文案风格（种草/促销/日常）— 覆盖主要使用场景
5. 重新生成 — 用户可能对第一次结果不满意

### 明确不做的功能
1. 多平台支持 — 先只做小红书，验证后再扩展
2. 账号系统 — MVP 阶段不需要用户管理
3. 数据分析 — MVP 阶段用日志记录即可
4. 自动发布 — 用户手动复制粘贴即可
5. 团队协作 — 只服务个体老板
6. 模板库 — 先用 Prompt 覆盖不同场景

### 成功标准
- 10 个用户连续使用 7 天
- 5 个用户愿意付费 ¥49/月
- 生成的文案 80% 被用户直接使用（不修改或少量修改）

### 时间预算
- 开发时间：7 天
- 验证周期：2 周
```

**要点**：
- 核心假设只能有一个，不能同时验证多个假设
- "明确不做的功能"和"Must Have"一样重要，写下来才能抵抗功能膨胀的诱惑
- 成功标准必须是可量化的，"用户觉得好用"不算成功标准
- 时间预算要严格遵守，时间到了就发布

### 练习三：砍功能练习

**思路**：如果只有 7 天，用"这个功能对验证核心假设是必须的吗？"这个问题逐个过滤。先做能让用户完成核心流程的功能（输入 → 生成 → 复制），其他全部砍掉。

**答案**：

```markdown
## 7 天 MVP 功能决策

### 保留的功能（3 个）
1. **菜品信息输入 + AI 文案生成** — 没有这个，产品不存在
2. **一键复制文案** — 没有这个，用户无法使用生成的文案
3. **基础错误处理** — API 失败时不能白屏，要有友好提示

### 砍掉的功能及理由

| 功能 | 砍掉理由 | 替代方案 |
|------|---------|---------|
| 用户注册/登录 | 不影响核心验证，用 session 或匿名使用 | 不做 |
| 3 种文案风格 | 先做"种草"一种风格，用 Prompt 控制 | 下个版本加 |
| 重新生成 | 用户可以刷新页面重新输入 | 下个版本加 |
| 数据库记录 | MVP 阶段不需要历史记录 | 用 Vercel 日志 |
| UI 美化 | Tailwind 默认样式已经够用 | 有时间再优化 |
| 移动端适配 | 先做桌面端，看用户是否需要 | 用响应式布局自动适配 |
| 反馈组件 | 上线后用微信收集反馈 | 下个版本加 |

### 7 天开发计划
- Day 1：项目初始化 + 基础页面
- Day 2：AI API 集成 + Prompt 设计
- Day 3：前后端联调
- Day 4：错误处理 + Loading 状态
- Day 5：测试和修复
- Day 6：部署上线
- Day 7：找 3 个用户试用 + 修 bug
```

**要点**：
- 砍功能的标准是"没有这个功能，用户能否完成核心流程"
- "3 种风格"看似重要，但一种风格就能验证核心假设
- 替代方案很重要——不是"不做"，是"用更简单的方式解决"
- 7 天时间很紧，任何犹豫都会导致延期

### 练习四：MVP 类型选择

**思路**：根据产品的核心假设和风险选择 MVP 类型。如果核心风险是"需求是否存在"，选 Landing Page；如果核心风险是"AI 能否可靠完成任务"，选 Wizard of Oz；如果核心风险是"功能是否有价值"，选单功能 MVP。

**答案**：

```markdown
## MVP 类型分析

### 产品：AI 餐饮营销助手

#### 核心风险评估
| 风险 | 严重程度 | 说明 |
|------|---------|------|
| 需求是否存在 | 中 | 已通过 Landing Page 初步验证 |
| AI 能否生成高质量文案 | 高 | Prompt 质量、风格匹配、行业术语 |
| 用户是否会持续使用 | 高 | 一次性使用 vs 长期依赖 |
| 用户是否愿意付费 | 高 | 价格敏感度未知 |

#### 推荐类型：单功能 MVP

**理由**：
1. 需求已通过 Landing Page 验证，不需要再做 Landing Page MVP
2. 核心风险在 AI 质量和付费意愿，需要用户实际使用后才能验证
3. 单功能 MVP 可以让用户完整体验"输入 → 生成 → 复制"的流程
4. 开发成本适中（1-2 周），验证周期合理（2-4 周）

**为什么不选其他类型**：
- Landing Page：需求已验证，不需要重复
- Wizard of Oz：AI 已经能调用 API，不需要人工模拟
- Concierge：产品不需要高度定制化服务

#### MVP 范围
只做一个页面：输入框（菜品信息）+ 生成按钮 + 结果展示 + 复制按钮
不做账号、不做历史记录、不做多平台、不做数据分析
```

**要点**：
- MVP 类型选择取决于"你最需要验证什么"，不是"哪种最简单"
- Wizard of Oz 适合验证 AI 能力但不想投入开发的场景
- 单功能 MVP 是最常见的选择，适合核心功能明确的产品
- 选择后要明确写出"为什么不选其他类型"，这能帮你想清楚决策逻辑
