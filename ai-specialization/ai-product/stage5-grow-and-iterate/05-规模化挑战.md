# 第5课：规模化挑战

> **课程定位**：理解产品规模化过程中的技术、组织和运营挑战
> **前置知识**：产品已有一定用户量
> **预计时长**：30 分钟

---

## 场景引入

你的 AI 产品从 100 个用户增长到了 10000 个用户。恭喜，但问题也来了：数据库查询变慢了，API 成本翻了 10 倍，你一个人改不过来代码了，用户投诉开始增多。规模化的挑战不是"能不能继续增长"，而是"增长了你能不能扛住"。

---

### 1.3 重构策略

```typescript
// 重构决策框架
function shouldRefactor(params: {
  painLevel: number       // 当前痛点程度（1-10）
  frequency: number       // 遇到频率（每天/每周/每月）
  effort: number          // 重构工作量（人天）
  risk: number            // 重构风险（1-10）
}): { shouldRefactor: boolean; priority: string } {
  const score = (params.painLevel * params.frequency) / (params.effort * params.risk)

  if (score >= 1) return { shouldRefactor: true, priority: '立即重构' }
  if (score >= 0.5) return { shouldRefactor: true, priority: '下个迭代重构' }
  return { shouldRefactor: false, priority: '继续观察' }
}
```

```typescript
// lib/cache/strategy.ts
export const cacheStrategy = {
  // 用户信息缓存
  user: {
    key: (userId: string) => `user:${userId}`,
    ttl: 300,  // 5 分钟
    invalidation: '写入时更新',
  },

  // 文档列表缓存
  documents: {
    key: (userId: string) => `docs:${userId}`,
    ttl: 60,  // 1 分钟（变化频繁）
    invalidation: '文档变更时清除',
  },

  // AI 回答缓存（相同问题可以复用）
  aiResponse: {
    key: (question: string) => `ai:${hash(question)}`,
    ttl: 3600,  // 1 小时
    invalidation: '文档更新时清除相关缓存',
  },

  // 热门内容缓存
  hotContent: {
    key: 'hot:questions',
    ttl: 300,
    invalidation: '定时更新',
  },
}

// Redis 缓存实现
export class CacheManager {
  private redis: Redis

  async get<T>(key: string): Promise<T | null> {
    const cached = await this.redis.get(key)
    return cached ? JSON.parse(cached) : null
  }

  async set(key: string, value: unknown, ttl: number) {
    await this.redis.set(key, JSON.stringify(value), 'EX', ttl)
  }

  async invalidate(pattern: string) {
    const keys = await this.redis.keys(pattern)
    if (keys.length > 0) {
      await this.redis.del(...keys)
    }
  }
}
```

### 3.2 成本监控

```typescript
// lib/cost/monitor.ts
export class CostMonitor {
  async getDailyCostReport() {
    const today = new Date().toISOString().split('T')[0]

    // 各功能的 AI 调用成本
    const featureCosts = await db.usageLog.groupBy({
      by: ['feature'],
      where: { date: today },
      _sum: { tokens: true, cost: true },
    })

    // 总成本
    const totalCost = featureCosts.reduce((sum, f) => sum + (f._sum.cost ?? 0), 0)

    // 预警
    const alerts = []
    if (totalCost > 100) alerts.push('日成本超过 $100')

    for (const feature of featureCosts) {
      if ((feature._sum.cost ?? 0) > 50) {
        alerts.push(`${feature.feature} 成本超过 $50`)
      }
    }

    return { date: today, featureCosts, totalCost, alerts }
  }
}
```

## 常见误区

### 误区一：过早优化

用户量 100 时不需要微服务架构。过早优化会增加复杂度，拖慢迭代速度。先用简单方案，遇到瓶颈再优化。

### 误区二：技术债务无限累积

不处理技术债务，代码会越来越难改。定期安排 20% 的时间处理技术债务。

### 误区三：盲目招人

招人不是解决所有问题的答案。招错人的成本远高于不招人。先确认有明确的、可交付的工作，再招人。

### 误区四：忽略运营成本

规模化后，服务器、AI API、客服、监控的成本会快速增长。要持续监控成本，确保增长是可持续的。

---

## 工程建议

### 1. 先测量，再优化

不要猜测瓶颈在哪，用工具测量。数据库慢查询日志、API 响应时间监控、错误追踪——用数据指导优化。

### 2. 保持简单

能用单体解决就不要用微服务，能用缓存解决就不要改架构。简单方案的维护成本最低。

### 3. 自动化一切

手动操作不可持续。CI/CD、自动化测试、自动化部署、自动化监控——能自动化的都自动化。

### 4. 写文档

代码会变，人会走，但文档会留下来。关键的架构决策、业务逻辑、运维流程都要有文档。

---

## 小结

规模化的核心挑战：技术债务（代码质量下降）、架构扩展（系统扛不住）、团队扩展（人力不足）、运营成本（成本失控）。应对策略：定期偿还技术债务、按需演进架构、适时招人、持续监控成本。保持简单，不过早优化。

### 练习二：性能测试

**思路**：性能测试的目标是找到系统的瓶颈在哪里。从正常负载开始，逐步增加压力，直到系统出现性能下降。重点关注响应时间、吞吐量、错误率三个指标。

**答案**：

```typescript
// API 性能测试方案

// 测试工具：使用 k6（开源性能测试工具）
// 安装：npm install -g k6

// 测试脚本：test-api-performance.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '1m', target: 10 },   // 1 分钟内逐步增加到 10 个并发用户
    { duration: '3m', target: 10 },   // 保持 10 个用户运行 3 分钟
    { duration: '1m', target: 50 },   // 1 分钟内增加到 50 个并发用户
    { duration: '3m', target: 50 },   // 保持 50 个用户运行 3 分钟
    { duration: '1m', target: 100 },  // 1 分钟内增加到 100 个并发用户
    { duration: '3m', target: 100 },  // 保持 100 个用户运行 3 分钟
    { duration: '2m', target: 0 },    // 2 分钟内逐步降到 0
  ],
  thresholds: {
    http_req_duration: ['p(95)<2000'],  // 95% 的请求响应时间 < 2 秒
    http_req_failed: ['rate<0.01'],     // 错误率 < 1%
  },
};

export default function () {
  // 测试文档上传 API
  const uploadRes = http.post('https://your-api.com/api/documents/upload', {
    file: open('./test-document.pdf', 'b'),
  });
  check(uploadRes, {
    'upload status is 200': (r) => r.status === 200,
    'upload time < 5s': (r) => r.timings.duration < 5000,
  });

  sleep(1);

  // 测试问答 API（核心接口）
  const queryRes = http.post('https://your-api.com/api/query', {

    'query status is 200': (r) => r.status === 200,
```

**要点**：

- 先测正常负载，再逐步加压，找到拐点（性能开始下降的点）
- 测试结果要记录下来，作为后续优化的基线
