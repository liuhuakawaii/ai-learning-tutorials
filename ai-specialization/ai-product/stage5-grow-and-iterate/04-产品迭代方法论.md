## 二、优先级框架

### 2.1 RICE 评分

```typescript
// RICE = Reach × Impact × Confidence / Effort
function calculateRICE(params: {
  reach: number      // 影响多少用户（每季度）
  impact: number     // 对用户的影响程度（0.25/0.5/1/2/3）
  confidence: number // 对估算的信心（0.5/0.8/1）
  effort: number     // 人月
}): { score: number; priority: string } {
  const { reach, impact, confidence, effort } = params
  const score = (reach * impact * confidence) / effort

  let priority: string
  if (score >= 100) priority = 'P0 - 立即做'
  else if (score >= 50) priority = 'P1 - 下个迭代'
  else if (score >= 20) priority = 'P2 - 计划中'
  else priority = 'P3 - 考虑中'

  return { score: Math.round(score), priority }
}

// 示例
const features = [
  {
    name: '支持 Word 文档上传',
    reach: 500,        // 500 用户/季度会用到
    impact: 1,         // 中等影响
    confidence: 0.8,   // 比较确定
    effort: 0.5,       // 半个人月
    // RICE = 500 × 1 × 0.8 / 0.5 = 800 → P0
  },
  {
    name: '语音输入功能',
    reach: 50,
    impact: 0.5,
    confidence: 0.5,
    effort: 2,
    // RICE = 50 × 0.5 × 0.5 / 2 = 6.25 → P3
  },
]
```

## 常见误区

### 误区一：用户要什么就做什么

用户说的需求不一定是真正的需求。用户说"我要一匹更快的马"，真正的需求是"更快地到达目的地"。要理解需求背后的问题。

### 误区二：功能越多越好

功能越多，产品越复杂，用户越困惑。少做几个功能，把核心功能做到极致，比做一堆平庸的功能更有价值。

### 误区三：不做验证直接开发

开发一个功能的成本远高于验证一个想法的成本。在写代码之前，先用原型、Mockup 或者假门测试验证需求。

### 误区四：上线后不追踪效果

功能上线不等于成功。上线后要追踪指标，验证是否达到了预期效果。如果没有，要分析原因并调整。

## 工程建议

### 1. 建立反馈闭环

用户提了反馈 → 告知用户已收到 → 功能上线后通知用户。这个闭环让用户感到被重视，也鼓励更多反馈。

### 2. 用数据说话

每个功能决策都要有数据支撑：多少用户有这个需求？预期影响多大？开发成本多高？

### 3. 保持迭代节奏

固定的迭代节奏（双周）比"做完再发"更健康。节奏带来可预测性，可预测性带来信任。

### 4. 学会说"不"

80% 的需求不应该做。说"不是现在"比说"好"更需要勇气，但这是产品经理最重要的能力。

---

## 小结

产品迭代的核心是：收集反馈 → 评估优先级 → 快速验证 → 迭代交付 → 追踪效果。用 RICE 框架决定做什么，用双周迭代保持节奏，用数据验证效果。最重要的是学会说"不"——不是所有需求都值得做。

## 参考答案

### 练习一：反馈收集

**思路**：反馈收集机制要让提交反馈尽可能简单（降低门槛），同时支持投票让需求自然排序（减少主观判断）。关键是闭环——用户提交的反馈要有回应。

**答案**：

```typescript
// 反馈收集系统设计

// 数据模型
interface Feedback {
  id: string;
  userId: string;
  title: string;
  description: string;
  category: 'bug' | 'feature' | 'improvement' | 'question';
  status: 'open' | 'planned' | 'in_progress' | 'done' | 'wont_do';
  votes: number;
  votedBy: string[];
  createdAt: Date;
  updatedAt: Date;
}

// 反馈提交 API
async function submitFeedback(userId: string, data: {
  title: string;
  description: string;
  category: Feedback['category'];
}) {
  // 检查是否有重复反馈
  const existing = await db.query(
    'SELECT * FROM feedback WHERE title LIKE ? AND status != ?',
    [`%${data.title}%`, 'wont_do']
  );

  if (existing.length > 0) {
    // 如果已有类似反馈，自动投票而不是重复创建
    await voteFeedback(userId, existing[0].id);
    return { action: 'voted', feedbackId: existing[0].id };
  }

  // 创建新反馈
  const feedback = await db.insert('feedback', {
    userId,
    title: data.title,
    description: data.description,
    category: data.category,
    status: 'open',
    votes: 1,
    votedBy: [userId],
  });

  // 通知产品团队（通过飞书/Slack webhook）
  await notifyTeam(`新反馈：${data.title}`, {
    category: data.category,
    user: userId,
  });

  return { action: 'created', feedbackId: feedback.id };
}

// 投票 API
async function voteFeedback(userId: string, feedbackId: string) {
  const feedback = await db.query('SELECT * FROM feedback WHERE id = ?', [feedbackId]);

  if (feedback.votedBy.includes(userId)) {
    return { error: '你已经投过票了' };
  }

  await db.query(
    'UPDATE feedback SET votes = votes + 1, votedBy = JSON_ARRAY_APPEND(votedBy, ?) WHERE id = ?',
    [userId, feedbackId]
  );

  return { success: true };
}

// 反馈状态更新（产品团队使用）
async function updateFeedbackStatus(feedbackId: string, status: Feedback['status'], reason?: string) {
  await db.query('UPDATE feedback SET status = ?, updated_at = NOW() WHERE id = ?', [status, feedbackId]);

  // 通知所有投票的用户
  const feedback = await db.query('SELECT * FROM feedback WHERE id = ?', [feedbackId]);
  for (const userId of feedback.votedBy) {
    await notifyUser(userId, `你关注的反馈"${feedback.title}"状态已更新为：${status}${reason ? `，原因：${reason}` : ''}`);
  }
}
```

**要点**：
- 反馈去重：相似反馈自动合并为投票，避免重复条目
- 状态闭环：用户提交的反馈要有状态更新和通知
- 投票机制让用户自己排序需求，减少产品团队的主观判断

### 练习二：RICE 评估

**思路**：RICE 框架的四个维度——Reach（影响多少用户）、Impact（影响多大）、Confidence（有多大把握）、Effort（需要多少工作量）——帮助你用数据而非直觉做决策。每个维度都要有明确的评分标准。

**答案**：

```typescript
// RICE 评分示例：10 个待做功能

const features = [
  {
    name: '支持语音输入提问',
    reach: 800,        // 每季度 800 个用户会使用
    impact: 2,         // 中等影响（0.25=微小, 0.5=低, 1=中, 2=高, 3=巨大）
    confidence: 0.8,   // 80% 把握（有用户调研支持）
    effort: 3,         // 需要 3 人周
    riceScore: 800 * 2 * 0.8 / 3, // = 426.7
  },
  {
    name: '支持更多文件格式（PPT、Excel）',
    reach: 1200,
    impact: 2,
    confidence: 0.9,

  {

    reach: 300,
    impact: 3,
    confidence: 0.7,
    effort: 10,

  {

  {

    effort: 2,

  {

    reach: 400,

    confidence: 0.6,
    effort: 4,
    riceScore: 400 * 0.5 * 0.6 / 4, // = 30
  },
  {
    name: '支持多语言文档',
    reach: 500,
    impact: 2,
    confidence: 0.7,

  },
  {
    name: '文档版本对比功能',
    reach: 150,
    impact: 2,
    confidence: 0.5,
    effort: 6,
    riceScore: 150 * 2 * 0.5 / 6, // = 25
  },
  {
    name: '暗色模式',
    reach: 1500,
    impact: 0.25,
    confidence: 0.9,
    effort: 2,
    riceScore: 1500 * 0.25 * 0.9 / 2, // = 168.75
  },
];

// 按 RICE 分数排序
const ranked = features.sort((a, b) => b.riceScore - a.riceScore);
// 优先顺序：
// 1. 支持更多文件格式（432）
// 2. 支持语音输入（426.7）
// 3. 导出 PDF（270）
// 4. 移动端适配（266.7）
// 5. 暗色模式（168.75）
// 6. 多语言支持（87.5）
// 7. API 接口（67.5）
// 8. 团队协作（63）
// 9. 自定义风格（30）
// 10. 版本对比（25）
```

**要点**：
- RICE 分数是参考不是绝对答案，要结合战略方向综合判断
- Confidence 低的功能要先做小规模验证再投入大量资源
- Effort 估算要让开发团队参与，不能产品自己拍脑袋

**要点**：
- Now/Next/Later 比精确时间表更适合早期产品——变化快，精确排期容易过时
- 路线图要公开给团队，让所有人知道方向和优先级
- "不做"列表和"要做"列表一样重要，明确说"不"才能聚焦

### 练习四：迭代复盘

**思路**：迭代复盘的核心是"做得好的继续保持，做得不好的下次改进"。复盘不是追责，而是学习。要从结果数据出发，而不是从感受出发。

**答案**：

```typescript
// 迭代复盘模板

const retrospective = {
  // 基本信息
  sprint: 'Sprint #6（2024.03.01 - 2024.03.14）',
  goal: '上线文件格式扩展功能（支持 PPT、Excel）',
  result: '目标完成，但延期 2 天',

  // 做得好的（继续保持）
  wentWell: [
    {
      item: '需求拆分合理',
      detail: '将"支持 PPT"拆成了 3 个子任务，每个都能独立上线',
      impact: '避免了大功能一次性上线的风险',
    },
    {
      item: '测试覆盖充分',
      detail: '写了 15 个单元测试 + 3 个集成测试',
      impact: '上线后没有出现严重 bug',
    },
  ],

  // 做得不好的（需要改进）
  wentWrong: [
    {
      item: '时间估算不准',
      detail: '预估 5 天，实际 7 天',
      reason: '低估了 PPT 解析库的兼容性问题',
      improvement: '下次技术调研时先做 spike（技术探针），再估算',
    },
    {
      item: '需求中途变更',
      detail: '开发到一半，用户反馈 Excel 公式也需要支持',
      reason: '需求评审时没有覆盖边界场景',
      improvement: '需求评审时列出"不做"清单，明确边界',
    },
  ],

  // 学到的经验
  learnings: [
    '技术探针（spike）能大幅减少估算误差',
    '需求评审要覆盖"不做什么"，不只是"做什么"',
    '小步快跑比大功能一次性上线更安全',
  ],

  // 下次迭代的改进项
  actionItems: [
    {
      action: 'Sprint #7 开始前先做 1 天 spike',
      owner: '技术负责人',
      deadline: 'Sprint #7 Day 1',
    },
    {
      action: '需求评审增加"边界场景和不做清单"环节',
      owner: '产品经理',
      deadline: 'Sprint #7 需求评审会',
    },
  ],
};
```

**要点**：
- 复盘要基于数据，不是感受——"延期 2 天"比"感觉做得不好"更有价值
- 每次复盘都要有可执行的改进项（action items），不能只停留在"下次注意"
- 复盘是团队活动，不是产品经理一个人的事
