# 第一课：AI 产品思维

## 场景引入

你刚学会调用 OpenAI 的 API，能用几行代码让 GPT 帮用户写邮件、总结文档、翻译段落。你兴奋地想："这东西太强了，随便包装一下就能卖钱！"于是你花了一个周末做了一个"AI 写作助手"，上线后却发现——没人用。用户说"我用 ChatGPT 就行了"，投资人问"你跟 ChatGPT 有什么区别"，你自己也答不上来。

问题出在哪？不是技术不行，是你还在用"技术思维"做产品。AI 产品的核心竞争力不在模型本身，而在于你如何把 AI 能力嵌入到用户的真实工作流中，解决一个具体到"非你不可"的问题。这一课，我们来完成从工程师到产品人的思维转变。

## 学习目标

1. 理解技术思维与产品思维的核心差异
2. 掌握 AI 产品与传统软件产品的关键区别
3. 学会用"用户问题驱动"而非"技术能力驱动"的方式思考产品
4. 建立 AI 产品的评估框架

## 一、技术思维 vs 产品思维

### 1.1 工程师的常见陷阱

作为开发者，我们天然倾向于从技术出发思考问题：

- "GPT-4 的能力很强，可以做 XXX"
- "这个模型的准确率达到了 95%，肯定有市场"
- "我用 RAG + Agent 做了一个很酷的 demo"

这些都是**技术驱动**的思维方式。它的核心问题是：你在找一个能用上这项技术的场景，而不是在找一个值得被解决的问题。

### 1.2 产品思维的本质

产品思维的起点完全不同：

```
技术思维：我有锤子 → 找钉子
产品思维：用户有痛点 → 找最佳解决方案（可能是锤子，也可能不是）
```

产品思维的核心问题只有三个：
1. **谁**有这个问题？（目标用户）
2. 这个问题**有多痛**？（支付意愿）
3. 现有方案**差在哪**？（你的机会）

### 1.3 一个真实的对比

| 维度 | 技术思维 | 产品思维 |
|------|---------|---------|
| 出发点 | GPT-4 能做什么 | 用户在什么场景下浪费了最多时间 |
| 核心指标 | 模型准确率、响应速度 | 用户留存率、付费转化率 |
| 竞争壁垒 | 我用了更先进的模型 | 我比任何人都懂这个行业的痛点 |
| 失败原因 | 技术方案不成熟 | 没人愿意为这个功能付钱 |

## 二、AI 产品与传统软件的核心差异

### 2.1 确定性 vs 概率性

传统软件是确定性的——用户点按钮 A，一定出现结果 B。但 AI 产品是概率性的——同一个输入，可能得到不同的输出。

```typescript
// 传统软件：确定性逻辑
function calculateDiscount(price: number, isVip: boolean): number {
  return isVip ? price * 0.8 : price;
}
// 输入相同，输出永远相同

// AI 产品：概率性逻辑
async function generateEmailReply(incomingEmail: string): Promise<string> {
  const response = await openai.chat.completions.create({
    model: "gpt-4",
    messages: [
      { role: "system", content: "你是一个专业的邮件回复助手" },
      { role: "user", content: `请回复这封邮件：${incomingEmail}` }
    ],
    temperature: 0.7  // 同样的输入，每次输出可能不同
  });
  return response.choices[0].message.content;
}
```

这意味着 AI 产品需要额外设计：
- **兜底机制**：AI 输出质量不达标时怎么处理？
- **用户预期管理**：如何让用户理解"有时候会出错"？
- **反馈回路**：用户如何纠正 AI 的错误？

### 2.2 功能价值 vs 智能价值

传统产品的价值在于"功能"——它能做某件事。AI 产品的价值在于"智能"——它能**理解**你的意图并做出合理判断。

这导致了一个关键区别：**用户对 AI 产品的期望是动态的**。

用户不会因为你能"自动生成周报"就满意，他们会问：
- 能不能按我们公司的格式来？
- 能不能自动从 JIRA 拉取本周的 task？
- 能不能区分"已完成"和"进行中"的事项？

每一个追问都是在要求 AI 产品更"懂"用户。这就是为什么 AI 产品的核心壁垒不是模型能力，而是**对用户场景的深度理解**。

### 2.3 开发周期的差异

```
传统软件：需求 → 设计 → 开发 → 测试 → 上线 → 迭代
         （每个阶段相对可预测）

AI 产品：需求 → 原型 → Prompt 调优 → 评估 → 上线 → 收集 badcase → 优化 Prompt → 再评估
         （Prompt 调优和评估可能反复多次，时间不可预测）
```

AI 产品开发中，最大的不确定性来自模型行为的不可预测性。你需要为"调 Prompt"预留大量时间，这是传统开发中不存在的环节。

## 三、AI 产品的四种类型

理解 AI 产品的类型，有助于你定位自己想做的产品属于哪一类。

### 3.1 效率工具型

**核心逻辑**：用 AI 替代用户完成重复性工作。

```
典型案例：
- Jasper：AI 营销文案
- GitHub Copilot：AI 代码补全
- Notion AI：AI 文档辅助

关键指标：节省时间（用户愿意为省下的时间付费）
壁垒：对工作流的深度集成
```

### 3.2 体验增强型

**核心逻辑**：用 AI 让现有体验变得更好。

```
典型案例：
- Spotify 推荐：AI 让听歌体验更个性化
- 美颜相机：AI 让拍照更好看
- 智能客服：AI 让客服响应更快

关键指标：用户满意度、使用频次
壁垒：数据飞轮（越多用户用，体验越好）
```

### 3.3 能力扩展型

**核心逻辑**：用 AI 让用户做到以前做不到的事。

```
典型案例：
- Midjourney：让不会画画的人生成图片
- Runway：让不会剪辑的人做视频
- Cursor：让非专业开发者写代码

关键指标：新用户转化（吸引原来不用这类工具的人）
壁垒：降低门槛的体验设计
```

### 3.4 行业重构型

**核心逻辑**：用 AI 重新定义某个行业的工作方式。

```
典型案例：
- Harvey：AI 法律助手，重构法律工作流
- Abridge：AI 医疗记录，重构医生问诊流程
- 企业级 RAG 系统：重构知识管理方式

关键指标：行业渗透率
壁垒：行业 know-how + 数据壁垒
```

## 四、用"问题-方案-能力"框架评估 AI 产品

当你有一个产品想法时，用这个框架快速评估：

```typescript
interface AIProductIdea {
  // 问题层
  targetUser: string;        // 谁？
  painPoint: string;         // 什么痛点？
  currentSolution: string;   // 现在怎么解决？
  painLevel: 1 | 2 | 3 | 4 | 5;  // 有多痛？（5 = 愿意立刻付钱）

  // 方案层
  coreAction: string;        // 用户的核心动作是什么？
  aiRole: string;            // AI 在其中扮演什么角色？
  nonAIValue: string;        // 除了 AI，你还提供什么价值？

  // 能力层
  aiCapability: string;      // 需要 AI 做什么？
  reliability: 'high' | 'medium' | 'low';  // AI 完成这个任务的可靠度
  fallbackPlan: string;      // AI 不可靠时怎么办？
}

// 评估示例：AI 周报生成器
const example: AIProductIdea = {
  targetUser: "互联网公司的产品经理",
  painPoint: "每周五花 1-2 小时写周报，内容琐碎且重复",
  currentSolution: "手动整理 JIRA ticket + 回忆本周工作 + 套模板",
  painLevel: 3,  // 痛，但不是最痛的

  coreAction: "一键生成周报初稿",
  aiRole: "从多个数据源提取信息并组织成文",
  nonAIValue: "与 JIRA/日历/Slack 的集成、公司周报模板",

  aiCapability: "信息提取 + 文本生成",
  reliability: "medium",  // 可能遗漏重要事项或加入不存在的内容
  fallbackPlan: "生成初稿 + 用户必须审核修改"
};
```

这个框架的关键在于：**AI 能力（第三层）决定了方案可行性，但问题（第一层）决定了产品是否有价值**。

再强的 AI 能力，如果解决的是一个"可有可无"的问题，产品也活不下去。

## 五、AI 产品思维的核心原则

### 原则一：从"AI 能做什么"转向"用户需要什么"

不要先看模型能力再找场景，而是先找到真实痛点再评估 AI 是否适合。

```
错误路径：GPT 能生成代码 → 做一个 AI 写代码的产品
正确路径：开发者在写重复代码时浪费大量时间 → AI 代码补全 → 评估 GPT 能否胜任
```

### 原则二：AI 是手段，不是目的

用户不关心你用了什么模型、多先进的技术。他们只关心：这个产品能不能帮我解决问题？

```
不要说："我们用 GPT-4 和 RAG 技术构建了智能知识库"
要说："你问任何关于公司流程的问题，3 秒内得到准确答案"
```

### 原则三：设计"AI + 人"的协作模式，而不是"AI 替代人"

最好的 AI 产品不是完全替代人类，而是在人类最薄弱的环节提供支持。

```
差：AI 自动回复所有客户邮件（出错后果严重）
好：AI 生成回复草稿，客服人员审核后发送（效率提升 + 质量保障）
```

### 原则四：数据飞轮比模型能力更重要

短期看，模型能力决定产品体验；长期看，用户使用产生的数据才是真正的壁垒。

```
用户使用产品 → 产生反馈数据 → 优化 AI 效果 → 更多用户使用
                ↑                                    ↓
                └────────────────────────────────────┘
```

## 常见误区

### 误区一：把 Demo 当产品

AI API 的 demo 效果往往很好——因为你在受控环境下测试。但真实用户会输入你意想不到的内容，会用你没考虑过的场景，会在你想不到的环节出错。Demo 距离产品之间，隔着 100 个 badcase。

### 误区二：过度依赖模型能力

"等 GPT-5 出来就好了"——这是一个危险的想法。如果你的产品价值完全取决于模型能力的提升，那你本质上是在给 OpenAI 打工。模型能力是公共的，你的行业理解、数据积累、用户体验才是私有的。

### 误区三：忽视非 AI 部分

一个 AI 产品的成功，往往取决于非 AI 的部分：产品设计、用户引导、数据集成、运营策略。只关注 AI 能力而忽视这些，就像开餐厅只关注食材而忽视选址、装修和服务。

### 误区四：用技术指标衡量产品价值

"我们的模型准确率是 97%"——用户不理解也不关心。他们关心的是："我用这个产品，能不能少加班一小时？"把技术指标翻译成用户价值，是产品思维的基本功。

## 工程建议

### 1. 先写"用户故事"再写代码

在动手写任何代码之前，先用一句话描述产品价值："作为 [目标用户]，我想 [做什么]，这样我就能 [获得什么价值]。"如果这句话说不清楚，先别动手。

### 2. 用"最差情况"评估 AI 可靠性

不要在最佳情况下测试 AI，要在最差情况下测试。用最模糊的输入、最边缘的场景、最恶意的用法来测试。如果最差情况下 AI 的表现不可接受，你需要设计兜底方案。

### 3. 为 AI 的错误设计"出口"

AI 一定会出错。你的产品设计必须包含用户发现错误后的修正路径。最简单的方案是"AI 生成初稿 + 用户编辑确认"，让 AI 的错误在到达最终结果之前被拦截。

### 4. 关注"80% 场景"而非"边缘场景"

AI 产品不需要覆盖所有场景。找到用户 80% 的使用场景，把这 80% 做到极致。剩下的 20% 交给人工处理或明确告知用户"暂不支持"。

## 小结

- **技术思维**从能力出发找场景，**产品思维**从问题出发找方案
- AI 产品的核心差异在于**概率性**、**动态期望**和**不可预测的开发周期**
- AI 产品分为四类：效率工具、体验增强、能力扩展、行业重构
- 评估 AI 产品用"问题-方案-能力"框架，**问题层决定价值，能力层决定可行性**
- AI 是手段不是目的，设计"AI + 人"的协作模式，关注数据飞轮

## 参考答案

### 练习一：思维转换练习

**思路**：以 ChatGPT 为例，从"解决什么问题"而非"有什么功能"切入，对比无 AI 时的替代方案，体会产品思维与技术思维的差异。

**答案**：

- **产品**：ChatGPT
- **解决的问题**：用户需要快速获取结构化的信息、翻译、写作辅助、代码调试，但传统搜索引擎需要自己筛选结果、拼凑答案，效率低
- **目标用户**：知识工作者（程序员、写作者、研究人员、学生）
- **无 AI 替代方案**：Google 搜索 + 自己阅读多篇文章 + 手动整理；或者付费咨询专业人士
- **核心价值**：将"搜索→阅读→整理→输出"的多步流程压缩为"提问→获取答案"的一步流程

**要点**：
- 产品思维的关键是先问"用户在解决什么问题"，而不是"AI 能做什么"
- 对比无 AI 替代方案，才能看清 AI 产品的真实增量价值
- 目标用户画像越具体，产品定位越清晰

### 练习二：产品分类练习

**思路**：逐一分析每个产品的核心价值主张，判断其属于效率工具、体验增强、能力扩展还是行业重构。

**答案**：

| 产品 | 分类 | 理由 |
|------|------|------|
| Grammarly | 效率工具 | 替代人工校对，提升写作效率，核心是"做同样的事更快" |
| TikTok 推荐算法 | 体验增强 | 没有推荐算法用户也能刷视频，但算法让体验从"随便看看"变成"越看越爱看" |
| DALL-E | 能力扩展 | 让没有绘画能力的人也能生成图像，创造了全新的能力 |
| 智能投顾 | 行业重构 | 改变了传统理财顾问的服务模式，让普通人也能获得专业资产配置建议 |

**要点**：
- 四类产品的核心区别在于：AI 是替代人力（效率）、改善体验（体验）、赋予新能力（扩展）、还是颠覆行业（重构）
- 同一产品可能横跨多个类型，但通常有一个主导分类

### 练习三：框架应用练习

**思路**：用"问题-方案-能力"三层框架逐一评估，重点关注问题的真实性、方案的匹配度、能力的可靠性。

**答案**：

**1. 用 AI 自动给论文写摘要**
- 问题层：✅ 真实痛点，研究者需要快速判断论文是否值得细读
- 方案层：✅ 提取式摘要技术成熟，生成式摘要质量可用
- 能力层：✅ 文本摘要是 LLM 的强项，可靠性高
- **评估：强候选**

**2. 用 AI 分析股票走势**
- 问题层：✅ 投资者确实需要分析辅助
- 方案层：⚠️ 市场受太多不可预测因素影响
- 能力层：❌ AI 无法可靠预测股价，且涉及合规风险
- **评估：高风险，不建议**

**3. 用 AI 为电商商品生成详情页**
- 问题层：✅ 电商运营者确实需要大量商品文案
- 方案层：✅ 结构化输入 → 文案输出，流程清晰
- 能力层：✅ 文本生成 + 排版是 LLM 强项
- **评估：强候选，且商业化路径清晰**

**结论**：第 3 个（电商商品详情页）最可能做成成功产品。原因：问题真实且高频、AI 能力匹配度高、商业模式清晰（按生成量收费）、用户愿意付费。

**要点**：
- 三层都要通过才算好方向，任何一层有硬伤都要谨慎
- 能力层是最常见的否决项——很多想法"听起来很酷"但 AI 做不到

### 练习四：用户故事练习

**思路**：用标准用户故事格式"作为[角色]，我想要[目标]，以便[价值]"，写出 3 个不同角度的版本。

**答案**（以"AI 自动生成周报"产品为例）：

**版本一（效率角度）**：作为一个每周五下午要写周报的产品经理，我想要一个自动汇总本周工作内容的工具，以便我能把 1 小时的写周报时间缩短到 5 分钟。

**版本二（质量角度）**：作为一个不擅长文字表达的后端工程师，我想要一个能把我的 git commit 和会议记录转化成结构化周报的工具，以便我的周报看起来更专业、更全面。

**版本三（管理角度）**：作为一个管理 15 人团队的技术总监，我想要一个能让团队成员高效提交周报并自动汇总团队进展的工具，以便我每周一能快速了解全局而不必逐个追问。

**选择**：版本三最打动人，因为它同时解决了"写的人省事"和"看的人高效"两个痛点，且涉及多人协作，传播潜力更大。

**要点**：
- 好的用户故事要包含具体的角色、明确的目标、清晰的价值
- 不同版本代表不同的切入角度，选择覆盖面广、价值感强的版本
