# AI 产品思维：从技术人到产品人的转变

你刚学会调 OpenAI API，能用几行代码让 GPT 帮用户写邮件、总结文档。你兴奋地花一个周末做了个"AI 写作助手"，上线后发现没人用——用户说"我用 ChatGPT 就行了"。

问题不在技术，在思维方式。这节课帮你完成从工程师到产品人的转变。

## 技术思维 vs 产品思维

工程师天然从技术出发思考：

- "GPT-4 能力很强，可以做 XXX"
- "这个模型准确率 95%，肯定有市场"

这是**找钉子**的思路。产品思维反过来——先找痛点，再选工具。

三个核心问题：
1. **谁**有这个问题？（目标用户要具体到角色和场景）
2. 这个问题**有多痛**？（用户愿不愿意掏钱）
3. 现有方案**差在哪**？（你的机会窗口）

```typescript
// 技术思维的典型产物
const product = {
  name: "AI 万能助手",
  targetUser: "所有人",
  value: "用 AI 帮你做任何事",
};
// 问题：目标用户太宽，价值太模糊，跟 ChatGPT 没区别

// 产品思维的典型产物
const product2 = {
  name: "餐饮营销文案生成器",
  targetUser: "三四线城市、3 人以下团队的餐饮店主",
  value: "输入菜品照片和价格，30 秒生成小红书 + 抖音 + 朋友圈三个版本的营销文案",
  painPoint: "每周花 3-5 小时写营销内容，写出来还不专业",
  currentSolution: "自己随便写，或者花钱请人代写（200-500 元/篇）",
};
```

## AI 产品与传统软件的关键区别

传统软件是确定性的——点按钮 A，一定出结果 B。AI 产品是概率性的——同一输入可能出不同输出。

这个区别带来三个设计挑战：

**兜底机制**。AI 输出质量不达标时怎么办？最简单的方案是"AI 生成初稿 + 用户确认"，让错误在到达最终结果前被拦截。

**用户预期管理**。用户对 AI 的期望是动态的。他们不会因为"能自动生成周报"就满足，会追问：能不能按我们公司格式来？能不能从 JIRA 拉数据？能不能区分已完成和进行中？

**开发周期不可预测**。传统开发是需求→设计→开发→测试→上线。AI 产品多了一个"调 Prompt"环节，可能反复多次，时间完全不可控。

## AI 产品的四种类型

| 类型 | 核心逻辑 | 典型案例 | 壁垒 |
|------|---------|---------|------|
| 效率工具 | 替代重复性工作 | Copilot、Jasper | 工作流深度集成 |
| 体验增强 | 让现有体验更好 | Spotify 推荐、美颜相机 | 数据飞轮 |
| 能力扩展 | 让用户做到以前做不到的事 | Midjourney、Cursor | 降低门槛的体验设计 |
| 行业重构 | 重新定义行业工作方式 | Harvey（法律）、Abridge（医疗） | 行业 know-how + 数据 |

知道自己想做哪一类，决定了后续所有决策。

## 用"问题-方案-能力"框架评估想法

当你有一个产品想法时，三层逐级评估：

```typescript
interface ProductIdea {
  // 第一层：问题（决定产品有没有价值）
  targetUser: string;      // 谁？
  painPoint: string;       // 什么痛点？
  painLevel: 1 | 2 | 3 | 4 | 5;  // 5 = 愿意立刻付钱

  // 第二层：方案（决定怎么做）
  coreAction: string;      // 用户的核心动作
  aiRole: string;          // AI 扮演什么角色
  nonAIValue: string;      // 除 AI 外还提供什么

  // 第三层：能力（决定能不能做）
  aiCapability: string;    // AI 需要做什么
  reliability: "high" | "medium" | "low";
  fallbackPlan: string;    // AI 不可靠时怎么办
}
```

关键判断：**问题层决定价值，能力层决定可行性**。再强的 AI 能力，解决的是"可有可无"的问题，产品也活不下去。

很多想法死在能力层——"听起来很酷但 AI 做不到"。比如用 AI 预测股价，问题真实、用户愿意付费，但 AI 无法可靠预测，这就是能力层的硬伤。

## 常见的误判

**把 Demo 当产品**。API demo 效果好是因为你在受控环境测试。真实用户会输入你意想不到的内容，用你没考虑过的场景。Demo 到产品之间隔着 100 个 badcase。

**"等 GPT-5 出来就好了"**。如果你的产品价值完全取决于模型能力提升，你本质上在给 OpenAI 打工。模型能力是公共的，你的行业理解、数据积累、用户体验才是私有的。

**用技术指标衡量产品价值**。"我们模型准确率 97%"——用户不理解也不关心。他们关心的是：用这个产品能不能少加班一小时？

**忽视非 AI 部分**。AI 产品的成功往往取决于非 AI 部分：产品设计、用户引导、数据集成、运营策略。只关注 AI 能力，像开餐厅只关注食材而忽视选址和服务。

## 四条核心原则

**从用户需要什么出发，不是从 AI 能做什么出发**。

**AI 是手段不是目的**。不要说"我们用 GPT-4 和 RAG 构建了智能知识库"，要说"你问任何关于公司流程的问题，3 秒内得到准确答案"。

**设计 AI + 人的协作模式**。差：AI 自动回复所有客户邮件。好：AI 生成回复草稿，客服审核后发送。

**数据飞轮比模型能力更重要**。短期看模型能力决定体验，长期看用户使用产生的数据才是壁垒。

## 练习

### 练习一：产品评估

选一个你最近用过的 AI 产品，用"问题-方案-能力"框架分析它：
- 目标用户是谁？解决什么痛点？
- AI 在其中扮演什么角色？非 AI 部分提供了什么价值？
- AI 的可靠性如何？有没有兜底方案？

写成代码形式的 `ProductIdea` 对象。

### 练习二：想法筛选

列出 5 个你想做的 AI 产品方向，每个用一句话描述"为谁解决什么问题"。然后用以下标准快速淘汰：
- 目标用户是否具体到角色和场景？（"所有人"不算）
- 用户是否愿意为此付费？（"免费用还行"不算）
- AI 能否可靠完成核心任务？（"理论上可以"不算）

选出得分最高的 1 个，写 3 个版本的用户故事（"作为[角色]，我想[目标]，以便[价值]"）。

## 参考答案

### 练习一

以 Cursor 为例：

```typescript
const cursor: ProductIdea = {
  targetUser: "日常写代码的软件工程师",
  painPoint: "写重复代码、查文档、调试占了大量时间，切换窗口打断心流",
  painLevel: 4,

  coreAction: "在编辑器内用自然语言描述需求，AI 直接生成代码",
  aiRole: "代码生成、补全、重构建议",
  nonAIValue: "与编辑器深度集成（不是单独的网页）、理解整个项目上下文、一键应用修改",

  aiCapability: "代码生成 + 上下文理解",
  reliability: "medium",
  fallbackPlan: "生成的代码需要用户审核，支持逐行接受/拒绝",
};
```

要点：Cursor 的壁垒不在 GPT-4 能力（任何人都能调），而在编辑器集成体验和项目级上下文理解。

### 练习二

淘汰过程示例：

| 想法 | 用户具体？ | 愿意付费？ | AI 可靠？ | 结论 |
|------|-----------|-----------|----------|------|
| AI 万能助手 | ❌ 所有人 | ❌ | - | 淘汰 |
| AI 股票预测 | ✅ 投资者 | ✅ | ❌ AI 无法可靠预测 | 淘汰 |
| AI 商品详情页生成 | ✅ 电商卖家 | ✅ | ✅ 文本生成是强项 | 保留 |
| AI 会议纪要 | ✅ 打工人 | ⚠️ 飞书已内置 | - | 淘汰 |
| AI 合同审查 | ✅ 律师/法务 | ✅ | ⚠️ 法律出错后果严重 | 保留但需人工兜底 |

最终选择"AI 商品详情页生成"，用户故事：
1. 作为每天要上架 10 个商品的电商运营，我想一键生成详情页文案，这样我能把时间花在选品上而不是写字上。
2. 作为管理 5 人运营团队的电商主管，我想统一团队的文案质量和品牌调性，这样不用逐个审核修改。
3. 作为同时经营淘宝和抖音两个店铺的店主，我想一次生成两个平台适配的文案，这样不用手动改格式。
