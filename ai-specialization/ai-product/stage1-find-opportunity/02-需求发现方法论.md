# 第二课：需求发现方法论

## 场景引入

你有了做 AI 产品的想法，但你怎么知道这个想法是真实的用户需求，而不是你自己"觉得"的需求？很多开发者犯过同一个错误：在自己的书房里"发明"需求。他们假设用户会喜欢某个功能，花三个月做出来，上线后发现——用户根本不需要。

需求发现不是拍脑袋，它是一套可以学习、可以重复的方法论。这一课，你会学到如何从真实世界中"挖"出值得用 AI 解决的问题，而不是凭空想象。

## 学习目标

1. 掌握用户访谈的核心技巧，学会问出真实需求
2. 学会用"痛点矩阵"筛选值得解决的问题
3. 理解需求验证的三个层次：存在性、频次、支付意愿
4. 掌握从行业报告和社区中发现需求的方法

## 一、需求的本质：不是用户说的，而是用户做的

### 1.1 用户说的 vs 用户做的

用户访谈中最危险的事情是：把用户说的话当成真实需求。

```
用户说："我希望能自动整理我的笔记。"
→ 你做了一个 AI 笔记整理工具
→ 用户不用

为什么？因为用户真正的问题不是"笔记乱"，
而是"找不到之前写过的某个关键信息"。
整理笔记是手段，快速检索才是目的。
```

这在需求分析中被称为**"说的"与"做的"之间的鸿沟**。用户的表述往往是表面的解决方案，而不是底层的问题。

### 1.2 五个为什么（5 Whys）

当用户提出一个需求时，连续问五次"为什么"，直到找到根本原因：

```
用户：我想要一个 AI 日报生成器。
→ 为什么？因为我每天要花 20 分钟写工作日报。
→ 为什么要写日报？因为老板要求每天汇报进度。
→ 为什么老板要求汇报？因为他想知道项目是否在正轨上。
→ 为什么他不直接看项目管理工具？因为他不会用 JIRA，只看邮件。
→ 为什么不做个自动从 JIRA 发邮件的功能？

→ 真正的需求是：老板想用最低成本了解项目状态。
   AI 日报只是众多可能方案中的一种。
```

## 二、用户访谈：问出真实需求的艺术

### 2.1 访谈的核心原则

**原则一：问过去的行为，不问未来的意愿**

```
❌ "你会不会用一个 AI 写周报的工具？"
   （用户几乎永远说"会"，但这不代表他们真的会用）

✅ "你上次写周报是什么时候？花了多久？过程中最烦的是什么？"
   （过去的行为比未来的意愿可靠 10 倍）
```

**原则二：问具体的场景，不问抽象的看法**

```
❌ "你觉得 AI 写作助手怎么样？"
✅ "你上次写方案的时候，从哪里开始写的？卡在哪里了？"
```

**原则三：让用户讲故事，不让他们给建议**

```
❌ "你希望这个产品有什么功能？"
✅ "你上次完成 [某任务] 的完整过程是怎样的？从头讲一遍。"
```

### 2.2 访谈问题模板

以下是一套经过验证的访谈问题结构：

```typescript
const interviewGuide = {
  // 第一阶段：了解现状（5 分钟）
  background: [
    "你的工作主要是什么？一天的典型工作流程是怎样的？",
    "在 [目标场景] 上，你一般怎么做的？能从头讲一遍吗？"
  ],

  // 第二阶段：挖掘痛点（10 分钟）
  painPoints: [
    "在 [目标场景] 中，最让你头疼的环节是什么？",
    "有没有哪次你花了很长时间但结果还是不满意的？发生了什么？",
    "你有没有试过什么方法来解决这个问题？效果如何？"
  ],

  // 第三阶段：了解现有方案（5 分钟）
  currentSolution: [
    "你现在用什么工具来完成这个任务？",
    "这些工具你最喜欢和最不喜欢的地方分别是什么？",
    "有没有你试过但放弃的工具？为什么放弃？"
  ],

  // 第四阶段：探索期望（5 分钟）
  expectations: [
    "如果有一个完美的解决方案，它应该是什么样的？",
    "你愿意为这样的解决方案付多少钱？",
    "你觉得这个功能应该多久用一次？"
  ]
};
```

### 2.3 访谈数量建议

```
5 人访谈：发现 80% 的明显痛点
10 人访谈：发现细分场景的差异
20 人访谈：开始看到需求的分层（不同用户群有不同需求）

建议：至少访谈 5 人，最好覆盖 3 种不同类型的用户。
```

## 三、痛点矩阵：筛选值得解决的问题

访谈收集到一堆痛点后，你需要用**痛点矩阵**来筛选：

### 3.1 二维评估模型

```typescript
interface PainPoint {
  description: string;       // 痛点描述
  frequency: number;         // 频次：1-5（1=偶尔，5=每天多次）
  intensity: number;         // 强度：1-5（1=轻微不便，5=严重影响工作）
  currentSolution: string;   // 现有解决方案
  willingness: number;       // 支付意愿：1-5（1=不愿付费，5=立刻付费）
}

function evaluatePain(pain: PainPoint): number {
  // 综合得分 = 频次 × 40% + 强度 × 30% + 支付意愿 × 30%
  return pain.frequency * 0.4 + pain.intensity * 0.3 + pain.willingness * 0.3;
}

// 示例：AI 周报生成
const weeklyReport: PainPoint = {
  description: "每周花 1-2 小时写周报",
  frequency: 2,        // 每周一次，频次中等
  intensity: 2,        // 烦但不致命
  willingness: 2,      // 愿意付一点钱
  currentSolution: "用模板手动填写"
};
// 得分：2×0.4 + 2×0.3 + 2×0.3 = 2.0 → 不够痛，谨慎投入

// 示例：合同审查
const contractReview: PainPoint = {
  description: "律师花 4-8 小时审查一份合同中的风险条款",
  frequency: 4,        // 每天都审
  intensity: 4,        // 漏掉一个条款可能损失百万
  willingness: 5,      // 律所愿意付高价
  currentSolution: "初级律师人工逐条审查"
};
// 得分：4×0.4 + 4×0.3 + 5×0.3 = 4.1 → 非常值得做
```

### 3.2 矩阵可视化

把所有痛点放到一个二维矩阵中：

```
                    高频
                     │
         ┌───────────┼───────────┐
         │  甜蜜区    │  必须做    │
         │ (值得做)   │ (优先做)   │
   低强度 ├───────────┼───────────┤ 高强度
         │  可忽略    │  看情况    │
         │ (不做)     │ (验证后做) │
         └───────────┼───────────┘
                     │
                    低频

优先做：高频 + 高强度（用户每天痛，且痛得厉害）
值得做：高频 + 低强度（小痛但天天痛，积少成多）
看情况：低频 + 高强度（偶尔很痛，需要验证频次）
可忽略：低频 + 低强度（既不频也不痛）
```

除了用户访谈，还有大量公开信息源可以帮你发现需求：

## 五、需求验证的三个层次

发现需求后，需要通过三个层次的验证：

### 层次一：存在性验证

这个问题真实存在吗？

```
验证方法：
- 至少 3 个不同的人描述了类似的痛点
- 在社区/论坛中找到了相关讨论
- 有竞品在解决类似问题（说明市场存在）

反信号：
- 只有你自己觉得这是个问题
- 访谈中用户说"嗯...还好吧"
- 搜不到任何相关讨论
```

### 层次二：频次验证

这个问题多久出现一次？

```
验证方法：
- 访谈中问"你多久遇到一次这个问题？"
- 观察用户现有解决方案的使用频率
- 分析用户的日历/工具使用数据（如果可以获取）

关键阈值：
- 每天至少一次 → 高频，适合做工具型产品
- 每周一次 → 中频，适合做效率提升产品
- 每月一次 → 低频，需要足够高的单价或足够大的市场
```

### 层次三：支付意愿验证

用户愿意为解决这个问题付钱吗？

```
验证方法（从弱到强）：
1. 访谈中问"你愿意付多少钱？"（最弱，用户说的不等于做的）
2. Landing Page 测试（看有多少人留邮箱）
3. 预售/众筹（看有多少人真的掏钱）
4. Beta 版收费（最强，真实付费行为）

关键原则：永远不要只用第一种方法。
```

## 六、需求文档：把想法变成可执行的规格

验证完需求后，用以下模板整理成需求文档：

```markdown
## 产品需求简报

### 1. 问题定义
- **目标用户**：[具体描述，不要写"所有人"]
- **核心痛点**：[一句话描述]
- **当前解决方案**：[用户现在怎么做的]
- **痛点评分**：频次 X/5 × 强度 X/5 × 支付意愿 X/5

### 2. 验证结果
- 访谈人数：X 人
- 存在性验证：✅/❌（X/Y 人确认）
- 频次验证：✅/❌（平均 X 次/周）
- 支付意愿验证：✅/❌（X 人愿意付 ¥X/月）

### 3. 解决方案概述
- **核心功能**：[一句话]
- **AI 的角色**：[AI 做什么，人做什么]
- **非 AI 价值**：[除了 AI，还有什么关键价值]

### 4. 竞争分析
- 最接近的竞品：[名称]
- 差异化点：[为什么用户会选你而不是竞品]
```

## 常见误区

### 误区一：只访谈身边的人

你的朋友和同事不代表目标用户。他们的反馈可能有偏见（不想伤害你的感情）或不具代表性（不是真正的目标群体）。尽量找到**不认识你的目标用户**进行访谈。

### 误区二：把"用户说想要"当成"用户会用"

用户说"我想要一个 AI 助手帮我做 XXX"和用户真的会每天打开你的产品使用，中间隔着巨大的鸿沟。永远用行为验证，不要只听口头承诺。

### 误区三：忽视"够用就好"的现有方案

很多痛点之所以没被解决，不是因为没有方案，而是因为现有方案"够用了"。用户用 Excel 管项目虽然笨拙，但已经习惯了。你需要提供的是 10 倍好的体验，而不是 1.1 倍。

### 误区四：一次访谈就下结论

单次访谈可能是个例。只有当多个独立用户描述了类似的痛点，并且在社区中也能找到相关讨论时，你才能初步确认需求存在。样本量很重要。

## 工程建议

### 1. 建立"需求池"持续积累

不要等到想创业才去发现需求。在日常工作中，留意同事的抱怨、社区的讨论、竞品的差评，持续记录到一个需求池中。好的产品想法往往是从长期观察中自然浮现的。

### 2. 用最轻的方式验证

在投入开发之前，先用最低成本的方式验证需求：发一个问卷、做一个 Landing Page、写一篇帖子看反馈。不要一上来就写代码。

### 3. 访谈时录音并转录

人的记忆不可靠。访谈时录音（征得同意），事后用 AI 转录并分析。这样你能专注于对话本身，而不是边听边记笔记。

### 4. 关注"已付费"行为

如果用户已经在为某个解决方案付费（哪怕是笨拙的方案），这比任何口头承诺都更能证明需求的真实性。找到那些已经在花钱解决这个问题的用户。

## 小结

- 需求的本质是用户**做了什么**，而不是**说了什么**
- 用户访谈用"五个为什么"深挖根本原因，问过去行为不问未来意愿
- 痛点矩阵用**频次 × 强度 × 支付意愿**三维评估
- 从社区差评、行业报告、竞品分析中系统性发现需求
- 需求验证三个层次：存在性 → 频次 → 支付意愿，逐层递进

## 练习

1. **访谈练习**：找 3 个在不同公司工作的朋友，每人聊 20 分钟，主题是"你工作中最重复、最烦的任务是什么"。用"五个为什么"挖掘根本原因，整理成需求简报。

2. **社区挖掘练习**：在 Reddit、知乎或 V2EX 上搜索"有没有什么工具可以"这个关键词，找到 5 个未被很好解决的需求，用痛点矩阵评分排序。

3. **竞品差评分析**：选一个你常用的 SaaS 产品（如 Notion、飞书、钉钉），去应用商店看 1-2 星评价，提取 3 个共性问题，评估每个问题是否值得用 AI 解决。

4. **需求验证设计**：为你从练习 1-3 中发现的最有潜力的需求，设计一个 1 周内可以完成的轻量级验证方案（不写代码）。

## 参考答案

### 练习一：访谈练习

**思路**：模拟访谈过程，展示如何用"五个为什么"从表面问题挖到根本需求，最终整理成需求简报。

**答案**：

**访谈对象**：某互联网公司运营专员小李

**对话记录**：
1. 最重复的任务是什么？→ 每天整理各渠道的运营数据到 Excel
2. 为什么这件事重复？→ 因为数据分散在 5 个平台，每天都要手动导出
3. 为什么不能自动化？→ 各平台格式不同，没有统一的 API
4. 为什么不用现成工具？→ 试过几个，但字段映射总是出错，还不如手动
5. 为什么字段映射会出错？→ 因为每个平台的指标定义不完全一样，比如"点击"的口径不同

**需求简报**：
- **用户**：中小公司的运营人员
- **痛点**：多平台数据分散，手动汇总耗时且容易出错
- **根本原因**：各平台数据口径不统一，简单拼接没有意义
- **AI 机会**：自动识别不同平台的指标含义，做智能映射和标准化

**要点**：
- "五个为什么"的关键是追问行为背后的决策逻辑，而非停留在表面描述
- 需求简报要包含用户、痛点、根本原因、AI 机会四个要素
- 记录用户的原话比自己的概括更有价值

### 练习二：社区挖掘练习

**思路**：展示如何从社区帖子中提取未被满足的需求，并用痛点矩阵量化排序。

**答案**：

**搜索结果示例**（知乎/V2EX）：

| 需求 | 频次 | 强度 | 支付意愿 | 总分 |
|------|------|------|----------|------|
| "有没有工具能把会议录音自动整理成待办？" | 高(8) | 高(9) | 中(7) | 24 |
| "能不能批量把 PDF 里的表格提取成 Excel？" | 高(8) | 中(7) | 高(8) | 23 |
| "有没有工具能自动对比两份合同的差异？" | 中(6) | 高(9) | 高(8) | 23 |
| "能不能自动把竞品的定价页面变化抓取下来？" | 中(5) | 中(7) | 中(6) | 18 |
| "有没有工具能自动把设计稿转成前端代码？" | 高(8) | 高(8) | 高(9) | 25 |

**排序结果**：设计稿转代码 > 会议录音转待办 > PDF 表格提取 ≈ 合同对比 > 竞品价格监控

**要点**：
- 社区挖掘的优势是用户自发表达需求，不存在访谈中的"讨好偏差"
- 痛点矩阵的三个维度要独立评分，避免"感觉很重要就全打高分"
- 关注反复出现的需求表述方式，这反映了用户的真实心智模型

### 练习三：竞品差评分析

**思路**：以飞书为例，系统性提取差评中的共性问题，评估 AI 解决的可行性。

**答案**：

**飞书 1-2 星差评提取**：

1. **搜索功能弱**："搜个文档搜不到，明明就在那里" — 全文搜索准确率低，尤其跨文档类型搜索
   - AI 解决评估：⭐⭐⭐⭐ RAG + 语义搜索可以显著改善，但需要处理权限问题

2. **通知过多且无法精细控制**："每天被通知轰炸，重要的反而被淹没了"
   - AI 解决评估：⭐⭐⭐⭐ AI 可以学习用户行为模式，智能过滤和优先级排序通知

3. **多维表格性能差**："数据多了就卡，筛选排序经常超时"
   - AI 解决评估：⭐ 这是基础设施性能问题，AI 无法解决

**结论**：第 1、2 个问题适合用 AI 解决，第 3 个是工程问题。

**要点**：
- 差评分析要区分"AI 可解决"和"AI 不可解决"的问题
- 关注频率最高的问题，而非最极端的差评
- 差评中隐藏着产品改进的具体方向

### 练习四：需求验证设计

**思路**：设计一个不写代码、1 周内可完成的轻量级验证方案，逐层验证需求的存在性、频次和支付意愿。

**答案**（以"会议录音自动整理待办"为例）：

**验证目标**：确认知识工作者是否真的需要"会议录音→待办"的自动化

**Day 1-2：存在性验证**
- 方法：在 3 个微信群发问卷（5 道选择题）
- 核心问题："你每周花多少时间整理会议纪要？"
- 成功标准：>60% 的人回答 >30 分钟/周

**Day 3-4：频次验证**
- 方法：在问卷中加开放题"你最近一次整理会议纪要是什么时候？"
- 追加：找 5 个问卷受访者做 10 分钟电话访谈
- 成功标准：>70% 的人在过去 1 周内做过

**Day 5-6：支付意愿验证**
- 方法：做一个 Figma 原型图（30 分钟），展示产品效果
- 在朋友圈发"如果有这样的工具，你愿意每月付多少钱？"配原型图
- 提供 0/9/29/49 四个选项
- 成功标准：>20% 的人选择 29 元或以上

**Day 7：汇总分析**
- 汇总三个层次的数据，判断是否继续推进

**要点**：
- 每个层次的验证都有明确的成功标准，避免"感觉还行"的模糊判断
- 不写代码的验证方式：问卷、访谈、原型图、落地页
- 验证成本要远低于开发成本
