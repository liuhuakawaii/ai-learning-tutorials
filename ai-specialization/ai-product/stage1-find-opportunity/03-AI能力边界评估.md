# 第三课：AI 能力边界评估

## 场景引入

你发现了一个真实的需求：用户每周要花 3 小时手动整理客户会议纪要，提取行动项并分配给团队成员。你兴奋地想："用 GPT-4 来做这个，分分钟搞定！"然后你开始做 demo——效果看起来不错。但当你把产品给真实用户用时，各种问题冒出来了：AI 分不清"需要跟进"和"仅供参考"的区别，把客户说的反话当成了正面反馈，偶尔还会编造出根本不存在的会议内容。

问题不在于 AI 不够聪明，而在于你没有准确评估 AI 的能力边界。这一课，你会学到如何系统性地评估当前 AI 能力能解决什么、不能解决什么，以及如何设计产品来规避 AI 的弱点。

## 学习目标

1. 了解当前主流大语言模型的真实能力水平和局限
2. 掌握评估 AI 能力边界的系统方法
3. 学会设计产品来规避 AI 的弱点
4. 理解 AI 能力的快速变化对产品策略的影响

## 一、大语言模型的真实能力图谱

### 1.1 模型擅长什么

大语言模型在以下任务上表现优秀：

```
✅ 强项（准确率 > 90%）
├── 文本摘要：把长文压缩成要点
├── 格式转换：Markdown ↔ JSON ↔ 表格
├── 语言翻译：主流语言之间的翻译
├── 代码生成：常见编程语言的标准功能
├── 文本分类：情感分析、意图识别
└── 内容扩写：基于大纲展开成段落

✅ 中等强项（准确率 70-90%）
├── 信息提取：从非结构化文本中提取结构化信息
├── 文本改写：改变语气、风格、长度
├── 简单推理：基于给定信息的逻辑推断
└── 创意内容：文案、故事、营销文本
```

### 1.2 模型不擅长什么

```
❌ 弱项（准确率不可靠）
├── 精确计算：数学、统计、财务计算
├── 最新信息：超出训练数据的时间范围
├── 事实核查：可能"一本正经地胡说八道"
├── 长文本一致性：超过一定长度后前后矛盾
├── 多步骤复杂推理：链条越长错误率越高
└── 领域专业知识：超出通用知识的垂直领域细节

❌ 高风险项（容易出错且后果严重）
├── 医疗诊断建议
├── 法律条文解读
├── 金融投资建议
├── 安全相关的决策
└── 涉及个人隐私的数据处理
```

## 二、系统性评估 AI 能力边界的框架

### 2.1 "任务分解"评估法

不要问"AI 能不能做 XXX"，而是把任务分解成子步骤，逐一评估：

```
原始问题："AI 能不能帮我写周报？"

分解：
1. 从 JIRA 获取本周完成的任务     → API 调用，非 AI 问题 ✅
2. 从日历获取本周的会议记录       → API 调用，非 AI 问题 ✅
3. 理解每个任务的重要程度         → 需要上下文理解，中等可靠性 ⚠️
4. 将信息组织成流畅的周报文本     → 文本生成，可靠性高 ✅
5. 区分"已完成"和"进行中"       → 信息提取，可靠性高 ✅
6. 识别本周的关键成果和风险       → 需要判断力，可靠性中 ⚠️

结论：AI 能完成 80% 的工作，但第 3 和第 6 步需要人工确认。
```

### 2.2 "最差情况"测试法

用以下方式测试 AI 的能力边界：

### 2.3 "可靠性-影响"矩阵

```typescript
interface TaskAssessment {
  taskName: string;
  aiReliability: number;    // 1-5，AI 完成这个任务的可靠程度
  errorImpact: number;      // 1-5，AI 出错的后果严重程度
}

function assessTask(assessment: TaskAssessment): {
  strategy: string;
  description: string;
} {
  const { aiReliability, errorImpact } = assessment;

  if (aiReliability >= 4 && errorImpact <= 2) {
    return {
      strategy: "全自动",
      description: "AI 独立完成，低频抽检"
    };
  }
  if (aiReliability >= 3 && errorImpact <= 3) {
    return {
      strategy: "AI 优先 + 人确认",
      description: "AI 生成结果，用户一键确认"
    };
  }
  if (aiReliability >= 2 && errorImpact <= 4) {
    return {
      strategy: "AI 辅助 + 人决策",
      description: "AI 提供选项或建议，用户做最终决定"
    };
  }
  return {
    strategy: "人为主 + AI 微辅助",
    description: "人做核心工作，AI 只做格式化等低风险环节"
  };
}

// 使用示例
const meetingSummary = assessTask({
  taskName: "会议纪要生成",
  aiReliability: 4,
  errorImpact: 2
});
// 结果：{ strategy: "AI 优先 + 人确认", ... }

const legalAdvice = assessTask({
  taskName: "法律风险评估",
  aiReliability: 2,
  errorImpact: 5
});
// 结果：{ strategy: "人为主 + AI 微辅助", ... }
```

## 三、设计产品来规避 AI 弱点

### 3.1 "人在回路"设计模式

最常用的策略是**Human-in-the-Loop（HITL）**——在 AI 流程的关键节点插入人工审核：

```typescript
// 模式一：生成-审核-发送
async function draftAndReview(content: string) {
  const draft = await ai.generate(content);
  // AI 生成草稿
  return {
    draft,
    actions: ["approve", "edit", "reject"]
    // 用户必须选择一个动作
  };
}

// 模式二：AI 排序-人选择
async function aiRankAndHumanChoose(options: string[]) {
  const ranked = await ai.rank(options);
  return {
    suggestions: ranked.slice(0, 3),
    // AI 只提供 Top 3 建议
    decision: "human"  // 最终决定权在人
  };
}

// 模式三：人操作-AI 优化
async function humanDraftAiPolish(draft: string) {
  // 用户先写出核心内容
  const polished = await ai.polish(draft, {
    preserveMeaning: true,  // 只改表达，不改含义
    showChanges: true       // 高亮所有修改
  });
  return polished;
}
```

### 3.2 "置信度"展示设计

让用户知道 AI 有多确定：

```typescript
interface AIResult {
  content: string;
  confidence: 'high' | 'medium' | 'low';
  reasoning?: string;
  needsReview: boolean;
}

function renderResult(result: AIResult) {
  const styles = {
    high: { color: 'green', icon: '✓' },
    medium: { color: 'yellow', icon: '?' },
    low: { color: 'red', icon: '⚠' }
  };

  return `
    <div class="ai-result">
      <span class="confidence" style="color: ${styles[result.confidence].color}">
        ${styles[result.confidence].icon} 置信度：${result.confidence}
      </span>
      <p>${result.content}</p>
      ${result.needsReview ? '<button>请人工确认</button>' : ''}
      ${result.reasoning ? `<details><summary>AI 推理过程</summary>${result.reasoning}</details>` : ''}
    </div>
  `;
}
```

### 3.3 "优雅降级"策略

当 AI 能力不足时，产品应该优雅地降级而不是硬撑：

```typescript
async function handleAITask(task: string) {
  try {
    const result = await ai.process(task);

    if (result.confidence < 0.6) {
      // AI 不确定时，降级为辅助模式
      return {
        mode: 'assisted',
        message: 'AI 对这个任务不太确定，为你提供了参考信息，请人工处理：',
        reference: result.content,
        fallbackAction: 'manual'
      };
    }

    return {
      mode: 'auto',
      result: result.content,
      fallbackAction: 'review'
    };
  } catch (error) {
    // AI 完全失败时，提供替代方案
    return {
      mode: 'manual',
      message: 'AI 暂时无法处理此任务，已为你准备好手动处理的模板：',
      template: generateManualTemplate(task)
    };
  }
}
```

## 四、不同场景的能力边界速查

### 4.1 文本处理类

```
场景：邮件分类
├── AI 能力：★★★★☆
├── 可靠度：高（常见分类准确率 95%+）
├── 风险：低（分错了不致命）

场景：合同条款提取
├── AI 能力：★★★☆☆

├── 风险：高（遗漏可能导致法律风险）

```

### 4.2 数据分析类

```
场景：销售数据趋势分析
├── AI 能力：★★★☆☆
├── 可靠度：中（趋势判断尚可，具体数字易错）
├── 风险：中（错误分析可能导致错误决策）
```

## 五、AI 能力的快速变化与产品策略

### 5.1 能力在快速提升

```
2023 年：GPT-3.5 做不了的事 → 2024 年：GPT-4 能做了
2024 年：GPT-4 做不好的事 → 2025 年：新模型可能能做好

产品策略：不要因为"现在做不好"就放弃一个方向，
但也不要假设"将来一定能做好"。
```

### 5.2 "能力赌注"策略

### 5.3 不要押注在"模型变好"上

```
危险策略："现在 AI 做得不好，但等 GPT-5 就好了"
安全策略："在当前 AI 能力下，产品就已经有价值"
```

你的产品应该在当前 AI 能力水平下就能为用户创造价值。模型变好是锦上添花，不是雪中送炭。

## 常见误区

### 误区一：被 Demo 效果迷惑

AI API 在精心构造的输入上效果惊人，但真实用户的输入千奇百怪。永远用真实场景、真实数据测试，而不是用"最佳案例"来评估。

### 误区二：忽视 AI 的"幻觉"问题

大语言模型会生成看似合理但完全错误的内容。在任何需要准确性的场景（法律、医疗、财务），必须有人工验证环节。"AI 说的"不等于"正确的"。

### 误区三：高估 AI 的一致性

同一个 Prompt，AI 可能给出不同的结果。不要假设 AI 的输出是稳定可靠的。在需要一致性的场景中，需要设计输出校验和标准化机制。

### 误区四：低估 Prompt 工程的复杂度

"写个 Prompt 让 AI 做这件事"听起来简单，但在实际产品中，Prompt 需要处理各种边界情况、用户输入的变化、输出格式的稳定性。这是一个需要持续迭代的工程问题。

## 工程建议

### 1. 建立 AI 能力评估清单

在确定产品方向后，列出所有需要 AI 完成的任务，逐一评估可靠性、风险和策略。这个清单应该在产品迭代中持续更新。

### 2. 设计"AI 失败"的用户体验

AI 出错时用户会看到什么？如何让用户轻松纠正？如何避免 AI 的错误造成不可挽回的后果？这些问题的答案应该在产品设计阶段就确定。

### 3. 收集 badcase 作为迭代依据

系统性地收集 AI 出错的案例，分析错误模式，优化 Prompt 或调整产品设计。badcase 是 AI 产品最宝贵的迭代依据。

### 4. 关注模型更新带来的机会

订阅 OpenAI、Anthropic、Google 等公司的模型更新公告。模型能力的提升可能让你之前"做不了"的功能变得可行，也可能让你的核心功能被模型内置能力替代。

## 小结

- 大语言模型在文本处理、格式转换、内容生成上表现优秀，在精确计算、事实核查、专业领域上不可靠
- 用"任务分解"法评估 AI 能力，不要笼统地问"AI 能不能做"
- 用"最差情况"测试 AI 的边界，而不是用最佳案例
- 设计"人在回路"的产品模式，在关键节点插入人工审核
- 产品价值不应依赖于"模型将来变好"，在当前能力下就应有价值

## 练习

1. **能力评估练习**：选择一个你想做的 AI 产品功能，把它分解成 5-8 个子任务，用"可靠性-影响"矩阵评估每个子任务，确定每个环节的策略（全自动/人确认/人决策）。

2. **最差情况测试**：选一个 AI API（如 GPT-4），给它 10 个你预期的真实用户输入，包括最模糊、最矛盾、最恶意的输入，记录它的表现和失败模式。

3. **产品设计练习**：为一个"AI 自动回复客户邮件"的功能，设计完整的"人在回路"方案，包括：AI 的角色、人工审核的触发条件、AI 失败时的降级方案、用户反馈的收集机制。

4. **能力变化分析**：对比 2023 年和 2025 年的 AI 能力变化，列出 3 个"以前做不了但现在能做"的任务，以及 3 个"现在仍然做不好"的任务。这对你的产品策略有什么启示？

## 参考答案

### 练习一：能力评估练习

**思路**：以"AI 自动生成社交媒体运营方案"为例，分解子任务并逐一评估可靠性与影响。

**答案**：

**子任务分解与评估**：

| 子任务 | 可靠性 | 影响 | 策略 |
|--------|--------|------|------|
| 分析品牌调性 | 高 | 高 | 全自动（输入品牌简介即可） |
| 研究竞品内容 | 中 | 高 | 人确认（AI 提取，人工核实） |
| 生成文案内容 | 高 | 中 | 全自动 + 人工微调 |
| 选择配图方向 | 中 | 中 | 人确认（AI 推荐 3 个方向供选择） |
| 排定发布时间 | 低 | 高 | 人决策（AI 提供建议，人工拍板） |
| 预测互动效果 | 低 | 低 | 参考即可（不作为核心承诺） |
| 生成多平台适配版本 | 高 | 高 | 全自动（格式转换是 AI 强项） |

**要点**：
- 可靠性高 + 影响高的任务适合全自动
- 可靠性低 + 影响高的任务必须人工决策
- 评估要基于实际测试，不能凭想象

### 练习二：最差情况测试

**思路**：针对"用户评论情感分析"API，设计 10 个包含边界情况的测试输入，记录失败模式。

**答案**：

**测试输入与结果**：

| 输入 | 预期 | 实际 | 是否正确 |
|------|------|------|----------|
| "这个产品太棒了！" | 正面 | 正面 | ✅ |
| "垃圾，退款！" | 负面 | 负面 | ✅ |
| "还行吧" | 中性 | 中性 | ✅ |
| "好个屁" | 负面 | 正面 | ❌ 反讽识别失败 |
| "如果不是贵了点就完美了" | 中性偏正 | 正面 | ❌ 忽略转折 |
| "呵呵" | 负面 | 中性 | ❌ 网络用语歧义 |
| "界面丑但功能强" | 中性 | 正面 | ❌ 忽略前半句 |
| "比上一代好" | 正面 | 正面 | ✅ |
| "电池续航3小时" | 中性/负 | 中性 | ✅（依赖语境） |
| "👍👎" | 模糊 | 正面 | ❌ 表情歧义 |

**失败模式总结**：
1. 反讽和网络用语识别差
2. 转折句只看后半句
3. 复合情感（正面+负面）处理粗糙

**要点**：
- 测试要包含真实用户会输入的"脏数据"
- 失败模式的分类比单次对错更有价值
- 最差情况测试决定了产品需要哪些降级方案

### 练习三：产品设计练习

**思路**：为"AI 自动回复客户邮件"设计完整的"人在回路"方案，覆盖 AI 角色、审核触发、降级方案和反馈机制。

**答案**：

**AI 角色**：
- 读取客户邮件，理解意图，生成回复草稿
- 自动匹配历史类似问题的回复模板
- 提取关键信息（订单号、问题类型、紧急程度）

**人工审核触发条件**：
- 涉及退款/赔偿（金额 > 100 元）
- 客户情绪为"愤怒"或"投诉"
- AI 置信度 < 80%
- 客户是 VIP 或首次投诉
- 涉及法律/合规敏感话题

**降级方案**：
- AI 生成失败时：转人工，并附上 AI 已识别的信息摘要
- AI 连续 3 次被人工大幅修改：暂停该类邮件的自动处理，通知管理员
- API 超时/错误：自动转人工队列，记录错误日志

**反馈收集机制**：
- 人工修改 AI 草稿后，自动记录"原始版本 vs 修改版本"
- 每周统计"AI 草稿通过率"（无需修改直接发送的比例）
- 人工可以直接标记"AI 回复质量差"，触发模型微调数据收集

**要点**：
- 人在回路不是"所有都人工审一遍"，而是按风险等级分层处理
- 降级方案要考虑 AI 系统性失败的场景
- 反馈机制要形成数据闭环，持续改善 AI 表现

### 练习四：能力变化分析

**思路**：对比 2023 年与 2025 年的 AI 能力变化，分析对产品策略的启示。

**答案**：

**以前做不了，现在能做**：
1. **长文档理解和摘要**：2023 年模型上下文窗口有限（4K-8K），2025 年 128K+ 成为标配，可以一次性处理整本书
2. **多模态理解**：2023 年 GPT-4V 刚发布且能力有限，2025 年可以准确理解图表、截图、手写内容
3. **复杂推理和代码生成**：2023 年生成的代码经常有 bug，2025 年可以完成中等复杂度的完整功能开发

**现在仍然做不好**：
1. **精确数学计算**：仍然需要调用计算器工具，不能依赖 LLM 直接算
2. **实时信息获取**：模型知识有截止日期，无法获取"今天"的信息（需配合搜索工具）
3. **长期记忆和个性化**：跨会话的用户偏好学习仍然不成熟

**产品策略启示**：
- 不要押注"模型将来变好"来设计产品，但要为能力提升预留架构空间
- 现在做不了的功能，可以用"人机协作"模式先跑起来
- 产品核心价值应该建立在"现在就能做好"的能力上

**要点**：
- AI 能力在快速变化，产品策略要定期重新评估
- "以前做不了现在能做"意味着新的产品机会窗口
- "现在仍然做不好"意味着这些领域仍需人工补充
