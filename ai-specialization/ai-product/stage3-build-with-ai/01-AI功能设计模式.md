# 第1课：AI 功能设计模式

> **课程定位**：理解 AI 功能的三种主流设计模式，为产品选择正确的 AI 交互形态
> **前置知识**：了解基本的 AI/LLM 概念
> **预计时长**：35 分钟

---

## 场景引入

你准备给产品加 AI 功能，打开竞品一看——有的是对话框让用户提问，有的是侧边栏自动给建议，有的完全不需要用户操作就在后台自动处理。你开始纠结：我的产品到底该用哪种交互形态？选错了，要么用户觉得多余，要么用户觉得难用。这个问题的答案不在技术层面，而在产品设计模式层面。

---

## 学习目标

完成本课学习后，你将能够：

1. 说出 AI 功能的三种主流设计模式及其核心差异
2. 为不同业务场景选择合适的 AI 设计模式
3. 理解每种模式的用户体验特征和适用边界
4. 避免"为了用 AI 而用 AI"的设计陷阱

## 一、三种 AI 设计模式概览

### 1.1 Copilot 模式：AI 在旁边帮忙

```
┌─────────────────────────────────────────────────────────────┐
│                    Copilot 模式                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  用户在主界面操作，AI 在侧边栏/浮层提供辅助                   │
│                                                             │
│  ┌──────────────────────┐  ┌──────────────────────────┐    │
│  │                      │  │  🤖 AI 助手               │    │
│  │   用户的主要工作区    │  │                          │    │
│  │                      │  │  "你可以试试这样改..."    │    │
│  │   写文档 / 做表格     │  │  "这段代码有个 bug..."    │    │
│  │                      │  │                          │    │
│  │                      │  │  [接受]  [忽略]           │    │
│  └──────────────────────┘  └──────────────────────────┘    │
│                                                             │
│  特征：用户主导，AI 辅助，用户可以选择接受或忽略              │
│  典型产品：GitHub Copilot、Notion AI、Grammarly             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 Agent 模式：AI 来干活，用户来审核

```
┌─────────────────────────────────────────────────────────────┐
│                    Agent 模式                                │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  用户下达任务，AI 自主执行多步骤，最后交付结果                 │
│                                                             │
│  用户："帮我分析这份销售数据并生成报告"                        │
│           │                                                  │
│           ▼                                                  │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  AI 执行过程：                                       │   │
│  │  1. 读取数据文件                                     │   │
│  │  2. 清洗和转换                                       │   │
│  │  3. 计算关键指标                                     │   │
│  │  4. 生成图表                                         │   │
│  │  5. 撰写分析报告                                     │   │
│  └─────────────────────────────────────────────────────┘   │
│           │                                                  │
│           ▼                                                  │
│  用户审核结果 → 接受 / 修改 / 重新执行                        │
│                                                             │
│  特征：AI 主导执行，用户审核结果，可中断或调整                │
│  典型产品：Cursor Agent、Devin、Replit Agent                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.3 自动化模式：AI 在后台默默工作

```

│                    自动化模式                                 │
├─────────────────────────────────────────────────────────────┤

│                                                             │
│  ┌─────────────┐     ┌─────────────┐     ┌─────────────┐   │

│  - 新邮件到达 → 自动分类和摘要                                │

│  - 数据更新 → 自动异常检测                                    │
│                                                             │
│  特征：无人值守，自动触发，结果直接生效或通知用户              │
│  典型产品：邮件过滤、垃圾内容检测、智能推荐                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 二、如何选择正确的模式

### 2.1 决策框架

选择哪种模式，取决于三个维度：

```typescript
interface AIModeDecision {
  // 维度 1：任务的确定性
  certainty: 'high' | 'medium' | 'low'
  // 确定性高 → 自动化；确定性低 → Agent 或 Copilot

  // 维度 2：错误的代价
  errorCost: 'low' | 'medium' | 'high'
  // 代价低 → 自动化；代价高 → Copilot（让用户确认）

  // 维度 3：用户需要的控制感
  controlNeed: 'low' | 'medium' | 'high'
  // 控制感需求低 → Agent；控制感需求高 → Copilot
}
```

### 2.2 场景对照表

| 场景 | 确定性 | 错误代价 | 控制需求 | 推荐模式 |
|------|--------|---------|---------|---------|
| 代码补全 | 中 | 低 | 高 | Copilot |
| 邮件分类 | 高 | 低 | 低 | 自动化 |
| 数据分析报告 | 低 | 中 | 中 | Agent |
| 客服自动回复 | 中 | 高 | 低 | 自动化 + 人工兜底 |
| 文档写作辅助 | 低 | 低 | 高 | Copilot |
| 安全漏洞扫描 | 高 | 高 | 低 | 自动化 + 人工审核 |
| 竞品调研 | 低 | 低 | 中 | Agent |

### 2.3 决策流程图

```
开始
  │
  ▼
任务结果可以直接生效吗？
  │
  ├── 是 → 错误代价高吗？
  │         │
  │         ├── 否 → 自动化模式
  │         └── 是 → 自动化 + 人工审核
  │
  └── 否 → 用户需要频繁交互吗？
            │
            ├── 是 → Copilot 模式
            └── 否 → Agent 模式
```

## 三、Copilot 模式深度设计

### 3.1 核心设计原则

Copilot 不是"把 ChatGPT 塞进侧边栏"。好的 Copilot 设计需要满足：

```typescript
// Copilot 的四个设计原则
const copilotPrinciples = {
  // 1. 上下文感知：AI 知道用户当前在做什么
  contextAware: '自动获取用户当前编辑的内容、选中的文本、打开的文件',

  // 2. 即时响应：不需要用户手动描述问题
  instantResponse: '用户选中文本就能看到建议，不需要复制粘贴到对话框',

  // 3. 非侵入性：不打断用户的工作流
  nonIntrusive: '建议出现在旁边，不是弹窗或全屏覆盖',

  // 4. 可选择性：用户可以接受、修改或忽略
  optional: '按 Tab 接受，按 Esc 忽略，不影响用户的主体操作',
}
```

### 3.2 Copilot 的交互模式

```typescript
// 典型的 Copilot 组件结构
interface CopilotPanel {
  // 触发方式
  trigger: 'selection' | 'command' | 'automatic'

  // 建议类型
  suggestionType: 'inline' | 'panel' | 'overlay'

  // 用户操作
  actions: {
    accept: () => void    // 接受建议
    modify: (input: string) => void  // 修改后接受
    dismiss: () => void   // 忽略建议
    regenerate: () => void // 重新生成
  }
}

// 代码示例：Next.js 中的 Copilot 侧边栏
function CopilotSidebar({ currentDocument }: { currentDocument: string }) {
  const [suggestions, setSuggestions] = useState<string[]>([])
  const [loading, setLoading] = useState(false)

  const requestSuggestion = async (selectedText: string) => {
    setLoading(true)
    const response = await fetch('/api/copilot/suggest', {
      method: 'POST',
      body: JSON.stringify({
        context: currentDocument,
        selection: selectedText,
      }),
    })
    const data = await response.json()
    setSuggestions(data.suggestions)
    setLoading(false)
  }

  return (
    <aside className="copilot-panel">
      <h3>AI 建议</h3>
      {loading ? (
        <Spinner />
      ) : (
        suggestions.map((s, i) => (
          <SuggestionCard
            key={i}
            content={s}
            onAccept={() => applySuggestion(s)}
            onDismiss={() => dismissSuggestion(i)}
          />
        ))
      )}
    </aside>
  )
}
```

## 四、Agent 模式深度设计

### 4.1 Agent 的执行模型

Agent 模式的关键是"自主执行 + 可控边界"：

```typescript
// Agent 执行流程
interface AgentExecution {
  // 任务定义
  task: string

  // 执行步骤（Agent 自主规划）
  steps: AgentStep[]

  // 人工检查点
  checkpoints: Checkpoint[]

  // 状态
  status: 'planning' | 'executing' | 'paused' | 'completed' | 'failed'
}

interface AgentStep {
  id: string
  action: string           // 要做什么
  tool: string             // 用什么工具
  input: unknown           // 输入
  output: unknown          // 输出
  requiresApproval: boolean // 是否需要用户确认
}

// 关键设计：哪些步骤需要人工确认
const approvalRules = {
  // 涉及外部操作必须确认
  externalActions: ['send_email', 'create_file', 'api_call', 'database_write'],

  // 涉及金钱操作必须确认
  financialActions: ['payment', 'subscription', 'refund'],

  // 不可逆操作必须确认
  irreversibleActions: ['delete', 'publish', 'deploy'],
}
```

### 4.2 Agent 的状态展示

用户需要知道 Agent "在做什么"和"做到哪了"：

```typescript
// Agent 执行状态组件
function AgentProgress({ execution }: { execution: AgentExecution }) {
  return (
    <div className="agent-progress">
      <div className="agent-header">
        <h3>正在执行：{execution.task}</h3>
        <button onClick={execution.cancel}>取消</button>
      </div>

      <div className="agent-steps">
        {execution.steps.map((step) => (
          <div key={step.id} className={`step ${step.status}`}>
            <StepIcon status={step.status} />
            <span>{step.action}</span>
            {step.status === 'executing' && <Spinner size="sm" />}
            {step.requiresApproval && step.status === 'pending' && (
              <button onClick={() => execution.approveStep(step.id)}>
                确认执行
              </button>
            )}
          </div>
        ))}
      </div>

      {execution.status === 'completed' && (
        <AgentResult result={execution.result} />
      )}
    </div>
  )
}
```

## 五、自动化模式深度设计

### 5.1 自动化的触发与执行

```typescript
// 自动化 AI 处理管道
interface AutomationPipeline {
  // 触发条件
  trigger: {
    event: string           // 触发事件类型
    condition?: (data: any) => boolean  // 额外条件
  }

  // AI 处理
  processor: {
    prompt: (data: any) => string  // 动态构造 Prompt
    model: string                  // 使用的模型
    maxTokens: number
  }

  // 输出方式
  output: {
    type: 'notify' | 'action' | 'store'
    // notify: 通知用户
    // action: 直接执行操作
    // store: 存储结果供后续使用
  }

  // 失败处理
  fallback: {
    retryCount: number
    notifyOnFailure: boolean
    fallbackAction?: () => void
  }
}

// 实例：代码提交自动 Review
const codeReviewAutomation: AutomationPipeline = {
  trigger: {
    event: 'git.push',
    condition: (data) => data.branch === 'main',
  },
  processor: {
    prompt: (data) => `
      请审查以下代码变更，关注：
      1. 潜在的 bug
      2. 安全问题
      3. 性能问题
      
      变更文件：${data.files.join(', ')}
      差异：${data.diff}
    `,
    model: 'gpt-4o',
    maxTokens: 2000,
  },
  output: {
    type: 'notify', // 将 review 结果发到 PR 评论
  },
  fallback: {
    retryCount: 2,
    notifyOnFailure: true,
  },
}
```

## 六、混合模式的实际应用

真实产品往往不是单一模式，而是混合使用：

```typescript
// 以 AI 写作平台为例，三种模式并存
const writingPlatformAI = {
  // Copilot：写作时的实时建议
  copilot: {
    trigger: '用户停顿 2 秒或按快捷键',
    feature: '续写、改写、润色建议',
  },

  // Agent：长文生成任务
  agent: {
    trigger: '用户下达"帮我写一篇关于 XX 的文章"',
    feature: '大纲生成 → 分段写作 → 整合 → 润色',
    checkpoints: ['大纲确认', '初稿确认'],
  },

  // 自动化：后台处理
  automation: {
    trigger: '文章保存时',
    feature: '自动检查 SEO 关键词密度、可读性评分、错别字检测',
  },
}
```

## 常见误区

### 误区一：所有 AI 功能都做成对话框

很多产品把 AI 功能做成一个聊天界面，用户需要打字描述需求。但大多数场景下，用户不想"和 AI 对话"，他们想"让 AI 帮忙做事"。Copilot 模式（选中文本 → 看到建议）比对话框高效得多。

### 误区二：Agent 模式不需要人工确认

Agent "自主执行"不等于"不需要用户参与"。涉及外部操作（发邮件、修改数据、花钱）的步骤必须让用户确认。没有确认机制的 Agent 就是一个不受控的定时炸弹。

### 误区三：自动化 = 无人工干预

自动化模式也需要"人工兜底"。AI 分类邮件分错了怎么办？自动回复答错了怎么办？每个自动化管道都需要设计失败路径：重试、降级、通知人工介入。

### 误区四：选一种模式就够了

真实产品通常需要混合使用多种模式。写作工具有 Copilot（实时建议）也有 Agent（长文生成），客服系统有自动化（常见问题自动回复）也有人工接管（复杂问题转人工）。根据功能选模式，不要被产品形态限制。

## 工程建议

### 1. 先画用户流程图，再选 AI 模式

不要先想"我要用 Agent"，而是先画出用户的操作流程，标注哪些步骤可以被 AI 辅助，再根据辅助方式选择模式。

### 2. 从 Copilot 开始，逐步进化

Copilot 是最低风险的 AI 集成方式——用户可以选择忽略。先做 Copilot 积累用户反馈，再根据需求升级为 Agent 或自动化。

### 3. 为每种模式设计退出机制

Copilot 要能关闭，Agent 要能中断，自动化要能暂停。用户必须感觉"AI 是工具，不是绑架"。

### 4. 记录模式选择的理由

在产品文档中记录"为什么这个功能用 Agent 而不是 Copilot"。三个月后你会忘记当初的考量，而这些记录是后续迭代的基础。

---

## 小结

AI 功能设计的核心不是技术选型，而是交互形态选型。三种模式各有适用场景：Copilot 适合需要用户主导的辅助场景，Agent 适合需要 AI 自主执行的复杂任务，自动化适合确定性高、错误代价低的无人值守场景。大多数产品需要混合使用多种模式，关键是为每个功能找到正确的 AI 交互形态。

## 参考答案

### 练习一

**思路**：使用课程中的决策框架（确定性、错误代价、控制需求三个维度）来判断每个功能适合的模式。先列出功能，再逐个分析三个维度，最后给出模式选择和理由。

**答案**：

以"在线文档协作产品"为例：

| 功能 | 确定性 | 错误代价 | 控制需求 | 推荐模式 | 理由 |
|------|--------|---------|---------|---------|------|
| 智能排版建议 | 中 | 低 | 高 | Copilot | 用户在写文档，AI 在侧边栏建议排版优化，用户可以选择接受或忽略。错误代价低（排版错了可以撤销），但用户需要保持对文档的控制感。 |
| 自动生成会议纪要 | 低 | 中 | 中 | Agent | 用户上传会议录音，AI 自主执行：转写→提取要点→生成纪要→格式化。任务步骤多、确定性低，但最终结果需要用户审核。 |
| 文档自动保存和版本管理 | 高 | 低 | 低 | 自动化 | 保存操作确定性高（内容变了就保存），错误代价低（有版本历史可回滚），用户不需要主动控制。 |
| 智能内容补全 | 中 | 低 | 高 | Copilot | 类似代码补全，用户写到一半 AI 提示后续内容。用户需要保持写作主导权，可以选择 Tab 接受或继续自己写。 |
| 批量文档格式转换 | 高 | 低 | 低 | 自动化 | 用户上传一批文档，系统自动转为统一格式。规则明确、错误代价低、不需要用户逐步确认。 |

**要点**：
- 没有"最佳模式"，只有"最适合的模式"——同一功能在不同产品中可能需要不同模式
- 错误代价是最重要的决策维度：代价高就让用户确认（Copilot），代价低就自动化
- 控制需求高的场景用 Copilot，低的场景用 Agent 或自动化

### 练习二

**思路**：选择有代表性的 AI 产品，逐个分析其核心功能使用的模式，并从用户视角评价模式选择是否合理。

**答案**：

**产品 1：Notion AI**
- 写作辅助（续写、改写、翻译）→ Copilot 模式：用户选中文本，AI 在浮层中提供建议，用户决定是否采纳。✅ 模式正确，写作需要用户主导。
- AI 自动摘要 → Agent 模式：用户给一篇长文档，AI 自主读取并生成摘要。✅ 模式正确，摘要任务步骤明确，结果需要用户审核。
- Q&A 问答 → Copilot 模式：用户在对话框提问，AI 基于 workspace 内容回答。✅ 合理，用户需要控制问答方向。

**产品 2：GitHub Copilot**
- 代码补全 → Copilot 模式：用户写代码时 AI 在行内灰色提示。✅ 模式正确，代码补全需要开发者保持主导权。
- Copilot Chat → Copilot 模式：侧边栏对话，用户提问代码相关问题。✅ 合理。
- Copilot Workspace（Agent 模式）→ Agent 模式：描述需求后 AI 自主修改多个文件。⚠️ 有争议——对于大范围代码修改，错误代价较高，应该在关键节点增加人工确认，而不是让 AI 直接改完。

**产品 3：某电商客服机器人**
- 自动回复常见问题 → 自动化模式：用户问退货流程，AI 自动回复标准答案。✅ 模式正确，FAQ 回复确定性高、错误代价低。
- 自动处理退款 → 自动化模式：符合条件的退款 AI 直接执行。⚠️ 模式有问题——退款涉及资金，错误代价高，应该用 Agent 模式（AI 建议退款方案，人工确认后执行），或者至少设置金额阈值，小额自动、大额人工确认。

**要点**：
- 分析竞品时重点关注"模式选择是否匹配错误代价"——这是最常见的设计失误
- 很多产品的问题是"自动化过度"——把该人工确认的场景也自动化了
- 好的 AI 产品往往混合使用多种模式，不同功能用不同模式

### 练习三

**思路**：选一个核心功能，画出完整的用户操作流程，在每个步骤标注 AI 可以辅助的方式和推荐的模式。

**答案**：

以"智能客服处理退货请求"为例：

```
用户流程图：

[用户发起退货]
    │
    ▼
[AI 自动识别意图] ──── 自动化模式：NLP 识别用户要退货
    │
    ▼
[AI 自动查询订单] ──── 自动化模式：根据用户信息查订单
    │
    ├── 订单不存在 → [AI 自动提示：未找到订单，请提供订单号]
    │                      Copilot 模式：用户手动输入订单号
    │
    ▼
[AI 判断退货资格] ──── 自动化模式：检查退货期限、商品状态
    │
    ├── 不符合条件 → [AI 自动说明原因，提供替代方案]
    │
    ▼
[AI 生成退货方案] ──── Agent 模式：AI 自主计算退款金额、选择退货方式
    │
    ▼
[用户确认退货方案] ──── 人工确认节点：用户审核退款金额和退货方式
    │
    ├── 用户要求修改 → [AI 重新计算] ──── Agent 模式
    │
    ▼
[AI 执行退货流程] ──── 自动化模式：创建退货单、通知仓库、发起退款
    │
    ▼
[AI 发送确认通知] ──── 自动化模式：给用户发退货确认和物流信息
```

**要点**：
- 用户流程中"AI 辅助"和"人工确认"应该交替出现，而不是全自动化
- 关键决策节点（涉及资金、不可逆操作）必须有人工确认
- 流程图中标注模式选择的理由，方便团队对齐

### 练习四

**思路**：为三种不同模式分别设计交互形态，重点展示用户与 AI 的交互差异。低保真原型不需要精美，关键是表达清楚交互逻辑。

**答案**：

以"文档协作产品"为例，三种模式的低保真原型设计：

**Copilot 模式原型（智能写作助手）：**
```
┌────────────────────────────┬─────────────────────────┐
│                            │  🤖 AI 助手              │
│  文档编辑区                 │                         │
│                            │  建议：这段可以更简洁     │
│  用户正在输入：             │                         │
│  "本季度的销售业绩          │  [接受建议]  [忽略]      │
│   相比上季度有了..."        │                         │
│                            │  ─────────────────────   │
│                            │  你也可以问：            │
│                            │  "帮我润色这段文字"      │
│                            │  "翻译成英文"            │
└────────────────────────────┴─────────────────────────┘
交互要点：用户在主编辑区工作，AI 在右侧辅助，所有建议都需要用户主动采纳
```

**Agent 模式原型（自动生成周报）：**
```
┌──────────────────────────────────────────────────────┐
│  📋 AI 周报生成                                       │
│                                                      │
│  任务：基于本周文档和日程生成周报                      │
│                                                      │
│  执行进度：                                           │
│  ✅ 读取本周创建的 12 份文档                           │
│  ✅ 提取关键成果和数据                                 │
│  ✅ 分析本周日程和会议记录                             │
│  🔄 正在生成周报草稿...                               │
│  ⬜ 等待审核                                          │
│                                                      │
│  ┌──────────────────────────────────────┐            │
│  │ [停止执行]                    [暂停]  │            │
│  └──────────────────────────────────────┘            │
│                                                      │
│  ── 生成结果 ──                                       │
│  [周报草稿预览区]                                     │
│                                                      │
│  [采纳]  [重新生成]  [手动编辑]                        │
└──────────────────────────────────────────────────────┘
交互要点：用户下达任务后 AI 自主执行，展示执行步骤，结果需要用户审核
```

**自动化模式原型（文档自动分类）：**
```
┌──────────────────────────────────────────────────────┐
│  ⚙️ 自动分类设置                                      │
│                                                      │
│  规则：新上传的文档自动按内容分类到对应文件夹           │
│                                                      │
│  分类规则：                                           │
│  ├── 包含"合同"关键词 → 📁 合同文件夹                 │
│  ├── 包含"会议"关键词 → 📁 会议记录                   │
│  ├── 包含"报告"关键词 → 📁 项目报告                   │
│  └── 其他 → 📁 未分类（通知用户）                     │
│                                                      │
│  最近执行记录：                                       │
│  ✅ "Q3销售报告.pdf" → 📁 项目报告                    │
│  ✅ "供应商合同.docx" → 📁 合同文件夹                 │
│  ⚠️ "随手笔记.txt" → 📁 未分类（需要您手动归类）      │
│                                                      │
│  [暂停自动分类]                                       │
└──────────────────────────────────────────────────────┘
交互要点：用户设置规则后无需操作，系统自动执行，只在异常时通知用户
```

**要点**：
- 低保真原型的核心是表达交互逻辑，不需要视觉精美
- 三种模式的核心差异在于"谁主导"：Copilot 用户主导、Agent 协作、自动化系统主导
- 每种模式都要提供"退出机制"：关闭 Copilot、中断 Agent、暂停自动化
