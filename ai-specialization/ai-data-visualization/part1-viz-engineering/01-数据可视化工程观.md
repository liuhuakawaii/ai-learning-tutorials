## 场景引入

你接到一个需求："在管理后台加一个销售数据看板。" 产品经理给了你一张截图，上面有折线图、柱状图、饼图、数字卡片。看起来很简单——找个图表库，调几个 API，绑上数据就完事了。

但当你真正开始做，问题接踵而来：

- 数据从哪来？后端返回的 JSON 结构和图表需要的格式对不上。
- 折线图的 X 轴是时间，但后端返回的时间戳格式不统一，有的是秒级，有的是毫秒级。
- 饼图的"其他"类别怎么处理？占比低于 2% 的数据要不要合并？
- 管理者想要"点击某个省份下钻到城市"，这个交互怎么实现？
- 看板需要同时支持 PC 和移动端，图表的响应式怎么做？
- 数据量大了之后，页面明显卡顿，怎么优化？

一个看似简单的"加几个图表"，实际上涉及数据处理、交互设计、性能优化、响应式适配等多个工程问题。这就是为什么我们需要用**工程化**的视角来看待数据可视化。

## 核心概念

### 一、为什么可视化不只是画图

很多人对可视化的理解停留在"选一个图表类型，绑定数据，渲染出来"。这个理解在 demo 阶段没问题，但在生产环境中远远不够。

一个真实的可视化系统需要回答以下问题：

```
┌─────────────────────────────────────────────────────┐
│                  可视化要解决的问题                    │
├─────────────────────────────────────────────────────┤
│                                                     │
│  1. 数据从哪来？         → 数据源对接、ETL、缓存策略    │
│  2. 数据怎么处理？       → 聚合、过滤、异常值处理       │
│  3. 用什么图表？         → 图表选型、视觉编码原则        │
│  4. 交互怎么做？         → 下钻、联动、筛选、缩放        │
│  5. 性能怎么保证？       → 大数据量渲染、增量更新        │
│  6. 多端怎么适配？       → 响应式、无障碍访问            │
│  7. 怎么维护和迭代？     → 组件化、主题系统、文档        │
│                                                     │
└─────────────────────────────────────────────────────┘
```

这些问题跨越了前端、后端、设计三个领域。如果不从工程角度系统性地解决，最终你会得到一个"能跑但难维护"的图表页面。

### 二、可视化工程的三个层次

我们可以把可视化工程拆成三个层次，每个层次有清晰的职责边界：

```
┌───────────────────────────────────────────────────────────┐
│                        表现层                              │
│  图表组件、交互逻辑、动画、响应式、主题                        │
│  技术栈：ECharts / D3 / AntV / Recharts                    │
├───────────────────────────────────────────────────────────┤
│                        编码层                              │
│  数据到视觉属性的映射：位置、颜色、大小、形状                   │
│  比例尺、坐标系、图例、标注                                  │
├───────────────────────────────────────────────────────────┤
│                        数据层                              │
│  数据获取、清洗、聚合、转换、缓存                             │
│  技术栈：API / SQL / 数据管道                               │
└───────────────────────────────────────────────────────────┘
```

**数据层**负责提供干净、结构化的数据。这一层的核心挑战是：原始数据往往不适合直接可视化。比如后端返回的是逐条订单记录，但折线图需要的是按天聚合的销售趋势。你需要在这一层完成数据的转换和聚合。

**编码层**负责把数据映射到视觉属性。这是可视化最核心的理论基础。比如：用 X 轴编码时间、Y 轴编码销售额、颜色编码产品类别、气泡大小编码利润率。这些映射关系决定了用户能否从图表中正确读取信息。

**表现层**负责最终的渲染和交互。这一层关注的是用户体验：图表是否美观、交互是否流畅、在不同设备上是否都能正常使用。

大多数开发者的问题是：**只关注表现层，忽视了数据层和编码层。** 结果就是图表"能看但不好用"——数据不准确、映射不合理、交互不直观。

### 三、从需求到交付的完整流程

一个可视化项目的标准流程如下：

```
需求分析 → 数据梳理 → 图表选型 → 视觉设计 → 技术实现 → 性能优化 → 测试验收
   │          │          │          │          │          │          │
   ▼          ▼          ▼          ▼          ▼          ▼          ▼
 明确指标   确定数据源  选择图表   确定配色    编码实现   大数据量    兼容性
 确定受众   数据格式    类型       布局规范    交互逻辑   渲染优化    交互测试
 交互需求   数据质量    视觉编码   响应式      主题系统   缓存策略    验收标准
```

**第一步：需求分析。** 不要拿到需求就开始写代码。先搞清楚：
- 这个看板的受众是谁？高管关注趋势，运营关注细节。
- 核心指标是什么？一个看板不要超过 5-7 个核心指标。
- 用户需要什么交互？是纯查看，还是需要筛选、下钻、导出？

**第二步：数据梳理。** 和后端对齐数据格式：
- 接口返回的数据粒度是什么？按天、按小时、按分钟？
- 数据量有多大？100 条和 10 万条的渲染策略完全不同。
- 数据是否有缺失或异常？缺失值怎么展示？

**第三步：图表选型。** 不是所有数据都适合用折线图。选图表类型的核心原则是：**你想表达什么关系？**
- 趋势 → 折线图、面积图
- 对比 → 柱状图、条形图
- 占比 → 饼图、环形图、堆叠图
- 分布 → 散点图、直方图、箱线图
- 关系 → 桑基图、力导向图、热力图

**第四步到第七步** 我们会在后续课程中逐步展开。

```
└──────────────┴──────────────┴──────────────┴──────────────┴──────────────┘
```

**选型建议：**

- **大多数业务场景选 ECharts 或 AntV**：开箱即用，覆盖 90% 的图表需求，社区活跃，文档完善。ECharts 在国内生态更成熟，AntV 在 React 集成上更友好。
- **需要高度定制选 D3**：当你需要做非标准图表、复杂动画、或者独特的数据可视化时，D3 是唯一选择。但代价是学习曲线陡峭，开发效率低。
- **纯 React 项目且需求简单选 Recharts**：API 设计优雅，和 React 配合最自然。但能力有限，不适合复杂场景。
- **不要重复造轮子**：除非你在做可视化基础设施（比如给公司造图表库），否则不要用 D3 从零开始画柱状图。

### 五、可视化系统的架构设计

一个可维护的可视化系统需要考虑以下架构问题：

```
                    ┌─────────────────────┐
                    │     看板页面层       │
                    │  Dashboard Page     │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
     ┌────────────┐   ┌────────────┐   ┌────────────┐
     │  图表组件层  │   │  筛选器层   │   │  布局层    │
     │ ChartComp  │   │  Filters   │   │  Layout    │
     └─────┬──────┘   └─────┬──────┘   └────────────┘
           │                │
           ▼                ▼
     ┌────────────────────────────┐
     │       数据管理层            │
     │  DataProvider / Store      │
     └────────────┬──────────────┘
                  │
                  ▼
     ┌────────────────────────────┐
     │       数据服务层            │
     │  API / WebSocket / Cache   │
     └────────────────────────────┘
```

**关键设计原则：**

1. **数据与视图分离**：图表组件不直接调用 API，而是通过数据管理层获取数据。这样可以方便地实现数据缓存、多图表联动、数据格式统一。

2. **图表组件封装**：不要在页面里直接写 ECharts 配置。把每个图表封装成独立组件，接收标准化的数据格式，内部处理图表的初始化、更新、销毁。

3. **主题系统**：颜色、字体、间距等视觉变量统一管理。支持动态切换主题（比如深色模式），不需要修改每个图表组件。

4. **响应式设计**：图表需要根据容器大小自适应。不是简单地设置 `width: 100%`，而是要根据容器尺寸调整图表的内部布局（比如图例位置、坐标轴标签旋转角度）。

### 六、真实案例：销售数据看板

假设我们要为一个电商公司搭建销售数据看板，需求如下：

- 顶部：4 个数字卡片（今日销售额、订单数、客单价、退货率）
- 中部左侧：近 30 天销售趋势折线图
- 中部右侧：品类销售占比饼图
- 底部：各省份销售热力地图

我们来拆解这个需求的工程实现：

```
看板页面 (DashboardPage)
├── 数字卡片组 (StatCards)
│   └── 数据来源: GET /api/stats/today
├── 销售趋势图 (SalesTrendChart)
│   └── 数据来源: GET /api/stats/trend?days=30
├── 品类占比图 (CategoryPieChart)
│   └── 数据来源: GET /api/stats/category-share
└── 省份热力图 (ProvinceMapChart)
    └── 数据来源: GET /api/stats/province-sales
```

每个图表组件需要处理：
- **加载状态**：数据未返回时显示骨架屏或 loading
- **空数据状态**：没有数据时显示友好的空状态提示
- **错误状态**：请求失败时显示重试按钮
- **响应式**：容器大小变化时图表自适应
- **数据更新**：定时刷新或手动刷新

### 图表自适应 Hook

```typescript
// src/hooks/useChartResize.ts
import { useEffect, useRef } from 'react'
import type { ECharts } from 'echarts'

export function useChartResize(chartRef: React.RefObject<ECharts | null>) {
  const containerRef = useRef<HTMLDivElement>(null)

  useEffect(() => {
    if (!containerRef.current || !chartRef.current) return

    const observer = new ResizeObserver(() => {
      chartRef.current?.resize()
    })

    observer.observe(containerRef.current)
    return () => observer.disconnect()
  }, [chartRef])

  return containerRef
}
```

### 销售趋势折线图

```tsx
// src/components/SalesTrendChart.tsx
import { useRef, useEffect } from 'react'
import * as echarts from 'echarts'
import { salesTheme } from '../utils/chartTheme'
import { useChartResize } from '../hooks/useChartResize'
import { ChartCard } from './ChartCard'
import type { DailySales } from '../types/dashboard'

interface Props {
  data: DailySales[]
  loading?: boolean
}

export function SalesTrendChart({ data, loading }: Props) {
  const chartInstanceRef = useRef<echarts.ECharts | null>(null)
  const containerRef = useChartResize(chartInstanceRef)

  useEffect(() => {
    if (!containerRef.current) return

    const chart = echarts.init(containerRef.current)
    chartInstanceRef.current = chart
    chart.setOption(salesTheme)

    return () => {
      chart.dispose()
      chartInstanceRef.current = null
    }
  }, [])

  useEffect(() => {
    if (!chartInstanceRef.current || data.length === 0) return

    const dates = data.map(item => item.date)
    const amounts = data.map(item => item.amount)
    const orders = data.map(item => item.orderCount)

    chartInstanceRef.current.setOption({
      tooltip: {
        trigger: 'axis',
        axisPointer: { type: 'cross' },
      },
      legend: {
        data: ['销售额', '订单数'],
        top: 0,
        right: 0,
      },
      xAxis: {
        type: 'category',
        data: dates,
        axisLabel: {
          formatter: (value: string) => {
            const parts = value.split('-')
            return `${parts[1]}-${parts[2]}`
          },
        },
      },
      yAxis: [
        {
          type: 'value',
          name: '销售额（元）',
          axisLabel: {
            formatter: (value: number) => {
              if (value >= 10000) return `${(value / 10000).toFixed(1)}万`
              return value.toString()
            },
          },
        },
        {
          type: 'value',
          name: '订单数',
          splitLine: { show: false },
        },
      ],
      series: [
        {
          name: '销售额',
          type: 'line',
          data: amounts,
          smooth: true,
          areaStyle: {
            color: new echarts.graphic.LinearGradient(0, 0, 0, 1, [
              { offset: 0, color: 'rgba(84, 112, 198, 0.3)' },
              { offset: 1, color: 'rgba(84, 112, 198, 0.05)' },
            ]),
          },
          itemStyle: { color: '#5470C6' },
        },
        {
          name: '订单数',
          type: 'bar',
          yAxisIndex: 1,
          data: orders,
          barWidth: '40%',
          itemStyle: {
            color: '#91CC75',
            borderRadius: [4, 4, 0, 0],
          },
        },
      ],
    })
  }, [data])

  return (
    <ChartCard title="近 30 天销售趋势" loading={loading} hasData={data.length > 0}>
      <div ref={containerRef} style={{ width: '100%', height: 300 }} />
    </ChartCard>
  )
}
```

### 品类占比饼图

```tsx
// src/components/CategoryPieChart.tsx
import { useRef, useEffect } from 'react'
import * as echarts from 'echarts'
import { salesTheme } from '../utils/chartTheme'
import { useChartResize } from '../hooks/useChartResize'
import { ChartCard } from './ChartCard'
import type { CategoryShare } from '../types/dashboard'

interface Props {
  data: CategoryShare[]
  loading?: boolean
}

export function CategoryPieChart({ data, loading }: Props) {

  const containerRef = useChartResize(chartInstanceRef)

  useEffect(() => {
    if (!containerRef.current) return

    chartInstanceRef.current = chart
    chart.setOption(salesTheme)

    return () => {

  useEffect(() => {
    if (!chartInstanceRef.current || data.length === 0) return

    chartInstanceRef.current.setOption({
      tooltip: {
        trigger: 'item',
        formatter: '{b}: ¥{c} ({d}%)',
      },
      legend: {
        orient: 'vertical',
        right: 10,

        {
          type: 'pie',

          },
          emphasis: {
            label: {

            },
          },
          data: data.map(item => ({
            name: item.category,
```

## 常见误区

### 误区一：一上来就选图表库

很多开发者接到需求后第一件事是 `npm install echarts`。正确的顺序是：先梳理数据和需求，再选工具。选错图表库的迁移成本远高于前期多花 30 分钟做技术选型。

### 误区二：在页面组件里直接写图表配置

把 ECharts 的 option 对象直接写在页面组件里，会导致代码难以复用和维护。应该封装成独立的图表组件，对外暴露数据接口，对内处理图表逻辑。

### 误区三：忽视数据层的处理

后端返回的数据很少能直接用于图表展示。时间格式不统一、数值精度不一致、缺少必要的聚合——这些都是常见问题。在图表组件里做数据处理会导致组件职责不清，应该在数据层统一处理。

### 误区四：不做响应式处理

设置了 `width: 100%` 就认为图表是响应式的。实际上 ECharts 不会自动监听容器大小变化，需要手动调用 `chart.resize()` 或使用 ResizeObserver 监听。

### 误区五：图表类型选择不当

用饼图展示超过 8 个类别的数据、用折线图展示没有时间关系的对比数据、用 3D 图表展示 2D 数据——这些错误的图表选型会让数据更难理解，而不是更容易。

## 参考答案

### 练习一

**思路**：需要综合考虑图表丰富度、定制能力、大数据量支持、React 集成和开发效率。

**答案**：

推荐方案：**AntV G2 + G2Plot 作为核心，D3.js 处理定制场景**

理由：
1. AntV 的图表类型覆盖广，G2Plot 开箱即用的图表超过 50 种，满足第一个需求。
2. G2 底层基于图形语法（Grammar of Graphics），定制能力强。交互式的散点图可以通过 G2 的交互机制实现，不需要从零造轮子。
3. AntV 5.x 支持 WebGL 渲染，10 万条数据量可以流畅渲染。
4. AntV 有 `@ant-design/charts` React 封装，集成自然。
5. 对于极特殊的定制需求，可以在个别页面引入 D3 作为补充。

不推荐全用 D3：3 个月周期内用 D3 实现 50+ 种图表不现实。
不推荐 Recharts：定制能力和大数据量支持都不够。

**要点**：
- 选型要考虑团队学习成本
- 核心需求用成熟方案，边缘需求可以用灵活方案补充
- 大数据量是关键约束，要提前做性能测试

### 练习二

**思路**：实时大屏的核心挑战是高频数据更新下的渲染性能和稳定性。

**答案**：

```
┌─────────────────────────────────────────────────────────┐
│                    大屏展示层                             │
│  全屏布局 → 响应式栅格 → 自适应缩放（scale transform）    │
├──────────┬──────────┬───────────┬───────────────────────┤
│ 折线图   │ 柱状图   │ 数字卡片   │      地图             │
│ (ECharts)│ (ECharts)│ (React)   │   (ECharts Map)      │
└────┬─────┴────┬─────┴─────┬─────┴───────────┬───────────┘
     │          │           │                 │
     ▼          ▼           ▼                 ▼
┌─────────────────────────────────────────────────────────┐
│                  数据管理层（Zustand）                     │
│  - 接收 WebSocket 数据                                    │
│  - 数据格式化与聚合                                        │
│  - 维护滑动窗口（保留最近 100 个数据点）                    │
│  - 深色主题状态管理                                        │
├─────────────────────────────────────────────────────────┤
│                  连接层                                   │
│  WebSocket Client → 自动重连 → 心跳检测                   │
└─────────────────────────────────────────────────────────┘
```

关键设计决策：
1. **滑动窗口**：实时数据不断累积会导致内存膨胀和渲染卡顿。只保留最近 100-200 个数据点，旧数据丢弃或归档。
2. **节流渲染**：5 秒一次的数据推送不需要每次都触发图表重绘。可以用 `requestAnimationFrame` 或 2 秒的节流来控制渲染频率。
3. **全屏适配**：大屏分辨率固定（通常 1920×1080），用 CSS `transform: scale()` 做整体缩放比响应式布局更可控。
4. **深色主题**：通过 CSS 变量 + ECharts 主题实现，切换时不需要重新初始化图表。

**要点**：
- 实时数据的关键是控制渲染频率，不是数据推送频率
- 大屏场景用固定比例缩放比响应式更稳定
- WebSocket 需要处理断线重连和数据积压
