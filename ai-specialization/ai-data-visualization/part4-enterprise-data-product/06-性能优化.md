## 场景引入

你交付了多数据源接入模块，客户正式上线使用。第一周一切正常。第二周，销售总监在看板上加载"全国门店年度销售趋势"——365 天 × 500 家门店的折线图，数据量 18 万行。页面白屏了 8 秒。

打开 DevTools 排查，发现三个问题叠加在一起：后端查询用了 2.1 秒（全表扫描无索引），数据传输用了 1.3 秒（JSON 体积 45MB），前端渲染用了 4.6 秒（Canvas 绑定 18 万个数据点）。

这不是一个层面的问题，而是**查询 → 传输 → 渲染**整条链路的系统性瓶颈。只优化其中一层，效果有限——必须逐层排查、逐层消灭。

更棘手的是，性能问题往往在数据量小时不暴露。开发环境用几千条测试数据，一切流畅；上线后数据积累到百万级，问题集中爆发。这就是为什么性能优化必须在架构设计阶段就考虑，而不是等到用户投诉时才临时补救。

## 核心概念

### 一、性能瓶颈分析：三层链路模型

数据可视化的性能瓶颈分布在三个阶段，每个阶段的优化手段完全不同：

```
数据可视化性能链路
┌───────────────────────────────────────────────────────┐
│  用户点击筛选                                           │
│     │                                                  │
│     ▼                                                  │
│  ┌─────────────────────────────────────────────┐       │
│  │  阶段 1: 数据查询 (后端)                      │       │
│  │  瓶颈: 全表扫描、复杂 JOIN、大量聚合计算       │       │
│  │  优化: 索引、物化视图、预聚合、分区             │       │
│  │  目标: 2.1s → 200ms                          │       │
│  └─────────────────────┬───────────────────────┘       │
│                        ▼                               │
│  ┌─────────────────────────────────────────────┐       │
│  │  阶段 2: 数据传输 (网络)                      │       │
│  │  瓶颈: JSON 体积大、序列化/反序列化慢          │       │
│  │  优化: 压缩、分页、增量传输、二进制格式         │       │
│  │  目标: 1.3s → 50ms                           │       │
│  └─────────────────────┬───────────────────────┘       │
│                        ▼                               │
│  ┌─────────────────────────────────────────────┐       │
│  │  阶段 3: 前端渲染                            │       │
│  │  瓶颈: DOM 节点过多、重排重绘、内存占用        │       │
│  │  优化: Canvas 渲染、虚拟裁剪、Web Worker      │       │
│  │  目标: 4.6s → 100ms                          │       │
│  └─────────────────────────────────────────────┘       │
│                                                        │
│  总耗时优化: 8s → 350ms (23x 提升)                      │
└───────────────────────────────────────────────────────┘
```

**关键认知**：大多数开发者只关注"查询慢"，但实际项目中三个阶段的耗时经常是同一量级。而且它们是串行的——任何一层慢了，整体就慢。优化必须逐层排查，不能只盯着一层。

**量化方法**：优化前先度量。在每一层的入口和出口埋点，记录耗时分布，找到真正的瓶颈所在。没有数据支撑的优化就是盲猜。

### 二、查询优化：物化视图与预聚合

物化视图（Materialized View）是把查询结果预先计算并存储的策略。本质是**用空间换时间**——牺牲一点存储空间和写入延迟，换取查询速度的数量级提升。

```
查询优化策略对比
┌──────────────────────────────────────────────────────┐
│  原始查询:                                            │
│  SELECT region, DATE(order_date) as day,              │
│         SUM(amount), COUNT(*)                         │
│  FROM orders                                          │
│  WHERE order_date >= '2025-01-01'                     │
│  GROUP BY region, DATE(order_date)                    │
│                                                       │
│  执行计划: 全表扫描 → 200万行 → 聚合 → 18万行结果      │
│  耗时: 2.1s                                           │
├──────────────────────────────────────────────────────┤
│  优化方案 A: 物化视图                                  │
│  CREATE MATERIALIZED VIEW mv_daily_region_sales AS    │
│  SELECT region, DATE(order_date) as day,              │
│         SUM(amount), COUNT(*)                         │
│  FROM orders GROUP BY region, DATE(order_date);       │
│                                                       │
│  查询改写为: SELECT * FROM mv_daily_region_sales       │
│  耗时: 45ms                                           │
├──────────────────────────────────────────────────────┤
│  优化方案 B: 多粒度预聚合表                             │
│  agg_hourly  → 小时级聚合 (7天内数据)                   │
│  agg_daily   → 天级聚合 (30天内数据)                    │
│  agg_monthly → 月级聚合 (历史数据)                      │
│  查询时根据时间范围自动选择最粗粒度                      │
│  耗时: 12ms                                           │
└──────────────────────────────────────────────────────┘
```

**预聚合粒度选择原则**：不是越细越好，也不是越粗越好。关键看查询的时间跨度：

- 查询最近 24 小时 → 用小时级聚合
- 查询最近 30 天 → 用天级聚合
- 查询最近一年 → 用月级聚合

查询路由逻辑应该自动选择合适的粒度，而不是让用户手动指定。这需要在查询引擎中加入一个**粒度路由器**：根据 SQL 中的时间范围条件，自动判断应该查哪张聚合表。

### 三、缓存策略：三级缓存架构

单一缓存层不够用。高性能数据产品通常采用三级缓存：

```
三级缓存架构
┌───────────────────────────────────────────────────────┐
│  用户请求                                              │
│     │                                                 │
│     ▼                                                 │
│  ┌───────────────────────────────────────────┐        │
│  │  L1: 浏览器缓存 (Memory / IndexedDB)      │        │
│  │  命中率目标: 40%                           │        │
│  │  过期时间: 30秒 - 5分钟                    │        │
│  │  适用: 当前会话的重复查询                   │        │
│  └───────────────────┬───────────────────────┘        │
│                      │ 未命中                          │
│                      ▼                                │
│  ┌───────────────────────────────────────────┐        │
│  │  L2: CDN / 边缘缓存                       │        │
│  │  命中率目标: 30%                           │        │
│  │  过期时间: 1分钟 - 1小时                   │        │
│  │  适用: 跨用户的公共数据                     │        │
│  └───────────────────┬───────────────────────┘        │
│                      │ 未命中                          │
│                      ▼                                │
│  ┌───────────────────────────────────────────┐        │
│  │  L3: Redis 缓存                           │        │
│  │  命中率目标: 25%                           │        │
│  │  过期时间: 5分钟 - 24小时                   │        │
│  │  适用: 计算密集型查询结果                   │        │
│  └───────────────────┬───────────────────────┘        │
│                      │ 未命中                          │
│                      ▼                                │
│  ┌───────────────────────────────────────────┐        │
│  │  源数据库查询 (5% 的请求真正到达这里)       │        │
│  └───────────────────────────────────────────┘        │
└───────────────────────────────────────────────────────┘
```

**缓存键设计**是缓存策略的灵魂。推荐格式：`{数据源}:{表名}:{查询哈希}:{用户角色哈希}`。其中查询哈希是对 SQL + 参数的哈希，用户角色哈希用于权限隔离——不同权限的用户看到的数据范围不同，不能共享缓存。

**缓存失效策略**的选择：

- **TTL（过期时间）**：最简单，但不精确。数据更新后缓存可能还没过期
- **主动失效**：数据写入时主动清除相关缓存。精确但需要知道缓存和数据的关联关系
- **版本号**：每次数据更新递增版本号，缓存键中包含版本号。版本变了自动失效

三种策略各有利弊，实际项目中通常组合使用：TTL 兜底 + 主动失效精确清除。

### 四、前端渲染优化

前端渲染百万级数据点，DOM 方案直接不可行——18 万个 SVG 节点足以让浏览器崩溃。需要换渲染策略：

```
渲染方案性能对比 (10万数据点)
┌─────────────┬────────────┬───────────┬──────────────┐
│ 方案         │ 渲染时间    │ 内存占用   │ 交互流畅度    │
├─────────────┼────────────┼───────────┼──────────────┤
│ SVG DOM     │ 4600ms     │ 850MB     │ 卡顿         │
│ Canvas 2D   │ 180ms      │ 120MB     │ 流畅         │
│ Canvas +    │ 95ms       │ 85MB      │ 非常流畅     │
│ 虚拟裁剪    │            │           │              │
│ WebGL       │ 35ms       │ 60MB      │ 极致流畅     │
└─────────────┴────────────┴───────────┴──────────────┘
```

**虚拟裁剪**的核心思想：只渲染可视区域内的数据点。如果屏幕宽度 1200px，每个数据点占 2px，那最多同时渲染 600 个点——不管总数据量是 1 万还是 100 万。

**Canvas 渲染**的关键技巧：

1. **分层 Canvas**：背景层（坐标轴、网格线）和数据层（折线、散点）分开，数据更新时只重绘数据层
2. **离屏 Canvas**：先把完整的图表绘制到离屏 Canvas 上，然后只把可视区域拷贝到屏幕 Canvas
3. **requestAnimationFrame**：避免强制同步布局，用 rAF 调度绘制
4. **Web Worker 排序**：大数据量的排序和过滤放到 Worker 线程，不阻塞主线程

### 五、增量更新与 LLM 推理优化

全量刷新是最浪费的更新方式。当数据源只新增了 10 条记录，为什么要重新拉取全部 18 万行？

**SSE（Server-Sent Events）** 是数据看板最推荐的增量更新方案：基于 HTTP 穿透防火墙、自动重连、服务端单向推送、浏览器原生支持。增量更新的实现关键是**变更标识**：每次数据更新时记录一个时间戳或版本号，前端只请求这个时间戳之后的变更。

**LLM 推理优化**在对话式 BI 中同样关键：

- **缓存常见查询**：用户问"本月销售额"的频率极高，缓存 NL2SQL 结果避免重复推理
- **小模型优先**：简单查询用 7B 模型处理，复杂分析再调用 70B 模型
- **Prompt 压缩**：Schema 信息只传相关表和字段，不传整个数据库元数据

### server/aggregation.py

```python
"""预聚合引擎：根据查询时间范围自动选择最粗粒度的聚合表。"""

from dataclasses import dataclass
from datetime import datetime, timedelta
from enum import Enum
from typing import Optional

import psycopg2


class Granularity(Enum):
    HOURLY = "hourly"
    DAILY = "daily"
    MONTHLY = "monthly"


@dataclass
class AggregatedResult:
    granularity: Granularity
    rows: list[dict]
    source_table: str
    query_ms: float


class AggregationRouter:
    AGG_TABLES = {
        Granularity.HOURLY: "agg_sales_hourly",
        Granularity.DAILY: "agg_sales_daily",
        Granularity.MONTHLY: "agg_sales_monthly",
    }

    THRESHOLDS = {
        Granularity.HOURLY: timedelta(days=7),
        Granularity.DAILY: timedelta(days=90),
    }

    def __init__(self, dsn: str):
        self.conn = psycopg2.connect(dsn)

    def choose_granularity(self, start: datetime, end: datetime) -> Granularity:
        span = end - start
        if span <= self.THRESHOLDS[Granularity.HOURLY]:
            return Granularity.HOURLY
        elif span <= self.THRESHOLDS[Granularity.DAILY]:
            return Granularity.DAILY
        return Granularity.MONTHLY

    def query(self, start: datetime, end: datetime, region: Optional[str] = None) -> AggregatedResult:
        import time

        granularity = self.choose_granularity(start, end)
        table = self.AGG_TABLES[granularity]

        where = ["time_bucket >= %s", "time_bucket < %s"]
        params: list = [start, end]
        if region:
            where.append("region = %s")
            params.append(region)

        sql = f"SELECT time_bucket, region, total_amount, order_count FROM {table} WHERE {' AND '.join(where)} ORDER BY time_bucket"

        t0 = time.perf_counter()
        with self.conn.cursor() as cur:
            cur.execute(sql, params)
            columns = [desc[0] for desc in cur.description]
            rows = [dict(zip(columns, row)) for row in cur.fetchall()]
        elapsed_ms = (time.perf_counter() - t0) * 1000

        return AggregatedResult(granularity=granularity, rows=rows, source_table=table, query_ms=round(elapsed_ms, 1))
```

```python
"""基于 Redis 的查询结果缓存，支持 TTL 和主动失效。"""

import hashlib
import json
from dataclasses import dataclass
from typing import Any, Optional

import redis


@dataclass
class CacheStats:
    hits: int = 0
    misses: int = 0

    @property
    def hit_rate(self) -> float:
        total = self.hits + self.misses
        return self.hits / total if total > 0 else 0.0


class QueryCache:
    def __init__(self, redis_url: str = "redis://localhost:6379/0", default_ttl: int = 300):
        self.redis = redis.from_url(redis_url, decode_responses=True)
        self.default_ttl = default_ttl
        self.stats = CacheStats()
        self._version_key = "cache:version"
        self.redis.setnx(self._version_key, "1")

    def _make_key(self, query_sql: str, params: dict, user_role: str) -> str:
        query_hash = hashlib.sha256(f"{query_sql}:{json.dumps(params, sort_keys=True)}".encode()).hexdigest()[:16]
        version = self.redis.get(self._version_key) or "1"
        return f"q:{query_hash}:role:{user_role}:v{version}"

    def get(self, query_sql: str, params: dict, user_role: str) -> Optional[Any]:
        key = self._make_key(query_sql, params, user_role)
        cached = self.redis.get(key)
        if cached:
            self.stats.hits += 1
            return json.loads(cached)
        self.stats.misses += 1
        return None

    def set(self, query_sql: str, params: dict, user_role: str, result: Any, ttl: Optional[int] = None) -> None:
        key = self._make_key(query_sql, params, user_role)
        self.redis.setex(key, ttl or self.default_ttl, json.dumps(result, default=str))

    def invalidate_by_version(self) -> None:
        self.redis.incr(self._version_key)
```

### server/sse_stream.py

```python
"""SSE 增量推送：基于时间戳的变更检测与推送。"""

import asyncio
import json
import time
from dataclasses import dataclass
from typing import AsyncGenerator

import psycopg2


@dataclass
class ChangeEvent:
    table: str
    operation: str
    row_id: str
    data: dict
    timestamp: float


class ChangeTracker:
    def __init__(self, dsn: str, poll_interval: float = 2.0):
        self.dsn = dsn
        self.poll_interval = poll_interval
        self._last_check: float = 0

    def get_changes_since(self, since: float) -> list[ChangeEvent]:
        conn = psycopg2.connect(self.dsn)
        try:
            with conn.cursor() as cur:
                cur.execute(
                    "SELECT id, region, total_amount, updated_at FROM agg_sales_daily "
                    "WHERE EXTRACT(EPOCH FROM updated_at) > %s ORDER BY updated_at",
                    (since,),
                )
                columns = [desc[0] for desc in cur.description]
                return [
                    ChangeEvent(
                        table="agg_sales_daily", operation="update",
                        row_id=str(row[0]), data=dict(zip(columns, row)),
                        timestamp=time.time(),
                    )
                    for row in cur.fetchall()
                ]
        finally:
            conn.close()


class SSEPublisher:
    def __init__(self, tracker: ChangeTracker):
        self.tracker = tracker
        self._subscribers: list[asyncio.Queue] = []

    def subscribe(self) -> asyncio.Queue:
        queue: asyncio.Queue = asyncio.Queue()
        self._subscribers.append(queue)
        return queue

    def unsubscribe(self, queue: asyncio.Queue) -> None:
        self._subscribers.remove(queue)

    async def publish(self, event: ChangeEvent) -> None:
        for queue in self._subscribers:
            await queue.put(event)

    async def poll_loop(self) -> None:
        while True:
            changes = self.tracker.get_changes_since(self.tracker._last_check)
            for change in changes:
                await self.publish(change)
            if changes:
                self.tracker._last_check = time.time()
            await asyncio.sleep(self.tracker.poll_interval)

    async def event_stream(self, queue: asyncio.Queue) -> AsyncGenerator[str, None]:
        try:
            while True:
                event = await queue.get()
                data = json.dumps({"table": event.table, "operation": event.operation, "row_id": event.row_id, "data": event.data}, default=str)
                yield f"event: {event.operation}\ndata: {data}\n\n"
        except asyncio.CancelledError:
            return
```

### server/app.py

```python
"""FastAPI 应用：聚合查询 + 缓存 + SSE 增量推送。"""

from contextlib import asynccontextmanager
from datetime import datetime
from typing import Optional

from fastapi import FastAPI, Query
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import JSONResponse
from sse_starlette.sse import EventSourceResponse

from aggregation import AggregationRouter
from cache import QueryCache
from sse_stream import ChangeTracker, SSEPublisher

DSN = "postgresql://localhost:5432/bi_platform"
REDIS_URL = "redis://localhost:6379/0"

router = AggregationRouter(DSN)
cache = QueryCache(REDIS_URL, default_ttl=300)
tracker = ChangeTracker(DSN, poll_interval=2.0)
publisher = SSEPublisher(tracker)


@asynccontextmanager
async def lifespan(app: FastAPI):
    import asyncio
    task = asyncio.create_task(publisher.poll_loop())
    yield
    task.cancel()


app = FastAPI(title="Performance Chart API", lifespan=lifespan)
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["*"])


@app.get("/api/chart-data")
async def get_chart_data(
    start: str = Query(...), end: str = Query(...),
    region: Optional[str] = None, user_role: str = Query("viewer"),
):
    start_dt, end_dt = datetime.fromisoformat(start), datetime.fromisoformat(end)
    sql_key = f"chart:{start}:{end}:{region or 'all'}"

    cached = cache.get(sql_key, {"region": region}, user_role)
    if cached:
        resp = JSONResponse(content=cached)
        resp.headers["Cache-Control"] = "public, max-age=300"
        return resp

    result = router.query(start_dt, end_dt, region)
    payload = {
        "granularity": result.granularity.value,
        "data": result.rows,
        "meta": {"source_table": result.source_table, "query_ms": result.query_ms, "row_count": len(result.rows)},
    }
    cache.set(sql_key, {"region": region}, user_role, payload, ttl=300)
    return JSONResponse(content=payload)


@app.get("/api/stream")
async def stream_changes():
    queue = publisher.subscribe()

    async def generate():
        try:
            async for event in publisher.event_stream(queue):
                yield event
        finally:
            publisher.unsubscribe(queue)

    return EventSourceResponse(generate())
```

## 常见误区

### 误区一：优化就是加缓存

很多开发者遇到性能问题第一反应是加缓存。但缓存只能解决重复查询的问题，不能解决首次查询慢的问题。如果一个查询本身需要 5 秒，缓存只是让第二次变快——但用户第一次体验仍然很差。正确的做法是先优化查询本身（索引、物化视图、预聚合），把首次查询降到可接受的范围，再用缓存锦上添花。

### 误区二：前端数据越多越好

"用户要看全量数据"是一个常见的伪需求。当数据量超过 1 万条时，人眼已经无法分辨每个数据点。18 万行数据和 1800 行降采样后的数据，在折线图上呈现的趋势几乎一样。正确的做法是根据可视区域的像素数决定数据点数量，超出部分在后端做降采样（LTTB 算法），而不是传到前端再裁剪。

### 误区三：SSE 比 WebSocket 更好

SSE 确实更适合数据看板的场景，但它有单域名连接数限制（浏览器对同一域名最多 6 个 SSE 连接）。如果用户同时打开 6 个看板标签页，第 7 个会连接失败。实际项目中需要做连接复用：多个看板共享一个 SSE 连接，通过事件类型区分不同的数据更新。或者在连接数接近限制时降级为轮询模式。

### 误区四：缓存命中率越高越好

盲目提高缓存命中率可能导致数据一致性问题。如果把缓存 TTL 设为 24 小时，命中率确实很高，但用户看到的可能是昨天的数据。正确的做法是根据数据更新频率设定 TTL：实时数据用短 TTL（30 秒），日报数据用长 TTL（1 小时）。对于关键指标，应该在数据写入时主动失效缓存。

## 小结与练习

### 小结

1. **三层链路模型**：数据可视化的性能瓶颈分布在查询、传输、渲染三个阶段，必须逐层排查
2. **物化视图与预聚合**：根据查询时间范围自动选择最粗粒度的聚合表，首次查询即可提速 10-100 倍
3. **三级缓存架构**：浏览器缓存 + CDN + Redis 组合使用，95% 的请求不需要访问源数据库
4. **Canvas 渲染与虚拟裁剪**：只渲染可视区域内的数据点，配合离屏 Canvas 和分层绘制
5. **SSE 增量推送**：基于时间戳的变更检测，避免全量刷新浪费带宽
6. **LLM 推理优化**：缓存常见查询、小模型优先、Prompt 压缩

## 参考答案

### 练习一

**思路**：LTTB 的核心思想是每次从当前桶中选出一个点，使得与前一个选中点和下一个桶的平均点构成的三角形面积最大。这样能保留数据的"转折点"，视觉上与原始曲线最接近。

**答案**：

```python
from typing import NamedTuple


class Point(NamedTuple):
    x: float
    y: float


def downsample_lttb(data: list[Point], target_count: int) -> list[Point]:
    if target_count >= len(data) or target_count < 3:
        return data

    sampled = [data[0]]
    bucket_size = (len(data) - 2) / (target_count - 2)

    for i in range(1, target_count - 1):
        bucket_start = int((i - 1) * bucket_size) + 1
        bucket_end = int(i * bucket_size) + 1
        next_start = int(i * bucket_size) + 1
        next_end = min(int((i + 1) * bucket_size) + 1, len(data))

        avg_x = sum(d.x for d in data[next_start:next_end]) / (next_end - next_start)
        avg_y = sum(d.y for d in data[next_start:next_end]) / (next_end - next_start)

        prev = sampled[-1]
        max_area, selected = -1.0, bucket_start
        for j in range(bucket_start, bucket_end):
            area = abs((prev.x - avg_x) * (data[j].y - prev.y) - (prev.x - data[j].x) * (avg_y - prev.y)) * 0.5
            if area > max_area:
                max_area, selected = area, j

        sampled.append(data[selected])

    sampled.append(data[-1])
    return sampled


data = [Point(i, i * 0.5 + (i % 3) * 10) for i in range(10000)]
result = downsample_lttb(data, 200)
print(f"原始: {len(data)} 点 → 降采样: {len(result)} 点")
```

**要点**：
- 第一个和最后一个点始终保留
- 三角形面积公式用叉积计算，避免三角函数开销
- bucket_size 是浮点数，确保最后一个桶能覆盖到倒数第二个点

### 练习二

**思路**：分析用户的访问日志，提取最常用的查询模式（高频表 + 常用时间范围），在应用启动时并行预加载这些查询的结果到缓存。

**答案**：

```python
from collections import Counter
from concurrent.futures import ThreadPoolExecutor, as_completed


class CachePreWarmer:
    def __init__(self, query_executor, cache, max_concurrent: int = 3):
        self.query_executor = query_executor
        self.cache = cache
        self.max_concurrent = max_concurrent

    def analyze_patterns(self, log_entries: list[dict]) -> list[dict]:
        counter = Counter()
        for entry in log_entries:
            key = f"{entry['table']}:{entry['time_range']}:{entry.get('region', 'all')}"
            counter[key] += 1
        return [
            {"table": parts[0], "time_range": parts[1], "region": parts[2] if parts[2] != "all" else None, "frequency": freq}
            for key, freq in counter.most_common(20)
            for parts in [key.split(":")]
        ]

    def warmup(self, patterns: list[dict]) -> dict:
        warmed, skipped, failed = 0, 0, 0
        with ThreadPoolExecutor(max_workers=self.max_concurrent) as executor:
            futures = {}
            for p in patterns:
                cache_key = f"warmup:{p['table']}:{p['time_range']}:{p.get('region', 'all')}"
                if self.cache.get(cache_key, {}, "system"):
                    skipped += 1
                    continue
                futures[executor.submit(self.query_executor, p)] = cache_key
            for future in as_completed(futures):
                try:
                    result = future.result()
                    self.cache.set(futures[future], {}, "system", result, ttl=600)
                    warmed += 1
                except Exception:
                    failed += 1
        return {"warmed": warmed, "skipped": skipped, "failed": failed}
```

**要点**：
- 优先预热"高频 × 高耗时"的查询，收益最大
- 并发控制在 3 以内，避免预热过程本身对数据库造成压力
- 已有缓存的查询直接跳过，不重复执行

### 练习三

**思路**：维护一个 FPS 监控器，当 FPS 低于阈值时逐步增加降采样比例，FPS 恢复后逐步减少。用指数移动平均平滑 FPS 波动，避免频繁切换。

**答案**：

```python
import time


class AdaptiveDownsampler:
    def __init__(self, target_fps: float = 55.0, min_ratio: float = 0.1):
        self.target_fps = target_fps
        self.min_ratio = min_ratio
        self.current_ratio = 1.0
        self._last_time: float = 0
        self._ema_fps: float = 60.0
        self._alpha = 0.2

    def record_frame(self) -> float:
        now = time.perf_counter()
        if self._last_time > 0:
            dt = now - self._last_time
            fps = 1.0 / dt if dt > 0 else 60.0
            self._ema_fps = self._alpha * fps + (1 - self._alpha) * self._ema_fps
        self._last_time = now
        return self._ema_fps

    def get_visible_count(self, total_count: int) -> int:
        self.record_frame()
        if self._ema_fps < self.target_fps * 0.8:
            self.current_ratio = max(self.min_ratio, self.current_ratio * 0.7)
        elif self._ema_fps < self.target_fps:
            self.current_ratio = max(self.min_ratio, self.current_ratio * 0.9)
        elif self._ema_fps > self.target_fps + 5:
            self.current_ratio = min(1.0, self.current_ratio * 1.3)
        return max(100, int(total_count * self.current_ratio))


sampler = AdaptiveDownsampler(target_fps=55.0)
total = 100000
for frame in range(200):
    visible = sampler.get_visible_count(total)
    if frame % 50 == 0:
        print(f"帧 {frame}: FPS={sampler._ema_fps:.1f}, 可见点={visible}, 比例={sampler.current_ratio:.2f}")
```

**要点**：
- FPS 用指数移动平均（EMA）平滑，避免单帧波动导致降采样比例频繁跳动
- 降采样比例下降用 0.7/0.8 的系数快速响应，上升用 1.3 的系数缓慢恢复
- 最小可见点数设为 100，避免降采样过度导致图表完全空白
