## 场景引入

想象一个真实场景：你是某电商公司的数据分析师，老板在会议上问——"帮我看看上个季度各品类的销售额对比，用柱状图展示，要能看出同比增长率。"

传统做法：打开 Excel 或 BI 工具，手动选数据、选图表类型、配颜色、加辅助线。整个过程少则 10 分钟，多则半小时。

现在我们想做的是：**用一句自然语言描述，直接生成可运行的图表代码。** 用户不需要知道 ECharts 的 `xAxis` 怎么配、D3 的 `scale` 怎么写，只需要说出想要什么。

这就是"代码生成式可视化"的核心价值——**把人的意图翻译成机器能执行的可视化代码。**

但这条路并不简单。LLM 生成的代码可能有语法错误、配置项遗漏、甚至安全问题。本节课会带你从原理到实践，完整走通这条链路。

## 一、代码生成式可视化的原理

### 1.1 为什么是"生成代码"而不是"直接生成图表"？

这个问题值得先想清楚。图表本质上是视觉像素，理论上可以直接用图像生成模型产出。但实际工程中，**代码生成**是更优的路径，原因有三：

```
┌─────────────────────────────────────────────────────────┐
│                两种生成路径对比                            │
├─────────────────┬───────────────────┬───────────────────┤
│     维度         │  直接生成图像      │  生成图表代码      │
├─────────────────┼───────────────────┼───────────────────┤
│  可编辑性        │  ❌ 像素不可编辑   │  ✅ 代码可修改     │
│  数据精确性      │  ❌ 可能有幻觉     │  ✅ 绑定真实数据   │
│  交互能力        │  ❌ 静态图片       │  ✅ 支持缩放/提示  │
│  一致性          │  ❌ 每次生成不同   │  ✅ 相同配置相同图 │
│  渲染质量        │  ⚠️ 依赖模型能力  │  ✅ 依赖渲染引擎   │
└─────────────────┴───────────────────┴───────────────────┘
```

代码是图表的"源代码"，它携带了完整的语义信息——数据映射、视觉编码、交互逻辑。生成代码意味着我们生成的是**图表的规范描述**，而非最终像素。这就像写文章和画画的区别：文字可以被精确引用、修改、版本控制，而图片不行。

### 1.2 技术架构总览

```
用户输入: "展示各城市销售额的柱状图"
          │
          ▼
┌─────────────────────┐
│   Prompt 构造层      │  ← 注入系统指令 + 数据 Schema + 示例
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│   LLM 生成层        │  ← GPT-4 / Claude / 开源模型
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│   代码解析层         │  ← 提取 JSON / JS 代码块
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│   验证与修复层       │  ← Schema 校验 + 静态分析 + 自动修复
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│   沙箱执行层         │  ← 安全渲染，防止恶意代码
└──────────┬──────────┘
           ▼
       图表输出
```

这个架构中，**Prompt 构造层**和**验证与修复层**是两个最关键的环节。Prompt 决定了生成质量的上限，验证保证了输出的可靠性。

## 二、Prompt 设计：如何描述可视化需求

### 2.1 好 Prompt 的三个层次

很多人以为 Prompt 就是把用户的话丢给 LLM，但实际上，一个高质量的可视化代码生成 Prompt 需要三层信息：

**第一层：角色与约束**——告诉模型它是什么角色，输出什么格式

```
你是一个 ECharts 配置生成器。
用户会用自然语言描述图表需求，你需要输出合法的 ECharts option JSON。
规则：
1. 只输出 JSON，不要解释
2. 使用用户数据中的真实字段名
3. 颜色使用 ECharts 默认配色方案
```

**第二层：数据上下文**——告诉模型可用的数据结构

```
当前可用数据集：sales_data
字段说明：
- city: string, 城市名称（如"北京"、"上海"）
- amount: number, 销售金额（单位：万元）
- growth_rate: number, 同比增长率（0.15 代表 15%）
- category: string, 商品品类
数据示例：[{"city":"北京","amount":1200,"growth_rate":0.15,"category":"电子产品"}]
```

**第三层：输出示例**——给模型一个"照着写"的模板

```json
{
  "xAxis": { "type": "category", "data": ["北京", "上海", "广州"] },
  "yAxis": { "type": "value", "name": "销售额（万元）" },
  "series": [{ "type": "bar", "data": [1200, 980, 850] }]
}
```

这三层缺一不可。没有角色约束，模型可能输出一大段解释而非代码；没有数据上下文，模型会编造假字段名；没有输出示例，模型的输出格式可能不稳定。

### 2.2 复杂需求的 Prompt 拆解策略

当用户需求变复杂时——"展示各品类的月度销售趋势，按季度分组，还要能看出环比增长率"——不要试图用一个 Prompt 搞定。更好的做法是**分步生成**：

```
步骤 1: 意图解析 → 结构化需求描述
步骤 2: 数据映射 → 确定用哪些字段、做什么聚合
步骤 3: 图表配置 → 生成最终的 ECharts option
```

这种拆解的好处是：每一步都可以独立验证和调试。如果最终图表不对，我们可以定位是意图理解错了、数据映射错了、还是配置生成错了。

## 三、ECharts 配置生成 vs D3 代码生成

### 3.1 两种方案的本质差异

ECharts 和 D3 是前端可视化领域最主流的两个库，但它们的抽象层次完全不同，这直接影响了 LLM 生成代码的难度和策略。

```
抽象层次对比：

高 ┌───────────────────────────────┐
   │    ECharts: 声明式配置        │  ← "描述你想要什么"
   │    { type: 'bar', data: [...] }│
   ├───────────────────────────────┤
   │    D3: 命令式编程             │  ← "描述怎么做"
   │    svg.selectAll('rect')      │
   │      .data(data)              │
   │      .enter().append('rect')  │
   │      .attr('x', ...)         │
低 └───────────────────────────────┘
```

**ECharts 是声明式的**——你告诉它"我要柱状图，数据是这些"，它自己处理 DOM 操作、动画、响应式。这意味着 LLM 只需要生成一个 JSON 配置对象，难度较低，成功率较高。

**D3 是命令式的**——你需要一步步告诉它"选中所有 rect 元素、绑定数据、创建新元素、设置属性"。这意味着 LLM 需要生成完整的 JavaScript 代码，难度更高，但灵活性也更强。

### 3.2 ECharts 配置生成的最佳实践

ECharts 的配置生成相对简单，但有几个容易出错的地方：

**问题一：字段名映射错误。** 用户说"销售额"，数据里的字段叫 `amount`，模型可能写成 `sales` 或 `value`。

解决方案：在 Prompt 中明确给出字段映射表，并要求模型严格使用。

**问题二：图表类型选择不当。** 用户说"看趋势"，应该用折线图，但模型可能生成柱状图。

解决方案：在 Prompt 中加入图表类型选择指南。

**问题三：缺少必要的配置项。** 比如漏掉 `tooltip`、`legend`，导致图表缺少交互。

解决方案：提供一个"必选配置清单"，让模型逐项检查。

### 3.3 D3 代码生成的挑战与策略

D3 代码生成的难度主要来自两个方面：

第一，D3 的 API 是链式调用，语法灵活，同样的效果可以有多种写法。LLM 生成的代码风格可能不稳定。

第二，D3 需要处理 DOM 操作，涉及到 SVG/Canvas 的底层知识。模型可能生成语法正确但视觉效果错误的代码。

针对这些挑战，推荐的策略是：**用模板约束生成**。预先定义几种常见图表类型的 D3 代码骨架，让模型只填充数据绑定和样式部分，而不是从零生成。

## 四、代码验证与安全沙箱执行

### 4.1 为什么需要验证？

LLM 生成的代码不能直接执行，原因有三：

1. **语法错误**：JSON 缺少括号、引号不匹配
2. **语义错误**：引用了不存在的字段、数据类型不匹配
3. **安全风险**：可能包含 `eval()`、`Function()` 等危险调用

```
验证流程：

LLM 输出
    │
    ▼
┌──────────────┐    失败     ┌──────────────┐
│  JSON 解析    │ ─────────→ │  语法修复     │
└──────┬───────┘             └──────┬───────┘
       │ 成功                       │
       ▼                           ▼
┌──────────────┐    失败     ┌──────────────┐
│  Schema 校验  │ ─────────→ │  字段补全     │
└──────┬───────┘             └──────┬───────┘
       │ 成功                       │
       ▼                           ▼
┌──────────────┐    失败     ┌──────────────┐
│  安全扫描     │ ─────────→ │  拒绝执行     │
└──────┬───────┘             └──────────────┘
       │ 成功
       ▼
   沙箱渲染
```

### 4.2 安全沙箱的设计

沙箱的核心原则是：**让代码在隔离环境中运行，无法访问外部资源或执行危险操作。**

对于 ECharts 配置（纯 JSON），安全风险较低，主要防止注入。对于 D3 代码（JavaScript），需要更严格的隔离：

```javascript
// 沙箱执行环境的核心思路
// 1. 创建一个受限的全局对象
// 2. 只暴露 D3 和 SVG 相关的 API
// 3. 禁止访问 fetch、XMLHttpRequest、eval 等
```

在浏览器端，可以使用 `iframe` 的 `sandbox` 属性或 Web Workers。在 Node.js 端，可以使用 `vm2` 或 `isolated-vm` 等沙箱库。

## 五、迭代优化：基于反馈的代码改进

### 5.1 为什么需要迭代？

第一次生成的代码很少能完美满足需求。常见的情况是：

- 图表类型对了，但颜色不好看
- 数据映射对了，但坐标轴标签被截断
- 整体布局对了，但缺少图例说明

因此，我们需要一个**反馈→改进→验证**的循环。

### 5.2 反馈的来源

```
反馈来源层次：

┌─────────────────────────────────────┐
│  Level 1: 自动化检查                  │
│  - 配置 Schema 是否合法              │
│  - 数据字段是否存在                   │
│  - 图表类型与数据类型是否匹配          │
├─────────────────────────────────────┤
│  Level 2: 视觉规则检查               │
│  - 颜色对比度是否足够                 │
│  - 标签是否重叠                      │
│  - 数据是否被截断                     │
├─────────────────────────────────────┤
│  Level 3: 用户反馈                   │
│  - "颜色换成蓝色"                    │
│  - "加上数据标签"                    │
│  - "Y轴从0开始"                      │
└─────────────────────────────────────┘
```

Level 1 可以完全自动化，Level 2 可以部分自动化（通过规则引擎），Level 3 需要将用户的自然语言反馈转化为具体的修改指令。

### 5.3 迭代优化的实现

实现迭代优化的关键是**维护修改历史**。每一轮修改都应该记录：原始配置、用户反馈、修改后的配置。这样当用户说"回到刚才的样子"时，我们可以回退到上一个版本。

```typescript
interface DataSchema {
  tableName: string;
  fields: Array<{
    name: string;
    type: "string" | "number" | "date";
    description: string;
    sampleValues: unknown[];
  }>;
}

interface PromptConfig {
  systemRole: string;
  chartTypeHints: string;
  outputFormat: string;
  exampleConfig: Record<string, unknown>;
}

function buildVisualizationPrompt(
  userQuery: string,
  dataSchema: DataSchema,
  config: PromptConfig
): string {
  const fieldDescriptions = dataSchema.fields
    .map(
      (f) =>
        `- ${f.name} (${f.type}): ${f.description}，示例值: ${f.sampleValues.slice(0, 3).join(", ")}`
    )
    .join("\n");

  return `${config.systemRole}

## 数据描述
数据表: ${dataSchema.tableName}
可用字段:
${fieldDescriptions}

## 图表类型指南
${config.chartTypeHints}

## 输出格式要求
${config.outputFormat}

## 示例输出
\`\`\`json
${JSON.stringify(config.exampleConfig, null, 2)}
\`\`\`

## 用户需求
${userQuery}

请根据用户需求，生成合法的 ECharts option JSON。只输出 JSON，不要其他内容。`;
}
```

### 6.3 LLM 调用层

```typescript
// src/llm-generator.ts

import OpenAI from "openai";

interface GenerationResult {
  success: boolean;
  config: Record<string, unknown> | null;
  rawOutput: string;
  error: string | null;
  tokenUsage: { prompt: number; completion: number };
}

class EChartsGenerator {
  private client: OpenAI;
  private model: string;
  private maxRetries: number;

  constructor(apiKey: string, model = "gpt-4o", maxRetries = 3) {
    this.client = new OpenAI({ apiKey });
    this.model = model;
    this.maxRetries = maxRetries;
  }

  async generate(prompt: string): Promise<GenerationResult> {
    let lastError: string | null = null;

    for (let attempt = 0; attempt < this.maxRetries; attempt++) {
      try {
        const response = await this.client.chat.completions.create({
          model: this.model,
          messages: [{ role: "user", content: prompt }],
          temperature: 0.1, // 低温度保证输出稳定性
          max_tokens: 2000,
          response_format: { type: "json_object" },
        });

        const rawOutput = response.choices[0]?.message?.content ?? "";
        const tokenUsage = {
          prompt: response.usage?.prompt_tokens ?? 0,
          completion: response.usage?.completion_tokens ?? 0,
        };

        const parsed = this.extractJSON(rawOutput);
        if (parsed) {
          return {
            success: true,
            config: parsed,
            rawOutput,
            error: null,
            tokenUsage,
          };
        }

        lastError = "无法从输出中提取合法 JSON";
      } catch (apiError: unknown) {
        const message =
          apiError instanceof Error ? apiError.message : "未知 API 错误";
        lastError = `API 调用失败 (第 ${attempt + 1} 次): ${message}`;

        if (attempt < this.maxRetries - 1) {
          await this.sleep(1000 * (attempt + 1)); // 指数退避
        }
      }
    }

    return {
      success: false,
      config: null,
      rawOutput: "",
      error: lastError,
      tokenUsage: { prompt: 0, completion: 0 },
    };
  }

  private extractJSON(raw: string): Record<string, unknown> | null {
    // 尝试直接解析
    try {
      return JSON.parse(raw);
    } catch {
      // 尝试从 markdown 代码块中提取
      const codeBlockMatch = raw.match(/```(?:json)?\s*([\s\S]*?)```/);
      if (codeBlockMatch) {
        try {
          return JSON.parse(codeBlockMatch[1].trim());
        } catch {
          // 继续尝试其他方式
        }
      }

      // 尝试找到第一个 { 和最后一个 } 之间的内容
      const firstBrace = raw.indexOf("{");
      const lastBrace = raw.lastIndexOf("}");
      if (firstBrace !== -1 && lastBrace > firstBrace) {
        try {
          return JSON.parse(raw.slice(firstBrace, lastBrace + 1));
        } catch {
          return null;
        }
      }

      return null;
    }
  }

  private sleep(ms: number): Promise<void> {
    return new Promise((resolve) => setTimeout(resolve, ms));
  }
}

export { EChartsGenerator, GenerationResult };
```

### 6.4 配置验证器

```typescript
// src/config-validator.ts

interface ValidationResult {
  valid: boolean;
  errors: string[];
  warnings: string[];
  fixedConfig: Record<string, unknown> | null;
}

interface FieldInfo {
  name: string;
  type: "string" | "number" | "date";
}

class ConfigValidator {
  private availableFields: FieldInfo[];

  constructor(fields: FieldInfo[]) {
    this.availableFields = fields;
  }

  validate(config: Record<string, unknown>): ValidationResult {
    const errors: string[] = [];
    const warnings: string[] = [];
    let fixedConfig = JSON.parse(JSON.stringify(config));

    // 检查 1: 必须有 series
    if (!fixedConfig.series) {
      errors.push("缺少 series 字段");
    }

    // 检查 2: xAxis/yAxis 存在性（非饼图/雷达图时）
    const chartType = this.detectChartType(fixedConfig);
    if (chartType !== "pie" && chartType !== "radar" && chartType !== "map") {
      if (!fixedConfig.xAxis) {
        warnings.push("缺少 xAxis，已自动添加");
        fixedConfig.xAxis = { type: "category" };
      }
      if (!fixedConfig.yAxis) {
        warnings.push("缺少 yAxis，已自动添加");
        fixedConfig.yAxis = { type: "value" };
      }
    }

    // 检查 3: tooltip 存在性
    if (!fixedConfig.tooltip) {
      warnings.push("缺少 tooltip，已自动添加");
      fixedConfig.tooltip = { trigger: "axis" };
    }

    // 检查 4: 数据字段引用是否合法
    const fieldNames = this.availableFields.map((f) => f.name);
    const referencedFields = this.extractFieldReferences(fixedConfig);
    for (const field of referencedFields) {
      if (!fieldNames.includes(field)) {
        errors.push(`引用了不存在的字段: ${field}，可用字段: ${fieldNames.join(", ")}`);
      }
    }

    // 检查 5: series 中的 type 是否合法
    const validTypes = [
      "line", "bar", "pie", "scatter", "radar",
      "map", "funnel", "gauge", "treemap", "boxplot",
    ];
    if (Array.isArray(fixedConfig.series)) {
      for (const seriesItem of fixedConfig.series) {
        if (seriesItem.type && !validTypes.includes(seriesItem.type)) {
          errors.push(`不支持的图表类型: ${seriesItem.type}`);
        }
      }
    }

    return {
      valid: errors.length === 0,
      errors,
      warnings,
      fixedConfig: errors.length === 0 ? fixedConfig : null,
    };
  }

  private detectChartType(config: Record<string, unknown>): string {
    const series = config.series;
    if (Array.isArray(series) && series.length > 0) {
      return (series[0] as Record<string, unknown>).type as string ?? "bar";
    }
    return "bar";
  }

  private extractFieldReferences(obj: unknown, fields: string[] = []): string[] {
    if (typeof obj === "string") {
      // 简单启发式：如果字符串匹配某个字段名模式
      if (this.availableFields.some((f) => f.name === obj)) {
        fields.push(obj);
      }
    } else if (Array.isArray(obj)) {
      for (const item of obj) {
        this.extractFieldReferences(item, fields);
      }
    } else if (obj && typeof obj === "object") {
      for (const value of Object.values(obj)) {
        this.extractFieldReferences(value, fields);
      }
    }
    return [...new Set(fields)];
  }
}

export { ConfigValidator, ValidationResult, FieldInfo };
```

```typescript
// src/feedback-loop.ts

interface HistoryEntry {
  round: number;
  userQuery: string;
  generatedConfig: Record<string, unknown>;
  timestamp: Date;
}

interface ModificationRequest {
  type: "color" | "label" | "axis" | "type" | "general";
  description: string;
}

class FeedbackLoop {
  private history: HistoryEntry[] = [];
  private currentRound = 0;

  addEntry(userQuery: string, config: Record<string, unknown>): void {
    this.currentRound++;
    this.history.push({
      round: this.currentRound,
      userQuery,
      generatedConfig: config,
      timestamp: new Date(),
    });
  }

  parseFeedback(feedback: string): ModificationRequest {
    const lowerFeedback = feedback.toLowerCase();

    if (/颜色|配色|color/i.test(lowerFeedback)) {
      return { type: "color", description: feedback };
    }
    if (/标签|label|文字|标题/i.test(lowerFeedback)) {
      return { type: "label", description: feedback };
    }
    if (/坐标|轴|axis|刻度/i.test(lowerFeedback)) {
      return { type: "axis", description: feedback };
    }
    if (/换成|改为|类型|折线|柱状|饼图|line|bar|pie/i.test(lowerFeedback)) {
      return { type: "type", description: feedback };
    }

    return { type: "general", description: feedback };
  }

  buildModificationPrompt(feedback: string): string {
    const lastEntry = this.history[this.history.length - 1];
    if (!lastEntry) {
      return "没有找到上一轮的配置记录。";
    }

    const modification = this.parseFeedback(feedback);

    return `你是一个 ECharts 配置修改器。

## 当前配置
\`\`\`json
${JSON.stringify(lastEntry.generatedConfig, null, 2)}
\`\`\`

## 用户修改要求
${modification.description}

## 修改类型
${modification.type}

## 规则
1. 在当前配置基础上进行修改，不要重写整个配置
2. 只修改与用户要求相关的部分
3. 保持其他配置不变
4. 输出修改后的完整 JSON

请输出修改后的完整 ECharts option JSON。`;
  }

  getHistory(): HistoryEntry[] {
    return [...this.history];
  }

  rollback(round: number): Record<string, unknown> | null {
    const entry = this.history.find((h) => h.round === round);
    return entry ? entry.generatedConfig : null;
  }
}
```

## 常见误区

### 误区一：Prompt 越长越好

很多人认为 Prompt 写得越详细，生成效果越好。但实际上，过长的 Prompt 会导致模型"注意力分散"，反而降低关键信息的权重。正确的做法是**精简而有层次**：角色约束要简短明确，数据描述要结构化，示例要典型而非冗余。

### 误区二：忽略输出格式约束

不指定输出格式时，LLM 可能输出一大段解释文字加上代码片段。这会导致后续解析困难。一定要在 Prompt 中明确"只输出 JSON"或使用 `response_format: { type: "json_object" }` 参数。

### 误区三：信任 LLM 的字段名

LLM 会"合理猜测"字段名。用户说"销售额"，它可能生成 `sales`、`revenue`、`income` 等。但你的数据里可能叫 `amount`。**永远在 Prompt 中提供真实的字段 Schema**，并要求模型严格使用。

### 误区四：不做安全检查就执行

即使是 ECharts 的 JSON 配置，如果数据来自用户输入，也可能被注入恶意内容（比如在 tooltip 的 formatter 中注入脚本）。执行前的安全扫描是必须的。

### 误区五：一次生成就交付

代码生成式可视化的体验核心在于**迭代**。第一次生成的结果通常只有 70-80 分，通过 1-2 轮反馈修改才能达到 95 分以上。不要跳过反馈循环。

### 练习二

**思路**：在现有 `validate` 方法中增加三个新的检查步骤，分别针对饼图数据总和、折线图排序、颜色对比度。

**答案**：

```typescript
// 在 ConfigValidator 类中增加以下方法

validate(config: Record<string, unknown>): ValidationResult {
  // ... 原有检查逻辑 ...

  // 新增检查 6: 饼图数据总和
  if (chartType === "pie") {
    const pieCheck = this.validatePieDataTotal(fixedConfig);
    if (!pieCheck.valid) {

    }
  }

  if (chartType === "line") {
    const sortCheck = this.validateLineSortOrder(fixedConfig);
    if (!sortCheck.valid) {

    }
  }

  // 新增检查 8: 颜色对比度
  const contrastCheck = this.validateColorContrast(fixedConfig);
  if (!contrastCheck.valid) {
    warnings.push(contrastCheck.message);
  }

  // ... 返回结果 ...
}

private validatePieDataTotal(config: Record<string, unknown>): { valid: boolean; message: string } {
  const series = config.series as Array<Record<string, unknown>>;
  if (!series?.[0]?.data) return { valid: true, message: "" };

  const pieData = series[0].data as Array<{ value: number }>;
  const total = pieData.reduce((sum, item) => sum + item.value, 0);

  if (total > 90 && total < 110) {
    return { valid: true, message: "" };
  }
  return {
    valid: false,
    message: `饼图数据总和为 ${total}，不接近 100%。如果数据不是百分比，请忽略此警告。`,
  };
}

private validateLineSortOrder(config: Record<string, unknown>): { valid: boolean; message: string } {
  const xAxis = config.xAxis as Record<string, unknown>;
  if (!xAxis?.data || !Array.isArray(xAxis.data)) {
    return { valid: true, message: "" };
  }

  const data = xAxis.data as string[];
  for (let i = 1; i < data.length; i++) {
    if (data[i] < data[i - 1]) {
      return {
        valid: false,
        message: `xAxis 数据未按升序排列: "${data[i - 1]}" 后出现了 "${data[i]}"`,
      };
    }
  }
  return { valid: true, message: "" };
}

private validateColorContrast(config: Record<string, unknown>): { valid: boolean; message: string } {
  const color = (config.color ?? []) as string[];
  if (!color.length) return { valid: true, message: "" };

  const bgColor = "#ffffff"; // 假设白色背景
  for (const fgColor of color) {
    const ratio = this.calculateContrastRatio(fgColor, bgColor);
    if (ratio < 3) {
      return {
        valid: false,
        message: `颜色 ${fgColor} 与背景对比度不足 (${ratio.toFixed(1)}:1)，建议使用更深的颜色`,
      };
    }
  }
  return { valid: true, message: "" };
}

private calculateContrastRatio(fg: string, bg: string): number {
  const fgLuminance = this.getRelativeLuminance(fg);
  const bgLuminance = this.getRelativeLuminance(bg);
  const lighter = Math.max(fgLuminance, bgLuminance);
  const darker = Math.min(fgLuminance, bgLuminance);
  return (lighter + 0.05) / (darker + 0.05);
}

private getRelativeLuminance(hex: string): number {
  const r = parseInt(hex.slice(1, 3), 16) / 255;
  const g = parseInt(hex.slice(3, 5), 16) / 255;
  const b = parseInt(hex.slice(5, 7), 16) / 255;

  const toLinear = (c: number) => (c <= 0.03928 ? c / 12.92 : Math.pow((c + 0.055) / 1.055, 2.4));

  return 0.2126 * toLinear(r) + 0.7152 * toLinear(g) + 0.0722 * toLinear(b);
}
```

**要点**：
- 饼图总和检查允许一定误差（90-110），因为有些场景数据确实不是百分比
- 折线图排序检查只针对字符串比较，日期格式需要额外处理
- 颜色对比度使用 WCAG 2.1 标准的相对亮度算法

### 练习三

**思路**：这是实践题，关键在于观察每轮迭代的 Prompt 结构变化。下面是预期的三轮交互分析。

**答案**：

**第一轮**：生成初始折线图
- Prompt 结构：系统角色 + 数据 Schema + 用户需求
- 生成的配置核心：`series: [{ type: 'line', data: [...] }]`
- xAxis 类型为 category，数据为月份

**第二轮**：改为带面积填充的折线图
- Prompt 结构：当前配置 + 用户反馈 + 修改指令
- 核心变更：series 中增加 `areaStyle: {}` 配置
- 分析：模型识别出"面积填充"对应 ECharts 的 `areaStyle` 属性，在原有配置基础上增量修改

**第三轮**：添加同比虚线对比
- Prompt 结构：当前配置 + 用户反馈 + 修改指令
- 核心变更：series 数组增加一个新元素，设置 `lineStyle: { type: 'dashed' }`
- 分析：模型需要理解"同比"是一个新的数据系列，"虚线"对应 `lineStyle.type = 'dashed'`

**观察要点**：
1. 迭代的 Prompt 比一次性生成的 Prompt 更复杂，因为它需要携带当前配置的完整上下文
2. 每轮修改都是增量的，不会破坏前几轮已经确认的配置
3. 修改类型的识别（颜色/标签/类型等）帮助模型聚焦到正确的配置区域
