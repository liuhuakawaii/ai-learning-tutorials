# 第17课：实时语音交互——ASR + LLM + TTS 的实时 Pipeline

## 场景引入

你正在开发一个智能语音助手的 3D 数字人版本。用户对着麦克风说："帮我查一下明天北京的天气"，数字人需要在 1-2 秒内用自然的语音和面部表情回答："明天北京晴转多云，最高温度 28 度，建议穿轻薄外套。"这个看似简单的交互，背后涉及三个核心 AI 模型的协同工作：语音识别（ASR）将用户的语音转为文字，大语言模型（LLM）理解语义并生成回答，语音合成（TTS）将回答文字转为语音。更关键的是，这三个模型必须以流式方式工作——用户说到一半时 ASR 就应该开始输出中间结果，LLM 应该在收到第一个词后就开始生成回答，TTS 应该在收到第一个句子时就开始合成语音。任何一个环节"等一等"，用户就会感觉到明显的延迟。

2025 年的技术栈已经让这个 Pipeline 的搭建变得可行：Whisper 和 SenseVoice 提供了高质量的流式 ASR，vLLM 和 TensorRT-LLM 支持高吞吐的流式 LLM 推理，CosyVoice 和 ChatTTS 实现了流式 TTS 合成。但将这三个环节串联成一个低延迟、高鲁棒、支持打断的实时 Pipeline，仍然需要精心的架构设计和工程优化。

本节课将深入讲解实时语音交互 Pipeline 的架构设计，覆盖流式 ASR、流式 LLM、流式 TTS 的实现细节，以及打断机制和端到端延迟优化策略。

## 学习目标

完成本课学习后，你将能够：

- 设计一个完整的流式语音交互 Pipeline，理解 VAD → ASR → LLM → TTS 各环节的数据流
- 实现流式 ASR，掌握 Whisper 和 SenseVoice 的 chunk-based 识别方法
- 优化 LLM 的流式推理性能，理解 vLLM 的 PagedAttention 和投机解码原理
- 实现流式 TTS 合成，掌握 CosyVoice 的 chunk-based 语音生成
- 设计打断（Barge-in）和话轮管理机制，实现自然的多轮对话
- 通过 Pipeline 并行化和投机技术优化端到端延迟

## 核心概念

### 一、实时语音交互 Pipeline 架构

一个实时语音交互系统的核心架构由四个模块串联而成：语音活动检测（VAD）→ 语音识别（ASR）→ 大语言模型（LLM）→ 语音合成（TTS）。每个模块都是流式的——输入数据边到达边处理，输出结果边生成边传递给下游。

```
┌────────────────────────────────────────────────────────────────────┐
│                实时语音交互 Pipeline 架构                            │
│                                                                    │
│  用户语音                                                           │
│    │                                                               │
│    ▼                                                               │
│  ┌─────┐    ┌─────┐    ┌─────┐    ┌─────┐    ┌──────────┐        │
│  │ VAD │───→│ ASR │───→│ LLM │───→│ TTS │───→│ 3D渲染   │        │
│  └─────┘    └─────┘    └─────┘    └─────┘    └──────────┘        │
│    │          │           │          │           │                 │
│  语音段     文字流       回答流     音频流      Blendshape          │
│  检测       实时输出     token输出  chunk输出   + 口型同步           │
│                                                                    │
│  数据格式:                                                          │
│  VAD → ASR: PCM 音频 chunk (40-100ms)                              │
│  ASR → LLM: 文字中间结果 + 最终结果                                 │
│  LLM → TTS: 文字 token 流 (按句/短语分段)                           │
│  TTS → 渲染: PCM/Opus 音频 chunk + Blendshape 权重                  │
│                                                                    │
│  关键约束:                                                          │
│  - VAD → ASR 延迟 < 300ms (说话人停顿即可开始识别)                   │
│  - ASR 首字延迟 < 500ms                                             │
│  - LLM 首 token 延迟 < 300ms                                        │
│  - TTS 首 chunk 延迟 < 200ms                                        │
│  - 端到端首字延迟 < 1.5s                                             │
└────────────────────────────────────────────────────────────────────┘
```

这个 Pipeline 的核心设计原则是**流水线并行**。理想情况下，当用户还在说话时，ASR 已经在实时输出中间识别结果；当 LLM 正在生成回答的第 5 个 token 时，TTS 已经在合成前 4 个 token 对应的语音。这种并行化让各环节的处理时间重叠而非累加，是实现低延迟的关键。

Pipeline 的另一个重要设计考量是**背压（Backpressure）管理**。当下游处理速度跟不上上游产生速度时，需要有缓冲和丢弃策略。例如，如果 LLM 的推理速度是每秒 50 个 token，而 TTS 的合成速度是每秒 30 个 token，那么 TTS 端的输入队列会不断增长。此时需要决定：是丢弃旧的 token（可能导致回答不完整），还是等待 TTS 处理完（会增加延迟）。

### 二、流式 ASR 实现

流式 ASR 的核心挑战是：在用户还在说话的过程中，实时输出识别结果。这与传统的"等用户说完再识别"模式有本质区别。

Whisper 是 OpenAI 开源的语音识别模型，其原始设计是"离线"模式——输入一段完整音频，输出完整转录。要将 Whisper 用于流式场景，需要做特殊处理。2025 年的主流方案有两种：

**Chunk-based Whisper**：将音频切分为 30 秒以内的 chunk（Whisper 的最大输入长度），每个 chunk 独立识别。相邻 chunk 之间保留一定的重叠区域（通常 5-10 秒），用于处理跨 chunk 边界的词语。这种方法实现简单，但存在两个问题：chunk 边界处可能丢失词语，以及每个 chunk 的处理延迟等于 chunk 长度。

**Streaming Whisper（如 faster-whisper streaming）**：使用滑动窗口和注意力缓存机制，让 Whisper 模型能够持续处理到达的音频数据。核心思想是维护一个"已处理"区域和一个"待确认"区域，新音频到达时只处理增量部分，并使用特殊的 prompt token 提示模型当前的上下文。

SenseVoice 是 FunASR 团队在 2024 年开源的语音理解模型，其架构天然支持流式推理。相比 Whisper，SenseVoice 在中文场景下的识别准确率更高，且支持情感识别和音频事件检测。SenseVoice 的流式模式通过 CTC（Connectionist Temporal Classification）解码器实现，每收到一帧音频（通常 10ms）就可以输出一个中间识别结果。

```
┌─────────────────────────────────────────────────────────────┐
│                流式 ASR 工作原理                              │
│                                                             │
│  音频时间轴:                                                 │
│  ─────────────────────────────────────────→                 │
│  │ chunk1(3s) │ chunk2(3s) │ chunk3(3s) │                  │
│  │            │←重叠1s→│   │            │                  │
│                                                             │
│  处理流程:                                                   │
│  t=0s: 收到 chunk1 → 开始识别                                │
│  t=3s: chunk1 识别完成, 输出 "你好"                           │
│        同时收到 chunk2 → 开始识别                             │
│  t=3.5s: chunk2 中间结果 "你好今天"                           │
│  t=6s: chunk2 识别完成, 输出 "你好今天天气"                    │
│        同时收到 chunk3 → 开始识别                             │
│                                                             │
│  用户感知:                                                   │
│  说话过程中就开始看到识别结果, 体验接近"实时字幕"              │
└─────────────────────────────────────────────────────────────┘
```

### 三、流式 LLM 推理

LLM 的流式推理相对直观：模型生成一个 token，就立即输出一个 token，不需要等整个回答生成完毕。但要在生产环境中实现高吞吐、低延迟的流式推理，需要解决几个工程挑战。

**vLLM 的 PagedAttention**：传统的 LLM 推理框架在处理 KV Cache 时，为每个请求预分配一块连续的 GPU 内存。由于不同请求的序列长度不同，预分配的内存往往有大量浪费（内部碎片和外部碎片）。vLLM 引入了 PagedAttention 机制，将 KV Cache 分割为固定大小的"页"，按需动态分配，类似操作系统的虚拟内存管理。这使得 GPU 内存利用率从传统的 50-60% 提升到 90% 以上，同样的 GPU 可以同时服务更多的并发请求。

**投机解码（Speculative Decoding）**：这是一个巧妙的加速技术。核心思想是用一个小型"草稿模型"（Draft Model，如 1B 参数）快速生成 5-10 个候选 token，然后用目标大模型（如 7B 参数）一次性验证这些 token。如果前 5 个 token 都被接受，就一次获得 5 个有效 token，而大模型只做了一次前向传播。在实际应用中，投机解码可以将生成速度提升 1.5-2.5 倍。

**Token Streaming 的工程实现**：通过 HTTP Server-Sent Events (SSE) 或 WebSocket 实现 token 级别的流式输出。每个 token 生成后，立即通过 SSE 发送给客户端，客户端收到 token 后立即传给 TTS 模块。关键的工程细节是控制 flush 频率——如果每个 token 都单独发送，会产生大量的小数据包，增加网络开销。通常的做法是将 token 缓冲 10-20ms，然后批量发送。

```
┌─────────────────────────────────────────────────────────────┐
│              流式 LLM 推理优化策略                            │
│                                                             │
│  传统方式:                                                   │
│  [输入] → 模型计算 → [完整输出]   延迟 = 全部生成时间         │
│                                                             │
│  Token Streaming:                                            │
│  [输入] → t1 → t2 → t3 → ... → tN                           │
│           │    │    │              │                         │
│          立即  立即  立即           立即                       │
│          输出  输出  输出           输出                       │
│                                                             │
│  投机解码:                                                   │
│  草稿模型(快): t1 t2 t3 t4 t5 (5个候选)                      │
│  目标模型(准): [验证] → 接受 t1-t3, 拒绝 t4                  │
│  结果: 一次前向传播获得 3 个有效 token                        │
│                                                             │
│  PagedAttention:                                             │
│  传统: [请求1: 60%][空闲: 40%]  内存浪费                     │
│  vLLM: [请求1页1][请求2页1][请求1页2][请求3页1]  按需分配     │
└─────────────────────────────────────────────────────────────┘
```

### 四、流式 TTS 合成

流式 TTS 的目标是在收到文本的同时，逐步生成语音音频 chunk。这与传统的"先合成完整音频再播放"模式不同，流式 TTS 可以在收到第一个句子片段时就开始输出音频，大幅缩短首包延迟。

CosyVoice 是阿里通义实验室在 2024 年开源的语音合成模型，支持流式合成模式。其流式工作原理是：将输入文本按句子或短语分段，每收到一段文本就启动一次合成，生成一个音频 chunk（通常 200-500ms 长度）。相邻 chunk 之间通过 crossfade 技术平滑拼接，避免拼接处的爆音或断裂感。

ChatTTS 是另一个支持流式的开源 TTS 模型，它的特点是支持更细粒度的控制——可以通过特殊标记控制语气、停顿、笑声等副语言特征。在数字人场景中，这些副语言特征对提升真实感非常重要。

流式 TTS 的一个关键工程挑战是**文本分段策略**。分段太短（如逐字合成），合成质量会下降，因为模型缺少足够的上下文来确定语调和韵律；分段太长（如逐段合成），首包延迟会增加。最佳实践是按**语义单元**分段：遇到句号、逗号、问号等标点时分段，同时设置分段的最小长度（5 个字符）和最大长度（50 个字符）。

```
┌─────────────────────────────────────────────────────────────┐
│                流式 TTS 合成流程                              │
│                                                             │
│  LLM token 流: "明天" "北京" "晴转" "多云" "," "最高" ...     │
│                                                             │
│  文本分段器:                                                  │
│  [收到"明天北京晴转多云,"] → 达到逗号分段点                    │
│  [继续收集"最高温度28度"] → 达到句号分段点                    │
│                                                             │
│  合成流程:                                                   │
│  段1: "明天北京晴转多云," → CosyVoice → [音频chunk1: 1.2s]   │
│  段2: "最高温度28度。" → CosyVoice → [音频chunk2: 0.8s]      │
│                                                             │
│  播放流程:                                                   │
│  收到 chunk1 → 立即开始播放                                  │
│  chunk1 播放到 80% 时 → 收到 chunk2 → crossfade 拼接          │
│  chunk2 播放到 80% 时 → 收到 chunk3 → crossfade 拼接          │
│  ...                                                        │
│                                                             │
│  首包延迟: LLM 首句完成时间 + TTS 首段合成时间 ≈ 800ms        │
└─────────────────────────────────────────────────────────────┘
```

### 五、打断与回话管理

在自然对话中，打断（Barge-in）是常见的行为。用户可能在数字人说话到一半时，突然说"等一下"或"不对"来打断。一个不支持打断的数字人会显得非常不自然——用户已经表达了不同意见，数字人还在继续说完之前的回答。

打断的技术实现依赖 VAD 的持续监测。在数字人说话的同时，系统需要持续监听用户的麦克风输入。当 VAD 检测到用户开始说话（语音活动开始），系统需要立即停止 TTS 的音频播放和 LLM 的 token 生成，然后将用户的语音输入转入新的 ASR → LLM 流程。

但打断的处理远比"检测到人声就停止"复杂。需要区分以下几种情况：

**有效打断**：用户确实在说有意义的话（如"不对，我要查的是上海的天气"），需要停止当前回答并处理新的请求。
**反馈性发声**：用户发出"嗯"、"哦"、"好的"等反馈性语音，不应该打断数字人，而是作为 backchannel（反馈信号）处理。
**环境噪声**：背景中有人说话或有噪音，不应该触发打断。

区分这三种情况的方法是：结合 VAD 的能量阈值、ASR 的中间识别结果、以及一个轻量级的意图分类器。当 VAD 检测到语音活动时，先用能量阈值过滤明显的噪声，然后启动 ASR 识别，如果识别出有意义的词语（非语气词），才触发打断。

```
┌─────────────────────────────────────────────────────────────┐
│                   打断处理状态机                              │
```

话轮管理（Turn-Taking）是另一个关键问题。在人类对话中，话轮的切换有明确的信号：语调下降、停顿、目光接触等。在语音数字人场景中，系统需要判断"用户是否说完了"。常用的方法是设置一个**静默超时**：当 VAD 检测到连续 600-1000ms 的静默时，认为用户说完了，开始处理。但这个超时值需要权衡——太短会误判（用户只是在思考），太长会增加等待感。

### 六、端到端延迟优化

端到端延迟是衡量实时语音交互系统质量的核心指标。用户从说完话到听到数字人回答的第一个字，中间的等待时间就是端到端首字延迟（Time to First Audio, TTFA）。研究表明，TTFA 超过 1.5 秒时，用户会明显感觉到"卡顿"，超过 3 秒时用户倾向于放弃交互。

优化端到端延迟的核心策略是**最大化流水线并行度**。在串行模式下，总延迟 = ASR 时间 + LLM 时间 + TTS 时间。在完全并行模式下，总延迟 ≈ max(ASR 首包, LLM 首 token, TTS 首 chunk) + 网络传输延迟。

**Pipeline 并行**的具体实现：ASR 不等用户说完就开始输出中间结果，LLM 不等 ASR 最终结果就开始基于中间结果生成回答，TTS 不等 LLM 生成完整句子就开始合成已有的 token。这要求每个模块都支持"不完整输入"的处理。

**投机 TTS（Speculative TTS）** 是一种更激进的优化策略。当 LLM 正在生成回答时，TTS 可以基于 LLM 已经生成的 token 进行"投机性"合成。如果 LLM 后续生成的内容与预期一致，投机合成的音频可以直接使用；如果不一致（如用户打断导致 LLM 改变回答方向），则丢弃已合成的音频并重新合成。在实际应用中，投机 TTS 的命中率通常在 70-85%，可以将 TTFA 降低 200-400ms。

```
┌──────────────────────────────────────────────────────────────┐
│            端到端延迟优化: 串行 vs 流式并行                     │
│                                                              │
│  串行模式 (总延迟 ≈ 2.5s):                                    │
│  │←── ASR 800ms ──→│←── LLM 1000ms ──→│←── TTS 700ms ──→│  │
│                                                              │
│  流式并行模式 (TTFA ≈ 1.0s):                                  │
│  │←─ ASR首包 300ms ─→│                                       │

│                    │←─ TTS首chunk 200ms ─→│                   │
│                    │←────── 总TTFA ≈ 800ms ──────→│           │
│                                                              │

│  │←─ ASR首包 300ms ─→│                                       │

│  3. TTS chunk-based (省 400ms)                               │
│  4. 投机 TTS (省 200-400ms)                                   │
│  5. 边缘部署 (省 50-100ms 网络延迟)                            │
```


## 常见误区

### 误区一：ASR 一定要等用户说完再传给 LLM

很多开发者习惯于"用户说完 → ASR 输出最终结果 → 传给 LLM"的串行流程。这种方式的延迟是 ASR 全量时间 + LLM 首 token 时间，通常超过 1.5 秒。更好的做法是利用 ASR 的中间结果：当 ASR 以 80% 以上的置信度识别出前几个词时，就可以将这些词作为 LLM 的输入前缀开始推理。LLM 可以基于不完整的输入开始"预热"（prefill），当 ASR 的最终结果到达时，只需要补全剩余的输入即可。这种方式可以将端到端延迟降低 300-500ms。

### 误区二：流式 TTS 一定要按完整句子分段

按完整句子分段是最简单的实现方式，但会导致较长的首包延迟——LLM 需要生成完整的一句话（通常 10-20 个 token，耗时 300-600ms），TTS 才能开始合成。更好的策略是按语义边界分段：逗号、分号、连词等都可以作为分段点。例如"明天北京晴转多云，最高温度28度"可以在逗号处分为两段，第一段"明天北京晴转多云"在 LLM 生成到逗号时就可以立即开始合成。这种方式将 TTS 首包延迟从"等一句完整话"降低到"等一个短语"。

### 误区三：打断检测只靠 VAD 能量阈值

仅靠 VAD 能量阈值做打断检测会产生大量误触发。环境噪声、用户清嗓子、旁边的对话都可能超过能量阈值，导致数字人突然停止说话。正确的做法是多级过滤：第一级用能量阈值粗筛，第二级用 ASR 识别结果判断是否有意义的词语，第三级用意图分类器判断用户是否真的要打断。只有通过三级过滤的语音才触发打断。这个过程虽然增加了 200-300ms 的判断时间，但大幅降低了误触发率。

### 误区四：Pipeline 延迟优化只需要关注 AI 模型推理

AI 模型推理确实是延迟的主要来源，但工程层面的开销同样不可忽视。WebSocket 的帧编码/解码、音频格式转换（如 WebM 转 PCM）、JSON 序列化/反序列化、队列的入队/出队——这些"微小"的操作累积起来可能有 50-100ms 的开销。优化方法包括：使用二进制协议代替 JSON 传输音频数据、在浏览器端直接输出 PCM 格式避免格式转换、使用共享内存代替队列传递大型数据块。这些工程优化看似琐碎，但在追求 1 秒以内 TTFA 的场景中，每一毫秒都很重要。

### 练习一：Pipeline 延迟计算

**思路**：分别计算串行模式和流式并行模式下的端到端延迟，量化优化效果。

**答案**：

给定各环节延迟：ASR 全量 800ms（首包 200ms）、LLM 全量 1000ms（首 token 150ms、每个 token 30ms）、TTS 全量 700ms（首 chunk 100ms、每 chunk 合成 50ms）、网络延迟 50ms。

**串行模式延迟**：
ASR(800ms) + LLM(1000ms) + TTS(700ms) + 网络(50ms×3) = 2650ms

**流式并行模式 TTFA**：
ASR 首包(200ms) + 网络(50ms) + LLM 首 token(150ms) + 网络(50ms) + TTS 首 chunk(100ms) + 网络(50ms) = 600ms

**加入投机 TTS 后**：
当 LLM 生成第一个 token "明" 时，TTS 就开始投机合成。但单个 token 信息不足，TTS 需要等待至少一个短语（约 5 个 token，耗时 150ms）。投机 TTS 将 TTS 首 chunk 延迟从 100ms 降低到约 50ms（因为已经开始预合成）。
投机 TTFA ≈ 200 + 50 + 150 + 50 + 50 + 50 = 550ms

**延迟降低比例**：(2650 - 550) / 2650 ≈ 79%

**要点**：
- 流式并行是降低端到端延迟最有效的策略
- 网络延迟在每个环节都会产生，边缘部署可以统一降低
- 投机 TTS 的收益取决于 LLM 生成速度和 TTS 最小合成单元

### 练习二：打断机制实现

**思路**：设计一个支持多级过滤的打断检测系统，平衡响应速度和误触发率。

**答案**：

```python
import time
import numpy as np

class BargeinDetector:
    def __init__(self, energy_threshold=0.03, confirm_window_ms=500):
        self.energy_threshold = energy_threshold
        self.confirm_window = confirm_window_ms / 1000
        self.candidate_start = None
        self.state = "idle"

    def process_audio(self, audio_chunk: np.ndarray) -> str:
        energy = np.sqrt(np.mean(audio_chunk.astype(np.float32) ** 2 / 32768 ** 2))

        if self.state == "idle":
            if energy > self.energy_threshold:
                self.state = "candidate"
                self.candidate_start = time.time()
                return "candidate_detected"
            return "no_action"

        elif self.state == "candidate":
            elapsed = time.time() - self.candidate_start
            if energy < self.energy_threshold * 0.5:
                self.state = "idle"
                self.candidate_start = None
                return "false_alarm"
            if elapsed >= self.confirm_window:
                self.state = "confirmed"
                return "bargein_confirmed"
            return "waiting_confirmation"

        elif self.state == "confirmed":
            return "processing_interrupt"

        return "no_action"

    def reset(self):
        self.state = "idle"
        self.candidate_start = None

```

**要点**：
- 多级过滤（能量 → 持续时间 → ASR 语义）是平衡误触发率和响应速度的关键
- `confirm_window` 参数需要根据场景调整：对话场景 300-500ms，演讲场景 800-1000ms
- 确认打断后需要立即停止 TTS 播放，否则用户会感觉到"数字人还在说话"

### 练习三：流式 TTS 分段策略

**思路**：实现一个按语义边界分段的文本分段器，优化 TTS 首包延迟。

**答案**：

```python
class TextSegmenter:
    STRONG_BREAKS = set("。！？!?;")
    WEAK_BREAKS = set("，,、：:")
    MIN_SEGMENT_LEN = 4
    MAX_SEGMENT_LEN = 50

    def __init__(self):
        self.buffer = ""
        self.segments = []

    def feed(self, text: str) -> list:
        new_segments = []
        for char in text:
            self.buffer += char
            if char in self.STRONG_BREAKS and len(self.buffer) >= self.MIN_SEGMENT_LEN:
                new_segments.append(self.buffer.strip())
                self.buffer = ""
            elif char in self.WEAK_BREAKS and len(self.buffer) >= self.MIN_SEGMENT_LEN * 2:
                new_segments.append(self.buffer.strip())
                self.buffer = ""
            elif len(self.buffer) >= self.MAX_SEGMENT_LEN:
                new_segments.append(self.buffer.strip())
                self.buffer = ""
        return new_segments

    def flush(self) -> str:
        remaining = self.buffer.strip()
        self.buffer = ""
        return remaining

seg = TextSegmenter()
test = "明天北京晴转多云，最高温度28度，最低温度18度。建议穿轻薄外套，出门记得带伞。"
for char in test:
    result = seg.feed(char)
    for r in result:
        print(f"  分段: '{r}'")
```

**要点**：
- 强分段符（句号、问号）优先级高于弱分段符（逗号）
- 最小分段长度防止过短片段导致 TTS 合成质量下降
- `flush()` 在 LLM 输出结束时调用，确保剩余文本不丢失
