# 第19课：数字人对话系统——记忆、情感、个性化

## 场景引入

你已经和"小雅"聊了三个月了。她是你手机里的 AI 健康顾问。第一次对话时，你告诉她你有轻度乳糖不耐受，她记住了；上周你说最近加班很多睡眠不好，她记住了；今天你打开对话，她微笑着说："最近加班好些了吗？上次你说的褪黑素有用的话，我帮你查了几个更温和的替代方案。"

这一刻你感受到的不是"一个程序在检索数据库"，而是"一个人在关心我"。这种感受的来源有三个层次：第一，她**记得**你之前说过的话（记忆）；第二，她用关心的语气而不是冰冷的报告语气来说（情感）；第三，她始终保持着那种温柔但专业的个性，不会突然变成一个搞笑的人（个性化）。

这一课我们要构建的，就是这样一个有记忆、有情感、有个性的数字人对话系统。它不是简单地把用户的话丢给大模型再把回复念出来——那只是语音转文字再转语音的管道。我们要做的是让数字人成为一个有连续性的"社交存在"。

## 学习目标

完成本课学习后，你将能够：

- 设计数字人对话系统的端到端架构，理解 ASR、NLU、对话管理、NLG、TTS 各模块的职责
- 实现三层记忆系统（工作记忆、情景记忆、语义记忆），支持高效检索和遗忘机制
- 构建情感对话引擎，跟踪用户和数字人双方的情感状态
- 设计个性化人设系统，确保数字人在长对话中保持角色一致性
- 利用 RAG 技术增强数字人的领域知识能力
- 建立对话质量评估体系，包括一致性、连贯性和 LLM-as-Judge 评估

## 核心概念

### 一、数字人对话系统架构

一个完整的数字人对话系统不是一条直线型的管道，而是一个多层循环的架构。用户说的话经过 ASR（自动语音识别）转成文本，NLU（自然语言理解）提取意图和情感，对话管理器决定如何回应，NLG（自然语言生成）生成回复文本，TTS（文本转语音）合成语音输出。但在这个主循环之外，还有记忆系统、情感引擎和人设系统在持续运行。

```
数字人对话系统全景架构

用户语音 ──▶ ┌─────────┐ ──▶ ┌─────────┐ ──▶ ┌──────────────┐
              │  ASR    │     │  NLU    │     │  对话管理器    │
              │语音→文本 │     │意图+情感 │     │ (Dialogue Mgr)│
              └─────────┘     └────┬────┘     └───────┬──────┘
                                   │                  │
                          ┌────────▼────────┐        │
                          │   情感引擎       │        │
                          │ Emotion Engine   │        │
                          │ ·用户情感追踪    │        │
                          │ ·数字人情感状态  │        │
                          └────────┬────────┘        │
                                   │                  │
                          ┌────────▼────────┐  ┌─────▼──────┐
                          │   记忆系统       │  │  人设系统    │
                          │ Memory System    │  │ Persona     │
                          │ ·工作记忆        │  │ ·角色定义    │
                          │ ·情景记忆        │  │ ·动态特质    │
                          │ ·语义记忆        │  │ ·风格控制    │
                          └────────┬────────┘  └─────┬──────┘
                                   │                  │
                                   └────────┬─────────┘
                                            │
              ┌─────────┐     ┌─────────────▼────────────┐
              │  TTS    │ ◀── │     NLG（语言生成）        │
              │文本→语音 │     │  ·RAG 知识增强            │
              └────▲────┘     │  ·情感化表达              │
                   │          │  ·个性化风格              │
              数字人语音       └──────────────────────────┘
```

各模块之间的通信不是简单的串行调用。对话管理器需要同时获取 NLU 的解析结果、记忆系统的相关上下文、情感引擎的当前状态、人设系统的风格约束，然后综合这些信息做出决策。这种"多源融合"的架构设计是数字人对话系统区别于普通聊天机器人的关键差异。

### 二、记忆系统设计

人类的记忆不是一块平板，而是分层组织的。认知科学中的经典三层记忆模型可以直接映射到数字人系统中：

**工作记忆（Working Memory）** 对应当前对话的上下文窗口。它容量有限（类似人类的 7±2 法则），只保留最近几轮对话内容。在实现上，工作记忆通常就是 LLM 的 context window，但我们需要主动管理它——当对话超过一定轮次时，旧的内容需要被"压缩"成摘要放入情景记忆，而不是简单截断。

**情景记忆（Episodic Memory）** 记录具体的交互事件。"用户在3月15日提到他有乳糖不耐受"就是一个情景记忆条目。每个条目包含时间戳、对话片段、提取的关键信息。情景记忆的存储通常用向量数据库，支持基于语义相似度的检索。

**语义记忆（Semantic Memory）** 存储从事实中提炼的结构化知识。"用户：乳糖不耐受"、"用户偏好：低糖饮食"、"用户职业：产品经理"。语义记忆更像一个知识图谱或结构化的用户画像，可以被快速查询。

```
记忆系统三层架构

┌─────────────────────────────────────────────────┐
│                 工作记忆 (Working)                │
│  ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐   │
│  │ R1  │ R2  │ R3  │ R4  │ R5  │ R6  │ R7  │   │  ← 最近 7 轮
│  └─────┴─────┴─────┴─────┴─────┴─────┴─────┘   │
│           ↕ 溢出时压缩为摘要                      │
├─────────────────────────────────────────────────┤
│               情景记忆 (Episodic)                 │
│  ┌─────────────────────────────────────────┐    │
│  │ [2025-03-15] 用户提到乳糖不耐受           │    │
│  │ [2025-03-20] 用户询问褪黑素替代方案        │    │
│  │ [2025-03-22] 用户反馈加班多、睡眠差        │    │
│  │ ...                                      │    │
│  └─────────────────────────────────────────┘    │
│           ↕ 提取结构化事实                        │
├─────────────────────────────────────────────────┤
│               语义记忆 (Semantic)                 │
│  ┌─────────────────────────────────────────┐    │
│  │ 健康状况: 乳糖不耐受, 轻度失眠            │    │
│  │ 生活习惯: 经常加班, 作息不规律             │    │
│  │ 偏好: 倾向自然疗法, 排斥药物依赖          │    │
│  │ 职业: 产品经理, 工作压力较大              │    │
│  └─────────────────────────────────────────┘    │
└─────────────────────────────────────────────────┘
```

记忆检索的策略很关键。不是所有记忆都需要在每次对话时调出来——这会浪费 token 也会干扰 LLM。正确的做法是：每次用户输入后，用当前对话的语义去向量数据库中检索最相关的 Top-K 条情景记忆，同时查询语义记忆中的相关条目，将这些作为额外上下文注入 LLM 的 prompt。2025 年的主流做法是用 embedding 模型（如 text-embedding-3-small）将记忆条目向量化，存储在 Chroma 或 Pinecone 中做相似度检索。

遗忘机制同样重要。如果记忆永远不衰减，系统会积累大量过时信息。推荐的做法是给每条记忆一个"最后访问时间"和"访问频率"的元数据，用一个简单的衰减公式来计算记忆的"活性"。超过阈值的记忆不删除（以防用户重新提起），但在检索排序时降低优先级。

### 三、情感对话引擎

情感对话引擎的核心任务有两个：追踪用户的情感状态，管理数字人自身的情感表达。这两个任务看似独立，实际上紧密耦合——数字人的情感回应应该是对用户情感的"社交适配"，而不是简单的镜像。

用户情感追踪的输入源有两个：文本内容和语音韵律。文本情感分析在前面的课已经讨论过，这里重点说语音维度。语音中的情感信号主要体现在四个特征上：基频（F0）的变化范围和速度、语速（syllable rate）、能量（RMS energy）的分布、频谱倾斜（spectral tilt）。一个简单的做法是从 ASR 的中间表示（如 Whisper 的 encoder 输出）中提取这些特征，用一个轻量分类器判断情感类别。

```
情感对话引擎管线

用户输入                           数字人输出
   │                                  ▲
   ▼                                  │
┌──────────┐    ┌──────────┐    ┌─────┴──────┐
│ 文本情感  │    │ 语音韵律  │    │ 情感适配器  │
│ 分析      │    │ 情感分析  │    │ Emotion    │
│(RoBERTa) │    │(轻量CNN) │    │ Adapter    │
└────┬─────┘    └────┬─────┘    └─────┬──────┘
     │               │               │
     └───────┬───────┘               │
             ▼                       │
     ┌──────────────┐         ┌─────┴──────┐
     │  情感融合器    │────────▶│ 数字人情感  │
     │  Weighted Avg │         │ 状态更新    │
     │  text: 0.6   │         │ PAD 空间    │
     │  voice: 0.4  │         └────────────┘
     └──────────────┘

情感适配规则示例：
  用户愤怒 → 数字人关切（不是镜像愤怒）
  用户悲伤 → 数字人温和（不是假装开心）
  用户兴奋 → 数字人同步兴奋（正向情感可镜像）
  用户中性 → 数字人友好（维持基线情感）
```

情感适配的关键原则是：**负面情感不镜像，正向情感可同步**。如果用户表达愤怒，数字人也表现出愤怒会让冲突升级；正确的回应是关切和歉意。但如果用户表达兴奋和开心，数字人同步表现出开心是自然的社交行为。这个规则可以用一个简单的映射表来实现，但在更精细的系统中，应该考虑对话场景（客服 vs 陪伴 vs 教育）来调整适配策略。

数字人自身的情感状态也需要维护一个 PAD 模型（在上一课已介绍），但这里的特殊之处在于：数字人的情感变化不仅取决于当前输入，还取决于**对话的走向**。如果用户连续三轮都在抱怨，数字人的"耐心值"（可以映射为 dominance 维度的下降）应该逐渐降低，表达出更委婉的"我理解您的感受"而不是重复道歉。

### 四、个性化人设系统

个性化人设是让数字人"不是千人一面"的核心技术。在大模型时代，人设控制的基本手段是 **Persona Prompt**——在系统提示词中定义数字人的身份、性格、说话风格和行为准则。

但 Persona Prompt 只是起点。一个真正一致的人设系统需要解决三个挑战：

第一，**长对话中的人设漂移**。LLM 在长上下文中容易"忘记"系统提示的约束，特别是在对话超过 20 轮之后。解决方案是定期在对话中"刷新"人设——不是每次都重复完整的人设描述，而是在关键节点插入一句角色锚定语，比如在生成回复前检查"这个回复是否符合角色设定"。

第二，**动态特质调整**。一个固定不变的人设会显得僵硬。数字人应该在保持核心性格不变的前提下，根据交互上下文动态调整表达风格。例如一个"温柔的健康顾问"在用户紧急求助时应该变得果断高效，在日常闲聊时可以更加轻松幽默。这种动态调整可以通过在 Persona Prompt 中设置"风格变量"来实现。

第三，**角色一致性评估**。如何衡量数字人是否"出了戏"？一个实用的方法是从每次数字人的回复中提取人设特征（语气词使用、句式长度、情感倾向），与预定义的角色画像做余弦相似度计算。如果相似度低于阈值，说明角色开始漂移，需要在下一轮对话中加强角色约束。

```
人设系统层次结构

┌─────────────────────────────────────────────┐
│  第一层：核心身份（不可变）                     │
│  · 名字：小雅                                 │
│  · 角色：健康顾问                             │
│  · 核心价值观：专业、温和、以用户健康为先       │
├─────────────────────────────────────────────┤
│  第二层：性格特质（半可变）                     │
│  · 外向性：0.7（偏外向，主动关心）             │
│  · 宜人性：0.9（高度友善、耐心）              │
│  · 尽责性：0.8（认真负责、注重细节）           │
│  · 情绪稳定性：0.85（沉稳，不易波动）         │
├─────────────────────────────────────────────┤
│  第三层：表达风格（动态可调）                   │
│  · 正式程度：0.6（中偏正式）                  │
│  · 幽默程度：0.3（轻度幽默，不轻浮）          │
│  · 详细程度：0.7（较详细，但不啰嗦）           │
│  · 情感表达强度：0.5（适度表达情感）           │
└─────────────────────────────────────────────┘
```

2025 年的前沿实践开始使用 **LoRA 人格微调** 来替代纯 prompt 的人设控制——通过对基础模型做人设数据的 LoRA 微调，让人设特质"写进"模型权重中，而不是依赖 prompt 指令。这种方法在长对话中的一致性显著优于 prompt-only 方案，但缺点是每次更换人设需要加载不同的 LoRA 权重，增加了部署复杂度。

### 五、RAG 增强的领域知识

通用大模型的知识有截止日期，且缺乏特定领域的深度知识。对于健康顾问、房产经纪人、法律顾问等垂直场景的数字人，RAG（检索增强生成）是补齐知识短板的标准方案。

数字人场景的 RAG 与普通 RAG 有几个特殊考量：

**知识粒度**。普通 RAG 通常以段落为单位切分文档，但数字人对话中用户的问题往往非常具体（"这个药和那个药能一起吃吗？"），需要更细粒度的知识切片——建议以"知识点"为单位，每个知识点是一个自包含的事实陈述，通常 50-150 字。

**多轮检索**。数字人对话不是一问一答，用户可能在第 3 轮对话中追问第 1 轮提到的内容。系统需要维护一个"检索上下文"，记录之前的检索结果，在后续轮次中优先检索相关但不重复的内容。

**安全过滤**。健康、法律等领域的错误信息可能造成实际伤害。RAG 检索到的内容需要经过可信度评估——来源是否权威、信息是否过时、是否与用户的具体情况匹配。宁可说"我不确定，建议咨询专业医生"，也不要给出可能有害的建议。

```
数字人 RAG 管线

用户问题 ──▶ ┌───────────┐    ┌──────────────┐
              │ Query      │    │ 向量检索      │
              │ 改写       │───▶│ Chroma/       │───▶ Top-K 知识片段
              │(上下文增强) │    │ Pinecone     │
              └───────────┘    └──────────────┘
                                      │
                                      ▼
                               ┌──────────────┐
                               │ 相关性重排    │
                               │ Cross-encoder │
                               │ + 安全过滤    │
                               └──────┬───────┘
                                      │
                                      ▼
              ┌───────────┐    ┌──────────────┐
              │ Prompt     │◀──│ 知识注入      │
              │ 组装       │    │ "基于以下信息"│
              └─────┬─────┘    └──────────────┘
                    │
                    ▼
              ┌───────────┐
              │ LLM 生成   │──▶ 数字人回复
              │(带人设约束)│
              └───────────┘
```

2025 年 RAG 技术的新趋势包括：**GraphRAG**（将知识组织为图谱而非扁平片段，适合需要推理链的场景）、**Agentic RAG**（让 LLM 自己决定是否需要检索、检索什么、检索几次）、以及 **Multimodal RAG**（检索图片、表格等非文本知识）。对于数字人场景，Agentic RAG 特别有价值——数字人可以在对话中自主判断"这个问题我需要查一下"，而不是每次都做检索，这既提升了效率也增强了自然感。

### 六、对话质量评估

数字人对话的质量评估比普通聊天机器人更复杂，因为除了"回答是否正确"之外，还要评估"表现是否一致"、"情感是否合适"、"人设是否稳定"。

评估维度可以分为客观指标和主观指标两类：

```
对话质量评估框架

┌─────────────────────────────────────────────────┐
│                 客观指标（可自动计算）              │
│                                                  │
│  一致性 (Consistency)                             │
│  · 同一话题内是否自相矛盾                          │
│  · 事实陈述是否与知识库一致                        │
│  · 人设特质是否前后一致                            │
│                                                  │
│  连贯性 (Coherence)                               │
│  · 回复是否与上文语义相关                          │
│  · 是否正确使用了对话上下文                        │
│  · 话题转换是否自然                                │
│                                                  │
│  信息量 (Informativeness)                         │
│  · 是否包含有价值的信息                            │
│  · 是否有冗余重复                                  │
│  · 是否主动提供了相关建议                          │
│                                                  │
├─────────────────────────────────────────────────┤
│                 主观指标（需人工/LLM评估）          │
│                                                  │
│  情感适当性 (Emotional Appropriateness)            │
│  · 情感回应是否匹配用户情绪                        │
│  · 是否在该共情时共情，该冷静时冷静                │
│                                                  │
│  人设符合度 (Persona Adherence)                    │
│  · 说话风格是否符合角色设定                        │
│  · 是否有"出戏"的表达                             │
│                                                  │
│  用户体验 (User Experience)                        │
│  · 用户是否感到被理解                              │
│  · 是否愿意继续对话                                │
│  · 是否信任数字人的建议                            │
└─────────────────────────────────────────────────┘
```

**LLM-as-Judge** 是 2025 年最主流的自动评估方法：用一个强大的 LLM（如 GPT-4o 或 Claude）作为"评委"，给数字人的每条回复打分。具体做法是将完整的对话历史和评估标准作为输入，让 Judge LLM 输出 1-5 分的评分和评语。这种方法与人工评估的相关性通常在 0.8 以上，成本却只有人工评估的 1/50。

但 LLM-as-Judge 有两个已知偏差：**位置偏差**（倾向于给排在前面的回复更高分）和**长度偏差**（倾向于给更长的回复更高分）。应对方法是在评估时随机调换候选回复的顺序，并在评分标准中明确要求"不要因为回复长就给高分"。

## 完整可运行代码

下面的代码实现了一个完整的数字人对话系统，集成了记忆管理、情感追踪、人设系统和 RAG 知识增强。系统使用 OpenAI 兼容 API，可以直接配置 endpoint 和 key 运行。

```python
"""
数字人对话系统 - 集成记忆、情感、人设与 RAG
运行方式：设置 OPENAI_API_KEY 环境变量后直接运行
"""
import json
import time
import hashlib
from dataclasses import dataclass, field
from typing import Optional
from collections import deque


@dataclass
class MemoryEntry:
    content: str
    timestamp: float
    memory_type: str       # "episodic" | "semantic"
    importance: float      # 0-1
    access_count: int = 0
    last_accessed: float = 0.0

    def get_relevance(self, current_time: float) -> float:
        age_hours = (current_time - self.timestamp) / 3600
        recency = 1.0 / (1.0 + age_hours * 0.05)
        frequency = min(1.0, self.access_count * 0.15)
        return 0.4 * recency + 0.3 * self.importance + 0.3 * frequency


@dataclass
class EmotionState:
    valence: float = 0.0
    arousal: float = 0.3

    def update(self, v: float, a: float, alpha: float = 0.25):
        self.valence = alpha * v + (1 - alpha) * self.valence
        self.arousal = alpha * a + (1 - alpha) * self.arousal

    def adapt_to_user(self, user_valence: float) -> tuple[float, float]:
        if user_valence < -0.3:
            return (-0.2, 0.4)
        elif user_valence > 0.3:
            return (user_valence * 0.7, 0.5)
        return (0.1, 0.3)

    def to_prompt_hint(self) -> str:
        if self.valence > 0.3:
            return "语气温暖积极"
        elif self.valence < -0.3:
            return "语气温和关切"
        return "语气平和友好"


@dataclass
class PersonaConfig:
    name: str = "小雅"
    role: str = "健康顾问"
    core_values: list = field(default_factory=lambda: ["专业", "温和", "以用户健康为先"])
    extraversion: float = 0.7
    agreeableness: float = 0.9
    formality: float = 0.6
    humor: float = 0.3
    detail_level: float = 0.7

    def to_system_prompt(self) -> str:
        style = "温和专业" if self.formality > 0.5 else "轻松随意"
        humor_hint = "偶尔加入适度的轻松表达" if self.humor > 0.3 else "保持严肃专业"
        return (
            f"你是{self.name}，一位{self.role}。"
            f"核心价值观：{'、'.join(self.core_values)}。"
            f"说话风格：{style}，{humor_hint}。"
            f"回复详细程度：{'较详细' if self.detail_level > 0.5 else '简洁明了'}。"
            f"记住：你是专业的健康顾问，不能给出诊断结论，"
            f"涉及严重健康问题时建议用户咨询医生。"
        )


class KnowledgeBase:
    def __init__(self):
        self.entries = [
            {"content": "乳糖不耐受人群可以选择酸奶、硬质奶酪代替牛奶，"
                        "这些乳制品中乳糖含量较低。",
             "topic": "乳糖不耐受", "importance": 0.8},
            {"content": "褪黑素的推荐起始剂量为0.5-1mg，建议在睡前30分钟服用。"
                        "长期使用前建议咨询医生。",
             "topic": "褪黑素", "importance": 0.7},
            {"content": "镁元素有助于改善睡眠质量，富含镁的食物包括深绿叶蔬菜、"
                        "坚果、全谷物。甘氨酸镁吸收率较好。",
             "topic": "镁与睡眠", "importance": 0.7},
            {"content": "睡前避免蓝光暴露（手机、电脑）至少30分钟，"
                        "可以帮助褪黑素自然分泌。",
             "topic": "睡眠卫生", "importance": 0.6},
            {"content": "规律的有氧运动可以改善睡眠质量，但建议在睡前3小时内"
                        "避免剧烈运动。",
             "topic": "运动与睡眠", "importance": 0.6},
        ]

    def search(self, query: str, top_k: int = 2) -> list[dict]:
        scored = []
        query_chars = set(query)
        for entry in self.entries:
            entry_chars = set(entry["content"] + entry["topic"])
            overlap = len(query_chars & entry_chars)
            score = overlap * entry["importance"]
            scored.append((score, entry))
        scored.sort(key=lambda x: x[0], reverse=True)
        return [e for _, e in scored[:top_k]]


class DigitalHumanDialogueSystem:
    def __init__(self, persona: Optional[PersonaConfig] = None,
                 api_key: str = "", base_url: str = "https://api.openai.com/v1"):
        self.persona = persona or PersonaConfig()
        self.working_memory: deque = deque(maxlen=7)
        self.episodic_memory: list[MemoryEntry] = []
        self.semantic_memory: dict[str, str] = {}
        self.user_emotion = EmotionState()
        self.digital_emotion = EmotionState()
        self.knowledge_base = KnowledgeBase()
        self.turn_count = 0
        self.api_key = api_key
        self.base_url = base_url
        self._try_init_client()

    def _try_init_client(self):
        self.client = None
        try:
            from openai import OpenAI
            if self.api_key:
                self.client = OpenAI(api_key=self.api_key, base_url=self.base_url)
        except ImportError:
            pass

    def _extract_key_info(self, text: str) -> Optional[dict]:
        keywords = ["喜欢", "不喜欢", "过敏", "不耐受", "习惯", "职业",
                     "偏好", "问题", "症状", "在吃", "经常"]
        for kw in keywords:
            if kw in text:
                return {"content": text[:100], "importance": 0.7,
                        "keyword": kw, "timestamp": time.time()}
        return None

    def _add_to_episodic(self, text: str, speaker: str):
        info = self._extract_key_info(text)
        if info:
            entry = MemoryEntry(
                content=f"[{speaker}] {info['content']}",
                timestamp=info["timestamp"],
                memory_type="episodic",
                importance=info["importance"],
            )
            self.episodic_memory.append(entry)

    def _retrieve_memories(self, query: str, top_k: int = 3) -> list[str]:
        now = time.time()
        for m in self.episodic_memory:
            m.access_count += 1
            m.last_accessed = now
        scored = []
        query_chars = set(query)
        for m in self.episodic_memory:
            overlap = len(query_chars & set(m.content))
            relevance = m.get_relevance(now)
            scored.append((overlap * relevance, m))
        scored.sort(key=lambda x: x[0], reverse=True)
        return [m.content for _, m in scored[:top_k]]

    def _analyze_user_emotion(self, text: str):
        emotion_map = {
            "开心": (0.8, 0.6), "高兴": (0.7, 0.5), "谢谢": (0.5, 0.4),
            "抱歉": (-0.3, 0.3), "难受": (-0.6, 0.4), "焦虑": (-0.5, 0.7),
            "生气": (-0.7, 0.8), "太好了": (0.9, 0.7), "担心": (-0.4, 0.5),
        }
        for kw, (v, a) in emotion_map.items():
            if kw in text:
                self.user_emotion.update(v, a, alpha=0.35)
                return
        self.user_emotion.update(0.0, 0.3, alpha=0.1)

    def _build_prompt(self, user_input: str) -> list[dict]:
        system_prompt = self.persona.to_system_prompt()
        emotion_hint = self.digital_emotion.to_prompt_hint()
        system_prompt += f"\n当前情感基调：{emotion_hint}。"
        messages = [{"role": "system", "content": system_prompt}]
        relevant_memories = self._retrieve_memories(user_input)
        if relevant_memories:
            memory_text = "\n".join(f"- {m}" for m in relevant_memories)
            messages.append({
                "role": "system",
                "content": f"以下是之前对话中记录的用户相关信息：\n{memory_text}"
            })
        knowledge_results = self.knowledge_base.search(user_input)
        if knowledge_results:
            knowledge_text = "\n".join(f"- {k['content']}" for k in knowledge_results)
            messages.append({
                "role": "system",
                "content": f"以下是相关知识（可参考但不要逐字引用）：\n{knowledge_text}"
            })
        if self.semantic_memory:
            profile_items = [f"- {k}: {v}" for k, v in self.semantic_memory.items()]
            messages.append({
                "role": "system",
                "content": "用户画像：\n" + "\n".join(profile_items)
            })
        for role, content in self.working_memory:
            messages.append({"role": role, "content": content})
        messages.append({"role": "user", "content": user_input})
        return messages

    def _generate_reply(self, messages: list[dict]) -> str:
        if self.client:
            try:
                response = self.client.chat.completions.create(
                    model="gpt-4o-mini",
                    messages=messages,
                    max_tokens=300,
                    temperature=0.7,
                )
                return response.choices[0].message.content
            except Exception as e:
                return f"[API 调用失败: {e}] 使用本地模拟回复。"
        if "睡眠" in str(messages):
            return "我理解睡眠问题确实很困扰。建议你先试试睡前减少蓝光暴露，"
            "同时可以适当补充镁元素。如果持续不好转，建议咨询医生。"
        if "你好" in str(messages) or "嗨" in str(messages):
            return f"你好！我是{self.persona.name}，很高兴见到你。今天有什么"
            f"我可以帮你的吗？"
        return "我理解你的感受。能告诉我更多细节吗？这样我可以给你更精准的建议。"

    def chat(self, user_input: str) -> dict:
        self.turn_count += 1
        self.working_memory.append(("user", user_input))
        self._add_to_episodic(user_input, "用户")
        self._analyze_user_emotion(user_input)
        adapted_v, adapted_a = self.digital_emotion.adapt_to_user(
            self.user_emotion.valence
        )
        self.digital_emotion.update(adapted_v, adapted_a, alpha=0.3)
        messages = self._build_prompt(user_input)
        reply = self._generate_reply(messages)
        self.working_memory.append(("assistant", reply))
        self._add_to_episodic(reply, self.persona.name)
        return {
            "reply": reply,
            "user_emotion": {
                "valence": round(self.user_emotion.valence, 2),
                "arousal": round(self.user_emotion.arousal, 2),
            },
            "digital_emotion": {
                "valence": round(self.digital_emotion.valence, 2),
                "arousal": round(self.digital_emotion.arousal, 2),
            },
            "memories_used": len(self._retrieve_memories(user_input)),
            "turn": self.turn_count,
        }
```

## 常见误区

### 误区一：把所有历史对话都塞进上下文

一个常见的做法是把完整的对话历史都作为 LLM 的输入，认为这样 LLM 就"什么都知道"。问题是：上下文窗口有限，成本随 token 数线性增长，而且 LLM 对长上下文中间部分的信息利用率很低（"lost in the middle"问题）。正确的做法是用记忆系统做分层管理——工作记忆只保留最近几轮，历史信息通过向量检索按需召回。

### 误区二：情感分析越精确越好

有些团队花大量精力训练高精度的细粒度情感分类模型（区分"焦虑"和"紧张"和"不安"），但对数字人对话系统来说，粗粒度的情感分类（正面/中性/负面 + 激活度高低）通常就够了。因为数字人的回应策略是基于情感大类的映射，而不是对用户情感的精确复刻。把精力花在情感适配策略的打磨上，比花在情感分类精度上更有 ROI。

### 误区三：RAG 检索到什么就说什么

RAG 检索到的知识片段不一定都适合在当前对话中使用。一个合格的数字人应该具备"信息筛选"能力——判断哪些知识对用户当前的问题有帮助，哪些可能造成困惑或不安。例如用户问"我头疼怎么办"，RAG 检索到了"头疼可能是严重疾病的症状"，直接说出来会引发用户焦虑。正确的做法是在 NLG 环节加入一个安全过滤层，根据对话场景和用户情感状态来决定信息的取舍和表达方式。

### 误区四：人设只在系统提示里定义就够了

系统提示中的人设描述在长对话中会逐渐被稀释。实验表明，当对话超过 20 轮时，LLM 对系统提示的遵从度会下降 15-30%。需要在对话过程中周期性地"加固"人设——一种实用的做法是在每 5-8 轮对话后，在 prompt 中插入一条人设检查指令（"请确保你的回复符合健康顾问小雅的身份"），或者用一个独立的 LLM 调用来审核回复是否符合人设。

## 小结与练习

本课构建了一个完整的数字人对话系统，从架构设计到各子系统的实现。核心要点是：记忆系统让数字人有连续性，情感引擎让数字人有温度，人设系统让数字人有个性，RAG 让数字人有知识。四者缺一不可——只有记忆没有情感是数据库客服，只有情感没有人设是情绪化聊天机器人，只有人设没有知识是空壳角色。

### 练习一：实现记忆遗忘机制

**思路**：给每条记忆计算一个"活性分数"，基于最后访问时间、访问频率和初始重要性。活性低于阈值的记忆在检索时降权但不删除。

**答案**：

```python
import math

class MemoryWithForgetting:
    def __init__(self, decay_rate: float = 0.01, threshold: float = 0.1):
        self.decay_rate = decay_rate
        self.threshold = threshold

    def compute_vitality(self, entry: MemoryEntry, current_time: float) -> float:
        age_hours = (current_time - entry.timestamp) / 3600
        time_decay = math.exp(-self.decay_rate * age_hours)
        frequency_boost = math.log1p(entry.access_count) * 0.2
        vitality = (entry.importance * 0.5 +
                    time_decay * 0.3 +
                    frequency_boost * 0.2)
        return max(0.0, vitality)

    def prune_memories(self, memories: list[MemoryEntry],
                       current_time: float) -> list[MemoryEntry]:
        active = []
        for m in memories:
            vitality = self.compute_vitality(m, current_time)
            if vitality >= self.threshold:
                active.append(m)
        return active

    def retrieve_with_forgetting(self, memories: list[MemoryEntry],
                                  query: str, current_time: float,
                                  top_k: int = 3) -> list[MemoryEntry]:
        scored = []
        for m in memories:
            vitality = self.compute_vitality(m, current_time)
            if vitality < self.threshold:
                continue
            text_similarity = len(set(query) & set(m.content)) * 0.01
            score = text_similarity * vitality
            scored.append((score, m))
        scored.sort(key=lambda x: x[0], reverse=True)
        return [m for _, m in scored[:top_k]]
```

**要点**：
- decay_rate 控制遗忘速度，0.01 意味着大约 3 天后未访问的记忆活性降至 50%
- 访问频率用 log 平滑，避免频繁访问的记忆永远不衰减
- 重要的语义记忆可以设置更高的 threshold 使其更难被遗忘

### 练习二：实现多轮 RAG 上下文累积

**思路**：维护一个"检索历史"，记录每轮对话检索到的知识片段，在后续轮次中避免重复检索，同时优先检索与之前结果互补的内容。

**答案**：

```python
class MultiTurnRAGContext:
    def __init__(self, knowledge_base: KnowledgeBase):
        self.kb = knowledge_base
        self.retrieval_history: list[dict] = []
        self.used_content_hashes: set[str] = set()

    def _hash_content(self, content: str) -> str:
        return hashlib.md5(content.encode()).hexdigest()[:8]

    def retrieve(self, query: str, top_k: int = 2) -> list[dict]:
        all_results = self.kb.search(query, top_k=top_k * 2)
        fresh_results = []
        for r in all_results:
            h = self._hash_content(r["content"])
            if h not in self.used_content_hashes:
                fresh_results.append(r)
                self.used_content_hashes.add(h)
            if len(fresh_results) >= top_k:
                break
        if len(fresh_results) < top_k:
            for r in all_results:
                if r not in fresh_results:
                    fresh_results.append(r)
                if len(fresh_results) >= top_k:
                    break
        self.retrieval_history.append({
            "query": query,
            "results": [r["content"][:50] for r in fresh_results],
            "turn": len(self.retrieval_history) + 1,
        })
        return fresh_results

    def get_context_summary(self) -> str:
        if not self.retrieval_history:
            return "暂无检索历史"
        lines = []
        for h in self.retrieval_history:
            lines.append(f"第{h['turn']}轮: {', '.join(h['results'])}")
        return "\n".join(lines)
```

**要点**：
- 用 content hash 去重，避免同一知识点在多轮中重复出现
- 当不重复的结果不够时，允许返回已用过的结果（宁可重复也不能空手）
- retrieval_history 可以作为调试工具，帮助分析 RAG 系统的检索质量

### 练习三：实现人设一致性检测器

**思路**：从数字人的回复中提取风格特征（句式长度、情感词比例、语气词使用），与人设配置的目标值做对比，输出一致性分数。

**答案**：

```python
class PersonaConsistencyChecker:
    def __init__(self, persona: PersonaConfig):
        self.persona = persona
        self.positive_words = {"好", "棒", "开心", "感谢", "温暖", "希望", "喜欢"}
        self.formal_words = {"您", "建议", "推荐", "请注意", "根据", "分析"}
        self.casual_words = {"哈", "嘿", "呀", "嘛", "哦", "呢", "啦"}
        self.humor_words = {"哈哈", "有趣", "有意思", "开玩笑"}

    def extract_features(self, text: str) -> dict:
        sentences = [s.strip() for s in text.replace("。", ".").replace("！", ".").replace("？", ".").split(".") if s.strip()]
        avg_len = sum(len(s) for s in sentences) / max(1, len(sentences))
        chars = set(text)
        positive_ratio = len(chars & self.positive_words) / max(1, len(text))
        formal_ratio = len(chars & self.formal_words) / max(1, len(text))
        casual_ratio = len(chars & self.casual_words) / max(1, len(text))
        humor_ratio = len(chars & self.humor_words) / max(1, len(text))
        return {
            "avg_sentence_length": avg_len,
            "positive_ratio": positive_ratio,
            "formal_ratio": formal_ratio,
            "casual_ratio": casual_ratio,
            "humor_ratio": humor_ratio,
        }

    def check_consistency(self, text: str) -> dict:
        features = self.extract_features(text)
        formality_score = 1.0 - abs(features["formal_ratio"] - self.persona.formality * 0.1) / 0.1
        humor_score = 1.0 - abs(features["humor_ratio"] - self.persona.humor * 0.05) / 0.05
        detail_score = min(1.0, features["avg_sentence_length"] / (20 * self.persona.detail_level))
        overall = (formality_score * 0.4 + humor_score * 0.3 + detail_score * 0.3)
        return {
            "overall": round(max(0, min(1, overall)), 2),
            "formality_match": round(max(0, formality_score), 2),
            "humor_match": round(max(0, humor_score), 2),
            "detail_match": round(max(0, detail_score), 2),
            "warning": overall < 0.5,
        }
```

**要点**：
- 特征提取要轻量，不能在每次回复后都做一次完整的 NLP 分析
- 一致性分数低于 0.5 时应该触发告警，下一轮对话加强人设约束
- 不同维度的权重可以根据应用场景调整——客服场景 formality 权重更高，陪伴场景 humor 权重更高
