## 常见误区

1. **将 100% 覆盖率等同于代码质量高**：全覆盖的测试可能只是执行了代码路径而没有验证输出，存在"绿色的虚假安全感"
2. **只关注行覆盖率而忽略分支覆盖率**：行覆盖率高不代表 if/else、try/catch 的每个分支都被测试到，分支覆盖率才是更严格的质量指标
3. **为了凑覆盖率而写无意义的测试**：测试应该验证行为正确性，而不是为了让覆盖率数字好看而编写断言空洞的测试用例
4. **忽略未覆盖代码的业务重要性**：一个低覆盖率的工具函数和一个低覆盖率的支付回调处理，其风险等级完全不同

## 工程建议

1. **设置合理的覆盖率阈值并渐进提升**：初始阈值设为 70%，随项目成熟度逐步提升到 80%-85%，避免一开始就设置过高导致团队为了达标而写低质量测试
2. **重点关注分支覆盖率和条件覆盖率**：在 CI 中单独配置分支覆盖率的阈值检查，确保复杂的条件逻辑都被测试到
3. **将未覆盖代码按业务风险排序**：优先为支付、权限、数据处理等高风险模块补充测试，而非均匀地补充所有未覆盖代码
4. **在 PR 流程中展示覆盖率变化**：不仅报告总体覆盖率，还要展示本次 PR 新增代码的覆盖率，防止新代码拉低整体水平

## 建议

- 优先补充分支覆盖率最低的文件
- 为错误处理路径添加测试
- 测试边界条件和空值情况
