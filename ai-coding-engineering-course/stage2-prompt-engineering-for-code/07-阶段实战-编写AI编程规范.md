## 场景引入

你的团队决定全面拥抱 AI 辅助开发，每个人都在用 Cursor、Copilot 等工具。但一个月后你发现：代码库变成了"风格博物馆"——有人用 callback，有人用 async/await，有人用 Express，有人用 Fastify，错误处理更是五花八门。代码审查从讨论业务逻辑退化成了争论代码风格。你意识到，需要一份统一的 AI 编程规范，让所有人在用 AI 生成代码时遵循同一套标准。本课就是教你怎么写这份规范。

## 一、为什么需要 AI 编程规范？

### 1.1 无规范 vs 有规范

```
无规范的 AI 编程体验：
┌──────────────────────────────────────────────────┐
│  开发者 A: "帮我写个接口"                         │
│  → AI 返回 JavaScript，用 callback 风格          │
│                                                   │
│  开发者 B: "写一个用户 API"                       │
│  → AI 返回 TypeScript，用 async/await            │
│                                                   │
│  开发者 C: "实现用户模块"                         │
│  → AI 返回 Python，用 Flask                      │
│                                                   │
│  结果：三个接口，三种风格，无法维护               │
└──────────────────────────────────────────────────┘

有规范的 AI 编程体验：
┌──────────────────────────────────────────────────┐
│  团队 AI 规范：                                   │
│  - 语言：TypeScript + Express                    │
│  - 风格：async/await + Zod 校验                  │
│  - 错误处理：统一 Error Middleware               │
│  - 响应格式：{ code, data, message }             │
│                                                   │
│  所有人使用相同 Prompt 模板                       │
│  → AI 输出风格一致，可直接合并                    │
└──────────────────────────────────────────────────┘
```

### 1.2 规范的价值

| 维度 | 无规范 | 有规范 |
|------|--------|--------|
| 代码风格 | 每人不同 | 统一标准 |
| AI 输出质量 | 不可预测 | 可预期 |
| 代码审查 | 反复修改风格 | 专注业务逻辑 |
| 新人上手 | 摸索中学习 | 模板即教程 |
| 知识沉淀 | 散落在聊天记录 | 结构化文档 |

### 4.3 规则配置文件

以下是 `.cursorrules` 的完整示例：

```markdown
# .cursorrules 示例

## 项目信息
这是一个 TypeScript + Express + Prisma 的后端 API 项目。

## 技术栈
- TypeScript 5.4+ 严格模式
- Express 4.18+
- Prisma 5.x + PostgreSQL
- Zod 3.x 请求校验
- Vitest 1.x 测试

## 代码规范
- 使用 async/await，禁止回调
- 使用 const 和 let，禁止 var
- 函数命名：camelCase
- 类/接口命名：PascalCase
- 常量命名：UPPER_SNAKE_CASE
- 文件命名：kebab-case

## 错误处理
- 使用自定义 AppError 类
- 业务逻辑抛出 AppError
- Controller 层不需要 try-catch（由错误中间件统一处理）
- 错误码规范：400(参数错误), 401(未认证), 403(未授权), 404(不存在), 500(服务端错误)

## 响应格式
所有 API 响应格式：
{
  "code": 0,       // 0=成功, 非0=失败
  "data": T,       // 响应数据
  "message": "ok"  // 描述信息
}

## 文件组织
- 每个路由对应一个 controller + service + repository
- Controller 只负责参数解析和响应
- Service 负责业务逻辑
- Repository 负责数据库操作
- 共用类型放在 types/ 目录

## 禁止事项
- 不使用 any 类型
- 不使用 console.log（使用 logger）
- 不硬编码配置值（使用环境变量）
- 不在 Controller 中直接操作数据库
- 不跳过输入校验
```

## 五、代码质量标准

### 5.1 命名规范对照表

| 场景 | 好的命名 | 差的命名 | 说明 |
|------|----------|----------|------|
| 用户列表获取 | `getUserList` | `getData` | 明确获取什么 |
| 创建订单 | `createOrder` | `add` | 明确操作对象 |
| 是否有效 | `isActive` | `status` | 布尔值用 is/has/can |
| 最大重试次数 | `MAX_RETRY_COUNT` | `max` | 常量要完整 |
| 用户信息 | `UserProfile` | `Data` | 类型要具体 |

## 七、常见误区

### ❌ 错误 1：规范过于笼统

```markdown
# 错误示例
"写代码要规范"
"AI 生成的代码要检查"
```

**问题**：没有可执行的标准，每个人理解不同。

**正确做法**：
```markdown
# 正确示例
"所有函数必须有 JSDoc 注释，包含 @param 和 @returns"
"AI 生成的代码必须通过 ESLint 检查且无 any 类型"
```

### ❌ 错误 2：Prompt 模板过于复杂

```
# 错误示例 - 一个 Prompt 里塞太多要求
请帮我写一个 API，要求：使用 TypeScript、Express、Prisma、
Zod、JWT、bcrypt、helmet、cors、rate-limit，
要有完整的 CRUD、分页、排序、过滤、缓存、日志、监控...
```

**问题**：信息过载，AI 输出质量下降。

**正确做法**：拆分为多个小任务，逐步完成。

### ❌ 错误 3：规范不更新

```markdown
# 问题场景
规范文档还是 6 个月前写的，技术栈已经换了两轮。
团队成员发现规范和实际代码不符，索性不看了。
```

**正确做法**：每次技术栈变更都同步更新规范，指定规范维护人。

---

## 工程建议

1. **规范文档要版本化**：给 AI 编程规范打版本号（如 v1.0），每次更新记录变更内容和原因。当团队成员发现 AI 生成的代码有问题时，先检查是否是规范过时导致的，而非直接修改 AI 输出。

2. **从一个模块开始试点**：不要试图一次性为整个项目编写完整规范。先选一个核心模块（如用户管理），用本课的模板编写规范并在该模块试运行，验证效果后再推广到其他模块。

3. **Prompt 模板要可复制粘贴**：将 Prompt 模板设计成可以直接复制粘贴使用的形式，包含占位符（如 `{资源名}`、`{任务描述}`）。团队成员只需替换占位符即可使用，降低采纳门槛。

4. **建立"规范→模板→审查"三层保障**：规范定义标准，模板降低使用成本，审查确保执行。三者缺一不可——没有规范模板是空中楼阁，没有审查规范形同虚设。

### 关键收获

1. **规范是基础**：没有规范，AI 编程会变成"随机代码生成器"
2. **模板化是关键**：好的 Prompt 模板能显著提升 AI 输出质量
3. **上下文管理很重要**：分层提供上下文，让 AI 理解你的项目
4. **迭代是常态**：规范需要持续更新和优化
5. **安全不能忘**：Prompt 和代码都要注意安全
