## 1. 补全的本质：上下文驱动的预测

```
┌──────────────────────────────────────────────────────────────┐
│              代码补全 = 上下文 → LLM 预测                      │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│   上下文信号                    AI 预测                       │
│   ┌───────────────┐          ┌──────────────────┐           │
│   │ ① 函数名       │          │                  │           │
│   │ ② 参数类型     │   ───►   │  最可能的代码     │           │
│   │ ③ 返回类型     │          │  (基于万亿token  │           │
│   │ ④ 注释         │          │   训练的统计模型) │           │
│   │ ⑤ 前面的代码   │          │                  │           │
│   │ ⑥ 相关文件     │          └──────────────────┘           │
│   └───────────────┘                                          │
│                                                              │
│   信号越强 ──► 预测越准                                       │
│   信号越弱 ──► 预测越随机                                     │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**核心原则**：你的代码不只是给人看的，也是给 AI 看的。写出"信息密度高"的代码，AI 就能给出更好的补全。

## 2. 五种提升补全质量的代码习惯

### 2.1 命名即提示（Naming is Prompting）

函数名、变量名是触发补全最强的信号。

```typescript
// ❌ 差的命名 — AI 不知道你想做什么
function process(data) {
  // AI: "可能是过滤？排序？转换？随便猜一个吧..."
}

// ✅ 好的命名 — AI 精准理解意图
function filterOutdatedOrders(orders: Order[], cutoffDate: Date): Order[] {
  // AI: "按日期过滤订单，很清楚"
}

// ❌ 差的变量名
const d = users.filter(u => u.a > 18);
// AI: "d 是什么？a 是什么？只能猜..."

// ✅ 好的变量名
const adultUsers = users.filter(user => user.age > 18);
// AI: "过滤成年用户，完全理解"
```

**命名规则总结**：

| 命名习惯 | 补全效果 | 示例 |
|----------|----------|------|
| 动词 + 名词 | ★★★★★ | `fetchUserProfile`, `calculateTotal` |
| 形容词 + 名词 | ★★★★☆ | `activeUsers`, `pendingOrders` |
| 单字母 | ★☆☆☆☆ | `d`, `x`, `arr` |
| 缩写 | ★★☆☆☆ | `procUsr`, `calcTot` |

### 2.2 类型注解是最好的提示

TypeScript 和 Python 的类型注解直接告诉 AI 数据的形状。

```typescript
// ❌ 无类型 — AI 需要猜参数结构
function createOrder(order) {
  // AI: "order 有什么字段？不知道，随便写几个常见的..."
}

// ✅ 有类型 — AI 精准生成代码
interface CreateOrderInput {
  userId: string;
  items: Array<{ productId: string; quantity: number; price: number }>;
  shippingAddress: Address;
  couponCode?: string;
}

function createOrder(input: CreateOrderInput): Promise<Order> {
  // AI: "我知道完整的数据结构了，可以精确生成逻辑"
}
```

```python
# ❌ 无类型
def calculate_discount(price, rate):
    ...

# ✅ 有类型
def calculate_discount(price: float, rate: float) -> float:
    """根据价格和折扣率计算折后价"""
    ...
```

### 2.3 注释作为"微型 Prompt"

简短的注释帮助 AI 理解你的意图，但不要写太长。

```typescript
// ❌ 注释太长 — 浪费时间，AI 可能忽略部分
/**
 * 这个函数的目的是处理用户提交的表单数据。
 * 首先需要验证邮箱格式，然后检查用户名是否已存在，
 * 如果都通过了就创建用户并发送欢迎邮件。
 * 注意：密码需要 bcrypt 加密，token 需要 24 小时过期。
 */

// ✅ 简短精准的注释
// 创建用户：验证邮箱 → 检查唯一性 → 加密密码 → 发送欢迎邮件
async function createUser(input: CreateUserInput): Promise<User> {
  // AI 完全理解上下文，精准生成每一步
}

// ✅ 用注释说明"非显而易见的意图"
// 使用二分查找，因为 products 已按 price 排序
function findProductByPrice(products: Product[], target: number): Product | null {
  // AI: "二分查找，清楚了"
}
```

### 2.4 先写骨架，再让 AI 填充

```
策略：先写函数签名和主要步骤的注释，让 AI 填充实现。

┌─────────────────────────────────────────────────┐
│  你写的骨架：                                     │
│  ┌───────────────────────────────────────────┐  │
│  │ // 1. 验证输入                             │  │
│  │ // 2. 查询数据库                           │  │
│  │ // 3. 计算结果                             │  │
│  │ // 4. 保存并返回                           │  │
│  └───────────────────────────────────────────┘  │
│                    │                            │
│                    ▼                            │
│  AI 填充的实现：                                 │
│  ┌───────────────────────────────────────────┐  │
│  │ 1. validateInput(input) // 详细校验逻辑    │  │
│  │ 2. db.query(...) // SQL 查询               │  │
│  │ 3. calculateResult(...) // 算法实现        │  │
│  │ 4. db.save(...) + return result            │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

```typescript
// 你写：
// 处理支付：验证金额 → 调用支付网关 → 更新订单状态 → 发送通知
async function processPayment(orderId: string, paymentMethod: PaymentMethod): Promise<PaymentResult> {

// AI 补全：
  // 1. 验证金额
  const order = await db.orders.findById(orderId);
  if (!order || order.status !== 'pending') {
    throw new PaymentError('Invalid order');
  }
  if (order.total <= 0) {
    throw new PaymentError('Invalid amount');
  }

  // 2. 调用支付网关
  const gatewayResult = await paymentGateway.charge({
    amount: order.total,
    currency: order.currency,
    method: paymentMethod,
  });

  // 3. 更新订单状态
  await db.orders.update(orderId, {
    status: gatewayResult.success ? 'paid' : 'failed',
    paymentId: gatewayResult.transactionId,
  });

  // 4. 发送通知
  if (gatewayResult.success) {
    await emailService.send(order.userEmail, 'payment-confirmation', { orderId });
  }

  return gatewayResult;
}
```

### 2.5 利用现有代码模式

AI 会学习你当前文件和项目中的代码模式。保持一致的风格能让补全更准确。

```typescript
// 如果你的项目中已有类似的模式：
async function getUserById(id: string): Promise<User | null> {
  const result = await db.query('SELECT * FROM users WHERE id = $1', [id]);
  return result.rows[0] ?? null;
}

// AI 补全新函数时会自动遵循同样的模式：
async function getOrderById(id: string): Promise<Order | null> {
  // AI 自动使用相同的 db.query 模式、相同的错误处理风格
  const result = await db.query('SELECT * FROM orders WHERE id = $1', [id]);
  return result.rows[0] ?? null;
}
```

### 3.3 部分接受策略

很多时候，补全的前几行是对的，后面偏离了。不要全盘接受或全盘拒绝。

```
策略：部分接受 + 手动调整

  第 1-3 行：完全正确 ✅
  第 4-6 行：逻辑对但风格不符 ⚠️
  第 7-10 行：方向错了 ❌

处理方式：
1. Tab 接受全部
2. 删除 7-10 行
3. 修改 4-6 行的风格
4. 手动补写 7-10 行
```

## 5. 补全中的常见陷阱

### 5.1 陷阱一：盲目接受安全相关代码

```typescript
// AI 补全的登录函数 — 有安全问题！
async function login(email: string, password: string) {
  const user = await db.query(
    `SELECT * FROM users WHERE email = '${email}'` // ❌ SQL 注入！
  );
  if (user.password === password) { // ❌ 明文比较！
    return generateToken(user);
  }
}

// ✅ 正确写法
async function login(email: string, password: string) {
  const user = await db.query(
    'SELECT * FROM users WHERE email = $1', [email] // 参数化查询
  );
  const isValid = await bcrypt.compare(password, user.passwordHash); // bcrypt
  if (!isValid) throw new AuthError('Invalid credentials');
  return generateToken(user);
}
```

### 5.2 陷阱二：忽略错误处理

```typescript
// AI 常常生成"快乐路径"代码，忽略异常情况
async function fetchUser(id: string): Promise<User> {
  const response = await fetch(`/api/users/${id}`); // ❌ 没检查状态码
  const data = await response.json(); // ❌ 没有 try-catch
  return data; // ❌ 没验证返回结构
}

// ✅ 加上错误处理
async function fetchUser(id: string): Promise<User> {
  try {
    const response = await fetch(`/api/users/${id}`);
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}: ${response.statusText}`);
    }
    const data = await response.json();
    return UserSchema.parse(data); // Zod 验证
  } catch (error) {
    logger.error('Failed to fetch user', { id, error });
    throw error;
  }
}
```

### 5.3 陷阱三：性能盲区

```typescript
// AI 补全的代码可能有 N+1 查询问题
async function getOrderDetails(orders: Order[]) {
  for (const order of orders) {
    order.user = await db.users.findById(order.userId); // ❌ N+1 查询！
    order.items = await db.items.findByOrderId(order.id); // ❌ N+1 查询！
  }
  return orders;
}

// ✅ 批量查询
async function getOrderDetails(orders: Order[]) {
  const userIds = [...new Set(orders.map(o => o.userId))];
  const orderIds = orders.map(o => o.id);

  const [users, items] = await Promise.all([
    db.users.findByIds(userIds),
    db.items.findByOrderIds(orderIds),
  ]);

  const userMap = new Map(users.map(u => [u.id, u]));
  const itemsMap = groupBy(items, 'orderId');

  return orders.map(order => ({
    ...order,
    user: userMap.get(order.userId),
    items: itemsMap.get(order.id) ?? [],
  }));
}
```

## 7. 常见错误

| 错误 | 为什么有问题 | 正确做法 |
|------|-------------|----------|
| 函数名用 `f`, `data`, `process` | AI 无法理解意图，补全质量极差 | 用描述性名称：`filterActiveUsers` |
| 不写类型注解 | AI 猜测数据结构，经常猜错 | 添加 TypeScript/Python 类型 |
| Tab 狂按，不看补全 | 引入 bug、安全漏洞、冗余代码 | 每次 Tab 前至少扫一眼逻辑 |
| 补全太长不截断 | 代码冗余，难以维护 | 接受后删除多余部分，保持精简 |
| 用注释写整段需求 | 浪费时间，AI 可能忽略部分 | 简短注释 + 清晰的函数签名 |
| 不检查边界情况 | AI 默认生成"快乐路径"代码 | 手动补充 null、空数组、并发处理 |
| 在敏感代码上完全依赖补全 | 密码、token、SQL 相关代码风险高 | 敏感部分手动编写或仔细审查 |

## 8. 总结

本课要点：

1. **命名即提示**：描述性的函数名和变量名是最强的补全信号
2. **类型注解**：TypeScript/Python 类型直接告诉 AI 数据形状
3. **骨架策略**：先写签名和注释，让 AI 填充实现
4. **审查习惯**：每次接受补全前检查逻辑、安全、边界情况
5. **人机协作**：你负责思考和决策，AI 负责加速实现
