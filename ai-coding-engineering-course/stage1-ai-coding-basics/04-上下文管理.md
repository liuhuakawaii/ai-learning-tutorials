# 04 - 上下文管理

> **课程定位**：理解 AI 的"记忆"机制，学会高效传递上下文以获得精准回答。
>
> **前置要求**：掌握 Chat 模式的基本用法（03 课）
>
> **预计时长**：1.5 小时

---

## 场景引入

你让 AI 帮你修复一个类型错误，直接说"这个函数有 bug"，AI 给了一堆泛泛的建议，没有一个能用。你很沮丧，但仔细一想——AI 根本不知道你在说哪个函数。同事的做法是先用 `#file:src/services/payment.ts` 引用文件，再附上错误信息和相关类型定义，AI 一次就定位了问题。AI 的回答质量，80% 取决于你给它的上下文质量。

---

## 学习目标

1. 理解上下文窗口的概念及其对 AI 输出质量的影响
2. 掌握 IDE 工具中的上下文引用机制（#file、@workspace 等）
3. 学会判断何时需要提供额外上下文，何时不需要
4. 掌握 5 种高效的上下文管理策略
5. 能处理超出上下文窗口的大型代码库场景

## 1. 什么是上下文窗口？

```

├──────────────────────────────────────────────────────────────────┤
│                                                                  │

│  │                    上下文窗口 (Context Window)              │  │
│  │                                                            │  │

│  │  │  系统提示      │  │  历史对话      │  │  你的输入      │    │  │
│  │  │  (System)     │  │  (History)    │  │  (User Input) │    │  │
│  │  │              │  │              │  │              │    │  │

│  │  │ • 代码规范    │  │ • AI的回答    │  │ • 引用的文件  │    │  │
│  │  │ • 项目结构    │  │ • 代码片段    │  │ • 代码片段    │    │  │

│  │                                                            │  │
│  │  总容量：4K ~ 200K tokens（取决于模型）                      │  │
│  │                                                            │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
│  1 token ≈ 4 个英文字符 ≈ 1-2 个中文字                            │

│                                                                  │
```

### 1.1 不同模型的上下文窗口

| Gemini 1.5 Pro | 1M tokens | ~2500 页 A4 文档 |
| Copilot（后端） | 8K-32K tokens | ~20-80 页代码 |

## 3. 五种高效的上下文管理策略

### 3.1 策略一：精确引用文件

```markdown
❌ 差：不引用文件
"这个函数有 bug，帮我看看"
→ AI 不知道你在说哪个函数，可能给出泛泛的建议

✅ 好：引用具体文件
"#file:src/services/payment.ts 第 45 行的 processPayment 函数，
   报错 'Cannot read property amount of undefined'"
→ AI 立刻定位问题，给出精准修复
```

### 3.2 策略二：提供相关类型定义

```typescript
// 当你让 AI 生成使用某个类型的代码时，先提供类型定义

// 你说：
// #file:src/types/order.ts 中的 Order 类型如下，
// 请帮我写一个过滤过期订单的函数

// order.ts 内容：
interface Order {
  id: string;
  status: 'pending' | 'paid' | 'shipped' | 'completed' | 'cancelled';
  createdAt: Date;
  expiresAt: Date;
  total: number;
}

// AI 就能精确生成：
function filterExpiredOrders(orders: Order[]): Order[] {
  const now = new Date();
  return orders.filter(order =>
    order.status === 'pending' && order.expiresAt < now
  );
}
```

### 3.3 策略三：分层提供上下文

```
┌──────────────────────────────────────────────────────────────┐
│               分层上下文策略                                    │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Layer 1: 必要上下文（每次都提供）                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ • 直接相关的文件                                        │  │
│  │ • 函数签名和类型定义                                     │  │
│  │ • 错误信息                                              │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  Layer 2: 有用上下文（复杂任务时提供）                          │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ • 相关的工具函数                                        │  │
│  │ • 数据库 Schema                                         │  │
│  │ • API 文档片段                                          │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  Layer 3: 背景上下文（首次对话时提供）                          │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ • 项目技术栈说明                                        │  │
│  │ • 代码规范和约定                                        │  │
│  │ • 整体架构描述                                          │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 3.4 策略四：利用 @workspace / #codebase

```
场景：你不确定需要引用哪个文件

你：@workspace 用户注册的流程是怎么实现的？
   哪些文件涉及注册逻辑？

AI 会：
1. 搜索整个代码库中与"注册"相关的文件
2. 识别路由 → 控制器 → 服务 → 数据库的调用链
3. 给出完整的文件列表和代码流程说明

适用场景：
• 了解项目结构
• 找到相关的代码位置
• 理解跨文件的调用关系
```

## 6. AGENTS.md 的作用

AGENTS.md 是一个放在项目根目录的文件，AI 工具会自动读取它作为项目上下文。

```markdown
# AGENTS.md 示例

## 项目简介
一个在线博客平台的后端 API

## 技术栈
- Runtime: Node.js 20
- Framework: Express 4 + TypeScript
- ORM: Prisma
- Database: PostgreSQL
- Auth: JWT + bcrypt
- Testing: Vitest

## 目录结构
src/
├── routes/       — Express 路由定义
├── services/     — 业务逻辑层
├── middleware/    — Express 中间件
├── types/        — TypeScript 类型定义
└── utils/        — 工具函数

## 代码规范
- 使用 async/await，不用 callback
- 错误处理用自定义 Error 类
- 所有函数必须有 TypeScript 类型
- 测试文件放在同目录下，命名为 *.test.ts

## 常用命令
- npm run dev — 启动开发服务器
- npm test — 运行测试
- npx prisma migrate dev — 运行数据库迁移
```

## 7. 常见误区

| 错误 | 为什么有问题 | 正确做法 |
|------|-------------|----------|
| 不引用文件直接问"这个函数" | AI 不知道你说的是哪个 | 用 #file 或 @file 引用 |
| 一次性引用 20 个文件 | 超出上下文窗口，AI 忽略大部分 | 只引用直接相关的 3-5 个文件 |
| 整个项目复制粘贴到对话 | 浪费 token，效果差 | 用 @workspace 或 AGENTS.md |
| 不提供类型定义 | AI 生成的代码类型不对 | 先引用 types 文件再提问 |
| 长对话不总结 | 早期决策被遗忘 | 每 3-5 轮总结关键信息 |
| 用新对话继续旧任务 | 丢失所有上下文 | 在同一对话中迭代，或总结后带入新对话 |
| 不用 AGENTS.md | 每次都要重复说明项目信息 | 创建 AGENTS.md 一次性配置 |

## 8. 工程建议

1. **为项目创建 AGENTS.md**：在项目根目录放置 AGENTS.md，记录技术栈、目录结构、代码规范和常用命令。这是性价比最高的上下文投资——一次编写，每次对话都自动生效。
2. **引用文件而非粘贴代码**：始终使用 `#file` 或 `@file` 引用文件，而不是复制粘贴代码片段。引用机制会自动注入文件路径和完整内容，AI 能更好地理解代码的上下文关系。
3. **长对话定期总结**：每 3-5 轮对话后，用一句话总结当前进展和关键决策。这能有效对抗上下文窗口的"遗忘"问题，避免 AI 在后续轮次中重复已解决的问题。
4. **大任务拆分为独立对话**：当任务涉及 5 个以上文件或超过 10 轮对话时，主动拆分为多个子任务对话。每个对话聚焦一个子问题，用文件记录中间结果，后续对话通过引用文件衔接。

## 9. 总结

本课要点：

1. **上下文窗口**：AI 的"工作记忆"，容量有限但足够处理大多数任务
2. **引用机制**：#file、@file、@workspace 等语法让你精确传递上下文
3. **分层策略**：必要上下文 → 有用上下文 → 背景上下文，按需提供
4. **溢出处理**：先搜索再引用、提供摘要、使用 AGENTS.md、拆分任务
5. **AGENTS.md**：项目级上下文配置，让 AI 自动了解你的项目

### 练习 1：上下文对比实验（20 分钟）

对同一个任务，用三种不同的上下文方式提问，对比 AI 回答质量：

### 练习 3：创建 AGENTS.md（25 分钟）
