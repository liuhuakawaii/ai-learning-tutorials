# 02 - AI 代码审查流程

> 将 AI 代码审查嵌入团队 CI/CD 流水线，实现自动化、标准化的质量保障

## 学习目标

- 理解 AI 代码审查与传统 code review 的区别与互补
- 掌握 GitHub Actions 自动审查工作流的搭建
- 学会设计审查规则和质量门禁
- 建立 AI 辅助的人工 review 流程

## 1. AI 代码审查概述

### 1.1 审查层次模型

```
┌─────────────────────────────────────────────┐
│            Layer 4: 架构审查（人工）          │
│         设计模式、系统架构、可扩展性           │
├─────────────────────────────────────────────┤
│          Layer 3: 业务逻辑审查（AI+人工）      │
│        业务正确性、边界条件、异常处理          │
├─────────────────────────────────────────────┤
│          Layer 2: 安全与性能审查（AI）         │
│       SQL 注入、XSS、内存泄漏、算法复杂度      │
├─────────────────────────────────────────────┤
│          Layer 1: 风格与规范检查（自动化）      │
│       代码格式、命名规范、注释完整度           │
└─────────────────────────────────────────────┘
```

### 1.2 AI 审查 vs 人工审查

| 维度 | AI 审查 | 人工审查 |
|------|--------|---------|
| 速度 | 秒级完成 | 数小时到数天 |
| 一致性 | 100% 一致 | 受审查者状态影响 |
| 覆盖面 | 可全量扫描 | 通常抽查 |
| 深度理解 | 模式匹配为主 | 真正理解业务 |
| 创造性 | 有限 | 可提出架构优化 |
| 最佳用途 | 规范检查、安全扫描 | 业务逻辑、架构评审 |

## 2. GitHub Actions 自动审查工作流

### 2.1 完整工作流配置

```yaml
# .github/workflows/ai-code-review.yml
name: AI Code Review

on:
  pull_request:
    types: [opened, synchronize]
    branches: [main, develop]

permissions:
  contents: read
  pull-requests: write

jobs:
  ai-review:
    runs-on: ubuntu-latest
    timeout-minutes: 10

    steps:
      - name: Checkout code
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Get changed files
        id: changed-files
        uses: tj-actions/changed-files@v44
        with:
          files: |
            **/*.ts
            **/*.tsx
            **/*.py
            **/*.js

      - name: Static analysis
        if: steps.changed-files.outputs.any_changed == 'true'
        run: |
          echo "Running static analysis on changed files..."
          npx eslint ${{ steps.changed-files.outputs.all_changed_files }} \
            --format json --output-file eslint-report.json || true

      - name: Security scan
        if: steps.changed-files.outputs.any_changed == 'true'
        run: |
          echo "Running security scan..."
          npx semgrep --config auto --json \
            ${{ steps.changed-files.outputs.all_changed_files }} \
            > semgrep-report.json || true

      - name: AI Review
        if: steps.changed-files.outputs.any_changed == 'true'
        uses: ./.github/actions/ai-review
        with:
          files: ${{ steps.changed-files.outputs.all_changed_files }}
          eslint-report: eslint-report.json
          semgrep-report: semgrep-report.json
        env:
          OPENAI_API_KEY: ${{ secrets.AI_REVIEW_API_KEY }}

      - name: Post review comment
        if: steps.changed-files.outputs.any_changed == 'true'
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            const review = fs.readFileSync('ai-review.md', 'utf8');
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: review
            });
```

### 2.2 自定义 AI Review Action

```yaml
# .github/actions/ai-review/action.yml
name: 'AI Code Review'
description: 'AI-powered code review for pull requests'

inputs:
  files:
    description: 'Changed files list'
    required: true
  eslint-report:
    description: 'ESLint report path'
    required: false
  semgrep-report:
    description: 'Semgrep report path'
    required: false

runs:
  using: 'composite'
  steps:
    - name: Run AI review
      shell: bash
      run: |
        node .github/actions/ai-review/review.js \
          --files "${{ inputs.files }}" \
          --eslint "${{ inputs.eslint-report }}" \
          --semgrep "${{ inputs.semgrep-report }}" \
          --output ai-review.md
```

### 2.3 Review 脚本核心逻辑

```javascript
// .github/actions/ai-review/review.js
const fs = require('fs');
const { execSync } = require('child_process');

async function reviewFiles(files, eslintReport, semgrepReport) {
  const results = [];

  for (const file of files.split(' ')) {
    if (!fs.existsSync(file)) continue;

    const content = fs.readFileSync(file, 'utf8');
    const lines = content.split('\n').length;

    // 跳过过大文件（AI token 限制）
    if (lines > 500) {
      results.push({
        file,
        issue: '文件过大，建议拆分后审查',
        severity: 'warning',
      });
      continue;
    }

    const prompt = buildReviewPrompt(file, content, eslintReport, semgrepReport);
    const review = await callAI(prompt);

    results.push({
      file,
      review: parseReview(review),
      severity: classifySeverity(review),
    });
  }

  return generateReport(results);
}

function buildReviewPrompt(filename, content, eslint, semgrep) {
  return `你是一位资深代码审查者。请审查以下代码文件：

**文件**: ${filename}

**ESLint 结果**: ${eslint || '无'}

**安全扫描结果**: ${semgrep || '无'}

**代码**:
\`\`\`
${content}
\`\`\`

请从以下维度审查：
1. 🔴 严重问题（必须修复）
2. 🟡 建议改进（推荐修复）
3. 🟢 代码亮点（值得学习）

输出格式为 Markdown 表格。`;
}
```

## 3. 审查规则设计

### 3.1 多维度审查矩阵

```typescript
interface ReviewRule {
  id: string;
  name: string;
  category: 'security' | 'performance' | 'style' | 'logic' | 'maintainability';
  severity: 'error' | 'warning' | 'info';
  autoFix: boolean;
  aiPrompt: string;
}

const REVIEW_RULES: ReviewRule[] = [
  {
    id: 'SEC-001',
    name: '硬编码密钥检测',
    category: 'security',
    severity: 'error',
    autoFix: false,
    aiPrompt: '检查代码中是否存在硬编码的密钥、密码、Token 或 API Key',
  },
  {
    id: 'PERF-001',
    name: 'N+1 查询检测',
    category: 'performance',
    severity: 'warning',
    autoFix: false,
    aiPrompt: '检查是否存在循环中的数据库查询（N+1 问题）',
  },
  {
    id: 'LOGIC-001',
    name: '边界条件检查',
    category: 'logic',
    severity: 'warning',
    autoFix: false,
    aiPrompt: '检查函数是否处理了空值、零值、负数、超大数组等边界情况',
  },
  {
    id: 'STYLE-001',
    name: '函数长度检查',
    category: 'style',
    severity: 'info',
    autoFix: true,
    aiPrompt: '检查函数是否超过 50 行，建议拆分',
  },
];
```

### 3.2 审查质量门禁

```yaml
# quality-gates.yaml
gates:
  - name: "安全门禁"
    blocking: true
    rules:
      - rule_id: "SEC-001"
        max_violations: 0
      - rule_id: "SEC-002"
        max_violations: 0

  - name: "性能门禁"
    blocking: true
    rules:
      - rule_id: "PERF-001"
        max_violations: 3

  - name: "风格门禁"
    blocking: false
    rules:
      - rule_id: "STYLE-001"
        max_violations: 10

on_failure:
  action: "block_merge"
  notify:
    - "@tech-lead"
    - pr_comment
```

## 4. 人工 Review 流程集成

### 4.1 Review 流程图

```
PR 提交
   │
   ▼
┌──────────────┐     失败
│  CI 自动检查  │──────────▶ 修复后重新提交
└──────┬───────┘
       │ 通过
       ▼
┌──────────────┐     发现问题
│  AI 自动审查  │──────────▶ 添加 Review 评论
└──────┬───────┘
       │ 通过
       ▼
┌──────────────┐     需要修改
│  人工 Review  │──────────▶ 讨论 → 修改 → 重新提交
└──────┬───────┘
       │ 批准
       ▼
┌──────────────┐
│   合并代码    │
└──────────────┘
```

## 6. 常见错误

### ❌ 错误 1：完全依赖 AI 审查结果

```
AI 可能漏报业务逻辑错误，或者误报正常代码。
AI 审查是辅助工具，不能替代人工 review。

正确做法：AI 审查 + 人工 review 双保险
```

### ❌ 错误 2：审查规则过于严格

```yaml
# ❌ 过于严格导致大量误报，开发者直接忽略所有警告
rules:
  max_function_lines: 10  # 太严格
  max_complexity: 3       # 太严格

# ✅ 合理设置
rules:
  max_function_lines: 50
  max_complexity: 10
```

### ❌ 错误 3：审查 Prompt 不够具体

```markdown
# ❌ 太模糊
请审查这段代码

# ✅ 具体明确
请从以下角度审查这段 TypeScript 代码：
1. 是否存在 SQL 注入风险
2. 错误处理是否完整
3. 是否有潜在的内存泄漏
以 Markdown 表格格式输出，包含行号和严重级别。
```

### ❌ 错误 4：不跟踪审查效果

```
问题：配置了 AI 审查但从不检查其效果

解决：定期统计
- AI 审查发现的问题数量
- 人工 review 发现但 AI 遗漏的问题
- AI 误报率
- 审查后线上 bug 变化趋势
```

1. 安全规则（至少 5 条）
2. 性能规则（至少 3 条）
3. 风格规则（至少 3 条）
4. 为每条规则编写 AI 审查 Prompt

### 练习 3：模拟 AI 审查实践（45 分钟）

使用以下代码片段，分别用 AI 和人工进行审查，对比结果：

```python
def transfer_money(from_account, to_account, amount):
    conn = database.connect()
    cursor = conn.cursor()
    cursor.execute(f"SELECT balance FROM accounts WHERE id = {from_account}")
    balance = cursor.fetchone()[0]
    if balance >= amount:
        cursor.execute(f"UPDATE accounts SET balance = balance - {amount} WHERE id = {from_account}")
        cursor.execute(f"UPDATE accounts SET balance = balance + {amount} WHERE id = {to_account}")
        conn.commit()
    return "success"
```
