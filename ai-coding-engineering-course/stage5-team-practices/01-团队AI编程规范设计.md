# 01 - 团队 AI 编程规范设计

> 建立团队统一的 AI 辅助编程标准，让 AI 成为团队的倍增器而非混乱源

## 场景引入

团队接入 AI 编程工具三个月后，问题开始浮现：张三用 Cursor 写的代码风格和李四用 Copilot 生成的完全不同，review 时互相看不懂；王五把公司 API 密钥直接贴进了 Prompt，代码被提交到了公开仓库；更头疼的是，每个人都说自己摸索出了一套"好用的 Prompt"，但这些经验随着人员流动全部丢失。技术负责人意识到，没有统一的 AI 编程规范，AI 工具不仅没有提效，反而在制造新的混乱。

## 学习目标

- 理解为什么团队需要统一的 AI 编程规范
- 掌握 AI 工具选型的方法论
- 学会设计和管理团队 Prompt 库
- 制定适合团队的 AI 编程编码规范

---

## 1. 为什么需要团队 AI 编程规范

### 1.1 无规范的痛点

```
团队成员各自使用不同 AI 工具
          │
          ▼
┌─────────────────────────────────┐
│  · 代码风格不一致               │
│  · Prompt 质量参差不齐          │
│  · 安全风险无人管控             │
│  · 知识无法复用沉淀             │
│  · 效果无法度量对比             │
└─────────────────────────────────┘
          │
          ▼
    AI 反而降低团队效率
```

### 1.2 规范化后的收益

| 维度 | 无规范 | 有规范 |
|------|--------|--------|
| 代码质量 | 风格混乱，review 困难 | 统一标准，自动化检查 |
| 安全性 | 密钥泄露、漏洞引入 | 自动检测，合规保障 |
| 效率 | 重复造轮子 | Prompt 库复用 |
| 知识 | 散落在个人电脑 | 结构化团队资产 |
| 度量 | 凭感觉评估 | 数据驱动决策 |

## 2. AI 工具选型框架

### 2.1 选型决策矩阵

```
                    高定制化
                       │
         ┌─────────────┼─────────────┐
         │   本地模型   │  企业私有化  │
         │  (Ollama)   │  (Azure AI)  │
         │             │              │
 低安全 ─┼─────────────┼─────────────┼─ 高安全
 要求    │   个人开发   │   团队标准   │  要求
         │  (Cursor)   │  (Copilot)  │
         │             │              │
         └─────────────┼─────────────┘
                       │
                    低定制化
```

### 2.2 工具对比表

| 工具 | 适用场景 | 安全性 | 成本 | 定制化 |
|------|---------|--------|------|--------|
| GitHub Copilot | 通用编码 | 中 | $19/月/人 | 低 |
| Cursor | 全栈开发 | 中 | $20/月/人 | 中 |
| Cline + 本地模型 | 高安全要求 | 高 | 硬件成本 | 高 |
| Continue.dev | 混合部署 | 高 | 免费 | 高 |
| 企业私有部署 | 金融/政府 | 最高 | 高 | 最高 |

### 2.3 选型决策流程

```python
def select_ai_tool(team_context: dict) -> str:
    """团队 AI 工具选型决策函数"""

    # 第一步：安全合规要求
    if team_context["data_classification"] == "机密":
        return "本地模型 + 私有部署"

    # 第二步：团队规模与预算
    if team_context["team_size"] < 5 and team_context["budget"] < 500:
        return "Cursor 或 Continue.dev"

    # 第三步：技术栈匹配
    if team_context["primary_language"] == "Python":
        return "GitHub Copilot（Python 优化最佳）"

    # 第四步：已有基础设施
    if team_context["has_github_enterprise"]:
        return "GitHub Copilot Enterprise"

    return "GitHub Copilot Business（默认推荐）"
```

## 4. AI 编码规范制定

### 4.1 代码风格规范

```typescript
// ✅ 正确：AI 生成代码也必须遵循团队 ESLint 规则
// .eslintrc.ai.js - AI 生成代码的额外检查项
module.exports = {
  extends: ['./.eslintrc.js'],
  rules: {
    // AI 常见问题检查
    'no-unused-vars': 'error',
    'no-implicit-any': 'error',
    'max-lines-per-function': ['warn', 50],
    'complexity': ['warn', 10],

    // AI 常见反模式
    'no-eval': 'error',
    'no-implied-eval': 'error',
    'no-new-func': 'error',
  },
};
```

## 6. 常见误区

### ❌ 错误 1：完全放任 AI 生成代码

```typescript
// AI 生成了看似正确但有安全隐患的代码
const query = `SELECT * FROM users WHERE id = ${userId}`;
// SQL 注入风险！必须人工审查并改用参数化查询
```

### ❌ 错误 2：Prompt 库没有版本管理

```
问题：Prompt 被随意修改，导致同一天不同人使用同一 Prompt
却得到完全不同的输出质量

解决：使用 Git 管理 Prompt，每次修改需要 PR review
```

### ❌ 错误 3：忽略团队成员的 AI 技能差异

```
错误做法：一刀切要求所有人使用相同的复杂 Prompt

正确做法：
  - 初级：使用预置 Prompt 模板
  - 中级：能够修改和组合 Prompt
  - 高级：能够创建和优化 Prompt
```

### ❌ 错误 4：不设安全红线

```bash
# 绝对禁止的操作
git commit -m "feat: add API key"  # AI 可能建议直接硬编码
# 必须使用环境变量或密钥管理服务
```

## 7. 工程建议

1. **先试点再推广**：不要一次性全团队铺开 AI 规范，先选 2-3 个志愿者项目跑通流程，收集真实反馈后再推广，避免"规范写了没人用"的尴尬。
2. **Prompt 库用 Git 管理**：把 Prompt 当代码管，每次修改走 PR review，这样既能追溯历史版本，也能让团队在 review Prompt 的过程中互相学习。
3. **安全红线必须自动化**：靠人工记住"不能把密钥提交到仓库"是不可靠的，必须在 CI/CD 中配置 Gitleaks 等工具自动拦截，把安全检查从"靠自觉"变成"靠系统"。
4. **规范文档控制在 10 页以内**：核心规范要精简可读，详细内容放附录或模板中。提供检查清单替代长篇文字，让开发者能在 5 分钟内了解关键要求。
