## 场景引入

你的爬虫在本地跑得好好的，一部署到服务器就开始出问题：有的请求莫名超时，有的返回 403，还有一个页面被爬了两次导致数据重复。你看了一圈代码，Spider 逻辑没问题，Pipeline 也没毛病——问题出在"请求本身"。你需要在请求发出去之前和响应回来之后插入一些通用逻辑：换个 User-Agent、加个代理、失败了自动重试。这就是中间件要解决的问题。

## 一、两种中间件——安检系统的比喻

### 1.1 从全局视角看中间件的位置

Scrapy 有两套中间件系统，分别位于数据流的不同位置。理解它们的位置是理解它们作用的前提。

```
┌─────────────────────────────────────────────────────────────────┐
│                    Scrapy 完整数据流                              │
│                                                                 │
│                        ┌──────────────┐                         │
│                        │   Internet   │                         │
│                        └──────┬───────┘                         │
│                               │                                 │
│                               ▼                                 │
│                  ┌────────────────────────┐                     │
│                  │  Downloader Middleware │  ← 请求发出前拦截     │
│                  │  (下载器中间件)          │  ← 响应返回后拦截     │
│                  └────────────┬───────────┘                     │
│                               │                                 │
│                               ▼                                 │
│                        ┌──────────────┐                         │
│                        │  Downloader  │  ← 真正发送 HTTP 请求    │
│                        │   (下载器)    │                         │
│                        └──────┬───────┘                         │
│                               │                                 │
│                               ▼                                 │
│                  ┌────────────────────────┐                     │
│                  │   Spider Middleware    │  ← 响应到达 Spider   │
│                  │   (爬虫中间件)          │  ← 请求从 Spider 出来│
│                  └────────────┬───────────┘                     │
│                               │                                 │
│                               ▼                                 │
│                        ┌──────────────┐                         │
│                        │    Spider    │  ← 解析数据，产出 Item   │
│                        │   (爬虫)      │                         │
│                        └──────┬───────┘                         │
│                               │                                 │
│                               ▼                                 │
│                        ┌──────────────┐                         │
│                        │   Pipeline   │  ← 处理 Item            │
│                        │   (管道)      │                         │
│                        └──────────────┘                         │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 生活中的类比

想象你要进入一座高档写字楼见客户：

- **Downloader Middleware** 就像大楼门口的保安：你进去之前（Request）他检查你的证件、给你刷卡；你出来之后（Response）他检查你带走了什么。他管的是"进出大楼"这件事。
- **Spider Middleware** 就像客户办公室门口的秘书：保安放你进来了，秘书在你见到客户之前再做一次筛选（比如客户正在开会，让你改天再来）；你和客户聊完出来，秘书帮你整理会议纪要。他管的是"进出办公室"这件事。

两者各管一段，互不干扰，但串联起来就是完整的安保链。

### 1.3 前端开发者类比：Express 中间件链

如果你用过 Express，整个 Scrapy 架构可以这样类比：

```
┌───────────────────────────────────────────────────────────────┐
│            Express vs Scrapy 中间件对比                         │
│                                                               │
│  Express:                                                     │
│  请求 → 中间件1 → 中间件2 → 路由处理 → 中间件2 → 中间件1 → 响应  │
│         (洋葱模型，进出都经过)                                   │
│                                                               │
│  Scrapy:                                                      │
│  Request → Downloader MW → Downloader → Downloader MW →       │
│           Spider MW → Spider → Spider MW → Pipeline           │
│         (分段模型，每段各管各的)                                  │
│                                                               │
│  关键区别：                                                    │
│  Express 是一条链，请求和响应走同一条路                           │
│  Scrapy 是两条链，Downloader MW 和 Spider MW 分开               │
└───────────────────────────────────────────────────────────────┘
```

## 二、Downloader Middleware 详解

### 2.1 两个核心方法

Downloader Middleware 有两个钩子方法，分别拦截请求和响应：

```python
class MyDownloaderMiddleware:
    """自定义下载器中间件"""

    def process_request(self, request, spider):
        """
        请求发出之前调用。
        - 返回 None：继续处理（交给下一个中间件或下载器）
        - 返回 Response：直接返回，不再发请求（缓存场景）
        - 返回 Request：替换当前请求，重新走一遍中间件链
        - 抛出 IgnoreRequest：丢弃这个请求
        """
        spider.logger.debug(f"准备请求: {request.url}")
        return None  # 放行

    def process_response(self, request, response, spider):
        """
        响应返回之后调用。
        - 返回 Response：传递给下一个中间件（朝 Spider 方向）
        - 返回 Request：重新调度这个请求
        - 抛出 IgnoreRequest：丢弃这个响应
        """
        spider.logger.debug(f"收到响应: {response.status} {request.url}")
        return response  # 放行
```

### 2.2 返回值的含义图解

```
┌───────────────────────────────────────────────────────────────┐
│               process_request 返回值                           │
│                                                               │
│  ┌─────────┐                                                  │
│  │ Request  │                                                  │
│  └────┬────┘                                                  │
│       │                                                       │
│       ▼                                                       │
│  process_request()                                            │
│       │                                                       │
│       ├──→ 返回 None      → 继续发送请求 ✅                     │
│       ├──→ 返回 Response  → 直接当作结果，不发请求 ⚡            │
│       ├──→ 返回 Request   → 用新请求替换，重新排队 🔄           │
│       └──→ 抛 IgnoreRequest → 丢弃请求 ❌                      │
│                                                               │
├───────────────────────────────────────────────────────────────┤
│               process_response 返回值                          │
│                                                               │
│  ┌──────────┐                                                 │
│  │ Response  │                                                 │
│  └────┬─────┘                                                 │
│       │                                                       │
│       ▼                                                       │
│  process_response()                                           │
│       │                                                       │
│       ├──→ 返回 Response  → 继续传递给 Spider ✅               │
│       ├──→ 返回 Request   → 重新调度（比如遇到验证码要重试）🔄   │
│       └──→ 抛 IgnoreRequest → 丢弃响应 ❌                      │
└───────────────────────────────────────────────────────────────┘
```

## 三、实战：User-Agent 中间件

### 3.1 为什么要设置 User-Agent

很多网站会根据 `User-Agent` 做统计、限流和问题排查。如果所有请求都使用 Scrapy 默认的 `Scrapy/2.x`，对方很难判断你的采集任务属于哪个产品、团队或联系方式。

更好的做法是设置清晰、稳定、可联系的 User-Agent。学习阶段也可以准备多个 UA 用于兼容性测试，但不应把 UA 轮换当成规避站点规则的手段。

### 3.2 代码实现

```python
class ProjectUserAgentMiddleware:
    """项目级 User-Agent 中间件"""

    USER_AGENT = 'MarketInsightCrawler/1.0 (+mailto:data-team@example.com)'

    def process_request(self, request, spider):
        request.headers['User-Agent'] = self.USER_AGENT
        return None  # 放行
```

在 `settings.py` 中启用：

```python
DOWNLOADER_MIDDLEWARES = {
    # 禁用 Scrapy 默认的 UserAgentMiddleware（优先级 500）
    'scrapy.downloadermiddlewares.useragent.UserAgentMiddleware': None,
    # 启用我们的自定义中间件（优先级 500，替代默认的）
    'myproject.middlewares.ProjectUserAgentMiddleware': 500,
}
```

### 3.3 为什么先禁用默认的

```
┌───────────────────────────────────────────────────────────────┐
│             中间件优先级冲突问题                                 │
│                                                               │
│  ❌ 如果不禁用默认的：                                          │
│                                                               │
│  默认 UserAgentMiddleware (优先级 500)                          │
│       │ 设置 User-Agent = "Scrapy/2.x"                        │
│       ▼                                                       │
│  自定义 ProjectUserAgentMiddleware (优先级 500)                 │
│       │ 设置 User-Agent = "MarketInsightCrawler/1.0"          │
│       ▼                                                       │
│  最终用的是我们的 ✅  （但默认的白跑了）                          │
│                                                               │
│  ✅ 正确做法：禁用默认的，只留自定义的                            │
│                                                               │
│  自定义 ProjectUserAgentMiddleware (优先级 500)                 │
│       │ 设置 User-Agent = "MarketInsightCrawler/1.0"          │
│       ▼                                                       │
│  干净利落，没有多余开销 ✅                                       │
└───────────────────────────────────────────────────────────────┘
```

## 四、实战：授权代理中间件

### 4.1 代理配置的思路

代理不是用来规避站点规则的工具。它适合公司内网出口、测试环境、供应商授权代理或跨区域可用性验证。遇到限流或拒绝访问时，优先做降频、暂停任务、申请授权或改用官方 API。

```
┌───────────────────────────────────────────────────────────────┐
│                   授权代理配置示意图                            │
│                                                               │
│  你的爬虫                                                     │
│    │                                                         │
│    │  请求1 (走代理A)  ──→ 代理服务器A ──→ 目标网站             │
│    │  请求2 (走代理B)  ──→ 代理服务器B ──→ 目标网站             │
│    │  请求3 (走代理C)  ──→ 代理服务器C ──→ 目标网站             │
│    │  请求4 (走代理A)  ──→ 代理服务器A ──→ 目标网站             │
│    │                                                         │
│  代理列表必须来自可控、授权的网络出口                            │
└───────────────────────────────────────────────────────────────┘
```

### 4.2 代码实现

```python
import random

class AuthorizedProxyMiddleware:
    """授权代理中间件"""

    def __init__(self, proxy_list):
        self.proxy_list = proxy_list

    @classmethod
    def from_crawler(cls, crawler):
        """
        Scrapy 推荐的初始化方式。
        从 settings 中读取配置，传给 __init__。
        """
        proxy_list = crawler.settings.getlist('AUTHORIZED_PROXY_LIST', [])
        if not proxy_list:
            raise ValueError("AUTHORIZED_PROXY_LIST 为空，请配置已授权代理列表")
        return cls(proxy_list)

    def process_request(self, request, spider):
        proxy = random.choice(self.proxy_list)
        request.meta['proxy'] = proxy
        spider.logger.debug(f"使用代理 {proxy} 请求 {request.url}")
        return None

    def process_exception(self, request, exception, spider):
        """
        请求发生异常时调用（比如代理不可用）。
        可以在这里切换到另一个已授权代理重试。
        """
        proxy = request.meta.get('proxy')
        spider.logger.warning(f"代理 {proxy} 请求失败: {exception}")

        # 从列表中移除不可用代理（可选）
        if proxy in self.proxy_list:
            self.proxy_list.remove(proxy)

        # 如果还有可用的授权代理，换一个重试
        if self.proxy_list:
            new_proxy = random.choice(self.proxy_list)
            request.meta['proxy'] = new_proxy
            return request  # 返回 Request 会重新调度

        spider.logger.error("所有代理都已失效！")
        return None  # 放弃
```

`settings.py` 配置：

```python
DOWNLOADER_MIDDLEWARES = {
    'myproject.middlewares.ProjectUserAgentMiddleware': 400,
    'myproject.middlewares.AuthorizedProxyMiddleware': 450,
}

# 授权代理列表（来自公司网络、测试环境或正式供应商）
AUTHORIZED_PROXY_LIST = [
    'http://proxy1.example.com:8080',
    'http://proxy2.example.com:8080',
    'http://proxy3.example.com:8080',
]
```

### 4.3 process_exception 方法

这是 Downloader Middleware 的第三个钩子，专门处理请求过程中的异常：

```
┌───────────────────────────────────────────────────────────────┐
│            Downloader Middleware 三个钩子方法                    │
│                                                               │
│  正常流程:                                                     │
│  process_request() → 下载器发请求 → process_response()          │
│                                                               │
│  异常流程:                                                     │
│  process_request() → 下载器发请求 → 失败！→ process_exception()  │
│                                           │                   │
│                                           ├──→ 返回 None      │
│                                           │    （交给下一个     │
│                                           │     中间件处理）    │
│                                           │                   │
│                                           └──→ 返回 Request   │
│                                                （重新调度重试）  │
└───────────────────────────────────────────────────────────────┘
```

## 五、重试中间件配置

### 5.1 Scrapy 内置的 RetryMiddleware

Scrapy 自带了一个重试中间件，遇到特定 HTTP 状态码或超时时会自动重试。你不需要自己写，但需要知道怎么配置：

```python
# settings.py

# 启用重试中间件（默认已启用）
DOWNLOADER_MIDDLEWARES = {
    'scrapy.downloadermiddlewares.retry.RetryMiddleware': 550,
}

# 最大重试次数（默认 2 次）
RETRY_TIMES = 3

# 触发重试的 HTTP 状态码（默认只包含部分状态码）
RETRY_HTTP_CODES = [500, 502, 503, 504, 408, 429]

# 重试的优先级（默认为 -1，表示重试请求优先处理）
RETRY_PRIORITY_ADJUST = -1
```

### 5.2 重试流程图解

```
┌───────────────────────────────────────────────────────────────┐

│                                                               │

│       │                                                       │
│       │  RetryMiddleware 检查:                                 │
```

## 六、Spider Middleware 详解

### 6.1 Spider Middleware 的位置和作用

Spider Middleware 位于 Downloader 和 Spider 之间，处理的是 Spider 的输入（Response）和输出（Request/Item）。

```python
class MySpiderMiddleware:
    """自定义爬虫中间件"""

    def process_spider_input(self, response, spider):
        """
        响应进入 Spider 之前调用。
        适合做全局的响应预处理（比如检查状态码、统一处理异常页面）。
        - 返回 None：继续传递
        - 抛出异常：不传递给 Spider
        """
        if response.status != 200:
            spider.logger.warning(f"非 200 响应: {response.status} {response.url}")
        return None  # 一般都返回 None

    def process_spider_output(self, response, result, spider):
        """
        Spider 处理完响应后，产出的 Request/Item 经过这里。
        result 是一个生成器，产出 Request 或 Item 对象。
        适合做全局的输出过滤或修改。
        """
        for item in result:
            yield item  # 逐个传递

    def process_spider_exception(self, response, exception, spider):
        """
        Spider 处理响应时抛出异常会调用这里。
        - 返回 None：继续让其他中间件处理
        - 返回 iterable：替代原来的输出
        """
        spider.logger.error(f"Spider 处理异常: {exception}")
        return None
```

### 6.2 Spider Middleware vs Downloader Middleware

```
┌───────────────────────────────────────────────────────────────┐
│            Spider MW vs Downloader MW 对比                     │
│                                                               │
│  ┌──────────────────┬────────────────────────────────────┐    │
│  │                  │  Downloader MW      Spider MW      │    │
│  ├──────────────────┼────────────────────────────────────┤    │
│  │ 拦截对象          │  Request / Response  Response /    │    │
│  │                  │                      Item / Request│    │
│  ├──────────────────┼────────────────────────────────────┤    │
│  │ 典型用途          │  设UA、授权代理、     全局响应检查、 │    │
│  │                  │  处理Cookie、重试     输出过滤       │    │
│  ├──────────────────┼────────────────────────────────────┤    │
│  │ 配置位置          │  DOWNLOADER_         SPIDER_       │    │
│  │                  │  MIDDLEWARES         MIDDLEWARES    │    │
│  ├──────────────────┼────────────────────────────────────┤    │
│  │ 使用频率          │  ⭐⭐⭐⭐⭐ 高        ⭐⭐ 低        │    │
│  ├──────────────────┼────────────────────────────────────┤    │
│  │ 前端类比          │  axios 拦截器        Vue 路由守卫   │    │
│  │                  │  (请求/响应)         (进入/离开页面) │    │
│  └──────────────────┴────────────────────────────────────┘    │
│                                                               │
│  日常开发中，Downloader MW 用得最多（请求治理）                   │
│  Spider MW 用得较少，主要处理特殊逻辑                            │
└───────────────────────────────────────────────────────────────┘
```

### 6.3 一个实用的 Spider Middleware 示例

```python
class FilterDuplicateResponseMiddleware:
    """
    过滤重复响应的 Spider Middleware。
    如果同一个 URL 返回了相同的内容，直接跳过。
    （某些网站会返回"假页面"，内容一样但状态码是 200）
    """
    def __init__(self):
        self.seen_responses = {}

    def process_spider_input(self, response, spider):
        # 计算响应内容的简单哈希（实际项目可用 hashlib）
        content_hash = hash(response.text[:500])  # 只取前 500 字符做快速判断
        url = response.url

        if url in self.seen_responses:
            if self.seen_responses[url] == content_hash:
                spider.logger.warning(f"检测到重复响应: {url}")
                # 注意：这里不能直接跳过，因为 process_spider_input
                # 返回 None 表示继续传递。要跳过需要在 Spider 层处理。

        self.seen_responses[url] = content_hash
        return None
```

## 七、请求去重机制

### 7.1 Scrapy 如何判断两个请求是"重复"的

Scrapy 会对每个 Request 计算一个**指纹（fingerprint）**，通过指纹来判断是否重复。

```
┌───────────────────────────────────────────────────────────────┐
│                  Request 指纹生成过程                           │
│                                                               │
│  Request(url='http://example.com/page1',                      │
│          method='GET',                                         │
│          body=b'',                                             │
│          headers={})                                           │
│         │                                                     │
│         ▼                                                     │
│  ┌─────────────────────────────────────────────┐              │
│  │  指纹计算内容（默认）：                        │              │
│  │  - HTTP 方法 (GET/POST)                      │              │
│  │  - URL（排序后的）                             │              │
│  │  - 请求体 (body)                              │              │
│  │  - 请求头（可选）                              │              │
│  └─────────────────────────────────────────────┘              │
│         │                                                     │
│         ▼                                                     │
│  hashlib.sha1(拼接后的字符串)                                  │
│         │                                                     │
│         ▼                                                     │
│  指纹: '3a7bd3e2f1c8...'  （40 位十六进制字符串）               │
│                                                               │
│  两个 Request 的指纹相同 → 视为重复，第二个被丢弃                 │
└───────────────────────────────────────────────────────────────┘
```

### 7.2 RFPDupeFilter——去重过滤器

Scrapy 内置了 `RFPDupeFilter`（Request Fingerprint DupeFilter）来实现去重：

```python
# 这是 Scrapy 源码的简化版，帮你理解去重原理

class RFPDupeFilter:
    """基于请求指纹的去重过滤器"""

    def __init__(self):
        self.fingerprints = set()  # 存储所有已见过的指纹

    def request_seen(self, request):
        """判断请求是否已经出现过"""
        fp = self.request_fingerprint(request)  # 计算指纹
        if fp in self.fingerprints:
            return True   # 见过了，是重复的
        self.fingerprints.add(fp)
        return False      # 没见过，是新的

    def request_fingerprint(self, request):
        """计算请求的指纹"""
        # 默认只用 method + url + body 计算
        return sha1(f"{request.method}{request.url}{request.body}")
```

去重开关在 `settings.py` 中：

```python
# 是否启用去重（默认 True）

# 如果想禁用去重（不推荐）
# DUPEFILTER_CLASS = 'scrapy.dupefilters.BaseDupeFilter'
```

## 八、自定义去重规则

### 8.1 为什么默认去重不够用

默认的去重只看 method + url + body，但有些场景需要更复杂的规则：

- 同一个商品页，翻页参数不同但内容相同
- URL 带有时间戳参数，每次都不一样但页面内容一样
- 需要对 POST 请求的某些参数忽略

### 8.2 自定义去重过滤器

```python
import hashlib
from scrapy.dupefilters import BaseDupeFilter
from scrapy.utils.request import fingerprint

class CustomDupeFilter(BaseDupeFilter):
    """自定义去重过滤器——忽略 URL 中的时间戳参数"""

    def __init__(self):
        self.fingerprints = set()

    @classmethod
    def from_settings(cls, settings):
        return cls()

    def request_seen(self, request):
        # 获取"干净"的 URL（去掉时间戳参数）
        clean_url = self._remove_timestamp(request.url)

        # 用干净的 URL 重新构造指纹
        # 方法：把 request 的 url 替换掉再算指纹
        from scrapy.http import Request
        clean_request = Request(
            url=clean_url,
            method=request.method,
            body=request.body,
        )
        fp = fingerprint(clean_request)

        if fp in self.fingerprints:
            return True
        self.fingerprints.add(fp)
        return False

    def _remove_timestamp(self, url):
        """从 URL 中移除时间戳参数"""
        from urllib.parse import urlparse, parse_qs, urlencode, urlunparse
        parsed = urlparse(url)
        params = parse_qs(parsed.query)

        # 移除常见的时间戳参数
        for ts_param in ['_t', 'timestamp', 't', 'time']:
            params.pop(ts_param, None)

        # 重新拼接 URL
        clean_query = urlencode(params, doseq=True)
        clean = parsed._replace(query=clean_query)
        return urlunparse(clean)

    def close(self, reason):
        """爬虫结束时调用"""
        self.fingerprints.clear()
```

在 `settings.py` 中使用：

```python
# 使用自定义去重过滤器
DUPEFILTER_CLASS = 'myproject.middlewares.CustomDupeFilter'
```

## 九、完整实战：授权代理中间件

让我们把前面学到的知识串起来，构建一个功能完整的授权代理中间件。它只处理网络出口配置和可用性问题，不把代理作为规避站点规则的手段：

```python
import random
import json
import os
import logging

logger = logging.getLogger(__name__)


class AuthorizedProxyMiddleware:
    """
    授权代理中间件。
    支持从配置文件加载已授权代理、剔除不可用代理、网络异常重试。
    """

    def __init__(self, proxy_list, max_failures=3):
        # 授权代理池：{proxy_url: fail_count}
        self.proxy_pool = {proxy: 0 for proxy in proxy_list}
        self.max_failures = max_failures  # 最大失败次数，超过则剔除

    @classmethod
    def from_crawler(cls, crawler):
        """从 Scrapy 配置中读取授权代理列表"""
        # 优先从 settings 读取
        proxy_list = crawler.settings.getlist('AUTHORIZED_PROXY_LIST', [])

        # 如果 settings 没配，尝试从文件读取
        if not proxy_list:
            proxy_file = crawler.settings.get('AUTHORIZED_PROXY_FILE', 'proxies.json')
            if os.path.exists(proxy_file):
                with open(proxy_file, 'r', encoding='utf-8') as f:
                    proxy_list = json.load(f)

        max_failures = crawler.settings.getint('AUTHORIZED_PROXY_MAX_FAILURES', 3)
        return cls(proxy_list, max_failures)

    def process_request(self, request, spider):
        """给请求分配已授权代理"""
        # 如果请求已经手动指定了代理，不覆盖
        if 'proxy' in request.meta:
            return None

        proxy = self._get_random_proxy()
        if proxy:
            request.meta['proxy'] = proxy
            logger.debug(f"[代理] {request.url} → {proxy}")
        else:
            logger.warning("[代理] 未配置可用授权代理，使用直连")

        return None

    def process_response(self, request, response, spider):
        """检查响应，区分代理故障和目标站点拒绝访问"""
        proxy = request.meta.get('proxy')

        # 407 表示代理认证失败，可以标记代理不可用
        if response.status == 407 and proxy:
            self._mark_proxy_failed(proxy)
            logger.warning(f"[代理] {proxy} 认证失败 (HTTP 407)，请检查授权配置")
            return response

        # 403/429 通常表示目标站点拒绝访问或限流，不应换代理继续请求
        if response.status in (403, 429):
            logger.warning(
                f"[访问控制] {request.url} 返回 HTTP {response.status}，"
                "请降低频率、暂停任务或申请授权"
            )
            return response

        return response

    def process_exception(self, request, exception, spider):
        """请求异常时标记代理失败"""
        proxy = request.meta.get('proxy')
        if proxy:
            self._mark_proxy_failed(proxy)
            logger.warning(f"[代理] {proxy} 请求异常: {exception}")

            # 只有网络异常才切换到其他已授权代理重试
            if self._has_available_proxies():
                return request  # 重新调度

        return None  # 放弃

    def _get_random_proxy(self):
        """随机获取一个可用代理"""
        available = [p for p, fails in self.proxy_pool.items() if fails < self.max_failures]
        return random.choice(available) if available else None

    def _mark_proxy_failed(self, proxy):
        """标记代理失败一次"""
        if proxy in self.proxy_pool:
            self.proxy_pool[proxy] += 1
            if self.proxy_pool[proxy] >= self.max_failures:
                logger.error(f"[代理] {proxy} 失败次数过多，已从代理池剔除")

    def _has_available_proxies(self):
        """检查是否还有可用代理"""
        return any(f < self.max_failures for f in self.proxy_pool.values())
```

## 十、中间件执行顺序总结

### 10.1 Downloader Middleware 执行顺序

```
┌───────────────────────────────────────────────────────────────┐
│           Downloader Middleware 执行顺序                       │
│                                                               │
│  Request 阶段（数字从小到大）:                                  │
│                                                               │
│  process_request(400) → process_request(450) →               │
│  process_request(500) → process_request(550) →               │
│  下载器发请求                                                  │
│                                                               │
│  Response 阶段（数字从大到小，反向）:                            │
│                                                               │
│  下载器收到响应 → process_response(550) →                      │
│  process_response(500) → process_response(450) →             │
│  process_response(400)                                        │
│                                                               │
│  ┌──────────────────────────────────────────┐                 │
│  │ 规律：                                   │                 │
│  │ Request: 小数字 → 大数字（像排队）         │                 │
│  │ Response: 大数字 → 小数字（像栈，后进先出） │                 │
│  └──────────────────────────────────────────┘                 │
│                                                               │
│  这和 Express 的洋葱模型一模一样！                               │
│  进去: middleware1 → middleware2 → 下载器                       │
│  出来: 下载器 → middleware2 → middleware1                       │
└───────────────────────────────────────────────────────────────┘
```

### 10.2 Spider Middleware 执行顺序

```
┌───────────────────────────────────────────────────────────────┐
│           Spider Middleware 执行顺序                           │
│                                                               │
│  响应进入 Spider 阶段（数字从小到大）:                           │
│  process_spider_input(100) → process_spider_input(200) →     │
│  Spider 处理                                                  │
│                                                               │
│  Spider 产出阶段（数字从大到小，反向）:                          │
│  Spider 产出 → process_spider_output(200) →                   │
│  process_spider_output(100)                                   │
│                                                               │
│  和 Downloader MW 一样，遵循"洋葱模型"                          │
└───────────────────────────────────────────────────────────────┘
```

## 常见误区

- **自定义中间件后忘记禁用默认中间件**：比如你写了 `ProjectUserAgentMiddleware`，但没把 Scrapy 默认的 `UserAgentMiddleware` 设为 `None`，结果两个都在跑，你的 UA 被默认的覆盖了。
- **把 Spider Middleware 当 Downloader Middleware 用**：两者的拦截对象和钩子方法完全不同。Downloader MW 管请求/响应（用得最多），Spider MW 管 Spider 的输入/输出（用得少）。别搞混了配置项——`DOWNLOADER_MIDDLEWARES` 和 `SPIDER_MIDDLEWARES` 是两个不同的字典。
- **在中间件里做耗时操作而不考虑并发影响**：中间件的 `process_request()` 是同步阻塞的，如果你在里面 `time.sleep(10)`，整个下载器都会被卡住。429 重试的等待应该交给专门的重试机制，而不是在中间件里硬等。
- **过度依赖 `dont_filter=True`**：对登录接口等特殊请求可以跳过去重，但如果对所有请求都设置 `dont_filter=True`，去重机制形同虚设，大量重复请求会浪费带宽。

---

## 工程建议

- **中间件优先级要拉开梯度**：不要所有自定义中间件都用 500。建议 UA 中间件用 400，代理用 450，重试用 550，中间留出空间方便后续插入新中间件。
- **代理池要有健康检查机制**：不要只是随机选代理。像实战示例那样记录每个代理的失败次数，超过阈值自动剔除，避免反复用一个已经挂掉的代理。
- **开发调试时开启 `DUPEFILTER_DEBUG = True`**：日志会显示哪些请求被去重过滤了，帮你排查"为什么某个 URL 没被爬取"的问题。
- **自定义去重要谨慎**：只在业务确实需要时才覆盖默认的 `RFPDupeFilter`。默认基于 method + url + body 的去重已经覆盖了 99% 的场景。

## 小结

本课的核心知识点：

1. **Scrapy 有两套中间件**：Downloader Middleware 管请求/响应，Spider Middleware 管 Spider 的输入/输出
2. **Downloader Middleware 最常用**，三个钩子：`process_request()`、`process_response()`、`process_exception()`
3. **User-Agent 设置、授权代理配置和异常重试**通过 Downloader Middleware 实现，是请求治理的基本手段
4. **优先级数字越小越先执行**，Request 阶段正序，Response 阶段反序（洋葱模型）
5. **内置 RetryMiddleware** 可自动重试失败请求，通过 `RETRY_TIMES` 和 `RETRY_HTTP_CODES` 配置
6. **Scrapy 通过 Request 指纹去重**，默认用 method + url + body 计算 SHA1 指纹
7. **RFPDupeFilter** 是默认的去重过滤器，可通过 `DUPEFILTER_CLASS` 替换为自定义实现
8. **`dont_filter=True`** 可对单个请求跳过去重
9. **中间件要先禁用同功能的默认中间件**，否则会出现优先级冲突或功能重复
