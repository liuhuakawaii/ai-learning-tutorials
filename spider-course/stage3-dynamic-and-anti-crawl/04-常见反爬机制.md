## 一、为什么网站要阻止爬虫？

### 1.1 先搞清楚"敌人"是谁

在你学爬虫之前，先站在网站的角度想一想：如果你是网站运营者，你会欢迎来路不明的程序疯狂抓取你的数据吗？

```
┌──────────────────────────────────────────────────────────┐
│  网站反爬的三大动机                                        │
│                                                          │
│  ┌──────────────┐                                        │
│  │  保护服务器   │  爬虫疯狂请求 → 服务器过载 → 真人用户打不开│
│  └──────────────┘                                        │
│  ┌──────────────┐                                        │
│  │  保护数据     │  竞争对手批量抓取 → 内容被搬运 → 商业价值流失│
│  └──────────────┘                                        │
│  ┌──────────────┐                                        │
│  │  保护用户     │  恶意爬虫抓取用户信息 → 隐私泄露风险      │
│  └──────────────┘                                        │
└──────────────────────────────────────────────────────────┘
```

**生活类比：** 想象一个商场。正常顾客（浏览器用户）走进去逛逛、买东西，商场很欢迎。但如果有一群机器人（爬虫）每秒钟冲进来 100 个，把货架上的商品全部拍照记录然后冲出去——商场肯定要装安检门（反爬机制）来拦住它们。

## 二、User-Agent 检测

### 2.1 什么是 User-Agent？

User-Agent（简称 UA）是 HTTP 请求头中的一个字段，用来告诉服务器"我是谁"。浏览器发请求时会自动带上这个字段，而 Python 的 requests 库默认带的是 `python-requests/x.x.x`。

```
┌──────────────────────────────────────────────────────────┐
│  不同客户端的 User-Agent 示例                              │
│                                                          │
│  Chrome 浏览器：                                          │
│  Mozilla/5.0 (Windows NT 10.0; Win64; x64)               │
│  AppleWebKit/537.36 (KHTML, like Gecko)                  │
│  Chrome/120.0.0.0 Safari/537.36                          │
│                                                          │
│  Python requests（默认）：                                 │
│  python-requests/2.31.0                                   │
│                                                          │
│  curl 命令行：                                            │
│  curl/7.64.1                                              │
│                                                          │
│  差别一目了然——服务器一眼就能认出谁是脚本！                 │
└──────────────────────────────────────────────────────────┘
```

### 2.2 网站怎么检测 User-Agent？

原理非常简单：服务器读取请求头中的 `User-Agent` 字段，如果发现是已知的爬虫库标识，直接拒绝。

```python
# 模拟服务器端的检测逻辑（伪代码）
user_agent = request.headers.get("User-Agent", "")

# 黑名单匹配
blocked_keywords = ["python-requests", "scrapy", "curl", "wget", "bot"]
for keyword in blocked_keywords:
    if keyword in user_agent.lower():
        return "403 Forbidden"  # 直接拒绝

# 白名单匹配（更严格的方式）
allowed_keywords = ["Mozilla", "Chrome", "Safari", "Firefox"]
if not any(kw in user_agent for kw in allowed_keywords):
    return "403 Forbidden"
```

### 2.3 被检测到的表现

```python
import requests

# ❌ 不加 User-Agent，直接被拦
response = requests.get("https://example.com")
print(response.status_code)   # 403 Forbidden
print(response.text)          # 可能返回 "Access Denied" 页面

# ✅ 伪装成浏览器
headers = {
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) "
                  "AppleWebKit/537.36 (KHTML, like Gecko) "
                  "Chrome/120.0.0.0 Safari/537.36"
}
response = requests.get("https://example.com", headers=headers)
print(response.status_code)   # 200 OK
```

**生活类比：** User-Agent 就像进小区时门卫问你"你是哪栋的？"。你说"我是 Python 脚本"，门卫直接拦住；你说"我是 3 号楼的住户"，门卫就让你进去了。

## 三、速率限制（Rate Limiting）

### 3.1 什么是速率限制？

网站会监控每个 IP 或每个用户在单位时间内的请求次数。如果超过阈值，就触发限制。

```
┌──────────────────────────────────────────────────────────┐
│  速率限制的工作原理                                        │
│                                                          │
│  时间线（1分钟）：                                         │
│                                                          │
│  0s    10s    20s    30s    40s    50s    60s             │
│  ├───┼───┼───┼───┼───┼───┼───┤                           │
│  │ req │ req │ req │ req │ req │ ...  每2秒一个请求        │
│                                                          │
│  服务器计数器：                                            │
│  ┌────────────────────────────────┐                      │
│  │  IP: 192.168.1.100             │                      │
│  │  请求数: 30 次/分钟             │                      │
│  │  阈值: 20 次/分钟               │                      │
│  │  状态: ⚠️ 已触发限制            │                      │
│  └────────────────────────────────┘                      │
│                                                          │
│  触发后的表现：                                            │
│  • 返回 429 Too Many Requests                            │
│  • 或返回 503 Service Unavailable                        │
│  • 或返回特殊页面（如"请稍后再试"）                        │
│  • 严重的直接封禁你的 IP 一段时间                          │
└──────────────────────────────────────────────────────────┘
```

### 3.2 常见的速率限制状态码

```python
import requests

response = requests.get("https://example.com/api/data")

if response.status_code == 429:
    # 429 Too Many Requests —— 最常见的速率限制响应
    print("请求太频繁了，稍后再试")

    # 有些网站会在响应头里告诉你等多久
    retry_after = response.headers.get("Retry-After")
    if retry_after:
        print(f"请等待 {retry_after} 秒后再试")

elif response.status_code == 503:
    # 503 Service Unavailable —— 服务器"假装"过载
    print("服务不可用（可能是反爬伪装）")

elif response.status_code == 200 and "验证码" in response.text:
    # 有些网站不返回错误码，而是返回一个验证页面
    print("页面被替换成了验证码")
```

### 3.3 爬虫为什么容易触发？

```
正常用户 vs 爬虫的行为对比：

┌─────────────────┬────────────────────┬────────────────────┐
│  对比维度        │  正常用户            │  爬虫程序            │
├─────────────────┼────────────────────┼────────────────────┤
│  请求频率        │  1-2 次/分钟        │  10-100 次/秒       │
│  请求间隔        │  不规律，有长有短    │  固定间隔，非常规律  │
│  访问路径        │  首页→列表→详情     │  直接跳到详情页      │
│  访问时间        │  白天为主           │  凌晨也在疯狂爬      │
│  页面停留        │  有阅读时间         │  0 秒就跳走          │
└─────────────────┴────────────────────┴────────────────────┘
```

## 四、IP 封禁

### 4.1 IP 是什么？为什么能用来封禁？

每个网络请求都携带发送方的 IP 地址，就像每封信都有寄件人地址。网站可以通过 IP 来识别和封禁"可疑分子"。

```
┌──────────────────────────────────────────────────────────┐
│  IP 封禁的层级                                            │
│                                                          │
│  轻度封禁：                                                │
│  ┌──────────────────────────────────────┐                │
│  │  IP: 203.0.113.50                    │                │
│  │  封禁时长: 10 分钟                    │                │
│  │  原因: 请求频率过高                    │                │
│  └──────────────────────────────────────┘                │
│                                                          │
│  中度封禁：                                                │
│  ┌──────────────────────────────────────┐                │
│  │  IP: 203.0.113.50                    │                │
│  │  封禁时长: 24 小时                    │                │
│  │  原因: 多次触发速率限制                │                │
│  └──────────────────────────────────────┘                │
│                                                          │
│  重度封禁：                                                │
│  ┌──────────────────────────────────────┐                │
│  │  IP 段: 203.0.113.0/24               │                │
│  │  封禁时长: 永久                       │                │
│  │  原因: 恶意爬取/攻击行为               │                │
│  └──────────────────────────────────────┘                │
│  （连带同网段的其他用户也遭殃）                            │
└──────────────────────────────────────────────────────────┘
```

### 4.2 单 IP 的困境

```python
# ❌ 用同一个 IP 疯狂请求
import requests

for page in range(1, 1000):
    response = requests.get(f"https://example.com/data?page={page}")
    # 前 50 页正常
    # 第 51 页开始返回 403 或 429
    # 你的 IP 被封了！
```

**生活类比：** IP 限制就像小区门禁系统。如果你每天从同一个门进出 100 次，保安（服务器）就会怀疑你，然后限制通行。正确做法不是想办法绕门禁，而是减少不必要访问、控制频率，或者在有授权的场景下使用合规的访问方式。

### 4.3 如何判断自己被 IP 封禁了？

```python
import requests

response = requests.get("https://example.com")

# 判断是否被封禁的几种信号
if response.status_code == 403:
    print("可能被封了（403 Forbidden）")
elif response.status_code == 429:
    print("请求太频繁（429 Too Many Requests）")
elif response.status_code == 200 and len(response.text) < 100:
    # 返回了极少内容，可能是空页面或错误提示
    print("内容异常，可能触发了反爬")
elif "captcha" in response.text.lower() or "验证" in response.text:
    print("被要求做验证码了")

# 换个网络环境（比如手机热点）再试
# 如果换了网络就正常了，基本确认是 IP 被封
```

## 五、Cookie / Session 检测

### 5.1 什么是 Cookie/Session 检测？

有些网站不只看你的请求头，还看你的 Cookie。没有合法的 Cookie 或 Session，服务器就认为你是"未经许可"的访问。

```
┌──────────────────────────────────────────────────────────┐
│  Cookie/Session 检测流程                                  │
│                                                          │
│  正常浏览器用户：                                          │
│  ① 访问首页 → 服务器返回 Set-Cookie: token=abc123         │
│  ② 浏览器自动保存 Cookie                                  │
│  ③ 访问详情页 → 自动带上 Cookie: token=abc123             │
│  ④ 服务器验证 token 有效 → 返回正常内容                    │
│                                                          │
│  爬虫（不处理 Cookie）：                                   │
│  ① 访问首页 → 服务器返回 Set-Cookie: token=abc123         │
│  ② 爬虫忽略了这个 Cookie                                  │
│  ③ 访问详情页 → 没带 Cookie                               │
│  ④ 服务器发现没有 token → 返回 403 或跳转到登录页          │
└──────────────────────────────────────────────────────────┘
```

### 5.2 常见的 Cookie 检测场景

```python
import requests

# 场景一：必须先访问首页获取 Cookie
session = requests.Session()

# ❌ 直接访问目标页面（没有 Cookie）
response = session.get("https://example.com/detail/123")
print(response.status_code)  # 403

# ✅ 先访问首页，让 Session 自动保存 Cookie
session.get("https://example.com/")  # 这一步会拿到 Cookie
response = session.get("https://example.com/detail/123")
print(response.status_code)  # 200

# 场景二：Cookie 中包含反爬 token
# 有些网站会在 Cookie 中加入一个经过 JavaScript 计算的 token
# 你必须先执行 JS 得到这个 token，才能正常请求
# 这类网站需要 Playwright 来处理（后续课程会讲）
```

### 5.3 "二次验证"型反爬

```
┌──────────────────────────────────────────────────────────┐
│  二次验证型反爬                                            │
│                                                          │
│  第一次请求（首页）：                                      │
│  服务器返回：                                              │
│    HTML + JavaScript（会计算一个签名）                      │
│    Set-Cookie: __cfduid=xxx（Cloudflare 标识）             │
│                                                          │
│  JavaScript 执行后：                                      │
│    计算签名 → 写入 Cookie: __cf_clearance=yyy             │
│                                                          │
│  第二次请求（带上新 Cookie）：                              │
│    Cookie: __cf_clearance=yyy                             │
│    → 服务器验证签名正确 → 返回正常页面                      │
│                                                          │
│  爬虫如果不执行 JavaScript，就拿不到 __cf_clearance        │
│  → 永远被拦截在"等待页面"                                   │
└──────────────────────────────────────────────────────────┘
```

**生活类比：** Cookie 检测就像进办公楼。你先在前台登记（访问首页），拿到访客卡（Cookie）。之后每过一道门禁都要刷访客卡。如果你没拿卡就往里走，保安会拦住你。

## 六、JavaScript 挑战页面

### 6.1 什么是 JS 挑战？

有些网站在你第一次访问时，不直接返回正常页面，而是返回一个特殊的"挑战页面"。这个页面包含一段 JavaScript 代码，浏览器会自动执行它，执行完成后才能看到真正的内容。

```
┌──────────────────────────────────────────────────────────┐
│  JS 挑战页面的工作流程                                     │
│                                                          │
│  ① 你请求 https://example.com                             │
│     ──────────────────────────→                           │
│                                                          │
│  ② 服务器返回一个"等待页面"（不是真正的内容）               │
│     ←──────────────────────────                           │
│     <html>                                                │
│       <body>                                              │
│         <div>正在验证您的浏览器...</div>                    │
│         <script>                                          │
│           // 复杂的 JS 计算                                │
│           var answer = complexCalculation();              │
│           // 把结果写入 Cookie 或提交给服务器               │
│           document.cookie = "token=" + answer;           │
│           // 跳转到真正的页面                              │
│           location.href = "/real-page";                   │
│         </script>                                         │
│       </body>                                             │
│     </html>                                               │
│                                                          │
│  ③ 浏览器执行 JS → 得到 token → 自动跳转                  │
│     ──────────────────────────→                           │
│                                                          │
│  ④ 服务器验证 token → 返回真正的页面                       │
│     ←──────────────────────────                           │
└──────────────────────────────────────────────────────────┘
```

### 6.2 为什么 requests 处理不了？

```python
import requests

# requests 只能获取 HTML 源码，不能执行 JavaScript
response = requests.get("https://example.com")

# 你拿到的是"挑战页面"的 HTML，不是真正的内容
print(response.text)
# 输出：<html><body>正在验证...</body></html>
# JS 代码只是文本，不会被执行！
# → 你永远拿不到真正的页面内容
```

```
┌──────────────────────────────────────────────────────────┐
│  requests vs 浏览器的本质区别                              │
│                                                          │
│  requests（无头 HTTP 客户端）：                             │
│  发请求 → 拿 HTML → 结束                                  │
│  （不会执行 JS、不会渲染 CSS、不会加载图片）                │
│                                                          │
│  浏览器（完整的渲染引擎）：                                │
│  发请求 → 拿 HTML → 执行 JS → 渲染 CSS → 加载资源 →       │
│  触发事件 → 再发 AJAX 请求 → 最终展示页面                  │
│                                                          │
│  JS 挑战网站利用的就是这个差异：                            │
│  只有"完整的浏览器"才能通过挑战                             │
└──────────────────────────────────────────────────────────┘
```

### 6.3 哪些网站在用 JS 挑战？

常见的 JS 挑战服务提供商：

```
┌────────────────┬─────────────────────────────────────────┐
│  服务商         │  常见场景                                │
├────────────────┼─────────────────────────────────────────┤
│  Cloudflare    │  "Checking your browser..." 页面         │
│  Akamai        │  电商网站（如 Nike、Adidas）              │
│  PerimeterX    │  票务网站、限量商品网站                    │
│  DataDome      │  社交媒体、分类信息网站                    │
│  阿里云 WAF    │  国内很多中小网站                         │
│  腾讯云 WAF    │  国内很多中小网站                         │
└────────────────┴─────────────────────────────────────────┘
```

**生活类比：** JS 挑战就像某些场所的"安检门"。你不能直接走进去，必须先通过安检（执行 JS），安检通过了才会放行。普通爬虫就像一个不会说话的人，无法回应安检员的提问。

## 七、蜜罐陷阱（Honeypot）

### 7.1 什么是蜜罐？

蜜罐是一种"诱捕"手段：在页面上放置一些人类看不到、但爬虫可能会访问的隐藏链接。如果有人访问了这些链接，就说明它是爬虫。

```
┌──────────────────────────────────────────────────────────┐
│  蜜罐陷阱原理                                             │
│                                                          │
│  页面 HTML 中可能有这样的隐藏元素：                         │
│                                                          │
│  方式一：CSS 隐藏                                         │
│  <a href="/trap" style="display:none">点击这里</a>        │
│  → 浏览器中看不到，但 HTML 源码里有                        │
│                                                          │
│  方式二：颜色伪装                                         │
│  <a href="/trap" style="color: white;                    │
│         background: white">隐藏链接</a>                   │
│  → 和背景色一样，肉眼看不出来                              │
│                                                          │
│  方式三：位置偏移                                         │
│  <a href="/trap" style="position: absolute;              │
│         left: -9999px">隐藏链接</a>                       │
│  → 被移到屏幕外面，看不见                                  │
│                                                          │
│  方式四：robots.txt 中声明禁止访问                         │
│  Disallow: /trap                                         │
│  → 规矩的爬虫会遵守，但不规矩的不会                        │
└──────────────────────────────────────────────────────────┘
```

### 7.2 爬虫是怎么中招的？

```python
from bs4 import BeautifulSoup

html = """
<div class="product-list">
    <a href="/product/1">商品1</a>
    <a href="/product/2">商品2</a>
    <a href="/trap" style="display:none">更多商品</a>  <!-- 蜜罐！ -->
</div>
"""

soup = BeautifulSoup(html, 'html.parser')

# ❌ 粗心的爬虫：提取所有链接，包括隐藏的
all_links = soup.select('a')
for link in all_links:
    print(link['href'])
# /product/1
# /product/2
# /trap        ← 中招了！访问了蜜罐链接

# ✅ 谨慎的爬虫：检查元素是否可见
import re

for link in all_links:
    style = link.get('style', '')
    # 检查是否有隐藏样式
    if 'display:none' in style.replace(' ', ''):
        print(f"跳过隐藏链接: {link['href']}")
        continue
    if re.search(r'left:\s*-9999', style):
        print(f"跳过偏移链接: {link['href']}")
        continue
    print(f"正常链接: {link['href']}")
```

### 7.3 蜜罐的危害

```
┌──────────────────────────────────────────────────────────┐
│  踩中蜜罐的后果                                           │
│                                                          │
│  轻的：                                                    │
│  • 你的 IP 被标记为"可疑"                                  │
│  • 后续请求被要求输入验证码                                 │
│                                                          │
│  中的：                                                    │
│  • 你的 IP 被直接封禁                                      │
│  • 你采集到的数据被替换成假数据（污染数据）                  │
│                                                          │
│  重的：                                                    │
│  • 蜜罐链接可能是法律"钓鱼"——记录你的行为作为证据            │

└──────────────────────────────────────────────────────────┘
```

**生活类比：** 蜜罐就像在仓库门口放一个写着"免费领取"的假箱子。正常人知道这里不该进，但机器人看到文字就会去打开——一打开就暴露身份了。

## 八、Referer 头校验

### 8.1 什么是 Referer？

Referer 请求头告诉服务器"你从哪个页面跳转过来的"。有些网站会检查这个字段——如果你直接请求一个子页面，而没有合法的来源页面，就会被拒绝。

```
┌──────────────────────────────────────────────────────────┐
│  Referer 的工作方式                                       │
│                                                          │
│  正常浏览流程：                                            │
│  用户在搜索引擎点击链接 → 进入列表页 → 点击某个商品          │
│                                                          │
│  请求详情页时，浏览器自动带上：                             │
│  Referer: https://example.com/list?page=1                 │
│                                                          │
│  爬虫直接请求详情页时：                                     │
│  没有 Referer（或者 Referer 为空）                         │
│  → 服务器发现你不是从正常路径进来的 → 可能拒绝              │
└──────────────────────────────────────────────────────────┘
```

### 8.2 Referer 检测的典型场景

```python
import requests

# 场景：图片防盗链
# 很多网站的图片会检查 Referer，防止被其他网站直接引用

# ❌ 直接请求图片（没有 Referer）
response = requests.get("https://example.com/images/photo.jpg")
print(response.status_code)  # 403 Forbidden
# 返回的是一个"禁止引用"的提示图片

# ✅ 带上合法的 Referer
headers = {
    "Referer": "https://example.com/article/123",
}
response = requests.get("https://example.com/images/photo.jpg", headers=headers)
print(response.status_code)  # 200 OK
```

### 8.3 API 请求中的 Referer 检查

```python
# 有些网站的 API 接口也会检查 Referer
# 比如某个数据接口只允许从自己的网页发起请求

headers = {
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) "
                  "AppleWebKit/537.36 Chrome/120.0.0.0 Safari/537.36",
    "Referer": "https://example.com/data-page",  # 假装你是从这个页面发起的
}
response = requests.get("https://example.com/api/data", headers=headers)
```

**生活类比：** Referer 就像介绍信。你去某个部门办事（请求数据），对方问"谁介绍你来的？"如果你说"没人介绍，我自己来的"（没有 Referer），对方可能不让你进。但如果你拿着"上一个部门"开的介绍信（合法 Referer），就畅通无阻了。

## 九、动态类名与混淆 HTML

### 9.1 什么是动态类名？

有些网站每次加载页面时，CSS 类名都会变化。你的爬虫今天写好选择器 `.product-title`，明天再跑就失效了——因为类名变成了 `.a3f2b1`。

```
┌──────────────────────────────────────────────────────────┐
│  动态类名示例                                              │
│                                                          │
│  第一次访问：                                              │
│  <div class="product-card a1b2c3">                       │
│      <h2 class="title x7y8z9">商品名称</h2>              │
│  </div>                                                  │
│                                                          │
│  第二次访问（类名变了！）：                                 │
│  <div class="product-card d4e5f6">                       │
│      <h2 class="title m9n0p1">商品名称</h2>              │
│  </div>                                                  │
│                                                          │
│  不变的部分：标签结构、类名中的 "product-card" 和 "title"  │
│  变化的部分：后面的哈希值 "a1b2c3" → "d4e5f6"             │
└──────────────────────────────────────────────────────────┘
```

### 9.2 应对动态类名的策略

```python
from bs4 import BeautifulSoup

html = '<div class="product-card a1b2c3"><h2 class="title x7y8z9">商品</h2></div>'
soup = BeautifulSoup(html, 'html.parser')

# ❌ 用完整类名匹配（容易失效）
item = soup.select_one('.product-card.a1b2c3')

# ✅ 用部分类名匹配（CSS 选择器 ^= 开头匹配, *= 包含匹配）
item = soup.select_one('[class*="product-card"]')  # 类名包含 "product-card"
item = soup.select_one('[class^="product-card"]')  # 类名以 "product-card" 开头

# ✅ 用标签结构匹配（不依赖类名）
item = soup.select_one('div > h2')  # div 下的第一个 h2

# ✅ 用 XPath 按结构匹配
# //div[contains(@class, 'product-card')]//h2
```

### 9.3 HTML 混淆

比动态类名更"狠"的是 HTML 混淆——整个页面结构被故意搞乱，用大量无意义的标签嵌套、假文本节点、Unicode 编码等手段让爬虫难以解析。

```
┌──────────────────────────────────────────────────────────┐
│  HTML 混淆手段举例                                         │
│                                                          │
│  手段一：Unicode 编码                                      │
│  正常：<span>¥99.9</span>                                 │
│  混淆：<span>&#xA5;9&#x39;.&#x39;</span>                 │
│                                                          │
│  手段二：CSS 伪元素插入内容                                 │
│  <span class="price" data-value="99.9"></span>           │
│  .price::before { content: "¥"; }                        │
│  .price::after { content: " 元"; }                       │
│  → 爬虫拿不到显示的价格，只能拿到 data 属性                 │
│                                                          │
│  手段三：SVG/Canvas 渲染文字                                │
│  价格用图片或 SVG 绘制，不是 HTML 文本                      │
│  → 爬虫完全无法提取                                        │
│                                                          │
│  手段四：假标签干扰                                         │
│  <div class="title">                                      │
│    <span style="display:none">假标题</span>               │
│    真标题                                                  │
│  </div>                                                   │
│  → 粗心的爬虫会提取到"假标题"                               │
└──────────────────────────────────────────────────────────┘
```

**生活类比：** 动态类名就像每天换锁的门——你配了一把钥匙（CSS 选择器），第二天锁就换了。HTML 混淆就像把文件用密码写成了一堆乱码，只有"翻译器"（浏览器渲染引擎）才能读懂。

## 十、如何判断目标网站用了哪种反爬？

### 10.1 诊断流程

面对一个网站，不要盲目开爬。先做"诊断"，搞清楚它用了什么反爬手段。

```
┌──────────────────────────────────────────────────────────┐
│  反爬诊断四步法                                            │
│                                                          │
│  第一步：直接用 requests 请求                              │
│  ├── 返回 200 + 正常内容 → 反爬很弱或没有                  │
│  ├── 返回 403/429 → 有请求层反爬（UA/IP/频率）             │
│  ├── 返回 200 + 空内容/验证页 → 可能有 JS 挑战             │
│  └── 返回 200 + "Please wait..." → 大概率 Cloudflare     │
│                                                          │
│  第二步：检查响应头                                        │
│  ├── Set-Cookie 中有 __cf_clearance → Cloudflare          │
│  ├── Retry-After 字段 → 速率限制                          │
│  └── X-Powered-By / Server → 识别防护服务                 │
│                                                          │
│  第三步：用浏览器 DevTools 观察                             │
│  ├── Network 面板：看请求是否有二次跳转                     │
│  ├── 看是否有 JS 计算后才发出的请求                         │
│  └── 看页面是否有验证码或"正在检查"提示                     │
│                                                          │
│  第四步：检查 HTML 源码                                     │
│  ├── 有 style="display:none" 的隐藏链接 → 蜜罐            │
│  ├── 类名是随机哈希 → 动态类名                             │
│  ├── 内容是 Unicode 编码 → HTML 混淆                      │
│  └── 有大量 <script> 标签 → JS 渲染依赖                   │
└──────────────────────────────────────────────────────────┘
```

### 10.2 用代码做初步探测

```python
import requests

def detect_anti_crawl(url):
    """探测目标网站的反爬机制"""
    headers = {
        "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) "
                      "AppleWebKit/537.36 Chrome/120.0.0.0 Safari/537.36"
    }

    # 第一步：直接请求
    response = requests.get(url, headers=headers, timeout=10)
    print(f"状态码: {response.status_code}")
    print(f"响应头: {dict(response.headers)}")

    # 第二步：检查状态码
    if response.status_code == 403:
        print("⚠️  403 Forbidden —— 可能是 UA/IP 被封")
    elif response.status_code == 429:
        retry_after = response.headers.get("Retry-After", "未知")
        print(f"⚠️  429 Too Many Requests —— 速率限制，建议等 {retry_after} 秒")

    # 第三步：检查响应内容
    text = response.text.lower()
    if "checking your browser" in text or "正在检查" in text:
        print("⚠️  检测到 JS 挑战页面（可能是 Cloudflare）")
    if "captcha" in text or "验证码" in text:
        print("⚠️  检测到验证码")
    if "access denied" in text:
        print("⚠️  访问被拒绝")

    # 第四步：检查 Cookie
    cookies = dict(response.cookies)
    if "__cf_clearance" in cookies:
        print("⚠️  Cloudflare 清除 Cookie —— 需要 JS 执行")
    print(f"收到的 Cookie: {cookies}")

    # 第五步：检查是否有隐藏元素（简单检测）
    if 'style="display:none"' in response.text or "display: none" in response.text:
        print("⚠️  页面中有隐藏元素 —— 注意蜜罐陷阱")

    return response

# 使用示例
# detect_anti_crawl("https://example.com")
```

## 十一、伦理考量：技术是一把双刃剑

### 练习二：对比有无 Cookie 的区别

```python
"""
目标：理解 Cookie 在反爬中的作用
步骤：
1. 创建一个 Session 对象
2. 先访问首页，让 Session 自动保存 Cookie
3. 打印保存的 Cookie
4. 再用同一个 Session 访问子页面
5. 对比：用普通 requests.get()（不带 Cookie）访问同一个子页面
"""
import requests

# 方式一：用 Session（自动管理 Cookie）
with requests.Session() as session:
    session.headers.update({
        "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/120.0.0.0"
    })
    # 先访问首页获取 Cookie
    session.get("https://httpbin.org/cookies/set/token/hello123")
    print(f"Session 的 Cookie: {dict(session.cookies)}")

    # 用同一个 Session 再次请求
    r = session.get("https://httpbin.org/cookies")
    print(f"携带的 Cookie: {r.json()}")

# 方式二：不用 Session（没有 Cookie）
r = requests.get("https://httpbin.org/cookies")
print(f"不带 Cookie: {r.json()}")  # {}
```

### 练习三：编写反爬检测报告生成器

```python
"""
目标：编写一个函数，自动检测 URL 并生成反爬报告
要求：
1. 输入一个 URL
2. 发起请求（带 UA 和不带 UA 各一次）
3. 检测状态码、响应头、Cookie、内容特征
4. 输出一份结构化的反爬检测报告
"""
import requests

def generate_report(url):
    """生成反爬检测报告"""
    report = {"url": url, "findings": []}

    # 测试1：不带 UA
    r1 = requests.get(url, timeout=10)
    if r1.status_code == 403:
        report["findings"].append("不带 UA 返回 403，存在 UA 检测")

    # 测试2：带 UA
    headers = {
        "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) "
                      "AppleWebKit/537.36 Chrome/120.0.0.0 Safari/537.36"
    }
    r2 = requests.get(url, headers=headers, timeout=10)

    # 分析响应
    if r2.status_code == 200:
        text = r2.text.lower()
        if "checking" in text and "browser" in text:
            report["findings"].append("检测到 JS 挑战页面")
        if "captcha" in text:
            report["findings"].append("检测到验证码")
        if "display:none" in r2.text:
            report["findings"].append("页面含隐藏元素（注意蜜罐）")

    # 输出报告
    print(f"\n{'='*50}")
    print(f"反爬检测报告: {url}")
    print(f"{'='*50}")
    if report["findings"]:
        for f in report["findings"]:
            print(f"  • {f}")
    else:
        print("  未检测到明显反爬机制")
    print(f"{'='*50}\n")
```

## 小结

本课的核心知识点：

1. **网站反爬的三大动机**：保护服务器资源、保护数据资产、保护用户隐私
2. **User-Agent 检测**是最基础的反爬——requests 默认的 UA 会暴露你是脚本，必须伪装
3. **速率限制**通过监控请求频率来阻止爬虫——返回 429 状态码或验证码页面
4. **IP 封禁**是更严厉的手段——频繁触发速率限制会导致 IP 被封
5. **Cookie/Session 检测**要求你携带合法的会话标识——用 Session 对象自动管理
6. **JS 挑战页面**要求执行 JavaScript 才能通过——requests 无法处理，需要 Playwright
7. **蜜罐陷阱**利用隐藏链接诱捕爬虫——解析页面时要注意过滤不可见元素
8. **Referer 校验**检查请求来源——需要模拟正常的页面跳转路径
9. **动态类名和 HTML 混淆**增加解析难度——用部分匹配和结构匹配来应对
10. **诊断反爬的四步法**：直接请求 → 检查响应头 → 浏览器观察 → 分析 HTML 源码
11. **技术是双刃剑**——学习反爬是为了理解原理和保护自己，不是为了做坏事
