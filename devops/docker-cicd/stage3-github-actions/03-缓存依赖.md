# 第三课：缓存依赖

> **课程定位**：优化 CI 构建速度，减少重复下载
> **前置知识**：workflow/job/step（第二课）
> **预计时长**：25 分钟

---

## 场景引入

你的 CI 流水线每次跑都要 3 分钟，其中 2 分钟花在 `npm install` 上。你明明只改了一行测试代码，为什么每次都要重新下载几百个依赖包？你开始想：能不能把下载过的依赖缓存起来，下次依赖没变就直接用？

---

## 学习目标

1. 理解为什么需要缓存
2. 掌握 actions/cache 的使用
3. 学会使用 setup-node 的内置缓存
4. 理解缓存键的设计

## 一、为什么需要缓存

```
没有缓存的 CI：

  每次运行都要：
  1. 下载 Node.js
  2. npm install（下载所有依赖）
  3. 运行测试

  npm install 可能需要 1-3 分钟
  如果依赖没变，这是完全浪费的时间

有缓存的 CI：

  第一次：下载依赖 → 存入缓存
  后续：依赖没变 → 直接使用缓存（几秒钟）
```

## 二、使用 setup-node 内置缓存

```yaml
steps:
  - uses: actions/checkout@v4
  
  - uses: actions/setup-node@v4
    with:
      node-version: 18
      cache: npm               # 自动缓存 npm 依赖
```

```
这是最简单的方式：
  - 自动根据 package-lock.json 生成缓存键
  - 自动保存和恢复缓存
  - 几乎零配置
```

## 三、使用 actions/cache

### 3.1 基本用法

```yaml
steps:
  - uses: actions/checkout@v4
  
  # 恢复缓存
  - uses: actions/cache@v3
    id: cache
    with:
      path: node_modules
      key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
      restore-keys: |
        ${{ runner.os }}-node-
  
  # 缓存未命中时才安装
  - if: steps.cache.outputs.cache-hit != 'true'
    run: npm ci
```

### 3.2 缓存键设计

```
缓存键的组成：

  ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
         │                    │
         │                    └── package-lock.json 的哈希值
         └── 操作系统

  含义：
  - 同一 OS + 同一 package-lock.json → 使用缓存
  - package-lock.json 变了 → 缓存未命中，重新安装

  restore-keys：
  - 主键未命中时，尝试匹配的前缀
  - ${{ runner.os }}-node- → 匹配任何 node 缓存
```

### 3.3 缓存路径

```yaml
# npm 缓存路径
- uses: actions/cache@v3
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}

# 或者缓存 node_modules
- uses: actions/cache@v3
  with:
    path: node_modules
    key: ${{ runner.os }}-modules-${{ hashFiles('**/package-lock.json') }}
```

```
两种方式的区别：

  缓存 ~/.npm（npm 缓存目录）：
  - 体积更小
  - npm ci 仍然需要执行，但速度快很多
  - 推荐

  缓存 node_modules：
  - 体积大
  - 可以跳过 npm ci
  - 可能有兼容性问题
```

## 五、Docker 构建缓存

```yaml
steps:
  - uses: actions/checkout@v4
  
  - uses: docker/setup-buildx-action@v3
  
  - uses: docker/build-push-action@v5
    with:
      context: .
      push: false
      cache-from: type=gha
      cache-to: type=gha,mode=max
```

```
GitHub Actions 缓存 Docker 层：
  - 使用 BuildKit 的 GHA 缓存后端
  - 自动缓存 Docker 构建层
  - 大幅加速重复构建
```

## 常见误区

- **"缓存会让依赖版本过旧"**：缓存键是基于 `package-lock.json` 的哈希值，依赖文件变了缓存自动失效。缓存不会让你用到旧版本的依赖。
- **"缓存 node_modules 比缓存 npm 目录好"**：缓存 `node_modules` 体积大、可能有平台兼容性问题。缓存 `~/.npm`（npm 缓存目录）更小、更可靠，虽然仍需执行 `npm ci`，但速度快很多。
- **"Docker 构建不能用 CI 缓存"**：Docker Buildx 支持 `cache-from: type=gha`，可以使用 GitHub Actions 的缓存来加速 Docker 构建层的复用。
- **"所有 CI 都需要手动配置缓存"**：`actions/setup-node` 内置了 `cache: npm` 选项，一行配置就能启用缓存，不需要手动配置 `actions/cache`。

---

## 工程建议

- **优先用 `setup-node` 的 `cache: npm`**：最简单、最可靠，自动处理缓存键和路径。只有需要缓存非 npm 依赖时才用 `actions/cache`。
- **缓存键要包含操作系统**：`${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}`，确保不同 OS 的缓存不混用。
- **Docker 构建用 GHA 缓存后端**：`cache-from: type=gha` 和 `cache-to: type=gha,mode=max` 配合使用，最大化 Docker 构建层的缓存命中率。
- **定期清理过期缓存**：GitHub 会自动清理 7 天未使用的缓存，但如果你的缓存键设计不合理，可能会积累大量无用缓存。

---

## 小结

1. **缓存**：避免每次都重新下载依赖
2. **setup-node 内置缓存**：最简单的方式，`cache: npm`
3. **actions/cache**：更灵活，可以缓存任何目录
4. **缓存键**：基于依赖文件的哈希值，依赖变化时自动失效

## 参考答案

### 练习一

**思路**：使用 `actions/setup-node` 的 `cache: npm` 选项启用依赖缓存。这是最简单的方式，自动根据 `package-lock.json` 的哈希值生成缓存键，依赖没变时直接使用缓存，跳过重复下载。

**答案**：

```yaml
name: CI with Cache

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 18
          cache: npm

      - run: npm ci
      - run: npm test
```

**要点**：
- `cache: npm` 是一行配置启用缓存的最简方式，自动处理缓存键和缓存路径
- 缓存键基于 `package-lock.json` 的哈希值，依赖文件变化时缓存自动失效
- 第一次运行会下载依赖并存入缓存，后续运行如果 `package-lock.json` 没变，`npm ci` 会直接使用缓存，速度大幅提升
- 如果使用 pnpm 或 yarn，将 `cache: npm` 改为 `cache: pnpm` 或 `cache: yarn`

### 练习二

**思路**：通过对比两次 CI 运行的时间来验证缓存效果。第一次运行会下载依赖并缓存，第二次运行（不修改依赖文件）应该直接使用缓存，CI 时间显著缩短。

**答案**：

操作步骤：
1. 第一次推送代码，观察 CI 运行时间（记为 T1）
2. 修改一个非依赖文件（如 README.md），再次推送
3. 观察第二次 CI 运行时间（记为 T2）
4. 对比 T1 和 T2，T2 应该明显快于 T1

在 GitHub Actions 日志中可以看到缓存命中情况：
- 第一次运行日志会显示 `Cache not found`，然后执行完整的 `npm ci`
- 第二次运行日志会显示 `Cache restored`，`npm ci` 执行速度大幅提升

**要点**：
- 缓存效果在依赖未变时最明显，`npm ci` 可能从 1-3 分钟缩短到几秒
- 缓存命中率取决于 `package-lock.json` 是否变化，修改代码不会导致缓存失效
- GitHub Actions 缓存有 7 天过期策略，超过 7 天未使用的缓存会被自动清理
- 可以在 Actions 页面的 Caches 标签页查看当前所有缓存及其大小
