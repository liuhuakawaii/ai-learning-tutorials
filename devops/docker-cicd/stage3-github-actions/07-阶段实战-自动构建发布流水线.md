## 二、CI Workflow（PR 检查）

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]

jobs:
  lint:
    name: Lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 18
          cache: npm
      - run: npm ci
      - run: npm run lint

  test:
    name: Test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 18
          cache: npm
      - run: npm ci
      - run: npm test

  build:
    name: Build
    runs-on: ubuntu-latest
    needs: [lint, test]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 18
          cache: npm
      - run: npm ci
      - run: npm run build
```

## 三、CD Workflow（自动构建发布）

```yaml
# .github/workflows/cd.yml
name: CD

on:
  push:
    branches: [main]
    tags: ['v*']

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  test:
    name: Test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 18
          cache: npm
      - run: npm ci
      - run: npm test

  build-and-push:
    name: Build and Push
    runs-on: ubuntu-latest
    needs: test
    permissions:
      contents: read
      packages: write
    outputs:
      image-tag: ${{ steps.meta.outputs.version }}
    
    steps:
      - uses: actions/checkout@v4
      
      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3
      
      - name: Login to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      
      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
            type=sha
      
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

## 四、部署脚本

```bash
#!/bin/bash
# scripts/deploy.sh

set -e

VERSION=${1:-latest}
IMAGE="ghcr.io/yourusername/yourrepo:${VERSION}"

echo "Deploying version: ${VERSION}"

# 在服务器上执行
ssh deploy@server << EOF
  cd /opt/my-app
  
  # 更新 .env 中的镜像版本
  echo "IMAGE_TAG=${VERSION}" > .env.deploy
  
  # 拉取新镜像
  docker pull ${IMAGE}
  
  # 更新并重启
  docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
  
  # 健康检查
  sleep 10
  curl -f http://localhost:3000/health || exit 1
  
  echo "Deployment successful!"
EOF
```

## 常见误区

- **"CI 和 CD 应该放在同一个 workflow 里"**：PR 检查（CI）和部署（CD）的触发条件不同，放在同一个文件里会导致逻辑混乱。分开管理更清晰，也更容易维护。
- **"main 分支合并后直接部署到生产"**：建议先部署到 staging 环境验证，再手动审批部署到生产。直接部署到生产风险太高。
- **"GITHUB_TOKEN 权限不够推送到 GHCR"**：需要在 workflow 中声明 `permissions: packages: write`，否则推送会失败。
- **"部署脚本不需要错误处理"**：部署脚本必须有 `set -e`、健康检查、失败通知。没有错误处理的部署脚本是定时炸弹。

---

## 工程建议

- **CI 和 CD 分开为两个 workflow 文件**：`ci.yml` 监听 PR，`cd.yml` 监听 main 分支推送和标签。职责清晰，便于维护。
- **用 `workflow_dispatch` 支持手动触发部署**：有时候需要手动部署特定版本，手动触发比修改 workflow 更灵活。
- **部署后自动通知**：部署成功或失败后发送通知（Slack、邮件、钉钉），让团队及时了解部署状态。
- **把部署脚本和回滚脚本放在 `scripts/` 目录**：版本控制、代码 review、本地测试都更方便。不要把部署逻辑散落在 YAML 文件里。

## 参考答案

### 练习一

**思路**：在 CD workflow 中添加一个 staging 部署 Job，依赖 `build-and-push` 完成后执行。使用 `environment` 字段指定部署环境，可以通过 GitHub 的环境保护规则添加审批流程。

**答案**：

```yaml
# 在 .github/workflows/cd.yml 的 jobs 中添加
deploy-staging:
  name: Deploy to Staging
  needs: build-and-push
  runs-on: ubuntu-latest
  if: github.ref == 'refs/heads/main'
  environment: staging
  steps:
    - uses: actions/checkout@v4

    - name: Deploy to staging server
      env:
        SERVER_HOST: ${{ secrets.STAGING_SERVER_HOST }}
        SERVER_USER: ${{ secrets.STAGING_SERVER_USER }}
        SERVER_SSH_KEY: ${{ secrets.STAGING_SERVER_SSH_KEY }}
        IMAGE_TAG: ${{ needs.build-and-push.outputs.image-tag }}
      run: |
        echo "$SERVER_SSH_KEY" > deploy_key
        chmod 600 deploy_key
        ssh -o StrictHostKeyChecking=no -i deploy_key ${SERVER_USER}@${SERVER_HOST} << 'REMOTE'
          cd /opt/my-app
          echo "IMAGE_TAG=${IMAGE_TAG}" > .env.deploy
          docker pull ghcr.io/${{ github.repository }}:${IMAGE_TAG}
          docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d
          sleep 10
          curl -f http://localhost:3000/health || exit 1
          echo "Staging deployment successful!"
        REMOTE
        rm deploy_key
```

**要点**：
- `environment: staging` 关联 GitHub 的环境配置，可以设置审批人、等待时间等保护规则
- `if: github.ref == 'refs/heads/main'` 确保只在主分支部署，避免 PR 触发部署
- `needs: build-and-push` 确保镜像构建推送完成后才执行部署
- SSH 私钥通过 Secrets 管理，部署完成后立即删除临时文件
- 部署后执行健康检查，失败时 workflow 会标记为失败

### 练习二

**思路**：创建一个独立的 rollback workflow，使用 `workflow_dispatch` 支持手动触发，通过输入参数指定要回滚的版本号。

**答案**：

```yaml
# .github/workflows/rollback.yml
name: Rollback

on:
  workflow_dispatch:
    inputs:
      version:
        description: 'Version to rollback to (e.g. v1.2.3 or sha-abc1234)'
        required: true
        type: string

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  rollback:
    name: Rollback
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Rollback to specified version
        env:
          SERVER_HOST: ${{ secrets.SERVER_HOST }}
          SERVER_USER: ${{ secrets.SERVER_USER }}
          SERVER_SSH_KEY: ${{ secrets.SERVER_SSH_KEY }}
          VERSION: ${{ github.event.inputs.version }}
        run: |
          IMAGE="${REGISTRY}/${IMAGE_NAME}:${VERSION}"
          echo "Rolling back to: ${IMAGE}"

          echo "$SERVER_SSH_KEY" > deploy_key
          chmod 600 deploy_key
          ssh -o StrictHostKeyChecking=no -i deploy_key ${SERVER_USER}@${SERVER_HOST} << REMOTE
            cd /opt/my-app
            docker pull ${IMAGE}
            echo "IMAGE_TAG=${VERSION}" > .env.deploy
            docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
            sleep 10
            curl -f http://localhost:3000/health || exit 1
            echo "Rollback successful!"
          REMOTE
          rm deploy_key

      - name: Notify rollback
        if: always()
        run: |
          echo "Rollback to ${{ github.event.inputs.version }} completed with status: ${{ job.status }}"
```

**要点**：
- `workflow_dispatch` 支持手动触发，可以在 GitHub Actions 页面点击 "Run workflow" 按钮
- `inputs.version` 定义输入参数，用户在触发时填写要回滚的版本号
- `environment: production` 可以配置审批流程，防止误操作
- 回滚本质上就是部署一个旧版本的镜像，复用部署脚本的逻辑
- 建议在部署成功后记录版本号（如写入 Git 标签或外部存储），方便回滚时查找
