# 阶段实战：自动构建发布流水线

> 前置知识：GitHub Actions 全部课程（第 1-6 课）

## 你要搭什么

一条完整的 CI/CD 流水线：

```
PR 提交 → lint + test + build → 合并 → 构建 Docker 镜像 → 推送 GHCR → 打标签 → 部署
```

这不是一个练习——这是你在真实项目里交给团队用的东西。

## 流水线设计

### 触发规则

| 事件 | 触发的工作 | 原因 |
|------|-----------|------|
| PR 提交到 main | lint + test + build | 拦截质量问题 |
| 合并到 main | 构建镜像 + 推送 GHCR | 主分支始终可部署 |
| 打 tag（v*） | 构建镜像 + 推送 + 创建 Release | 标记可发布版本 |

### 为什么用 tag 触发部署

很多团队用合并到 main 直接触发部署。这在小团队没问题，但随着团队增长，main 分支的合并频率会变高——可能一天合并十几个 PR。每次合并都部署到生产，发布节奏太快，出问题不好定位。

用 tag 触发部署意味着：合并到 main 只是"准备好了"，打 tag 才是"我要发布"。这给了团队一个明确的发布控制点。

## workflow 文件

```yaml
# .github/workflows/ci-cd.yml
name: CI/CD Pipeline

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
    tags: ['v*']

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  # ---- CI: PR 和 push 时都跑 ----
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 18
          cache: npm

      - run: npm ci

      - name: Lint
        run: npm run lint

      - name: Test
        run: npm test

      - name: Build
        run: npm run build

  # ---- 构建并推送镜像：只在 main 分支和 tag 时 ----
  build:
    needs: ci
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    outputs:
      image-tag: ${{ steps.meta.outputs.tags }}
    steps:
      - uses: actions/checkout@v4

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=sha,prefix=

      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

  # ---- 部署：只在打 tag 时 ----
  deploy:
    needs: build
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to server
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          DEPLOY_HOST: ${{ secrets.DEPLOY_HOST }}
          DEPLOY_USER: ${{ secrets.DEPLOY_USER }}
        run: |
          mkdir -p ~/.ssh
          echo "$SSH_PRIVATE_KEY" > ~/.ssh/id_rsa
          chmod 600 ~/.ssh/id_rsa
          ssh-keyscan $DEPLOY_HOST >> ~/.ssh/known_hosts

          ssh $DEPLOY_USER@$DEPLOY_HOST << 'EOF'
            cd /opt/myapp
            docker pull ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:${{ github.ref_name }}
            docker compose up -d
          EOF
```

## 需要配置的 Secrets

在 GitHub 仓库 Settings → Secrets and variables → Actions 中添加：

| Secret 名称 | 用途 | 获取方式 |
|-------------|------|----------|
| `SSH_PRIVATE_KEY` | SSH 登录部署服务器 | `ssh-keygen -t ed25519` 生成密钥对 |
| `DEPLOY_HOST` | 部署服务器地址 | 你的服务器 IP 或域名 |
| `DEPLOY_USER` | SSH 用户名 | 通常是 `deploy` |

`GITHUB_TOKEN` 是 GitHub 自动提供的，不需要手动配置。它有推送 GHCR 镜像的权限（因为 workflow 里声明了 `packages: write`）。

## 部署服务器端的准备

```bash
# 在服务器上
mkdir -p /opt/myapp
cd /opt/myapp

# docker-compose.yml
cat > docker-compose.yml << 'EOF'
services:
  app:
    image: ghcr.io/your-org/your-repo:main
    ports:
      - "3000:3000"
    environment:
      - NODE_ENV=production
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      retries: 3
EOF

# 把 SSH 公钥添加到 authorized_keys
echo "your-public-key" >> ~/.ssh/authorized_keys
```

## 完整流程验证

```bash
# 1. 创建功能分支
git checkout -b feature/test-ci

# 2. 提交代码
git add .
git commit -m "feat: add new feature"
git push origin feature/test-ci

# 3. 创建 PR → CI 自动跑 lint + test + build

# 4. 合并 PR → 自动构建镜像并推送到 GHCR

# 5. 打 tag → 自动部署到生产
git tag v1.0.0
git push origin v1.0.0
```

## 回滚策略

如果 v1.0.1 部署后发现问题，回滚到 v1.0.0：

```bash
# 在服务器上
cd /opt/myapp
docker pull ghcr.io/your-org/your-repo:v1.0.0
# 修改 docker-compose.yml 中的 tag
docker compose up -d
```

或者在 workflow 中增加一个手动触发的回滚 job：

```yaml
rollback:
  workflow_dispatch:
    inputs:
      version:
        description: 'Tag to rollback to'
        required: true
```

## 练习

### 练习一：添加安全扫描

在 CI job 的 `npm run build` 之后，添加一个步骤运行 `npm audit --audit-level=high`。如果有高危漏洞，workflow 应该失败。

### 练习二：多环境部署

修改 workflow，让它在 push 到 main 时自动部署到 staging，在打 tag 时部署到 production。提示：使用 GitHub Environments。

### 练习三：Slack 通知

在 deploy job 完成后，添加一个步骤发送 Slack 通知。使用 `slackapi/slack-github-action` action。成功和失败都应该通知。

## 参考答案

### 练习一

```yaml
      - name: Security audit
        run: npm audit --audit-level=high
```

添加在 `npm run build` 之后。`--audit-level=high` 表示只有高危和严重漏洞才会导致命令返回非零退出码。

### 练习二

```yaml
  deploy-staging:
    needs: build
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy to staging
        run: |
          ssh ${{ secrets.STAGING_USER }}@${{ secrets.STAGING_HOST }} << 'EOF'
            cd /opt/myapp-staging
            docker pull ghcr.io/${{ github.repository }}:main
            docker compose up -d
          EOF

  deploy-production:
    needs: build
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Deploy to production
        run: |
          ssh ${{ secrets.PROD_USER }}@${{ secrets.PROD_HOST }} << 'EOF'
            cd /opt/myapp
            docker pull ghcr.io/${{ github.repository }}:${{ github.ref_name }}
            docker compose up -d
          EOF
```

在 GitHub Settings → Environments 中分别创建 `staging` 和 `production` 环境，配置对应的 secrets。`production` 环境可以设置"Required reviewers"，需要人工批准才能部署。

### 练习三

```yaml
      - name: Notify Slack
        if: always()
        uses: slackapi/slack-github-action@v1
        with:
          payload: |
            {
              "text": "Deployment ${{ job.status }}: ${{ github.ref_name }}",
              "blocks": [
                {
                  "type": "section",
                  "text": {
                    "type": "mrkdwn",
                    "text": "*${{ github.repository }}* deploy ${{ job.status }}\nVersion: `${{ github.ref_name }}`\nActor: ${{ github.actor }}"
                  }
                }
              ]
            }
        env:
          SLACK_WEBHOOK_URL: ${{ secrets.SLACK_WEBHOOK_URL }}
```

`if: always()` 确保无论成功还是失败都会发送通知。
