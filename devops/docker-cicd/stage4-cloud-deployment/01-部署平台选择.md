# 部署平台选择

> 前置知识：Docker、Compose、CI/CD 基础（前三个阶段）

## 你的项目准备上线

CI/CD 流水线搭好了，Docker 镜像构建好了，现在需要选一个地方把应用跑起来。打开云平台控制台：

Vercel、Railway、Render、Fly.io、AWS ECS、GCP Cloud Run、阿里云 ECS、自建 VPS……

每个都说自己好，价格从免费到几百美元不等。你开始纠结：选哪个？

这个问题没有通用答案，但有一个通用的决策框架：**先搞清楚你的约束条件，再看哪个平台最匹配。**

## 约束条件清单

在选平台之前，回答这几个问题：

```
1. 预算：每月愿意花多少钱？（$0 / $20 / $100 / $500+）
2. 数据合规：数据能不能出境？有没有行业监管要求？
3. 技术栈：是纯前端？还是有后端 + 数据库？
4. 流量模式：稳定流量还是突发流量？
5. 运维能力：团队有没有人管服务器？
6. 上线速度：需要今天就上线，还是可以花一周配置？
```

## 主流方案对比

### 纯前端 / Serverless

适合：静态网站、Next.js SSR、API 不多的项目。

| 平台 | 免费额度 | 优点 | 缺点 |
|------|---------|------|------|
| Vercel | 有 | Next.js 原生支持、自动预览 | 国内访问慢、绑定 Next.js 生态 |
| Cloudflare Pages | 有 | 全球 CDN、Workers 边缘计算 | 不支持 Node.js 服务端 |
| Netlify | 有 | 简单易用、表单功能 | 构建时间限制、国内访问慢 |

这类平台的共同特点：你只需要推代码，平台帮你构建和部署。不需要管服务器、不需要写 Dockerfile。代价是灵活性有限——你的应用必须符合平台的运行模型。

### 容器托管

适合：有 Docker 镜像、需要自定义运行环境、有后端服务的项目。

| 平台 | 免费额度 | 优点 | 缺点 |
|------|---------|------|------|
| Railway | 有（有限） | 简单、支持数据库 | 免费额度用完就贵 |
| Fly.io | 有 | 全球边缘部署、支持持久化卷 | 学习曲线 |
| Google Cloud Run | 有（慷慨） | 按请求计费、自动缩到 0 | 需要 GCP 知识 |
| AWS App Runner | 无 | 和 AWS 生态集成 | 配置复杂 |

### VPS / 云服务器

适合：需要完全控制、预算有限、团队有运维能力。

| 平台 | 月费起 | 优点 | 缺点 |
|------|-------|------|------|
| 搅搅云 / Vultr | $5 | 便宜、完全控制 | 需要自己管一切 |
| 阿里云 ECS | ¥50+ | 国内访问快 | 需要备案 |
| DigitalOcean | $6 | 简单、文档好 | 国内访问慢 |

### 自建 K8s

适合：多服务架构、需要自动扩缩容、有专职运维团队。

这条路的学习成本和运维成本最高。如果你只是想把一个项目上线，不建议从这里开始。

## 决策流程

```
你的项目是纯前端吗？
├── 是 → Vercel / Cloudflare Pages
└── 否 → 你需要自定义运行环境吗？
         ├── 否 → Railway / Cloud Run
         └── 是 → 你有运维能力吗？
                  ├── 是 → VPS（自己管）
                  └── 否 → Railway / Fly.io（平台管）
```

## 最小可行方案

如果你不确定选什么，从最小的方案开始：

1. **前端**：Vercel（免费，一分钟部署）
2. **API + 数据库**：Railway（支持 Docker，自带 PostgreSQL）
3. **需要国内访问**：阿里云 ECS + Docker Compose（$10/月起）

先跑起来，遇到瓶颈再迁移。不要在第一天就选"最终方案"——你还不知道自己的真实需求是什么。

## 成本陷阱

### 流量费

很多平台的免费额度只包含计算时间，不包含流量。如果你的应用有大量静态资源或 API 响应体较大，流量费可能比计算费还高。

### 数据库费

Serverless 平台通常不提供数据库，或者提供但很贵。一个 PostgreSQL 实例在 Railway 上可能 $10/月，在 Supabase 免费但在连接数上有限制。

### 冷启动

Cloud Run 和 Lambda 这类按请求计费的平台，空闲时会缩到 0。第一个请求需要等容器启动，延迟可能 1-5 秒。对 API 来说这不可接受——需要设置最小实例数，但那就不是免费了。

## 练习

### 练习一：为你的项目选平台

根据约束条件清单，为你的项目选择部署平台。写出你的约束条件和选择理由。

### 练习二：成本估算

假设你有一个 Next.js 应用 + PostgreSQL 数据库，月 PV 10 万，数据库 2GB。分别估算在 Vercel + Supabase、Railway、阿里云 ECS 三个方案上的月费。

### 练习三：迁移方案

假设你当前用 Vercel 部署，但业务增长导致需要自定义后端服务。画一个从 Vercel 迁移到 VPS + Docker Compose 的方案，包括：迁移步骤、需要处理的 DNS 切换、数据迁移、回滚计划。

## 参考答案

### 练习一

没有标准答案。关键是用约束条件做排除法，而不是被平台的营销文案吸引。

### 练习二

| 方案 | 计算费 | 数据库费 | 流量费 | 估算月费 |
|------|-------|---------|-------|---------|
| Vercel + Supabase | $0（免费额度） | $0（免费 500MB） | $0（100GB 免费） | $0-20 |
| Railway | $5-10 | $5-10 | 包含在内 | $10-20 |
| 阿里云 ECS | ¥50-100 | 包含在内 | ¥0.8/GB | ¥60-120 |

### 练习三

迁移步骤：

1. 在 VPS 上配置 Docker Compose + Nginx + PostgreSQL
2. 从 Supabase 导出数据，导入 VPS 的 PostgreSQL
3. 在 VPS 上部署应用，验证功能正常
4. DNS 切换：把域名指向 VPS IP
5. 保留 Vercel 部署一周，作为回滚方案
6. 确认稳定后，删除 Vercel 项目

DNS 切换有 TTL 缓存，可能需要 24-48 小时才能全球生效。在切换期间，两个环境同时运行。
