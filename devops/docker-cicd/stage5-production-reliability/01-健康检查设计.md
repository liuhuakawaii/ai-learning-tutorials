# 健康检查设计

> 前置知识：Docker 基础、Compose（前两个阶段）

## 一个监控盲区

你的服务部署到生产环境了。Docker 显示容器状态是 "Up"，CPU 和内存正常。但用户反馈"页面打不开"。

你登上服务器排查：

```bash
docker ps
# 容器状态：Up 2 hours

curl http://localhost:3000/health
# 响应正常：{"status":"ok"}
```

看起来没问题。但用户确实打不开。最后发现是 PostgreSQL 容器挂了——磁盘空间满了，PostgreSQL 拒绝写入。API 容器还在运行，进程没死，但它依赖的数据库已经不可用了。

Docker 认为 API 容器是"健康的"，因为它只检查了进程是否存活。**进程存活不等于服务可用。** 健康检查要解决的就是这个问题。

## 健康检查的三个层次

```
Layer 1: 进程存活（Docker 自动检测）
  └── 进程还在吗？在 → "Up"
  └── 问题：进程可能在，但已经无法处理请求

Layer 2: 服务可用（应用自己报告）
  └── /health 端点能响应吗？能 → "healthy"
  └── 问题：应用能响应，但依赖可能挂了

Layer 3: 依赖就绪（检查下游服务）
  └── 数据库能连吗？Redis 能连吗？能 → 真正健康
  └── 这才是用户能正常使用服务的保证
```

大多数健康检查只做到 Layer 1 或 Layer 2。你需要做到 Layer 3。

## 设计健康检查端点

一个好的 `/health` 端点应该检查什么？

```typescript
// 推荐：分级健康检查
app.get('/health', async (req, res) => {
  const checks = {
    status: 'ok',
    timestamp: new Date().toISOString(),
    uptime: process.uptime(),
    version: process.env.npm_package_version,
    dependencies: {} as Record<string, string>,
  };

  // 检查数据库
  try {
    await db.query('SELECT 1');
    checks.dependencies.postgres = 'ok';
  } catch (err) {
    checks.dependencies.postgres = 'fail';
    checks.status = 'degraded';
  }

  // 检查 Redis
  try {
    await redis.ping();
    checks.dependencies.redis = 'ok';
  } catch (err) {
    checks.dependencies.redis = 'fail';
    checks.status = 'degraded';
  }

  const statusCode = checks.status === 'ok' ? 200 : 503;
  res.status(statusCode).json(checks);
});
```

关键设计决策：

**为什么返回 503 而不是 200？** 健康检查工具（Docker、负载均衡器、Kubernetes）通常根据 HTTP 状态码判断健康状态。503 表示"服务不可用"，触发自动重启或流量切换。

**为什么检查 `SELECT 1` 而不是复杂查询？** 健康检查需要快速返回。复杂查询可能需要几百毫秒，健康检查应该在 3 秒内完成。

**为什么是"分级"而不是"全有全无"？** Redis 挂了不代表 API 完全不可用——可能只是缓存失效，核心功能还能用。分级返回让调用方决定怎么处理。

## Docker 中的健康检查

### Dockerfile

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD curl -f http://localhost:3000/health || exit 1
```

参数说明：

| 参数 | 含义 | 建议值 |
|------|------|-------|
| `--interval` | 检查频率 | 30s（不要太频繁） |
| `--timeout` | 单次检查超时 | 3s（健康检查要快） |
| `--start-period` | 启动宽限期 | 10-30s（给应用初始化时间） |
| `--retries` | 连续失败几次标记为 unhealthy | 3（避免偶发失败误判） |

### docker-compose.yml

```yaml
services:
  api:
    image: my-api:1.0
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 3s
      start_period: 10s
      retries: 3

  db:
    image: postgres:14
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5
```

### 配合 depends_on

```yaml
services:
  api:
    depends_on:
      db:
        condition: service_healthy
```

这保证 API 在数据库真正就绪后才启动，而不是仅仅"容器启动了"。

## Liveness vs Readiness

这两个概念来自 Kubernetes，但思路适用于任何健康检查：

**Liveness（存活检查）**：进程还在吗？如果不在，杀掉重启。检查的是"进程是否卡死"。

**Readiness（就绪检查）**：能处理请求吗？如果不能，从负载均衡器摘掉。检查的是"依赖是否就绪"。

```
Liveness 失败 → 重启容器
Readiness 失败 → 停止接收流量（但不重启）
```

在 Docker 中，HEALTHCHECK 指令同时承担了两个角色。如果需要区分，可以在应用层实现两个端点：

```typescript
// /healthz — liveness：进程是否卡死
app.get('/healthz', (req, res) => res.json({ status: 'ok' }));

// /readyz — readiness：依赖是否就绪
app.get('/readyz', async (req, res) => {
  const dbOk = await checkDb();
  const redisOk = await checkRedis();
  if (dbOk && redisOk) {
    res.json({ status: 'ready' });
  } else {
    res.status(503).json({ status: 'not ready' });
  }
});
```

## 常见错误

### 只检查进程存活

```dockerfile
# 不推荐：只检查进程是否在
HEALTHCHECK CMD pgrep node || exit 1
```

进程在不代表能处理请求。Node.js 可能在 event loop 阻塞、内存泄漏、数据库断连等情况下"活着但无法服务"。

### 健康检查太频繁

```yaml
# 不推荐：每秒检查一次
healthcheck:
  interval: 1s
```

健康检查本身消耗资源。如果 10 个容器每秒都发一个 HTTP 请求到数据库，这些检查请求本身就可能成为性能问题。

### 健康检查做了太多事

```typescript
// 不推荐：健康检查跑了复杂查询
app.get('/health', async (req, res) => {
  const users = await db.query('SELECT COUNT(*) FROM users');
  const orders = await db.query('SELECT COUNT(*) FROM orders WHERE created_at > NOW() - INTERVAL 1 DAY');
  // ...
});
```

健康检查应该在 3 秒内返回。复杂查询放到监控指标里，不要放到健康检查里。

### 练习二

```bash
# 启动服务
docker compose up -d

# 确认健康
docker compose ps  # STATUS 列应显示 healthy

# 杀掉数据库
docker compose kill db

# 等待 30 秒，观察 api 的健康状态
watch -n 2 docker compose ps
# api 的 STATUS 应该从 healthy 变为 unhealthy
# 如果配置了 restart: unless-stopped，unhealthy 后会自动重启
```

### 练习三

| 维度 | 健康检查 | 监控 |
|------|---------|------|
| 回答的问题 | 服务现在能不能用？ | 服务的长期表现如何？ |
| 频率 | 秒到分钟级 | 分钟到小时级 |
| 动作 | 失败 → 重启/摘流量 | 失败 → 告警/分析 |
| 数据 | 二元的（健康/不健康） | 时序的（趋势、百分位） |
| 示例 | /health 返回 200？ | P99 延迟过去 1 小时从 50ms 升到 500ms |

两者配合：健康检查负责"快速恢复"，监控负责"发现问题根因"。健康检查让系统自动从故障中恢复，监控让你知道为什么出故障以及如何预防。
