# 第五课：数据持久化和备份

> **课程定位**：确保数据安全，容器重启不丢数据
> **前置知识**：Compose 基础、Volume 概念（第 1-3 课）
> **预计时长**：30 分钟

---

## 场景引入

你的项目跑了一个月，积累了大量用户数据。某天服务器磁盘满了，你 `docker compose down` 停掉服务清理磁盘，然后 `docker compose up -d` 重新启动——数据库是空的。你这才想起来：数据存在容器里，没用 Volume。更糟糕的是，你从来没有做过数据库备份。

1. 理解容器数据丢失的原因

4. 知道数据迁移的基本方法

## 一、为什么数据会丢失

```
容器的文件系统是临时的：

  docker run postgres     → 容器创建，数据写入
  docker rm postgres      → 容器删除，数据丢失 💀

  原因：
  容器的可写层随容器生命周期，
  容器删除，可写层也一起删除。
```

## 二、数据持久化方案

### 2.1 Named Volume（推荐用于数据库）

```yaml
services:
  postgres:
    image: postgres:14
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

```
特点：
  ✅ Docker 管理存储位置
  ✅ 容器删除后数据保留
  ✅ 性能好（Docker 优化过）
  ✅ 可以在多个容器间共享
  ❌ 不方便直接在宿主机查看文件
```

### 2.2 Bind Mount（推荐用于开发）

```yaml
services:
  app:
    volumes:
      - ./src:/app/src
      - ./data:/app/data
```

```
特点：
  ✅ 容器和宿主机实时同步
  ✅ 方便在宿主机编辑文件
  ❌ 依赖宿主机目录结构
  ❌ 性能略差（macOS/Windows）
  ❌ 宿主机删除文件，容器也会丢失
```

### 2.3 选择建议

```
┌──────────────────┬──────────────────┬──────────────────┐
│   场景            │   推荐方案        │   原因           │
├──────────────────┼──────────────────┼──────────────────┤
│   数据库数据      │   Named Volume   │   数据安全       │
│   Redis 数据      │   Named Volume   │   数据安全       │
│   文件上传        │   Named Volume   │   数据安全       │
│   源代码（开发）   │   Bind Mount     │   实时同步       │
│   配置文件        │   Bind Mount     │   方便修改       │
│   日志文件        │   Bind Mount     │   方便查看       │
└──────────────────┴──────────────────┴──────────────────┘
```

## 三、数据库备份与恢复

### 3.1 PostgreSQL 备份

```bash
# 备份
docker compose exec postgres pg_dump -U postgres mydb > backup.sql

# 带时间戳的备份
docker compose exec postgres pg_dump -U postgres mydb > "backup_$(date +%Y%m%d_%H%M%S).sql"

# 压缩备份
docker compose exec postgres pg_dump -U postgres mydb | gzip > backup.sql.gz
```

### 3.2 PostgreSQL 恢复

```bash
# 恢复
docker compose exec -T postgres psql -U postgres mydb < backup.sql

# 从压缩文件恢复
gunzip -c backup.sql.gz | docker compose exec -T postgres psql -U postgres mydb
```

### 3.3 自动备份脚本

```bash
#!/bin/bash
# scripts/backup-db.sh

BACKUP_DIR="./backups"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="${BACKUP_DIR}/backup_${TIMESTAMP}.sql"

mkdir -p "$BACKUP_DIR"

echo "Backing up PostgreSQL..."
docker compose exec -T postgres pg_dump -U postgres mydb > "$BACKUP_FILE"

# 压缩
gzip "$BACKUP_FILE"

# 删除 7 天前的备份
find "$BACKUP_DIR" -name "*.gz" -mtime +7 -delete

echo "Backup completed: ${BACKUP_FILE}.gz"
```

### 3.4 Redis 备份

```bash
# Redis 自动持久化（RDB + AOF）
# 数据在 redis-data volume 中

# 手动触发 RDB 快照
docker compose exec redis redis-cli BGSAVE

# 备份 Redis 数据
docker compose exec redis redis-cli BGSAVE
docker cp $(docker compose ps -q redis):/data/dump.rdb ./redis-backup.rdb
```

## 四、Volume 管理

```bash
# 查看所有 volume
docker volume ls

# 查看 volume 详情
docker volume inspect pgdata

# 手动备份 volume
docker run --rm -v pgdata:/data -v $(pwd):/backup alpine \
  tar czf /backup/pgdata-backup.tar.gz -C /data .

# 恢复 volume
docker run --rm -v pgdata:/data -v $(pwd):/backup alpine \
  tar xzf /backup/pgdata-backup.tar.gz -C /data

# 删除 volume（危险！数据会丢失）
docker volume rm pgdata

# 清理未使用的 volume
docker volume prune
```

## 五、动手练习

### 练习一：验证数据持久化

```bash
# 1. 启动 PostgreSQL
docker compose up -d postgres

# 2. 创建测试数据
docker compose exec postgres psql -U postgres -c "
  CREATE TABLE users (id serial, name text);
  INSERT INTO users (name) VALUES ('Alice'), ('Bob');
"

# 3. 停止并删除容器
docker compose down

# 4. 重新启动
docker compose up -d postgres

# 5. 验证数据还在
docker compose exec postgres psql -U postgres -c "SELECT * FROM users;"
```

### 练习二：备份和恢复

```bash
# 1. 备份
docker compose exec postgres pg_dump -U postgres mydb > backup.sql

# 2. 删除一些数据
docker compose exec postgres psql -U postgres -c "DELETE FROM users;"

# 3. 恢复
docker compose exec -T postgres psql -U postgres mydb < backup.sql

# 4. 验证数据恢复
docker compose exec postgres psql -U postgres -c "SELECT * FROM users;"
```

## 常见误区

- **"docker compose down 不会删数据"**：默认不会删 Volume 数据，但 `docker compose down -v` 会。执行前确认是否需要保留数据，养成先备份的习惯。
- **"有了 Volume 就不需要备份"**：Volume 只保证容器删除后数据还在，但磁盘损坏、误操作 `docker volume rm`、Volume corruption 都会导致数据丢失。Volume 和备份是两回事。
- **"Redis 是缓存，不需要持久化"**：Redis 作为缓存确实可以丢数据，但如果用作会话存储、排行榜等场景，数据丢失会影响用户体验。根据业务场景决定是否持久化。
- **"备份文件存在服务器上就够了"**：服务器磁盘损坏或被攻击，备份文件也会丢失。备份应该存储在独立位置（如对象存储、异地服务器）。

---

## 工程建议

- **数据库必须用 Named Volume**：任何有状态服务（PostgreSQL、Redis、MongoDB）的数据目录都应该挂载到 Named Volume。
- **自动化备份脚本**：用 `pg_dump` 定期备份 PostgreSQL，配合 cron 任务每天执行，自动清理超过 7 天的旧备份。
- **备份前先测试恢复**：备份不等于安全，定期测试恢复流程，确保备份文件可用。
- **用 `docker volume inspect` 检查 Volume 状态**：排查数据问题时，先确认 Volume 是否存在、挂载路径是否正确。

---

## 小结

1. **Named Volume**：数据库数据持久化的首选方案
2. **Bind Mount**：开发环境挂载源代码
3. **定期备份**：使用 `pg_dump` 备份 PostgreSQL
4. **备份脚本**：自动化备份，定期清理旧备份

## 参考答案

### 练习一

**思路**：通过创建数据 → 删除容器 → 重新启动 → 验证数据的完整流程，证明 Named Volume 的数据持久化特性。

**答案**：

```bash
# 1. 确保 compose.yml 中 postgres 使用了 Named Volume
# volumes:
#   - pgdata:/var/lib/postgresql/data

# 2. 启动 PostgreSQL
docker compose up -d postgres

# 3. 等待数据库就绪
docker compose exec postgres pg_isready -U postgres

# 4. 创建测试数据
docker compose exec postgres psql -U postgres -c "
  CREATE TABLE users (id serial PRIMARY KEY, name text);
  INSERT INTO users (name) VALUES ('Alice'), ('Bob');
"
# 预期：CREATE TABLE / INSERT 0 2

# 5. 确认数据存在
docker compose exec postgres psql -U postgres -c "SELECT * FROM users;"
# 预期：
#  id | name
# ----+-------
#   1 | Alice
#   2 | Bob

# 6. 停止并删除容器（不加 -v，保留 Volume）
docker compose down

# 7. 确认 Volume 仍然存在
docker volume ls | grep pgdata
# 预期：能看到 pgdata volume

# 8. 重新启动
docker compose up -d postgres

# 9. 验证数据完好
docker compose exec postgres psql -U postgres -c "SELECT * FROM users;"
# 预期：数据和第 5 步完全一致

# 清理
docker compose down -v
```

**要点**：
- 关键在第 6 步：`docker compose down` 不带 `-v`，Volume 保留
- 如果带了 `-v`，Volume 被删除，第 9 步会报错 `relation "users" does not exist`
- Named Volume 的生命周期独立于容器和 Compose 项目
- `docker volume ls` 可以确认 Volume 是否存在
- 这个实验应该在学习 Volume 的第一天就做，建立直觉

### 练习二

**思路**：先备份数据库，再故意删除数据，最后从备份恢复。这是生产环境必须掌握的技能。

**答案**：

```bash
# 1. 确保数据库中有测试数据（参考练习一）
docker compose up -d postgres
docker compose exec postgres psql -U postgres -c "SELECT * FROM users;"

# 2. 备份数据库
docker compose exec postgres pg_dump -U postgres mydb > backup.sql
# 预期：当前目录生成 backup.sql 文件

# 确认备份文件存在
ls -la backup.sql

# 3. 模拟数据丢失——删除所有数据
docker compose exec postgres psql -U postgres -c "DELETE FROM users;"
# 预期：DELETE 2

# 4. 确认数据已丢失
docker compose exec postgres psql -U postgres -c "SELECT * FROM users;"
# 预期：空结果

# 5. 从备份恢复
docker compose exec -T postgres psql -U postgres mydb < backup.sql
# 注意：-T 参数用于管道输入，禁用 TTY 分配

# 6. 验证数据恢复
docker compose exec postgres psql -U postgres -c "SELECT * FROM users;"
# 预期：
#  id | name
# ----+-------
#   1 | Alice
#   2 | Bob

# 清理
docker compose down -v
rm backup.sql
```

**要点**：
- `pg_dump` 导出的是 SQL 语句，可以用文本编辑器查看
- `-T` 参数在 `exec` 管道输入时必须加，否则可能报 TTY 错误
- 恢复操作会执行备份中的 SQL，包括 `CREATE TABLE` 和 `INSERT`
- 如果表已存在，`pg_dump` 默认不会包含 `DROP TABLE`，可能需要先清空表
- 生产环境应该用带时间戳的备份文件名（`backup_20240101_120000.sql`），方便管理
