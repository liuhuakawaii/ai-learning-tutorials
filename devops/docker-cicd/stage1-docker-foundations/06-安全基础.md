## 一、非 root 用户运行

### 1.1 为什么需要非 root

```
容器默认以 root 运行，这有安全风险：

  以 root 运行的风险：
  ├── 容器逃逸后获得宿主机 root 权限
  ├── 可以修改系统文件
  ├── 可以安装恶意软件
  └── 可以访问其他容器的资源

  以非 root 运行：
  ├── 即使被攻破，权限有限
  ├── 无法修改系统文件
  ├── 限制了攻击的影响范围
  └── 符合最小权限原则
```

### 1.2 如何配置

```dockerfile
# ❌ 默认以 root 运行（危险）
FROM node:18-alpine
WORKDIR /app
COPY . .
CMD ["node", "src/index.js"]

# ✅ 创建专用用户（推荐）
FROM node:18-alpine

# 创建用户组和用户
RUN addgroup -g 1001 -S nodejs \
    && adduser -S nodeuser -u 1001 -G nodejs

WORKDIR /app

# 设置目录权限
COPY --chown=nodeuser:nodejs . .

# 切换到非 root 用户
USER nodeuser

CMD ["node", "src/index.js"]
```

### 1.3 验证

```bash
# 以默认（root）用户运行
docker run --rm node:18-alpine whoami
# 输出：root

# 以指定用户运行
docker run --rm --user 1001:1001 node:18-alpine whoami
# 输出：uid=1001

# 在 Dockerfile 中设置 USER 指令后
docker run --rm my-app whoami
# 输出：nodeuser
```

## 二、安全反模式

### 2.1 常见错误

```dockerfile
# ❌ 错误 1：在镜像中硬编码密钥
ENV DB_PASSWORD=secret123
ENV API_KEY=sk-1234567890

# ❌ 错误 2：使用 latest 标签
FROM node:latest

# ❌ 错误 3：以 root 运行（没有 USER 指令）

# ❌ 错误 4：安装不需要的工具
RUN apt-get install -y vim nano curl wget git

# ❌ 错误 5：COPY 整个目录包括 .env
COPY . .
```

### 2.2 正确做法

```dockerfile
# ✅ 正确 1：运行时传入环境变量
# docker run -e DB_PASSWORD=secret my-app

# ✅ 正确 2：使用固定版本
FROM node:18.17.0-alpine

# ✅ 正确 3：非 root 用户
USER nodeuser

# ✅ 正确 4：只安装必要工具
RUN apk add --no-cache curl

# ✅ 正确 5：使用 .dockerignore 排除 .env
```

### 2.3 真实案例：敏感 token 写入 Dockerfile

```
某个项目的 Dockerfile 中直接写死了 Sentry token：

  ENV SENTRY_AUTH_TOKEN="sntrys_eyJ..."

这个 token 会被：
  1. 写入镜像层，docker history 可以看到
  2. 推送到镜像仓库后，任何能拉取的人都能看到
  3. 即使后来删除，旧层中仍然保留

正确做法：
  - 构建时通过 --build-arg 传入（ARG 不会留在最终镜像）
  - 或通过 CI/CD 环境变量注入
  - 绝对不要写死在 Dockerfile 中
```

## 三、镜像安全扫描

### 3.1 为什么需要扫描

```
镜像中可能存在的安全漏洞：

  基础镜像中的系统库
  ├── openssl 可能有已知漏洞
  ├── curl 可能有已知漏洞
  └── 其他系统包

  应用依赖中的 npm 包
  ├── express 可能有已知漏洞
  ├── lodash 可能有已知漏洞
  └── 其他依赖
```

### 3.2 扫描工具

```bash
# 使用 Docker Scout 扫描（Docker Desktop 自带）
docker scout cves my-app:latest

# 使用 Trivy 扫描（开源，推荐）
trivy image my-app:latest

# 使用 Snyk 扫描
snyk container test my-app:latest
```

## 四、其他安全措施

### 4.1 只读文件系统

```bash
# 以只读模式运行容器
docker run --read-only my-app

# 如果需要写入临时文件，挂载 tmpfs
docker run --read-only --tmpfs /tmp my-app
```

### 4.2 限制资源

```bash
# 限制 CPU 和内存
docker run --memory=512m --cpus=1 my-app

# 限制重启次数
docker run --restart=on-failure:3 my-app
```

## 五、安全检查清单

```
Dockerfile 安全清单：

  基础镜像：
  ✅ 使用特定版本标签，不用 latest
  ✅ 优先选择 alpine 或 slim 版本
  ✅ 定期更新基础镜像以获取安全补丁

  构建：
  ✅ 使用多阶段构建
  ✅ 使用 .dockerignore 排除 .env 和敏感文件
  ✅ 不在镜像中硬编码密钥

  运行：
  ✅ 以非 root 用户运行
  ✅ 限制 CPU 和内存
  ✅ 设置重启策略
  ✅ 定期扫描镜像漏洞
```

## 参考答案

### 练习一

**思路**：对比 root 用户和非 root 用户运行容器的行为差异，理解 USER 指令的作用。

**答案**：

```bash
# 1. 以默认（root）用户运行
docker run -it --rm node:18-alpine whoami
# 输出：root

# 2. 以指定用户运行
docker run -it --rm --user 1001:1001 node:18-alpine whoami
# 输出：uid=1001 (可能显示用户名为数字，因为该 UID 没有对应的用户名)

# 3. 创建带 USER 指令的 Dockerfile
cat > Dockerfile.secure << 'EOF'
FROM node:18-alpine

RUN addgroup -g 1001 -S nodejs \
    && adduser -S nodeuser -u 1001 -G nodejs

WORKDIR /app
COPY --chown=nodeuser:nodejs . .

USER nodeuser

CMD ["node", "src/index.js"]
EOF

# 4. 构建并验证
docker build -t secure-app .
docker run --rm secure-app whoami
# 输出：nodeuser
```

**要点**：
- 容器默认以 root 用户运行，存在安全风险
- `USER` 指令切换到非 root 用户，限制容器内进程的权限
- `COPY --chown` 确保非 root 用户对文件有读写权限
- 即使容器被攻破，攻击者也只有普通用户权限，无法控制系统文件

### 练习二

**思路**：使用 Docker Scout 扫描镜像，了解镜像中存在哪些已知漏洞。

**答案**：

```bash
# 1. 构建一个镜像
docker build -t security-test .

# 2. 使用 Docker Scout 扫描（需要 Docker Desktop 或 Docker CLI 支持）
docker scout cves security-test

# 输出示例：
#   Overview
#   ════════
#   ✓ Analyzed image security
#   ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
#   Target:  security-test:latest
#   Base:    node:18-alpine
#
#   Vulnerabilities
#   ═══════════════
#   CRITICAL  0  HIGH  2  MEDIUM  5  LOW  10

# 3. 如果没有 Docker Scout，可以用 Trivy（需要单独安装）
# trivy image security-test

# 4. 根据报告修复高危漏洞：
#    - 更新基础镜像版本
#    - 更新有漏洞的依赖包
#    - 重新构建并扫描
```

**要点**：
- 漏洞来源主要有两个：基础镜像的系统库和应用的 npm 依赖
- `docker scout cves` 显示漏洞的严重级别（Critical/High/Medium/Low）
- 高危漏洞（Critical/High）应该在部署前修复
- 定期扫描很重要，新的漏洞每天都在被发现

### 练习三

**思路**：对比有无 `.dockerignore` 时镜像内容的差异，理解敏感文件泄露的风险。

**答案**：

```bash
# 1. 假设项目目录下有 .env 文件
echo "DATABASE_URL=postgres://user:password@host/db" > .env
echo "API_KEY=sk-1234567890" >> .env

# 2. 不使用 .dockerignore 构建
docker build -t test:unsafe .

# 3. 检查镜像中是否有 .env
docker run -it test:unsafe cat /app/.env
# 输出：DATABASE_URL=postgres://user:password@host/db
#       API_KEY=sk-1234567890
# 敏感信息泄露了！

# 4. 添加 .dockerignore
echo ".env" >> .dockerignore
echo ".env.*" >> .dockerignore

# 5. 重新构建
docker build -t test:safe .

# 6. 验证 .env 不在镜像中
docker run -it test:safe cat /app/.env
# 输出：cat: can't open '/app/.env': No such file or directory
# 敏感文件被排除了！
```

**要点**：
- 没有 `.dockerignore` 时，`COPY . .` 会把所有文件（包括 `.env`）复制进镜像
- 敏感信息一旦进入镜像，即使后来删除，旧层中仍然保留
- 推送到镜像仓库后，任何能拉取的人都能通过 `docker history` 看到敏感信息
- `.dockerignore` 必须排除：`.env`、`.git`、密钥文件、`node_modules`

## 常见误区

- **"容器隔离了就很安全"**：容器共享宿主机内核，隔离强度不如虚拟机。以 root 运行的容器如果存在内核漏洞，可能导致容器逃逸。安全需要多层防护，不能只依赖隔离。
- **"小项目不需要关注安全"**：攻击者不会因为项目小就放过你。自动化扫描工具会无差别地探测所有暴露的服务，安全防护应该从一开始就做。
- **"扫描一次就够了"**：新的漏洞每天都在被发现，今天安全的镜像明天可能就有漏洞。应该在 CI/CD 中集成自动扫描，每次构建都检查。
- **"Alpine 镜像就没有漏洞"**：Alpine 体积小、攻击面小，但不代表没有漏洞。系统库和应用依赖都可能有已知漏洞，必须定期扫描。

---

## 工程建议

- **在 CI/CD 中集成镜像扫描**：用 Trivy、Docker Scout 等工具在构建流水线中自动扫描，发现高危漏洞时阻断部署。
- **用固定版本标签构建基础镜像**：`node:18.17.0-alpine` 比 `node:18-alpine` 更可预测，避免基础镜像悄悄更新导致意外。
- **定期更新基础镜像**：每月至少更新一次，获取最新的安全补丁。可以用 Dependabot 或 Renovate 自动化这个过程。
- **敏感信息用运行时注入**：数据库密码、API Key 等通过 `docker run -e`、Docker secrets 或 Kubernetes secrets 注入，绝不写进镜像。

---

## 小结

1. **非 root 用户**：容器默认以 root 运行有安全风险，应该创建专用用户
2. **不硬编码密钥**：密钥通过运行时环境变量或 CI/CD 注入
3. **安全扫描**：定期用 Docker Scout / Trivy 扫描镜像漏洞
4. **.dockerignore**：排除 .env、密钥等敏感文件，防止泄露
5. **安全清单**：固定版本、非 root、排除敏感文件、限制资源
