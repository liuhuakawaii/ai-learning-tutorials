## 一、构建缓存深入

### 1.1 缓存机制

```
Docker 逐层构建，每一层都会检查是否有缓存：

  ┌─────────────────────────────────────────────────────┐
  │  构建过程                                            │
  │                                                      │
  │  Step 1: FROM node:18-alpine    → 缓存命中 ✅        │
  │  Step 2: WORKDIR /app           → 缓存命中 ✅        │
  │  Step 3: COPY package.json .    → 检查文件 hash       │
  │    ├── 没变 → 缓存命中 ✅                             │
  │    └── 变了 → 缓存失效 ❌ → 后续全部重建              │
  │  Step 4: RUN npm install        → 依赖 Step 3        │
  │  Step 5: COPY src/ ./src/       → 检查文件 hash       │
  └─────────────────────────────────────────────────────┘

  关键规则：一旦某层缓存失效，该层及后续所有层都重建。
```

### 1.2 优化原则：变化频率从低到高

```dockerfile
# ✅ 好的顺序：变化频率从低到高排列

# 1. 基础镜像（几乎不变）
FROM node:18-alpine

# 2. 系统依赖（很少变）
RUN apk add --no-cache tini

# 3. 依赖文件（偶尔变）
COPY package.json package-lock.json ./

# 4. 安装依赖（依赖文件变才变）
RUN npm ci

# 5. 配置文件（偶尔变）
COPY tsconfig.json ./

# 6. 源代码（经常变）
COPY src/ ./src/

# 7. 构建（源代码变才变）
RUN npm run build
```

### 1.3 npm ci vs npm install

```
npm install：
  - 可能更新 package-lock.json
  - 安装结果可能不一致（不同时间装出不同版本）
  - 适合本地开发

npm ci：
  - 严格按照 package-lock.json 安装
  - 安装结果完全一致（可重复构建）
  - 速度更快（跳过依赖解析）
  - 适合 CI/CD 和 Docker

结论：Dockerfile 中必须用 npm ci
```

## 二、为什么需要多阶段构建

### 2.1 单阶段构建的问题

```
一个 Node.js 项目的构建过程：

  源代码 + package.json
       │
       ▼
  npm install          ← 安装所有依赖（包括 devDependencies）
       │
       ▼
  npm run build        ← 编译 TypeScript / 打包
       │
       ▼
  产物（dist/）
       │
       ▼
  node src/index.js    ← 运行只需要：node + 产物 + 生产依赖

  问题：构建工具（TypeScript、Webpack、Babel 等）也被打包进了最终镜像
```

```
单阶段构建的镜像内容：

  ┌─────────────────────────────────────┐
  │           最终镜像                   │
  │                                      │
  │  node:18-alpine         170MB       │
  │  node_modules/          50MB        │
  │  node_modules/.cache/   20MB        │  ← npm 缓存
  │  src/ (源代码)          5MB         │  ← 不需要
  │  TypeScript             30MB        │  ← 运行时不需要
  │  Webpack                20MB        │  ← 运行时不需要
  │                                      │
  │  总计：~295MB                        │
  │  实际需要：~230MB                    │
  └─────────────────────────────────────┘

  浪费了 ~65MB 的空间给构建工具和源代码
```

### 2.2 多阶段构建的思路

```
多阶段构建：

  阶段一（builder）：         阶段二（production）：
  ┌─────────────────┐       ┌─────────────────┐
  │ node:18-alpine  │       │ node:18-alpine  │
  │ + 源代码        │       │ + 产物（dist/）  │
  │ + 所有依赖      │  COPY │ + 生产依赖       │
  │ + 构建工具      │ ────→ │                  │
  │                 │       │                  │
  │ npm install     │       │ 只保留运行需要的  │
  │ npm run build   │       │                  │
  └─────────────────┘       └─────────────────┘
        ~295MB                   ~230MB

  关键：阶段一的构建工具不会进入阶段二
```

## 三、多阶段构建语法

### 3.1 基本语法

```dockerfile
# 阶段一：构建阶段
FROM node:18-alpine AS builder

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

# 阶段二：运行阶段
FROM node:18-alpine AS production

WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package.json ./

CMD ["node", "dist/index.js"]
```

```
关键语法：

  FROM node:18-alpine AS builder
                       ↑
                       给阶段起名字

  COPY --from=builder /app/dist ./dist
              ↑
              从指定阶段复制文件
```

### 3.2 执行流程

```
docker build 的执行流程：

  Step 1: FROM node:18-alpine AS builder    ← 开始阶段一
  Step 2: WORKDIR /app
  Step 3: COPY package.json package-lock.json ./
  Step 4: RUN npm ci
  Step 5: COPY . .
  Step 6: RUN npm run build
                                   ← 阶段一结束

  Step 7: FROM node:18-alpine AS production  ← 开始阶段二
  Step 8: WORKDIR /app
  Step 9: COPY --from=builder /app/dist ./dist  ← 从阶段一复制
  Step 10: COPY --from=builder /app/node_modules ./node_modules
  Step 11: COPY package.json ./
  Step 12: CMD ["node", "dist/index.js"]

  最终镜像只包含阶段二的内容
```

### 3.3 前端项目为什么最终镜像里没有 Node.js？

```
思考：为什么前端项目的 Dockerfile 只有两行 FROM？

  React / Vue / Angular 项目 build 之后就是纯静态文件：
    index.html + JS + CSS + 图片

  运行时只需要一个 HTTP 服务器（nginx）来托管这些文件，
  根本不需要 Node.js。

  所以：
    第一阶段 FROM node:18  → 用来编译源码
    第二阶段 FROM nginx    → 只拷贝编译产物

  最终镜像里只有 nginx + 静态文件，Node.js 完全不在里面。
```

```dockerfile
# 前端项目多阶段构建示例

# ---- 构建阶段 ----
FROM node:18-alpine AS builder

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

# ---- 运行阶段 ----
FROM nginx:1.25-alpine

# 复制自定义 Nginx 配置
COPY nginx.conf /etc/nginx/conf.d/default.conf

# 从构建阶段复制静态文件
COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

对应的 `nginx.conf`：

```nginx
server {
    listen 80;
    server_name localhost;
    root /usr/share/nginx/html;
    index index.html;

    # SPA 路由支持
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 静态资源缓存
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
}
```

## 四、实战示例

### 4.1 Node.js API（TypeScript）

```dockerfile
# ---- 构建阶段 ----
FROM node:18-alpine AS builder

WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci

COPY tsconfig.json ./
COPY src/ ./src/

RUN npm run build

RUN npm prune --production

# ---- 运行阶段 ----
FROM node:18-alpine AS production

WORKDIR /app

# 创建非 root 用户
RUN addgroup -g 1001 -S nodejs \
    && adduser -S nodeuser -u 1001

COPY --from=builder --chown=nodeuser:nodejs /app/dist ./dist
COPY --from=builder --chown=nodeuser:nodejs /app/node_modules ./node_modules
COPY --from=builder --chown=nodeuser:nodejs /app/package.json ./

USER nodeuser

EXPOSE 3000

CMD ["node", "dist/index.js"]
```

### 4.2 Next.js 应用

```dockerfile
# ---- 依赖阶段 ----
FROM node:18-alpine AS deps

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

# ---- 构建阶段 ----
FROM node:18-alpine AS builder

WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .

ENV NEXT_TELEMETRY_DISABLED=1
RUN npm run build

# ---- 运行阶段 ----
FROM node:18-alpine AS runner

WORKDIR /app

ENV NODE_ENV=production
ENV NEXT_TELEMETRY_DISABLED=1

RUN addgroup -g 1001 -S nodejs \
    && adduser -S nextjs -u 1001

COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

USER nextjs

EXPOSE 3000

ENV PORT=3000
ENV HOSTNAME="0.0.0.0"

CMD ["node", "server.js"]
```

## 五、构建目标（--target）

### 5.1 选择性构建

```bash
# 只构建到 builder 阶段（用于调试）
docker build --target builder -t my-app:builder .

# 构建到最后一个阶段（默认）
docker build -t my-app .
```

### 5.2 开发和生产共用一个 Dockerfile

```dockerfile
# ---- 基础阶段 ----
FROM node:18-alpine AS base
WORKDIR /app
COPY package.json package-lock.json ./

# ---- 依赖阶段 ----
FROM base AS deps
RUN npm ci

# ---- 开发阶段 ----
FROM base AS development
COPY --from=deps /app/node_modules ./node_modules
COPY . .
CMD ["npm", "run", "dev"]

# ---- 构建阶段 ----
FROM deps AS builder
COPY . .
RUN npm run build

# ---- 生产阶段 ----
FROM node:18-alpine AS production
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package.json ./
CMD ["node", "dist/index.js"]
```

```bash
# 开发模式
docker build --target development -t my-app:dev .
docker run -d -p 3000:3000 -v $(pwd)/src:/app/src my-app:dev

# 生产模式
docker build --target production -t my-app:prod .
docker run -d -p 3000:3000 my-app:prod
```

## 六、镜像体积优化技巧

### 6.1 选择基础镜像

```
Node.js 18 镜像体积对比：

  node:18              ~900MB   ← 完整版（Debian）
  node:18-slim         ~200MB   ← 精简版（Debian）
  node:18-alpine       ~170MB   ← Alpine 版

  Alpine：
  - 体积最小
  - 使用 musl libc（某些 npm 包可能不兼容原生模块）
  - 适合纯 Node.js 项目

  Slim：
  - 基于 Debian，兼容性好
  - 体积适中
  - 需要编译原生模块时推荐（如 bcrypt、sharp）
```

### 6.2 合并 RUN 并清理

```dockerfile
# ❌ 多层且不清理
RUN apt-get update
RUN apt-get install -y curl
RUN apt-get install -y wget

# ✅ 合并为一层并清理
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl wget \
    && rm -rf /var/lib/apt/lists/*
```

```
清理技巧：

  Debian/Ubuntu：rm -rf /var/lib/apt/lists/*
  Alpine：       apk add --no-cache package
  npm：          npm cache clean --force
  pip：          pip install --no-cache-dir package
```

### 6.3 使用 tini 作为 init 进程

```dockerfile
FROM node:18-alpine

# 安装 tini
RUN apk add --no-cache tini

# 使用 tini 作为入口
ENTRYPOINT ["/sbin/tini", "--"]

CMD ["node", "src/index.js"]
```

```
为什么用 tini？

  Node.js 在容器中作为 PID 1 运行时的问题：
  - 不会正确处理信号（SIGTERM）
  - 子进程可能变成僵尸进程
  - 优雅关闭可能不工作

  tini 解决这些问题，让 Node.js 正确响应容器停止信号
```

## 参考答案

### 练习一

**思路**：分别用单阶段和多阶段构建同一个 TypeScript 项目，对比镜像体积差异，理解多阶段构建的价值。

**答案**：

```bash
# 1. 创建项目
mkdir ts-demo && cd ts-demo
npm init -y
npm install express typescript @types/node @types/express ts-node

# 2. 创建 tsconfig.json
cat > tsconfig.json << 'EOF'
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "commonjs",
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true,
    "esModuleInterop": true
  }
}
EOF

# 3. 创建 src/index.ts
mkdir src
cat > src/index.ts << 'EOF'
import express from 'express';
const app = express();
app.get('/', (req, res) => res.json({ message: 'Hello TypeScript!' }));
app.listen(3000, () => console.log('Server on 3000'));
EOF

# 4. 在 package.json 中添加 build 脚本
# "scripts": { "build": "tsc" }

# 5. 创建单阶段 Dockerfile
cat > Dockerfile.single << 'EOF'
FROM node:18-alpine
WORKDIR /app
COPY . .
RUN npm ci
RUN npx tsc
CMD ["node", "dist/index.js"]
EOF

# 6. 创建多阶段 Dockerfile
cat > Dockerfile.multi << 'EOF'
FROM node:18-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npx tsc
RUN npm prune --production

FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
COPY package.json ./
CMD ["node", "dist/index.js"]
EOF

# 7. 构建并对比
docker build -f Dockerfile.single -t demo:single .
docker build -f Dockerfile.multi -t demo:multi .
docker images demo
# demo:multi 通常比 demo:single 小 30-50MB（少了 typescript、ts-node 等 devDependencies）
```

**要点**：
- 单阶段构建把 TypeScript 编译器等构建工具也打包进了最终镜像
- 多阶段构建只复制编译产物和生产依赖，构建工具不进入最终镜像
- `npm prune --production` 在构建阶段删除 devDependencies，进一步减小体积
- 实际项目中差异可能更大（Webpack、Babel 等工具链体积更大）

### 练习二

**思路**：使用 `--target` 参数选择性构建不同阶段，理解一个 Dockerfile 如何同时服务开发和生产。

**答案**：

```bash
# 使用第五节中的开发/生产共用 Dockerfile

# 开发模式构建
docker build --target development -t demo:dev .
# 生产模式构建
docker build --target production -t demo:prod .

# 对比大小
docker images demo
# demo:dev 更大（包含所有依赖和源代码）
# demo:prod 更小（只有编译产物和生产依赖）

# 开发模式运行（带热更新）
docker run -d -p 3000:3000 -v $(pwd)/src:/app/src demo:dev

# 生产模式运行
docker run -d -p 3000:3000 demo:prod
```

**要点**：
- `--target` 指定构建到哪个阶段，不指定则构建到最后一个阶段
- 开发阶段包含所有依赖，方便调试；生产阶段只包含运行所需
- 同一个 Dockerfile 维护开发和生产配置，减少配置文件数量
- 开发模式可以用 Bind Mount 挂载源码实现热更新

### 练习三

**思路**：用 `--target` 构建到中间阶段，进入容器检查构建产物是否正确。

**答案**：

```bash
# 1. 构建到 builder 阶段
docker build --target builder -t my-app:debug .

# 2. 进入容器检查
docker run -it my-app:debug /bin/sh

# 在容器内检查：
ls -la /app/dist/
# 应该看到编译后的 .js 文件
ls -la /app/node_modules/
# 应该看到所有依赖包
cat /app/dist/index.js
# 检查编译产物是否正确
exit
```

**要点**：
- `--target builder` 只构建到 builder 阶段，不执行后续的生产阶段
- 进入中间镜像可以验证构建产物、检查文件结构、排查构建问题
- 这是调试多阶段构建最有效的方法，比看日志更直观
- 确认产物正确后再构建最终镜像，避免反复构建浪费时间

## 常见误区

- **"多阶段构建只是减少了镜像大小"**：多阶段构建不仅减小体积，更重要的是把构建工具和运行时依赖分离，减少攻击面，提升安全性。
- **"npm install 和 npm ci 效果一样"**：`npm install` 可能更新 lock 文件，导致不同时间构建出不同版本的依赖。Dockerfile 中必须用 `npm ci` 保证可重复构建。
- **"缓存命中了就一定没问题"**：缓存可能导致你使用过期的依赖版本。定期用 `--no-cache` 全量构建，确保依赖是最新的。
- **"Alpine 镜像一定比 Slim 好"**：Alpine 使用 musl libc，某些 npm 原生模块（如 bcrypt、sharp）可能编译失败。需要编译原生模块时，Slim 是更安全的选择。

---

## 工程建议

- **按变化频率排列 Dockerfile 指令**：基础镜像 → 系统依赖 → 依赖文件 → 源代码 → 构建。这样能最大化利用缓存，只重建变化的部分。
- **用 `--target` 调试中间阶段**：构建失败时，用 `docker build --target builder` 只构建到某个阶段，进入容器检查产物，比看日志更直观。
- **前端项目最终镜像用 nginx**：React/Vue/Angular 构建后是静态文件，最终镜像只需要 nginx 托管，不需要 Node.js，体积可以小一个数量级。
- **用 tini 作为 init 进程**：Node.js 作为 PID 1 运行时不会正确处理信号，子进程可能变成僵尸进程。`tini` 解决这个问题，让容器优雅关闭。

---

## 小结

1. **构建缓存**：按层缓存，变化频率低的指令放前面，npm install 可以跳过
2. **npm ci**：Dockerfile 中必须用 npm ci，保证构建可重复
3. **多阶段构建**：把构建环境和运行环境分开，减小镜像体积 30-50%
4. **前端项目**：build 后是静态文件，最终镜像只需要 nginx，不需要 Node.js
5. **`--target`**：可以选择性构建到某个阶段，一个 Dockerfile 同时用于开发和生产
