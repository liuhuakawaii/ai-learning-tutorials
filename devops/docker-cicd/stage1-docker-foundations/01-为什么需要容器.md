# 第一课：为什么需要容器

> **课程定位**：Docker 零基础入门第一课，帮你理解"为什么"比"怎么用"更重要
> **前置知识**：会基本的命令行操作，了解 Web 应用的运行方式
> **预计时长**：30 分钟

---

## 场景引入

你刚加入一个团队，花了两天时间在本地把项目跑起来了。同事说"你提交个 PR 吧"，CI 流水线一跑，红了——测试环境的 Node 版本是 16，你本地是 18，某个 API 不兼容。你改了半天兼容代码，终于 CI 过了。结果部署到生产环境，又报错了——服务器上少装了一个系统库。你开始怀疑：到底有没有一种方式，能让"在我电脑上能跑"这件事，在任何地方都成立？

## 一、"在我电脑上能跑啊"

### 1.1 开发者最头疼的一句话

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   开发者："我电脑上能跑啊！"                                  │
│   运维：  "我这里跑不起来。"                                  │
│                                                             │
│   ┌──────────┐              ┌──────────┐                    │
│   │ 开发者电脑 │    ≠        │ 服务器    │                    │
│   │          │              │          │                    │
│   │ Node 18  │              │ Node 16  │                    │
│   │ npm 9    │              │ npm 8    │                    │
│   │ macOS    │              │ Ubuntu   │                    │
│   │ 本地数据库│              │ 无数据库  │                    │
│   └──────────┘              └──────────┘                    │
│                                                             │
│   环境不同 → 行为不同 → 结果不同                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

这个问题困扰了软件行业几十年。根本原因是：**每台机器的环境不一样。**

### 1.2 环境差异到底在哪？

```
一个 Web 应用的运行依赖：

  ┌─────────────────────────────────────────┐
  │            你的应用代码                   │
  │         （这部分你控制得了）               │
  ├─────────────────────────────────────────┤
  │  运行时        Node.js / Python / Java   │
  │  依赖包        npm / pip / maven         │
  │  系统库        libc / openssl / zlib     │
  │  操作系统      Ubuntu / CentOS / macOS   │
  │  内核          Linux kernel              │
  │  硬件          x86 / ARM                 │
  └─────────────────────────────────────────┘
     ↑ 这些你控制不了，但它们影响你的应用
```

任何一个层面的差异，都可能导致应用行为不同：

| 差异点 | 常见问题 |
|--------|---------|
| Node.js 版本 | API 不兼容，新特性不可用 |
| 系统库版本 | `glibc` 版本不同导致编译失败 |
| 操作系统 | Windows 路径 vs Linux 路径 |
| 环境变量 | 缺少 `DATABASE_URL` 导致连接失败 |
| 依赖版本 | 锁文件不一致导致安装不同版本 |

### 1.3 传统解决方案的痛点

在容器出现之前，人们尝试过很多方案：

```
方案一：文档记录
  └── 写一个 SETUP.md，记录所有安装步骤
      └── 问题：容易遗漏、过时、不同人理解不同

方案二：配置管理脚本
  └── 写 shell 脚本自动化安装
      └── 问题：不同系统不兼容，维护成本高

方案三：虚拟机镜像
  └── 打包整个操作系统
      └── 问题：太大、太慢、太重

方案四：包管理器版本锁定
  └── package-lock.json / requirements.txt
      └── 问题：只管了依赖包，没管系统环境
```

这些方案都有一个共同问题：**没有把"运行环境"当作代码来管理。**

## 二、虚拟机 vs 容器

### 2.1 虚拟机：模拟一整台电脑

虚拟机（Virtual Machine）是最早尝试解决环境一致性问题的方案：

```
┌─────────────────────────────────────────────────┐
│                物理服务器                         │
│                                                  │
│  ┌──────────────┐  ┌──────────────┐             │
│  │   虚拟机 1    │  │   虚拟机 2    │             │
│  │ ┌──────────┐ │  │ ┌──────────┐ │             │
│  │ │  Ubuntu   │ │  │ │  CentOS  │ │             │
│  │ │  App A    │ │  │ │  App B   │ │             │
│  │ └──────────┘ │  │ └──────────┘ │             │
│  │   完整的OS    │  │   完整的OS    │             │
│  └──────────────┘  └──────────────┘             │
│                                                  │
│  ┌──────────────────────────────────┐           │
│  │          Hypervisor              │           │
│  │      （虚拟化层）                  │           │
│  └──────────────────────────────────┘           │
│  ┌──────────────────────────────────┐           │
│  │          宿主机操作系统            │           │
│  └──────────────────────────────────┘           │
└─────────────────────────────────────────────────┘
```

**虚拟机的问题：**

```
每个虚拟机包含：
  ├── 完整的操作系统        →  几 GB
  ├── 系统内核              →  重复加载
  ├── 系统服务              →  大部分用不到
  └── 你的应用              →  只有这部分是你需要的

  启动时间：分钟级
  磁盘占用：GB 级
  内存占用：GB 级
```

### 2.2 容器：只打包应用需要的部分

容器（Container）换了一个思路：不模拟整台电脑，只打包应用和它的依赖。

```
┌─────────────────────────────────────────────────┐
│                物理服务器                         │
│                                                  │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐   │
│  │容器 1   │ │容器 2   │ │容器 3   │ │容器 4   │   │
│  │App A   │ │App B   │ │App C   │ │App D   │   │
│  │依赖 A  │ │依赖 B  │ │依赖 C  │ │依赖 D  │   │
│  └────────┘ └────────┘ └────────┘ └────────┘   │
│                                                  │
│  ┌──────────────────────────────────┐           │
│  │        容器运行时 (Docker)        │           │
│  └──────────────────────────────────┘           │
│  ┌──────────────────────────────────┐           │
│  │          宿主机操作系统            │           │
│  └──────────────────────────────────┘           │
└─────────────────────────────────────────────────┘
```

### 2.3 对比

```
┌─────────────┬──────────────────┬──────────────────┐
│   维度       │     虚拟机        │      容器         │
├─────────────┼──────────────────┼──────────────────┤
│ 隔离级别     │ 硬件级（完整OS）  │ 进程级（共享内核） │
│ 启动时间     │ 分钟              │ 秒               │
│ 磁盘占用     │ GB               │ MB               │
│ 内存占用     │ GB               │ MB               │
│ 性能损耗     │ 5-15%            │ 接近 0%           │
│ 隔离强度     │ 强               │ 较强              │
│ 密度         │ 一台机器跑几个    │ 一台机器跑几十个   │
│ 适用场景     │ 需要不同OS内核    │ 应用级隔离         │
└─────────────┴──────────────────┴──────────────────┘
```

**一句话总结：** 虚拟机模拟的是"电脑"，容器模拟的是"进程运行环境"。

## 三、容器解决的三个核心问题

### 3.1 一致性：在哪跑都一样

```
没有容器：
  开发者电脑 → "能跑"
  测试环境   → "报错了"
  生产环境   → "又不一样了"

有了容器：
  ┌──────────┐    ┌──────────┐    ┌──────────┐
  │  开发环境  │    │  测试环境  │    │  生产环境  │
  │          │    │          │    │          │
  │ ┌──────┐ │    │ ┌──────┐ │    │ ┌──────┐ │
  │ │ 容器  │ │ =  │ │ 容器  │ │ =  │ │ 容器  │ │
  │ │      │ │    │ │      │ │    │ │      │ │
  │ │App   │ │    │ │App   │ │    │ │App   │ │
  │ │依赖   │ │    │ │依赖   │ │    │ │依赖   │ │
  │ │配置   │ │    │ │配置   │ │    │ │配置   │ │
  │ └──────┘ │    │ └──────┘ │    │ └──────┘ │
  └──────────┘    └──────────┘    └──────────┘

  同一个镜像 → 同一个行为
```

### 3.2 可移植性：一次构建，到处运行

```
构建一次镜像，可以部署到：

  Docker 镜像
      │
      ├── 本地开发机（macOS / Windows / Linux）
      ├── 测试服务器（Ubuntu）
      ├── 生产服务器（CentOS）
      ├── 云服务（AWS / GCP / 阿里云）
      └── CI/CD 环境（GitHub Actions）

  不需要重新编译，不需要调整配置
```

### 3.3 隔离性：互不干扰

```
同一台服务器上运行多个应用：

  ┌─────────────────────────────────────────┐
  │              宿主机                      │
  │                                          │
  │  ┌──────────┐  ┌──────────┐             │
  │  │ Node 18  │  │ Node 20  │             │
  │  │ App v1   │  │ App v2   │  ← 版本不同 │
  │  │ port 3000│  │ port 3000│  ← 端口不冲突│
  │  └──────────┘  └──────────┘             │
  │                                          │
  │  ┌──────────┐  ┌──────────┐             │
  │  │ PostgreSQL│  │  MySQL   │             │
  │  │ 5432     │  │ 3306     │  ← 数据隔离 │
  │  └──────────┘  └──────────┘             │
  └─────────────────────────────────────────┘

  每个容器有自己独立的：
  ├── 文件系统
  ├── 网络空间
  ├── 进程空间
  └── 资源配额
```

## 四、Docker 是什么

### 4.1 一句话定义

> **Docker 是一个开源的容器化平台，让你可以把应用和它的运行环境打包成一个标准化的单元（容器），在任何地方一致地运行。**

### 4.2 Docker 的核心组件

```
┌─────────────────────────────────────────────────────┐
│                    Docker 架构                        │
│                                                      │
│  ┌─────────────────────────────────────────────────┐ │
│  │              Docker Client                       │ │
│  │         （docker 命令行工具）                      │ │
│  └──────────────────────┬──────────────────────────┘ │
│                         │                            │
│                         ▼                            │
│  ┌─────────────────────────────────────────────────┐ │
│  │              Docker Daemon                       │ │
│  │         （dockerd - 后台服务）                     │ │
│  │                                                  │ │
│  │  ┌───────────┐  ┌───────────┐  ┌───────────┐   │ │
│  │  │  镜像管理  │  │  容器管理  │  │  网络管理  │   │ │
│  │  └───────────┘  └───────────┘  └───────────┘   │ │
│  └─────────────────────────────────────────────────┘ │
│                                                      │
│  ┌─────────────────────────────────────────────────┐ │
│  │              Docker Registry                     │ │
│  │         （镜像仓库，如 Docker Hub）                │ │
│  └─────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────┘
```

### 4.3 Docker 的工作流程

```
开发者视角的完整流程：

  1. 写 Dockerfile        ← 描述"怎么构建环境"
     │
     ▼
  2. docker build         ← 构建镜像（打包应用+环境）
     │
     ▼
  3. 镜像 (Image)         ← 一个只读的模板
     │
     ▼
  4. docker run           ← 启动容器（镜像的运行实例）
     │
     ▼
  5. 容器 (Container)     ← 应用在里面跑

  类比：
    Dockerfile = 菜谱
    镜像       = 半成品菜
    容器       = 做好的菜
```

### 4.4 用前端思维理解

```
前端开发者的类比：

  Dockerfile      ≈  package.json + webpack.config.js
                    （描述项目依赖和构建方式）

  镜像 (Image)    ≈  node_modules + 打包产物
                    （构建好的、可以直接运行的东西）

  容器 (Container) ≈  npm start 跑起来的进程
                    （正在运行的应用实例）

  Docker Hub      ≈  npm registry
                    （存储和分发镜像的仓库）
```

## 五、容器在开发生命周期中的位置

### 5.1 开发到上线的完整流程

```
┌─────────────────────────────────────────────────────────────┐
│                   应用生命周期                                │
│                                                              │
│  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐        │
│  │  编码   │──→│  构建   │──→│  测试   │──→│  部署   │        │
│  └────────┘   └────────┘   └────────┘   └────────┘        │
│       │            │            │            │               │
│       ▼            ▼            ▼            ▼               │
│  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐        │
│  │Dockerfile│  │docker  │   │docker  │   │docker  │        │
│  │        │   │ build  │   │ run    │   │ run    │        │
│  │编写环境 │   │构建镜像 │   │启动容器 │   │生产部署 │        │
│  │描述文件 │   │        │   │跑测试  │   │        │        │
│  └────────┘   └────────┘   └────────┘   └────────┘        │
│                                                              │
│  同一个镜像在每个阶段的行为一致                                 │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 没有容器 vs 有容器

```
没有容器的部署流程：

  1. 写代码
  2. 手动在服务器上安装 Node.js
  3. 手动安装依赖
  4. 手动配置环境变量
  5. 手动启动应用
  6. 换一台服务器？重复步骤 2-5
  7. 服务器出问题？重新来一遍

有容器的部署流程：

  1. 写代码 + 写 Dockerfile
  2. docker build（构建镜像）
  3. docker run（启动容器）
  4. 换一台服务器？docker run
  5. 服务器出问题？docker run（秒级恢复）
```

## 六、Docker 的实际应用场景

### 6.1 本地开发环境

```
场景：新同事入职，需要搭建开发环境

没有容器：
  1. 安装 Node.js 18
  2. 安装 PostgreSQL 14
  3. 安装 Redis 7
  4. 创建数据库
  5. 导入初始数据
  6. 配置环境变量
  7. 可能遇到各种版本冲突...
  耗时：半天到一天

有容器：
  1. git clone 项目
  2. docker compose up
  耗时：5 分钟
```

### 6.2 CI/CD 流水线

```
GitHub Actions 中使用容器：

  PR 提交
    │
    ▼
  ┌──────────────────────────────────────┐
  │  GitHub Actions Runner               │
  │                                      │
  │  ┌──────────────────────────────┐   │
  │  │  容器：Node.js 18            │   │
  │  │  ├── npm install             │   │
  │  │  ├── npm run lint            │   │
  │  │  ├── npm test                │   │
  │  │  └── npm run build           │   │
  │  └──────────────────────────────┘   │
  └──────────────────────────────────────┘
    │
    ▼
  部署到生产环境

  每次构建环境完全一致，不会因为 Runner 更新而出问题
```

### 6.3 微服务架构

```
一个电商系统的微服务拆分：

  ┌─────────┐  ┌─────────┐  ┌─────────┐
  │ 用户服务  │  │ 商品服务  │  │ 订单服务  │
  │ Node.js │  │ Python  │  │ Go      │
  └─────────┘  └─────────┘  └─────────┘
       │            │            │
       └────────────┼────────────┘
                    │
  ┌─────────────────┼─────────────────┐
  │                 ▼                 │
  │  ┌─────────┐  ┌─────────┐       │
  │  │ PostgreSQL│  │  Redis  │       │
  │  └─────────┘  └─────────┘       │
  │         同一台宿主机               │
  └───────────────────────────────────┘

  每个服务用不同语言、不同版本，互不影响
```

## 参考答案

### 练习一

**思路**：以一个典型的 Node.js + PostgreSQL 项目为例，逐层梳理运行依赖，从应用层到系统层不遗漏。

**答案**：

以一个 Express + PostgreSQL 的全栈项目为例，完整环境依赖清单：

| 类别 | 依赖项 | 版本要求 | 说明 |
|------|--------|---------|------|
| 编程语言 | Node.js | 18.x | LTS 版本，部分 API 在 16 中不可用 |
| 包管理器 | npm | 9.x | 需与 Node.js 版本匹配 |
| 数据库 | PostgreSQL | 14.x | 需要安装并初始化 |
| 缓存 | Redis | 7.x | 用于 session 和缓存 |
| 系统依赖 | python3 | 3.10+ | node-gyp 编译原生模块需要 |
| 系统依赖 | build-essential | - | C++ 编译器，bcrypt 等模块需要 |
| 系统依赖 | libpq-dev | - | PostgreSQL 客户端库 |
| 环境变量 | DATABASE_URL | - | 数据库连接字符串 |
| 环境变量 | REDIS_URL | - | Redis 连接字符串 |
| 环境变量 | NODE_ENV | - | 运行环境标识 |
| 环境变量 | JWT_SECRET | - | 签名密钥 |

搬到全新电脑的耗时估计：
- 有经验的开发者：2-4 小时（可能遇到各种版本冲突、系统库缺失）
- 新人：半天到一天（需要排查各种环境问题）
- 如果涉及不同操作系统（如 macOS → Linux）：可能需要额外 1-2 天调试兼容性

**要点**：
- 环境依赖不仅仅是 npm 包，还包括运行时、系统库、环境变量
- 跨操作系统时路径、编译工具链差异是最大的坑
- 这正是容器要解决的核心问题——把这些依赖全部打包成一个标准化单元

### 练习二

**思路**：判断标准是"是否需要环境一致性"和"是否需要隔离"，同时考虑复杂度是否值得容器化。

**答案**：

| 场景 | 是否适合容器化 | 理由 |
|------|--------------|------|
| A：静态 HTML 网站 | 不太适合 | 没有运行时依赖，一个 nginx 就能搞定，容器化增加复杂度但收益小 |
| B：GPU 机器学习训练 | 不太适合 | 容器对 GPU 直通支持有限，需要 nvidia-docker 等特殊配置，且训练任务通常在专用集群上运行 |
| C：Node.js API + PostgreSQL | 非常适合 | 多服务架构，需要环境一致性，容器间通信方便，docker-compose 一键启动 |
| D：访问 USB 设备的应用 | 不太适合 | 容器对硬件设备访问支持有限，需要 `--privileged` 或设备映射，牺牲了隔离性 |
| E：Next.js 多服务器部署 | 非常适合 | 容器化后镜像一致，部署到任意服务器行为相同，天然适合水平扩展 |

**要点**：
- 容器化的价值在于"环境一致性"和"多服务编排"，不是所有场景都需要
- 涉及硬件直通、GPU 等特殊资源时，容器化的复杂度可能超过收益
- 微服务、全栈项目、多环境部署是容器化的最佳场景

### 练习三

**思路**：以一个典型的全栈项目为例，拆分为独立容器，明确每个容器的职责、通信方式和数据持久化需求。

**答案**：

以一个"任务管理系统"（Node.js API + PostgreSQL + Redis + Nginx 前端）为例：

```
┌─────────────────────────────────────────────────┐
│                  宿主机                          │
│                                                  │
│  ┌──────────────┐  ┌──────────────┐             │
│  │  nginx 容器   │  │  node-api    │             │
│  │  (前端静态文件)│  │  (Express)   │             │
│  │  port: 80    │  │  port: 3000  │             │
│  └──────┬───────┘  └──────┬───────┘             │
│         │                 │                      │
│         └────────┬────────┘                      │
│                  │                               │
│         ┌────────┴────────┐                      │
│         │  app-network    │                      │
│         └────────┬────────┘                      │
│                  │                               │
│  ┌───────────────┴──────────────┐               │
│  │                              │               │
│  ┌──────────────┐  ┌───────────┴──┐             │
│  │  postgres    │  │  redis       │             │
│  │  port: 5432  │  │  port: 6379  │             │
│  └──────────────┘  └──────────────┘             │
│                                                  │
│  持久化卷：                                      │
│  ├── pgdata → /var/lib/postgresql/data           │
│  └── redis-data → /data                          │
└─────────────────────────────────────────────────┘
```

需要的容器：4 个（nginx、node-api、postgres、redis）
通信方式：所有容器加入同一个自定义网络 `app-network`，通过容器名互相访问
需要持久化的数据：
- PostgreSQL 数据 → Named Volume `pgdata`
- Redis 数据 → Named Volume `redis-data`
- 上传的文件 → Named Volume `uploads`

**要点**：
- 每个容器只跑一个服务，职责单一
- 容器间通过自定义网络 + 容器名通信，不需要暴露内部端口到宿主机
- 只有 nginx 需要 `-p 80:80` 对外暴露，其他容器只在内部网络通信
- 有状态服务（数据库、缓存）必须用 Named Volume 持久化

## 常见误区

- **"容器就是轻量级虚拟机"**：容器和虚拟机的隔离机制完全不同，容器共享宿主机内核，不模拟硬件。把容器当虚拟机用会导致安全和资源管理上的误判。
- **"Docker 能解决所有环境问题"**：Docker 解决了运行环境一致性，但不解决代码质量问题。如果代码本身有 bug，容器化后 bug 还在。
- **"容器化之后就不需要了解操作系统了"**：容器底层还是 Linux，理解文件权限、网络、进程管理对排查问题至关重要。
- **"每个应用都需要容器化"**：简单的静态网站、一次性脚本用容器化反而增加复杂度，要根据场景判断。

---

## 工程建议

- **从开发环境开始容器化**：不要直接上生产，先在本地用 Docker 搭建开发环境，让团队成员都用同一套环境，验证容器化方案可行后再推进 CI/CD。
- **用 docker-compose 管理多服务项目**：真实项目通常需要数据库、缓存等多个服务，docker-compose 能一键启动整套环境，比逐个 `docker run` 高效得多。
- **把 Dockerfile 当代码维护**：Dockerfile 应该纳入版本控制，和应用代码一起 review，记录每次变更的原因。
- **定期更新基础镜像**：基础镜像中的系统库会有安全漏洞，定期更新（至少每月一次）是基本的安全卫生。

## 小结

本课的核心要点：

1. **"在我电脑上能跑"问题**：本质是每台机器的运行环境不一致
2. **虚拟机 vs 容器**：虚拟机模拟整台电脑（重），容器只打包应用环境（轻）
3. **容器三大优势**：一致性（在哪跑都一样）、可移植性（一次构建到处运行）、隔离性（互不干扰）
4. **Docker 核心概念**：Dockerfile → 镜像 → 容器，就像菜谱 → 半成品 → 成品
5. **容器的价值**：把"运行环境"当作代码来管理，实现环境的版本控制和可重复性
