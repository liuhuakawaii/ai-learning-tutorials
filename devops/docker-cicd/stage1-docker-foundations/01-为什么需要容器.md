# 为什么需要容器

> 前置知识：会基本的命令行操作，了解 Web 应用的运行方式

## 一个真实的排查现场

周五下午四点，你把开发了两周的 Node.js API 提交了 PR。CI 流水线跑起来，红了。

```
Error: Cannot find module 'bcrypt'
  at Function.Module._resolveFilename (internal/modules/cjs/loader.js:880:15)
```

你本地跑得好好的，bcrypt 装得好好的。打开 CI 日志一看——Runner 的 Node 版本是 16.13，你本地是 18.17。bcrypt 的原生编译在这两个版本上产物不同。

你花了一小时把 CI 的 Node 版本改成和本地一致。CI 过了。部署到测试环境，又报了另一个错：

```
/lib/x86_64-linux-gnu/libc.so.6: version `GLIBC_2.28' not found
```

测试服务器是 Ubuntu 18.04，glibc 版本太老。你又花了一小时改 Dockerfile——等一下，项目还没有 Dockerfile。

这就是"在我电脑上能跑"问题的完整复现链：**不是你的代码有 bug，是你的代码运行的环境在每一层都不一样。**

## 环境差异到底在哪

一个 Web 应用的运行依赖是分层的：

```
┌─────────────────────────────────────────┐
│            你的应用代码                   │
│         （这部分你控制得了）               │
├─────────────────────────────────────────┤
│  运行时        Node.js 16 vs 18         │
│  依赖包        bcrypt 5.0 vs 5.1        │
│  系统库        glibc 2.27 vs 2.31       │
│  操作系统      Ubuntu 18 vs 22          │
│  内核          4.15 vs 5.15             │
└─────────────────────────────────────────┘
     ↑ 这些你控制不了，但它们决定你的代码能不能跑
```

任何一个层面的差异都可能导致行为不同。传统解决方案——文档记录、Shell 脚本、锁文件——只管了其中一两层。**没有一种方案把"完整的运行环境"当作一个可版本控制、可复制、可分发的单元。**

容器就是来做这件事的。

## 容器解决了什么

把上面那个排查现场反过来想：如果有一种技术，能把"Node 18 + bcrypt 5.1 + glibc 2.31 + Ubuntu 22"打包成一个文件，在任何机器上解压就能跑——CI 和生产环境拿到的是同一个包——那些问题就不存在了。

这个包就是容器镜像。运行中的包就是容器。

```
┌─────────────────────────────────────────────────┐
│                物理服务器                         │
│                                                  │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐   │
│  │容器 1   │ │容器 2   │ │容器 3   │ │容器 4   │   │
│  │Node 18 │ │Node 16 │ │Python  │ │Go      │   │
│  │App A   │ │App B   │ │App C   │ │App D   │   │
│  └────────┘ └────────┘ └────────┘ └────────┘   │
│                                                  │
│  ┌──────────────────────────────────┐           │
│  │        容器运行时 (Docker)        │           │
│  └──────────────────────────────────┘           │
│  ┌──────────────────────────────────┐           │
│  │          宿主机操作系统            │           │
│  └──────────────────────────────────┘           │
└─────────────────────────────────────────────────┘
```

每个容器有自己的文件系统、网络空间、进程空间，互不干扰。容器共享宿主机内核，不需要像虚拟机那样模拟整台电脑，所以启动是秒级，内存开销是 MB 级。

## 容器 vs 虚拟机

容器不是轻量级虚拟机。它们的隔离机制完全不同：

```
┌─────────────┬──────────────────┬──────────────────┐
│   维度       │     虚拟机        │      容器         │
├─────────────┼──────────────────┼──────────────────┤
│ 隔离级别     │ 硬件级（完整OS）  │ 进程级（共享内核） │
│ 启动时间     │ 分钟              │ 秒               │
│ 磁盘占用     │ GB               │ MB               │
│ 隔离强度     │ 强               │ 较强              │
│ 适用场景     │ 需要不同OS内核    │ 应用级隔离         │
└─────────────┴──────────────────┴──────────────────┘
```

虚拟机模拟的是"电脑"，容器模拟的是"进程运行环境"。大多数 Web 应用不需要模拟整台电脑，只需要保证运行环境一致——这正是容器的用武之地。

## Docker 是什么

Docker 是目前最主流的容器运行时。它的核心工作流只有三步：

```
1. 写 Dockerfile        ← 描述"怎么构建环境"
       ↓
2. docker build         ← 构建镜像（打包应用+环境）
       ↓
3. docker run           ← 启动容器（镜像的运行实例）
```

用前端思维类比：Dockerfile 是 `package.json + webpack.config.js`，镜像是 `node_modules + 打包产物`，容器是 `npm start` 跑起来的进程。

## 回到开头的问题

如果那个项目一开始就有 Dockerfile：

```dockerfile
FROM node:18.17-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
CMD ["node", "dist/index.js"]
```

CI 和测试环境用的是同一个镜像，Node 版本、系统库、依赖版本全部锁死。那些排查时间可以省下来写功能代码。

## 练习

### 练习一：环境依赖清单

列出你当前项目运行所需的全部环境依赖，至少包括运行时版本、系统库、数据库、环境变量。如果让你把这些搬到一台全新电脑上，需要多久？

### 练习二：场景判断

以下场景哪些适合用容器，哪些不适合？说明理由。

- A：一个静态 HTML 网站
- B：一个需要 GPU 的机器学习训练任务
- C：一个 Node.js API + PostgreSQL 的全栈项目
- D：一个 Next.js 应用，需要在三台服务器上部署

### 练习三：画架构图

为你当前正在开发的项目画一个容器化后的架构图。需要哪些容器？哪些数据需要持久化？容器之间如何通信？

## 参考答案

### 练习一

以 Express + PostgreSQL 项目为例：

| 类别 | 依赖项 | 版本要求 |
|------|--------|---------|
| 运行时 | Node.js | 18.x LTS |
| 系统依赖 | python3, build-essential | bcrypt 等原生模块编译需要 |
| 数据库 | PostgreSQL | 14.x |
| 缓存 | Redis | 7.x |
| 环境变量 | DATABASE_URL, JWT_SECRET, NODE_ENV | - |

搬到全新电脑的耗时：有经验 2-4 小时，新人半天到一天，跨 OS 可能需要 1-2 天。**这正是容器要解决的痛点。**

### 练习二

| 场景 | 适合容器化？ | 理由 |
|------|------------|------|
| A：静态 HTML | 不太适合 | 没有运行时依赖，nginx 就够了 |
| B：GPU 训练 | 不太适合 | 需要 nvidia-docker 特殊配置 |
| C：Node.js + PG | 非常适合 | 多服务编排，环境一致性 |
| D：Next.js 多服务器 | 非常适合 | 镜像一致，天然适合水平扩展 |

### 练习三

一个典型的全栈项目容器化架构：

```
宿主机
├── nginx 容器（前端静态文件，port 80）
├── node-api 容器（Express，port 3000，内部网络）
├── postgres 容器（port 5432，Named Volume 持久化）
└── redis 容器（port 6379，Named Volume 持久化）

通信方式：自定义网络 app-network，通过容器名互相访问
对外暴露：只有 nginx 的 80 端口
```

要点：每个容器只跑一个服务；有状态服务必须用 Named Volume；容器间通过自定义网络 + 容器名通信。
