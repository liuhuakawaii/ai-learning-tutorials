# 测试思维与原则

## 先看一个失败的测试

```typescript
// 这个测试覆盖了 convertTemperature 函数，覆盖率 100%
function convertTemperature(celsius: number): number {
  if (typeof celsius !== 'number') throw new Error('输入必须是数字')
  return celsius * 9 / 5 + 32
}

test('温度转换', () => {
  expect(convertTemperature(100)).toBe(212) // 只测了 happy path
})
```

覆盖率 100%，但没有测 `typeof celsius !== 'number'` 的分支。如果有人传了字符串 `"100"`，函数会抛异常，测试不会发现。

这说明一个问题：**覆盖率不等于测试质量**。你需要的是正确的测试策略，而不是更多的测试。

## 测试金字塔：比例比数量重要

```
        /  E2E  \          ← 少量：验证关键业务流程
       /----------\
      /  集成测试   \       ← 适量：验证模块协作
     /--------------\
    /    单元测试     \     ← 大量：验证独立逻辑
   /__________________\
```

为什么是金字塔而不是倒三角？因为 E2E 测试又慢又脆弱：

```typescript
// E2E 测试：启动浏览器、填写表单、点击提交、检查数据库
test('用户注册流程', async () => {
  await browser.goto('/register')
  await browser.fill('#email', 'test@example.com')
  await browser.fill('#password', 'StrongPass123!')
  await browser.click('#submit')
  const user = await db.query('SELECT * FROM users WHERE email = ?', ['test@example.com'])
  expect(user).toBeTruthy()
})
// 运行时间：10 秒+
// 失败原因：可能是邮箱验证、数据库连接、前端按钮 ID 变了
```

分层后的做法：

```typescript
// 单元测试：验证邮箱格式（< 1ms）
test('验证邮箱格式', () => {
  expect(isValidEmail('test@example.com')).toBe(true)
  expect(isValidEmail('invalid')).toBe(false)
})

// 集成测试：验证注册服务（~100ms）
test('注册服务写入数据库', async () => {
  const user = await registerService.create('test@example.com', 'StrongPass123!')
  expect(user.id).toBeDefined()
})

// E2E：只覆盖最关键的 happy path（1-2 个）
test('完整注册流程', async () => { /* ... */ })
```

## FIRST 原则：判断测试质量的标尺

**Fast**：单元测试应该毫秒级完成。如果一个测试要等几秒，它要么不是单元测试，要么被测代码有设计问题。

**Isolated**：每个测试独立运行，不依赖其他测试的执行顺序或状态。

```typescript
// 错误：测试之间有依赖
let sharedUser: User
test('创建用户', async () => { sharedUser = await createUser('test@example.com') })
test('修改用户名', async () => { await updateUser(sharedUser.id, { name: '新名字' }) })

// 正确：每个测试自己准备数据
test('修改用户名', async () => {
  const user = await createUser('test@example.com')
  const updated = await updateUser(user.id, { name: '新名字' })
  expect(updated.name).toBe('新名字')
})
```

**Repeatable**：无论运行多少次，结果都一样。不依赖当前时间、随机数、外部服务。

**Self-validating**：测试通过或失败，不需要人工判断。`console.log` 不是断言。

**Timely**：测试应该在编写功能代码的同时编写，而不是事后补。

## AAA 模式：让测试可读

```typescript
describe('购物车', () => {
  test('添加商品后总价应更新', () => {
    // Arrange（准备）
    const cart = new ShoppingCart()
    const product = { id: '1', name: '手机', price: 2999 }

    // Act（执行）
    cart.add(product, 1)

    // Assert（断言）
    expect(cart.totalPrice()).toBe(2999)
    expect(cart.itemCount()).toBe(1)
  })
})
```

AAA 的好处是可读性。任何人看到测试，都能快速理解：准备了什么、做了什么、验证了什么。

当 Arrange 部分变长时，提取到 `beforeEach` 或工厂函数。

## TDD 的红-绿-重构

TDD 的核心循环：

1. **红**：先写一个失败的测试
2. **绿**：写最少量的代码让测试通过
3. **重构**：优化代码，保持测试通过

```typescript
// 红：fizzBuzz 还不存在，测试失败
test('输入 3 返回 "Fizz"', () => {
  expect(fizzBuzz(3)).toBe('Fizz')
})

// 绿：最简实现
function fizzBuzz(n: number): string {
  if (n % 3 === 0) return 'Fizz'
  return String(n)
}

// 继续红-绿：输入 5 返回 "Buzz" 失败 → 加代码 → 通过
// 重构：
function fizzBuzz(n: number): string {
  const rules: [number, string][] = [[15, 'FizzBuzz'], [3, 'Fizz'], [5, 'Buzz']]
  for (const [divisor, word] of rules) {
    if (n % divisor === 0) return word
  }
  return String(n)
}
```

TDD 不是所有场景都适用。但对于有明确输入输出的纯函数，它是最好的开发方式。

## 三个最常见的测试错误

**测试实现细节而非行为**：用 `spyOn` 验证内部方法调用，重构时测试就挂。应该测试行为——输入什么，输出什么。

**测试中包含复杂逻辑**：if/else、循环。如果测试比被测代码还复杂，说明测试写错了。

**追求 100% 覆盖率**：100% 行覆盖率不等于没有 bug。合理目标是核心逻辑 90%+，整体 75-85%。

## 参考答案

### 练习一

- testA：单元测试 — 只测试纯函数，无外部依赖
- testB：集成测试 — 涉及订单服务和库存服务的协作
- testC：E2E 测试 — 从用户视角覆盖完整浏览器流程

### 练习二

问题：`toBe` 做引用比较，`new Date()` 每次创建新对象，即使时间相同也不相等。

```typescript
test('订单创建时间', () => {
  const before = Date.now()
  const order = createOrder()
  const after = Date.now()
  expect(order.createdAt.getTime()).toBeGreaterThanOrEqual(before)
  expect(order.createdAt.getTime()).toBeLessThanOrEqual(after)
})
```

### 练习三

```typescript
// 测试先行
describe('truncate', () => {
  test('短字符串不截断', () => { expect(truncate('hello', 10)).toBe('hello') })
  test('超长字符串截断加省略号', () => { expect(truncate('hello world', 8)).toBe('hello...') })
  test('刚好等于长度不截断', () => { expect(truncate('hello', 5)).toBe('hello') })
  test('maxLength 为 3 时截断到省略号', () => { expect(truncate('hello', 3)).toBe('...') })
  test('maxLength 小于 3 抛出异常', () => { expect(() => truncate('hello', 2)).toThrow() })
})

// 实现
function truncate(str: string, maxLength: number): string {
  if (maxLength < 3) throw new Error('maxLength 必须 >= 3')
  if (str.length <= maxLength) return str
  return str.slice(0, maxLength - 3) + '...'
}
```
