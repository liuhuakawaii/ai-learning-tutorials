# 测试思维与原则

## 场景引入

小王刚接手一个电商项目，前任开发者留下了 2000 多个测试用例，运行一次要 15 分钟。更糟糕的是，这些测试大部分是端到端测试——打开浏览器、模拟用户点击、等待页面加载。每次改一行代码，CI 要跑半小时才能给出反馈。团队开始跳过测试，"反正也来不及等结果"。

与此同时，另一个团队的项目只有 500 个测试用例，3 分钟跑完，但他们几乎没有线上 bug。区别在哪？不是测试数量，而是**测试策略**。

这一课，我们从测试的底层思维开始，建立正确的测试心智模型。

## 学习目标

- 理解测试金字塔的结构和各层的比例关系
- 掌握 FIRST 原则，判断测试质量
- 熟练使用 AAA 模式编写结构清晰的测试
- 理解 TDD 的红-绿-重构循环

## 测试金字塔

### 什么是测试金字塔

测试金字塔由 Mike Cohn 在 2009 年提出，它描述了不同层级测试的理想比例：

```
        /  E2E  \          ← 少量：验证关键业务流程
       /----------\
      /  集成测试   \       ← 适量：验证模块协作
     /--------------\
    /    单元测试     \     ← 大量：验证独立逻辑
   /__________________\
```

**理想比例**大约是 70% 单元测试、20% 集成测试、10% E2E 测试。这不是精确数字，而是一个方向指引。

### 为什么是金字塔而不是倒三角

当测试比例变成倒三角（大量 E2E、少量单元），会出现以下问题：

```typescript
// 假设你有一个用户注册模块，包含邮箱验证、密码强度检查、数据库写入

// 倒三角做法：只写 E2E 测试
// 这个测试要启动浏览器、填写表单、点击提交、检查数据库
test('用户注册流程', async () => {
  await browser.goto('/register')
  await browser.fill('#email', 'test@example.com')
  await browser.fill('#password', 'StrongPass123!')
  await browser.click('#submit')
  const user = await db.query('SELECT * FROM users WHERE email = ?', ['test@example.com'])
  expect(user).toBeTruthy()
})
```

这个测试的问题：

1. **运行慢**：启动浏览器需要几秒，整个测试可能要 10 秒以上
2. **定位难**：如果失败了，你不知道是邮箱验证出了问题，还是数据库连接断了
3. **脆弱**：前端改个按钮 ID，测试就挂了，但业务逻辑没变
4. **反馈慢**：2000 个这样的测试，CI 要跑半小时

```typescript
// 金字塔做法：分层测试
// 1. 单元测试：验证邮箱格式（纯逻辑，< 1ms）
test('验证邮箱格式', () => {
  expect(isValidEmail('test@example.com')).toBe(true)
  expect(isValidEmail('invalid')).toBe(false)
  expect(isValidEmail('test@')).toBe(false)
})

// 2. 单元测试：验证密码强度（纯逻辑，< 1ms）
test('密码必须包含大小写字母和数字', () => {
  expect(isStrongPassword('weak')).toBe(false)
  expect(isStrongPassword('StrongPass123')).toBe(true)
})

// 3. 集成测试：验证注册服务（不涉及浏览器，~100ms）
test('注册服务写入数据库', async () => {
  const user = await registerService.create('test@example.com', 'StrongPass123!')
  expect(user.id).toBeDefined()
  expect(user.email).toBe('test@example.com')
})

// 4. E2E 测试：只覆盖关键路径（1-2 个）
test('完整注册流程', async () => {
  // 只验证端到端的 happy path
})
```

分层后，单元测试在 1 秒内跑完，集成测试在 10 秒内跑完，E2E 测试只覆盖最关键的流程。开发者每次保存文件就能得到即时反馈。

### 各层测试的职责

```typescript
// 单元测试：验证一个函数/方法的输入输出
// 不依赖外部系统（数据库、网络、文件系统）
function calculateDiscount(price: number, rate: number): number {
  if (rate < 0 || rate > 1) throw new Error('折扣率必须在 0-1 之间')
  return Math.round(price * (1 - rate) * 100) / 100
}

test('100 元打 8 折应该是 80 元', () => {
  expect(calculateDiscount(100, 0.2)).toBe(80)
})

// 集成测试：验证多个模块协作
// 可能涉及数据库、API，但不涉及 UI
test('创建订单后库存应减少', async () => {
  const order = await orderService.create({ productId: 'p1', quantity: 2 })
  const stock = await inventoryService.getStock('p1')
  expect(stock).toBe(initialStock - 2)
})

// E2E 测试：验证完整的用户流程
// 从用户视角，覆盖 UI → API → 数据库 → UI 的完整链路
test('用户购买商品流程', async () => {
  // 打开商品页 → 加入购物车 → 结算 → 查看订单
})
```

## FIRST 原则

FIRST 是五个单词的首字母缩写，用于判断测试质量：

### Fast（快速）

单元测试应该在毫秒级完成。如果一个测试要等几秒，要么它不是单元测试，要么被测代码有设计问题。

```typescript
// 不好的写法：测试依赖真实 API 调用
test('获取用户信息', async () => {
  const user = await fetch('https://api.example.com/users/1').then(r => r.json())
  expect(user.name).toBeTruthy()
})

// 好的写法：用 mock 替代外部依赖
test('获取用户信息', async () => {
  const mockApi = { getUser: () => Promise.resolve({ name: '张三' }) }
  const user = await mockApi.getUser()
  expect(user.name).toBe('张三')
})
```

### Isolated（隔离）

每个测试独立运行，不依赖其他测试的执行顺序或状态。

```typescript
// 不好的写法：测试之间有依赖
let sharedUser: User

test('创建用户', async () => {
  sharedUser = await createUser('test@example.com')
  expect(sharedUser.id).toBeDefined()
})

test('修改用户名', async () => {
  // 依赖上一个测试创建的用户
  const updated = await updateUser(sharedUser.id, { name: '新名字' })
  expect(updated.name).toBe('新名字')
})

// 好的写法：每个测试自己准备数据
test('创建用户', async () => {
  const user = await createUser('test@example.com')
  expect(user.id).toBeDefined()
})

test('修改用户名', async () => {
  const user = await createUser('test@example.com')
  const updated = await updateUser(user.id, { name: '新名字' })
  expect(updated.name).toBe('新名字')
})
```

### Repeatable（可重复）

无论运行多少次，测试结果都一样。不依赖当前时间、随机数、外部服务状态。

```typescript
// 不好的写法：依赖当前时间
test('订单创建时间', () => {
  const order = createOrder()
  expect(order.createdAt).toBe(new Date()) // 可能差几毫秒就失败
})

// 好的写法：注入时间或使用近似匹配
test('订单创建时间', () => {
  const before = Date.now()
  const order = createOrder()
  const after = Date.now()
  expect(order.createdAt.getTime()).toBeGreaterThanOrEqual(before)
  expect(order.createdAt.getTime()).toBeLessThanOrEqual(after)
})
```

### Self-validating（自验证）

测试通过或失败，不需要人工判断。

```typescript
// 不好的写法：需要人工看输出
test('用户列表', async () => {
  const users = await getUsers()
  console.log(JSON.stringify(users, null, 2)) // 靠人眼判断对错
})

// 好的写法：断言明确
test('用户列表应按创建时间倒序排列', async () => {
  const users = await getUsers()
  expect(users).toHaveLength(3)
  expect(users[0].createdAt.getTime()).toBeGreaterThan(users[1].createdAt.getTime())
})
```

### Timely（及时）

测试应该在编写功能代码的同时（或之前）编写，而不是事后补测试。

## AAA 模式

AAA 是 Arrange-Act-Assert 的缩写，是最基础的测试结构：

```typescript
describe('购物车', () => {
  test('添加商品后总价应更新', () => {
    // Arrange（准备）：设置测试环境和数据
    const cart = new ShoppingCart()
    const product = { id: '1', name: '手机', price: 2999 }

    // Act（执行）：调用被测功能
    cart.add(product, 1)

    // Assert（断言）：验证结果
    expect(cart.totalPrice()).toBe(2999)
    expect(cart.itemCount()).toBe(1)
  })

  test('添加多个相同商品应合并数量', () => {
    // Arrange
    const cart = new ShoppingCart()
    const product = { id: '1', name: '手机', price: 2999 }

    // Act
    cart.add(product, 1)
    cart.add(product, 2)

    // Assert
    expect(cart.itemCount()).toBe(1) // 只有一个商品条目
    expect(cart.getQuantity('1')).toBe(3) // 数量合并为 3
    expect(cart.totalPrice()).toBe(2999 * 3)
  })
})
```

AAA 模式的好处是**可读性**。任何人看到测试代码，都能快速理解：准备了什么、做了什么、验证了什么。

当 Arrange 部分变得很长时，考虑提取为工厂函数或 beforeEach：

```typescript
describe('订单服务', () => {
  let orderService: OrderService
  let testUser: User
  let testProduct: Product

  beforeEach(() => {
    // Arrange 提取到 beforeEach
    orderService = new OrderService()
    testUser = createUserFixture({ email: 'test@example.com' })
    testProduct = createProductFixture({ price: 99 })
  })

  test('创建订单', async () => {
    // Act
    const order = await orderService.create(testUser.id, testProduct.id, 2)

    // Assert
    expect(order.totalPrice).toBe(198)
    expect(order.status).toBe('pending')
  })
})
```

## TDD：红-绿-重构

TDD（Test-Driven Development）的核心循环只有三步：

1. **红**：先写一个失败的测试
2. **绿**：写最少量的代码让测试通过
3. **重构**：优化代码，保持测试通过

```typescript
// 需求：实现一个 FizzBuzz 函数
// 输入 1-100 的数字，3 的倍数返回 Fizz，5 的倍数返回 Buzz，15 的倍数返回 FizzBuzz

// === 第一步：红（写失败的测试）===
test('输入 1 返回 "1"', () => {
  expect(fizzBuzz(1)).toBe('1') // fizzBuzz 还不存在，测试失败
})

// === 第二步：绿（最简实现）===
function fizzBuzz(n: number): string {
  return String(n) // 只让第一个测试通过
}

// === 第三步：继续红-绿循环 ===
test('输入 3 返回 "Fizz"', () => {
  expect(fizzBuzz(3)).toBe('Fizz') // 失败
})

function fizzBuzz(n: number): string {
  if (n % 3 === 0) return 'Fizz' // 加最小量代码
  return String(n)
}

test('输入 5 返回 "Buzz"', () => {
  expect(fizzBuzz(5)).toBe('Buzz') // 失败
})

function fizzBuzz(n: number): string {
  if (n % 15 === 0) return 'FizzBuzz'
  if (n % 3 === 0) return 'Fizz'
  if (n % 5 === 0) return 'Buzz'
  return String(n)
}

// === 重构 ===
function fizzBuzz(n: number): string {
  const rules: [number, string][] = [[15, 'FizzBuzz'], [3, 'Fizz'], [5, 'Buzz']]
  for (const [divisor, word] of rules) {
    if (n % divisor === 0) return word
  }
  return String(n)
}
```

## 常见误区

### 误区一：追求 100% 覆盖率

100% 的行覆盖率不等于没有 bug。覆盖率只告诉你哪些代码被执行了，不告诉你测试的质量。

```typescript
// 这个测试覆盖了 convertTemperature 函数，但只测了 happy path
function convertTemperature(celsius: number): number {
  if (typeof celsius !== 'number') throw new Error('输入必须是数字')
  return celsius * 9 / 5 + 32
}

test('温度转换', () => {
  expect(convertTemperature(100)).toBe(212) // 覆盖率 100%，但没测边界和异常
})
```

### 误区二：测试实现细节而非行为

```typescript
// 不好的写法：测试内部实现
test('应该调用内部的 format 方法', () => {
  const spy = vi.spyOn(formatter, 'format')
  formatter.process('hello')
  expect(spy).toHaveBeenCalled() // 内部重构就会挂
})

// 好的写法：测试行为
test('处理后文本应为大写', () => {
  expect(formatter.process('hello')).toBe('HELLO')
})
```

### 误区三：测试中包含过多逻辑

测试代码本身不应该包含 if/else、循环等复杂逻辑。如果测试比被测代码还复杂，说明测试写错了。

## 工程建议

1. **新代码先写测试**：哪怕是简单的函数，先写测试再写实现，养成习惯
2. **测试命名要描述行为**：`test('空密码应返回验证失败')` 而非 `test('test1')`
3. **一个测试只验证一件事**：如果一个测试有多个 assert，考虑拆分
4. **测试失败信息要有价值**：好的断言失败信息能直接告诉你哪里出了问题
5. **定期清理测试**：删除重复测试、修复 flaky 测试、更新过时的测试

## 小结

- 测试金字塔告诉我们：大量快速的单元测试 + 适量集成测试 + 少量 E2E 测试
- FIRST 原则帮助我们判断测试质量：快速、隔离、可重复、自验证、及时
- AAA 模式让测试结构清晰：准备、执行、断言
- TDD 通过红-绿-重构循环，让测试驱动设计

## 参考答案

### 练习一

**思路**：根据测试的依赖范围和执行速度判断层级

**答案**：
- testA：单元测试 — 只测试纯函数，无外部依赖
- testB：集成测试 — 涉及订单服务和库存服务的协作
- testC：E2E 测试 — 从用户视角覆盖完整浏览器流程

**要点**：
- 单元测试只测纯逻辑，不依赖外部系统
- 集成测试验证多个模块之间的协作
- E2E 测试从用户视角验证完整流程

### 练习二

**思路**：按 Arrange-Act-Assert 三段重组代码，添加注释标明各部分

**答案**：
```typescript
test('订单计算', async () => {
  // Arrange
  const order = new Order()

  // Act
  order.addItem({ price: 100, quantity: 2 })
  order.addItem({ price: 50, quantity: 1 })

  // Assert
  expect(order.total).toBe(250)
  expect(order.itemCount).toBe(2)
})
```

**要点**：
- Arrange 部分创建测试所需的对象和数据
- Act 部分执行被测功能，通常是单一操作
- Assert 部分验证结果，本例中两个断言验证同一操作的不同方面，可以保留
