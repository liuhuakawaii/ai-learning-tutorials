### 下单流程代码骨架

```python
class OrderService:
    def create_order(self, user_id: str, cart_items: list) -> Order:
        # 1. 验证用户
        user = self.user_client.get_user(user_id)
        if not user or not user.is_active:
            raise BusinessError("用户不存在或已禁用")

        # 2. 预占库存（同步调用）
        stock_results = []
        for item in cart_items:
            result = self.inventory_client.pre_deduct(
                sku_id=item.sku_id,
                quantity=item.quantity
            )
            if not result.success:
                # 库存不足，回滚已预占的库存
                self._rollback_stock(stock_results)
                raise BusinessError(f"商品 {item.sku_id} 库存不足")
            stock_results.append(result)

        # 3. 计算价格（同步调用）
        price_result = self.price_client.calculate(
            user_id=user_id,
            items=cart_items,
            coupon_ids=self._get_selected_coupons(user_id)
        )

        # 4. 创建订单（本地事务）
        order = Order(
            order_id=generate_order_id(),
            user_id=user_id,
            items=cart_items,
            total_amount=price_result.total_amount,
            discount_amount=price_result.discount_amount,
            pay_amount=price_result.pay_amount,
            status=OrderStatus.PENDING_PAYMENT
        )
        self.order_repo.save(order)

        # 5. 发布领域事件
        self.event_bus.publish(OrderCreatedEvent(
            order_id=order.order_id,
            user_id=user_id,
            items=cart_items,
            total_amount=order.pay_amount
        ))

        # 6. 发起支付（同步调用）
        payment = self.payment_client.create_payment(
            order_id=order.order_id,
            amount=order.pay_amount,
            payment_method=user.preferred_payment
        )

        return OrderResponse(order=order, payment_url=payment.pay_url)
```

## 分布式事务：Saga 模式

下单流程涉及库存扣减、订单创建、支付发起等多个服务，需要分布式事务保证一致性。

**为什么选 Saga 而不是 2PC**：2PC（两阶段提交）要求所有参与者同步阻塞等待，性能差且存在协调者单点问题。电商场景下订单量大，2PC 的性能瓶颈不可接受。Saga 模式通过**本地事务 + 补偿操作**实现最终一致性，性能更好。

**Saga 执行流程**：

```
正向流程（T1 → T2 → T3）：
T1: 库存服务 - 预占库存（本地事务）
T2: 订单服务 - 创建订单（本地事务）
T3: 支付服务 - 发起支付（本地事务）

补偿流程（任一步骤失败时反向补偿）：
C3: 支付服务 - 取消支付
C2: 订单服务 - 取消订单
C1: 库存服务 - 释放库存

执行顺序：
成功：T1 → T2 → T3
T2 失败：T1 → T2(失败) → C1（释放库存）
T3 失败：T1 → T2 → T3(失败) → C2（取消订单）→ C1（释放库存）
```

**关键设计**：每个正向操作都必须有对应的补偿操作。补偿操作必须是幂等的，因为网络抖动可能导致补偿请求被重复发送。

### Saga 编排器实现

```python
class OrderSagaOrchestrator:
    """下单 Saga 编排器"""

    def execute(self, order_request):
        saga_id = generate_saga_id()
        completed_steps = []

        try:
            # Step 1: 预占库存
            self.inventory_client.pre_deduct(
                saga_id=saga_id,
                sku_id=order_request.sku_id,
                quantity=order_request.quantity
            )
            completed_steps.append("inventory_pre_deduct")

            # Step 2: 创建订单
            order = self.order_service.create_order(order_request)
            completed_steps.append("create_order")

            # Step 3: 发起支付
            payment = self.payment_client.create_payment(
                order_id=order.order_id,
                amount=order.pay_amount
            )
            completed_steps.append("create_payment")

            return SagaResult.success(order, payment)

        except Exception as e:
            # 补偿已完成的步骤（逆序）
            self._compensate(saga_id, completed_steps, order_request)
            return SagaResult.failure(str(e))

    def _compensate(self, saga_id, completed_steps, request):
        for step in reversed(completed_steps):
            try:
                if step == "create_payment":
                    self.payment_client.cancel_payment(saga_id)
                elif step == "create_order":
                    self.order_service.cancel_order(saga_id)
                elif step == "inventory_pre_deduct":
                    self.inventory_client.release_stock(saga_id)
            except Exception as e:
                # 补偿失败记录到日志，人工处理
                logger.error(f"Compensation failed for {step}: {e}")
```

## 库存超卖问题

库存超卖是电商系统最经典的并发问题：两个用户同时购买最后一件商品，都显示库存充足，导致超卖。

**解决方案：Redis 预扣减 + 数据库乐观锁**

```
┌─────────────────────────────────────────────────────────────┐
│                 库存扣减流程                                  │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  第一步：Redis 预扣减（快速判断）                              │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ EVAL script:                                        │   │
│  │   local stock = redis.call('GET', key)              │   │
│  │   if stock >= quantity then                          │   │
│  │     redis.call('DECRBY', key, quantity)              │   │
│  │     return 1  -- 成功                                │   │
│  │   else                                               │   │
│  │     return 0  -- 库存不足                             │   │
│  │   end                                                │   │
│  │                                                     │   │
│  │ Redis Lua 脚本保证原子性，快速拦截无效请求               │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  第二步：数据库扣减（持久化）                                  │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ UPDATE stock                                        │   │
│  │ SET quantity = quantity - 1,                         │   │
│  │     version = version + 1                            │   │
│  │ WHERE sku_id = ? AND version = ? AND quantity >= 1   │   │
│  │                                                     │   │
│  │ 乐观锁：version 不匹配则更新失败，重试或返回失败         │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  第三步：Redis 回补（补偿机制）                                │
│  ┌─────────────────────────────────────────────────────┐   │
│  │ 如果数据库扣减失败（乐观锁冲突）：                       │   │
│  │   INCRBY stock:{sku_id} 1  -- Redis 回补库存          │   │
│  │   返回"库存不足"给用户                                 │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**为什么分两步**：Redis 单线程 + Lua 脚本保证原子性，QPS 可达 10 万+，用于快速拦截无效请求。数据库乐观锁作为最终一致性保障，即使 Redis 和数据库短暂不一致，乐观锁也能防止超卖。

## 高并发设计：缓存与 MQ 削峰

### 缓存策略

商品详情页是读取量最大的接口，需要多层缓存：

```
请求路径：
客户端 → CDN 缓存 → 本地缓存 → Redis 集群 → 数据库

CDN 缓存：静态资源（图片、CSS、JS）+ 商品详情页 HTML
本地缓存（Caffeine）：热点商品数据，TTL 30 秒
Redis 集群：全量商品数据，TTL 5 分钟
数据库：最终数据源

缓存更新策略：
- 商品信息变更 → 删除 Redis 缓存（Cache Aside Pattern）
- 不直接更新缓存，避免并发写入导致数据不一致
- 下次读取时自动回填缓存
```

### 缓存一致性保障

```python
class ProductService:
    def update_product(self, product_id, update_data):
        # 1. 更新数据库
        self.product_repo.update(product_id, update_data)

        # 2. 删除缓存（不是更新缓存）
        self.redis.delete(f"product:{product_id}")

        # 3. 发布变更事件（通知搜索服务等下游）
        self.event_bus.publish(ProductUpdatedEvent(product_id))

    def get_product(self, product_id):
        # 1. 查本地缓存
        product = self.local_cache.get(f"product:{product_id}")
        if product:
            return product

        # 2. 查 Redis
        product = self.redis.get(f"product:{product_id}")
        if product:
            self.local_cache.set(f"product:{product_id}", product, ttl=30)
            return product

        # 3. 查数据库
        product = self.product_repo.find_by_id(product_id)
        if product:
            self.redis.setex(f"product:{product_id}", 300, product)
            self.local_cache.set(f"product:{product_id}", product, ttl=30)

        return product
```

### MQ 削峰

秒杀场景下，瞬间流量远超系统承受能力。使用消息队列削峰：

```
瞬间 10000 QPS
       │
       ▼
┌──────────┐
│ 订单服务  │ → 快速校验 + 写入 MQ（10000 QPS）
└────┬─────┘
     │
     ▼
┌──────────┐
│ 消息队列  │ → 缓冲区（按 1000 QPS 消费）
└────┬─────┘
     │
     ▼
┌──────────┐
│ 库存服务  │ → 按 1000 QPS 处理扣减
└──────────┘
```

订单服务收到秒杀请求后，快速校验（用户资格、库存预判断），然后将请求写入消息队列。库存服务按自己的处理能力消费消息，实现流量削峰。用户端显示"排队中"，消费完成后通知用户下单结果。

## 常见误区

1. **服务拆分过细**：把每个功能都做成独立服务（如"地址服务""评价服务"），导致服务间调用链路过长，运维成本飙升。初期应该粗粒度拆分，随业务增长再细化。

2. **忽略数据一致性**：服务拆了但数据库没拆，所有服务连同一个数据库。或者拆了数据库但没有设计分布式事务方案，导致数据不一致。

3. **过度设计缓存**：所有数据都加缓存，缓存和数据库的一致性维护成本远超收益。只缓存读多写少的数据（商品详情、用户信息），写多读少的数据（订单状态）不缓存。

4. **秒杀场景直接打数据库**：秒杀请求不做流量控制，瞬间万级 QPS 直接打到数据库，导致数据库崩溃。必须用 Redis 预扣减 + MQ 削峰。

5. **忽略可观测性**：微服务系统没有链路追踪和日志聚合，出问题时无法快速定位。可观测性是微服务架构的基础设施，必须从第一天就建设。

6. **同步调用链路过长**：下单流程中同步调用 6-7 个服务，任何一个环节故障都会导致整个下单失败。应评估哪些调用可以改为异步。

7. **忽视补偿操作的幂等性**：Saga 补偿操作不做幂等处理，网络抖动导致补偿请求重复执行，造成数据不一致（如库存重复释放）。

## 工程建议

1. **从模块化单体开始**：如果团队规模小（< 10 人），不需要一开始就拆成十几个微服务。先在单体内部按限界上下文划分模块，等团队和业务增长后再拆。

2. **核心链路和非核心链路分离**：订单、支付、库存是核心链路，推荐、积分、通知是非核心链路。核心链路用同步调用保证一致性，非核心链路用异步事件解耦。

3. **数据库读写分离**：商品服务读多写少，主库写、从库读。订单服务写多读少，考虑分库分表。

4. **建立容灾预案**：每个服务都有降级方案。价格服务不可用时用默认价格，推荐服务不可用时展示热门商品。降级方案必须提前演练。

5. **持续演进架构**：架构不是一步到位的。初期粗粒度拆分，中期细化核心链路，后期引入 Service Mesh 和全链路压测。每个阶段的架构应该匹配当前的业务规模和团队能力。

6. **建立服务等级协议（SLA）**：每个核心服务定义 SLA（如订单服务 P99 < 500ms，可用性 > 99.9%），通过监控和告警保障。

7. **定期做全链路压测**：在预发环境模拟真实流量，验证系统的容量和稳定性。压测发现的问题比线上故障成本低得多。

## 小结

微服务电商系统的设计需要综合运用前五节课的知识：用 DDD 限界上下文指导服务拆分，用同步/异步通信组合设计核心流程，用 API 网关统一管理流量，用配置中心管理环境差异和动态开关，用链路追踪保障可观测性。核心挑战在于分布式事务（Saga 模式）和高并发场景（Redis 预扣减 + MQ 削峰）。架构设计没有银弹，每个决策都是在一致性、可用性、复杂度之间做权衡。

### 练习一

**思路**：退款是下单的逆向流程，Saga 的正向流程是退款操作，补偿流程是退款失败时的回滚。

**答案**：

```
退款 Saga 流程：

正向流程（T1 → T2 → T3 → T4）：
T1: 支付服务 - 发起第三方退款（调用支付渠道 API）
T2: 订单服务 - 更新订单状态为"退款中"
T3: 库存服务 - 回补库存
T4: 积分服务 - 扣减积分

补偿流程（任一步骤失败时反向补偿）：
T1 失败：退款发起失败，直接返回用户"退款失败，请稍后重试"
T2 失败：C1 - 取消第三方退款（如果支持撤销）
T3 失败：C2 - 订单状态回退为"已支付"，C1 - 取消退款
T4 失败：C3 - 库存回退（扣减回补的库存），C2 - 订单状态回退，C1

关键设计：
1. 支付服务的退款接口必须支持幂等（用退款单号去重）
2. 库存回补可能与新的下单请求冲突，需要加锁或排队
3. 积分扣减要考虑用户积分不足的情况（如果积分已消费，标记为"积分待追回"）
4. 整个流程通过事件驱动，每个步骤完成后发布事件触发下一步
```

**要点**：
- 退款流程比下单流程更复杂，因为涉及逆向操作
- 第三方退款接口可能有延迟（T+1 到账），需要异步回调确认
- 补偿操作必须幂等，因为可能被重复调用

### 练习二

**思路**：分层过滤，用 Redis 快速拦截，用 MQ 削峰，用数据库乐观锁兜底。

**答案**：

```
秒杀方案设计：

第一层：前端限流
- 按钮点击后置灰，防止重复提交
- 前端倒计时，不到开始时间不允许请求
- 验证码/答题，过滤机器人

第二层：API 网关限流
- 按 IP 限流：单 IP 每秒最多 1 次请求
- 按用户限流：单用户整个活动只能请求 1 次
- 总 QPS 限流：超过 1 万 QPS 直接拒绝，返回"活动太火爆"

第三层：Redis 预扣减
- 秒杀开始前，将 100 件库存写入 Redis
- 使用 Lua 脚本原子操作：检查库存 → 检查用户是否已购买 → 扣减库存 → 记录用户
- Redis 返回成功才进入下一步，直接拦截 99% 的无效请求

第四层：消息队列削峰
- Redis 预扣减成功的请求写入 Kafka
- 订单服务按 500 QPS 消费（数据库承受能力）
- 消费后创建订单，扣减数据库库存

第五层：数据库乐观锁
- UPDATE stock SET quantity = quantity - 1
-   WHERE sku_id = ? AND version = ? AND quantity >= 1
- version 不匹配则说明已被其他请求扣减，返回失败

用户感知：
- 提交请求后显示"排队中"
- 3 秒内返回结果：成功（跳转支付页面）或失败（库存已售罄）
```

**要点**：
- 每一层过滤掉大量请求，到达数据库的请求只有几百
- Redis Lua 脚本是核心，保证原子性和高性能
- 用户体验的关键是快速返回结果，不能让用户等待太久
