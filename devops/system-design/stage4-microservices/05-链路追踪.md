# 链路追踪

## 场景引入

凌晨两点，你被报警电话叫醒：用户反馈下单失败，返回 500 错误。你登上服务器查看日志，订单服务报错"调用库存服务超时"。你去看库存服务的日志，库存服务说"数据库查询慢"。你去看数据库监控，发现某个慢查询。但问题是：这个慢查询是哪个用户的哪个请求触发的？这条请求经过了哪些服务？每个环节花了多少时间？

在单体应用时代，一个请求的所有日志都在一个进程里，用一个线程 ID 就能串起来。但在微服务架构中，一个用户请求可能经过 5-10 个服务，每个服务的日志分散在不同机器上，传统的日志排查方式完全失效。

这就是**分布式链路追踪**要解决的问题——把一个请求在多个服务间的完整调用路径串联起来。

## 学习目标

- 理解分布式链路追踪的核心概念：Span、Trace、Context Propagation
- 掌握 OpenTelemetry 标准及其在链路追踪中的作用
- 了解 Jaeger 和 Zipkin 的架构差异与选型
- 理解采样策略的设计与权衡
- 掌握链路追踪与日志、指标的关联方法

## 核心概念：Span、Trace、Context

**Trace**（链路）：一个完整请求从入口到结束的完整调用路径。每个 Trace 有一个全局唯一的 Trace ID。

**Span**（跨度）：Trace 中的一个操作单元。每个 Span 记录了操作名称、开始时间、持续时间、状态。Span 之间有父子关系，形成树状结构。

**Context Propagation**（上下文传播）：在服务间传递 Trace ID 和 Span ID 的机制，通常通过 HTTP Header 传递。

```
┌─────────────────────────────────────────────────────────────┐
│                    Span 关系图                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Trace ID: abc-123                                          │
│                                                             │
│  Span A: API Gateway (根 Span, 150ms)                       │
│  └─ Span B: Order Service (子 Span, 115ms)                  │
│     ├─ Span C: Inventory Service (孙 Span, 50ms)            │
│     │  └─ Span D: MySQL Query (曾孙 Span, 40ms)             │
│     └─ Span E: Payment Service (孙 Span, 45ms)              │
│        └─ Span F: Payment Gateway (曾孙 Span, 35ms)         │
│                                                             │
│  调用链路：                                                  │
│  API Gateway → Order Service → Inventory → MySQL            │
│                            → Payment Service → Payment GW   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

每个 Span 包含：Trace ID、Span ID、Parent Span ID、Operation Name、Start Time、Duration、Tags、Logs、Status。

## OpenTelemetry 标准

OpenTelemetry（OTel）是 CNCF 孵化的可观测性标准，由 OpenTracing 和 OpenCensus 合并而来。它定义了链路追踪、指标、日志的统一采集规范。

**为什么要用 OpenTelemetry**：统一标准、厂商无关、自动埋点、三合一（链路追踪、指标、日志统一采集）。

**核心组件**：
1. **API**：定义创建 Span、注入/提取 Context 的接口
2. **SDK**：API 的具体实现，包含采样、Span 处理等配置
3. **Collector**：独立的采集进程，负责接收、处理和导出遥测数据

```
应用 A/B/C (OTel SDK)
    │ OTLP/gRPC
    ▼
┌─────────────────────────────┐
│   OpenTelemetry Collector   │
│   Receivers → Processors    │
│            → Exporters      │
└──────────┬──────────────────┘
     ┌─────┴──────┐
     ▼            ▼
  Jaeger      Prometheus
  (链路)       (指标)
```

**OTel 的价值**：应用只需集成 OTel SDK，通过 Collector 可以将数据导出到任何后端。切换后端不需要改应用代码。

## Jaeger 架构

Jaeger 是 Uber 开源的分布式链路追踪系统，CNCF 毕业项目。

```
应用 A/B/C (Jaeger Client)
    │ UDP
    ▼
Agent × N (Sidecar, 每台机器一个)
    │
    ▼
Collector (集中部署, 验证/处理/存储)
    │
    ├─→ Elasticsearch (查询存储)
    └─→ Kafka (缓冲)
         │
         ▼
    Query (Web UI, 按 Trace ID/服务名/时间查询)
```

**核心组件**：
- **Agent**：部署在每台机器上，接收应用通过 UDP 发送的 Span 数据，批量转发给 Collector
- **Collector**：接收 Agent 转发的 Span 数据，验证、处理后存储到后端
- **Query**：提供 Web UI 和 API，用于查询和展示链路数据
- **Storage**：支持 Elasticsearch、Cassandra、Kafka

**Jaeger vs Zipkin**：Jaeger 架构更复杂（Agent + Collector + Query 分离），支持自适应采样，适合大规模生产环境。Zipkin 将 Agent 和 Collector 合并为一个 Server，架构更简单，适合小规模快速上手。

## Trace ID 传播

链路追踪的关键是**上下文传播**——在服务间调用时传递 Trace ID 和 Span ID。

**HTTP 传播**：通过 HTTP Header 传递。W3C Trace Context 标准定义了 `traceparent` Header：

```
traceparent: 00-abc123def456-span789012-01
              │  │            │            │
              │  Trace ID     Span ID     采样标志
              版本号
```

**gRPC 传播**：通过 gRPC 的 Metadata 传递。OTel SDK 自动处理。

**消息队列传播**：在消息的 Header 中注入 Trace ID。消费方从消息中提取 Context，创建新的 Span。

## 采样策略

在高并发系统中，记录每一个请求的链路数据会产生巨大的存储和网络开销。采样策略决定哪些请求需要记录完整链路。

**固定采样**：按固定比例采样，如 1% 的请求记录链路。实现简单，但可能漏掉异常请求。

**自适应采样**：根据系统负载动态调整采样率。负载低时多采样，负载高时少采样。

**基于规则的采样**：对特定接口、特定状态码的请求全量采样。例如所有 5xx 错误都记录链路。

**头部采样**：在链路的第一个 Span 创建时就决定是否采样，整个链路保持一致。

**采样率建议**：

| 场景 | 采样率 | 理由 |
|------|--------|------|
| 开发/测试环境 | 100% | 调试需要完整数据 |
| 生产环境-核心链路 | 100% | 支付、订单不能漏 |
| 生产环境-高频接口 | 1-10% | 平衡成本和可观测性 |
| 错误请求 | 100% | 必须能追踪到错误原因 |

## 日志关联

链路追踪、日志、指标是可观测性的三大支柱。将它们关联起来才能快速定位问题。

在日志中注入 Trace ID 和 Span ID，当发现链路中某个 Span 耗时异常时，通过 Trace ID 搜索日志，找到对应的详细错误信息。

```json
{
  "timestamp": "2024-01-15T10:30:00Z",
  "level": "ERROR",
  "message": "Database query timeout",
  "trace_id": "abc123def456",
  "span_id": "span789012",
  "service": "inventory-service"
}
```

## 性能指标采集

OpenTelemetry 还支持采集性能指标（Metrics）：

- **RED 指标**：Rate（请求速率）、Error（错误率）、Duration（延迟分布）
- **USE 指标**：Utilization（利用率）、Saturation（饱和度）、Errors（错误数）

这些指标可以与链路数据关联，在 Jaeger UI 中点击某个慢 Span，可以看到该服务在对应时间段的指标。

## 常见误区

1. **生产环境不采样**：100% 采样导致存储和网络成本飙升。高并发系统必须采样，但要确保错误请求全量采样。

2. **只追踪不关联日志**：链路追踪只能告诉你哪个环节慢，不能告诉你为什么慢。必须将 Trace ID 注入日志。

3. **在应用代码中手动埋点**：应使用 OpenTelemetry 的自动埋点，只在关键业务逻辑手动埋点。

4. **忽略 Context 传播**：异步操作中没有正确传播 Context，导致链路断裂。

5. **链路追踪取代日志**：两者是互补关系，不是替代关系。

6. **采样策略不一致**：链路中不同服务的采样率不同，导致链路数据不完整。应在入口层统一决定采样，中间层透传采样标志。

7. **忽略 Collector 的容量规划**：高并发系统中 Collector 可能成为瓶颈。需要根据 Span 数据量规划 Collector 的实例数和资源配置。

## 工程建议

1. **统一使用 OpenTelemetry**：不要为每个服务选不同的追踪库。

2. **采样策略分层**：入口层决定采样（头部采样），中间层透传采样标志。

3. **关键路径全量采样**：支付、订单创建等核心链路 100% 采样。

4. **建立告警规则**：基于链路数据建立告警——P99 延迟超过阈值、错误率超过阈值时自动告警。

5. **链路数据定期清理**：设置合理的 TTL（如 7 天），定期清理过期数据。

6. **链路追踪的性能开销**：自动埋点会带来 1-5% 的性能开销。在性能敏感的场景，可以通过采样率和批量导出（BatchSpanProcessor）降低开销。

7. **建立链路分析看板**：基于链路数据建立服务依赖拓扑图、延迟热力图、错误率趋势图。这些看板能帮助团队快速了解系统健康状态。

## 小结

分布式链路追踪通过 Trace ID 将一个请求在多个服务间的调用路径串联起来，核心概念是 Trace、Span 和 Context Propagation。OpenTelemetry 是统一的可观测性标准，推荐作为首选。Jaeger 适合大规模生产环境，Zipkin 适合快速上手。采样策略要在成本和可观测性之间权衡，错误请求必须全量采样。

## 参考答案

### 练习一

**思路**：每个服务调用对应一个 Span，父子关系反映调用顺序。

**答案**：

```
Span 1: API Gateway - POST /api/orders (根 Span)
└── Span 2: Order Service - createOrder
    ├── Span 3: Inventory Service - deductStock
    │   └── Span 4: MySQL - UPDATE stock ...
    ├── Span 5: Price Service - calculatePrice
    │   └── Span 6: Redis - GET promotion:product:123
    └── Span 7: Payment Service - initiatePayment
        └── Span 8: Payment Gateway - POST /charge
```

**要点**：库存扣减和价格计算可以并行；数据库查询和缓存查询也应该是独立 Span。

### 练习二

**思路**：计算存储需求，设计分层采样策略。

**答案**：

```
全量存储：1亿 × 2KB × 7天 = 1.4TB（成本过高）

采样方案（5% 基础 + 错误全量）：
- 正常请求：(1亿 - 10万) × 5% = 500万次/天
- 错误请求：10万次/天（假设错误率 0.1%）
- 总计：510万次/天 × 2KB = 10.2GB/天，7天 71.4GB

策略：
1. 头部采样：API Gateway 层决定
2. 基础采样率：5%
3. 错误全量：HTTP 5xx 100% 采样
4. 关键链路全量：支付、订单创建 100% 采样
5. 高延迟全量：响应时间 > 1 秒 100% 采样
```

**要点**：500 万样本足够分析 P50/P99；错误和关键链路必须全量采样。

### 练习三

**思路**：通过链路数据筛选慢请求，逐步缩小排查范围。

**答案**：

```
排查方案：

第一步：筛选慢链路
- 在 Jaeger 中搜索延迟 > 2s 的链路（订单服务，最近 1 小时）
- 筛选结果：找到 100 条慢链路

第二步：分析慢链路的共性
- 对比 100 条慢链路的 Span 耗时分布
- 发现：80% 的慢链路中，库存服务的数据库查询 Span 耗时 > 1.5s
- 正常情况下该 Span 只需要 50ms

第三步：深入分析库存服务
- 用 Trace ID 在 ELK 中搜索库存服务的日志
- 发现日志中有 "lock wait timeout" 警告
- 时间分布：集中在每小时的第 0-5 分钟

第四步：定位根因
- 发现每小时第 0 分钟有一个定时任务在执行库存盘点
- 盘点任务持有行锁时间过长，阻塞了正常的库存扣减查询
- 解决方案：盘点任务改为乐观锁或在低峰期执行

第五步：验证
- 修改定时任务后，观察 P99 延迟恢复正常
```

**要点**：
- 链路追踪的核心价值是将"P99 飙升"转化为具体的慢 Span
- 日志关联是找到根因的关键步骤
- 时间维度的分析能帮助定位定时任务等周期性问题
