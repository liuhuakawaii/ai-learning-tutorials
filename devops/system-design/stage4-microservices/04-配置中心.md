# 配置中心

## 场景引入

你的微服务系统已经有 20 多个服务，每个服务有数据库连接串、缓存地址、第三方 API 密钥、业务开关等配置项。最初这些配置写在每个服务的 `application.yml` 里，和代码一起打包部署。问题开始出现了：

- 开发环境和生产环境的数据库地址不同，每次部署都要手动改配置文件
- 想关闭某个功能开关，需要修改配置、重新打包、重新部署，整个流程要 30 分钟
- 某次误改了数据库连接串导致线上故障，无法快速回滚
- 配置分散在各个服务的代码仓库里，没有统一管理，安全审计困难

这些问题的解决方案是**配置中心**——一个集中管理所有服务配置的基础设施组件。

## 学习目标

- 理解为什么微服务架构需要配置中心
- 掌握 Nacos 和 Apollo 两大主流配置中心的特点与选型
- 理解动态配置推送的实现机制（长轮询 vs WebSocket）
- 了解配置加密和多环境管理的最佳实践

## 为什么需要配置中心

**环境差异管理**：同一个服务在开发、测试、预发、生产环境有不同的配置。配置中心通过命名空间隔离环境，服务启动时根据环境标识拉取对应配置。

**动态配置推送**：修改配置后实时推送到所有服务实例，不需要重启。例如发现推荐服务有 Bug，通过配置中心关闭推荐功能开关，所有实例立即生效。

**配置审计与版本控制**：每次配置变更都有记录——谁改的、什么时候改的、改了什么。出问题时可以快速回滚。

**配置安全**：敏感配置（数据库密码、API 密钥）加密存储，运行时解密。

### 没有配置中心时的痛点

```
痛点 1：配置散落在各处
  服务 A (app.yml) / 服务 B (env vars) / 服务 C (.properties)
  每个服务用不同的格式、不同的位置管理配置

痛点 2：环境切换靠手动
  开发环境：jdbc:mysql://dev-db:3306/order
  生产环境：jdbc:mysql://prod-db:3306/order
  每次部署都要改配置文件，容易出错

痛点 3：配置变更无法追溯
  "谁把数据库密码改了？" "什么时候改的？" 没有变更记录

痛点 4：敏感配置泄露风险
  数据库密码、API Key 写在配置文件里，提交到 Git
```

## Nacos 配置管理

Nacos 是阿里巴巴开源的注册中心和配置中心，国内使用最广泛。

```
┌─────────────────────────────────────────────────────────────┐
│                    Nacos 配置管理架构                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  命名空间(dev)    命名空间(test)    命名空间(prod)           │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐              │
│  │ 订单服务  │    │ 订单服务  │    │ 订单服务  │              │
│  │ 配置(dev) │    │ 配置(test)│    │ 配置(prod)│              │
│  └──────────┘    └──────────┘    └──────────┘              │
│                                                             │
│  配置格式（YAML）：                                          │
│  Data ID: order-service.yaml                                │
│  Group: DEFAULT_GROUP                                       │
│  内容：database.url / feature.recommendation 等              │
│                                                             │
│  服务启动时：根据环境标识 → 拉取配置 → 监听变更               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Nacos 核心概念**：
- **命名空间（Namespace）**：环境隔离，如 dev/test/prod
- **分组（Group）**：业务分组，如 DEFAULT_GROUP
- **Data ID**：配置文件标识，通常用 `{服务名}.yaml`

**配置监听**：Nacos 客户端通过长轮询机制监听配置变更。客户端发起 HTTP 请求到服务端，服务端 hold 住请求直到配置变更或超时（默认 30 秒）。配置变更后立即响应，延迟在秒级。

## Apollo 配置中心

Apollo 是携程开源的配置中心，功能比 Nacos 更丰富，尤其在灰度发布和配置回滚方面。

**Apollo 核心特性**：

1. **灰度发布**：配置变更可以先推送到部分实例验证，确认无问题后再全量发布。
2. **配置回滚**：每次配置发布都有版本记录，可以一键回滚到任意历史版本。
3. **权限管理**：细粒度的权限控制，不同角色可以管理不同的配置项。
4. **配置审计**：完整的操作日志，满足安全审计要求。

```
┌─────────────────────────────────────────────────────────────┐
│                    Apollo 架构                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Portal (Web UI) → Admin Service → Config Service           │
│       │                                │                    │
│    配置发布                          配置读取                 │
│       │                                │                    │
│       ▼                                ▼                    │
│    MySQL                           服务实例                  │
│  (配置存储)                    (长轮询监听变更)               │
│                                  + 本地文件缓存              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 动态配置推送机制

**长轮询（Long Polling）**：客户端定期向服务端发起 HTTP 请求，如果配置没变更，服务端 hold 住请求不响应，直到配置变更或超时。Nacos 和 Apollo 都使用这种方式。优点是实现简单、兼容性好。

**WebSocket**：客户端与服务端建立 WebSocket 长连接，配置变更时服务端主动推送。优点是延迟低（毫秒级）；缺点是实现复杂。

**实践选择**：长轮询对于配置变更场景已经足够。配置变更不是高频操作，秒级延迟完全可以接受。

## 配置加密

敏感配置不能明文存储在配置中心。加密方案：

1. **配置中心内置加密**：Nacos 和 Apollo 都支持配置项加密，存储时加密，客户端拉取后解密。
2. **KMS 集成**：使用云厂商的密钥管理服务管理加密密钥。配置中心只存密文，客户端通过 KMS 解密。
3. **环境变量注入**：最敏感的配置通过环境变量注入，不经过配置中心。

**最佳实践**：配置中心存储密文 + KMS 管理密钥。密钥和密文分离存储，即使配置中心泄露，没有密钥也无法解密。

```
配置加密架构：
┌──────────┐                  ┌──────────┐
│ 配置中心  │                  │ KMS      │
│ 存储密文: │                  │ 存储密钥: │
│ "ENC(xxx)"│                 │ key-001  │
└────┬─────┘                  └────┬─────┘
     │ 拉取密文                     │ 获取密钥
     ▼                             ▼
┌─────────────────────────────────────────┐
│  服务实例                                │
│  1. 从配置中心获取密文                    │
│  2. 从 KMS 获取解密密钥                   │
│  3. 本地解密得到明文                      │
│  4. 用明文初始化数据库连接池               │
└─────────────────────────────────────────┘
```

## 多环境管理

微服务系统通常有开发（dev）、测试（test）、预发（staging）、生产（prod）四套环境。

**环境隔离策略**：

1. **命名空间隔离**：每个环境一个命名空间，配置完全独立。Nacos 推荐这种方式。
2. **独立集群**：每个环境部署独立的配置中心集群。生产环境物理隔离，安全性最高。

**公共配置**：多个服务共享的配置（如公共中间件地址）应提取为公共配置，避免重复维护。Nacos 支持 shared-configs 引用公共配置。

## Nacos vs Apollo 选型对比

| 维度 | Nacos | Apollo |
|------|-------|--------|
| 功能定位 | 注册中心 + 配置中心 | 专注配置中心 |
| 灰度发布 | Beta 发布（较弱） | 原生支持（强） |
| 权限管理 | 基础 | 细粒度 |
| 性能 | 高 | 中等 |
| 社区活跃度 | 高（阿里维护） | 中等（携程维护） |

**选型建议**：需要同时具备注册中心和配置中心选 Nacos，对配置管理有更高要求选 Apollo。

## 常见误区

1. **配置和代码不分离**：配置硬编码在代码里，不同环境靠注释切换。必须用配置中心替代。

2. **配置变更不测试**：直接在生产环境修改配置，不做预发验证。配置变更和代码变更一样需要测试。

3. **过度依赖动态配置**：把所有配置都做成动态的，导致系统行为难以预测。只有需要运行时变更的配置才应该放在配置中心。

4. **忽略配置版本控制**：配置变更没有记录，出问题时无法回滚。

5. **敏感配置明文存储**：数据库密码、API 密钥以明文形式存储在配置中心。

6. **配置中心单点部署**：配置中心只部署一个实例，挂了所有服务都无法获取配置。配置中心必须集群部署，客户端要有本地缓存兜底。

7. **配置变更不做通知**：配置变更后没有通知相关人员，导致运维和开发对线上状态认知不一致。

## 工程建议

1. **配置命名规范化**：统一配置项命名格式，如 `服务名.模块.配置项`。

2. **配置变更审批流程**：生产环境配置变更必须经过审批。

3. **配置监听优雅处理**：配置变更回调中不要做重逻辑，应该用异步方式处理。

4. **配置降级方案**：配置中心不可用时，服务应能使用本地缓存的配置正常启动。

5. **定期审计配置**：定期检查是否有过期的配置项、是否有敏感配置泄露风险。

6. **配置命名规范化示例**：
```yaml
# 推荐：服务名.模块.配置项
order.service.timeout: 3000
order.database.max-connections: 20
order.feature.new-checkout: true

# 避免：没有服务前缀、命名风格不统一
timeout: 3000
orderServiceTimeout: 3000
```

7. **配置变更的监控告警**：配置变更后自动触发关键指标监控（错误率、延迟），如果指标异常自动告警并建议回滚。

## 小结

配置中心是微服务基础设施的核心组件，解决环境差异管理、动态配置推送、配置审计和安全等问题。Nacos 适合需要同时具备注册中心和配置中心的场景，Apollo 适合对配置管理有更高要求的场景。配置推送通过长轮询实现，配置加密应结合 KMS 使用。

## 练习

### 练习一：配置中心选型

某公司的微服务系统有以下需求：(1) 需要同时做服务注册和配置管理；(2) 配置变更需要灰度发布能力；(3) 需要配置变更审批流程；(4) 技术栈主要是 Java 和 Go。请分析 Nacos 和 Apollo 哪个更适合。

### 练习二：配置分层设计

一个电商系统有 10 个微服务，它们共享 MySQL 集群地址、Redis 集群地址、Kafka 集群地址、日志级别。每个服务还有自己的数据库名、业务开关等私有配置。请设计配置的分层方案。

### 练习三：配置故障应急

凌晨 3 点，运维人员误将生产环境的数据库连接串改为测试环境地址，导致所有服务连接测试数据库。请设计一个配置变更应急方案，包括：(1) 如何快速发现问题；(2) 如何快速回滚；(3) 如何防止类似问题再次发生。

## 参考答案

### 练习一

**思路**：逐条匹配需求，分析两个方案的优劣。

**答案**：

Nacos 更适合。理由：

1. **注册中心 + 配置中心一体化**：不需要维护两套系统
2. **灰度发布**：Nacos 2.x 通过 Beta 发布功能支持灰度推送
3. **审批流程**：可通过外部工单系统实现
4. **多语言支持**：Java 和 Go 客户端都有良好支持

如果灰度发布和审批流程是强需求，可以组合使用：Nacos 做注册中心，Apollo 做核心业务配置管理。

### 练习二

**思路**：按变更频率和共享范围分层，避免重复配置。

**答案**：

```
第一层：公共配置（shared-configs 引用）
├── common-datasource.yaml（MySQL/Redis/Kafka 地址）
└── common-logging.yaml（日志级别和格式）

第二层：服务私有配置
├── order-service.yaml（订单库名、业务开关）
├── product-service.yaml（商品库名、缓存 TTL）
└── ...

命名空间：dev / test / staging / prod
每个命名空间下配置结构相同，但值不同
```

**要点**：
- 公共配置用 shared-configs 引用，避免重复
- 敏感配置用 KMS 加密
- 服务私有配置的 Data ID 与服务名一致

### 练习三

**思路**：快速发现 → 快速回滚 → 防止复发。

**答案**：

```
1. 快速发现问题（< 1 分钟）
   - 配置变更后自动触发监控告警
   - 关键指标：数据库连接数、错误率、响应延迟
   - 告警规则：错误率 > 5% 或 P99 延迟 > 2 秒
   - 告警通知：钉钉群 + 电话（凌晨时段）

2. 快速回滚（< 2 分钟）
   - 方案 A（推荐）：配置中心一键回滚到上一版本
   - 方案 B：手动修改为正确的连接串 → 立即发布
   - 回滚后验证：检查服务日志，确认连接到正确的数据库

3. 防止类似问题再次发生
   - 配置变更必须经过审批（至少一人审核）
   - 生产环境配置变更限制操作人员范围
   - 关键配置（数据库连接串）设置变更告警
   - 配置变更前自动对比新旧配置差异，高亮关键字段变化
```

**要点**：
- 凌晨操作更需要审批和告警机制
- 配置中心的回滚功能是应急的核心手段
- 预防比应急更重要，建立审批和告警机制是长期方案
