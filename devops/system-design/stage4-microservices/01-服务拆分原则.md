# 服务拆分原则

## 场景引入

你接手了一个已经开发了三年的电商系统。最初它是一个单体应用，所有模块——商品、订单、支付、库存、用户——都打包在一个 WAR 包里部署。随着业务增长，这个单体应用膨胀到了几十万行代码，每次发布都要全量部署，一个小模块的改动可能导致整个系统崩溃。更糟糕的是，不同模块的资源需求完全不同：商品服务是读多写少，需要大量缓存；订单服务是写密集型，需要强一致性；推荐服务需要 GPU 算力。把它们绑在一起，资源利用效率极低。

老板说："我们要上微服务。" 但问题是：**怎么拆？** 拆得太细，服务间调用链路爆炸，运维成本飙升；拆得太粗，等于换了个名字的单体。本节课系统性地讲解服务拆分的原则和方法。

## 学习目标

- 理解 DDD 限界上下文（Bounded Context）的概念，能用它指导服务边界划分
- 掌握上下文映射的几种模式（共享内核、防腐层、开放主机服务）
- 了解从单体到微服务的演进策略（绞杀者模式、修缮者模式）
- 能判断拆分粒度是否合理，识别"分布式单体"等反模式
- 理解领域事件在服务解耦中的作用

## 单一职责原则在服务层面的应用

单一职责原则（SRP）在微服务中的含义是：**一个服务应该只有一个变更的理由**。这不意味着一个服务只做一件事，而是说一个服务的所有功能应该因为同一个业务原因而变化。

举例来说，"订单服务"负责订单的创建、查询、状态流转。当订单业务规则变化时（比如新增一种订单类型），只有订单服务需要修改。如果"订单服务"里还包含了库存扣减逻辑，那库存规则变化也会迫使订单服务修改——这就是职责不清。

## DDD 限界上下文

领域驱动设计（DDD）中的**限界上下文**（Bounded Context）是服务拆分最重要的理论工具。

限界上下文的核心思想是：**同一个业务概念在不同上下文中可以有不同的含义和模型**。例如"商品"这个概念：

- 在商品管理上下文中：商品包含详情、SKU、图片、描述
- 在订单上下文中：商品只是一个快照（名称、价格、数量）
- 在库存上下文中：商品是一个 SKU 编号 + 库存数量
- 在推荐上下文中：商品是一组特征向量

如果你试图用一个统一的"商品模型"服务所有场景，最终会得到一个巨大的、充满可选字段的上帝模型。限界上下文允许每个领域拥有自己的"商品"模型，彼此独立演进。

```
┌─────────────────────────────────────────────────────────────────┐
│                    DDD 限界上下文映射图                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────────┐    防腐层     ┌──────────────┐               │
│  │  商品管理      │◄──────────►│  订单管理      │               │
│  │  上下文        │   (ACL)     │  上下文        │               │
│  │  商品详情      │             │  订单快照      │               │
│  │  SKU 管理     │             │  订单状态      │               │
│  └──────┬───────┘             └──────┬───────┘               │
│         │                            │                        │
│         │ 共享内核(SKU ID)            │ 领域事件                 │
│         ▼                            ▼                        │
│  ┌──────────────┐    开放主机    ┌──────────────┐               │
│  │  库存管理      │◄──────────►│  支付管理      │               │
│  │  上下文        │   (OHS)     │  上下文        │               │
│  │  SKU 库存     │             │  支付单        │               │
│  │  预留/扣减    │             │  退款          │               │
│  └──────────────┘             └──────────────┘               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 上下文映射模式

当两个限界上下文需要协作时，有几种标准的映射模式：

**共享内核（Shared Kernel）**：两个上下文共享一小部分模型。例如商品管理和库存管理都使用相同的 SKU ID。共享内核应该尽可能小，因为它的变更会影响两个上下文。

**防腐层（Anti-Corruption Layer, ACL）**：当一个上下文需要依赖另一个上下文的模型时，通过一个翻译层来隔离。订单服务不直接使用商品服务的内部模型，而是通过防腐层将商品模型转换为订单快照。这样商品服务的内部变化不会波及订单服务。

**开放主机服务（Open Host Service, OHS）**：服务通过标准化的协议（如 REST API、事件总线）对外暴露能力，任何消费方都可以接入，而不需要特别的适配。

**发布语言（Published Language）**：配合 OHS 使用，定义一套双方都能理解的数据格式（如 Protobuf Schema、AsyncAPI 规范）。

## 领域事件与服务解耦

领域事件是服务间解耦的关键手段。当一个服务的状态发生变化时，它发布一个事件，其他服务订阅这些事件来同步状态，而不是直接调用。

```
订单服务                    事件总线                   其他服务
   │                         │                         │
   │  OrderCreated           │                         │
   │────────────────────────►│  ──► 库存服务（扣减库存） │
   │                         │  ──► 支付服务（发起支付） │
   │                         │  ──► 通知服务（发送短信） │
   │                         │  ──► 积分服务（增加积分） │
   │                         │                         │
   │  PaymentCompleted       │                         │
   │────────────────────────►│  ──► 订单服务（更新状态） │
   │                         │  ──► 物流服务（创建运单） │
```

领域事件的好处：生产者不需要知道谁在消费，新增消费者时生产者无需修改。这是开闭原则在服务层面的体现。

### 领域事件设计规范

```json
{
  "event_id": "evt-20240115-001",
  "event_type": "OrderCreated",
  "timestamp": "2024-01-15T10:30:00Z",
  "source": "order-service",
  "version": "1.0",
  "data": {
    "order_id": "ORD-20240115-001",
    "user_id": "USR-12345",
    "total_amount": 299.00,
    "items": [
      {"product_id": "PROD-001", "sku_id": "SKU-001-A", "quantity": 2, "unit_price": 149.50}
    ]
  },
  "metadata": {
    "correlation_id": "req-abc-123",
    "causation_id": "cmd-create-order-001"
  }
}
```

事件设计要点：
- `event_id` 全局唯一，用于幂等处理
- `event_type` 命名规范：`{实体}{动词过去式}`
- `correlation_id` 串联整条链路
- `causation_id` 指明触发事件的命令

## 拆分粒度判断标准

拆多细合适？没有标准答案，但有判断标准：

1. **团队规模**：一个服务应该能被一个小团队（2-8 人）完全拥有。
2. **变更频率**：变更频率差异大的模块应该拆开。
3. **扩展性需求**：资源需求差异大的模块应该拆开。
4. **故障隔离**：核心链路和非核心链路应该拆开。
5. **数据自治**：每个服务应该有自己的数据库。

### 拆分粒度评分矩阵

| 维度 | 权重 | 评分标准（1-5 分） |
|------|------|-------------------|
| 团队规模 | 25% | 1=需要 20+ 人，5=2-3 人即可拥有 |
| 变更频率差异 | 25% | 1=完全相同，5=差异极大 |
| 资源需求差异 | 15% | 1=完全相同，5=完全不同（如 CPU vs GPU） |
| 故障隔离需求 | 20% | 1=强耦合不可拆，5=完全可独立运行 |
| 数据自治程度 | 15% | 1=共享数据库，5=完全独立数据源 |

总分 ≥ 3.5 建议拆分，≤ 2.5 建议合并，中间区域需结合具体情况判断。

## 单体到微服务的演进策略

### 绞杀者模式（Strangler Fig Pattern）

像绞杀榕一样，逐步用新服务包围和替换旧系统：

1. 在单体前加一层代理（API 网关）
2. 将新功能直接用微服务实现
3. 逐步将旧功能从单体中剥离为独立服务
4. 通过路由规则将流量从旧模块切到新服务
5. 旧模块功能迁移完毕后下线

```
         客户端请求
              │
              ▼
      ┌───────────────┐
      │   API 网关     │
      └───────┬───────┘
         ┌────┴────┐
         ▼         ▼
   ┌──────────┐  ┌──────────────┐
   │  单体应用  │  │  新微服务群    │
   │ 订单(旧)  │  │ 商品(新)      │
   │ 用户(旧)  │  │ 推荐(新)      │
   └──────────┘  └──────────────┘
   
   逐步迁移：订单(旧) → 订单(新) → 从单体移除
```

### 修缮者模式（Branch by Abstraction）

在单体内部先做抽象层重构，再将抽象实现替换为远程服务调用。适合无法通过路由切换流量的场景。先定义接口，单体和微服务都实现这个接口，通过配置切换。

```java
// 1. 定义抽象接口
public interface InventoryService {
    boolean deductStock(String skuId, int quantity);
    int queryStock(String skuId);
}

// 2. 本地实现（原单体中的代码）
public class LocalInventoryService implements InventoryService {
    @Autowired
    private StockRepository stockRepository;
    @Override
    public boolean deductStock(String skuId, int quantity) {
        return stockRepository.deduct(skuId, quantity) > 0;
    }
}

// 3. 远程实现（新的微服务）
public class RemoteInventoryService implements InventoryService {
    private final InventoryGrpcClient grpcClient;
    @Override
    public boolean deductStock(String skuId, int quantity) {
        return grpcClient.deductStock(skuId, quantity).getSuccess();
    }
}

// 4. 通过配置切换
@ConditionalOnProperty(name = "inventory.mode", havingValue = "remote")
public InventoryService remoteInventoryService() { ... }

@ConditionalOnProperty(name = "inventory.mode", havingValue = "local", matchIfMissing = true)
public InventoryService localInventoryService() { ... }
```

## 反模式：分布式单体

最危险的反模式是**分布式单体**——表面上是微服务，实际上：

- 服务间共享数据库，改一个表结构影响多个服务
- 服务间强耦合，一个服务挂了整个链路不可用
- 发布时需要多个服务同时上线
- 没有独立的团队所有权

分布式单体兼具单体的耦合问题和分布式的复杂性，是最糟糕的架构状态。

### 分布式单体检测清单

```
□ 是否有多个服务连接同一个数据库？
□ 修改一个服务的 API 是否需要同时修改多个调用方？
□ 部署一个服务时是否需要同时部署其他服务？
□ 一个服务宕机是否会导致其他服务不可用？
□ 是否有超过 3 个服务参与同一个请求的同步调用链？
□ 是否有跨服务的数据库 JOIN 查询？
□ 是否有服务间共享的库（library）且该库包含业务逻辑？

如果以上问题有 3 个以上回答"是"，你的系统很可能是分布式单体。
```

## 常见误区

1. **按技术层次拆分**：把系统拆成"数据访问层服务""业务逻辑层服务""展示层服务"。应该按业务能力拆分。

2. **一开始就拆得很细**：对新项目直接上几十个微服务。应该从单体开始，等边界清晰后再拆。

3. **忽略数据拆分**：服务拆了但数据库没拆，所有服务连同一个数据库。数据库是最大的耦合点。

4. **追求"一步到位"**：试图一次性把单体拆成微服务。正确做法是渐进式演进。

5. **忽视组织结构**：康威定律指出，系统架构往往反映组织结构。如果团队还是按前端/后端/DBA 划分，微服务架构很难落地。

6. **过度追求"纯粹"**：为了拆分而拆分，把所有共享逻辑都做成独立服务。共享库在某些场景比共享服务更合适——如果共享逻辑不需要独立部署和伸缩，做成库比做成服务更简单。

7. **忽视拆分成本**：只看到微服务的好处（独立部署、技术多样性），忽视了额外的运维成本（服务发现、链路追踪、分布式事务、配置管理）。如果团队没有能力治理 20 个服务，先从 5 个开始。

## 工程建议

1. **先用 DDD 建模再拆分**：先用事件风暴（Event Storming）梳理业务流程，识别限界上下文和领域事件。

2. **数据库跟着服务走**：每个微服务拥有自己的数据库（Database per Service），不允许跨服务直接访问数据库。

3. **为拆分预留退路**：使用防腐层隔离服务间依赖，确保一个服务的内部模型变化不会波及其他服务。

4. **渐进式演进**：从"模块化单体"开始，在单体内部按限界上下文划分模块，模块间通过接口通信。

5. **建立服务治理基线**：在拆分微服务之前，确保已具备基本的服务治理能力——服务发现、配置管理、链路追踪、日志聚合。

6. **拆分粒度与团队规模匹配**：遵循"两个披萨团队"原则——一个团队（6-8 人）能完全拥有一个服务的设计、开发、运维。如果一个服务需要多个团队协作，说明它太大了。

7. **先拆变化频率高的模块**：优先将变更频率最高的模块从单体中剥离。这样能最快获得独立部署的收益，同时风险最低（高频变更的模块边界通常最清晰）。

## 小结

服务拆分的核心是**按业务能力拆，不按技术层次拆**。DDD 的限界上下文是划分服务边界的最佳工具。上下文映射模式（共享内核、防腐层、开放主机服务）定义了服务间协作的方式。从单体到微服务应该采用渐进式演进，绞杀者模式是最成熟的实践。最重要的是警惕分布式单体。

## 参考答案

### 练习一

**思路**：按业务领域聚合概念，核心标准是"变更频率相似"和"数据内聚"。

**答案**：

| 限界上下文 | 核心概念 | 职责 |
|-----------|---------|------|
| 用户管理 | 用户 | 注册、登录、个人信息、权限管理 |
| 教学内容 | 课程、章节 | 课程创建、章节管理、内容组织 |
| 学习管理 | 学习进度、作业、考试、成绩 | 学习跟踪、作业提交、考试评分 |
| 认证与证书 | 证书 | 证书生成、证书验证 |
| 支付与订单 | 支付记录 | 课程购买、退款、支付记录 |

**要点**：
- "成绩"属于学习管理而非教学内容，因为成绩是学习行为的结果
- "证书"单独成上下文，因为它涉及发放规则和验证逻辑
- 如果平台规模较小，部分上下文可以合并

### 练习二

**思路**：分析各功能的变更理由、访问模式和团队归属是否一致。

**答案**：

建议拆分为三个服务：

- **订单核心服务**：创建订单、取消订单、查询订单、订单支付回调、订单发货。围绕"订单生命周期"，变更理由一致。
- **退款服务**：退款申请、退款审批。退款有独立的审批流程和状态机。
- **发票服务**：发票管理。发票涉及税务合规，有独立的外部依赖。

**要点**：
- 拆分的依据不是功能数量，而是变更理由和外部依赖
- "订单支付回调"必须在订单核心服务中，因为它直接改变订单状态
- 退款和发票虽然与订单相关，但它们有独立的业务规则和生命周期

**常见错误**：
- 把所有与"订单"相关的功能都放在一个服务里，导致服务职责过重
- 拆分过细，把每个功能都做成独立服务，导致调用链路过长

### 练习三

**思路**：按风险从低到高排列迁移顺序，先迁移边界最清晰、依赖最少的模块。

**答案**：

```
月份 1-2：基础设施建设
- 在单体前加 API 网关（Nginx → Kong/APISIX）
- 部署链路追踪（Jaeger）和日志聚合（ELK）
- 部署配置中心（Nacos）
- 搭建 CI/CD 流水线
- 目标：基础设施就绪，单体功能不受影响

月份 3：迁移客户管理模块
- 理由：客户管理边界最清晰，被其他模块依赖但不依赖其他模块
- 做法：在单体内部将客户管理代码隔离 → 创建独立微服务 → API 网关灰度路由
- 风险控制：保留单体中的客户模块代码，随时可回滚

月份 4：迁移工单管理模块
- 理由：工单管理依赖客户管理（已迁移），被报表分析依赖
- 风险控制：工单服务调用客户服务设置超时和降级

月份 5：迁移销售管理模块
- 理由：销售管理依赖客户管理和工单管理（均已迁移）
- 风险控制：销售数据涉及业绩统计，迁移期间保持双写

月份 6：迁移报表分析模块 + 清理单体
- 理由：报表分析依赖所有其他模块，最后迁移
- 清理：删除单体中已迁移的代码，单体变为"遗留核心"或下线
```

**要点**：
- 迁移顺序遵循"依赖最少的先迁"原则
- 每个模块迁移前必须先在单体内部做好模块隔离
- 灰度发布是风险控制的关键手段
- 每个阶段都要有回退方案
