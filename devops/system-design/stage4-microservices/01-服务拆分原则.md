# 服务拆分原则

## 一个膨胀了三年的单体

你接手一个电商系统，所有模块——商品、订单、支付、库存、用户——都打包在一个 WAR 包里。几十万行代码，每次发布全量部署，一个小模块的改动可能导致整个系统崩溃。商品服务需要大量缓存，订单服务需要强一致性，推荐服务需要 GPU。绑在一起，资源利用效率极低。

老板说"上微服务"。但怎么拆？拆太细，调用链路爆炸；拆太粗，等于换了个名字的单体。

## 按业务能力拆，不按技术层次拆

错误做法：拆成"数据访问层服务""业务逻辑层服务""展示层服务"。这是按技术层次拆，每个需求变更都会穿透所有层。

正确做法：按业务能力拆。DDD 的限界上下文是最重要的工具。

同一个业务概念在不同上下文中含义不同：

```
商品管理上下文：商品 = 详情 + SKU + 图片 + 描述
订单上下文：商品 = 快照（名称、价格、数量）
库存上下文：商品 = SKU 编号 + 库存数量
推荐上下文：商品 = 一组特征向量
```

如果用一个统一的"商品模型"服务所有场景，最终会得到一个充满可选字段的上帝模型。限界上下文允许每个领域拥有自己的模型，彼此独立演进。

## 上下文映射：服务间怎么协作

**共享内核**：两个上下文共享一小部分模型（如 SKU ID）。共享内核应该尽可能小。

**防腐层（ACL）**：订单服务不直接使用商品服务的内部模型，通过翻译层隔离。商品服务内部变化不会波及订单服务。

**开放主机服务（OHS）**：服务通过标准化协议（REST API、事件总线）对外暴露能力。

**领域事件**：订单服务发布 `OrderCreated` 事件，库存、支付、通知、积分服务各自订阅。生产者不需要知道谁在消费。新增消费者时生产者无需修改。

```json
{
  "event_id": "evt-20240115-001",
  "event_type": "OrderCreated",
  "source": "order-service",
  "data": {
    "order_id": "ORD-001",
    "total_amount": 299.00,
    "items": [{"sku_id": "SKU-001", "quantity": 2}]
  }
}
```

## 拆多细合适

五个判断标准：

```
团队规模：一个服务应该能被 2-8 人的小团队完全拥有
变更频率：变更频率差异大的模块应该拆开
扩展性需求：资源需求差异大的模块应该拆开
故障隔离：核心链路和非核心链路应该拆开
数据自治：每个服务应该有自己的数据库
```

评分矩阵（总分 ≥ 3.5 建议拆分，≤ 2.5 建议合并）：

```
维度            权重    评分标准（1-5）
──────────────────────────────────────────
团队规模        25%     1=需要 20+ 人，5=2-3 人即可拥有
变更频率差异    25%     1=完全相同，5=差异极大
资源需求差异    15%     1=完全相同，5=完全不同
故障隔离需求    20%     1=强耦合不可拆，5=完全可独立运行
数据自治程度    15%     1=共享数据库，5=完全独立数据源
```

## 从单体到微服务：绞杀者模式

像绞杀榕一样，逐步用新服务包围和替换旧系统：

```
1. 在单体前加一层代理（API 网关）
2. 新功能直接用微服务实现
3. 逐步将旧功能从单体中剥离
4. 通过路由规则将流量从旧模块切到新服务
5. 旧模块迁移完毕后下线
```

```
客户端请求 → API 网关
              ┌────┴────┐
              ▼         ▼
        ┌──────────┐  ┌──────────────┐
        │  单体应用  │  │  新微服务群    │
        │ 订单(旧)  │  │ 商品(新)      │
        │ 用户(旧)  │  │ 推荐(新)      │
        └──────────┘  └──────────────┘
```

## 最危险的反模式：分布式单体

表面上是微服务，实际上：
- 服务间共享数据库，改一个表结构影响多个服务
- 服务间强耦合，一个服务挂了整个链路不可用
- 发布时需要多个服务同时上线

分布式单体兼具单体的耦合问题和分布式的复杂性。

检测清单：
```
□ 是否有多个服务连接同一个数据库？
□ 修改一个服务的 API 是否需要同时修改多个调用方？
□ 部署一个服务时是否需要同时部署其他服务？
□ 一个服务宕机是否会导致其他服务不可用？
□ 是否有超过 3 个服务参与同一个请求的同步调用链？

如果有 3 个以上回答"是"，很可能是分布式单体。
```

### 练习三

```typescript
function evaluateSplit(scores: {
  teamSize: number; changeFreq: number;
  resourceNeeds: number; faultIsolation: number;
  dataAutonomy: number
}): { score: number; recommendation: 'split' | 'merge' | 'analyze' } {
  const weights = [0.25, 0.25, 0.15, 0.20, 0.15]
  const values = [scores.teamSize, scores.changeFreq, scores.resourceNeeds,
                  scores.faultIsolation, scores.dataAutonomy]
  for (const v of values) { if (v < 1 || v > 5) throw new Error('评分必须在 1-5 之间') }
  const score = values.reduce((sum, v, i) => sum + v * weights[i], 0)
  const recommendation = score >= 3.5 ? 'split' : score <= 2.5 ? 'merge' : 'analyze'
  return { score: Math.round(score * 100) / 100, recommendation }
}
```
