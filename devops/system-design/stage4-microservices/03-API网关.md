# API 网关

## 场景引入

你的微服务电商系统已经上线，前端团队开始抱怨：每次调用接口都要处理认证逻辑，不同服务的地址和端口各不相同，跨域问题层出不穷。后端团队也有苦水：限流逻辑在每个服务里重复实现，灰度发布需要手动改 Nginx 配置，接口版本管理混乱。

这些问题的根源在于：**微服务架构缺少一个统一的流量入口**。客户端不应该直接面对十几个微服务，它需要一个"门卫"——这就是 API 网关。

## 学习目标

- 理解 API 网关的核心职责：路由、认证、限流、日志
- 掌握 Kong 和 APISIX 两大主流网关的特点与选型
- 理解 JWT、OAuth2、API Key 三种认证方式的适用场景
- 掌握限流的实现原理和灰度发布的策略
- 理解 API 网关与 Nginx 直接代理的本质区别

## API 网关的职责

API 网关是微服务架构的**统一入口**，所有外部请求都经过网关再转发到后端服务。

```
┌─────────────────────────────────────────────────────────────┐
│                  API 网关请求处理流程                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  客户端请求                                                  │
│      │                                                      │
│      ▼                                                      │
│  ┌──────────┐                                               │
│  │ 路由匹配  │ ← 根据路径/方法/Header 路由到目标服务          │
│  └────┬─────┘                                               │
│       ▼                                                     │
│  ┌──────────┐                                               │
│  │ 认证鉴权  │ ← 验证 Token、检查权限                        │
│  └────┬─────┘                                               │
│       ▼                                                     │
│  ┌──────────┐                                               │
│  │ 限流熔断  │ ← 令牌桶限流、熔断降级                         │
│  └────┬─────┘                                               │
│       ▼                                                     │
│  ┌──────────┐                                               │
│  │ 请求转换  │ ← 添加 Header、修改路径、协议转换              │
│  └────┬─────┘                                               │
│       ▼                                                     │
│  ┌──────────┐                                               │
│  │ 日志采集  │ ← 记录请求日志、链路追踪                       │
│  └────┬─────┘                                               │
│       ▼                                                     │
│  后端微服务                                                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**路由**：根据请求路径、HTTP 方法、Header 等条件，将请求转发到对应的后端服务。例如 `/api/v1/orders/*` 转发到订单服务。

**认证鉴权**：在网关层统一验证用户身份，后端服务不需要重复实现认证逻辑。

**限流**：保护后端服务不被突发流量击垮。可以按服务、按用户做细粒度限流。

**日志与监控**：统一记录请求日志、响应时间、错误率，为链路追踪提供入口。

## Kong vs APISIX

**Kong** 基于 Nginx + Lua，采用传统的配置模型。核心概念是 Service（后端服务）和 Route（路由规则），通过插件扩展功能。配置变更通常需要通过 Admin API 写入 PostgreSQL 数据库。

**APISIX** 同样基于 Nginx + Lua，但采用**动态路由**和**插件热加载**机制。配置存储在 etcd 中，变更实时监听生效，不需要重启。性能在高并发场景下优于 Kong。

```
┌─────────────────────────────────────────────────────────────┐
│               Kong vs APISIX 架构对比                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Kong:                                                      │
│  Admin API ──► PostgreSQL ──► Kong 代理 (Nginx)             │
│  配置变更延迟：秒级（轮询间隔）                               │
│                                                             │
│  APISIX:                                                    │
│  Dashboard ──► etcd ──► APISIX 代理 (Nginx) 实时 Watch     │
│  配置变更延迟：毫秒级                                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**选型建议**：新项目优先考虑 APISIX（性能更好、配置更灵活），已有 Kong 生态的团队继续用 Kong。

## 认证鉴权

**API Key**：最简单的认证方式，每个调用方分配一个唯一密钥。适合对外公开的 API。缺点是安全性较低。

**JWT（JSON Web Token）**：用户登录后签发一个包含用户信息的 Token，网关验证签名和有效期，无需查询数据库。适合无状态认证。

**OAuth2**：授权框架，允许第三方应用在用户授权下访问资源。适合"用微信登录""用 GitHub 登录"等场景。

**实践建议**：内部服务间调用不需要认证（通过网络隔离保证安全），外部用户认证用 JWT，第三方接入用 OAuth2。

### JWT 认证流程

```
1. 用户登录 → 用户服务签发 JWT Token
2. 客户端携带 Token 请求 API 网关
   Header: Authorization: Bearer <token>
3. 网关验证签名、检查过期时间
4. 验证通过 → 提取用户 ID 注入 Header: X-User-ID: 123
5. 转发给后端服务（后端无需再验证 Token）

JWT Payload 示例：
{
  "sub": "user-123",        // 用户 ID
  "name": "张三",            // 用户名
  "roles": ["user"],        // 角色
  "exp": 1705308600         // 过期时间
}
```

## 限流实现

**令牌桶**：以固定速率往桶里放令牌，请求需要消耗一个令牌。允许一定程度的突发流量。

**滑动窗口**：统计最近 N 秒内的请求数，超过阈值则拒绝。比固定窗口更平滑。

限流粒度可以是全局、按服务、按用户、按 IP。实践中通常组合使用：全局限流保护整体容量，按服务限流保护单个服务，按用户限流防止单个用户滥用。

### 令牌桶实现伪代码

```python
class TokenBucket:
    def __init__(self, rate: float, capacity: int):
        self.rate = rate          # 每秒产生的令牌数
        self.capacity = capacity  # 桶的最大容量
        self.tokens = capacity
        self.last_refill = time.time()
        self.lock = threading.Lock()

    def try_acquire(self) -> bool:
        with self.lock:
            now = time.time()
            elapsed = now - self.last_refill
            new_tokens = elapsed * self.rate
            self.tokens = min(self.capacity, self.tokens + new_tokens)
            self.last_refill = now
            if self.tokens >= 1:
                self.tokens -= 1
                return True
            return False

bucket = TokenBucket(rate=1000, capacity=2000)  # 1000 QPS，突发 2000
```

## 灰度发布

灰度发布是将新版本先部署到少量实例，逐步放量验证。

常见策略：

1. **按比例分流**：5% 的流量发到新版本，95% 发到旧版本。
2. **按用户分流**：内部员工先使用新版本，确认无问题后扩展到白名单用户。
3. **按 Header 分流**：请求头中携带 `X-Canary: true` 的请求路由到新版本。

```
                    请求
                     │
                     ▼
              ┌──────────┐
              │ API 网关  │
              │ 5% → v2  │
              │ 95% → v1 │
              └────┬─────┘
              ┌────┴────┐
              ▼         ▼
        ┌──────────┐ ┌──────────┐
        │ 服务 v1   │ │ 服务 v2   │
        │ (稳定版)  │ │ (灰度版)  │
        └──────────┘ └──────────┘
```

## API 网关 vs Nginx 直接代理

Nginx 是通用的反向代理和负载均衡器。API 网关在 Nginx 基础上增加了：

- **动态路由**：路由规则可以通过 API 动态修改，不需要重启
- **认证鉴权**：内置 JWT、OAuth2、API Key 认证插件
- **限流熔断**：内置令牌桶、滑动窗口等限流算法
- **可观测性**：内置请求日志、指标采集、链路追踪集成

简单来说，Nginx 适合静态路由和简单反向代理，API 网关适合微服务架构下的流量治理。

### 网关高可用设计

```
           DNS 解析（多 A 记录或 GSLB）
                    │
         ┌──────────┼──────────┐
         ▼          ▼          ▼
    ┌────────┐ ┌────────┐ ┌────────┐
    │ LB-1   │ │ LB-2   │ │ LB-3   │  负载均衡层
    └───┬────┘ └───┬────┘ └───┬────┘
    ┌───┴──────────┴──────────┴───┐
    │        网关集群              │
    │  ┌─────┐ ┌─────┐ ┌─────┐   │
    │  │GW-1 │ │GW-2 │ │GW-3 │   │
    │  └─────┘ └─────┘ └─────┘   │
    └─────────────────────────────┘

关键点：
1. 网关至少 3 实例，跨可用区部署
2. 前面挂负载均衡器，负载均衡器也需要高可用
3. 网关配置存储在 etcd/数据库，不依赖本地文件
4. 网关健康检查：定期探测后端服务，自动摘除不健康实例
```

## 常见误区

1. **网关承载业务逻辑**：在网关里写业务逻辑，导致网关变成"分布式单体"。网关只做流量治理，不做业务。

2. **所有功能都在网关层实现**：认证、限流、日志、转换全部堆在网关，导致网关成为性能瓶颈。应根据职责分层。

3. **忽略网关的高可用**：网关是所有流量的入口，它挂了整个系统不可用。网关必须集群部署。

4. **硬编码路由规则**：路由规则写死在配置文件里，每次变更都要重启。应使用支持动态路由的网关。

5. **网关层做数据库查询**：在认证插件里查询数据库验证用户权限。认证信息应缓存在网关本地或 Redis 中。

6. **忽略网关性能监控**：不监控网关自身的延迟和错误率。网关作为流量入口，它的性能指标是系统健康度的晴雨表。

7. **单网关承担所有职责**：内部服务间通信也经过外部网关，增加不必要的延迟。应区分外部网关和内部网关。

## 工程建议

1. **网关分层部署**：外部网关处理认证、限流、WAF，内部网关处理服务间路由和负载均衡。

2. **统一错误响应格式**：网关层的错误（如 401、429）应返回统一的 JSON 格式，而不是 HTML 错误页。

3. **监控网关指标**：重点关注请求延迟（P50/P99）、错误率（4xx/5xx 比例）、限流触发次数。

4. **渐进式引入**：小规模用 Nginx + Lua 足够，中等规模用 Kong/APISIX，大规模再考虑 Service Mesh。

5. **网关配置版本化**：路由规则、限流配置、认证配置都应该纳入版本控制，支持回滚。

6. **统一错误响应格式**：网关层的错误应返回统一 JSON 格式：
```json
{"error": {"code": 429, "message": "请求过于频繁，请稍后重试", "retry_after": 5}}
```

7. **API 文档自动生成**：利用网关的路由配置自动生成 API 文档（OpenAPI/Swagger），保持文档与实际接口一致。

## 小结

API 网关是微服务架构的统一流量入口，核心职责是路由、认证、限流和日志。Kong 和 APISIX 是主流开源网关，APISIX 在动态路由和性能方面更有优势。认证方式根据场景选择：API Key 适合第三方接入，JWT 适合用户认证，OAuth2 适合第三方授权。网关不应承载业务逻辑，只做流量治理。

## 练习

### 练习一：网关架构设计

某公司有以下服务：用户服务、商品服务、订单服务、支付服务、推荐服务。外部客户端包括 Web 前端、iOS/Android App、第三方合作伙伴。请设计 API 网关的部署架构，说明需要几个网关、各自的职责、路由规则。

### 练习二：限流方案设计

商品服务的查询接口在促销期间 QPS 从 1000 飙升到 10000。商品服务最多能承受 5000 QPS。请设计网关层的限流方案，要求：保护商品服务不被击垮，同时尽量不影响正常用户的访问体验。

### 练习三：灰度发布方案设计

订单服务需要发布一个大版本更新（v2），涉及数据库表结构变更和 API 接口变更。请设计灰度发布方案，要求：(1) 零停机发布；(2) 发现问题能快速回滚；(3) 不影响正在处理中的订单。

## 参考答案

### 练习一

**思路**：按访问来源和安全要求分层部署网关。

**答案**：

```
外部流量 → 外部 API 网关（认证、限流、WAF）
              │
         ┌────┴────┐
         ▼         ▼
    Web 前端    App/第三方
         │
         ▼
    内部 API 网关（服务路由、负载均衡）
         │
    ┌────┼────┬────────┐
    ▼    ▼    ▼        ▼
  用户  商品  订单    支付
```

认证策略：Web/App 用 JWT，第三方用 OAuth2 + API Key。

### 练习二

**思路**：分层限流，优先保护核心服务，对超限请求做优雅降级。

**答案**：

- 第一层：全局限流 8000 QPS（令牌桶，允许短暂突发）
- 第二层：商品服务限流 4500 QPS（留 10% 余量）
- 第三层：单用户限流 50 QPS（防止单点滥用）
- 降级策略：超限请求返回缓存数据或热门商品列表
- 实现：Redis 滑动窗口计数器，HTTP 429 + Retry-After

### 练习三

**思路**：通过流量切换实现零停机，数据库兼容性是关键。

**答案**：

```
阶段 1：数据库兼容（提前 1 周）
- v2 的数据库变更必须向后兼容（只加字段、不删字段、不改类型）
- 执行 DDL 变更，v1 代码不受影响

阶段 2：部署 v2 实例
- 部署 2 台 v2 实例（总共 10 台中的 2 台）
- 网关配置：5% 流量路由到 v2

阶段 3：灰度放量
- 第 1 天：5% 流量到 v2，监控错误率和延迟
- 第 3 天：20% 流量到 v2
- 第 5 天：50% 流量到 v2
- 第 7 天：100% 流量到 v2，v1 保留 2 台作为回滚备用

阶段 4：清理
- v2 稳定运行 1 周后，下线 v1 实例

回滚方案：
- 发现问题立即将流量切回 v1（秒级生效）
- v2 的数据库变更是向后兼容的，v1 可以直接读取
- 正在处理中的订单：v2 会完成处理，新请求走 v1

关键约束：
- v2 必须能处理 v1 创建的订单（向前兼容）
- v1 必须能读取 v2 写入的数据（向后兼容）
```
