# 服务通信

## 场景引入

你已经把电商系统拆成了商品服务、订单服务、库存服务、支付服务等多个微服务。现在面临第一个技术问题：**这些服务之间怎么通信？**

用户下单时，订单服务需要调用库存服务检查库存、调用价格服务计算优惠、调用支付服务发起支付。这些调用是同步等待还是异步处理？用 HTTP REST 还是 gRPC？如果调用超时了怎么办？如果库存服务挂了怎么办？

选择错误的通信方式会导致严重的性能问题。某电商团队把所有服务间调用都用 HTTP/REST 实现，结果一个下单请求链路中有 8 次 HTTP 调用，每次序列化/反序列化 JSON 的开销累加，导致下单接口 P99 延迟超过 3 秒。后来内部调用改用 gRPC，延迟降到了 800ms。

服务通信是微服务架构的神经系统，选择合适的通信模式直接决定了系统的性能、可靠性和可维护性。

## 学习目标

- 理解同步通信和异步通信的区别及适用场景
- 掌握 HTTP/REST、gRPC、Thrift 三种同步通信协议的特点和选型
- 理解消息队列在异步通信中的作用，掌握发布-订阅模式
- 了解服务网格（Service Mesh）的架构原理和解决的问题
- 掌握超时设置、重试策略、服务发现等关键机制

## 同步通信：HTTP/REST vs gRPC vs Thrift

同步通信的特点是调用方发出请求后**阻塞等待**响应。适合需要立即获取结果的场景。

```
┌─────────────────────────────────────────────────────────────┐
│                  同步通信协议对比                              │
├──────────┬──────────────┬──────────────┬───────────────────┤
│          │ HTTP/REST    │ gRPC         │ Thrift            │
├──────────┼──────────────┼──────────────┼───────────────────┤
│ 协议层   │ HTTP/1.1 或 2│ HTTP/2       │ 自定义 TCP        │
│ 编码格式 │ JSON         │ Protobuf     │ Protobuf/自定义   │
│ 性能     │ 一般         │ 高           │ 高                │
│ 浏览器   │ 原生支持     │ 需要 gRPC-Web│ 不支持            │
│ 接口定义 │ 无强制约束   │ .proto 文件  │ .thrift 文件      │
│ 流式传输 │ 不支持       │ 支持双向流   │ 支持单向流        │
│ 生态     │ 最成熟       │ 快速增长     │ 稳定但增长放缓    │
└──────────┴──────────────┴──────────────┴───────────────────┘
```

**HTTP/REST**：最通用的选择，几乎所有语言和框架都有良好支持。适合对外 API、跨团队协作、需要浏览器直接调用的场景。缺点是 JSON 序列化开销大，HTTP/1.1 的连接复用能力有限。

**gRPC**：Google 开源的 RPC 框架，基于 HTTP/2 和 Protobuf。性能优异（序列化体积小、速度快，比 JSON 小 3-10 倍），支持双向流式通信。适合内部服务间高频调用。缺点是调试不如 JSON 直观。

**Thrift**：Facebook 开源的 RPC 框架，性能与 gRPC 相当。缺点是社区活跃度不如 gRPC，生态相对封闭。

**选型建议**：对外 API 用 REST，内部高频通信用 gRPC。很多团队采用混合策略——对外暴露 REST，内部用 gRPC。

## 异步通信：消息队列与事件总线

异步通信的核心思想是：**发送方不等待接收方处理完成**。发送方将消息放入消息队列，接收方按自己的节奏消费。

```
┌──────────────────────────────────────────────────────────────┐
│             同步 vs 异步通信对比                               │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  同步通信：                                                   │
│  ┌──────────┐    请求     ┌──────────┐                       │
│  │ 订单服务  │───────────►│ 库存服务  │                       │
│  │          │◄───────────│          │                       │
│  └──────────┘    响应     └──────────┘                       │
│  特点：阻塞等待，实时响应，强耦合                               │
│                                                              │
│  异步通信（消息队列）：                                        │
│  ┌──────────┐  消息入队  ┌──────────┐  消费  ┌──────────┐   │
│  │ 订单服务  │──────────►│ 消息队列  │──────►│ 库存服务  │   │
│  └──────────┘           └──────────┘       └──────────┘   │
│  特点：不阻塞，削峰解耦，最终一致                              │
│                                                              │
│  异步通信（事件总线）：                                        │
│  ┌──────────┐  OrderCreated   ┌──────────┐                  │
│  │ 订单服务  │────────────────►│ 事件总线  │                  │
│  └──────────┘                 └────┬─────┘                  │
│                              ┌─────┼─────┐                  │
│                              ▼     ▼     ▼                  │
│                          ┌─────┐┌─────┐┌─────┐              │
│                          │库存  ││通知  ││积分  │              │
│                          └─────┘└─────┘└─────┘              │
│  特点：一对多分发，生产者不感知消费者                           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**请求-响应 vs 发布-订阅**：

- **请求-响应**：点对点通信，一个调用方对应一个服务方。适合"检查库存是否充足"这类需要立即回答的查询。
- **发布-订阅**：一对多广播，发布者不关心谁在订阅。适合"订单已创建"这类需要多个下游响应的事件。

**选型原则**：需要立即得到结果用同步，不需要立即结果或需要通知多个服务用异步。

## 服务网格（Service Mesh）

当微服务数量增长到几十上百个时，服务通信的治理变得极其复杂：每个服务都要实现重试、超时、熔断、链路追踪、mTLS 加密等逻辑。如果把这些逻辑写在业务代码里，会导致大量重复代码，而且每种编程语言都要实现一遍。

服务网格的核心思想是：**把通信治理逻辑从业务代码中剥离，下沉到基础设施层**。

```
┌─────────────────────────────────────────────────────────────┐
│                  Service Mesh 架构                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  控制平面（Control Plane）：Istio                            │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  Pilot（配置分发）│ Citadel（证书管理）│ Galley（验证）│   │
│  └─────────────────────────────────────────────────────┘   │
│         │ 配置下发                                           │
│         ▼                                                   │
│  数据平面（Data Plane）：Envoy Sidecar                       │
│                                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ 服务 A    │  │ 服务 B    │  │ 服务 C    │  │ 服务 D    │  │
│  │ ┌──────┐ │  │ ┌──────┐ │  │ ┌──────┐ │  │ ┌──────┐ │  │
│  │ │Envoy│ │  │ │Envoy│ │  │ │Envoy│ │  │ │Envoy│ │  │
│  │ └──────┘ │  │ └──────┘ │  │ └──────┘ │  │ └──────┘ │  │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘  │
│                                                             │
│  所有服务间流量都经过 Envoy Sidecar 代理                      │
│  业务代码无需感知重试、熔断、mTLS 等治理逻辑                   │
└─────────────────────────────────────────────────────────────┘
```

每个服务实例旁边部署一个 **Envoy Sidecar** 代理，所有出入流量都经过这个代理。代理负责负载均衡、重试、超时、熔断、mTLS 加密、链路追踪等。业务代码只需发送普通 HTTP/gRPC 请求，完全不感知这些治理逻辑。

**Istio** 是最流行的服务网格控制平面，负责向所有 Envoy 代理分发配置（路由规则、重试策略、熔断规则等）。

**适用场景**：服务数量超过 50 个、多语言技术栈、对安全通信（mTLS）有强需求。对于小规模系统，引入 Service Mesh 的运维成本可能大于收益。

## 超时设置

超时是防止级联故障的第一道防线。没有超时的调用可能无限阻塞，最终耗尽线程池。

**超时设置原则**：

1. **每一层都要设超时**：从客户端到 API 网关、从网关到服务、从服务到数据库，每一层都要有超时。
2. **超时时间逐层递减**：如果用户可接受的总延迟是 2 秒，网关超时设 1.8 秒，服务调用超时设 1.5 秒，数据库查询超时设 1 秒。
3. **区分连接超时和读取超时**：连接超时通常很短（100-500ms），读取超时根据业务逻辑的执行时间设置。
4. **不要用默认超时**：很多框架的默认超时是 30 秒甚至无超时，这对线上服务来说太长了。

## 重试策略

重试可以应对瞬时故障，但不恰当的重试可能加剧问题。

**重试的关键设计**：

1. **指数退避（Exponential Backoff）**：第一次重试等 1 秒，第二次等 2 秒，第三次等 4 秒。避免所有重试请求同时到达。
2. **设置最大重试次数**：通常 3 次。超过后快速失败，触发降级。
3. **区分可重试错误**：网络超时、503 可以重试；400（参数错误）、401（未认证）不应该重试。
4. **重试预算（Retry Budget）**：限制重试请求占总请求的比例（如 10%），防止重试风暴。
5. **幂等性保证**：重试的操作必须是幂等的，否则重复执行可能导致数据不一致。

## 服务发现

微服务实例动态伸缩，IP 地址随时变化，服务发现解决"如何找到目标服务"的问题。

**客户端发现**：调用方直接查询注册中心（如 Eureka、Nacos），获取目标服务的实例列表，自己做负载均衡。优点是少一跳，缺点是每种语言都要实现发现逻辑。

**服务端发现**：调用方通过一个代理（如 DNS、负载均衡器）访问服务，代理负责查询注册中心和路由。优点是调用方简单，缺点是多一跳延迟。

```
客户端发现：                     服务端发现：
┌────────┐                     ┌────────┐
│ 调用方  │                     │ 调用方  │
└───┬────┘                     └───┬────┘
    │ 查询注册中心                   │ 请求代理
    ▼                              ▼
┌────────┐                     ┌────────┐
│注册中心│                     │ 代理   │──► 查询注册中心
└───┬────┘                     └───┬────┘
    │ 返回实例列表                   │ 路由到实例
    ▼                              ▼
┌────────┐                     ┌────────┐
│目标服务│                     │目标服务│
└────────┘                     └────────┘
```

## 常见误区

1. **所有通信都用 HTTP/REST**：内部高频调用也用 REST，导致序列化开销大、连接效率低。内部服务间应优先考虑 gRPC。

2. **过度使用同步调用**：一个请求链路中同步调用 5-6 个服务，延迟累加严重。应评估哪些调用可以改为异步。

3. **忽略超时和重试**：服务调用没有设置超时，一个慢服务拖垮整条链路。重试没有指数退避，导致故障服务被重试请求淹没。

4. **Service Mesh 万能论**：小规模系统（< 20 个服务）强行引入 Istio，运维成本远超收益。Service Mesh 是解决大规模服务治理的工具，不是银弹。

5. **消息队列当作万能解耦工具**：所有通信都走消息队列，导致系统变成"消息驱动的意大利面"，消息追踪和调试极其困难。

6. **忽略消息顺序性**：在需要保证消息顺序的场景（如同一订单的状态变更）使用了不保证顺序的队列配置，导致状态错乱。

7. **同步调用链路过长**：A → B → C → D → E 的同步调用链，任意一个环节故障都会导致整条链路失败。同步调用链不应超过 3 层。

## 工程建议

1. **同步与异步混合使用**：查询类操作用同步（gRPC/REST），状态变更通知用异步（消息队列/事件总线）。不要非此即彼。

2. **统一通信协议**：内部服务间统一使用 gRPC，对外统一使用 REST。避免每个团队选不同协议导致集成困难。

3. **从简单的服务发现开始**：小规模用 Nacos 或 Consul 做注册中心，DNS 做服务发现。规模大了再考虑 Service Mesh。

4. **建立通信规范**：所有服务必须设置超时、所有重试必须有指数退避、所有异步消息必须有死信队列。这些应该写入团队规范，而不是靠自觉。

5. **监控通信链路**：为每个服务间调用采集延迟、错误率、吞吐量指标。没有可观测性的微服务就是在裸奔。

6. **消息队列的死信队列**：消费失败超过最大重试次数的消息进入死信队列，人工处理。不要让失败消息无限重试阻塞队列。

7. **接口版本管理**：API 变更时通过版本号（如 `/v1/`、`/v2/`）管理，旧版本至少保留 6 个月，给调用方迁移时间。

## 小结

服务通信是微服务架构的基础。同步通信（HTTP/REST、gRPC）适合需要立即响应的场景，异步通信（消息队列、事件总线）适合解耦和削峰。服务网格将通信治理逻辑下沉到基础设施层，适合大规模系统。超时、重试、服务发现是每一种通信模式都需要关注的基础机制。选择通信模式时，应根据业务场景混合使用，而不是一刀切。

## 参考答案

### 练习一

**思路**：核心判断标准是"是否需要立即得到结果"以及"是否影响主流程"。

**答案**：

| 步骤 | 通信模式 | 理由 |
|------|---------|------|
| 检查库存 | 同步 | 必须立即知道库存是否充足，库存不足则无法下单 |
| 创建订单 | 同步（本地操作） | 订单服务自身的数据库操作，不是跨服务调用 |
| 扣减库存 | 同步 | 推荐用 TCC 模式同步扣减，因为库存超卖代价高 |
| 发起支付 | 同步 | 需要立即获取支付链接/支付状态返回给用户 |
| 发送通知短信 | 异步 | 不影响下单主流程，短信延迟几秒用户无感知 |
| 增加用户积分 | 异步 | 积分到账可以有延迟，不影响核心交易流程 |

**要点**：
- 核心交易链路（检查库存→创建订单→扣减库存→发起支付）用同步
- 非核心链路（通知、积分）用异步，通过事件订阅实现
- 扣减库存的通信模式取决于分布式事务方案的选择

### 练习二

**思路**：在用户可接受延迟内，为价格服务设置合理的超时和重试次数，同时考虑降级方案。

**答案**：

```
超时设置：
- 连接超时：200ms（价格服务正常情况下 200ms 内响应）
- 读取超时：800ms（留出足够余量，同时不允许等待 2 秒的慢请求）

重试策略：
- 最大重试次数：2 次（总共 3 次尝试）
- 重试间隔：指数退避，200ms → 400ms
- 只对 5xx 错误和超时重试，4xx 不重试

时间预算：
- 第 1 次：连接 200ms + 读取 800ms = 1s
- 第 2 次：等待 200ms + 连接 200ms + 读取 800ms = 1.2s
- 第 3 次：等待 400ms + 连接 200ms + 读取 800ms = 1.4s
- 总计最坏情况：约 3.6s，超过 3s 预算

优化方案：
- 减少读取超时到 600ms，总共最坏 2.8s，在预算内
- 或者只重试 1 次，总共最坏 2.2s

降级方案：
- 如果 3 次都失败，使用本地缓存的默认优惠规则（不计算精确优惠）
- 记录异常日志，事后人工处理优惠差额
```

**要点**：
- 超时时间应基于 P99 延迟设置，而不是平均延迟
- 重试次数要控制，避免总延迟超过上游可接受范围
- 必须有降级方案，不能因为价格服务不可用而阻塞下单

### 练习三

**思路**：按业务域划分 Topic，每个消费者组独立消费，保证幂等性和失败处理。

**答案**：

```
Topic 设计：
- order.events：订单相关事件（OrderCreated, OrderPaid, OrderCancelled）
- 不同事件类型通过 message header 中的 event_type 区分

消费组设计：
- inventory-consumer-group（库存服务）：消费 OrderCreated 扣减库存
- points-consumer-group（积分服务）：消费 OrderPaid 增加积分
- notification-consumer-group（通知服务）：消费 OrderCreated 发短信
- analytics-consumer-group（数据分析）：消费所有事件更新报表

消息格式：
{
  "event_id": "evt-uuid-001",
  "event_type": "OrderCreated",
  "timestamp": "2024-01-15T10:30:00Z",
  "data": { "order_id": "ORD-001", "user_id": "USR-123", "total_amount": 29900 }
}

幂等方案：
- 消费者用 event_id 做幂等键
- Redis 记录已处理的 event_id（TTL 7 天）
- 数据库用唯一约束兜底

失败处理：
- 消费失败重试 3 次，间隔指数退避
- 3 次失败后进入死信队列
- 死信队列消息人工处理或自动告警
```

**要点**：
- 每个消费组独立消费，互不影响
- event_id 全局唯一，是幂等性的基础
- 死信队列是消息队列方案的必备组件
