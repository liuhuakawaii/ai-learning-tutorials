# 设计搜索引擎

## 场景引入

你的公司有一个电商网站，商品数量超过 1000 万。用户搜索"红色连衣裙"时，系统需要在 200 毫秒内返回相关商品，并按相关性排序。当前的数据库 LIKE 查询已经无法满足需求——全表扫描一条 SQL 要跑 3 秒，而且无法支持分词、纠错、同义词等搜索功能。

你需要设计一个搜索引擎，支持全文检索、分词、相关性排序、搜索建议等能力。这是 Elasticsearch 最典型的应用场景。

## 学习目标

- 理解倒排索引的原理和构建过程
- 掌握中文分词的技术方案（jieba/IK Analyzer）
- 了解 Elasticsearch 的架构（节点/分片/副本）
- 理解相关性评分算法（TF-IDF/BM25）
- 掌握搜索建议（AutoComplete）的实现方案

## 需求分析

### 功能性需求

```
核心功能：
1. 全文搜索    — 用户输入关键词，返回匹配的商品列表
2. 分词搜索    — "红色连衣裙" 拆分为 "红色" + "连衣裙" 分别匹配
3. 搜索建议    — 用户输入时实时给出补全建议
4. 筛选与排序  — 按价格、销量、评分等维度筛选和排序
5. 高亮显示    — 搜索结果中高亮匹配的关键词

非功能性需求：
- 延迟：搜索请求 < 200ms（P99）
- 可用性：99.99%
- 数据量：支持 1000 万级文档
- 索引更新：新商品上架后 5 分钟内可被搜索到
```

## 倒排索引

倒排索引是搜索引擎的核心数据结构。它将"文档包含哪些词"转换为"词出现在哪些文档中"。

### 正排索引 vs 倒排索引

```
正排索引（文档 → 词）：
  文档1: ["红色", "连衣裙", "女", "夏季"]
  文档2: ["红色", "高跟鞋", "女", "细跟"]
  文档3: ["蓝色", "连衣裙", "女", "长款"]

倒排索引（词 → 文档）：
  "红色"   → [文档1, 文档2]
  "连衣裙" → [文档1, 文档3]
  "女"     → [文档1, 文档2, 文档3]
  "高跟鞋" → [文档2]
  "蓝色"   → [文档3]
  "夏季"   → [文档1]
```

### 倒排索引结构

```
┌─────────────────────────────────────────────────────────────┐
│                      Term Dictionary                         │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐          │
│  │ "红色"  │ │"连衣裙" │ │ "高跟鞋"│ │ "蓝色"  │  ...     │
│  └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘          │
│       │           │           │           │                │
│       ▼           ▼           ▼           ▼                │
│  ┌─────────────────────────────────────────────────┐       │
│  │              Posting List                        │       │
│  │                                                  │       │
│  │  "红色": [(doc1, tf=1, pos=[0]),                │       │
│  │           (doc2, tf=1, pos=[0])]                 │       │
│  │                                                  │       │
│  │  "连衣裙": [(doc1, tf=1, pos=[1]),              │       │
│  │             (doc3, tf=1, pos=[1])]               │       │
│  │                                                  │       │
│  │  "女": [(doc1, tf=1, pos=[2]),                  │       │
│  │         (doc2, tf=1, pos=[2]),                   │       │
│  │         (doc3, tf=1, pos=[2])]                   │       │
│  └─────────────────────────────────────────────────┘       │
│                                                             │
│  tf = term frequency（词频）                                 │
│  pos = position（词在文档中的位置，用于短语查询）              │
└─────────────────────────────────────────────────────────────┘
```

### 搜索过程

```
用户搜索："红色 连衣裙"

1. 分词：["红色", "连衣裙"]
2. 查倒排索引：
   - "红色"   → [doc1, doc2]
   - "连衣裙" → [doc1, doc3]
3. 取交集：[doc1]（同时包含两个词的文档）
4. 计算相关性评分，排序
5. 返回结果
```

## 中文分词

中文分词比英文复杂得多。英文单词之间有空格分隔，中文没有。

### 分词挑战

```
英文："I love red dress" → ["I", "love", "red", "dress"]
中文："我爱红色连衣裙" → ["我", "爱", "红色", "连衣裙"] 或
                         ["我", "爱", "红", "色", "连衣", "裙"]  ← 错误分词
```

### 分词器对比

```
分词器       算法              特点                    适用场景
──────────────────────────────────────────────────────────────────
jieba        HMM + 前缀词典   Python 生态，开箱即用     离线处理、Python 项目
IK Analyzer  词典 + 正反向     Java 生态，ES 插件       Elasticsearch 首选
HanLP        多种算法组合      功能全面，支持命名实体    需要 NLP 能力的场景
THULAC       清华大学开发      准确率高                 学术研究
```

### IK Analyzer 配置

```json
// Elasticsearch 索引配置
{
  "settings": {
    "analysis": {
      "analyzer": {
        "ik_max_analyzer": {
          "type": "custom",
          "tokenizer": "ik_max_word"
        },
        "ik_smart_analyzer": {
          "type": "custom",
          "tokenizer": "ik_smart"
        }
      }
    }
  }
}

// ik_max_word: 最细粒度分词
// "中华人民共和国" → ["中华人民共和国", "中华", "华人", "人民共和国", "人民", "共和国", "共和", "国"]

// ik_smart: 智能分词
// "中华人民共和国" → ["中华人民共和国"]
```

**索引时用 ik_max_word**（最细粒度，提高召回率），**搜索时用 ik_smart**（智能分词，提高准确率）。

### 核心概念

```
概念          说明
──────────────────────────────────────────────────
Cluster      ES 集群，由多个节点组成
Node         单个 ES 实例
Index        索引，类似数据库的表
Shard        分片，索引的水平拆分单元
Replica      副本，分片的复制，提供高可用和读扩展
Document     文档，索引中的一条记录（JSON 格式）
```

### 分片策略

```
分片数选择原则：
  - 每个分片建议 10-50GB 数据
  - 分片数 = 预期数据量 / 单分片大小
  - 分片数确定后不能修改（需要重建索引）

示例：
  1000 万商品，每条约 2KB → 总量约 20GB
  分片数 = 20GB / 20GB = 1 个分片（足够）
  副本数 = 1（一主一副本，提供高可用）

注意：分片过多会导致资源浪费和查询性能下降
```

## 查询 DSL

Elasticsearch 使用 JSON 格式的 DSL 进行查询。核心概念：`must` 必须匹配且影响评分，`filter` 必须匹配但不影响评分（可缓存，性能更好）。

```json
{
  "query": {
    "bool": {
      "must": [{ "match": { "title": "红色连衣裙" } }],
      "filter": [
        { "range": { "price": { "gte": 100, "lte": 500 } } },
        { "term": { "category": "女装" } }
      ]
    }
  },
  "sort": [{ "_score": "desc" }, { "sales": "desc" }],
  "from": 0, "size": 20,
  "highlight": { "fields": { "title": {} } }
}
```

## 相关性评分

### TF-IDF

TF（词频）= 词在文档中出现次数 / 文档总词数，IDF（逆文档频率）= log(总文档数 / 包含该词的文档数)。TF-IDF = TF × IDF。词频越高相关性越高，越稀有的词区分度越高。

### BM25（Elasticsearch 默认）

BM25 是 TF-IDF 的改进版，解决了两个问题：**TF 饱和**（词频增加到一定程度后贡献不再显著增加）和**文档长度归一化**（长文档词频天然更高，需要惩罚）。公式中 k1=1.2 控制词频饱和，b=0.75 控制长度归一化。

## 搜索建议（AutoComplete）

推荐使用 ES 内置的 **Completion Suggester**，基于 FST（有限状态转换器），性能优于 Edge Ngram 和模糊匹配。索引时将标题存为 `completion` 类型字段，查询时按前缀匹配。

优化策略：热度排序（按搜索频次）、拼音支持（输入首字母匹配）、纠错（编辑距离）、个性化（用户历史搜索）。

## 常见误区

1. **用数据库 LIKE 代替搜索引擎**：LIKE '%关键词%' 无法走索引，全表扫描性能极差。数据量超过百万就必须用搜索引擎。
2. **分词粒度越细越好**：过细的分词会产生大量无意义的词项，增加索引体积和查询噪音。需要根据业务场景选择合适的分词粒度。
3. **分片越多越好**：分片过多会导致每个分片的数据量太小，查询时需要合并多个分片的结果，反而降低性能。
4. **忽略 filter 和 must 的区别**：filter 不计算评分且可缓存，性能优于 must。能用 filter 的条件不要用 must。
5. **搜索建议用模糊匹配**：模糊匹配（wildcard）性能极差，应该用 Completion Suggester 或 Edge Ngram。

## 工程建议

1. **索引时用 ik_max_word，搜索时用 ik_smart**：索引时最细粒度分词提高召回率，搜索时智能分词提高准确率。
2. **合理设置分片数**：根据数据量预估分片数，每个分片 10-50GB。分片数确定后不可修改，需要提前规划。
3. **使用 alias 实现零停机重建索引**：通过索引别名切换，可以在不停机的情况下重建索引、修改映射。
4. **监控集群健康状态**：关注集群状态（绿/黄/红）、分片分布、查询延迟、索引速率等指标。
5. **冷热数据分离**：近期数据放 SSD 节点（热数据），历史数据放 HDD 节点（冷数据），降低成本。

## 小结

搜索引擎的核心是**倒排索引**——将词映射到文档，支持高效的全文检索。中文分词是中文搜索的关键环节，推荐使用 IK Analyzer（ES 生态首选）。Elasticsearch 通过分片实现水平扩展，通过副本实现高可用和读扩展。相关性评分用 BM25 算法（TF-IDF 的改进版）。搜索建议用 Completion Suggester，性能优于模糊匹配。

关键设计决策：分词器选择、分片数规划、索引更新策略。这些决策直接影响搜索质量和系统性能。

## 参考答案

### 练习一

**思路**：将每个词映射到包含它的文档列表。

**答案**：
```
倒排索引：
  "苹果" → [(doc1, pos=[0]), (doc2, pos=[0])]
  "手机" → [(doc1, pos=[1]), (doc3, pos=[1])]
  "红色" → [(doc1, pos=[2]), (doc3, pos=[2])]
  "电脑" → [(doc2, pos=[1])]
  "银色" → [(doc2, pos=[2])]
  "华为" → [(doc3, pos=[0])]

搜索 "苹果 红色"：查倒排索引取交集 → 只有 doc1 同时包含两个词。
```

**要点**：多词搜索时先查各自的 Posting List，再取交集；Posting List 中的 pos 信息用于短语查询。

### 练习二

**思路**：根据数据量、增长预期和查询模式规划。

**答案**：
```
数据量：5000 万 × 3KB = 150GB，两年后约 216GB。
分片数：216GB / 25GB ≈ 10 个主分片。
副本数：1（一主一副本），总 20 个分片。
节点数：3 个专用主节点 + 4 个数据节点（每节点 5-8 分片）。
存储：每节点 200GB SSD（含倒排索引 30-50% 额外开销）。
```

**要点**：分片数确定后不可修改，必须提前规划 1-2 年增长；副本数影响可用性和存储成本。

### 练习三

**思路**：分析分词和评分机制，提出优化方案。

**答案**：
```
原因："苹果手机壳" 被分为 ["苹果", "手机", "壳"]，而非 ["苹果", "手机壳"]。

优化方案：
1. 自定义词典：将 "手机壳" 加入 IK 分词器词典
2. 短语查询：用 match_phrase 代替 match，要求词序匹配
3. 权重调整：给标题字段更高的 boost 值
4. 同义词配置：配置 "手机壳" = "手机保护套"
```

**要点**：搜索质量问题通常是分词问题，优先检查分词结果；自定义词典是最有效的手段。
