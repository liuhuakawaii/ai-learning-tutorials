# 设计 Twitter 信息流系统

## 场景引入

你加入了一家社交平台创业公司，产品形态类似 Twitter：用户可以发帖、关注其他用户、浏览信息流（Timeline）。早期用户量不大，直接查数据库就能出信息流。但当用户量突破百万，关注关系复杂度爆炸——一个大 V 有 500 万粉丝，他每发一条帖子，信息流系统需要在几秒内让这 500 万人都能看到。

这是一个经典的系统设计面试题，也是真实社交平台的核心技术挑战。信息流系统的设计直接决定了用户体验和系统成本。

## 学习目标

- 理解信息流系统的核心需求和功能边界
- 掌握推模式（Fan-out on Write）和拉模式（Fan-out on Read）的原理与取舍
- 理解混合模式如何解决名人问题（Celebrity Problem）
- 掌握时间线排序的工程实现（合并 K 个有序列表）
- 了解缓存策略和通知系统的设计

## 需求分析

### 功能性需求

```
核心功能：
1. 发布推文（Post Tweet）     — 用户发布文字/图片/视频内容
2. 关注用户（Follow）         — 建立用户间的关注关系
3. 查看信息流（View Timeline） — 获取关注的人的推文列表，按时间倒序
4. 通知（Notification）       — 被关注、被点赞、被转发时通知用户

非功能性需求：
- 低延迟：信息流加载 < 500ms
- 高可用：系统可用性 99.99%
- 最终一致性：信息流可以有秒级延迟，但不能丢数据
```

### 容量估算

```
假设：
- DAU（日活用户）：1 亿
- 每用户每天发 2 条推文 → 日写入 2 亿条
- 每用户每天刷 10 次信息流 → 日读请求 10 亿次
- 读写比 = 500:1（读远多于写）

推文存储：
- 每条推文元数据 ≈ 500 字节
- 日增量：2亿 × 500B = 100GB/天
- 年增量：约 36TB（不含媒体文件）
```

读写比悬殊意味着读优化是关键。

## 推模式 vs 拉模式

### 推模式（Fan-out on Write）

用户发推时，系统立刻将推文"推"到所有粉丝的信息流缓存中。

```
用户 A 发推
    │
    ▼
┌──────────────┐
│  Tweet 服务   │
└──────┬───────┘
       │ 查询 A 的粉丝列表
       ▼
┌──────────────┐
│  粉丝服务     │  → 返回 [B, C, D, E, F, ...]
└──────┬───────┘
       │ 并行写入每个粉丝的 Timeline 缓存
       ▼
┌──────────────────────────────────────┐
│  Timeline Cache (Redis)              │
│                                      │
│  user:B → [tweet_101, tweet_99, ...] │
│  user:C → [tweet_101, tweet_98, ...] │
│  user:D → [tweet_101, tweet_97, ...] │
│  ...                                 │
└──────────────────────────────────────┘
```

**优点**：读信息流极快，直接从缓存取，O(1) 复杂度。

**缺点**：写入放大严重。一个有 500 万粉丝的大 V 发一条推文，需要写 500 万次缓存。写入延迟高，系统负载大。

### 拉模式（Fan-out on Read）

用户刷信息流时，系统实时查询该用户关注的所有人，合并他们最近的推文。

```
用户 B 刷信息流
    │
    ▼
┌──────────────┐
│  Timeline 服务 │
└──────┬───────┘
       │ 查询 B 关注的人列表
       ▼
┌──────────────┐
│  关注服务     │  → 返回 [A, X, Y, Z]
└──────┬───────┘
       │ 并行查询每人的最近推文
       ▼
┌──────────────┐
│  Tweet 服务   │  → A: [tweet_101], X: [tweet_99], ...
└──────┬───────┘
       │ 合并排序，取 Top N
       ▼
    返回信息流
```

**优点**：写入零放大，发推只写一条记录。

**缺点**：读取延迟高，需要实时合并多个用户的推文。如果用户关注了 500 人，每次刷信息流都要查 500 次。

### 两种模式对比

```
维度          推模式              拉模式
────────────────────────────────────────────────
写入开销      高（粉丝数倍）      低（1 倍）
读取开销      低（直接读缓存）    高（实时合并）
延迟          写慢读快            写快读慢
适用场景      粉丝数少的普通用户  粉丝数多的大 V
实时性        高                  中等
```

## 混合模式：工程实践的最优解

现实中的大型社交平台几乎都采用混合模式：对普通用户用推模式，对大 V 用拉模式。

```
用户 A 发推
    │
    ▼
┌──────────────┐
│  Tweet 服务   │
└──────┬───────┘
       │
       ▼
┌──────────────────────┐     粉丝数 < 阈值（如 1000）
│  判断粉丝数量         │──────────────────────────┐
└──────────┬───────────┘                           │
           │ 粉丝数 >= 阈值                         │
           ▼                                       ▼
┌──────────────────┐              ┌──────────────────────────┐
│  仅存储推文       │              │  推模式：写入所有粉丝缓存  │
│  不做 Fan-out    │              │  Timeline Cache          │
└──────────────────┘              └──────────────────────────┘
           │
           ▼
┌──────────────────────────────────────────────────┐
│  用户 B 刷信息流时：                               │
│  1. 读取自己的 Timeline 缓存（推模式的结果）        │
│  2. 实时拉取关注的大 V 的最新推文（拉模式）          │
│  3. 合并排序后返回                                 │
└──────────────────────────────────────────────────┘
```

**阈值的选择**是关键工程决策。Twitter 的经验值大约是粉丝数超过一定量级（如数千到数万）的用户走拉模式。这个阈值需要根据实际写入负载动态调整。

## 时间线排序：合并 K 个有序列表

信息流的核心算法是将多个用户的推文列表合并成一个按时间排序的列表。这是一个经典的"合并 K 个有序链表"问题。

```
用户关注了 A, B, C 三人：

A 的推文: [101, 95, 88]  ← 按时间倒序
B 的推文: [100, 92, 85]
C 的推文: [99, 96, 80]

合并过程（最大堆）：
1. 取每个列表头部 → 堆: {101(A), 100(B), 99(C)}
2. 弹出最大值 101 → 结果: [101]
3. A 的下一个 95 入堆 → 堆: {100(B), 99(C), 95(A)}
4. 弹出 100 → 结果: [101, 100]
5. 重复直到结果足够...

最终: [101, 100, 99, 96, 95, 92, 88, 85, 80]
```

时间复杂度 O(N log K)，其中 N 是总推文数，K 是关注人数。工程实现中，只需要取 Top 200 条即可，不需要合并全部。

## 缓存策略

信息流缓存是系统性能的关键。使用 Redis Sorted Set 存储每个用户的时间线。

```
Redis 数据结构：
  Key:    timeline:{user_id}
  Value:  Sorted Set
  Score:  tweet 发布时间戳（毫秒）
  Member: tweet_id

操作：
  ZADD   timeline:user_123 1699000000000 "tweet_101"   # 写入
  ZREVRANGE timeline:user_123 0 199                     # 读取 Top 200
  ZREMRANGEBYRANK timeline:user_123 0 -1001             # 保留最新 1000 条
```

**缓存容量规划**：每个用户缓存最近 1000 条推文 ID。假设每条 ID 占 20 字节，每用户缓存约 20KB。1 亿用户需要约 2TB Redis 内存。

**缓存淘汰策略**：
- 每个用户的 Timeline 缓存保留最近 1000 条
- 超过数量时用 `ZREMRANGEBYRANK` 淘汰最旧的
- 热点用户的缓存设置较长 TTL（如 7 天）

## 通知系统

通知系统与信息流是独立的子系统，通过事件队列（Kafka）解耦。核心挑战：**去重**（同一事件不重复通知）、**聚合**（「A 和 B 等 15 人点赞了你的推文」而非 15 条独立通知）、**限流**（防止大 V 被 @ 时产生海量通知）。通知渠道包括推送通知（APNs/FCM）、站内通知（未读计数）、邮件通知（低频聚合）。

## 常见误区

1. **所有用户都用推模式**：大 V 发推会导致写入风暴，系统扛不住。必须区分普通用户和大 V。
2. **信息流必须实时**：秒级延迟对用户体验影响极小。过度追求实时性会大幅增加系统复杂度和成本。
3. **缓存可以无限增长**：不做淘汰的缓存会把 Redis 内存撑爆。必须有容量上限和淘汰策略。
4. **只关注信息流，忽略通知**：通知系统和信息流是独立的，不能混为一谈。通知有自己的去重、聚合、限流逻辑。
5. **一开始就设计混合模式**：如果用户量不大，拉模式足够用。混合模式是业务增长到一定规模后的演进方案。

## 工程建议

1. **先用拉模式验证产品**：早期用户量小，拉模式实现简单、成本低。等业务增长到瓶颈再考虑推模式。
2. **阈值动态可调**：大 V 的粉丝数阈值不要硬编码，做成可配置的，根据系统负载动态调整。
3. **推文和信息流解耦**：推文存储用持久化数据库（如 MySQL），信息流缓存用 Redis。推文写入成功后再异步更新缓存。
4. **监控写入放大比**：推模式下，监控每条推文的实际写入次数。如果放大比过高，说明阈值需要调整。
5. **预估存储成本**：信息流缓存的内存成本是主要支出。做好容量规划，避免 Redis 成本失控。

## 小结

信息流系统的核心挑战在于**读写比悬殊**（500:1），以及**大 V 问题**导致的写入放大。推模式让读快但写慢，拉模式让写快但读慢，混合模式结合两者优势是工业界的主流方案。时间线排序用最大堆合并 K 个有序列表，Redis Sorted Set 是缓存层的标准选择。

关键设计决策：混合模式的阈值、缓存容量、推文存储与缓存的解耦。这些决策没有绝对正确答案，需要根据业务规模和成本约束做取舍。

## 参考答案

### 练习一

**思路**：计算总写入量除以写入速度。

**答案**：
```
总写入量：1000 万次
写入速度：10 万次/秒
延迟 = 10,000,000 / 100,000 = 100 秒
```

100 秒的延迟意味着粉丝最快也要 1 分 40 秒后才能看到这条推文。对于社交产品来说，这个延迟不可接受。这就是为什么大 V 必须走拉模式——大 V 的推文只写一份，粉丝在刷信息流时实时拉取。

**要点**：
- 推模式的写入延迟与粉丝数成正比
- 粉丝数超过一定量级后，推模式的延迟会超出可接受范围
- 实际工程中可以用批量写入（pipeline）优化，但本质瓶颈不变

### 练习二

**思路**：先算全量缓存的内存需求，再考虑优化方案。

**答案**：
```
全量缓存：
  2 亿用户 × 500 条 × 20 字节 = 200 亿字节 ≈ 186 GB
  月成本：186 × 30 = 5,580 美元/月

实际考虑：
  - 5000 万日活用户需要缓存，其余可以不缓存
  - 5000 万 × 500 × 20B ≈ 46.5 GB
  - 月成本：46.5 × 30 ≈ 1,395 美元/月
```

**优化方案**：
- 只缓存活跃用户（LRU 淘汰不活跃用户的缓存）
- 推文 ID 用雪花算法生成，8 字节足够，不需要 20 字节
- 非活跃用户的缓存从数据库实时构建（拉模式兜底）

**要点**：
- 缓存成本与活跃用户数成正比，不是注册用户数
- ID 长度优化可以显著降低内存消耗
- 分级缓存策略（热数据内存、冷数据磁盘）可以进一步降低成本

### 练习三

**思路**：根据系统写入负载动态调整阈值。

**答案**：
```python
import time

class DynamicThreshold:
    def __init__(self):
        self.base_threshold = 10000      # 基础阈值：粉丝数
        self.min_threshold = 1000        # 最低阈值
        self.target_write_qps = 500000   # 目标写入 QPS 上限
        self.current_threshold = self.base_threshold
        self.check_interval = 60         # 每 60 秒检查一次

    def adjust(self, current_write_qps):
        if current_write_qps > self.target_write_qps * 1.2:
            # 写入压力过大，降低阈值（让更多用户走拉模式）
            self.current_threshold = max(
                self.min_threshold,
                self.current_threshold * 0.8
            )
        elif current_write_qps < self.target_write_qps * 0.5:
            # 写入压力小，可以提高阈值（让更多用户走推模式）
            self.current_threshold = min(
                self.base_threshold,
                self.current_threshold * 1.1
            )

    def should_fan_out(self, follower_count):
        return follower_count < self.current_threshold
```

**要点**：
- 阈值调整要有上下限，避免极端情况
- 调整幅度要渐进（0.8/1.1），避免震荡
- 需要监控调整后的效果，形成闭环
