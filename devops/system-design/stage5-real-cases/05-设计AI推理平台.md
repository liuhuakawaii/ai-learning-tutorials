# 设计 AI 推理平台

## 场景引入

2023 年以来，大语言模型的爆发让 AI 推理从一个边缘需求变成了基础设施级别的挑战。一个中等规模的 AI 公司可能同时运行数十个模型版本，服务数百万用户请求，每天消耗数千 GPU 小时。

与传统 Web 服务不同，AI 推理有几个独特特征：GPU 是昂贵且稀缺的资源；模型加载需要数十秒甚至数分钟；单个推理请求的延迟可能从几十毫秒到几十秒不等；批处理可以显著提升吞吐但会增加延迟。

如何在有限的 GPU 资源下，高效地调度多个模型、管理多个版本、保证服务质量？这就是 AI 推理平台要解决的核心问题。

## 学习目标

- 理解 AI 推理平台的核心组件和请求流转过程
- 掌握 GPU 调度策略（共享、独占、MPS）的适用场景和取舍
- 设计模型版本管理和灰度发布方案
- 理解推理优化技术（量化、蒸馏、剪枝）的工程价值
- 掌握批处理（Batching）策略对吞吐和延迟的影响

## GPU 调度策略

GPU 是推理平台最昂贵的资源，调度策略直接影响成本和服务质量：

### 独占模式

```
+-------------------------------------------+
|            GPU 服务器 (8 卡)               |
+-------------------------------------------+
|  GPU 0  |  GPU 1  |  GPU 2  |  GPU 3     |
| 模型 A  | 模型 A  | 模型 B  | 模型 C     |
| 独占    | 独占    | 独占    | 独占       |
+-------------------------------------------+
```

**特点**：一个 GPU 只运行一个模型实例。性能可预测，隔离性强。
**适用**：延迟敏感的在线服务、大模型（显存需求接近单卡容量）。

### 共享模式（MPS / MIG）

```
+-------------------------------------------+
|            GPU 服务器 (8 卡)               |
+-------------------------------------------+
|  GPU 0 (MIG 分片)                         |
|  +--------+ +--------+ +--------+        |
|  | 分片 1 | | 分片 2 | | 分片 3 |        |
|  | 模型 A | | 模型 B | | 模型 C |        |
|  +--------+ +--------+ +--------+        |
+-------------------------------------------+
```

**特点**：单个 GPU 可被多个模型/任务共享。NVIDIA MPS 允许多个进程共享 GPU，MIG 将 A100/H100 切分为独立实例。
**适用**：小模型、批量推理、资源利用率优先的场景。

### 调度策略对比

| 策略 | 隔离性 | 利用率 | 延迟确定性 | 适用场景 |
|------|--------|--------|-----------|---------|
| 独占 | 强     | 低     | 高        | 在线大模型 |
| MPS  | 中     | 高     | 中        | 小模型混部 |
| MIG  | 强     | 中     | 高        | 多租户隔离 |

**工程建议**：按业务 SLA 分层。延迟敏感的在线服务用独占模式，离线批量任务用共享模式，通过调度器统一管理。

## 模型版本管理与灰度发布

模型迭代频繁，版本管理是平台的核心能力：

```
模型仓库 (Model Registry)
    |
    +-- text-encoder/
    |       +-- v1.0 (stable, 100% 流量)
    |       +-- v1.1 (canary, 5% 流量)
    |       +-- v1.2-dev (测试环境)
    |
    +-- image-classifier/
            +-- v2.0 (stable, 95% 流量)
            +-- v2.1 (灰度, 5% 流量)
```

**灰度发布策略**：

1. **流量百分比**：新版本接收 5% 流量，监控关键指标（延迟、准确率、错误率）
2. **用户分组**：内测用户先体验新版本，收集反馈
3. **地域灰度**：先在低峰区域上线，再逐步扩大
4. **自动回滚**：当新版本的错误率或延迟超过阈值，自动切回旧版本

**A/B 测试框架**：推理平台需要支持同时运行多个模型版本，并对结果进行对比分析。关键是保证分流的一致性（同一用户始终路由到同一版本）。

## 推理优化技术

在不显著降低模型质量的前提下，有多种优化手段可以提升推理效率：

### 量化（Quantization）

将模型权重从 FP32 降低到 FP16/INT8/INT4，减少显存占用和计算量：

| 精度 | 模型大小 | 推理速度 | 精度损失 |
|------|---------|---------|---------|
| FP32 | 100%   | 基准    | 无      |
| FP16 | 50%    | 1.5-2x | 极小    |
| INT8 | 25%    | 2-3x   | 小      |
| INT4 | 12.5%  | 3-4x   | 中等    |

**工程实践**：大多数场景 INT8 量化是最优选择，精度损失可接受，速度提升明显。INT4 需要配合 GPTQ/AWQ 等高级量化方法。

### 蒸馏（Distillation）

用大模型（教师）的输出训练小模型（学生），在保持大部分能力的同时大幅降低推理成本。

### 剪枝（Pruning）

移除模型中不重要的权重或层，减少计算量。结构化剪枝（移除整个注意力头或层）对硬件更友好。

## 批处理策略（Batching）

批处理是提升 GPU 利用率的关键技术：

```
请求到达时间：
  t0: 请求 A
  t1: 请求 B
  t2: 请求 C
  t3: 等待超时...

静态批处理 (Static Batching)：
  +---+---+---+---+
  | A | B | C |   |  <- 凑满一批或超时后统一处理
  +---+---+---+---+

连续批处理 (Continuous Batching)：
  批次 1: [A, B, C]    <- 立即处理
  批次 2: [D, E]       <- A 完成后立即补入新请求
  批次 3: [F, G, H]    <- B、C 完成后补入
```

**连续批处理**（也叫 Iteration-level Batching）是 LLM 推理的关键优化。它不需要等整个批次完成，某个请求生成完毕后立即让位给新请求，避免 GPU 空闲。

**动态批处理参数**：
- `max_batch_size`：单批最大请求数，受 GPU 显存限制
- `max_wait_ms`：最大等待时间，超过后即使未满也立即处理
- `max_sequence_length`：最大输入长度，防止单个请求占用过多资源

## 自动扩缩容

推理平台的流量通常有明显的波峰波谷，自动扩缩容是控制成本的关键：

**扩缩容指标**：

1. **GPU 利用率**：超过 80% 触发扩容，低于 30% 触发缩容
2. **请求队列深度**：队列积压超过阈值时扩容
3. **P99 延迟**：延迟超过 SLA 时扩容

**扩容策略**：

```
                    指标监控
                       |
                       v
                +------------------+
                |   扩缩容决策器   |
                +------------------+
                  |       |       |
                  v       v       v
             快速扩容  预测扩容  定时扩容
             (队列积压) (流量预测) (已知高峰)
                  |       |       |
                  v       v       v
                +------------------+
                |   节点调度器     |
                |  K8s + GPU 调度  |
                +------------------+
```

**冷启动优化**：GPU 节点启动和模型加载可能需要 30-120 秒。优化手段包括：模型预加载到镜像、使用模型缓存池、预留最小节点数。

## 请求队列设计

请求队列是推理平台的缓冲层，需要处理多种复杂场景：

```
                  请求接入
                     |
                     v
            +-----------------+
            |   优先级路由    |
            +-----------------+
              |     |     |
              v     v     v
          +-----+ +---+ +---+
          | P0  | | P1| | P2|   <- 优先级队列
          |实时 | |普通| |批处|
          +-----+ +---+ +---+
              |     |     |
              v     v     v
            +-----------------+
            |   调度器        |
            +-----------------+
```

**队列设计要点**：

1. **优先级分级**：实时交互请求（P0）优先于普通请求（P1），批处理任务（P2）最后
2. **背压控制**：队列满时拒绝新请求，返回 429 状态码，避免系统过载
3. **超时处理**：请求在队列等待超过阈值后自动取消，通知客户端
4. **公平调度**：同一租户的请求不能独占队列，需要按租户权重分配

## 模型仓库

模型仓库管理模型的全生命周期：

```
模型仓库
    |
    +-- 存储层：S3/OSS 存储模型文件（权重、配置、tokenizer）
    +-- 元数据层：PostgreSQL 存储版本信息、训练参数、评估指标
    +-- 版本控制：Git LFS 或 DVC 管理大文件版本
    +-- 访问控制：RBAC 权限管理，审计日志
```

**模型格式标准化**：统一使用 ONNX、TensorRT、vLLM 等标准化格式，避免每个模型都需要定制化的加载逻辑。

## 常见误区

1. **GPU 利用率越高越好**：GPU 利用率接近 100% 意味着请求排队等待，延迟会急剧上升。在线服务的目标利用率通常是 60-80%，留出余量应对突发流量。

2. **所有模型都用同一套优化策略**：不同模型的瓶颈不同。Transformer 模型受 attention 计算限制，CNN 受内存带宽限制。需要针对模型特点选择优化策略。

3. **批处理越大越好**：增大 batch size 可以提升吞吐，但会增加单个请求的延迟。在线服务需要在吞吐和延迟之间找到平衡点。

4. **量化一定会降低精度**：现代量化技术（如 GPTQ、AWQ）在 INT4 精度下对大语言模型的质量影响很小。应该通过 A/B 测试验证，而不是一概而论。

5. **忽略模型加载时间**：模型从存储加载到 GPU 显存可能需要数十秒。扩缩容时需要考虑冷启动延迟，不能简单地按请求量线性扩展。

## 工程建议

1. **分层部署策略**：将模型按延迟要求分为在线（<100ms）、近线（<5s）、离线三个层级，分别使用独占 GPU、共享 GPU、CPU 推理。

2. **模型缓存池**：维护一个预加载的模型缓存池，新版本上线时先加载到缓存池，扩缩容时直接从缓存池拉取，避免重复加载。

3. **请求级别的资源配额**：按租户/项目设置 GPU 使用配额和请求优先级，防止单个租户耗尽共享资源。

4. **端到端可观测性**：追踪从请求接入到推理完成的全链路延迟，包括排队时间、模型加载时间、预处理时间、推理时间、后处理时间。

5. **成本归因模型**：建立从请求到 GPU 成本的归因链路，让业务方清楚每个 API 调用的真实成本，驱动资源使用优化。

## 小结

AI 推理平台的核心挑战在于高效管理稀缺的 GPU 资源。关键设计决策包括：按业务 SLA 分层调度（独占/共享/MIG）；通过模型仓库和灰度发布管理版本迭代；利用量化、蒸馏、剪枝优化推理效率；采用连续批处理提升 GPU 利用率；基于多维指标实现自动扩缩容。推理平台的设计需要在成本、延迟、吞吐三者之间找到最优平衡点。

## 练习

### 练习一：GPU 资源规划

你的推理平台需要同时运行 3 个模型：模型 A（7B 参数，FP16 需要 14GB 显存，QPS 需求 100）、模型 B（13B 参数，FP16 需要 26GB 显存，QPS 需求 50）、模型 C（1.5B 参数，FP16 需要 3GB 显存，QPS 需求 200）。单张 A100 80GB 的推理吞吐为：模型 A 50 QPS、模型 B 20 QPS、模型 C 150 QPS。请设计 GPU 分配方案。

### 练习二：批处理延迟分析

一个 LLM 推理服务使用连续批处理，单个请求的平均推理时间为 2 秒。当 batch size 为 1 时，GPU 利用率为 20%；batch size 为 8 时，GPU 利用率为 70%，单请求平均延迟增加到 2.5 秒；batch size 为 32 时，GPU 利用率为 90%，单请求平均延迟增加到 5 秒。如果 SLA 要求 P99 延迟 < 3 秒，应该如何配置 batch size？

---

## 参考答案

### 练习一

**思路**：根据 QPS 需求和单卡吞吐计算 GPU 数量。

**答案**：
- 模型 A：100 / 50 = 2 张；模型 B：50 / 20 = 3 张；模型 C：200 / 150 = 2 张；共 7 张
- 模型 C 显存需求小（3GB），可用 MPS 共享模式与其他小模型混部
- 预留 1 张作为故障冗余，最终方案：8 张 A100 80GB

**要点**：显存限制和吞吐限制都要考虑，取较大值；小模型适合共享模式；生产环境需要预留冗余。

### 练习二

**思路**：在 SLA 延迟约束下找到 GPU 利用率最高的 batch size。

**答案**：SLA 要求 P99 < 3 秒，batch size=8 时延迟 2.5 秒满足 SLA 且 GPU 利用率 70%，是最优配置。batch size=32 虽然利用率 90%，但延迟 5 秒超出 SLA。建议配置 batch size 范围为 4-12，动态调整。

**要点**：batch size 不是越大越好，需要在延迟和利用率之间找平衡；连续批处理可以动态调整。

| Batch Size | GPU 利用率 | 平均延迟 | P99 延迟估算 |
|-----------|-----------|---------|-------------|
| 1         | 20%       | 2.0s    | ~2.5s       |
| 8         | 70%       | 2.5s    | ~3.5s       |
| 32        | 90%       | 5.0s    | ~8.0s       |

P99 延迟通常比平均延迟高 30-50%（取决于请求分布）。

SLA 要求 P99 < 3 秒：
- Batch size 32：P99 约 8 秒，不满足
- Batch size 8：P99 约 3.5 秒，不满足
- Batch size 1：P99 约 2.5 秒，满足但利用率太低

**推荐方案**：使用动态 batch 策略：
- 设置 `max_batch_size = 8`，`max_wait_ms = 200`
- 当队列深度 < 4 时，使用较小的 batch（快速响应）
- 当队列深度 ≥ 4 时，使用 batch size 8（提升吞吐）
- 监控 P99 延迟，动态调整 max_batch_size

或者使用 batch size 2-4 作为折中，在延迟和利用率之间找到平衡点。

**要点**：
- P99 延迟比平均延迟更重要，SLA 通常约束的是 P99
- 动态批处理可以根据负载自动调整
- 监控数据驱动配置调整，而不是静态设置
