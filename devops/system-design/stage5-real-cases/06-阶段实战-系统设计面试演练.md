# 阶段实战：系统设计面试演练

## 场景引入

你坐在面试室里，面试官说：请设计一个类似 WhatsApp 的即时通讯系统。你有 45 分钟。

你打开白板笔，脑海中浮现出无数个技术名词：消息队列、WebSocket、分库分表、CDN、最终一致性...... 但该从哪里开始？先画架构图？先讨论数据模型？先估算规模？

系统设计面试是高级工程师面试中最具挑战性的环节。它不仅考察技术广度和深度，更考察你在模糊问题下的结构化思考能力、沟通能力和工程判断力。很多人技术能力很强，但在面试中无法在有限时间内有条理地展示出来。

本节课将提供一个可复用的面试框架，并通过两个完整的面试模拟案例，帮你掌握系统设计面试的节奏和技巧。

## 学习目标

- 掌握系统设计面试的标准框架（4 步法）
- 学会在有限时间内合理分配各步骤的时间
- 理解面试官的评分维度和期望
- 通过完整模拟案例（URL 短链服务、聊天系统）练习面试流程
- 掌握白板作图和沟通表达的技巧

## 第 1 步：需求澄清

需求澄清是面试中最容易被忽略但最重要的步骤。它展示了你的工程思维——优秀的工程师不会拿到需求就开始写代码。

**功能性需求**（问面试官）：
- 系统的核心功能是什么？哪些是 must-have，哪些是 nice-to-have？
- 用户规模是多少？日活/月活？
- 关键业务流程是什么？

**非功能性需求**（主动提出）：
- **可用性**：99.9% 还是 99.99%？
- **一致性**：强一致还是最终一致？
- **延迟**：P99 延迟要求是多少？
- **数据规模**：数据量级、增长速度、保留策略

**示例对话**：

```
你：在开始设计之前，我想确认几个关键问题。
    1. 这个短链服务的预期规模是多少？每天创建多少短链？
    2. 读写比例大概是多少？
    3. 短链需要支持自定义别名吗？
    4. 链接有过期时间吗？

面试官：假设每天创建 1 亿个短链，读写比 100:1，支持自定义别名，
        链接永不过期。

你：好的，那我再确认非功能性需求。我假设：
    - 高可用性，系统不能有单点故障
    - 读延迟 P99 < 100ms
    - 短链一经创建不可修改
    这些合理吗？

面试官：合理，继续。
```

## 第 2 步：高层设计

### 估算

估算环节展示工程直觉，不需要精确，数量级正确即可：

```
写 QPS = 1 亿 / 86400 ≈ 1160，读 QPS = 1160 × 100 ≈ 12 万
5 年存储 = 1 亿 × 365 × 5 × 500B ≈ 91TB
Base62 6 位 = 568 亿种组合，足够 5 年
```

### API 设计

```
POST /api/v1/urls  → 创建短链（long_url, custom_alias, expire_at）
GET /{short_code}  → 301 重定向到长链接
GET /api/v1/urls/{short_code}/stats → 点击统计
```

### 数据模型

urls 表：short_code（VARCHAR(7) PK）、long_url（TEXT）、user_id（BIGINT）、created_at、expire_at、click_count

## 第 3 步：深入设计

面试官会根据你的高层设计，选择一个方向深入。常见的深入方向包括：

- **数据分片**：如何将数据分散到多个节点？
- **缓存策略**：如何设计多级缓存？
- **一致性保证**：分布式环境下如何保证数据一致？
- **故障处理**：节点故障时如何保证服务可用？

**深入设计的表达模板**：

```
你：我想深入讨论一下缓存策略的设计。
    考虑到读 QPS 是 12 万，数据库直接扛不住，需要引入缓存。
    我的设计方案是两级缓存：

    客户端 → 本地缓存（LRU，容量 10 万条）
           → Redis 集群（容量 1000 万条，命中率 95%+）
           → 数据库（全量数据）

    缓存更新策略使用 Cache-Aside：
    读：先查缓存，未命中查库并回填缓存
    写：先更新数据库，再删除缓存

    为什么不选择 Write-Through？
    因为短链是一次写入、多次读取的场景，写操作频率低，
    Cache-Aside 更简单且性能足够。
```

## 第 4 步：扩展与总结

```
你：最后讨论一下系统的扩展性。
    当前设计可以支撑 12 万 QPS 的读取，但如果增长到 100 万 QPS：

    1. 数据库瓶颈：引入读写分离，主库写、从库读
    2. 缓存瓶颈：Redis 集群水平扩展，按 short_code 哈希分片
    3. 单点故障：所有组件都部署多副本，使用负载均衡

    监控指标：
    - P99 重定向延迟
    - 缓存命中率
    - 数据库连接池使用率
    - 短链创建成功率
```

## 常见面试题类型

系统设计面试题通常可以分为以下几类：

| 类型 | 代表题目 | 核心挑战 |
|------|---------|---------|
| 存储系统 | 设计 KV 存储、分布式文件系统 | 一致性、分片、复制 |
| 社交系统 | 设计 Twitter、Instagram | Feed 流、关系图、热点 |
| 通讯系统 | 设计 WhatsApp、Slack | 实时性、消息顺序、已读状态 |
| 基础设施 | 设计 URL 短链、限流器 | 高并发、分布式 ID 生成 |
| 数据系统 | 设计搜索引擎、推荐系统 | 索引、排序、召回 |
| 流媒体 | 设计 YouTube、Netflix | 编码、CDN、自适应码率 |

## 沟通技巧

**白板作图技巧**：

1. **从左到右、从上到下**：数据流方向与阅读方向一致
2. **先画大方框，再填细节**：不要一开始就画完整的架构图
3. **用不同颜色区分**：数据流、控制流、缓存层用不同颜色
4. **边画边讲**：不要沉默地画图，边画边解释设计意图

**沟通模板**：

```
"我打算这样设计...... 原因是...... 但这里有个 tradeoff......
 如果遇到...... 的情况，我会......"
```

**时间管理**：

- 需求澄清不要超过 5 分钟，问 3-5 个关键问题即可
- 高层设计是核心，要花最多时间（15 分钟）
- 深入设计展示技术深度（15 分钟）
- 扩展讨论展示工程视野（10 分钟）

## 评分标准

面试官从 5 个维度评估：问题探索能力（20%）、高层设计能力（30%）、深入设计能力（25%）、沟通表达能力（15%）、扩展思维（10%）。其中**高层设计**权重最高，**问题探索**最容易被忽略但影响最大。

## 常见误区

1. **拿到需求就开始设计**：不澄清需求就动手，很可能设计出一个不符合实际场景的方案。先花 5 分钟确认关键需求，比直接画架构图更有价值。

2. **追求完美方案**：系统设计没有唯一正确答案。面试官考察的是你的思考过程和 tradeoff 分析能力，而不是某个特定的技术方案。

3. **忽略估算环节**：估算不是可选步骤。不做估算就不知道系统需要多大的规模，也就无法做出合理的技术选型。

4. **在所有方向都深入**：时间有限，不可能在每个方向都深入。选择 1-2 个最能展示你技术深度的方向深入讨论。

5. **沉默设计**：面试是沟通能力的考察。不要沉默地画图 10 分钟，然后说"我设计完了"。要边画边讲，让面试官跟上你的思路。

## 工程建议

1. **准备一个模板框架**：在面试前熟练掌握 4 步法的流程，这样在面试中可以自然地按照框架推进，把精力集中在技术讨论上。

2. **积累常见组件的优缺点**：MySQL vs PostgreSQL、Redis vs Memcached、Kafka vs RabbitMQ。不需要背诵，但要能清楚地说明在什么场景下选择什么。

3. **练习白板作图**：在白板上画架构图需要练习。使用简单的方框和箭头，保持图面整洁。先画高层架构，再逐步细化。

4. **准备 tradeoff 表达**：每个设计决策都有 tradeoff。练习用"这样做的好处是......，代价是......"的句式表达。

5. **模拟真实面试**：找同伴进行模拟面试，练习在 45 分钟内完成完整的设计。录音回放，检查自己的时间分配和表达清晰度。

## 小结

系统设计面试的核心是展示结构化思考能力。通过 4 步法（需求澄清 → 高层设计 → 深入设计 → 扩展讨论），你可以在 45 分钟内有条理地完成一个完整的设计。关键技巧包括：主动澄清需求而非假设、先估算规模再做技术选型、选择 1-2 个方向深入而非面面俱到、边画边讲保持沟通。记住，面试官考察的是你的思考过程，不是最终答案。

## 参考答案

### 练习一

**思路**：按 4 步法逐步展开，重点展示估算能力和 tradeoff 分析。

**答案**：需求确认（每天 1 亿短链，读写比 100:1，P99 < 100ms）→ 估算（写 QPS 1160，读 QPS 11.6 万，5 年存储 91TB）→ API（POST /urls 创建、GET /{code} 重定向）→ 数据模型（urls 表：short_code PK、long_url、user_id、click_count）→ 架构（负载均衡→应用→Redis 缓存→DB）→ 深入方向：短链生成算法（Base62 自增 ID vs 哈希+冲突检测）→ 扩展：读写分离、Redis 集群、按 user_id 分库分表。

**要点**：估算环节展示工程直觉；算法选择展示 tradeoff 分析能力；缓存策略与读写比匹配。

### 练习二

**思路**：重点讨论消息顺序性、群聊分发、已读状态三个核心问题。

**答案**：

- **消息顺序性**：用 Snowflake ID 保证全局有序，不依赖物理时钟
- **群聊分发**：小群（< 100 人）用扩散写，大群（> 100 人）用扩散读，阈值 100-200 人
- **已读状态**：bitmap 压缩存储（500 人 = 63 bytes），异步同步不阻塞消息发送

**要点**：消息顺序性是核心问题；群聊分发策略需根据群规模选择；已读状态需要压缩存储。

### 练习三

**思路**：从 5 个维度分析候选人表现。

**答案**：

| 维度 | 评分 | 说明 |
|------|------|------|
| 问题探索 | 1/4 | 没有问任何澄清问题 |
| 高层设计 | 3/4 | 索引构建合理，但缺少查询链路 |
| 深入设计 | 2/4 | 索引构建花太多时间，排序讨论不足 |
| 沟通表达 | 2/4 | 被动回答，缺少主动同步思路 |
| 扩展思维 | 2/4 | 只提到缓存，未系统讨论扩展 |

综合评分 2.0/4.0。改进：至少问 3 个澄清问题；留时间讨论查询排序（TF-IDF/BM25）；讨论分片策略和冷热分离；边画边讲让面试官跟上思路。
