# 阶段实战：系统设计面试演练

## 45 分钟，从零开始

面试官说：请设计一个类似 WhatsApp 的即时通讯系统。你有 45 分钟。

你打开白板笔，脑海中浮现出无数技术名词：消息队列、WebSocket、分库分表、CDN...... 但该从哪里开始？

系统设计面试考察的不是你记住了多少技术名词，而是在模糊问题下的结构化思考能力和工程判断力。

## 4 步法框架

```
第 1 步：需求澄清（5 分钟）
  功能性需求 → 核心用例
  非功能性需求 → 规模、可用性、一致性、延迟
  约束条件 → 预算、团队、时间线

第 2 步：高层设计（15 分钟）
  估算 → QPS、存储、带宽
  API 设计 → 核心接口
  数据模型 → 表结构、存储选型
  系统架构 → 核心组件和数据流

第 3 步：深入设计（15 分钟）
  选择 1-2 个核心组件深入
  讨论设计取舍和替代方案
  处理边界情况和故障场景

第 4 步：扩展与总结（10 分钟）
  瓶颈分析 → 扩展瓶颈在哪里
  扩展方案 → 如何处理 10x/100x 规模
  监控运维 → 如何保证系统健康
```

## 第 1 步：需求澄清

需求澄清展示工程思维——优秀的工程师不会拿到需求就开始写代码。

```
你：在开始设计之前，我想确认几个关键问题。
   1. 短链服务的预期规模？每天创建多少短链？
   2. 读写比例大概是多少？
   3. 短链需要支持自定义别名吗？

面试官：每天 1 亿短链，读写比 100:1，支持自定义别名。

你：非功能需求方面，我假设：
   - 高可用，不能有单点故障
   - 读延迟 P99 < 100ms
   - 短链一经创建不可修改
```

主动提出非功能需求，比等面试官告诉你更有价值。

## 第 2 步：高层设计

估算展示工程直觉，不需要精确，数量级正确即可：

```
写 QPS = 1 亿 / 86400 ≈ 1160
读 QPS = 1160 × 100 ≈ 12 万
5 年存储 = 1 亿 × 365 × 5 × 500B ≈ 91TB
```

API 设计：
```
POST /api/v1/urls  → 创建短链
GET /{short_code}  → 302 重定向
GET /api/v1/urls/{short_code}/stats → 点击统计
```

## 第 3 步：深入设计

面试官会根据你的高层设计选择方向深入。常见方向：数据分片、缓存策略、一致性保证、故障处理。

表达模板：
```
"我想深入讨论缓存策略。
 考虑到读 QPS 12 万，数据库扛不住，需要引入缓存。
 设计方案是两级缓存：本地缓存 → Redis → 数据库。
 缓存更新策略用 Cache-Aside。
 为什么不选 Write-Through？
 因为短链是一次写入多次读取，Cache-Aside 更简单。"
```

## 第 4 步：扩展与总结

```
"如果读 QPS 增长到 100 万：
 1. 数据库瓶颈 → 读写分离
 2. 缓存瓶颈 → Redis 集群水平扩展
 3. 单点故障 → 所有组件多副本 + 负载均衡

 监控指标：P99 延迟、缓存命中率、数据库连接池使用率、短链创建成功率"
```

## 评分维度

```
问题探索能力    20%  ← 最容易被忽略但影响最大
高层设计能力    30%  ← 权重最高
深入设计能力    25%
沟通表达能力    15%
扩展思维        10%
```

## 沟通技巧

**白板作图**：从左到右、从上到下。先画大方框再填细节。用不同颜色区分数据流和控制流。边画边讲。

**时间管理**：需求澄清 5 分钟，高层设计 15 分钟（核心），深入设计 15 分钟（展示深度），扩展 10 分钟（展示视野）。

## 常见错误

1. **拿到需求就开始设计**：花 5 分钟确认需求比花 30 分钟设计错误系统有价值
2. **追求完美方案**：面试官考察思考过程和 tradeoff 分析，不是特定方案
3. **忽略估算**：不做估算就不知道系统规模，无法合理选型
4. **沉默设计**：不要沉默画图 10 分钟然后说"设计完了"。边画边讲

## 练习

### 练习一：短链服务面试模拟

45 分钟内按 4 步法完成短链服务设计。DAU 1 亿，读写比 100:1，支持自定义别名，P99 < 100ms。写出设计思路。

### 练习二：聊天系统面试模拟

45 分钟完成即时通讯系统设计。DAU 5000 万，群聊上限 500 人，消息持久化，已读回执。重点讨论消息顺序性、群聊分发策略、已读状态同步。

### 练习三：评估一个候选人

候选人拿到"设计搜索引擎"后：没问任何澄清问题，直接画倒排索引架构图。花 20 分钟画索引构建流程。面试官问"查询结果排序"只说了"用 PageRank"。最后 5 分钟提到缓存。从 5 个维度评分。

## 参考答案

### 练习一

需求确认 → 估算（写 1160 QPS，读 12 万，存储 91TB）→ API（POST /urls 创建、GET /{code} 重定向）→ 数据模型（urls 表）→ 架构（负载均衡→应用→Redis→DB）→ 深入：短码生成算法（Base62 自增 vs 哈希+冲突检测）→ 扩展：读写分离、Redis 集群、按 user_id 分库分表。

### 练习二

消息顺序性：Snowflake ID 保证全局有序。群聊分发：小群（< 100 人）扩散写，大群（> 100 人）扩散读。已读状态：bitmap 压缩存储（500 人 = 63 bytes），异步同步。

### 练习三

| 维度 | 评分 | 说明 |
|------|------|------|
| 问题探索 | 1/4 | 没问任何澄清问题 |
| 高层设计 | 3/4 | 索引构建合理，但缺少查询链路 |
| 深入设计 | 2/4 | 索引构建花太多时间，排序讨论不足 |
| 沟通表达 | 2/4 | 被动回答，缺少主动同步思路 |
| 扩展思维 | 2/4 | 只提到缓存 |

综合 2.0/4.0。改进：至少问 3 个澄清问题；留时间讨论查询排序；讨论分片策略和冷热分离。
