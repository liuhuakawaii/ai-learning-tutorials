# 设计即时通讯系统

## 场景引入

你的团队决定开发一款企业级即时通讯工具，类似 Slack 或飞书。核心功能包括单聊、群聊、已读回执、离线消息同步。产品经理告诉你："消息必须可靠送达，不能丢；群聊要支持万人规模；用户换设备登录后要能看到完整的历史消息。"

即时通讯是系统设计中最复杂的场景之一，因为它同时涉及实时性、可靠性、有序性三个维度的挑战。

## 学习目标

- 理解 IM 系统的核心需求和架构分层
- 掌握 WebSocket 长连接管理和消息路由机制
- 理解写扩散与读扩散的取舍
- 掌握消息 ID 设计方案（保证有序性）
- 了解消息可靠性保障机制（ACK/重试/幂等）

## 需求分析

### 功能性需求

```
核心功能：
1. 单聊（One-on-One Chat）  — 两个用户之间的实时消息
2. 群聊（Group Chat）       — 多人实时消息，支持大规模群组
3. 已读回执（Read Receipt）  — 消息是否被对方/群成员阅读
4. 离线消息（Offline Msg）   — 用户离线期间的消息在上线后同步
5. 历史消息（History）       — 支持向上翻页加载历史消息
6. 在线状态（Presence）      — 显示用户是否在线

非功能性需求：
- 实时性：消息端到端延迟 < 200ms
- 可靠性：消息不丢失、不重复
- 有序性：同一会话内消息严格有序
- 可扩展：支持百万级并发连接
```

### 容量估算

```
假设：
- 总用户数：5000 万
- 日活用户：1000 万
- 每用户每天发 50 条消息 → 日消息量 5 亿条
- 平均每条消息 500 字节 → 日存储增量 250GB
- 峰值在线连接数：500 万
```

## WebSocket 长连接管理

IM 系统的核心是 WebSocket 长连接。每个在线用户与服务器保持一个持久连接，消息通过这个连接实时推送。

### 连接管理流程

```
客户端                          Gateway 集群
  │                                 │
  │── 建立 WebSocket 连接 ────────→ │
  │                                 │── 验证 Token
  │                                 │── 注册：user_id → connection_id
  │                                 │── 写入 Redis：ONLINE:user_id = gateway_3
  │←── 连接成功 ────────────────── │
  │                                 │
  │── 心跳 Ping（每 30s）────────→ │
  │←── 心跳 Pong ──────────────── │
  │                                 │
  │── 发送消息 ──────────────────→ │── 路由到目标用户所在的 Gateway
  │                                 │
  │←── 推送新消息 ─────────────── │
```

### 连接路由

当用户 A 给用户 B 发消息时，Gateway 需要知道 B 连接在哪台服务器上。

```
方案一：集中式路由（Redis）
  Redis 记录：user_id → gateway_server_id
  查找开销：每次发消息都要查 Redis

方案二：一致性哈希
  hash(user_id) → gateway_server_id
  无需查询，但扩缩容时需要迁移连接

推荐方案：一致性哈希 + Redis 兜底
  正常情况用哈希快速定位
  服务器变更时用 Redis 记录迁移状态
```

## 消息存储：写扩散 vs 读扩散

### 写扩散（Fan-out on Write）

用户 A 给 B 发消息时，系统将消息分别写入 A 和 B 的收件箱。

```
A 发消息给 B：
  1. 写入消息表：messages(msg_id, sender=A, content=...)
  2. 写入 A 的发件箱：inbox(A) += msg_id
  3. 写入 B 的收件箱：inbox(B) += msg_id

B 查看消息：
  SELECT * FROM inbox WHERE user_id = B ORDER BY msg_id DESC
```

**优点**：读取简单，直接查自己的收件箱。
**缺点**：群聊写入放大严重——1000 人的群每条消息写 1000 次。

### 读扩散（Fan-out on Read）

消息只写一份，用户查看消息时实时查询所有相关会话。

```
A 发消息给 B：
  1. 写入消息表：messages(msg_id, conversation_id, sender=A, content=...)

B 查看消息：
  SELECT * FROM messages
  WHERE conversation_id IN (B 参与的所有会话)
  ORDER BY msg_id DESC
```

**优点**：写入零放大。
**缺点**：读取开销大，需要聚合多个会话的消息。

### 工程实践

```
场景              推荐方案
────────────────────────────
单聊              写扩散（2 倍写入，可接受）
小群（< 200 人）   写扩散
大群（>= 200 人）  读扩散
```

## 消息 ID 设计

消息 ID 必须满足两个要求：**全局唯一**和**可排序**（反映发送顺序）。常见的方案：

### 雪花算法（Snowflake）

```
消息 ID 结构（64 位）：
┌─────────┬──────────┬──────────┐
│ 时间戳   │ 机器 ID  │ 序列号   │
│ 41 bit  │ 10 bit   │ 12 bit   │
└─────────┴──────────┴──────────┘

- 时间戳：毫秒级，可用约 69 年
- 机器 ID：支持 1024 台机器
- 序列号：每毫秒 4096 个 ID
```

雪花算法生成的 ID 天然按时间有序，可以直接用作消息排序。但需要注意**时钟回拨问题**——如果服务器时钟被回调，可能生成重复 ID。

### 数据库自增 ID 的局限

```
问题：自增 ID 在分布式环境下不唯一
方案：不同分片用不同步长（分片 1: 1,3,5... 分片 2: 2,4,6...）
缺点：扩容困难，ID 不连续
```

推荐使用雪花算法或类似方案，不依赖数据库自增。

## 消息可靠性：ACK/重试/幂等

### 三层 ACK 机制

```
A 发消息 → Gateway → 消息服务 → B

ACK 1：Gateway 收到消息 → 返回给 A "服务端已收到"
ACK 2：消息服务持久化成功 → 通知 Gateway
ACK 3：B 的客户端收到消息 → 返回 "客户端已收到"

如果某层 ACK 超时：
  ACK 1 超时 → A 重发（客户端重试）
  ACK 3 超时 → Gateway 重推（服务端重试，最多 N 次）
```

### 幂等性保障

由于重试机制的存在，消息可能被投递多次。客户端和服务端都需要做幂等处理。

```
幂等方案：
  每条消息携带 client_msg_id（客户端生成的唯一 ID）
  服务端收到消息后：
    if exists(client_msg_id):
        return 已存在的消息  # 不重复处理
    else:
        处理并存储消息
```

## 群聊扇出

群聊的核心挑战是消息扇出。假设一个群有 1000 人，A 发一条消息，需要让其他 999 人都看到。

```
群消息投递流程：

1. A 发消息到群
2. 消息服务写入群消息表
3. 查询群成员列表（1000 人）
4. 判断在线/离线状态
5. 在线用户 → 通过 Gateway 实时推送
6. 离线用户 → 写入离线消息队列，上线后同步

优化：群成员列表缓存在 Redis，避免每次查数据库
```

大群（如万人群）需要特殊处理：不为每个成员写收件箱（读扩散），而是在用户打开群聊时实时拉取。

## 在线状态管理

在线状态通过心跳机制维护：客户端每 30s 发送 Ping，服务端更新 Redis `ONLINE:user_id = timestamp + 60s`。判断在线时检查 Redis 中的时间戳是否大于当前时间。在线状态是高频读取数据，必须缓存在 Redis 中，群聊场景可批量查询成员状态。

## 历史消息同步

用户换设备登录或重新上线时，需要同步离线期间的消息。

```
同步方案（基于序列号）：

1. 客户端记录最后收到的消息序列号 last_seq
2. 上线后请求：GET /messages/sync?last_seq=12345
3. 服务端返回 last_seq 之后的所有消息
4. 客户端逐条确认收到

数据量控制：
  - 如果离线消息过多（如超过 7 天），只同步最近的消息
  - 更早的消息通过历史消息接口翻页加载
```

## 常见误区

1. **所有群都用写扩散**：万人群每条消息写一万次，存储和写入成本不可接受。大群必须用读扩散。
2. **忽略消息有序性**：如果没有全局有序的 ID，用户看到的消息顺序可能与发送顺序不一致，体验很差。
3. **只推不确认**：不实现 ACK 机制就无法保证消息可靠性。网络抖动时消息会静默丢失。
4. **在线状态查数据库**：在线状态是高频读写场景，查数据库会把数据库打垮。必须用 Redis。
5. **过度设计初期架构**：早期用户量小，单机 WebSocket + 单库就能支撑。分布式架构是规模增长后的演进方案。

## 工程建议

1. **协议用 Protobuf**：JSON 解析开销大，Protobuf 序列化/反序列化快 5-10 倍，带宽占用小 3-5 倍。对 IM 这种高频通信场景效果显著。
2. **消息先写 Kafka 再投递**：消息写入 Kafka 后立即返回 ACK，异步投递给接收方。这样即使投递服务故障，消息也不会丢失。
3. **分库分表按会话 ID**：消息表按会话 ID 分片，同一会话的消息在同一个分片上，查询效率高。
4. **已读回执批量处理**：不要每条消息的已读状态都实时同步。客户端批量上报已读序列号，服务端批量更新。
5. **连接数监控和预警**：WebSocket 连接数是系统容量的核心指标。设置阈值预警，及时扩容 Gateway 节点。

## 小结

IM 系统的核心挑战在于**实时性**（WebSocket 长连接）、**可靠性**（三层 ACK + 幂等）、**有序性**（雪花算法）三个维度的平衡。写扩散适合单聊和小群，读扩散适合大群。消息 ID 用雪花算法保证全局唯一且有序。在线状态必须缓存在 Redis 中，不能查数据库。

关键架构决策：接入层用 WebSocket 长连接 + 一致性哈希路由；存储层消息用 HBase/Cassandra（写密集型），元数据用 MySQL；缓存层用 Redis 存在线状态和未读计数。

## 参考答案

### 练习一

**思路**：利用序列号机制，客户端记录最后收到的序列号，上线后拉取增量。

**答案**：消息写入 HBase 并分配全局递增序列号 seq。B 离线期间，投递失败的消息写入离线队列（Kafka）。B 重新上线后发送同步请求（last_seq=56700），服务端返回 seq > 56700 的所有消息。客户端用 msg_id 去重，确认后更新本地 last_seq。

**要点**：序列号是同步的核心，必须持久化；客户端需要本地持久化 last_seq，不能只存在内存中。

### 练习二

**思路**：用"最后已读消息"方案代替"每条消息的已读集合"。

**答案**：Redis 存储 `last_read:{group_id}:{user_id} = msg_id`，记录每个用户在每个群的最后已读消息。查询"A 发的消息谁已读"时，比较成员的 last_read 与消息的 msg_id。客户端每 5 秒批量上报一次 last_read 更新，而非每条消息都上报。500 人群只需存储 500 条记录。

**要点**：用"最后已读消息"比"每条消息的已读集合"更节省存储；大群的已读回执可以做降级处理。

### 练习三

**思路**：客户端主动重连 + 消息暂存 + 序列号同步。

**答案**：旧 Gateway 标记为 draining，给所有客户端发送 "reconnect" 指令并携带新节点地址。迁移期间发给旧 Gateway 的消息写入 Kafka。客户端重连后发送同步请求（last_seq），服务端返回断连期间的消息。30 秒内未重连的客户端标记为离线。

**要点**：不能直接杀进程，必须优雅迁移；消息暂存（Kafka）是迁移期间不丢消息的关键；客户端必须有自动重连机制。
