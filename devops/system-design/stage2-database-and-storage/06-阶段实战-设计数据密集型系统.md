# 阶段实战：设计数据密集型系统

## 场景

在线教育平台，日活 500 万，每天产生大量行为数据：课程浏览、视频观看进度、练习答题、弹幕互动、购买订单。产品经理要求：

1. **实时看板**：运营看到当前在线人数、课程热度、实时销售额，延迟 < 30 秒
2. **离线报表**：每天生成用户增长、课程完成率、转化漏斗
3. **用户画像**：基于行为数据构建标签体系，支持推荐和营销

这需要一条完整的数据管道：采集 → 传输 → 处理 → 存储 → 服务。

## 数据源和处理需求

```
数据源：
  应用服务器日志（Nginx access log）
  业务数据库（MySQL：用户、订单、课程）
  埋点数据（前端 SDK 上报的用户行为）
  第三方数据（支付回调、短信状态）

处理需求：
  实时处理：在线人数、实时销售额（延迟 < 30s）
  准实时处理：课程热度排行（延迟 < 5min）
  批量处理：日报、用户画像（T+1）
```

## 第一个决策：ETL 还是 ELT

```
ETL（Extract → Transform → Load）：
  数据进入仓库前已经处理好
  适合：传统数仓、数据量小、转换逻辑简单

ELT（Extract → Load → Transform）：
  原始数据先存下来，按需转换
  适合：大数据场景、转换逻辑多变、需要保留原始数据
```

本案例选 ELT。原因：数据源多、转换逻辑会随业务变化，保留原始数据可以反复分析。没有元数据管理的数据湖会变成"数据沼泽"——必须配合 Iceberg/Delta Lake 等表格式。

## 第二个决策：批处理、流处理还是两者都要

```
                批处理                    流处理
──────────────────────────────────────────────────
数据粒度        一天/一小时的数据          单条/微批
处理延迟        分钟到小时级              秒级甚至毫秒级
计算框架        Spark / Hive             Flink / Kafka Streams
适用场景        日报、月报、画像          实时监控、实时推荐
复杂度          低                       高
```

本案例两者都需要。采用 Kappa 架构（比 Lambda 更简洁）：用一套流处理系统同时处理实时和批量需求。需要重算时，重放 Kafka 中的历史数据即可。

## 实时数据管道设计

以"实时课程热度排行"为例：

```
数据源                    传输层          处理层              存储层
┌──────────┐
│ 应用服务  │──┐
├──────────┤  │    ┌─────────┐    ┌──────────┐    ┌──────────────┐
│ 前端埋点  │──┼───→│  Kafka   │───→│  Flink   │───→│ Redis(实时)  │
├──────────┤  │    │         │    │          │    ├──────────────┤
│ 业务库   │──┤    │user-event│    │1.事件关联│    │ClickHouse   │
│(Debezium)│  │    │db-changes│    │2.窗口聚合│    │(准实时分析)  │
└──────────┘  │    │page-views│    │3.排名计算│    ├──────────────┤
              │    └─────────┘    └──────────┘    │S3/数据湖     │

```

## 数据质量监控

数据管道最容易出问题的不是架构，而是数据质量：

```
维度        含义              示例
───────────────────────────────────
完整性      数据是否缺失       用户ID为空
准确性      数据是否正确       年龄=999
一致性      多源数据是否一致   订单金额不匹配
及时性      数据是否按时到达   日报延迟3小时
唯一性      是否有重复数据     同一事件重复
```

数据质量问题应该在源头解决。如果采集端的数据就是脏的，下游再怎么清洗也补不回来。

## 技术选型总结

```
需求                技术选型              理由
──────────────────────────────────────────────────
数据采集            Debezium + Fluentd   CDC 保证一致性，Fluentd 处理日志
数据传输            Kafka                高吞吐、持久化、支持回放
实时处理            Flink                低延迟、状态管理、Exactly-once
批处理              Spark                生态成熟、与数据湖集成好
实时缓存            Redis                毫秒级响应
分析查询            ClickHouse           列式存储，聚合查询极快
数据湖              S3 + Iceberg         低成本，支持 Schema 演进
BI 报表             Superset             开源、功能丰富
```

## 练习

### 练习一：短视频平台数据系统设计

日均 10 亿条播放事件，需要实时播放量（延迟 < 10 秒）、日活报表、视频推荐特征计算。给出技术选型。

### 练习二：数据清洗方案

埋点数据存在问题：部分事件缺失 user_id、同一事件重复上报、时间戳乱序。设计清洗方案。

### 练习三：实现数据质量检查函数

编写一个 TypeScript 函数 `checkDataQuality(records, rules)`，检查数据完整性（必填字段是否为空）和唯一性（指定字段是否重复）。返回检查结果。

---

## 参考答案

### 练习一

10 亿条/天 ≈ 11.5 万条/秒。Kafka 多分区 + Flink 多并行度可以处理。实时播放量用 Redis INCR 最简单。日报和画像用 Spark。分析存储用 ClickHouse。数据湖用 S3 + Iceberg。

### 练习二

1. **缺失 user_id**：有 session_id/device_id 则关联补全，否则标记匿名。在采集端加强校验。
2. **重复上报**：每条事件生成唯一 event_id，Flink 基于状态去重，ClickHouse 用 ReplacingMergeTree。
3. **时间戳乱序**：Flink Watermark 机制处理乱序，允许 5 秒内乱序，超出范围的打到侧输出流。

### 练习三

```typescript
interface QualityRule {
  requiredFields?: string[]
  uniqueFields?: string[]
}

interface QualityResult {
  totalRecords: number
  missingFieldCounts: Record<string, number>
  duplicateCounts: Record<string, number>
  isValid: boolean
}

function checkDataQuality(records: Record<string, any>[], rules: QualityRule): QualityResult {
  const missingFieldCounts: Record<string, number> = {}
  const duplicateCounts: Record<string, number> = {}

  for (const field of rules.requiredFields ?? []) {
    missingFieldCounts[field] = records.filter(r => r[field] == null || r[field] === '').length
  }

  for (const field of rules.uniqueFields ?? []) {
    const values = records.map(r => r[field]).filter(v => v != null)
    duplicateCounts[field] = values.length - new Set(values).size
  }

  const isValid = Object.values(missingFieldCounts).every(c => c === 0)
    && Object.values(duplicateCounts).every(c => c === 0)

  return { totalRecords: records.length, missingFieldCounts, duplicateCounts, isValid }
}

describe('checkDataQuality', () => {
  test('正常数据', () => {
    const records = [{ id: '1', name: 'A' }, { id: '2', name: 'B' }]
    const result = checkDataQuality(records, { requiredFields: ['id', 'name'], uniqueFields: ['id'] })
    expect(result.isValid).toBe(true)
  })
  test('缺失字段', () => {
    const records = [{ id: '1', name: '' }, { id: '2' }]
    const result = checkDataQuality(records, { requiredFields: ['id', 'name'] })
    expect(result.missingFieldCounts.name).toBe(2)
    expect(result.isValid).toBe(false)
  })
  test('重复 ID', () => {
    const records = [{ id: '1' }, { id: '1' }, { id: '2' }]
    const result = checkDataQuality(records, { uniqueFields: ['id'] })
    expect(result.duplicateCounts.id).toBe(1)
  })
})
```
