# 阶段实战：设计数据密集型系统

## 场景引入

你所在的公司是一家在线教育平台，日活用户 500 万，每天产生大量的用户行为数据：课程浏览记录、视频观看进度、练习答题数据、弹幕互动、购买订单。产品经理要求你设计一个数据分析系统，需要满足以下需求：

1. **实时看板**：运营人员可以看到当前在线人数、课程热度排行、实时销售额，延迟不超过 30 秒
2. **离线报表**：每天生成用户增长、课程完成率、转化漏斗等分析报表
3. **用户画像**：基于用户行为数据构建标签体系，支持精准推荐和营销

这是一个典型的数据密集型系统。你需要设计一条完整的数据管道，从数据采集、传输、存储到分析，每一步都要做出合理的技术选型和架构决策。

## 学习目标

- 理解 ETL 和 ELT 的区别及适用场景
- 掌握批处理和流处理的选型依据
- 理解数据湖和数据仓库的定位差异
- 能够设计实时数据管道（Kafka + Flink）
- 了解数据质量监控的核心方法

## 数据管道需求分析

在动手设计之前，先把需求拆解为具体的数据流：

```
数据源：
  ├── 应用服务器日志（Nginx access log）
  ├── 业务数据库（MySQL：用户、订单、课程）
  ├── 埋点数据（前端 SDK 上报的用户行为）
  └── 第三方数据（支付回调、短信状态）

数据处理：
  ├── 实时处理：在线人数、实时销售额（延迟 < 30s）
  ├── 准实时处理：课程热度排行（延迟 < 5min）
  └── 批量处理：日报、用户画像（T+1）

数据输出：
  ├── 实时看板（Grafana / 自建大屏）
  ├── 分析报表（BI 工具：Metabase / Superset）
  └── 推荐系统（用户画像 → 特征服务）
```

## ETL vs ELT

两种数据处理范式的根本区别在于"转换"发生在哪里。

```
ETL（Extract → Transform → Load）：
  数据源 → 提取 → 转换（清洗/聚合） → 加载到数据仓库
  特点：数据进入仓库前已经处理好，仓库中只存干净数据
  适合：传统数据仓库、数据量较小、转换逻辑简单

ELT（Extract → Load → Transform）：
  数据源 → 提取 → 加载到数据湖/仓库 → 在仓库中转换
  特点：原始数据先存下来，按需转换
  适合：大数据场景、转换逻辑多变、需要保留原始数据
```

```
┌─────────────────────────────────────────────────────────┐
│                   ETL 流程                               │
│                                                         │
│  数据源 → [Extract] → 原始数据 → [Transform] → 清洗数据  │
│                                                    ↓    │
│                                               [Load]    │
│                                                    ↓    │
│                                              数据仓库    │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│                   ELT 流程                               │
│                                                         │
│  数据源 → [Extract] → 原始数据 → [Load] → 数据湖        │
│                                               ↓         │
│                                          [Transform]    │
│                                               ↓         │
│                                         分析用数据集     │
└─────────────────────────────────────────────────────────┘
```

本案例采用 ELT 模式：原始数据先进入数据湖（S3/MinIO），然后在数据仓库中按需转换。原因是数据源多、转换逻辑会随业务需求变化，保留原始数据可以反复分析。

## 批处理 vs 流处理

```
                批处理                    流处理
───────────────────────────────────────────────────
数据粒度        一天/一小时的数据          单条/微批
处理延迟        分钟到小时级              秒级甚至毫秒级
计算框架        Spark / Hive             Flink / Kafka Streams
适用场景        日报、月报、画像          实时监控、实时推荐
容错机制        重新计算整个任务           Checkpoint + 状态恢复
复杂度          低                       高
```

实际项目中，批处理和流处理通常共存（Lambda 架构或 Kappa 架构）：

```
┌─────────────────────────────────────────────────────────┐
│              Lambda 架构                                 │
│                                                         │
│  数据源 ──┬──→ 批处理层（Spark）──→ 批处理视图           │
│           │                          ↓                  │
│           │                     服务层（合并）→ 查询     │
│           │                          ↑                  │
│           └──→ 实时层（Flink）──→ 实时视图               │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│              Kappa 架构（推荐）                           │
│                                                         │
│  数据源 ──→ Kafka ──→ 流处理（Flink）──→ 输出            │
│                │                                        │
│                └──→ 批量回放（需要重算时重放 Kafka 数据） │
└─────────────────────────────────────────────────────────┘
```

Kappa 架构更简洁：用一套流处理系统同时处理实时和批量需求。需要重算时，重放 Kafka 中的历史数据即可。

## 数据湖 vs 数据仓库

```
┌─────────────────────────────────────────────────────────┐
│                  数据湖 vs 数据仓库                        │
├──────────────┬────────────────┬─────────────────────────┤
│              │ 数据湖          │ 数据仓库                  │
├──────────────┼────────────────┼─────────────────────────┤
│ 存储内容      │ 原始数据(所有格式) │ 结构化数据(清洗后)       │
│ Schema       │ 读时模式(Schema-on-Read) │ 写时模式(Schema-on-Write) │
│ 用户          │ 数据工程师/科学家 │ 业务分析师               │
│ 存储成本      │ 低(S3/对象存储)  │ 高(高性能存储)           │
│ 查询性能      │ 较慢            │ 快(预计算/索引)           │
│ 典型技术      │ S3 + Spark      │ ClickHouse / Snowflake  │
└──────────────┴────────────────┴─────────────────────────┘
```

现代趋势是"湖仓一体"：用数据湖的低成本存储 + 数据仓库的查询性能。典型方案是 Delta Lake、Apache Iceberg 等表格式。

## 数据质量监控

数据管道中最容易出问题的不是架构，而是数据质量。脏数据进入分析系统后，会导致错误的业务决策。

```
数据质量维度：
┌─────────────────────────────────────────────────┐
│ 维度          │ 含义              │ 示例          │
├─────────────────────────────────────────────────┤
│ 完整性        │ 数据是否缺失       │ 用户ID为空    │
│ 准确性        │ 数据是否正确       │ 年龄=999     │
│ 一致性        │ 多源数据是否一致   │ 订单金额不匹配│
│ 及时性        │ 数据是否按时到达   │ 日报延迟3小时 │
│ 唯一性        │ 是否有重复数据     │ 同一事件重复  │
└─────────────────────────────────────────────────┘
```

监控方案：

```python
# 数据质量检查示例
class DataQualityChecker:
    def check_completeness(self, df, required_columns):
        """检查必填字段是否为空"""
        for col in required_columns:
            null_rate = df[col].isnull().mean()
            if null_rate > 0.01:  # 空值率超过 1%
                alert(f"字段 {col} 空值率: {null_rate:.2%}")

    def check_timeliness(self, expected_time, actual_time):
        """检查数据是否按时到达"""
        delay = (actual_time - expected_time).total_seconds()
        if delay > 300:  # 延迟超过 5 分钟
            alert(f"数据延迟: {delay} 秒")

    def check_volume(self, today_count, yesterday_count):
        """检查数据量是否异常"""
        change_rate = abs(today_count - yesterday_count) / yesterday_count
        if change_rate > 0.5:  # 变化超过 50%
            alert(f"数据量异常变化: {change_rate:.2%}")
```

## 常见误区

1. **"上 Kafka 就是大数据"**：Kafka 只是数据传输层，没有处理层和存储层的配合，它只是一个消息队列。大数据系统需要完整的数据管道。

2. **"实时一定比批处理好"**：实时处理的开发和运维成本远高于批处理。如果业务可以接受 T+1 的延迟，批处理是更简单可靠的选择。

3. **"数据湖可以替代数据仓库"**：数据湖存储原始数据，查询性能差；数据仓库存储结构化数据，查询快。两者互补，不是替代关系。

4. **"数据质量是下游的事"**：数据质量问题应该在源头解决。如果采集端的数据就是脏的，下游再怎么清洗也补不回来。

5. **"架构设计完就可以不管了"**：数据系统需要持续运维。数据量增长、业务需求变化、组件版本升级都会影响系统表现，需要定期审视和优化。

6. **"数据湖就是把数据扔进 S3"**：没有元数据管理和 Schema 管理的数据湖会变成"数据沼泽"。必须配合 Iceberg/Delta Lake 等表格式和 Glue/Hive Metastore 等元数据服务。

7. **"流处理比批处理实时性更高所以更好"**：流处理的开发复杂度远高于批处理，状态管理、Exactly-Once 语义、窗口计算等问题都需要额外处理。如果业务不需要秒级延迟，批处理的 ROI 更高。

8. **"数据管道不需要版本管理"**：数据 Schema 变更、ETL 逻辑变更、调度配置变更都需要版本管理。没有版本管理的数据管道，出了问题无法回滚。

9. **"监控只关注数据处理速度"**：除了延迟和吞吐量，还要监控数据质量指标（空值率、重复率、数据量波动）。数据质量下降可能比处理延迟更危险。

10. **"数据安全可以最后再加"**：数据安全（脱敏、加密、访问控制）必须在架构设计阶段就考虑。后期改造的成本是前期设计的 10 倍以上。

## 工程建议

1. **从最简单的架构开始**：不要一开始就设计 Lambda 架构。先用批处理满足基本需求，等实时需求明确后再引入流处理。

2. **数据管道要可观测**：每个环节的延迟、吞吐量、错误率都要监控。数据延迟和数据丢失是最常见的问题，没有监控就无法发现。

3. **Schema 管理要从第一天开始**：数据格式的变化会导致下游处理失败。使用 Schema Registry 管理数据格式，任何变更都要走兼容性检查。

4. **保留原始数据**：即使当前不需要，也要把原始数据存下来（数据湖）。未来的分析需求可能需要用到今天认为不重要的字段。

5. **数据安全贯穿全链路**：用户隐私数据（手机号、身份证）在采集端就要脱敏。数据传输加密，存储加密，访问控制到字段级别。

6. **数据管道要做幂等设计**：管道故障恢复后可能重复处理同一批数据。每个处理环节都要保证幂等性，避免数据重复或指标虚高。

7. **建立数据血缘关系**：记录每个数据字段从哪里来、经过什么处理、被谁使用。出问题时可以快速定位影响范围，变更时可以评估下游影响。

8. **设置数据 SLA**：明确每个数据产品的交付时间和质量要求。如"实时看板延迟不超过 30 秒"、"日报在每天 8:00 前生成"、"数据准确率 99.9%"。

9. **数据归档策略要和业务对齐**：不同数据的保留周期不同。原始事件保留 90 天，聚合数据保留 1 年，用户画像永久保留。归档策略要和数据使用方确认。

10. **定期做数据回溯测试**：模拟管道故障，验证从 Kafka 重放数据能否正确恢复。回溯能力是数据管道可靠性的终极检验。

## 小结

设计数据密集型系统需要理解完整的数据管道：采集 → 传输 → 处理 → 存储 → 服务。ETL 和 ELT 是两种数据处理范式，现代趋势是 ELT + 数据湖。批处理和流处理各有适用场景，实际项目中通常共存。数据质量监控是数据系统可靠运行的保障，应该从源头抓起。架构设计要从简单开始，随业务增长逐步演进，不要过度设计。

### 练习一：架构选型

一个短视频平台需要设计数据分析系统，核心需求包括：实时视频播放量统计（延迟 < 10 秒）、每日用户活跃度报表、视频推荐的用户特征计算。数据量级：日均 10 亿条播放事件。请给出技术选型和架构设计。

### 练习二：数据质量设计

用户行为埋点数据存在以下质量问题：部分事件缺失 user_id、同一事件重复上报、事件时间戳乱序。请设计数据清洗方案。

### 练习三：成本优化

当前数据管道每天处理 500GB 原始数据，存储在 S3 上，保留 3 年。数据量每年增长 50%。请设计存储成本优化方案，包括冷热分层、数据压缩、生命周期策略。

### 练习四：数据回溯与重放

Kafka 中存储了过去 7 天的用户行为日志。业务方发现 3 天前的用户画像计算有 bug，需要重新计算过去 3 天的画像数据。请设计一个支持数据回溯重放的方案。

## 参考答案

### 练习一

**思路**：10 亿条日均事件是高吞吐场景，需要流处理 + 列式存储。

**答案**：数据传输用 Kafka（高吞吐），实时处理用 Flink（10 秒延迟），批处理用 Spark（日报和画像），实时缓存用 Redis（播放量计数），分析存储用 ClickHouse，数据湖用 S3 + Iceberg。

架构：短视频播放事件 → Kafka → Flink(实时聚合) → Redis(实时播放量)；同时写入 S3/Iceberg → Spark(日报/画像) → ClickHouse → BI报表/推荐系统。

**要点**：10 亿条/天 ≈ 11.5 万条/秒，Kafka 多分区 + Flink 多并行度可以处理。播放量统计用 Redis INCR 最简单。

### 练习二

**思路**：三个问题分别对应不同的处理策略。

**答案**：
1. **缺失 user_id**：有 session_id/device_id 则关联补全，否则标记为匿名用户。在采集端加强校验从源头减少缺失。
2. **重复上报**：每条事件生成唯一 event_id，Flink 处理时基于状态去重，ClickHouse 用 ReplacingMergeTree 引擎自动去重。
3. **时间戳乱序**：Flink 的 Watermark 机制处理乱序事件，允许 5 秒内的乱序，超出范围的事件打到侧输出流单独处理。

**要点**：数据清洗要在进入数据湖之前完成，清洗规则要版本化管理。

### 练习三

**思路**：3 年数据量增长很快，需要分层存储和生命周期管理。

**答案**：当前 500GB/天，3 年后约 2.6PB（不压缩）。优化方案：冷热分层（7 天内标准存储，7-90 天低频存储，90 天以上归档）；数据压缩（Parquet 格式压缩比可达 10:1）；生命周期策略（自动化迁移 + 过期删除）；聚合降采样（原始事件保留 90 天，之后只保留小时级聚合数据，数据量减少 99%）。

**要点**：压缩 + 格式转换可节省 90% 存储成本，聚合降采样是最有效的成本优化手段。

### 练习四

**思路**：Kafka 的数据回溯能力是 Kappa 架构的核心优势。通过重置 Consumer Group 的 offset，可以重新消费历史数据。

**答案**：

```
数据回溯重放方案：

步骤 1：修复 bug 并部署新版本的画像计算服务
  → 确保新版本能正确处理历史数据

步骤 2：创建新的 Consumer Group
  → 不复用旧的 Consumer Group，避免影响正在运行的消费
  → 新 Group 名称：user-profile-recompute-v2

步骤 3：重置 offset 到 3 天前
  kafka-consumer-groups.sh \
    --bootstrap-server kafka:9092 \
    --group user-profile-recompute-v2 \
    --topic user-events \
    --reset-offsets \
    --to-datetime 2024-06-12T00:00:00.000 \
    --execute

步骤 4：启动消费者，从 3 天前开始重新计算
  → 计算结果写入新的临时表/临时 Key
  → 避免覆盖正在使用的画像数据

步骤 5：数据校验
  → 对比重算前后的画像数据差异
  → 抽样验证画像标签的准确性

步骤 6：切换
  → 校验通过后，将临时数据切换为正式数据
  → 停止重算 Consumer Group
```

注意事项：
```
1. 重算期间，实时管道不能停
   → 实时管道继续处理新数据到 user-profile-realtime
   → 重算管道处理历史数据到 user-profile-recompute
   → 最终合并：取重算结果 + 实时增量

2. 避免重复计算导致指标膨胀
   → 画像计算使用覆盖写（PUT），不是累加写
   → 同一用户多次计算，结果应该一致

3. 控制重算速度
   → 限制 Consumer 的消费速率，避免压垮下游存储
   → 建议限制为正常消费速度的 2-3 倍

4. Kafka 数据保留时间要足够
   → 默认 7 天，如果需要回溯更长时间，需要提前调整 retention
   → 也可以配合 S3 存储历史数据，用 Flink 从 S3 重放
```

**要点**：
- Kappa 架构的核心优势就是数据可重放，Kafka 的 retention 策略决定了可回溯的时间窗口
- 重算时使用独立的 Consumer Group，不影响实时管道
- 重算结果要先写入临时位置，校验通过后再切换
