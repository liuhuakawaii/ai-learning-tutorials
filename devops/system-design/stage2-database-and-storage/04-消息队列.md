# 消息队列：异步解耦与流式处理

## 场景引入

你的电商系统在用户下单后需要做一系列操作：扣减库存、发送订单确认短信、通知仓库发货、更新用户积分、记录数据分析日志。如果这些操作全部同步执行，下单接口的响应时间会超过 3 秒，用户根本等不起。

更糟糕的是，短信服务偶尔会超时，导致整个下单流程失败。用户看到"下单失败"的提示，但其实订单已经创建了，只是短信没发出去。

消息队列就是用来解决这类问题的。它让核心流程（创建订单）和非核心流程（发短信、通知仓库）解耦，各自独立运行，互不影响。

## 学习目标

- 理解消息队列的核心概念和使用场景
- 掌握 Kafka、RabbitMQ、Redis Streams 的架构特点和适用场景
- 理解消息可靠性保证（ACK 机制、持久化、重试）
- 掌握消息积压、死信队列、顺序消费等实战问题的处理方法
- 能够设计消息幂等方案

## Kafka 架构

Kafka 是分布式流处理平台，以高吞吐、持久化、水平扩展著称。

```
┌─────────────────────────────────────────────────────────────┐
│                    Kafka 架构                                │
│                                                             │
│  Producer ──→ ┌─────────────────────────────────┐           │
│               │          Topic: orders           │           │
│               │                                 │           │
│               │  Partition 0  Partition 1  Partition 2       │
│               │  ┌─────────┐ ┌─────────┐ ┌─────────┐       │
│               │  │msg0,msg3│ │msg1,msg4│ │msg2,msg5│       │
│               │  │msg6,msg9│ │msg7,msg10│ │msg8,msg11│      │
│               │  └─────────┘ └─────────┘ └─────────┘       │
│               │       ↑           ↑           ↑             │
│               └───────┼───────────┼───────────┼─────────────┘
│                       │           │           │             │
│               ┌───────▼───────────▼───────────▼──────────┐  │
│               │          Consumer Group: group-A          │  │
│               │  Consumer 1   Consumer 2   Consumer 3     │  │
│               └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### 分区（Partition）

Topic 是逻辑概念，Partition 是物理分片。每个 Partition 内的消息有序，但跨 Partition 无序。Partition 数量决定了消费者的最大并行度。

### 副本（Replica）

每个 Partition 有多个副本，分为 Leader 和 Follower。Leader 处理读写请求，Follower 同步数据。Leader 故障时，ISR（In-Sync Replicas）中的 Follower 会被选举为新 Leader。

### 消费者组（Consumer Group）

同一消费者组内的消费者分摊消费 Partition，不同消费者组独立消费。一个 Partition 只能被同一组内的一个消费者消费。

```
消费者组的 Rebalance 机制：

场景：3 个 Partition，消费者组有 2 个 Consumer

初始分配：
  Consumer 1 → Partition 0, Partition 1
  Consumer 2 → Partition 2

Consumer 2 宕机后触发 Rebalance：
  Consumer 1 → Partition 0, Partition 1, Partition 2

Consumer 3 加入后再次 Rebalance：
  Consumer 1 → Partition 0, Partition 1
  Consumer 2 → Partition 2
  Consumer 3 → （无分区可分配，空闲）

注意：消费者数量 > Partition 数量时，多余的消费者会空闲
建议：消费者数量 ≤ Partition 数量
```

### 生产者核心配置

```java
// Kafka Producer 关键配置
Properties props = new Properties();
props.put("bootstrap.servers", "kafka1:9092,kafka2:9092");
props.put("acks", "all");  // 确认机制：all=所有ISR确认, 1=Leader确认, 0=不确认
props.put("retries", 3);  // 发送失败重试次数
props.put("batch.size", 16384);  // 批量发送大小（字节）
props.put("linger.ms", 5);  // 等待凑批时间（毫秒）
props.put("buffer.memory", 33554432);  // 发送缓冲区大小
props.put("max.in.flight.requests.per.connection", 5);  // 每个连接的最大未确认请求数
```

acks 配置的权衡：
```
acks=0: 性能最高，但可能丢消息（网络故障、Broker 宕机）
acks=1: Leader 确认即返回，Leader 宕机可能丢数据
acks=all: 所有 ISR 确认才返回，最安全但延迟最高
```

### Exactly-Once 语义

Kafka 通过幂等 Producer + 事务 API 实现 Exactly-Once。Producer 发送消息时携带序列号，Broker 去重；消费端通过手动提交 offset + 业务幂等保证。

## RabbitMQ 架构

RabbitMQ 是传统的消息代理，以灵活的路由和可靠性著称。

```
┌───────────────────────────────────────────────────┐
│                RabbitMQ 消息路由                    │
│                                                   │
│  Producer ──→ ┌─────────────┐                     │
│               │  Exchange    │                     │
│               └──┬───┬───┬──┘                     │
│                  │   │   │                         │
│          ┌───────┘   │   └───────┐                 │
│          │           │           │                 │
│    ┌─────▼────┐ ┌────▼─────┐ ┌──▼───────┐        │
│    │ Queue A  │ │ Queue B  │ │ Queue C  │        │
│    └─────┬────┘ └────┬─────┘ └──┬───────┘        │
│          │           │           │                 │
│    ┌─────▼────┐ ┌────▼─────┐ ┌──▼───────┐        │
│    │Consumer 1│ │Consumer 2│ │Consumer 3│        │
│    └──────────┘ └──────────┘ └──────────┘        │
│                                                   │
│  Exchange 类型：                                   │
│  - Direct: 精确匹配 routing key                    │
│  - Fanout: 广播到所有绑定的队列                     │
│  - Topic:  通配符匹配 routing key                   │
│  - Headers: 按消息头匹配                            │
└───────────────────────────────────────────────────┘
```

### ACK 机制

RabbitMQ 支持两种确认模式：
- **自动 ACK**：消息发送给消费者后立即删除，可能因消费者处理失败而丢失
- **手动 ACK**：消费者处理完成后显式确认，未确认的消息会重新投递

```python
# RabbitMQ 手动 ACK 示例
def callback(ch, method, properties, body):
    try:
        process_message(body)
        ch.basic_ack(delivery_tag=method.delivery_tag)  # 处理成功，确认
    except Exception:
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)  # 处理失败，重新入队
```

## Redis Streams

Redis 5.0 引入的数据结构，提供轻量级的消息队列功能，适合不需要独立消息中间件的场景。

```python
# Redis Streams 生产者
redis.xadd("orders", {"user_id": "123", "product_id": "456", "amount": "99.9"})

# Redis Streams 消费者组
redis.xgroup_create("orders", "group-a", id="0", mkstream=True)
messages = redis.xreadgroup("group-a", "consumer-1", {"orders": ">"}, count=10)

# 确认消费
redis.xack("orders", "group-a", message_id)
```

### Kafka 持久化原理

Kafka 的高吞吐很大程度归功于其高效的磁盘写入机制：

```
Kafka 写入流程：

Producer 发送消息
  │
  ▼
写入 Page Cache（操作系统内存）
  │
  ▼
顺序写入磁盘日志文件（append-only）
  │
  ▼
Broker 返回确认

关键优化点：
1. 顺序写入：磁盘顺序写速度接近内存随机写
2. 零拷贝：sendfile() 系统调用，数据直接从磁盘到网卡
3. 批量发送：Producer 和 Broker 都支持批量操作
4. 分段存储：每个 Partition 分成多个 Segment 文件
```

```
Segment 文件结构：

partition-0/
├── 00000000000000000000.log   ← 消息数据
├── 00000000000000000000.index ← 偏移量索引
├── 00000000000000000000.timeindex ← 时间戳索引
├── 00000000000000000128.log
├── 00000000000000000128.index
└── ...
```

## 消息积压处理

消费者处理速度跟不上生产速度时，会出现消息积压。这是消息队列最常见的运维问题。

```
排查步骤：
1. 检查消费者是否正常运行（进程是否挂了）
2. 检查消费者处理速度（是否有慢查询或外部调用超时）
3. 检查消息量是否突增（是否有异常流量）

处理方案：
┌─────────────────────────────────────────────┐
│           消息积压应急处理                     │
├─────────────────────────────────────────────┤
│ 1. 紧急扩容消费者实例                         │
│ 2. 增加 Partition 数量（Kafka）               │
│ 3. 临时降低消费端业务逻辑（跳过非关键处理）    │
│ 4. 积压过多时，新建 Topic 转移消息            │
└─────────────────────────────────────────────┘
```

## 死信队列

当消息多次重试仍然失败时，为了避免阻塞队列，将其转入死信队列（DLQ）进行人工处理。

```python
# RabbitMQ 死信队列配置
# 正常队列设置死信交换机
channel.queue_declare(
    queue="orders",
    arguments={
        "x-dead-letter-exchange": "dlx.exchange",
        "x-dead-letter-routing-key": "dlq.orders",
        "x-message-ttl": 60000,  # 消息 TTL 60 秒
        "x-max-retries": 3       # 最多重试 3 次
    }
)

# 死信队列
channel.queue_declare(queue="dlq.orders")
channel.queue_bind(queue="dlq.orders", exchange="dlx.exchange", routing_key="dlq.orders")
```

## 顺序消费

有些业务场景要求消息按顺序处理（如订单状态变更），但消息队列的并行消费会打乱顺序。

```
保证顺序的方案：

1. Kafka: 同一业务 key 的消息发到同一 Partition
   Producer: send("orders", key=order_id, value=msg)
   → order_id 相同的消息一定在同一个 Partition
   → 该 Partition 只分配给一个 Consumer

2. RabbitMQ: 单消费者 + 内存队列分发
   Queue → Consumer(单个) → 按 key 分发到内存队列
   → 内存队列按 key 并行处理

3. 全局有序 vs 局部有序
   全局有序：只有一个 Partition，性能差，几乎不用
   局部有序：同一 key 有序，不同 key 可并行，推荐
```

## 消息幂等

网络抖动或消费者重试可能导致同一条消息被处理多次。幂等性保证多次处理的结果和一次处理相同。

```
常见幂等方案：

1. 唯一消息 ID + 去重表
   每条消息携带唯一 ID，处理前查询去重表
   INSERT INTO message_dedup (msg_id) VALUES (?) ON DUPLICATE KEY IGNORE

2. 数据库唯一约束
   利用业务数据的唯一性（如订单号）
   INSERT INTO orders (order_no, ...) VALUES (?, ...)
   → 重复插入会触发唯一约束，捕获异常即可

3. 乐观锁/版本号
   UPDATE inventory SET stock = stock - 1, version = version + 1
   WHERE product_id = ? AND version = ?
   → 版本不匹配则更新失败，说明已被处理过
```

## 常见误区

1. **"消息队列可以保证消息不丢失"**：消息队列只能尽量保证不丢失，极端情况下（如 Broker 全部宕机）仍可能丢消息。关键业务需要在消费端做幂等和补偿。

2. **"用消息队列就能解耦"**：消息队列提供了物理上的解耦，但如果生产者和消费者仍然依赖相同的消息格式和业务语义，逻辑耦合仍然存在。

3. **"Kafka 比 RabbitMQ 好"**：两者定位不同。Kafka 适合高吞吐的日志和流处理，RabbitMQ 适合需要灵活路由和可靠投递的业务消息。选错了反而增加复杂度。

4. **"消息可以无限堆积"**：虽然消息队列支持大量堆积，但磁盘空间是有限的。积压过多会导致磁盘满、性能下降。应该设置合理的过期策略和监控告警。

5. **"同步调用改消息队列就行"**：不是所有同步调用都适合改异步。如果下游处理结果需要立刻返回给用户（如支付扣款），就不应该用消息队列。

6. **"消息队列可以保证全局顺序"**：Kafka 只保证 Partition 内有序，RabbitMQ 只保证单个队列内有序。全局有序需要牺牲并行度（单 Partition/单 Consumer），生产环境几乎不用。

7. **"消费者越多消费越快"**：消费者数量不能超过 Partition 数量。Kafka 中多余的消费者会空闲；RabbitMQ 中多个消费者竞争同一个队列会增加协调开销。

8. **"消息发送失败重试就行"**：重试可能导致消息重复。如果消费端不做幂等处理，重试会造成业务数据错误。重试策略还需要考虑指数退避，避免重试风暴。

9. **"消息队列不需要监控"**：消费延迟、消息积压、Broker 负载、Partition 分布不均等问题都需要监控。没有监控的消息队列就像没有仪表盘的汽车，出了问题才知道。

10. **"消息格式可以随意变更"**：消息格式变更（如字段重命名、类型修改）会导致消费者解析失败。必须使用 Schema Registry 管理消息格式，变更要走兼容性检查。

## 工程建议

1. **明确消息队列的使用目的**：解耦、异步、削峰是三大核心场景。如果只是为了"用新技术"而引入消息队列，只会增加系统复杂度。

2. **消费端必须是幂等的**：不管消息队列提供什么保证，消费端都应该假设同一条消息可能被投递多次，并做好幂等处理。

3. **监控消费延迟和积压量**：设置消费延迟告警阈值，发现积压及时处理。Kafka 通过 consumer lag 监控，RabbitMQ 通过队列深度监控。

4. **消息体尽量精简**：大消息会占用大量网络带宽和存储空间。如果需要传递大文件，只在消息中携带文件路径，让消费端自行下载。

5. **做好消息的序列化和版本管理**：使用 Avro、Protobuf 等 Schema 化的序列化方式，配合 Schema Registry 管理消息格式的演进，避免新旧版本不兼容。

6. **Kafka Topic 命名规范**：使用 `业务域.实体.事件` 的格式，如 `order.order.created`、`user.profile.updated`。命名规范便于运维管理和权限控制。

7. **消息队列的容量规划**：根据峰值流量和可接受的堆积时间计算存储需求。峰值 10 万条/秒，允许堆积 1 小时，消息平均 1KB，需要约 360GB 存储。

8. **消费端要做好限流**：消费速度过快可能压垮下游服务。在消费端添加限流器（如令牌桶），控制对下游的调用频率。

9. **消息队列要做多机房容灾**：关键业务的消息队列需要跨机房部署。Kafka 通过 MirrorMaker 2 做集群间复制，RabbitMQ 通过 Federation 插件做跨机房同步。

10. **定期清理过期消息**：设置合理的 retention 策略（Kafka）和 TTL（RabbitMQ），避免历史消息占用过多存储空间。日志类 Topic 保留 7 天，业务 Topic 保留 30 天是常见配置。

## 小结

消息队列是分布式系统中实现异步解耦的核心组件。Kafka 适合高吞吐的流处理场景，RabbitMQ 适合需要灵活路由的业务消息，Redis Streams 适合轻量级队列需求。使用消息队列时，需要重点关注消息可靠性、消费幂等、顺序保证和积压处理。不要为了用而用，要根据实际业务需求选择合适的消息队列方案。

## 参考答案

### 练习一

**思路**：三种消息的特点不同，分别对应不同的最优方案。

**答案**：
- 用户行为日志 → Kafka：每秒 10 万条是高吞吐场景，Kafka 的分区和批量发送机制天然适合。配合 Flink 或 Spark Streaming 做实时分析。
- 订单状态变更 → RabbitMQ：需要可靠投递，RabbitMQ 的手动 ACK + 持久化 + 死信队列机制可以保证消息不丢失。Exchange 的路由能力可以灵活分发到不同下游。
- 缓存失效通知 → Redis Streams：如果系统已经有 Redis，用 Redis Streams 最简单，不需要引入额外组件。轻量级场景足够。

**要点**：
- 没有万能的消息队列，每种都有最适合的场景
- 考虑运维成本，能复用现有基础设施就不引入新组件

### 练习二

**思路**：同一订单的状态变更必须按顺序处理，但不同订单之间可以并行。

**答案**：
方案：Kafka 分区保证局部有序。

```java
// 生产端：以 order_id 作为 key，保证同一订单的消息进入同一 Partition
producer.send(new ProducerRecord<>("order-status", orderId, statusChange));

// 消费端：每个 Partition 只分配给一个消费者
// 同一 Partition 内的消息是有序的，所以同一订单的状态变更也是有序的
```

兜底机制：消费端处理前检查状态流转是否合法。
```python
def handle_status_change(order_id, new_status):
    current_status = get_order_status(order_id)
    if not is_valid_transition(current_status, new_status):
        log.warn(f"非法状态流转: {current_status} -> {new_status}, 跳过")
        return
    update_order_status(order_id, new_status)
```

**要点**：
- 局部有序（同一订单有序）比全局有序更实用
- 消费端要做状态流转合法性校验，防止乱序消息导致状态错误

### 练习三

**思路**：生产速度是消费速度的 10 倍，需要同时提升消费能力和降低生产压力。

**答案**：
应急处理（按优先级执行）：

1. **紧急扩容消费者**：将消费者实例从当前数量扩到 10 个以上（假设 Partition 足够）。如果 Partition 数量不足，先扩容 Partition（注意：Kafka 扩容 Partition 不会重新分配已有数据）。

2. **排查生产端异常**：确认是正常业务增长还是异常流量。如果是异常流量（如爬虫、重试风暴），在生产端限流。

3. **临时提升消费能力**：
   - 批量消费：每次拉取 500 条而非 10 条
   - 跳过非关键处理：日志记录、指标上报等可以暂时跳过
   - 异步化消费端的 IO 操作

4. **如果积压量太大**：创建新 Topic，让消费者组同时消费新旧 Topic，积压消息慢慢消化。

**要点**：
- 扩容消费者前确认 Partition 数量是否足够
- 区分正常流量增长和异常流量，处理方式不同

### 练习四

**思路**：核心问题是数据库操作和消息发送的一致性。不能先写库再发消息（消息可能发送失败），也不能先发消息再写库（库可能写入失败）。

**答案**：

方案：本地消息表 + 事务保障

```
┌──────────────────────────────────────────────────────────┐
│                  本地消息表方案                             │
│                                                          │
│  1. 开启数据库事务                                        │
│     ┌──────────────────────────────────┐                 │
│     │ BEGIN;                           │                 │
│     │ INSERT INTO orders (...);        │  ← 业务数据     │
│     │ INSERT INTO outbox_messages (...);│  ← 消息记录    │
│     │ COMMIT;                          │                 │
│     └──────────────────────────────────┘                 │
│                                                          │
│  2. 后台任务轮询 outbox_messages 表                        │
│     SELECT * FROM outbox_messages                        │
│     WHERE status='PENDING' LIMIT 100;                    │
│     → 发送到 Kafka                                       │
│     → 更新 status='SENT'                                 │
│                                                          │
│  3. 消费者处理消息                                        │
│     库存扣减服务 ← Kafka ← order.created topic            │
│     短信通知服务 ← Kafka ← order.created topic            │
│     积分更新服务 ← Kafka ← order.created topic            │
└──────────────────────────────────────────────────────────┘
```

代码示例：
```python
def create_order(order_data):
    with db.transaction():
        # 1. 创建订单
        order_id = db.insert('orders', order_data)
        # 2. 写入本地消息表（同一个事务）
        db.insert('outbox_messages', {
            'id': generate_uuid(),
            'topic': 'order.created',
            'payload': json.dumps({'order_id': order_id, **order_data}),
            'status': 'PENDING',
            'created_at': now()
        })
    return order_id

# 后台轮询任务
def poll_outbox():
    messages = db.query(
        "SELECT * FROM outbox_messages WHERE status='PENDING' LIMIT 100"
    )
    for msg in messages:
        try:
            kafka.send(msg['topic'], msg['payload'])
            db.update('outbox_messages', msg['id'], status='SENT')
        except Exception as e:
            log.error(f"消息发送失败: {msg['id']}, {e}")
```

优势：
- 业务数据和消息在同一个事务中，保证原子性
- 消息发送失败不影响订单创建，后台任务会重试
- 消费者幂等保证即使消息重复也不会出错

**要点**：
- 本地消息表需要定期清理已发送的消息
- 轮询间隔要权衡实时性和数据库压力（建议 1-5 秒）
- 消息发送失败要记录重试次数，超过阈值告警人工处理
