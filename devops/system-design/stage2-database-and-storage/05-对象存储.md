# 对象存储：海量非结构化数据的存储方案

## 场景引入

你的平台每天新增 10 万张用户上传的图片，加上视频、文档、备份文件，一年下来要存储几十 TB 的数据。把这些文件放在应用服务器的本地磁盘？磁盘早就满了。放在数据库里？BLOB 字段会让数据库性能急剧下降。用 NFS 共享文件系统？单机性能扛不住并发访问。

对象存储就是为解决这类问题而生的。它将文件作为"对象"存储在扁平的命名空间中，没有目录层级的概念，天然支持海量数据和高并发访问。S3 API 已经成为对象存储的事实标准，几乎所有云厂商和自建方案都兼容这套接口。

## 学习目标

- 理解对象存储、文件存储、块存储的区别和适用场景
- 掌握 S3 API 的核心操作和兼容性
- 能够设计自建对象存储方案（MinIO）
- 了解 CDN 集成和图片处理方案
- 掌握分片上传、预签名 URL、生命周期管理等实战技术

## 存储类型对比

```
┌─────────────────────────────────────────────────────────────┐
│                  三种存储类型对比                              │
├──────────────┬──────────────┬──────────────┬────────────────┤
│              │ 块存储        │ 文件存储      │ 对象存储        │
├──────────────┼──────────────┼──────────────┼────────────────┤
│ 数据模型      │ 原始磁盘块    │ 目录树+文件   │ 扁平命名空间    │
│ 访问协议      │ iSCSI/FC     │ NFS/SMB      │ HTTP REST API  │
│ 元数据        │ 无           │ 文件属性      │ 自定义丰富元数据│
│ 扩展性        │ TB 级        │ PB 级        │ EB 级          │
│ 典型场景      │ 数据库/虚拟机 │ 共享文件系统  │ 图片/视频/备份  │
│ 性能特征      │ 低延迟高IOPS  │ 中等延迟      │ 高延迟高吞吐    │
│ 成本          │ 高(SSD)      │ 中等          │ 低             │
└──────────────┴──────────────┴──────────────┴────────────────┘
```

简单理解：
- **块存储**：像一块裸硬盘，给数据库用最合适
- **文件存储**：像共享文件夹，给需要目录结构的应用用
- **对象存储**：像网盘，给海量文件存取用

## S3 API 兼容性

Amazon S3 定义了对象存储的 API 标准。核心操作包括：

```python
import boto3

s3 = boto3.client('s3',
    endpoint_url='http://minio:9000',  # 兼容 S3 API 的任何服务
    aws_access_key_id='xxx',
    aws_secret_access_key='xxx'
)

# 创建 Bucket
s3.create_bucket(Bucket='my-images')

# 上传文件
s3.put_object(
    Bucket='my-images',
    Key='avatars/user123.jpg',
    Body=image_bytes,
    ContentType='image/jpeg',
    Metadata={'user_id': '123', 'uploaded_at': '2024-06-15'}
)

# 下载文件
response = s3.get_object(Bucket='my-images', Key='avatars/user123.jpg')
data = response['Body'].read()

# 列出文件
response = s3.list_objects_v2(
    Bucket='my-images',
    Prefix='avatars/',
    MaxKeys=100
)

# 删除文件
s3.delete_object(Bucket='my-images', Key='avatars/user123.jpg')
```

S3 兼容意味着你的代码可以无缝切换底层存储：开发环境用 MinIO，测试环境用 LocalStack，生产环境用 AWS S3 或阿里云 OSS。

## MinIO 自建方案

MinIO 是最流行的开源对象存储服务，单机和分布式部署都支持，兼容 S3 API。

### 单机部署

```yaml
# docker-compose.yml
version: '3'
services:
  minio:
    image: minio/minio:latest
    command: server /data --console-address ":9001"
    ports:
      - "9000:9000"   # API 端口
      - "9001:9001"   # 管理控制台
    volumes:
      - minio-data:/data
    environment:
      MINIO_ROOT_USER: admin
      MINIO_ROOT_PASSWORD: your-strong-password

volumes:
  minio-data:
```

### 分布式部署

分布式 MinIO 通过纠删码（Erasure Coding）分散存储，最多允许一半磁盘故障。典型部署为 4 节点 × 4 磁盘，数据均匀分布在所有节点上。部署命令只需指定所有节点地址：

```bash
# 4 节点分布式部署
minio server http://node{1...4}/data{1...4}
```

### MinIO 纠删码原理

```
纠删码（Erasure Coding）工作原理：

原始文件 100MB
  │
  ▼
拆分为 N 个数据块 + M 个校验块
  │
  ├── 数据块 1 (25MB) ──→ Node 1 Disk 1
  ├── 数据块 2 (25MB) ──→ Node 2 Disk 2
  ├── 数据块 3 (25MB) ──→ Node 3 Disk 3
  ├── 数据块 4 (25MB) ──→ Node 4 Disk 4
  ├── 校验块 1 (25MB) ──→ Node 1 Disk 2
  ├── 校验块 2 (25MB) ──→ Node 2 Disk 3
  ├── 校验块 3 (25MB) ──→ Node 3 Disk 4
  └── 校验块 4 (25MB) ──→ Node 4 Disk 1

4 数据 + 4 校验 = 最多允许 4 块磁盘同时故障
存储开销：2 原始大小（相比 3 副本方案节省 33%）
```

与多副本方案对比：
```
方案          存储开销    可靠性    恢复速度
─────────────────────────────────────────
3 副本        3x         高       快（直接读副本）
纠删码 4+4    2x         高       较慢（需要计算恢复）
```

## CDN 集成

对象存储 + CDN 是静态资源分发的标准架构。对象存储负责持久化，CDN 负责就近分发。

```
┌─────────────────────────────────────────────────────────┐
│              对象存储 + CDN 架构                           │
│                                                         │
│  用户请求 ──→ ┌──────────┐    命中     ──→ 返回缓存      │
│              │ CDN 边缘节点│                             │
│              └─────┬────┘                             │
│                    │ 未命中                             │
│              ┌─────▼────┐                             │
│              │ CDN 回源   │                             │
│              └─────┬────┘                             │
│                    │                                  │
│              ┌─────▼────┐                             │
│              │ 对象存储   │  ← MinIO / S3 / OSS        │
│              │ (源站)     │                             │
│              └──────────┘                             │
└─────────────────────────────────────────────────────────┘
```

CDN 配置要点：
- **缓存策略**：静态资源设置长缓存（如 1 年），通过文件名哈希控制版本更新
- **回源鉴权**：防止绕过 CDN 直接访问源站，配置 Referer 白名单或签名
- **HTTPS**：全链路 HTTPS，CDN 证书配置

## 分片上传

大文件（如视频）上传时，需要分片传输以支持断点续传和并行上传。

```python
# S3 分片上传核心流程
def multipart_upload(bucket, key, file_path, part_size=10*1024*1024):
    resp = s3.create_multipart_upload(Bucket=bucket, Key=key)
    upload_id = resp['UploadId']
    parts = []
    with open(file_path, 'rb') as f:
        part_num = 1
        while data := f.read(part_size):
            resp = s3.upload_part(Bucket=bucket, Key=key,
                PartNumber=part_num, UploadId=upload_id, Body=data)
            parts.append({'PartNumber': part_num, 'ETag': resp['ETag']})
            part_num += 1
    s3.complete_multipart_upload(Bucket=bucket, Key=key,
        UploadId=upload_id, MultipartUpload={'Parts': parts})
```

## 预签名 URL

预签名 URL 允许客户端直接上传/下载文件到对象存储，无需经过应用服务器中转，减轻服务器压力。

```python
# 生成上传用的预签名 URL
def generate_upload_url(bucket, key, expires=3600):
    return s3.generate_presigned_url(
        'put_object',
        Params={'Bucket': bucket, 'Key': key, 'ContentType': 'image/jpeg'},
        ExpiresIn=expires
    )

# 前端直接上传
# PUT https://minio:9000/my-images/avatars/user123.jpg?X-Amz-Signature=xxx
```

```
传统方案：前端 → 应用服务器 → 对象存储（服务器带宽瓶颈）
预签名方案：前端 → 对象存储（直接传输，服务器只生成URL）
```

## 生命周期管理

数据随时间推移价值递减，生命周期管理可以自动将数据迁移到更便宜的存储层或删除过期数据。

```json
// S3 生命周期策略示例
{
  "Rules": [
    {
      "ID": "logs-lifecycle",
      "Prefix": "logs/",
      "Status": "Enabled",
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 365 }
    }
  ]
}
```

存储层级：
```
热数据（频繁访问）  → 标准存储（Standard）
温数据（偶尔访问）  → 低频访问存储（Standard-IA / Infrequent Access）
冷数据（极少访问）  → 归档存储（Glacier / Archive）
过期数据           → 自动删除
```

## 常见误区

1. **"对象存储可以替代文件系统"**：对象存储没有目录概念，不支持文件追加写入，不适合需要随机读写的场景（如数据库文件）。它是为"写一次读多次"的场景设计的。

2. **"S3 API 都一样"**：虽然很多服务声称兼容 S3 API，但实际兼容程度不同。迁移时需要测试所有用到的 API，特别是分片上传、生命周期管理等高级功能。

3. **"对象存储不需要备份"**：云厂商的对象存储通常有 11 个 9 的持久性，但这不意味着不需要备份。误删除、逻辑错误、账户安全问题仍然可能导致数据丢失。重要数据应该跨区域备份。

4. **"所有文件都放对象存储"**：小文件（如缩略图）如果数量极大（亿级），会产生大量 API 调用费用。需要评估访问模式和成本。

5. **"CDN 可以无限缓存"**：CDN 节点的存储空间有限，低频访问的内容会被淘汰。冷门资源可能需要回源，首次访问延迟较高。

6. **"预签名 URL 是安全的"**：预签名 URL 一旦生成，任何拿到 URL 的人都可以使用。有效期要尽量短，敏感操作（如删除）不应该生成预签名 URL。

7. **"对象存储的 Key 就是文件路径"**：对象存储是扁平的命名空间，`a/b/c.jpg` 中的 `/` 只是 Key 的一部分，不是真正的目录结构。不要依赖 `/` 做层级查询。

8. **"分片上传可以不限分片数"**：S3 最多支持 10000 个分片。如果分片大小设置过小（如 1MB），超过 10GB 的文件就无法上传。分片大小建议 5-100MB。

9. **"对象存储的性能都一样"**：不同存储类的性能差异很大。标准存储适合频繁访问，归档存储需要解冻才能访问（可能需要数小时）。选择存储类时要考虑访问延迟要求。

10. **"删除文件后存储费用立即归零"**：部分云厂商对删除的文件仍然计费（直到生命周期完成），或者有最低存储时间要求（如 30 天）。选型时要仔细阅读计费规则。

## 工程建议

1. **使用 S3 API 作为标准接口**：不要直接依赖某个云厂商的私有 SDK。使用 boto3 或各语言的 S3 兼容客户端，方便在不同存储后端之间切换。

2. **预签名 URL 用于客户端直传**：大文件上传和下载都应该走预签名 URL，避免应用服务器成为带宽瓶颈。应用服务器只负责生成 URL 和鉴权。

3. **图片处理走独立服务或 CDN 边缘函数**：不要在应用服务器里做图片缩放，用 CDN 的边缘计算能力或独立的图片处理服务（如 imgproxy、Thumbor）。

4. **设置合理的生命周期策略**：日志、临时文件、用户上传的临时素材都应该设置自动过期删除。长期不访问的数据迁移到低成本存储层。

5. **监控存储成本**：对象存储的费用不只是存储空间，还有 API 调用次数、数据传输费用。定期审查存储使用情况，清理不需要的数据。

6. **Key 命名要有规律**：使用 `{业务}/{日期}/{ID}.{扩展名}` 的格式，如 `avatars/2024/06/15/user123.jpg`。便于按前缀查询、生命周期管理和成本分析。

7. **使用 multipart upload 的 AbortIncompleteMultipartUpload 策略**：未完成的分片上传会持续占用存储空间。设置自动清理策略，超过 7 天未完成的分片自动删除。

8. **客户端上传要校验文件类型和大小**：预签名 URL 虽然限制了 ContentType，但客户端可能绕过。上传完成后在服务端校验文件头（magic number），防止恶意文件上传。

9. **跨区域复制（CRR）用于灾备**：关键数据启用跨区域自动复制。源区域故障时可以从目标区域恢复服务。注意：CRR 有额外的存储和流量成本。

10. **使用 Transfer Acceleration 加速跨地域上传**：S3 的 Transfer Acceleration 通过 CloudFront 边缘节点中转上传，对跨国上传速度提升明显。

## 小结

对象存储是处理海量非结构化数据的标准方案。S3 API 是事实标准，MinIO 是最流行的自建方案。对象存储通常配合 CDN 使用，前者负责持久化，后者负责分发。分片上传支持大文件传输，预签名 URL 让客户端直传成为可能。生命周期管理帮助控制存储成本。选择对象存储时，要明确它是为"写一次读多次"的场景设计的，不适合需要随机读写的场景。

## 参考答案

### 练习一

**思路**：根据访问频率和数据特征选择不同的存储层级。

**答案**：
- 用户头像 → 对象存储标准层 + CDN：频繁访问，需要 CDN 加速。图片格式统一，可以用 CDN 边缘函数做动态裁剪。
- 系统日志 → 对象存储低频访问层：每天 50GB，偶尔查询。30 天后自动转为低频存储，90 天后归档。
- 数据库备份 → 对象存储归档层（Glacier）：极少访问，归档存储成本最低。设置 1 年后自动删除。
- 用户视频 → 对象存储标准层 + CDN + 生命周期：上传后 7 天内走标准存储 + CDN，7 天后自动转为低频存储。

**要点**：
- 生命周期策略可以自动管理数据在不同存储层之间的迁移
- CDN 只缓存热数据，冷数据回源到对象存储

### 练习二

**思路**：预签名 URL 实现客户端直传，上传后触发异步图片处理。

**答案**：
架构设计：

1. 前端请求上传 → 后端生成预签名 URL 返回给前端
2. 前端用预签名 URL 直接上传原图到对象存储
3. 对象存储上传完成事件触发 Lambda/云函数
4. 云函数生成 3 种尺寸的缩略图，存入对象存储

```
前端 ──→ 后端API（获取上传URL）
  │           │
  │     ┌─────▼─────┐
  │     │返回预签名URL│
  │     └───────────┘
  │
  ├──→ 对象存储（直传原图）
  │         │
  │    上传完成事件
  │         │
  │    ┌────▼────┐
  │    │图片处理  │  → 生成 64x64, 200x200, 800x800
  │    └─────────┘
  │
  └──→ 更新数据库（图片URL）
```

**要点**：
- 预签名 URL 有有效期，防止滥用
- 图片处理异步化，不阻塞上传流程
- 存储路径用 user_id/size.jpg 的结构便于管理

### 练习三

**思路**：分片上传天然支持断点续传，关键是记录已上传的分片信息。

**答案**：
方案设计：

1. 前端将文件切片（如每片 5MB），2GB 文件共 400 片
2. 初始化分片上传，获取 upload_id
3. 前端逐片上传，每片上传成功后记录到本地（localStorage）
4. 断网重连后，前端查询已上传的分片列表（通过 upload_id 调用后端接口，后端查询对象存储的已上传分片）
5. 跳过已上传的分片，继续上传剩余分片
6. 所有分片上传完成后，调用合并接口

```python
# 后端：查询已上传分片
def list_uploaded_parts(bucket, key, upload_id):
    response = s3.list_parts(Bucket=bucket, Key=key, UploadId=upload_id)
    return [part['PartNumber'] for part in response.get('Parts', [])]

# 前端：断点续传逻辑
# 1. 获取已上传分片列表
# 2. 只上传不在列表中的分片
# 3. 全部完成后调用 complete_multipart_upload
```

**要点**：
- upload_id 是续传的关键标识，需要持久化保存
- 已上传的分片在合并前不会计入存储费用
- 设置合理的分片大小（5-100MB），太小会增加请求次数，太大不利于断点续传

### 练习四

**思路**：通过 Bucket/Key 前缀实现租户隔离，配合元数据服务统计用量。

**答案**：

```
存储架构设计：

方案一：每个租户独立 Bucket
  tenant-001/avatars/user1.jpg
  tenant-001/documents/report.pdf
  tenant-002/avatars/user2.jpg

  优点：隔离性最好，生命周期策略可以按租户定制
  缺点：Bucket 数量有上限（S3 默认 100 个），需要申请提升

方案二：按租户 ID 前缀（推荐）
  {tenant_id}/avatars/user1.jpg
  {tenant_id}/documents/report.pdf

  优点：单 Bucket 管理简单，无数量限制
  缺点：需要 Bucket Policy 限制跨租户访问
```

用量统计方案：
```python
# 上传时记录元数据
def upload_file(tenant_id, file_key, file_data):
    # 1. 上传到对象存储
    s3_key = f"{tenant_id}/{file_key}"
    s3.put_object(Bucket=BUCKET, Key=s3_key, Body=file_data)

    # 2. 记录元数据到数据库
    db.insert('file_metadata', {
        'tenant_id': tenant_id,
        'key': s3_key,
        'size': len(file_data),
        'uploaded_at': now()
    })

    # 3. 更新租户用量
    db.execute("""
        UPDATE tenant_quota
        SET used_bytes = used_bytes + %s
        WHERE tenant_id = %s AND used_bytes + %s <= max_bytes
    """, (len(file_data), tenant_id, len(file_data)))

# 配额检查
def check_quota(tenant_id, file_size):
    quota = db.query("SELECT * FROM tenant_quota WHERE tenant_id = %s", tenant_id)
    if quota.used_bytes + file_size > quota.max_bytes:
        raise QuotaExceededError(f"租户 {tenant_id} 存储配额已满")
```

**要点**：
- 元数据服务是用量统计和配额管理的关键，不能只依赖对象存储的 LIST 操作
- 删除文件时必须同步更新用量统计
- 定期用对象存储的 LIST 结果校准数据库中的用量数据，防止不一致
