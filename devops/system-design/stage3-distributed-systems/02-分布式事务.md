# 02 分布式事务

## 场景引入

你在一个电商平台下单购买一台笔记本电脑。这个操作涉及三个服务：订单服务创建订单、库存服务扣减库存、账户服务扣款。如果订单创建成功、库存扣减成功，但扣款失败了，会发生什么？你已经有了订单，库存被扣了，但钱没付——这就是分布式事务要解决的问题。

在单体应用中，数据库事务可以保证 ACID 特性。但在微服务架构下，每个服务有自己的数据库，传统的事务机制不再适用。本课将介绍分布式事务的主流解决方案，帮助你根据业务场景选择合适的方案。

## 学习目标

- 理解分布式事务产生的背景和核心挑战
- 掌握 2PC、TCC、Saga、本地消息表等主流方案的原理和优缺点
- 能够根据业务场景选择合适的分布式事务方案
- 了解 Seata 等分布式事务框架的设计思想

## 两阶段提交（2PC）

2PC 是最经典的分布式事务协议，将事务分为准备阶段和提交阶段：

```
                  协调者 (Coordinator)
                 /        |        \
                ▼          ▼          ▼
          参与者1     参与者2     参与者3

第一阶段 - Prepare:
  协调者 ──Prepare──> 参与者 ──Yes/No──> 协调者

第二阶段 - Commit/Abort:
  全部 Yes → 协调者 ──Commit──> 所有参与者
  任一 No  → 协调者 ──Abort───> 所有参与者
```

### 2PC 的问题

1. **同步阻塞**：参与者在准备阶段后等待协调者决定，期间资源被锁定
2. **单点故障**：协调者宕机后，参与者会一直持有锁资源
3. **数据不一致**：第二阶段协调者发送 Commit 后宕机，部分参与者收到 Commit，部分没有
4. **性能差**：两轮网络通信 + 资源锁定，延迟高

## TCC 模式

TCC（Try-Confirm-Cancel）是业务层面的两阶段提交：

```
订单服务          库存服务          账户服务
    │                │                │
    |--Try---------->|                |
    |  冻结库存       |                |
    |--Try------------------------------->|
    |                |                |  冻结金额
    |  全部 Try 成功  |                |
    |--Confirm------>|                |
    |  扣减冻结库存    |                |
    |--Confirm--------------------------->|
    |                |                |  扣减冻结金额
```

**Try**：预留资源（冻结库存、冻结金额），不做实际业务操作。

**Confirm**：确认提交，使用预留的资源。只做确认，不做业务检查。

**Cancel**：释放所有预留的资源。

### TCC 的关键设计

- **幂等性**：Confirm 和 Cancel 必须幂等，可能被重试
- **空回滚**：Try 没执行但收到 Cancel 时，直接返回成功
- **悬挂**：Cancel 执行后又收到 Try，需要拒绝

## Saga 模式

Saga 将长事务拆分为一系列本地事务，每个事务都有对应的补偿操作。

### 编排式 Saga（Orchestration）

由中心协调者指挥整个流程：

```
Orchestrator
    │
    |--执行--> 创建订单 (T1)
    |              │
    |              |--成功--> 扣减库存 (T2)
    |              |              │
    |              |              |--成功--> 扣款 (T3)
    |              |              |              │
    |              |              |              |--成功--> 完成
    |              |              |              |
    |              |              |              |--失败--> 补偿T2 --> 补偿T1
```

### 协同式 Saga（Choreography）

没有中心协调者，每个服务监听事件并决定行动：

```
订单服务                    库存服务                   账户服务
    |--发布: 订单已创建--------->|                         |
    |                          |--扣减库存                |
    |                          |--发布: 库存已扣减-------->|
    |                          |                         |--扣款
```

| 维度 | 编排式 | 协同式 |
|------|--------|--------|
| 复杂度 | 集中在 Orchestrator | 分散在各服务 |
| 耦合度 | 低 | 高 |
| 可追踪性 | 高 | 低 |
| 适用场景 | 流程复杂 | 流程简单 |

## 本地消息表

核心思想：将业务操作和消息写入放在同一个本地事务中。

```
订单服务数据库:
┌─────────────────────────────────────────┐
│  订单表              消息表              │
│  ┌──────────┐       ┌────────────────┐ │
│  │ order_id │       │ msg_id         │ │
│  │ amount   │       │ content        │ │
│  │ status   │       │ status(待发送)  │ │
│  └──────────┘       │ create_time    │ │
│                     └────────────────┘ │
│  同一个本地事务，要么都成功，要么都回滚    │
└─────────────────────────────────────────┘

流程:
1. 订单服务: 开启事务 → 插入订单 + 插入消息 → 提交事务
2. 定时任务: 扫描待发送消息 → 发送到 MQ → 更新为已发送
3. 库存服务: 消费消息 → 扣减库存 → 发送确认
4. 订单服务: 收到确认 → 更新消息为已完成
```

## 最大努力通知

最简单的方案，适用于对一致性要求不高的场景。系统尽力通知下游，失败则定期重试，不保证一定成功。适用于支付回调、短信通知等场景。

```
支付网关 ──回调──> 商户系统
          │
          ├── 成功 → 返回确认
          └── 失败 → 加入重试队列
                     ├── 第 1 次重试: 1 分钟后
                     ├── 第 2 次重试: 5 分钟后
                     ├── 第 3 次重试: 30 分钟后
                     └── 超过最大次数 → 人工介入
```

## 各方案对比

| 方案 | 一致性 | 性能 | 复杂度 | 业务侵入 | 适用场景 |
|------|--------|------|--------|----------|----------|
| 2PC | 强 | 低 | 中 | 低 | 数据库层面，短事务 |
| TCC | 强 | 中 | 高 | 高 | 资金交易，精确控制 |
| Saga | 最终 | 高 | 中 | 中 | 长事务，跨多服务 |
| 本地消息表 | 最终 | 高 | 中 | 低 | 异步场景，可靠消息 |
| 最大努力通知 | 最终 | 高 | 低 | 低 | 对一致性要求不高 |

## Seata 框架概述

Seata 是阿里巴巴开源的分布式事务框架，支持 AT、TCC、Saga、XA 四种模式。

**AT 模式**通过拦截 SQL 自动生成回滚日志，实现无侵入的分布式事务：

```
1. 执行前记录 Before Image
2. 执行业务 SQL
3. 执行后记录 After Image
4. 生成 undo log
5. 全局提交：异步删除 undo_log
6. 全局回滚：根据 undo_log 反向生成补偿 SQL
```

## 常见误区

1. **"分布式事务就是保证强一致性"**：一致性可以是强一致也可以是最终一致。很多场景下最终一致性就够了。

2. **"Saga 的补偿操作就是回滚"**：补偿不是真正的回滚，而是"向前恢复"。退款不是撤销扣款，而是一笔新的反向交易。

3. **"TCC 比 Saga 更可靠"**：两者适用场景不同。TCC 适合高一致性的短事务，Saga 适合长事务和跨多服务场景。

4. **"本地消息表可以保证 100% 一致"**：极端情况下（如 MQ 持久化失败）仍可能不一致，但已是工程上最可靠的方案之一。

5. **"2PC 已经过时没人用"**：2PC 在数据库内部（如 MySQL XA、PostgreSQL 两阶段提交）仍然广泛使用。它的问题在于跨服务场景，而非数据库内部场景。理解 2PC 是理解其他方案的基础。

## 工程建议

1. **优先考虑是否真的需要分布式事务**：通过业务设计（合并服务、引入中间状态）可以规避分布式事务。

2. **根据业务特点选择方案**：资金相关用 TCC，订单流程用 Saga，异步通知用本地消息表。

3. **做好幂等和重试设计**：无论使用哪种方案，服务接口都必须支持幂等。

4. **监控事务成功率**：建立完善的监控和告警机制。关注事务超时率、补偿触发率、人工介入率等指标，这些直接反映系统的健康度。

5. **准备好人工补偿机制**：需要有后台管理界面，支持人工查看和补偿未完成的事务。任何自动补偿都可能失败，人工兜底是最后的安全网。

## 小结

分布式事务是微服务架构下数据一致性的核心挑战。2PC 是理论基础但工程问题多，TCC 适合高一致性要求的场景，Saga 适合长事务流程，本地消息表是可靠的最终一致性方案。选择方案时要根据业务对一致性、性能、复杂度的要求综合考虑。

## 参考答案

### 练习一

**思路**：涉及外部服务（航空公司、酒店），这些服务通常不支持 TCC 接口。

**答案**：
- 推荐使用 **Saga 编排式**。外部服务通常不支持 Try/Confirm/Cancel 接口，Saga 的正向操作 + 补偿操作更容易集成。
- **酒店预订失败**：执行机票预订的补偿（取消机票），回滚订单状态。补偿操作可能涉及退票费用。
- **退款流程**：支付后取消是独立的 Saga 流程：取消保险 → 取消酒店 → 取消机票 → 退款。

**要点**：Saga 补偿不是免费的，可能涉及真实世界的费用；编排式适合流程复杂、需要清晰追踪的场景。

### 练习二

**思路**：每个步骤的补偿操作需要考虑业务语义。

**答案**：

| 步骤 | 正向操作 | 补偿操作 |
|------|----------|----------|
| 创建订单 | INSERT 订单 | UPDATE 状态为已取消 |
| 扣减库存 | 库存 -N | 库存 +N |
| 扣款 | 余额 -N | 发起退款 |
| 通知物流 | 创建物流单 | 取消物流单 |

扣款失败时：补偿库存（+N）→ 补偿订单（取消）。顺序为正向操作的逆序。

幂等性要求：每个补偿操作都必须幂等。以订单 ID 为幂等键，多次补偿返回相同结果。

**要点**：补偿操作必须幂等（可能被重试）；补偿顺序是正向操作的逆序；补偿可能失败，需要重试和人工介入机制。

### 练习三

**思路**：本地消息表的核心是将业务操作和消息写入放在同一个本地事务中，通过定时重试保证消息最终送达。

**答案**：

消息表设计：

```sql
CREATE TABLE outbox_message (
    msg_id VARCHAR(64) PRIMARY KEY,
    msg_type VARCHAR(32),
    payload TEXT,
    status ENUM('pending', 'sent', 'confirmed', 'failed'),
    retry_count INT DEFAULT 0,
    max_retry INT DEFAULT 5,
    created_at DATETIME,
    updated_at DATETIME,
    INDEX idx_status_retry (status, retry_count)
);
```

三种故障场景处理：
- **消息发送失败**：定时任务扫描 `pending` 状态消息，重新发送到 MQ。指数退避重试。
- **消费失败**：消费者返回 NACK，MQ 重新投递。消费者必须幂等处理（检查转账单号是否已处理）。
- **确认丢失**：消费者处理成功但 ACK 丢失，MQ 重复投递。消费者通过转账单号去重，已处理则直接返回成功。

数据清理策略：已确认且超过 7 天的消息定期归档到历史表，然后从主表删除。保留历史表用于审计和问题排查。

**要点**：消息表和业务操作必须在同一事务中；幂等是消费者的生命线；消息表不能无限增长，需要定期清理。
