# 01 CAP 与一致性

## 场景引入

2015 年 5 月 28 日，携程全线服务宕机近 8 小时，损失超过千万美元。事后复盘发现，核心数据库在做主从切换时，部分节点认为主节点已下线（网络分区），另一部分节点仍然向旧主库写入数据，导致脑裂。恢复后数据不一致，最终只能回滚到前一天的备份。

这个事故的根源，正是分布式系统中最基本的取舍问题：**当网络分区发生时，你选择保证一致性还是可用性？**

无论你是设计一个电商库存系统、社交平台的消息推送，还是金融交易系统，只要涉及多台机器协作，就绕不开 CAP 定理。本课将从 CAP 出发，逐步深入一致性模型和共识算法，帮助你建立分布式系统设计的理论基础。

## 学习目标

- 理解 CAP 定理的三个要素及其实际含义
- 能够根据业务场景选择 CP 或 AP 架构
- 掌握强一致性、最终一致性、因果一致性的区别与适用场景
- 理解 Raft 共识算法的核心机制（Leader 选举、日志复制、安全性）
- 了解 Quorum 机制和一致性级别的工程实现

## CAP 定理

CAP 定理由 Eric Brewer 在 2000 年提出，2002 年被 Gilbert 和 Lynch 证明。它指出在一个分布式系统中，以下三个性质最多只能同时满足两个：

```
                    一致性 (C)
                       /\
                      /  \
                     /    \
                    /  CA   \
                   / (单机)  \
                  /            \
                 /______________ \
        可用性 (A)              分区容错 (P)
              CP                  AP
         (放弃可用)           (放弃强一致)
```

**一致性 (Consistency)**：所有节点在同一时刻看到相同的数据。注意这里的一致性是线性一致性（Linearizability），不是数据库 ACID 中的一致性。

**可用性 (Availability)**：每个请求都能在有限时间内收到非错误的响应，但不保证返回的是最新数据。

**分区容错 (Partition Tolerance)**：系统在网络分区（节点之间通信中断）的情况下仍能继续运行。

### 为什么 P 是必选项

在真实的分布式环境中，网络分区是不可避免的——交换机故障、机房断网、光缆被挖断都会导致分区。因此实际的选择不是"三选二"，而是**在分区发生时，选择 C 还是 A**。

```
正常运行:  C + A + P  都可以满足
分区发生:  只能选 C (CP) 或 A (AP)
```

### CP vs AP 系统选择

| 维度 | CP 系统 | AP 系统 |
|------|---------|---------|
| 代表系统 | ZooKeeper、etcd、HBase | Cassandra、DynamoDB、CouchDB |
| 分区时行为 | 拒绝部分请求，保证数据正确 | 继续响应，可能返回旧数据 |
| 适用场景 | 配置中心、分布式锁、金融交易 | 社交动态、购物车、用户画像 |
| 数据丢失风险 | 低 | 需要冲突解决机制 |
| 性能 | 相对较低 | 高 |

举个具体例子：银行转账系统必须选择 CP，宁可暂时不可用也不能出现余额不一致；而用户的朋友圈动态可以选择 AP，短暂看到旧数据是可以接受的。

## 一致性模型

### 强一致性（线性一致性）

所有操作表现得好像只有一个副本，且操作按全局时间顺序执行。这是最强的一致性模型，但代价最高。

```
Client A:  write(x=1) -------->
                                 \
Client B:          read(x) -----> 必须返回 1
```

### 最终一致性

系统保证如果没有新的写入，最终所有副本会收敛到相同的值。"最终"没有时间上限，但通常在毫秒到秒级完成。

```
Client A:  write(x=1) --------> Node1: x=1
                                 Node2: x=0 (暂时)
                                 Node3: x=0 (暂时)
                   ... 复制同步 ...
                                 Node1: x=1
                                 Node2: x=1
                                 Node3: x=1  (最终一致)
```

### 因果一致性

保证有因果关系的操作按顺序被所有节点看到，无因果关系的操作可以被不同节点以不同顺序看到。

```
场景：社交平台评论
  User1: 发帖 "今天天气不错"
  User2: 回复 "确实很好"  (因果依赖于 User1 的帖子)

  所有节点必须先看到 User1 的帖子，再看到 User2 的回复
  但 User3 的无关帖子可以以任意顺序出现
```

## Raft 共识算法

Raft 是一种易于理解的共识算法，将问题分解为三个子问题：Leader 选举、日志复制和安全性。etcd、Consul、TiKV 等系统都基于 Raft 实现。

### 节点状态

每个 Raft 节点处于以下三种状态之一：

```
              超时未收到心跳
        ┌──────────────────────┐
        │                      ▼
   ┌─────────┐  发起选举  ┌─────────┐
   │ Follower │ ─────────>│ Candidate│
   └─────────┘            └─────────┘
        ▲    获得多数票      │  │
        │    ┌──────────────┘  │
        │    ▼                 │ 发现新 Leader 或
        │ ┌───────┐            │ 新 Term
        └─│Leader │<───────────┘
          └───────┘   赢得选举
```

**Follower**：被动接收 Leader 的心跳和日志，超时未收到心跳则转变为 Candidate。

**Candidate**：发起选举投票，获得多数票成为 Leader。

**Leader**：处理所有客户端请求，通过心跳维持权威。

### Leader 选举

1. 初始所有节点都是 Follower
2. Follower 在选举超时（通常 150-300ms 随机）内未收到心跳，转变为 Candidate
3. Candidate 递增当前 Term，向所有节点发送 RequestVote RPC
4. 获得多数票的 Candidate 成为 Leader
5. 每个节点在一个 Term 内只能投一票（先到先得）

随机超时机制是 Raft 避免脑裂的关键设计——通过错开选举时间，减少同时出现多个 Candidate 的概率。

### 日志复制

```
Leader 收到写请求:

Client ──> Leader
              │
              ├── AppendEntries ──> Follower1
              ├── AppendEntries ──> Follower2
              │
              │   多数确认后
              ▼
         commit 应用到状态机
              │
              ├── 下次心跳通知 Follower 提交
```

1. Leader 将新条目追加到本地日志
2. Leader 通过 AppendEntries RPC 将条目发送给所有 Follower
3. 多数节点确认后，Leader 将条目标记为已提交
4. Leader 在下次心跳中通知 Follower 提交该条目
5. 各节点将已提交的条目应用到状态机

### 安全性保证

Raft 通过以下机制保证正确性：

- **选举安全**：每个 Term 最多一个 Leader
- **Leader 只追加**：Leader 从不覆盖或删除自己的日志
- **日志匹配**：如果两个日志在某个索引处有相同的 Term 和命令，则该索引之前的所有条目都相同
- **Leader 完整性**：如果一条日志在某个 Term 被提交，它必然出现在所有更高 Term 的 Leader 日志中
- **状态机安全**：如果一个节点在某个索引处应用了日志条目，其他节点在同一索引处不会应用不同的条目

## Quorum 与一致性级别

在多副本系统中，Quorum 机制通过读写多数来保证一致性：

```
N = 总副本数
W = 写入成功所需最小节点数
R = 读取成功所需最小节点数

当 W + R > N 时，读写集合必然有交集，可以保证读到最新数据
```

| 配置 | 一致性 | 可用性 | 适用场景 |
|------|--------|--------|----------|
| W=N, R=1 | 强 | 写入脆弱 | 读多写少 |
| W=1, R=N | 弱 | 写入可用 | 写多读少 |
| W=Quorum, R=Quorum | 强 | 平衡 | 通用 |
| W=1, R=1 | 最终 | 最高 | 可容忍短暂不一致 |

Cassandra 提供可调一致性级别：ONE、QUORUM、ALL，开发者可以根据接口重要性灵活配置。比如订单创建用 QUORUM，用户头像查询用 ONE。

## 常见误区

1. **"CA 系统不存在"**：CA 不是说完全不存在，而是在没有分区时可以同时满足 C 和 A。但真实环境中分区必然发生，所以需要做好 CP 或 AP 的设计准备。单机数据库（如 MySQL 单实例）在不分区时就是 CA 的。

2. **"最终一致性等于数据丢失"**：最终一致性不是放弃一致性，而是在时间维度上放宽要求。数据最终会收敛，不会丢失。但需要配合冲突解决机制（如向量时钟、Last-Write-Wins）。

3. **"Raft 选出 Leader 就万事大吉"**：Leader 只是共识的第一步。日志复制的延迟、网络分区下的 Leader 重新选举、脑裂防护等都是需要持续关注的问题。

4. **"一致性级别越高越好"**：强一致性的代价是更高的延迟和更低的可用性。不是所有接口都需要强一致性，应该根据业务需求分级处理。

5. **"CAP 三选二是精确描述"**：CAP 定理是一个理论框架，实际系统设计中 C 和 A 都是连续的光谱，不是非此即彼的选择。

## 工程建议

1. **按业务分级选择一致性**：核心交易链路用强一致性，用户画像、推荐等用最终一致性。不要一刀切地为所有功能选择同一种一致性模型。

2. **为网络分区做好预案**：无论选择 CP 还是 AP，都需要明确分区发生时的降级策略。CP 系统要考虑分区期间的用户体验（如返回友好提示），AP 系统要设计冲突解决机制。

3. **监控 Raft 集群健康状态**：关注 Leader 选举频率、日志复制延迟、Follower 落后进度等指标。频繁的 Leader 切换通常意味着网络问题或节点故障。

4. **Quorum 配置要考虑读写比例**：读多写少的场景可以增加 R、减少 W；写多读少则反过来。核心是保证 W + R > N。

5. **测试分区场景**：使用 Chaos Engineering 工具（如 Chaos Monkey、Litmus）主动注入网络分区，验证系统在分区下的行为是否符合预期。

6. **理解线性一致性的性能代价**：线性一致性需要全局排序，通常意味着所有写操作都要经过 Leader 节点。在跨机房部署中，一次写入的延迟等于最慢副本的往返时间。如果业务可以接受因果一致性，性能可以提升数倍。

7. **合理设置 Quorum 的 N 值**：副本数 N 不是越多越好。N=5 比 N=3 多容忍 1 个节点故障，但写入延迟更高（需要等更多确认）。大多数场景 N=3 就够了。

## 小结

本课从 CAP 定理出发，讨论了分布式系统最核心的取舍问题。在真实工程中，P（分区容错）是必选项，因此设计者需要在一致性（C）和可用性（A）之间做出权衡。一致性模型从强到弱有线性一致性、因果一致性、最终一致性等，各有适用场景。Raft 共识算法通过 Leader 选举和日志复制机制，在工程上实现了强一致性的多节点共识。Quorum 机制则提供了灵活的一致性级别配置。理解这些基础理论，是设计可靠分布式系统的第一步。

## 练习

### 练习一：场景分析

你在设计一个跨国电商平台的库存系统。该平台在全球 3 个区域（亚太、欧洲、北美）部署了数据中心，每个区域有自己的库存副本。请分析：
- 该系统应该选择 CP 还是 AP？
- 库存扣减和库存查询应该分别使用什么一致性级别？
- 如果发生跨区域网络分区，如何处理？

### 练习二：Raft 日志复制

一个 5 节点的 Raft 集群，当前 Leader 在索引 10 处有一条日志条目，Term 为 3。此时发生网络分区，Leader 被隔离到只有 1 个节点的分区中。请问：
- 被隔离的 Leader 能否继续提交新的日志条目？为什么？
- 另一个分区（3 个节点）会发生什么？
- 分区恢复后，如何保证日志的一致性？

### 练习三：Quorum 设计

一个分布式 KV 存储系统有 5 个副本，需要满足以下要求：写入操作必须持久化到至少 3 个节点，读取操作必须能读到最新数据。请问：
- 最小的 W 和 R 值分别是多少？
- 如果希望最大化读取性能（最小化 R），W 应该设为多少？
- 如果一个节点永久丢失，这个配置是否仍然可用？

---

## 参考答案

### 练习一

**思路**：库存系统的核心矛盾是"超卖"vs"用户体验"。强一致性可以避免超卖但可能降低可用性，最终一致性可能导致超卖但用户体验更好。需要按操作类型分级。

**答案**：
- 库存系统建议选择 **CP**，因为超卖的代价（订单无法履约、赔偿、品牌受损）远高于暂时不可用的代价。
- **库存扣减**：使用强一致性（Quorum 或 ALL），确保扣减操作在全球范围内串行执行。可以通过中心化的库存服务或分布式锁实现。
- **库存查询**：使用最终一致性，允许各区域有短暂的数据延迟。可以展示"约 XX 件"来降低用户对精确性的期望。
- **跨区域分区时**：各区域的库存查询可以继续工作（展示本地缓存的库存），但库存扣减操作应该路由到主区域或暂停服务，返回"库存确认中，请稍后重试"。

**要点**：
- 核心交易链路不要妥协一致性
- 读写分离是平衡一致性和性能的常用手段
- 分区时的降级策略要提前设计，不能临时决策

### 练习二

**思路**：Raft 的提交规则要求多数节点确认。被隔离的 Leader 无法获得多数确认，因此无法提交。

**答案**：
- **被隔离的 Leader 不能提交新条目**。Raft 要求日志条目被多数节点确认后才能提交。被隔离的 Leader 只有 2 个节点（包括自己），无法获得 5 节点集群的多数（3 票）。
- **另一个分区会选举新的 Leader**。3 个节点的分区满足多数条件，它们会在选举超时后发起选举，选出新的 Leader。新 Leader 的 Term 会递增（变为 4 或更高）。
- **分区恢复后**：旧 Leader 收到新 Leader 的心跳（带有更高的 Term），自动退化为 Follower。旧 Leader 中未提交的日志条目会被新 Leader 的日志覆盖，保证一致性。

**要点**：
- Raft 的"多数派"机制是防止脑裂的关键
- 未提交的日志可以被覆盖，已提交的日志永远不会被覆盖
- Term 机制用于识别过期的 Leader

### 练习三

**思路**：应用 Quorum 公式 W + R > N，确保读写集合有交集。

**答案**：
- **最小 W=3, R=3**。因为 3 + 3 = 6 > 5，满足 Quorum 条件。
- **最大化读取性能**：W = 5, R = 1。写入所有节点，读取只需一个节点。但这会降低写入性能和可用性（任意一个节点写入失败就会导致写入不完整）。
- **一个节点永久丢失后**：W=3, R=3 的配置仍然可用。剩余 4 个节点，写入需要 3 个成功（4 >= 3），读取也需要 3 个成功（4 >= 3）。但如果丢失 2 个节点，则写入和读取都可能失败。

**要点**：
- Quorum 机制的核心是读写集合的交集
- W 和 R 的选择需要权衡读写性能
- 副本数决定了系统的容错能力（N 个副本最多容忍 N-Quorum 个节点故障）
