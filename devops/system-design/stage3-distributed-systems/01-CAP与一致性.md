# CAP 与一致性

## 从一次真实事故说起

2015 年 5 月 28 日，携程全线服务宕机近 8 小时，损失超过千万美元。事后复盘发现，核心数据库在做主从切换时，部分节点认为主节点已下线（网络分区），另一部分节点仍然向旧主库写入数据，导致脑裂。恢复后数据不一致，最终只能回滚到前一天的备份。

这个事故的根源是分布式系统中最基本的取舍：当网络分区发生时，你选择保证一致性还是可用性？

## CAP 定理的真实含义

```
                     一致性 (C)
                        /\
                       /  \
                      /    \
                     /  CA   \
                    / (单机)  \
                   /            \
                  /______________ \
         可用性 (A)              分区容错 (P)
               CP                  AP
          (放弃可用)           (放弃强一致)
```

**一致性**：所有节点在同一时刻看到相同的数据（线性一致性）。

**可用性**：每个请求都能在有限时间内收到非错误的响应，但不保证返回最新数据。

**分区容错**：系统在网络分区的情况下仍能继续运行。

关键认知：在真实分布式环境中，网络分区不可避免——交换机故障、机房断网、光缆被挖断都会导致分区。因此实际选择不是"三选二"，而是**在分区发生时，选择 C 还是 A**。

```
正常运行:  C + A + P 都可以满足
分区发生:  只能选 C (CP) 或 A (AP)
```

## CP vs AP：选错了代价很大

```
CP 系统（ZooKeeper、etcd、HBase）：
  分区时拒绝部分请求，保证数据正确
  适用：配置中心、分布式锁、金融交易

AP 系统（Cassandra、DynamoDB、CouchDB）：
  分区时继续响应，可能返回旧数据
  适用：社交动态、购物车、用户画像
```

银行转账必须选 CP——宁可暂时不可用也不能余额不一致。朋友圈动态可以选 AP——短暂看到旧数据可以接受。

## 一致性模型不只是"强"和"弱"

**线性一致性（最强）**：所有操作表现得好像只有一个副本，按全局时间顺序执行。代价最高。

```
Client A:  write(x=1) -------->
                                 \
Client B:          read(x) -----> 必须返回 1
```

**因果一致性**：有因果关系的操作按顺序被所有节点看到，无因果关系的可以不同顺序。社交评论天然适合——回复必须在帖子之后看到，但无关帖子可以乱序。

**最终一致性**：如果没有新写入，所有副本最终收敛到相同值。"最终"没有时间上限，但通常毫秒到秒级完成。需要配合冲突解决机制（向量时钟、Last-Write-Wins）。

## Raft 共识算法的核心机制

Raft 将共识分解为三个子问题：

**Leader 选举**：
1. 所有节点初始为 Follower
2. 超时未收到心跳 → 变为 Candidate → 发起投票
3. 获得多数票 → 成为 Leader
4. 随机超时机制错开选举时间，减少脑裂

**日志复制**：
```
Client → Leader → AppendEntries → Followers
                     ↓
              多数确认后 commit
                     ↓
              下次心跳通知 Followers
```

**安全性保证**：每个 Term 最多一个 Leader；Leader 只追加不覆盖；已提交的日志永远不会被覆盖。

## Quorum 机制

```
N = 总副本数
W = 写入成功所需最小节点数
R = 读取成功所需最小节点数

当 W + R > N 时，读写集合必然有交集，保证读到最新数据
```

```
配置          一致性    可用性    适用场景
──────────────────────────────────────────
W=N, R=1      强        写入脆弱   读多写少
W=1, R=N      弱        写入可用   写多读少
W=Q, R=Q      强        平衡      通用
W=1, R=1      最终      最高      可容忍短暂不一致
```

Cassandra 提供可调一致性级别：ONE、QUORUM、ALL。订单创建用 QUORUM，用户头像查询用 ONE。

## 练习

### 练习一：跨国库存系统设计

你设计一个跨国电商平台库存系统，全球 3 个区域部署。分析应该选 CP 还是 AP？库存扣减和查询分别用什么一致性级别？跨区域网络分区时如何处理？

### 练习二：Raft 分区场景

5 节点 Raft 集群，Leader 被隔离到只有 1 个节点的分区。被隔离的 Leader 能否继续提交日志？另一个分区会发生什么？分区恢复后如何保证一致性？

### 练习三：实现 Quorum 检查函数

编写一个 TypeScript 函数，检查给定的 W、R、N 配置是否满足 Quorum 条件（W + R > N）。用 Vitest 测试。

---

## 参考答案

### 练习一

选 CP。超卖代价（订单无法履约、赔偿）远高于暂时不可用。库存扣减用强一致性（Quorum），库存查询用最终一致性（展示"约 XX 件"）。跨区域分区时各区域查询继续（本地缓存），扣减路由到主区域或暂停。

### 练习二

被隔离的 Leader 不能提交新条目——Raft 要求多数确认，2 节点无法获得 5 节点集群的 3 票多数。另一个分区（3 节点）会选举新 Leader（Term 递增）。分区恢复后旧 Leader 收到更高 Term 的心跳，自动退化为 Follower，未提交日志被覆盖。

### 练习三

```typescript
function satisfiesQuorum(w: number, r: number, n: number): boolean {
  if (w < 1 || r < 1 || n < 1) throw new Error('W, R, N must be positive')
  if (w > n || r > n) throw new Error('W and R cannot exceed N')
  return w + r > n
}

describe('satisfiesQuorum', () => {
  test('W=3, R=3, N=5 满足', () => { expect(satisfiesQuorum(3, 3, 5)).toBe(true) })
  test('W=1, R=1, N=3 不满足', () => { expect(satisfiesQuorum(1, 1, 3)).toBe(false) })
  test('W=5, R=1, N=5 满足', () => { expect(satisfiesQuorum(5, 1, 5)).toBe(true) })
  test('W=1, R=5, N=5 满足', () => { expect(satisfiesQuorum(1, 5, 5)).toBe(true) })
  test('W=0 抛出异常', () => { expect(() => satisfiesQuorum(0, 1, 3)).toThrow() })
})
```
