# 06 阶段实战：设计分布式任务调度系统

## 场景引入

你所在的数据团队有一个每天凌晨 2 点执行的 ETL 流程：从数据源抽取数据 → 清洗转换 → 写入数据仓库 → 生成报表。之前用 Linux crontab 管理，问题开始出现：

- 某个脚本执行超时，后面的脚本不知道，仍然按原计划执行，导致数据不完整
- 服务器重启后，正在执行的任务丢失，无人知晓
- 任务越来越多，单机 crontab 无法承载
- 任务之间有依赖关系（报表生成依赖数据清洗完成），crontab 无法表达

你需要设计一个分布式任务调度系统。本课将综合运用前面学习的分布式锁、幂等设计、限流熔断等知识，完成完整的系统设计。

## 学习目标

- 能够分析分布式任务调度的核心需求
- 掌握 Master-Worker 架构的设计要点
- 理解任务分片、失败重试、依赖管理的设计
- 了解 XXL-Job、Airflow 等主流系统的设计思想

## 需求分析

### 功能需求

1. **定时调度**：支持 Cron 表达式
2. **手动触发**：支持立即执行
3. **任务依赖**：DAG 定义依赖关系
4. **失败重试**：配置重试次数和间隔
5. **任务分片**：大任务拆分为子任务并行执行
6. **超时控制**：超时自动终止
7. **执行日志**：记录详细日志

### 非功能需求

1. **高可用**：调度器和执行器不能单点故障
2. **高性能**：支持 10 万级任务调度
3. **可扩展**：动态增减执行器节点

## Master 节点设计

### Leader 选举

多个 Master 通过分布式锁选举 Leader，只有 Leader 负责调度：

```
Master A ──竞争分布式锁──> 获取成功 ──成为 Leader
Master B ──竞争分布式锁──> 获取失败 ──成为 Follower
Master C ──竞争分布式锁──> 获取失败 ──成为 Follower

Leader 定期续约（看门狗）
Leader 崩溃 → 锁过期 → 竞争锁 → 新 Leader
```

### 调度引擎

每秒扫描待执行任务：

1. 扫描触发时间 <= 当前时间的待执行任务
2. 检查依赖是否满足（DAG 前置任务完成）
3. 检查任务是否被暂停
4. 需要分片的任务生成子任务
5. 放入消息队列，更新状态为"已分发"

### 时间轮算法

高效处理大量定时任务：

```
时间轮 (tick=1s, wheel_size=60):

    0   1   2   3   4   5  ...  59
    │   │   │   │   │   │       │
  [T1] [] [T2] [] [T3] []     [Tn]

指针每秒移动一格，执行当前格子中的任务
超过 60 秒的任务使用多级时间轮:
  秒级轮 (0-59) → 分级轮 (0-59) → 时级轮 (0-23)
```

## Worker 节点设计

### 心跳注册

Worker 启动时向注册中心注册，每 10 秒发送心跳，包含：节点状态、当前任务数、CPU/内存使用率。

### 任务执行

```
1. 从消息队列获取任务
2. 幂等检查（防止重复执行）
3. 上报状态（执行中）
4. 独立线程执行任务
5. 上报结果（成功/失败/超时）
6. ACK 消息
```

### 超时控制

| 方式 | 说明 | 优缺点 |
|------|------|--------|
| 线程中断 | Thread.interrupt() | 简单，但任务可能不响应 |
| 进程隔离 | 独立进程，超时 kill | 安全，但开销大 |
| 协作式 | 任务检查超时标志 | 需要任务代码配合 |

## 任务分片策略

将大任务拆分为子任务并行执行：

```
场景: 批量处理 100 万条用户数据

按范围分片:
  分片1: user_id 1~250000
  分片2: user_id 250001~500000
  分片3: user_id 500001~750000
  分片4: user_id 750001~1000000

按哈希分片:
  分片号 = hash(user_id) % 分片数
  保证同一用户在同一分片
```

分配策略：
- **静态分配**：创建时确定，简单但不适应负载变化
- **动态分配**：根据 Worker 负载分配，更灵活
- **主动拉取**：Worker 空闲时从队列获取，天然负载均衡

## 失败重试与补偿

```
任务失败:
  ├── 重试次数 < 最大值 → 计算下次重试时间（指数退避）→ 重新入队
  └── 重试次数 >= 最大值 → 标记最终失败 → 告警通知

补偿策略:
  1. 自动重试（临时故障：网络超时、服务短暂不可用）
  2. 人工介入（持久故障：数据格式错误、逻辑 Bug）
  3. 跳过任务（非关键任务：日志清理、缓存预热）
  4. 回滚操作（数据一致性：使用 Saga 补偿）
```

## 任务依赖 DAG

```
数据 ETL 流程:

  [数据抽取A] ──> [数据清洗] ──> [数据加载] ──> [报表生成]
       │                              ↑
       └──> [数据抽取B] ──> [数据转换] ┘

DAG 定义:
  {
    "tasks": [
      {"id": "extract_a", "depends": []},
      {"id": "extract_b", "depends": []},
      {"id": "clean", "depends": ["extract_a"]},
      {"id": "transform", "depends": ["extract_b"]},
      {"id": "load", "depends": ["clean", "transform"]},
      {"id": "report", "depends": ["load"]}
    ]
  }
```

执行引擎：找出入度为 0 的任务 → 并行执行 → 完成后更新依赖图 → 找出新的可执行任务 → 重复直到全部完成。

## 高可用设计

### 调度器高可用

```
多 Master 部署:
  Master A (Leader) ──调度任务──> 消息队列
  Master B (Follower) ──同步状态──> 待命
  Master C (Follower) ──同步状态──> 待命

  Leader 崩溃 → 分布式锁过期 → Follower 竞争 → 新 Leader
  新 Leader 从数据库恢复任务状态
```

### 执行器高可用

```
Worker 集群:
  Worker A ──心跳──> 注册中心
  Worker B ──心跳──> 注册中心
  Worker C ──心跳──> 注册中心

  Worker 崩溃 → 心跳超时 → Master 标记下线 → 任务重新分配
```

### 数据高可用

任务状态以数据库为唯一真实来源。即使消息队列丢失，也可从数据库恢复。

## 与主流系统对比

### XXL-Job

轻量级分布式任务调度，适合中小规模：

- 调度中心（单/集群）通过 HTTP 调用执行器
- 执行器嵌入业务应用，无需独立部署
- 支持 Cron、分片、失败重试
- 不支持复杂 DAG

### Apache Airflow

工作流编排平台，适合复杂数据管道：

- DAG 用 Python 代码定义，灵活强大
- 丰富的 Operator（Bash、Python、SQL、Spark）
- 支持多种 Executor（Local、Celery、K8s）
- 调度延迟较高（分钟级），不适合实时任务

### 对比总结

| 维度 | 自建系统 | XXL-Job | Airflow |
|------|----------|---------|---------|
| 适用规模 | 按需设计 | 中小 | 大规模 |
| DAG 支持 | 需开发 | 不支持 | 完善 |
| 调度精度 | 秒级 | 秒级 | 分钟级 |
| 部署复杂度 | 高 | 低 | 中 |
| 学习成本 | 高 | 低 | 高 |

## 常见误区

1. **"任务调度就是 Crontab"**：Crontab 只能处理单机定时任务，不支持分布式执行、依赖管理、失败重试。

2. **"消息队列可以替代任务调度"**：MQ 实现任务分发，但缺乏调度、依赖管理、重试策略等能力。

3. **"分片越多越好"**：分片有额外开销（创建、状态管理、结果汇总），粒度太细调度开销大于执行开销。

4. **"重试可以解决所有失败"**：重试只适合临时故障。持久故障（数据错误、逻辑 Bug）重试只会浪费资源。

5. **"高可用就是多部署几台"**：还需要考虑状态一致性、故障检测、任务接管、数据持久化。

## 工程建议

1. **数据库是任务状态的唯一真实来源**：所有状态变更先写数据库。

2. **任务设计要考虑幂等**：任务可能被重复执行（重试、Worker 崩溃恢复）。

3. **监控调度延迟和执行耗时**：调度延迟高意味着调度器性能不足，执行耗时长需要优化或增加分片。

4. **渐进式设计**：从单机调度开始，逐步添加分布式执行、DAG 依赖、分片等功能。

5. **任务执行环境隔离**：不同任务可能有不同的依赖和资源需求。使用容器化（Docker）隔离任务执行环境，避免依赖冲突。对资源密集型任务设置 CPU 和内存限制，防止一个任务拖垮整个 Worker。

## 小结

本课通过设计分布式任务调度系统，综合运用了分布式锁、幂等设计、限流熔断等知识。核心设计点：Master-Worker 架构、Leader 选举、任务分片、DAG 依赖管理、失败重试与补偿、高可用设计。选择自建还是 XXL-Job/Airflow 取决于业务规模和功能需求。记住：任务状态以数据库为准，任务代码必须幂等。

## 练习

### 练习一：架构设计

为日均处理 1000 万条数据的 ETL 系统设计任务调度。流程：数据抽取（3 个数据源）→ 清洗 → 合并 → 写入仓库。设计整体架构、分片策略、DAG 依赖。

### 练习二：故障处理

设计以下故障的处理方案：Master Leader 崩溃、Worker 执行时崩溃、消息队列短暂不可用、任务执行超时。

### 练习三：方案选择

团队需要任务调度方案：200 个定时任务，部分有依赖，需要失败重试。5 人团队，希望快速上线。对比自建 vs XXL-Job vs Airflow。

---

## 参考答案

### 练习一

**答案**：

架构：3 Master（Leader 选举）+ 8 Worker（3 抽取 + 5 处理）+ RocketMQ。

分片：抽取按数据源天然分片（3 个任务并行）；清洗按数据量分片（每 10 万条一个分片）；合并不拆分；写入按日期分区并行。

DAG：`[抽取A] + [抽取B] → [清洗] → [合并] → [写入仓库]`，抽取阶段天然并行。

### 练习二

**答案**：

- **Master 崩溃**：分布式锁过期，Follower 竞争锁成为新 Leader，从数据库恢复状态。调度暂停几秒。
- **Worker 崩溃**：心跳超时标记下线，任务重新分配给其他 Worker。任务需要幂等，支持重跑。
- **MQ 不可用**：Master 缓存待发送消息，恢复后重发。任务状态在数据库中，不丢失。
- **任务超时**：Master 通知 Worker 终止任务，根据重试策略重新分发。

### 练习三

**答案**：

推荐 **XXL-Job**。原因：5 人团队自建成本太高（2-3 人月）；200 个任务 XXL-Job 完全胜任；通过"任务链"模拟简单依赖；1-2 天即可部署。

未来扩展（10 倍增长）：调度中心集群化 + 数据库读写分离；执行器按业务线分组；DAG 复杂时引入 Airflow。
