# 阶段实战：设计分布式任务调度系统

## 从 crontab 的痛点说起

你的数据团队有一个每天凌晨 2 点执行的 ETL 流程。之前用 Linux crontab 管理，问题开始出现：

- 某个脚本超时，后面的脚本不知道，仍然按原计划执行
- 服务器重启后，正在执行的任务丢失，无人知晓
- 任务越来越多，单机 crontab 无法承载
- 任务之间有依赖关系（报表生成依赖数据清洗完成），crontab 无法表达

你需要一个分布式任务调度系统。本课综合运用分布式锁、幂等设计、限流熔断等知识，完成完整设计。

## 需求分析

```
功能需求：
  定时调度（Cron 表达式）、手动触发、任务依赖（DAG）
  失败重试、任务分片、超时控制、执行日志

非功能需求：
  高可用（调度器和执行器不能单点）
  高性能（支持 10 万级任务）
  可扩展（动态增减执行器节点）
```

## 整体架构

```
管理控制台（任务管理/日志查看/监控大盘）
         │
      API 网关
         │
  ┌──────┼──────┐
  ▼      ▼      ▼
Master  Master  Master    ← Leader 选举
 (A)     (B)     (C)
  │
  ▼ 任务分发
消息队列 (Task Queue)
  │    │    │    │
  ▼    ▼    ▼    ▼
Worker Worker Worker Worker
```

## Master 节点设计

**Leader 选举**：多个 Master 通过分布式锁竞争，只有 Leader 负责调度。Leader 崩溃 → 锁过期 → 竞争锁 → 新 Leader。

**调度引擎**：每秒扫描待执行任务。
1. 扫描触发时间 ≤ 当前时间的待执行任务
2. 检查依赖是否满足（DAG 前置任务完成）
3. 需要分片的任务生成子任务
4. 放入消息队列，更新状态为"已分发"

**时间轮算法**：高效处理大量定时任务。

```
时间轮 (tick=1s, wheel_size=60):
    0   1   2   3   4   5  ...  59
    │   │   │   │   │   │       │
  [T1] [] [T2] [] [T3] []     [Tn]

指针每秒移动一格，执行当前格子中的任务
超过 60 秒的任务使用多级时间轮：
  秒级轮 (0-59) → 分级轮 (0-59) → 时级轮 (0-23)
```

## Worker 节点设计

Worker 启动时向注册中心注册，每 10 秒发送心跳（节点状态、当前任务数、CPU/内存使用率）。

任务执行流程：
```
从消息队列获取任务
  → 幂等检查（防止重复执行）
  → 上报状态（执行中）
  → 独立线程执行
  → 上报结果（成功/失败/超时）
  → ACK 消息
```

超时控制三种方式：线程中断（简单但任务可能不响应）、进程隔离（安全但开销大）、协作式（需要任务代码配合）。

## 任务分片

将大任务拆分为子任务并行执行：

```
场景: 批量处理 100 万条用户数据

按范围分片:
  分片1: user_id 1~250000
  分片2: user_id 250001~500000
  分片3: user_id 500001~750000
  分片4: user_id 750001~1000000
```

分配策略：静态分配（简单但不适应负载变化）、动态分配（根据 Worker 负载）、主动拉取（Worker 空闲时从队列获取，天然负载均衡）。

## 失败重试与 DAG 依赖

```
任务失败:
  ├── 重试次数 < 最大值 → 指数退避 → 重新入队
  └── 重试次数 >= 最大值 → 标记最终失败 → 告警

DAG 执行:
  找出入度为 0 的任务 → 并行执行 → 完成后更新依赖图
  → 找出新的可执行任务 → 重复直到全部完成
```

## 练习

### 练习一：架构设计

日均处理 1000 万条数据的 ETL 系统。流程：数据抽取（3 个数据源）→ 清洗 → 合并 → 写入仓库。设计整体架构、分片策略、DAG 依赖。

### 练习二：故障处理

设计以下故障的处理方案：Master Leader 崩溃、Worker 执行时崩溃、消息队列短暂不可用、任务执行超时。

### 练习三：实现 DAG 调度器

编写一个 TypeScript 函数 `getExecutableTasks(tasks)`，输入任务列表（每个任务有 id 和 depends 数组），返回当前可执行的任务列表（所有依赖已完成或无依赖的任务）。

## 参考答案

### 练习一

架构：3 Master（Leader 选举）+ 8 Worker（3 抽取 + 5 处理）+ RocketMQ。分片：抽取按数据源天然分片（3 个任务并行）；清洗按数据量分片（每 10 万条一个分片）。DAG：`[抽取A] + [抽取B] → [清洗] → [合并] → [写入仓库]`。

### 练习二

- **Master 崩溃**：分布式锁过期，Follower 竞争锁成为新 Leader，从数据库恢复状态。
- **Worker 崩溃**：心跳超时标记下线，任务重新分配。任务需要幂等。
- **MQ 不可用**：Master 缓存待发送消息，恢复后重发。任务状态在数据库中。
- **任务超时**：Master 通知 Worker 终止，根据重试策略重新分发。

### 练习三

```typescript
interface Task {
  id: string
  depends: string[]
  status?: 'pending' | 'running' | 'done' | 'failed'
}

function getExecutableTasks(tasks: Task[]): Task[] {
  const completedIds = new Set(
    tasks.filter(t => t.status === 'done').map(t => t.id)
  )
  return tasks.filter(t =>
    (t.status === 'pending' || t.status == null) &&
    t.depends.every(dep => completedIds.has(dep))
  )
}

describe('getExecutableTasks', () => {
  test('无依赖的任务可执行', () => {
    const tasks: Task[] = [
      { id: 'a', depends: [] },
      { id: 'b', depends: ['a'] },
    ]
    expect(getExecutableTasks(tasks).map(t => t.id)).toEqual(['a'])
  })
  test('依赖已完成的任务可执行', () => {
    const tasks: Task[] = [
      { id: 'a', depends: [], status: 'done' },
      { id: 'b', depends: ['a'] },
    ]
    expect(getExecutableTasks(tasks).map(t => t.id)).toEqual(['b'])
  })
  test('依赖未完成的任务不可执行', () => {
    const tasks: Task[] = [
      { id: 'a', depends: [], status: 'running' },
      { id: 'b', depends: ['a'] },
    ]
    expect(getExecutableTasks(tasks).map(t => t.id)).toEqual([])
  })
  test('并行无依赖任务', () => {
    const tasks: Task[] = [
      { id: 'a', depends: [] },
      { id: 'b', depends: [] },
      { id: 'c', depends: ['a', 'b'] },
    ]
    expect(getExecutableTasks(tasks).map(t => t.id).sort()).toEqual(['a', 'b'])
  })
})
```
