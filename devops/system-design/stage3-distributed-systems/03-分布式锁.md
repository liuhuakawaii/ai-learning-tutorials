# 03 分布式锁

## 场景引入

你负责一个电商平台的秒杀系统。某天上午 10 点，一款限量 100 台的手机开始秒杀。系统部署了 4 台应用服务器，每台服务器同时收到大量请求。如果两个请求同时查到库存为 1，都执行扣减操作，最终库存可能变成 -1——这就是经典的并发超卖问题。

在单机环境下，可以用 Java 的 `synchronized` 或 `ReentrantLock` 解决。但在分布式系统中，多个进程运行在不同的机器上，JVM 级别的锁完全无效。你需要一把"分布式锁"。

## 学习目标

- 理解分布式锁的核心需求和设计约束
- 掌握 Redis 分布式锁的实现（SET NX EX、Lua 释放、Redlock）
- 了解 ZooKeeper 分布式锁的实现原理
- 掌握可重入锁、看门狗续期等高级特性

## 分布式锁的基本要求

1. **互斥性**：任意时刻只能有一个客户端持有锁
2. **无死锁**：持有锁的客户端崩溃后，锁能自动释放
3. **容错性**：锁服务节点故障时，客户端仍能获取和释放锁
4. **可重入性**：同一个客户端可以多次获取同一把锁（可选）
5. **高性能**：获取和释放锁的操作延迟要低

## Redis 分布式锁

### 基础实现：SET NX EX

```bash
SET lock_key unique_value NX EX 30
```

- `NX`：只在 key 不存在时设置（保证互斥）
- `EX 30`：设置 30 秒过期（防止死锁）
- `unique_value`：客户端唯一标识（释放锁时验证身份）

```
Client A: SET lock:order:123 uuid-a NX EX 30 → OK，获取成功
Client B: SET lock:order:123 uuid-b NX EX 30 → nil，获取失败
```

### 安全释放：Lua 脚本

释放锁时不能直接 DEL，必须先验证 value 再删除：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

### 看门狗续期

如果业务执行时间超过锁的过期时间，锁会自动释放，导致并发问题。看门狗机制通过后台线程定期续期：

```
0s   ─── 获取锁 (EX 30s)
10s  ─── 看门狗续期 (重置为 30s)
20s  ─── 看门狗续期 (重置为 30s)
25s  ─── 业务完成，释放锁，看门狗停止

如果客户端崩溃:
0s   ─── 获取锁 (EX 30s)
15s  ─── 客户端崩溃，看门狗停止
45s  ─── 锁自动过期，其他客户端可获取
```

### Redlock 算法

单个 Redis 实例的锁在主从切换时可能丢失。Redlock 通过多个独立 Redis 实例解决：

```
1. 获取当前时间 T1
2. 依次向 N 个独立 Redis 实例获取锁
3. 如果在多数节点 (N/2+1) 获取成功，且耗时 < 过期时间 → 成功
4. 锁实际有效期 = 过期时间 - 获取耗时
5. 如果失败，向所有节点释放锁

5 个实例:
  Redis1: ✓  Redis2: ✓  Redis3: ✓  Redis4: ✗  Redis5: ✗
  结果: 3/5 成功 → 获取锁成功
```

## ZooKeeper 分布式锁

### 基本原理

使用临时顺序节点实现，天然防死锁（客户端会话结束时节点自动删除）：

```
/locks
├── lock-0000000001  (Client A，最小节点，获得锁)
├── lock-0000000002  (Client B，监听 lock-0000000001)
└── lock-0000000003  (Client C，监听 lock-0000000002)

流程:
1. Client A 创建临时顺序节点，发现自己最小 → 获得锁
2. Client B 创建节点，监听前一个节点
3. Client A 释放锁（删除节点）
4. ZooKeeper 通知 Client B，B 获得锁
```

### Curator 框架

```java
InterProcessMutex lock = new InterProcessMutex(client, "/locks/my-lock");
try {
    if (lock.acquire(10, TimeUnit.SECONDS)) {
        // 获得锁，执行业务逻辑
    }
} finally {
    lock.release();
}
```

### ZK 锁 vs Redis 锁

| 维度 | ZooKeeper | Redis |
|------|-----------|-------|
| 可靠性 | 高（ZAB 协议） | 中（主从切换可能丢锁） |
| 性能 | 中 | 高 |
| 防死锁 | 天然支持（临时节点） | 需要过期时间 |
| 公平性 | 天然支持（顺序节点） | 需要额外实现 |
| 适用场景 | 可靠性要求高 | 性能要求高 |

## 数据库分布式锁

```sql
-- 悲观锁：创建锁表
CREATE TABLE distributed_lock (
    lock_key VARCHAR(128) PRIMARY KEY,
    lock_value VARCHAR(128),
    expire_time DATETIME
);

-- 获取锁
INSERT INTO distributed_lock (lock_key, lock_value, expire_time)
VALUES ('order_lock', 'client_uuid', NOW() + INTERVAL 30 SECOND)
ON DUPLICATE KEY UPDATE
    lock_value = IF(expire_time < NOW(), VALUES(lock_value), lock_value),
    expire_time = IF(expire_time < NOW(), VALUES(expire_time), expire_time);
```

优点：不需要额外组件。缺点：性能差，锁表可能成为瓶颈。适用场景：并发量不高、不想引入额外组件的小型系统。

## 高级特性

### 可重入锁

允许同一个客户端多次获取同一把锁，在 value 中记录客户端标识和重入次数：

```
获取: 锁不存在 → SET {client_id:1} | 锁属于自己 → 重入次数+1 | 否则失败
释放: 重入次数-1 | 重入次数==0 → DEL
```

### 读写锁

区分读操作和写操作：多个读可以并发，写需要独占。Redis 使用两个 key 分别表示读锁和写锁。

## 常见误区

1. **"SET NX 就够了"**：没有过期时间会死锁，没有唯一 value 会误删。SET NX EX + Lua 释放是最低要求。

2. **"过期时间越长越安全"**：太长会导致持有者崩溃后等待太久。应结合看门狗机制续期。

3. **"Redlock 万无一失"**：在时钟跳跃等极端场景下仍可能不安全。极高可靠性场景用 ZooKeeper。

4. **"分布式锁解决所有并发问题"**：很多场景下乐观锁、队列串行化、原子操作更合适。分布式锁是最重的方案，不应该作为首选。

5. **"锁释放后业务就安全了"**：锁只能保证互斥访问，不能保证业务逻辑正确。比如库存扣减，锁保证了串行执行，但如果扣减逻辑本身有 Bug（比如没判断库存是否足够），锁也救不了。

## 工程建议

1. **根据场景选择**：高并发低延迟用 Redis，高可靠用 ZooKeeper，简单场景用数据库。

2. **锁粒度尽量细**：按商品 ID 加锁，不要对所有商品用同一把锁。

3. **做好监控**：关注锁获取成功率、持有时间、等待时间等指标。

4. **设置超时**：获取锁的操作应有超时，避免无限等待。

5. **考虑锁的公平性**：在任务调度等场景中，先到先得的公平性很重要。Redis 原生锁不保证公平，ZooKeeper 的顺序节点天然公平。如果用 Redis 实现公平锁，需要额外维护一个等待队列。

## 小结

分布式锁是分布式系统中实现互斥访问的核心机制。Redis 分布式锁性能高但可靠性相对较低，ZooKeeper 可靠性高但性能相对较低，数据库锁适合简单场景。选择方案时要综合考虑性能、可靠性、复杂度。无论使用哪种方案，都需要注意锁的过期管理、可重入性等问题。

## 参考答案

### 练习一

**思路**：获取锁需要 NX+EX，释放需要 Lua 验证，看门狗需要后台线程续期。

**答案**：

```python
import uuid, threading, time

class RedisDistributedLock:
    def __init__(self, redis_client, key, expire=30):
        self.redis = redis_client
        self.key = key
        self.expire = expire
        self.value = str(uuid.uuid4())
        self.locked = False

    def acquire(self, timeout=10):
        end_time = time.time() + timeout
        while time.time() < end_time:
            if self.redis.set(self.key, self.value, nx=True, ex=self.expire):
                self.locked = True
                self._start_watchdog()
                return True
            time.sleep(0.1)
        return False

    def release(self):
        self.locked = False
        lua = """if redis.call("GET",KEYS[1])==ARGV[1] then
            return redis.call("DEL",KEYS[1]) else return 0 end"""
        return self.redis.eval(lua, 1, self.key, self.value) == 1

    def _start_watchdog(self):
        def renew():
            while self.locked:
                time.sleep(self.expire / 3)
                if self.locked:
                    lua = """if redis.call("GET",KEYS[1])==ARGV[1] then
                        return redis.call("PEXPIRE",KEYS[1],ARGV[2]) else return 0 end"""
                    self.redis.eval(lua, 1, self.key, self.value, self.expire*1000)
        threading.Thread(target=renew, daemon=True).start()
```

**要点**：UUID 作为唯一标识；Lua 保证验证+删除原子性；看门狗在 1/3 过期时间续期。

### 练习二

**思路**：任务执行时间不确定，Redis 过期时间难以设置。

**答案**：选择 **ZooKeeper 分布式锁**。临时节点绑定客户端会话，只要心跳正常节点就不会删除，不需要手动续期。Worker 崩溃时临时节点自动删除，其他 Worker 可接管任务。任务需要支持幂等，因为可能被多个 Worker 执行。

### 练习三

**思路**：多锁场景必须按固定顺序获取，防止死锁。

**答案**：
- 用户信息：以用户 ID 为粒度 `lock:user:{user_id}`
- 订单状态：以订单 ID 为粒度 `lock:order:{order_id}`
- 商品库存：以商品 ID 为粒度 `lock:product:{product_id}`
- 同时更新订单和库存：按固定顺序获取（先订单锁，再库存锁），或使用更粗粒度的锁

**要点**：粗粒度锁简单但并发差，细粒度锁性能好但复杂度高。
