# 04 限流与熔断

## 场景引入

2019 年 3 月，某电商平台大促活动开始瞬间，流量激增至平时的 50 倍。没有有效的限流机制，流量打穿网关层涌入后端服务。数据库连接池被打满，服务超时，超时导致上游重试，重试进一步放大流量——最终整个平台瘫痪 2 小时。

事后复盘发现，如果在网关层设置了合理的限流，只放行系统能承载的流量，虽然部分请求会被拒绝，但核心业务不会崩溃。**限流的价值：牺牲一部分请求，保护整体系统可用性**。

如果说限流是"控制入口流量"，熔断就是"切断故障传播"。当下游服务出现故障时，继续调用只会浪费资源并拖垮上游。本课将介绍限流和熔断的核心机制。

## 学习目标

- 掌握四种主流限流算法的原理和适用场景
- 理解分布式限流的实现方式（Redis + Lua）
- 掌握熔断器模式的三种状态和转换逻辑
- 了解主流熔断框架（Sentinel、Resilience4j）的设计差异

## 限流算法

### 固定窗口计数器

在固定时间窗口内计数，最简单的限流算法：

```
窗口: 1 分钟，阈值: 100 次

|-------- 窗口1 --------|-------- 窗口2 --------|
  00:00              01:00              02:00

问题：窗口边界突刺。00:59~01:01 之间来 200 个请求，
每个窗口都没超限，但 2 秒内 200 个可能超出系统承载。
```

### 滑动窗口计数器

将窗口细分为多个小格子，滑动统计：

```
窗口: 1 分钟，6 个格子（每格 10 秒），阈值: 100

当前: 01:15，统计: 00:15~01:15
格子: [00:15-00:25]=15 [00:25-00:35]=20 [00:35-00:45]=18
      [00:45-00:55]=22 [00:55-01:05]=10 [01:05-01:15]=8
总计: 93 < 100，允许
```

### 漏桶算法

请求进入漏桶，以固定速率流出。桶满则拒绝：

```
        请求进入
           │
           ▼
      ┌─────────┐
      │ 漏桶     │ ← 容量: 10
      │ ████████ │
      │ ████████ │
      └────┬─────┘
           │ 固定速率: 5个/秒
           ▼
        处理请求

特点: 输出速率恒定，平滑突发流量
缺点: 无法应对突发流量（即使系统有余力）
```

### 令牌桶算法

以固定速率添加令牌，请求需要获取令牌才能通过：

```
        令牌生成器 (5个/秒)
           │
           ▼
      ┌─────────┐
      │ 令牌桶   │ ← 容量: 10
      │ ● ● ●   │
      │ ● ● ●   │
      └────┬─────┘
           │ 获取令牌
           ▼
        请求处理

特点: 允许突发流量（桶中积累的令牌），比漏桶更灵活
```

### 算法对比

| 算法 | 平滑性 | 突发处理 | 复杂度 | 适用场景 |
|------|--------|----------|--------|----------|
| 固定窗口 | 差 | 无 | 低 | 简单限流 |
| 滑动窗口 | 好 | 无 | 中 | 精确限流 |
| 漏桶 | 最好 | 不支持 | 低 | 流量整形 |
| 令牌桶 | 好 | 支持 | 中 | 通用限流 |

## 分布式限流

单机限流用本地内存即可，分布式环境需要共享限流状态。最常用方案是 Redis + Lua：

```lua
-- 滑动窗口限流
local key = KEYS[1]
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local current = tonumber(ARGV[3])

redis.call("ZREMRANGEBYSCORE", key, 0, current - window)
local count = redis.call("ZCARD", key)

if count < limit then
    redis.call("ZADD", key, current, current .. math.random())
    redis.call("EXPIRE", key, window)
    return 1  -- 允许
else
    return 0  -- 拒绝
end
```

### 限流粒度

| 粒度 | 说明 | 示例 |
|------|------|------|
| 全局限流 | 整个系统的总流量 | 总 QPS 不超过 10000 |
| 接口限流 | 单个 API | /api/orders 不超过 1000/s |
| 用户限流 | 单个用户 | 每用户每分钟 60 次 |

实际工程中组合使用：全局限流保护系统，接口限流保护热点接口，用户限流防止单用户滥用。

## 熔断器模式

借鉴电路保险丝概念：检测到下游故障时快速失败。

### 三种状态

```
                失败率超过阈值
        ┌──────────────────────┐
        │                      ▼
   ┌─────────┐  超时后尝试  ┌─────────┐
   │  关闭    │ ──────────>│  半开    │
   │ (正常)   │            │ (探测)   │
   └─────────┘            └─────────┘
        ▲                      │
        │    探测成功           │ 探测失败
        └──────────────────────┘
                          │
                    ┌─────────┐
                    │  打开    │
                    │ (熔断)   │
                    └─────────┘
```

**关闭**：正常处理请求，统计失败率。超过阈值（如 50%）→ 打开。

**打开**：所有请求直接失败，不调用下游。超时后 → 半开。

**半开**：允许少量请求探测。成功 → 关闭；失败 → 打开。

### 关键参数

```
failureRateThreshold = 50%        -- 失败率阈值
slowCallDurationThreshold = 2s    -- 慢调用判定时间
slidingWindowSize = 100           -- 滑动窗口大小
minimumNumberOfCalls = 10         -- 最小请求数
waitDurationInOpenState = 30s     -- 打开状态等待时间
```

## 主流框架对比

| 维度 | Hystrix | Sentinel | Resilience4j |
|------|---------|----------|--------------|
| 隔离策略 | 线程池/信号量 | 信号量/并发数 | 信号量/线程池 |
| 统计方式 | 滑动窗口 | 滑动窗口 | Ring Bit Buffer |
| 规则配置 | 静态 | 动态推送 | 动态 |
| 社区活跃度 | 低（停止维护） | 高 | 中 |

**Sentinel**：阿里巴巴开源，支持热点参数限流、集群限流，与 Dubbo/Spring Cloud 深度集成。特色功能包括：系统自适应保护（根据系统负载自动调整阈值）、热点参数限流（对 URL 参数级别的精细化控制）、集群限流（分布式环境下统一限流）。

**Resilience4j**：轻量级，专为 Java 8+ 函数式编程设计，模块化（熔断、限流、重试独立可用）。核心优势是函数式 API 和装饰器模式，可以灵活组合多个保护策略。适合不需要重量级框架的场景。

## 降级策略

限流或熔断触发时的降级方式：

1. **返回默认值**：推荐服务熔断时返回热门列表
2. **返回缓存数据**：数据库超时时返回缓存旧数据
3. **功能降级**：关闭非核心功能，保证核心功能
4. **排队等待**：请求放入队列，恢复后处理
5. **友好提示**：返回"系统繁忙，请稍后重试"

### 降级策略选择矩阵

| 触发场景 | 推荐降级方式 | 用户感知 | 示例 |
|----------|-------------|----------|------|
| 接口限流 | 排队等待 / 友好提示 | 低 | 下单排队 |
| 下游熔断 | 返回缓存 / 默认值 | 中 | 商品详情展示缓存 |
| 系统过载 | 功能降级 | 高 | 关闭推荐、评论等非核心功能 |
| 数据库故障 | 返回缓存 + 只读模式 | 高 | 允许浏览，禁止写入 |

降级策略需要提前配置，不能临时决定。建议在配置中心统一管理降级规则，支持动态切换。

## 常见误区

1. **"限流就是直接拒绝"**：还可以排队、降级、返回缓存。直接拒绝最简单但不一定最好。

2. **"熔断和超时是一回事"**：超时是单次请求的等待限制，熔断是基于统计的自动开关。

3. **"阈值设得越高越好"**：应基于系统实际承载能力设置，留出安全余量。

4. **"熔断后就不管了"**：需要配置合理的超时时间和半开探测策略。

5. **"限流只在网关层做就够了"**：网关层限流保护整体系统，但服务内部也需要限流保护自身。一个服务可能被多个上游调用，网关层无法精确控制每个上游的流量。分层限流才是完整方案。

## 工程建议

1. **分层限流**：网关层全局限流，服务层接口限流，应用层用户限流。

2. **限流和熔断配合使用**：限流控制入口流量，熔断切断故障传播。

3. **做好监控告警**：限流和熔断触发时及时告警，长时间处于保护状态可能需要扩容。

4. **测试限流效果**：用压测工具模拟流量高峰，验证阈值是否合理。

## 小结

限流和熔断是保障分布式系统稳定性的两大核心机制。四种限流算法各有特点，令牌桶最常用。熔断器的三种状态构成完整的故障检测和恢复机制。工程实践中需要根据业务场景选择合适的算法和框架，做好分层限流和降级策略。

## 参考答案

### 练习一

**答案**：
- **登录接口**：固定窗口计数器。防攻击不需要处理突发，key=`login:{user_id}`，窗口 60s，阈值 5。
- **商品详情**：滑动窗口计数器。需要精确控制 QPS，key=`api:product_detail`，窗口 1s，阈值 10000。
- **下单接口**：令牌桶。允许突发流量，令牌速率 1000/s，桶容量 2000。

### 练习二

**答案**：
- **失败率阈值**：30%。正常 5% 超时，超过 30% 说明严重问题，留出缓冲避免正常波动触发熔断。
- **滑动窗口**：100 次请求，时间窗口 10 秒。太小不稳定，太大延迟熔断。
- **半开请求数**：5 次。足够判断服务是否恢复，又不会给恢复中的服务太大压力。

### 练习三

**答案**：

```lua
local function check_limit(key, limit, window, current)
    redis.call("ZREMRANGEBYSCORE", key, 0, current - window)
    local count = redis.call("ZCARD", key)
    if count < limit then
        redis.call("ZADD", key, current, current .. math.random())
        redis.call("EXPIRE", key, window)
        return 1
    end
    return 0
end

-- 全局限流 → 用户限流 → 接口限流
-- 返回不同状态码区分限流原因
```

**要点**：三层限流独立计数；全局限流放前面减少计算；Lua 脚本保证原子性。
