# 数据建模

## 场景引入

你正在设计一个电商系统的数据库。第一个问题是：商品表应该包含哪些字段？价格变化历史放在商品表里还是单独建表？商品分类是一对多还是多对多？

这些看似简单的决定，会在系统运行几个月后暴露问题：查询越来越慢，因为没有合适的索引；数据冗余导致不一致，因为同一个信息存在多个地方；分表时发现关联查询无法拆分，因为外键关系设计不合理。

数据建模是系统设计的基石。好的数据模型让查询高效、扩展容易；差的数据模型让系统在数据量增长后变得难以维护。本节课从 ER 图设计到索引策略，帮你建立扎实的数据建模能力。

## 学习目标

- 掌握 ER 图设计方法，能识别实体、关系和属性
- 理解三大范式（1NF/2NF/3NF）的含义，以及何时需要反范式化
- 掌握索引设计原则（B+树、哈希、复合索引），了解索引失效场景
- 学会根据业务场景选择合适的数据类型
- 理解分表策略及其适用场景

## ER 图设计

ER 图（Entity-Relationship Diagram）是数据建模的基础工具。三个核心概念：

- **实体（Entity）**：业务中的对象，如用户、订单、商品
- **关系（Relationship）**：实体之间的关联，如用户下订单、订单包含商品
- **属性（Attribute）**：实体或关系的特征，如用户名、订单金额

### 电商系统 ER 图示例

```
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│    User      │         │    Order     │         │  OrderItem   │
├──────────────┤    1:N  ├──────────────┤    1:N  ├──────────────┤
│ id (PK)      │────────→│ id (PK)      │────────→│ id (PK)      │
│ username     │         │ user_id (FK) │         │ order_id (FK)│
│ email        │         │ total_amount │         │ product_id   │
│ phone        │         │ status       │         │ quantity     │
│ created_at   │         │ created_at   │         │ unit_price   │
└──────────────┘         └──────────────┘         └──────────────┘
                                                          │
                                                          │ N:1
                                                          ▼
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│   Category   │    N:M  │   Product    │         │ProductCategory│
├──────────────┤←───────→├──────────────┤         ├──────────────┤
│ id (PK)      │         │ id (PK)      │         │ product_id   │
│ name         │         │ name         │         │ category_id  │
│ parent_id    │         │ price        │         └──────────────┘
└──────────────┘         │ stock        │
                         │ created_at   │
                         └──────────────┘
```

### 关系类型

| 关系 | 示例 | 实现方式 |
|------|------|----------|
| 一对一（1:1） | 用户 - 用户详情 | 外键或合并为一张表 |
| 一对多（1:N） | 用户 - 订单 | 多的一方持有外键 |
| 多对多（N:M） | 商品 - 分类 | 中间关联表 |

## 三大范式与反范式化

### 第一范式（1NF）

**每个字段必须是原子的，不可再分。**

```
❌ 违反 1NF：
┌─────────┬─────────────────┐
│ user_id │ phones          │
├─────────┼─────────────────┤
│ 1       │ 138xxx,139xxx   │  ← 一个字段存了多个值
└─────────┴─────────────────┘

✅ 满足 1NF：
┌─────────┬──────────┐
│ user_id │ phone    │
├─────────┼──────────┤
│ 1       │ 138xxx   │
│ 1       │ 139xxx   │
└─────────┴──────────┘
```

### 第二范式（2NF）

**在满足 1NF 的基础上，非主键字段必须完全依赖主键，不能只依赖主键的一部分。**

```
❌ 违反 2NF（联合主键 order_id + product_id）：
┌──────────┬────────────┬─────────┬──────────────┐
│ order_id │ product_id │quantity │ product_name │
├──────────┼────────────┼─────────┼──────────────┤
│ 1        │ 100        │ 2       │ iPhone       │  ← product_name 只依赖 product_id
└──────────┴────────────┴─────────┴──────────────┘

✅ 满足 2NF：
OrderItem 表：order_id, product_id, quantity
Product 表：product_id, product_name
```

### 第三范式（3NF）

**在满足 2NF 的基础上，非主键字段不能传递依赖于主键。**

```
❌ 违反 3NF：
┌─────────┬──────────┬─────────────┐
│ user_id │ dept_id  │ dept_name   │
├─────────┼──────────┼─────────────┤
│ 1       │ 10       │ 研发部      │  ← dept_name 依赖 dept_id，dept_id 依赖 user_id
└─────────┴──────────┴─────────────┘

✅ 满足 3NF：
User 表：user_id, dept_id
Department 表：dept_id, dept_name
```

### 反范式化权衡

范式化减少冗余，但会增加关联查询。在读多写少的场景中，适当的反范式化可以提升查询性能：

```
范式化（3NF）：
  优点：数据无冗余，更新一致
  缺点：查询需要 JOIN，性能差

反范式化：
  优点：查询快，无需 JOIN
  缺点：数据冗余，更新需要同步多处

示例：订单表中冗余商品名称
  - 范式化：查订单详情需要 JOIN 商品表
  - 反范式化：订单表直接存 product_name，查询快但商品改名需要同步
```

反范式化的常见场景：商品快照（下单时的价格和名称）、统计计数（文章评论数）、搜索冗余字段。

## 索引设计

### B+ 树索引

B+ 树是关系数据库最常用的索引结构：

```
              [30 | 60]                    ← 根节点
             /    |    \
      [10|20]  [40|50]  [70|80]           ← 内部节点
      /  |  \  /  |  \  /  |  \
    [10][20][30][40][50][60][70][80]       ← 叶子节点（有序链表）
```

B+ 树的特点：
- 叶子节点存储实际数据指针，且通过链表连接，支持范围查询
- 树的高度通常 3~4 层，亿级数据只需 3~4 次磁盘 IO
- 适合等值查询和范围查询

### 索引类型

| 类型 | 说明 | 适用场景 |
|------|------|----------|
| 主键索引 | 唯一且非空 | 数据行定位 |
| 唯一索引 | 值唯一 | 邮箱、手机号 |
| 普通索引 | 无约束 | 加速查询 |
| 复合索引 | 多列组合 | 多条件查询 |
| 覆盖索引 | 查询列全在索引中 | 避免回表 |
| 前缀索引 | 字符串前 N 个字符 | 长字符串列 |

### 复合索引与最左前缀

复合索引遵循最左前缀原则：

```sql
-- 创建复合索引
CREATE INDEX idx_status_created ON orders(status, created_at);

-- ✅ 能使用索引：
SELECT * FROM orders WHERE status = 'paid';
SELECT * FROM orders WHERE status = 'paid' AND created_at > '2024-01-01';

-- ❌ 不能使用索引：
SELECT * FROM orders WHERE created_at > '2024-01-01';
-- 跳过了最左列 status，索引失效
```

### 索引失效场景

以下情况即使有索引也不会使用：

```sql
-- 1. 对索引列使用函数
SELECT * FROM users WHERE YEAR(created_at) = 2024;
-- 改为：WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'

-- 2. 隐式类型转换
SELECT * FROM users WHERE phone = 13800138000;
-- phone 是 varchar，数字比较导致索引失效
-- 改为：WHERE phone = '13800138000'

-- 3. LIKE 左模糊
SELECT * FROM users WHERE name LIKE '%张';
-- 改为前缀匹配：WHERE name LIKE '张%'

-- 4. OR 条件中有非索引列
SELECT * FROM users WHERE indexed_col = 1 OR non_indexed_col = 2;
-- non_indexed_col 没有索引，导致全表扫描
```

## 数据类型选择

选择合适的数据类型直接影响存储效率和查询性能：

| 场景 | 推荐类型 | 不推荐 | 原因 |
|------|----------|--------|------|
| 主键 | BIGINT | UUID/字符串 | 整数比较快，占用空间小 |
| 金额 | DECIMAL(10,2) | FLOAT/DOUBLE | 浮点数有精度问题 |
| 手机号 | VARCHAR(20) | BIGINT | 可能有前导 0，且不需要计算 |
| 时间 | DATETIME/TIMESTAMP | 字符串 | 支持时间函数和范围查询 |
| 短文本 | VARCHAR(n) | TEXT | TEXT 不能有默认值，查询效率低 |
| 布尔 | TINYINT(1) | VARCHAR | 存储空间小 |

## 分表策略

当单表数据量超过千万级时，需要考虑分表：

### 垂直分表

将一张宽表按列拆分为多张表：

```
原始表 users（30 列）：
  ↓ 拆分
users_base（id, username, email）        ← 高频访问
users_profile（id, avatar, bio, address） ← 低频访问
```

适用场景：表字段太多，部分字段访问频率低。

### 水平分表

将一张大表按行拆分到多张表：

```
原始表 orders（1 亿行）：
  ↓ 按 user_id % 8 分片
orders_0  user_id % 8 = 0
orders_1  user_id % 8 = 1
...
orders_7  user_id % 8 = 7
```

分片键选择原则：
- 选择查询频率最高的字段
- 数据分布要均匀
- 避免跨分片查询

## 常见误区

1. **过度范式化**：为了满足 3NF，把所有关联都拆成独立表，导致查询需要大量 JOIN。在读多写少的场景中，适当的冗余是合理的。
2. **滥用索引**：索引不是越多越好。每个索引都会占用存储空间，且降低写入速度。只为真正需要加速的查询创建索引。
3. **忽略数据类型**：用 VARCHAR 存储金额、用字符串存储日期，会导致查询效率低且容易出错。
4. **过早分表**：单表千万级数据在合理索引下仍然可以有良好的查询性能。过早分表增加系统复杂度。
5. **分片键选择不当**：按时间分片导致热点数据集中在最后一个分片，按随机值分片导致范围查询需要扫描所有分片。
6. **外键约束过多**：在高并发系统中，过多的外键约束会影响写入性能。可以在应用层保证数据一致性，数据库层面不建外键。
7. **忽略字符集和排序规则**：不同字符集（utf8 vs utf8mb4）在存储 emoji 等 4 字节字符时会出错。建议统一使用 utf8mb4 + utf8mb4_unicode_ci。

## 工程建议

1. **先范式化，再按需反范式化**：初始设计遵循 3NF，在性能瓶颈出现时有针对性地冗余。
2. **为查询设计索引**：先分析业务中的高频查询，再设计对应的索引。不要盲目创建索引。
3. **使用 EXPLAIN 验证**：创建索引后，用 `EXPLAIN` 查看查询计划，确认索引是否生效。
4. **主键用自增 BIGINT**：除非有特殊需求，否则不要用 UUID 作为主键。UUID 无序会导致 B+ 树页分裂，影响写入性能。
5. **监控慢查询**：开启慢查询日志，定期分析并优化。单条查询超过 100ms 就需要关注。
6. **预留扩展字段**：表设计时可以预留几个 JSON 类型的扩展字段（如 `extra_info`），应对未来不确定的需求变更，避免频繁 DDL。
7. **软删除代替硬删除**：重要数据使用 `is_deleted` 标记而非物理删除，便于数据恢复和审计。配合定期归档策略清理历史数据。

## 小结

本课介绍了数据建模的核心知识：

- ER 图是数据建模的基础工具，识别实体、关系和属性
- 三大范式减少数据冗余，但实际项目中需要权衡查询性能做反范式化
- 索引是查询性能的关键，B+ 树是最常用的索引结构
- 复合索引遵循最左前缀原则，注意索引失效的常见场景
- 数据类型选择影响存储效率和查询准确性
- 分表策略在数据量大时使用，垂直分表拆列、水平分表拆行

## 参考答案

### 练习一

**思路**：识别实体和关系，注意多对多关系需要中间表。

**答案**：

```
Student(N:M)Course  → 通过 StudentCourse 中间表关联
Course(1:N)Chapter  → Chapter 持有 course_id 外键
Chapter(1:N)Video   → Video 持有 chapter_id 外键
Student(1:N)StudyProgress → 记录到视频粒度，student_id + video_id 联合主键
```

**要点**：学习进度记录到视频粒度而非课程粒度，可以精确追踪每个视频的观看情况。

### 练习二

**思路**：根据查询条件设计索引，考虑最左前缀原则。

**答案**：

```sql
CREATE UNIQUE INDEX idx_email ON users(email);                    -- 唯一索引
CREATE INDEX idx_status_created ON users(status, created_at);     -- 复合索引
CREATE INDEX idx_city_created ON users(city, created_at);         -- 复合索引
```

**要点**：唯一索引保证唯一性和查询性能；复合索引利用最左前缀原则，等值条件在前、范围/排序条件在后；第三个索引让 MySQL 在索引层面完成排序，避免 filesort。

### 练习三

**思路**：根据查询模式选择分片键和分片策略。

**答案**：

- 分片键：user_id，分片策略：user_id % 16
- 订单号嵌入分片信息（如雪花算法），避免跨分片查询
- 按时间范围的统计报表同步到数据仓库用 OLAP 引擎处理

**要点**：选择 user_id 作为分片键是因为最常见的查询模式是按用户查订单。每张表预估数据量：5 亿 / 16 ≈ 3125 万/年。
