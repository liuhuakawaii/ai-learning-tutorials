# 需求分析与估算

## 一个真实的翻车案例

2019 年，某团队接到一个"设计内部工单系统"的需求。团队花了两周设计了一套基于 Kafka + Elasticsearch + 微服务的架构，支持百万级工单、全文检索、实时统计大屏。上线后发现：日均工单量不到 200 条，用户只有 30 人，全文检索功能从没人用过。

问题出在第一步——没有人问清楚"这个系统到底要支撑多大规模"。

需求分析和容量估算不是走形式。它们决定了你用单机还是分布式、用 PostgreSQL 还是分库分表、用本地缓存还是 Redis 集群。算错一个数量级，架构可能完全走偏。

## 功能需求和非功能需求是两回事

功能需求回答"系统做什么"，非功能需求回答"系统做得怎么样"。

以短链服务为例：

```
功能需求：
  - 输入长链接，生成短链接
  - 访问短链接，重定向到原始链接
  - 查看点击次数

非功能需求：
  - 重定向延迟 P99 < 50ms
  - 可用性 99.99%
  - 短码不可被猜测
```

非功能需求往往决定了架构的核心走向。功能需求决定你有哪些模块，非功能需求决定这些模块怎么设计。

很多项目翻车，不是功能做不出来，而是非功能需求没对齐——你以为要支持千万用户，实际上只有几百人；你以为可以接受最终一致性，结果业务要求强一致。

## 容量估算是建立直觉，不是精确计算

容量估算的目的是建立数量级的直觉：这个系统是千级、万级还是亿级？不需要精确到个位数。

核心公式：

```
QPS = 总请求数 / 时间窗口（秒）
峰值 QPS ≈ 平均 QPS × 3~5
存储 = 每条记录大小 × 每天新增记录数 × 保留天数
带宽 = QPS × 每次响应大小
```

一个实际估算的例子：

```
假设短链服务 DAU 1000 万，每人每天点击 10 次：
  平均 QPS = 1000 万 × 10 / 86400 ≈ 1157
  峰值 QPS = 1157 × 3 ≈ 3500

每条记录 500 字节，每天新增 1000 万条，保留 5 年：
  总存储 = 500B × 1000 万 × 365 × 5 ≈ 9.1 TB
```

记住一些常用数字能帮你快速建立直觉：

- 1 天 = 86400 秒
- 1 个月 ≈ 260 万秒
- 单机 MySQL 大约支撑 5000 QPS
- 单机 Redis 大约支撑 10 万 QPS

## DAU 和读写比直接影响架构

DAU 是容量规划的起点。推算路径：

```
注册用户 → DAU（转化率 10%~30%）
DAU → QPS（乘以人均请求次数）
QPS → 峰值 QPS（乘以 3~5）
峰值 QPS → 服务器数量（除以单机承载能力）
```

读写比决定架构方向：

```
读多写少（10:1）→ 加缓存、读写分离
读写均衡（1:1）→ 兼顾读写性能
写多读少（1:10）→ 高写入吞吐、批量写入
```

社交信息流是典型的读多写少（500:1），日志收集是典型的写多读少。选错方向会导致架构先天不足。

## SLA、SLO、SLI 不是同义词

这三个概念经常被混用：

- **SLI**：实际度量值。例如 P99 延迟 = 200ms，错误率 = 0.1%
- **SLO**：内部目标。例如 P99 ≤ 300ms，可用性 ≥ 99.9%
- **SLA**：对外承诺的合同，包含违反后果（如赔偿）

```
SLI（实际度量）→ SLO（内部目标）→ SLA（对外承诺）
P99 = 200ms      P99 ≤ 300ms       P99 ≤ 500ms
错误率 = 0.05%   错误率 ≤ 0.1%     错误率 ≤ 1%
                                      └─ 违反赔偿 10% 月费
```

设计系统时，SLA 是底线，SLO 是目标，SLI 是监控。

## 常见的翻车模式

**拿到需求就画架构图**：不问清楚需求就设计，等于闭着眼开车。花 5 分钟确认需求，比花 30 分钟设计一个错误的系统有价值得多。

**用注册用户做容量规划**：注册用户数通常远大于 DAU。转化率通常只有 10%~30%。用注册用户做规划会导致资源严重浪费。

**忽视峰值**：用平均 QPS 设计系统，上线后遇到峰值直接崩溃。永远用峰值来设计。

**估算过度精确**：花 20 分钟精确到个位数没有意义。数量级正确就够了。

## 练习

### 练习一：容量估算

一个类似 Instagram 的图片平台，预计 DAU 5000 万。每用户每天上传 2 张图片、浏览 50 张详情页。每张图片元数据约 1KB。请估算：

1. 平均 QPS 和峰值 QPS
2. 每天新增元数据存储量（保留 3 年）

### 练习二：需求分析

你需要设计一个在线协作文档系统（类似 Google Docs）。请列出：
1. 3 个核心功能需求
2. 3 个关键非功能需求
3. 这些非功能需求如何影响架构选择？

### 练习三：写一个容量估算函数

编写一个 TypeScript 函数，输入 DAU、人均请求次数、峰值系数，输出平均 QPS 和峰值 QPS。用 Vitest 写测试覆盖正常值、边界值（DAU=0）、大数值（DAU=10亿）。

## 参考答案

### 练习一

```
上传 QPS：5000 万 × 2 / 86400 ≈ 1157，峰值 ≈ 3500
浏览 QPS：5000 万 × 50 / 86400 ≈ 28935，峰值 ≈ 87000
总峰值 QPS ≈ 90000

每天新增元数据：5000 万 × 2 × 1KB = 100GB
3 年总存储：100GB × 365 × 3 ≈ 109.5 TB
```

图片本身的存储（几 MB 一张）远大于元数据，实际需要单独考虑对象存储。

### 练习二

核心功能：多人实时编辑、版本历史回滚、权限管理。

非功能需求：实时性（编辑延迟 < 100ms）、可用性 99.99%、最终一致性。

架构影响：实时性 → WebSocket + OT/CRDT 算法；高可用 → 多副本跨地域；最终一致性 → 乐观锁 + 冲突解决。

### 练习三

```typescript
function estimateQPS(dau: number, requestsPerUser: number, peakFactor: number = 3) {
  if (dau < 0 || requestsPerUser < 0) throw new Error('输入不能为负数')
  if (dau === 0) return { avgQPS: 0, peakQPS: 0 }
  const avgQPS = Math.ceil((dau * requestsPerUser) / 86400)
  const peakQPS = Math.ceil(avgQPS * peakFactor)
  return { avgQPS, peakQPS }
}
```

```typescript
describe('estimateQPS', () => {
  test('DAU 1000 万，人均 10 次', () => {
    const { avgQPS, peakQPS } = estimateQPS(10_000_000, 10)
    expect(avgQPS).toBe(1158)
    expect(peakQPS).toBe(3474)
  })
  test('DAU 为 0', () => {
    expect(estimateQPS(0, 10)).toEqual({ avgQPS: 0, peakQPS: 0 })
  })
  test('DAU 10 亿', () => {
    const { avgQPS } = estimateQPS(1_000_000_000, 5)
    expect(avgQPS).toBeGreaterThan(50000)
  })
  test('负数输入抛出异常', () => {
    expect(() => estimateQPS(-1, 10)).toThrow()
  })
})
```
