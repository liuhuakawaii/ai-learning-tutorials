# 需求分析与估算

## 场景引入

假设你接到一个任务："设计一个类似微博的社交系统"。你可能第一时间想到的是用什么数据库、要不要上消息队列、微服务怎么拆——但在动手画架构图之前，有一件更重要的事：**搞清楚到底要设计什么**。

很多系统设计面试或实际项目失败，不是因为技术选型错误，而是因为需求理解偏差。你花了一个小时设计了一个支持十亿用户的系统，结果面试官只需要一个内部工具级别的方案。或者你在项目初期就上了分布式架构，最后发现日活只有几百人。

需求分析与容量估算是系统设计的**第一步**，也是最容易被忽略的一步。本节课教你如何在动手设计之前，把问题问清楚、把数字算明白。

## 学习目标

- 掌握功能需求与非功能需求的分析方法，学会用结构化方式拆解需求
- 理解容量估算的核心指标（QPS、存储、带宽），能独立完成粗略估算
- 掌握 DAU/MAU 的计算方式及其在容量规划中的作用
- 理解读写比对架构设计的影响
- 掌握 SLA/SLO/SLI 三个概念的区别与实际应用

## 需求分析流程

在系统设计中，需求分析不是随便聊聊，而是一个有结构的过程：

```

├─────────────────────────────────────────────────────┤
│                                                     │

│     ┌───────────┐                                   │

│     └───────────┘                                   │
│           │                                         │
│           ▼                                         │
│  2. 功能需求拆解                                     │
│     ┌───────────┐                                   │
│     │ 核心功能   │──→ 用户能做什么？                   │
│     │ 边界功能   │──→ 哪些功能不做？                   │
│     └───────────┘                                   │
│           │                                         │
│           ▼                                         │
│  3. 非功能需求                                       │
│     ┌───────────┐                                   │
```

## 功能需求 vs 非功能需求

**功能需求**描述系统"做什么"——用户可以执行的具体操作。**非功能需求**描述系统"做得怎么样"——性能、可用性、安全性等质量属性。

以设计一个短链服务为例：

| 类型 | 示例 |
|------|------|
| 功能需求 | 用户输入长链接，生成短链接；访问短链接时重定向到原始链接；查看链接点击次数 |
| 非功能需求 | 重定向延迟 < 100ms；系统可用性 99.99%；短码不能被猜测 |

在实际项目中，非功能需求往往决定了架构的核心走向。功能需求决定了你有哪些模块，非功能需求决定了这些模块怎么设计。

## 容量估算方法

容量估算是一个"先假设、再验证"的过程。核心公式很简单，关键是建立直觉。

### QPS 估算

```
QPS = 总请求数 / 时间窗口（秒）

示例：
- 日活用户 1000 万
- 每个用户每天平均发送 10 次请求
- 日总请求 = 1000 万 × 10 = 1 亿
- 平均 QPS = 1 亿 / 86400 ≈ 1157

峰值 QPS（经验公式）：
- 峰值 QPS ≈ 平均 QPS × 3~5
- 1157 × 3 ≈ 3500 QPS
```

### 存储估算

```
存储 = 每条记录大小 × 每天新增记录数 × 保留天数

示例（短链服务）：
- 每条记录 ≈ 500 字节（短码 + 长链接 + 时间戳 + 统计字段）
- 每天新增 1000 万条
- 保留 5 年
- 总存储 = 500B × 1000 万 × 365 × 5 ≈ 9.1 TB
```

### 带宽估算

```
带宽 = QPS × 每次请求的平均响应大小

示例：
- QPS = 3500
- 每次响应平均 1 KB
- 带宽 = 3500 × 1KB = 3.5 MB/s ≈ 28 Mbps
```

## DAU/MAU 与读写比

### DAU/MAU

- **DAU**（Daily Active Users）：日活跃用户数
- **MAU**（Monthly Active Users）：月活跃用户数
- **DAU/MAU 比率**：衡量用户粘性，比值越高说明用户越活跃

在容量估算中，DAU 是关键输入。通常用以下方式推算：

```
注册用户 → DAU（转化率通常 10%~30%）
DAU → QPS（乘以人均请求次数）
QPS → 峰值 QPS（乘以峰值系数 3~5）
峰值 QPS → 服务器数量（除以单机承载能力）
```

### 读写比

读写比直接影响架构设计：

| 读写比 | 典型场景 | 架构影响 |
|--------|----------|----------|
| 读多写少（10:1） | 社交媒体信息流、电商商品页 | 适合加缓存、读写分离 |
| 读写均衡（1:1） | 即时通讯 | 需要兼顾读写性能 |
| 写多读少（1:10） | 日志收集、IoT 数据上报 | 需要高写入吞吐，考虑批量写入 |

## SLA/SLO/SLI

这三个概念经常被混用，但含义不同：

- **SLI**（Service Level Indicator）：服务等级指标，是具体的度量值。例如：请求延迟 P99 = 200ms，错误率 = 0.1%。
- **SLO**（Service Level Objective）：服务等级目标，是 SLI 的目标值。例如：P99 延迟 ≤ 300ms，可用性 ≥ 99.9%。
- **SLA**（Service Level Agreement）：服务等级协议，是对外承诺的合同，包含违反 SLO 的后果（如赔偿）。

```
SLI（实际度量）──→ SLO（内部目标）──→ SLA（对外承诺）
   │                    │                    │
   │ P99 = 200ms       │ P99 ≤ 300ms       │ P99 ≤ 500ms
   │ 错误率 = 0.05%    │ 错误率 ≤ 0.1%     │ 错误率 ≤ 1%
   │                    │                    │
   │                    │                    └─ 违反赔偿 10% 月费
```

在实际设计中，SLA 是底线，SLO 是目标，SLI 是监控。你设计的系统要满足 SLO，并在监控中持续追踪 SLI。

## 需求优先级矩阵

当需求很多时，用优先级矩阵排序：

```
         紧急
          ▲
          │
    ┌─────┼─────┐
    │  ② │  ①  │
    │紧急 │紧急且│
    │不重 │重要  │
    │要   │     │
重要├─────┼─────┤不重要
    │  ④ │  ③  │
    │不紧 │重要  │
    │急也 │不紧  │
    │不重 │急   │
    │要   │     │
    └─────┼─────┘
          │
          ▼
        不紧急
```

- **① 紧急且重要**：核心功能、阻塞性问题
- **② 紧急不重要**：临时需求、紧急修复
- **③ 重要不紧急**：性能优化、架构改进
- **④ 不紧急不重要**：锦上添花的功能

## 常见误区

1. **一上来就画架构图**：不问清楚需求就设计，等于闭着眼开车。先确认"设计什么"，再考虑"怎么设计"。
2. **忽略非功能需求**：只关注功能列表，不讨论性能、可用性、一致性，会导致架构无法满足实际要求。
3. **估算过于精确**：容量估算是粗略计算，目的是建立数量级的直觉。花 20 分钟精确到个位数没有意义。
4. **忽视峰值**：用平均 QPS 设计系统，上线后遇到峰值直接崩溃。永远用峰值（通常 3~5 倍平均值）来设计。
5. **不做优先级排序**：试图一次性满足所有需求，结果什么都做不好。先做核心功能，再迭代扩展。
6. **把注册用户当 DAU**：注册用户数通常远大于 DAU，用注册用户做容量规划会导致资源严重浪费。注册到 DAU 的转化率通常只有 10%~30%。
7. **忽视长尾效应**：热点数据的访问分布往往符合二八定律——20% 的数据承载 80% 的流量。设计时要考虑热点打散和差异化缓存策略。

## 工程建议

1. **先问再画**：系统设计面试或实际项目中，花 5~10 分钟确认需求，比花 30 分钟设计一个错误的系统有价值得多。
2. **建立数量级直觉**：记住一些常用数字——1 天 86400 秒、1 个月约 260 万秒、单机 MySQL 大约支撑 5000 QPS、单机 Redis 大约支撑 10 万 QPS。
3. **用具体数字沟通**：不要说"系统要快"，要说"P99 延迟 < 200ms"；不要说"支持大量用户"，要说"DAU 1000 万"。
4. **区分硬需求和软需求**：硬需求是必须满足的（如数据不能丢失），软需求是可以妥协的（如延迟可以从 100ms 放宽到 300ms）。
5. **定期回顾估算**：随着业务发展，容量估算需要更新。建议每季度重新评估一次。
6. **记录估算假设**：每次估算时明确记录假设条件（如 DAU、读写比、峰值系数），方便后续回溯和修正。
7. **预留余量**：容量规划时建议预留 30%~50% 的余量，应对突发流量和业务增长。系统利用率超过 70% 就应该考虑扩容。

## 小结

本课介绍了系统设计的第一步——需求分析与容量估算。核心要点：

- 需求分为功能需求（做什么）和非功能需求（做得怎么样），两者缺一不可
- 容量估算的核心指标是 QPS、存储、带宽，关键是建立数量级直觉
- DAU/MAU 是容量规划的起点，读写比直接影响架构选型
- SLI 是度量、SLO 是目标、SLA 是承诺，三者层层递进
- 用优先级矩阵对需求排序，先做最重要的事

## 练习

### 练习一：估算 QPS 和存储

一个类似 Instagram 的图片分享平台，预计 DAU 为 5000 万。每个用户每天平均上传 2 张图片，浏览 50 张图片的详情页。每张图片元数据（不含图片本身）约 1KB。请估算：
1. 平均 QPS 和峰值 QPS
2. 每天新增的元数据存储量（保留 3 年）

### 练习二：需求分析

你需要设计一个在线协作文档系统（类似 Google Docs）。请列出：
1. 3 个核心功能需求
2. 3 个关键非功能需求
3. 这些非功能需求会如何影响架构选择？

### 练习三：读写比分析

一个实时评论系统（类似 B 站弹幕），用户在观看视频时可以发送弹幕，弹幕会实时显示在所有观看同一视频的用户的屏幕上。请分析：
1. 这个系统的读写比大概是多少？
2. 峰值场景是什么（如热门视频直播）？
3. 这种读写模式对架构有什么要求？

## 参考答案

### 练习一

**思路**：从 DAU 出发，分别计算上传和浏览的 QPS，再推算存储。

**答案**：

1. QPS 估算：
   - 上传 QPS：5000 万 × 2 / 86400 ≈ 1157，峰值 ≈ 3500
   - 浏览 QPS：5000 万 × 50 / 86400 ≈ 28935，峰值 ≈ 87000
   - 总平均 QPS ≈ 30092，总峰值 QPS ≈ 90000

2. 存储估算：
   - 每天新增元数据：5000 万 × 2 × 1KB = 100GB
   - 3 年总存储：100GB × 365 × 3 ≈ 109.5 TB

**要点**：图片本身的存储（通常几 MB 一张）远大于元数据，实际设计中需要单独考虑图片存储（如对象存储）。

### 练习二

**思路**：从用户体验和业务场景出发，识别最关键的需求。

**答案**：

1. 核心功能需求：
   - 多人实时编辑同一文档，支持光标位置同步
   - 文档版本历史，支持回滚到任意版本
   - 权限管理（查看/编辑/管理）

2. 关键非功能需求：
   - 实时性：编辑操作延迟 < 100ms，多人协作时无感知冲突
   - 可用性：99.99%，文档不能丢失
   - 一致性：多人同时编辑时最终一致，不能出现内容丢失

3. 架构影响：
   - 实时性要求 → WebSocket 长连接，OT 或 CRDT 算法处理并发冲突
   - 高可用 → 多副本存储，跨地域部署
   - 最终一致性 → 乐观锁 + 冲突解决策略，而非强一致的分布式锁

**要点**：Google Docs 的核心难点在于多人实时编辑的冲突解决，这是 OT（Operational Transformation）或 CRDT（Conflict-free Replicated Data Type）算法的典型应用场景。

### 练习三

**思路**：弹幕系统的特点是大量用户同时读写，且写操作需要实时广播。

**答案**：

1. 读写比：
   - 每条弹幕需要广播给所有观看同一视频的用户
   - 假设一个热门直播间有 10 万人观看，每秒 1000 条弹幕
   - 写：1000 QPS，读：1000 × 10 万 = 1 亿 QPS（广播）
   - 读写比约 10 万:1，读远大于写

2. 峰值场景：
   - 热门事件直播（如春晚、电竞决赛）
   - 瞬时弹幕量可达每秒数万条
   - 观看人数可达百万级别

3. 架构要求：
   - 高写入吞吐：消息队列缓冲弹幕
   - 高读取吞吐：WebSocket 推送 + 本地缓存
   - 实时性：端到端延迟 < 500ms
   - 分区策略：按视频 ID 分区，同一视频的弹幕在同一分区处理

**要点**：弹幕系统的核心挑战不是存储，而是实时广播。10 万人同时在线观看，每条弹幕都要推送给所有人，这对消息推送系统的吞吐量要求极高。
