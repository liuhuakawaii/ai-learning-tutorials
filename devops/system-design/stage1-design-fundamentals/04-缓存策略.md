# 缓存策略

## 场景引入

你的电商系统上线了，数据库用的是 MySQL。一开始系统运行良好，但随着用户量增长，商品详情页的响应时间从 50ms 飙升到 2 秒。DBA 看了慢查询日志，发现 90% 的查询都是在反复读取同样的热门商品数据。

你决定加一个 Redis 缓存。上线后效果立竿见影，响应时间降到了 5ms。但三天后的凌晨，Redis 节点宕机，所有请求直接打到数据库，数据库连接池瞬间被打满，整个系统雪崩。

缓存是提升系统性能最有效的手段之一，但用不好会带来比没有缓存更严重的问题。本节课系统讲解缓存的三大经典问题（穿透、击穿、雪崩）及其解决方案，以及缓存与数据库的一致性保证。

## 学习目标

- 理解缓存穿透、击穿、雪崩的成因和区别
- 掌握布隆过滤器、互斥锁、随机过期等解决方案
- 了解 Redis 数据结构选型和 CDN 缓存策略
- 理解缓存与数据库的一致性模式（旁路缓存、读写穿透）
- 能根据业务场景设计合适的多级缓存架构

## 多级缓存架构

```
┌─────────────────────────────────────────────────────────────┐
│                      多级缓存架构                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  用户请求                                                    │
│     │                                                       │
│     ▼                                                       │
│  ┌─────────┐   命中                                       │
│  │ CDN缓存 │────────→ 返回静态资源                          │
│  └────┬────┘                                               │
│       │ 未命中                                              │
│       ▼                                                     │
│  ┌─────────┐   命中                                       │
│  │本地缓存 │────────→ 返回结果（进程内，最快）              │
│  │(Caffeine)│                                               │
│  └────┬────┘                                               │
│       │ 未命中                                              │
│       ▼                                                     │
│  ┌─────────┐   命中                                       │
│  │ Redis   │────────→ 返回结果（分布式共享缓存）            │
│  └────┬────┘                                               │
│       │ 未命中                                              │
│       ▼                                                     │
│  ┌─────────┐                                               │
│  │ 数据库   │──→ 查询结果 ──→ 写入 Redis ──→ 返回          │
│  └─────────┘                                               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

每层缓存的特点：

| 层级 | 速度 | 容量 | 适用场景 |
|------|------|------|----------|
| CDN | 最快（就近访问） | 大 | 静态资源、不常变的 API |
| 本地缓存 | 极快（无网络 IO） | 小（受内存限制） | 热点数据、配置信息 |
| Redis | 快（内存读写） | 中 | 共享缓存、会话数据 |
| 数据库 | 慢（磁盘 IO） | 大 | 持久化存储 |

## 缓存穿透

**问题**：查询一个根本不存在的数据，缓存和数据库都查不到，每次请求都穿透到数据库。

```
恶意请求：GET /products/99999999  （不存在的商品）

用户请求 → 缓存未命中 → 数据库未命中 → 返回空
用户请求 → 缓存未命中 → 数据库未命中 → 返回空
... 每次都打到数据库
```

### 解决方案一：布隆过滤器

```
┌─────────────────────────────────────────┐
│              布隆过滤器                    │
├─────────────────────────────────────────┤
│                                         │
│  请求 → 布隆过滤器判断 → 不存在 → 直接返回│
│              │                          │
│              │ 可能存在                  │
│              ▼                          │
│          查询缓存/数据库                  │
│                                         │
│  特点：                                  │
│  - 说不存在，一定不存在                   │
│  - 说存在，可能存在（误判率 1%~5%）       │
│  - 不支持删除                            │
│  - 空间效率极高                          │
└─────────────────────────────────────────┘
```

在系统启动时将所有合法 ID 加载到布隆过滤器中。请求先过布隆过滤器，如果判定不存在，直接返回，不再查询数据库。

### 解决方案二：空值缓存

```python
def get_product(product_id):
    # 先查缓存
    cached = redis.get(f"product:{product_id}")
    if cached is not None:
        return None if cached == "NULL" else cached
    
    # 查数据库
    product = db.query(product_id)
    if product is None:
        # 缓存空值，设置较短过期时间
        redis.setex(f"product:{product_id}", 300, "NULL")
        return None
    
    redis.setex(f"product:{product_id}", 3600, product)
    return product
```

空值缓存简单有效，但如果有大量不同的不存在 ID，会占用较多缓存空间。可以配合布隆过滤器使用。

## 缓存击穿

**问题**：某个热点 key 在过期的瞬间，大量并发请求同时打到数据库。

```
时间线：
  T1: 热点 key "product:123" 过期
  T2: 1000 个并发请求同时发现缓存未命中
  T3: 1000 个请求同时查询数据库
  T4: 数据库压力骤增，可能崩溃
```

### 解决方案一：互斥锁

```python
def get_product_with_lock(product_id):
    cached = redis.get(f"product:{product_id}")
    if cached:
        return cached
    
    # 尝试获取分布式锁
    lock_key = f"lock:product:{product_id}"
    if redis.set(lock_key, 1, nx=True, ex=10):
        try:
            product = db.query(product_id)
            redis.setex(f"product:{product_id}", 3600, product)
            return product
        finally:
            redis.delete(lock_key)
    else:
        # 未获取到锁，等待后重试
        time.sleep(0.1)
        return get_product_with_lock(product_id)
```

互斥锁保证同一时刻只有一个请求去数据库加载数据，其他请求等待。

### 解决方案二：逻辑过期

```python
def get_product_logical_expire(product_id):
    cached = redis.get(f"product:{product_id}")
    if cached is None:
        return None
    
    data = json.loads(cached)
    if data["expire_time"] > time.time():
        return data["value"]
    
    # 已逻辑过期，异步刷新
    if redis.set(f"lock:product:{product_id}", 1, nx=True, ex=10):
        # 获取到锁，异步更新
        threading.Thread(target=refresh_product, args=(product_id,)).start()
    
    # 返回旧数据（不阻塞）
    return data["value"]
```

逻辑过期不设置真实的 TTL，而是在数据中记录过期时间。读取时判断是否逻辑过期，过期则异步刷新，返回旧数据。优点是不阻塞请求，缺点是可能短暂返回旧数据。

## 缓存雪崩

**问题**：大量缓存 key 在同一时间过期，或 Redis 节点宕机，导致请求全部打到数据库。

### 解决方案

```
┌─────────────────────────────────────────────────┐
│             缓存雪崩解决方案                       │
├─────────────────────────────────────────────────┤
│                                                 │
│  1. 随机过期时间                                  │
│     TTL = base_ttl + random(0, 300)             │
│     避免大量 key 同时过期                         │
│                                                 │
│  2. 多级缓存                                      │
│     本地缓存（Caffeine）+ Redis                   │
│     Redis 挂了还有本地缓存兜底                    │
│                                                 │
│  3. 熔断降级                                      │
│     检测到数据库压力过大时                         │
│     直接返回默认值或错误页面                       │
│                                                 │
│  4. Redis 高可用                                  │
│     Redis Sentinel 或 Redis Cluster              │
│     主从切换，避免单点故障                         │
│                                                 │
└─────────────────────────────────────────────────┘
```

## Redis 数据结构选型

| 数据结构 | 适用场景 | 示例 |
|----------|----------|------|
| String | 简单 KV 缓存 | 用户信息、商品详情 |
| Hash | 对象的多个字段 | 用户的多个属性，可单独更新 |
| List | 有序列表 | 消息队列、最新动态 |
| Set | 无序集合 | 标签、共同好友 |
| ZSet | 有序集合 | 排行榜、延迟队列 |
| Bitmap | 布尔型统计 | 用户签到、在线状态 |
| HyperLogLog | 基数统计 | UV 统计（误差 0.81%） |

选型原则：能用 String 就用 String，需要部分更新字段用 Hash，需要排序用 ZSet。

## CDN 缓存策略

CDN 将内容缓存到离用户最近的节点。适合缓存静态资源（图片、CSS、JS）、不常变的 API 响应和大文件下载。不适合个性化数据和实时性要求高的数据。

缓存控制通过 HTTP 头实现：

```
Cache-Control: public, max-age=3600          # 公共缓存 1 小时
Cache-Control: private, max-age=300          # 仅浏览器缓存 5 分钟
Cache-Control: no-cache                      # 每次验证缓存是否过期
ETag: "abc123"                               # 内容摘要，变化则重新获取
Last-Modified: Wed, 21 Oct 2024 07:28:00 GMT # 最后修改时间
Vary: Accept-Encoding                       # 按编码格式分别缓存
```

CDN 缓存失效策略：
- **主动刷新**：内容更新后，调用 CDN API 主动清除缓存
- **版本号哈希**：静态资源文件名加哈希（如 `app.a1b2c3.js`），更新后自动失效
- **短 TTL + 回源校验**：设置较短 TTL，配合 ETag 做回源校验，平衡实时性和回源压力

## 缓存与数据库一致性

### 旁路缓存（Cache-Aside）

最常见的模式，应用层同时管理缓存和数据库：

```
读操作：
  1. 读缓存 → 命中则返回
  2. 未命中 → 读数据库
  3. 写入缓存 → 返回

写操作：
  1. 更新数据库
  2. 删除缓存（而非更新缓存）
```

为什么删除缓存而不是更新缓存？
- 避免并发写导致缓存与数据库不一致
- 如果缓存值需要复杂计算，删除比更新更简单
- 下次读取时自然会重建缓存

### 延迟双删与读写穿透

延迟双删解决并发不一致：先删缓存 → 更新数据库 → sleep(0.5) → 再删缓存。

读写穿透模式中，缓存层统一代理数据库访问，应用只和缓存交互。优点是代码简单，缺点是缓存层复杂度高。

## 常见误区

1. **缓存一切**：不是所有数据都适合缓存。写多读少、强一致性要求的数据不适合缓存。
2. **只设一个过期时间**：大量 key 使用相同的 TTL，会导致同时过期引发雪崩。应该加随机偏移量。
3. **更新缓存而不是删除**：在并发场景下，更新缓存容易导致数据库和缓存不一致。删除缓存让下次读取重建是更安全的策略。
4. **忽略缓存预热**：系统刚启动时缓存为空，所有请求都会打到数据库。应该在启动时加载热点数据到缓存。
5. **Redis 宕机没有降级方案**：缓存不是银弹，必须有降级策略。Redis 不可用时，可以返回默认值、走数据库或返回错误页面。
6. **缓存与数据库操作顺序错误**：先更新数据库再删缓存是安全的顺序。如果先删缓存再更新数据库，并发读请求可能读到旧值并写入缓存，造成不一致。
7. **不做缓存预热**：系统重启或 Redis 故障恢复后，缓存为空，大量请求瞬间涌向数据库（冷启动问题）。应该用脚本批量加载热点数据。

## 工程建议

1. **缓存 key 命名规范**：使用 `业务:实体:ID` 格式，如 `product:detail:123`，便于管理和排查。
2. **设置合理的 TTL**：根据数据更新频率设置过期时间。频繁更新的数据 TTL 短，稳定数据 TTL 长。永远加随机偏移。
3. **监控缓存命中率**：命中率低于 80% 说明缓存策略有问题，可能是 key 设计不合理或 TTL 太短。
4. **热点 key 打散**：对于特别热的 key（如秒杀商品），可以加随机后缀分散到多个 key，避免单点压力。
5. **缓存降级预案**：提前准备降级策略，在缓存不可用时自动切换，避免连锁故障。
6. **批量操作优化**：使用 `MGET/MSET` 替代多次 `GET/SET`，减少网络往返。但单次批量不要超过 500 个 key，避免阻塞 Redis。
7. **监控关键指标**：监控缓存命中率、Redis 内存使用率、连接数、慢查询。命中率持续低于 80% 需要排查原因。

## 小结

本课系统讲解了缓存策略的核心知识：

- 缓存穿透用布隆过滤器或空值缓存解决
- 缓存击穿用互斥锁或逻辑过期解决
- 缓存雪崩用随机过期时间、多级缓存和熔断降级解决
- Redis 数据结构根据业务场景选择，String 是默认选择
- CDN 适合静态资源，不适合个性化数据
- 旁路缓存是最常用的一致性模式，写操作优先删除缓存

## 参考答案

### 练习一

**思路**：根据数据特征和访问模式选择合适的缓存策略。

**答案**：

| 场景 | 缓存层级 | TTL | 说明 |
|------|----------|-----|------|
| 首页新闻列表 | Redis + CDN | 60 秒 + 随机 10 秒 | 更新频率高，TTL 短；CDN 减少后端压力 |
| 新闻详情 | Redis + CDN | 24 小时 | 发布后基本不变，TTL 长 |
| 用户已读记录 | 本地缓存 + Redis | 30 分钟 | 用 Redis Bitmap 存储，每个 bit 代表一篇新闻 |

**要点**：首页列表虽然更新频繁，但可以接受 60 秒的延迟。

### 练习二

**思路**：布隆过滤器 + 空值缓存双重防护。

**答案**：

1000 万用户、误判率 1% 的布隆过滤器约 12 MB 内存。请求先过布隆过滤器，不存在则直接返回 404。可能存在则查 Redis，未命中则查数据库，数据库未命中则缓存空值（TTL 5 分钟）。

**要点**：两层防护确保数据库不被恶意请求打垮。

### 练习三

**思路**：根据读写比例和一致性要求选择方案。

**答案**：

1. **用户基本信息 → 旁路缓存 + 删除策略**：读多写少，更新时删除缓存，TTL 30 分钟
2. **商品库存 → 不缓存库存数值，缓存库存状态**：缓存"有货/无货"（变化频率低），实际扣减走数据库用乐观锁
3. **购物车 → Redis 作为主存储**：Redis Hash 存储，定期异步持久化到数据库

**要点**：不同场景需要不同的策略，关键是理解业务特点选择合适的平衡点。
