# 负载均衡

## 场景引入

你的 Web 应用上线了，一开始只部署在一台服务器上。随着用户增长，单台服务器已经无法承受高峰时段的请求量。你买了第二台服务器，但问题来了：怎么让请求均匀地分配到两台服务器上？

更复杂的是：两台服务器的配置不同（一台 8 核 16G，另一台 4 核 8G），某些用户的状态（如登录会话）需要保持在同一台服务器上，而且某台服务器可能会宕机，需要自动摘除。

负载均衡就是解决这些问题的核心组件。它是分布式系统的入口，决定了请求如何分配、故障如何处理、会话如何保持。本节课从 L4/L7 负载均衡的区别，到一致性哈希的实现，系统讲解负载均衡的原理和实践。

## 学习目标

- 理解 L4 和 L7 负载均衡的区别和适用场景
- 掌握常见负载均衡算法（轮询、加权、最少连接、IP 哈希）
- 理解一致性哈希的原理和虚拟节点的作用
- 了解健康检查机制和会话保持方案
- 能根据业务场景选择合适的负载均衡策略

## L4 负载均衡

L4（传输层）负载均衡工作在 TCP/UDP 层，只看 IP 地址和端口号，不解析应用层内容。

```
┌─────────────────────────────────────────────┐
│            L4 负载均衡 (LVS)                 │
├─────────────────────────────────────────────┤
│                                             │
│  客户端 ──→ LVS (VIP:80)                   │
│              │                              │
│              │ 修改目标 IP                   │
│              ▼                              │
│         Server1 (192.168.1.1:80)            │
│                                             │
│  特点：                                      │
│  - 工作在内核态，性能极高（百万级并发）        │
│  - 只转发，不解析内容                        │
│  - 支持 NAT、DR、TUN 三种模式               │
│  - 不能做 URL 路由、Header 修改              │
│                                             │
│  典型实现：                                  │
│  - LVS (Linux Virtual Server)               │
│  - AWS NLB (Network Load Balancer)          │
│                                             │
└─────────────────────────────────────────────┘
```

L4 适用场景：对性能要求极高的场景，如游戏服务器、数据库代理、大规模微服务内部通信。

## L7 负载均衡

L7（应用层）负载均衡能解析 HTTP 内容，根据 URL、Header、Cookie 等信息做路由决策。

```
┌─────────────────────────────────────────────┐
│            L7 负载均衡 (Nginx)               │
├─────────────────────────────────────────────┤
│                                             │
│  GET /api/users ──→ Nginx ──→ API Server    │
│  GET /static/js ──→ Nginx ──→ Static Server │
│  GET /ws/chat   ──→ Nginx ──→ WS Server    │
│                                             │
│  特点：                                      │
│  - 解析 HTTP 协议，支持复杂路由              │
│  - 可以做 SSL 终止、压缩、缓存              │
│  - 支持 URL 路径、Header、Cookie 路由       │
│  - 性能比 L4 低（需要解析应用层）            │
│                                             │
│  典型实现：                                  │
│  - Nginx / OpenResty                        │
│  - HAProxy                                  │
│  - AWS ALB (Application Load Balancer)      │
│                                             │
└─────────────────────────────────────────────┘
```

L7 适用场景：需要根据 URL 路径分流、需要 SSL 终止、需要灰度发布、需要内容缓存。

## L4 vs L7 对比

| 维度 | L4 | L7 |
|------|----|----|
| 工作层级 | 传输层（TCP/UDP） | 应用层（HTTP） |
| 路由依据 | IP + 端口 | URL、Header、Cookie |
| 性能 | 极高（百万并发） | 较高（万~十万并发） |
| SSL 终止 | 不支持 | 支持 |
| 内容缓存 | 不支持 | 支持 |
| 典型实现 | LVS、NLB | Nginx、ALB |
| 适用场景 | 高性能、简单转发 | 复杂路由、Web 应用 |

实际架构中常常组合使用：LVS 做第一层（高性能入口），Nginx 做第二层（智能路由）。

## 负载均衡算法

### 轮询（Round Robin）

```
请求 1 → Server A
请求 2 → Server B
请求 3 → Server C
请求 4 → Server A
...
```

最简单的算法，适合服务器配置相同的场景。

### 加权轮询（Weighted Round Robin）

```
Server A (weight=5): 5/10 的请求
Server B (weight=3): 3/10 的请求
Server C (weight=2): 2/10 的请求
```

适合服务器配置不同的场景，配置高的服务器分配更多请求。

### 最少连接（Least Connections）

```
Server A: 当前 10 个连接
Server B: 当前 5 个连接  ← 新请求分配到这里
Server C: 当前 8 个连接
```

将新请求分配给当前连接数最少的服务器，适合请求处理时间差异大的场景。

### IP 哈希（IP Hash）

```
hash(client_ip) % server_count = server_index

客户端 192.168.1.100 → hash → Server A（固定）
客户端 192.168.1.200 → hash → Server B（固定）
```

同一客户端的请求总是被分配到同一台服务器，可以实现简单的会话保持。但服务器增减时，大部分映射会变化。

## 一致性哈希

普通哈希的问题：当服务器数量变化时，几乎所有请求的映射都会变化，导致缓存大面积失效。

### 一致性哈希环

```
                    0
                    │
            ┌───────┼───────┐
            │       │       │
           NodeC    │     NodeA
            │       │       │
            │       │       │
            └───────┼───────┘
                    │
                   NodeB
                    │
               2^32 - 1

数据映射：
  Key1 → hash → 落在 NodeA 和 NodeB 之间 → 归 NodeB
  Key2 → hash → 落在 NodeB 和 NodeC 之间 → 归 NodeC
```

一致性哈希将整个哈希值空间组织成一个环（0 ~ 2^32-1），节点和数据都映射到环上。数据由顺时针方向遇到的第一个节点负责。

### 虚拟节点

问题：节点数量少时，数据分布不均匀。

```
不使用虚拟节点：
  NodeA 负责 60% 的数据
  NodeB 负责 30% 的数据
  NodeC 负责 10% 的数据   ← 严重不均

使用虚拟节点（每个真实节点 150 个虚拟节点）：
  NodeA 负责 33% 的数据
  NodeB 负责 34% 的数据
  NodeC 负责 33% 的数据   ← 均匀分布
```

虚拟节点是真实节点的副本，映射到环上的多个位置。通过增加虚拟节点数量，可以让数据分布更均匀。实际应用中，每个真实节点通常有 100~200 个虚拟节点。

一致性哈希的优势：当增加或删除一个节点时，只有该节点相邻区间的数据需要迁移，其他数据的映射不变。这使得扩缩容对系统的影响最小。

## 健康检查

负载均衡器定期检测后端服务器是否健康，自动摘除故障节点：

- **主动检查**：定期发送 `GET /health`，连续 3 次失败标记为不健康，连续 3 次成功恢复
- **被动检查**：通过实际请求的响应判断，连续 N 次超时/错误标记为不健康
- **检查参数**：间隔 5~10 秒，超时 3~5 秒，阈值连续 3 次
- 健康检查端点应轻量级，检查关键依赖（数据库、Redis），返回 200/503

## 会话保持

某些场景需要同一用户的请求被分配到同一台服务器：

1. **IP 哈希**：简单但不精确，NAT 环境下多个用户共享同一出口 IP，导致请求被分配到同一台服务器，造成负载不均。适合内部网络或小规模部署。
2. **Cookie 注入**：LB 在首次响应中注入 `SERVERID=A` Cookie，后续请求通过 Cookie 精确路由到 Server A。比 IP 哈希更精确，但 LB 需要解析和修改 HTTP 响应。
3. **共享会话存储（推荐）**：会话数据存 Redis，所有服务器共享，不依赖 LB 的绑定策略，服务器可自由扩缩容。这是微服务架构中的主流方案。
4. **Session Affinity 配置示例**：
   ```
   # Nginx ip_hash
   upstream backend { ip_hash; server 10.0.0.1; server 10.0.0.2; }
   
   # Nginx sticky cookie
   upstream backend { sticky cookie srv_id expires=1h; server 10.0.0.1; server 10.0.0.2; }
   ```

## 常见误区

1. **负载均衡等于高可用**：负载均衡器本身也可能成为单点故障。需要为主负载均衡器配置备用节点（如 Nginx + Keepalived）。
2. **只用一种算法**：不同业务场景需要不同的算法。Web 服务器用轮询，长连接服务用最少连接，需要会话保持用 IP 哈希或 Cookie。
3. **忽略健康检查**：没有健康检查，负载均衡器会把请求发到已经宕机的服务器，导致部分用户请求失败。
4. **会话保持过度依赖**：过度依赖会话保持会导致服务器负载不均。更好的方案是将状态外置到 Redis。
5. **一致性哈希万能**：一致性哈希适合缓存场景，但对无状态服务，简单的加权轮询就够了。
6. **忽略连接耗尽**：L7 负载均衡器有最大连接数限制，未配置连接超时会导致连接被长期占用。需设置合理的 `keepalive_timeout` 和最大连接数。
7. **DNS TTL 设置过长**：DNS 负载均衡时，TTL 过长会导致故障切换慢。建议 DNS TTL 设为 60~300 秒，配合健康检查快速切换。

## 工程建议

1. **分层负载均衡**：大规模系统使用 LVS/NLB 做入口，Nginx 做应用层路由，各司其职。
2. **配置健康检查**：所有后端服务必须配置健康检查，参数根据业务容忍度调整（通常 5 秒间隔，3 次阈值）。
3. **状态外置**：尽量让应用服务器无状态，将会话、缓存等状态数据存储在 Redis 等外部存储中。
4. **灰度发布**：利用 L7 负载均衡的能力，按 Header、Cookie 或比例将流量导向新版本服务器。
5. **监控与告警**：监控负载均衡器的 QPS、延迟、错误率、后端健康状态，异常时及时告警。
6. **优雅下线**：后端服务器发布时，先从负载均衡器摘除，等待存量请求处理完成（graceful shutdown）后再停止服务，避免请求中断。
7. **限流与降级**：在负载均衡层配置限流（如每 IP 每秒 100 次请求），超出直接返回 429。配合后端熔断，防止级联故障。

## 小结

本课系统讲解了负载均衡的原理和实践：

- L4 负载均衡工作在传输层，性能极高但功能简单
- L7 负载均衡工作在应用层，支持复杂路由但性能略低
- 常见算法有轮询、加权轮询、最少连接、IP 哈希，需根据场景选择
- 一致性哈希通过虚拟节点实现均匀分布，适合缓存场景
- 健康检查自动摘除故障节点，是高可用的基础
- 会话保持推荐使用共享会话存储（Redis），而非负载均衡层的绑定策略

1. 3 台配置相同的 Web 服务器
2. 1 台 8 核服务器和 2 台 4 核服务器
3. 在线游戏服务器，每个连接持续数小时

### 练习二：一致性哈希计算

一个分布式缓存系统有 3 个节点（A、B、C），哈希环上的位置分别是 100、200、300。请计算以下数据 key 应该存储在哪个节点：
1. key1 的哈希值为 150
2. key2 的哈希值为 250
3. key3 的哈希值为 50
4. 如果新增一个节点 D，位置为 250，哪些数据需要迁移？

一个系统使用 Nginx 做负载均衡，后端有 4 台应用服务器。请设计一个高可用方案，确保：
1. Nginx 本身不是单点故障
2. 后端服务器宕机时自动摘除
3. 支持滚动发布（逐台更新后端服务器）

## 参考答案

### 练习一

**思路**：根据服务器配置、连接特点和会话需求选择算法。

**答案**：

1. **配置相同的 Web 服务器 → 轮询**：实现简单，分配均匀
2. **混合配置服务器 → 加权轮询**：8 核权重 2，4 核权重 1
3. **在线游戏服务器 → 最少连接**：连接持续时间长，轮询会导致连接数不均
4. **需要会话保持 → IP 哈希或 Cookie 注入**：最佳方案是会话数据存 Redis，用轮询即可

### 练习二

**思路**：一致性哈希中，数据由顺时针方向遇到的第一个节点负责。

**答案**：

哈希环：0 ── 100(A) ── 200(B) ── 300(C) ── 2^32-1

1. key1(150) → B(200)，key2(250) → C(300)，key3(50) → A(100)
2. 新增 D(250)：只有哈希值在 (200, 250] 区间的数据从 C 迁移到 D，其他不变

**要点**：一致性哈希的优势在于增删节点时只影响相邻区间的数据。

### 练习三

**思路**：从入口层、应用层、发布流程三个维度设计高可用方案。

**答案**：

```
DNS → Nginx-1(Master) ←VRRP→ Nginx-2(Backup)  ← Keepalived 双主
              ↓
    App-1 / App-2 / App-3 / App-4  ← 健康检查 5s 间隔
```

1. **Nginx 高可用**：两台 Nginx + Keepalived，VIP 自动漂移
2. **后端健康检查**：`max_fails=3 fail_timeout=30s`，连续 3 次失败后摘除
3. **滚动发布**：逐台从 upstream 移除 → graceful shutdown → 部署新版本 → 健康检查通过后重新加入

**要点**：高可用不是单点解决方案，而是多层防护。
