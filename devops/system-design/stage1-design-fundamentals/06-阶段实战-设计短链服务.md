# 阶段实战：设计短链服务

## 场景引入

你收到一个需求：设计一个类似 bit.ly 的短链服务。用户输入一个长链接，系统生成一个短链接（如 `https://short.url/abc123`）。其他用户访问这个短链接时，会被重定向到原始的长链接。

这个需求看起来简单，但它涵盖了前 5 课学习的所有核心知识：需求分析、API 设计、数据建模、缓存策略、负载均衡。本节课将综合运用这些知识，从零开始设计一个生产级的短链服务。

## 学习目标

- 综合运用需求分析方法，完成短链服务的完整需求拆解
- 掌握容量估算方法，计算存储、QPS、带宽需求
- 设计符合 RESTful 规范的 API 接口
- 完成数据库建模，包括索引和分表策略
- 理解短码生成算法的原理和权衡
- 设计高可用、高性能的完整架构

## 需求分析

### 功能需求

- **核心功能**：长链接生成短链接、短链接 302 重定向、自定义短码（可选）、过期时间设置
- **扩展功能**：访问统计（点击次数、来源）、批量生成、API 访问
- **不做**：用户注册登录、链接安全检测、自定义域名（后续迭代）

### 非功能需求

| 需求 | 目标 | 说明 |
|------|------|------|
| 可用性 | 99.99% | 短链是入口服务，宕机影响所有下游 |
| 延迟 | 重定向 < 50ms | 用户体验要求快速跳转 |
| 读写比 | 100:1 | 读远多于写（创建少，访问多） |
| 数据持久化 | 短链不能丢失 | 已分发的短链必须永久可用 |
| 不可预测 | 短码不能被猜测 | 防止遍历攻击 |

## 容量估算

```
假设：
  - 日均创建短链：1000 万
  - 读写比：100:1（每创建 1 条，被访问 100 次）
  - 数据保留：5 年

QPS 估算：
  写 QPS = 1000 万 / 86400 ≈ 116
  读 QPS = 116 × 100 = 11600
  峰值读 QPS = 11600 × 3 ≈ 35000

存储估算：
  每条记录 ≈ 500 字节（短码 + 长链接 + 时间戳 + 统计）
  日新增存储 = 500B × 1000 万 = 5 GB
  5 年总存储 = 5 GB × 365 × 5 ≈ 9.1 TB

带宽估算：
  请求：35000 QPS × 200B（请求头）≈ 7 MB/s
  响应：35000 QPS × 500B（302 响应 + Location）≈ 17.5 MB/s
  总带宽 ≈ 25 MB/s ≈ 200 Mbps
```

## API 设计

```
创建短链：
  POST /api/v1/urls
  Request:
  {
    "long_url": "https://example.com/very/long/path?param=value",
    "custom_code": "my-link",     // 可选
    "expire_at": "2025-12-31"     // 可选
  }
  Response (201):
  {
    "short_url": "https://short.url/abc123",
    "long_url": "https://example.com/very/long/path?param=value",
    "short_code": "abc123",
    "created_at": "2024-01-15T10:30:00Z",
    "expire_at": null
  }

获取短链详情：
  GET /api/v1/urls/{short_code}
  Response (200):
  {
    "short_code": "abc123",
    "long_url": "https://example.com/very/long/path",
    "click_count": 12345,
    "created_at": "2024-01-15T10:30:00Z"
  }

访问短链（重定向）：
  GET /{short_code}
  Response (302):
  Location: https://example.com/very/long/path

获取统计数据：
  GET /api/v1/urls/{short_code}/stats
  Response (200):
  {
    "short_code": "abc123",
    "total_clicks": 12345,
    "clicks_by_date": [
      { "date": "2024-01-15", "clicks": 5000 },
      { "date": "2024-01-16", "clicks": 7345 }
    ],
    "top_referrers": [
      { "source": "twitter.com", "clicks": 8000 },
      { "source": "direct", "clicks": 4345 }
    ]
  }
```

301 vs 302 选择：
- **301 Moved Permanently**：浏览器缓存重定向，后续访问不再经过短链服务。减少服务器压力，但无法统计点击。
- **302 Found**：每次访问都经过短链服务。可以统计点击，但服务器压力大。
- **建议**：使用 302，统计数据是核心价值。通过缓存策略减轻服务器压力。

## 数据库设计

### 表结构

```sql
CREATE TABLE urls (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    short_code  VARCHAR(10) NOT NULL UNIQUE,
    long_url    VARCHAR(2048) NOT NULL,
    user_id     BIGINT DEFAULT NULL,
    created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expire_at   DATETIME DEFAULT NULL,
    click_count BIGINT NOT NULL DEFAULT 0,
    INDEX idx_short_code (short_code),
    INDEX idx_long_url (long_url(100)),
    INDEX idx_expire (expire_at)
);

CREATE TABLE click_logs (
    id          BIGINT PRIMARY KEY AUTO_INCREMENT,
    short_code  VARCHAR(10) NOT NULL,
    clicked_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    ip_address  VARCHAR(45),
    user_agent  VARCHAR(500),
    referer     VARCHAR(2048),
    INDEX idx_code_time (short_code, clicked_at)
);
```

### 索引设计

- `short_code` 唯一索引：重定向查询的核心索引
- `long_url` 前缀索引：检查长链接是否已存在（去重）
- `expire_at` 索引：定时清理过期链接

### ER 图

```
urls(1:N)click_logs
urls: id, short_code, long_url, user_id, created_at, expire_at, click_count
click_logs: id, short_code, clicked_at, ip_address, user_agent, referer
```

点击日志表数据量大，需要按时间分表或归档。

## 短码生成算法

### 方案一：哈希 + 截取

对长链接计算 MD5/SHA256，取前 N 位做 Base62 编码。冲突则换一段哈希。优点：同一长链接生成相同短码（可去重）。缺点：需要处理哈希冲突。

### 方案二：自增 ID + Base62

数据库自增 ID（或分布式 ID 生成器）转换为 Base62。62^6 ≈ 568 亿，6 位短码足够。优点：无冲突、实现简单。缺点：短码可预测，需额外处理安全性。

### 方案三：预生成 + 池化（推荐）

后台任务批量生成短码，随机打乱存入 Redis 队列。创建短链时 `LPOP` 取一个短码关联长链接。队列不足时触发异步补充。优点：短码不可预测、无冲突、创建速度快（O(1)）。

## 缓存策略

重定向路径采用三级缓存：Nginx 本地缓存 → Redis → MySQL，逐级回填。Redis key 设计 `url:{short_code}`，TTL 24 小时，热点数据延长至 7 天。

```
重定向三级缓存流程：
  1. Nginx proxy_cache 检查本地缓存
     - 命中 → 直接返回 302（最快，微秒级）
     - 未命中 → 转发到应用层
  2. 应用层查询 Redis
     - 命中 → 写入 Nginx 缓存 → 返回 302（毫秒级）
     - 未命中 → 查询 MySQL
  3. MySQL 查询结果
     - 命中 → 回填 Redis（TTL 24h）→ 返回 302
     - 未命中 → 返回 404

缓存 Key 设计：
  Redis: url:{short_code} → { long_url, expire_at }
  Nginx: proxy_cache_key $uri → 302 Location header
```

点击统计采用异步方式：重定向同步返回（< 50ms），点击事件发送到 Kafka，消费者批量写入 click_logs 表。每批次 1000 条，每秒刷新一次，兼顾实时性和写入性能。


| 组件 | 选型 | 说明 |
|------|------|------|
| 入口 | Nginx + Keepalived | L7 负载均衡，双机热备 |
| 应用层 | 无状态 API 服务 | 水平扩展，支持滚动发布 |
| 缓存 | Redis Cluster | 短码缓存 + 预生成队列 |
| 数据库 | MySQL 主从 | 写主读从，定期归档 |
| 消息队列 | Kafka | 点击事件异步处理 |

### 请求流程

```
创建短链：POST /api/v1/urls → Redis LPOP 获取短码 → MySQL 写入 → Redis SET 缓存 → 返回
访问短链：GET /{short_code} → Nginx 缓存 → Redis → MySQL → 302 重定向 + 异步 Kafka
```

## 扩展讨论

### 分表策略

当数据量达到亿级时，需要对 urls 表分表：
- 分片键：short_code 的哈希值
- 分片数：16 或 32（2 的幂次）
- 路由：hash(short_code) % 分片数

### 短码用完怎么办

6 位 Base62 可表示约 568 亿个短码。当接近耗尽时：
- 扩展到 7 位（3.5 万亿）
- 回收过期短码
- 允许更长的短码

### 安全考虑

- 短码不可预测：预生成 + 随机打乱
- 限流：每个 IP 每分钟最多创建 10 个短链
- 黑名单：禁止指向恶意网站的长链接
- 监控：异常访问模式告警

## 常见误区

1. **用 301 重定向**：301 会被浏览器缓存，后续访问不再经过短链服务，无法统计点击。应该用 302。
2. **同步写统计**：每次点击都同步写数据库会严重影响重定向性能。应该用消息队列异步处理。
3. **短码用自增 ID**：自增 ID 可被遍历，存在安全风险。应该使用随机短码或预生成方案。
4. **忽略缓存**：短链服务是读密集型，没有缓存的话数据库会被读请求压垮。至少需要两级缓存（Redis + 本地缓存）。
5. **过度设计**：第一版不需要分表、不需要分布式 ID 生成器。先用单机 MySQL + Redis 跑起来，数据量大了再优化。
6. **忽略长链接去重**：同一长链接生成多个短码会浪费存储空间。可以在写入前查询 `long_url` 索引，或对长链接哈希后查重。
7. **统计数据不设上限**：click_logs 表无限增长会拖垮数据库。需要按时间归档（如保留近 90 天明细，历史数据聚合到统计表）。

## 工程建议

1. **先做 MVP**：第一版只需要创建和重定向功能，统计、自定义短码等功能后续迭代。
2. **监控先行**：上线前部署好监控（QPS、延迟、错误率、缓存命中率），出问题时能快速定位。
3. **压测验证**：上线前做压力测试，验证系统能否承受预估的峰值 QPS。
4. **灰度发布**：新版本先切 10% 流量，观察无异常后再全量发布。
5. **文档即代码**：用 OpenAPI 规范定义 API，自动生成文档和 SDK。
6. **定期清理过期数据**：用定时任务扫描 `expire_at` 已过期的短链，从数据库和 Redis 中同时清除，释放存储空间。
7. **容量预估迭代**：上线后根据真实流量数据修正容量估算，调整缓存 TTL、数据库连接池大小、Kafka 分区数等参数。

## 参考答案

### 练习一

**思路**：从 DAU 出发，按之前的估算方法重新计算。

**答案**：

- 读 QPS：5 亿 × 3 / 86400 ≈ 173,611，峰值 ≈ 520,833
- 写 QPS：173,611 / 100 ≈ 1,736，峰值 ≈ 5,208
- 存储：1,736 × 86400 × 500B × 365 × 5 ≈ 136.9 TB
- 带宽：520,833 × 500B ≈ 2 Gbps

**要点**：5 亿 DAU 级别需要考虑分布式数据库（如 TiDB）、多机房部署、CDN 加速重定向。

### 练习二

**思路**：分析新功能对架构的影响。

**答案**：

1. **实时统计仪表盘**：Flink 实时消费 Kafka 点击事件 → 聚合结果写入 Redis → WebSocket 推送
2. **自定义域名**：Nginx 泛域名解析 + 数据库增加 custom_domain 字段 + DNS CNAME 指向短链服务

### 练习三

**思路**：从常见故障模式分析原因。

**答案**：

1. **创建 API 延迟飙升**：Redis 短码队列耗尽退化到实时生成，或 MySQL 写入慢。监控队列长度，检查慢查询日志。
2. **缓存命中率下降**：大量新链接缓存未预热，或 Redis 内存不足频繁淘汰。增加内存，优化淘汰策略。
3. **统计延迟**：Kafka 消费者积压，或 click_logs 表写入瓶颈。增加消费者实例，批量写入。

**要点**：没有监控就没有排查依据。每个关键环节都需要监控 QPS、延迟、错误率。
