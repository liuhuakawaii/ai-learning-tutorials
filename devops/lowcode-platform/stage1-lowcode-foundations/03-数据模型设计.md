# 数据模型设计：可视化建模与 API 自动生成

## 场景引入

王芳是一家物流公司的产品经理，需要用低代码平台搭建一套运单管理系统。在搭建过程中，她遇到了一个棘手的问题：运单需要关联客户、司机、车辆、路线四个实体，每个实体有十几到二十几个字段，实体之间存在复杂的一对多和多对多关系。

她尝试在平台上拖拽创建数据表，但因为缺乏数据建模经验，一开始把所有字段都塞进了一张"运单"大表里。结果在做数据查询时频繁出错，统计报表的数字也对不上。后来在技术同事的指导下，她将数据拆分为规范的多张表并建立了关系，问题才得以解决。

数据模型是低代码应用的地基。地基打歪了，上面的表单、流程、报表都会跟着出问题。本节课将教你如何用低代码平台进行规范的数据模型设计。

## 学习目标

- 理解实体-关系模型的基本概念
- 掌握在低代码平台上可视化创建数据表和字段的方法
- 能够正确设计一对一、一对多、多对多关系
- 了解 API 自动生成的原理和使用方式

## 实体-关系模型基础

在关系型数据库中，数据模型由三个核心元素构成：

- **实体（Entity）**：业务中的对象，如"客户""订单""商品"。在数据库中表现为一张表。
- **属性（Attribute）**：实体的特征，如客户的"姓名""电话""地址"。在数据库中表现为表的字段。
- **关系（Relationship）**：实体之间的关联，如"一个客户有多个订单"。

在低代码平台上，你通常不需要直接写 SQL 建表，而是通过可视化界面完成：创建实体 → 添加属性 → 建立关系 → 配置校验。

## 字段类型详解

低代码平台通常支持以下字段类型：

| 字段类型 | 用途 | 示例 | 注意事项 |
|----------|------|------|----------|
| 文本（Text） | 短文本内容 | 姓名、地址 | 注意最大长度限制 |
| 长文本（Long Text） | 大段文字 | 备注、描述 | 不适合做索引字段 |
| 数字（Number） | 整数或小数 | 数量、金额 | 区分整数和浮点数 |
| 布尔（Boolean） | 是/否状态 | 是否激活 | 存储"软删除"标记 |
| 日期/日期时间 | 时间相关 | 创建日期 | 统一使用 UTC 存储 |
| 枚举（Enum） | 固定选项集合 | 状态、优先级 | 选项变更需考虑兼容性 |
| 关联（Relation） | 指向其他表 | 客户ID | 本课重点 |
| JSON | 半结构化数据 | 动态表单 | 查询性能低于结构化字段 |

以"客户"实体为例，完整的字段设计：

```json
{
  "entity": "Customer",
  "fields": [
    { "name": "id", "type": "UUID", "primary": true, "auto": true },
    { "name": "name", "type": "Text", "required": true, "maxLength": 100 },
    { "name": "phone", "type": "Text", "unique": true, "pattern": "^1[3-9]\\d{9}$" },
    { "name": "email", "type": "Text", "unique": true, "format": "email" },
    { "name": "level", "type": "Enum", "options": ["普通", "银卡", "金卡", "钻石"] },
    { "name": "balance", "type": "Decimal", "precision": 10, "scale": 2, "default": 0 },
    { "name": "is_active", "type": "Boolean", "default": true },
    { "name": "created_at", "type": "DateTime", "auto": true },
    { "name": "updated_at", "type": "DateTime", "auto": true }
  ]
}
```

## 关系设计

关系是数据模型中最容易出错的部分。低代码平台通常提供可视化的关系配置界面，但你需要先理解三种基本关系类型。

### 一对一关系（1:1）

一个实体 A 的一条记录对应实体 B 的一条记录。典型场景：用户与用户详情、订单与发票。

```javascript
// 在 user_profiles 表中添加关联字段
{
  "field": "user",
  "type": "Relation",
  "target": "users",
  "relationType": "one-to-one",
  "onDelete": "CASCADE"  // 用户删除时，详情也删除
}
```

### 一对多关系（1:N）

一个实体 A 的多条记录对应实体 B 的一条记录。典型场景：客户与订单、部门与员工。

```javascript
// 在 orders 表中添加外键
{
  "field": "customer",
  "type": "Relation",
  "target": "customers",
  "relationType": "many-to-one"
}
// 或者在 customers 表中添加反向关联
{
  "field": "orders",
  "type": "Relation",
  "target": "orders",
  "relationType": "one-to-many",
  "foreignKey": "customer_id"
}
```

### 多对多关系（M:N）

实体 A 的多条记录对应实体 B 的多条记录。典型场景：学生与课程、标签与文章。

```javascript
// 多对多关系需要中间表，平台通常自动创建
{
  "field": "courses",
  "type": "Relation",
  "target": "courses",
  "relationType": "many-to-many",
  "through": "student_courses",  // 中间表名
  "extraFields": [                // 中间表的额外字段
    { "name": "enrolled_at", "type": "DateTime" },
    { "name": "score", "type": "Number" }
  ]
}
```

## 常见数据模型模式

### 模式一：树形结构

适用于组织架构、商品分类、评论回复。通过自引用外键实现：

```json
{
  "entity": "Category",
  "fields": [
    { "name": "id", "type": "UUID", "primary": true },
    { "name": "name", "type": "Text", "required": true },
    { "name": "parent", "type": "Relation", "target": "Category", "nullable": true },
    { "name": "level", "type": "Number", "default": 1 },
    { "name": "sort_order", "type": "Number", "default": 0 }
  ]
}
```

### 模式二：状态机

适用于订单状态流转、审批流程。用枚举字段加状态转换规则：

```json
{
  "entity": "Order",
  "fields": [
    { "name": "status", "type": "Enum", "options": ["待支付", "已支付", "已发货", "已完成", "已取消"] },
    { "name": "status_history", "type": "JSON" }
  ],
  "transitions": [
    { "from": "待支付", "to": "已支付", "action": "pay" },
    { "from": "已支付", "to": "已发货", "action": "ship" },
    { "from": "已发货", "to": "已完成", "action": "confirm" },
    { "from": "待支付", "to": "已取消", "action": "cancel" }
  ]
}
```

### 模式三：多态关联

适用于评论可以关联文章、商品、视频等不同类型的内容：

```json
{
  "entity": "Comment",
  "fields": [
    { "name": "content", "type": "LongText", "required": true },
    { "name": "commentable_type", "type": "Enum", "options": ["Article", "Product", "Video"] },
    { "name": "commentable_id", "type": "UUID" }
  ]
}
```

## API 自动生成

低代码平台在你创建数据模型后，会自动生成标准的 CRUD API：

```
GET    /api/products          → 查询列表（支持分页、筛选、排序）
GET    /api/products/:id      → 查询详情
POST   /api/products          → 创建记录
PUT    /api/products/:id      → 更新记录
DELETE /api/products/:id      → 删除记录
```

查询参数示例：

```javascript
GET /api/products?filter[price][gt]=100     // 筛选
GET /api/products?sort=-created_at           // 排序
GET /api/products?page=2&pageSize=20         // 分页
GET /api/products?populate=category          // 关联查询
GET /api/products?fields=name,price,category // 字段筛选
```

API 自动生成的同时，平台也会在接口层强制执行数据校验：

```json
{
  "entity": "Product",
  "validation": {
    "name": { "required": true, "minLength": 2, "maxLength": 200 },
    "price": { "required": true, "min": 0, "type": "number" },
    "sku": { "required": true, "unique": true, "pattern": "^[A-Z]{2}-\\d{4}$" }
  }
}
```

校验不通过时，API 返回结构化错误信息：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "details": [
      { "field": "name", "message": "名称不能为空" },
      { "field": "price", "message": "价格必须大于 0" }
    ]
  }
}
```

## 常见误区

1. **一张大表塞所有字段**：把所有信息放在一张表里，会导致数据冗余、更新异常和查询效率低下。正确做法是按实体关系拆分为多张表，通过关联字段连接。

2. **忽视字段类型的精确选择**：用文本类型存储数字会导致排序和计算出错；用文本类型存储日期会导致日期范围查询困难。字段类型直接影响数据的正确性和查询性能。

3. **过度设计关系**：不是所有关联都需要建立正式的数据库关系。对于低频查询或临时关联，可以用 JSON 字段存储引用，避免过度规范化导致查询时需要大量 JOIN。

## 工程建议

1. **先画 ER 图，再建数据表**：在动手之前，用纸笔或工具画出实体关系图。返工数据模型的成本远高于前期设计的成本。

2. **为每个表添加审计字段**：`created_at`、`updated_at`、`created_by`、`updated_by` 应该成为每个表的标配，在排查问题和审计时非常有价值。

3. **使用软删除而非硬删除**：添加 `is_deleted` 或 `deleted_at` 字段标记删除状态，而不是真正从数据库中删除数据。这在误操作恢复和数据审计场景下能救命。

## 小结

- 数据模型由实体、属性和关系三个核心元素构成，是低代码应用的地基
- 字段类型的选择直接影响数据正确性和查询性能，需要精确匹配业务语义
- 三种基本关系类型（一对一、一对多、多对多）覆盖了绝大多数业务场景
- API 自动生成是低代码平台的核心能力，理解生成规则有助于高效使用
- 软删除、审计字段、索引设计是生产环境的必备实践

### 练习一

**思路**：识别核心实体，分析实体间关系，为每个实体设计字段

**答案**：

```
Student ──M:N── Course ──1:N── Chapter ──1:N── Lesson

```

```json
[
  { "entity": "Student", "fields": [
    { "name": "id", "type": "UUID", "primary": true },
    { "name": "name", "type": "Text", "required": true },
    { "name": "email", "type": "Text", "unique": true },
    { "name": "created_at", "type": "DateTime", "auto": true }
  ]},
  { "entity": "Course", "fields": [
    { "name": "id", "type": "UUID", "primary": true },
    { "name": "title", "type": "Text", "required": true },
    { "name": "price", "type": "Decimal", "default": 0 },
    { "name": "status", "type": "Enum", "options": ["草稿", "已发布", "已下架"] }
  ]},
  { "entity": "Chapter", "fields": [
    { "name": "id", "type": "UUID", "primary": true },
    { "name": "title", "type": "Text", "required": true },
    { "name": "sort_order", "type": "Number" },
    { "name": "course", "type": "Relation", "target": "Course", "relationType": "many-to-one" }
  ]},
  { "entity": "Lesson", "fields": [
    { "name": "id", "type": "UUID", "primary": true },
    { "name": "title", "type": "Text", "required": true },
    { "name": "content_type", "type": "Enum", "options": ["视频", "文档", "测验"] },
    { "name": "chapter", "type": "Relation", "target": "Chapter", "relationType": "many-to-one" }
  ]},
  { "entity": "StudentProgress", "fields": [
    { "name": "student", "type": "Relation", "target": "Student" },
    { "name": "lesson", "type": "Relation", "target": "Lesson" },
    { "name": "status", "type": "Enum", "options": ["未开始", "学习中", "已完成"] },
    { "name": "progress_percent", "type": "Number", "default": 0 }
  ]}
]
```

**要点**：
- 多对多关系需要中间表（如 StudentProgress）
- 树形结构用自引用外键实现
- 排序字段 `sort_order` 用于支持拖拽排序

### 练习二

**思路**：根据关系类型选择正确的查询参数（populate、filter）

**答案**：

```javascript
// 1. 获取某个学生已报名的所有课程
GET /api/students/STUDENT_UUID?populate=courses

// 2. 获取某门课程下所有章节和课时
GET /api/courses/COURSE_UUID?populate={ chapters: { populate: ['lessons'] } }

// 3. 更新某个学生在某个课时的学习进度
PATCH /api/student-progress/PROGRESS_UUID
{ "status": "已完成", "progress_percent": 100 }
```

**要点**：
- `populate` 参数用于加载关联数据，避免 N+1 查询问题
- 嵌套 populate 可以一次加载多层关系的数据
- 更新操作使用 PATCH 进行部分更新，比 PUT 更灵活
