# 权限与角色：构建安全可控的访问体系

## 场景引入

刘洋是一家集团公司的 IT 经理，负责搭建一套覆盖总部和 8 个分公司的采购管理系统。系统上线一个月后，他收到了一个严重的安全投诉：某分公司的采购员误操作删除了总部的供应商数据。

排查后发现，问题出在权限配置上——系统只按"角色"控制了功能权限（谁能访问采购模块），但没有按"数据范围"控制数据权限（谁能看到哪些数据）。所有采购员都能看到并操作全集团的供应商数据，这显然是不合理的。

这个案例说明了一个关键问题：权限控制不仅是"能不能访问"的问题，更是"能访问哪些数据"和"能对数据做什么操作"的问题。本节课将系统讲解低代码平台中的权限体系设计。

## 学习目标

- 理解 RBAC（基于角色的访问控制）模型的原理
- 掌握功能权限和数据权限的区别与配置方法
- 了解行级和列级权限的实现方式
- 理解多租户架构的基本概念

## RBAC 模型基础

RBAC（Role-Based Access Control）的核心思想是：**用户不直接关联权限，而是通过角色间接获取权限**。

```
RBAC 核心模型：
  用户 (User) ──→ 角色 (Role) ──→ 权限 (Permission)

示例：
  张三 ──→ 采购主管 ──→ [采购单: 创建, 查看, 审批]
  李四 ──→ 采购员   ──→ [采购单: 创建, 查看]
  王五 ──→ 财务     ──→ [采购单: 查看, 付款]
```

为什么不让用户直接关联权限？因为当组织有几百人时，逐个配置权限是不可维护的。通过角色抽象，你只需要维护几十个角色的权限，然后把用户分配到对应角色即可。

### 角色设计原则

```
1. 最小权限原则：角色只授予完成工作所需的最小权限
2. 职责分离原则：关键操作需要多个角色配合完成
3. 角色继承原则：高级角色可以继承低级角色的权限
4. 动态调整原则：角色权限应能随业务变化灵活调整
```

## 功能权限

功能权限控制用户能访问哪些页面、按钮和操作。通常按"资源 + 操作"的粒度定义：

```json
{
  "roles": [
    {
      "name": "采购员",
      "permissions": [
        { "resource": "purchase_orders", "actions": ["create", "read", "update"] },
        { "resource": "suppliers", "actions": ["read"] }
      ]
    },
    {
      "name": "采购主管",
      "permissions": [
        { "resource": "purchase_orders", "actions": ["create", "read", "update", "approve"] },
        { "resource": "suppliers", "actions": ["create", "read", "update"] },
        { "resource": "reports", "actions": ["read", "export"] }
      ]
    },
    {
      "name": "系统管理员",
      "permissions": [{ "resource": "*", "actions": ["*"] }]
    }
  ]
}
```

按钮级权限通过条件渲染实现：

```javascript
{
  "type": "Button",
  "label": "审批",
  "visible": { "condition": "hasPermission('purchase_orders', 'approve')" }
}

{
  "type": "Button",
  "label": "删除",
  "visible": { "condition": "hasPermission('purchase_orders', 'delete') && (isOwner() || hasRole('admin'))" }
}
```

## 数据权限

功能权限解决"能不能访问"，数据权限解决"能访问哪些数据"。

### 行级权限（Row-Level Security）

行级权限控制用户能看到哪些行（记录）：

```
采购员张三 ──→ 只能看到自己创建的采购单
采购主管李四 ──→ 能看到本部门所有采购单
财务王五 ──→ 能看到所有已审批的采购单
系统管理员 ──→ 能看到所有采购单
```

```json
{
  "resource": "purchase_orders",
  "row_level_rules": [
    { "role": "采购员", "filter": "created_by = currentUser().id" },
    { "role": "采购主管", "filter": "department_id = currentUser().department_id" },
    { "role": "财务", "filter": "status = '已审批'" },
    { "role": "系统管理员", "filter": "true" }
  ]
}
```

### 列级权限（Column-Level Security）

列级权限控制用户能看到哪些列（字段）：

```
字段         采购员  采购主管  财务  管理员
─────────────────────────────────────────
采购单号       ✓      ✓      ✓     ✓
供应商         ✓      ✓      ✓     ✓
采购金额       ✗      ✓      ✓     ✓
成本价         ✗      ✗      ✓     ✓
利润率         ✗      ✗      ✓     ✓
```

```json
{
  "resource": "purchase_orders",
  "column_level_rules": [
    {
      "role": "采购员",
      "visible_fields": ["order_number", "supplier", "items", "status"],
      "hidden_fields": ["amount", "cost_price", "profit_rate"]
    }
  ]
}
```

### API 层实现

数据权限在 API 查询时自动注入查询条件：

```javascript
// 采购员张三的实际查询（平台自动注入行级权限）
SELECT * FROM purchase_orders
WHERE created_by = '张三的ID' AND deleted_at IS NULL

// 采购主管李四的实际查询
SELECT * FROM purchase_orders
WHERE department_id = '李四所在部门ID' AND deleted_at IS NULL
```

## 多租户架构

当一套系统需要服务多个独立组织时，需要引入多租户架构。

### 三种隔离模式

```
模式一：独立数据库 → 隔离性最强，成本最高
模式二：共享数据库，独立 Schema → 隔离性适中
模式三：共享数据库，共享 Schema（推荐）→ 成本最低，通过 tenant_id 隔离
```

低代码平台通常采用模式三：

```json
{
  "multi_tenant": {
    "strategy": "shared_schema",
    "tenant_field": "tenant_id",
    "auto_filter": true
  }
}
```

```javascript
// 所有查询自动注入租户过滤条件
SELECT * FROM orders WHERE tenant_id = '当前租户ID' AND deleted_at IS NULL

// 创建数据时自动填充租户ID
INSERT INTO orders (customer, amount, tenant_id) VALUES ('张三', 1000, '当前租户ID')
```

## 权限分层模型

在实际项目中，权限通常分为四层：

```
├── 第一层：认证（Authentication）→ 你是谁？
├── 第二层：功能权限（Function Permission）→ 你能做什么？
├── 第三层：数据权限（Data Permission）→ 你能看哪些数据？
└── 第四层：字段级权限（Field Permission）→ 你能改哪些字段？
```

权限查询是高频操作，需要合理的缓存策略（如 Redis 缓存用户角色和权限列表，设置 5-10 分钟 TTL，在权限变更时主动失效）。

## 常见误区

1. **只做功能权限，不做数据权限**：这是最常见的安全隐患。功能权限只控制"能不能访问"，数据权限控制"能访问哪些数据"。缺少数据权限意味着用户可能看到不属于自己的敏感数据。

2. **过度依赖管理员角色**：为了省事给太多人分配管理员角色，等于没有权限控制。管理员角色应该严格限制人数，并开启操作审计日志。

3. **权限配置后不测试**：配置完权限后，必须用不同角色的账号登录测试。重点测试：越权访问、数据泄露、权限残留（角色变更后旧权限是否清理）。

## 工程建议

1. **权限设计先行**：在开发功能之前，先设计好权限模型。列出所有资源、操作和角色，画出权限矩阵。后期再补权限往往会遗漏关键控制点。

2. **使用标准化的权限命名规范**：采用 `资源:操作` 的命名格式，如 `orders:create`、`orders:read`。便于权限的批量管理和自动化检查。

3. **开启操作审计日志**：记录所有敏感操作的操作人、操作时间、操作内容和 IP 地址。审计日志是安全事件追溯的关键依据。

## 小结

- RBAC 通过"用户-角色-权限"三层模型实现灵活的权限管理
- 功能权限控制访问入口，数据权限控制数据范围，两者缺一不可
- 行级权限按记录过滤，列级权限按字段过滤，共同构成细粒度的数据安全
- 多租户架构通过 tenant_id 实现数据隔离，是 SaaS 产品的基础能力
- 权限设计应在开发前完成，配置后必须充分测试

## 参考答案

### 练习一

**思路**：先列出所有资源和操作，再按角色逐一填写权限矩阵

**答案**：

```
资源     操作      项目经理  开发人员  客户
──────────────────────────────────────────
项目     创建       ✓        ✗        ✗
项目     查看       ✓        ✓        ✓
项目     编辑       ✓        ✗        ✗
任务     创建       ✓        ✓        ✗
任务     查看       ✓        ✓        ✓
任务     编辑       ✓        仅自己    ✗
文档     创建       ✓        ✓        ✗
文档     查看       ✓        ✓        ✓
工时     创建       ✓        ✓        ✗
工时     查看       ✓        仅自己    ✗
```

数据权限规则：

```json
{
  "row_level_rules": {
    "tasks": [
      { "role": "项目经理", "filter": "project_id IN (SELECT id FROM projects WHERE manager_id = currentUser().id)" },
      { "role": "开发人员", "filter": "assignee_id = currentUser().id" },
      { "role": "客户", "filter": "project_id IN (SELECT id FROM projects WHERE client_id = currentUser().company_id)" }
    ]
  }
}
```

**要点**：
- 客户角色不能创建和编辑，只能查看
- 开发人员只能编辑自己的任务，但能看到项目中所有任务
- 数据权限通过子查询实现跨表过滤

### 练习二

**思路**：从数据层、API 层、防护层三个维度设计

**答案**：

```sql
-- 1. 所有业务表都添加 tenant_id 字段
CREATE TABLE employees (
  id UUID PRIMARY KEY,
  tenant_id UUID NOT NULL,
  name VARCHAR(100),
  email VARCHAR(200),
  created_at TIMESTAMP DEFAULT NOW()
);
CREATE INDEX idx_employees_tenant ON employees(tenant_id);
```

```javascript
// 2. API 层租户过滤中间件
const tenantMiddleware = (req, res, next) => {
  req.tenantFilter = { tenant_id: req.user.tenantId };
  next();
};

async function getOrders(req, res) {
  const orders = await db.orders.findMany({
    where: { ...req.tenantFilter, ...req.query.filter }
  });
  return res.json(orders);
}
```

```javascript
// 3. 防护措施
// PostgreSQL 行级安全策略（最后一道防线）
ALTER TABLE employees ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON employees
  USING (tenant_id = current_setting('app.current_tenant')::UUID);

// 防止 tenant_id 被篡改
const sanitizeTenantId = (req, res, next) => {
  delete req.body.tenant_id;  // 不允许客户端设置租户ID
  next();
};
```

**要点**：
- tenant_id 必须在每个表和每个查询中存在，不能遗漏
- API 层自动注入，开发者不需要手动添加
- 数据库层面的 RLS 策略是最后一道防线
