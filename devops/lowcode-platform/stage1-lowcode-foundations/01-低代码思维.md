# 低代码思维：重新理解软件开发

> 前置知识：HTML/CSS/JavaScript 基础，了解 REST API 概念

## 一个需求排队三个月的故事

张伟是一家中小型电商公司的运营负责人。公司需要一个内部库存管理系统，但技术团队排期已满，最快三个月后才能启动。张伟用 Excel 管了一段时间，但 SKU 突破 5000 后表格变得难以维护，数据冲突频繁。

某天他试用了一款低代码平台——用拖拽搭建数据表单、配置库存预警规则、串起采购审批流程。不到一周，一个能用的库存管理系统就上线了。

这个故事代表了低代码最典型的场景：需求紧迫、技术资源有限、核心功能明确。但低代码不是万能药——它有自己的边界。

## 低代码 vs 无代码

```
纯代码开发 ←————————————→ 低代码 ←————————→ 无代码
完全灵活，成本高         灵活+效率平衡         效率最高，灵活性最低
```

**低代码平台**通过可视化界面完成大部分开发，但仍允许写自定义代码处理复杂逻辑。典型代表：Retool、Appsmith。

**无代码平台**完全屏蔽代码，目标用户是没有编程背景的业务人员。典型代表：宜搭、简道云。

实际项目中，低代码平台通常同时提供两种模式：简单功能用无代码配置，复杂逻辑用低代码扩展。

## 低代码的核心能力模型

```
┌─────────────────────────────────────────┐
│  展示层：拖拽构建 UI 界面                │
├─────────────────────────────────────────┤
│  逻辑层：业务规则、工作流、自动化         │
├─────────────────────────────────────────┤
│  数据层：可视化定义数据模型、关系         │
├─────────────────────────────────────────┤
│  集成层：对接外部 API、Webhook           │
├─────────────────────────────────────────┤
│  权限层：RBAC、数据权限、多租户           │
└─────────────────────────────────────────┘
```

评估一个低代码平台时，逐一检查每一层是否满足需求。

## 适用场景

```
适合低代码的场景：
  ✓ 内部管理系统（CRM、ERP、OA）
  ✓ 数据看板和报表
  ✓ 审批流程和工作流
  ✓ CRUD 密集型应用
  ✓ 原型验证和 MVP

不适合低代码的场景：
  ✗ 高性能要求的实时系统
  ✗ 复杂的算法和数据处理
  ✗ 需要深度定制 UI 的消费者产品
  ✗ 需要精细控制底层架构的系统
  ✗ 对数据主权有严格要求的场景
```

## 低代码 vs 传统开发的权衡

| 维度 | 低代码 | 传统开发 |
|------|-------|---------|
| 开发速度 | 快（天/周） | 慢（周/月） |
| 灵活性 | 中等 | 完全灵活 |
| 学习曲线 | 低 | 高 |
| 维护成本 | 低（平台负责） | 高（自己负责） |
| 性能上限 | 中等 | 高 |
| 供应商锁定 | 有风险 | 无 |
| 适用场景 | 内部工具、标准业务 | 消费者产品、复杂系统 |

## 选型决策框架

```
你的需求是什么？
├── 内部管理工具 → 低代码平台（Retool/Appsmith）
├── 客户面向的产品 → 传统开发
├── 快速验证想法 → 低代码 + 后续重构
├── 复杂业务逻辑 → 传统开发为主，低代码辅助
└── 数据分析和报表 → 低代码平台
```

选型时关注的维度：
1. **数据模型能力**：能否定义复杂关系、支持自定义字段
2. **扩展能力**：能否写自定义代码、能否接入自定义组件
3. **集成能力**：能否对接现有系统的 API
4. **部署方式**：SaaS 还是私有化部署
5. **成本模型**：按用户数、按请求数还是按功能

## 参考答案

### 练习一

| 场景 | 选择 | 理由 |
|------|------|------|
| A：请假审批 | 低代码 | 标准 CRUD + 审批流程，低代码效率最高 |
| B：社交 App | 传统开发 | 消费者产品需要精细 UI 和高性能 |
| C：ETL 管理 | 低代码 | 内部工具，数据展示为主 |
| D：高频交易 | 传统开发 | 性能要求极高，低代码无法满足 |
| E：MVP | 低代码 | 速度优先，验证想法后再决定是否重构 |

### 练习二

以 Retool 为例：

| 能力层 | 得分 | 说明 |
|--------|------|------|
| 数据层 | 4/5 | 支持多种数据源，可视化建模 |
| 逻辑层 | 3/5 | 支持 JavaScript 自定义逻辑 |
| 展示层 | 4/5 | 丰富的组件库，拖拽布局 |
| 集成层 | 5/5 | 支持 REST API、GraphQL、Webhook |
| 权限层 | 3/5 | 基本 RBAC，数据权限有限 |

### 练习三

数据表：projects（项目）、tasks（任务）、users（用户）
页面：项目列表、任务看板、任务详情、个人任务视图
工作流：任务状态变更通知、任务到期提醒、任务分配通知
