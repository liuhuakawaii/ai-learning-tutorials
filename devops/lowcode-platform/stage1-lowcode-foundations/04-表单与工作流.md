# 表单与工作流：构建业务交互的核心

## 场景引入

赵强是一家互联网公司的行政主管，公司有 300 多名员工。每个月他要处理上百份报销申请，每份申请需要经过"员工提交 → 直属主管审批 → 财务复核 → 出纳打款"四个环节。过去，这个流程完全靠邮件和 Excel 运转，经常出现审批人遗漏、金额填写错误、附件丢失等问题。

赵强决定用低代码平台重构这个流程。他先用表单设计器搭建了报销申请表，配置了金额校验和发票附件上传；然后用工作流编辑器串起了四级审批，每级审批都设置了条件分支——金额低于 500 元主管直接审批，高于 500 元需要总监加签。系统上线后，报销处理时间从平均 5 天缩短到 1.5 天，错误率下降了 90%。

表单是用户与系统交互的入口，工作流是业务逻辑的骨架。这两者是低代码平台最核心的能力，也是本节课的学习重点。

## 学习目标

- 掌握表单设计器的核心组件和配置方法
- 理解条件显示、联动逻辑的实现方式
- 学会配置数据校验引擎
- 掌握工作流设计器的节点类型和流转逻辑

## 表单设计器

低代码平台的表单设计器通常采用拖拽式操作，将预定义的组件拖放到画布上，然后配置属性和行为。核心组件分为四类：

```
表单组件分类：
├── 输入类：文本输入、数字输入、日期选择、下拉选择、单选框、多选框、开关、评分
├── 展示类：标题、描述文本、分割线、提示信息
├── 高级类：文件上传、富文本编辑器、子表单、关联选择、地图选址
└── 布局类：栅格布局、标签页、折叠面板
```

### 表单布局配置

一个典型的报销申请表单：

```json
{
  "form": {
    "layout": "horizontal",
    "labelCol": { "span": 6 },
    "wrapperCol": { "span": 18 },
    "sections": [
      { "title": "基本信息", "fields": [
          { "type": "Input", "name": "title", "label": "报销标题", "required": true },
          { "type": "Select", "name": "category", "label": "费用类型", "options": ["差旅", "办公", "招待", "交通"] },
          { "type": "DatePicker", "name": "expense_date", "label": "费用日期", "required": true }
      ]},
      { "title": "费用明细", "fields": [
          { "type": "SubForm", "name": "items", "label": "费用明细", "children": [
            { "type": "Input", "name": "description", "label": "费用说明" },
            { "type": "Number", "name": "amount", "label": "金额", "min": 0, "precision": 2 },
            { "type": "ImageUpload", "name": "receipt", "label": "发票照片" }
          ]}
      ]}
    ]
  }
}
```

## 条件显示与联动

表单中的字段经常需要根据其他字段的值动态显示或隐藏：

```javascript
// 当"费用类型"选择"差旅"时，显示"出发地"字段
{
  "type": "Input",
  "name": "departure",
  "label": "出发地",
  "visible": {
    "condition": "category === '差旅'",
    "dependencies": ["category"]
  }
}

// 选择客户后，自动填充联系人信息
{ "type": "RelationSelect", "name": "customer", "label": "客户", "target": "customers",
  "onChange": { "action": "setFields",
    "mapping": { "contact_name": "{{customer.contact_name}}", "contact_phone": "{{customer.contact_phone}}" } } }

// 级联选择：省份 → 城市 → 区县
{
  "type": "CascadeSelect",
  "name": "region",
  "label": "所在地区",
  "levels": [
    { "target": "provinces", "field": "province_id" },
    { "target": "cities", "field": "city_id", "filter": "province_id = {{province_id}}" },
    { "target": "districts", "field": "district_id", "filter": "city_id = {{city_id}}" }
  ]
}
```

## 数据校验引擎

### 基础校验规则

```json
{
  "validation": {
    "title": [
      { "type": "required", "message": "标题不能为空" },
      { "type": "minLength", "value": 2, "message": "标题至少 2 个字符" },
      { "type": "maxLength", "value": 100, "message": "标题不能超过 100 个字符" }
    ],
    "amount": [
      { "type": "required", "message": "金额不能为空" },
      { "type": "min", "value": 0.01, "message": "金额必须大于 0" }
    ],
    "phone": [
      { "type": "pattern", "value": "^1[3-9]\\d{9}$", "message": "手机号格式不正确" }
    ]
  }
}
```

### 自定义校验函数

当内置规则不够用时，通过自定义函数实现复杂校验：

```javascript
// 费用明细的总金额不能超过预算
const validateTotalAmount = (formData) => {
  const total = formData.items.reduce((sum, item) => sum + (item.amount || 0), 0);
  if (total > formData.budget) {
    return { valid: false, message: `总金额 ${total} 超出预算 ${formData.budget}` };
  }
  return { valid: true };
};

// 结束日期不能早于开始日期
const validateDateRange = (formData) => {
  if (formData.end_date && formData.start_date &&
      new Date(formData.end_date) < new Date(formData.start_date)) {
    return { valid: false, message: '结束日期不能早于开始日期' };
  }
  return { valid: true };
};
```

## 工作流设计器

### 工作流节点类型

```
节点类型：
├── 触发节点：数据变更触发、定时触发、API 触发、手动触发
├── 逻辑节点：条件判断（If/Else）、并行分支、循环、延迟
├── 动作节点：数据操作、发送通知、调用 API、代码执行
└── 审批节点：单人审批、多人会签、多人或签、加签/转签
```

### 审批流程配置

以报销审批为例，配置一个四级审批流程：

```yaml
workflow:
  name: 报销审批流程
  trigger: { type: data_change, entity: expense_reports, event: created }
  steps:
    - name: 主管审批
      type: approval
      assignee: { type: "直属主管", field: "applicant.manager" }
      actions:
        - { label: 通过, next: 条件判断 }
        - { label: 驳回, next: 通知申请人 }
    - name: 条件判断
      type: condition
      rules:
        - { condition: "total_amount > 500", next: 总监审批 }
        - { condition: "total_amount <= 500", next: 财务复核 }
    - name: 总监审批
      type: approval
      assignee: { type: "指定角色", role: "财务总监" }
      actions:
        - { label: 通过, next: 财务复核 }
        - { label: 驳回, next: 通知申请人 }
    - name: 财务复核
      type: approval
      assignee: { type: "指定角色", role: "财务专员" }
      actions:
        - { label: 通过, next: 更新状态 }
        - { label: 驳回, next: 通知申请人 }
    - name: 更新状态
      type: action
      operations: { update: { entity: expense_reports, field: status, value: "已通过" } }
    - name: 通知申请人
      type: notification
      channels: { type: email, to: "{{applicant.email}}", template: "报销审批结果通知" }
```

### 条件逻辑与分支

工作流中的条件判断支持复杂表达式：

```javascript
// 多条件组合
{ "condition": "total_amount > 1000 && category === '差旅'", "next": "总经理审批" }
// 嵌套条件
{ "condition": "total_amount > 5000",
  "true": { "condition": "is_first_time", "true": "财务总监", "false": "部门总监" },
  "false": "主管审批" }
// 列表数据条件
{ "condition": "items.some(item => item.amount > 2000)", "next": "需详细说明" }
```

## 常见误区

1. **表单字段越多越好**：表单设计的核心原则是"只问必要信息"。每多一个字段，用户的填写意愿就下降一分。只收集业务流程真正需要的数据，非必要信息可以后续补充。

2. **审批流程越复杂越严谨**：过多的审批节点不仅拖慢效率，还会导致"审批疲劳"。应该根据金额、风险等级设置分级审批，低风险的走快速通道。

3. **忽视表单的移动端体验**：很多审批操作是在手机上完成的。如果表单在移动端显示异常，会严重影响使用率。设计表单时必须测试移动端的显示效果。

## 工程建议

1. **表单设计遵循"渐进式披露"原则**：默认只显示核心字段，高级选项折叠在"更多"区域。既满足简单场景的快速填写，又不遗漏复杂场景的必要信息。

2. **工作流设计要预留异常处理路径**：每个审批节点都应该设置超时机制（如 48 小时未审批自动提醒），并配置"转签"和"加签"功能，避免流程因审批人缺席而卡住。

3. **校验规则要在前端和后端同时配置**：前端校验提供即时反馈（用户体验），后端校验保证数据安全（防止绕过前端）。

## 小结

- 表单设计器通过拖拽组件和配置属性完成 UI 搭建，核心是选择正确的组件和校验规则
- 条件显示和字段联动让表单具备动态能力
- 工作流设计器将业务流程自动化，核心节点包括触发、条件判断、审批和动作
- 审批流程应根据风险等级分级设计，避免过度复杂化
- 移动端体验和异常处理是容易忽视但至关重要的环节

## 参考答案

### 练习一

**思路**：先确定字段类型，再配置条件显示和计算逻辑

**答案**：

```json
{
  "form": {
    "name": "请假申请表",
    "sections": [
      { "title": "基本信息", "fields": [
          { "type": "Select", "name": "leave_type", "label": "请假类型", "required": true,
            "options": ["年假", "事假", "病假", "婚假", "产假"] },
          { "type": "DateRange", "name": "date_range", "label": "请假时间", "required": true,
            "fields": ["start_date", "end_date"] },
          { "type": "Number", "name": "days", "label": "请假天数", "readonly": true,
            "computed": { "expression": "Math.ceil((new Date(end_date) - new Date(start_date)) / 86400000) + 1",
              "dependencies": ["start_date", "end_date"] } },
          { "type": "TextArea", "name": "reason", "label": "请假事由", "required": true, "minLength": 10 }
      ]},
      { "title": "附件", "fields": [
          { "type": "FileUpload", "name": "hospital_cert", "label": "医院证明", "accept": ".jpg,.png,.pdf",
            "visible": { "condition": "leave_type === '病假'", "dependencies": ["leave_type"] } },
          { "type": "RelationSelect", "name": "handover_person", "label": "工作交接人", "target": "users",
            "visible": { "condition": "days > 3", "dependencies": ["days"] } }
      ]}
    ],
    "validation": [{ "rule": "end_date >= start_date", "message": "结束日期不能早于开始日期" }]
  }
}
```

**要点**：
- `DateRange` 组件同时选择开始和结束日期
- `computed` 字段自动计算天数，用户不需要手动输入
- `visible` 配置实现条件显示，依赖字段变化时自动重新计算

### 练习二

**思路**：根据天数设置条件分支，每个分支配置不同的审批链

**答案**：

```yaml
workflow:
  name: 请假审批流程
  trigger: { type: data_change, entity: leave_requests, event: created }
  steps:
    - name: 主管审批
      type: approval
      assignee: { type: "直属主管", field: "applicant.manager" }
      actions:
        - { label: 通过, next: 天数判断 }
        - { label: 驳回, next: 通知申请人 }
    - name: 天数判断
      type: condition
      rules:
        - { condition: "days > 1", next: 部门经理审批 }
        - { condition: "days <= 1", next: 更新状态 }
    - name: 部门经理审批
      type: approval
      assignee: { type: "指定角色", role: "部门经理" }
      actions:
        - { label: 通过, next: HR判断 }
        - { label: 驳回, next: 通知申请人 }
    - name: HR判断
      type: condition
      rules:
        - { condition: "days > 3", next: HR审批 }
        - { condition: "days <= 3", next: 更新状态 }
    - name: HR审批
      type: approval
      assignee: { type: "指定角色", role: "HR专员" }
      actions:
        - { label: 通过, next: 更新状态 }
        - { label: 驳回, next: 通知申请人 }
    - name: 更新状态
      type: action
      operations: { update: { entity: leave_requests, field: status, value: "已通过" } }
    - name: 通知申请人
      type: notification
      channels: { type: email, to: "{{applicant.email}}", subject: "请假审批结果" }
```

**要点**：
- 条件判断节点实现分级审批逻辑
- 每个审批节点的驳回都指向统一的通知节点
- 流程尽量复用节点，避免重复配置
