# 私有化部署

## 场景引入

某中型制造企业采购了一套低代码平台，用于构建内部的生产管理系统和审批流程。IT 部门接到任务：将平台部署到公司自有机房的服务器上，而不是使用 SaaS 版本。原因是生产数据涉及核心工艺参数，安全合规要求数据不出公司网络。

私有化部署看似只是"把代码跑起来"，实际涉及容器编排、网络配置、域名证书、持久化存储、监控告警等一系列工程问题。如果部署方案设计不当，轻则服务不稳定，重则数据丢失。本课将从 Docker Compose 单机部署讲起，逐步演进到 Kubernetes 集群部署，覆盖生产环境所需的完整部署链路。

## 学习目标

- 掌握使用 Docker Compose 编排多容器应用的完整流程
- 理解 Dockerfile 最佳实践（多阶段构建、非 root 用户、镜像瘦身）
- 学会使用 Kubernetes Deployment/Service/Ingress 部署低代码平台
- 掌握域名配置与 SSL 证书自动化管理

## Docker Compose 部署

低代码平台通常包含多个服务：API 服务、前端静态资源、数据库、缓存、反向代理。Docker Compose 适合单机或小规模部署场景。

### 多容器编排

```yaml
# docker-compose.yml
version: "3.8"

services:
  server:
    build:
      context: ./server
      dockerfile: Dockerfile
    environment:
      - DATABASE_URL=postgresql://lowcode:secret@db:5432/lowcode
      - REDIS_URL=redis://redis:6379
      - JWT_SECRET=${JWT_SECRET}
      - NODE_ENV=production
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 5s
      retries: 3

  client:
    build:
      context: ./client
      dockerfile: Dockerfile
    restart: unless-stopped

  db:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB: lowcode
      POSTGRES_USER: lowcode
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./scripts/init.sql:/docker-entrypoint-initdb.d/init.sql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lowcode"]
      interval: 10s
      timeout: 5s
      retries: 5

  redis:
    image: redis:7-alpine
    command: redis-server --requirepass ${REDIS_PASSWORD}
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD}", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5

  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./nginx/ssl:/etc/nginx/ssl:ro
      - client_dist:/usr/share/nginx/html:ro
    depends_on:
      - server
      - client

volumes:
  pgdata:
  redisdata:
  client_dist:
```

### Nginx 反向代理配置

```nginx
# nginx/nginx.conf
events {
    worker_connections 1024;
}

http {
    upstream api {
        server server:3000;
    }

    server {
        listen 80;
        server_name lowcode.example.com;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl http2;
        server_name lowcode.example.com;

        ssl_certificate     /etc/nginx/ssl/fullchain.pem;
        ssl_certificate_key /etc/nginx/ssl/privkey.pem;
        ssl_protocols       TLSv1.2 TLSv1.3;

        location /api/ {
            proxy_pass http://api;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        location / {
            root /usr/share/nginx/html;
            try_files $uri $uri/ /index.html;
        }

        location /static/ {
            expires 1y;
            add_header Cache-Control "public, immutable";
        }
    }
}
```

## Dockerfile 最佳实践

### 多阶段构建

```dockerfile
# server/Dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production && \
    cp -R node_modules /prod_modules && \
    npm ci
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
RUN addgroup -g 1001 -S lowcode && \
    adduser -S lowcode -u 1001
WORKDIR /app
COPY --from=builder /prod_modules ./node_modules
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/package.json ./
USER lowcode
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

关键点说明：
- **builder 阶段**：安装全部依赖（含 devDependencies）用于编译，同时分离生产依赖
- **runner 阶段**：仅复制生产依赖和编译产物，镜像体积减少 60% 以上
- **非 root 用户**：避免容器内进程以 root 运行，降低安全风险
- **Alpine 基础镜像**：相比完整 Debian 镜像，体积从 900MB 降至约 150MB

## Kubernetes 部署

当需要高可用、水平扩展时，应迁移到 Kubernetes 集群。

### Deployment 与 Service

```yaml
# k8s/server-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lowcode-server
  labels:
    app: lowcode-server
spec:
  replicas: 3
  selector:
    matchLabels:
      app: lowcode-server
  template:
    metadata:
      labels:
        app: lowcode-server
    spec:
      containers:
        - name: server
          image: registry.example.com/lowcode-server:v1.2.0
          ports:
            - containerPort: 3000
          envFrom:
            - configMapRef:
                name: lowcode-config
            - secretRef:
                name: lowcode-secrets
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 1000m
              memory: 512Mi
          livenessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 15
            periodSeconds: 20
          readinessProbe:
            httpGet:
              path: /ready
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: lowcode-server
spec:
  selector:
    app: lowcode-server
  ports:
    - port: 3000
      targetPort: 3000
  type: ClusterIP
```

### ConfigMap 与 Secret

```yaml
# k8s/config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: lowcode-config
data:
  NODE_ENV: "production"
  LOG_LEVEL: "info"
  DB_HOST: "postgres-service"
  DB_PORT: "5432"
  DB_NAME: "lowcode"
---
apiVersion: v1
kind: Secret
metadata:
  name: lowcode-secrets
type: Opaque
stringData:
  DB_PASSWORD: "your-secure-password"
  JWT_SECRET: "your-jwt-secret"
  REDIS_PASSWORD: "your-redis-password"
```

### Ingress 与域名配置

```yaml
# k8s/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: lowcode-ingress
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prospec"
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/rate-limit: "100"
spec:
  ingressClassName: nginx
  tls:
    - hosts:
        - lowcode.example.com
      secretName: lowcode-tls
  rules:
    - host: lowcode.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: lowcode-server
                port:
                  number: 3000
          - path: /
            pathType: Prefix
            backend:
              service:
                name: lowcode-client
                port:
                  number: 80
```

## 健康检查与监控

```typescript
// server/src/health.ts
import { Router } from 'express';
import { pool } from './db';
import { redis } from './redis';

const router = Router();

router.get('/health', (req, res) => {
  res.json({ status: 'ok', timestamp: Date.now() });
});

router.get('/ready', async (req, res) => {
  try {
    await pool.query('SELECT 1');
    await redis.ping();
    res.json({ status: 'ready', db: 'ok', redis: 'ok' });
  } catch (err) {
    res.status(503).json({ status: 'not ready', error: err.message });
  }
});

export default router;
```

## 常见误区

1. **数据卷不做持久化**：将数据库数据存在容器内部，容器重建后数据全部丢失。必须使用 Volume 或 PVC 持久化关键数据
2. **Secret 硬编码在 YAML 中**：将密码、密钥明文写在 Kubernetes 配置文件中并提交到 Git。应使用 Sealed Secrets 或外部密钥管理服务
3. **不做健康检查**：缺少 liveness/readiness 探针，Kubernetes 无法感知服务真实状态，可能将流量发送到已崩溃的实例

## 工程建议

1. **先用 Docker Compose 验证，再迁移 Kubernetes**：不要一上来就搞复杂的集群编排，先确保所有服务能在单机上正确运行
2. **镜像标签用版本号，不用 latest**：`latest` 标签无法追溯、无法回滚，生产环境必须使用明确的版本号（如 `v1.2.0`）
3. **将部署配置纳入版本控制**：所有 Kubernetes YAML、Helm values、Nginx 配置都应提交到 Git，实现基础设施即代码

## 小结

- Docker Compose 适合单机部署，通过 YAML 编排多容器（API/前端/数据库/缓存/代理）
- Dockerfile 多阶段构建配合非 root 用户，既能减小镜像体积又能提升安全性
- Kubernetes 通过 Deployment 实现高可用，Service 提供服务发现，Ingress 管理外部访问
- 域名配置需配合 Cert-Manager 实现 SSL 证书自动化签发和续期
- 健康检查是生产部署的必备项，区分 liveness（存活）和 readiness（就绪）两种探针

## 参考答案

### 练习一

**思路**：使用 node 镜像构建，nginx 镜像托管。构建阶段仅安装依赖并执行 build，运行阶段复制产物到 nginx。

**答案**：
```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine AS runner
RUN addgroup -g 1001 -S app && adduser -S app -u 1001
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
RUN chown -R app:app /usr/share/nginx/html
USER app
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
```

**要点**：
- 构建阶段使用 node 镜像，运行阶段切换为 nginx 镜像，最终体积约 25MB
- 必须配置 nginx 的 `try_files` 以支持前端路由

### 练习二

**思路**：Deployment 定义副本数和资源限制，Service 提供内部访问，HPA 根据 CPU 自动扩缩。

**答案**：
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lowcode-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: lowcode-api
  template:
    metadata:
      labels:
        app: lowcode-api
    spec:
      containers:
        - name: api
          image: registry.example.com/lowcode-api:v1.0.0
          ports:
            - containerPort: 3000
          resources:
            requests:
              cpu: 200m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi
---
apiVersion: v1
kind: Service
metadata:
  name: lowcode-api
spec:
  selector:
    app: lowcode-api
  ports:
    - port: 3000
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: lowcode-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: lowcode-api
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

**要点**：
- HPA 的 minReplicas 应与 Deployment 的 replicas 一致，避免缩容到更少
- resources.requests 是调度依据，必须合理设置，否则 HPA 计算利用率不准确
