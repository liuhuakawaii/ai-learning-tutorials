# 第五课：错误处理与重试

> **课程定位**：让工作流在面对失败时不是静默崩溃，而是优雅恢复和及时告警
> **前置知识**：了解 n8n 节点和表达式，有基本的 API 调用经验
> **预计时长**：35 分钟

---

## 场景引入

你的工作流运行了两周一切正常。第三周的某个凌晨，第三方 API 临时维护，返回 503 错误。工作流静默失败了，没有人知道。直到客户投诉说没收到通知，你才发现工作流已经停了 8 小时。

问题不在于 API 会挂——任何外部依赖都可能出问题。问题在于你的工作流**没有错误处理策略**。

完成本课学习后，你将能够：

1. 理解 n8n 的错误处理机制

3. 配置节点级别的重试策略
4. 实现错误告警通知
5. 设计容错的工作流架构

## 一、n8n 的错误模型

### 1.1 默认错误行为

当一个节点执行失败时，n8n 的默认行为是：

```
节点执行失败 → 工作流停止 → 记录错误日志 → 状态标记为 Error
```

这在开发阶段没问题，但生产环境需要更细粒度的控制。

### 1.2 错误类型

| 错误类型 | 原因 | 例子 |
|---------|------|------|
| API 错误 | 外部服务不可用 | 503 Service Unavailable |
| 认证错误 | 凭证过期或无效 | 401 Unauthorized |
| 数据错误 | 数据格式不对 | JSON 解析失败 |
| 超时错误 | 操作耗时过长 | 请求超过 30 秒 |
| 资源错误 | 资源不存在 | 404 Not Found |
| 限流错误 | API 调用频率超限 | 429 Too Many Requests |

### 1.3 错误数据结构

当节点失败时，n8n 会生成错误信息：

```json
{
  "error": {
    "message": "Request failed with status code 503",
    "description": "Service temporarily unavailable",
    "node": "HTTP Request",
    "timestamp": "2024-03-15T10:30:00.000Z",
    "execution_id": "exec_123456"
  }
}
```

## 二、节点级别错误处理

### 2.1 Continue On Fail

每个节点都有 `Continue On Fail` 选项。开启后，即使节点失败，工作流也会继续执行。

```
使用场景：
├── 非关键节点（如日志记录、通知）
├── 可以接受部分失败的批处理
└── 需要收集所有错误而不是遇到第一个就停止
```

配置方式：节点设置 → Options → Continue On Fail = true

开启后，失败节点的输出会包含错误信息：

```json
{
  "json": {
    "error": true,
    "message": "Request failed with status code 503",
    "statusCode": 503
  }
}
```

### 2.2 节点重试策略

n8n 支持在节点级别配置自动重试：

```
节点设置 → Options → On Error → Retry

配置项：
├── Max Retries: 最大重试次数（如 3 次）
├── Wait Between Retries: 重试间隔（如 1000ms）
└── Retry Policy: 重试策略
    ├── Fixed: 固定间隔
    └── Exponential: 指数退避
```

指数退避策略：

```
第 1 次重试：等 1 秒
第 2 次重试：等 2 秒
第 3 次重试：等 4 秒
第 4 次重试：等 8 秒
```

这种策略在应对临时性故障（如 API 限流）时非常有效。

### 2.3 错误输出分支

从 n8n 1.0 开始，每个节点都有一个额外的错误输出端口：

```
正常输出 ──→ 继续处理
     节点
错误输出 ──→ 错误处理分支
```

配置方式：节点设置 → Options → On Error → Error Output

错误输出的数据包含：

```json
{
  "json": {
    "error": {
      "message": "Connection timeout",
      "description": "Failed to connect to api.example.com:443",
      "code": "ETIMEDOUT"
    },
    "input_data": { ... }
  }
}
```

## 三、Error Trigger

### 3.1 工作流级别的错误捕获

Error Trigger 是一个特殊的触发器节点，当同一工作流中的任何节点失败时自动触发。

```
正常工作流：  A → B → C → D
                    ↓ (C 失败)
错误处理流：  Error Trigger → 告警 → 记录日志
```

### 3.2 配置 Error Trigger

1. 在同一工作流中添加 Error Trigger 节点
2. Error Trigger 会自动捕获该工作流的所有错误
3. 连接后续的错误处理节点

Error Trigger 的输出：

```json
{
  "execution": {
    "id": "exec_123456",
    "url": "http://localhost:5678/executions/exec_123456",
    "retryOf": null,
    "lastNodeExecuted": "HTTP Request",
    "mode": "trigger"
  },
  "workflow": {
    "id": "workflow_789",
    "name": "客户通知工作流"
  },
  "error": {
    "message": "Request failed with status code 503",
    "node": "HTTP Request",
    "timestamp": "2024-03-15T10:30:00.000Z"
  }
}
```

### 3.3 错误处理工作流

最佳实践是创建一个专门的错误处理工作流：

```
错误处理工作流：
Error Trigger
    ↓
判断错误类型
    ├─ 认证错误 → 通知管理员检查凭证
    ├─ 限流错误 → 等待后重试
    ├─ 数据错误 → 记录到错误日志表
    └─ 其他错误 → 发送告警通知
```

## 四、实现错误告警

### 4.1 Slack 告警

```
Error Trigger
    ↓
Set（格式化错误信息）
    ↓
Slack（发送告警）
```

Set 节点格式化：

```json
{
  "text": "🔴 工作流执行失败\n\n工作流：{{ $json.workflow.name }}\n节点：{{ $json.error.node }}\n错误：{{ $json.error.message }}\n时间：{{ $json.error.timestamp }}\n执行ID：{{ $json.execution.id }}",
  "channel": "#alerts"
}
```

### 4.2 邮件告警

```
Error Trigger
    ↓
Set（格式化邮件内容）
    ↓
Send Email（发送告警邮件）
```

### 4.3 错误日志记录

把错误信息记录到数据库，方便后续分析：

```
Error Trigger
    ↓
PostgreSQL（插入错误日志）
```

SQL：

```sql
INSERT INTO error_logs (workflow_id, workflow_name, error_node, error_message, execution_id, created_at)
VALUES (
  '{{ $json.workflow.id }}',
  '{{ $json.workflow.name }}',
  '{{ $json.error.node }}',
  '{{ $json.error.message }}',
  '{{ $json.execution.id }}',
  NOW()
)
```

## 五、容错工作流设计

### 5.1 幂等性设计

幂等性是指同一个操作执行多次，结果和执行一次相同。

```
非幂等：发送邮件 → 每次执行都会发一封新邮件
幂等：更新订单状态 → 执行多次结果都是"已处理"
```

实现幂等性的方法：

| 方法 | 说明 | 适用场景 |
|------|------|---------|
| 状态检查 | 执行前检查是否已处理 | 数据库更新 |
| 唯一 ID | 用唯一标识去重 | Webhook 回调 |
| 乐观锁 | 用版本号避免并发冲突 | 多系统同步 |

### 5.2 熔断器模式

当某个外部服务连续失败时，暂时停止调用，避免无意义的重试：

```
检查熔断器状态
    ├─ 熔断中 → 走降级路径
    ↓
调用外部服务
    ├─ 成功 → 重置失败计数
    ├─ 失败 → 增加失败计数
           ├─ 计数 > 阈值 → 触发熔断
           └─ 计数 < 阈值 → 继续
```

在 n8n 中实现：

```javascript
// Code 节点：检查熔断器
const cacheKey = 'circuit_breaker_api';
const failures = $getWorkflowStaticData('global')[cacheKey] || 0;

if (failures >= 5) {
  return [{ json: { circuit_open: true, message: '熔断器已打开，跳过 API 调用' } }];
}

return [{ json: { circuit_open: false, failures } }];
```

### 5.3 降级策略

当主路径失败时，使用备用方案：

```
主路径：调用 API A 获取数据
    ├─ 成功 → 继续
    ├─ 失败 → 降级路径
              ├─ 从缓存读取
              ├─ 调用备用 API B
              └─ 使用默认值
```

### 5.4 批量操作的容错

处理批量数据时，单条失败不应影响整体：

```javascript
// Code 节点：逐条处理，收集错误
const items = $input.all();
const successes = [];
const failures = [];

for (const item of items) {
  try {
    // 处理逻辑
    const result = processItem(item.json);
    successes.push({ json: result });
  } catch (error) {
    failures.push({
      json: {
        ...item.json,
        error: error.message
      }
    });
  }
}

// 正常数据走主输出，错误数据走错误输出
return [successes, failures];
```

## 六、监控与调试

### 6.1 执行日志

n8n 自动记录每次执行的详细日志：

- 执行 ID 和时间
- 每个节点的输入输出
- 错误信息和堆栈
- 执行耗时

在 n8n 编辑器中，点击左侧的 Executions 面板可以查看历史执行记录。

### 6.2 调试技巧

| 技巧 | 说明 |
|------|------|
| Pin Data | 固定某个节点的输出数据，不需要每次都调用真实 API |
| Step Through | 逐步执行每个节点，查看数据变化 |
| Output Panel | 查看节点的实际输出，确认数据结构 |
| Console Log | 在 Code 节点中用 `console.log` 输出调试信息 |

### 6.3 健康检查

为关键工作流添加健康检查：

```
Schedule Trigger（每 5 分钟）
    ↓
HTTP Request（调用自己的 Webhook）
    ↓
IF（响应正常？）
    ├─ 正常 → 无操作
    └─ 异常 → 告警通知
```

## 常见误区

### 误区一："开启 Continue On Fail 就万事大吉"

Continue On Fail 只是让工作流继续执行，但错误仍然发生。如果不处理错误输出，问题会被掩盖。应该在继续执行的同时记录和告警。

### 误区二："重试次数越多越好"

过多的重试会浪费资源，也可能加重已经过载的外部服务。一般重试 3 次就够了，超过 3 次应该告警并走降级路径。

### 误区三："Error Trigger 能捕获所有错误"

Error Trigger 只能捕获工作流级别的错误。如果错误发生在 Code 节点的 try/catch 中，Error Trigger 不会触发。需要在 Code 节点内部处理错误。

### 误区四："错误处理只在生产环境需要"

开发阶段就应该设计错误处理逻辑。等到上线再加，往往会遗漏边界情况。

---

## 工程建议

1. **为每个外部调用配置重试**：API 调用、数据库操作、文件读写都应该有重试策略。
2. **区分临时错误和永久错误**：503（临时不可用）应该重试，400（请求格式错误）不应该重试。
3. **告警要有上下文**：错误告警应该包含工作流名称、失败节点、错误信息和执行链接。
4. **记录错误趋势**：把错误信息写入数据库，定期分析错误频率和模式。
5. **定期测试错误路径**：模拟 API 失败、数据异常等场景，验证错误处理逻辑是否正常工作。

---

## 小结

- n8n 支持节点级别（Continue On Fail、重试策略）和工作流级别（Error Trigger）的错误处理
- 重试策略推荐指数退避，3 次重试通常足够
- Error Trigger 可以捕获工作流中的任何错误，用于告警和日志记录
- 容错设计包括幂等性、熔断器、降级策略和批量容错
- 错误告警应该包含足够的上下文信息，方便快速定位问题

## 参考答案

### 练习一

**思路**：用 HTTP Request 调用一个会返回 503 的 URL，配置节点重试策略。

**答案**：

1. **Manual Trigger**
2. **HTTP Request**：
   - URL: `https://httpstat.us/503`
   - Options → On Error → Retry
   - Max Retries: 3
   - Wait Between Retries: 2000
   - Retry Policy: Fixed

执行后观察：节点会尝试 4 次（1 次初始 + 3 次重试），每次间隔 2 秒，最终失败。

**要点**：
- httpstat.us 是一个用于测试 HTTP 状态码的公共服务
- 指数退避更适合生产环境：`Wait Between Retries: 1000, Policy: Exponential`
- 重试间隔单位是毫秒

### 练习二

**思路**：在工作流中添加 Error Trigger，连接 Slack 或文件写入节点。

**答案**：

在同一工作流中添加：

1. **Error Trigger**（自动捕获 HTTP Request 的失败）
2. **Set**（格式化告警信息）：
   ```json
   {
     "alert_text": "🔴 工作流执行失败\n\n工作流：客户数据同步\n节点：{{ $json.error.node }}\n错误：{{ $json.error.message }}\n时间：{{ $now.toFormat('yyyy-MM-dd HH:mm:ss') }}\n执行ID：{{ $json.execution.id }}"
   }
   ```
3. **Slack** 或 **Write Binary File**（发送告警）

**要点**：
- Error Trigger 不需要连接到其他节点，它独立存在于工作流中
- 重试 3 次后仍然失败，Error Trigger 才会被触发
- 告警信息应该包含足够的上下文

### 练习三

**思路**：用 Code 节点遍历订单数组，用 try/catch 处理单条失败，分别返回成功和失败的数据。

**答案**：

```javascript
const items = $input.all();
const successes = [];
const failures = [];

for (const item of items) {
  try {
    // 模拟处理逻辑：金额 > 500 的订单"处理失败"
    if (item.json.amount > 500) {
      throw new Error(`金额超限: ${item.json.amount}`);
    }
    
    successes.push({
      json: {
        order_id: item.json.order_id,
        amount: item.json.amount,
        status: 'processed'
      }
    });
  } catch (error) {
    failures.push({
      json: {
        order_id: item.json.order_id,
        amount: item.json.amount,
        error: error.message,
        status: 'failed'
      }
    });
  }
}

return [successes, failures];
```

连接方式：
- Code 节点的第一个输出 → 处理成功的订单
- Code 节点的第二个输出 → 处理失败的订单

**要点**：
- Code 节点可以返回多个数组，每个数组对应一个输出端口
- 单条失败不应该影响其他条目的处理
- 失败的数据应该保留原始信息，方便后续重试或人工处理
