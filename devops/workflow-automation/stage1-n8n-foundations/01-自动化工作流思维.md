# 第一课：自动化工作流思维

> **课程定位**：理解自动化工作流的本质，建立"用工作流替代脚本"的工程思维
> **前置知识**：有基本的 Web 开发经验，了解 API 和 HTTP 请求
> **预计时长**：30 分钟

---

## 场景引入

你的团队每周要从 5 个不同渠道收集客户反馈：邮件、Slack、表单、社交媒体、客服系统。有人手动把这些数据汇总到 Google Sheets，再发一封周报邮件。这个过程每周花 2 小时，偶尔还会漏数据或格式出错。你写了几个 Python 脚本来自动化，但脚本散落在不同服务器上，某天某个 API 改了，脚本静默失败了一周才被发现。

问题不在于"能不能写代码"，而在于：**这些分散的自动化缺乏统一的编排、监控和错误处理。**

## 一、什么是工作流

### 1.1 从手动流程到自动化

工作流是一系列按顺序或条件执行的步骤。日常工作中到处都是工作流：

```
客户下单 → 检查库存 → 扣款 → 发货通知 → 更新 CRM
         ↓
      库存不足 → 通知采购 → 生成补货单
```

手动执行这些步骤的问题：

| 问题 | 表现 |
|------|------|
| 速度慢 | 人工操作每步都有延迟 |
| 易出错 | 漏步骤、格式错、发错人 |
| 不可追踪 | 谁做的、什么时候做的、做到哪了 |
| 难以扩展 | 量大了人力跟不上 |

自动化工作流的核心价值：**把确定性流程交给机器，让人专注于需要判断力的环节。**

### 1.2 工作流的基本组成

```
┌─────────┐     ┌─────────┐     ┌─────────┐     ┌─────────┐
│  触发器  │ ──→ │  处理器  │ ──→ │  条件判断│ ──→ │  输出动作│
│ Trigger  │     │ Process  │     │ Condition│     │  Action  │
└─────────┘     └─────────┘     └─────────┘     └─────────┘
  新邮件到达      提取内容         是否紧急？       发 Slack
  定时触发        解析附件          ↓      ↓       更新数据库
  Webhook         格式转换        是      否       发送通知
                                 加急    普通
                                 通知    入队
```

每个工作流都由这四类组件构成：

- **触发器**：什么条件下启动工作流
- **处理器**：对数据做转换、 enrichment、校验
- **条件判断**：根据数据决定走哪条分支
- **输出动作**：调用外部服务、写数据库、发通知

## 二、为什么用 n8n 而不是写代码

### 2.1 写脚本的问题

你完全可以用 Python 或 Node.js 写自动化脚本。但当自动化规模扩大后，纯代码方案会遇到这些问题：

```python
# 一个典型的"胶水脚本"
import requests
import smtplib
from slack_sdk import WebClient

# 从 CRM 拉数据
customers = requests.get("https://crm.example.com/api/customers", 
                         headers={"Authorization": "Bearer xxx"}).json()

# 过滤活跃客户
active = [c for c in customers if c["last_active"] > "2024-01-01"]

# 发欢迎邮件
for customer in active:
    send_email(customer["email"], "欢迎回来", template="winback")

# 通知 Slack
slack = WebClient(token="xoxb-xxx")
slack.chat_postMessage(channel="#sales", 
                       text=f"已发送 {len(active)} 封召回邮件")
```

这段代码能跑，但存在以下问题：

| 问题 | 说明 |
|------|------|
| 无可视化 | 看不出流程全貌，新人接手困难 |
| 无重试 | API 调用失败就静默跳过 |
| 无监控 | 脚本挂了没人知道 |
| 无版本 | 改了代码不知道改了什么 |
| 硬编码 | 凭证散落在代码里 |
| 难扩展 | 加一个步骤就要改代码、测试、部署 |

### 2.2 工作流平台解决了什么

n8n 这类工作流平台的核心价值不是"不用写代码"，而是提供了**编排层**：

```
┌─────────────────────────────────────────────────┐
│                  n8n 编排层                       │
│                                                  │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐        │
│  │触发器 │→│处理器 │→│条件   │→│输出   │        │
│  └──────┘  └──────┘  └──────┘  └──────┘        │
│                                                  │
│  内置能力：                                       │
│  ✓ 可视化编排        ✓ 自动重试                   │
│  ✓ 执行日志          ✓ 错误通知                   │
│  ✓ 凭证管理          ✓ 版本控制                   │
│  ✓ 定时调度          ✓ Webhook 入口               │
│  ✓ 数据映射          ✓ 子工作流复用               │
└─────────────────────────────────────────────────┘
         ↕           ↕           ↕
     CRM API     Email API   Slack API
```

对比：

| 维度 | 写脚本 | n8n |
|------|--------|-----|
| 开发速度 | 快（小流程） | 快（任何规模） |
| 可视化 | 无 | 完整流程图 |
| 错误处理 | 自己实现 | 内置重试、告警 |
| 监控 | 自己搭 | 内置执行日志 |
| 凭证管理 | .env 文件 | 加密凭证库 |
| 协作 | 代码审查 | 可视化 + 导出 JSON |
| 扩展性 | 改代码 | 加节点 |

### 2.3 什么时候该写代码

工作流平台不是万能的。以下场景仍然适合写代码：

- **高性能计算**：大量数据处理、实时流处理
- **复杂算法**：机器学习训练、图像处理
- **低延迟要求**：毫秒级响应的 API
- **高度定制**：工作流平台的节点无法满足需求

最佳实践是**混合使用**：用 n8n 编排流程，关键节点调用自定义代码服务。

## 三、自动化工具对比

### 3.1 Zapier

```
定位：非技术用户的自动化工具
特点：5000+ 集成、模板丰富、上手极快
限制：免费版 100 任务/月、复杂逻辑受限、价格随量增长
适合：简单的"触发-动作"场景
```

Zapier 的核心概念是 Zap（一条自动化规则），由 Trigger + Action 组成。适合"收到邮件 → 保存到 Google Sheets"这类简单场景。

### 3.2 Make（原 Integromat）

```
定位：中级用户的可视化自动化
特点：可视化流程图、支持复杂分支、性价比高
限制：学习曲线比 Zapier 陡、社区较小
适合：需要分支和循环的中等复杂度场景
```

Make 用场景（Scenario）来组织工作流，支持 Router（分支）、Iterator（迭代）、Aggregator（聚合）等高级组件。

### 3.3 n8n

```
定位：开发者友好的开源自动化平台
特点：开源可自部署、支持代码节点、社区活跃、可扩展
限制：需要自己托管、部分高级功能付费
适合：需要自定义、数据隐私要求高、复杂工作流
```

n8n 的核心优势是**可自部署**和**代码节点**。你可以在任何节点中写 JavaScript/Python，也可以用 TypeScript 开发自定义节点。

### 3.4 选型决策

```
你是谁？ → 你的需求是什么？
  │
  ├─ 非技术用户 → 简单触发-动作 → Zapier
  │
  ├─ 有一定技术背景 → 中等复杂度 → Make
  │
  └─ 开发者/团队 → 复杂逻辑 + 数据隐私 → n8n
                    │
                    ├─ 需要自部署 → n8n（开源版）
                    │
                    └─ 不想运维 → n8n Cloud
```

## 四、识别自动化机会

### 4.1 适合自动化的特征

不是所有流程都值得自动化。适合自动化的流程有这些特征：

| 特征 | 说明 | 例子 |
|------|------|------|
| 重复性 | 同一流程每周执行 3 次以上 | 周报生成、数据同步 |
| 确定性 | 步骤固定，不需要人工判断 | 订单处理、发票生成 |
| 多系统 | 涉及 2 个以上系统的数据流转 | CRM → 邮件 → Slack |
| 时效性 | 需要快速响应 | 客户投诉、异常告警 |
| 容错性 | 偶尔出错可以重试或人工补救 | 数据同步、报表生成 |

### 4.2 不适合自动化的场景

| 场景 | 原因 |
|------|------|
| 需要创造性判断 | AI 可以辅助但不能完全替代 |
| 流程频繁变化 | 自动化的维护成本超过收益 |
| 一次性任务 | 不值得投入时间自动化 |
| 出错代价极高 | 需要人工确认每一步 |

### 4.3 ROI 评估框架

```
自动化价值 = (手动耗时 × 频率 × 人力成本) - (开发时间 + 维护成本)

示例：
- 手动处理一次订单同步：15 分钟
- 每周处理 20 次
- 人力成本：100 元/小时
- 年度成本：15/60 × 20 × 52 × 100 = 26,000 元

- 开发自动化工作流：8 小时
- 年度维护：20 小时
- 开发成本：28 × 100 = 2,800 元

净收益：23,200 元/年
```

## 常见误区

### 误区一："自动化能解决所有问题"

自动化只能解决确定性流程的问题。如果流程本身定义不清，自动化只会更快地制造混乱。先理清流程，再考虑自动化。

### 误区二："选最贵的工具就对了"

Zapier 的 5000+ 集成看起来很强大，但如果你只需要 5 个集成和一个条件分支，n8n 的免费版就够了。工具选型要看实际需求，不是功能列表。

### 误区三："自动化了就不需要人了"

大多数自动化流程仍然需要人工监控和异常处理。完全无人值守的自动化只适合非常成熟、出错后果可控的流程。

### 误区四："先自动化再说"

有些流程手动执行比自动化更高效，特别是执行频率低、流程变化快的场景。先评估 ROI，再决定是否自动化。

---

## 工程建议

1. **从小处开始**：先自动化一个高频、低风险的流程，积累经验后再扩展。
2. **文档先行**：自动化之前先画流程图，明确每个步骤的输入、输出和异常处理。
3. **保留人工入口**：自动化流程应该有"人工介入"的开关，而不是完全黑盒。
4. **监控比自动化更重要**：没有监控的自动化是定时炸弹。确保每个工作流都有失败告警。
5. **定期审视**：业务在变，自动化流程也需要定期审查和更新。

---

## 小结

- 工作流自动化的核心是**编排**，而不仅仅是"不用写代码"
- n8n 适合需要自定义和数据隐私的场景，Zapier 适合简单场景，Make 适合中等复杂度
- 自动化的前提是流程清晰、步骤确定、有明确的输入输出
- 先评估 ROI，再决定是否自动化
- 监控和错误处理比流程本身更重要

## 参考答案

### 练习一

**思路**：用 ROI 公式评估，优先自动化高频、多系统、耗时长的流程。

**答案**：

示例评估表：

| 流程 | 手动耗时 | 频率/周 | 涉及系统 | 年度成本 | 自动化成本 | ROI |
|------|---------|---------|---------|---------|-----------|-----|
| 客户数据同步 | 30 分钟 | 10 次 | CRM + 数据库 | 26,000 元 | 3,000 元 | 高 |
| 周报生成 | 2 小时 | 1 次 | 数据库 + 邮件 | 10,400 元 | 2,000 元 | 高 |
| 发票审批 | 10 分钟 | 5 次 | 财务系统 + 邮件 | 4,333 元 | 4,000 元 | 低 |

**要点**：
- 优先自动化涉及多系统、手动步骤多的流程
- 单一系统内的流程可能用系统自带的自动化功能更合适
- ROI 低于 2 倍的流程建议保持手动

### 练习二

**思路**：分析场景的技术需求——条件分支（urgent 标签）、多系统集成（GitHub、Jira、Slack、邮件）、Webhook 触发。

**答案**：

推荐 **n8n**，理由：

1. 需要条件分支（检查 urgent 标签），Zapier 的多步 Zaps 费用高
2. 涉及 4 个系统集成，Make 也可以但 n8n 的 GitHub 和 Jira 节点更成熟
3. Webhook 触发 + 条件逻辑 + 多路输出，n8n 的可视化编排更清晰
4. 如果团队有开发者，n8n 的代码节点可以在需要时做自定义处理

**要点**：
- Zapier 适合简单"触发-动作"，不适合有分支的场景
- Make 和 n8n 都可以，选 n8n 是因为社区更大、文档更全
- 如果团队没有开发者，Make 的可视化界面更友好

### 练习三

**思路**：拆解订单处理的每个步骤，识别正常流程和异常分支。

**答案**：

```
用户下单
  ↓
验证订单信息（地址、商品）
  ├─ 信息不完整 → 通知用户补充 → 结束
  ↓
检查库存
  ├─ 库存不足 → 通知用户 + 采购补货 → 结束
  ↓
发起支付
  ├─ 支付失败 → 通知用户重试 → 结束
  ↓
扣减库存
  ↓
分配物流
  ↓
发送订单确认邮件
  ↓
更新 CRM（客户订单记录）
  ↓
通知仓库发货
  ↓
发送发货通知（含物流单号）
```

**要点**：
- 每个步骤都有异常分支，不能只考虑正常流程
- 库存检查和支付之间需要事务性保证（要么都成功，要么都回滚）
- 通知用户和内部通知是并行的，不需要串行等待
