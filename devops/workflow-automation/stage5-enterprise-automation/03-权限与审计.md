## 场景引入

你的团队有 10 个人使用 n8n。开发人员需要创建和修改工作流，运营人员只能查看执行结果，管理员需要管理凭证和配置。你需要一套权限系统，确保每个人只能访问自己需要的功能。

## 一、n8n 权限模型

### 1.1 角色类型

| 角色 | 权限 |
|------|------|
| Owner | 所有权限 |
| Admin | 管理用户、工作流、凭证 |
| Member | 创建和编辑自己的工作流 |
| Viewer | 只读访问 |

### 1.2 团队管理

n8n 支持多团队（Multi-Team）：

```
Organization
├── Team A（开发团队）
│   ├── Admin: 张三
│   └── Member: 李四
├── Team B（运营团队）
│   ├── Admin: 王五
│   └── Viewer: 赵六
```

### 1.3 工作流权限

每个工作流可以设置：

| 权限 | 说明 |
|------|------|
| Personal | 只有创建者可访问 |
| Team | 团队成员可访问 |
| Organization | 所有人可访问 |

## 二、审计日志

### 2.1 记录什么

| 事件 | 说明 |
|------|------|
| workflow.created | 工作流创建 |
| workflow.updated | 工作流修改 |
| workflow.deleted | 工作流删除 |
| workflow.activated | 工作流激活 |
| workflow.deactivated | 工作流停用 |
| credential.created | 凭证创建 |
| credential.updated | 凭证修改 |
| user.login | 用户登录 |
| user.logout | 用户登出 |

### 2.2 实现审计日志

n8n 内置了审计日志功能（Enterprise 版本）。开源版本需要自行实现：

```
Webhook（接收 n8n 事件）
    ↓
Code（解析事件）
    ↓
PostgreSQL（写入审计表）
```

审计表设计：

```sql
CREATE TABLE audit_logs (
  id SERIAL PRIMARY KEY,
  timestamp TIMESTAMP DEFAULT NOW(),
  user_id VARCHAR(50),
  user_email VARCHAR(100),
  action VARCHAR(50),
  resource_type VARCHAR(50),
  resource_id VARCHAR(50),
  details JSONB,
  ip_address VARCHAR(50)
);
```

### 2.3 审计查询

```sql
-- 查询某用户的所有操作
SELECT * FROM audit_logs 
WHERE user_email = 'zhangsan@example.com'
ORDER BY timestamp DESC;

-- 查询凭证变更历史
SELECT * FROM audit_logs 
WHERE resource_type = 'credential'
AND action IN ('created', 'updated', 'deleted');

-- 查询异常登录
SELECT * FROM audit_logs 
WHERE action = 'user.login'
AND timestamp > NOW() - INTERVAL '24 hours'
AND details->>'success' = 'false';
```

## 三、合规策略

### 3.1 最小权限原则

```
开发人员：
✓ 创建/编辑自己的工作流
✓ 执行工作流
✗ 管理凭证
✗ 管理用户

运营人员：
✓ 查看工作流
✓ 查看执行结果
✗ 编辑工作流
✗ 管理凭证

管理员：
✓ 所有权限
```

### 3.2 凭证管理策略

| 策略 | 说明 |
|------|------|
| 集中管理 | 凭证由管理员统一创建 |
| 权限分离 | 创建者和使用者不同人 |
| 定期轮换 | 每 90 天轮换一次 |
| 审计追踪 | 记录所有凭证操作 |

### 3.3 数据保护

| 措施 | 说明 |
|------|------|
| 加密存储 | 凭证使用 AES-256 加密 |
| 传输加密 | 使用 HTTPS |
| 日志脱敏 | 审计日志不记录敏感数据 |
| 访问控制 | 限制 n8n 的网络访问 |

## 四、安全最佳实践

### 4.1 认证安全

```bash
# 使用 SSO/LDAP
N8N_AUTH_EXCLUDE_ENDPOINTS=/healthz
N8N_SSO_LOGIN_LABEL="使用企业账号登录"

# 密码策略
N8N_PASSWORD_MIN_LENGTH=12
N8N_PASSWORD_REQUIRE_UPPERCASE=true
N8N_PASSWORD_REQUIRE_NUMBER=true
```

### 4.2 网络安全

```nginx
# Nginx 配置
server {
    listen 443 ssl;
    server_name n8n.example.com;
    
    ssl_certificate /etc/ssl/cert.pem;
    ssl_certificate_key /etc/ssl/key.pem;
    
    # IP 白名单
    allow 10.0.0.0/8;
    deny all;
    
    location / {
        proxy_pass http://n8n:5678;
    }
}
```

### 4.3 定期安全审查

```
每月审查：
├── 用户列表（离职人员清理）
├── 凭证使用情况
├── 异常登录记录
├── 工作流权限设置
└── 网络访问日志
```

## 常见误区

### 误区一："权限设置一次就够了"

人员变动、角色调整都需要及时更新权限。建议每月审查一次。

### 误区二："审计日志占用空间就关掉"

审计日志是合规和安全调查的关键证据。不能关闭，需要定期归档。

### 误区三："内网不需要安全防护"

内部威胁同样危险。权限控制和审计在内网同样重要。

---

## 工程建议

1. **最小权限**：每个人只获得完成工作所需的最小权限。
2. **定期审查**：每月审查用户权限和审计日志。
3. **凭证集中管理**：凭证由管理员统一创建和维护。
4. **SSO 集成**：使用企业 SSO 统一认证。
5. **安全培训**：定期对团队进行安全意识培训。

## 小结

- n8n 支持 Owner、Admin、Member、Viewer 四种角色
- 审计日志记录所有关键操作，支持合规和安全调查
- 最小权限原则是权限设计的基础
- 凭证管理需要集中化、定期轮换和审计追踪
- 安全审查应该定期进行
