## 场景引入

你的电商客户需要一个自动化订单处理系统：

1. 接收来自多个渠道的订单（Webhook、CSV 导入、API 轮询）
2. 校验订单信息（地址、商品、金额）
3. 检查库存，自动分配仓库
4. 根据金额走不同审批流程
5. 批量更新数据库
6. 发送确认通知
7. 生成每日汇总报表

这是一个典型的多分支、多循环、多子工作流的复杂场景。

## 一、系统架构

### 1.1 整体设计

```
触发层：
├── Webhook（实时订单）
├── Schedule（CSV 导入）
└── Schedule（API 轮询）

处理层（子工作流）：
├── validate-order：数据验证
├── check-inventory：库存检查
├── route-approval：审批路由
└── send-notification：通知服务

数据层：
├── PostgreSQL（订单数据库）
└── S3（CSV 文件存储）

输出层：
├── 邮件通知
├── Slack 通知
└── 每日报表
```

### 1.2 数据模型

```sql
-- 订单表
CREATE TABLE orders (
  order_id VARCHAR(50) PRIMARY KEY,
  customer_id VARCHAR(50),
  customer_name VARCHAR(100),
  customer_email VARCHAR(100),
  items JSONB,
  total_amount DECIMAL(10,2),
  status VARCHAR(20),

  warehouse_id VARCHAR(20),

  product_id VARCHAR(50) PRIMARY KEY,

  id SERIAL PRIMARY KEY,
  order_id VARCHAR(50),
```

## 二、实现步骤

### 2.1 Step 1：多触发源

```
Webhook（POST /orders）──────────┐
                                 ├→ Set（统一格式）→ 主处理流程
Schedule（每小时拉取 CSV）────────┘
```

**Webhook 触发器**：接收实时订单

**CSV 导入触发器**：

```
Schedule（每小时）
    ↓
S3（下载最新 CSV）
    ↓
Spreadsheet File（解析 CSV）
    ↓
Loop（逐条处理）
    ↓
主处理流程
```

### 2.2 Step 2：数据验证子工作流

```
输入：原始订单数据
    ↓
Code（验证逻辑）
    ├─ 检查必填字段
    ├─ 验证邮箱格式
    ├─ 验证金额范围
    └─ 验证商品 ID 格式
    ↓
输出：{ valid: true/false, errors: [], data: {...} }
```

验证逻辑：

```javascript
const order = $input.first().json;
const errors = [];

// 必填字段
if (!order.order_id) errors.push('缺少 order_id');
if (!order.customer_id) errors.push('缺少 customer_id');
if (!order.customer_email) errors.push('缺少 customer_email');
if (!order.items || order.items.length === 0) errors.push('订单无商品');

// 邮箱格式
if (order.customer_email && !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(order.customer_email)) {
  errors.push('邮箱格式无效');
}

// 金额验证
const total = order.items?.reduce((sum, item) => sum + (item.price * item.qty), 0) || 0;
if (total <= 0) errors.push('订单金额必须大于 0');
if (total !== order.total_amount) errors.push('金额计算不一致');

// 商品 ID 格式
for (const item of order.items || []) {
  if (!item.product_id || !item.product_id.startsWith('PROD-')) {
    errors.push(`商品 ID 格式无效: ${item.product_id}`);
  }
}

return [{
  json: {
    valid: errors.length === 0,
    errors,
    data: { ...order, calculated_total: total }
  }
}];
```

### 2.3 Step 3：库存检查子工作流

```
输入：订单商品列表
    ↓
Loop（遍历商品）
    ↓
PostgreSQL（查询库存）
    ↓
IF（库存充足？）
    ├─ 是 → 标记可用仓库
    └─ 否 → 标记缺货
    ↓
输出：{ available: true/false, items: [{product_id, available_qty, warehouse}] }
```

库存检查 SQL：

```sql
SELECT product_id, quantity, warehouse_id
FROM inventory
WHERE product_id = ANY({{ $json.product_ids }})
AND quantity >= {{ $json.required_qty }}
ORDER BY quantity DESC
LIMIT 1;
```

### 2.4 Step 4：审批路由

```
输入：订单数据
    ↓
Code（计算审批级别）
    ↓
Switch（按金额路由）
    ├─ < 1000    → 自动通过
    ├─ 1000-5000 → 经理审批
    └─ > 5000    → 总监审批
    ↓
输出：{ approval_level, requires_approval, approver }
```

### 2.5 Step 5：主流程编排

```
触发源
    ↓
Execute Workflow（数据验证）
    ↓
IF（验证通过？）
    ├─ 否 → 记录错误 → 通知
    ↓
Execute Workflow（库存检查）
    ↓
IF（库存充足？）
    ├─ 否 → 通知缺货 → 标记待补货
    ↓
Execute Workflow（审批路由）
    ↓
IF（需要审批？）
    ├─ 是 → 发送审批请求 → Wait（等待审批）
    ↓
PostgreSQL（更新订单状态为 confirmed）
    ↓
并行：
├─ 发送确认邮件
├─ Slack 通知仓库
└─ 更新 CRM
```

### 2.6 Step 6：批处理更新

```
Schedule（每天凌晨 2:00）
    ↓
PostgreSQL（查询当日订单）
    ↓
Split In Batches（每批 100）
    ↓
Code（计算统计）
    ↓
PostgreSQL（更新统计表）
    ↓ 回连
    ↓ 完成后
Code（生成报表）
    ↓
Send Email（发送每日报表）
```

报表生成：

```javascript
const orders = $input.all();

const stats = {
  date: $now.toFormat('yyyy-MM-dd'),
  total_orders: orders.length,
  total_amount: orders.reduce((sum, o) => sum + o.json.total_amount, 0),
  by_status: {},
  by_approval_level: {},
  top_products: {}
};

for (const order of orders) {
  const o = order.json;
  stats.by_status[o.status] = (stats.by_status[o.status] || 0) + 1;
  stats.by_approval_level[o.approval_level] = (stats.by_approval_level[o.approval_level] || 0) + 1;
  
  for (const item of o.items || []) {
    stats.top_products[item.product_id] = (stats.top_products[item.product_id] || 0) + item.qty;
  }
}

// 排序取 Top 10
const topProducts = Object.entries(stats.top_products)
  .sort(([,a], [,b]) => b - a)
  .slice(0, 10);

return [{
  json: {
    ...stats,
    top_products: Object.fromEntries(topProducts),
    average_order_value: Math.round(stats.total_amount / stats.total_orders)
  }
}];
```

## 三、错误处理设计

### 3.1 全局错误处理

```
Error Trigger
    ↓
Code（分类错误）
    ↓
Switch（按错误类型）
    ├─ 认证错误 → 通知管理员
    ├─ 数据错误 → 记录到错误表
    ├─ 外部服务错误 → 重试队列
    └─ 未知错误 → 告警 + 日志
```

### 3.2 订单级错误隔离

```javascript
// 循环中处理单条订单错误
const order = $input.first().json;

try {
  const result = await processOrder(order);
  return [{ json: { success: true, order_id: order.order_id, ...result } }];
} catch (error) {
  // 记录错误但不中断
  await logError(order.order_id, error.message);
  return [{ json: { success: false, order_id: order.order_id, error: error.message } }];
}
```

## 常见误区

### 误区一："所有逻辑放在一个工作流中"

复杂的订单处理应该拆分成多个子工作流。每个子工作流负责一个明确的功能，便于测试和维护。

### 误区二："不需要数据验证"

来自外部的数据永远不可信。必须在处理之前验证数据的完整性和格式。

### 误区三："批处理不需要错误处理"

批处理中的单条失败不应该影响整个批次。需要逐条捕获错误，记录日志，继续处理。

---

## 工程建议

1. **子工作流拆分**：验证、库存、审批、通知各自独立。
2. **数据验证前置**：在进入业务逻辑之前完成所有验证。
3. **错误隔离**：单条订单的失败不影响其他订单。
4. **监控告警**：关键指标（处理量、失败率、延迟）要有监控。
5. **幂等设计**：Webhook 可能重复推送，订单处理要幂等。

## 小结

- 订单处理系统涉及多触发源、多分支、多循环和多子工作流
- 子工作流实现模块化：验证、库存、审批、通知各自独立
- 批量操作需要分批处理和错误隔离
- 监控和告警是生产环境的必要保障
- 测试要覆盖正常流程和各种异常场景

## 参考答案

### 练习一

**思路**：按步骤实现各子工作流，主流程串联调用。

**答案**：

主工作流结构：
```
Webhook → 验证子流程 → IF(valid) → 库存子流程 → IF(available) → 更新DB → 通知
```

关键点：
- 每个子流程返回 `{ success: boolean, data: {...} }`
- 主流程根据返回值决定下一步
- 失败时记录到错误表

### 练习二

**思路**：Schedule Trigger → PostgreSQL 查询 → Code 统计 → 邮件发送。

**答案**：

```javascript
const orders = $input.all();
const today = $now.toFormat('yyyy-MM-dd');

const stats = {
  date: today,
  total: orders.length,
  total_amount: orders.reduce((s, o) => s + o.json.total_amount, 0),
  by_status: {}
};

for (const o of orders) {
  stats.by_status[o.json.status] = (stats.by_status[o.json.status] || 0) + 1;
}

const report = `订单日报 ${today}
总订单数: ${stats.total}
总金额: ¥${stats.total_amount.toFixed(2)}
状态分布: ${JSON.stringify(stats.by_status)}`;

return [{ json: { subject: `订单日报 ${today}`, body: report } }];
```

### 练习三

**思路**：在每个关键节点添加错误捕获和处理。

**答案**：

- 验证失败 → PostgreSQL INSERT INTO error_logs
- 库存不足 → Slack 通知 #purchasing

- 全局 Error Trigger → 告警 + 日志
