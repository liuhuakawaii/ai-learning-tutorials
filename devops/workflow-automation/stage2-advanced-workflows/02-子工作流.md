> **课程定位**：掌握工作流复用、参数传递和错误传播机制
> **前置知识**：了解 n8n 的基本节点和条件分支

## 场景引入

你的系统有 5 个不同的工作流，每个都需要"发送通知"这个功能：有的发邮件，有的发 Slack，有的发短信。你在每个工作流里都复制粘贴了相同的节点。现在要改通知模板，你需要修改 5 个地方。更要命的是，有个 bug 你只修了 3 个工作流，另外 2 个还在用旧逻辑。

这就是子工作流要解决的问题：**把公共逻辑抽取成可复用的模块**。

## 一、子工作流基础

### 1.1 什么是子工作流

子工作流是被其他工作流调用的独立工作流。它有明确的输入、处理逻辑和输出。

```
主工作流：
    节点 A → 调用子工作流 → 节点 C
                   ↓
              子工作流内部：
              参数接收 → 处理 → 返回结果
```

### 1.2 Execute Workflow 节点

在主工作流中使用 Execute Workflow 节点调用子工作流：

```json
{
  "workflowId": "workflow_123",
  "mode": "each"  // 每个输入项调用一次
}
```

调用模式：

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| each | 每个输入项调用一次 | 逐条处理 |
| once | 所有输入项一次性传入 | 批量处理 |

### 1.3 子工作流的触发器

子工作流使用 "Execute Workflow Trigger" 作为触发器：

```
子工作流：
Execute Workflow Trigger
    ↓
处理逻辑
    ↓
输出结果
```

Execute Workflow Trigger 接收主工作流传入的数据，格式和普通节点的输入相同。

## 二、参数设计

### 2.1 输入参数

子工作流通过 Execute Workflow Trigger 接收输入数据：

```json
// 主工作流传入的数据
[
  {
    "json": {
      "action": "send_email",
      "to": "zhangsan@example.com",
      "subject": "订单确认",
      "body": "您的订单已确认..."
    }
  }
]
```

### 2.2 输出参数

子工作流的最后一个节点的输出会返回给主工作流：

```json
// 子工作流返回的数据
[
  {
    "json": {
      "success": true,
      "message_id": "msg_123456",
      "sent_at": "2024-03-15T10:30:00Z"
    }
  }
]
```

### 2.3 参数验证

在子工作流中验证输入参数：

```javascript
// Code 节点：参数验证
const input = $input.first().json;
const errors = [];

if (!input.action) errors.push('缺少 action 参数');
if (!input.to) errors.push('缺少 to 参数');
if (input.action === 'send_email' && !input.subject) {
  errors.push('发送邮件需要 subject 参数');
}

if (errors.length > 0) {
  return [{
    json: {
      success: false,
      errors: errors
    }
  }];
}

return [{ json: { valid: true, ...input } }];
```

## 三、错误传播

### 3.1 默认行为

子工作流中的错误会传播到主工作流：

```
主工作流：A → Execute Workflow → C
                  ↓
             子工作流：X → Y（失败）→ Z
                  ↓
             错误传播到主工作流
             Execute Workflow 节点标记为失败
```

### 3.2 错误处理策略

**策略一：子工作流内部处理**

```
子工作流：
Execute Workflow Trigger
    ↓
处理逻辑
    ↓
Error Trigger → 返回错误信息
```

**策略二：主工作流处理**

```
主工作流：
Execute Workflow
    ├─ 正常输出 → 继续处理
    └─ 错误输出 → 错误处理分支
```

### 3.3 返回错误而不中断

在子工作流中返回错误信息，而不是抛出错误：

```javascript
try {
  const result = await processData($input.first().json);
  return [{ json: { success: true, ...result } }];
} catch (error) {
  return [{ json: { success: false, error: error.message } }];
}
```

主工作流检查返回结果：

```json
{
  "conditions": {
    "boolean": [
      {
        "value1": "={{ $json.success }}",
        "value2": true
      }
    ]
  }
}
```

## 四、实战：通知服务子工作流

### 4.1 设计

创建一个通用的通知服务子工作流：

```
输入参数：
{
  "channel": "email" | "slack" | "sms",
  "to": "目标地址",
  "subject": "标题（邮件需要）",
  "body": "内容",
  "priority": "high" | "normal" | "low"
}

输出参数：
{
  "success": true | false,
  "message_id": "消息ID",
  "channel": "使用的渠道",
  "sent_at": "发送时间"
}
```

### 4.2 实现

**子工作流结构：**

```
Execute Workflow Trigger
    ↓
Code（参数验证）
    ↓
Switch（按 channel 分支）
    ├─ email → Send Email
    ├─ slack → Slack
    └─ sms   → HTTP Request（短信 API）
    ↓
Set（统一输出格式）
```

**参数验证：**

```javascript
const input = $input.first().json;
const errors = [];

const validChannels = ['email', 'slack', 'sms'];
if (!validChannels.includes(input.channel)) {
  errors.push(`无效的渠道: ${input.channel}，支持: ${validChannels.join(', ')}`);
}
if (!input.to) errors.push('缺少 to 参数');
if (!input.body) errors.push('缺少 body 参数');
if (input.channel === 'email' && !input.subject) {
  errors.push('邮件通知需要 subject 参数');
}

if (errors.length > 0) {
  return [{ json: { success: false, errors } }];
}

return [{ json: { valid: true, ...input } }];
```

**Switch 分支后，每个渠道节点的输出统一格式：**

```javascript
// Set 节点
{
  "success": true,
  "message_id": "={{ $json.id ?? $json.message_id ?? '' }}",
  "channel": "={{ $json.channel ?? 'unknown' }}",
  "sent_at": "={{ $now.toISO() }}"
}
```

### 4.3 在主工作流中调用

```
Webhook（新订单）
    ↓
Execute Workflow（调用通知服务）
    - workflowId: 通知服务子工作流 ID
    - 传入参数：
      {
        "channel": "email",
        "to": "={{ $json.customer_email }}",
        "subject": "订单确认",
        "body": "您的订单 {{ $json.order_id }} 已确认"
      }
    ↓
IF（通知成功？）
    ├─ 成功 → 更新订单状态
    └─ 失败 → 重试或告警
```

## 五、高级模式

### 5.1 动态选择子工作流

根据条件调用不同的子工作流：

```javascript
// Code 节点：确定要调用的工作流 ID
const input = $input.first().json;

const workflowMap = {
  'order_processing': 'workflow_001',
  'customer_onboarding': 'workflow_002',
  'invoice_generation': 'workflow_003'
};

const workflowId = workflowMap[input.process_type];
if (!workflowId) {
  throw new Error(`未知的处理类型: ${input.process_type}`);
}

return [{ json: { ...input, workflow_id: workflowId } }];
```

### 5.2 子工作流编排

用子工作流构建复杂的处理管道：

```
主工作流：
    数据验证子流程 → 业务处理子流程 → 通知子流程
         ↓                ↓                ↓
    返回验证结果      返回处理结果      返回通知结果
```

### 5.3 共享状态

子工作流和主工作流之间通过输入输出传递数据。如果需要共享状态，可以用：

1. **数据库**：写入共享的数据库表
2. **静态数据**：`$getWorkflowStaticData('global')`（同一工作流内）
3. **外部存储**：Redis、文件等

## 六、工作流模块化设计原则

### 6.1 单一职责

每个子工作流只做一件事：

```
✓ 好的设计：
- send-notification：发送通知
- validate-order：验证订单
- update-crm：更新 CRM

✗ 不好的设计：
- process-everything：处理所有事情
```

### 6.2 明确的接口

子工作流应该有清晰的输入输出文档：

```json
{
  "name": "send-notification",
  "description": "发送通知到指定渠道",
  "input": {
    "channel": "string (email|slack|sms)",
    "to": "string (目标地址)",
    "body": "string (通知内容)"
  },
  "output": {
    "success": "boolean",
    "message_id": "string"
  }
}
```

### 6.3 错误处理契约

定义子工作流的错误处理方式：

- 返回 `{ success: false, error: "..." }` 表示业务错误
- 抛出异常表示系统错误
- 主工作流根据 `success` 字段决定后续处理

---

## 常见误区

### 误区一："子工作流会增加延迟"

子工作流的调用开销很小（毫秒级）。相比它带来的可维护性和复用性，这点开销可以忽略。

### 误区二："子工作流不能访问主工作流的数据"

子工作流只能访问通过参数传入的数据。如果需要主工作流的某些数据，必须显式传入。

### 误区三："修改子工作流会影响所有调用方"

是的，这正是子工作流的优势。但修改时需要考虑向后兼容性，避免破坏已有的调用方。

---

## 工程建议

1. **抽取公共逻辑为子工作流**：通知、数据验证、日志记录等通用功能应该抽成子工作流。
2. **参数要明确**：子工作流的输入输出应该有清晰的文档和验证。
3. **错误要可追溯**：子工作流的错误应该包含足够的上下文信息。
4. **版本管理**：修改子工作流前先备份，确保可以回滚。
5. **测试要独立**：子工作流应该能独立测试，不依赖主工作流。

---

## 小结

- 子工作流通过 Execute Workflow 节点调用，用 Execute Workflow Trigger 接收参数
- 参数通过 JSON 数据传递，子工作流的输出返回给主工作流
- 错误可以内部处理（返回 success: false）或传播到主工作流
- 模块化设计原则：单一职责、明确接口、错误处理契约
- 子工作流是构建可维护自动化系统的关键

## 参考答案

### 练习一

**思路**：创建子工作流（Execute Workflow Trigger → Switch → Email/Slack），主工作流调用它。

**答案**：

子工作流：
1. Execute Workflow Trigger
2. Switch（channel 字段）
   - email → Send Email 节点
   - slack → Slack 节点
3. Set（统一输出格式）

主工作流：
1. Manual Trigger
2. Execute Workflow
   - workflowId: 子工作流 ID
   - 传入：`{ channel: "email", to: "test@example.com", subject: "测试", body: "Hello" }`

**要点**：
- 子工作流的 ID 可以在编辑器的 URL 中找到
- 传参时用表达式动态设置

### 练习二

**思路**：在子工作流开头添加 Code 节点做参数验证。

**答案**：

在 Execute Workflow Trigger 之后添加 Code 节点：

```javascript
const input = $input.first().json;
const errors = [];
if (!input.channel) errors.push('缺少 channel');
if (!input.to) errors.push('缺少 to');
if (!input.body) errors.push('缺少 body');
if (input.channel === 'email' && !input.subject) errors.push('邮件需要 subject');

if (errors.length > 0) {
  return [{ json: { success: false, errors } }];
}
return [{ json: { valid: true, ...input } }];
```

后续 IF 节点判断 valid 字段，false 时直接返回错误。

### 练习三

**思路**：主工作流串联三个 Execute Workflow 节点。

**答案**：

```
Manual Trigger
    ↓
Execute Workflow 1（数据验证）
    - 传入原始数据
    - 返回 { valid: true/false, data: ... }
    ↓
IF（验证通过？）
    ├─ False → 结束（返回验证错误）
    ↓
Execute Workflow 2（数据处理）
    - 传入验证后的数据
    - 返回 { success: true, result: ... }
    ↓
Execute Workflow 3（结果通知）
    - 传入处理结果
    - 返回 { sent: true }
```

**要点**：
- 每个子工作流独立验证输入
- 主工作流根据子工作流的返回决定下一步
- 失败时可以记录日志或通知管理员
