# 任务分配

## 场景引入

团队接到一个紧急需求：要在两周内完成支付系统的重构。新经理老王看了看团队六个人，心想："小张技术最强，这种关键任务只能交给他。"于是把整个重构任务都分给了小张，其他人继续做日常需求。

两周后，小张确实完成了重构，代码质量很高。但问题来了：小张连续加班两周，身心俱疲；其他团队成员觉得核心任务从来轮不到自己，缺乏成长机会；而且整个团队只有小张一个人理解新的支付架构，他一旦请假或离职，系统就成了黑盒。

老王犯了新经理最常见的错误：**把任务分给"最能干的人"，而不是分给"最合适的人"**。任务分配不是简单的"谁有空谁做"，而是一门需要系统思考的管理技术。

## 学习目标

- 区分委派与授权的本质差异，理解两者的适用场景
- 掌握识人矩阵（能力 × 意愿），根据下属状态选择管理风格
- 学会使用 RACI 模型明确角色分工
- 建立有效的任务跟进机制（站会、周报、里程碑）
- 识别并避免任务分配的五个常见陷阱

## 委派 vs 授权

很多管理者把"委派"和"授权"混为一谈，但它们有本质区别：

```
委派（Delegation）：
  "小王，你来实现这个 API 接口，按我给的方案做。"
  → 你保留决策权，下属负责执行
  → 适合：下属能力不足、任务风险高、时间紧迫

授权（Empowerment）：
  "小王，这个功能模块交给你，你来决定技术方案和实现方式。"
  → 你把决策权也交给下属，只保留监督权
  → 适合：下属能力成熟、任务有成长价值、可以容忍一定的试错
```

| 维度 | 委派 | 授权 |
|------|------|------|
| 决策权 | 在管理者手中 | 在下属手中 |
| 关注点 | 过程和方法 | 结果和目标 |
| 管理者角色 | 指导者 | 支持者 |
| 下属成长 | 学习执行 | 学习决策 |
| 风险 | 低（过程可控） | 中高（结果导向） |
| 适用场景 | 新人、高风险任务 | 成熟员工、成长型任务 |

**关键认知：** 好的任务分配是**逐步从委派过渡到授权**。一个下属刚加入时，你需要委派具体任务并指导方法；当他逐渐成熟，你应该逐步授权，让他自己做决策。如果你永远停留在委派模式，下属永远学不会独立。

## 识人矩阵：能力 × 意愿

任务分配的第一步是了解你的下属。最实用的工具是**情境领导力模型**，它用两个维度来评估下属状态：

```
            高意愿
              │
     ┌────────┼────────┐
     │   热情的初学者   │
     │   (S2: 教练型)   │
     │                  │
     ├────────┼────────┤
     │   沮丧的学习者   │
     │   (S3: 支持型)   │
     │                  │
低能力 ───────┼────────── 高能力
     │                  │
     │   消极的执行者   │
     │   (S4: 委派型)   │
     │                  │
     ├────────┼────────┤
     │   有能力但缺乏    │
     │   信心的员工      │
     │   (S1: 指令型)   │
     │                  │
     └────────┼────────┘
              │
            低意愿
```

**四种管理风格：**

| 象限 | 下属特征 | 管理风格 | 任务分配方式 |
|------|----------|----------|-------------|
| S1 低能力高意愿 | 新入职、热情但缺乏经验 | 指令型 | 明确任务、详细指导、高频跟进 |
| S2 低能力低意愿 | 新手遇到挫折、缺乏信心 | 教练型 | 明确任务、鼓励参与、多给正面反馈 |
| S3 高能力低意愿 | 老员工倦怠、缺乏动力 | 支持型 | 共同决策、激发主动性、关注动机 |
| S4 高能力高意愿 | 核心骨干、自驱力强 | 委派型 | 授权决策、只关注结果、提供资源 |

**重要提醒：** 同一个下属在不同任务上可能处于不同象限。一个后端专家在做前端任务时可能是 S1（低能力高意愿），做后端任务时是 S4（高能力高意愿）。你要根据具体任务来判断，而不是给人贴固定标签。

## RACI 模型

当一个任务涉及多个人时，角色不清晰是最大的混乱来源。RACI 模型帮你明确每个人的职责：

```
RACI 模型

  R - Responsible（执行者）：实际做这件事的人
  A - Accountable（负责人）：对结果负最终责任的人（每个任务只能有一个）
  C - Consulted（咨询者）：做决策前需要咨询的人
  I - Informed（知情者）：决策后需要通知的人
```

**示例：支付系统重构的 RACI 矩阵**

| 任务 | 老王(经理) | 小张(高级) | 小王(中级) | 小李(初级) |
|------|-----------|-----------|-----------|-----------|
| 技术方案设计 | A | R | C | I |
| 数据库迁移 | A | C | R | I |
| API 重构 | A | R | R | I |
| 单元测试编写 | I | C | R | R |
| Code Review | A | R | C | I |
| 上线部署 | A | R | C | I |

**RACI 的好处：**
- 避免"三个和尚没水喝"——每个人都知道自己该做什么
- 避免"越俎代庖"——不会有人去做别人负责的事
- 避免"信息孤岛"——该知道的人都会被通知到

## 跟进机制

分配任务不是"扔出去就不管了"。你需要建立合适的跟进机制，既不过度干预，也不失控。

```
跟进频率与任务风险匹配：

  低风险 + 低复杂度  →  周报 + 里程碑检查
  低风险 + 高复杂度  →  日站会 + 周报
  高风险 + 低复杂度  →  日站会 + 关键节点 review
  高风险 + 高复杂度  →  每日 sync + 代码审查 + 里程碑演示
```

**日站会（15 分钟）**
- 昨天完成了什么？
- 今天计划做什么？
- 有什么阻塞？

**周报模板**
```
本周进展：
- [完成] 支付接口重构，已通过 Code Review
- [进行中] 数据库迁移脚本，进度 70%

下周计划：
- 完成数据库迁移
- 开始单元测试编写

阻塞/风险：
- 测试环境数据库权限还没申请下来，需要经理协助
```

**里程碑检查**
在项目开始时定义 3-5 个里程碑，每个里程碑有明确的交付物和时间点。在里程碑节点进行正式的进度审查。

## 常见误区

### 陷阱一：微管理

**症状：** 每天问下属"做到哪了？"、要求每一步都汇报、对实现细节指手画脚。

**后果：** 下属失去自主性，变成"等指令"的执行者；管理者时间被大量消耗。

**解法：** 用里程碑替代过程监控。明确"什么时候完成什么"，而不是"每一步怎么做"。

### 陷阱二：甩手掌柜

**症状：** 任务分出去后就不管了，直到最后才发现问题。

**后果：** 项目延期、质量不达标、下属觉得不被支持。

**解法：** 建立固定的检查点。不是干预，而是"我在关注，需要帮助随时说"。

### 陷阱三：只分给最能干的人

**症状：** 所有重要任务都给同一两个人，其他人做边角料。

**后果：** 能干的人累死，其他人没有成长机会；团队形成"单点依赖"。

**解法：** 用识人矩阵评估每个人，把任务分给"合适的人"而不是"最强的人"。对于成长型任务，允许 80 分的交付，换取团队能力的提升。

### 陷阱四：没有明确截止日期

**症状：** "这个不急，你有空的时候做一下。"

**后果：** 任务永远排在最后，永远不会完成。

**解法：** 每个任务必须有明确的截止日期和验收标准。"周五下班前完成，通过所有单元测试"比"有空做一下"有效一万倍。

### 陷阱五：只分配执行，不分配思考

**症状：** 所有设计方案你来做，下属只负责写代码。

**后果：** 下属永远学不会独立思考，你永远是瓶颈。

**解法：** 逐步让下属参与设计决策。从"你来写实现方案，我来 review"开始，逐步过渡到"你来做技术决策，我只关注方向"。

## 工程建议

1. **分配任务时说清楚三件事**：目标（为什么做）、边界（做什么不做什么）、标准（怎样算完成）。
2. **给下属拒绝的权利**。如果下属说"我做不了"，不要强迫，而是了解原因，调整任务或提供支持。
3. **公开透明地分配任务**。让团队知道每个任务分给了谁、为什么分给他。避免"暗箱操作"导致的不公平感。
4. **保留 20% 的 buffer**。不要把团队的时间排满，留出空间应对突发需求和技术债务。
5. **定期复盘任务分配**。每个迭代结束时回顾：任务分配是否合理？有没有人过载？有没有人没有挑战？

## 小结

任务分配是管理者最核心的工作之一。做好任务分配需要三步：

1. **识人**：用能力 × 意愿矩阵了解每个下属的状态，选择对应的管理风格
2. **分工**：用 RACI 模型明确每个任务中每个人的角色和责任
3. **跟进**：根据任务风险等级选择合适的跟进频率，既不过度干预也不失控

记住：**好的任务分配不是让最强的人做最多的事，而是让每个人在合适的位置上发挥最大的价值。**

## 参考答案

### 练习一

**思路**：识人矩阵的关键是"针对具体任务"评估，不是给人贴固定标签。同一个人在不同任务上可能处于不同象限。

**答案**：

- 小 A（S4 委派型）：高能力高意愿。授权他主导重构方案设计和关键模块实现，只关注结果，不干预过程。
- 小 B（S3 支持型）：高能力但低意愿。先了解积极性不高的原因，分配有一定挑战性的子任务，让他感受到被信任和重视。共同讨论任务目标，激发主动性。
- 小 C（S1 指令型）：低能力高意愿。分配明确的小任务，详细说明实现方法，安排小 A 做 Code Review。高频跟进，及时给予正面反馈。
- 小 D（S3 支持型）：高能力但意愿可能不稳定。分配有技术深度的核心任务，让他觉得工作有挑战。同时通过 1:1 了解他的真实想法，看是否有挽留空间。

**要点**：
- 识人矩阵是动态的，每次分配任务前都要重新评估
- "合适的人"不等于"最强的人"，要考虑成长性和团队平衡

### 练习二

**思路**：RACI 矩阵的核心是每个任务只有一个 A（Accountable），R 负责执行，C 和 I 分别表示咨询和知情。

**答案**：

| 任务 | 经理 | 后端高级 | 后端初级 | 前端 | 测试 |
|------|------|---------|---------|------|------|
| 技术方案设计 | A | R | C | C | I |
| 后端 API 开发 | A | R | R | I | I |
| 前端页面开发 | A | C | I | R | I |
| 测试用例编写 | I | C | I | C | R |
| 测试执行 | I | I | I | I | R |
| 部署上线 | A | R | I | I | C |

**说明**：
- 经理对所有任务负最终责任（A），但不亲自执行（R）
- 后端高级负责方案设计和核心 API 开发，同时指导后端初级
- 后端初级参与 API 开发，借此成长
- 前端独立负责前端开发，后端高级在接口设计上提供咨询
- 测试独立负责测试工作，部署时提供咨询

**要点**：
- 每个任务只能有一个 A，避免"共同负责"变成"无人负责"
- C（咨询者）要在决策前沟通，I（知情者）在决策后通知

### 练习三

**思路**：分析管理者在任务分配、跟进机制和风险控制三个方面的失误。

**答案**：

老李犯了三个错误：

1. **任务分配不清晰**：只说了"你来做"，没有明确目标、边界和验收标准。正确做法：明确说明功能需求、技术约束、完成标准和关键里程碑。

2. **跟进机制缺失**：三周没有任何检查，直到最后才问。正确做法：建立固定的里程碑检查，比如第一周完成方案设计 review、第二周完成核心功能 demo。

3. **没有建立沟通机制**：小赵遇到问题不知道找谁，说明老李没有明确沟通渠道和升级路径。正确做法：在分配任务时明确"遇到阻塞找谁"、"需要跨团队协调时怎么处理"。

**改进后的做法**：
- 第一天：明确任务目标、验收标准、关键里程碑、沟通机制
- 第一周末：方案设计 review，确认方向正确
- 第二周末：核心功能 demo，检查进度和质量
- 第三周末：功能完整测试，预留 buffer 处理问题

**要点**：
- 任务分配不是"扔出去就不管了"
- 跟进不是微管理，而是确保项目在正确的轨道上
- 管理者有责任建立清晰的沟通和升级机制
