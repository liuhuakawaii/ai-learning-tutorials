# 从 IC 到 Manager

> 前置知识：有至少 3 年工程经验，正在或即将带团队

## 一个典型的翻车现场

张伟是团队里公认技术最强的高级工程师。三个月前 CTO 找他谈话："团队要扩编，你来带这个组吧。"

上任第二周，他就陷入了困境。一个初级工程师写的代码有明显的性能问题，张伟花了两个小时帮他重写了一遍。结果那天下午，他错过了和产品负责人关于下个季度规划的会议。到了月底，他发现自己几乎没写过一行代码，但 PR 积压了 20 个，两个下属因为任务分配不全产生了矛盾，而他连一次正式的 1:1 都没做过。

"我到底在干什么？"

这不是张伟一个人的问题。这是几乎每个新经理都会经历的阵痛。问题不在于张伟不够努力，而在于他还在用 IC 的方式做 Manager 的工作。

## IC 和 Manager 的本质区别

区别不在于谁更"高级"，而在于通过什么方式创造价值。

```
IC 的价值公式：
  个人产出 = 代码质量 × 技术难度 × 完成速度

Manager 的价值公式：
  团队产出 = 团队人数 × 平均产出 × 协作效率 × 方向正确性
```

这个公式揭示了一个关键事实：Manager 的杠杆点不在自己的双手，而在整个团队的效能。

| 维度 | IC | Manager |
|------|------|---------|
| 核心产出 | 代码、设计文档 | 团队效能、人才成长 |
| 成功标准 | 我做的东西好不好 | 团队做的东西好不好 |
| 时间分配 | 90%+ 在技术上 | 30-50% 在技术上 |
| 影响范围 | 个人负责的模块 | 整个团队 |
| 反馈周期 | 代码跑通就知道 | 可能需要一个季度 |

## 时间分配：你应该把时间花在哪

新经理最常问的问题："我应该花多少时间在管理上？"

```
管理时间占比参考：

  3-5 人团队（新组建）    ████████████████░░░░  60-70% 管理
  3-5 人团队（成熟期）    ██████████░░░░░░░░░░  40-50% 管理
  6-10 人团队            ████████████████░░░░  60-80% 管理
  10-15 人团队           ██████████████████░░  80-90% 管理
```

一个实用的审计方法：连续两周，每天下班前花 5 分钟记录当天的时间分配，按"团队管理 / 技术工作 / 沟通协调 / 人才培养 / 战略思考"分类。大多数新经理会发现自己在技术工作上花了 60%+ 的时间——这是 IC 思维的惯性。

## 新经理的三个困境

### 困境一：想写代码但没时间

解决方案不是"挤时间写代码"，而是明确你在技术工作中的角色：

| 场景 | 你应该做 | 你不应该做 |
|------|----------|------------|
| 核心架构设计 | 主导方案评审，做最终决策 | 自己写全部代码 |
| 线上故障 | 判断优先级，协调资源 | 第一个冲上去 debug |
| Code Review | Review 关键 PR | Review 每一个 PR |

底线：保留 20-30% 的技术时间用于保持技术判断力。你的手感来自对系统全局的理解，不是写代码的速度。

### 困境二：下属做得不如自己

你用了十年经验的标准去要求一个三年经验的人。正确做法：

1. 接受"够好"的标准——代码不需要和你写得一样好
2. 把"不如自己"转化为教学机会
3. 用 Code Review checklist 替代"我觉得不够好"
4. 区分"风格不同"和"质量不达标"

### 困境三：失去技术深度的焦虑

"我不写代码了，技术会不会退化？"

有策略地保持技术敏感度：每周读 2-3 个关键 PR，参加技术方案评审用提问保持思考，每季度做一个小型技术探索。

## 心态转变的三个练习

**练习一：重新定义"完成"**

以前你"完成"一个任务意味着代码合并。现在你需要问：这个任务的负责人理解了背后的原理吗？下次遇到类似问题，他能独立解决吗？

**练习二：计算你的乘数效应**

如果你花 1 小时辅导一个初级工程师，使他后续效率提升 10%，而他每周写 40 小时代码，你的 1 小时投入带来每周 4 小时的团队产出增长。

**练习三：建立团队仪表盘**

每周记录：PR 平均合并时间、线上事故数量、团队成员的 blockers 数量、跨团队协作的阻塞点。用这些替代你之前关注的个人代码量。

## 练习

### 练习一：时间审计

回顾你过去一周的工作时间，按五个类别分类并计算占比。和建议目标对比，找出最大的差距。

### 练习二：价值公式推演

假设你带 6 人团队，目前每人每周完成 5 个 story points。如果你花 20% 时间做 Code Review 和技术辅导，预计能把平均产出提升到 6 SP。计算：你作为 IC 每周能完成 10 SP，转型后团队总产出变化了多少？

### 练习三：困境诊断

> 小李是新上任的 Tech Lead，带 5 人团队。他发现 CI/CD 流水线经常失败，于是花了一整天重写了 Jenkins pipeline。第二天，小王来找他讨论下一个迭代的技术方案，小李说"你先自己想想，我很忙"。到了周五，他这周只和团队成员做过两次简短对话。

小李犯了什么错误？应该怎么改正？

---

## 参考答案

### 练习一

没有标准答案，关键是诚实记录。典型差距：技术工作占比 60%+（建议降到 30%）；人才培养占比 0%（完全没投入）；战略思考占比 0%（在"救火"而不是"管理"）。

### 练习二

作为 IC：你 10 SP + 团队 5×5=25 SP = 35 SP
转型后：6×6=36 SP
虽然你个人产出从 10 降到 0，但团队总产出增加了 1 SP。更重要的是随着团队能力提升，差距会越来越大。管理者的**乘数效应**：不是加法，而是乘法。

### 练习三

小李犯了三个错误：

1. **角色定位错误**：用 IC 的方式解决 CI/CD 问题（自己重写），应该分配给团队成员借此培养能力
2. **时间分配错误**：花一整天在技术实现上，没有时间做管理工作
3. **沟通缺失**：一周只做两次简短对话，没有建立有效沟通节奏

"你先自己想想"可以，但需要给出明确时间点来讨论，而不是无限期推后。
