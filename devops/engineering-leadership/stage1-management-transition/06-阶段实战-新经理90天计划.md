# 阶段实战：新经理 90 天计划

> 前置知识：从 IC 到 Manager、一对一会议、任务分配、技术决策、向上管理（第 1-5 课）

## 你要做什么

你刚被任命为工程团队经理。团队 8 个人，负责一个用户量 50 万的 SaaS 产品。前任经理离职了，你是从团队内部提拔上来的——上周你还是他们的同事。

你的上级给了你一句话："三个月内让我看到变化。"

你需要输出一份可执行的 90 天计划。不是理论框架，而是具体到每一周要做什么、产出什么、怎么衡量。

## 90 天分三个阶段

```
前 30 天：听        中 30 天：想        后 30 天：做
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ 了解人        │  │ 诊断问题      │  │ 推动改变      │
│ 了解流程      │→ │ 制定计划      │→ │ 建立机制      │
│ 了解业务      │  │ 赢得小胜利    │  │ 展示成果      │
└──────────────┘  └──────────────┘  └──────────────┘
    信任基础          可执行方案          可见成果
```

## 前 30 天：倾听与了解

核心原则：**不要急于改变任何事情。** 你的首要任务是建立信任、收集信息、理解现状。

### 第一周：建立关系

| 任务 | 具体行动 | 产出 |
|------|----------|------|
| 和上级 1:1 | 明确上级对你的期望、团队的优先级 | 期望清单 |
| 和每个下属 1:1 | 了解工作内容、职业目标、对团队看法 | 人员档案 |
| 了解团队历史 | 团队怎么组建的？前任做了什么？ | 背景笔记 |
| 熟悉技术栈 | 了解系统架构、技术债务 | 技术现状 |

**1:1 问题清单（前 30 天专用）：**

```
关于工作：
- 你目前负责什么？最有挑战的部分是什么？
- 你觉得团队目前最大的问题是什么？
- 有什么事情你一直想做但没机会做的？

关于团队：
- 谁是团队里最有影响力的人？为什么？
- 团队里有什么"房间里的大象"？

关于你自己：
- 你希望一年后自己在做什么？
- 你需要我提供什么支持？
```

### 前 30 天里程碑

```
✓ 和上级完成一次深入的期望对齐对话
✓ 和每个下属完成至少 2 次 1:1
✓ 和 3-5 个跨团队伙伴完成 1:1
✓ 完成一份团队现状报告
✓ 识别出 3-5 个最紧迫的问题
```

## 中 30 天：诊断与规划

### 问题优先级矩阵

```
            紧急
              │
 ┌────────────┼────────────┐
 │  立即处理   │  优先处理   │
 │ (救火型)    │ (改善型)    │
重要──────────┼──────────不重要
 │  委托处理   │  暂时搁置   │
 │ (支持型)    │ (观察型)    │
 └────────────┼────────────┘
              │
            不紧急
```

### 选择小胜利

中 30 天最重要的策略是找到一个能快速见效的小胜利。

选择标准：
- 团队普遍感到痛苦
- 解决方案相对简单
- 效果可以在两周内显现
- 不需要大量额外资源

常见机会：简化审批流程、解决环境配置问题、建立文档规范、协调解决跨团队阻塞。

### 中 30 天里程碑

```
✓ 完成问题诊断和优先级排序
✓ 制定详细的后 60 天行动计划
✓ 赢得至少一个小胜利
✓ 和上级完成一次计划对齐
✓ 向团队沟通你的计划和愿景
```

## 后 30 天：执行与建制

管理者的工作不是解决每一个具体问题，而是建立让问题自动被解决的机制。

| 机制 | 具体形式 | 频率 |
|------|----------|------|
| 1:1 机制 | 和每个下属的固定 1:1 | 每周/双周 |
| 团队同步 | 周会或双周迭代回顾 | 每周/双周 |
| 技术治理 | Code Review 规范、技术方案评审 | 持续 |
| 绩效跟踪 | 季度目标设定和进度检查 | 每季度 |

### 后 30 天里程碑

```
✓ 完成至少一个流程优化并被团队采纳
✓ 推动解决一个重要的技术债务
✓ 为每个下属完成一次成长对话
✓ 建立 1:1、周会等基本管理机制
✓ 向上级汇报 90 天成果和下一步计划
```

## 常见误区

**上任就烧三把火。** 第一周就大改流程、换工具。你还不了解现状就急于改变，很可能会改错方向。

**只关注技术，忽略人。** 花大量时间看代码、改架构，但不和团队成员 1:1。团队的问题往往不是技术问题，而是人的问题。

**试图取悦所有人。** 对每个人的要求都说"好"，不敢做艰难的决定。

**独自承担一切。** 所有问题都自己扛，不寻求支持。

## 练习

### 练习一：定制你的 90 天计划

假设你刚接手一个 6 人团队，负责一个 B2B SaaS 产品。团队士气低落，最近三个月有两个人离职。产品延期严重，客户投诉很多。请定制一份 90 天计划，重点标注前 30 天的优先任务。

### 练习二：小胜利选择

你观察到团队有以下问题，选择一个作为"小胜利"并说明为什么：

1. 每次部署都需要手动操作，经常出错
2. Code Review 积压了 30 个 PR，平均等待 5 天
3. 团队没有技术文档，新人入职需要一个月上手
4. 每周例会超时，没有明确产出

---

## 参考答案

### 练习一

**前 30 天（止血）：** 先和每个下属 1:1 了解离职真实原因，向团队坦诚沟通稳定军心。同时和产品经理、客户成功团队沟通了解核心投诉。第三周评估是否需要紧急招聘。第四周整合信息制定后 60 天计划。

**中 30 天（治病）：** 推动紧急招聘，重新梳理产品优先级，建立基本项目管理流程。

**后 30 天（建制）：** 建立 1:1 和绩效反馈机制，推动技术债务清理，建立代码规范。

要点：士气低落的团队，前 30 天首要任务是"稳定"而不是"改变"。

### 练习二

**选择：问题 2——Code Review 积压 30 个 PR**

每个开发者都在等 Review，直接影响开发效率和士气。解决方案：建立 Review 轮值制度、设定 24 小时响应 SLA。两周内就能看到 PR 合并时间显著下降，不需要额外资源。

为什么不选其他：手动部署改造周期长；文档建设短期效果不明显；例会超时影响范围小。
