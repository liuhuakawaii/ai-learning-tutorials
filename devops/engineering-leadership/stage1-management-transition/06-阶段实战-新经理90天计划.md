# 阶段实战：新经理 90 天计划

## 场景引入

恭喜你，你刚刚被任命为工程团队的经理。团队有 8 个人，负责一个用户量 50 万的 SaaS 产品。前任经理因为个人原因离职了，你是从团队内部提拔上来的——上周你还是他们的同事，这周你变成了他们的老板。

你的上级给了你一句话："三个月内让我看到变化。"

但什么是"变化"？你应该先做什么？先改流程还是先了解人？先解决技术债还是先推进新需求？先和上级对齐还是先稳住团队？

90 天是新经理最关键的窗口期。做得好，你建立起信任和权威；做得差，你可能永远失去团队的信任。本节课给你一份**可执行的 90 天计划模板**，帮你系统地度过转型期。

## 学习目标

- 掌握新经理 90 天计划的三阶段框架：倾听了解 → 诊断规划 → 执行建制
- 了解每个阶段的核心任务、里程碑和可交付物
- 学会根据自身情况定制 90 天计划
- 避免新经理在 90 天内最常犯的错误

## 90 天计划总览

```
新经理 90 天计划

  前 30 天：倾听与了解        中 30 天：诊断与规划        后 30 天：执行与建制
  ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
  │                  │    │                  │    │                  │
  │  了解人           │    │  诊断问题         │    │  推动改变         │
  │  了解流程         │ →  │  制定计划         │ →  │  建立机制         │
  │  了解业务         │    │  赢得小胜利       │    │  展示成果         │
  │                  │    │                  │    │                  │
  │  关键词：听       │    │  关键词：想       │    │  关键词：做       │
  │                  │    │                  │    │                  │
  └──────────────────┘    └──────────────────┘    └──────────────────┘
         ↓                        ↓                        ↓
    信任基础              可执行方案              可见成果
```

## 前 30 天：倾听与了解

前 30 天的核心原则是：**不要急于改变任何事情。** 你的首要任务是建立信任、收集信息、理解现状。

### 第一周：建立关系

| 任务 | 具体行动 | 产出 |
|------|----------|------|
| 和上级 1:1 | 明确上级对你的期望、团队的优先级、可用资源 | 期望清单 |
| 和每个下属 1:1 | 了解他们的工作内容、职业目标、对团队的看法 | 人员档案 |
| 了解团队历史 | 团队是怎么组建的？经历过什么变化？前任经理做了什么？ | 团队背景笔记 |
| 熟悉技术栈 | 了解系统架构、技术债务、开发流程 | 技术现状笔记 |

**1:1 问题清单（前 30 天专用）：**

```
前 30 天 1:1 问题清单

  关于工作：
  - 你目前负责什么？最有挑战的部分是什么？
  - 你觉得团队目前最大的问题是什么？
  - 有什么事情是你一直想做但没机会做的？

  关于团队：
  - 你觉得团队的协作方式怎么样？
  - 谁是团队里最有影响力的人？为什么？
  - 团队里有什么"房间里的大象"（大家都知道但没人说的问题）？

  关于你自己：
  - 你希望一年后自己在做什么？
  - 你需要我提供什么支持？
  - 你对新经理（我）有什么期望？
```

### 第二到四周：深入了解

| 任务 | 具体行动 | 产出 |
|------|----------|------|
| 参加所有团队会议 | 观察团队的沟通方式、决策模式、冲突处理 | 团队动态笔记 |
| 和跨团队伙伴 1:1 | 了解其他团队怎么看你们团队、有什么协作痛点 | 跨团队关系图 |
| 了解业务上下文 | 产品的商业模式、用户画像、核心指标 | 业务理解笔记 |
| Review 代码和文档 | 了解代码质量、文档完善程度、技术债务情况 | 技术债务清单 |

### 前 30 天里程碑

```
前 30 天可交付物

  ✓ 和上级完成一次深入的期望对齐对话
  ✓ 和每个下属完成至少 2 次 1:1
  ✓ 和 3-5 个跨团队伙伴完成 1:1
  ✓ 完成一份团队现状报告（人员、技术、流程、文化）
  ✓ 识别出 3-5 个最紧迫的问题
```

## 中 30 天：诊断与规划

经过前 30 天的倾听，你已经对团队有了基本了解。现在是时候**把观察转化为行动方案**了。

### 问题诊断框架

用以下框架对发现的问题进行分类和排序：

```
问题优先级矩阵

                紧急
                  │
     ┌────────────┼────────────┐
     │   立即处理   │   优先处理   │
     │  (救火型)    │  (改善型)    │
     │             │             │
重要 ─────────────┼────────────── 不重要
     │             │             │
     │   委托处理   │   暂时搁置   │
     │  (支持型)    │  (观察型)    │
     │             │             │
     └────────────┼────────────┘
                  │
                不紧急
```

### 制定 90 天计划

基于诊断结果，制定后 60 天的行动计划。计划要符合 SMART 原则：

```
SMART 原则

  S - Specific（具体）：明确要做什么
  M - Measurable（可衡量）：有量化的成功标准
  A - Achievable（可实现）：在资源和时间约束内可行
  R - Relevant（相关）：和团队目标对齐
  T - Time-bound（有时限）：有明确的截止日期
```

**反面示例：** "改善团队代码质量" —— 太模糊，无法执行和衡量。

**正面示例：** "在第 60 天前，将 Code Review 平均响应时间从 3 天缩短到 1 天，PR 合并前的测试覆盖率从 40% 提升到 70%。" —— 具体、可衡量、有时限。

### 赢得小胜利

中 30 天最重要的策略是**找到一个能快速见效的小胜利**。小胜利的价值：

1. **建立信任**：让团队看到你的能力
2. **积累势能**：为后续更大的改变铺路
3. **提振士气**：让团队感受到"事情在变好"

**选择小胜利的标准：**
- 团队普遍感到痛苦的问题
- 解决方案相对简单
- 效果可以在两周内显现
- 不需要大量额外资源

**常见的小胜利机会：**
- 简化一个繁琐的审批流程
- 解决一个长期存在的环境配置问题
- 建立一个大家一直想要的文档规范
- 协调解决一个跨团队的阻塞问题

### 中 30 天里程碑

```
中 30 天可交付物

  ✓ 完成问题诊断和优先级排序
  ✓ 制定详细的 90 天行动计划
  ✓ 赢得至少一个小胜利
  ✓ 和上级完成一次计划对齐，获得支持
  ✓ 向团队沟通你的计划和愿景
```

## 后 30 天：执行与建制

后 30 天是**把计划变成现实**的阶段。核心是两件事：推动改变和建立机制。

### 推动改变

| 任务 | 具体行动 | 成功标准 |
|------|----------|----------|
| 流程优化 | 建立或改进至少一个关键流程 | 流程被团队采纳并持续执行 |
| 技术改善 | 推动解决一个重要的技术债务 | 技术指标有可量化的改善 |
| 团队建设 | 组织一次团队活动或建立一个团队习惯 | 团队氛围有积极变化 |
| 人才培养 | 为每个下属制定一个成长计划 | 下属明确了自己的发展方向 |

### 建立机制

管理者的工作不是解决每一个具体问题，而是**建立让问题自动被解决的机制**。

| 机制 | 具体形式 | 频率 |
|------|----------|------|
| 1:1 机制 | 和每个下属的固定 1:1 | 每周/双周 |
| 团队同步 | 周会或双周迭代回顾 | 每周/双周 |
| 技术治理 | Code Review 规范、技术方案评审流程 | 持续 |
| 绩效跟踪 | 季度目标设定和进度检查 | 每季度 |
| 知识沉淀 | 文档规范、技术分享机制 | 持续 |

### 后 30 天里程碑

```
后 30 天可交付物

  ✓ 完成至少一个流程优化并被团队采纳
  ✓ 推动解决一个重要的技术债务
  ✓ 为每个下属完成一次成长对话
  ✓ 建立 1:1、周会等基本管理机制
  ✓ 向上级汇报 90 天成果和下一步计划
```

## 常见误区

**误区一：上任就烧三把火。** 第一周就大改流程、换工具、调整架构。你还不了解现状就急于改变，很可能会改错方向。前 30 天以倾听为主。

**误区二：只关注技术，忽略人。** 花大量时间看代码、改架构，但不和团队成员 1:1。团队的问题往往不是技术问题，而是人的问题。把至少 50% 的时间花在"人"上。

**误区三：试图取悦所有人。** 对每个人的要求都说"好"，不敢做艰难的决定。你不可能让所有人都满意，你的工作是做对团队最好的决定。

**误区四：独自承担一切。** 所有问题都自己扛，不寻求支持。找一个管理导师，定期和上级沟通困难，加入管理者社群交流经验。

## 工程建议

1. **90 天计划不是一成不变的**。每两周回顾一次计划，根据实际情况调整。计划是指南针，不是铁轨。
2. **记录你的学习和反思**。每天花 10 分钟写管理日志，记录你做了什么决定、效果如何、学到了什么。90 天后回看，你会惊讶于自己的成长。
3. **向上级要反馈**。每个月问上级："你觉得我这 month 做得怎么样？有什么需要改进的？"主动寻求反馈，比被动等待评估有效得多。
4. **保持技术敏感度**。虽然你的主要工作是管理，但每周仍然要花 20% 的时间在技术上——review 关键 PR、参加技术评审、了解技术趋势。
5. **照顾好自己**。新经理的压力很大，但不要用加班来弥补焦虑。保持运动、睡眠和社交，你才能持续做出好的决策。

## 小结

新经理 90 天计划的核心逻辑：

1. **前 30 天听**：建立信任、收集信息、理解现状。不要急于改变。
2. **中 30 天想**：诊断问题、制定计划、赢得小胜利。把观察转化为行动。
3. **后 30 天做**：推动改变、建立机制、展示成果。把计划变成现实。

记住：**90 天不是终点，而是起点。** 90 天结束后，你应该已经有了稳定的管理节奏、清晰的团队方向和上级的信任。接下来，你需要在这个基础上持续迭代和改进。

## 练习

### 练习一：定制你的 90 天计划

假设你刚接手一个 6 人团队，负责一个 B2B SaaS 产品。团队士气低落，最近三个月有两个人离职。产品延期严重，客户投诉很多。请根据这些情况，定制一份 90 天计划，重点标注前 30 天的优先任务。

### 练习二：小胜利选择

你观察到团队有以下问题，请选择一个作为"小胜利"的目标，并说明为什么选择它：

1. 每次部署都需要手动操作，经常出错
2. Code Review 积压了 30 个 PR，平均等待时间 5 天
3. 团队没有技术文档，新人入职需要一个月才能上手
4. 每周的例会总是超时，而且没有明确的产出

## 参考答案

### 练习一

**思路**：团队士气低落、人员流失、产品延期——这是一个需要"先止血再治病"的场景。前 30 天的重点应该是了解离职原因、稳定军心、建立信任。

**答案**：

**前 30 天重点（止血）：** 先和每个下属 1:1 了解离职真实原因，向团队坦诚沟通稳定军心。同时和产品经理、客户成功团队沟通，了解客户投诉核心。第三周评估是否需要紧急招聘，优先解决一个最紧急的客户投诉来建立信任。第四周整合信息，制定后 60 天计划。

**中 30 天重点（治病）：** 推动紧急招聘补充人力，重新梳理产品优先级，建立基本的项目管理流程（站会、周报、里程碑）。

**后 30 天重点（建制）：** 建立 1:1 和绩效反馈机制，推动技术债务清理，建立代码规范和 Code Review 流程。

**要点**：
- 士气低落的团队，前 30 天的首要任务是"稳定"而不是"改变"
- 人员流失问题要优先处理，否则会形成恶性循环
- 客户投诉是展示能力的好机会，快速解决一个能赢得信任

### 练习二

**思路**：选择小胜利的标准是"团队普遍痛苦、解决简单、效果快速显现"。

**答案**：

**选择：问题 2——Code Review 积压 30 个 PR**

每个开发者都在等 Review，直接影响开发效率和士气。核心问题是 Review 响应慢，可以通过建立 Review 轮值制度、设定响应时间 SLA 来解决。两周内就能看到 PR 合并时间显著下降，且不需要额外资源。

具体方案：每天指定一个人负责 Review，确保 PR 在 24 小时内响应；花两天集中清理积压的 30 个 PR；设定 SLA：PR 提交后 24 小时内必须有第一个人 Review。

为什么不选其他：手动部署涉及 CI/CD 改造周期长；文档建设是长期工程短期效果不明显；例会超时影响范围小不够亮眼。

**要点**：
- 小胜利要选"痛点大、见效快"的问题
- 不要选太大的问题，否则会陷入泥潭
- 小胜利的目的是建立信任和势能，为后续更大的改变铺路
