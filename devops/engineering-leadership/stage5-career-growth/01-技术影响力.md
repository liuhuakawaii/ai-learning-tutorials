# 技术影响力

> 前置知识：管理转型、团队建设、技术战略（阶段一至三）

## 一个晋升对比

张工和李工同期入职，技术能力不相上下。五年后，张工还是高级工程师，李工已经晋升为 Staff Engineer。

差距在哪里？李工从三年前开始写技术博客，坚持每周一篇，积累了两万粉丝。他在公司内部定期组织技术分享，在行业大会上做过两次演讲。当公司需要推选技术委员会成员时，大家第一个想到的就是李工。

技术影响力不是虚名。它是技术领导者的核心竞争力——你的判断能影响多少人的决策。

## 技术影响力的本质

技术影响力 = **深度 × 传播度**

```
深度不够、传播度高：网红型，能吸引注意但缺乏信任
深度够、传播度低：隐士型，有能力但没人知道
深度够、传播度高：这才是技术领导者
```

深度来自：解决过真实问题、踩过坑、做过艰难的技术决策。
传播度来自：写下来、讲出来、让更多人知道。

## 构建技术影响力的路径

### 路径一：技术博客

写技术博客是最容易开始的方式。

```
选题公式：
  我遇到了什么问题 → 我怎么解决的 → 这个方案的边界在哪

好的选题：
  ✓ "我们如何把部署时间从 2 小时缩短到 10 分钟"
  ✓ "Node.js 内存泄漏排查实录"
  ✓ "为什么我们从微服务回到了单体"

差的选题：
  ✗ "TypeScript 入门教程"（太泛，网上已有无数篇）
  ✗ "2024 年最流行的 10 个框架"（列表文，没有深度）
```

坚持输出的关键：不要追求完美，先写出来。一篇 80 分的文章发出去，比一篇 100 分的文章永远在草稿箱里有价值。

### 路径二：内部技术分享

```
内部分享的正确做法：
  - 选一个团队正在遇到的真实问题
  - 分享你调研和决策的过程（不只是结论）
  - 留出充分的 Q&A 时间
  - 把分享内容整理成文档

内部分享的错误做法：
  - 做一个 50 页的 PPT 念一遍
  - 讲一个和团队工作无关的技术话题
  - 没有互动，变成单向输出
```

### 路径三：开源贡献

```
开源贡献的路径：
  1. 使用中发现问题 → 提 Issue
  2. Issue 没人修 → 自己提 PR
  3. 持续贡献 → 成为 Reviewer
  4. 深度参与 → 成为 Committer/Maintainer
```

不需要从零写一个开源项目。给现有项目提 PR、修 bug、写文档，都是有价值的贡献。

### 路径四：行业交流

```
从小到大：
  1. 公司内部分享（最容易，风险最低）
  2. 本地技术 Meetup（30-50 人，压力小）
  3. 线上直播/播客（不需要面对面）
  4. 行业大会演讲（需要申请和准备）
```

## 常见误区

### 误区一：影响力 = 粉丝数

粉丝数是传播度的指标，不是深度的指标。一个有 10 万粉丝但内容空洞的技术博主，影响力不如一个只有 1000 粉丝但在某个领域有深度贡献的工程师。

### 误区二：写博客浪费时间

写博客的过程本身就是深度思考的过程。当你试图把一个技术方案讲清楚时，你会发现自己的理解哪里有漏洞。

### 误区三：等我足够厉害了再分享

没有人"足够厉害"。你解决过的问题、踩过的坑，对还没遇到这些问题的人来说就是有价值的。

## 参考答案

### 练习一

示例：

1. "我们如何用 Docker Compose 统一了 8 个人的开发环境"——问题：新人入职要一天搭环境；方案：docker-compose.yml；边界：不适合需要 GPU 的场景。

2. "PostgreSQL 查询从 3 秒优化到 50 毫秒的过程"——问题：某个接口越来越慢；方案：索引优化 + 查询重写；边界：数据量再大可能需要分库分表。

3. "CI/CD 流水线从 Jenkins 迁移到 GitHub Actions 的踩坑记"——问题：Jenkins 维护成本高；方案：GitHub Actions；边界：私有仓库需要注意 Runner 成本。

### 练习二

```
月度技术分享计划

第 1 个月：代码审查的最佳实践
  - 为什么要 Code Review
  - Review 时关注什么
  - 团队当前 Review 的问题和改进

第 2 个月：我们系统的架构演进
  - 从单体到现在的架构变化
  - 每次变化的原因和代价
  - 当前架构的已知问题

第 3 个月：故障排查方法论
  - 最近一次线上故障的复盘
  - 排查思路和工具
  - 如何建立排查 SOP
```
