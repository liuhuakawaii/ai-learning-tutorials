# 招聘与面试

> 前置知识：管理转型基础（阶段一）

## 一份有问题的 JD

你刚接手一个 8 人后端团队，业务增长迅速，需要再招 3 名工程师。你打开 HR 发的 JD：

```
要求：
- 985/211 本科及以上学历
- 35 岁以下
- 5 年以上 Java 经验
- 精通 Spring Boot、微服务、分布式系统
- 能承受高强度加班
```

你意识到这份 JD 有三个问题：学历要求排除了大量自学成才的工程师；"精通"吓跑了合格候选人；"高强度加班"让优秀候选人直接关掉页面。

更糟糕的是团队之前的面试流程：一个技术面聊 30 分钟就决定要不要。没有评分标准，没有交叉验证，面试官凭"感觉"做判断。

你需要从头梳理招聘和面试的整个流程。这不只是"招人"——这是你在构建团队的入口质量。

## JD 设计的核心原则

一份好的 JD 需要回答三个问题：

1. **这个岗位做什么？**（职责，不是要求清单）
2. **做好了会怎样？**（成长空间和影响力）
3. **什么样的人能做好？**（能力要求，不是学历要求）

```
不推荐：
  "要求 5 年以上 Java 经验，精通 Spring Boot"

推荐：
  "你会负责订单系统的核心模块设计和开发。
   目前系统日处理 50 万笔订单，你需要在高并发
   场景下保证数据一致性。如果你有处理过类似
   规模系统的经验，我们会很感兴趣。"
```

区别在哪里？第一种是"筛选清单"，把不符合条件的人挡在门外。第二种是"场景描述"，让候选人判断自己是否适合，同时展示了工作的挑战性和价值。

## 面试流程设计

```
简历筛选 → 电话初筛（30 分钟）→ 技术面试（60 分钟）→ 系统设计（60 分钟）→ 文化匹配（45 分钟）→ Offer 讨论
```

每个环节的目标和通过标准要提前定义：

| 环节 | 目标 | 评估维度 | 通过标准 |
|------|------|---------|---------|
| 电话初筛 | 确认基本匹配度 | 经验、动机、薪资预期 | 5 项中 4 项匹配 |
| 技术面试 | 验证技术能力 | 编码、调试、工程实践 | 平均分 ≥ 3/5 |
| 系统设计 | 验证架构思维 | 需求分析、方案设计、权衡取舍 | 平均分 ≥ 3/5 |
| 文化匹配 | 验证协作方式 | 沟通、价值观、自驱力 | 无红旗项 |

## 面试评估标准

"凭感觉"做判断是面试最大的问题。你需要一个可量化、可对比的评分表：

```
技术面试评分表（每项 1-5 分）

编码能力：
  □ 能写出可运行的代码（不是伪代码）
  □ 变量命名有业务语义
  □ 处理了边界条件
  □ 代码结构清晰

调试能力：
  □ 能系统性地定位问题
  □ 不盲目猜测，用数据验证假设
  □ 知道常用调试工具

工程实践：
  □ 理解测试的价值
  □ 了解 CI/CD 的基本概念
  □ 有代码审查的意识
```

## 常见面试方法对比

| 方法 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 算法题 | 标准化、易评分 | 和实际工作关联弱 | 初级岗位筛选 |
| 项目深挖 | 能了解真实能力 | 依赖候选人的表达能力 | 中高级岗位 |
| Pair Programming | 最接近真实工作 | 耗时、需要好的题目 | 所有岗位 |
| 系统设计 | 验证架构思维 | 对初级岗位太难 | 高级岗位 |
| Take-home | 不受时间限制 | 候选人负担重 | 需要看实际代码质量 |

推荐组合：电话初筛用项目深挖，技术面试用 Pair Programming 或实际编码题，高级岗位加系统设计。

## 候选人体验

候选人体验不只是"面试礼仪"——它直接影响你能不能招到优秀的人。

```
好的候选人体验：
  ✓ 面试前：发送面试流程说明和准备建议
  ✓ 面试中：准时开始、尊重时间、清晰提问
  ✓ 面试后：3 个工作日内给反馈（无论是否通过）

差的候选人体验：
  ✗ 面试前：没有任何说明，候选人不知道要准备什么
  ✗ 面试中：迟到、打断、问和岗位无关的问题
  ✗ 面试后：石沉大海，候选人发邮件也不回
```

优秀的候选人往往同时有多个 offer。如果面试体验差，即使你开了更高的薪资，他也可能选择别家。

```
前端工程师 — 用户平台团队

你会负责什么：
  - 构建和维护面向 200 万用户的 Web 应用
  - 和产品、设计团队协作，将用户需求转化为交互体验
  - 推动前端工程化：组件库、性能优化、测试覆盖

我们希望你：
  - 有 3 年以上使用 React 构建 Web 应用的经验
  - 熟悉 TypeScript，理解类型系统的价值
  - 遇到性能问题时，能用工具定位瓶颈而不是凭猜测
  - 重视代码质量，写过测试，做过 Code Review

加分项：
  - 有大规模用户产品的经验
  - 了解 Web 性能优化（Core Web Vitals）
  - 有开源贡献或技术博客

我们提供：
  - 有竞争力的薪资和股权
  - 灵活的工作时间和远程办公选项
  - 每年参加技术大会的预算
```

### 练习二

题目：实现一个简单的 URL 短链接服务的 API。

功能要求：
- `POST /shorten`：接收 `{ url: string }`，返回 `{ shortCode: string }`
- `GET /:shortCode`：重定向到原始 URL
- 用内存存储即可（不需要数据库）

考察点：
- 编码能力：能否写出结构清晰的代码
- 错误处理：URL 格式校验、短码不存在时返回 404
- 工程实践：是否有日志、是否有基本的输入验证

### 练习三

评分：

| 维度 | 得分 | 理由 |
|------|------|------|
| 编码能力 | 3/5 | 代码能运行，但缺少错误处理，没有边界条件考虑 |
| 调试能力 | 2/5 | "加个 try-catch"太笼统，没有说明如何分类错误、如何重试、如何降级 |
| 工程实践 | 1/5 | "手动用 Postman 测试"说明没有自动化测试意识 |

总分：6/15（平均 2/5），不推荐录用。

关键问题不是技术能力不够，而是**工程意识不足**。错误处理和自动化测试是后端工程师的基本素养，不是加分项。
