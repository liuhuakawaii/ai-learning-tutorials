# 架构治理

## 场景引入

你的团队有 8 个微服务。某天你发现，A 团队用 RabbitMQ 做消息队列，B 团队用 Kafka，C 团队用 Redis 的 Pub/Sub。每个团队都认为自己的选择是合理的，但结果是运维团队要同时维护三套消息中间件。

这不是技术问题，是治理问题。架构治理不是限制团队的自由，而是在自由和一致性之间找到平衡点。

## 学习目标

1. 设计并实施架构评审机制
2. 编写规范的 ADR（Architecture Decision Record）
3. 建立团队的技术雷达
4. 使用架构适应度函数守护架构规则
5. 把握治理的度，避免官僚主义

## 架构评审机制

### 何时需要架构评审

触发条件：
- **引入新的技术栈**：新增语言、框架、中间件
- **改变系统架构**：拆分服务、合并模块、改变部署拓扑
- **影响多个团队**：跨团队的技术方案
- **涉及重大资源投入**：超过 10 人天的技术改造
- **有安全或合规影响**：涉及用户数据、权限模型变更

### 评审的参与者

| 角色 | 职责 | 何时参与 |
|------|------|---------|
| 方案提出者 | 演示方案、回答质疑 | 全程 |
| 相关团队代表 | 评估对自身的影响 | 全程 |
| 架构师/Tech Lead | 评估技术合理性 | 全程 |
| 安全/合规代表 | 评估安全和合规风险 | 涉及安全时 |
| 运维/SRE | 评估运维可行性 | 涉及部署变更时 |

### 评审标准

1. **必要性**：这个问题是否真的需要解决？
2. **合理性**：方案是否是解决这个问题的合理方式？
3. **一致性**：方案是否与团队的技术方向一致？
4. **可行性**：方案在当前资源下是否可执行？
5. **风险性**：方案的风险是否可控？

## ADR：Architecture Decision Record

ADR 是记录架构决策的标准格式。它的价值在于记录决策的上下文和理由。

### ADR 完整模板

```markdown
# ADR-{编号}：{决策标题}

## 状态
{提议中 | 已接受 | 已废弃 | 已取代}

## 日期
{YYYY-MM-DD}

## 背景
{描述决策的背景和问题}

## 决策
{清晰描述做出的决策，用"我们决定..."开头}

## 备选方案
### 方案 A：{名称}
- 描述 / 优点 / 缺点

### 方案 B：{名称}
- 描述 / 优点 / 缺点

## 理由
{为什么选择这个方案而不是其他方案}

## 影响
- 正面影响 / 负面影响 / 风险

## 相关方
{谁参与了决策，谁需要知道这个决策}
```

### ADR 实际案例

```markdown
# ADR-007：统一消息队列为 Kafka

## 状态
已接受

## 日期
2025-06-15

## 背景
目前团队使用了三种消息中间件：RabbitMQ（订单团队）、Kafka（数据团队）、
Redis Pub/Sub（通知团队）。运维团队需要维护三套集群，跨团队消息交互需要
额外适配层。随着业务增长，消息量预计一年内增长 5 倍。

## 决策
我们决定在未来 6 个月内，将所有消息中间件统一为 Kafka。

## 备选方案
### 方案 A：统一为 RabbitMQ
- 优点：团队已有使用经验
- 缺点：吞吐量上限较低

### 方案 B：统一为 Kafka
- 优点：高吞吐、持久化、社区活跃
- 缺点：运维复杂度较高

### 方案 C：维持现状
- 优点：无迁移成本
- 缺点：运维成本持续增长

## 理由
Kafka 吞吐量能支撑未来 3 年增长，消息持久化满足流处理需求，
人才市场更容易招聘到有经验的工程师。

## 影响
- 正面：运维成本降低 40%，跨团队协作更顺畅
- 负面：迁移期间需额外投入约 20 人天
- 风险：迁移过程中可能出现消息丢失或重复

## 相关方
订单团队、数据团队、通知团队、运维团队
```

## 技术雷达

技术雷达是一种可视化的技术选型参考工具，帮助团队对"可以用什么技术"达成共识。

### 四个环

| 环 | 含义 | 行动 |
|---|------|------|
| Adopt（采用） | 已验证，推荐新项目使用 | 默认选择 |
| Trial（试验） | 正在或计划试用 | 限试点项目 |
| Assess（评估） | 值得关注，但未实际使用 | 做 POC 调研 |
| Hold（暂缓） | 不推荐新项目使用 | 避免使用 |

### 技术雷达示例

```
                    Adopt              Trial              Assess             Hold
         ┌───────────────────┬───────────────────┬───────────────────┬───────────────────┐
语言和框架│ TypeScript         │ Rust               │ Kotlin             │ CoffeeScript      │
         │ React              │ Svelte             │ Solid.js           │ Angular.js        │
         │ FastAPI            │                    │                    │                   │
平台     │ PostgreSQL         │ DynamoDB           │ CockroachDB        │ MongoDB(新项目)   │
         │ AWS                │ Cloudflare Workers │                    │ 自建机房           │
工具     │ GitHub Actions     │ Dagger             │                    │ Jenkins           │
         │ Grafana            │                    │                    │                   │
技术     │ 微服务              │ 事件驱动架构        │ 区块链              │ SOAP              │
         │ TDD                │ DDD                │                    │                   │
         └───────────────────┴───────────────────┴───────────────────┴───────────────────┘
```

### 维护节奏

- 每季度更新一次
- 由架构师/Tech Lead 主导，团队成员可提议
- 新技术通常从 Assess 开始，逐步向 Adopt 移动

## 架构适应度函数

架构适应度函数是自动化的架构规则检查工具，把"架构应该怎样"变成"代码是否符合"。

### 示例：检查 Controller 层不直接依赖数据库

```python
def test_controller_no_direct_db_dependency():
    controller_files = glob.glob("src/controllers/**/*.py")
    for file in controller_files:
        content = read_file(file)
        assert "import sqlalchemy" not in content, \
            f"{file} 直接依赖了数据库，应该通过 Repository 层访问"
```

### 示例：检查 API 响应使用统一格式

```javascript
function testApiResponsesFollowStandardFormat() {
    const apiFiles = glob.sync('src/api/**/*.ts');
    apiFiles.forEach(file => {
        const content = fs.readFileSync(file, 'utf-8');
        if (content.includes('res.json(')) {
            const hasStandardWrapper = content.includes('ApiResponse.success');
            assert(hasStandardWrapper,
                `${file} 的 API 响应未使用统一的 ApiResponse 包装`);
        }
    });
}
```

### 运行时机

- **CI/CD 流水线**：每次提交自动运行
- **定期检查**：每天运行一次，生成报告

## 治理的度

### 治理的边界

| 需要治理 | 不需要治理 |
|---------|-----------|
| 引入新的基础设施 | 代码风格偏好 |
| 跨团队的技术方案 | 模块内部的实现细节 |
| 影响系统安全的决策 | 工具的个人选择 |
| 涉及重大资源投入 | 小范围的试验 |

### 轻量级治理原则

1. **默认信任**：团队的决策默认合理，只在触发条件时才评审
2. **文档优先**：ADR 比会议更有效
3. **自动化守护**：能用适应度函数检查的，就不要靠人工
4. **渐进式约束**：新规则先小范围试行，验证有效后再推广
5. **定期清理**：过时的规则要及时废弃

## 常见误区

**误区一：架构评审是"找茬"**。评审的目的是帮助方案更完善，不是否定。

**误区二：ADR 要写得像论文**。核心是记录决策理由，一份好的 ADR 应该 5 分钟内读完。

**误区三：技术雷达是"推荐清单"**。Hold 区域同样重要，明确"不要用什么"更能避免混乱。

**误区四：适应度函数能替代架构评审**。适应度函数检查已知规则，评审判断方案是否合理。

**误区五：治理越严格越好**。过度治理会扼杀创新。最好的治理是"关键节点把关，日常不碍事"。

## 工程建议

1. **ADR 存放在代码仓库中**，和代码一起版本管理。
2. **技术雷达用团队能看懂的语言描述**，不要堆术语。
3. **架构评审控制在 1 小时以内**。超时通常意味着方案需要先完善文档。
4. **适应度函数的规则要少而精**。先覆盖最重要的 5 条。
5. **治理规则本身也需要治理**。每半年审视一次现有规则。

## 小结

- 架构评审要在正确的时机触发，不是所有决策都需要评审
- ADR 是记录架构决策的标准格式，核心是记录"为什么这样决定"
- 技术雷达帮助团队对技术选型达成共识
- 架构适应度函数把架构规则自动化
- 治理的目标是"关键节点把关，日常不碍事"

## 参考答案

### 练习一

```markdown
# ADR-001：前端框架选择 React

## 状态
已接受

## 背景
新项目需要选择前端框架。3 个月上线时间约束，团队 5 人中 3 人熟悉 React。

## 决策
选择 React 作为前端框架。

## 备选方案
### React
- 优点：3 人熟悉，学习成本低；社区生态成熟；招聘市场人才多
- 缺点：需要额外选择状态管理方案

### Vue
- 优点：上手简单，文档友好
- 缺点：仅 2 人熟悉，需要额外学习时间

## 理由
团队技能匹配度最高。3 个月的上线时间不允许花太多时间在框架学习上。

## 影响
- 正面：项目启动快，团队信心足
- 负面：2 名成员需要 1-2 周学习时间
```

### 练习三

**规则一检查逻辑**：扫描 API 处理函数，检查函数体是否超过 20 行（疑似包含业务逻辑），检查是否直接调用数据库操作。
