# 技术债务管理

## 场景引入

产品经理说："这个需求很简单，改个字段就行。"你打开代码一看，这个字段散落在 15 个文件里，没有统一的数据模型，改一个地方要同步改其他 14 个。你心里知道这是技术债，但你没法跟产品经理解释"为什么改个字段要三天"。

技术债务是每个团队都面对的现实。问题不是有没有技术债，而是你有没有一套机制来管理它。

## 学习目标

1. 对技术债务进行分类和分级
2. 用量化方法评估技术债务的影响
3. 制定切实可行的技术债务偿还策略
4. 建立技术债务看板并与产品团队协作
5. 用业务语言向非技术人员解释技术债务

## 技术债务的分类

### 按意图分类

| 类型 | 说明 | 例子 |
|------|------|------|
| 有意-战略型 | 知道有债，为了赶时间主动选择 | "先硬编码，下个迭代再抽象" |
| 有意-战术型 | 知道有债，但为了长期利益接受 | "先用简单方案验证，复杂方案等需求确认后再做" |
| 无意-知识型 | 因为不知道更好的做法而产生 | 没听说过连接池，每次请求都新建数据库连接 |
| 无意-疏忽型 | 因为赶工、缺乏 review 而产生 | 没写测试、没有 code review 就合并了 |

### 按影响范围分类

| 类型 | 说明 | 处理优先级 |
|------|------|-----------|
| 架构层 | 系统结构层面的设计缺陷 | 高（修复成本高，影响面广） |
| 模块层 | 单个模块内部的设计问题 | 中（影响局部，修复成本中等） |
| 代码层 | 代码质量、命名、格式等问题 | 低（影响局部，修复成本低） |
| 文档层 | 缺失或过时的文档 | 低到中 |

### 技术债务四象限

```
         高影响
            │
   ┌────────┼────────┐
   │ 紧急处理 │ 专项治理 │
低 ─┼────────┼────────┼─ 高
紧迫│ 暂时忽略 │ 日常清理 │
   └────────┼────────┘
            │
         低影响
```

## 量化技术债务

### 修复成本评估

| 度量维度 | 说明 | 示例 |
|---------|------|------|
| 人天 | 修复需要多少人天 | 重构订单模块：5 人天 |
| 风险等级 | 不修复的潜在后果 | P0（可能造成数据丢失） |
| 影响范围 | 影响多少个模块/服务 | 影响 3 个核心服务 |
| 发生频率 | 问题多久触发一次 | 每周至少 1 次线上告警 |

### 技术债务记分卡示例

```
技术债务项：订单状态机硬编码

修复成本：5 人天
风险等级：8/10（状态混乱可能导致订单数据不一致）
影响范围：7/10（影响订单、支付、物流三个服务）
发生频率：6/10（每周约 2 次需要人工介入）
阻塞程度：9/10（每次新增订单状态都要改代码上线）

总分：30/40 → 优先级：高
```

### 自动化度量

- **代码重复率**：重复代码行数 / 总代码行数
- **圈复杂度**：函数的分支数量
- **测试覆盖率**：被测试覆盖的代码比例
- **依赖老化度**：依赖版本与最新版本的差距

## 偿还策略

### 策略一：Boy Scout Rule（童子军规则）

> "离开时比来时更干净。"

每次修改代码时，顺手改善周围的代码。适用场景：代码层技术债，改动小、风险低。不适用于架构层债务。

### 策略二：专项 Sprint

每隔几个迭代，安排一个专门的技术债偿还 sprint。适用场景：技术债积累较多，需要集中清理。建议频率：每 4-6 个迭代一次，需要和产品团队提前沟通。

### 策略三：Refactor Friday

每周五下午留出半天处理技术债。好处是固定时间、形成习惯。注意：不要把这半天当作"可牺牲的缓冲时间"，要有计划。

### 策略四：嵌入式偿还

将技术债偿还嵌入到正常的功能开发中。在需求评估时，如果某个需求涉及的技术区域有技术债，就把偿还工作纳入需求估算。

示例：需求"新增订单导出功能"估算 3 天（其中 1 天重构订单查询模块，2 天实现实现导出功能）。

## 与产品团队沟通技术债

### 用业务语言描述技术债

**不好的说法**："这个模块的耦合度太高了，我们需要重构。"

**好的说法**："目前客户下单和支付用的是同一套代码。每次改支付规则，都有可能影响到下单流程。上个月就因为改了一个支付参数，导致 200 个订单状态异常。如果我们把它们分开，这类事故可以完全避免。"

### 沟通框架

1. **描述现状**：用具体事件说明问题
2. **说明影响**：用业务指标（客户数、订单量、故障次数）
3. **提出方案**：简述解决方案和所需时间
4. **量化收益**：修复后的业务改善

## 防止技术债积累的机制

- **代码审查**：防止技术债进入代码库的第一道防线
- **架构守护**：在 CI/CD 中加入自动化检查（依赖版本、代码质量、测试覆盖率）
- **定期审视**：每月安排一次技术债审视会议

## 常见误区

**误区一：技术债是坏事**。有意的战略型技术债是合理的商业决策。问题在于没有偿还计划的"坏债"。

**误区二：重构就是还债**。加一层抽象、写一份文档、增加一个测试，都是有效的还债方式。

**误区三：等有时间再还**。你永远不会"有时间"。技术债偿还需要被计划、被排期。

**误区四：还债和新功能是对立的**。短期内有竞争，但长期来看还债会提升开发效率。

**误区五：所有技术债都需要还**。如果一个模块即将被废弃，投入资源修复它的技术债就是浪费。

## 工程建议

1. **新项目启动时就建立技术债看板**。从第一天开始记录。
2. **技术债的修复估算要加上测试时间**。修复本身很快，回归测试很耗时。
3. **在 sprint planning 中固定预留 15-20% 的容量给技术债**。
4. **技术债的卡片要关联到具体的业务影响**。
5. **定期清理技术债看板**。已不相关的条目果断删除。
6. **在技术债偿还完成后做一次复盘**。记录决策过程，为未来提供参考。

## 小结

- 技术债有多种分类方式，分类的目的是决定优先级
- 量化技术债需要多维度评估：修复成本、风险等级、影响范围、发生频率
- 偿还策略要根据债务类型选择：Boy Scout Rule、专项 Sprint、Refactor Friday、嵌入式偿还
- 与产品团队沟通要用业务语言，用具体事件说明影响

### 练习一：技术债分类

对以下 5 个场景进行分类（按意图和影响范围），并评估优先级：

### 练习三：偿还计划

你的团队有以下技术债，总修复成本约 30 人天。请制定一个季度内的偿还计划。

| 技术债 | 修复成本 | 风险等级 | 业务影响 |
|-------|---------|---------|---------|
| 支付模块耦合 | 10 人天 | P0 | 每次改支付规则影响下单 |

## 参考答案

### 练习一

**答案**：

1. **没有参数校验**：有意-战略型 / 代码层 → 中优先级（有意为之但风险在增长）
2. **jQuery 和 React 并存**：无意-知识型 / 架构层 → 高优先级（影响团队技能聚焦和维护效率）
3. **数据库无索引**：无意-疏忽型 / 模块层 → 高优先级（直接影响性能，修复成本相对低）
4. **配置硬编码**：有意-战略型 / 代码层 → 中优先级（影响运维效率，修复成本不高）
5. **没有单元测试**：无意-疏忽型 / 模块层 → 高优先级（影响每次发布的信心和质量）

**要点**：有意的技术债不等于低优先级，要看风险等级。架构层的技术债通常优先级最高。

### 练习二

**答案**：

> "我理解下个季度的功能压力。过去 3 个月，因为支付模块的问题导致了 3 次线上事故，影响了约 500 个客户，团队花了 15 个人天在紧急修复上。
>
> 我的建议是：在下个季度排期中预留 20% 的容量给支付模块解耦。改造完成后，改支付规则的时间可以从 3 天缩短到半天，实际上会加速功能交付。
>
> 其他的技术债可以推迟，但支付模块的问题每多拖一个月，就多一次出事故的风险。"

**要点**：用具体数字、提出折中方案、强调正向循环。

### 练习三

**答案**：

| 月份 | 技术债 | 策略 | 人天 |
|------|-------|------|------|
| 第 1 个月 | 支付模块解耦 | 专项 sprint | 10 |
| 第 1-2 个月 | 监控告警建设 | 嵌入式偿还 | 5 |
| 第 2 个月 | 依赖版本更新 | Refactor Friday | 3 |
| 第 3 个月 | 代码重复率 | Boy Scout Rule + 1 天专项 | 8 |
| 持续进行 | 文档补充 | 嵌入式偿还 | 4 |

**要点**：优先级排序 P0 > P1 > P2 > P3，策略选择要匹配债务类型和团队节奏。
