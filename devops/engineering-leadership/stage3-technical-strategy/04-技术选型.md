# 技术选型

## 场景引入

团队要为新项目选择后端框架。三个开发者分别推荐了 Go、Node.js 和 Python。讨论了两周没有结论。最后 CTO 说"就用 Node.js 吧"，Go 的拥护者开始消极怠工，Python 的拥护者觉得决策不透明。

技术选型是技术 leader 最常面对的决策之一。问题不在于选哪个，而在于怎么选。

## 学习目标

1. 使用评估框架对技术选型进行系统化评估
2. 识别和分析技术选型中的风险
3. 设计和执行 POC 验证
4. 制定技术迁移策略
5. 组织高效的技术选型决策会议

## 技术选型评估框架

### 评估维度

| 维度 | 权重 | 评估要点 |
|------|------|---------|
| 成熟度 | 20% | 版本稳定性、生产环境验证案例 |
| 社区活跃度 | 15% | GitHub stars、文档质量 |
| 团队技能匹配 | 25% | 现有团队掌握程度、学习曲线 |
| 许可证 | 5% | 开源许可类型 |
| 性能 | 15% | 基准测试数据 |
| 成本 | 20% | 许可费用、运维成本、人才招聘成本 |

### 评估矩阵示例

```
评估维度        权重    React   Vue    Angular
─────────────────────────────────────────────
成熟度          20%     9       8      9
社区活跃度      15%     9       8      7
团队技能匹配    25%     8       6      5
许可证          5%      10      10     10
性能            15%     8       8      7
成本            20%     8       8      6
─────────────────────────────────────────────
加权总分               8.45    7.55   6.75
```

### 评分标准示例

**成熟度**：9-10（生产大规模使用 5 年+）/ 7-8（2-5 年）/ 5-6（1-2 年）/ 3-4（刚进生产）/ 1-2（实验阶段）

**团队技能匹配**：9-10（全员熟练）/ 7-8（多数人熟悉）/ 5-6（部分人熟悉）/ 3-4（少数人了解）/ 1-2（无人使用过）

## 风险分析

### 常见风险类型

| 风险类型 | 说明 | 评估方法 |
|---------|------|---------|
| 供应商锁定 | 过度依赖单一供应商 | 评估迁移成本、是否有标准接口 |
| 迁移成本 | 从现有技术迁移的代价 | 评估代码改造量、数据迁移、人员培训 |
| 安全风险 | 技术本身的安全漏洞 | 评估 CVE 记录、安全更新响应速度 |
| 社区风险 | 社区衰退、维护停滞 | 评估贡献者数量、最近更新频率 |
| 人才风险 | 难以招聘到合适的人 | 评估招聘市场、薪资水平 |

### 风险评估矩阵

```
影响程度
  高 │  中风险    高风险    极高风险
  中 │  低风险    中风险    高风险
  低 │  可忽略    低风险    中风险
     └──────────────────────────
        低         中         高
                发生概率
```

## POC 验证方法

### POC 设计原则

1. **聚焦关键假设**：验证最担心的风险
2. **时间盒**：通常 1-2 周
3. **成功标准**：开始前就定义好
4. **可复现**：代码和环境要可复现

### POC 计划模板

```markdown
# POC 计划：{技术名称} 在 {场景} 中的适用性验证

## 验证目标
验证 {技术名称} 是否能满足 {具体场景} 的需求。

## 关键假设
1. {假设 1}：例如"在 1000 QPS 下延迟低于 50ms"
2. {假设 2}：例如"能与现有数据库无缝集成"

## 成功标准
- [ ] 假设 1：{具体指标}
- [ ] 假设 2：{具体指标}

## 时间安排
总时长：{X} 个工作日

## 输出物
- POC 代码仓库
- 测试报告
```

## 迁移策略

### Big Bang（大爆炸迁移）

一次性迁移所有内容。适用场景：旧系统很小、有严重问题必须尽快替换。风险：迁移期间不可用、回滚困难。

### Strangler Fig（绞杀者模式）

逐步用新系统替换旧系统功能。

```
阶段 1：新功能用新系统        阶段 3：旧系统完全退役
┌───────────────────┐      ┌───────────────────┐
│  负载均衡器        │      │  负载均衡器        │
│  ┌──────┬──────┐  │      │  ┌──────────────┐  │
│  │ 旧系统│ 新系统│  │  →   │  │    新系统     │  │
│  └──────┴──────┘  │      │  └──────────────┘  │
└───────────────────┘      └───────────────────┘
```

适用场景：系统较大、需要保持业务连续性。风险：迁移周期长、两套系统并存的维护成本。

### Branch by Abstraction

通过抽象层实现迁移，对外接口不变。步骤：建立抽象层 → 新实现对接抽象层 → 配置切换 → 移除旧实现。适用场景：核心模块不能有中断。

## 技术选型决策会议

### 会前准备（至少 3 天）

- 发布评估文档（各方案的初步评分）
- 发布 POC 报告
- 要求参与者提前阅读

### 会议流程

| 阶段 | 时长 | 内容 |
|------|------|------|
| 背景回顾 | 10 分钟 | 为什么做选型，约束条件 |
| 方案演示 | 30 分钟 | 每个方案的评估结果 |
| 质疑讨论 | 30 分钟 | 对评估结果提出质疑 |
| 风险评估 | 15 分钟 | 各方案的风险和缓解 |
| 决策 | 15 分钟 | 基于评估做出决策 |

### 决策方法

- **加权评分法**：选择加权总分最高的方案
- **反向排除法**：先排除有致命缺陷的方案
- **共识决策法**：讨论后由技术负责人决策，记录所有意见

## 常见误区

**误区一：选"最好"的技术**。没有最好的技术，只有最适合当前场景的。

**误区二：技术选型是纯技术决策**。涉及团队、业务、成本、风险等多个维度。

**误区三：POC 能解决所有问题**。有些问题（如长期维护成本）需要更长时间才能显现。

**误区四：迁移可以一步到位**。大多数迁移需要分阶段进行。

**误区五：选型完成后就不需要关注了**。需要定期评估现有技术栈的适用性。

## 工程建议

1. **评估维度和权重在选型开始前就确定**。不要看到结果后再调整权重。
2. **POC 要验证最担心的风险**。担心性能就重点压测，担心集成就重点测集成。
3. **选型会议前至少给 3 天准备时间**。匆忙的会议容易变成"谁声音大听谁的"。
4. **迁移策略要和业务节奏配合**。不要在业务高峰期做大规模迁移。
5. **保留回滚能力**。任何迁移都应该有回滚方案。
6. **记录选型过程**。半年后可能会有人问"为什么选了这个"。

## 小结

- 使用评估框架进行系统化评估，避免主观判断
- 风险分析要覆盖供应商锁定、迁移成本、安全、社区、人才
- POC 验证聚焦关键假设，有明确的时间盒和成功标准
- 迁移策略根据系统规模和风险选择
- 决策会议需要结构化流程和明确的输出

## 参考答案

### 练习一

**评估维度和权重**：

| 维度 | 权重 | 理由 |
|------|------|------|
| 团队技能匹配 | 25% | 团队规模小，学习成本直接影响交付 |
| 运维成本 | 25% | 预算有限 |
| 吞吐能力 | 20% | 日均 1000 万条 |
| 消息持久化 | 15% | 业务要求 |
| 社区活跃度 | 10% | 影响长期维护 |
| 许可证 | 5% | 都是开源 |

**评估矩阵**：

```
评估维度        权重    Kafka   RabbitMQ  Redis Streams
──────────────────────────────────────────────────────
团队技能匹配    25%     7       5         9
运维成本        25%     5       7         8
吞吐能力        20%     9       7         8
消息持久化      15%     9       8         6
社区活跃度      10%     9       8         7
```

**建议**：选择 Redis Streams。团队最熟悉，运维成本最低，综合评分最高。

### 练习二

```markdown
# POC 计划：Kafka 高吞吐场景验证

## 关键假设
1. 单分区写入吞吐 ≥ 10,000 条/秒
2. 端到端延迟 P99 < 100ms
3. 节点故障后消息不丢失

## 验证方案
- 环境：3 节点 Kafka 集群（8C16G）
- 数据：模拟真实消息格式，每条约 1KB
- 方法：逐步增加压力，记录吞吐和延迟；模拟节点故障

## 成功标准
- [ ] 单分区吞吐 ≥ 10,000 条/秒
- [ ] 端到端延迟 P99 < 100ms
- [ ] 节点故障后消息不丢失

## 时间安排
总时长：5 个工作日（准备 1 天，验证 3 天，报告 1 天）
```

### 练习三

**选择：Strangler Fig（绞杀者模式）**

理由：系统规模中等，不能接受长时间停机，分阶段迁移可验证和回滚。

| 阶段 | 时间 | 内容 |
|------|------|------|
| 1 | 第 1-2 周 | 搭建 Kafka 集群，建立双写机制 |
| 2 | 第 3-4 周 | 迁移 3 个非核心消费者 |
| 3 | 第 5-6 周 | 迁移剩余消费者 |
| 4 | 第 7-8 周 | 迁移生产者，关闭双写 |
| 5 | 第 9-10 周 | 监控稳定后下线 RabbitMQ |
