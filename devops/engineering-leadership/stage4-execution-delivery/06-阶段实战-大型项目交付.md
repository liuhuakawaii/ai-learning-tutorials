# 阶段实战：大型项目交付

> 前置知识：敏捷实践、项目管理、发布管理、质量保障、跨团队协作（第 1-5 课）

## 你要做什么

你被任命为"智能客服系统"项目的技术负责人。项目涉及 5 个团队（NLP、后端、前端、数据、运维），目标 16 周内完成 MVP 上线。CTO 要求你提交一份完整的项目交付方案。

你需要输出：项目章程、技术方案评审流程、发布计划、质量计划、风险登记册、沟通计划。

## 项目章程

```markdown
# 智能客服系统 — 项目章程

## 项目背景
公司客服团队处理量已达到上限，平均响应时间 15 分钟，客户满意度 72%。
目标：通过 AI 辅助将响应时间降到 3 分钟，满意度提升到 85%。

## 项目范围
- 在线客服聊天界面（前端）
- NLP 意图识别和回复生成（NLP 团队）
- 客服工单系统（后端）
- 知识库管理（数据团队）
- 部署和监控（运维团队）

## 不在范围内
- 电话客服集成（二期）
- 多语言支持（二期）
- 自定义训练模型（二期）

## 关键里程碑
- W4：技术方案评审完成
- W8：核心功能联调通过
- W12：内测版本上线
- W16：正式发布

## 团队与职责
| 团队 | 负责人 | 职责 | 人力 |
|------|--------|------|------|
| NLP | 张工 | 意图识别、回复生成 | 4 人 |
| 后端 | 李工 | API、工单系统、知识库 | 5 人 |
| 前端 | 王工 | 聊天界面、管理后台 | 3 人 |
| 数据 | 赵工 | 数据管道、知识库数据 | 2 人 |
| 运维 | 刘工 | 部署、监控、告警 | 2 人 |

## 成功标准
- AI 回复准确率 ≥ 80%
- 平均响应时间 ≤ 3 分钟
- 系统可用性 ≥ 99.9%
- 客户满意度 ≥ 85%
```

## 发布计划

```
W12：内测版本
  ├── 只对内部客服团队开放
  ├── 收集使用反馈
  └── 监控 AI 回复准确率

W14：灰度发布
  ├── 对 10% 的客户流量开放
  ├── 对比 AI 辅助 vs 纯人工的效果
  └── 如果指标恶化，立即回滚

W16：正式发布
  ├── 100% 流量切换
  ├── 保留人工客服兜底（AI 无法识别时转人工）
  └── 持续监控和优化
```

回滚预案：

```
触发条件：
  - AI 回复准确率 < 70%
  - 系统可用性 < 99%
  - 客户投诉量上升 50% 以上

回滚步骤：
  1. 切换 Nginx 路由，流量回到旧系统（5 分钟）
  2. 通知客服团队回到纯人工模式
  3. 通知技术团队排查问题
  4. 问题修复后重新灰度
```

## 风险登记册

| 风险 | 概率 | 影响 | 应对策略 |
|------|------|------|---------|
| NLP 准确率不达标 | 高 | 高 | 提前做 PoC，W4 前验证核心场景 |
| 跨团队联调延迟 | 中 | 高 | 每周联调会议，提前定义接口契约 |
| 知识库数据质量差 | 中 | 中 | W2 前完成数据质量评估 |
| 关键人员离职 | 低 | 高 | 每个模块至少 2 人熟悉 |
| 第三方 API 不稳定 | 低 | 中 | 设计降级方案，AI 不可用时转人工 |

## 沟通计划

| 会议 | 参与者 | 频率 | 目的 |
|------|--------|------|------|
| 项目站会 | 各团队负责人 | 每天 15 分钟 | 暴露阻塞 |
| 周报 | CTO + 各负责人 | 每周 | 进展汇报、风险预警 |
| 联调会议 | 全体开发 | 每周 2 小时 | 跨团队集成测试 |
| 里程碑 Review | 全体 + 利益相关者 | 每 4 周 | 阶段验收、调整方向 |

## 参考答案

### 练习一

没有标准答案。关键是：范围要明确（"不做什么"和"做什么"一样重要），里程碑要可衡量，成功标准要量化。

### 练习二

示例：

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 需求频繁变更 | 高 | 高 | 建立变更流程，每个 Sprint 只接受 N 个变更 |
| 第三方服务不稳定 | 中 | 高 | 设计降级方案，关键接口有 fallback |
| 技术债务积累 | 高 | 中 | 每个 Sprint 分配 20% 容量清理 |
| 关键人员请假 | 中 | 中 | 知识文档化，关键模块双人负责 |
| 性能不达标 | 低 | 高 | 提前做压测，W8 前验证核心场景 |
