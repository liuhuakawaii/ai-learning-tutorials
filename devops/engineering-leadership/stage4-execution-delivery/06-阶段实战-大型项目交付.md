# 第六课：阶段实战：大型项目交付

## 场景引入

你被任命为"智能客服系统"项目的技术负责人。项目涉及 5 个团队（NLP、后端、前端、数据、运维），目标是在 16 周内完成 MVP 上线。CTO 要求你提交一份完整的项目交付方案。

你需要输出什么？一份能让 CTO 有信心批准、让团队有清晰方向、让利益相关者知道预期的**交付方案**。这一课，我们综合运用前五课的知识，输出一份完整的大型项目交付方案模板。

## 学习目标

完成本课学习后，你将能够：

1. 编写完整的项目章程
2. 组织技术方案评审
3. 设计发布计划（灰度策略、回滚预案）
4. 制定质量计划（测试策略、SLA、代码审查）
5. 维护风险登记册和沟通计划
6. 使用复盘模板进行项目复盘

## 一、项目章程

```
项目章程 - 智能客服系统 v1.0

1. 项目背景
   当前客服系统依赖人工客服，响应时间平均 5 分钟，高峰期排队超过 15 分钟。
   客服人力成本每年 800 万，且随业务增长线性增加。需要引入 AI 客服系统，
   自动处理 60% 的常见问题。

2. 项目目标
   业务目标：自动解决率 ≥ 60%，平均响应时间 < 3 秒，用户满意度 ≥ 85%
   技术目标：NLP 意图识别准确率 ≥ 90%，系统可用性 ≥ 99.9%，p99 < 500ms

3. 范围
   包含：意图识别引擎、多轮对话管理、知识库管理、客服工作台、数据分析看板
   不包含：语音识别（二期）、情感分析（二期）、多语言支持（二期）

4. 里程碑
   M1（第 4 周）：NLP 引擎 MVP + 知识库基础版
   M2（第 8 周）：对话管理 + 客服工作台
   M3（第 12 周）：系统集成 + 灰度发布
   M4（第 16 周）：全量上线 + 效果评估

5. 关键干系人
   项目发起人：CTO | 技术负责人：XXX | 产品负责人：XXX

6. 预算与资源
   开发团队：15 人（NLP 4 + 后端 4 + 前端 3 + 数据 2 + 运维 2）
   计算资源：GPU 服务器 4 台、应用服务器 8 台

7. 成功标准
   自动解决率 ≥ 60%，可用性 ≥ 99.9%，满意度 ≥ 85%，16 周内完成
```

## 二、技术方案评审

### 2.1 评审清单

```
架构设计：
  ☐ 系统架构图清晰？组件职责明确？
  ☐ 可扩展性、高可用性考虑？
  ☐ 技术选型有充分理由？

接口设计：
  ☐ 内部/外部接口定义清晰？有契约文档？
  ☐ 错误处理完整？向后兼容性？

数据设计：
  ☐ 数据模型合理？存储方案合适？
  ☐ 数据迁移、备份恢复策略明确？

性能与安全：
  ☐ 性能基准和瓶颈识别？缓存策略？
  ☐ 安全威胁分析？认证授权？数据加密？
```

### 2.2 评审流程

```
1. 方案编写（技术 Lead）→ 2. 预审（2-3 位资深工程师，提前 2 天）
→ 3. 评审会议（1-2 小时）→ 4. 方案修订 → 5. 最终确认签署
```

## 三、发布计划

### 3.1 灰度策略

```
阶段 1：内部测试（第 13 周）
  范围：公司内部客服团队（50 人），验证功能和体验，持续 1 周

阶段 2：1% 灰度（第 14 周）
  范围：1% 真实用户，观察自动解决率/满意度/错误率/延迟
  回滚条件：自动解决率 < 40% 或错误率 > 1%

阶段 3：10% 灰度（第 14-15 周）
  范围：10% 真实用户，增加系统资源使用率观察
  回滚条件：自动解决率 < 50% 或错误率 > 0.5%

阶段 4：50% 灰度（第 15-16 周）
  范围：50% 真实用户，验证大规模负载下的稳定性

阶段 5：全量发布（第 16 周）
  持续观察 1 周，保留快速回滚能力
```

### 3.2 回滚预案

```
代码回滚：负载均衡器切换旧版本，< 5 分钟
配置回滚：恢复配置文件到上一版本，< 5 分钟
数据回滚：回滚脚本 + 备份恢复，< 30 分钟（前提：迁移必须可逆）
NLP 模型回滚：切换到上一版本模型，< 10 分钟

发布前 1 周做回滚演练，验证全流程可行性。
```

## 四、质量计划

### 4.1 测试策略

```
┌──────────────┬────────┬──────────────────────────────────────┐
│ 测试类型      │ 比例   │ 覆盖范围                              │
├──────────────┼────────┼──────────────────────────────────────┤
│ 单元测试      │ 70%   │ NLP引擎、后端逻辑、前端组件，覆盖率≥80% │
│ 集成测试      │ 20%   │ API接口、数据库交互、第三方服务调用      │
│ E2E 测试     │ 10%   │ 核心用户流程（咨询→回答→满意/转人工）   │
└──────────────┴────────┴──────────────────────────────────────┘

性能测试：1000 并发负载测试，5000 并发压力测试，72 小时稳定性测试
安全测试：渗透测试、认证测试、数据安全测试
```

### 4.2 SLA 定义

```
┌──────────────────┬────────────────────────────────────┐
│ 指标              │ 目标值                              │
├──────────────────┼────────────────────────────────────┤
│ 可用性            │ ≥ 99.9%（每月最多 43.8 分钟停机）   │
│ 响应延迟          │ p99 < 500ms                        │
│ 错误率            │ < 0.1%                             │
│ 自动解决率        │ ≥ 60%                              │
│ 用户满意度        │ ≥ 85%                              │
└──────────────────┴────────────────────────────────────┘

违约：可用性<99% 分析根因；<95% 影响季度绩效；自动解决率<50% 暂停全量发布
```

### 4.3 代码审查规范

所有 PR 至少 1 人审查，关键模块（NLP 引擎）需 2 人。普通 PR 24 小时内完成，紧急 PR 4 小时内。审查标准：逻辑正确性、安全性、性能、可读性、测试覆盖。

## 常见误区

1. **"项目章程太形式化"** — 它是团队的"宪法"，定义目标和成功标准，是所有决策的参考依据。

2. **"技术方案评审浪费时间"** — 早期发现设计问题成本最低。等到开发完成才发现，修复成本是 10 倍。

3. **"灰度发布只适用于大公司"** — 即使只有 100 个用户，也可以先让 10 个使用新版本。

4. **"复盘是追责会"** — 复盘的目的是改进。如果变成追责会，团队就不会说真话。

5. **"风险登记册列完就行"** — 需要持续更新。风险是动态变化的。

6. **"沟通计划太官僚"** — 它确保正确的人在正确的时间获得正确的信息。

---

## 工程建议

1. **项目章程是第一步**。花 2 小时编写，让后续所有决策有依据。

2. **技术方案评审在编码前完成**。先评审再编码，不要边写边设计。

3. **灰度发布是必须的**。范围和时间可以调整，但不能省略。

4. **质量计划在项目启动时制定**。测试策略、SLA、代码审查规范不是快结束时才考虑的。

5. **风险登记册持续更新**。每周花 15 分钟，新风险会出现，旧风险会消失。

6. **复盘要坦诚**。作为技术负责人，带头承认自己的错误。

---

## 小结

- **项目章程** 定义目标、范围、里程碑和成功标准
- **技术方案评审** 在早期发现设计问题，评审清单确保全面性
- **发布计划** 包含灰度策略和回滚预案
- **质量计划** 包含测试策略、SLA 和代码审查规范
- **风险登记册** 需要持续跟踪，每个风险有预案和负责人
- **沟通计划** 确保信息透明，升级机制确保问题及时解决
- **复盘模板** 总结经验教训，产出可执行的改进措施

## 练习

### 练习一：项目章程编写

你要开发一个"内部知识管理系统"，目标是让公司 500 名员工高效搜索和分享内部文档。请编写项目章程，包含目标、范围、里程碑、干系人和成功标准。

### 练习二：风险识别

你负责将单体应用拆分为微服务架构，涉及 6 个团队，计划 6 个月。请识别至少 6 个关键风险，填写风险登记册并设计预案。

### 练习三：复盘分析

某项目复盘数据：目标 12 周完成 MVP，实际 16 周；自动解决率目标 60%，实际 45%；可用性目标 99.9%，实际 99.5%；上线后 3 次 P0 故障；团队加班率 40%。请分析失败原因并给出改进建议。

## 参考答案

### 练习一

**答案：**
项目章程包含：背景（共享文件夹搜索困难）→ 业务目标（搜索10分→1分，月活≥300）→ 技术目标（p95<1秒，可用性≥99.5%）→ 范围（包含：上传/搜索/分类/权限/版本；不包含：在线编辑/工作流/AI摘要）→ 里程碑（3周上传→6周搜索→9周权限→12周上线）→ 成功标准（搜索<1分钟，月活≥300，满意度≥80%）

### 练习二

**答案：**
```
R1 数据一致性(高/高/极高)：Saga模式+梳理依赖 | R2 团队缺经验(中/高/高)：非核心先练手
R3 拆分中故障(中/高/高)：旧系统可回退+灰度 | R4 通信性能(中/中/中)：基准测试+SLA
R5 运维复杂度(高/中/高)：同步建设监控 | R6 团队协调(中/中/中)：跨团队站会+契约
```

### 练习三

**答案：**
```
一、延期（12→16周）：需求变更无冻结 + 估算未含协调成本 + 资源被抽调
二、解决率不达标（60→45%）：训练数据质量差 + 知识库覆盖不全
三、可用性不达标（99.9→99.5%）：架构/测试不足 + 监控不完善
四、加班率40%：排期紧 + 需求返工 + 技术债
五、综合改进：启动阶段充分评审+估算+确认资源；执行阶段需求冻结+站会+风险评审；发布阶段灰度+回滚+监控
```
**要点：** 加班率过高是管理问题，不是团队问题。
