# 第四课：质量保障

## 场景引入

你的团队每周发布两个版本，每次发布后平均出现 3-5 个线上 Bug。开发花 30% 时间修 Bug，测试抱怨"提测质量太差"。你查了一下：单元测试覆盖率 12%，代码审查平均 5 分钟（基本点 Approve），集成测试只有 3 条。

问题的根源不是"测试不够多"，而是**质量保障体系缺失**。质量不是测出来的，而是设计出来的。

## 学习目标

完成本课学习后，你将能够：

1. 建立有效的代码审查机制，避免形式化
2. 设计测试策略，理解测试金字塔
3. 定义 SLA 并转化为可度量指标
4. 追踪质量指标（缺陷率、MTTR、变更失败率）
5. 理解 Shift-left 测试的理念和实践

---

## 一、代码审查

### 1.1 审查的三个价值

```
知识传递：团队了解彼此代码，避免知识孤岛
质量把关：发现逻辑错误、安全漏洞、性能问题
设计讨论：在实现前讨论方案，避免返工
```

### 1.2 审查清单

```
逻辑 ★★★★★：代码逻辑正确？边界情况遗漏？错误处理完整？
安全 ★★★★★：SQL注入/XSS/CSRF？敏感数据处理？
设计 ★★★★：符合现有架构？抽象层次合理？
测试 ★★★★：有对应测试？覆盖正常和异常路径？
性能 ★★★★：N+1查询？不必要内存分配？
可读 ★★★：命名清晰？复杂逻辑有注释？
```

### 1.3 异步审查 vs 同步审查

```
异步审查（PR方式）：80% 变更使用，24小时内完成
同步审查（Pair Review）：20% 关键变更使用——复杂功能、架构变更、安全相关
新人前 3 个月所有 PR 都用同步审查
```

### 1.4 避免形式化

```
形式化信号：审查<5分钟、只有LGTM、从不提改进建议
改进措施：
  - 每100行至少审查15分钟
  - 审查意见模板："这段逻辑的意图是？""是否考虑了XX场景？"
  - 追踪审查者的平均审查时间和意见数量
  - 轮换审查者，避免固定搭配
```

## 二、测试策略

### 2.1 测试金字塔

```
        ╱╲
       ╱E2E╲         少量：核心用户流程（10%）
      ╱──────╲
     ╱ 集成测试 ╲      适量：模块间协作（20%）
    ╱────────────╲
   ╱   单元测试    ╲    大量：单个函数/类逻辑（70%）
  ╱──────────────────╲
```

### 2.2 不同测试类型

```
单元测试（70%，<1分钟）：
  好的特征：测行为不测方法、不依赖外部、毫秒级、独立运行
  示例：calculateOrderPrice(1200, {discount:0.1}) → 1080

集成测试（20%，<10分钟）：
  范围：API接口、数据库读写、消息队列、第三方服务调用
  策略：测试数据库（每次清空）、Mock 第三方服务

E2E 测试（10%，<30分钟）：
  只覆盖核心流程：注册登录、下单支付
  维护原则：稳定选择器(data-testid)、定期清理过时测试
```

## 三、SLA 定义

### 3.1 核心概念

```
SLI（具体指标）→ SLO（目标值）→ SLA（正式承诺+违约后果）

示例：推荐系统
  SLI：过去30天请求成功率 = 99.95%
  SLO：请求成功率 ≥ 99.95%
  SLA：低于此值赔偿当月服务费的10%
```

### 3.2 可用性级别

```
┌──────────┬──────────────┬──────────────────────┐
│ 可用性    │ 每月停机      │ 典型场景              │
├──────────┼──────────────┼──────────────────────┤
│ 99%      │ 7.2 小时     │ 内部工具              │
│ 99.9%    │ 43.8 分钟    │ 一般 B 端服务         │
│ 99.95%   │ 21.9 分钟    │ 电商、SaaS           │
│ 99.99%   │ 4.38 分钟    │ 支付、金融            │
└──────────┴──────────────┴──────────────────────┘
```

### 3.3 SLA 定义示例

```
推荐系统 SLA：
  可用性 ≥ 99.95% | p99 < 100ms | 错误率 < 0.1% | 数据新鲜度 < 1小时
  违约：可用性<99.9% 赔偿10%，<99% 赔偿30%
```

## 四、质量指标

### 4.1 DORA 四大指标

```
┌──────────────────┬──────────────────────────────────────┐
│ 指标              │ 精英/高效/低效                        │
├──────────────────┼──────────────────────────────────────┤
│ 部署频率          │ 每天多次 / 每周到月 / 每月以下         │
│ 变更前置时间      │ <1小时 / 1天-1周 / 1周以上            │
│ 变更失败率        │ 0-15% / 16-30% / 30%以上             │
│ 故障恢复时间      │ <1小时 / 1天-1周 / 1周以上            │
└──────────────────┴──────────────────────────────────────┘
```

### 4.2 其他核心指标

```
缺陷率：线上Bug数/功能点数，目标<0.5
MTTR：平均故障恢复时间=总恢复时间/故障次数，目标<30分钟
变更失败率：导致故障的部署/总部署，目标<5%
```

## 五、Shift-left 测试

### 5.1 核心思想

把质量保障活动尽早移到开发流程前端。

```
传统：需求→设计→开发→测试→修复→上线（问题在测试阶段发现，修复成本50x）
Shift-left：需求评审→设计评审→代码审查→单元测试→集成测试→上线
  需求阶段发现：1x | 设计阶段：5x | 开发阶段：10x | 测试阶段：50x | 上线后：200x
```

### 5.2 实践

```
需求阶段：测试参与需求评审、定义验收标准、识别边界情况
设计阶段：可测试性评估、接口契约先定义、测试策略制定
开发阶段：TDD、代码审查、静态分析
提测阶段：CI自动运行测试、冒烟测试、性能基准
```

## 常见误区

1. **"覆盖率越高越好"** — 100% 覆盖率但没有断言正确行为等于没有测试。关注质量。
2. **"代码审查太慢"** — 审查不是瓶颈，返工才是。30 分钟审查避免 2 天返工。
3. **"SLA 是运维的事"** — 开发、运维、产品共同参与定义。
4. **"E2E 越多越好"** — E2E 慢、脆弱、维护成本高。只覆盖核心路径。
5. **"质量是测试人员的责任"** — 质量是整个团队的责任。
6. **"出了 Bug 就加测试"** — 先分析根因，针对根因改进。

---

## 工程建议

1. **从代码审查开始改进**。成本最低、效果最明显的质量保障手段。
2. **投资自动化测试**。优先自动化单元和集成测试。
3. **定义明确的 SLA**。没有 SLA 就不知道"好"是什么标准。
4. **建立质量看板**。让质量数据可见，团队看到改善会有动力保持。
5. **Shift-left 需要文化支撑**。让测试参与需求评审，让开发写测试。
6. **质量改进是持续过程**。每次回顾会讨论一个质量改进项。

---

## 小结

- **代码审查** 核心价值是知识传递和设计讨论，避免形式化需规范+追踪
- **测试策略** 遵循金字塔：70%单元、20%集成、10%E2E
- **SLA** 从 SLI→SLO→SLA 逐步转化，是团队的质量承诺
- **DORA 四大指标** 是行业标准，缺陷率和 MTTR 是最常用的内部指标
- **Shift-left** 把质量保障前移到需求和设计阶段，显著降低修复成本

## 参考答案

### 练习一

**思路：** 形式化根源是缺乏规范和激励。

**答案：**
1. 建立规范：每100行至少15分钟，每个PR至少2条具体意见，使用标准化审查清单
2. 工具支持：CI自动运行测试/Lint/安全扫描，追踪审查时间和意见数量
3. 文化建设：鼓励肯定好的设计，新人前3个月同步审查，每月分享"最佳审查意见"

### 练习二

**思路：** 认证系统是安全关键系统，需覆盖功能正确性和安全性。

**答案：**
```
单元测试（70%）：密码强度验证、Token生成验证、会话过期、输入清理
集成测试（20%）：注册/登录/密码重置完整流程、OAuth流程、数据库交互、并发测试
E2E测试（10%）：完整注册/登录/密码重置/OAuth流程
安全测试：SQL注入、XSS、暴力破解防护、Token安全性、CSRF防护
```

### 练习三

**思路：** 内部平台SLA可以宽松但不能没有。

**答案：**
```
可用性≥99.5%（每月最多3.6小时）| 查询延迟p95<5秒(简单)/<30秒(复杂)
报表生成p95<2分钟 | 数据新鲜度T+1在次日8:00前 | 错误率<1%
维护窗口：每周三22:00-次日02:00
升级：P0(不可用)5分钟响应 | P1(降级)15分钟响应 | P2(异常)工作时间处理
```
