# 第三课：发布管理

## 场景引入

周五下午 4 点，你的团队刚合并了一个"小改动"到主分支。CI 通过了，代码审查也过了。你决定直接部署到生产环境。5 分钟后，客服群涌入投诉：用户无法下单。你紧急回滚，但数据已经不一致了。周末两天，团队都在修复数据。

发布管理不是"点一下部署按钮"，它是一套完整的工程实践，涵盖发布节奏、灰度策略、回滚预案和发布后的监控。

## 学习目标

完成本课学习后，你将能够：

1. 根据团队特点选择时间箱或功能箱发布节奏
2. 设计灰度发布策略（金丝雀、蓝绿部署、Feature Flag）
3. 制定回滚策略，包括数据回滚预案
4. 编写发布检查清单
5. 建立发布后监控和 Hotfix 流程

---

## 一、发布节奏：时间箱 vs 功能箱

```
时间箱（Time-boxed）：固定时间发布，功能可推迟到下一版本
  适用：SaaS 产品、用户端应用，典型周期每周/每两周

功能箱（Feature-boxed）：功能完整才发布，时间不固定
  适用：ToB 软件、大版本升级，典型周期每月/每季度

大多数团队应该追求时间箱发布——它迫使团队拆分功能、控制范围、投资自动化。
```

### 发布列车模型

```
发布列车 v2.3（4月15日发车）
  代码截止：4月12日 | 灰度：4月13日 | 全量：4月15日
  上车：推荐算法优化 ✅、用户画像 API ✅
  没赶上：新版搜索 UI ❌（测试未完成）→ 推迟到 v2.4
  规则：功能没准备好？等下一班车。不要为了赶车降低质量。
```

## 二、灰度发布

### 2.1 金丝雀发布

```
1% 用户 → 观察1h → 无异常 → 5% → 观察2h → 20% → 观察4h → 50% → 观察1天 → 100%
任何阶段发现异常 → 立即回滚

监控指标：错误率<0.1%、p99延迟<200ms、CPU<80%、业务指标不低于基线95%
```

### 2.2 蓝绿部署

```
用户 → 负载均衡器 → 蓝环境(v1, 100%流量) / 绿环境(v2, 0%)
步骤：部署v2到绿 → 健康检查 → 切换流量 → 观察 → 有问题切回蓝

优点：零停机、回滚极快
缺点：双倍资源、数据库迁移需特殊处理
```

### 2.3 Feature Flag

```
if feature_flag.enabled('new_recommendation', user):
    return new_recommendation(user)
else:
    return old_recommendation(user)

管理原则：
  ✓ 每个 Flag 有拥有者和过期日期  ✓ 默认值是"关闭"  ✓ 定期清理
  ✗ 不要嵌套 Flag  ✗ 不要用 Flag 替代代码分支
```

## 三、回滚策略

### 3.1 三种回滚层次

```
代码回滚：切换负载均衡器/重新部署旧版本，最简单
配置回滚：恢复配置文件/环境变量，中等
数据回滚：恢复数据库状态，最复杂——必须有备份、迁移脚本可逆
```

### 3.2 数据回滚黄金规则

```
规则 1：所有数据库迁移必须可逆（CREATE TABLE 写好 DROP TABLE）
规则 2：迁移和回滚脚本必须在预发布环境验证
规则 3：大数据量迁移用双写策略（创建新表→双写→回填→切换读→停止写旧表→删除旧表）
规则 4：保留回滚窗口（24-72小时），新旧版本数据格式必须兼容
```

### 3.3 自动 vs 手动回滚

```
自动回滚：错误率>1%连续5分钟、p99>500ms连续5分钟、健康检查3次失败 → 自动切回
手动回滚：告警→确认→执行回滚→验证→通知→记录事故报告
建议：代码回滚用自动，数据回滚用手动（风险更高，需人工确认）
```

## 四、发布检查清单

```
┌─────┬───────────────────────────────────────────┬───────────┐
│ 序号 │ 检查项                                     │ 状态      │
├─────┼───────────────────────────────────────────┼───────────┤
│  1  │ 所有 PR 已合并且通过代码审查                  │ ☐         │
│  2  │ CI/CD 流水线全部通过                         │ ☐         │
│  3  │ 单元测试覆盖率 ≥ 80%                         │ ☐         │
│  4  │ 安全扫描无高危漏洞                           │ ☐         │
│  5  │ 性能测试通过                                │ ☐         │
│  6  │ 数据库迁移脚本已审查且可逆                    │ ☐         │
│  7  │ 回滚方案已准备且已测试                        │ ☐         │
│  8  │ 监控和告警已配置                             │ ☐         │
│  9  │ 发布时间窗口确认（避开业务高峰期）            │ ☐         │
│ 10  │ 值班人员确认、干系人已通知                    │ ☐         │
│ 11  │ 功能开关已配置（默认关闭）                    │ ☐         │
│ 12  │ Release Notes 已编写                        │ ☐         │
└─────┴───────────────────────────────────────────┴───────────┘

发布中：按灰度策略逐步放量，每阶段观察监控指标和业务指标
发布后：全量后观察30分钟，对比基线确认无异常，清理临时Flag
```

## 五、发布后监控和告警

### 5.1 监控指标优先级

```
第一优先级：错误率(5xx)、延迟(p50/p95/p99)、可用性(健康检查)、流量(QPS)
第二优先级：业务指标(下单率/支付成功率)、资源(CPU/内存/磁盘)、依赖(DB连接数/缓存命中率)
第三优先级：用户行为路径、告警频率
```

### 5.2 告警分级

```
┌──────┬──────────────────────┬──────────────┬──────────────┐
│ 级别  │ 定义                  │ 响应时间      │ 处理方式      │
├──────┼──────────────────────┼──────────────┼──────────────┤
│ P0   │ 服务完全不可用         │ 5 分钟       │ 立即回滚      │
│ P1   │ 核心功能降级          │ 15 分钟      │ 值班响应+评估  │
│ P2   │ 指标异常但服务正常     │ 1 小时       │ 工作时间处理  │
│ P3   │ 潜在风险              │ 下个工作日    │ 记录并排期    │
└──────┴──────────────────────┴──────────────┴──────────────┘
```

### 5.3 告警疲劳预防

```
  1. 告警必须可操作：✓"CPU 85%持续10分钟，建议检查部署或扩容"
  2. 阈值基于历史数据：用 p99 + 20%
  3. 聚合相关告警：同一原因触发的多个告警合并
  4. 每月清理无效告警
```

## 六、Hotfix 流程

```
Hotfix 流程（简化但不省略）：
  1. 问题确认（5分钟）：确认真实问题、影响范围、是否需要Hotfix（能回滚先回滚）
  2. 修复开发（1-4小时）：从main创建hotfix分支，最小化改动，必须有测试
  3. 审查（30分钟）：至少一人审查，重点：改动范围、副作用、测试覆盖
  4. 部署（30分钟）：简化流程但有灰度，确认回滚方案
  5. 验证（30分钟）：确认问题解决、无副作用、监控正常
  6. 事后复盘（第二天）：根因分析、改进措施、更新监控

Hotfix 边界：
  ✅ 允许：修复Bug、安全漏洞、恢复可用性、修复数据不一致
  ❌ 不允许：顺便加功能、重构、升级依赖、优化性能（除非是根因）
```

## 常见误区

1. **"我们没有用户，不需要灰度"** — 灰度的价值还有验证部署流程和监控配置。

2. **"回滚就是重新部署旧版本"** — 数据库 schema 变更后，旧版本可能无法工作。回滚必须考虑数据层。

3. **"Feature Flag 不需要管理"** — 没人管理的 Flag 会变成技术债。每个 Flag 必须有拥有者和过期日期。

4. **"发布前检查清单太浪费时间"** — 15 分钟可以完成。一次线上事故的修复成本是 100 倍。

5. **"Hotfix 不需要测试"** — 需要测试，只是范围更聚焦。没有测试的 Hotfix 可能引入新问题。

6. **"蓝绿部署成本太高"** — 云环境下可以用按需扩容，不需要永久双倍资源。

---

## 工程建议

1. **投资 CI/CD 流水线**。自动化是发布管理的技术基础。

2. **发布频率越高，风险越低**。小批量发布意味着每次变更范围小，出问题容易定位和回滚。

3. **回滚能力比发布能力更重要**。发布之前先确认能回滚。

4. **监控是发布的眼睛**。没有监控的发布是盲人开车。

5. **建立发布文化**。发布应该是常态，不是事件。目标是"发布是一个无聊的过程"。

6. **记录每次发布**。出了问题需要排查时，完整的发布记录是最重要的线索。

---

## 小结

- **发布节奏** 中时间箱适合大多数团队，发布列车确保可预测性
- **灰度发布** 是降低风险的核心手段：金丝雀、蓝绿部署、Feature Flag 各有适用场景
- **回滚策略** 覆盖代码、配置和数据三层，数据回滚需特别谨慎
- **发布检查清单** 防止遗漏，发布前/中/后各有重点
- **监控告警** 要可操作、分级、避免疲劳
- **Hotfix** 简化但不省略，改动范围必须最小化

## 练习

### 练习一：灰度发布策略设计

你要发布一个支付系统的核心接口升级，涉及金额计算逻辑修改。用户量 100 万，日交易额 5000 万。请设计灰度发布策略，包括灰度阶段、观察指标、回滚条件和时间安排。

### 练习二：回滚方案设计

你的团队要发布数据库 schema 变更：将 users 表的 phone 字段从 VARCHAR(11) 改为 VARCHAR(20)，同时新增 country_code 字段。请设计完整的发布和回滚方案。

### 练习三：发布检查清单编写

你的团队即将发布电商后台管理系统新版本，涉及：新功能（商品批量导入）、Bug 修复（订单统计不准确）、性能优化（报表查询速度提升）。请编写发布检查清单。

## 参考答案

### 练习一

**思路：** 支付系统涉及资金安全，观察指标必须包含业务指标（交易成功率、金额准确性）。

**答案：**

```
阶段 1：内部测试环境（1天）→ 用真实数据副本验证金额计算正确性
阶段 2：1% 灰度（2小时）→ 观察交易成功率/金额偏差/延迟
阶段 3：10% 灰度（4小时）→ 增加支付渠道回调成功率观察
阶段 4：50% 灰度（1天）→ 全面监控技术+业务指标
阶段 5：100% 全量 → 持续观察3天，保留回滚能力1周

回滚条件（任一触发）：
  交易成功率下降>0.01% | 金额偏差>0 | p99>500ms | 金额相关投诉
```

**要点：** 支付系统回滚条件必须包含金额准确性；灰度观察时间比普通功能更长。

### 练习二

**思路：** VARCHAR 扩展可在线完成，但需考虑旧代码兼容性、锁表风险和回滚数据丢失问题。

**答案：**

```
阶段 1：兼容性变更（第1周）
  1. 新增 country_code 字段（默认'+86'）
  2. phone 字段 VARCHAR(11)→VARCHAR(20)，用在线DDL避免锁表
  3. 验证旧代码可正常读写新格式
  4. 灰度发布新代码

阶段 2：数据回填（第2周）
  1. 回填历史数据的 country_code
  2. 验证数据一致性
  3. 清理旧格式数据

回滚方案：
  阶段1回滚：代码回滚即可（旧代码兼容新字段）
  阶段2回滚：停止回填+代码回滚+从备份恢复（保留72小时回滚窗口）
```

**要点：** Schema 变更分阶段：先兼容后切换；回滚要考虑数据层。

### 练习三

**思路：** 三种变更类型有不同的验证重点。

**答案：**

```
功能验证：
  ☐ 批量导入正常/异常格式/大文件测试通过
  ☐ 并发导入测试、导入失败错误提示和回滚机制
  ☐ 导入后数据一致性验证

Bug修复验证：
  ☐ 订单统计准确性对比（修复前后一致）
  ☐ 边界情况（退款/取消/部分退款）
  ☐ 历史数据回溯正确

性能验证：
  ☐ 报表查询速度对比（p95延迟）
  ☐ 大数据量测试（100万条）
  ☐ 不影响查询结果正确性

发布准备：
  ☐ 数据库迁移脚本已审查且可逆
  ☐ 回滚方案已准备、监控已配置
  ☐ 发布时间避开月末报表高峰
  ☐ 值班人员确认、干系人已通知
```

**要点：** 性能优化必须有量化对比；发布时间要考虑业务周期。
