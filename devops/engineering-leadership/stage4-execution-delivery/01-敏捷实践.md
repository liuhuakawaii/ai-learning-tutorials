# 敏捷实践

> 前置知识：管理转型、团队建设（阶段一、二）

## 一个"伪敏捷"团队

你刚接手一个 8 人后端团队，前任留下的"敏捷流程"是这样的：每两周开一次站会，每人汇报 15 分钟；Sprint 评审变成 PPT 演示大会；回顾会议从来没人提尖锐问题。

团队对"敏捷"两个字已经麻木，私下叫它"站着开的周会"。

这不是敏捷，这是**机械执行仪式**。真正的敏捷不是照搬 Scrum Guide，而是让反馈循环更短、交付节奏更稳、改进持续发生。

## Scrum 的四个仪式到底在干什么

### 站会（Daily Standup）

```
正确的站会（15 分钟以内）：
  每人回答三个问题：
  1. 昨天完成了什么？
  2. 今天打算做什么？
  3. 有什么阻塞？

错误的站会：
  ✗ 每人讲 15 分钟技术细节
  ✗ 变成向经理汇报的会议
  ✗ 站着开但没有时间限制
  ✗ 只讲"做了什么"不讲"遇到什么问题"
```

站会的目的是**暴露阻塞**，不是汇报工作。如果站会变成了汇报会，说明你把它当成了管理工具而不是协作工具。

### Sprint Planning

```
正确的 Planning：
  - 团队一起决定这个 Sprint 做什么
  - 每个任务有明确的完成标准（Definition of Done）
  - 任务拆分到 1-2 天能完成
  - 团队对容量有共识（不要承诺过多）

错误的 Planning：
  ✗ 经理分配任务，团队只是接收
  ✗ 任务太大，一个 Sprint 做不完
  ✗ 没有完成标准，"做完"的定义模糊
```

### Sprint Review

```
正确的 Review：
  - 演示可工作的软件（不是 PPT）
  - 邀请利益相关者参加
  - 收集反馈，调整 Backlog
  - 30 分钟以内

错误的 Review：
  ✗ 变成 PPT 汇报大会
  ✗ 没有利益相关者参加
  ✗ 演示的是"代码"而不是"可工作的功能"
```

### Sprint Retrospective

```
正确的 Retro：
  - 讨论"怎么做得更好"，不是"谁的错"
  - 每次产出 1-2 个可执行的改进行动
  - 跟踪上次 Retro 的改进是否落地
  - 安全的氛围——可以讲真话

错误的 Retro：
  ✗ 没人提尖锐问题
  ✗ 讨论了很多但没有行动
  ✗ 变成批斗会或甩锅会
```

## Kanban：另一种选择

如果你的团队不适合固定周期的 Sprint（比如运维团队、需求频繁变化的团队），Kanban 可能更适合。

Kanban 的核心原则：

```
1. 可视化工作流
   ┌──────────┬──────────┬──────────┬──────────┐
   │  Backlog  │  To Do   │ In Progress │  Done   │
   ├──────────┼──────────┼──────────┼──────────┤
   │ 任务 A   │ 任务 D   │ 任务 G   │ 任务 J   │
   │ 任务 B   │ 任务 E   │ 任务 H   │ 任务 K   │
   │ 任务 C   │ 任务 F   │          │          │
   └──────────┴──────────┴──────────┴──────────┘

2. 限制在制品（WIP Limit）
   In Progress 最多 3 个任务
   → 完成一个才能开始下一个
   → 减少多任务切换的损耗

3. 管理流动
   关注任务从"开始"到"完成"的周期时间
   目标：让周期时间越来越稳定
```

## Scrum vs Kanban

| 维度 | Scrum | Kanban |
|------|-------|--------|
| 节奏 | 固定 Sprint（1-4 周） | 持续流动 |
| 角色 | Product Owner、Scrum Master | 无强制角色 |
| 计划 | Sprint Planning | 按需拉取 |
| 变更 | Sprint 内不变更 | 随时可变 |
| 适合 | 产品开发、需求相对稳定 | 运维、支持、需求频繁变化 |

## 敏捷反模式

### 反模式一：仪式化

```
症状：所有仪式都在做，但没有实际效果
根因：把敏捷当成了流程而不是思维方式
解决：砍掉不产生价值的仪式，只保留必要的
```

### 反模式二：假自治

```
症状：名义上团队自组织，实际经理在背后操控
根因：经理不信任团队的判断力
解决：从小决策开始放权，逐步建立信任
```

### 反模式三：速度崇拜

```
症状：Sprint Velocity 成了 KPI，团队为了数字虚报点数
根因：用 Velocity 衡量团队产出，而不是衡量交付节奏
解决：Velocity 只用于团队内部计划，不用于对外汇报
```

## 练习

### 练习一：诊断你的团队

用以下维度评估你当前团队的敏捷成熟度（1-5 分）：

- 反馈循环：从发现问题到修复上线需要多久？
- 交付节奏：团队能否稳定地每个 Sprint 交付可工作的软件？
- 改进机制：回顾会议的改进行动是否落地？
- 协作效率：团队成员之间的沟通是否顺畅？

### 练习二：改进站会

观察你团队的下一次站会，记录：每人发言时长、是否暴露了阻塞、会后是否有行动。然后设计一个改进方案。

---

## 参考答案

### 练习一

没有标准答案。关键是诚实评估。大多数团队在"改进机制"上得分最低——讨论了很多但行动不落地。

### 练习二

改进方案示例：

```
当前问题：站会每人 10 分钟，总时长 80 分钟，没有暴露阻塞

改进：
1. 设置计时器，每人 2 分钟
2. 只回答三个问题：昨天、今天、阻塞
3. 技术讨论记录下来，会后单独讨论
4. 每周指定一个人负责"阻塞追踪"——跟踪上周暴露的阻塞是否解决

预期效果：站会从 80 分钟缩短到 20 分钟，阻塞暴露率提升
```
