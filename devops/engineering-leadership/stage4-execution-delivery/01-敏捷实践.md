# 第一课：敏捷实践

## 场景引入

你刚接手一个8人的后端团队，前任经理留下的"敏捷流程"是这样的：每两周开一次站会，每人汇报15分钟；Sprint评审变成PPT演示大会；回顾会议从来没人提尖锐问题。团队对"敏捷"两个字已经麻木，私下叫它"站着开的周会"。

这不是敏捷，这是**机械执行仪式**。真正的敏捷不是照搬 Scrum Guide，而是让反馈循环更短、交付节奏更稳、改进持续发生。

## 学习目标

完成本课学习后，你将能够：

1. 理解 Scrum 四大仪式的真正目的，避免形式化执行
2. 掌握 Kanban 的核心原则：WIP 限制和流动效率
3. 根据团队特点选择 Scrum 或 Kanban
4. 组织有效的站会和回顾会议
5. 识别并纠正常见的敏捷反模式

---

## 一、Scrum 框架

### 1.1 Sprint 的本质

Sprint 的核心价值是**创造可预测性**。一个健康的 Sprint 回答三个问题：承诺了什么？完成了多少？什么阻碍了达成目标？

Sprint 长度选择：1 周（需求变化极快）、2 周（大多数团队默认）、3-4 周（需求稳定的基础设施团队）。新团队从 2 周开始，运行 3-4 个 Sprint 后根据回顾结果调整。

### 1.2 Sprint Planning

Sprint Planning 不是"产品经理把需求丢过来，开发接单"。正确做法分两部分：

**Part 1 为什么做**：产品介绍业务目标，团队讨论技术风险和依赖，共同确认 Sprint Goal。

**Part 2 怎么做**：团队自行拆分任务（不是产品拆），估算工作量，识别 Spike 任务。

## 二、站会的正确打开方式

### 2.1 站会不是汇报会

```
错误：每个人面向经理汇报 → 正确：团队面向看板同步信息
```

### 2.2 改良三问（聚焦价值流动）

1. 哪张卡片从"进行中"移到了"完成"？（聚焦完成）
2. 哪张卡片今天会移到"完成"？（聚焦承诺）
3. 有没有卡片停留超过 3 天？阻碍是什么？（聚焦瓶颈）

### 2.3 执行技巧

```
✓ 固定时间地点  ✓ 严格15分钟（用计时器）  ✓ 每人≤2分钟
✓ 复杂讨论记录到 Parking Lot 会后讨论
✗ 经理主导点评  ✗ 变成技术讨论会  ✗ 连续跳过3次以上
```

## 三、Kanban：流动效率优先

### 3.1 核心思想

Kanban 不是"没有 Sprint 的 Scrum"。它关注**工作流动**而非人员忙碌。

### 3.2 WIP 限制（Kanban 的灵魂）

> 同时做 5 件事每件完成 20%，不如一次做完 2 件事。

WIP 限制初始值 = 团队人数 × 1.5。经常堆积说明 WIP 太高，经常空闲说明 WIP 太低。

### 3.3 流动效率指标

```
前置时间(Lead Time)：需求提出到上线的总时间
周期时间(Cycle Time)：开发开始到完成的时间
吞吐量(Throughput)：单位时间完成的卡片数
```

## 四、Scrum vs Kanban

```
┌──────────────────┬──────────────────┬──────────────────┐
│ 维度             │ 选 Scrum          │ 选 Kanban          │
├──────────────────┼──────────────────┼──────────────────┤
│ 需求变化频率      │ 中等（可规划）    │ 极高（随时插入）   │
│ 工作类型          │ 项目制/功能开发   │ 运维/支持/持续交付  │
│ 交付节奏          │ 固定节奏很重要    │ 按需发布           │
└──────────────────┴──────────────────┴──────────────────┘

混合方案 Scrumban：保留 Scrum 的节奏感 + Kanban 的 WIP 限制和流动效率指标。
```

## 五、回顾会议的有效组织

### 5.1 Start-Stop-Continue 模型

```
Start（开始做）          Stop（停止做）          Continue（继续做）
• 写集成测试             • 开冗长需求评审会       • 每天站会15分钟
• Sprint 中期检查        • 直接在主分支开发       • PR 24小时内审查
```

### 5.2 执行步骤

```
1. 营造安全感（5分钟）：强调"对事不对人"，匿名收集反馈
2. 数据呈现（10分钟）：Sprint 完成率、Bug 数量、线上事故
3. 问题归因（15分钟）：Start-Stop-Continue 分组讨论，投票选 2-3 项
4. 制定行动项（10分钟）：做什么、谁负责、什么时候完成（最多2项）
5. 闭环（5分钟）：回顾上一次行动项完成情况
```

## 六、敏捷反模式

```
假敏捷（Zombie Scrum）：
  有Sprint → 但Goal从来没达成过
  有站会 → 但每个人只是汇报给经理听
  有回顾会 → 但行动项从来没人跟
  有用户故事 → 但写的是"作为开发，我要实现XX接口"

机械Scrum：严格遵守规则但不理解原因
  "Sprint不能取消" → 即使需求全变了也不取消
  "不能有Sprint 0" → 基础架构搭建也必须在正式Sprint里做

修正建议：
  "很忙但没交付" → 引入WIP限制，强制完成后再开始新任务
  "估算永远不准" → 用相对估算（故事点），不承诺绝对时间
  "回顾会没人说话" → 先匿名收集再讨论，经理最后发言
  "技术债越来越多" → 每Sprint预留20%容量处理技术债
```

## 常见误区

1. **"敏捷就是快"** — 敏捷不是更快，而是更早发现问题。
2. **"Scrum 和 Kanban 必须二选一"** — 很多高效团队用混合方案。
3. **"站会必须站着"** — 站着只是手段，目的是控制时长。
4. **"回顾会是浪费时间"** — 它是唯一专门用来改进的仪式。
5. **"敏捷不需要文档"** — 敏捷宣言说"高于"，不是"不要"。关键决策仍需文档。
6. **"换框架就能解决问题"** — 如果信任缺失、技术债堆积，换什么框架都没用。

## 工程建议

1. **从一个痛点开始改进**，不要一次性引入所有实践。
2. **让团队自己选择工具和流程**，经理提出方向，团队决定怎么做。
3. **度量流动效率，而非忙碌程度**。关注 Cycle Time 和吞吐量。
4. **投资自动化**。手动测试/部署/检查是敏捷的敌人。
5. **保护团队专注时间**。频繁会议、临时需求、跨团队协调是 Sprint 节奏的破坏者。
6. **持续改进是目标，不是仪式**。不要等到回顾会才提问题。

---

## 小结

- **Scrum** 提供节奏和结构，**Kanban** 关注流动效率
- **站会** 是信息同步工具，面向看板而非面向经理
- **回顾会议** 需要安全感、具体行动项和闭环跟踪
- **敏捷反模式** 比不做敏捷更危险——让团队误以为自己在改进
- 选择框架的依据是**团队实际情况**

## 练习

### 练习一：站会诊断

团队站会每天 25 分钟，每人轮流汇报，经理点评。最近 3 人开始经常缺席。请诊断问题并给出改进方案。

### 练习二：Kanban 看板设计

6 人运维团队，同时处理 15+ 任务，每周只能完成 5-6 个。工作包括：线上 Bug、基础设施维护、工具开发、安全漏洞。请设计 Kanban 看板。

### 练习三：回顾会议设计

团队连续 3 个 Sprint 未达成目标。反馈"需求总在中途变"和"技术债太多"。Scrum Master 说"回顾会讨论过但没改善"。请设计一个能产出可执行改进措施的回顾会议方案。

---

## 参考答案

### 练习一

**思路：** 核心问题是"面向经理汇报"而非"面向看板同步"。25 分钟对 8 人太长，缺席说明认为没价值。

**答案：**
1. 改变形式：移到看板前，用改良三问，每人 90 秒，总计 12 分钟内。经理不点评，复杂问题 Parking Lot。
2. 恢复参与度：不强制但让缺席者明白信息缺失的后果。站会后群里发总结。
3. 每月 5 分钟回顾站会本身效果。

### 练习二

**思路：** 运维团队多类型工作并存，需区分工作类型和优先级。

**答案：**
```
待办池(无限制) → 分析中(WIP:2) → 处理中(WIP:4) → 验证中(WIP:2) → 待部署(WIP:2) → 完成
标签：🔴线上Bug/安全(最高优先级，可突破WIP) 🟡维护 🟢工具开发
规则：每人同时最多2张卡片；处理中超过2天必须升级；每周一下午排优先级
```

### 练习三

**思路：** 连续 3 个 Sprint 没达成目标，之前的回顾会没有产出有效行动项或没有跟踪。

**答案：**
1. 数据呈现（10分钟）：展示 3 个 Sprint 的完成率、需求变更次数、技术债 Bug 数量
2. 问题归因（20分钟）：用"5个为什么"做根因分析
3. 制定行动项（20分钟）：SMART 原则，如"进入 Sprint 的需求必须有验收标准"、"每 Sprint 预留 20% 容量处理技术债"
4. 跟踪机制（10分钟）：行动项写在看板上跟踪，每次回顾会先检查上次行动项
