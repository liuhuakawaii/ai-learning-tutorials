# 第二课：项目管理

## 场景引入

你被任命为新项目的技术负责人。目标是"三个月内上线新一代推荐系统"。产品经理说"需求还在细化"，业务方说"这个功能一定要有"，CTO 问你"能不能按时交付"。你手里没有需求文档、没有排期、没有风险评估。

项目管理不是填表格、画甘特图。它的核心是**在不确定性中做出可执行的决策**。

## 学习目标

完成本课学习后，你将能够：

1. 定义 MVP 并有效防控范围蔓延
2. 使用多种估时方法
3. 构建风险矩阵和预警机制
4. 识别和管理关键干系人
5. 编写 RACI 矩阵和项目状态报告

---

## 一、范围管理

### 1.1 MVP 定义

MVP 不是"砍掉大部分功能的残缺品"，而是**用最少的功能验证核心假设**。

```
推荐系统 MVP 示例：
  完整版本（3个月）：用户画像 + 实时推荐 + A/B测试 + 推荐理由 + 多策略融合
  MVP（6周）：基于历史行为的离线推荐 + 简单API + 手动A/B测试
  → 验证假设：推荐是否比热门列表提升点击率
```

### 1.2 范围蔓延防控

三个信号："这个也要加进去" / "很简单顺便做了" / "做到一半才发现要做更多"。

**防控机制一：变更请求流程** — 新需求评估影响 → 审批 → 批准则有等量功能移出。

**防控机制二：MoSCoW 优先级法** — Must（必须有）/ Should（应该有）/ Could（可以有）/ Won't（这次不做）。MVP 只包含 Must。

## 二、时间管理：估时方法

```
┌─────────────────┬──────────────────┬──────────────────┬──────────────────┐
│ 方法             │ 故事点           │ 理想人天          │ T-shirt Sizing   │
├─────────────────┼──────────────────┼──────────────────┼──────────────────┤
│ 表达方式         │ 相对大小1/2/3/5  │ 绝对时间          │ XS/S/M/L/XL     │
│ 适用阶段         │ Sprint 规划      │ 任务拆分后        │ 早期粗估         │
│ 精度             │ 中等             │ 较高              │ 低               │
└─────────────────┴──────────────────┴──────────────────┴──────────────────┘
```

**Planning Poker 流程**：产品讲解 → 团队提问 → 私下选牌 → 同时翻牌 → 差异大时讨论 → 重新投票至收敛。

**常见陷阱**：
- "很简单"→实际3天：低估测试/联调/部署时间，用 2-3x 开发系数修正
- 按最厉害的人估算→其他人完不成：用团队平均能力估算
- 需求不清楚就估→估算变承诺：不清楚的只做 T-shirt sizing

## 三、风险管理

### 3.1 风险矩阵

```
影响↑
  高│  中风险   │  高风险   │  极高风险  │
  中│  低风险   │  中风险   │  高风险    │
  低│  低风险   │  低风险   │  中风险    │
    └──────────┴──────────┴───────────┘→概率
```

### 3.2 风险登记册示例

```
┌────┬──────────────────┬──────┬──────┬──────┬──────────────────┬──────────┐
│ ID │ 风险描述          │ 概率 │ 影响 │ 等级 │ 预案              │ 负责人    │
├────┼──────────────────┼──────┼──────┼──────┼──────────────────┼──────────┤
│ R1 │ 第三方API响应不达标│ 中   │ 高   │ 高  │ 准备自研备选方案   │ 张工     │
│ R2 │ 核心开发人员离职   │ 低   │ 高   │ 中  │ 知识文档+交叉培训  │ 技术Lead │
│ R3 │ 数据质量不达标     │ 高   │ 中   │ 高  │ 提前做数据审计     │ 数据工程 │
│ R4 │ 需求频繁变更       │ 高   │ 中   │ 高  │ 冻结需求变更流程   │ 产品经理 │
└────┴──────────────────┴──────┴──────┴──────┴──────────────────┴──────────┘
```

### 3.3 预警机制

```
项目健康度仪表盘：
  进度：60%（计划65%）⚠️ 偏差5%  |  Bug数12（阈值15）✅
  风险：R1概率升高 ⚠️            |  加班率20%（阈值15%）🔴

预警规则：🟢正常 | 🟡偏差10%内需关注 | 🔴偏差超10%需立即行动
```

## 四、干系人管理

### 4.1 权力-利益矩阵

```
权力↑
  高│ 保持满意(CTO)    │  重点管理(直接上级/产品) │
  低│ 最少精力(其他部门)│  保持信息同步(最终用户) │
    └──────────────────┴─────────────────────────┘→利益
```

### 4.2 沟通计划

```
┌──────────────┬──────────┬──────────┬──────────────┐
│ 干系人        │ 沟通频率  │ 沟通方式  │ 内容          │
├──────────────┼──────────┼──────────┼──────────────┤
│ CTO          │ 双周     │ 邮件+1:1 │ 架构决策/风险  │
│ 直接上级      │ 每周     │ 周报+会议 │ 进度/资源需求  │
│ 产品负责人    │ 每日     │ 站会+即时 │ 需求澄清/进度  │
│ 业务方       │ 每两周    │ 演示会   │ 功能演示/里程碑 │
└──────────────┴──────────┴──────────┴──────────────┘
```

## 五、项目文档

### 5.1 RACI 矩阵

```
R=执行者  A=负责人（每个任务只能一个）  C=咨询者  I=知情人

示例：
┌──────────────────┬──────┬──────┬──────┬──────┬──────┐
│ 任务              │ 技术 │ 产品 │ 数据 │ 运维 │ CTO  │
├──────────────────┼──────┼──────┼──────┼──────┼──────┤
│ 技术方案设计       │ R/A  │ C    │ C    │ I    │ I    │
│ 需求定义          │ C    │ R/A  │ I    │ I    │ I    │
│ 上线审批          │ C    │ C    │ I    │ I    │ A    │
└──────────────────┴──────┴──────┴──────┴──────┴──────┘
```

### 5.2 项目状态报告模板

```
项目状态周报 - 推荐系统 v2.0 | 报告日期：2024-03-15

整体状态：进度🟢(60%,计划62%) | 风险🟡(第三方API响应时间升高) | 质量🟢(Bug8,阈值15)
本周完成：用户画像API完成、离线推荐模型管道搭建、数据格式对齐
下周计划：推荐引擎核心逻辑、A/B测试框架、性能基准测试
风险问题：[风险]第三方API p99>200ms需评估自研 | [问题]15%行为日志缺失
需要支持：运维3/20前提供压测环境 | CTO审批自研方案技术选型
```

### 5.3 项目章程

项目章程是项目的"宪法"，包含：项目背景、目标（业务+技术）、范围（包含/不包含）、里程碑、关键干系人、预算与资源、成功标准。

## 常见误区

1. **"项目管理就是画甘特图"** — 甘特图只是沟通工具，真正的管理是识别风险、协调资源、做决策。
2. **"估算要准确"** — 估算偏差 30% 正常，重要的是持续校准。
3. **"范围蔓延是产品经理的问题"** — Tech Lead 有责任说"这个需求不做"。
4. **"风险清单列完就行"** — 每个风险必须有预案、负责人和触发条件。
5. **"干系人管理就是汇报"** — 核心是管理期望，确保对结果有合理预期。
6. **"项目文档是浪费时间"** — 适度文档是投资，减少沟通成本和决策延迟。

---

## 工程建议

1. **MVP 从"验证假设"出发**，不是从"砍功能"出发。
2. **估算时考虑完整生命周期**（编码+测试+审查+部署），用 2-3x 开发系数修正。
3. **风险要在项目早期识别**。启动时花 2 小时做风险识别，每周 15 分钟更新登记册。
4. **沟通计划比技术方案更重要**。很多项目失败是因为干系人期望不一致。
5. **状态报告要诚实**。绿色不代表没有问题，黄色不代表项目要失败。
6. **RACI 矩阵在项目启动时就定好**。不要等到出问题才讨论职责。

---

## 小结

- **范围管理** 核心是 MVP 定义和变更控制，MoSCoW 优先级法是实用工具
- **估时方法** 根据场景选择：T-shirt sizing（早期）、故事点（规划）、理想人天（拆分后）
- **风险管理** 需要风险矩阵 + 预案 + 预警机制
- **干系人管理** 用权力-利益矩阵分类，制定差异化沟通计划
- **项目文档** 中 RACI 明确权责，项目章程定义目标和范围

## 练习

### 练习一：MVP 定义

开发"代码质量看板"，完整需求：覆盖率趋势、Bug趋势、技术债清单、团队对比、自动化报告、自定义仪表盘。3 人 4 周。请定义 MVP。

### 练习二：风险识别

将单体应用拆分为微服务，8 人 6 个月。请识别至少 5 个关键风险，填写风险登记册。

### 练习三：RACI 矩阵

开发支付系统，角色：后端、前端、产品、安全、运维、QA。任务：支付接口设计、安全审查、压力测试、上线部署、故障响应。请编写 RACI 矩阵。

## 参考答案

### 练习一

**思路：** MVP 核心假设是"团队是否会主动查看质量数据并据此改进"。

**答案：** MVP 保留：覆盖率趋势（从CI拉取）+ Bug趋势（从Issue Tracker拉取）+ 团队概览卡片。砍掉：技术债清单（需人工维护）、团队对比（团队少时意义不大）、自动化报告（先手动看）、自定义仪表盘（需求不明确）。

### 练习二

**思路：** 微服务拆分风险集中在数据一致性、团队能力、业务连续性。

**答案：**
```
R1 数据一致性(高/高/极高)：先梳理数据依赖，引入Saga模式
R2 团队缺经验(中/高/高)：非核心服务先练手
R3 拆分中故障(中/高/高)：保持旧系统可回退，灰度切换
R4 通信性能下降(中/中/中)：提前性能基准测试
R5 运维复杂度上升(高/中/高)：同步建设监控链路追踪
```

### 练习三

**答案：**
```
支付接口设计：后端R/A，前端/产品/安全 C
安全审查：安全R/A，后端C
压力测试：QA R/A，后端/运维C
上线部署：运维R/A，后端C
故障响应：运维A，后端R
```

每个任务只有一个 A；支付系统安全审查不能省略。
