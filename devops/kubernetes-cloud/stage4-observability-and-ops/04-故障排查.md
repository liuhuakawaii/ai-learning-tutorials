# 故障排查

## 场景引入

Pod 处于 CrashLoopBackOff 状态，你看了日志发现是数据库连接失败。但数据库 Pod 运行正常啊？你 exec 进入应用 Pod 尝试 ping 数据库 Service，发现 DNS 解析失败。再看 kube-system 的 CoreDNS Pod，发现它 OOM Kill 了。

K8s 的故障排查是一个系统性的过程：从现象出发，逐步缩小范围，找到根因。这个课教你一套标准的排查方法论。

## 学习目标

1. 掌握 K8s 故障排查的系统方法论
2. 学会使用 kubectl debug 进行在线调试
3. 了解常见故障的原因和解决方案
4. 掌握网络排查的基本工具

## 排查方法论

```
1. 确认现象：什么异常？影响范围？
2. 查看状态：kubectl get/describe
3. 查看日志：kubectl logs
4. 进入容器：kubectl exec/debug
5. 检查网络：DNS、Service、Ingress
6. 检查依赖：数据库、缓存、外部 API
7. 检查资源：CPU、内存、磁盘
8. 定位根因：修复并验证
```

## Pod 状态异常排查

### Pending

Pod 一直处于 Pending 状态，没有被调度到任何 Node。

```bash
kubectl describe pod <pod-name>
# 看 Events 部分
```

常见原因和解决方案：

```
原因：Insufficient cpu / Insufficient memory
解决：减少 requests、扩容 Node、清理不用的 Pod

原因：nodeSelector/nodeAffinity 不匹配
解决：检查 Node 标签是否正确

原因：PVC 未绑定
解决：检查 PV 是否可用、StorageClass 是否正确

原因：Taint 不容忍
解决：添加 Toleration 或移除 Taint
```

### ImagePullBackOff

镜像拉取失败。

```bash
kubectl describe pod <pod-name>
# Events: Failed to pull image "xxx": rpc error
```

```
原因：镜像名或 tag 错误
解决：检查 image 字段拼写

原因：私有仓库需要认证
解决：创建 imagePullSecrets

原因：网络问题
解决：检查 Node 是否能访问镜像仓库

原因：Kind/Minikube 环境
解决：kind load docker-image <image> --name <cluster>
```

### CrashLoopBackOff

容器反复崩溃重启。

```bash
# 查看当前日志
kubectl logs <pod-name>

# 查看前一个容器的日志（如果容器重启过）
kubectl logs <pod-name> --previous

# 查看退出码
kubectl describe pod <pod-name>
# Last State: Terminated, Exit Code: 1
```

```
Exit Code 1：应用自身错误（查看日志）
Exit Code 137：OOM Kill（增加 memory limits）
Exit Code 139：SIGSEGV（程序 bug）
Exit Code 143：SIGTERM（被外部终止）
```

### Evicted

Pod 被驱逐。

```bash
kubectl describe pod <pod-name>
# Reason: Evicted, Message: The node was low on resource: memory
```

```
原因：Node 资源不足
解决：
1. 增加 Node 资源
2. 减少 Pod 的 memory requests
3. 配置 ResourceQuota 限制 Namespace 资源使用
4. 清理已完成的 Job/Pod
```

## kubectl debug

K8s 1.25+ 提供了 `kubectl debug` 命令，可以在运行中的 Pod 旁边附加一个调试容器。

```bash
# 在 Pod 中添加调试容器
kubectl debug -it <pod-name> --image=busybox:1.36 --target=<container-name>

# 创建 Pod 的调试副本（不影响原 Pod）
kubectl debug <pod-name> -it --image=ubuntu --copy-to=<pod-name>-debug

# 调试 Node
kubectl debug node/<node-name> -it --image=ubuntu

# 调试失败的 Job
kubectl debug -it job/<job-name> --image=busybox --restart=Never
```

### 使用 ephemeral containers

```yaml
# 临时容器（K8s 1.25+）
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  ephemeralContainers:
    - name: debugger
      image: nicolaka/netshoot
      command: ['sleep', '3600']
      targetContainerName: app
```

## 网络排查

### DNS 排查

```bash
# 在 Pod 中测试 DNS
kubectl exec -it <pod-name> -- nslookup kubernetes.default
kubectl exec -it <pod-name> -- nslookup <service-name>.<namespace>.svc.cluster.local

# 检查 CoreDNS 状态
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns

# 测试 DNS 解析
kubectl run dns-test --image=busybox:1.36 --rm -it -- nslookup <service-name>
```

### Service 排查

```bash
# 检查 Service
kubectl get svc <service-name>
kubectl describe svc <service-name>

# 检查 Endpoints
kubectl get endpoints <service-name>
# 如果 Endpoints 为空，说明没有匹配的 Pod

# 检查 Pod 的 label 是否和 Service 的 selector 匹配
kubectl get pods --show-labels
```

### 网络连通性测试

```bash
# 从 Pod 内部测试
kubectl exec -it <pod-name> -- curl http://<service-name>:<port>
kubectl exec -it <pod-name> -- wget -qO- http://<service-name>

# 使用 netshoot 镜像进行高级网络调试
kubectl run netshoot --rm -it --image=nicolaka/netshoot -- /bin/bash

# 在 netshoot 容器中
ping <service-ip>
curl <service-name>
nslookup <service-name>
traceroute <service-ip>
tcpdump -i eth0 port 80
```

## 资源排查

```bash
# 查看 Node 资源使用
kubectl top nodes

# 查看 Pod 资源使用
kubectl top pods -n <namespace>
kubectl top pods -n <namespace> --sort-by=memory
kubectl top pods -n <namespace> --sort-by=cpu

# 查看 Pod 的实际资源限制
kubectl get pod <pod-name> -o jsonpath='{.spec.containers[0].resources}'

# 查看 Node 上的 Pod 分布
kubectl get pods -o wide --all-namespaces | grep <node-name>
```

## 常见故障速查表

| 现象 | 可能原因 | 排查命令 |
|------|---------|---------|
| Pod Pending | 资源不足 | `kubectl describe pod` |
| ImagePullBackOff | 镜像不存在/网络问题 | `kubectl describe pod` |
| CrashLoopBackOff | 应用启动失败 | `kubectl logs --previous` |
| OOMKilled | 内存超限 | `kubectl describe pod` |
| Service 不通 | Endpoints 为空 | `kubectl get endpoints` |
| DNS 失败 | CoreDNS 异常 | `kubectl logs -n kube-system -l k8s-app=kube-dns` |
| Ingress 404 | 路由规则不匹配 | `kubectl describe ingress` |
| Node NotReady | kubelet 异常 | `journalctl -u kubelet` |

## 常见误区

**误区一："Pod Running 就代表正常"**

Running 只表示容器在运行，不代表应用正常。需要检查 Readiness Probe、日志和实际请求。

**误区二："重启 Pod 能解决所有问题"**

重启可能暂时解决问题，但根因还在。应该先排查原因，再决定是否重启。

**误区三："kubectl logs 只能看当前容器"**

`kubectl logs --previous` 可以看前一个容器的日志，对排查 CrashLoopBackOff 非常有用。

## 工程建议

1. **所有 Pod 都配置 Readiness Probe**：K8s 可以自动检测应用是否正常
2. **使用结构化日志**：方便搜索和过滤
3. **保留足够的日志历史**：至少 7 天
4. **建立故障排查手册**：常见问题和解决方案
5. **定期演练故障恢复**：模拟故障并练习排查

## 小结

- 故障排查遵循系统方法论：现象 → 状态 → 日志 → 调试 → 网络 → 资源
- kubectl debug 可以在不停止 Pod 的情况下进行调试
- 网络排查重点：DNS、Service Endpoints、连通性
- 资源排查：CPU、内存、磁盘使用率
- 建立排查手册和演练机制

## 参考答案

### 练习一

**答案**：

```bash
# 1. 不存在的镜像
kubectl run bad-image --image=nginx:nonexistent-tag
kubectl describe pod bad-image
# Events 中看到 ImagePullBackOff

# 2. OOM Kill
kubectl run oom-test --image=nginx --limits='memory=10Mi' --command -- stress --vm 1 --vm-bytes 50M --vm-hang 0
kubectl describe pod oom-test
# Last State: Terminated, Reason: OOMKilled, Exit Code: 137

# 3. Service 不匹配
kubectl run test-pod --image=nginx --labels=app=wrong-label
kubectl expose pod test-pod --port=80 --name=test-svc
kubectl get endpoints test-svc
# Endpoints 为空（selector 是 app=test-pod，但 label 是 app=wrong-label）
```

### 练习二

**答案**：

```bash
# 启动 netshoot
kubectl run netshoot --rm -it --image=nicolaka/netshoot -- /bin/bash

# DNS 测试
nslookup kubernetes.default
nslookup kube-dns.kube-system.svc.cluster.local

# Service 测试
curl http://<service-name>.<namespace>.svc.cluster.local

# 外部网络
ping 8.8.8.8
curl https://google.com
```

**要点**：
- DNS 失败通常意味着 CoreDNS 有问题
- Service 不通先检查 Endpoints
- 外部网络不通可能是 Node 的网络配置问题
