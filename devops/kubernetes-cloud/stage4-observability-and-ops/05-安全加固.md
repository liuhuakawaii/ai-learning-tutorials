# 安全加固

## 场景引入

你的 K8s 集群运行着多个团队的应用。某天，一个开发环境的 Pod 被入侵，攻击者通过这个 Pod 访问到了生产环境的数据库。原因是：默认配置下，集群内所有 Pod 可以互相访问，没有网络隔离，也没有权限控制。

K8s 安全不是一个功能，而是一系列措施的组合：RBAC 控制谁能做什么、NetworkPolicy 控制谁能访问谁、Pod Security 控制容器能做什么。

## 学习目标

1. 掌握 RBAC 权限控制模型
2. 学会配置 NetworkPolicy 网络隔离
3. 了解 Pod Security Standards
4. 学会安全管理 Secret
5. 掌握 K8s 安全最佳实践

## RBAC 权限控制

RBAC（Role-Based Access Control）是 K8s 的权限管理机制。

### 核心概念

```
Subject（谁）──→ RoleBinding ──→ Role（能做什么）
  │                                   │
  User/Group/ServiceAccount           对资源的操作权限
```

### Role 和 ClusterRole

```yaml
# Role：命名空间级别
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]

---
# ClusterRole：集群级别
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: node-reader
rules:
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get", "list", "watch"]
```

### RoleBinding 和 ClusterRoleBinding

```yaml
# RoleBinding：将 Role 绑定到 Subject
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: default
subjects:
  - kind: User
    name: alice
    apiGroup: rbac.authorization.k8s.io
  - kind: Group
    name: developers
    apiGroup: rbac.authorization.k8s.io
  - kind: ServiceAccount
    name: my-app-sa
    namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### ServiceAccount

```yaml
# 创建 ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: my-app-sa
  namespace: default

---
# 在 Pod 中使用
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  serviceAccountName: my-app-sa
  containers:
    - name: app
      image: my-app:1.0
```

### RBAC 调试

```bash
# 检查权限
kubectl auth can-i create pods --as=alice -n default
kubectl auth can-i '*' '*' --as=system:serviceaccount:default:my-app-sa

# 查看 Role 和 RoleBinding
kubectl get roles,rolebindings -n default
kubectl get clusterroles,clusterrolebindings
```

## NetworkPolicy 网络隔离

默认情况下，集群内所有 Pod 可以互相访问。NetworkPolicy 可以限制 Pod 的入站和出站流量。

### 前置条件

NetworkPolicy 需要 CNI 插件支持：
- **Calico**：支持完整 NetworkPolicy
- **Cilium**：支持完整 NetworkPolicy + L7 策略
- **Kindnet**：Kind 默认，不支持 NetworkPolicy

### 基本 NetworkPolicy

```yaml
# 只允许 frontend 访问 backend
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: backend-policy
  namespace: default
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - port: 8080
```

### 默认拒绝所有入站

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: default
spec:
  podSelector: {}    # 匹配所有 Pod
  policyTypes:
    - Ingress
```

### 允许特定命名空间访问

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-monitoring
  namespace: production
spec:
  podSelector: {}
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              name: monitoring
```

### 限制出站流量

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: restrict-egress
  namespace: default
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              name: kube-system
      ports:
        - port: 53
          protocol: UDP
        - port: 53
          protocol: TCP
    - to:
        - podSelector:
            matchLabels:
              app: database
      ports:
        - port: 5432
```

## Pod Security Standards

K8s 1.25+ 推出了 Pod Security Standards（PSS），替代已废弃的 PodSecurityPolicy。

### 三个安全级别

| 级别 | 说明 |
|------|------|
| Privileged | 无限制 |
| Baseline | 最低限制，防止已知的权限提升 |
| Restricted | 严格限制，最佳实践 |

### 配置 Namespace 安全级别

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/warn: restricted
```

### Restricted 级别的要求

```yaml
# 符合 restricted 级别的 Pod 配置
spec:
  securityContext:
    runAsNonRoot: true
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: my-app:1.0
      securityContext:
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        runAsUser: 1000
        capabilities:
          drop:
            - ALL
```

## Secret 安全管理

### etcd 加密

```yaml
# /etc/kubernetes/encryption-config.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <base64-encoded-secret>
      - identity: {}
```

### Sealed Secrets

Sealed Secrets 允许将 Secret 加密后存储在 Git 中：

```bash
# 安装 kubeseal
brew install kubeseal

# 加密 Secret
kubectl create secret generic my-secret --from-literal=password=abc123 -o yaml --dry-run=client | kubeseal -o yaml > sealed-secret.yaml

# sealed-secret.yaml 可以安全提交到 Git
```

### External Secrets Operator

从外部密钥管理服务（AWS Secrets Manager、HashiCorp Vault）同步 Secret。

## 安全最佳实践

### 集群级别

1. **启用 RBAC**：不要使用 `--authorization-mode=AlwaysAllow`
2. **限制 kubeconfig 权限**：不要共享 admin kubeconfig
3. **启用审计日志**：记录所有 API Server 操作
4. **定期更新 K8s 版本**：修复已知安全漏洞
5. **启用 etcd 加密**：保护 Secret 数据

### 命名空间级别

1. **配置 ResourceQuota**：防止资源耗尽攻击
2. **配置 LimitRange**：设置默认资源限制
3. **使用 NetworkPolicy**：隔离不同应用
4. **设置 Pod Security Standards**：限制容器权限

### Pod 级别

1. **以非 root 用户运行**：`runAsNonRoot: true`
2. **只读文件系统**：`readOnlyRootFilesystem: true`
3. **禁止特权提升**：`allowPrivilegeEscalation: false`
4. **移除不需要的 Linux capabilities**
5. **使用 distroless 或 scratch 基础镜像**

## 常见误区

**误区一："K8s 默认配置是安全的"**

K8s 默认配置为了易用性做了很多妥协。RBAC 默认开启但权限较宽松，NetworkPolicy 需要 CNI 支持，Pod Security 需要手动配置。

**误区二："网络隔离就够了"**

网络隔离只是一层。还需要 RBAC（防止未授权操作）、Pod Security（防止容器逃逸）、Secret 管理（保护敏感数据）。

**误区三："安全和便利性不可兼得"**

通过合理的分层设计，可以在保证安全的同时不影响开发效率。比如开发环境用宽松策略，生产环境用严格策略。

## 工程建议

1. **最小权限原则**：每个 ServiceAccount 只给必要的权限
2. **默认拒绝网络**：先 deny all，再逐步 allow
3. **生产环境用 restricted 安全级别**
4. **不要把 Secret 提交到 Git**：使用 Sealed Secrets 或 External Secrets
5. **定期审计 RBAC 和 NetworkPolicy**

## 小结

- RBAC 控制"谁能做什么"，NetworkPolicy 控制"谁能访问谁"
- Pod Security Standards 分三级：Privileged、Baseline、Restricted
- Secret 安全：etcd 加密、Sealed Secrets、External Secrets
- 安全是分层的：集群 → 命名空间 → Pod → 容器
- 最小权限原则是安全设计的核心

## 参考答案

### 练习一

**答案**：

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: dev-viewer
  namespace: dev
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-service-viewer
  namespace: dev
rules:
  - apiGroups: [""]
    resources: ["pods", "services"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-viewer-binding
  namespace: dev
subjects:
  - kind: ServiceAccount
    name: dev-viewer
    namespace: dev
roleRef:
  kind: Role
  name: pod-service-viewer
  apiGroup: rbac.authorization.k8s.io
```

```bash
# 验证
kubectl auth can-i get pods --as=system:serviceaccount:dev:dev-viewer -n dev    # yes
kubectl auth can-i create pods --as=system:serviceaccount:dev:dev-viewer -n dev  # no
kubectl auth can-i get pods --as=system:serviceaccount:dev:dev-viewer -n prod    # no
```

### 练习二

**答案**：

```yaml
# 1. 默认拒绝
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
# 2. 允许 frontend 访问 backend
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - port: 8080
---
# 3. 允许 monitoring 访问 metrics
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-monitoring-metrics
spec:
  podSelector: {}
  policyTypes: [Ingress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              name: monitoring
      ports:
        - port: 9090
```

**要点**：
- 多个 NetworkPolicy 会叠加生效（取并集）
- 先 deny all，再逐步 allow 需要的流量
- monitoring 的 metrics 端口通常是 9090 或 /metrics
