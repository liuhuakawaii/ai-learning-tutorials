# 日志体系

## 场景引入

Prometheus 监控告诉你"错误率升高了"，但不告诉你"是哪个请求报了什么错"。要回答这个问题，你需要日志。在 K8s 中，Pod 的日志默认输出到 stdout/stderr，通过 `kubectl logs` 查看。但 Pod 重启后日志就没了，跨 Pod 查询也很麻烦。

你需要一个集中式日志系统：所有 Pod 的日志自动收集到一个地方，支持全文搜索、结构化查询、长期保留。

## 学习目标

1. 理解 K8s 日志的分类和采集方式
2. 掌握 EFK（Elasticsearch + Fluentd + Kibana）方案
3. 了解 Loki + Grafana 轻量日志方案
4. 学会设计结构化日志格式
5. 掌握日志查询和分析技巧

## K8s 日志分类

### 容器日志

应用输出到 stdout/stderr 的日志，存储在 Node 的 `/var/log/containers/` 目录。

```bash
# 查看容器日志
kubectl logs <pod-name>
kubectl logs <pod-name> -c <container-name>  # 多容器 Pod
kubectl logs <pod-name> --previous            # 前一个容器的日志
kubectl logs -f <pod-name>                    # 实时跟踪
```

### 系统组件日志

kubelet、kube-proxy、API Server 等组件的日志。

### Node 系统日志

操作系统级别的日志，如 systemd、内核日志。

## EFK 方案

EFK（Elasticsearch + Fluentd + Kibana）是经典的 K8s 日志方案。

### 架构

```
Pod stdout/stderr
       │
       ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Fluentd/    │────►│ Elasticsearch│────►│  Kibana      │
│  Fluent Bit  │     │ 存储和索引   │     │  查询和可视化│
└──────────────┘     └──────────────┘     └──────────────┘
```

### 安装 EFK

```bash
# 使用 Helm 安装 Elasticsearch
helm repo add elastic https://helm.elastic.co
helm install elasticsearch elastic/elasticsearch \
  --namespace logging \
  --create-namespace \
  --set replicas=1 \
  --set resources.requests.memory=1Gi

# 安装 Kibana
helm install kibana elastic/kibana \
  --namespace logging

# 安装 Fluent Bit（比 Fluentd 更轻量）
helm repo add fluent https://fluent.github.io/helm-charts
helm install fluent-bit fluent/fluent-bit \
  --namespace logging \
  --set output.elasticsearch.host=elasticsearch-master
```

### Fluent Bit 配置

```yaml
# Fluent Bit ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: fluent-bit-config
  namespace: logging
data:
  fluent-bit.conf: |
    [SERVICE]
        Flush         5
        Log_Level     info
        Daemon        off

    [INPUT]
        Name              tail
        Path              /var/log/containers/*.log
        Parser            cri
        Tag               kube.*
        Refresh_Interval  5
        Mem_Buf_Limit     5MB

    [FILTER]
        Name                kubernetes
        Match               kube.*
        Kube_URL            https://kubernetes.default.svc:443
        Kube_Tag_Prefix     kube.var.log.containers.
        Merge_Log           On
        K8S-Logging.Parser  On

    [OUTPUT]
        Name            es
        Match           *
        Host            elasticsearch-master
        Port            9200
        Index           kubernetes
        Type            _doc
```

## Loki 方案

Loki 是 Grafana Labs 开发的轻量级日志系统，设计理念是"like Prometheus, but for logs"。

### 架构

```
Pod stdout/stderr
       │
       ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  Promtail    │────►│  Loki        │────►│  Grafana     │
│  日志采集    │     │  日志存储    │     │  日志查询    │
└──────────────┘     └──────────────┘     └──────────────┘
```

### 安装 Loki Stack

```bash
# 使用 Helm 安装完整的 Loki 栈
helm repo add grafana https://grafana.github.io/helm-charts
helm install loki grafana/loki-stack \
  --namespace logging \
  --create-namespace \
  --set grafana.enabled=true \
  --set promtail.enabled=true
```

### Loki vs EFK

| 特性 | Loki + Promtail | EFK |
|------|----------------|-----|
| 资源占用 | 低 | 高 |
| 索引方式 | 标签索引 | 全文索引 |
| 查询语言 | LogQL | KQL/Lucene |
| 全文搜索 | 不支持 | 支持 |
| 存储成本 | 低 | 高 |
| 适用场景 | K8s 原生、小规模 | 企业级、大规模 |

## 结构化日志

### 为什么需要结构化日志

非结构化日志：
```
2024-01-15 10:30:45 ERROR Failed to connect to database: connection timeout
```

结构化日志（JSON）：
```json
{
  "timestamp": "2024-01-15T10:30:45Z",
  "level": "ERROR",
  "message": "Failed to connect to database",
  "error": "connection timeout",
  "service": "api",
  "trace_id": "abc123",
  "user_id": "user-456"
}
```

结构化日志的好处：
- 可以按字段精确查询（`level=ERROR AND service=api`）
- 方便统计和聚合
- 支持分布式追踪关联

### 日志格式建议

```json
{
  "timestamp": "ISO 8601",
  "level": "DEBUG|INFO|WARN|ERROR",
  "message": "人类可读的描述",
  "service": "服务名称",
  "trace_id": "分布式追踪 ID",
  "span_id": "Span ID",
  "error": "错误详情（如有）",
  "context": {
    "user_id": "xxx",
    "request_id": "xxx",
    "method": "GET",
    "path": "/api/users",
    "status": 500,
    "duration_ms": 1234
  }
}
```

## LogQL 查询

Loki 使用 LogQL 查询语言。

```logql
# 基本查询：选择标签
{namespace="default", app="api"}

# 过滤日志内容
{namespace="default"} |= "ERROR"
{namespace="default"} != "healthcheck"
{namespace="default"} |~ "timeout|connection refused"

# 组合过滤
{namespace="default"} |= "ERROR" != "healthcheck"

# 解析 JSON 日志
{namespace="default"} | json
{namespace="default"} | json | level="ERROR"

# 统计查询
count_over_time({namespace="default"} |= "ERROR" [5m])
sum(rate({namespace="default"} |= "ERROR" [5m]))

# 按标签分组
sum by (app) (count_over_time({namespace="default"} |= "ERROR" [5m]))
```

## 常见误区

**误区一："kubectl logs 就够了"**

kubectl logs 只能查看单个 Pod 的日志，Pod 重启后日志丢失。生产环境必须有集中式日志系统。

**误区二："所有日志都要采集"**

健康检查、readiness probe 的日志通常不需要采集。在 Fluent Bit 配置中过滤掉，减少存储成本。

**误区三："日志越多越好"**

过多的日志会增加存储成本和查询延迟。合理设置日志级别，生产环境默认 INFO。

## 工程建议

1. **使用结构化日志**：JSON 格式，方便查询和分析
2. **设置合理的日志保留期**：通常 7-30 天
3. **过滤无用日志**：健康检查、kube-system 的 verbose 日志
4. **日志和追踪关联**：通过 trace_id 关联日志和分布式追踪
5. **监控日志系统本身**：Loki/Elasticsearch 的存储和查询性能

## 小结

- K8s 日志需要集中式采集和存储
- EFK 适合大规模企业场景，Loki 适合轻量级 K8s 场景
- 结构化日志（JSON）便于查询和分析
- LogQL 是 Loki 的查询语言，支持标签过滤和内容过滤
- 合理设置日志级别和保留期


### 练习二

**答案**：

```logql
# 1. 所有 ERROR 级别的日志
{namespace="default"} | json | level="ERROR"
# 或非结构化日志
{namespace="default"} |= "ERROR"

# 2. 过去 5 分钟每个服务的错误数量
sum by (app) (count_over_time({namespace="default"} |= "ERROR" [5m]))

# 3. 包含 timeout 的日志
{namespace="default"} |~ "timeout"
```

**要点**：
- `|=` 是包含过滤，`!=` 是排除过滤，`|~` 是正则匹配
- `json` 解析器用于结构化 JSON 日志
- `count_over_time` 统计时间窗口内的日志条数
