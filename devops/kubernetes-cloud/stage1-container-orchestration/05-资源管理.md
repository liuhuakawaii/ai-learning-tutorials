# 资源管理

## 场景引入

你的 K8s 集群有 3 台 Node，每台 8 CPU、16GB 内存。你把各种应用部署上去后发现两个问题：

1. 某个 Java 应用吃掉了大量内存，导致同一 Node 上的其他 Pod 被 OOM Kill
2. 调度器把太多 Pod 放在同一台机器上，其他机器却很空闲

根本原因是你没有告诉 K8s 每个 Pod 需要多少资源，也没有设置资源上限。K8s 调度器不知道该把 Pod 放在哪里，也无法防止某个 Pod 独占所有资源。

## 学习目标

1. 理解 Requests 和 Limits 的区别和关系
2. 掌握三种 QoS 等级及其触发条件
3. 了解 K8s 调度器的资源匹配逻辑
4. 学会合理设置资源请求和限制
5. 了解 LimitRange 和 ResourceQuota 的作用

## Requests 与 Limits

K8s 中每个容器都可以设置两类资源参数：

```yaml
resources:
  requests:
    cpu: "250m"        # 需要 0.25 个 CPU 核心
    memory: "128Mi"    # 需要 128MB 内存
  limits:
    cpu: "500m"        # 最多使用 0.5 个 CPU 核心
    memory: "256Mi"    # 最多使用 256MB 内存
```

### Requests：调度依据

Requests 是 K8s 调度器用来决定 Pod 放在哪台 Node 的依据。调度器会确保 Node 上所有 Pod 的 requests 之和不超过 Node 的总资源。

```
Node 资源：8 CPU, 16GB 内存

Pod A requests: 2 CPU, 4GB
Pod B requests: 3 CPU, 4GB
Pod C requests: 2 CPU, 4GB
─────────────────────────────
总 requests：7 CPU, 12GB → 可以调度

Pod D requests: 2 CPU, 4GB
─────────────────────────────
总 requests：9 CPU, 16GB → 超出 CPU，不能调度到这个 Node
```

### Limits：运行上限

Limits 是容器运行时的资源上限。超过 limit 的行为取决于资源类型：

**CPU Limit**：容器被限流（throttle），不会被杀掉，但性能会下降。

```yaml
resources:
  limits:
    cpu: "500m"  # 最多使用 0.5 核，超过时被 CFS 限流
```

**Memory Limit**：容器被 OOM Kill（Out of Memory），然后根据 Pod 的 restartPolicy 重启。

```yaml
resources:
  limits:
    memory: "256Mi"  # 超过 256MB 时被 OOM Kill
```

### Requests 和 Limits 的关系

```
requests ≤ limits

# 合理配置
resources:
  requests:
    cpu: "250m"      # 保证至少有 0.25 核
    memory: "128Mi"  # 保证至少有 128MB
  limits:
    cpu: "500m"      # 最多用 0.5 核
    memory: "256Mi"  # 最多用 256MB
```

CPU 是可压缩资源（compressible）：超了会被限流，不会被杀。
内存是不可压缩资源（incompressible）：超了会被 OOM Kill。

## QoS 等级

K8s 根据 requests 和 limits 的配置自动为每个 Pod 分配 QoS 等级：

### Guaranteed（保证级别）

所有容器的 requests 和 limits 完全相等。

```yaml
# Guaranteed QoS
containers:
  - name: app
    resources:
      requests:
        cpu: "500m"
        memory: "256Mi"
      limits:
        cpu: "500m"
        memory: "256Mi"
```

特点：资源有保证，Node 资源不足时最后被 OOM Kill。

### Burstable（突发级别）

至少一个容器设置了 requests 或 limits，且 requests ≠ limits。

```yaml
# Burstable QoS
containers:
  - name: app
    resources:
      requests:
        cpu: "250m"
        memory: "128Mi"
      limits:
        cpu: "1"
        memory: "512Mi"
```

特点：平时用 requests 保证的资源，忙时可以突发到 limits。Node 资源不足时在 Guaranteed 之后被 OOM Kill。

### BestEffort（尽力级别）

没有任何容器设置 requests 或 limits。

```yaml
# BestEffort QoS
containers:
  - name: app
    image: nginx:1.25
    # 没有 resources 字段
```

特点：没有任何资源保证，Node 资源不足时最先被 OOM Kill。

### OOM Kill 优先级

当 Node 内存不足时，kubelet 按以下顺序杀 Pod：

```
BestEffort → Burstable → Guaranteed
```

同等级内，OOM Score 越高越先被杀。Pod 的 OOM Score 基于其实际内存使用量与 requests 的偏差：使用量远超 requests 的 Pod 优先被杀。

## 资源单位

### CPU 单位

```yaml
cpu: "1"      # 1 个 CPU 核心
cpu: "500m"   # 0.5 个 CPU 核心（m = milli）
cpu: "250m"   # 0.25 个 CPU 核心
cpu: "100m"   # 0.1 个 CPU 核心
```

### 内存单位

```yaml
memory: "128Mi"   # 128 Mebibytes（二进制）
memory: "1Gi"     # 1 Gibibyte
memory: "128M"    # 128 Megabytes（十进制，少用）
memory: "1G"      # 1 Gigabyte（十进制，少用）
```

注意：Mi 和 M 不一样，Gi 和 G 不一样。Mi = 1024×1024 字节，M = 1000×1000 字节。

## 调度策略

### 节点选择器（nodeSelector）

```yaml
spec:
  nodeSelector:
    disk: ssd
    gpu: "true"
```

Node 需要有对应的标签：
```bash
kubectl label nodes node-1 disk=ssd
kubectl label nodes node-1 gpu=true
```

### 亲和性与反亲和性（Affinity）

```yaml
spec:
  affinity:
    # Node 亲和性：Pod 倾向于调度到哪里
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: kubernetes.io/arch
                operator: In
                values:
                  - amd64

    # Pod 反亲和性：Pod 之间互相排斥
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchExpressions:
                - key: app
                  operator: In
                  values:
                    - web
            topologyKey: kubernetes.io/hostname
```

Pod 反亲和性的典型用途：确保同一应用的多个副本分散在不同 Node 上，避免单点故障。

### 污点与容忍（Taints and Tolerations）

```bash
# 给 Node 添加 Taint
kubectl taint nodes node-1 dedicated=gpu:NoSchedule

# 只有匹配 Toleration 的 Pod 才能调度到这个 Node
```

```yaml
spec:
  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "gpu"
      effect: "NoSchedule"
```

Taint 的效果：
- **NoSchedule**：新 Pod 不会调度到这里（已运行的不受影响）
- **PreferNoSchedule**：尽量不调度到这里
- **NoExecute**：新 Pod 不调度，已运行的 Pod 也会被驱逐

## LimitRange 与 ResourceQuota

### LimitRange：单 Pod 资源限制

LimitRange 为 Namespace 中的 Pod 设置默认资源限制：

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: my-team
spec:
  limits:
    - default:           # 默认 limits
        cpu: "500m"
        memory: "256Mi"
      defaultRequest:    # 默认 requests
        cpu: "100m"
        memory: "128Mi"
      max:               # 最大 limits
        cpu: "2"
        memory: "2Gi"
      min:               # 最小 requests
        cpu: "50m"
        memory: "64Mi"
      type: Container
```

### ResourceQuota：Namespace 资源总量

ResourceQuota 限制整个 Namespace 的资源使用总量：

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: my-team
spec:
  hard:
    requests.cpu: "10"         # Namespace 总 CPU requests 不超过 10 核
    requests.memory: "20Gi"    # Namespace 总内存 requests 不超过 20GB
    limits.cpu: "20"           # Namespace 总 CPU limits 不超过 20 核
    limits.memory: "40Gi"      # Namespace 总内存 limits 不超过 40GB
    pods: "50"                 # 最多 50 个 Pod
    services: "10"             # 最多 10 个 Service
```

## 常见误区

**误区一："不设置 requests/limits 就不限制资源"**

不设置 limits 时容器确实可以使用 Node 上所有可用资源，但这很危险。一个失控的容器可能耗尽整台机器的资源，导致其他 Pod 被 OOM Kill。

**误区二："requests 和 limits 设成一样的最安全"**

Guaranteed QoS 确实最安全，但会降低资源利用率。大部分应用的实际资源使用是波动的，设成 Burstable 可以在保证基本资源的同时允许突发。

**误区三："CPU limits 设高点没关系"**

CPU limits 是硬限制。即使 Node 上有空闲 CPU，超过 limit 的容器也会被限流。如果你的应用是 CPU 密集型且对延迟敏感，限制 CPU 会直接影响性能。

## 工程建议

1. **所有 Pod 都应该设置 requests 和 limits**：至少设置 requests，让调度器能做出合理决策
2. **先观察再调整**：部署后通过 `kubectl top pod` 观察实际资源使用，再调整 requests/limits
3. **Memory limits 要略高于实际需求**：内存超限会被 OOM Kill，留一些余量
4. **用 LimitRange 兜底**：为每个 Namespace 设置默认的 requests/limits，防止忘记配置
5. **用 ResourceQuota 防止资源耗尽**：限制每个团队/项目的资源使用上限

## 小结

- Requests 是调度依据，Limits 是运行上限
- CPU 超限被限流，内存超限被 OOM Kill
- QoS 等级：Guaranteed > Burstable > BestEffort
- 调度策略：nodeSelector、Affinity、Taints/Tolerations
- LimitRange 控制单 Pod 限制，ResourceQuota 控制 Namespace 总量

## 练习

### 练习一：QoS 等级判断

判断以下 Pod 的 QoS 等级：

```yaml
# Pod A
containers:
  - name: app
    resources:
      requests:
        cpu: "250m"
        memory: "128Mi"
      limits:
        cpu: "250m"
        memory: "128Mi"

# Pod B
containers:
  - name: app
    resources:
      requests:
        cpu: "100m"

# Pod C
containers:
  - name: app
    resources:
      requests:
        cpu: "250m"
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "256Mi"
```

### 练习二：资源规划

你有以下应用需要部署到一个 4 CPU、8GB 内存的集群节点上：
- 前端（Nginx）：实际使用约 0.1 CPU、64MB 内存
- 后端 API（Node.js）：实际使用约 0.3 CPU、256MB 内存，高峰期可到 0.8 CPU、512MB
- 数据库（PostgreSQL）：实际使用约 0.5 CPU、1GB 内存

为每个应用设计合理的 requests 和 limits 配置。

## 参考答案

### 练习一

**答案**：

- **Pod A**：Guaranteed — 所有容器的 requests 和 limits 完全相等
- **Pod B**：Burstable — 只设置了 requests，没有设置 limits（或只有部分设置），且至少有一个容器有 requests 或 limits
- **Pod C**：Burstable — requests ≠ limits

**要点**：
- Guaranteed 要求所有容器的所有资源（CPU 和内存）的 requests 和 limits 都相等
- 只要有一个不相等就是 Burstable
- 完全没有设置就是 BestEffort

### 练习二

**思路**：requests 设为实际使用量，limits 设为允许突发的上限。留出一些余量给系统进程。

**答案**：

```yaml
# 前端 Nginx
resources:
  requests:
    cpu: "100m"
    memory: "64Mi"
  limits:
    cpu: "200m"
    memory: "128Mi"
# 说明：Nginx 资源使用稳定，requests 和 limits 接近

# 后端 API
resources:
  requests:
    cpu: "300m"
    memory: "256Mi"
  limits:
    cpu: "1000m"
    memory: "512Mi"
# 说明：高峰期 CPU 和内存都会翻倍，limits 留出突发空间

# PostgreSQL
resources:
  requests:
    cpu: "500m"
    memory: "1Gi"
  limits:
    cpu: "1000m"
    memory: "1.5Gi"
# 说明：数据库需要稳定的资源保证，limits 留一些余量
```

资源核算：
```
requests 总计：100m + 300m + 500m = 900m CPU，64Mi + 256Mi + 1Gi ≈ 1.3Gi 内存
limits 总计：200m + 1000m + 1000m = 2200m CPU，128Mi + 512Mi + 1.5Gi ≈ 2.1Gi 内存
节点剩余：3100m CPU（requests），5.9Gi 内存（requests）→ 有足够空间容纳更多 Pod
```

**要点**：
- requests 设为稳定使用量，确保调度合理
- limits 设为突发上限 + 余量，避免 OOM Kill
- 总 requests 不要超过节点资源的 80%，给系统进程留空间
