# 多集群管理

## 场景引入

你的应用服务全球用户，需要在美国、欧洲、亚太三个区域部署。每个区域一个 K8s 集群，以降低延迟并满足数据合规要求（GDPR）。但管理三个独立的集群意味着：三套 CI/CD、三套监控、三套配置，配置漂移几乎不可避免。

多集群管理的核心挑战是：如何统一管理多个集群的部署、配置和监控，同时保持各集群的独立性。

## 学习目标

1. 理解多集群管理的动机和挑战
2. 了解集群联邦（KubeFed）的概念
3. 掌握 ArgoCD 多集群管理
4. 了解跨集群服务发现的方案
5. 学会设计多集群架构

## 多集群的动机

```
1. 地理分布：降低延迟，满足数据合规
2. 高可用：单集群故障不影响其他区域
3. 环境隔离：生产/测试/开发分离
4. 团队隔离：不同团队使用不同集群
5. 避免单集群过大：减少"爆炸半径"
```

## 集群联邦（KubeFed）

KubeFed 是 K8s 的集群联邦方案，将多个集群统一管理。

```yaml
# KubeFed 核心概念
apiVersion: types.kubefed.io/v1beta1
kind: FederatedDeployment
metadata:
  name: my-app
  namespace: default
spec:
  template:
    spec:
      replicas: 2
      selector:
        matchLabels:
          app: my-app
      template:
        spec:
          containers:
            - name: app
              image: my-app:1.0
  placement:
    clusters:
      - name: us-cluster
      - name: eu-cluster
      - name: ap-cluster
  overrides:
    - clusterName: eu-cluster
      clusterOverrides:
        - path: "/spec/replicas"
          value: 3
```

KubeFed 的问题：
- 项目活跃度下降
- 不支持所有 K8s 资源类型
- 配置同步有延迟

## ArgoCD 多集群管理

ArgoCD 是目前最流行的多集群管理方案。

### 注册远程集群

```bash
# 方式一：通过 CLI 注册
argocd cluster add us-cluster-context --name us-cluster
argocd cluster add eu-cluster-context --name eu-cluster
argocd cluster add ap-cluster-context --name ap-cluster

# 查看已注册集群
argocd cluster list
```

### ApplicationSet 多集群部署

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: my-app
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - cluster: us-cluster
            url: https://us-cluster.example.com:6443
            region: us-east
          - cluster: eu-cluster
            url: https://eu-cluster.example.com:6443
            region: eu-west
          - cluster: ap-cluster
            url: https://ap-cluster.example.com:6443
            region: ap-southeast
  template:
    metadata:
      name: 'my-app-{{cluster}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/myteam/k8s-manifests.git
        targetRevision: main
        path: apps/my-app
      destination:
        server: '{{url}}'
        namespace: production
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
```

### 按区域差异化配置

```yaml
generators:
  - list:
      elements:
        - cluster: us-cluster
          url: https://us-cluster:6443
          replicas: "3"
          region: us-east
        - cluster: eu-cluster
          url: https://eu-cluster:6443
          replicas: "2"
          region: eu-west
template:
  spec:
    source:
      path: 'apps/my-app/overlays/{{region}}'
```

## 跨集群服务发现

### 服务发现方案

```
方案一：全局 DNS
  每个集群的 Ingress 对应一个 DNS 记录
  DNS 按地理位置解析到最近的集群

方案二：全局负载均衡
  云厂商的 Global Load Balancer
  AWS Global Accelerator / GCP Global LB / Azure Front Door

方案三：Service Mesh 联邦
  Istio Multi-Cluster
  跨集群的服务发现和流量管理
```

### Istio 多集群

```yaml
# 主集群配置
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  meshConfig:
    defaultConfig:
      proxyMetadata:
        ISTIO_META_DNS_CAPTURE: "true"
        ISTIO_META_DNS_AUTO_ALLOCATE: "true"
  values:
    global:
      meshID: mesh1
      multiCluster:
        clusterName: primary
      network: network-primary
```

## 配置管理

### Kustomize 多集群

```
my-app/
├── base/
└── overlays/
    ├── us-east/
    │   └── kustomization.yaml
    ├── eu-west/
    │   └── kustomization.yaml
    └── ap-southeast/
        └── kustomization.yaml
```

### Helm 多集群 values

```bash
# 每个集群一套 values 文件
helm install my-app ./chart -f values-us.yaml -n production
helm install my-app ./chart -f values-eu.yaml -n production
```

## 常见误区

**误区一："多集群就是把同一个应用部署三次"**

不同集群可能有不同的配置（副本数、资源限制、域名），需要差异化管理。

**误区二："一个大集群比多个小集群好"**

大集群的"爆炸半径"更大。一个 etcd 故障影响所有工作负载。

**误区三："多集群不需要跨集群通信"**

有些场景确实需要跨集群通信（全局搜索、数据同步），需要设计好网络方案。

## 工程建议

1. **从两个集群开始**：生产 + 灾备，不要一开始就搞全球部署
2. **使用 ArgoCD ApplicationSet**：避免手动为每个集群创建 Application
3. **配置标准化**：base 配置统一，overlays 按集群差异化
4. **监控全局视图**：Thanos 或 Cortex 聚合多集群指标
5. **测试灾难恢复**：定期演练集群故障切换

## 小结

- 多集群管理解决地理分布、高可用、环境隔离的需求
- ArgoCD ApplicationSet 是最流行的多集群 GitOps 方案
- 跨集群服务发现需要全局 DNS 或全局负载均衡
- 配置管理使用 Kustomize overlays 或 Helm values 差异化
- 从简单开始，逐步扩展

```yaml
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

### 练习二

**答案**：

```yaml
# values-us-east.yaml
replicaCount: 3
resources:
  requests:
    cpu: 250m
    memory: 256Mi
ingress:
  host: app.us.example.com

# values-eu-west.yaml
replicaCount: 2
resources:
  requests:
    cpu: 200m
    memory: 256Mi
ingress:
  host: app.eu.example.com
```

**要点**：
- 不同区域的副本数可以不同（根据流量）
- 域名按区域区分
- 资源限制可以按集群能力差异化
