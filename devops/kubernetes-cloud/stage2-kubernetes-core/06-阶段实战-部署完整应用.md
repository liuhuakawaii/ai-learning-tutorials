# 阶段实战：部署完整应用

> 前置知识：Deployment、Service、Ingress、ConfigMap/Secret、PersistentVolume（Stage 2 第 1-5 课）

## 你要做什么

将一个包含前端、后端 API 和数据库的完整应用部署到 K8s。从外部能正常访问，数据能持久化。

这不是单个 YAML 的练习——这是你在真实项目里要做的事。

## 应用架构

```
外部请求
    │
    ▼
┌──────────┐
│ Ingress  │   ← 路由规则：/ → frontend, /api → backend
└──────────┘
    │
    ├──→ Service (frontend)
    │       └── Deployment (frontend:3000) × 2
    │
    └──→ Service (backend)
            └── Deployment (backend:8080) × 2
                    │
                    ├──→ Service (postgres)
                    │       └── StatefulSet (postgres:5432) × 1
                    │
                    └──→ Service (redis)
                            └── Deployment (redis:6379) × 1
```

## 部署顺序

K8s 资源之间有依赖关系。创建顺序很重要：

```
1. Namespace
2. ConfigMap + Secret（配置和密钥）
3. PersistentVolumeClaim（存储声明）
4. StatefulSet（数据库，有状态服务）
5. Deployment（无状态服务）
6. Service（服务发现）
7. Ingress（外部访问）
```

为什么这个顺序？因为后面的资源依赖前面的。Service 依赖 Deployment 的 Pod 存在，Ingress 依赖 Service 存在。

## YAML 文件

### Namespace

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: myapp
```

### Secret

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
  namespace: myapp
type: Opaque
data:
  POSTGRES_PASSWORD: c2VjcmV0    # echo -n 'secret' | base64
```

### ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: myapp
data:
  DATABASE_URL: postgres://postgres:secret@postgres:5432/myapp
  REDIS_URL: redis://redis:6379
  NODE_ENV: production
```

### PostgreSQL StatefulSet

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: myapp
spec:
  serviceName: postgres
  replicas: 1
  selector:
    matchLabels:
      app: postgres
  template:
    metadata:
      labels:
        app: postgres
    spec:
      containers:
        - name: postgres
          image: postgres:14
          ports:
            - containerPort: 5432
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: POSTGRES_PASSWORD
            - name: POSTGRES_DB
              value: myapp
          volumeMounts:
            - name: pgdata
              mountPath: /var/lib/postgresql/data
          resources:
            limits:
              memory: "512Mi"
              cpu: "500m"
  volumeClaimTemplates:
    - metadata:
        name: pgdata
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 1Gi
```

### Backend Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: myapp
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
        - name: backend
          image: ghcr.io/myorg/backend:latest
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: app-config
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
          resources:
            limits:
              memory: "256Mi"
              cpu: "250m"
```

## 部署和验证

```bash
# 按顺序部署
kubectl apply -f namespace.yaml
kubectl apply -f secret.yaml
kubectl apply -f configmap.yaml
kubectl apply -f postgres-statefulset.yaml
kubectl apply -f redis-deployment.yaml
kubectl apply -f backend-deployment.yaml
kubectl apply -f frontend-deployment.yaml
kubectl apply -f services.yaml
kubectl apply -f ingress.yaml

# 验证
kubectl get pods -n myapp
kubectl get services -n myapp
kubectl get ingress -n myapp

# 测试后端
kubectl port-forward service/backend -n myapp 8080:8080
curl http://localhost:8080/health

# 测试数据库连接
kubectl exec -it postgres-0 -n myapp -- psql -U postgres myapp -c "\dt"
```

## 常见问题排查

### Pod 一直 CrashLoopBackOff

```bash
kubectl logs <pod-name> -n myapp
kubectl describe pod <pod-name> -n myapp
```

常见原因：数据库连接失败（Secret 或 ConfigMap 配置错误）、端口不对、依赖服务还没就绪。

### Service 无法访问

```bash
kubectl get endpoints backend -n myapp
# 如果 Endpoints 为空，说明 Service 的 selector 和 Pod 的 labels 不匹配
```

## 练习

### 练习一：添加前端

参考 backend 的部署方式，部署一个 frontend Deployment 和 Service。配置 Ingress 规则，让 `/` 路由到 frontend。

### 练习二：健康检查

为 backend 添加 livenessProbe 和 readinessProbe。故意部署一个会启动失败的版本，观察 K8s 的行为。

### 练习三：配置热更新

修改 ConfigMap 中的 `NODE_ENV` 值，验证 Pod 是否自动获取了新配置。如果没有，思考为什么。

## 参考答案

### 练习一

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: myapp
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
  template:
    metadata:
      labels:
        app: frontend
    spec:
      containers:
        - name: frontend
          image: ghcr.io/myorg/frontend:latest
          ports:
            - containerPort: 3000
```

### 练习二

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 15
  failureThreshold: 3
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 10
```

部署一个启动会失败的版本：把 image 改成一个不存在的 tag。观察 `kubectl get pods`——状态会从 ContainerCreating → CrashLoopBackOff → 自动重启。

### 练习三

ConfigMap 更新后，Pod 不会自动获取新配置——因为环境变量是在 Pod 启动时注入的。需要重启 Pod：

```bash
kubectl edit configmap app-config -n myapp   # 修改 NODE_ENV
kubectl rollout restart deployment/backend -n myapp   # 重启 Pod
```

如果用 `envFrom` 注入环境变量，必须重启。如果用 `volumeMount` 挂载 ConfigMap 文件，可以自动更新（有延迟）。
