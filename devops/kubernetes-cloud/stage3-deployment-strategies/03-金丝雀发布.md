# 金丝雀发布

## 场景引入

蓝绿部署虽然安全，但需要双倍资源。而且它是一次性切换——要么全走新版本，要么全走旧版本。如果你想先让 10% 的用户体验新版本，观察一段时间没问题后再逐步扩大到 100%，蓝绿部署做不到。

金丝雀发布（Canary Release）是更精细的发布策略：新版本只接收一小部分流量，观察指标正常后再逐步增加比例。这种方式更安全、更省资源，是互联网公司最常用的发布策略之一。

## 学习目标

1. 理解金丝雀发布的原理和流量切分方式
2. 掌握基于 Pod 数量比例的金丝雀实现
3. 了解基于 Nginx Ingress 权重的金丝雀实现
4. 学会设计金丝雀发布的监控和回滚策略

## 金丝雀发布原理

```
10% 流量 ──────────► 新版本 Pod（1 个）
                      │
90% 流量 ──────────► 旧版本 Pod（9 个）
                      │
                 观察指标（错误率、延迟、CPU）
                      │
              ┌───────┴───────┐
              │指标正常        │指标异常
              ▼               ▼
        扩大到 50%        回滚到 0%
        再到 100%
```

## 方式一：基于 Pod 数量比例

最简单的金丝雀实现：调整新旧版本的 Pod 数量比例。

```yaml
# 旧版本：9 个副本
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-stable
spec:
  replicas: 9
  selector:
    matchLabels:
      app: web
      track: stable
  template:
    metadata:
      labels:
        app: web
        track: stable
    spec:
      containers:
        - name: web
          image: my-app:1.0.0
---
# 新版本：1 个副本（金丝雀）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-canary
spec:
  replicas: 1
  selector:
    matchLabels:
      app: web
      track: canary
  template:
    metadata:
      labels:
        app: web
        track: canary
    spec:
      containers:
        - name: web
          image: my-app:2.0.0
---
# Service 用通用 label 选择器，同时匹配两个 Deployment
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    app: web    # 匹配 stable 和 canary
  ports:
    - port: 80
```

流量分配：10 个 Pod 中 1 个是新版本，约 10% 流量。

```bash
# 逐步扩大金丝雀比例
kubectl scale deployment web-canary --replicas=3   # 30%
kubectl scale deployment web-canary --replicas=5   # 50%
kubectl scale deployment web-canary --replicas=10  # 100%

# 回滚
kubectl scale deployment web-canary --replicas=0
```

## 方式二：Nginx Ingress 权重

Nginx Ingress Controller 支持通过注解设置流量权重，更精确地控制流量比例。

```yaml
# stable-ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-stable
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-canary-svc
                port:
                  number: 80
```

```yaml
# 主 Ingress（接收剩余流量）
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-main
spec:
  ingressClassName: nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-stable-svc
                port:
                  number: 80
```

```bash
# 调整金丝雀权重
kubectl annotate ingress web-stable \
  nginx.ingress.kubernetes.io/canary-weight="30" --overwrite

# 基于 Header 的金丝雀（测试用户固定走新版本）
kubectl annotate ingress web-stable \
  nginx.ingress.kubernetes.io/canary-by-header="X-Canary" \
  nginx.ingress.kubernetes.io/canary-by-header-value="always" \
  --overwrite

# 基于 Cookie 的金丝雀
kubectl annotate ingress web-stable \
  nginx.ingress.kubernetes.io/canary-by-cookie="canary" \
  --overwrite
```

## 方式三：Istio VirtualService

如果使用 Istio Service Mesh，可以用 VirtualService 精确控制流量分配：

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: web-vs
spec:
  hosts:
    - app.example.com
  http:
    - route:
        - destination:
            host: web-svc
            subset: stable
          weight: 90
        - destination:
            host: web-svc
            subset: canary
          weight: 10
```

## 监控金丝雀发布

金丝雀发布的核心是"观察"。你需要监控以下指标：

```bash
# 1. 错误率
# 金丝雀 Pod 的错误率不应该显著高于稳定版本

# 2. 延迟
# P50/P95/P99 延迟不应该明显增加

# 3. 资源使用
# CPU、内存使用不应该异常飙升

# 4. 业务指标
# 转化率、点击率等业务指标不应该下降
```

### 自动化金丝雀判断

```yaml
# 伪代码：自动化金丝雀流程
canary-deploy:
  steps:
    - deploy canary (10%)
    - wait 5 minutes
    - check metrics:
        error_rate_canary < error_rate_stable * 1.1
        p99_latency_canary < p99_latency_stable * 1.2
    - if metrics_ok:
        - scale canary to 30%
        - wait 5 minutes
        - check metrics
        - if metrics_ok:
            - scale to 100%
            - remove stable
    - else:
        - rollback canary to 0
```

工具推荐：
- **Flagger**：K8s 的自动化金丝雀工具，集成 Prometheus 和 Istio
- **Argo Rollouts**：Argo 生态的渐进式发布工具

## 金丝雀发布流程

```bash
# 完整的金丝雀发布流程

# 1. 部署稳定版本
kubectl apply -f stable-deployment.yaml

# 2. 部署金丝雀版本（少量副本）
kubectl apply -f canary-deployment.yaml

# 3. 监控指标（5-10 分钟）
kubectl top pods -l track=canary
kubectl logs -l track=canary --tail=100

# 4. 判断指标是否正常
# 正常：逐步扩大金丝雀比例
kubectl scale deployment web-canary --replicas=3
# 等待并观察
kubectl scale deployment web-canary --replicas=5
# 等待并观察
kubectl scale deployment web-canary --replicas=10

# 5. 全量切换后，下线旧版本
kubectl delete deployment web-stable

# 异常：回滚金丝雀
kubectl delete deployment web-canary
```

## 金丝雀 vs 蓝绿 vs 滚动更新

| 特性 | 金丝雀 | 蓝绿 | 滚动更新 |
|------|--------|------|---------|
| 流量控制 | 精细（百分比） | 瞬间切换 | 逐步替换 |
| 资源开销 | 小（只多 1-2 个 Pod） | 大（双倍） | 中等 |
| 回滚速度 | 快（删除金丝雀） | 快（切回蓝） | 中等 |
| 验证能力 | 强（小流量观察） | 中 | 弱 |
| 实现复杂度 | 中 | 低 | 低 |

## 常见误区

**误区一："金丝雀就是少部署几个 Pod"**

Pod 数量比例只是近似的流量分配。实际流量分配取决于负载均衡算法和请求分布。要精确控制流量，需要 Ingress 权重或 Service Mesh。

**误区二："金丝雀发布不需要监控"**

金丝雀的核心价值就是"先观察再扩大"。没有监控的金丝雀发布和直接全量发布没有区别。

**误区三："金丝雀可以完全替代蓝绿"**

金丝雀适合渐进式验证，蓝绿适合需要瞬间切换的场景（如数据库 schema 变更）。

## 工程建议

1. **金丝雀比例从 5-10% 开始**：先用小流量验证
2. **观察时间 5-15 分钟**：太短可能无法发现问题
3. **设置自动回滚条件**：错误率超阈值自动回滚
4. **金丝雀和监控必须配合**：没有监控就不要做金丝雀
5. **使用 Flagger 或 Argo Rollouts**：自动化金丝雀流程

## 小结

- 金丝雀发布先用小流量验证新版本，逐步扩大到全量
- 三种实现方式：Pod 数量比例、Ingress 权重、Service Mesh
- 核心是监控：错误率、延迟、业务指标
- 工具推荐：Flagger、Argo Rollouts
- 适合渐进式验证，不适合需要瞬间切换的场景

## 参考答案

### 练习一

**答案**：

```bash
# 1. 部署稳定版本
kubectl create deployment web-stable --image=nginx:1.25 --replicas=3

# 2. 创建 Service（注意 selector 只用 app=web）
kubectl expose deployment web-stable --port=80 --name=web-svc
# 修改 label
kubectl label deployment web-stable app=web track=stable --overwrite
kubectl label pods -l app=web-stable app=web track=stable --overwrite

# 3. 部署金丝雀
kubectl create deployment web-canary --image=nginx:1.26 --replicas=1
kubectl label deployment web-canary app=web track=canary --overwrite

# 4. 修改 Service selector
kubectl patch svc web-svc -p '{"spec":{"selector":{"app":"web"}}}'

# 5. 验证流量分配（多次请求统计）
for i in $(seq 1 20); do
  kubectl exec -it deploy/web-stable -- curl -s http://web-svc 2>/dev/null | grep -o "nginx/[^ <]*" || echo "canary"
done

# 6. 扩大金丝雀
kubectl scale deployment web-canary --replicas=3

# 7. 全量切换
kubectl scale deployment web-stable --replicas=0
kubectl scale deployment web-canary --replicas=6

# 8. 下线旧版本
kubectl delete deployment web-stable
```

### 练习二

**答案**：

```yaml
# 金丝雀 Ingress（10% 流量）
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"
spec:
  ingressClassName: nginx
  rules:
    - host: app.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-canary-svc
                port:
                  number: 80
```

```bash
# 调整权重
kubectl annotate ingress web-canary \
  nginx.ingress.kubernetes.io/canary-weight="50" --overwrite
```

**要点**：
- 需要两个 Ingress：主 Ingress 和金丝雀 Ingress
- 金丝雀 Ingress 的 canary-weight 注解控制流量比例
- 权重变更后立即生效，不需要重启 Pod
