# 多环境管理

## 场景引入

你的应用需要部署到三个环境：开发（Dev）、测试（Staging）、生产（Prod）。三个环境的 K8s 资源结构基本相同，但配置有差异：副本数、资源限制、日志级别、数据库地址、域名。如果为每个环境维护一套独立的 YAML 文件，修改一个字段要在三个地方同步——这正是配置漂移的根源。

多环境管理的核心是：**一份基础配置 + 环境差异覆盖**。

## 学习目标

1. 理解多环境管理的核心挑战
2. 掌握 Kustomize 的 base + overlays 模式
3. 学会使用 Helm values 文件管理多环境配置
4. 了解命名空间隔离和 RBAC 策略
5. 设计合理的多环境 GitOps 流程

## Kustomize

Kustomize 是 K8s 原生的配置管理工具，内置在 kubectl 中。它通过 base + overlays 的方式实现多环境配置复用。

### 目录结构

```
my-app/
├── base/
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   ├── service.yaml
│   └── configmap.yaml
└── overlays/
    ├── dev/
    │   ├── kustomization.yaml
    │   └── patch-replicas.yaml
    ├── staging/
    │   ├── kustomization.yaml
    │   └── patch-replicas.yaml
    └── prod/
        ├── kustomization.yaml
        ├── patch-replicas.yaml
        └── patch-resources.yaml
```

### base 配置

```yaml
# base/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yaml
  - service.yaml
  - configmap.yaml
commonLabels:
  app: my-app
```

```yaml
# base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: app
          image: my-app:latest
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
```

### overlays 配置

```yaml
# overlays/dev/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
namespace: dev
namePrefix: dev-
patches:
  - path: patch-replicas.yaml
configMapGenerator:
  - name: app-config
    behavior: merge
    literals:
      - LOG_LEVEL=debug
      - DB_HOST=postgres.dev.svc
```

```yaml
# overlays/dev/patch-replicas.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
```

```yaml
# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - ../../base
namespace: production
namePrefix: prod-
patches:
  - path: patch-replicas.yaml
  - path: patch-resources.yaml
configMapGenerator:
  - name: app-config
    behavior: merge
    literals:
      - LOG_LEVEL=info
      - DB_HOST=postgres.production.svc
```

```yaml
# overlays/prod/patch-replicas.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
```

```yaml
# overlays/prod/patch-resources.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    spec:
      containers:
        - name: app
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 1
              memory: 512Mi
```

### 使用 Kustomize

```bash
# 预览渲染结果
kubectl kustomize overlays/dev/
kubectl kustomize overlays/prod/

# 应用到集群
kubectl apply -k overlays/dev/
kubectl apply -k overlays/prod/

# 查看差异
kubectl diff -k overlays/prod/
```

## Helm 多环境

使用 Helm 管理多环境在 Stage 3 第 1 课已经介绍过，这里补充最佳实践。

### values 文件组织

```
my-app-chart/
├── Chart.yaml
├── values.yaml           # 基础默认值
├── values-dev.yaml       # 开发环境覆盖
├── values-staging.yaml   # 测试环境覆盖
├── values-prod.yaml      # 生产环境覆盖
└── templates/
```

### 环境差异设计

```yaml
# values.yaml（基础）
replicaCount: 1
image:
  repository: my-app
  tag: "latest"
env:
  LOG_LEVEL: info
resources:
  requests:
    cpu: 100m
    memory: 128Mi
autoscaling:
  enabled: false
ingress:
  enabled: false
```

```yaml
# values-dev.yaml
replicaCount: 1
image:
  tag: "latest"
env:
  LOG_LEVEL: debug
ingress:
  enabled: true
  hosts:
    - host: dev.app.local
```

```yaml
# values-prod.yaml
replicaCount: 3
image:
  tag: "1.2.3"    # 生产用固定版本
env:
  LOG_LEVEL: warn
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 1
    memory: 512Mi
autoscaling:
  enabled: true
  minReplicas: 3
  maxReplicas: 20
ingress:
  enabled: true
  hosts:
    - host: app.example.com
  tls:
    - secretName: app-tls
      hosts:
        - app.example.com
```

## 命名空间隔离

```yaml
# 每个环境一个命名空间
apiVersion: v1
kind: Namespace
metadata:
  name: dev
  labels:
    environment: dev
---
apiVersion: v1
kind: Namespace
metadata:
  name: staging
  labels:
    environment: staging
---
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    environment: production
```

### RBAC 环境隔离

```yaml
# 开发者只能操作 dev 命名空间
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: dev-binding
  namespace: dev
subjects:
  - kind: Group
    name: developers
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: edit
  apiGroup: rbac.authorization.k8s.io
---
# 只有 SRE 能操作生产环境
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: prod-binding
  namespace: production
subjects:
  - kind: Group
    name: sre-team
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: admin
  apiGroup: rbac.authorization.k8s.io
```

## Kustomize vs Helm

| 特性 | Kustomize | Helm |
|------|-----------|------|
| 模板语法 | 无（原生 YAML） | Go Template |
| 学习曲线 | 低 | 中 |
| 多环境 | base + overlays | values 文件 |
| 依赖管理 | 不支持 | 支持 |
| 生态 | kubectl 内置 | 独立工具 |
| 适合场景 | 简单覆盖 | 复杂应用 |

## 环境 Promotion 流程

```
代码提交 → CI 构建 → 自动部署到 Dev
                         │
                    手动验证通过
                         │
                    部署到 Staging
                         │
                    QA 验证通过
                         │
                    部署到 Production（金丝雀/蓝绿）
```

### GitOps 中的环境 Promotion

```yaml
# ArgoCD ApplicationSet 管理多环境
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: my-app
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - env: dev
            namespace: dev
            revision: develop
          - env: staging
            namespace: staging
            revision: main
          - env: prod
            namespace: production
            revision: main
  template:
    metadata:
      name: 'my-app-{{env}}'
    spec:
      project: default
      source:
        repoURL: https://github.com/myteam/k8s-manifests.git
        targetRevision: '{{revision}}'
        path: 'apps/my-app/overlays/{{env}}'
      destination:
        server: https://kubernetes.default.svc
        namespace: '{{namespace}}'
```

## 常见误区

**误区一："三个环境用三套独立 YAML"**

这是配置漂移的根源。应该用一份 base 配置 + 环境差异覆盖。

**误区二："生产和开发用同一套配置，只是副本数不同"**

不同环境的差异不只是副本数。日志级别、资源限制、域名、数据库地址、特性开关都可能不同。

**误区三："手动在生产环境 kubectl apply"**

所有环境的变更都应该通过 GitOps 工具同步。手动修改会被 selfHeal 自动恢复。

## 工程建议

1. **简单项目用 Kustomize，复杂项目用 Helm**：Kustomize 学习成本低，Helm 功能更强大
2. **生产环境用固定版本号**：不要用 `latest` 标签
3. **通过 PR 审核环境 Promotion**：代码审核通过后才能部署到下一个环境
4. **RBAC 隔离环境权限**：开发者不能直接操作生产环境
5. **监控所有环境的一致性**：定期检查是否有配置漂移

## 小结

- 多环境管理的核心是"一份基础配置 + 环境差异覆盖"
- Kustomize 用 base + overlays 模式，Helm 用 values 文件
- 命名空间 + RBAC 实现环境隔离
- GitOps + ApplicationSet 管理多环境自动同步
- 环境 Promotion 应该有审核流程

## 练习

### 练习一：Kustomize 多环境

使用 Kustomize 创建 base + overlays 结构，部署到 dev 和 prod 两个命名空间。

### 练习二：Helm 多环境

使用 Helm 创建两套 values 文件，部署到不同命名空间并验证配置差异。

## 参考答案

### 练习一

**答案**：

```bash
# 创建目录结构
mkdir -p my-app/base my-app/overlays/dev my-app/overlays/prod

# 创建 base 配置
# base/deployment.yaml, base/service.yaml, base/kustomization.yaml

# 创建 overlays
# overlays/dev/kustomization.yaml, overlays/prod/kustomization.yaml

# 预览
kubectl kustomize my-app/overlays/dev/
kubectl kustomize my-app/overlays/prod/

# 部署
kubectl apply -k my-app/overlays/dev/
kubectl apply -k my-app/overlays/prod/

# 验证
kubectl get all -n dev
kubectl get all -n prod
```

### 练习二

**答案**：

```bash
# 安装到 dev
helm install my-app ./my-app-chart -f values-dev.yaml -n dev --create-namespace

# 安装到 prod
helm install my-app ./my-app-chart -f values-prod.yaml -n prod --create-namespace

# 验证差异
kubectl get deploy -n dev my-app -o jsonpath='{.spec.replicas}'   # 1
kubectl get deploy -n prod my-app -o jsonpath='{.spec.replicas}'  # 3
```

**要点**：
- 同一个 Chart 通过不同 values 文件适配不同环境
- 生产环境的资源限制和副本数应该高于开发环境
