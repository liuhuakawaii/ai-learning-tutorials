# 01 工作流引擎设计

> 工作流引擎是 AI 平台的"大脑"——让复杂的 AI 任务变得可编排、可复用、可监控。

## 场景引入

你正在开发一个 AI 客服平台，产品经理提出一个需求：当用户发送消息时，先用 LLM 分析意图，再根据意图类型调用不同的工具（查订单、退款、转人工），最后生成回复。如果用硬编码实现，每次调整流程都要改代码、测试、上线。当流程变复杂——加入并行查询、条件分支、人工审批——代码会变成一团意大利面。你需要一个可视化的流程编排系统，让非开发人员也能拖拽配置工作流，这就是工作流引擎存在的意义。

## 学习目标

- 理解 DAG（有向无环图）工作流模型
- 设计节点类型和边的语义
- 理解工作流执行模型

## 核心概念

### DAG 模型

```python
# backend/app/workflow/models.py
from enum import Enum
from pydantic import BaseModel

class NodeType(str, Enum):
    LLM = "llm"                    # LLM 调用节点
    TOOL = "tool"                  # 工具调用节点
    CONDITION = "condition"        # 条件分支节点
    HUMAN = "human"                # 人工审批节点
    PARALLEL = "parallel"          # 并行执行节点
    INPUT = "input"                # 输入节点
    OUTPUT = "output"              # 输出节点

class NodeConfig(BaseModel):
    """节点配置"""
    id: str
    type: NodeType
    label: str
    config: dict                   # 节点特定配置
    position: dict                 # 画布位置 {x, y}

class Edge(BaseModel):
    """边（连接线）"""
    id: str
    source: str                    # 源节点 ID
    target: str                    # 目标节点 ID
    source_handle: str | None = None  # 源端口（条件分支用）
    label: str | None = None

class WorkflowDefinition(BaseModel):
    """工作流定义"""
    id: str
    name: str
    description: str
    nodes: list[NodeConfig]
    edges: list[Edge]
    variables: dict = {}           # 全局变量
    version: int = 1
```

### 节点类型定义

| 节点类型 | 功能 | 输入 | 输出 |
|----------|------|------|------|
| INPUT | 接收用户输入 | 用户消息 | 文本 |
| LLM | 调用大模型 | Prompt + 变量 | AI 回复 |
| TOOL | 调用工具 | 参数 | 工具结果 |
| CONDITION | 条件判断 | 条件表达式 | true/false 分支 |
| HUMAN | 人工审批 | 待审批内容 | 审批结果 |
| PARALLEL | 并行执行 | 多个分支 | 聚合结果 |
| OUTPUT | 输出结果 | 最终结果 | 返回给用户 |

## 练习

### 练习 1：模型设计

用 Pydantic 定义完整的工作流模型：

1. 节点配置（各类型的特定配置）
2. 边的定义（包括条件分支的 handle）
3. 工作流定义（包含变量和版本）

### 练习 2：DAG 验证

实现 DAG 验证逻辑：

1. 检测环路
2. 检测孤立节点
3. 检测缺失的输入/输出节点

## 常见误区

- 认为工作流就是简单的线性步骤串联，忽略了 DAG 中的并行、条件和循环场景
- 在节点配置中硬编码业务参数，导致每次调整都要修改代码重新部署
- 忽略 DAG 验证，不检测环路和孤立节点，导致执行时出现死循环或数据丢失

## 工程建议

- 先定义清晰的节点类型和数据模型，再实现编辑器和执行引擎，模型设计决定后续扩展性
- DAG 验证要前置——在保存工作流时就检测环路、孤立节点、缺失的输入输出节点，而不是执行时才发现
- 节点配置使用 JSON Schema 定义，方便前端自动生成表单和后端校验
- 版本管理要从一开始就做好，工作流定义变更时需要支持回滚和灰度发布

## 本节要点

- 工作流 = DAG（节点 + 边）
- 节点类型决定执行逻辑，边决定执行顺序
- 验证是第一步——不合法的 DAG 不能执行
