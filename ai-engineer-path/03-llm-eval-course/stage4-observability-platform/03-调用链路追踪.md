# 03 调用链路追踪——从用户输入到模型输出的全链路可视化

> 看见全链路，才能找到瓶颈。追踪是调试 AI 应用的"时光机"。

## 场景引入

用户反馈"这个问题的回答不对"，你打开 Langfuse 看到该条 Trace 的总耗时 4.2 秒，质量评分 2/5。但问题出在哪？是 RAG 检索召回了错误的文档，还是 Prompt 组装时上下文被截断了，还是模型本身产生了幻觉？如果你的追踪只记录了"一次 LLM 调用"，那和没追踪没有区别。你需要的是从用户输入到模型输出的每一步都可视化的全链路追踪。

## 学习目标

- 掌握 AI 应用的全链路追踪方法
- 学会分析追踪数据定位问题
- 建立链路追踪的最佳实践

## 二、追踪实现

### 2.1 完整追踪示例

```python
from langfuse.decorators import observe, langfuse_context

@observe()
def process_user_query(query: str, user_id: str) -> dict:
    """完整追踪的用户查询处理"""
    
    # 设置用户信息
    langfuse_context.update_current_trace(
        user_id=user_id,
        session_id=f"session_{user_id}"
    )
    
    # 1. 输入处理
    processed_input = preprocess_input(query)
    
    # 2. RAG 检索
    retrieval_result = rag_retrieve(processed_input)
    
    # 3. 上下文组装
    prompt = assemble_prompt(query, retrieval_result["contexts"])
    
    # 4. LLM 调用
    answer = call_llm_with_tracking(prompt)
    
    # 5. 后处理
    final_result = post_process(answer, retrieval_result["sources"])
    
    # 6. 自动评估
    eval_score = auto_evaluate(query, final_result["answer"], retrieval_result["contexts"])
    
    return final_result

@observe()
def rag_retrieve(query: str) -> dict:
    """RAG 检索（带追踪）"""
    
    # 查询重写
    rewritten_query = rewrite_query(query)
    
    # 向量搜索
    search_results = vector_search(rewritten_query)
    
    # 重排序
    reranked = rerank(query, search_results)
    
    return {
        "contexts": reranked[:5],
        "sources": [r["metadata"] for r in reranked[:5]]
    }

@observe()
def call_llm_with_tracking(prompt: str) -> str:
    """带详细追踪的 LLM 调用"""
    
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": prompt}],
        stream=True
    )
    
    # 流式收集
    full_response = ""
    for chunk in response:
        if chunk.choices[0].delta.content:
            full_response += chunk.choices[0].delta.content
    
    return full_response
```

## 三、追踪数据分析

### 3.1 性能瓶颈分析

```python
def analyze_trace_performance(trace_id: str) -> dict:
    """分析追踪性能"""
    
    # 从 Langfuse 获取追踪数据
    trace = langfuse.get_trace(trace_id)
    
    spans = trace.spans
    
    # 找出耗时最长的 Span
    longest_span = max(spans, key=lambda s: s.end_time - s.start_time)
    
    # 计算各阶段耗时占比
    total_duration = trace.end_time - trace.start_time
    
    span_durations = {}
    for span in spans:
        duration = span.end_time - span.start_time
        span_durations[span.name] = {
            "duration": duration,
            "percentage": duration / total_duration * 100
        }
    
    return {
        "total_duration": total_duration,
        "longest_span": longest_span.name,
        "span_durations": span_durations
    }
```

### 3.2 问题定位

```
常见性能问题：

问题 1：RAG 检索耗时长
  表现：rag-retrieval Span 占比 > 50%
  原因：
    - 向量搜索慢（索引问题）
    - 重排序慢（模型问题）
    - 检索数量过多
  优化：
    - 优化向量索引
    - 减少检索数量
    - 使用更快的重排序模型

问题 2：LLM 调用慢
  表现：llm-call Span 占比 > 70%
  原因：
    - 输入 Token 过多
    - 模型选择不当
    - 网络延迟
  优化：
    - 精简 Prompt
    - 使用更快的模型
    - 流式输出

问题 3：后处理慢
  表现：post-processing Span 占比 > 30%
  原因：
    - 复杂的格式化逻辑
    - 外部 API 调用
  优化：
    - 异步处理
    - 缓存结果
```

## 四、最佳实践

```
追踪最佳实践：

1. 命名规范
   - Trace：{功能}-{操作}
   - Span：{模块}-{步骤}
   - Generation：{model}-{task}

2. 属性记录
   - 记录关键业务参数
   - 记录用户标识
   - 记录会话信息

3. 错误追踪
   - 记录错误类型和消息
   - 记录错误堆栈
   - 关联用户反馈

4. 性能追踪
   - 记录 Token 消耗
   - 记录延迟
   - 记录成本

5. 采样策略
   - 生产环境可以采样（如 10%）
   - 错误请求 100% 记录
   - 慢请求 100% 记录
```

## 常见误区

1. **追踪粒度要么太粗要么太细**：只记录一个 `process_query` 的总耗时，或者把每个变量赋值都建 Span。正确的粒度是按"可独立优化的步骤"划分——RAG 检索、LLM 调用、后处理各一个 Span，内部再按需嵌套。

2. **流式响应不记录 TTFT（首 Token 延迟）**：只记录了总延迟，但用户体验差的根因是首 Token 来得太慢。流式场景下必须同时追踪 TTFT 和总延迟，它们对应不同的优化方向。

3. **错误追踪只记录"失败了"**：Trace 中只标记 `success: false`，没有记录错误类型（超时/限流/内容过滤）、重试次数、fallback 模型。排查时只能看到"这里挂了"，不知道为什么挂、有没有自动恢复。

4. **生产环境不设采样策略**：100% 采样所有请求的完整 Trace，导致追踪存储成本飙升。应该对正常请求采样（如 10%），但对错误请求和慢请求 100% 记录。

## 工程建议

1. **Trace 命名遵循"动词-对象"规范**：如 `query-knowledge-base`、`generate-summary`、`rewrite-query`。不要用 `process`、`handle` 这种模糊命名。清晰的 Trace 名称让你在 Langfuse 列表页一眼就能看出请求类型。

2. **在 Span 属性中记录业务语义**：除了 `model`、`input_tokens` 等技术字段，还要记录 `user_query_intent`（用户意图分类）、`retrieved_doc_count`（召回文档数）、`rerank_score`（重排序分数）。这些业务语义字段是分析质量退化根因的关键线索。

3. **为流式响应分别记录 TTFT 和 TPS**：首 Token 延迟（TTFT）影响用户"感知到的响应速度"，每秒 Token 数（TPS）影响"内容生成的流畅度"。两者对应不同的优化手段——TTFT 主要受模型预填充阶段影响，TPS 主要受解码阶段和输出 token 数影响。

4. **建立"慢请求"自动分析管道**：对超过 P95 延迟的 Trace 自动提取并归档，按瓶颈阶段（检索/生成/后处理）分类统计。每周 review 一次慢请求分布，持续优化性能热点。
