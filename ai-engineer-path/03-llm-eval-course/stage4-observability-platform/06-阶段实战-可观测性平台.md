## 场景引入

你已经分别学了日志、追踪、指标、成本监控、质量 Dashboard，但它们各自为政：日志在 ELK 里，追踪在 Langfuse 里，成本数据在自建脚本里，质量评分在 Jupyter Notebook 里。当一个问题出现时，你需要在四五个系统之间来回切换才能拼凑出完整画面。现在是时候把它们整合成一个统一的可观测性平台——让一个 Dashboard 就能看到全局，一条告警就能定位根因。

## 二、核心实现

```python
# core/observability.py

class ObservabilityPlatform:
    """可观测性平台"""
    
    def __init__(self, config):
        self.logger = StructuredLogger(config)
        self.tracer = LangfuseTracer(config)
        self.metrics = MetricsCollector(config)
        self.cost_monitor = CostMonitor(config)
        self.alerter = AlertManager(config)
    
    def track_request(self, request_id: str, user_id: str):
        """开始追踪请求"""
        self.tracer.start_trace(request_id, user_id)
        self.metrics.increment("requests_total")
    
    def track_llm_call(
        self,
        request_id: str,
        model: str,
        input_tokens: int,
        output_tokens: int,
        latency: float,
        success: bool
    ):
        """追踪 LLM 调用"""
        # 记录日志
        self.logger.log_llm_call(
            request_id, model, input_tokens, output_tokens, latency, success
        )
        
        # 记录追踪
        self.tracer.log_generation(
            request_id, model, input_tokens, output_tokens, latency
        )
        
        # 记录指标
        self.metrics.record_latency(latency)
        self.metrics.record_tokens(input_tokens + output_tokens)
        
        # 记录成本
        cost = self.cost_monitor.record_usage(
            model, input_tokens, output_tokens, "llm_call"
        )
        
        # 检查告警
        self.alerter.check({
            "latency": latency,
            "cost": cost,
            "success": success
        })
    
    def track_quality_score(self, request_id: str, score: float):
        """追踪质量评分"""
        self.tracer.log_score(request_id, "quality", score)
        self.metrics.record_quality(score)
        
        if score < 0.7:
            self.alerter.trigger("low_quality", {"score": score})
    
    def get_dashboard_data(self) -> dict:
        """获取 Dashboard 数据"""
        return {
            "overview": self.metrics.get_overview(),
            "trends": self.metrics.get_trends(),
            "alerts": self.alerter.get_active_alerts(),
            "cost": self.cost_monitor.get_report()
        }
```

## 三、集成示例

```python
# 使用示例

from core.observability import ObservabilityPlatform

# 初始化
platform = ObservabilityPlatform(config)

# 在 AI 应用中使用
def process_query(query: str, user_id: str) -> dict:
    request_id = str(uuid.uuid4())
    
    # 开始追踪
    platform.track_request(request_id, user_id)
    
    try:
        # RAG 检索
        contexts = retrieve_contexts(query)
        
        # LLM 调用
        start_time = time.time()
        answer = call_llm(query, contexts)
        latency = time.time() - start_time
        
        # 记录 LLM 调用
        platform.track_llm_call(
            request_id,
            model="gpt-4o",
            input_tokens=500,
            output_tokens=200,
            latency=latency,
            success=True
        )
        
        # 评估质量
        quality_score = evaluate_quality(query, answer, contexts)
        platform.track_quality_score(request_id, quality_score)
        
        return {"answer": answer, "request_id": request_id}
    
    except Exception as e:
        platform.track_llm_call(
            request_id, "gpt-4o", 0, 0, 0, False
        )
        raise
```

## 常见误区

1. **过度追求架构完美而迟迟不上线**：花三周设计一个"完美"的可观测性平台架构，结果应用已经带着问题跑了三周没有监控。正确的做法是先用 Langfuse + 最简 Dashboard 跑起来，再逐步迭代完善。

2. **可观测性平台本身没有可观测性**：平台的各个模块（日志采集、指标上报、告警推送）自身也可能出故障，但没有对平台自身的健康检查。如果 Langfuse SDK 连接断了，你的应用反而失去了所有追踪能力，而你毫不知情。

3. **告警渠道太多导致告警疲劳**：同时配置了邮件、Slack、短信、电话告警，结果每天收到几十条低优先级告警，真正重要的告警反而被淹没了。应该严格分级：P0 电话、P1 即时消息、P2 邮件、P3 Dashboard 展示。

4. **只建平台不建流程**：平台搭好了，但没有人负责每天检查 Dashboard、没有人负责响应告警、没有人负责分析低分案例。可观测性的价值在于"有人看、有人反应、有人改进"，技术平台只是载体。

## 工程建议

1. **分阶段落地，不要一步到位**：第一周接入 Langfuse 做基础追踪 + 一个概览 Dashboard；第二周加成本监控和预算预警；第三周加质量评估和告警规则。每阶段验证可用再进入下一阶段，比一次性搭建一个复杂但未经验证的系统更可靠。

2. **用 OpenTelemetry 作为统一数据采集层**：日志用 OTel Logs、追踪用 OTel Traces、指标用 OTel Metrics，三者共享同一个 Trace ID。这样未来如果要从 Langfuse 迁移到其他平台（如 SigNoz、Grafana Tempo），只需更换后端存储，不需要改应用代码。

3. **为可观测性平台写集成测试**：模拟一次完整的 LLM 调用，验证 Trace 是否正确创建、成本是否正确计算、告警是否正确触发。当平台代码更新时，用测试保证核心链路不 break，避免"监控系统本身坏了而你不知道"。

4. **建立可观测性 Runbook**：为每类告警写一份标准处理流程（Runbook），包含排查步骤、常见根因、修复方案。值班人员收到告警时按 Runbook 操作，不需要每次都从零开始排查。随着经验积累持续更新 Runbook。
