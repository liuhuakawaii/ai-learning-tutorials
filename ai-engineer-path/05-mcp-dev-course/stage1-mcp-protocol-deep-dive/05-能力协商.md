# 05 能力协商——Client 与 Server 的能力发现与协商机制

> Client 和 Server 在连接时需要交换能力信息，确保双方理解对方支持的功能。

## 场景引入

你写了一个支持 Resource 订阅的 MCP Server，部署后发现某些 Client 连上来后直接调用 resources/subscribe 却报错了。排查后发现，这些 Client 在初始化时没有声明 subscribe 能力，Server 却没有检查就直接处理了请求。反过来，有些 Client 声明了 prompts 能力，但你的 Server 根本没实现 prompts——Client 发 prompts/list 请求时 Server 返回了 Method not found。能力协商到底该怎么正确实现？

## 一、能力协商流程

```
能力协商流程：

1. Client 发送初始化请求
   {
     "method": "initialize",
     "params": {
       "capabilities": {
         "tools": {},
         "resources": {"subscribe": true},
         "prompts": {}
       }
     }
   }

2. Server 返回能力
   {
     "result": {
       "capabilities": {
         "tools": {"listChanged": true},
         "resources": {"subscribe": true},
         "prompts": {}
       }
     }
   }

3. Client 发送初始化完成通知
   {
     "method": "notifications/initialized"
   }
```

## 二、能力定义

```python
class ServerCapabilities:
    """Server 能力"""
    
    def __init__(self):
        self.tools = {"listChanged": True}
        self.resources = {"subscribe": True}
        self.prompts = {}
    
    def to_dict(self) -> dict:
        return {
            "tools": self.tools,
            "resources": self.resources,
            "prompts": self.prompts
        }

class ClientCapabilities:
    """Client 能力"""
    
    def __init__(self):
        self.tools = {}
        self.resources = {"subscribe": True}
        self.prompts = {}
    
    def to_dict(self) -> dict:
        return {
            "tools": self.tools,
            "resources": self.resources,
            "prompts": self.prompts
        }
```

## 三、能力检查

```python
class CapabilityChecker:
    """能力检查器"""
    
    def check_tool_support(self, server_caps: dict, tool_name: str) -> bool:
        """检查 Server 是否支持工具"""
        return "tools" in server_caps
    
    def check_resource_subscription(self, server_caps: dict) -> bool:
        """检查 Server 是否支持资源订阅"""
        resources = server_caps.get("resources", {})
        return resources.get("subscribe", False)
```

## 四、动态能力更新

```python
class DynamicCapabilities:
    """动态能力管理"""
    
    def __init__(self):
        self.capabilities = {}
        self.change_listeners = []
    
    def update(self, new_capabilities: dict):
        """更新能力"""
        self.capabilities = new_capabilities
        self._notify_change()
    
    def on_change(self, listener):
        """监听能力变更"""
        self.change_listeners.append(listener)
    
    def _notify_change(self):
        """通知变更"""
        for listener in self.change_listeners:
            listener(self.capabilities)
```

## 常见误区

```
误区 1：能力协商只是形式，可以跳过
  能力协商是 MCP 协议的必要步骤。跳过协商直接调用方法，
  会导致 Server 不支持的功能被调用，产生不可预期的错误。

误区 2：Server 必须支持 Client 声明的所有能力
  能力协商是"广告"机制，不是"承诺"机制。
  Server 只需要支持自己声明的能力，Client 声明的能力 Server 可以忽略。

误区 3：能力在初始化后就不能变了
  MCP 支持动态能力更新。Server 可以通过 notifications/tools/list_changed
  通知 Client 工具列表已变更，Client 应重新获取工具列表。

误区 4：能力字段为空表示不支持
  空对象 {} 通常表示"支持该能力但没有特殊配置"，
  完全不出现该字段才表示"不支持"。两者含义不同。
```

## 工程建议

```
1. 初始化时严格校验能力
   在 initialize 处理器中，检查 Client 声明的能力是否与 Server 匹配。
   对于不支持的能力，要在响应中明确不包含该字段。

2. 调用前检查能力可用性
   在处理 tools/call、resources/read 等请求之前，
   先检查对应的 capabilities 是否在初始化时协商通过。

3. 用 listChanged 支持热更新
   如果你的 Server 支持运行时增删 Tool，要在 capabilities 中声明 listChanged。
   Tool 列表变化时发送通知，让 Client 及时更新缓存。

4. 记录协商结果用于调试
   把初始化时的 Client/Server 能力交换记录到日志中。
   连接问题排查时，能力不匹配是最常见的原因之一。
```

## 小结

1. 能力协商在初始化时进行
2. Client 和 Server 交换支持的功能列表
3. 能力检查确保调用时功能可用
4. 支持动态能力更新和通知
