# 04 传输层——stdio / SSE / Streamable HTTP 的选型与实现

> MCP 支持多种传输方式。选择合适的传输层是部署的关键。

## 场景引入

你在本地用 stdio 模式开发了一个 MCP Server，跑得好好的。但产品上线时，运维说 Server 必须部署在远程服务器上，客户端通过网络调用。你发现 stdio 根本不支持远程通信，需要换成 SSE 或 Streamable HTTP。可是这两种传输方式有什么区别？SSE 的单向流够用吗？Streamable HTTP 的双向流又该怎么实现？选错传输层，后面改起来成本巨大。

## 一、三种传输方式

```
┌─────────────────────────────────────────────────────────────┐
│                    三种传输方式                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. stdio（标准输入输出）                                     │
│  ├── 通过进程的 stdin/stdout 通信                            │
│  ├── 适用于本地工具                                          │
│  ├── 简单、低延迟                                            │
│  └── 不支持远程调用                                          │
│                                                             │
│  2. SSE（Server-Sent Events）                               │
│  ├── 基于 HTTP 的单向流                                      │
│  ├── 适用于远程服务                                          │
│  ├── 支持流式响应                                            │
│  └── 需要额外的请求通道                                      │
│                                                             │
│  3. Streamable HTTP                                         │
│  ├── 基于 HTTP 的双向流                                      │
│  ├── 适用于远程服务                                          │
│  ├── 支持流式请求和响应                                      │
│  └── 更灵活，但实现复杂                                      │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 二、stdio 实现

```python
import sys
import json

class StdioTransport:
    """stdio 传输"""
    
    def send(self, message: dict):
        """发送消息"""
        json_str = json.dumps(message)
        sys.stdout.write(json_str + "\n")
        sys.stdout.flush()
    
    def receive(self) -> dict:
        """接收消息"""
        line = sys.stdin.readline()
        return json.loads(line)
```

## 四、传输方式选择

```
选择指南：

本地工具 → stdio
- 简单、低延迟
- 无需网络配置
- 适用于 CLI 工具

远程服务 → SSE
- 支持流式响应
- 基于 HTTP，易于部署
- 适用于 Web 服务

高要求场景 → Streamable HTTP
- 支持双向流
- 更灵活
- 适用于复杂场景
```

## 五、MCP SDK 传输层

```python
from mcp.server import Server
from mcp.transport.stdio import StdioServerTransport

# 创建 Server
server = Server("my-server")

# 使用 stdio 传输
transport = StdioServerTransport()

```

## 常见误区

```
误区 1：stdio 只能用于开发环境
  stdio 不仅可以用于开发调试，也是 Claude Desktop 等产品的标准通信方式。
  它延迟低、无需网络配置，非常适合本地工具场景。

误区 2：SSE 和 Streamable HTTP 是同一种东西
  SSE 是单向流（Server → Client），Client 的请求需要走另一个 HTTP 通道。
  Streamable HTTP 是双向流，请求和响应都在同一个连接上完成。

误区 3：选传输层只看功能需求
  传输层的选择还要考虑部署环境、网络拓扑、防火墙策略。
  比如有些企业网络会阻断长连接，SSE 就可能不稳定。

误区 4：切换传输层只需要改一行配置
  不同传输层的消息分帧方式、连接管理、错误恢复机制都不同。
  从 stdio 切换到 SSE 意味着要处理网络断连、重连、心跳等问题。
```

## 工程建议

```
1. 本地工具优先选 stdio
   如果 Server 和 Client 在同一台机器上，stdio 是最简单的选择。
   不需要处理网络、端口、CORS 等问题。

2. 远程服务用 SSE，复杂场景用 Streamable HTTP
   SSE 基于 HTTP，部署简单，适合大多数远程场景。
   只有在需要真正的双向流式通信时，才考虑 Streamable HTTP。

3. 做好连接生命周期管理
   无论哪种传输层，都要处理连接建立、保活、断开、重连。
   在 Server 的 shutdown hook 中优雅关闭所有连接。

4. 测试时覆盖网络异常
   用 tc（Linux）或 Network Link Conditioner（macOS）模拟丢包、延迟、断连。
   传输层的健壮性比功能正确性更难测试，也更重要。
```

## 小结

1. 三种传输方式：stdio、SSE、Streamable HTTP
2. stdio 适用于本地工具，SSE 适用于远程服务
3. 选择依据：部署环境、性能要求、复杂度
4. MCP SDK 提供了传输层的封装
