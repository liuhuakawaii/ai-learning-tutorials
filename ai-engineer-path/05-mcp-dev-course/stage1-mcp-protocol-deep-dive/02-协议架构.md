# 02 协议架构——Host / Client / Server 三层模型与消息流

> MCP 的三层架构：Host 管理环境，Client 负责通信，Server 提供能力。

## 场景引入

你在团队里搭建了一个数据库查询的 MCP Server，本以为接入 Claude Desktop 就完事了。结果产品经理说要在 VS Code 里也能用，另一个团队说要在他们的自定义 Web 应用里集成。你发现不同宿主环境对 Client 的管理方式完全不同——有的允许并行连接多个 Server，有的只支持单连接。Host、Client、Server 三层之间到底该怎么分工？消息从用户输入到工具结果返回，中间经过了哪些环节？不搞清楚这些，集成工作就是一团乱麻。

## 学习目标

- 深入理解 MCP 的三层架构
- 掌握消息流的完整路径
- 理解各层的职责和交互

## 一、三层架构

```
┌─────────────────────────────────────────────────────────────┐
│                    MCP 三层架构                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Host（宿主）                                                │
│  ├── 运行 AI 应用的环境                                      │
│  ├── 管理 Client 的生命周期                                  │
│  ├── 处理用户交互                                            │
│  └── 例：VS Code、Claude Desktop、自定义应用                  │
│                                                             │
│  Client（客户端）                                            │
│  ├── 与 Server 建立连接                                      │
│  ├── 发现 Server 提供的工具                                  │
│  ├── 发送工具调用请求                                        │
│  └── 处理 Server 返回的结果                                  │
│                                                             │
│  Server（服务端）                                            │
│  ├── 提供工具能力（Tool / Resource / Prompt）                │
│  ├── 处理 Client 的请求                                      │
│  ├── 执行具体的工具逻辑                                      │
│  └── 例：数据库工具、文件系统工具、API 工具                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 二、消息流

```
完整消息流：

1. 初始化
   Host → Client: 创建 Client 实例
   Client → Server: 建立连接
   Client → Server: 初始化请求（capabilities）
   Server → Client: 初始化响应（capabilities）

2. 工具发现
   Client → Server: tools/list 请求
   Server → Client: 工具列表（名称、描述、参数）

3. 工具调用
   User → Host: 用户请求
   Host → Client: 转发请求
   Client → Server: tools/call 请求
   Server: 执行工具
   Server → Client: 返回结果
   Client → Host: 转发结果
   Host → User: 展示结果
```

## 三、消息格式

```json
// 请求
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "database_query",
    "arguments": {
      "sql": "SELECT * FROM users LIMIT 10"
    }
  }
}

// 响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "[{\"id\": 1, \"name\": \"Alice\"}, ...]"
      }
    ]
  }
}
```

## 四、能力协商

```python
# Client 初始化请求
{
    "capabilities": {
        "tools": {},
        "resources": {"subscribe": true},
        "prompts": {}
    }
}

# Server 初始化响应
{
    "capabilities": {
        "tools": {"listChanged": true},
        "resources": {"subscribe": true},
        "prompts": {}
    }
}
```

## 常见误区

```
误区 1：Host 和 Client 是同一个东西
  Host 是运行环境（如 VS Code），Client 是通信模块。
  一个 Host 可以管理多个 Client，每个 Client 连接一个 Server。

误区 2：Server 只能提供 Tool
  MCP Server 可以同时提供三种原语：Tool（操作）、Resource（数据）、Prompt（模板）。
  根据场景选择合适的原语，不要把所有东西都塞进 Tool。

误区 3：消息流是单向的
  MCP 的消息流是双向的。Server 可以主动发送通知给 Client，
  比如资源变更通知、进度更新等，不只是被动响应请求。

误区 4：能力协商只在初始化时发生一次
  虽然主要协商在初始化时完成，但能力可以动态更新。
  Server 可以通过 notifications/tools/list_changed 通知 Client 工具列表已变更。
```

## 工程建议

```
1. 画出你的消息流图
   在开发之前，先画出从用户输入到工具结果返回的完整消息流。
   这能帮你明确哪些逻辑放在 Host、哪些放在 Client、哪些放在 Server。

2. Host 层做权限控制
   Host 负责管理 Client 生命周期和用户交互，是实施权限控制的最佳位置。
   不要把权限逻辑下沉到 Server，那样每个 Server 都要重复实现。

3. Client 层做错误转换
   Client 应该把 Server 返回的协议级错误转换为对 Host 友好的格式。
   Host 不应该知道 JSON-RPC 错误码的细节。

4. Server 层保持无状态（尽量）
   Server 应该尽量无状态，状态由 Host 或外部系统管理。
   这样 Server 才能水平扩展，支持多实例部署。
```
