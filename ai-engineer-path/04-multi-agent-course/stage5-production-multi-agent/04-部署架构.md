# 04 部署架构——容器化部署、服务发现、负载均衡

> 多 Agent 系统的部署比单服务更复杂。容器化是标准方案。

## 场景引入

你在本地开发环境运行多 Agent 系统一切正常，但部署到服务器后，Agent 之间的通信出了问题：服务发现失败、负载不均衡、容器频繁重启。多 Agent 系统的部署不是"打个 Docker 镜像"那么简单——你需要考虑容器编排、服务注册和网络策略。

## 一、容器化部署

```yaml
# docker-compose.yml
version: '3.8'

services:
  supervisor:
    build: ./supervisor
    ports:
      - "8000:8000"
    depends_on:
      - researcher
      - analyst
      - writer
  
  researcher:
    build: ./agents/researcher
    environment:
      - OPENAI_API_KEY=${OPENAI_API_KEY}
  
  analyst:
    build: ./agents/analyst
    environment:
      - OPENAI_API_KEY=${OPENAI_API_KEY}
  
  writer:
    build: ./agents/writer
    environment:
      - OPENAI_API_KEY=${OPENAI_API_KEY}
  
  redis:
    image: redis:7
    ports:
      - "6379:6379"
```

## 二、服务发现

```python
class ServiceRegistry:
    """服务注册中心"""
    
    def __init__(self):
        self.services = {}
    
    def register(self, name: str, address: str, port: int):
        """注册服务"""
        self.services[name] = {
            "address": address,
            "port": port,
            "status": "healthy",
            "last_heartbeat": datetime.now()
        }
    
    def discover(self, name: str) -> dict:
        """发现服务"""
        return self.services.get(name)
    
    def health_check(self):
        """健康检查"""
        for name, service in self.services.items():
            if datetime.now() - service["last_heartbeat"] > timedelta(seconds=30):
                service["status"] = "unhealthy"
```

## 三、负载均衡

```python
class LoadBalancer:
    """负载均衡器"""
    
    def __init__(self, services: list):
        self.services = services
        self.current = 0
    
    def get_next(self) -> dict:
        """获取下一个服务（轮询）"""
        service = self.services[self.current]
        self.current = (self.current + 1) % len(self.services)
        return service
    
    def get_healthy(self) -> list:
        """获取健康的服务"""
        return [s for s in self.services if s["status"] == "healthy"]
```

## 四、Kubernetes 部署

```yaml
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: multi-agent-system
spec:
  replicas: 3
  selector:
    matchLabels:
      app: multi-agent
  template:
    metadata:
      labels:
        app: multi-agent
    spec:
      containers:
        - name: supervisor
          image: multi-agent/supervisor:latest
          ports:
            - containerPort: 8000
          env:
            - name: OPENAI_API_KEY
              valueFrom:
                secretKeyRef:
                  name: api-keys
                  key: openai
```

## 常见误区

1. **容器间网络配置不当**：Agent 容器之间无法互相访问，原因是 Docker 网络配置错误。多 Agent 系统的容器需要在同一个 Docker 网络中，才能通过服务名互相访问。
2. **没有健康检查和自动重启**：某个 Agent 容器挂了，但编排器不知道，继续向它发送请求。需要为每个容器配置健康检查，让编排器能及时发现故障容器并重启。
3. **环境变量管理混乱**：API Key、数据库密码等敏感信息直接写在 docker-compose.yml 中。应该使用 Docker Secrets 或 Kubernetes Secret 来管理敏感配置。

## 工程建议

1. **从单 Agent 开始，按需演进**：先用单 Agent 验证核心逻辑，当遇到上下文瓶颈、能力稀释或需要并行处理时，再拆分为多 Agent。不要为了"看起来高级"而引入多 Agent 架构。
2. **为每个 Agent 定义清晰的职责边界**：每个 Agent 应该有单一、明确的职责（如"只负责搜索""只负责分析"），输入输出格式在设计阶段就确定下来，避免职责重叠和数据格式混乱。
3. **建立可观测性基础设施**：从第一版开始就为每个 Agent 添加结构化日志和追踪机制，记录输入、输出、耗时、错误。多 Agent 系统的调试难度远高于单 Agent，没有日志就是在"盲人摸象"。
4. **在关键决策节点加入人工审批**：涉及高风险操作（删除数据、发送消息、支付）和不可逆操作时，使用 Human-in-the-loop 机制暂停执行，等待人类确认后再继续。
