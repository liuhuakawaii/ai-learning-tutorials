# 01 为什么微调——Prompt Engineering vs RAG vs Fine-tuning 的选型

> 不是所有问题都需要微调。选对方法比选对模型更重要。

## 场景引入

你的老板说："这个通用大模型回答我们公司的产品问题总是胡说八道，微调一下就好了。"你花了一周准备数据、租了 GPU、跑完微调，结果发现效果还不如在 Prompt 里加几句产品说明。问题出在哪？不是微调本身有问题，而是你选错了方法。Prompt Engineering、RAG、Fine-tuning 各有适用场景，选错方法就是白费力气。

---

## 学习目标

- 理解 Prompt Engineering、RAG、Fine-tuning 的区别
- 掌握三种方法的适用场景
- 学会根据需求选择合适的方法

## 一、三种方法对比

```
┌─────────────────────────────────────────────────────────────┐
│           Prompt Engineering vs RAG vs Fine-tuning          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Prompt Engineering                                         │
│  ├── 原理：通过提示词引导模型行为                            │
│  ├── 成本：低（无需训练）                                    │
│  ├── 效果：有限（受限于模型能力）                            │
│  └── 适用：简单任务、快速迭代                                │
│                                                             │
│  RAG（检索增强生成）                                         │
│  ├── 原理：检索外部知识辅助生成                              │
│  ├── 成本：中（需要构建知识库）                              │
│  ├── 效果：好（可以访问最新信息）                            │
│  └── 适用：知识密集型任务                                    │
│                                                             │
│  Fine-tuning（微调）                                        │
│  ├── 原理：用领域数据训练模型                                │
│  ├── 成本：高（需要数据和计算资源）                          │
│  ├── 效果：好（可以改变模型行为）                            │
│  └── 适用：特定领域、特定风格                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 二、选型决策树

```
选型决策树：

你的需求是什么？
├── 简单任务优化 → Prompt Engineering
│   ├── 调整输出格式
│   ├── 改变回答风格
│   └── 添加约束条件
│
├── 访问外部知识 → RAG
│   ├── 最新信息
│   ├── 私有数据
│   └── 专业知识
│
└── 改变模型行为 → Fine-tuning
    ├── 特定领域
    ├── 特定风格
    └── 特定任务
```

## 三、适用场景

```
适用场景：

Prompt Engineering：
- 快速原型开发
- 简单任务调整
- 成本敏感场景

RAG：
- 知识问答系统
- 文档检索
- 实时信息查询

Fine-tuning：
- 特定领域（医疗、法律、金融）
- 特定风格（正式、口语、专业）
- 特定任务（代码生成、文本分类）
```

---

## 四、组合使用

```
组合使用：

1. Prompt + RAG
   - 用 Prompt 引导 RAG 行为
   - 优化检索结果的使用

2. RAG + Fine-tuning
   - 微调模型更好地使用检索结果
   - 提高 RAG 的效果

3. Prompt + Fine-tuning
   - 微调后用 Prompt 进一步优化
   - 适应不同场景
```

## 五、决策矩阵

```
决策矩阵：

| 因素 | Prompt | RAG | Fine-tuning |
|------|--------|-----|-------------|
| 开发成本 | 低 | 中 | 高 |
| 维护成本 | 低 | 中 | 高 |
| 效果提升 | 有限 | 好 | 很好 |
| 灵活性 | 高 | 中 | 低 |
| 适用范围 | 广 | 中 | 窄 |
```

## 常见误区

1. **遇到效果不好就想微调**：很多时候 Prompt Engineering 或 RAG 就能解决问题，微调是成本最高的方案。先试 Prompt 优化，再试 RAG，最后才考虑微调。

2. **认为微调能让模型"学会新知识"**：微调主要是调整模型的行为方式和输出风格，而不是注入新知识。需要模型掌握最新信息，应该用 RAG 而不是微调。

3. **忽略组合使用的效果**：Prompt、RAG、Fine-tuning 不是互斥的。微调后的模型配合精心设计的 Prompt 和 RAG 检索，效果通常远超单独使用任何一种方法。

4. **只考虑效果不考虑维护成本**：微调模型需要持续维护——数据更新、模型重训、版本管理。如果团队没有持续投入的能力，RAG 可能是更可持续的方案。

---

## 工程建议

1. **用决策树做选型**：面对需求时，按"简单调整？→ Prompt；需要外部知识？→ RAG；需要改变模型行为？→ 微调"的顺序逐级判断，避免过早进入微调。

2. **先做 MVP 验证**：在投入大量资源做微调前，先用 Prompt + 小规模 RAG 做一个 MVP，验证需求是否真的需要微调级别的效果提升。

3. **量化微调 ROI**：微调的收益要能衡量——准确率提升多少、用户满意度提升多少、节省了多少人工审核成本。没有明确 ROI 的微调项目不值得启动。

4. **建立方法切换的评估标准**：定义清晰的指标（如准确率 > 85%），当某种方法达到标准就停止升级，避免过度工程化。
