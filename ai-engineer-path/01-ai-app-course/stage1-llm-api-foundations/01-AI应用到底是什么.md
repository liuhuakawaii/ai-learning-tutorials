## 一、AI 应用不是"套个 ChatGPT"

### 1.1 一个常见的误解

很多人以为 AI 应用就是：

```
用户输入 → 发给 ChatGPT → 显示回答
```

如果真是这样，那所有人都能做，根本不需要学。

### 1.2 真正的 AI 应用长什么样

来看一个真实的场景：你正在用一个 AI 知识工作台，上传了 3 份产品文档，然后问："我们的登录流程有哪些安全要求？"

```
┌─────────────────────────────────────────────────────────────────┐
│                        AI 知识工作台                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  用户提问："我们的登录流程有哪些安全要求？"                        │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │                    系统内部发生了什么？                    │   │
│  ├─────────────────────────────────────────────────────────┤   │
│  │                                                         │   │
│  │  1. 理解意图                                            │   │
│  │     用户在问安全要求，不是在问登录流程本身                 │   │
│  │                                                         │   │
│  │  2. 检索知识库                                          │   │
│  │     从 3 份文档中找到 5 个相关片段                        │   │
│  │                                                         │   │
│  │  3. 组装上下文                                          │   │
│  │     把检索到的片段 + 用户问题 + 系统指令拼成 Prompt       │   │
│  │                                                         │   │
│  │  4. 调用模型                                            │   │
│  │     发送给 GPT-4，等待生成回答                           │   │
│  │                                                         │   │
│  │  5. 后处理                                              │   │
│  │     添加引用来源、检查是否包含敏感信息、记录日志          │   │
│  │                                                         │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  回答："根据《安全规范 v2.1》第 3.2 节，登录流程要求：           │
│   1. 密码必须 8 位以上，包含大小写和特殊字符 [1]                 │
│   2. 连续 5 次失败后锁定账号 30 分钟 [1]                        │
│   3. 敏感操作需二次验证 [2]                                     │
│                                                                 │
│   [1] 安全规范 v2.1 - 3.2 认证要求                              │
│   [2] 安全规范 v2.1 - 4.1 操作权限"                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

这个过程中，"调用模型"只是第 4 步。前面有意图理解、知识检索，后面有后处理和引用。**这才是 AI 应用。**

## 二、AI 应用的五个核心组成

### 2.1 全景图

```
┌─────────────────────────────────────────────────────────────────┐
│                       AI 应用的五个组成                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────┐                                                  │
│  │  1. Prompt │  ← 系统指令 + 用户输入 + 上下文                 │
│  │  （指令）  │     告诉模型"你是谁、做什么、怎么做"             │
│  └─────┬────┘                                                  │
│        │                                                       │
│        ▼                                                       │
│  ┌──────────┐                                                  │
│  │ 2. 上下文 │  ← 检索到的知识、历史对话、用户信息              │
│  │ （背景）  │     模型回答问题所需的所有信息                    │
│  └─────┬────┘                                                  │
│        │                                                       │
│        ▼                                                       │
│  ┌──────────┐                                                  │
│  │  3. 模型  │  ← GPT-4、Claude、Gemini 等                     │
│  │ （大脑）  │     理解上下文，生成回答                          │
│  └─────┬────┘                                                  │
│        │                                                       │
│        ▼                                                       │
│  ┌──────────┐                                                  │
│  │  4. 工具  │  ← 搜索、数据库、文件操作、API 调用              │
│  │ （手脚）  │     模型自己做不到的事情，通过工具来完成          │
│  └─────┬────┘                                                  │
│        │                                                       │
│        ▼                                                       │
│  ┌──────────┐                                                  │
│  │  5. 状态  │  ← 会话历史、任务进度、用户偏好                  │
│  │ （记忆）  │     让应用记住之前发生了什么                      │
│  └──────────┘                                                  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 用前端开发来类比

| AI 应用概念 | 前端类比 | 说明 |
|---|---|---|
| Prompt | 组件的 props + 模板 | 定义"渲染"什么、怎么"渲染" |
| 上下文 | 全局状态（Redux/Zustand） | 组件能访问的所有数据 |
| 模型 | 渲染引擎（React） | 接收数据，输出结果 |
| 工具 | API 调用、副作用 | 与外部世界交互 |
| 状态 | localStorage / 会话 | 跨请求保持信息 |

### 2.3 一个具体例子

假设你要做一个"AI 竞品分析助手"：

```
用户输入："帮我对比 Notion 和 Obsidian 的优缺点"

Prompt（指令）：
  "你是一个产品分析师。用户会给你两个产品名称，
   你需要从功能、价格、用户体验三个维度进行对比。
   输出格式为 Markdown 表格。"

上下文（背景）：
  - 用户之前上传的竞品调研报告
  - 之前对话中提到的"我们团队 5 人，预算有限"
  - 检索到的 Notion 和 Obsidian 的最新功能列表

模型（大脑）：
  - 理解"对比"的含义
  - 从上下文中提取关键信息
  - 生成结构化的对比表格

工具（手脚）：
  - 搜索最新价格信息
  - 查询数据库中的历史对比记录
  - 保存分析结果到文件

状态（记忆）：
  - 用户偏好"简洁风格"
  - 之前已经对比过 3 个工具
  - 当前会话的分析主题
```

## 三、为什么不能只靠 Prompt

### 3.1 Prompt 的局限

很多人花大量时间调 Prompt，但忽略了一个事实：

```
┌─────────────────────────────────────────────────────────────┐
│                    Prompt 能做什么 / 不能做什么               │
├──────────────────────┬──────────────────────────────────────┤
│  ✅ Prompt 能做的     │  ❌ Prompt 做不到的                   │
├──────────────────────┼──────────────────────────────────────┤
│  定义角色和风格       │  让模型知道你公司的内部文档            │
│  指定输出格式         │  让模型访问实时数据                    │
│  设置回答边界         │  让模型执行文件操作                    │
│  提供示例             │  让模型记住上次对话                    │
│  引导推理过程         │  让模型验证自己的回答是否正确           │
└──────────────────────┴──────────────────────────────────────┘
```

### 3.2 一个真实的失败案例

```
场景：用户问 AI 助手"我上周提交的 bug 修复了吗？"

只靠 Prompt 的回答：
  "抱歉，我无法访问你的 bug 跟踪系统，不知道你上周提交了什么。"

AI 应用的回答：
  1. 调用工具查询 Jira API
  2. 找到用户上周提交的 3 个 bug
  3. 检查它们的状态
  4. 回答："你上周提交的 3 个 bug 中，2 个已修复（#1234, #1237），
     1 个还在处理中（#1236，预计明天完成）。"
```

**差距一目了然。**

### 3.3 "AI 应用 = 产品系统"的思维方式

```
传统 Web 应用：
  用户 → 前端 → API → 数据库 → 返回结果
         │
         └─ 你需要设计：路由、状态管理、错误处理、权限、缓存...

AI 应用：
  用户 → 前端 → Prompt 组装 → 模型调用 → 后处理 → 返回结果
                │                              │
                ├─ 检索知识库                    ├─ 引用标注
                ├─ 注入用户上下文                ├─ 安全过滤
                └─ 历史对话                      ├─ 日志记录
                                                 └─ 成本统计

  你需要设计的比传统应用更多，不是更少。
```

## 四、AI 应用 vs 传统应用

### 4.1 核心差异

```
┌─────────────────────────────────────────────────────────────────┐
│                AI 应用 vs 传统应用                               │
├─────────────────┬──────────────────┬────────────────────────────┤
│     维度         │    传统应用       │       AI 应用              │
├─────────────────┼──────────────────┼────────────────────────────┤
│ 输出确定性      │ 确定的            │ 概率性的                    │
│ 同样的输入       │ 永远同样的输出    │ 可能不同的输出              │
│ 错误模式        │ 代码 bug          │ 幻觉、偏见、格式错误        │
│ 测试方式        │ 单元测试、E2E     │ 评估集、人工抽检            │
│ 性能瓶颈        │ 数据库、网络      │ 模型推理速度、token 限制    │
│ 成本模型        │ 服务器固定成本    │ 按 token 计费，用多少花多少 │
│ 用户预期        │ 精确、快速        │ 有用、准确、能自我修正      │
└─────────────────┴──────────────────┴────────────────────────────┘
```

### 4.2 "概率性输出"意味着什么

```
传统应用：
  输入：2 + 2
  输出：永远是 4

AI 应用：
  输入："总结这篇文章的要点"
  输出（第一次）："文章讨论了三个要点：..."
  输出（第二次）："本文主要探讨了..."
  输出（第三次）："作者提出了以下观点：..."

  三次输出都对，但措辞不同。
  偶尔也会出错——这就是"概率性"。
```

**这意味着：**
- 你不能用 `expect(output).toBe(expected)` 来测试 AI 输出
- 你需要评估"回答质量"，而不是"回答是否完全一致"
- 你需要设计容错机制，而不是假设永远正确

## 五、AI 应用的典型架构

### 5.1 一个完整的请求生命周期

```
用户输入
  │
  ▼
┌──────────────────┐
│  1. 输入处理       │  解析用户意图、检测敏感内容
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  2. 上下文组装     │  检索知识库 + 历史对话 + 用户信息
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  3. Prompt 构建    │  系统指令 + 上下文 + 用户输入
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  4. 模型调用       │  发送给 LLM API（可能是流式的）
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  5. 工具调用       │  如果模型请求调用工具，执行并返回结果
│    （可能多轮）    │  → 回到第 3 步继续
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  6. 后处理         │  添加引用、安全检查、格式化
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  7. 响应返回       │  流式推送给前端 / 一次性返回
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  8. 日志与统计     │  记录 token、耗时、错误、用户反馈
└──────────────────┘
```

### 5.2 用 Next.js 实现的简化版

```typescript
// app/api/chat/route.ts
import { openai } from '@/lib/openai'
import { searchKnowledge } from '@/lib/knowledge'
import { logRequest } from '@/lib/logger'

export async function POST(req: Request) {
  const { message, conversationId } = await req.json()

  // 1. 检索知识库
  const context = await searchKnowledge(message)

  // 2. 获取历史对话
  const history = await getHistory(conversationId)

  // 3. 构建 Prompt
  const systemPrompt = buildSystemPrompt(context)

  // 4. 调用模型
  const response = await openai.responses.create({
    model: 'gpt-5.5',
    input: [
      { role: 'system', content: systemPrompt },
      ...history,
      { role: 'user', content: message }
    ]
  })

  // 5. 后处理
  const answer = addCitations(response.output_text, context)

  // 6. 记录日志
  await logRequest({ conversationId, tokens: response.usage })

  // 7. 返回
  return Response.json({ answer })
}
```

这段代码虽然简单，但已经包含了 AI 应用的核心骨架。

## 小结

本课的核心要点：

1. **AI 应用 ≠ 套个 API**：真正的 AI 应用有五个核心组成——Prompt、上下文、模型、工具、状态
2. **Prompt 只是起点**：知识检索、工具调用、后处理、日志记录才是产品化的关键
3. **概率性输出**：AI 输出是不确定的，需要用评估而非断言来测试
4. **AI 应用是产品系统**：你需要设计的比传统应用更多——输入处理、上下文组装、后处理、安全过滤、成本控制
5. **这门课的目标**：从"会调 API"到"能做产品"
