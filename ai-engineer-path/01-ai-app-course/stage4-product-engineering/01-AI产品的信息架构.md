# 第1课：AI 产品的信息架构

> **课程定位**：设计 AI 产品的整体结构
> **前置知识**：阶段一到三的全部内容
> **预计时长**：35 分钟

## 场景引入

你所在的团队正在开发一款 AI 知识工作台产品，产品经理丢过来一句"做一个像 ChatGPT 那样的页面"。你打开编辑器准备写代码，却发现第一个问题就卡住了：对话列表放哪里？知识库管理怎么做？用户设置怎么组织？传统 Web 应用的信息架构经验在这里似乎不够用了——AI 产品有"对话"这个全新的核心实体，有"模型选择""System Prompt""知识库关联"等传统产品不存在的维度，还有"token 用量""配额限制"这种跨层的数据需求。如果一开始不把这些模块的关系理清楚，后面改架构的代价会非常大。

## 三、数据模型设计

### 3.1 用户相关

```typescript
// 用户表
interface User {
  id: string
  email: string
  name: string
  avatar?: string
  plan: 'free' | 'pro' | 'enterprise'
  tokenLimit: number        // 每月 token 配额
  tokenUsed: number         // 已使用 token
  createdAt: Date
  updatedAt: Date
}
```

### 3.2 对话相关

```typescript
// 对话表
interface Conversation {
  id: string
  userId: string
  title: string
  model: string             // 使用的模型
  systemPrompt?: string
  knowledgeBaseId?: string  // 关联的知识库
  isArchived: boolean
  createdAt: Date
  updatedAt: Date
}

// 消息表
interface Message {
  id: string
  conversationId: string
  role: 'user' | 'assistant' | 'system' | 'tool'
  content: string
  toolCalls?: any[]
  toolCallId?: string
  tokenUsage?: {
    prompt: number
    completion: number
  }
  createdAt: Date
}
```

### 3.3 知识库相关

```typescript
// 知识库表
interface KnowledgeBase {
  id: string
  userId: string
  name: string
  description?: string
  documentCount: number
  chunkCount: number
  status: 'ready' | 'indexing' | 'error'
  createdAt: Date
  updatedAt: Date
}

// 文档表
interface Document {
  id: string
  knowledgeBaseId: string
  filename: string
  type: 'pdf' | 'markdown' | 'txt' | 'web'
  size: number
  chunkCount: number
  status: 'indexing' | 'ready' | 'error'
  createdAt: Date
}
```

### 3.4 使用统计

```typescript
// 使用记录表
interface UsageRecord {
  id: string

  completionTokens: number
  totalTokens: number
  cost: number              // 费用（美元）
  duration: number          // 耗时（毫秒）

}
```

## 四、API 设计

### 4.1 核心 API

```
对话相关：
  POST   /api/conversations          创建对话
  GET    /api/conversations          获取对话列表
  GET    /api/conversations/:id      获取对话详情
  PATCH  /api/conversations/:id      更新对话
  DELETE /api/conversations/:id      删除对话

消息相关：
  POST   /api/conversations/:id/messages     发送消息（流式）
  GET    /api/conversations/:id/messages     获取消息历史

知识库相关：
  POST   /api/knowledge-bases        创建知识库
  GET    /api/knowledge-bases        获取知识库列表
  DELETE /api/knowledge-bases/:id    删除知识库

文档相关：
  POST   /api/knowledge-bases/:id/documents    上传文档
  DELETE /api/documents/:id                     删除文档

使用统计：
  GET    /api/usage                  获取使用统计
```

## 常见误区

1. **把 AI 产品当传统 CRUD 做**：只设计了用户表和文章表，忽略了"对话""消息""知识库"这些 AI 特有的核心实体，导致后期不得不大规模重构数据模型。
2. **页面结构按功能堆砌**：把所有功能平铺在导航栏里，没有区分"高频核心功能"（对话）和"低频管理功能"（设置、统计），用户进入产品后不知道该点哪里。
3. **数据模型只考虑读不考虑写**：对话和消息是一对多关系，但没有在 Conversation 上维护 messageCount、tokenUsage 等冗余统计字段，导致列表页每次都要聚合查询，性能随数据量线性下降。
4. **API 设计忽略流式需求**：AI 产品的对话接口必须支持 SSE 或 WebSocket 流式响应，如果一开始设计成普通 REST 请求-响应模式，前端打字机效果的实现会非常别扭。

---

## 工程建议

1. **先画实体关系图再写代码**：在动手之前，用 Mermaid 或 draw.io 把 User、Conversation、Message、KnowledgeBase、Document、Chunk、UsageRecord 之间的关系画清楚，确认主键、外键和索引字段。
2. **冗余统计字段是必要的**：在 Conversation 上维护 messageCount 和 tokenUsage，在 KnowledgeBase 上维护 documentCount 和 chunkCount。这些字段可以通过触发器或应用层逻辑同步，换来的是列表查询的高性能。
3. **API 路由按资源分组**：对话相关放 `/api/conversations`，知识库相关放 `/api/knowledge-bases`，使用统计放 `/api/usage`。每个资源遵循 RESTful 的 CRUD 模式，对话消息用 `/api/conversations/:id/messages` 子路由。
4. **从第一天就设计流式接口**：对话 API 返回 `text/event-stream`，前端用 `EventSource` 或 `fetch` + `ReadableStream` 消费。不要先做普通请求再改成流式——两套前端逻辑的维护成本很高。

## 小结

本课的核心要点：

1. **AI 产品有特殊性**：输出不确定、成本按量计费、需要评估体系
2. **信息架构**：用户层、功能层、AI 层、数据层
3. **页面结构**：对话、知识库、历史、统计、设置
4. **数据模型**：用户、对话、消息、知识库、文档、使用记录
5. **API 设计**：RESTful 风格，支持流式响应
