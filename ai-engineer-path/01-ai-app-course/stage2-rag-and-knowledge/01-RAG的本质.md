# 第1课：RAG 的本质——为什么模型需要检索

> **课程定位**：理解 RAG 的核心思想和价值
> **前置知识**：阶段一的大模型 API 基础
> **预计时长**：30 分钟

---

## 场景引入

你刚入职一家公司，领导让你做一个内部知识问答助手。你兴冲冲地接入了 GPT-4，把公司的规章制度文档发给它，结果它回答的内容驴唇不对马嘴——既引用了过时的政策，又编造了根本不存在的条款。你去查原因，发现模型的训练数据根本不包含你们公司的私有文档，而且它的知识截止在去年。这时候你需要的不是更大的模型，而是让模型在回答之前先"查资料"——这就是 RAG 要解决的问题。

## 一、大模型的知识问题

### 1.1 知识截止

```
大模型的知识来自训练数据，训练数据有一个截止日期：

  GPT-4o：训练数据截止到 2024 年初
  Claude：训练数据截止到 2024 年初

  你问："2025 年发生了什么？"
  模型："抱歉，我没有 2025 年的信息。"

  你问："我们公司的内部文档里写了什么？"
  模型："我没有访问你们公司文档的权限。"
```

## 二、什么是 RAG

### 2.1 一句话定义

```
RAG = Retrieval-Augmented Generation
    = 检索增强生成

核心思想：
  在让模型回答问题之前，先检索相关的资料，
  把检索到的资料作为上下文传给模型，
  让模型基于这些资料来回答。

  不是让模型"凭记忆回答"，而是让模型"看着资料回答"。
```

### 2.2 用考试来类比

```
┌─────────────────────────────────────────────────────────────────┐
│                    两种考试方式                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  方式 A：闭卷考试（普通大模型）                                   │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  考生（模型）凭记忆答题                                   │   │
│  │  - 记得的答得好                                          │   │
│  │  - 不记得的就编（幻觉）                                   │   │
│  │  - 无法回答训练后的新知识                                 │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│  方式 B：开卷考试（RAG）                                        │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │  考生（模型）可以翻阅资料                                 │   │
│  │  - 先找到相关资料（检索）                                 │   │
│  │  - 基于资料回答（生成）                                   │   │
│  │  - 可以引用出处                                          │   │
│  │  - 不知道就说"资料里没提到"                               │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 RAG 的流程

```
用户提问
  │
  ▼
┌──────────────────┐
│  1. 检索（Retrieval）│  从知识库中找到与问题相关的文档片段
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  2. 增强（Augmented）│  把检索到的片段作为上下文，注入到 Prompt 中
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│  3. 生成（Generation）│  模型基于上下文生成回答
└────────┬─────────┘
         │
         ▼
  回答 + 引用来源
```

## 三、RAG vs 微调

### 3.1 两种方案的对比

```
┌─────────────────────────────────────────────────────────────────┐
│                    RAG vs 微调                                    │
├───────────────┬──────────────────────┬──────────────────────────┤
│  维度          │  RAG                 │  微调                     │
├───────────────┼──────────────────────┼──────────────────────────┤
│  原理          │  检索外部知识         │  用新数据训练模型          │
│  知识更新      │  更新文档即可         │  需要重新训练              │
│  成本          │  低（只需检索）       │  高（需要 GPU 和数据）     │
│  时效性        │  实时                 │  有延迟                   │
│  可解释性      │  高（可引用来源）     │  低（黑盒）               │
│  适用场景      │  知识问答、文档助手    │  风格迁移、特定任务优化    │
│  幻觉控制      │  好（基于资料回答）   │  一般                     │
└───────────────┴──────────────────────┴──────────────────────────┘
```

### 3.2 什么时候用 RAG

```
用 RAG 当：
  ✅ 你需要回答基于特定文档的问题
  ✅ 知识需要频繁更新
  ✅ 需要引用来源
  ✅ 需要控制成本
  ✅ 需要实时性

用微调当：
  ✅ 你需要改变模型的"风格"或"语气"
  ✅ 你需要模型在特定任务上表现更好
  ✅ 你有大量高质量的训练数据
  ✅ 你有足够的 GPU 资源

很多时候，RAG + 微调可以结合使用。
```

## 五、RAG 的完整链路

```
┌─────────────────────────────────────────────────────────────────┐
│                    RAG 的完整链路                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  索引阶段（离线，一次性）：                                       │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐  │
│  │ 文档上传  │───→│ 文本切分  │───→│ 向量化   │───→│ 存储索引  │  │
│  │ PDF/MD   │    │ chunking │    │embedding │    │ vector DB│  │
│  └──────────┘    └──────────┘    └──────────┘    └──────────┘  │
│                                                                 │
│  查询阶段（在线，每次请求）：                                     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐  │
│  │ 用户提问  │───→│ 问题向量化│───→│ 相似度检索│───→│ 组装Prompt│  │
│  │          │    │          │    │          │    │          │  │
│  └──────────┘    └──────────┘    └──────────┘    └────┬─────┘  │
│                                                       │        │
│                                                       ▼        │
│  ┌──────────┐    ┌──────────┐                      ┌────────┐  │
│  │ 返回回答  │←───│ 模型生成  │←─────────────────────│ 模型   │  │
│  │ + 引用   │    │          │                      │        │  │
│  └──────────┘    └──────────┘                      └────────┘  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.1 索引阶段详解

```
1. 文档上传
   用户上传 PDF、Markdown、TXT 等文件

2. 文本切分（Chunking）
   把长文档切成小段（chunk），每段 200-1000 个字符
   为什么？太长的内容无法精确检索

3. 向量化（Embedding）
   把每个 chunk 转换成一个向量（一组数字）
   语义相似的内容，向量也相似

4. 存储索引
   把向量存入向量数据库（如 Pinecone、pgvector）
   支持快速的相似度搜索
```

### 5.2 查询阶段详解

```
1. 用户提问
   "我们的退款政策是什么？"

2. 问题向量化
   把问题转换成向量

3. 相似度检索
   在向量数据库中找到与问题最相似的 chunk
   返回 top 3-5 个相关片段

4. 组装 Prompt
   System: "基于以下资料回答问题，如果资料中没有相关信息，
           请说'抱歉，资料中没有找到相关信息'。"
   Context: [检索到的 chunk 1, chunk 2, chunk 3]
   User: "我们的退款政策是什么？"

5. 模型生成
   模型基于资料生成回答

6. 返回回答 + 引用
   "根据《退款政策》第 3 条... [来源: 退款政策.pdf, 第 3 页]"
```

## 常见误区

1. **认为 RAG 能解决一切幻觉问题**：RAG 只是把"凭空编造"变成了"基于资料编造"。如果检索到的资料本身有误，或者模型在整合信息时产生误解，幻觉仍然会发生。RAG 降低幻觉概率，但不能消除。

2. **把 RAG 当成万能知识方案**：RAG 适合回答"资料里写了什么"这类事实性问题，但不适合创意写作、代码生成、风格迁移等任务。这些场景可能微调或纯模型生成更合适。

3. **忽略检索质量直接调模型**：很多开发者花大量时间调 prompt 和模型参数，却不去检查检索到的 chunk 是否真的相关。RAG 的瓶颈往往在检索环节，不在生成环节。

4. **认为向量数据库越大越好**：盲目把所有文档都塞进向量库，不做去重、不做质量筛选，反而会引入噪声，降低检索精度。

---

## 工程建议

1. **先跑通再优化**：第一版 RAG 系统用最简单的方案（固定大小切分 + 向量检索 + topK=3），先验证整个链路能跑通，再逐步优化切分策略、检索方式和 prompt 设计。

2. **建立评测集**：准备 20-50 条问答对（问题 + 期望答案 + 来源文档），作为回归测试基准。每次调整策略后跑一遍评测集，用数据说话而不是凭感觉判断效果。

3. **监控检索命中率**：在日志中记录每次查询的 topK 结果和相似度分数，定期分析"检索到了但不相关"和"相关但没检索到"的比例，这是优化检索策略的最重要依据。

4. **成本意识**：Embedding 成本很低，但生成回答的成本不低。对于高频问题可以缓存检索结果，对于明显无关的查询（如闲聊）可以提前拒答，避免浪费 API 调用。

---

## 小结

本课的核心要点：

1. **RAG = 检索增强生成**：先检索相关资料，再让模型基于资料回答
2. **解决两个问题**：知识过时和知识缺失
3. **比微调更轻量**：更新文档即可，不需要重新训练
4. **核心价值**：降低幻觉、支持引用、知识实时更新
5. **完整链路**：文档 → 切分 → 向量化 → 检索 → 生成 → 引用
